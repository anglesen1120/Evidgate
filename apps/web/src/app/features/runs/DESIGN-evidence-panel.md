# Run detail: Evidence panel and Decision view

Design specification for **09.3.1-T3.1–T3.4 and T5.1–T5.2**. Design only; no implementation, runtime verification, or owner approval is implied.

## 1. Goal, authority and assumptions

Enable a QA engineer or release approver to answer, in order: **Which immutable evidence revision am I viewing? What is missing? What did the live evaluator actually decide, and on which revision?** Never compute a verdict, completeness, or outcome in the browser.

- `apps/web/README.md:560–615`: Angular i18n, vi default/en source, v2 continuity, no horizontal page overflow at 360px.

## 2. Truth boundaries and revision identity

### 2.1 Data-source matrix

| Presentation                                        | Authoritative source                                                             | Rule                                                                                                                                                    |
| --------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Collection state in existing header                 | Existing run response                                                            | Do not relabel collection state as an evaluation.                                                                                                       |
| Header collection completeness before an evaluation | `RunSummary.completeness`, only where actually available                         | Pass through to `EvidenceBadge`; absent field means unavailable, not complete. Never infer completeness from state/attempt counts.                      |
| Selected evaluated revision's completeness/missing  | Decision body when its `evidence_revision` exactly matches the selected revision | Bind that immutable snapshot; never combine one revision's badge with another revision's reasons.                                                       |
| Any other selected revision's completeness/missing  | Matching item from `GET /v1/runs/{run_id}/evidence-revisions`                    | `revision_no`, `created_at`, `completeness`, `missing[]`, nullable `evaluation_id`; list newest first using server order and cursor pagination.         |
| Live decision, outcome, reasons and provenance      | One accepted `GET /v1/runs/{r}/decision` response                                | Every rendered member comes from that response, with explicit response revision. No deriving PASS from complete/all_passed, or FAIL from missing codes. |
| Reason target                                       | Existing producer/attempt identity with a demonstrated relation to the reason    | Codes alone are not identifiers. No guess based on row order, display name, current failing row, or a similar status.                                   |

`missing: null` is **unavailable**, not an empty list. Only an explicit array permits the missing-reason list; only explicit `[]` permits “No missing evidence reasons reported.” A known incomplete revision with unavailable reasons retains its incomplete badge and explanatory unavailable copy. Do not mount the shared list with its default `[]` while data is unresolved.

For `status: pending`, render `pending` and no verdict colour. All evaluation-derived members are null, including `missing`, `reasons`, `mode` and `evidence_revision`; do not show dummy hashes or revision zero. The contract's convenience `url` may still exist while pending; it is not evidence and is not needed in this surface.

For `status: evaluated`, require a supported decision and `mode: live` before filling the live slot. An unknown missing-code literal, unsupported decision, missing required member, or contradictory evaluated body is an unavailable/contract-error presentation, never a successful result. Keep the literal visible as escaped diagnostic text where safe; do not silently discard it or invent a ninth missing code.

### 2.2 Pinning and historical decisions

URL state: `/projects/:projectId/runs/:runId?evidence_revision=<revision_no>#<anchor>`. Preserve unrelated query parameters and the fragment. Use the positive integer server revision number, never list index, evaluation UUID, `ev-3`, or run version as the key. The view identity is `(run_id, evidence_revision)`.

- On first load without an explicit pin, prefer the accepted live decision's `evidence_revision`; if pending, use the newest actual revision from the revision list. Once selected, commit the number to the URL using replacement navigation. Do not later auto-select a different revision when a slower request completes.
- A direct URL pin takes precedence over both responses. Resolve it from the actual list, retaining it in the URL while pages load. No fabricated revision detail request is assumed. Offer “Load older revisions” when more cursor pages exist; do not call a not-yet-loaded revision nonexistent. If not found after the available pages are exhausted, show “Selected revision unavailable” without substituting the newest revision.
- Changing the revision combobox updates the pin and local evidence snapshot, never mutates or overwrites the revision. Browser Back/Forward restores it. No confirmation dialog is needed for a read-only change.
- When a newer server revision is known, show **“A newer revision exists”** above the selected evidence. Keep all selected data. Its one primary contextual action is “View latest revision”; it updates the URL only on activation. No dismiss-and-forget behaviour.
- A newer revision is not necessarily evaluated. Viewing it may show a newer evidence snapshot alongside an older, explicitly identified live decision. This is not a reason to manufacture pending if the decision API returned an evaluated older revision.
- The decision endpoint serves only the latest live evaluation. A list item's `evaluation_id` is a reference, **not** a historical decision response. Therefore the Decision region is always labelled **“Latest live decision”**, with its own “Decision evidence revision” value. If different from the evidence pin, show the mismatch explanation and “View decision evidence” link. Do not relabel its verdict as the selected historical revision's verdict.
- An old revision stays fully viewable for the fields the revision list supplies. Show its `evaluation_id`, or “No live evaluation recorded for this revision.” Historical verdict/reasons/provenance are unavailable from the reference alone. This design neither assumes a historical decision endpoint nor promises historical snapshots of attempts/producer data that the list does not carry.

### 2.3 Refresh and independent failures

Fetch run and decision alongside each other after the existing route permission gate; fetch revision pages independently. Decision or revision-list failures must not erase a successfully loaded manifest/attempt table. Maintain distinct request status/error/retry state for each region.

An `evaluation.created` refresh signal from the existing polling mechanism triggers a decision re-read and refresh of the newest revision-list page. It does not append locally constructed evaluations. Retain the selected evidence pin; atomically replace the accepted live decision body, not individual fields. Ignore stale responses after run/revision navigation using the store's existing generation pattern (`run-detail.store.ts:95–212`). No new polling transport or interval is specified here.

A shadow row must never populate or replace the live slot. If a refresh explicitly delivers `mode: shadow`, ignore that candidate, preserve any previously accepted live response, and show a neutral “Shadow evaluation ignored” notice. If no accepted live response exists, show “Live decision unavailable,” not a synthetic pending or a shadow verdict. Do not add an operator shadow-report link. Keep existing attempt-level healed/shadow annotations separate from this decision state.

## 4. Layout and hierarchy

Use a quiet evidence workbench, not a new KPI dashboard. The visual emphasis is the explicit separation of **Evidence revision** and **Decision evidence revision**, so provenance cannot be missed.

DOM/reading order: existing h1 and back link → run identity/header completeness → manifest → Evidence → Latest live decision → existing Attempts → existing producer targets. The two new regions may sit side by side visually but never change keyboard/reading order.

```text
Run identity / collection state / collection completeness
Manifest and pinned build context (existing)

Evidence                              Latest live decision
Revision [3 · UTC date/time       v]   Decision: FAIL       Outcome: Has failures
[A newer revision exists]             Decision evidence revision: 4
[View latest revision]                This decision uses revision 4, not viewed revision 3.
Selected evidence revision: 3          [View decision evidence]
Completeness: Evidence incomplete     reasons[] (literal ordered list)
missing_shard  Shard evidence missing  policy_hash / manifest_hash
  shard-3 [View producer shard-3]      evaluator_version / mode: live / evaluation_id
Evaluation reference: <uuid or none>

Attempts (existing; original failure stays visible)
Producer target hosts (existing or minimal identity target)
```

The sample FAIL is illustrative, not computed from the example missing shard. No PASS appears anywhere in the AC1 fixture. A PASS from a different live revision is not hidden in production; it is clearly scoped to that decision's revision.

Render the exact code as `<code>` beside translated explanation; translations never replace the wire literal. Preserve server order and duplicates. **Association limitation:** both specified `missing[]` arrays contain strings, not per-reason shard/attempt metadata. A reason code cannot determine its target. Name and link identities only when the existing run/manifest/attempt data establishes the relation. With several possible targets, render an explicit list of confirmed contextual links, not an arbitrary first match. With none, retain plain explanation and “Target details unavailable.” The AC1 specimen must supply an authoritative missing-shard identity; never hardcode `shard-3` or derive it solely from the reason string. This design requires no new wire field and does not claim all reasons can always link.

### 6.1 Stable anchor ownership

- Producer target DOM id: `producer-<shard>`; attempt target DOM id: `attempt-<execution_key>-<n>`. `n` is the actual server attempt number, never array index, retry count, or screen page. For ordinary URI-safe identifiers examples are `#producer-shard-3` and `#attempt-exec_42-2`.
- Identity is case-sensitive and locale-independent. Never slugify, lowercase, truncate, translate, or derive identity from rendered/format-character-escaped text. Use the same helper at both link and target. For identifiers containing URI-reserved characters, percent-encode the component with `encodeURIComponent` in the DOM id and URI-encode the complete id when constructing the fragment; decode the fragment once when resolving it. For ordinary identifiers this produces exactly the fragments above. This prevents whitespace/`#` from changing navigation and preserves exact identity without CSS-selector interpolation.
- Resolve with an exact DOM-id lookup after parsing the known prefix/suffix, not `querySelector` with untrusted fragments. Never treat a fragment as HTML, external URL, filesystem path, or authorization.
- Attach attempt ids to the existing row/focusable row-header target, with one unique target per `(execution_key, attemptNo)`. Attach producer ids to the existing slot row or a minimal labelled slot-identity block. A manifest-identified absent slot can show “No producer evidence” without inventing a producer record. Do not implement the full T6 producer view in this slice.
- Do not duplicate ids between compact/mobile and desktop markup; use one responsive target. Add `tabindex="-1"` to the destination focus target, not every row to the sequential tab order. Scroll margin accounts for the existing shell's sticky header using existing spacing/layout tokens.
- On initial fragment navigation or link activation: load the run and selected revision; reveal an already-loaded attempt group/page if needed; wait for Angular rendering; scroll and programmatically focus the exact target. Existing attempts pagination must expose a loaded target even when it is not on the active local page. Do not change the evidence pin to satisfy a fragment.
- If the row needs an unfetched server cursor page, retain the fragment and offer the existing Load more action. Resolve after each accepted page; no unbounded automatic page scan, invented seek endpoint, or false “not found” before pages are exhausted. If exhausted or forbidden, announce target unavailable and focus the appropriate region heading.
- Producer/attempt targets from current run reads are explicitly labelled current context when a historical pin is active; they are diagnostic navigation, not proof of a historical producer/attempt snapshot.
- Inbox `09.4.1-T4` and healing `09.5.1-T3` use the run-detail URL plus the same anchor helper/contract. Preserve locale prefix and project/run identity; no alternative `#row-N`, `#test-...`, or translated anchor aliases.

## 7. Decision content, tokens and accessibility

### 7.1 Decision content

Use `h2` Latest live decision. Place `DecisionChip` and `OutcomePill` in separate labelled summary items. Render `reasons[]` in a semantic ordered list, exact literal strings, original order and duplicates, escaped text. It is a different catalogue from `missing[]`; do not translate/reinterpret `expected_count_zero` or reuse the missing-reason mapping. Explicit `reasons: []` gets neutral “No decision reasons reported”; null/pending never does.

Provenance is a semantic definition list with these values, each from the same accepted body: `status`, `evidence_revision`, `policy_hash`, `manifest_hash`, `evaluator_version`, `mode`, `evaluation_id`. Show integer revisions normally, hashes/ids/version in mono with full wrap and bidirectional isolation. `completeness`/`missing` belong to the Evidence summary when its revision matches; otherwise their decision scope remains clear through the decision's own revision label and mismatch explanation. No `exceptions_hash`, `exceptions_as_of`, fabricated policy revision, percentage score, local verdict explanation, or copy-to-clipboard dependency is introduced.

Light and dark resolve entirely through existing theme tokens and the shell's explicit theme choice / OS fallback. No raw colour, alpha overlay, new typeface, spacing token, or alternate pending palette. The documented contrast table in `docs/design/web/tokens.md:273–356` records existing token-pair measurements, not a new verification of this design. Implementation must retain those pairings and verify WCAG 2.2 AA: text ≥4.5:1, large text and required control/focus boundaries ≥3:1; decorative `--eg-border` is not an accessible control boundary.

### 7.3 Semantics, focus and announcements

- Region ids `evidence-panel` and `decision-panel`; headings `evidence-title` and `decision-title`, referenced by `aria-labelledby`. Selector has a persistent visible label and `aria-describedby` for pin/availability guidance; do not use placeholder-only labelling.
- Native select gives standard arrow/typing behaviour; Tab reaches select, pagination, newer-revision action, reason links, then Decision links and existing attempts. No custom tab roles, roving tabindex, or page shortcuts.
- On revision change keep focus on selector. Banner arrival and polling never steal focus or scroll. Button activation that navigates to a revision preserves focus where possible; if its control disappears, move to Evidence heading. Back/Forward restores view without focusing an unrelated row unless a fragment requested it.
- One concise polite `role="status"` announces selected revision/newer revision, refresh result or ignored shadow candidate. Do not make the entire panel or raw reasons a live region. Set `aria-busy` on the region during its read; skeleton geometry is aria-hidden. Repeated identical polls are silent.
- Error messages are programmatically associated with the region/control; preserve request ID but never echo request bodies or sensitive report content. Reuse existing request patterns rather than nested duplicate alerts.
- Full keyboard-only operation; clearly visible focus that is not obscured by sticky shell content; 44×44px coarse-pointer targets, including padded contextual links. Do not reduce contrast through disabled opacity; disabled actions have explanatory text.
- Use `<time datetime="...">` with localized readable date/time plus explicit UTC label; retain full ISO UTC in metadata if needed. Use `<bdi>`/existing identifier-display conventions for server identifiers. Data is interpolated text, never innerHTML or sanitizer bypasses.
- No essential information on hover, colour, animation, truncation tooltip, or icon alone. No automatic focus moves for refresh. No new overlay, so no new Escape trap; if future work introduces one it must supply proper dialog focus containment/restoration and Escape dismissal.
