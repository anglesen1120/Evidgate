# ADR-0007 — Single GitHub App per environment (production + non-production)

## Status

proposed (2026-10-11; custodian [OPEN], DECISIONS §8 O11)

## Date

2026-10-11

## Context

- 02.4.3 §1 goal: **one** Evidgate GitHub App, many installations, one active installation per org. The installation id is stored per org; a short-lived installation token is minted on demand from an RS256 app JWT and cached in memory below expiry, never persisted. This ADR refines the goal to one production App plus one non-production App (§Decision).
- Four consumers need GitHub and none of them stores the installation: 07.6.1-T1 (check runs), 03.4.1-T1 (catalog webhooks + sync), 03.4.2-T1 + 08.6.1-T1 (healing branch/PR), 05.5.2-T3 (re-run trigger). `plans/REVIEW-2026-10-02.md` §5.4 ("GitHub App installation model: one App or several, installation id and token storage and rotation (four tasks use an App; no task stores the installation) — in 02.4/07.6") is the review item this ADR closes.
- 00 §5.4.8: `POST /v1/webhooks/github` is a pre-tenant entry point — it resolves the tenant through an owner-owned `SECURITY DEFINER` function (`evidgate_resolve.installation_by_id` / `github_repo`) that returns only `(org_id, …, status)`; the app role holds `EXECUTE` and nothing else outside RLS. 00 §5.4 rules 6–7 add `unique (org_id, id)` and composite FKs.
- Rulings (plans/features/README.md §3): **T46** — the GitHub App uses a typed `HttpClient` + RS256 app JWT via `Microsoft.IdentityModel.JsonWebTokens`, no Octokit dependency; **T62** — GitHub delivery is a check run first, commit status only as fallback when the App lacks `checks:write`.
- D-A2 (DECISIONS §8.1): secrets reach the process by environment injection through the one secret-provider interface (10.1.1-T2 `ISecretProvider`); each is `secret: true` with a versioned name in `infra/config-matrix.json`, generated per environment, never committed; a managed store replaces it after O3. D-A4 is the precedent for key custody: the ingest-token pepper lives in the secret store, the owner is custodian, versioned `pepper_vN`.
- O3 (cloud provider/region) is deferred (DECISIONS §8 O3), so V1 resolves secrets through the environment-injected provider and the managed store arrives later.
- Open items this ADR must not silently close: OI-02-13 (GitHub App API facts ⚠️), OI-02-14 (App name, distribution, key custodian), OI-03-06 (minimal permission set ⚠️).

## Decision

One Evidgate-owned GitHub App per environment, installed many times — one installation per customer org, one active installation per org (02.4.3 §4). Two Apps exist: the **production App** (owned by the Evidgate GitHub organization, customer-facing, public so any account can install it ✅) and one **non-production App** (private, owned by ONE Evidgate-owned test organization, installable only on that account ✅; dev, staging and CI share that one installation account). Each App has its own private key, client secret, webhook secret and webhook URL; the production key and secrets are never loaded outside production. The same versioned secret names are used in every environment (`github_app_private_key_vN`, `github_app_client_secret_vN`, `github_webhook_secret_vN`), with values generated per environment (D-A2). The installation id is stored per org in `github_installation`; the App private key, App id, client secret and webhook secret live only in the secret store.

### Install binding

The production App and the non-production App are both registered with **Request user authorization (OAuth) during installation** ✅ ([Generating a user access token for a GitHub App → "Generating a user access token when a user installs your app"](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)). GitHub warns that the setup URL's `installation_id` query parameter is spoofable and must not be trusted on its own ✅ ([About the setup URL](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url): "Bad actors can hit this URL with a spoofed `installation_id`. Therefore, you should not rely on the validity of the `installation_id` parameter. Instead, you should generate a user access token for the user who installed the GitHub App and then check that the installation is associated with that user."). ⚠️ What the install-time redirect carries is not documented precisely: the OAuth callback is documented to carry `code` (and `state` when sent), while `installation_id` and `setup_action` are documented on the setup URL redirect — confirm in 02.4.3-T2 which parameters arrive on our callback. Fallback if the callback does not carry `installation_id` and our `state`: use the setup URL redirect (`installation_id` + our `state`) followed by the web application flow with our own `redirect_uri` and `state`, then the ownership check below, before binding. The install callback therefore exchanges the OAuth `code` for a user access token and binds the row only when both hold: (a) the `installation_id` appears in `GET /user/installations` (paginated) for the user who completed OAuth ✅ ([List app installations accessible to the user access token](https://docs.github.com/en/rest/apps/installations#list-app-installations-accessible-to-the-user-access-token): "Lists installations of your GitHub App that the authenticated user has explicit permission (:read, :write, or :admin) to access."); and (b) that user administers the installation account — for a User account, `account.id` equals the `id` from `GET /user` ✅ ([Get the authenticated user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user): "A token without scopes still authenticates as the token's owner"; the response `id` is required, integer); for an Organization account, `GET /user/memberships/orgs/{org}` returns `state: active` and `role: admin` ✅ ([Get an organization membership for the authenticated user](https://docs.github.com/en/rest/orgs/members#get-an-organization-membership-for-the-authenticated-user): "If the authenticated user is an active or pending member of the organization, this endpoint will return the user's membership."; response `state` enum `active`/`pending`, `role` enum `admin`/`member`/`billing_manager`; the endpoint is listed for user access tokens only). Otherwise the callback returns 403 `installation_not_owned`. The user token is used once and discarded, never stored. An `installation_id` taken from the query string alone is never trusted. The App client id is config; the App client secret is a secret (versioned, secret store, rotated with the key). This amends 02.4.3 AC2 and T2.2 — [OPEN] DECISIONS §8 O12 (recommended [INFERENCE]: the ownership check above).

One row per consumer. The App-level **registered** permission set is the **union** of the rows; each row is the **ceiling** for that feature — a feature mints a token with only its own row's permissions and never more. The **Registered at** column records when a row joins the registered set: the V1 rows are registered when the App is first registered; the V2 rows are added by an ADR-0007 amendment plus customer re-consent when 03.4.2 starts.

The healing row's `contents: write` cannot be narrowed by GitHub scope, so its guards are Evidgate-side: refs are created only under an `evidgate/` prefix, the default or a protected branch is never the target, and no merge capability is exposed (T64b / 08.6.1 NoMerge test).

Events consumed: `installation` and `installation_repositories` are received by every App by default and cannot be manually subscribed ✅; `check_run`/`check_suite` are automatic once the App has Checks write ✅. The receiver (03.4.1-T2) acks and ignores any event not in this table. One App-wide webhook secret per App verifies every tenant's deliveries: HMAC-SHA256 over the raw body in `X-Hub-Signature-256` before parsing, constant-time compare, and dedupe by `X-GitHub-Delivery` ✅ ([Validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)). A leaked webhook secret lets an attacker forge events for any installation id — accepted risk, mitigated by rotation per the runbook.

Every write is justified; read is used wherever the endpoint permits it:

- `checks: write` — creating and updating a check run is a write-only endpoint; there is no read-level way to publish one, and T62 makes it the primary delivery surface.
- `statuses: write` — the T62 fallback path only: it fires when the installation did not grant `checks: write`, and it is the only way to publish a commit status.
- `contents: write` — creating the branch, commit and blobs of a healing PR is a write; the catalog sync stays on `contents: read`.
- `pull_requests: write` — opening a PR is a write. The `pull_request` webhook subscription needs only read-level "Pull requests", but the row's ceiling is the write the PR creation needs.
- `actions: write` — re-running a workflow is a write-only endpoint.
- **Residual capability.** The registered write scopes exceed the endpoints each feature uses: `contents: write` also permits `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge`, `POST /repos/{owner}/{repo}/merges`, `DELETE /repos/{owner}/{repo}/git/refs/{ref}`, direct ref updates (`PATCH /repos/{owner}/{repo}/git/refs/{ref}`) and `PUT /repos/{owner}/{repo}/contents/{path}` ✅ ([Repository permissions for "Contents"](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-contents)); `actions: write` also permits `POST /repos/{owner}/{repo}/actions/runs/{run_id}/cancel`, `DELETE /repos/{owner}/{repo}/actions/runs/{run_id}` and `/logs`, and `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` ✅ ([Repository permissions for "Actions"](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-actions)). GitHub scope cannot express "no merge" or "only `evidgate/` refs", so those are Evidgate-side controls: the 03.4.2 path guard, the 08.6.1 NoMerge architecture test (T64b) and the key-custody runbook. A compromised App key or token inherits these capabilities within the installation.

App-level endpoints used with the app JWT need no repository permission: `GET /app/installations`, `GET /app/installations/{installation_id}` and `POST /app/installations/{installation_id}/access_tokens` each state "You must use a JWT to access this endpoint" ✅.

Re-run vs checks re-request: `POST /repos/{owner}/{repo}/actions/runs/{run_id}/rerun` requires `actions: write` ✅ ([workflow-runs → "Actions" repository permissions (write)](https://docs.github.com/en/rest/actions/workflow-runs#re-run-a-workflow--fine-grained-access-tokens)). The checks re-request endpoint `POST /repos/{owner}/{repo}/check-runs/{check_run_id}/rerequest` requires `checks: write` ✅ ([checks/runs → "Checks" repository permissions (write)](https://docs.github.com/en/rest/checks/runs#rerequest-a-check-run--fine-grained-access-tokens)) but only triggers the `check_run` `rerequested` event for a check run owned by the authenticated App ✅ ([403 "if the check run is not rerequestable or doesn't belong to the authenticated GitHub App"](https://docs.github.com/en/rest/checks/runs#rerequest-a-check-run)) — it does **not** re-run the customer's GitHub Actions workflow, so it is **not** an alternative for 05.5.2-T3 ✅ ([checks/runs](https://docs.github.com/en/rest/checks/runs#rerequest-a-check-run)).

### Token-per-feature subset rule

Each consumer mints its own installation token through `IGitHubInstallationTokens.GetAsync(orgId, feature, repositoryIds, ct)` (02.4.3 §5). The feature→permission map is a **static compiled table keyed by the feature enum**; callers cannot pass permissions, and an empty map is a bug that throws. The mint sends only that row's permissions in the `permissions` body of `POST /app/installations/{installation_id}/access_tokens`, and repo-scoped features MUST pass `repository_ids` taken from the stored project/repo binding, never from request input. Both are mandatory because the GitHub defaults are the unsafe ones: omitting `permissions` yields a token with **all** permissions granted to the installation, and omitting `repositories`/`repository_ids` yields a token for **all** repositories of the installation ✅ ([Generating an installation access token — "If `permissions` is not specified…" / "If you don't use `repositories` or `repository_ids`…"](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app); up to 500 repositories). Tokens are never shared across features and are cached per `(org, installation_id, feature, permission set, repo set)`, in memory only, reused until 5 min before `expires_at` (installation tokens expire after 1 h ✅). The cache for an installation is flushed on `installation` `deleted`/`suspend`/`unsuspend`/`new_permissions_accepted` and on `installation_repositories` events, and on admin disconnect. A feature requesting a permission the installation did not grant gets 409 `permission_not_granted` (02.4.3 §7) — there is no fallback to a broader token. Adding a permission to the App is an ADR amendment plus GitHub re-consent: the account owner is prompted to approve the new permissions ✅, and the `installation` `new_permissions_accepted` event ✅ updates the stored `permissions` map. Performance: one mint per cache key per ~55 min, with a single-flight lock per cache key.

### Key custody

The App private key (PEM), App id, client secret and webhook secret reach the process only through the one secret-provider interface (D-A2, 10.1.1-T2 `ISecretProvider`); secret names are versioned (e.g. `github_app_private_key_v1`, `github_app_client_secret_v1`, `github_webhook_secret_v1`) and are registered in `infra/config-matrix.json` by 02.4.3-T2, not here. The key is never in the repo, the database, logs or CI variables; a managed store replaces the environment-injected provider after O3. The custodian is the named role **GitHub App key custodian** — proposed default the owner (O2: the team is one person; D-A4 precedent), recorded as [OPEN] in DECISIONS §8 O11.

Compromise response is **generate-then-delete**, because GitHub forbids deleting an App's only key: "you must regenerate a new key before you can delete the existing key" ✅ ([Managing private keys for GitHub Apps → Deleting private keys](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)). The order is: (1) turn `github_app_enabled` off; (2) revoke every Evidgate-held installation token by calling `DELETE /installation/token` with each cached token ✅ — before any restart, because a restart only discards them from memory and they would stay valid up to 1 h; (3) generate a new key at GitHub; (4) delete the compromised key at once — this is the revoke, and it stops new app JWTs signed with it; (5) identify and close the exposure path before loading the new key; (6) load the new key into the secret store and deploy/restart Api+Worker; (7) tokens an attacker minted with the stolen key cannot be enumerated or revoked by Evidgate and stay valid up to 1 h after minting ✅ — this residual window is accepted and stated; (8) rotate the webhook and client secrets; redeliver failed webhook deliveries or run the 02.4.3-T3.2 reconcile task; (9) incident per 10.7.1-T6; notify affected org admins with the App id, the window, and to review their org audit log for the App's bot actor. No standby key is kept (a standby would need custody too). The full procedure is in the runbook [`../runbooks/github-app-key-custody.md`](../runbooks/github-app-key-custody.md).

Redaction (00 §5.7 S3): the App private key, the app JWT and installation access tokens (`ghs_` prefix ✅, [GitHub's token formats](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#githubs-token-formats)) are on the redaction list — absent from logs, metric labels and exception messages.

## Alternatives rejected

- **One App per feature** — four Apps to register, four private keys to custody, four webhook secrets and four install flows for the same customer org; the customer would install four Apps and re-consent four times. One App with per-feature token subsets gives the same least privilege **for Evidgate-minted tokens** with one install (02.4.3 §1); it does not constrain anyone holding the private key (see §Consequences).
- **One App for all environments** — a single App shared by production, dev, staging and CI would need the production key, webhook secret and webhook URL in every environment, so a lower-environment leak equals a production compromise for every customer, and D-A2 requires each secret to be generated per environment. Rejected: two Apps (production + non-production), each with its own key, secrets and webhook URL.
- **Per-customer self-registered Apps** — every customer would create and own an App; Evidgate could not ship a fixed permission manifest, key custody would move to the customer, and 02.4.3's install callback and `evidgate_resolve.installation_by_id` would have no stable App id. Rejected: it removes Evidgate's ability to enforce the minimal permission set.
- **OAuth App / personal access token (PAT)** — an OAuth App requires interactive user authentication and its tokens are long-lived by default ✅, so it acts on behalf of a user, not an org installation; a PAT is a long-lived user credential carrying the user's whole scope, not a per-feature short-lived token. Both contradict 02.4.3 AC3/AC4 (no long-lived credential, token in memory only) and T46.
- **GitHub Actions `GITHUB_TOKEN` only** — GitHub creates the `GITHUB_TOKEN` per workflow job and it expires when the job finishes ✅, so it is scoped to that run and cannot be minted by Evidgate's server to post a check run, open a PR or re-run a workflow from outside the run. Rejected: it cannot serve the four consumers.

## Consequences

- Unblocks 02.4.3-T2/T3 (install callback, token provider, webhooks/reconcile) and, through them, 07.6.1-T1 (Stage B), 03.4.1-T1 (Stage C), 03.4.2-T1 (V2/Stage D) and 05.5.2-T3 (Stage C).
- **Registration owner.** 03.4.1-T1 (sub-task 03.4.1-T1.1, "GitHub App registration + installation binding…") registers both Apps from this matrix (V1 rows) and verifies the manifest against it, including the ⚠️ `metadata: read` mandatory check; O11's "needed before" is before that task registers the App.
- **V2 amendment cost.** The V2 healing rows (`contents: write`, `pull_requests: write`) are not in the registered set at first registration; adding them is an ADR-0007 amendment plus one customer re-consent prompt per installation. The 08.6.1-T3 head-drift check run adds no App-level permission (`checks: write` is already registered via 07.6.1-T1), so it needs no amendment or re-consent.
- One App means one permission set to register and one re-consent prompt per customer when a feature adds a permission; the `new_permissions_accepted` event keeps the stored map current.
- The App-level registered set is the union of the matrix; a feature that needs a permission outside its row is an ADR amendment, not a code change.
- **Blast radius.** Anyone holding the App private key can mint a token carrying the full registered union for every installation; the subset rule only constrains Evidgate-minted tokens. GitHub states the key "grants access to every account that the app is installed on" ✅ ([Best practices for creating a GitHub App → Private keys](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)). Accepted for V1 (one custodian), mitigated by the V1-only registration scope, the production/non-production App split, the custody runbook and the fact that the key signs only in-process.
- **Install binding.** The user-authorization binding above amends 02.4.3 AC2 and T2.2: the callback verifies the installation against `GET /user/installations` for the installing user and that the user administers the installation account, not the app JWT alone — [OPEN] DECISIONS §8 O12 (recommended [INFERENCE]: the ownership check above).
- GitHub Enterprise Server is out of V1 [OPEN] (02.4.3 §1); the App model assumes github.com.
- The custodian role and the App name/distribution stay [OPEN] (DECISIONS §8 O11, OI-02-14) until the owner names them; `github_app_enabled` stays off until then (02.4.3 §11).

- ✅ Managing private keys for GitHub Apps — https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps (fetched 2026-10-11): up to 25 private keys per app; use multiple keys to rotate without downtime; keys do not expire and are manually revoked; store the key in a key vault, sign-only. "You can remove a lost or compromised private key by deleting it, but you must regenerate a new key before you can delete the existing key."; "If your GitHub App has only one key, you will need to generate a new key before deleting the old key."
- ✅ Webhook events and payloads — https://docs.github.com/en/webhooks/webhook-events-and-payloads (fetched 2026-10-11): `installation` actions `created`, `deleted`, `new_permissions_accepted`, `suspend`, `unsuspend` and `installation_repositories` are received by all GitHub Apps by default (cannot be manually subscribed); `push` needs at least read-level "Contents"; `pull_request` needs at least read-level "Pull requests"; `check_run` and `check_suite` — "GitHub Apps with write-level access for the "Checks" permission are automatically subscribed to this webhook event."
- ✅ Rerequest a check run — https://docs.github.com/en/rest/checks/runs#rerequest-a-check-run (fetched 2026-10-11): "The fine-grained token must have the following permission set:" → "Checks" repository permissions (write); `POST /repos/{owner}/{repo}/check-runs/{check_run_id}/rerequest` triggers the `check_run` `rerequested` event for a check run owned by the authenticated App (403 "if the check run is not rerequestable or doesn't belong to the authenticated GitHub App"); it does not re-run a workflow.
- ✅ Choosing permissions for a GitHub App — https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app (fetched 2026-10-11): "GitHub Apps don't have any permissions by default"; when permissions change, the owner of each account where the app is installed is prompted to approve the new permissions.
- ✅ Differences between GitHub Apps and OAuth apps — https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps (fetched 2026-10-11): installation access tokens expire after a predefined time (currently 1 hour); OAuth app tokens are long-lived by default; an OAuth app requires interactive user authentication.
- ✅ `GITHUB_TOKEN` — https://docs.github.com/en/actions/concepts/security/github_token (fetched 2026-10-11): GitHub creates a unique `GITHUB_TOKEN` at the start of each workflow job; it expires when the job finishes.
- ✅ About the setup URL — https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url (fetched 2026-10-11): "Bad actors can hit this URL with a spoofed `installation_id`. Therefore, you should not rely on the validity of the `installation_id` parameter. Instead, you should generate a user access token for the user who installed the GitHub App and then check that the installation is associated with that user."
- ✅ Generating a user access token for a GitHub App — https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app (fetched 2026-10-11): "If you select **Request user authorization (OAuth) during installation** in your app settings, GitHub will start the web application flow immediately after a user installs your app."; the `code` is exchanged at `POST https://github.com/login/oauth/access_token` with the client id and client secret; the user access token starts with `ghu_` and expires after 8 hours by default.
- ✅ REST API endpoints for GitHub App installations — https://docs.github.com/en/rest/apps/installations#list-app-installations-accessible-to-the-user-access-token (fetched 2026-10-11): `GET /user/installations` "Lists installations of your GitHub App that the authenticated user has explicit permission (:read, :write, or :admin) to access."
- ✅ Get the authenticated user — https://docs.github.com/en/rest/users/users#get-the-authenticated-user (fetched 2026-10-11): `GET /user` returns the authenticated user; "A token without scopes still authenticates as the token's owner"; the response `id` (required, integer) is the account id compared with an installation's `account.id`.
- ✅ Get an organization membership for the authenticated user — https://docs.github.com/en/rest/orgs/members#get-an-organization-membership-for-the-authenticated-user (fetched 2026-10-11): `GET /user/memberships/orgs/{org}`; "If the authenticated user is an active or pending member of the organization, this endpoint will return the user's membership. If the authenticated user is not affiliated with the organization, a 404 is returned."; response `state` enum `active`/`pending` and `role` enum `admin`/`member`/`billing_manager`; Permissions required for GitHub Apps lists the endpoint for user access tokens only (UAT).
