## Context

Review finding S1 (`plans/REVIEW-2026-10-02.md` §2.4) and ASVS-GAP-24 (`docs/security/asvs-l2-mapping.md` §4, carried row `ASVS L2 gaps: 11.5.2-T1`) record that the audit hash chain lives inside the PostgreSQL database it protects and uses no secret, so anyone able to rewrite the audit rows can recompute every hash and nothing would notice.

Facts about the code on `develop` at da6a5001 (read from the files, not from plan text):

- The shipped table is `audit_log` with `seq`, `prev_hash` and `entry_hash` (`migrations/0015_identity_audit_log.sql:12-15`, `:39-40`); `seq` is dense per org and the first row has `prev_hash` of 32 zero bytes. The 11.5.2 plan and the T8 ruling call the same columns `audit_event` and `row_hash`. This ADR uses the shipped names and treats the plan names as the same objects (naming reconciliation is an open item).
- `audit_log_chain_guard` (`migrations/0015_identity_audit_log.sql:89-117`) only checks that a new row extends the tip (`seq`, `prev_hash`, `created_at`); it holds no secret, so a database-privileged actor can bypass or replace it.
- The verifier recomputes the same unkeyed hash from the same database (`src/BuildingBlocks/Persistence/Audit/AuditChainVerifier.cs:65`; run by `VerifyAuditChainTaskHandler`, `VerifyAuditChainTask.cs:57`). Its three blind spots are carried row `Audit chain verifier blind spots (S105 review: G1, G2, G4)`: G1 tail truncation is undetectable without an external anchor, G2 an emptied chain is invisible to the sweep, G4 malformed metadata aborts verification.
- A second, SQL-side writer exists: the definer function `evidgate_resolve.session_revoke_one` appends its audit row inside PL/pgSQL and computes `entry_hash = sha256(prev_hash || canonical)` there (`migrations/0050_identity_session_revoke_audit.sql:108`, `:247`, `:274-279`; re-created whole by `migrations/0051_identity_session_revoke_audit_ids.sql:87`, `:285-290`). It runs as `evidgate_owner` and cannot reach a secret, so after the keyed cutover it would append rows with a null `chain_key_id` past the legacy bound and fail verification (Decision 1, Decision 4); Decision 1 proposes the rule that removes or wraps this path.

Object-storage seam: `IObjectStorage` / `S3ObjectStorage` over `AWSSDK.S3` (`src/BuildingBlocks/ObjectStorage/IObjectStorage.cs:18`, `S3ObjectStorage.cs:32`), which exposes no conditional put today (F19).

## Decision

1. **Keyed chain.** New audit rows store `entry_hash = HMAC-SHA-256(chain_key[key_id], key_id || prev_hash || canonical)`, where `key_id` is its 2-byte big-endian value and `canonical` is the RFC 8785 input the chain uses today (00 §7); binding the id into the MAC means an attacker without the key cannot relabel a row. The writer calls `System.Security.Cryptography.HMACSHA256` (F15) through an `IAuditChainSigner` port that returns the digest and the `key_id`; the key never reaches SQL. Rows get an additive nullable `chain_key_id smallint`; the app role cannot update it. A signer failure fails the request closed: no unsigned audit row, HTTP 503.
    - **SQL definer writer path (decided by the owner 2026-10-29: option A, DECISIONS §8.2 `D-S131-N1`).** `session_revoke_one` appends its audit row in SQL (`migrations/0050:274-279`, `0051:285-290`), where no secret exists, so it cannot produce a keyed row. Exactly one rule must hold before the first keyed row is written; the owner confirmed **option A** and the code fix is 02.7.1-T2 (carried row `ADR-0010 N1: SQL definer audit writer (S131, #270)`, not in this ADR and not delivered by 11.5.2):
        - **A (decided 2026-10-29).** 02.7.1-T2 moves the revoke path's audit append into the application writer before the keyed cutover: the definer function returns its result only, every row goes through `IAuditChainSigner` in the caller's transaction, and the legacy bound then covers exactly the rows written before the cutover. One writer, one place where the key is used, and no known writer left that appends unkeyed rows after the cutover; any other append is caught by Decision 4, because a row with a null `chain_key_id` above `legacy_unkeyed_through_seq` is a verification failure.
        - **B.** The definer path stays and calls a signer service over an authenticated internal call inside the same transaction; a signer failure aborts the revoke. Not recommended as the default: it puts a network round trip inside a security-critical definer, keeps two writers on one chain, and needs an internal authorization path the repo does not have (`[INFERENCE]`).
        - Either way the invariant is the same and is not optional: a row with a null `chain_key_id` after the org's `legacy_unkeyed_through_seq` is a verification failure (Decision 4), never a tolerated legacy row, so the cutover cannot proceed without a rule; the owner chose A on 2026-10-29 and 02.7.1-T2 delivers it. Until 02.7.1-T2 lands, every row the `0050`/`0051` definer writes carries a null `chain_key_id`: it is valid only at or below its org's `legacy_unkeyed_through_seq`, and above that bound it is flagged and reported as a failure at its `seq`, never silently verified as a keyed row; receiver 02.7.1-T2.
2. **Key custody.** The chain key and the checkpoint signing key are secret-store references only (00 §5.7 S3, §11): neither is stored in, derivable from or readable by the application database or the app DB role, and neither is in an image, a config file or a log. The two key classes are `audit_chain_key` and `audit_checkpoint_signing_key`, 32 random bytes for the HMAC key and a P-256 private key for the signer, generated outside the database. In V1 the secret seam delivers by environment injection per workload, so the separation below is a deployment property, proved by a `check-env-matrix` entry and a role-grant test in T2 rather than by the provider. Human access goes through 10.7.1-T4 break-glass.
3. **Identities.** Three workload identities, each in its own process and environment: the **writer** (any host that flushes audit rows through `AuditTrail`) holds the HMAC key only; the **exporter** holds the checkpoint signing key only, reads the chains through its own DB role with `SELECT` on `audit_log` and the org list (named in T2, not the app role) and holds a bucket policy scoped to the single prefix `audit-checkpoints/v1/`: `PutObject`, `ListBucket` with that prefix and `GetObject` on it, and nothing else — the listing and the reads are required because `checkpoint_seq` is derived from the highest existing object and `prev_checkpoint_hash` hashes the previous document (Decision 7); `DeleteObject`, `PutObjectAcl`, `DeleteBucket` and any key outside `audit-checkpoints/v1/` are denied to it, so it cannot remove an existing checkpoint and cannot touch any other path in the account; overwriting an existing key is refused only where the store enforces Object Lock or a deny-overwrite policy (Decision 11, conditional on F21/F22), and where it does not, a second write is detected by the signature and link checks, not blocked (Decision 11 fallback); the **verifier** holds the HMAC keys read-only plus the checkpoint public keys, a read-only DB and bucket credential, and an append-only credential (read and write, no update and no delete) on its own high-water backup target, which lives outside the checkpoint bucket and outside the database (Decision 8). The exporter must not share a process or environment with any host that writes audit rows, because one process holding both keys could forge and hide; T2 acceptance names the host for each identity.
4. **Key id on every row.** Every keyed row carries `chain_key_id` and every checkpoint carries `key_id` for its signature. `chain_key_id` null is valid only at `seq` up to the org's `legacy_unkeyed_through_seq`, recorded per org exactly as Decision 7 defines it; a null id above that bound, a listed org with no bound, or an id the verifier does not know, is a verification failure and is never skipped.
5. **Rotation without rewriting history.** Rotation adds a new key id; the old key becomes verify-only and stays with the verifier until its last row is outside audit retention. Order: provision the new key to the verifier first, then switch the writer, so a new row never carries an id the verifier lacks. No existing row or checkpoint is changed. Because `SecretNames` is a closed list and runbook §2.3 documents one slot per class, this needs a key-set mechanism the repo does not have (a keyring secret or pre-registered versioned names) and does not follow the single-slot pattern; T2.3 chooses it and writes the runbook rows and drill.
6. **Compromise.** HMAC key: rotate immediately and record the first suspect `seq` per org in the next checkpoint; rows before it stay covered by checkpoints cut before the compromise and rows after it under the compromised id are unproven — they are still recomputed and compared against every later checkpoint and any mismatch is reported at its `seq`, so the flag labels the attestation that cannot exclude the compromised key, it never turns a failure into a pass. Checkpoint signing key: revoke the key id and re-anchor the public-key list out of band; that list records per `key_id` the inclusive `checkpoint_seq` range the key may sign, and a checkpoint whose own `checkpoint_seq` falls outside its key's range is unproven — `cut_at` is signer-written and never decides key validity, so a key holder cannot widen its own window by restating a time. The public-key list (`key_id` to public key, with the algorithm pinned) is held by the verifier outside the database and the bucket.
7. **Signed external checkpoints.** A scheduled exporter cuts a checkpoint from a repeatable-read snapshot without the writer lock: RFC 8785 JSON of `{checkpoint_seq, cut_at, key_id, prev_checkpoint_hash, prev_trusted_checkpoint_seq, orgs[{org_id, last_seq, last_row_hash, legacy_unkeyed_through_seq, deleted_at_seq, first_suspect_seq}]}`. The per-org fields beyond the tail: `deleted_at_seq` is the `seq` of the org's `org_deleted` tombstone (null while the org stands, and non-null is terminal for that org's chain, AC11); `first_suspect_seq` is the first `seq` per org whose rows are unproven after a suspected HMAC-key compromise (null when there is none, set by Decision 6 and never cleared by a later checkpoint; it is a label, not an exemption — rows at or after it are verified, recomputed and reported exactly like every other row); `legacy_unkeyed_through_seq` is the highest `seq` written by the pre-cutover unkeyed writer — the first checkpoint records it for every org it lists, an org that first appears in a later checkpoint records it in the checkpoint where it first appears, and that value is `0` when the org was created after the keyed cutover, so a null `chain_key_id` on any of its rows is a failure under Decision 4. A listed org with a missing bound is a schema failure, never an unbounded legacy window, and a bound may never increase from one checkpoint to the next. `prev_trusted_checkpoint_seq` is defined by Decision 8, and the exporter derives both it and `checkpoint_seq` only from objects whose own `.sig` verifies under its trusted key list and whose `prev_checkpoint_hash` link holds: an unverified object in the prefix contributes neither a number to continue from nor a trusted link, so a bucket-write attacker cannot push the exporter's numbering or its trusted chain forward (the verifier applies the same rule, Decision 8). It is a new object `audit-checkpoints/v1/<checkpoint_seq zero-padded>.json` plus a detached `.sig` over exactly those RFC 8785 bytes, in a bucket the application database role and the application's storage credential cannot delete from, and cannot overwrite where Decision 11's Object Lock or deny-overwrite policy holds (else a bad overwrite is detected by the signature and link checks). `prev_checkpoint_hash` hashes the previous checkpoint document only (not its signature, which is not canonical). Checkpoints hold ids and hashes only, no payload and no personal data.
8. **Anti-rollback rules the verifier enforces.** Per org, `last_seq` never decreases from one checkpoint to the next; an org present in an earlier checkpoint is present again or carries a deletion tombstone; a `checkpoint_seq` below the verifier's high-water, or one already consumed, is a failure. A restore that shortens the chain therefore alerts by default (O-11.5.2-2); a sanctioned rewind would need an owner-authorised, separately audited `restore_epoch` act, which is the one way history can be shortened on purpose.
    - **The high-water is the highest signature-verified `checkpoint_seq`, not the highest seen.** The verifier store advances only for an object whose `.sig` verified under a public key trusted for that `key_id` over the `checkpoint_seq` range recorded out of band for that key (Decision 6; `cut_at` never decides validity) and whose `prev_checkpoint_hash` link held. An object with a missing, invalid or untrusted signature never raises the value, and neither does a name read from the bucket listing, the database or a local index: the value is evidence-derived, so an attacker who can add objects cannot advance it and one who can delete objects cannot lower it.
    - **Custody.** The store belongs to the verifier identity alone (Decision 3); no writer, exporter, application role or human role has write access; it is not derived from the bucket or the database, so a bucket rollback, a database restore or a rebuild of the exporter's local index cannot rewind it; and it is written atomically (temp file, fsync, rename) so a crash leaves the previous value rather than a torn one.
    - **Backup and restore.** Every advance is copied to a backup target outside the checkpoint bucket and the database, retained at least as long as the checkpoints. A restore may only reinstall the highest value that backup holds: it never lowers the value, and a restored verifier treats every `checkpoint_seq` at or below it as already consumed, so a reused number is a failure rather than a fresh checkpoint. If the backup is missing, or lower than the newest **signature-verified** `checkpoint_seq` the bucket holds, the verifier fails closed and reports `audit_verify_unavailable` — never green — until the owner authorises a re-seed (O-11.5.2-2); an object whose signature or link did not verify never makes the backup look stale, never triggers fail-closed and never motivates a re-seed — it is only reported (next bullet) — and this comparison uses verified numbers alone. A re-seed runs under the verifier identity after an audited owner act (break-glass 10.7.1-T4, recorded as `restore_epoch`), may only set the high-water to the highest signature-verified `checkpoint_seq` the bucket holds — never to a number an unverified object asserts and never above what verified — and appends that act to the backup target before the value changes, so the re-seed itself stays part of the evidence.
    - **An unproven object never blocks verification.** The verifier reports `checkpoint_signature_invalid` or `checkpoint_link_broken` for it, keeps walking the prefix, and verifies the database against the highest trusted checkpoint it already holds, raising the high-water only from verified objects; it neither stops at the unproven number nor advances past it, and it keeps the alert open until the object is resolved. A bucket-write attacker with no keys therefore cannot downgrade the verifier to "nothing verified" by publishing a bogus higher `checkpoint_seq`: the result is a paging storm and an unproven object, not a blind spot.
    - **Links across revoked or unproven checkpoints.** `prev_checkpoint_hash` always hashes the canonical bytes of the immediately preceding document (`checkpoint_seq − 1`), whatever that document's verification status, so the document chain never has a hole and a revoked checkpoint never forces a re-cut; `prev_trusted_checkpoint_seq` names the highest earlier checkpoint that verified, is monotone, and is the only field a verifier uses to continue its trusted chain. A revoked or unproven checkpoint therefore stays in the link chain and leaves the trusted chain: the rows it covered are re-established by the recompute from the last trusted checkpoint (Decision 10), not trusted, and a checkpoint whose `prev_trusted_checkpoint_seq` disagrees with the verifier's trusted chain is `checkpoint_link_broken`. Re-cutting under a different `checkpoint_seq` to paper over a revoked signature is not allowed; the object is retained and recorded as unproven.
9. **Signature algorithm: ECDSA P-256 with SHA-256**, the algorithm the verifier pins. It is the asymmetric signature this repo can use with no package (F16); Ed25519 is not chosen because in-box ECDSA suffices and a library would need the ADR-0002 matrix path (its absence from .NET 10 is unverified, F17). **Encoding: IEEE P1363 fixed-length `r||s`, 64 bytes for P-256** — the form .NET's two-argument `ECDsa.SignData` emits — and the `.sig` object is exactly those 64 raw bytes; the verifier accepts that encoding only, and a DER signature is a verification failure rather than an accepted alternative, so there is one parser on the wire. DER (`DSASignatureFormat.Rfc3279DerSequence`) stays available for local debugging only. `[verified locally 2026-10-29, node v26.10.0, .NET 10.0.12]` A throwaway harness (outside the repo) signed with both runtimes and verified in the other: Node `crypto.verify("sha256", msg, {key, dsaEncoding: "ieee-p1363"})` returns `true` for .NET's default signature and `{dsaEncoding: "der"}` returns `true` for the RFC 3279 form; .NET `VerifyData` with `IeeeP1363FixedFieldConcatenation` returns `True` for Node's P1363 signature and `Rfc3279DerSequence` returns `True` for Node's DER signature; and each encoding returns `false`/`False` under the other's label in both runtimes, so the encoding must be pinned in code and in `audit-checkpoint.v1.json`, never defaulted. The check ran on macOS 27.0.1 arm64 (SDK 10.0.401); it proves the API-level encoding contract, not every host, because the signature backend behind `ECDsa` is platform-specific ⚠️. With this the Node-verification blocking check for accepting the ADR is satisfied for the encoding decision (F17); 11.5.2-T3 still owns the verifier implementation and its negative tests.
10. **Cadence: every 15 minutes** `[INFERENCE]`, matching the 15 min RPO in 00 §11 (the plan's default); it is the longest window in which rows can be added and removed again with nothing left to compare against, so the cadence bounds that exposure instead of removing it (Decision 13). The alarm `audit_chain_verified_through_age_seconds` fires when the newest verified checkpoint is older than 2 cadences (30 min). The verifier runs hourly, verifying every checkpoint signature and link and recomputing from the last verified checkpoint, with a weekly full walk `[INFERENCE]`.
11. **Write-once.** Conditional create (`If-None-Match: *`, F18) protects against an accidental second write by a well-behaved client; it does not stop a credential that omits the header, a later delete or a versioned shadow. Preventing overwrite and delete needs Object Lock or a deny-overwrite bucket policy.
    - Dev: SeaweedFS with a deny-delete policy, Object Lock documented (F21) and proved only by the T2.1 negative test, which must cover overwrite as well as delete; an existing dev bucket may need recreating because Object Lock can be enabled only at creation. Production is undecided with O3.
    - **Fallback** (F22): a separate account whose policy grants the platform `PutObject` on the checkpoint prefix plus the exporter's `ListBucket`/`GetObject` on it (Decision 3) and nothing else, plus versioning; this is detection-only, since a bad overwrite is caught by the signature and link checks rather than blocked.
12. **Rollback.** The exporter and the verifier are disabled independently; checkpoint objects stay; the `chain_key_id` column stays. Reverting to an unkeyed chain is not supported once keyed rows exist.
13. **What T2 and T3 will and will not detect.** Detected, and only where a checkpoint has already attested the fact: an edited row at or below that checkpoint's `last_seq` per org when the attacker has no key; a recomputed unkeyed hash on a legacy row a checkpoint already covers, because `last_row_hash` contradicts it; a relabelled key id; a tail truncation that leaves the org's `last_seq` below a checkpointed `last_seq` (S105 G1); an interior gap at or below that bound; a modified or replaced checkpoint; a deleted interior checkpoint; an org dropped without a tombstone (G2); malformed metadata reported as a mismatch at its `seq` (G4).
    - Detected only by the staleness alarm: deletion of the newest checkpoint.
    - Detected only by the anti-rollback rules and never from the objects alone: a bucket rolled back wholesale to an earlier `checkpoint_seq` (Decision 8).
    - **Not detected: anything no checkpoint has attested yet.** Tail truncation between two checkpoints is invisible — rows appended after the newest checkpoint and deleted again before the next cut leave nothing that says they existed, so truncation becomes detectable only once a checkpoint pins a `last_seq` the database no longer reaches. Pinning a forged row does not detect it either: a checkpoint attests that history was not rewritten after the cut, not that it was true at the cut, so a forgery completed before the cut is attested by it. Both are inherent to cut-based evidence: the only lever this design has is cadence (Decision 10) or an independent source (a writer-side log, a second store) that is out of scope here.
    - Latency: an edit, truncation or gap below a checkpointed bound is caught at the first verifier run after the checkpoint that contradicts it (about 75 min worst case with hourly runs); the weekly full walk catches a divergence that the incremental walk's pinned hashes miss, up to 7 days; a forgery no source contradicts is never caught.
    - Not detected at all: tampering before the first checkpoint, and a fully compromised operator holding both keys and the store. Retention of the chain and of the bucket (S105 G5) is the 11.5.1/11.8.1 decision, not made here (`[OPEN]`, no legal minimum asserted).

## Alternatives rejected

- **Unkeyed chain only (today).** Rejected: the attacker needs only database write access to recompute every hash, so the chain proves nothing against the actor it exists for (S1, ASVS-GAP-24).
- **DB-side trigger only.** Rejected: the guard in migration 0015 runs inside the same database; a privileged actor can disable or replace the trigger, and a trigger can neither hold a secret outside the database nor detect truncation.
- **External anchoring service (public transparency log or third-party timestamping).** Rejected for V1: it adds a hosted dependency and a data-residency question for no gain over a write-once bucket we already need, and it publishes org ids and hashes outside our control. `[INFERENCE]` it may return in V2 as an extra anchor on top of these checkpoints.

## Consequences

- Needs 02.7.1 to add `chain_key_id` and the `IAuditChainSigner` writer path (gap note appended to the 02.7.1 plan; T2.3 defines the contract, 02.7.1 implements it), the exporter and verifier (11.5.2-T2, T3), a key-set mechanism and two key rows in the key-rotation runbook (11.5.2-T2.3) and a contract change request to 00 §5.4/T8 and §15 (queued, not applied).
- The keyed cutover additionally waits on the code fix in 02.7.1-T2 for the SQL definer writer `session_revoke_one` (`migrations/0050:274-279`, `0051:285-290`); Decision 1's owner choice is settled on 2026-10-29 as option A (DECISIONS §8.2 `D-S131-N1`), so only that code fix remains; until it lands, a keyed row and a definer-written row cannot share a chain: a definer-written row stays inside its org's `legacy_unkeyed_through_seq` and is flagged and reported as a failure above it (Decision 1), never counted as keyed; receiver 02.7.1-T2, so the column, the signer and the cutover ship together or not at all. That item stays open (carried row `ADR-0010 N1: SQL definer audit writer (S131, #270)`); this ADR does not close it.
- A new secret to provision per environment and a new compromise class. Losing an HMAC key makes the rows under that id unverifiable, so key backup follows 10.7.1-T4.
- The shipped chain and `docs/security/audit-taxonomy.md` stay true (unkeyed) until 02.7.1 ships the writer change; ASVS-GAP-24 stays open until T2 and T3 ship.
- **Residual risk.** By attacker capability (the first column is what the attacker has; the cadence is 15 min per Decision 10, and rows name where cadence is the only lever and where it does not help):

| Attacker holds | Outcome |
|---|---|
| Database write only | Cannot forge a keyed row; edits and truncations at or below the newest checkpointed `last_seq` are detected (Decision 13) |
| Database write plus the newest checkpoint document | Can delete rows appended after that checkpoint and stay consistent with every checkpoint: never detected, because nothing records that those rows existed. Cadence shrinks this window, it cannot empty it |
| HMAC key and database write | Can forge rows before they are cut; the next checkpoint attests the forgery instead of detecting it, so it stands unless an independent source contradicts it. Cadence does not help here — only such a source does |
| Checkpoint signing key only, no HMAC key | Cannot forge or relabel a keyed row, so no forged history is attested as true; it can sign bogus checkpoint documents, which either fall outside its key's `checkpoint_seq` range or below the org's checkpointed `last_seq` (unproven or monotonicity failure) or attest rows the database does not hold (`truncated_tail`, a false alarm), and it cannot lower the verifier's high-water (Decision 8) |
| Database admin and bucket admin, no keys | Can roll back the database and the bucket to an older checkpoint; caught only by the anti-rollback high-water and the staleness alarm (Decision 8) |
| Bucket write only, no keys | Can publish bogus checkpoints at higher numbers and corrupt or add documents; each is `checkpoint_signature_invalid` / `checkpoint_link_broken`, skipped in the trusted chain and never advancing the high-water (Decision 8), so the outcome is paging and noise, not a blind spot |
| HMAC key and checkpoint signing key and bucket write | Can forge rows and later checkpoints undetected |
| A compromised verifier | Holds every HMAC key for the ids it verifies, so it can forge them |
| A compromised writer process | Appends false rows with valid HMACs; checkpoints prove only that earlier history was not rewritten |

- The first checkpoint signs the database's view without independent proof, so history before it (rows kept unkeyed) is protected only from that checkpoint forward. On a one-person team (O2) the owner holds every key, so separation of duties is technical only. Out of scope: tamper prevention against a fully compromised platform operator (11.5.2 §1 non-goals).

- **Cross-runtime signature check (D4, `[verified locally 2026-10-29, node v26.10.0, .NET 10.0.12]`, macOS 27.0.1 arm64, SDK 10.0.401).** Throwaway harness outside the repo (`$HOME/tmp-s141`, deleted after the run, never committed), signed bytes = the whole `message.txt` exactly as written (an abbreviated JSON wrapper, `{"format":"evidgate-adr-0010-ecdsa-interop","message":"evidgate checkpoint v1 …"}`, whose `message` field holds the checkpoint text; each runtime read and signed the entire file — Node with `fs.readFileSync`, .NET over that same string — so the signed bytes are the file bytes and no byte count or digest of the original run is claimed here), P-256 keys generated independently in each runtime, SPKI DER exchanged:
    - `node gen.js message.txt` → `node v26.10.0`, `node sig ieee-p1363: 64 bytes`, `node sig der: 70 bytes`, `node self-verify p1363-as-p1363=true der-as-der=true p1363-as-der=false der-as-p1363=false`; writes the SPKI DER (91 bytes), message and both signatures to JSON.
    - `dotnet run -- message.txt.node.json message.txt.dotnet.json` → `.NET 10.0.12`, `.NET import node SPKI DER: 91 bytes read of 91`, `verify node ieee-p1363 with IeeeP1363FixedFieldConcatenation: True`, `verify node der with Rfc3279DerSequence: True`, `False` for both cross checks, `.NET key: ECDSA nistP256, SPKI DER = 91 bytes`, `.NET sig default (SignData 2-arg): 64 bytes`, `.NET sig Rfc3279DerSequence: 70 bytes`, exit 0.
    - `node verify.js message.txt.dotnet.json` → `dotnet sig default (ieee-p1363): 64 bytes`, `dotnet sig Rfc3279DerSequence: 70 bytes`, `verify dotnet p1363 with dsaEncoding=ieee-p1363: true`, `verify dotnet der with dsaEncoding=der: true`, `false` for both cross checks, exit 0.
    - Conclusion carried into Decision 9: both encodings round-trip between the two runtimes; neither runtime guesses the label, so the wire encoding must be pinned (chosen: IEEE P1363, 64 bytes).
