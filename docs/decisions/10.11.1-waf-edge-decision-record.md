## 1. What this document is, and what it is not

It is the decision record required by story acceptance AC9: it states the edge/WAF stance (dependent on O3), what protection runs without a WAF, what is not covered, and the criteria an edge candidate must meet as an input to 10.8.1-T1.

It is **not** a build, a test or a procurement step. It does not choose, rank or price any product; it contains no measurement; it changes no code, route, contract schema or configuration key. It does not restate O3 as decided, and it does not re-score the hosting criteria C1–C6 of [`10.8.1-provider-selection-criteria.md`](10.8.1-provider-selection-criteria.md).

The story's own acceptance checks AC1–AC8 (plan §2) belong to 10.11.1-T1 and 10.11.1-T2. On `535fe560` none of 10.11.1-T1, 10.11.1-T2 or 04.1.2-T1 is merged (`git log origin/develop --grep` finds no merge commit for any of them; STATUS §5 lists all three as ready), so §3.2 names them as **planned, not merged**.

## 2. Stance and O3

O3 as it reads in DECISIONS §8: "Cloud provider/region for PostgreSQL + object storage (VN residency?). **Deferred 2026-10-02 [DECISION] (owner): decided later, "phase 2"**" (read as after the Stage B decision point and before any real customer data).

Stance `[OPEN]` O3:

1. **Without a provider decision there is no managed WAF/CDN.** Compose and any single-host staging run with the in-app limits only (plan §7: TLS and a reverse proxy, `[INFERENCE]` Caddy or nginx, optionally adding connection limits). This is the V1 baseline recorded for OI-10-03.
2. **A managed WAF, bot rules and volumetric absorption are provider-dependent**, so they are neither promised nor excluded. They are decided with O3, or after it, by the owner. This record keeps the decision open and only fixes what must be true of any edge (§6) and what the application keeps doing whether or not one exists (§3.3).
3. The application never relies on an edge for correctness: every protection in §3 is an in-process control that must stay on when an edge is added (the plan's rollback line: "Do not remove Kestrel body limits").

## 3. What runs without a WAF

### 3.1 Shipped on `535fe560`

Only per-endpoint throttle helpers around one in-process limiter ship today. Verified in the code graph and the files on `535fe560`:

| Protection | Where (`file:line`) | Real properties |
|---|---|---|
| `ExchangeRateLimiter.TryAcquire` | `src/Modules/Evidgate.Modules.Identity/Ci/ExchangeRateLimiter.cs:13-60`, sweep `:95-110` | In-memory per process; fixed window per key (`ExchangeWindowSeconds`, budget `ExchangeBurstLimit`); expired windows swept at most once per window; at 50 000 live keys new keys are refused (fail closed) while tracked keys keep their budget |
| `ExchangeRateLimiter.ClientKey` | same file `:62-86` | Key is the socket `RemoteIpAddress`; IPv6 reduced to its /64 |
| Sign-in throttle | `src/Modules/Evidgate.Modules.Identity/Endpoints/LoginEndpoints.cs:498-517` | 429 `rate_limited` + `Retry-After`; extra attempts cost more budget |
| Invite throttle | `src/Modules/Evidgate.Modules.Identity/Endpoints/InviteTokenEndpoints.cs:140-156` | 429 `rate_limited` + `Retry-After`, key = prefix + client key |
| Provider-link throttle | `src/Modules/Evidgate.Modules.Identity/Endpoints/LinkEndpoints.cs:703-724` | same shape, with cost |
| CI token exchange throttle | `src/Modules/Evidgate.Modules.Identity/Endpoints/CiTokenEndpoints.cs:185-195` | 429 `rate_limited` + `Retry-After` |
| Error code | `src/BuildingBlocks/SharedKernel/Api/ErrorEnvelope.cs:150` | `ApiErrorCode.QuotaExceeded` exists; no ingest quota uses it yet |

Absent on this base (searched under `src/`, no hit): `AddRateLimiter`, `UseRateLimiter`, `MaxRequestBodySize`, `UseForwardedHeaders`, `IngestQuota`. Consequences:

- **No Kestrel body, header or timeout limit is configured by Evidgate code**: ASP.NET Core defaults apply (the 30 MB default body size is recorded in the carried row on the unread body, §5).
- **No per-IP policy on unauthenticated routes beyond the four helpers above**, and no per-org read or presign limit.
- **No forwarded-headers handling.** Limiter keys use the socket address, so behind any reverse proxy or WAF all clients share the proxy's address until T1.2 configures trusted proxies (carried row on the shared per-IP pool, §5). An edge placed in front today would make the shipped per-IP limiters throttle all clients as one.

### 3.3 What the application keeps doing when an edge exists

`[INFERENCE]`, from the plan and the prior art in §7: the in-app limits stay on (the edge is outer, the app limits are inner and per-tenant); the app keeps emitting the §9.2 envelope and `Retry-After`; limiter keys must use a client address validated against the configured edge ranges, never a blindly trusted forwarded header (plan §7). Only the edge can do volumetric absorption, TLS handling before the origin, and rules across many instances.

## 6. Criteria an edge/WAF candidate must satisfy (input to 10.8.1-T1)

These are **additive** to C1–C6: an edge product that is part of a hosting offer inherits that offer's C1–C6 verdict and is not re-scored on them here. No weights, scores or candidates are set in this record; 10.8.1-T1 owns the scale. A criterion stays unscored until documentation or the 10.8.1-T2 spike evidences it.

| # | Criterion | What it means for Evidgate | Evidenced by |
|---|---|---|---|
| E1 | Trusted client-IP propagation | Forwards the original client address in a documented header and publishes stable egress ranges, so `KnownProxies`/`KnownNetworks` (plan §7) can validate it; without this the per-IP limiters key on the edge (§3.1) | provider docs; staging check in the spike |
| E2 | Rate-rule expressiveness | Per-route match, counting key (IP and at least one header or token characteristic), window, action and mitigation period; documented counting accuracy (§7: counters can lag and be per-location) | provider docs |
| E3 | Coexistence with in-app limits | Edge limits must be outer and looser than the app's per-org/per-project budgets; 429 from the edge needs `Retry-After` and must not hide the §9.2 envelope from CLI/adapter clients (edge-generated pages are not in the envelope) | provider docs; abuse suite run through the edge |
| E4 | Request-size and slow-client limits | Maximum request body, header size and slow-client timeouts at the edge; upload traffic to object storage is presigned and may bypass the API edge, so the edge scope must be stated | provider docs |
| E5 | Response controls | Maximum response size or error-page behaviour (carried row on response bytes) | provider docs |
| E6 | TLS and origin handling | Minimum TLS version, certificate management, TLS to the origin, origin reachable only via the edge, connection limits | provider docs |
| E7 | Volumetric absorption and bot rules | Documented network-layer absorption included in the plan tier; bot/CAPTCHA rules are optional (non-goal in plan §1) | provider docs |
| E8 | Data handling at the edge | The edge terminates TLS and sees bearer tokens and artifact metadata; where it runs and logs follows the residency gate C1 (referenced, not re-scored); client IPs in edge logs must satisfy the plan's IP-privacy rule (§8: IPs only as in-memory limiter keys, not logged by default; ⚠️ IP as personal data under PDPL to be confirmed by plan 11) | provider docs; plan 11 |
| E9 | Observability and operations | Export of rejection counts and logs into 10.3.1 (`ingress_rejected_total` semantics), dry-run or log-only mode before enforcement, rules as code so config is reviewable | provider docs |
| E10 | Fail mode and burden for one team | What happens when the edge is down or bypassed; no extra control plane beyond what C6 allows | provider docs; spike |
