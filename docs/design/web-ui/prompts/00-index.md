# Evidgate — Web UI OpenDesign prompt inventory

## How to use
Create the OpenDesign project **Evidgate — Web UI** and submit one complete numbered prompt per run, in the order below. Each prompt is self-contained: it begins with the required frontend-design skill instruction and inlines the condensed brand/app brief; OpenDesign does not need repository access or a separate shared-file attachment. Pass skill=frontend-design in start_run as requested by the owner. This folder contains prompt text only, not OpenDesign runs, HTML outputs, owner-approved wireframes, app tokens or implemented UI.

[00-shared-brief.md](00-shared-brief.md) is the complete cross-page contract. Numbered prompts request one single high-fidelity HTML artifact each, with light/dark, EN/VI, desktop/tablet/read-only mobile, default/loading/empty/error/403/412 state switcher and local illustrative domain fixtures. No real secrets or live requests. The design-review toolbar is explicitly not a production feature. App dark/status/layout tokens are proposals pending approval; landing foundation/overrides are reused exactly.

## Open questions and conservative design decisions
1. **Q1 — Secrets, owner decision required.** Assignment says never display secrets; 09.2.1 AC2/T2, 09.7.1 AC10/T3/T8 and 09.7.2 AC4/T1 require one-time plaintext reveal/copy. **23/29/35/37** cover creation/rotation/transient-clear/copy-feedback with a REDACTED design fixture only. They do not claim plaintext-reveal ACs met. Decide whether a narrowly scoped one-time reveal exception is allowed in production; never supply real credentials to OpenDesign.
2. **Q2 — Canceled onboarding sample.** 09.2.1 AC3 and T3.2 enable Next on any terminal state including canceled, while §6 step3_done allows complete/incomplete only and canceled shows retry. **23** designs canceled distinctly with retry and no automatic completion; the final Next/progress behavior needs contract alignment.
3. **Q3 — Policy tab visibility.** 09.7.1 AC1 hides the Policy tab without policy:write; §5 route table and §8 rationale allow policy:read and describe read-only viewer/QA policy/quarantine. **27/30** use conservative AC1 tab visibility and clearly distinguish publish rights; decide whether policy readers should have the tab before implementation. Waivers/results remain readable at run surfaces.
4. **Q4 — Official verdict inside shadow comparison.** 09.5.1 AC4/T3 asks to render official decision via the reused DecisionView; FR-09-8 and 09.5.1 §8 say healing screen never renders a release verdict. **13** keeps original/shadow outcomes side by side and links the unchanged official decision in Run detail instead of rendering a release-decision chip inside healing. Owner must confirm this presentation exception against AC4; no verdict is overwritten.
5. **Q5 — Quality Overview source gaps.** 09.9.1 leaves exact run:read/decision:read permission, latency/day-bucketing definition, projection watermark schema, range cap/read-model budget and chart-library choice open. **22** renders supplied fields/sample sizes, never computes rates/percentiles, labels illustrative fixture values and zero-denominator no-data. Do not turn 366-day inference into a product promise.
6. **Q6 — Studio/CLI concrete contracts.** 09.6.1 leaves template/draft/suite endpoints and merge eligibility API details for source contracts; suite write/publish permissions are not specified fully. **17–20** use server-provided allowed actions and do not invent merge or publish APIs. **24** quickstart syntax is illustrative and needs CLI-contract confirmation, with no credentials.
7. **Q7 — Admin endpoint/permission details.** 09.7.1 agents exact 05.7.3 endpoint, webhook CRUD/rotation/redelivery paths and rollout shorthand; 09.7.2 api_token/deploy_target permission names/CRUD, target update support and token maximum expiry remain source-open. **34–38** show planned metadata/actions with server authority, no guessed endpoint paths or hard-coded expiration cap. Known permissions are design gating labels pending the permissions source of truth.
8. **Q8 — Future screen scope.** V3 root-cause analytics, SSO/SAML and visual-regression review have names but no 09 feature contract/AC/page specification. Their current boundary mappings are above; obtain those contracts before requesting distinct OpenDesign runs. Do not misread future names as permission to invent features. Customer public-share page remains explicitly out of scope.
9. **Q9 — Approval of app design system and source placement.** 09.1.1 AC9 requires owner-approved wireframes in docs/design/web/ and light/dark tokens in apps/web/src/styles/tokens.css. This assignment writes only the untracked owner prompt folder docs/design/web-ui/prompts/; it does not touch either required implementation path. Landing specifies light brand/font/logo, not an approved dark app/table/token system. OpenDesign's app-specific tokens remain proposals for owner review.
