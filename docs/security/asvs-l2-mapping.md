## 1. Level statement (2026-10-27)

**Target.** OWASP Application Security Verification Standard (ASVS) **5.0.0**, level **L2**, for the web application (the Angular app origin) and the `/v1` HTTP API. L1 requirements are included by definition; L3 requirements are **not** claimed. ASVS version verified 2026-10-27 at the tag [`https://github.com/OWASP/ASVS/tree/v5.0.0/5.0/en`](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0/en): 17 chapters, `0x10-V1-Encoding-and-Sanitization.md` … `0x26-V17-WebRTC.md`.

**What the level means here.** L2 is a **verification target, not a certification** (`[DECISION]` D3, [`plans/11-security-compliance.md:75`](../../plans/11-security-compliance.md); FR-11-11, [`plans/11-security-compliance.md:51`](../../plans/11-security-compliance.md)). Nothing in this document asserts that Evidgate *is* L2 today: §3 states per chapter what the code does and §4 publishes what it does not.

**Decision and paper trail.** The decided level equals the level the area plan proposed, so **no contract change request is filed against 00 §11**; 11-CR-1 is already applied (`[DECISION]`, [`plans/11-security-compliance.md:381`](../../plans/11-security-compliance.md)) and task 11.1.1-T3.2 files a CR only if the decided level differs from the proposed L2. Decision id **D-S107-Q1** (COORDINATOR-DECISION, accepted 2026-10-27): ASVS 5.0.0, level L2 confirmed for web and API, chapter-level mapping, V17 marked not applicable. It **closes area-plan open question 1** ("ASVS target level ⚠️: confirm L2 or accept a documented subset", owner Tech Lead, needed by M2/11.1.1-T3 — [`plans/11-security-compliance.md:348`](../../plans/11-security-compliance.md)) and supplies what open item OI-11-18 asks for in this file — the current version number, a dated chapter list and a published gap list ([`plans/open-items/04-ops-security-commercial.md:51`](../../plans/open-items/04-ops-security-commercial.md)); the requirement-level walkthrough half of OI-11-18 stays with 11.7.1-T5.

**Accountable person.** The solo founder, who is the Tech Lead and QA/PO for this program (O2, [`plans/00-overview.md:530`](../../plans/00-overview.md)). Each gap in §4 repeats that owner because, at this team size, the receiver of the work and the person who accepts the residual are the same.

**Scope boundary.** The mapping is chapter level, not requirement level: a chapter marked `partial` has landed controls and published gaps, and a requirement inside a landed control may still be unmet. The evidence walkthrough at requirement level is 11.7.1-T5 (V2, phase G4).

## 2. Version note (4.0.3 → 5.0)

ASVS 5.0 renumbered and rewrote the standard — of the 286 requirements in v4.0.3 only 11 are unchanged and 109 are no longer separate requirements ([`0x05-For-Users-Of-4.0.md`](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x05-For-Users-Of-4.0.md)) — so the 4.0.3 chapters map to 5.0 only approximately: V2 Authentication → V6, V3 Session Management → V7, V4 Access Control → V8, V5 Validation/Sanitization/Encoding → V2 (validation, moved next to business logic) and V1 (encoding and sanitization), V6 Stored Cryptography → V11, V7 Error Handling and Logging → V16, V8 Data Protection → V14, V9 Communication → V12, V10 Malicious Code → largely withdrawn (the surviving defensive-coding content sits in the new V15), V11 Business Logic → V2, V12 Files and Resources → V5, V13 API and Web Service → V4, V14 Configuration → V13; 5.0 adds V3 Web Frontend Security, V9 Self-contained Tokens (formerly under session management), V10 OAuth and OIDC, V15 Secure Coding and Architecture and V17 WebRTC, and removes the 4.0.3 V1 Architecture chapter by redistributing its content. `[INFERENCE]` used only for the one-to-one arrows; the structural statements are the 5.0 change note's own.

## 5. How to keep this current

- **11.7.1-T5 is the walkthrough that turns `control:` into evidence** (V2, phase G4). It walks each chapter, re-reads every cited file:line on the head it reviews, replaces a named control with the test, artefact or measurement that proves it, and either closes a gap or republishes it against a receiver. The requirement-level verdict is that task's output, not this file's.
- **Every milestone-exit re-review** of the threat model (11.1.1-T1.4, M1–M3 slots in `docs/security/threat-model-v1.md`) re-opens this mapping for the chapters whose boundaries changed, because a new boundary or transport changes applicability before it changes code.
- **A chapter row is only valid while its Evidence cell carries exactly one `control:` or `gap:` line.** The chapter check in the story's test plan ([11.1.1 §9](../../plans/features/11-security-compliance/11.1.1-a-living-threat-model-acceptance-v1.md)) is satisfied when all 17 rows do, so a mechanical grep over the table is enough to fail a chapter that loses its disposition.
- **V17 is conditional, not permanent.** The day a peer-to-peer media or streaming feature is planned, V17 becomes applicable, this row changes from `not applicable` to a real disposition, and the change belongs in the same PR that introduces the dependency.
- **When the standard moves**, the version statement in §1 changes with it: a new ASVS tag is verified at its own URL, dated, and the chapter list re-read before any row below is touched.
