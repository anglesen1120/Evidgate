#### A.2 Findings

**A-F1 — `evidgate.purge_expired_ci_token_issue`: the replacement migration restates no ACL, and no test pins the guard.** Rule id `definer_acl_restated`. `migrations/0019_identity_ci_review_fixes.sql:8-27` rewrites the body but has no `revoke … from public` / `grant execute` pair, while every other sweep migration pairs the definition with both statements (0007:158-159, 0015:146-147, 0043:208-211, 0048:561,567, 0058:85-87, 0067:308-309, 0076:145-146). The live ACL today is correct only because 0017 applied first and `create or replace` preserves it (`0017_identity_ci_token_issue.sql:88-89`).

*Failure scenario.* A future file that drops and re-creates the function with a changed signature, or a replay of 0019 against a schema where 0017's grant was lost, leaves the hourly `ci_token_issue.purge` sweep owner-only: the task fails with 42501 at runtime and dead-replays expired replay-cache rows forever. The mirror failure is silent: nothing in the suite asserts the app role is *refused* this function (`tests/Tasks.IntegrationTests/CiTokenIssuePurgeTaskTests.cs:24-39` exercises the happy path only), so an accidental default-ACL change that grants `evidgate_app` EXECUTE would let any tenant transaction delete another tenant's `ci_token_issue` rows and no test would fail.

*Severity:* P3 — no live hole; forward-only hygiene plus a missing negative test.
*Receiver:* owning stories `01.5.1-T6` (the T80 sweep rule, `plans/features/01-foundation/01.5.1-durable-internal-tasks.md:37`) and `02.4.2-T1` are both landed (`STATUS.md:128`, `:135`), so no open task owns this artifact. Nearest precedent for filing: `11.2.1-T3`'s T3-G1..G5 were filed as STATUS §6 queue rows with open receivers — that is the shape this needs (owner decision between a one-line migration `0019:27`-style ACL restatement, or a test-only fix).

**A-F2 — `evidgate.healing_switch_set_system`: the platform-wide kill switch still has no durable audit record.** Rule id `definer_audit`. The exemption is recorded (`scripts/check-rls.py:179-195`) because `public.audit_log.org_id` is NOT NULL (0015:27) and the hash chain is per org (`prev_hash`/`entry_hash` 0015:39-40 with `unique (org_id, seq)` at 0015:44), so a platform-scope write has no chain to append to. Today the *only* record of a system switch change is the mutable `public.healing_switch` row (mode, reason, set_by, at, version) plus an information log line (`src/Modules/Evidgate.Modules.Healing/Application/HealingSystemSwitch.cs:94`).

*Failure scenario.* An operator disables (or shadows) healing during an incident and later restores it; the row shows only the last value and `version` count, and the log line is not an immutable, verifiable store. An incident review cannot prove who changed the platform-wide kill switch, when, or how often, and the append cannot be checked by the chain verifier. D-S137-OWNER already put the fix in `platform_security_event` (never a nullable `org_id`), and that table plus its emitter remain owed (`docs/status-carried.md:395`; the same hand-over is restated at `docs/status-carried.md:344`, `:374`).

*Severity:* P2 — an audited platform capability is unverifiable after the fact; no correctness or isolation failure, and the caller is gated (see matrix).
*Receiver:* the open queue item of carried row **"Platform security event table (D-S137-OWNER)"** (`docs/status-carried.md:395`: "queue task (table+emitter) after 11.1.1-T4.1's type") — 11.1.1 is landed (`STATUS.md:263`), so the table+emitter task is the open receiver. Scope of the gap, checked per caller rather than by the absence of an INSERT: `session_create` is covered by the caller's `auth.login` row per active org (`audit-taxonomy.md:170`) — with the recorded residual that an account holding no active org leaves no row at all; `session_revoke_all_for_user` is covered by the calling command's own row in the same transaction (`[AuditedAction("membership.remove")]` `src/Modules/Evidgate.Modules.Identity/Application/Commands/RemoveMember.cs:42` calling it at `:139`; `[AuditedAction("membership.update")]` `UpdateMembership.cs:71` calling it at `:156`); `session_require_rotation` likewise (`RevokeRole.cs:49,:146`; `GrantRole.cs:61,:170`). `session_authenticate` runs on every request and correctly writes no per-call row.
