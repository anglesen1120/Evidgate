## 2. Token model

### 2.1 The two kinds

| Kind | Form and life | Where minted | What a caller holds |
|---|---|---|---|
| Tenant **ingest token** | `egt_<12-char public prefix>_<43-char base64url secret>`; a long-lived tenant credential, optionally with `expires_at` (§2.3) | `POST /v1/projects/{p}/ingest-tokens` (`IngestTokenCommands.cs:56-130`); rotate `POST /v1/ingest-tokens/{t}/rotate` (`:140-222`) | The plaintext, once (§4) |
| Minted **`ci_producer` JWT** | HS256 JWT, `token_use=ci_producer`, one `project_id`, 1–60 min (`CiProducerTokens.cs:70-113`; `CiAuthOptions.cs:32-34`) | `POST /v1/ci/token`, from a verified GitHub OIDC token (`ExchangeCommands.cs:47-153`) or from an ingest token (`:197-249`) | A bearer token for the ingest routes |

The route is one: an `ingest_token` field in the body selects the ingest grant, otherwise the `Authorization: Bearer` JWT is treated as a GitHub OIDC token (`CiTokenEndpoints.cs:76-90`). Both grants are off with 503 `unavailable` when no signing key or pepper is configured (`:60-63`; `CiErrors.NotConfigured` at `CiBindingCommands.cs:272-276`).

### 2.2 Scope binding

- Ingest token → project: the row carries `org_id`/`project_id` (`migrations/0018_identity_ingest_token.sql:14-16`), the resolver returns the tenant tuple for the prefix (`:81-97`), and the endpoint publishes that tenant before the command runs (`CiTokenEndpoints.cs:167-179`). The command re-checks `token.OrgId != orgId` and answers `token_unknown` (`ExchangeCommands.cs:210-213`).
- Ingest token → scopes: `event:write`, `artifact:write`, `run:create` only, 1–3 distinct entries (`IngestTokenCommands.cs:22-26,47-52`; CHECK `migrations/0018_identity_ingest_token.sql:39-40`). The minted producer carries the token's scopes intersected with the service ceiling (`ExchangeCommands.cs:236`; ceiling at `CiProducerTokens.cs:246-250`).
- GitHub binding → project: the binding's `project_id` is copied into the producer (`ExchangeCommands.cs:99-106`); the repository is matched by immutable `repository_id`, never by name (`:61-64`; a rename only updates the display name, `:91-97`).
- Producer → one project at enforcement time: a service principal whose `project_id` claim differs from the addressed project is 403 `project_scope_mismatch` (`src/Modules/Evidgate.Modules.Identity/Authorization/PermissionEvaluator.cs:127-130`; test `CiAuthTests.cs:186`).
- Run claims: only the GitHub grant attaches `repository_id`, `repository`, `ref`, `sha`, `run_id`, `run_attempt`, `job_workflow_ref` (`CiProducerTokens.cs:90-99`), all copied from the validated OIDC token (`ExchangeCommands.cs:108-126`); the ingest grant mints with `Run: null` (`:238`), so an ingest-minted producer binds producer slots by `jti` only (`CiProducerTokens.cs:165,174-184`).
- **A fork PR's ref can never match any allowlist, by construction.** Every `allowed_ref_patterns` entry must match `^refs/(heads|tags)/[A-Za-z0-9._/*+@-]{1,200}\z` (`RefGlob.cs:65-66,74`, enforced at binding create and update, `CiBindingCommands.cs:44,132`), and every `allowed_workflow_refs` entry must end in `@refs/(heads|tags)/…` (`RefGlob.cs:77`, `CiBindingCommands.cs:45,135`). GitHub's fork-PR ref is `refs/pull/<n>/merge` (`docs/security/customer-ci-recipe.md:69`), which satisfies neither shape, so no administrator can configure an allowlist that a fork-PR ref matches. ⚠️ the shape validators have no test of their own (no `IsRefPattern` case in `tests/**`), so this ceiling rests on the regex, not on a test.

### 2.4 Revocation semantics

| Credential | Revocable? | Effect | Evidence |
|---|---|---|---|
| Ingest token | Yes, immediate | `DELETE /v1/ingest-tokens/{t}` sets `revoked_at` (or cuts a live rotation overlap); the next exchange answers `token_revoked` | `IngestTokenCommands.cs:231-283`; `CiAuthTests.cs:436-456` |
| Ingest token, rotated predecessor | Overlap end | The predecessor expires at `overlap_ends_at`; deleting it ends the overlap now | `IngestTokenCommands.cs:200-211,261-264`; `CiAuthTests.cs:480-484` |
| **Minted `ci_producer` JWT** | **No** | Validation reads no database and no status: a producer keeps working for its full lifetime after the parent token is revoked or the binding is disabled; the only thing that ends it early is a signing-key cutover (a restart-only break-glass, [`docs/status-carried.md:267`](../../STATUS.md)) | `CiProducerAuthenticator.AuthenticateAsync` → `CiProducerTokens.ValidateAsync` and nothing else (`CiProducerTokens.cs:136-166,256-273`); `ci_token_issue` has no status or revocation column (`migrations/0017_identity_ci_token_issue.sql:10-33`); [INFERENCE] the same holds for a disabled binding, since only the exchange path reads `CiBindingStatus` (`ExchangeCommands.cs:66-82`) |
| GitHub binding | Yes, for new exchanges | `Disabled` refuses exchange (`ExchangeCommands.cs:68-69`); already-minted producers are unaffected (row above) | Same |

The residual is bounded by the producer lifetime (at most 60 minutes plus 30 s skew, `CiAuthOptions.cs:33-34`; `CiProducerTokens.cs:126`). It is dispositioned as an accepted risk in §6 row 5 and as gap **T3-G2** for the runbook text and the missing test.

### 2.5 Replay

| What | Present today | Evidence |
|---|---|---|
| GitHub OIDC token replay | **Blocked at mint time only.** `ci_token_issue.jti` is `unique`; a second exchange of the same OIDC token is 401 `token_replayed` and records nothing new | `migrations/0017_identity_ci_token_issue.sql:4-8,30`; `ExchangeCommands.cs:108-136`; test `CiAuthTests.cs:296-310` |
| Minted producer replay | **Not prevented, and no ledger exists.** Each mint takes a **freshly generated** `jti` (`CiProducerRequest.Jti`, `CiProducerTokens.cs:12-27`; the value is `Guid.CreateVersion7()` at `ExchangeCommands.cs:105` and `:237`), which is carried into the principal (`CiProducerTokens.cs:165`) but written to no table: the `ci_token_issue` row stores the **OIDC** token's `jti`, not the producer's (`Jti = command.Claims.Jti`, `ExchangeCommands.cs:116`). No request path consults a producer `jti`, so a captured producer is a bearer credential until `exp` | `migrations/0017_identity_ci_token_issue.sql:10-33` (no producer column); `ExchangeCommands.cs:105-126,237`; `CiProducerTokens.cs:136-166` (no DB read) |
| Ingest token replay | **By design a bearer credential.** The exchange mints a fresh `jti` per call (`ExchangeCommands.cs:237`), so presenting the same token again simply mints again; only `last_used_at` is rewritten, at most every 60 s | `:231-244`; `TouchSql` `:194-195`; test `CiAuthTests.cs:415-434` |
| Have the two grants distinct meanings? | The GitHub grant binds one *job* to one token; the ingest grant binds one *project credential* whose holder may exchange repeatedly. That asymmetry is what makes ingest tokens the higher-value secret, and why the recipe forbids them in fork-reachable workflows (`docs/security/customer-ci-recipe.md:90`) | — |

### 2.7 The `workflow_run` question, and the `ExchangeCommands.cs:87` comment

**Comment disposition — deny as written (partially).** The comment at `ExchangeCommands.cs:87` says a fork PR is refused because "a fork runs under another `repository_id` (no binding) or an unlisted workflow". The second half is the control that actually ships; the first half is only partly borne out by the shipped evidence. A fork's own `repository_id` path *is* tested: repo id `999_999` against unbound state returns `binding_mismatch` (`CiAuthTests.cs:266-267`, whose comment names a fork PR), and the case that models a fork PR's *token* mints the **upstream** `repository_id` and varies the workflow ref (`:268-270`). The refusal path is therefore tested; only the claim *semantics* — which `repository_id` GitHub actually puts in a fork-PR token — are `[INFERENCE]`: GitHub serves a `pull_request` OIDC token for the run in the **base** repository, whose `ref` is `refs/pull/<n>/merge` (`docs/security/customer-ci-recipe.md:69`, `:82` — repository evidence for the ref shape, GitHub documentation for the repository), so `repository_id` matches the base binding and the refusal comes from the **ref/workflow allowlists** (`ExchangeCommands.cs:84-89`). The comment and the test comment at `CiAuthTests.cs:266` should be corrected the next time either file is touched; no behaviour changes.

**`workflow_run` disposition — `[DECISION]` owner, 2026-10-27: APPROVED — deny `workflow_run` by default in the server, not only in the recipe.** At the time of the decision, only `pull_request_target` was denied (`CiAuthOptions.cs:70`; `GitHubOidc.cs:133-137`), and the check is a **deny list**: an event not named passes, so the control fails open for every future event name. A `workflow_run` of the allowed workflow file on `main` carries `ref` `refs/heads/main` and the allowed `job_workflow_ref`, so it passes both allowlists and mints a producer; only the workflow file content guards it (recipe rule `R1`, branch protection). Approved option (owner, 2026-10-27): add `workflow_run` to the `DeniedEventNames` default in code and in the configuration matrix, **and** make `event_name` a required claim in `Extract` (`GitHubOidc.cs:144-154`) so that a token which omits it cannot skip the deny check at all: today the check is `jwt.TryGetPayloadValue<string>("event_name", out var eventName) && _denied.Contains(eventName)`, so a token that simply omits the claim skips the deny list altogether, and a default-list-only fix leaves that bypass in place. That is a one-line default change, one required-claim line, a matrix-default change and two matrix cases in `Exchange_ClaimMatrix_RefusesEveryInvalidToken` (one for `workflow_run`, one for a token without `event_name`); the `environment`-claim check and a positive event allowlist are larger changes and are not needed for the residual, because the ref/workflow allowlists stay the primary control. This is **not** a new gap: it is already the STATUS §6 row "OIDC grant accepts `workflow_run` (from S17, 11.2.1-T1)" ([`docs/status-carried.md:49`](../../STATUS.md)), so it is dispositioned here and linked, not re-filed. The code change is a change request against the shipped 02.4.1-T1.3 (the event-name claim check and the default deny set live in that task's file) and is now **coordinator queue row F50** — backend, T3, size S, no migration, **high priority because it must land before any pilot data**; F50 carries all three cases in the `CiAuthTests` matrix (`workflow_run` refused, missing `event_name` refused, `push`/`workflow_dispatch` still mint), while 11.2.1-T2.2 keeps only its fork-context fixture (plan `:121`). Long term the deny list becomes an **event allowlist with a per-binding audited opt-in** — an opt-in recorded as an audit row — which is a larger change and is deliberately outside F50. **Implemented by F50 (S110, PR #238, f59ec29):** the `DeniedEventNames` default is now `pull_request_target,workflow_run` (`CiAuthOptions.cs:67-73`) and `event_name` is a required, non-empty claim — a missing, empty or blank value is refused with `token_invalid` before extraction (`GitHubOidc.cs:133-138`), so the bypass above is closed; the configuration-matrix note carries the same default (`infra/config-matrix.json:343-360`), and the matrix refuses `workflow_run` and a missing/empty/blank `event_name` while `push`/`workflow_dispatch`/`pull_request`/`merge_group`/`schedule`/`release` still mint (`CiAuthTests.cs:216-220,248-263`). Comparison is ordinal and case-exact, so a differently cased `Workflow_Run` still mints (pinned at `CiAuthTests.cs:269-278`), and an explicit override replaces the default — `EVIDGATE__CI__DENIEDEVENTNAMES=schedule` refuses `schedule` and mints `workflow_run` (`CiAuthTests.cs:280-297`). Recipe lint `R1` and branch protection stay as defence in depth; the event allowlist with per-binding audited opt-in is the open F50 follow-up (c), recorded as a STATUS §6 row.

## 5. Pepper custody and rotation

**Where it lives.** `EVIDGATE__CI__PEPPER` and `EVIDGATE__CI__PREVIOUSPEPPER` are declared `secret: true` with `source: secret-store` for staging and prod, while `EVIDGATE__CI__PEPPERVERSION` and `EVIDGATE__CI__PREVIOUSPEPPERVERSION` are plain integers with the default source (`infra/config-matrix.json:157-235`); the producer signing key is the same secret shape (`:74-92`).

**How it is read.** The three key-material properties have internal setters, so the configuration binder cannot fill them; `CiAuthOptionsSecretPostConfigure` writes them from `ISecretProvider` under `SecretNames.CiSigningKey`, `CiPepper`, `CiPreviousPepper` (`CiSecrets.cs:159-173`; `SecretNames.cs:22-29`), registered as a post-configurer (`IdentityModule.cs:199-200`).

**What "secret store" means today.** The single `ISecretProvider` registration is `EnvironmentSecretProvider`, reading the host configuration by the configuration spelling of the secret name (`SecretProviderExtensions.cs:29-36`), so in V1 the "store" is the deployment's environment/secret-delivery injection; a managed store replaces that one registration and nothing else (`:17-23`), and the platform-secret store choice remains open (runbook §1, [`../runbooks/key-rotation.md:13`](../runbooks/key-rotation.md); `STATUS.md` row 741 is the database-credential half (O-C, receiver O3), not this choice). Custody is therefore ✅ met at the seam and ⚠️ unverified as a *managed* store — no claim beyond injection is made here.

**Startup validation.** `AddOptions<CiAuthOptions>().Bind(...).ValidateDataAnnotations().ValidateOnStart()` (`IdentityModule.cs:191-196`) plus `CiAuthOptionsValidator`: present values must be base64 and at least 32 bytes (`CiSecrets.cs:131-149`, `MinKeyBytes = 32` at `:17`), `PreviousPepperVersion` must differ from `PepperVersion` (`:115-118`), and `GithubJwksUri` must be https on the issuer host (`:120-126`). Absent values are allowed on purpose: the exchange answers 503 instead of failing the host (`CiAuthOptions.cs:5-15`; `CiTokenEndpoints.cs:60-63`).

**Never printed.** Validation failures name only the property, never the value (`CiSecrets.cs:142,147`); the matrix marks the values `secret: true`; the logging pipeline redacts Authorization headers and secret-named assignments before export (`LogRedactionProcessor.cs:51,69,93-102`; `SecretRedactor.cs:252-278`). The redactor's known residual shapes are already recorded (`docs/status-carried.md:252`).

**Versioned rotation.** Verified against the runbook rather than restated here: new tokens are hashed with the current pepper (`HashCurrent`, `CiSecrets.cs:41-46`), exchange accepts the stored version under either the current or the previous pepper and returns null for a retired version (`HashWithVersion`, `:51-61`; `ExchangeCommands.cs:215-221`), and a retired version behaves like an unknown token (`CiAuthTests.cs:487-527`). The procedure, its failure modes and its open items are [`../runbooks/key-rotation.md` §3.1](../runbooks/key-rotation.md), with **O-D** (no re-hash/sweep of old-version rows — `:180`, also `docs/status-carried.md:270`) and **O-G** (no audit action for pepper rotation — `:183`, also `docs/status-carried.md:271`). This review found **no new pepper-custody gap**: the one thing the code adds to the runbook's picture is that rotation copies `ExpiresAt` unchanged (`IngestTokenCommands.cs:196`), so a never-expiring token stays never-expiring across rotations — recorded as **T3-G1**, not as a rotation gap.
