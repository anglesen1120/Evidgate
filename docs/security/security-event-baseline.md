# Security-event baseline (V1)

Owner: 11.1.1-T4.1 (task [11.1.1](../../plans/features/11-security-compliance/11.1.1-a-living-threat-model-acceptance-v1.md) `:116`, AC6). This page fixes the V1 `security_event` type set: what each type means, its severity, where the condition is detected in code today, and who consumes the row. The table (`migrations/0053_security_security_event.sql`, shipped) and the read endpoint are [11.5.1](../../plans/features/11-security-compliance/11.5.1-who-saw-what-provably-acceptance-audit.md)-T5's, not this page's.

## 1. Purpose and scope

- **The V1 set, and only it.** `auth_failure`, `cross_tenant_probe` (foreign-id 404 patterns), `secret_scanner_alert`, `kill_switch_used`, and `support_access` rows from [02.8.1](../../plans/features/02-identity-tenancy/02.8.1-time-boxed-operator-access.md)-T1 — the five types 11.1.1-T4.1 defines, fixed as a closed enum by [11.5.1](../../plans/features/11-security-compliance/11.5.1-who-saw-what-provably-acceptance-audit.md) `:47`. `injection_attempt` is listed there as `(V2)` and assigned to 11.4.1-T2 (`:79`); it is not in this set and V1 consumers must not serve it.
- **Severity vocabulary is closed:** `info | warning | critical` (`11.5.1` `:48`). No plan fixes a per-type severity, so §2's values are derived from impact and recorded here for 11.5.1-T3.1 to reuse; §3 states the rationale and marks each `[INFERENCE]`.
- **Action names are the shipped ones.** This page reuses `audit_log` action literals from [audit-taxonomy](audit-taxonomy.md) (§3–§4) and never renames or invents a second vocabulary; a security event *references* the action it accompanies, it does not duplicate the action catalogue.
- **Emitters are per-module.** 11.5.1-T5 owns the schema and the read, not the emitters (`11.5.1` `:75`); modules 02/04/06/08/10 write rows. `audit-taxonomy.md:176-177` records the same split.
- **Metadata rule for every type.** `actor` and `details` carry ids, closed enums and counts only — never a secret, credential, cookie, raw payload, foreign org/project name or other PII (`11.5.1` `:49-50`, `:96`; the web brief bars foreign targets, [33-security-events.md:22](../../docs/design/web-ui/prompts/33-security-events.md)).
- **No row exists yet.** The table exists since migration 0053 (11.5.1-T5) and T5.2 serves the read (`11.5.1` `:152`), but no emitter writes rows yet (`audit-taxonomy.md:176-177,194`). Every "emit point" below is therefore a **detection** site, not an emitter, unless a task id is named. This is the control that [threat-model-v1](threat-model-v1.md) `:199` (TH-audit-6) dispositions as `[planned]`.

## 3. Per-event notes

### 3.1 `auth_failure`

- **Detection.** Session cookie refused: an unmintable value (`SessionAuthenticationStore.cs:93-106`) and a dead status mapped to a closed 00 §9.2 code (`:162-178`). Federated login refused: EventId 2432 with a closed category (`GitHubLoginProvider.cs:575-579,581-585`) and 2431 the same shape for Google (`GoogleLoginProvider.cs:273-283`). CI exchange: invalid OIDC `401` (`CiTokenEndpoints.cs:112`), binding refused `403` (`:127-133`), ingest token unknown `401` (`:158-174`); inside the transaction, `token_replayed` (`ExchangeCommands.cs:134-140`) and ingest unknown/bad-secret/revoked/expired (`:212-228`). A `429` from the exchange limiter (`CiTokenEndpoints.cs:115-118,162-165`) is a throttle, not a refused credential `[INFERENCE]`.
- **Allowed `details`** `[INFERENCE]`: `{surface: login|session|ci_exchange|ingest_token, reason: <the 00 §9.2 code the route answered>}`; `actor` stays `{kind, id}` over the existing `PrincipalKind` set (`audit-taxonomy.md:52-58`). No credential, token prefix, cookie, address or provider claim value.
- **Related actions (success-only, unchanged):** `auth.login` (`audit-taxonomy.md:125`), `ci_token.exchange` (`:106`), `ingest_token.exchange` (`:107`).
- **Already metered on the login half:** `evidgate_login_attempts_total` (`src/BuildingBlocks/Observability/EvidgateTelemetry.cs:65,142-145,281-285`) and `evidgate_session_auth_total` (`:73,147-150,293-294`). For that half the event is the auditable, tenant-visible counterpart of an existing counter, not the first detection. The CI/ingest half has no metric and no `EventId` (`CiTokenEndpoints.cs`, `ExchangeCommands.cs`; tracing only — `ExchangeCommands.cs:49,199`), so there the event is the only security signal (§5).

### 3.2 `cross_tenant_probe`

- **Detection.** A member names an org it has no membership in → `403`, the same answer whether or not the org exists (`TenantResolver.cs:66-70`). A service principal names an org that is not its own → `404` (`:84-86`). A handler returns one `404` for an unknown id, a foreign-org row and a sibling-project row (`GetRun.cs:64-66,92`). Underneath, the NULL-safe helper makes a foreign id simply "no row" (`migrations/0002_foundation_evidgate_schema.sql:26-33`).
- **Severity rationale** `[INFERENCE]`: one foreign-id `404` is indistinguishable from a stale bookmark or a deleted row, so `critical` per row would be noise; the *pattern* (repeat count per principal and route in a window) is what deserves `critical`, and that threshold belongs to the 11.5.1-T3.1 rule (`11.5.1` `:138`).
- **Allowed `details`** `[INFERENCE]`: `{response: 404|403, surface: member_org|service_org|foreign_id}` — and **no** foreign org/project id, which the design brief forbids disclosing.
- **Related actions:** none. A denied read writes no `audit_log` row: the authorization stage records only on success and the tenant stage rolls back (`audit-taxonomy.md:62`). `audit.export` (`:113`) stays success-only.

### 3.3 `secret_scanner_alert`

- **Detection state exists, the scan does not.** `artifact.scan_state` is a closed `pending|clean|flagged` column (`migrations/0028_evidence_artifact.sql:59,72`); `complete` writes `ready` with `scan_state=pending` (`src/Modules/Evidgate.Modules.Evidence/Domain/Artifact.cs:253`; the column default is `EvidenceDbContext.cs:53`); nothing writes `clean` or `flagged`. Planned detection: 06.2.3-T1 sets `scan_state`, writes one `masking_event` per pattern class with `hit_count`, raises `sensitivity` to `sensitive` and enforces `reject_on_secret` (`06.2.3` `:23-26`, `:118`); 11.3.1-T3.1 only verifies the fail-closed behaviour ([11.3.1](../../plans/features/11-security-compliance/11.3.1-secrets-never-leave-a-reference-acceptance.md) `:116`).
- **Severity rationale** `[INFERENCE]`: `critical` because the condition means a secret is already stored in tenant-visible evidence and the disclosure clock has started — the platform already serves `pending` as `sensitive` for exactly that reason (`06.2.3` `:25`).
- **Allowed `details`** `[INFERENCE]`: `{pattern_class, hit_count, artifact_id, action}` copied from `masking_event` — never the matched value (`06.2.3` `:114`).
- **Related actions:** none. `quarantine.create` (`audit-taxonomy.md:97`) is policy quarantine, a different object.
- **No existing signal:** no artifact-scan counter among the security counters (`EvidgateTelemetry.cs:65-73`) and no `EventId` anywhere in `src/Modules/Evidgate.Modules.Evidence`.

### 3.4 `kill_switch_used`

- **Detection: none.** Healing is an empty contract (`IHealing.cs:8-10`) that the orchestrator names as its reason to refuse replay (`…/Orchestrator/Application/Runs/CreateRunCommand.cs:141`); the switch route exists only in the contract (`openapi.yaml:4338` GET, `:4368` PUT), and no `healing_switch` table exists in `migrations/` yet — `08.6.3-T1.1` creates it ([08.6.3](../../plans/features/08-healing-learning/08.6.3-kill-switches-and-degradation.md) `:108`).
- **Planned detection:** 08.6.3-T1.2 ships `SetHealingSwitch`/`GetHealingSwitch`, `PUT|GET /v1/healing/switch` and the operator route (`08.6.3` `:109`); 08.6.3-T2.2 emits only the `healing_availability{resolved}` metric (`:116`).
- **Severity rationale** `[INFERENCE]`: using the switch is a deliberate, authorised operator action whose interest is visibility (who stopped healing, and why), not alarm. An *automatic* degradation trip is a different signal, planned for 08.6.3-T2.2 (`08.6.3` `:116`) and not emitted today, so the two should be distinguished in `details` rather than by inflating every row. The type is explicitly allowed to exist before its producer (`11.5.1` `:36`).
- **Allowed `details`** `[INFERENCE]`: `{scope: system|tenant|project, mode, previous_mode, automatic: bool}`.
- **Related actions:** none yet. The switch's own `[AuditedAction]` is 08.6.3-T1.2's decision; do not invent one here.

### 3.5 `support_access`

- **Detection: none.** There is no `support_grant` table; the operator principal carries no permissions (`IRequestPrincipal.cs:145-146`), the evaluator denies the kind outright (`PermissionEvaluator.cs:63`), `TenantResolver` refuses operator principals (`TenantResolver.cs:45-48`), and the operator ingress is fail-closed and writes no log line (`OperatorGate.cs:30-34,68-81`).
- **Planned emitter:** 02.8.1-T2.2 — session banner marker plus `security_event` emission on grant create and on sensitive reads (`02.8.1` `:116`; AC6 `:27`). Support: 02.8.1-T1.1/T1.2 ship the table, permissions and commands (`:108-109`).
- **Severity rationale** `[INFERENCE]`: a single grant row is expected traffic and must be visible to the tenant, so `critical` on every row would fire on legitimate access; the `critical` variant is the unauthorised attempt (expired or revoked grant, out-of-scope object), distinguished in `details`, not by inflating every row.
- **Allowed `details`** `[INFERENCE]`: `{grant_id, scopes[], expires_at, action: grant_requested|approved|revoked|read|write, sensitivity}`.
- **Related actions (never renamed):** `support.read` / `support.write` with the grant id in metadata (`02.8.1` `:26`); grant request/approve/revoke are planned audit actions with owner 02.8.1-T1.2 (`audit-taxonomy.md:181`). Success-only actions stay as they are: `audit.export` (`:113`), `ci_binding.disable` (`:110`), `ingest_token.revoke` (`:123`).
