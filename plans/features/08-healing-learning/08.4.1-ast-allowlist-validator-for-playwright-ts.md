## 1. Goal and non-goals

**Goal.** `packages/healing-validator` — a Node 26 / TypeScript 6.0 child process using the TypeScript compiler API — decides whether a Playwright-TS patch changes **only mechanics node kinds** (locator and wait mechanics) and rejects every forbidden pattern of DECISIONS §5.2 with a machine-readable reason code. `Evidgate.Worker` hosts it under hard resource limits; the API process never runs it.

**Non-goals.** Assertion-hash equality and semantic checks (08.4.2); sandbox replay (08.4.3); the Playwright healer that produces patches (08.5.4); validating non-Playwright engines (Appium/mobile is V3, 08.9.2).

## 2. User stories and acceptance criteria

- As the healing pipeline, I get a deterministic accept/reject verdict with a reason code for every candidate patch, so a mechanics-only fix passes and anything touching intent is rejected.
- As a Tech Lead, I can see the validator is a bounded child process, so a malformed or hostile patch can never stall the worker or touch the API.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Given a fixture patch that changes only a locator call argument or a wait mechanic (`getByRole`/`getByTestId`/locator chain argument, `waitFor`/`waitForSelector` mechanics), the validator exits 0 with `{ verdict: "accept" }` |
| AC2 | Each DECISIONS §5.2 pattern in the Vitest fixture corpus is rejected with its own stable `reason_code` (`assertion_removed`, `assertion_weakened`, `skip_fixme_injected`, `force_true`, `catch_swallowed`, `business_mock`, `network_check_disabled`, `unbounded_retry`, `testid_change`, `build_config_change`, `policy_change`, `data_change`) — 100% detection on the corpus |
| AC3 | A patch adding an import, a new top-level helper/function or a config/spec-file edit is rejected `patch_scope_exceeded` |
| AC4 | Child-process contract: malformed input → `{ verdict: "reject", reason_code: "input_invalid" }` on stdout and exit ≠ 0 never reaches the worker as a hang — kill at the wall-time limit |
| AC5 | An architecture test asserts `Evidgate.Api` has no project/package reference or `Process` invocation of the validator; only `Evidgate.Worker` does |
| AC6 | Validator cold-start + verdict on the fixture corpus stays under the worker budget (p95 < 5 s/patch on CI hardware; measured and recorded) |

## 3. Contracts touched

- DECISIONS §5.2 forbidden-pattern list — implemented 1:1; any pattern addition lands in the allowlist spec + fixture corpus together.
- New workspace `packages/healing-validator` under 00 §5.2; package versions pinned via root `package.json` workspaces + `package-lock.json` (T40).
- Internal worker command contract (not `/v1`): `ValidateCandidatePatch` input = `candidate_id`, `patch_artifact_id`; output = verdict + reason code written to `candidate_validation.checks` (00 §8.7 `checks` jsonb).
- Reason-code enum is published in `contracts/healing/validation-reasons.json` so 08.4.2/08.4.3/09.5.1 share one vocabulary.
- Note: the DECISIONS §5.2 pattern list may grow; the reason-code enum version (`reason_spec_version`) is stored on each verdict so a later spec change does not rewrite history.

## 4. Data model and migrations

- `candidate_validation` (from area §4.1, created by 08.3.2's ledger context but first written here; `migrations/NNNN_candidate_validation.sql` if not already applied): `org_id`, `id`, `unique (org_id, id)`, `candidate_id` composite FK `(org_id, candidate_id)` → `healing_candidate`, `round_no int check (round_no between 1 and 2)`, `sandbox_run_id`, `app_digest`, `fixture_hash`, `env_hash`, `assertion_hash_before`, `assertion_hash_after`, `checks jsonb` (per-check `{name, verdict, reason_code, reason_spec_version}`), `verdict`, `reason_code`, `created_at`; append-only (`REVOKE UPDATE, DELETE` from app role), RLS via `evidgate.current_org_id()`.
- No other tables; validator state is ephemeral (child process), verdicts live in `candidate_validation`.

## 5. API shapes (commands, queries, endpoints)

- No `/v1` endpoint. Internal only:

| Shape | Detail |
|---|---|
| Command `ValidateCandidatePatch` (`ICommand<ValidationOutcome>`) | Worker-side Mediator command inside the C2 pipeline for task handlers (telemetry → tenant scope → handler): loads candidate + patch artifact bytes, invokes `IHealingValidator` (the child-process adapter), writes `candidate_validation` row, on `reject` transitions the candidate `proposed → rejected` with `reason_code`, emits `healing.candidate_changed` outbox (C7) |
| `IHealingValidator` (internal to `Evidgate.Worker`) | Interface `ValidateAsync(patchSource, baselineSource, ct) → {verdict, reason_code?, checks[]}`; implementation spawns `node packages/healing-validator/dist/cli.js`, writes the request JSON to stdin, parses one stdout JSON line |
| Validator CLI protocol | stdin `{request_id, baseline_source, patch_source, spec_version}` → stdout one line `{request_id, verdict: "accept"\|"reject", reason_code?, checks: [{name, verdict, reason_code?}], ast_diff_summary}`; stderr is logged, never parsed; any non-JSON stdout → `validator_protocol_error` |
| Errors | Worker maps validator failures to candidate exit `insufficient_evidence` + `reason_code` (`validator_timeout`, `validator_crash`, `validator_protocol_error`), never `rejected` — a validator failure is not evidence the patch is bad |

## 6. States and transitions

- Validator verdicts feed the existing candidate machine (00 §8.7): `proposed → rejected` (`reason_code` recorded) or continue to semantic checks (08.4.2). A validator crash/timeout does not transition the candidate — the round is retried once within the ≤ 2-round budget, then `insufficient_evidence` (08.3.2-T3).

## 7. Jobs and integrations

- Triggered by the outbox/`task` queue from candidate mint (`healing.candidate_changed`), claimed `FOR UPDATE SKIP LOCKED`, natural key `(candidate_id, round_no)` — at-least-once, idempotent write (00 §5.3, A10).
- The validator process has **no DB, no network** (unshare/`--experimental-permission`-style denial ⚠️ exact Node 26 sandbox flag verified in T3.1; fallback: seccomp-free but cwd-restricted spawn + firewall-level egress deny on the worker pod) — data in via stdin, verdict out via stdout only.
- Consumed later by: 08.4.2 (adds semantic checks to `checks`), 08.4.3 (sandbox replay writes `sandbox_run_id`), 08.5.4 (healer output passes this same validator, FR-08-13).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T36 | TS validator is `packages/healing-validator`, child of `Evidgate.Worker` only, JSON stdin/stdout, CPU/mem/wall limits, pinned Node in the worker image | `ApiNeverRunsValidator` architecture test (AC5); spawn-limit unit test (AC4) |
| S1 | No SQL in the validator path; all writes parameterised EF Core | code review + P3 command counter |
| S3 | Patch text and AST summaries never logged beyond `patch_artifact_id` + hashes; artifact bytes fetched via 06's sensitive-artifact path (T57 `sensitive` default for `patch` kind handled by artifact service) | Log-redaction test |
| S5 (untrusted input) | Patch is attacker-influenceable: TS parser runs with a size cap, no `eval`/code execution — analysis only; input > 1 MiB rejected `patch_too_large` | Corpus test with oversized/malformed TS |
| P5 | No network call inside a DB transaction: child process spawn happens **before** the `candidate_validation` write transaction opens | Pipeline test asserting spawn outside tenant tx |
| P3 | `ValidateCandidatePatch` ≤ 4 SQL statements (read candidate, read artifact meta, insert validation, update candidate + outbox) | Command-count assertion |
| T40 | `packages/healing-validator` deps pinned in `package-lock.json`; `npm ci` only | Lockfile check (01.1.1 pattern) |
| RLS (00 §5.4) | Validation rows are `org_id` rows, composite FK, app role, `FORCE ROW LEVEL SECURITY` | Testcontainers cross-tenant test |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Mechanics-only patch accepted | `accepts_locator_argument_change`, `accepts_wait_mechanic_change` (Vitest, AC1) |

## 11. Rollout

- Merge order: T1 → T2 → T3 (worker host lands last, consumes the stable CLI protocol).
- No feature flag: the validator only runs when a candidate exists (08.3.x); shadow mode (08.3.3) keeps it away from any write path.
- Monitoring: counter `evidgate.healing.validator_runs_total{verdict,reason_code}`, histogram `validator_duration_ms`, alert on `validator_protocol_error` spike.
- Rollback: revert; `candidate_validation` rows are append-only history and remain valid evidence.
