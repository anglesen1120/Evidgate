## 1. Goal and non-goals

**Goal.** Build the curated, versioned evaluation corpus that 08.8.2 metrics and 08.8.3 phase gates read from: one corpus row set covering the seven FR-08-18 categories (real locator breaks, real product bugs, business UI changes, duplicate names, locales, network errors, data errors), the seven named rejection fixtures from §7, an adjudication step with an independent reviewer, and a deterministic holdout split by time or project so no incident appears in the retrieval corpus and the holdout at once.

**Non-goals.** Computing metrics on the corpus (08.8.2); the V2/V3 gate checks (08.8.3); the validator fixtures' code (08.4.1/08.4.2 own `packages/healing-validator` and the seeded broken states — this story registers them in the corpus, it does not re-implement them); mobile evaluation rows (08.9.2 — the schema carries `platform_context` from day one so no second table migration is needed).

## 2. User stories and acceptance criteria

- As the QA lead, I curate a corpus where every category of failure the product must distinguish is represented and adjudicated, so metrics and gates measure reality, not anecdotes.
- As a `test_maintainer`, I can adjudicate a corpus case exactly once; corrections go through supersede, never silent edits, so the metric denominator is stable and auditable.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A corpus coverage query returns a count for every one of the seven `category` values; the pilot corpus must reach ≥ 5 adjudicated cases per category before 08.8.3's V2 gate reads it |
| AC2 | All seven named rejection fixtures exist as `evaluation_case` rows (`fixture_name` ∈ `reject-pay-button-save-order`, `reject-assertion-weakened`, `reject-skip-injected`, `reject-force-click`, `reject-stale-context`, `reject-duplicate-name`, `reject-cross-tenant-record`) with `expected_label = 'reject'` and an `expected_reason_code` matching the 08.4.1-T2 detector taxonomy |
| AC3 | `split` is assigned once at adjudication by rule (`time`: created_at cut-off declared on the corpus row; `project`: named holdout project ids on the corpus row) and is never reassigned; an invariant test asserts no `incident_id` appears in `split = 'retrieval'` and `split = 'holdout'` rows at the same time |
| AC4 | `AdjudicateEvaluationCaseCommand` rejects with `403 adjudicator_conflict` when the adjudicator equals the member who created the incident's current human label **or** the member who approved the underlying candidate (T100: adjudicator ≠ author ≠ approver, extending T35); the same rule is enforced by a CHECK on the adjudication row, so a conflict can never persist |
| AC5 | After adjudication the case row is immutable to direct update; a second `adjudicate` returns `409 evaluation_case_final`; corrections use `SupersedeEvaluationCaseCommand` which inserts a new row and sets `superseded_by` |
| AC6 | `POST /v1/projects/{p}/healing/evaluation-cases` with an `incident_id` or `fixture_name` already present as a non-superseded row returns `409 evaluation_case_exists` |
| AC7 | Every mutation endpoint requires `Idempotency-Key` (00 §9.1); cross-tenant ids return `404` |

## 3. Contracts touched
- 00 §8.7: only `label_source = 'human'` incident labels may seed a corpus case — a `rule` or `model` label is a hypothesis and is rejected by `CreateEvaluationCaseCommand` (`422 label_not_human`). This is the ground-truth rule applied to corpus admission.
- 00 §5.4.6 / T3: `evaluation_corpus` and `evaluation_case` are business tables — `org_id`, composite FKs, `unique (org_id, id)`, RLS via `evidgate.current_org_id()` (T2).
- Resolved (T65): corpus adjudication and metric reports reuse `healing:approve` — no `healing:evaluate` string is added. This plan uses `healing:approve` (`test_maintainer`) for `CreateEvaluationCase`, `AdjudicateEvaluationCase`, `SupersedeEvaluationCase`, and `healing:triage` (`qa_engineer`) for reads, matching the ruling.
- Resolved (T65 / RECOMMENDATIONS Q-08-2): the first real locator-break corpus is Evidgate's own CI, then the pilot; the schema supports either via `project_id` + `source`.

## 5. API shapes (commands, queries, endpoints)

| Command | Endpoint | Permission | Notes |
|---|---|---|---|
| `CreateEvaluationCorpusCommand` | `POST /v1/projects/{p}/healing/evaluation-corpora` | `healing:configure` | `Idempotency-Key` required; 201 `{ id }` |
| `CreateEvaluationCaseCommand` | `POST /v1/projects/{p}/healing/evaluation-cases` | `healing:approve` [OPEN §3] | `Idempotency-Key`; 201 `{ id }`; `422 label_not_human` when the source incident's current label is not human; `409 evaluation_case_exists` on the dedupe uniques |
| `AdjudicateEvaluationCaseCommand(CaseId, ExpectedLabel, ExpectedReasonCode?, Split)` | `POST /v1/healing/evaluation-cases/{c}/adjudicate` | `healing:approve` [OPEN §3] | `Idempotency-Key`; 200 `{ id, split }`; `403 adjudicator_conflict` (AC4, T100); `409 evaluation_case_final` (AC5); `422 split_rule_violation` when the requested split contradicts the corpus rule |
| `SupersedeEvaluationCaseCommand(CaseId, Patch)` | `POST /v1/healing/evaluation-cases/{c}/supersede` | `healing:approve` [OPEN §3] | `Idempotency-Key`; 201 `{ id }` (new row); sets `superseded_by` on the old row in the same tx |

| Query | Endpoint | Permission | Notes |
|---|---|---|---|
| `ListEvaluationCasesQuery` | `GET /v1/projects/{p}/healing/evaluation-cases?corpus_id=&category=&split=&cursor=` | `healing:triage` | Dapper; keyset cursor `(created_at, id)`; served by `ix_evaluation_case_corpus_category` |

Errors: `404` unknown/cross-tenant ids · `400 validation_failed` missing `Idempotency-Key` · `409` / `422` codes as listed per command (envelope 00 §9.2).

## 6. States and transitions

New local state (not in 00 §8; documented here as the contract for this entity): `evaluation_case`: `pending_adjudication → adjudicated → superseded` where `superseded` is terminal and reached only via the supersede command. A `pending_adjudication` row does not count in coverage or metric denominators. This extension is additive to 00 §8 and does not alter any existing machine.

## 7. Jobs and integrations

- No scheduled job: corpus construction is explicit curation, not automated harvest (auto-harvesting production incidents into `holdout` would break the adjudication-before-use invariant).
- Downstream consumers: 08.8.2-T1 reads adjudicated rows for metric denominators; 08.8.3-T1 reads `expected_label = 'reject'` rows for the V2-gate forbidden-case check; 08.9.1-T1 restricts its reuse matcher to incidents whose `evaluation_case` row (if any) is `split = 'retrieval'` or absent — a holdout incident must never trigger a stored mapping (leakage guard, wired in 08.9.1).
- Validator integration: each `fixture_name` row maps to a `packages/healing-validator` Vitest fixture and a 08.4.3 seeded broken state; T2 wires the ids, not the fixtures themselves.
