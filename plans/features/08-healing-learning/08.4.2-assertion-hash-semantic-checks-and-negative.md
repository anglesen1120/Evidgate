## 1. Goal and non-goals

**Goal.** Prove a mechanics-only patch keeps test **intent**: compute the assertion hash before and after, require equality (necessary, never sufficient), then run semantic checks — role/name/test-id identity, unique match, business region, independent post-condition — and a negative control: a seeded broken state must still fail.

**Non-goals.** The AST allowlist itself (08.4.1); executing the replay (08.4.3 supplies the runner; this story defines the checks + control fixture); the full evaluation corpus and phase gates (08.8.x).

## 2. User stories and acceptance criteria

- As the healing pipeline, I reject a candidate that passes the AST allowlist but points at a different business object, so a product bug is never hidden by a passing test.
- As a reviewer, every `candidate_validation` row shows per-check evidence (hashes, check outcomes), so a `validated` verdict is auditable.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `assertion_hash` is computed over the normalised assertion subtree (kind, callee, expected-value literals, matcher chain — whitespace/formatting ignored) and stored in `assertion_hash_before`/`_after`; a patch altering any assertion node → `rejected` with `assertion_hash_mismatch`, even if the AST allowlist passed |
| AC2 | Equal hash + changed business object (fixture `reject-pay-button-save-order`) → `rejected` `business_region_changed` |
| AC3 | Two elements with the same accessible name → unique-match check fails → `rejected` `non_unique_match` (incident returns to triage) |
| AC4 | Weak/trivially-true assertion (`expect(true)` or equivalent) with equal hash → `rejected` `post_condition_missing` — hash equality is necessary, not sufficient |
| AC5 | Negative control: the candidate applied to a seeded broken state still fails → passes control; if the patched test passes on broken state → `rejected` `negative_control_passed` |
| AC6 | All check verdicts are recorded in `candidate_validation.checks` jsonb with `reason_code` from `contracts/healing/validation-reasons.json` (one vocabulary with 08.4.1) |

## 4. Data model and migrations

- `candidate_validation` (owned by 08.4.1's `migrations/NNNN_candidate_validation.sql`): this story first writes `assertion_hash_before`, `assertion_hash_after` (`text`, SHA-256 hex of the RFC 8785 canonical assertion document) and `checks` jsonb rows for the four semantic checks + negative control.
- `assertion_snapshot` (new, `migrations/NNNN_assertion_snapshot.sql`): `org_id`, `id`, `unique (org_id, id)`, `candidate_id` composite FK, `side check (side in ('before','after'))`, `canonical_doc text`, `hash text`; stores the exact canonical input that produced each hash so a reviewer can diff it. RLS via `evidgate.current_org_id()`, append-only.
- Index `candidate_validation (org_id, candidate_id, round_no)` (already §4.1) serves the validation read used by 09.5.1.

## 5. API shapes (commands, queries, endpoints)

- No new `/v1` endpoint (read of validation detail rides on `GET /v1/healing/candidates/{c}`, 08.3.x).
- Internal shapes:

| Shape | Detail |
|---|---|
| Command `RunSemanticValidation` (`ICommand<ValidationOutcome>`) | Worker command after 08.4.1's AST verdict = `accept`: computes both hashes via `IAssertionHasher`, runs the four semantic checks via `ISemanticCheckRunner` (executed against the DOM/a11y artifacts inside the replay harness interface supplied by 08.4.3), writes `assertion_snapshot` rows + updates `candidate_validation.checks`, transitions candidate `rejected` with `reason_code` or continues to negative control |
| `IAssertionHasher` | Pure function: Playwright-TS AST (from healing-validator) → assertion subtree → canonical doc (RFC 8785) → SHA-256. Deterministic across runs/locales (00 §5.7 P7 — no culture-dependent normalisation) |
| `ISemanticCheckRunner` | Pure functions over `(baseline_a11y_tree, candidate_locator, patched_source)`: `identity_check`, `unique_match_check`, `business_region_check`, `post_condition_check`; each returns `{name, verdict, reason_code, evidence}` |
| `INegativeControlRunner` | Applies the candidate patch against the seeded broken fixture build (08.4.3 runner interface): patched test must **fail** on the broken state and **pass** on the baseline state |

## 6. States and transitions

- Feeds existing candidate exits (00 §8.7): any check `reject` → `rejected` + `reason_code`; negative control inconclusive (broken state unreachable) → `insufficient_evidence` `negative_control_error`. No new states.

## 7. Jobs and integrations

- Runs inside the same outbox/`task`-queue step as AST validation (natural key `(candidate_id, round_no)`); semantic checks needing the app under test are executed via 08.4.3's sandbox runner interface — this story defines the check contract, 08.4.3 provides execution.
- `assertion_snapshot` feeds the 09.5.1 reviewer diff view.
- Named fixtures: `reject-pay-button-save-order` (area §5 row 1 / §7) is seeded here and reused by 08.8.1-T2 corpus.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Rule 2/4 (area) | Hash equality enforced AND semantic checks run — hash alone can never validate a candidate | AC1, AC4 |
| P7 determinism | Hash input is canonicalised; no `CultureInfo`-dependent formatting; `InvariantGlobalization` on | `hash_stable_across_locales` unit test |
| S5 untrusted input | DOM/a11y artifacts are `sensitive` (T57), fetched read-only, size-capped; a11y tree parsed with depth/entry caps | Parser-fuzz fixture test |
| P3/P4 | `RunSemanticValidation` ≤ 4 SQL statements (candidate, artifacts meta, insert snapshots, update validation); artifact bytes fetched by id (no N+1) | Command-counter assertion |
| P5 | Check execution (sandbox runner call) happens outside the write transaction | Pipeline-order test |
| C1/C7 | One command writes snapshots + checks + outbox `healing.candidate_changed` in one tx; reads are `IQuery` Dapper elsewhere | Architecture + integration test |
| 00 §5.4 RLS | `assertion_snapshot` is `org_id` scoped, composite FK, `FORCE ROW LEVEL SECURITY` | Cross-tenant isolation test |
| Privacy | Canonical docs contain assertion text only — no input values/credentials (already masked at capture, 08.1.2-T2) | Redaction passthrough test |
