## 1. Goal and non-goals

**Goal.** A triager can attach one link to the team's own tracker (Jira, Linear, GitHub issue, any https page) to an incident, so a triage result is traceable there. The link is plain data: `https` only, length-capped, edited by an audited PATCH, shown in the failure detail and carried in the incident webhook payload. The server never fetches, resolves, previews or unfurls it.

**Non-goals.** Any tracker connector, issue creation, status sync or two-way link (not before V3, 00 §1.3); link validation by calling the tracker; multiple links per incident (one in V1, `[INFERENCE]`); link on candidates or evaluations; auto-detecting the tracker kind.

## 2. User stories and acceptance criteria

- As a QA engineer, I paste the Jira ticket URL on the incident I triaged so the team can jump from Evidgate to the ticket and back.
- As an integrator, the incident webhook payload carries the link so my tracker automation can correlate.
- As a security reviewer, I know Evidgate never contacts that URL.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `PATCH /v1/incidents/{i}` with `{external_issue_url}` (`healing:triage`, `If-Match`) sets the link; `null` clears it; the response returns the incident with the new value and ETag |
| AC2 | Validation: scheme must be `https` (case-insensitive scheme, other schemes such as `http`, `javascript`, `data`, `file`, `ftp` refused); length ≤ 2048; must parse as an absolute URL with a host; no userinfo (`user:pass@`); no control characters or whitespace; violation returns 422 `invalid_external_url` with the failing rule name |
| AC3 | The URL is stored normalized only for scheme/host case (`[INFERENCE]`); the path, query and fragment are stored verbatim; no resolution, no redirect following, no DNS lookup, no outbound call of any kind occurs on set, read or webhook delivery |
| AC4 | An unchanged value is a no-op (200, no audit row, no new version); a change writes one audit row with before/after hashes of the URL (not the URL itself in the hash input log) via 02.7.1 in the same transaction |
| AC5 | Only members with `healing:triage` on the incident's project may set or clear; `viewer` gets 403; another tenant's incident gets 404; a stale `If-Match` gets 412 |
| AC6 | The link may be set on an incident in any state including `closed` (`[INFERENCE]`, traceability after close); runs with `purpose = replay` never have incidents (T67), so nothing to set |
| AC7 | The failure detail response (`GET /v1/incidents/{i}`) and list contract include `external_issue_url` (nullable); the UI shows it as a plain `<a rel="noopener noreferrer nofollow" target="_blank">` with the host visible, never auto-opened or previewed |
| AC8 | The incident webhook payload (07.6.2 delivery) carries `external_issue_url` when set; a payload for a cleared link carries `null`; the webhook schema in `contracts/` is updated additively |
| AC9 | The field is rendered as text everywhere (untrusted input, S5/XSS): CSP unchanged, no `href` binding for non-https values, snapshot test with hostile strings |

## 4. Data model and migrations

`incident` (08.1.1-T1) gains `external_issue_url text null` with `check (external_issue_url is null or (external_issue_url ~ '^https://' and char_length(external_issue_url) <= 2048))`. The check mirrors, but does not replace, application validation (defence in depth). No index (never queried by value in V1). Existing RLS, `unique (org_id, id)`, version and `updated_at` trigger apply unchanged. Migration: `migrations/NNNN_incident_external_issue_url.sql` (additive, nullable, no backfill).

## 6. States and transitions

None added. The field is a plain attribute, independent of the incident state machine (§8.7, `open → triaged(label) → closed`) and of `label_source` precedence; setting it never changes the label or enables any automation.

## 7. Jobs and integrations

- No job. The webhook payload is built from the incident row by the 07.6.2 delivery path at event time; nothing in this story performs HTTP.
- UI: 09.4.1-T3 failure detail gets an edit control (T2.2); strings in vi + en.
- Architecture guard: a test asserts no `HttpClient` usage in the `Healing` module's incident handlers (the URL is never fetched).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Never fetched (00 §5.7 S4) | no outbound call on set/read/deliver; the only HTTP in the module is allow-listed elsewhere | `ExternalUrl_NoOutboundCall` (fake handler fails on any request), architecture test |
| https only | validator + DB check | `Patch_NonHttpsSchemes_422`, `Db_CheckRejectsHttp` |
| No credentials in URL | userinfo refused; query verbatim but length-capped | `Patch_Userinfo_422` |
| XSS / injection (S5) | rendered as text, `href` only for validated https, `rel` hardened | `ExternalUrl_HostileStrings_RenderedInert` (UI snapshot) |
| 00 §5.5 C2/C3 | `healing:triage` attribute, one tenant transaction, audit in same transaction | pipeline test + `Patch_ChangeWritesOneAuditRow` |
| 00 §5.7 P1 | one UPDATE with `If-Match` version; no extra query | command-counter assertion |
| Privacy | the URL may contain a ticket id or internal host name; treated as tenant data, not logged at info level (log-allowlist), webhook delivery goes only to the org's own endpoints (07.6.3) | log-allowlist test |

Authorization: `healing:triage` to set or clear the link; reading follows the incident read permission; another tenant's incident is 404.
Retention/deletion: the value is part of the incident row and lives and dies with the incident (08.1.1-T1 retention, project/org delete); clearing sets `null`; audit rows keep hashes only.
Telemetry: audit row `incident.external_issue_url.set` (actor, before/after hash, `request_id`); counter `incident_external_issue_url_set_total{outcome}`; no URL in labels or logs.
Failure path: a bad URL gives 422 `invalid_external_url` with the rule name; a stale ETag gives 412 and the UI reloads; no tracker outage can affect this story because nothing is fetched.
