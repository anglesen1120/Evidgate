## 1. Goal and non-goals

**Goal.** A triaged `test_drift` incident with usable context can produce at most 3 `healing_candidate` rows via deterministic locator-substitution rules, each bound to a canonical `candidate_hash` (`base_commit` + context + patch), an expiry, and the retrieval evidence that motivated it — all inside the tenant scope, all shadow (nothing touches a repository).

**Non-goals.** The validation loop and quota mechanics — 08.3.2 (this story defines the `IHealingQuota` contract with a permit-all default implementation so mint has no forward dependency on 08.3.2; 08.3.2-T2.1 replaces the default with the real atomic implementation behind the same interface, T32); AST validation, semantic checks, replay — 08.4.x; LLM/healer generators — 08.5.x (V2); the review queue UI — 09.5.1; approval/apply and the kill-switch degradation path/drill — 08.6.1/08.6.2/08.6.3-T2/T3 (V2) — this story consumes only the switch **resolver** shipped by 08.6.3-T1 (moved to V1/M3, TL decision 2026-09-25).

## 2. User stories and acceptance criteria

- As a test maintainer, a drifted locator incident can yield a small, reviewable set of candidate patches with their hashes, so I can see *what would be tried* before any apply exists.
- As the Tech Lead, I know candidates are bounded (≤ 3 live), hash-identified, expiring and produced only from `ready` context with a non-`unknown` label.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Generation mints at most 3 live (`proposed`, `validated`) candidates per incident; a fourth mint attempt returns without writing (`healing_candidate` partial unique on live states enforces it) |
| AC2 | `candidate_hash` = `sha256:` over the RFC 8785-canonical `{patch, base_commit, context_hash, rule_version}`; identical input → identical hash; any byte change → different hash |
| AC3 | A candidate is minted only when the automation gate passes: context artifacts `ready` (T31 via 08.1.2-T5.2), label `test_drift` non-`unknown` (08.2.2-T3.1), and the healing switch (08.6.3-T1, `IHealingSwitchResolver`, resolved system → tenant → project, most restrictive wins, T33) resolves to `enabled` or `shadow` for the incident's project — `disabled` or `unavailable` blocks the mint before any DB write |
| AC4 | The patch is stored as an artifact of kind `patch` (T20) through the Evidence write contract; `healing_candidate.patch_artifact_id` references it; `context_hash` equals the incident's `content_hash` |
| AC5 | Rule strategies cover the four V1 kinds — `role`, `label`, `test_id`, `text` — each producing a locator-substitution patch from the incident's `old_locator` + retrieval results; a strategy with no plausible substitute contributes no candidate |
| AC6 | Every mint emits `healing.candidate_changed` outbox rows and an audit row; `GET /v1/healing/candidates/{c}` returns the candidate with `candidate_hash`, `base_commit`, `expires_at`, `state`, `strategy`, `rule_version` and the retrieval record ids used |
| AC7 | Generation re-delivery (task retry) is idempotent: no duplicate candidate for the same `(incident_id, candidate_hash)` |
| AC8 | `GET /v1/projects/{p}/healing/candidates` lists with keyset pagination and `state` filter; other-tenant candidate id → 404 |
| AC9 | When the switch resolves `disabled` (or `unavailable`) for the tenant/project, generation writes zero `healing_candidate` rows and makes no retrieval call and no patch-artifact write; a switch flip to `disabled` observed before the mint transaction opens aborts the task with reason `healing_disabled`, never a partial candidate |

## 4. Data model and migrations

`migrations/NNNN_healing_candidate.sql`:

- `healing_candidate`: `id`, `org_id`, `incident_id`, `project_id` (denormalised for list filtering + quota joins), `candidate_hash text not null`, `base_commit text not null`, `context_hash text not null`, `strategy text not null` (`role`, `label`, `test_id`, `text`, later `llm`, `healer`), `patch_artifact_id uuid`, `retrieval_refs jsonb` (incident ids that motivated the patch), `requested_by uuid`, `edited_by uuid`, `state text not null default 'proposed' check (state in ('proposed','validated','approved','applied','rejected','insufficient_evidence','expired','revoked'))`, `expires_at timestamptz not null`, `rule_version text`, `model_version text`, `prompt_version text`, `created_at`, `updated_at`, `version int`.
- Constraints: `unique (org_id, id)` (T3); `unique (org_id, incident_id, candidate_hash)` (idempotent mint, AC7); **partial unique** `unique (org_id, incident_id) include (…) where state in ('proposed','validated')` is not expressible for a *cap of 3* — the cap is enforced by a `CHECK`-free approach: mint handler counts live rows inside the transaction (`SELECT … FOR UPDATE` on the incident row) and refuses at 3 (AC1; documented because a unique index cannot express "≤ 3") [INFERENCE: standard approach for bounded-cardinality children].
- Composite FKs `(org_id, incident_id)` → `incident`, `(org_id, patch_artifact_id)` → `artifact`, `(org_id, project_id)` → `project`.
- Indexes: `(org_id, project_id, created_at desc, id)` for the list endpoint; `(org_id, incident_id, state)` for live-cap counting; `(org_id, expires_at) where state in ('proposed','validated')` partial for the expiry sweep (08.3.2-T2).
- RLS `org_id = evidgate.current_org_id()`, `FORCE ROW LEVEL SECURITY` (T2); audit on every state transition (T8).

|---|---|---|---|---|

| `ListCandidates` | `IQuery<Page<CandidateListItem>>` | `GET /v1/projects/{p}/healing/candidates?cursor=&state=` | `healing:triage` | 200 · 403 |

- `GenerateCandidates` handler (single tenant tx): switch-resolver check (AC9, `08.6.3-T1`, before `BEGIN`) → gate check (AC3: context ready + label) → live-count `FOR UPDATE` on the incident row → quota consume via `IHealingQuota` (T32; this story defines the interface with a permit-all default in 08.3.1-T1.5, so mint order has no cycle — 08.3.2-T2.1 swaps in the real atomic `UPDATE … RETURNING` implementation without touching this handler) → rule strategies → patch artifact write → candidate insert → outbox + audit → commit. No network call inside the transaction (P5): patch bytes are computed before `BEGIN`.
- `expires_at` = `created_at + EVIDGATE_HEALING_CANDIDATE_TTL` (default 72 h [INFERENCE: plan names no value; config-defaults to runbook]).

## 6. States and transitions

- `healing_candidate.state`: `proposed` on mint. `proposed → validated` is written by 08.3.2/08.4.x; exits `rejected`, `insufficient_evidence`, `expired`, `revoked` per 00 §8.7. `approved`/`applied` have no writer until V2 (08.6.x) — the enum admits them, no transition reaches them.
- Any change to patch content is a *new* candidate row (new `candidate_hash`), never an update — immutability enforced by trigger on hash-bearing columns (C6).

## 7. Jobs and integrations

- `generate_candidates` task: idempotency key `(org_id, incident_id, generation_no)`; fired by `incident.labeled` and re-firable after context settle (T31: a `partial` context that later gains `ready` artifacts re-triggers; generation re-gates).
- Evidence module write contract stores the patch artifact (kind `patch`); retrieval contract (08.2.1) supplies `retrieval_refs`.
- No repository, GitHub, LLM or object-storage egress happens in this story (V1 shadow, FR-08-9).
- Switch resolution: `IHealingSwitchResolver.Resolve(orgId, projectId)` (08.6.3-T1) is called once per generation attempt, outside any DB transaction; its result gates the mint (AC3, AC9).
