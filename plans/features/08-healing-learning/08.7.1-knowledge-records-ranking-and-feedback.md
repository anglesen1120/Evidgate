## 1. Goal and non-goals

**Goal.** Every candidate that reaches `applied` writes exactly one tenant/project-scoped `knowledge_record`; feedback on a candidate is captured as append-only `healing_feedback` rows with labels `accepted | rejected | reverted | unknown`, where a single passing (canary-green) run never by itself creates a ground-truth label; the retrieval ranker (08.2) may weight its ordering by these records and their feedback but never authorises generation, validation or approval.

**Non-goals.** Lineage fields (rule/model/prompt version, retrieved-record ids, patch hash, validation run ids) and the revocation cascade across dependent candidates — that is 08.7.2, which this story's write path feeds. The retrieval query itself and its tenant filter (08.2.1, dependency only). The canary/rollback mechanics that produce the `reverted` signal (08.6.2, dependency only, this story only consumes its outcome).

## 2. User stories and acceptance criteria

- As a test maintainer, once I approve and merge a heal, Evidgate remembers it as one record I (or the ranker) can find again for a similar future break — never duplicated, never silently multiplied.
- As the Tech Lead, I can prove feedback labelling is honest: a canary that merely passes is reported `unknown`, not `accepted`; only an explicit human/process signal (merge stays green past the canary window, explicit accept, or a rollback) produces `accepted`/`rejected`/`reverted`.
- As a ranker maintainer, I can weight retrieval order by feedback history without that weighting ever bypassing validation, approval or the kill switch.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | When `healing_candidate.state → applied` (08.6.1/08.6.2 path), exactly one `knowledge_record` row is written in the same logical operation (idempotent on the candidate's natural key: a retried `applied` transition never creates a second record) |
| AC2 | A canary-green outcome alone (`canary_passed` event) writes `healing_feedback(label = unknown)`, never `accepted`; explicit acceptance signals — no rollback within the configured observation window, or an explicit maintainer accept action — write `label = accepted` |
| AC3 | A rollback (08.6.2 revoke, either canary-triggered or manual) writes `healing_feedback(label = reverted)` and `label = rejected` is reserved for a maintainer-driven reject that happens before merge (08.6.1 `reject` endpoint) — both are append-only, never overwritten |
| AC4 | The ranker (08.2.1-T3) reads `knowledge_record` + `healing_feedback` to compute a weight that only reorders retrieval candidates; a query that stubs the ranker to return the *opposite* order still lets an equally-scored non-ranked candidate through generation — proving the ranker never gates |
| AC5 | Every `knowledge_record` and `healing_feedback` row is `org_id`/`project_id`-scoped with RLS; a cross-tenant read returns zero rows even for records with an identical `fingerprint`/`old_locator` |

## 3. Contracts touched

- 08 area plan §4.1 `knowledge_record`, `healing_feedback` — implemented as specified; `knowledge_record.source_candidate_id` gains `unique (org_id, source_candidate_id)` to enforce AC1's one-record invariant.

## 4. Data model and migrations

`migrations/NNNN_healing_knowledge_feedback.sql`:

| Table | Columns / constraints |
|---|---|
| `knowledge_record` | (per 08 §4.1) `org_id`, `project_id`, `engine`, `test_revision_id`, `fingerprint`, `old_locator`, `new_locator`, `context_hash`, `label`, `label_source`, `state (active\|revoked)`, `source_candidate_id`; `unique (org_id, id)`; **`unique (org_id, source_candidate_id)`** (AC1 — one record per candidate, enforced at the DB, not just app logic); composite FK `(org_id, project_id)` → `project (org_id, id)`; composite FK `(org_id, source_candidate_id)` → `healing_candidate (org_id, id)`; RLS via `evidgate.current_org_id()` |
| `healing_feedback` | (per 08 §4.1) `org_id`, `candidate_id`, `label (accepted\|rejected\|reverted\|unknown)`, `at`, `by`; append-only (`REVOKE UPDATE, DELETE` from app role); composite FK `(org_id, candidate_id)` → `healing_candidate (org_id, id)`; RLS |
| `healing_feedback_window` (new) | `org_id`, `candidate_id`, `observe_until timestamptz`; one row per applied candidate, created alongside the `knowledge_record`; consumed by the `healing.feedback_settle` task to decide `accepted` after the window closes with no `reverted` row |

Indexes: `knowledge_record (org_id, project_id, fingerprint, state)` — serves 08.2.1 retrieval; `healing_feedback (org_id, candidate_id, at)` — serves the feedback timeline and 08.7.2's lineage query; `healing_feedback_window (observe_until)` — serves the settle-task scan (bounded, indexed range read, P4).

## 5. API shapes (commands, queries, endpoints)

| Operation | Type | Caller | Result |
|---|---|---|---|
| `WriteKnowledgeRecord` | `ICommand<KnowledgeRecordResult>` | outbox consumer on `healing.candidate_changed` (`applied` transition) | inserts `knowledge_record` + `healing_feedback_window`; `ON CONFLICT (org_id, source_candidate_id) DO NOTHING` makes retries a no-op (AC1) |
| `RecordFeedback` | `ICommand<FeedbackResult>` | outbox consumers on `canary_passed` (`unknown`), `healing.rollback` (`reverted`), 08.6.1 reject (`rejected`), settle task (`accepted`) | append-only insert; never updates a prior row |
| `SettleFeedbackWindow` | `ICommand` | `healing.feedback_settle` Cronos task | for each expired `observe_until` with no `reverted` row yet, inserts `accepted` |
| `RankByKnowledge` | `IQuery<RankedRecordSet>` (`.Contracts` interface consumed by 08.2.1) | 08.2.1 ranker | tenant/project-filtered `knowledge_record` + latest `healing_feedback` per candidate, weighted; read-only, never authorises (C1: a query never writes) |

All writes happen inside the tenant transaction opened by the pipeline (C2/C3); no network call inside any of these transactions (P5) — they are pure DB operations reacting to already-computed events.

## 6. States and transitions

`knowledge_record`: `active → revoked` (revocation itself owned by 08.7.2 — out of scope here beyond the column existing). `healing_feedback.label`: append-only sequence per candidate, no state machine — the *latest* row is the effective label, read by 08.7.2/08.8.2, but every row is retained (audit trail, rule-of-three denominator in 08.8). `healing_feedback_window`: implicit — created once, consumed once by the settle task, no update (row can be left as a completed marker or deleted by the same task; this plan keeps it for traceability, matching NFR-08-4 append-then-final read pattern rather than mutate-in-place).

## 7. Jobs and integrations

- Outbox consumers wired to `healing.candidate_changed`: `applied` → `WriteKnowledgeRecord`; `canary_passed` → `RecordFeedback(unknown)`; `healing.rollback` completion → `RecordFeedback(reverted)`.
- `healing.feedback_settle` Cronos schedule (unique `(schedule_name, fire_at)`, 00 §5.3): scans `healing_feedback_window` for `observe_until < now()` with no later `reverted` feedback row, writes `accepted`.
- Consumed by: 08.2.1-T3 ranker (read-only), 08.7.2-T1 lineage (reads `knowledge_record.source_candidate_id`), 08.8.2 metrics pipeline (adjudicated denominator draws on `healing_feedback` labels, excluding `unknown` per rule 8), 06.4.4 (dashboard/reporting consumer of knowledge/feedback rows).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| One record per applied candidate | `WriteKnowledgeRecordTests` (Testcontainers): redelivered `applied` event → still one row (`ON CONFLICT`) |
| Canary-green ≠ accepted | `FeedbackLabelTests`: `canary_passed` → `unknown`; window closes clean → `accepted` written by the settle task |
| Rollback labelling | `RevertedFeedbackTests`: canary regression and manual revoke both → `reverted`; pre-merge reject → `rejected` |
| Append-only integrity | attempt to `UPDATE`/`DELETE` a `healing_feedback` row as the app role fails (`REVOKE` enforced) |
| Ranker never authorises | `RankerNeverGatesTests`: ranker stubbed to invert order; generation still proceeds through validation/approval unaffected — ranking only changes retrieval order, not eligibility |
| Cross-tenant isolation | RLS test: identical `fingerprint` in two orgs never cross-visible via `RankByKnowledge` |
| Settle-task scan bound | `EXPLAIN` plan assertion: settle query uses the `observe_until` index, not a sequential scan |

## 11. Rollout

- No feature flag: this story only reacts to events already gated by the kill switch (08.6.3) and the apply flag (08.6.1) — if healing never applies, no knowledge records are ever written, so the story is inert until upstream is live.
- Monitoring: knowledge-record write rate vs `applied` transitions (should track 1:1, AC1), feedback-label distribution (a spike in `unknown` past the observation window signals a settle-task problem).
- Rollback: no data mutation to undo — knowledge/feedback rows are additive and append-only; disabling the outbox consumers stops new writes without touching history.
