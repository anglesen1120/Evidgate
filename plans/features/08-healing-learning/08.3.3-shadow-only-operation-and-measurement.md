## 1. Goal and non-goals

**Goal.** V1 healing runs and measures itself **without ever touching a repository or an official decision**: the switch resolution can only produce `shadow` (V1), shadow verdicts are stored on the incident/candidate — never on `evaluation` — and per-project candidate quality and triage time are reported.

**Non-goals.** The apply path (PR/approve/canary: 08.6.x, V2); the LLM gateway (08.5.1, V2); the shadow review UI (09.5.1, reads the query this story exposes); metric aggregation internals (12.5.1, consumed); evaluation write path itself (07.2.x).

## 2. User stories and acceptance criteria

- As a Tech Lead, I can prove no V1 code path writes to a customer repository, so the pilot can run healing with zero blast radius.
- As a project manager, I can see per-project shadow quality (validated / rejected / insufficient_evidence) and triage time, so I can judge whether healing helps before any apply capability exists.
- As the platform, shadow results never change the run's official `evaluation` row or release decision.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `Architecture.Tests` pass asserting (a) `Evidgate.Modules.Healing` does not reference `Evidgate.Modules.Catalog` Git/PR integration interfaces and (b) no Healing command handler accepts a repository/patch target — attempted repo-write calls cannot compile |
| AC2 | Each `shadow_validation_verdict` row stores `resolved_mode` (`shadow`/`disabled`/`unavailable`), read directly via 08.6.3-T1's `IHealingSwitchResolver.Resolve` (08.3.1:70 pattern) at write time; shadow-quality metrics (08.3.3-T3) exclude `disabled` and `unavailable` rows from validated/rejected counts |
| AC3 | A completed shadow replay writes one `candidate_validation` row + shadow verdict on the incident; the run's `evaluation` table has no row with `mode = 'live'` touched and the decision endpoint output is byte-identical with and without the shadow result |

## 4. Data model and migrations

All tables from `plans/08-healing-learning.md` §4.1; this story adds/changes:

- `healing_switch` — owned by 08.6.3-T1 (T33 extension, V1/M3); not written here. This story only depends on its exported `IHealingSwitchResolver`.
- `shadow_validation_verdict` (new, `migrations/NNNN_shadow_validation_verdict.sql`): `org_id uuid not null`, `id uuid`, `unique (org_id, id)`, `project_id uuid not null` composite FK `(org_id, project_id)` → `project`, `incident_id uuid` FK `(org_id, incident_id)` → `incident`, `candidate_id uuid` FK `(org_id, candidate_id)` → `healing_candidate`, `candidate_validation_id uuid` FK `(org_id, candidate_validation_id)` → `candidate_validation`, `verdict text check (verdict in ('pass','fail','insufficient_evidence'))`, `resolved_mode text check (resolved_mode in ('shadow','disabled','unavailable'))` (read via `IHealingSwitchResolver.Resolve` at write time; `disabled`/`unavailable` rows are excluded from validated/rejected counts), `reason_code text`, `assertion_hash_before`, `assertion_hash_after`, `created_at`. Index `(org_id, project_id, verdict, created_at)` serving AC4 filters. RLS policy via `evidgate.current_org_id()`.
- Indexes for the metrics query: `incident_label (org_id, incident_id, created_at)` already from 08.2.2; add `incident (org_id, project_id, created_at)` if absent.

## 5. API shapes (commands, queries, endpoints)

| Shape | Handler / endpoint | Detail |
|---|---|---|
| Command `RecordShadowVerdict` (internal, worker) | no HTTP; Mediator command | Reads `resolved_mode` via a direct `IHealingSwitchResolver.Resolve` call (08.3.1:70 pattern, outside the write transaction, P5); writes `candidate_validation` (from 08.4) + `shadow_validation_verdict` (incl. `resolved_mode`) + candidate state transition + outbox `healing.candidate_changed` (00 §9.5) in one transaction; idempotent by `(org_id, candidate_id, round_no)` natural key |
| Query `GetProjectShadowMetrics` (`IQuery<ShadowMetricsDto>`) | `GET /v1/projects/{p}/healing/shadow-metrics` · `healing:triage` | Dapper; keyset pagination (00 §9.1); window `?from=&to=`; counts over `shadow_validation_verdict` joined to incident, excluding rows where `resolved_mode in ('disabled','unavailable')` from validated/rejected counts; triage time = `incident.created_at → incident_label(created_at, source='human'\|first)`; 404 for other-tenant `{p}` |

## 6. States and transitions

- Switch state machine (00 §8.7) is owned by 08.6.3-T1 (T33 extension): settable `enabled | shadow | disabled`, resolved `enabled | shadow | disabled | unavailable` (most restrictive wins, `unavailable` derived, never stored). That story's V1 clamp guarantees resolution never yields `enabled` before the V2 apply stories ship (T29). This story only consumes the resolved value.
- Shadow result is terminal data (`pass | fail | insufficient_evidence`), not a candidate state change beyond the existing `validated | rejected | insufficient_evidence` exits (00 §8.7) — no new states.

## 7. Jobs and integrations

- `RecordShadowVerdict` (08.3.3-T2.2) calls 08.6.3-T1's `IHealingSwitchResolver.Resolve` directly, once per verdict write, outside the write transaction (P5), and stamps the result as `resolved_mode` — no separate stamping component.
- Outbox `healing.candidate_changed` emitted with each shadow verdict (00 §9.5) → consumed by 09.5.1 review queue and 12.5.1 metric pipeline.
- Metric emission: OpenTelemetry counters `evidgate.healing.candidates_total{org,project,verdict}` + histogram `evidgate.healing.triage_time_ms` feeding 12.5.1.
- No external network integration. Shadow validation tasks claim via `task` queue `SKIP LOCKED`, natural key `(candidate_id, round_no)`.
