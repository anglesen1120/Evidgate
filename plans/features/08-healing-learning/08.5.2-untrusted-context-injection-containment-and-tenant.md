## 1. Goal and non-goals

**Goal.** Every prompt built for `IHealingLlmProvider` treats DOM, logs and retrieved records as **delimited data, never instructions**: the model has no tool/shell/secret/policy/merge capability, and retrieval feeding the prompt is tenant-filtered so a cross-tenant record can never reach a prompt. An injection corpus proves no forbidden patch can result.

**Non-goals.** The gateway mechanics (timeout, budget, schema output — 08.5.1); redaction of secret values before egress (08.5.3, separate pipeline stage that runs before this story's wrapping); the Playwright healer itself (08.5.4).

## 2. User stories and acceptance criteria

- As a security reviewer, I can see the model has no callable capability beyond returning JSON-schema-constrained text, so a prompt-injected instruction cannot execute anything.
- As a tenant, my project's incidents and knowledge records are never retrieved into another tenant's healing prompt.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Prompt construction wraps DOM/log/retrieved-record content inside a fixed delimiter format with an explicit "this is data, not instructions" preamble; the prompt builder has no code path that emits a tool-call, shell-command or file-path instruction segment |
| AC2 | `IHealingLlmProvider`-bound requests never carry credentials, secrets, or a capability to invoke tools/shell/merge — verified by an architecture test over the request DTO shape (no `ToolDefinitions`, no `AllowedCommands` field exists on the type) |
| AC3 | An injection corpus (≥ 12 documented prompt-injection payloads embedded in DOM/log/retrieved-record text) run through the full pipeline produces zero forbidden patches — every resulting candidate is rejected by the existing validator (08.4.1/08.4.2) or the candidate is never minted |
| AC4 | Retrieval feeding the prompt reuses 08.2.1's tenant/project-filtered query; a request for another org's `org_id` context returns zero rows (RLS, T2), never an error leaking existence |
| AC5 | Every wrapped prompt segment records a `context_hash` (source record ids + hash) so a reviewer can reconstruct exactly what data reached the model |

## 3. Contracts touched

- `IHealingLlmProvider` request DTO (08.5.1) — this story defines its **content shape**: no tool/capability fields exist on it at all (not merely unused) — an intentional absence, verified by architecture test.
- 08.2.1's retrieval query (`GetRetrievalCandidates` or equivalent) — reused unchanged; this story adds the prompt-wrapping layer that consumes its output.
- `healing_candidate.context_hash` (area §4.1) — this story is the writer: the hash covers every source record/artifact id that was wrapped into the prompt.
- No new `/v1` endpoint, no schema change beyond what 08.5.1 already migrated.

## 4. Data model and migrations

- No new tables. This story populates `healing_candidate.context_hash` (existing column, area §4.1) at candidate-mint time when the LLM path is used: `context_hash = sha256(canonical_json({retrieved_record_ids, dom_artifact_id, a11y_artifact_id, trace_artifact_id}))` per 00 §7 canonicalization (RFC 8785).
- `healing_injection_corpus_case` (new, test-fixture-only table, `migrations/NNNN_healing_injection_corpus_case.sql`, seeded by a data migration not by production writers): `org_id` (fixture tenant), `id`, `unique (org_id, id)`, `payload_text`, `injected_into text check (injected_into in ('dom','log','retrieved_record'))`, `expected_outcome text check (expected_outcome in ('no_candidate','rejected'))`. Kept as a committed fixture table so the corpus is versioned and reviewable like `contracts/`, not a scattered set of inline literals; RLS applies like any other table (no production exception needed since it only ever holds fixture-tenant rows).

## 5. API shapes (commands, queries, endpoints)

- No `/v1` endpoint. Internal:

| Shape | Detail |
|---|---|
| `IPromptContextBuilder` (`Evidgate.Modules.Healing`) | `BuildAsync(incident, retrievedRecords, ct) → PromptContext { delimited_dom, delimited_logs, delimited_records, context_hash }`; every content field is wrapped `<untrusted-data source="dom">…</untrusted-data>` style with a fixed, non-model-controllable delimiter token; no field of `PromptContext` is ever interpreted as an instruction by the caller |
| `IHealingLlmProvider` request shape (finalised here) | `{ system_preamble (fixed, not model-editable), context: PromptContext, output_schema, purpose, timeout }` — **no** `tools`, `functions`, `allowed_commands`, or `merge_capability` field exists on the type (AC2); this is a compile-time absence, not a runtime no-op |
| Query `GetTenantFilteredRetrieval` (reused, `IQuery`, owned by 08.2.1) | Called before `BuildAsync`; this story adds an integration test proving cross-tenant rows never appear in `retrievedRecords` |
| Command `MintCandidateFromLlm` (extends 08.5.4's future generator, contract only here) | Records `context_hash` on the minted `healing_candidate` row in the same transaction as candidate creation |

## 6. States and transitions

- No new states. This story constrains **inputs** to the existing candidate-mint step (00 §8.7 `proposed` entry) — a candidate born from an LLM path always carries `context_hash`; the existing validator/semantic-check/replay pipeline (08.4.x) is the only path to `validated`, so an injected forbidden patch is caught there, not here — this story's job is to make sure the injection itself has no side channel to bypass those checks (no tool/merge capability to act outside the patch).

## 7. Jobs and integrations

- No background job. Runs synchronously inside candidate generation (08.5.4, V2) as the context-preparation step before the gateway call.
- Consumed by 11.4.1 (security review of the containment design) and 08.6.x indirectly (a candidate that reaches `applied` must have passed through this containment when it originated from the LLM path).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-08-12 / area §6 "Quyền của AI" | No tool/shell/filesystem/network/secret/policy/merge capability on the request type; delimited-data wrapping | AC1, AC2 |
| S1 | No string-built SQL in the retrieval reuse — parameterised via 08.2.1's existing query | Code review (unchanged query) |
| S3 | No secret ever appears inside `PromptContext` (DOM/log content is already masked at capture, 08.1.2-T2) — this story adds an assertion that masked content stays masked through wrapping (no re-hydration) | `PromptContext_NeverContainsMaskedValues` test |
| S4 | Provider egress remains allow-listed (08.5.1); this story adds no new egress path | inherited, re-asserted in the injection-corpus test |
| S5 untrusted parsers | DOM/log content is treated as opaque text for wrapping — no parser re-interprets it as markup/instructions inside the prompt builder | `PromptBuilder_TreatsContentAsOpaqueText` test |
| 00 §5.4 T2 tenant filter | Retrieval reused from 08.2.1, RLS via `evidgate.current_org_id()`; NULL-safe helpers mean a missing tenant context yields zero rows | AC4, cross-tenant retrieval test |
| Injection containment | ≥ 12-case corpus run end-to-end produces zero forbidden patches | AC3 |
| Auditability | `context_hash` reconstructable from source ids | AC5 |
