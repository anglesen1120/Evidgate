## 1. Goal and non-goals

**Goal.** Every candidate's validation is bounded: at most 2 `candidate_validation` rounds, per-project quota consumed atomically at mint (`candidates/day`, `replay minutes/day`, T32), a wall-clock deadline that stops any loop, an expiry sweeper that moves stale `proposed` candidates to `expired`, and explicit `insufficient_evidence` transitions with reason codes when validation cannot prove anything.

**Non-goals.** The validators/replay that *fill* a round — 08.4.1/08.4.2/08.4.3 (this story defines the ledger, caps and transitions they write through); quota values per pilot — 12.x ops config; approval/apply — V2.

## 2. User stories and acceptance criteria

- As the Tech Lead, I know a stuck or flaky candidate stops consuming resources at a recorded limit, with a reason a human can read.
- As a pilot operator, per-project healing spend is hard-capped per day — a bug in generation cannot mint unbounded candidates.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `candidate_validation` is append-only with `round_no ≤ 2` (`check (round_no between 1 and 2)` + unique `(org_id, candidate_id, round_no)`); inserting a third round fails with a check-violation and the handler maps it to `422`-equivalent domain result `validation_round_cap` |
| AC2 | Quota consume is atomic inside the candidate-mint transaction: `UPDATE healing_quota … WHERE used < cap RETURNING` — two concurrent mints at cap mint only `cap` total (T32); zero returned rows → no candidate, reason `quota_exceeded` recorded on the incident's generation log |
| AC3 | `healing_quota` defaults (`candidates_per_day`, `replay_minutes_per_day`, `deadline_minutes`) exist per project; a mint without a quota row creates the row from defaults in the same transaction (no silent unlimited) |
| AC4 | Wall-clock deadline: a validation task exceeding `deadline_minutes` is stopped by the sweeper and the candidate transitions to `insufficient_evidence` with `reason_code = 'deadline_exceeded'` |
| AC5 | Expiry sweeper (Cronos, unique `(schedule_name, fire_at)`): `proposed` candidates past `expires_at` → `expired`, releasing the live-slot count; a validating candidate is not expired mid-round (round in flight holds the slot) |
| AC6 | `insufficient_evidence` transitions carry one of a closed reason set (`baseline_not_reproducible`, `non_comparable_run`, `deadline_exceeded`, `validator_unavailable`, `quota_exceeded`); every transition writes actor=`system`, reason and hashes to audit (NFR-08-4) |
| AC7 | Replay minutes accumulate on the quota row when a `candidate_validation` round closes with a measured duration; the cap refuses new rounds beyond `replay_minutes_per_day` |

## 4. Data model and migrations

`migrations/NNNN_healing_validation_loop.sql`:

- `candidate_validation`: `id`, `org_id`, `candidate_id`, `round_no int not null check (round_no between 1 and 2)`, `sandbox_run_id uuid null` (replay run id when 08.4.3 exists), `app_digest text`, `fixture_hash text`, `env_hash text` (comparability triple, FR-08-9), `assertion_hash_before text`, `assertion_hash_after text`, `checks jsonb`, `verdict text` (`passed` | `failed` | `inconclusive`), `reason_code text`, `started_at`, `finished_at`, `replay_minutes numeric`, `created_at`.
- Constraints: `unique (org_id, id)`; `unique (org_id, candidate_id, round_no)` (AC1); composite FK `(org_id, candidate_id)` → `healing_candidate (org_id, id)`; append-only via `REVOKE UPDATE, DELETE` for the app role (C6 immutability in SQL).
- `healing_quota`: `id`, `org_id`, `project_id`, `candidates_per_day int`, `candidates_used_today int`, `candidates_open int` (live-slot counter released on terminal state — AC5), `replay_minutes_per_day numeric`, `replay_minutes_used_today numeric`, `deadline_minutes int`, `period date` (UTC day), `updated_at`; `unique (org_id, id)`; `unique (org_id, project_id, period)`; composite FK `(org_id, project_id)` → `project`; RLS.
- Indexes: `candidate_validation (org_id, candidate_id)`; `healing_candidate` expiry partial index added by 08.3.1 is consumed by the sweeper.
- RLS `evidgate.current_org_id()` on both (T2); audit rows on every candidate state transition (T8).

## 5. API shapes (commands, queries, endpoints)

No new HTTP endpoints (candidate reads already expose `state`; validation rows surface via `GetCandidate.checks` summary — additive DTO field `validations[]` on `GET /v1/healing/candidates/{c}`).

| Shape | Kind | Trigger | Result |
|---|---|---|---|
| `StartValidationRound` | `ICommand<int>` | 08.4.x validator pipeline / validation task | appends `candidate_validation` round 1 or 2; refuses round 3 |
| `CloseValidationRound` | `ICommand<Unit>` | round verdict arrives | sets verdict/reason/finished_at; accumulates `replay_minutes`; transitions candidate (`validated`, `insufficient_evidence`, `rejected`) |
| `ExpireCandidates` | `ICommand<int>` | Cronos `candidate_expire` | `proposed` past `expires_at` → `expired`, `candidates_open` released |
| `StopOverdueRounds` | `ICommand<int>` | Cronos `candidate_deadline` | rounds past `deadline_minutes` → closed `inconclusive`/`deadline_exceeded`, candidate → `insufficient_evidence` |
| `IHealingQuota` | internal contract | mint (08.3.1) + round start | atomic consume per T32 |

## 6. States and transitions

- `healing_candidate`: `proposed → validated` (round verdict `passed`), `proposed → insufficient_evidence` (closed reason set, AC6), `proposed → expired` (sweeper, AC5), `validated → insufficient_evidence` is not allowed — a second failed round after a pass keeps `validated` state but no `approved` path exists in V1; `rejected`/`revoked` writers come with 08.4.x/08.6.x. Every transition audits (T8).
- `candidate_validation`: insert-only rows; `started_at` set on open, `finished_at` on close — an open round older than `deadline_minutes` is sweepable (AC4).

## 7. Jobs and integrations

- Schedules (00 §5.3, unique `(schedule_name, fire_at)`, `ON CONFLICT DO NOTHING`, no leader): `candidate_expire` every 15 min; `candidate_deadline` every 5 min.
- Consumed by 08.4.x: validators call `StartValidationRound`/`CloseValidationRound`; the replay executor (08.4.3, O10-gated) writes `sandbox_run_id` + comparability triple.
- Quota rows surface to plan 12 usage reporting via the shared ledger interfaces; `healing_quota` itself is tenant data under RLS (NFR-08-3/4).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T32 + FR-08-6, NFR-08-3 | atomic quota UPDATE inside the mint tx; replay-minute accumulation at round close; hard refuse at cap | `quota_atomic_consume` (concurrent mints), `replay_minutes_cap` |
| P5 | consume and ledger writes are DB-only; validator/replay processes run outside DB transactions | transaction-boundary review + `round_tx_is_db_only` |
| P2 | sweeper transitions are one `UPDATE … WHERE … RETURNING` per schedule fire, bounded batch | `sweeps_are_single_statement` |
| P3 | round reads are keyset-bounded; candidate detail adds ≤ 1 extra query for `validations[]` | statement counter in `get_candidate_with_validations` |
| 00 §5.4 rules 1, 3, 6, 7 + T2/T3 | `org_id`, composite FKs, `unique (org_id, id)`, forced RLS on both tables | Isolation.Tests |
| C6 | `candidate_validation` append-only enforced by `REVOKE UPDATE/DELETE` + insert-only domain type | `validation_update_rejected` SQL test |
| T8 | every state transition audits actor/reason/hashes | `transition_audited` |
| S3 | reason codes are enums, never free text carrying data | code review |
