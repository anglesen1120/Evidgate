## 1. Goal and non-goals

**Goal.** Give mobile healing its own, independently-gated go-live: capture `ui_hierarchy` context (T20) with native/webview platform discrimination, a distinct Appium-locator AST allowlist in `packages/healing-validator` (separate from the Playwright web ruleset), and a mobile-specific evaluation corpus + phase gate — all defaulting **off** per project until that gate passes, per FR-08-19.

**Non-goals.** The general web validator/AST allowlist (08.4.1, unchanged); the general V2/V3 gate mechanism (08.8.3, extended here only by adding a `mobile_v3` gate value); the Appium adapter/reporter itself (owned by 04.5.1 — this story only consumes its artifact output); iOS/Android device-farm execution (out of program scope, 00 §1.3).

## 2. User stories and acceptance criteria

- As a `qa_engineer` on a mobile project, a locator break on a native screen captures the accessibility hierarchy, not a DOM snapshot, so retrieval and validation see the right shape of evidence.
- As a `tenant_admin`, mobile healing stays off for my project until its own evaluation corpus and validator have passed their own gate — enabling web healing never silently turns on mobile.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A mobile incident (produced via the 04.5.1 Appium path) stores `hierarchy_artifact_id` (artifact kind `ui_hierarchy`, T20) and `platform_context ∈ {native, webview}`; a mobile incident is never created with `platform_context = 'web'` |
| AC2 | `packages/healing-validator` gains a `mobile_ast` ruleset (Appium locator mechanics: accessibility id, resource-id, XPath changes only, same forbidden-pattern discipline as 08.4.1-T2 adapted to the Appium/WebdriverIO surface); each validation round records `candidate_validation.validator_kind ∈ {web_ast, mobile_ast}` |
| AC3 | A candidate validated under `web_ast` is never applied against a `platform_context ∈ {native, webview}` incident, and vice versa — cross-kind application returns `422 validator_kind_mismatch` |
| AC4 | `healing_mobile_pilot_scope.enabled = false` by default for every project; while `false`, mobile incidents never generate a candidate (they stay open for manual triage, same as a healing-`unavailable` incident) |
| AC5 | `PUT /v1/projects/{p}/healing/mobile-pilot-scope` (`healing:configure`) can set `enabled = true` only when `healing_phase_gate_result(gate = 'mobile_v3', passed = true)` exists for the project; otherwise `422 mobile_gate_not_passed` |
| AC6 | A mobile evaluation corpus (`evaluation_corpus.platform_context = 'mobile'`) covers the same seven FR-08-18 categories with mobile-sourced incidents, gating the `mobile_v3` result the same way 08.8.1's web corpus gates `v2`/`v3` |
| AC7 | The 08.9.1 reuse matcher never matches a `native`-context incident against a `webview`-context knowledge record or vice versa — the match key gains `platform_context` |

## 3. Contracts touched

- 00 §7 artifact kind `ui_hierarchy` (T20) is already a closed-list value; this story is its first consumer.
- T36: the mobile ruleset lives in the same `packages/healing-validator` Node 26/TypeScript 6.0.x child process as the web ruleset, run by `Evidgate.Worker`, never by the API process — no second validator host.
- Extends (does not redefine) `healing_phase_gate_result.gate`'s check constraint from `{'v2','v3'}` (08.8.3) to `{'v2','v3','mobile_v3'}`, and `evaluation_corpus.platform_context`'s check from `{'web'}` implicit default to the already-present `{'web','mobile'}` (08.8.1 already defined this column with both values, so no schema surprise here — only rows change).
- `[OPEN]` 04.5.1-T1's exact Appium artifact/event shape was not re-read in this session (outside this story's file budget); this plan treats it as an opaque producer of `ui_hierarchy` artifacts and raw mobile case results, consistent with the area plan's own citation of `04.5.1-T1`/`04.5.1-T2` as the Appium mapper dependency. If 04.5.1's actual output shape differs, 08.9.2-T1.1's context-capture hook is the only place that needs to change.

## 11. Rollout

- Fail-closed by construction: `healing_mobile_pilot_scope.enabled = false` by default and cannot be flipped without a passed `mobile_v3` gate (AC5) — no separate feature flag needed beyond this mechanism.
- Merge order: T1 → T2.
- Monitoring: a defensive alert on any mobile candidate generated while `enabled = false` for its project (should be structurally impossible — an alert here indicates a bug in the gate check, not normal operation).
- Rollback: set `enabled = false` per project (instant), or revert the PR.
