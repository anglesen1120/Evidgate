## 1. Goal and non-goals

**Goal.** Keep the proposed content and its hash on the healing candidate until a reviewer approves it against its base script revision. Only approval publishes an immutable `script_revision`. Sensitive cases require an independent approver; the approval route defaults off.

**Non-goals.** Repository access, canary and rollback (08.6.2), kill-switch implementation (08.6.3), validation (08.4.3) and review UI (09.5.1).

## 2. User stories and acceptance criteria

- As a test maintainer, I review the proposed revision with its diff, original failure, validation results and hashes.
- As a reviewer, I can see which script revision an approval covers; another user must approve sensitive cases, and an edit or change of base requires fresh review.
- As the Tech Lead, I ship the apply path dark: the feature flag defaults off and the kill switch resolves before a single approval can succeed.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The candidate stores the proposed content, diff, original failure and incident, context and assertion hashes, validation results, expiry, `candidate_hash` and base script revision. Validation and its retries publish zero script revisions. |
| AC2 | An authorized approval rechecks `If-Match` and the base script revision. Success appends one `script_revision` through 13.5.1-T5, records its id, actor and hashes, and enqueues `healing.candidate_changed` atomically. Replay returns the same id. Stale hash or base returns 412; stale and rejected reviews each publish zero revisions. |
| AC3 | A context change, base revision change or candidate edit invalidates approval; the previous approval cannot be replayed for changed inputs. |
| AC4 | On a sensitive case (payment/authorization/deletion/security flag on the case metadata), approve returns 403 `approver_is_author` when the approver equals `requested_by`/`edited_by` or the member whose human label set `test_drift` (T35); a different `healing:approve` member succeeds |
| AC5 | Approval writes only inside Evidgate; the operation succeeds with network egress disabled and requires no repository client or credentials. |
| AC8 | If the base revision changes during review, approval cannot apply to its successor: the candidate returns to `proposed` with a recorded reason. |
| AC6 | With the feature flag off, the approve endpoint is not routed (404) and `healing.apply` tasks no-op; with it on but the resolved switch (T33) `disabled`/`unavailable`, approve returns 403 `healing_unavailable` |
| AC7 | `expires_at` reached → the expiry task sets `expired`, releases the quota slot, notifies the requester; an approve call on an expired candidate returns 409 `candidate_expired` |

## 5. API shapes (commands, queries, endpoints)

| Operation | Type | Endpoint | Permission | Codes |
|---|---|---|---|---|
| `ProposeScriptRevision` | `ICommand` | internal, on validation | task | Persist proposed content and hash on the candidate only. Replaying validation neither duplicates it nor writes to `script_revision`. |
| `ApproveCandidate` | `ICommand<ApproveResult>` | `POST /v1/healing/candidates/{c}/approve` | `healing:approve` | Recheck eligibility, candidate and base before the 13.5.1-T5 approval append. Idempotent replay returns its revision id. Refuse author/switch (403), off/other tenant (404), expired (409) or stale (412) without publishing. |
| `RejectCandidate` | `ICommand<RejectResult>` | `POST /v1/healing/candidates/{c}/reject` | `healing:approve` | 200; reason required (422 `reason_required`); audited |
| `GetCandidateReview` | `IQuery<CandidateReviewView>` | `GET /v1/healing/candidates/{c}` | `healing:triage` | Return proposed content/diff, validation, hashes, expiry, base revision and the approved revision id when published. |

Within the tenant transaction, recheck the candidate hash, base revision, expiry, switch and approver. Only then publish through the 13.5.1-T5 approval path and atomically record its revision id, history and outbox event. Rejection records its reason without publishing.

## 6. States and transitions

Approval transitions `validated → approved`; changed context, revision or content transitions `approved → proposed`. Expiry ends the proposal. 08.6.2 records application separately. Every transition records actor, reason and hashes and emits `healing.candidate_changed`.

## 7. Jobs and integrations

- On validation, persist proposed content, hash and evidence on the candidate with its base revision. Retrying validation reuses the proposal without appending a `script_revision`.
- `healing/candidate-expiry` Cronos schedule: fires every 15 min; unique `(schedule_name, fire_at)` fire inserts one task; handler sweeps `expires_at < now()` in `proposed|validated|approved` → `expired`, releases the `healing_quota` slot held since mint, notifies the requester (outbox `notification` row for 09/webhook).
- `healing.candidate_changed` outbound webhook per 00 §9.5.
- A change to the current script revision invalidates candidates approved against its predecessor; recheck the base inside the approval transaction as well.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T29 | Approve route registered only when `Healing:Apply` flag on (default off); switch resolved inside the approve tx; dependency on 08.6.3-T1 keeps kill switch first | AC6 flag + resolution tests |
| T35 | Sensitive-case approver set check = `approver ∉ {requested_by, edited_by, human test_drift labeller}` enforced in handler, not UI | AC4 integration tests (all three author kinds denied) |
| Revision binding | Only the reviewed candidate and base revision may be applied | Change the base after review; approval fails and no script is applied |
| 00 §5.7 P5 | Approval writes state, audit and outbox locally | One transaction, no network requests |
| S2/T51 | `healing:approve`/`healing:revoke` on handlers; `x-permission` parity asserted by `Architecture.Tests` | AC4/AC5 + architecture test |
| Idempotency (00 §9.1) | `Idempotency-Key` on approve/reject; same key+hash → original response; different → 409 `idempotency_conflict` | AC2 idempotency test |
| Audit (NFR-08-4) | `healing_candidate_state_history` append-only rows with actor/reason/hashes; `REVOKE UPDATE` enforced at SQL level | history-row assertions; tamper attempt fails |
| S4 | No customer-repository access or external URL is needed | Approval works with outbound access denied |
| Agent identity | agent identities hold no `healing:approve` permission; approve via agent token → 403 | permission matrix test (08.6.1-T2.2), incl. agent-token 403 |
| Retention | Candidate rows and revision references are tenant data — covered by tenant deletion; `patch` artifact retention per plan 06 | deletion test |

- **Authorization:** approve needs the `healing:approve` permission and is bound to the candidate hash, base script revision and evidence context; a mismatch is refused.
- **Telemetry:** approve latency, invalidation rate and expiry sweeps (see Monitoring); every approve and invalidation writes an audit row.
- **Failure path:** Stale candidate hash or base returns 412; expiry returns 409. Rejected, stale or expired reviews publish zero script revisions.

## 11. Rollout

**Notes (D-NO-GITHUB, 2026-11-27):** Validation stores a proposal on the candidate. Only authorized approval publishes to the script store; 08.6.2 consumes that revision without appending it again.

- `Healing:Apply` flag ships default-off (T29); enabling is per-environment config after the kill-switch drill (08.6.3-T3) passes.
- Monitoring: approve latency (P1 budget per 00 §11), invalidation rate (high rate = context too stale), expiry sweeps, `healing.candidate_changed` delivery.
- Rollback: turn the approval route off. Existing approvals remain reviewable; expiry and revocation still apply.

**Notes (08.6.1-T1, hand-over from 08.6.3-T1 / S124; STATUS row "08.6.3-T1 delta items (S124)", item SD-2):** the V1 clamp (`Healing:Apply` off rejects `enabled`) runs on write only. If a row holding `enabled` exists and the flag is later turned off, `IHealingAvailabilityResolver` and `GET /v1/healing/switch` still resolve `enabled`. This task is the first consumer of the resolver for apply decisions, so it must clamp on read: `enabled` counts as `shadow` while `Healing:Apply` is off. Acceptance to add: a test with a stored `enabled` row and the flag off asserting the apply and approve routes treat the tenant as `shadow` (and the resolved value the switch GET reports), and a test with the flag on that returns `enabled`.
