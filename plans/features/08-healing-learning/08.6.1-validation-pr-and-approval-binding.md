## 1. Goal and non-goals

**Goal.** For every `validated` candidate, build a validation PR on the customer's repository carrying the diff, the original failure, the context hash, the full validation results, the assertion hash and an expiry; bind approval to `candidate_hash` + base commit via `If-Match` **and** record the PR head SHA it approved (`approved_head_sha`, T73) so a stale review or a post-approval push can never stand in for the reviewed code; enforce sensitive-case approver rules; and gate the whole apply path behind a feature flag that defaults off until the kill switch ships (T29 — already satisfied by the dependency on 08.6.3-T1).

**Non-goals.** Merging (the customer's Git flow merges; Evidgate never merges by default — D3); canary/rollback after merge (08.6.2); the kill-switch implementation (08.6.3, dependency); the sandbox validation itself (08.4.3); the review queue UI (09.5.1); GitHub App installation and token issuance (03.4.2-T1).

## 2. User stories and acceptance criteria

- As a `test_maintainer`, I review a PR that shows the patch, the original failure and all validation evidence with hashes I can verify, so approval is a review of *this exact* candidate, not of a description.
- As a security reviewer, I can prove approval binds `candidate_hash` + base commit + the PR head SHA it was taken on (`approved_head_sha`, T73): any edit, rebase, context drift or `pull_request.synchronize` to a different head after approval demotes the candidate to `proposed` and posts a failing check run, sensitive cases demand a different approver, and approval alone never merges.
- As the Tech Lead, I ship the apply path dark: the feature flag defaults off and the kill switch resolves before a single approval can succeed.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST` a validation PR (via the 03.4.2 GitHub App flow) creates a branch + PR whose body contains: unified diff, original failure text + incident link, `context_hash`, validation report (per-check verdicts + `assertion_hash_before == assertion_hash_after`), `expires_at`, `candidate_hash`; the `healing_candidate` row stores the PR URL and `expires_at` in the same transaction |
| AC2 | `POST /v1/healing/candidates/{c}/approve` without a valid `If-Match` candidate-hash returns 412 with the current `candidate_hash` in `error.details`; with a matching hash and `base_commit` it transitions `validated → approved`, writes the audit row (actor, reason, hashes) and emits `healing.candidate_changed` via outbox |
| AC3 | After approval, any of — context artifact re-read (new `context_hash`), rebase (new `base_commit`), candidate edit — transitions `approved → proposed` with `reason` recorded; an attempt to approve the re-entered candidate with the old hash returns 412 |
| AC4 | On a sensitive case (payment/authorization/deletion/security flag on the case metadata), approve returns 403 `approver_is_author` when the approver equals `requested_by`/`edited_by` or the member whose human label set `test_drift` (T35); a different `healing:approve` member succeeds |
| AC5 | Approval never merges (T64b: no merge capability exists in V1–V2 at all): the API performs no Git merge operation — a mocked GitHub client asserts zero merge calls across every approval test, **and** an architecture test fails the build if any route, or any `IGitHubRepoWriter` method (03.4.2), implements a merge operation; merge stays entirely the customer's manual act, never gated by a permission Evidgate grants |
| AC8 | On `pull_request.synchronize` (or the PR-state sync detecting a head SHA ≠ the stored `approved_head_sha`), an `approved` candidate demotes to `proposed` with `invalidated_reason = head_moved`, and a **failing** check run is posted on the new head via the GitHub App (T73) so the unapproved code can never inherit the approval's green status |
| AC6 | With the feature flag off, the approve endpoint is not routed (404) and `healing.apply` tasks no-op; with it on but the resolved switch (T33) `disabled`/`unavailable`, approve returns 403 `healing_unavailable` |
| AC7 | `expires_at` reached → the expiry task sets `expired`, releases the quota slot, notifies the requester; an approve call on an expired candidate returns 409 `candidate_expired` |

## 3. Contracts touched

- 00 §9.3 rows `POST /v1/healing/candidates/{c}/approve`, `…/reject` — implemented as specified (`If-Match`, `healing:approve`, reason required, audited); webhook `healing.candidate_changed` per 00 §9.5 emitted on `validated → approved`, `approved → proposed`, `expired`.
- New error codes into `contracts/openapi.yaml`: `approver_is_author` (403), `candidate_expired` (409), `healing_unavailable` (403); `x-permission: healing:approve`/`healing:revoke`/`healing:configure` (T51) — permission catalogue rows added in the 02 seed migration listed in §4 (they exist per 08 §4.2 but the catalogue seed lands here).
- `healing_candidate` gains `pr_url`, `pr_number`, `expires_at` (already in §4.1), `sensitive_case`, `approved_by`, `approved_at` columns — additive migration.
- Resolved: TL ruling T64(b) (README §3) settles FR-08-14's "unless the integration is explicitly permitted" clause — there is **no** merge capability in V1–V2 at all; the escape hatch is out of scope for every story in this plan set, not merely undesigned. The enforcement mechanism is **not** the `draft:merge_request` permission (that permission gates 03.6.1's `POST /v1/drafts/{d}/pull-request`, which only opens a PR and never merges — it is not a merge control) — it is the structural absence of any merge endpoint or `IGitHubRepoWriter` merge method anywhere in the codebase, made testable by the architecture test named in T2.3/§9 (`NoMergeTests` + `Architecture.Tests`). A future merge capability, if ever wanted, is a DECISIONS §2/CR-level change for a later version, not a gap in this story.
- Resolved (T73): approval binds the merged code. `ApproveCandidate` stores `approved_head_sha`; a `pull_request.synchronize` to a different head demotes `approved → proposed` and posts a failing check run (this story); on `merged`, 08.6.2 verifies the merged diff of the candidate's files equals the approved patch (`candidate_hash`) — mismatch ⇒ `revoked`/`merge_mismatch` + alert, never `applied`.

## 5. API shapes (commands, queries, endpoints)

| Operation | Type | Endpoint | Permission | Codes |
|---|---|---|---|---|
| `CreateValidationPr` | `ICommand<CandidatePrResult>` | internal, task `healing.build_pr` (outbox on `validated`) | n/a (task) | PR created + `pr_url` stored; failure retries then marks candidate `rejected`/`pr_build_failed` |
| `ApproveCandidate` | `ICommand<ApproveResult>` | `POST /v1/healing/candidates/{c}/approve` | `healing:approve` | 200 — stores `approved_head_sha` (fetched during the bound PR build) alongside `approved_by`/`approved_at` (T73); 403 `approver_is_author`, `healing_unavailable`; 404 flag off / other tenant; 409 `candidate_expired`; 412 stale `If-Match` (current hash in `error.details`); `Idempotency-Key` required |
| `RejectCandidate` | `ICommand<RejectResult>` | `POST /v1/healing/candidates/{c}/reject` | `healing:approve` | 200; reason required (422 `reason_required`); audited |
| `GetCandidateReview` | `IQuery<CandidateReviewView>` | `GET /v1/healing/candidates/{c}` | `healing:triage` | diff pointer (artifact id), validation report, hashes, expiry, PR URL |

Pipeline specifics (C2): the approve handler re-reads the candidate inside the tenant tx, re-validates `If-Match` hash + `base_commit` + `expires_at` + resolved switch (T33) + T35 set — all inside one transaction so a concurrent edit can't interleave. No GitHub call inside that tx (P5): the PR build is a separate task.

## 6. States and transitions

`validated → approved` (approve — records `approved_head_sha`, T73) · `approved → proposed` (context/rebase/edit invalidation **or** `pull_request.synchronize` to a different head — `invalidated_reason` set, failing check run posted, T73) · `validated|proposed → expired` (expiry task) · `approved → applied` is recorded by 08.6.2 when the customer merges **and** the merged diff equals `candidate_hash` (T73) — never by this story's approve call. Every transition writes `healing_candidate_state_history` with actor/reason/hashes and emits `healing.candidate_changed` (outbox, C7).

## 7. Jobs and integrations

- `healing.build_pr` task (outbox on `validated`): calls GitHub App installation token flow (03.4.2-T1: typed `HttpClient` + RS256 app JWT, T46), creates branch `evidgate/heal/<candidate-id>`, pushes the `patch` artifact as a commit, opens PR idempotent by `(branch, commit)` (reuses `draft:merge_request` semantics of `POST /v1/drafts/{d}/pull-request`, idempotent per 00 §9.3).
- `healing/candidate-expiry` Cronos schedule: fires every 15 min; unique `(schedule_name, fire_at)` fire inserts one task; handler sweeps `expires_at < now()` in `proposed|validated|approved` → `expired`, releases the `healing_quota` slot held since mint, notifies the requester (outbox `notification` row for 09/webhook).
- `healing.candidate_changed` outbound webhook per 00 §9.5.
- **Head-drift watch (T73):** GitHub `pull_request.synchronize` deliveries for healing PRs (webhook plumbing of 03.4.x) — and the `healing.pr_state_sync` poll of 08.6.2 as fallback — feed the demotion path: head SHA ≠ `approved_head_sha` ⇒ `approved → proposed` (`invalidated_reason = head_moved`) + failing check run on the new head. The check-run write happens in the demotion task, never inside the candidate-update tx (P5).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T29 | Approve route registered only when `Healing:Apply` flag on (default off); switch resolved inside the approve tx; dependency on 08.6.3-T1 keeps kill switch first | AC6 flag + resolution tests |
| T35 | Sensitive-case approver set check = `approver ∉ {requested_by, edited_by, human test_drift labeller}` enforced in handler, not UI | AC4 integration tests (all three author kinds denied) |
| T73 | `approved_head_sha` stored at approve; head-moved detection demotes to `proposed` and posts a failing check run on the new head — approval can never cover code the reviewer did not see | AC8 `HeadMovedTests`; demotion + check-run asserted on a mocked GitHub client |
| 00 §5.7 P5 | Approve tx = reads + state transition + audit + outbox only; GitHub calls live in `healing.build_pr` task | command-counter test: approve = 1 tx, 0 network |
| S2/T51 | `healing:approve`/`healing:revoke` on handlers; `x-permission` parity asserted by `Architecture.Tests` | AC4/AC5 + architecture test |
| Idempotency (00 §9.1) | `Idempotency-Key` on approve/reject; same key+hash → original response; different → 409 `idempotency_conflict` | AC2 idempotency test |
| Audit (NFR-08-4) | `healing_candidate_state_history` append-only rows with actor/reason/hashes; `REVOKE UPDATE` enforced at SQL level | history-row assertions; tamper attempt fails |
| S4 | GitHub egress only through the reviewed installation-token client of 03.4.2, never a user-supplied URL | 03.4.2 contract reused; no new outbound host |
| Agent identity | agent identities hold no `healing:approve` permission; approve via agent token → 403 | permission matrix test (08.6.1-T2.2), incl. agent-token 403 |
| Retention | Candidate rows/PR URLs are tenant data — covered by tenant deletion; `patch` artifact retention per plan 06 | deletion test |

- **Authorization:** approve needs the `healing:approve` permission and is bound to the candidate, the head sha and the evidence context; a mismatch is refused.
- **Telemetry:** approve latency, invalidation rate and expiry sweeps (see Monitoring); every approve and invalidation writes an audit row.
- **Failure path:** a stale, expired or mismatched context answers 409/422 and leaves the candidate unchanged; the flag off removes the route.

## 11. Rollout

- `Healing:Apply` flag ships default-off (T29); enabling is per-environment config after the kill-switch drill (08.6.3-T3) passes.
- Monitoring: approve latency (P1 budget per 00 §11), invalidation rate (high rate = context too stale), expiry sweeps, `healing.candidate_changed` delivery.
- Rollback: flag off removes the route; candidates already `approved` stay reviewable (no merge ever happened server-side) and expire naturally or get revoked by 08.6.2's revoke path.

**Notes (08.6.1-T1, hand-over from 08.6.3-T1 / S124; STATUS row "08.6.3-T1 delta items (S124)", item SD-2):** the V1 clamp (`Healing:Apply` off rejects `enabled`) runs on write only. If a row holding `enabled` exists and the flag is later turned off, `IHealingAvailabilityResolver` and `GET /v1/healing/switch` still resolve `enabled`. This task is the first consumer of the resolver for apply decisions, so it must clamp on read: `enabled` counts as `shadow` while `Healing:Apply` is off. Acceptance to add: a test with a stored `enabled` row and the flag off asserting the apply and approve routes treat the tenant as `shadow` (and the resolved value the switch GET reports), and a test with the flag on that returns `enabled`.
