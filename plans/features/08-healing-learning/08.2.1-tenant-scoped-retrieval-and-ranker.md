## 1. Goal and non-goals

**Goal.** A deterministic, in-database retrieval service returns prior incidents for the same tenant/project/engine ordered by fingerprint match then similarity, each carrying its current `label` and `label_source`; a v0 ranker orders them with an inspectable explanation. Similarity only *ranks* — it never authorises, approves or applies anything (FR-08-5).

**Non-goals.** Candidate generation that consumes the results — 08.3.1; `incident_label` storage — 08.2.2 (this story reads the contract column shape defined there; against an unlabeled incident the label is null); knowledge-record weighting — 08.7.1 (V2); embeddings/vector search — rejected by D1 until measured need.

## 2. User stories and acceptance criteria

- As the healing generator, I get the tenant's own prior incidents ranked by how close they are to the current break, so rule generation can propose the mapping that worked before.
- As a security reviewer, I can prove no code path turns a similarity score into a permission.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `IRetrievalQuery.FindAsync(orgId, projectId, engine, fingerprint, k)` runs inside the caller's tenant scope (C3) and returns ≤ `k` rows from that project only; a seeded cross-tenant row with an identical fingerprint is never returned |
| AC2 | Every returned row carries `incident_id`, `fingerprint`, `fingerprint_version`, `old_locator`, `label`, `label_source` (null label allowed pre-triage), `created_at` |
| AC3 | Ranking is deterministic: exact `fingerprint` matches outrank `error_class` matches, which outrank trigram similarity on `old_locator`/`error_text`; each result carries an `explanation` array of the match signals used |
| AC4 | The query issues ≤ 2 SQL statements (counted), uses the 08.1.2 `fingerprint` index plus a `pg_trgm` index for similarity, and returns in a single round trip |
| AC5 | A record ranked #1 by similarity confers nothing: the permission checks of `POST /v1/incidents/{i}/label`, candidate generation and (V2) approval are unaffected by rank — verified by a test asserting no authorization decision reads the similarity score |
| AC6 | When no prior rows match, the result is an empty list — generation falls back to rules only, no error |

## 4. Data model and migrations

`migrations/NNNN_healing_retrieval_indexes.sql`:

- `CREATE EXTENSION IF NOT EXISTS pg_trgm;` (owner role).
- `CREATE INDEX … ON incident (org_id, project_id, engine, fingerprint)` — the AC4 retrieval index (the 08.1.2 fingerprint index is subsumed by this composite for retrieval; kept for single-column lookups) [INFERENCE: keep both, fingerprint-only index serves backfill/settle scans].
- `CREATE INDEX … ON incident USING gin (old_locator gin_trgm_ops)` and `… (error_text gin_trgm_ops)` — trigram similarity source columns.
- Read view `incident_retrieval` (module-owned): `incident` left-joined to the current `incident_label` row (from 08.2.2's table) exposing the AC2 fields only.

## 5. API shapes (commands, queries, endpoints)

No HTTP endpoints. Internal contract:

| Shape | Kind | Signature | Result |
|---|---|---|---|
| `FindSimilarIncidents` | `IQuery<IReadOnlyList<RetrievedIncident>>` | `FindAsync(orgId, projectId, engine, fingerprint, fingerprintVersion, k)` | ≤ `k` `RetrievedIncident` rows, rank-ordered, `explanation[]` per row |

- Dapper implementation over `incident_retrieval`, read-only transaction inside the caller's `ITenantScope` (C3/C5). SQL: one statement scoring match class (`fingerprint =` → 3, `error_class =` → 2, else `similarity(old_locator)+similarity(error_text)`), ordered, `LIMIT k` (k ≤ 20).
- Errors: none of its own — it throws only on infrastructure failure; callers treat it as advisory (AC6).

## 6. States and transitions

None. Retrieval reads committed rows; it mutates nothing and moves no state machine.

## 7. Jobs and integrations

- Called by candidate generation (08.3.1-T1) inside the generation task's tenant scope, and later by the V2 prompt builder (08.5.2) — always with the incident's own `org_id`/`project_id`, never a caller-supplied scope (the cross-tenant filter is structural, not a parameter any caller can widen).
- Consumed by the ranker unit only; no background job of its own.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.4.2/7 + T2 | retrieval runs inside the established tenant scope; RLS on `incident`/`incident_label` enforces the tenant filter even if SQL drifts | `retrieval_cross_tenant_excluded` (Isolation.Tests) |
| FR-08-5 | similarity is a `double` in the result DTO, never an input to any authorization, approval or apply path | `similarity_grants_nothing` test greps authorization attributes + asserts approval path ignores rank |
| S1 | parameterised Dapper (`@org_id` etc.); no string-built similarity clauses | code review + S1 lint |
| P3 | ≤ 2 statements per call, asserted by command counter | `retrieval_statement_budget` |
| P4 | filter/score columns covered by the composite + GIN indexes of this story's migration | `EXPLAIN` assertion in `retrieval_uses_indexes` |
| P5 | pure DB read, no network inside the transaction | transaction-boundary review |
| S3 | result rows never include `error_text` beyond what masking already stored; nothing logged above ids | redaction list check |
| PDPL | results stay in-process in-tenant; provider egress (V2) passes through 08.5.3 redaction before any row content leaves | stated |
| Retention/deletion | reads follow artifact/incident retention; nothing new persisted | — |
