## 1. Goal and non-goals

**Goal.** When the 08.8.3 V3 gate has passed for a project, an incoming incident that exactly matches an **approved** `knowledge_record` on `(org_id, project_id, engine, context_hash, case_id)` generates a candidate directly from the stored mapping instead of running the LLM/rule generation loop — cheaper and higher-precision than a fresh generation — while every existing safety rail (kill switch, human approval, canary, revoke) stays exactly as it is for a normally-generated candidate, and reuse never crosses tenants.

**Non-goals.** Skipping human approval (08.6.1) or auto-merging (D3) — ruled: T65 confirms V3 narrow-context reuse still requires human approval; skipping it would be an explicit DECISIONS §5.7 change the owner has not made, and it stays out of scope. Also non-goals: the V3 gate mechanism itself (08.8.3); mobile reuse discrimination (08.9.2, which extends this story's match key).

## 2. User stories and acceptance criteria

- As a `qa_engineer`, when a break exactly matches a previously-approved fix on the same test, the candidate that comes back uses the known mapping directly — no LLM call, no waiting on retrieval ranking — while I still get to approve it before it ships.
- As a `tenant_admin`, a reused mapping that regresses in canary is revoked along with the underlying knowledge record, so the same bad mapping cannot be proposed again.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An incident with `(org_id, project_id, engine, context_hash, case_id)` exactly matching an `active` `knowledge_record` on the same four columns triggers `strategy = 'reuse'` candidate generation from the record's `new_locator`; no `healing_llm_call` row is written for a reuse candidate |
| AC2 | Reuse generation is skipped — falling back to normal 08.3/08.5 generation, still bound by the FR-08-6 quota — whenever `healing_switch` resolves to anything other than `enabled` for the project (`shadow`, `disabled`, `unavailable`) |
| AC3 | A reuse candidate still passes the full 08.4 validator (AST allowlist, forbidden patterns, assertion hash, negative control) and the full 08.6.1 human approval flow; `healing:approve` is still required and T35's approver-conflict rule still applies — no state or permission bypass |
| AC4 | A reuse candidate's canary (08.6.2) detecting regression revokes both the candidate and `source_knowledge_record_id`'s `knowledge_record` (`state: active → revoked`), which triggers the 08.7.2 cascade on any other candidate depending on that record |
| AC5 | A `knowledge_record` belonging to another org, or one whose `context_hash` coincidentally matches but `case_id` differs, is never matched (negative test with a synthetic hash collision across two orgs and across two unrelated cases) |
| AC6 | Reuse matching runs only when `healing_phase_gate_result(gate = 'v3', passed = true)` exists for the project (08.8.3 cross-story contract); absent or failed ⇒ the matcher returns no match, falling back to normal generation, never a hard error |

## 3. Contracts touched

- 00 §8.7 candidate/knowledge states are unchanged: `strategy = 'reuse'` is a generation-strategy tag on the existing `healing_candidate.strategy` column, not a new state or a new exit.
- DECISIONS rule 7 / D7: this plan's conservative reading (§1 non-goals) is recorded here as the interpretation this feature plan builds to; it does not reopen or answer whether V3 should ever skip human approval.
- T35 (approver ≠ author) applies unchanged to reuse candidates (AC3) — no new exemption is created for the reuse path.

## 4. Data model and migrations

`migrations/0155_healing_candidate_reuse_fields.sql` — on `healing_candidate` (already carries `strategy`, per area plan §4.1):

| Column | Type | Notes |
|---|---|---|
| `source_knowledge_record_id` | `uuid null` | composite FK `(org_id, source_knowledge_record_id)` → `knowledge_record (org_id, id)`; set only when `strategy = 'reuse'` |

Check added to the existing `strategy` column's allowed values to include `'reuse'` (extends whatever enum/check 08.3.1-T1 defined).

Index (serves the matcher, P4): `create index ix_knowledge_record_reuse_match on knowledge_record (org_id, project_id, engine, context_hash) where state = 'active';` — the match query also filters `case_id` via a join to `healing_candidate` (the knowledge record's originating candidate) rather than duplicating `case_id` onto `knowledge_record`, avoiding a second source of truth for lineage.

## 5. API shapes (commands, queries, endpoints)

No new public endpoint. This story extends the internal candidate-generation entry point (owned by 08.3.1/08.5.1) with a `reuse` strategy branch, and extends 08.6.2's regression handler.

| Internal command | Trigger | Notes |
|---|---|---|
| `TryReuseCandidateCommand(IncidentId)` | called first by the existing generation entry point, before the LLM/rule path | one bounded SELECT against the index above + the `case_id` join + the V3-gate precondition (AC6) + the kill-switch check (AC2); on no match, falls through to the existing generation command unchanged |
| `RevokeReuseSourceOnRegressionCommand` | called by 08.6.2's existing canary-regression handler when the regressed candidate's `strategy = 'reuse'` | reuses 08.7.2's `RevokeKnowledgeRecordCommand` internally — no duplicated revoke logic |

Read surface: `GET /v1/healing/candidates/{c}` (08.1.1, extended with lineage by 08.7.2) already exposes `strategy`; this story adds `source_knowledge_record_id` to that same projection (one extra column, no new query shape).

Errors: unchanged from 08.3/08.4/08.6 — reuse is an internal generation-strategy choice, not a new public contract surface.

## 6. States and transitions

None beyond 00 §8.7 (§3). `strategy = 'reuse'` is a tag, never a state.

## 7. Jobs and integrations

- The match runs synchronously inside the same transaction as normal candidate generation (no separate job, no network call — faster than the LLM path precisely because it makes none, P5).
- The V3-gate and kill-switch checks are read-only lookups against `healing_phase_gate_result` (08.8.3) and `healing_switch` (08.6.3) — no write, no new integration event.
- Consumed by: 08.9.2's mobile reuse discrimination, which adds `platform_context` to this story's match key without changing its shape.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T3 / 00 §5.4.6 | match query always filters `org_id = evidgate.current_org_id()` via RLS, plus an explicit `WHERE org_id = @org` defense-in-depth (S1) since `context_hash` collisions across orgs are only cryptographically unlikely, not impossible | `Reuse_CrossOrgKnowledgeRecord_NeverMatches` |
| Lineage integrity | `case_id` equality (via the candidate join) prevents a coincidental `context_hash` collision on an unrelated test from ever matching | `Reuse_ContextHashCollisionDifferentCase_NeverMatches` |
| T33 (kill switch, most restrictive wins) | reuse only fires when `healing_switch` resolves `enabled`; `shadow`/`disabled`/`unavailable` fall back to normal generation | `Reuse_SwitchNotEnabled_FallsBackToNormalGeneration` |
| Fail-closed on ungated capability (08.8.3, T29 pattern) | reuse never runs without a passed V3 gate | `Reuse_V3GateNotPassed_FallsBackToNormalGeneration` |
| No permission bypass (S2, T35) | `healing:approve` and the approver-conflict rule apply unchanged to reuse candidates | `Reuse_StillRequiresHumanApproval_NoBypassOfHealingApprovePermission` |
| 00 §5.7 P4/P5 | match query served by the partial index above; no network call in the transaction (it makes none, being the point of reuse) | `EXPLAIN` assertion in the matcher's integration test |

## 11. Rollout

- Two independent off-switches gate all reuse traffic before this story's code path can fire at all: the V3-gate precondition (fails closed absent a passed gate) and the existing kill switch — no separate feature flag is needed on top of them.
- Merge order: T1 → T2 in one PR series.
- Monitoring: alert on `strategy = 'reuse'` candidate volume and its false-heal rate segmented from normally-generated candidates (feeds 08.8.2's report; segmentation by strategy is a follow-up to that story, not built here).
- Rollback: flip the project's `healing_switch` to `disabled` for an immediate stop, or revert the PR; no reused candidate bypasses approval, so nothing is left silently applied.
