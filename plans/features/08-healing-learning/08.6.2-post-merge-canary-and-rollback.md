## 1. Goal and non-goals

**Goal.** Exercise the approved script revision on the selected canary suite. A regression or suspected false heal disables the rule and revokes the candidate with a reason. Restore its predecessor only if the healed revision is still active; never overwrite a successor. Historical release decisions do not change.

**Non-goals.** Candidate approval (08.6.1), feedback labels (08.7.1), the V2 gate report (08.8.3), and any repository access.

## 2. User stories and acceptance criteria

- As a maintainer, I can see which revision the canary tested and whether rollback restored its predecessor or preserved a successor.
- As the Tech Lead, I can audit the disable, revoke and restore actions without changing historical decisions.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Applying the approved candidate against its reviewed base records the applied revision and enqueues a bounded canary on the selected suite. |
| AC2 | The canary creates a rerun with `parent_run_id` + `rerun_scope = failed_subset` against the pinned manifest/policy/environment; the run never mutates the original run's evidence revision or decisions |
| AC3 | A FAIL or INCONCLUSIVE canary on the healed case disables the rule and revokes the candidate with reason `canary_regression`. Restore the predecessor only if the applied revision is still active; otherwise keep the successor and record `rollback_conflict` for review. Audit the outcome and notify through the outbox. |
| AC4 | A human-suspected false heal: `POST /v1/healing/candidates/{c}/revoke` with `reason` follows AC3's guarded rollback and labels the incident for re-triage; old `evaluation`/`release` decision rows are byte-identical before and after (asserted by checksum) |
| AC5 | Canary green → no rollback; the candidate stays `applied` and an outbox event emits `canary_passed` for 08.7.1 feedback (`unknown` — never a ground-truth label by itself, FR-08-16) |
| AC6 | Rollback under `healing:revoke` only; agent identities denied; `Idempotency-Key` required; a second revoke on an already `revoked` candidate returns the original response (idempotent) or 409 `already_revoked` on different payload |
| AC7 | If the candidate hash or base no longer matches the approval, do not apply the candidate or enqueue a canary; record the invalidation for review. |

## 5. API shapes (commands, queries, endpoints)

| Operation | Type | Endpoint / caller | Permission | Codes |
|---|---|---|---|---|
| `MarkCandidateApplied` | `ICommand` | internal, on approved revision application | task | Check candidate and base; write `applied` with its revision and enqueue the canary only on a match. |
| `RunCanary` | `ICommand` | task `healing.canary` | n/a | creates failed-subset rerun (05 rerun endpoint semantics, server-side) |
| `RollbackCandidate` | `ICommand<RollbackResult>` | task `healing.rollback` (canary path) + `POST /v1/healing/candidates/{c}/revoke` (manual path) | `healing:revoke` | 200; 403 `healing_unavailable`/forbidden; 409 `already_revoked`; `Idempotency-Key` |
| `GetRollback` | `IQuery` | candidate review view | `healing:triage` | Return reason, actor, outcome and restored revision id (null for `rollback_conflict`). |

Manual revoke (false-heal suspicion) and canary-triggered rollback share the `RollbackCandidate` handler so both paths produce identical effects (invariant: one code path = one audit shape).

## 6. States and transitions

The candidate moves from `approved` to `applied` only for the reviewed change. On regression or manual revocation it moves from `applied` to `revoked` and the rule is disabled, whether restoration succeeds or conflicts. The canary state is `pending`, `green`, `regressed` or `skipped`. Existing evaluations and release decisions remain immutable.

## 7. Jobs and integrations

- Consume approved revision application idempotently; record the applied revision and enqueue one canary for the selected suite. A stale base or changed candidate cannot be applied.
- `healing.canary` task: builds the rerun (`rerun_scope = failed_subset`, same suite revision pinned at mint); completion arrives via the existing evaluation pipeline — a `healing.canary_verdict` consumer task reads the run decision and either marks `canary_state = green` (emit `canary_passed`) or enqueues `healing.rollback`.
- In one rollback transaction, disable the candidate's rule, revoke the candidate with reason and compare-and-set the active revision from its recorded applied revision to its predecessor. If the comparison fails, leave the active revision untouched and record `rollback_conflict` for review; do not undo the disable or revocation. Audit the outcome and enqueue notification in either case. No repository job is scheduled.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T33 | `RollbackCandidate` checks the resolved switch: `unavailable` still permits rollback (rollback is the safe direction — never blocked by the switch); `disabled` healing still allows revoke | `RollbackUnderSwitchTests` |
| 00 §5.7 P5 | Canary and rollback writes are local transactions with no network calls | Transaction and outbox tests |
| S2/T51 | `healing:revoke` in pipeline; `x-permission` in OpenAPI; agent token → 403 | AC6 |
| Immutability | Historical `evaluation`/`release_run`/decision rows are never updated by rollback; asserted by content checksum | AC4 checksum test |
| Audit NFR-08-4 | `healing_rollback` + state-history rows carry trigger, reason, actor, hashes | audit assertions |
| Idempotency | `unique (org_id, candidate_id)` on `healing_rollback` + `Idempotency-Key` arbiter (T11) | AC6 duplicate-revoke test |
| Performance | Canary is a bounded `failed_subset` rerun on the existing run pipeline — no new hot path; `pr_state_sync` poll uses one indexed query | index on `canary_state` |
| Approval binding | Apply only the reviewed candidate against the reviewed base | Stale input produces neither application nor canary |

- **Authorization:** Manual revocation requires `healing:revoke` in the candidate’s tenant; agent credentials are refused. Disabling healing does not disable rollback.
- **Retention/deletion:** Rollback and history rows belong to the tenant and follow tenant deletion. Restoring the previous revision never edits historical evaluations or release decisions.
- **Telemetry:** Record the trigger, actor, reason, revision references and hashes in rollback history; emit the change notification through the outbox.
- **Failure path:** A stale approval cannot apply or enqueue a canary. A failed or inconclusive canary revokes the candidate; a successor remains active on `rollback_conflict`. Idempotent replay does not repeat the rollback.

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Approved revision applied | One matching application records the revision and enqueues one canary |
| Canary regression while the healed revision is active | FAIL or INCONCLUSIVE disables the rule, revokes with reason and restores the predecessor |
| Delayed rollback after a successor is active | Apply healed B over A, make C current, then roll back B. C remains active, B is revoked, its rule is disabled and the review shows `rollback_conflict` with no restored revision. |
| Manual false-heal revoke | `ManualRevokeTests`: reason required (422 without); same guarded rollback as canary; incident re-triaged |
| Decisions untouched | `ImmutabilityTests`: decision/`release_run` checksums identical pre/post rollback |
| Green canary | `CanaryGreenTests`: `canary_passed` event, no rollback, candidate stays `applied` |
| Idempotent revoke | double revoke → original response; different payload → 409 |
| Stale approval | Changed candidate or base: no applied state and no canary task |
| Successful restoration | Check the active revision id against the stored predecessor; historical revisions and decisions remain unchanged |

## 11. Rollout

- Canary runs on normal infrastructure (`failed_subset` rerun) — no flag of its own; it only activates for candidates `applied` through the 08.6.1 path, so disabling `Healing:Apply` also starves this flow.
- Monitoring: canary queue age, `canary_state` distribution, rollback count per project (feeds the rollback-rate metric in 08.8.2 and the rollback drill evidence for 08.8.3-T1).
- Rollback: this story *is* the rollback; if the rollback task itself fails, `healing_rollback` absence + `dead_letter` alerting (00 §5.3) surfaces it to operators for the manual path.
