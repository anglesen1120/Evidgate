## 1. Goal and non-goals

**Goal.** After the customer merges an approved candidate, run a canary — a bounded rerun of the selected suite — that detects regression; on regression or a suspected false heal, disable the generated `healing_rule`, revoke the candidate with a mandatory reason, and open a revert PR draft; all of it audited, with old release decisions never rewritten.

**Non-goals.** Detecting merge itself beyond reading the candidate's PR state (the customer's Git flow merges — D3; detection comes from the PR build integration of 08.6.1-T1.3 polling/webhook); the approve/PR path (08.6.1); knowledge-record feedback labels that consume rollback outcomes (08.7.1); the V2 gate report that cites this drill (08.8.3).

## 2. User stories and acceptance criteria

- As a test maintainer, a merged heal is exercised once against the selected suite before we call it good; if it regresses or looks like a false heal, one action rolls everything back and tells me why.
- As the Tech Lead, I can prove the rollback path is a real drill: rule disabled, candidate `revoked` with reason, revert PR drafted, and historical release decisions untouched.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | When an `approved` candidate's PR reaches merged state **and** the merged diff of the candidate's files equals the approved patch (`candidate_hash`, T73), `healing_candidate.state → applied` (actor = integration, hashes recorded) and an outbox task `healing.canary` is enqueued for the incident's suite with a bounded scope (the canary suite selection stored at mint) |
| AC2 | The canary creates a rerun with `parent_run_id` + `rerun_scope = failed_subset` against the pinned manifest/policy/environment; the run never mutates the original run's evidence revision or decisions |
| AC3 | Canary run reaches `FAIL` or `INCONCLUSIVE` on the healed case → outbox task `healing.rollback` performs: `healing_rule.state → disabled` (`disabled_reason`), `healing_candidate.state → revoked` (reason `canary_regression`), revert PR draft opened via the 03.4.2 flow, audit rows for all three — inside one transaction plus one follow-up task for the PR (P5) |
| AC4 | A human-suspected false heal: `POST /v1/healing/candidates/{c}/revoke` with `reason` performs the same three effects plus labels the incident for re-triage; old `evaluation`/`release` decision rows are byte-identical before and after (asserted by checksum) |
| AC5 | Canary green → no rollback; the candidate stays `applied` and an outbox event emits `canary_passed` for 08.7.1 feedback (`unknown` — never a ground-truth label by itself, FR-08-16) |
| AC6 | Rollback under `healing:revoke` only; agent identities denied; `Idempotency-Key` required; a second revoke on an already `revoked` candidate returns the original response (idempotent) or 409 `already_revoked` on different payload |
| AC7 | When a merged PR's diff of the candidate's files does **not** equal the approved patch (`candidate_hash`, T73) — e.g. the customer edited the PR before merging — the candidate transitions `approved → revoked` with reason `merge_mismatch`, an alert fires (outbox `notification` + `healing.candidate_changed`), no `applied` state is ever recorded and no canary is enqueued; `applied` is unreachable for mismatched merges |

- 00 §9.3 `POST /v1/healing/candidates/{c}/revoke` — implemented as specified (reason required, audited, blocks future use).
- 00 §8.1 rerun semantics — canary uses `rerun_scope = failed_subset`; labelled, never a full regression.

- `healing_rule.disabled_reason` and `healing_candidate` transition history (08.6.1's `healing_candidate_state_history`) — reused, no new columns.
- Revert PR reuses the 08.6.1 PR builder with strategy `revert`.

## 5. API shapes (commands, queries, endpoints)

| Operation | Type | Endpoint / caller | Permission | Codes |
|---|---|---|---|---|
| `MarkCandidateApplied` | `ICommand` | task `healing.pr_state_sync` (polls merged PRs via 03.4.2 client) | n/a | merged-diff equality check first (T73): match ⇒ `approved → applied` + `healing.canary` outbox; mismatch ⇒ `approved → revoked` (`merge_mismatch`) + alert outbox |
| `RunCanary` | `ICommand` | task `healing.canary` | n/a | creates failed-subset rerun (05 rerun endpoint semantics, server-side) |
| `RollbackCandidate` | `ICommand<RollbackResult>` | task `healing.rollback` (canary path) + `POST /v1/healing/candidates/{c}/revoke` (manual path) | `healing:revoke` | 200; 403 `healing_unavailable`/forbidden; 409 `already_revoked`; `Idempotency-Key` |
| `GetRollback` | `IQuery` | part of `GET /v1/healing/candidates/{c}` review view | `healing:triage` | rollback record + revert PR URL |

Manual revoke (false-heal suspicion) and canary-triggered rollback share the `RollbackCandidate` handler so both paths produce identical effects (invariant: one code path = one audit shape).

## 6. States and transitions

Candidate: `approved → applied` (merge detected **and** merged diff = `candidate_hash`, T73) · `approved → revoked` (`merge_mismatch` when the merged diff differs, T73 — with alert) · `applied → revoked` (canary regression or manual revoke). `healing_rule`: `active → disabled`. `healing_candidate.canary_state`: `pending → green | regressed | skipped`. Revert draft follows the 03 draft flow (`draft → pr_open`), never `merged` by us. Old `evaluation`/`release` rows immutable — untouched, only referenced.

## 7. Jobs and integrations

- `healing.pr_state_sync` Cronos every 5 min (unique `(schedule_name, fire_at)`): polls `applied-pending` candidates' PRs via the GitHub installation client; on `merged` it first verifies the merged diff of the candidate's files equals the approved patch (`candidate_hash`, T73): equal ⇒ writes `applied` + enqueues `healing.canary`; different ⇒ writes `revoked`/`merge_mismatch` + alert outbox, and no canary. The same sync detects head SHA ≠ `approved_head_sha` on still-open PRs and reports it to 08.6.1's demotion path (T73).
- `healing.canary` task: builds the rerun (`rerun_scope = failed_subset`, same suite revision pinned at mint); completion arrives via the existing evaluation pipeline — a `healing.canary_verdict` consumer task reads the run decision and either marks `canary_state = green` (emit `canary_passed`) or enqueues `healing.rollback`.
- `healing.rollback` task: tx = rule disable + candidate revoke + `healing_rollback` row + audit + outbox (revert-PR task + notification). Revert PR opened by a follow-up `healing.build_revert_pr` task (no GitHub call inside the tx, P5).

## 11. Rollout

- Canary runs on normal infrastructure (`failed_subset` rerun) — no flag of its own; it only activates for candidates `applied` through the 08.6.1 path, so disabling `Healing:Apply` also starves this flow.
- Monitoring: canary queue age, `canary_state` distribution, rollback count per project (feeds the rollback-rate metric in 08.8.2 and the rollback drill evidence for 08.8.3-T1).
- Rollback: this story *is* the rollback; if the rollback task itself fails, `healing_rollback` absence + `dead_letter` alerting (00 §5.3) surfaces it to operators for the manual path.
