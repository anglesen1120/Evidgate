## 1. Goal and non-goals

**Goal.** Give the program a single, auditable pass/fail decision for each phase boundary: the **V2 gate** (every forbidden case in the evaluation set blocked, reproducible validation, hash-bound review, a successful rollback drill) before M4's V2 healing PR flow is trusted, and the **V3 gate** (a severity-weighted false-heal threshold agreed by the owner, O6, plus an independent evaluation) before 08.9.1's narrow-context reuse is allowed to run.

**Non-goals.** Computing the metrics the gates read (08.8.2); building the evaluation corpus (08.8.1); the reuse feature itself (08.9.1, which only *reads* this story's V3 gate result); deciding O6's actual numeric threshold (an owner + QA-lead decision, DECISIONS §8) — this story only builds the mechanism to store and enforce whatever value is agreed, and fails closed while it is unset.

## 2. User stories and acceptance criteria

- As the Tech Lead, I run the V2 gate at the end of M4 and get one pass/fail report citing every forbidden case, the reproducibility check, the hash-binding audit and the rollback drill, so the M4 exit decision is evidence-based, not a vibe check.
- As the owner, I set the V3 false-heal threshold once O6 is decided, and reuse (08.9.1) simply cannot start until an independent evaluator confirms the measured rate is under it.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/healing/phase-gates/v2/evaluate` checks: (a) every `evaluation_case` with `source = 'seeded_fixture'` (the seven named forbidden cases, 08.8.1) has an actual validator verdict `= 'reject'`; (b) the two `candidate_validation` rounds for the same candidate/digest/fixture/env agree (reproducibility); (c) every `approved` candidate audit row has non-null `candidate_hash` and `base_commit` (hash-bound review); (d) a successful rollback drill (08.6.2/08.6.3) is recorded within the configured freshness window |
| AC2 | All four V2 checks pass ⇒ `healing_phase_gate_result { gate: 'v2', passed: true }` is written; any single check failing ⇒ `passed: false` with a `reasons[]` entry per failed check (`forbidden_case_not_blocked`, `non_reproducible_validation`, `unbound_approval`, `rollback_drill_missing`) |
| AC3 | `PUT /v1/projects/{p}/healing/phase-gates/v3/threshold` sets the O6-agreed `value`, `agreed_by`, `agreed_at`; absent this row, `POST .../v3/evaluate` always returns `passed: false, reasons: ["threshold_not_agreed"]` (fails closed) |
| AC4 | `POST /v1/projects/{p}/healing/phase-gates/v3/evaluate` compares the latest severity-weighted `false_heal_rate` (08.8.2) against the agreed threshold; rate above threshold ⇒ `passed: false, reasons: ["threshold_exceeded"]` |
| AC5 | The V3 evaluate command rejects with `422 gate_evaluator_conflict` when `independent_evaluator` equals any `requested_by`/`edited_by`/approver recorded on the candidates in the report's sample (independence, T35 pattern applied to the gate) |
| AC6 | `GET /v1/projects/{p}/healing/phase-gates/{gate}/latest` returns the most recent result for `gate ∈ {v2, v3}`; `404` when none has been evaluated yet |

## 3. Contracts touched

- 00 §8.7 candidate/knowledge states are read-only inputs here (approval hash-binding, D3) — this story never mutates candidate or knowledge state, it only audits them.
- T35 pattern (approver ≠ author) is extended by analogy to "gate evaluator ≠ candidate author/approver" (AC5) — not a new permission rule in 00 §2, an application of the same independence principle to a new actor; flagged for the contracts owner to confirm or reject.
- Resolved (RECOMMENDATIONS O6, owner working default): the V3 gate scope is the severity-weighted false-heal threshold — critical and sensitive cases get no threshold path (a non-author reviewer always decides, DECISIONS §5.5); the gate passes only while the ~95 % upper bound of the false-heal rate is ≤ 2 % (high) / ≤ 5 % (medium, low), needing ≥ 150 / ≥ 60 labelled candidates with no false heal. This story stores the agreed values per project in `healing_phase_gate_config` and fails the V3 gate closed until one exists — matching the kill-switch-before-apply philosophy (T29). Per-project rather than platform-global storage: `healing_phase_gate_config` is not on the T3 platform-exception list, so it stays `org_id`-scoped like every other business table.
- Note: `healing_phase_gate_result.gate` is defined here as `text check (gate in ('v2','v3'))`; 08.9.2 extends this constraint to add `'mobile_v3'` in its own migration — recorded so a future reader of this file is not surprised by that later `ALTER TABLE`.

## 6. States and transitions

None beyond 00 §8.7 (read-only inputs). `healing_phase_gate_result` rows are immutable, append-only facts, never a state machine — a new evaluation always writes a new row (mirrors 08.8.2's report immutability).

## 7. Jobs and integrations

- Both evaluate commands run synchronously: bounded read queries over `evaluation_case`, `candidate_validation`, `healing_candidate`, `healing_metric_report`, and the 08.6.2/08.6.3 rollback-drill record, no network call in the transaction (P5).
- Consumed by: 08.9.1-T1's reuse matcher, which reads `healing_phase_gate_result(gate = 'v3', passed = true)` as its single precondition before generating a reuse candidate (cross-story contract, verified in 08.9.1's own test suite, not duplicated here); the M4/M5 exit-gate review process (00 §4) reads the V2/V3 results as its evidence.

## 11. Rollout

- No feature flag on the V2 gate: it is a reporting/decision tool consulted at the M4 exit review, not a runtime switch. The V3 gate's own safe default (fails closed until O6's threshold is set, AC3) is the effective flag — no separate toggle is needed.
- Monitoring: the M4/M5 exit review process reads `GET .../latest`; no automated alert beyond that manual gate.
- Rollback: revert the PR; gate results are advisory/audit rows only — reverting removes the mechanism, not any applied healing state, since 08.9.1 (the only consumer) is designed to fall back to normal generation when no passed V3 result exists.
