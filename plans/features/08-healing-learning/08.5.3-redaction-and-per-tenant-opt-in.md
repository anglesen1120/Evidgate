## 1. Goal and non-goals

**Goal.** Before any incident context leaves the tenant boundary toward an LLM provider, a versioned redaction pipeline removes secrets, credentials and personal-data patterns and writes a verifiable `redaction_report_hash`; provider use is per-tenant opt-in via a two-person flow (one `tenant_admin` requests, a *different* `tenant_admin` approves as the data-owner signatory, per TL ruling T64) that is revocable; a detected residual leak blocks the call, is audited, and the cross-border transfer evidence record needed by plan 11 is written.

**Non-goals.** The provider adapter, budget hard stop and `healing_llm_call` schema (08.5.1); untrusted-input delimiting and injection containment (08.5.2); the PDPL filings and impact assessment themselves (plan 11, this story only writes the evidence); redaction of stored incident context at capture time (08.1.2 already masks before insert — this story governs *egress* redaction).

## 2. User stories and acceptance criteria

- As a data owner, I approve one named provider for my organisation's healing calls — as a person distinct from whoever requested it — and can revoke that approval at any time, so no tenant data crosses the border without a genuine second signatory's consent.
- As the Tech Lead, I can prove no context reaches the provider before redaction: the egress boundary calls the pipeline first, every call carries a `redaction_report_hash`, and a simulated leak produces a blocked call plus an audit row, never an HTTP request; and I can prove opt-in is never a rubber stamp: the same person can never request and approve, a request that nobody approves never silently activates, and an abandoned request cannot block the provider for the org forever.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | With no `healing_optin` row in `active` state for the org/provider (none exists, or one exists only as `requested`), any candidate-generation call that would egress is refused before `HttpClient.SendAsync` runs: `healing_llm_call.status = blocked_no_optin`, audit row written, and (for the admin-facing preflight) HTTP 403 `healing_provider_not_approved` |

| AC4 | Revoking an `active` opt-in (`POST /v1/orgs/{o}/healing/optin-requests/{id}/revoke`, state → `revoked`) makes the *next* call return the AC1 refusal; in-flight calls already dispatched are not recalled but consume no further budget; revocation is audited with actor + reason |
| AC5 | (T64a) Every opt-in needs two distinct `tenant_admin`s: `POST /v1/orgs/{o}/healing/optin-requests` records `requested_by`; `POST …/optin-requests/{id}/approve` requires `signatory_name`, `signatory_role`, `dpa_reference`, `transfer_assessment_reference` and transitions `requested → active` **only** when the caller differs from `requested_by` — the same person attempting to approve their own request gets 403 `approver_must_differ` and the row stays `requested` |

| AC7 | A `requested` row always has an exit that does not require the original requester's cooperation: `POST …/optin-requests/{id}/reject` (any `healing:configure` holder, including the requester themself as a self-withdraw, reason required) transitions `requested → rejected`; separately, `requested_expires_at` (set at creation) is checked **lazily** — the next command that touches that provider's row for the org (a new `request` attempt, `approve`, `reject`, or a `GET` list read) atomically flips a stale `requested` row to `expired` in the same transaction before proceeding — either way the provider becomes requestable again without any background job (the partial unique on `(org_id, provider)` only blocks while `state in (requested, active)`) |

Optimistic concurrency via `version` on each transition; no `If-Match` needed since each endpoint targets one `id` and enforces its own state-transition precondition (`approve`/`reject` require `state = requested`; `revoke` requires `state = active`).

## 6. States and transitions

`healing_optin`: `requested` (created by one `tenant_admin`) exits three ways — `→ active` (approved by a *different* `tenant_admin`, signatory fields recorded, T64a), `→ rejected` (explicit reject or self-withdraw, reason required), or `→ expired` (lazy: flipped by the next `request`/`approve`/`reject`/`GET` that touches the same `(org_id, provider)` row and finds `requested_expires_at` past, "silence is not consent", AC6/AC7); `active → revoked`. A `requested` row never auto-transitions to `active` — no schedule, no default, no elapsed-time rule ever grants approval; the only elapsed-time-driven transition is the *negative* one, to `expired`, and it fires opportunistically rather than on a schedule. `rejected`/`expired`/`revoked` are all terminal and all free the provider for a new request (the partial unique only holds while `state in (requested, active)`). Re-request after any terminal state creates a new row (history kept, prior rows immutable). `healing_llm_call.status` gains `blocked_no_optin` and `blocked_leak` as terminal non-billing statuses (no provider tokens/cost recorded). No candidate state change.

## 7. Jobs and integrations

- Runs inside the `08.5.1` LLM gateway flow (typed `HttpClient` + resilience handlers, P6): order is `AssertProviderApproved` → `RedactContext` (report persisted in the same transaction that writes `healing_llm_call`) → egress → `cross_border_transfer_evidence` insert on success.
- Lazy expiry, no schedule: `RequestHealingOptIn`, `ApproveHealingOptIn` and `RejectHealingOptIn` each run a targeted `UPDATE healing_optin SET state='expired', closed_at=now(), close_reason='expired' WHERE org_id=@org AND provider=@provider AND state='requested' AND requested_expires_at < now()` before their own logic, in the same write transaction — a stale request is physically closed by whichever *command* next touches it. `GetHealingOptIn` never writes (C1): it only computes the expired view for display.
- Consumed by 11.4.1 (security/compliance reporting reads `cross_border_transfer_evidence` + `healing_redaction_report`) and by 12 usage reconciliation (`healing_llm_call` rows, T30).
- Purge of closed (`rejected`/`expired`/`revoked`) rows follows tenant deletion (plan 11); no separate retention sweep for the rows themselves.

## 11. Rollout

- Ship behind the same healing availability resolution (T33): with no `active` opt-in the gateway fails closed, so enabling the story is safe by default; first provider approval is an explicit two-`tenant_admin` act per org (one requests, a different one approves and signs).
- Monitoring: counter `healing_llm_call` by `status` (blocked calls alert), `cross_border_transfer_evidence` rows reconciled by plan 11.
- Rollback: revoke opt-in per org (data kept); dropping the migration is unnecessary — tables stay empty without approvals.
