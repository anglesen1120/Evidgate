## 1. Goal and non-goals

**Goal.** Every verified failure of a required case in a frozen evidence revision produces exactly one `incident` row keyed `(org_id, run_id, execution_key)`, linked to run, first failing attempt, case and case revision; failed retries attach as `incident_attempt` rows on that incident; the incident starts `state = open`, `context_state = pending` (T31); the linkage columns are immutable once written.

**Non-goals.** Context payload columns (error text, DOM/a11y/trace refs, `content_hash`, fingerprint) — 08.1.2-T1's migration; `incident_label` and the label endpoint — 08.2.2; retrieval — 08.2.1; candidates — 08.3.1; the web triage screen — 09.4.1.

## 2. User stories and acceptance criteria

- As a QA engineer, I see one incident per failed required case after a run freezes, so triage starts from a deduplicated list, not from raw attempt noise.
- As the Tech Lead, I know retries never fork incident identity and the failure linkage cannot be edited, so downstream healing evidence is trustworthy.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Freezing an evidence revision with two failed required executions creates exactly two `incident` rows (`unique (org_id, run_id, execution_key)`, T34), each `state = open`, `context_state = pending` |
| AC2 | A failed attempt 2 on the same `(org_id, run_id, execution_key)` inserts an `incident_attempt` row on the existing incident — never a second incident |
| AC3 | Re-delivering the same freeze event (at-least-once delivery, A10) creates no duplicate rows; the task handler is idempotent on `(org_id, run_id, evidence_revision)` |
| AC4 | `GET /v1/incidents/{i}` for another tenant's id returns 404; `GET /v1/projects/{p}/incidents` under another tenant returns zero of this tenant's rows (RLS, 00 §5.4.7) |
| AC5 | `UPDATE` of linkage columns (`run_id`, `attempt_id`, `case_id`, `case_revision_id`, `execution_key`, `project_id`) as the app role fails; `state`/`context_state` transitions and `version` bumps still succeed (C6: immutability in SQL, not only in the domain) |
| AC6 | `GET /v1/projects/{p}/incidents` honours `?cursor=&limit=` keyset pagination on `(created_at, id)` and filters `state` and `execution_key` (00 §9.1) |
| AC7 | Incident creation runs in the worker on a queued `task` row: the evidence-freeze commit of 05.3.2-T5 is not delayed by healing work (NFR-08-1) |
| AC8 | A failed required execution on a run with `purpose = replay` (05.2.1-T5) creates no incident and no `incident_attempt` row — the recorder reads `run.purpose` and skips replay runs entirely (ruling T67) |

## 4. Data model and migrations

`migrations/NNNN_healing_incident.sql` (DbUp, forward-only, applied by `Evidgate.Migrator` as owner role):

- `incident`: `id uuid` (UUIDv7, app-generated), `org_id uuid not null`, `project_id uuid not null`, `run_id uuid not null`, `attempt_id uuid not null` (first failing `case_attempt`), `case_id uuid not null`, `case_revision_id uuid not null`, `execution_key text not null`, `engine text not null` (denormalised adapter engine family from the run's manifest, e.g. `playwright`, for retrieval filtering in 08.2.1), `state text not null default 'open' check (state in ('open','triaged','closed'))`, `context_state text not null default 'pending' check (context_state in ('pending','complete','partial'))`, `created_at`, `updated_at`, `version int not null` (optimistic concurrency, C4).
- Constraints: `unique (org_id, id)` (T3); `unique (org_id, run_id, execution_key)` (T34); composite FKs `(org_id, project_id)` → `project`, `(org_id, run_id)` → `run`, `(org_id, case_id)` → `case`, `(org_id, case_revision_id)` → `case_revision`, `(org_id, attempt_id)` → `case_attempt` (00 §5.4.1).
- Indexes: `(org_id, project_id, created_at desc, id)` covering the AC6 keyset list; `(org_id, project_id, state)` for the triage filter (P4 — same migration).
- `incident_attempt`: `id`, `org_id`, `incident_id`, `attempt_id`, `attempt_no int`, `result text` (normalised status per 00 §8.3), `created_at`; `unique (org_id, id)`; `unique (org_id, incident_id, attempt_id)`; composite FK `(org_id, incident_id)` → `incident (org_id, id)`, `(org_id, attempt_id)` → `case_attempt`.
- RLS: `FORCE ROW LEVEL SECURITY`, policy `org_id = evidgate.current_org_id()` on both tables (T2); immutability trigger `BEFORE UPDATE` rejects changes to the linkage columns for the app role (C6).
- Audit: every `state`/`context_state` write goes through the 02 audit row (actor, action, object id, `request_id`, hash chain per T8).

## 5. API shapes (commands, queries, endpoints)

| Shape | Kind | Endpoint / trigger | Permission | Result |
|---|---|---|---|---|
| `RecordIncidentsForEvidenceRevision` | `ICommand<int>` (internal) | worker `task` row, fired by the freeze integration event from 05.3.2-T5 | system identity, not HTTP | rows written count; idempotent |
| `ListIncidents` | `IQuery<Page<IncidentListItem>>` | `GET /v1/projects/{p}/incidents?cursor=&limit=&state=&execution_key=` | `healing:triage` | 200 `{items, next_cursor}` |
| `GetIncident` | `IQuery<IncidentDetail>` | `GET /v1/incidents/{i}` | `healing:triage` | 200; 404 unknown or other-tenant id |

Rules: the command runs inside the C2 pipeline in the worker (telemetry → tenant tx → handler → commit; validation/idempotency steps are no-ops for internal dispatch); queries are Dapper over a module-owned `incident_list` view in a read-only transaction (C1, C5). Errors per 00 §9.2: 403 on project/scope mismatch, 422 on an invalid `state` filter value. The select of failed required executions excludes runs where `run.purpose = 'replay'` (05.2.1-T5, T67) before any insert. The command emits outbox `incident.created` per new incident (C7) for the rule-triage task (08.2.2-T2).

## 6. States and transitions

- `incident.state`: `open → triaged(label) → closed` (00 §8.7). This story writes only `open`; `triaged` is written by 08.2.2-T3; `closed` by the human close action / terminal candidate handling (later story). Enum covers all three values.
- `incident.context_state`: `pending → complete | partial` (T31). This story writes `pending`; settlement is 08.1.2-T5.
- `incident_attempt` rows are append-only; a retry never moves `state`.

## 7. Jobs and integrations

- Consumed: evidence-freeze integration event (05.3.2-T5) → outbox → `task` row `record_incidents` keyed `(org_id, run_id, evidence_revision)`; any worker may claim it (`FOR UPDATE SKIP LOCKED`, 00 §5.3); delivery at-least-once → handler is idempotent via the `(org_id, run_id, execution_key)` unique + `ON CONFLICT DO NOTHING` on `incident_attempt`.
- Replay guard (T67): the handler reads `run.purpose` (05.2.1-T5) before selecting failed executions; `purpose = replay` runs are skipped entirely — no `incident`/`incident_attempt` row is ever written for them.
- Batch write: one `INSERT … SELECT FROM unnest(@arrays)` per revision (P2), failures of required cases only (a skipped/blocked case is not a failure — those stay completeness reasons, 00 §8.5).
- Produced: `incident.created` outbox rows consumed by 08.2.2 rule triage.

## 11. Rollout

- No feature flag: incident recording is additive worker-side work; the two endpoints are read-only. Migration is expand-only and safe to ship before consumers.
- Merge order: T1 (schema + recorder) → T2 (API). One PR series on `develop`.
- Monitoring: `task` dead-letter depth for `record_incidents`, `incident_created_total` counter, outbox lag (00 §11 operational SLIs).
- Rollback: stop the consumer registration and revert the PR; tables are inert without the writer; a separate contract migration would remove them only if the story is abandoned.
