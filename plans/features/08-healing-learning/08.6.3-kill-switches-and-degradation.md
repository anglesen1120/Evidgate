## 1. Goal and non-goals

**Goal.** System/tenant/project kill switches that persist only `enabled | shadow | disabled`, resolve (most restrictive wins) to `enabled | shadow | disabled | unavailable` where `unavailable` is a derived, never-settable outcome of dependency health; the switch exists and takes effect **before** any apply capability ships (T29 — this is why 08.6.1-T1 depends on 08.6.3-T1); this story is the **sole owner** of `healing_switch` (migration + commands + resolver — 08.3.3 consumes only) and enforces a V1 mode clamp: `mode = enabled` is rejected until the V2 apply capability (08.6.1) is live, so V1 tenants can only choose `shadow`/`disabled`; when the LLM gateway or knowledge store fails, ingestion, evaluation and the release gate keep running unaffected and healing simply resolves `unavailable`.

**Non-goals.** The apply/approve path itself (08.6.1, which depends on this story); the LLM gateway's own retry/timeout handling (08.5.1, this story only reads its health); the operations runbook content beyond the drill hookup (10.7.1 owns the runbook, this story owns the drill test and alerting wiring).

## 2. User stories and acceptance criteria

- As an operator, I can set a system-wide, per-tenant, or per-project healing mode, and the most restrictive of the three always wins, with no way to ever set `unavailable` by hand.
- As the Tech Lead, I can prove the switch existed and was enforced before any approve/apply code shipped — 08.6.3-T1 has no dependency on 08.6.1, only the reverse.
- As an SRE, when the LLM provider or the knowledge store is down, ingest and the release decision are completely unaffected; healing alone reports `unavailable`, and an alert fires.
- As a pilot tenant admin, I can set `disabled` during the V1 pilot (08.6.3-T1 ships in M3) and immediately stop shadow candidate generation and any LLM/replay calls, even though approve/apply itself only exists from M4 (08.6.1).

## 4. Data model and migrations

`migrations/NNNN_healing_switch.sql`:

| Table | Columns / constraints |
|---|---|
| `healing_switch` | `id uuid pk`, `scope text not null check (scope in ('system','tenant','project'))`, `org_id uuid` (**NULL exactly when `scope='system'`** — `check ((scope='system') = (org_id is null))`, T72), `project_id uuid` (null unless `scope='project'`), `mode text not null check (mode in ('enabled','shadow','disabled'))`, `reason text`, `set_by uuid not null`, `at timestamptz not null`, `created_at`, `updated_at`, `version`; `unique (org_id, id)` (T3) on the tenant-scoped rows; partial uniques: `unique (scope) where scope='system'`, `unique (org_id) where scope='tenant'`, `unique (org_id, project_id) where scope='project'` — at most one live row per scope key; composite FK `(org_id, project_id)` → `project (org_id, id)` when `scope='project'`; RLS `USING (org_id IS NULL OR org_id = evidgate.current_org_id()) WITH CHECK (org_id = evidgate.current_org_id())` (T72 — the NULL row is readable by every tenant, writable by no app role) |

Index: `healing_switch (scope, org_id, project_id)` — already the uniqueness index, serves the resolution read directly (single covering lookup, P4).

No table for `unavailable`: it is computed at read time from `IHealingDependencyHealth`, never stored (T33 — storing it would let it be "set").

## 5. API shapes (commands, queries, endpoints)

| Operation | Type | Endpoint | Permission | Codes |
|---|---|---|---|---|
| `SetHealingSwitch` | `ICommand<SwitchResult>` | `PUT /v1/healing/switch` (tenant/project scope only — `scope=system` → 403 `forbidden_scope`, T72); `POST /internal/operator/healing/switch` (system scope, operator ingress, platform-operator role, audited) | `healing:configure` (tenant) / platform operator (system) | 200; 403 `forbidden_scope`; 422 `invalid_switch_mode`; 422 `mode_not_available` (`mode = enabled` while the `Healing:Apply` flag is off, V1 clamp); `Idempotency-Key` required; optimistic concurrency via `version` (no `If-Match` needed — single-row-per-scope upsert) |
| `GetHealingSwitch` | `IQuery<ResolvedSwitchView>` | `GET /v1/healing/switch` | `healing:triage` | 200 `{system, tenant, project, resolved, dependency_health: {llm, knowledge_store}}` |
| `ResolveHealingAvailability` | internal `IHealingAvailabilityResolver` (not an endpoint) | called by every healing command handler (candidate mint, approve, canary, generation) at the top of C2's handler step | — | in-process resolution reused everywhere — one source of truth |

`ResolveHealingAvailability` reads the three `healing_switch` rows (one indexed query, P2/P3: a single `SELECT … WHERE org_id = @org OR scope='system' OR (project_id=@project)` returns ≤ 3 rows, no per-row loop) plus `IHealingDependencyHealth.IsHealthy()` (in-memory circuit-breaker state, no network call — P5) and picks the most restrictive of the three persisted modes, downgrading to `unavailable` if unhealthy and the persisted resolution would otherwise be `enabled`/`shadow`.

## 6. States and transitions

Persisted: none of `healing_switch`'s three scope rows have their own lifecycle beyond upsert (mode changes in place, `version` bumped). Resolved (computed, not stored): `enabled | shadow | disabled | unavailable`, per 00 §8.7. Every persisted change is audited via the command's own outbox row (no separate history table needed — `updated_at`/`version` plus the outbox event `healing.switch_changed` cover it, matching NFR-08-4).

## 7. Jobs and integrations

- No background task of its own; the resolver is a pure read used synchronously by every healing command (08.1–08.7) — this is why 08.6.1-T1 and every mint/approve/canary path depends on this story shipping first (T29).
- `IHealingDependencyHealth` for the LLM side reads 08.5.1's existing circuit-breaker/resilience-handler state (no new health-check network call, P5/P6); for the knowledge store it uses a cheap `SELECT 1` against the module's own connection pool with a short timeout, cached for a few seconds to avoid a query per healing call (P1).
- 10.7.1-T5 runbook entry + alert rule (Prometheus/OTel counter `healing_availability{resolved}` sampled by the health probe) — this story wires the metric, 10.7.1 owns the alert threshold and runbook prose.

- **Authorization:** `PUT /v1/healing/switch` needs `healing:configure`, `GET` needs `healing:triage` (permission catalogue 0010), both checked by the pipeline before the handler; `scope=system` is refused on `/v1` (403 `forbidden_scope`) and written only on `POST /internal/operator/healing/switch` behind the fail-closed operator gate.
- **Telemetry:** every tenant/project change writes an audit row and a `healing.switch_changed` outbox event; every operator system write emits one structured log event (mode, set_by, version, never the reason); the `healing_availability{resolved}` gauge belongs to 08.6.3-T2.
- **Failure path:** a refused mode answers 422 (`invalid_switch_mode`, `mode_not_available`), a foreign or deleted project 404, a system scope on `/v1` 403; a denied or unauthenticated operator call answers 401/403 and writes nothing; every refusal leaves the stored rows unchanged.

## 11. Rollout

- No feature flag needed for the switch endpoints themselves: they exist and are reachable from V1/M3 on. The `Healing:Apply` flag governs only the *mode value* (`enabled` clamped off until 08.6.1 ships) and, separately, 08.6.1's own apply-route registration — one flag, two consumers, no circular dependency since 08.6.3 only reads it.
- 08.6.3-T1 ships in V1/M3 with the pilot itself (00 §9.3 lists the switch endpoint as V1): pilot tenants can set `shadow`/`disabled` from day one, well before the V2/M4 apply path exists; `enabled` stays clamped off (422 `mode_not_available`) until the `Healing:Apply` flag turns on with 08.6.1 in M4. 08.6.3-T2/T3 (degradation, drill) stay V2/M4 alongside the LLM gateway they degrade. 08.6.1 still ships fully on only after this story is on, exactly per T29.
- Monitoring: `healing_availability{resolved}` gauge, switch-change audit events, degradation alert wired to 10.7.1's on-call rotation.
- Rollback: setting system scope to `disabled` (via `POST /internal/operator/healing/switch`, T72) is the universal rollback for any healing incident — no deploy needed, takes effect on the next resolution read (AC5).
