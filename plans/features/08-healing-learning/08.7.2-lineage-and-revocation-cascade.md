## 1. Goal and non-goals

**Goal.** Every `healing_candidate` and `knowledge_record` row carries its full lineage (rule/model/prompt version, retrieved record ids, patch hash, validation run ids), queryable from the candidate detail view (T1); revoking a `knowledge_record` marks every still-open candidate that depended on it and stops the record from being returned by retrieval or reuse, and tenant deletion removes it (T2).

**Non-goals.** Writing the `knowledge_record` on `applied` (08.7.1-T1); feedback labels and the `reverted` detection (08.7.1-T2); the narrow-context reuse policy itself (08.9.1); LLM call metering (08.5.1); changing a candidate's own state machine (00 §8.7) — revocation of a *knowledge record* never forces a dependent *candidate* into its own `revoked` exit state; that remains a separate, explicit action (08.6.2).

## 2. User stories and acceptance criteria

- As a `test_maintainer`, I open a candidate and see exactly which prior knowledge, rule/model/prompt version and validation runs produced it, so I can judge whether to trust it.
- As a `tenant_admin`, I revoke a knowledge record that turned out wrong, and every in-flight candidate that used it is flagged before I have to hunt for it manually.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `GET /v1/healing/candidates/{c}` response includes `lineage: { rule_version, model_version, prompt_version, retrieved_record_ids: [], patch_hash, validation_run_ids: [] }`; a candidate generated without retrieval returns `retrieved_record_ids: []`, never `null` |
| AC2 | `POST /v1/healing/knowledge/{k}/revoke` (permission `healing:revoke`, `Idempotency-Key` required) sets `knowledge_record.state = 'revoked'` and returns `200 { id, state: "revoked" }` |
| AC3 | In the same transaction as AC2, every `healing_candidate` row in the org whose `lineage.retrieved_record_ids` contains `k` and whose `state` is not `applied`, `rejected`, `expired` or `revoked` is updated with `depends_on_revoked_knowledge = true`; `healing.candidate_changed` is emitted once per affected candidate |
| AC4 | A `healing_candidate` already `applied`, `rejected`, `expired` or `revoked` is never updated by the cascade (its `depends_on_revoked_knowledge` stays as it was) |
| AC5 | A revoked `knowledge_record` is never returned by the 08.2.1 retrieval query (`WHERE state = 'active'`) — an integration test seeds one revoked and one active record and asserts only the active one comes back |
| AC6 | Revoking an already-`revoked` record is idempotent: `200 { id, state: "revoked" }`, no error, no duplicate cascade update or duplicate `healing.candidate_changed` |
| AC7 | `POST /v1/healing/knowledge/{k}/revoke` for a `k` belonging to another org returns `404` (never `403`, 00 §9.1) |

## 3. Contracts touched

- 00 §8.7 knowledge record state `active → revoked` (unchanged) and candidate states `proposed → validated → approved → applied` with exits `rejected | insufficient_evidence | expired | revoked` (unchanged) — this story never conflates the two: the cascade sets a flag column on candidates, it never drives a candidate into its own `revoked` exit.
- 00 §5.4 tenancy: `knowledge_record` and `healing_candidate` stay `org_id`-scoped, RLS, composite FK, `unique (org_id, id)` (T3).
- Resolved (T65): `POST /v1/healing/knowledge/{k}/revoke` (`healing:revoke`, `test_maintainer`, audited, cascades per this story) is an accepted additive endpoint — the same pattern as T56's additive reads, applied here to an additive write. It enters `contracts/openapi.yaml` with this story; no area-plan follow-up remains.

## 4. Data model and migrations

`migrations/0141_healing_candidate_lineage_fields.sql` — on `healing_candidate` (owned by `healing` module, extends the 08.3.1/08.7.1 table):

| Column | Type | Notes |
|---|---|---|
| `retrieved_record_ids` | `uuid[] not null default '{}'` | ids of `knowledge_record` rows read by the 08.2.1 retrieval query when this candidate was generated |
| `validation_run_ids` | `uuid[] not null default '{}'` | ids of `candidate_validation` rows for this candidate |
| `depends_on_revoked_knowledge` | `boolean not null default false` | set by the revoke cascade (T2); never cleared automatically — a human must re-review |

Index (serves the cascade lookup and P4): `create index ix_healing_candidate_retrieved_record_ids on healing_candidate using gin (retrieved_record_ids);`

No change to `knowledge_record`'s columns (state, `source_candidate_id` already exist per area plan §4.1); its `unique (org_id, id)` and RLS are already in place from 08.7.1-T1.

`patch_hash` in the lineage response is not a stored column: it is the `artifact.checksum` of `healing_candidate.patch_artifact_id` (artifact kind `patch`, T20), read by a join in the lineage query — no duplicated hash column, avoiding a second source of truth.

## 5. API shapes (commands, queries, endpoints)

| Command | Endpoint | Permission | Notes |
|---|---|---|---|
| `RevokeKnowledgeRecordCommand(OrgId, KnowledgeRecordId, Reason)` | `POST /v1/healing/knowledge/{k}/revoke` | `healing:revoke` | `Idempotency-Key` required (00 §9.1); one UPDATE sets `state='revoked'` (no-op if already revoked) then one `UPDATE … RETURNING id` for the cascade (P2, single round trip) then one `INSERT … SELECT` of outbox rows from the returned ids |

| Query | Endpoint | Permission | Notes |
|---|---|---|---|
| `GetHealingCandidateQuery` (extended) | `GET /v1/healing/candidates/{c}` | `healing:triage` | Dapper, read-only tx; projects `lineage` by joining `candidate_validation` (for `validation_run_ids`) and `artifact` (for `patch_hash`); one statement, no N+1 (P3) |

Errors: `404` other-tenant or unknown `k`/`c` · `400 validation_failed` missing `Idempotency-Key` on the revoke command (00 §9.1 general rule: mutations with side effects require it).

## 6. States and transitions

Unchanged from 00 §8.7. `depends_on_revoked_knowledge` is a boolean audit flag, not a state; a candidate carrying it can still move through its normal states (a human may still approve it after reviewing the flag) — this is intentional: the flag informs review, it does not block it.

## 7. Jobs and integrations

- The cascade (AC3) runs synchronously inside the revoke command's transaction — no async job, no network call in the transaction (P5).
- T2's tenant-deletion coverage is a `task`-queue consumer, natural key `org_id`, subscribed to the org-deletion outbox event emitted by the operator deletion flow (`POST /internal/operator/orgs/{o}/deletion`, T16, owned outside this module): on delivery it sets every `knowledge_record` for the org to `revoked` and clears `retrieved_record_ids`/`validation_run_ids` on every `healing_candidate` for the org (idempotent re-delivery: a second run finds nothing left to change).
- Consumed by: 08.9.1's reuse matcher (only reads `state='active'` knowledge records — AC5 is the guarantee it relies on); 09.5.1's review queue (renders `lineage` and `depends_on_revoked_knowledge`).

- Rollback: revert the PR; the cascade and revoke are data-only changes (no code path removed elsewhere), so rollback has no cleanup beyond the schema migration's `DOWN`.
