## 1. Goal and non-goals

**Goal.** Run the Playwright healer agent (F1 ✅) as one additional candidate generator, only inside the already-built replay sandbox (08.4.3), map its patched-file output into a `healing_candidate` diff artifact, feed it through the same allowlist validator (08.4.1) so `skip`/`fixme`/removal output is rejected, and regenerate the agent definitions on every Playwright version bump behind a compatibility gate.

**Non-goals.** The sandbox itself, leases and replay plumbing (08.4.3); the AST allowlist validator and its rules (08.4.1); the LLM gateway (08.5.1) — the healer is a local engine run, not a provider call; adopting healer output without validation (rejected in D2); merge or apply (08.6.1).

## 2. User stories and acceptance criteria

- As a test maintainer, locator drift that rules can't fix may be healed by the Playwright engine itself — but only inside the sandbox and under the same validator, so the healer is one generator among peers, not a privileged path.
- As the Tech Lead, I can prove healer output is never adopted raw: a generated `skip`/`fixme` is rejected by the same forbidden-pattern detector, and every Playwright dependency bump forces the agent definitions through the compatibility suite first.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A healer run executes only inside the sandbox job (one-shot identity, network allowlist, no tenant secrets — 11.2.1-T6 contract already owned by 08.4.3); invoking it outside the sandbox context fails with 422 `sandbox_required` and no candidate row |
| AC2 | On a locator-break fixture, a healer run produces a patch mapped to a `healing_candidate` with `patch_artifact_id` (kind `patch`, T20), `strategy = playwright_healer`, `base_commit`, `context_hash`, and the patch bytes uploaded as an artifact before the candidate row is visible |
| AC3 | Healer output containing `test.skip`/`test.fixme`, a removed or weakened assertion, or `force: true` is rejected by the 08.4.1 validator with the same `verdict = rejected` + `reason_code` taxonomy; the candidate exits `rejected` and the incident returns to triage |
| AC4 | Generation respects the shared bounds: ≤ 3 candidates per incident, atomic quota (`UPDATE healing_quota … WHERE used < cap RETURNING`, T32) and the wall-clock deadline; a healer run past deadline writes `insufficient_evidence` with the stop reason |
| AC5 | After a Playwright package bump, `scripts/regen-healer-agents.sh` regenerates `packages/healer-agents/definitions/` deterministically; `npm run test:healer-compat` (Vitest compatibility suite) must pass or the bump PR fails |

## 4. Data model and migrations

None new. `healing_candidate` already carries `strategy`, `patch_artifact_id`, `base_commit`, `context_hash`, `rule_version`, `model_version`, `prompt_version` (08 §4.1); for healer candidates `model_version` records `playwright@<version>` and `prompt_version` records `agents.version`. `candidate_validation` rows are appended by the existing validation path. No migration file in this story.

## 5. API shapes (commands, queries, endpoints)

| Operation | Type | Caller | Result |
|---|---|---|---|
| `RunHealerCandidate` | `ICommand<HealerRunResult>` | task-queue handler `healing.run_healer` (outbox row written by candidate mint, C7) | creates sandbox job + candidate row or writes `insufficient_evidence`/`rejected` transition |
| `MapHealerOutput` | internal step inside `RunHealerCandidate` | parses healer patch output (unified diff) | artifact upload (kind `patch`) + `patch_artifact_id`; unparseable output → `rejected`, `reason_code = healer_output_unusable` |
| Validator gate | reuses `08.4.1` `ValidateCandidate` command | after mapping, before `proposed → validated` | same verdict/reason taxonomy; `reject-skip-injected` named test applies verbatim |

No new REST endpoints. Errors surface on the candidate row (`verdict`, `reason_code`) and the incident view, not a new envelope.

## 6. States and transitions

Candidate lifecycle per 00 §8.7: `proposed → (validator) → validated` or exit `rejected` / `insufficient_evidence`. Healer-specific exit reasons: `healer_output_unusable`, `sandbox_required` (invocation guard). Replay results stay `shadow`-scoped: a healer candidate never appears on the run's official evaluation (00 §8.6, "candidate passes only in shadow → original decision kept").

## 7. Jobs and integrations

- `healing.run_healer` task row: natural idempotency key `(incident_id, base_commit, agents.version)`; claimed `FOR UPDATE SKIP LOCKED`; retry cap then `dead_letter` (00 §5.3). No DB lock held while the sandbox test runs (job/lease pattern).
- Sandbox job = the 08.4.3 executor with healer capabilities in its capability mask; network allowlist covers only the app-under-test and the pinned Playwright registry-free runtime (no npm egress inside the sandbox, S4).
- Playwright version source: `packages/adapter-playwright`'s pinned peer; `regen-healer-agents.sh` reads it so a bump without regeneration fails the compat gate.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |

| FR-08-12 | Healer output is untrusted data: it becomes a `patch` artifact and must pass the 08.4.1 validator like every candidate | AC3 `reject-skip-injected` on healer-originated output |
| T32 / NFR-08-3 | Same atomic quota update inside the mint transaction; healer minutes count as replay minutes against `replay_minutes_per_day` | AC4 quota test (cap reached → zero-row UPDATE stops minting) |
| T31 | Healer input context restricted to `ready` artifacts of the incident | context-gate test: `pending` artifact → generation skipped |

| S6/T40 | Agent definitions + Playwright pinned via `package-lock.json`; regen is deterministic, diff-checked in CI | AC5 gate |
| Retention | `patch` artifacts follow artifact retention (plan 06); `sensitive` per T57 project policy | existing retention tests |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Healer fixes a locator break | Vitest `healer-fixture.test.ts`: golden incident bundle → patched spec replays green in the sandboxed mini-suite |

| Removed/weakened assertion | `assertion_hash_before == assertion_hash_after` enforced on healer output; weakened-assertion fixture → `rejected` |

| Quota/deadline | Testcontainers: cap reached → atomic UPDATE returns 0 rows → `insufficient_evidence`, stop reason recorded |
| Deterministic regeneration | `npm run regen --check` diff-clean; Playwright bump without regen fails `test:healer-compat` |
| Mapping integrity | `MapHealerOutputTests`: unified diff → `patch` artifact; malformed diff → `healer_output_unusable` |

## 11. Rollout

- The healer is just another `strategy`: it inherits the healing availability switch (T33) — `shadow` mode means healer candidates validate but never propose; `disabled`/`unavailable` stops `healing.run_healer` at the task handler.
- Monitoring: candidates per `strategy`, validator rejection rate for `playwright_healer` (a spike after a Playwright bump means the compat gate missed something).
- Rollback: disable the strategy via the kill switch or a project `healing_rule`; no schema to revert.
