## 1. Goal and non-goals

**Goal.** Compute and persist, per project and period, the six FR-08-18 metrics — candidate precision, false-heal rate (adjudicated denominator, `unknown` reported separately), missed-bug rate, review rate, rollback rate, cost per accepted fix — from 08.8.1's adjudicated corpus and 08.7.1's feedback, applying the rule-of-three (≈ 3/n) whenever a metric's adjudicated event count is zero, and never presenting that bound as a model confidence score (rule 8, D4).

**Non-goals.** Building the evaluation corpus (08.8.1); the V2/V3 gate pass/fail decision (08.8.3, which reads this story's reports); rendering the report in the web UI (09, 12.5.1-T1); computing feedback labels themselves (08.7.1-T2, this story only reads them).

## 2. User stories and acceptance criteria

- As the Tech Lead, I generate a metric report for a period and get honest numbers with an explicit caveat when the sample is too thin to trust a raw rate, so I never mistake "zero observed failures" for "safe."
- As a `test_maintainer`, I see cost per accepted fix attributable to the LLM calls that actually produced it, so the pilot's healing spend is auditable.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/healing/metric-reports` for a `(corpus_id, period_start, period_end)` writes one `healing_metric_report` row with all six metrics, `unknown_count` and `sample_size` populated from adjudicated `evaluation_case` and `healing_feedback` rows in that period |
| AC2 | When a metric's adjudicated event count is `0`, the report sets `rule_of_three_applied = true` and `rule_of_three_bound = 3 / sample_size` for that metric instead of reporting a bare `0` rate |
| AC3 | `false_heal_rate`'s denominator excludes candidates whose only feedback label is `unknown`; `unknown_count` is a separate field, never folded into the rate or the denominator |
| AC4 | `cost_per_accepted_fix_cents` = `sum(healing_llm_call.cost)` for the org/project/period ÷ `count(candidates with feedback = 'accepted')`; when there are zero accepted fixes the field is `null` and `caveats[]` contains `no_accepted_fixes_in_period` — never a division by zero, never a misleading `0` |
| AC5 | Recomputing the same `(org_id, project_id, corpus_id, period_start, period_end)` creates a new `healing_metric_report` row, never an update to the existing one; both rows remain readable |
| AC6 | No field in the persisted report or its JSON response is named or documented as a "confidence"; a scanner test asserts this over the DTO |
| AC7 | `GET /v1/healing/metric-reports/{r}` for another org's report returns `404` |

## 3. Contracts touched

- DECISIONS §5 rule 8 and D4: the rule-of-three bound is a statistical honesty device, not a probability estimate; this plan enforces it structurally (AC6) rather than by convention alone.
- 00 §5.4.6 / T3: `healing_metric_report` is `org_id`-scoped, composite FK to `evaluation_corpus`, `unique (org_id, id)`, RLS.
- Resolved (T65): report generation reuses `healing:approve` (`test_maintainer`) — no `healing:evaluate` string is added.
- 00 §7 identifier contract: `healing_llm_call.cost` (already minted per call, T30) is the sole cost source — this story adds no second cost ledger, avoiding drift from 12's usage ledger.

## 4. Data model and migrations

`migrations/0152_healing_metric_report.sql` — `healing_metric_report`:

| `cost_per_accepted_fix_cents` | `bigint null` | `null` when zero accepted fixes (AC4) |

`unique (org_id, id)` (T3); index `ix_healing_metric_report_period on healing_metric_report (org_id, project_id, corpus_id, period_start, period_end)` serving lookup and recompute-detection (P4). RLS `org_id = evidgate.current_org_id()`.

## 6. States and transitions

None. A `healing_metric_report` row is create-once and immutable; recomputation creates a new row (§4, AC5) rather than transitioning a state.

## 7. Jobs and integrations

- Generation runs synchronously in the command's transaction: aggregate SQL over `evaluation_case`, `healing_feedback`, `healing_candidate`, `candidate_validation` and `healing_llm_call`, no network call inside the transaction (P5).
- Consumed by: 08.8.3-T1/T2 (reads the latest report for the gate decision); 12.5.1-T1 (rolls the same query into the pilot cost/quality dashboard, per area plan §10); 09.5.1 (candidate-level, not this report — no dependency).
