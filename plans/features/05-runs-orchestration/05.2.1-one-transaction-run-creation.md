## 1. Goal and non-goals

**Goal.** `POST /v1/projects/{p}/runs` locks the manifest, suite revision and environment revision (and the policy revision when one is active — the run-pinning handshake is 07.1.1-T4, M2), then writes `run` + `planned_execution` rows + one `producer_slot` registration per manifest shard (T9, via 04's `IProducerRegistry.RegisterSlotsAsync`) + the outbox row in a **single** tenant transaction before returning `201`. Same `Idempotency-Key` + same canonical payload returns the original run; a different payload returns `409 idempotency_conflict` (T11). No lost dispatch and no orphan run (D2).

**Non-goals.** The run state machine's later transitions beyond `created`/`queued` (05.3.1); finalize/reconcile (05.3.2); case attempt persistence (05.3.3); cancel (05.4.1); the actual `release_run` write-bind (05.6.1-T2 — see §3; this story only validates the `release` field); policy revision pinning logic itself (07.1.1); the `replay_grant` table (08.4.3 — this story validates the grant, it does not issue it).

## 2. User stories and acceptance criteria

- As a CI pipeline, I create a run once per manifest and get back the same run on a retried request, so a network retry never duplicates work.
- As the platform, I never have a run without its planned executions or its outbox row, so a crash mid-create never leaves an orphan.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Valid request (manifest id, optional release name, optional components) → `201 {run_id, state: "queued"}` — slots committed in the same transaction fire `created → queued` (T13), so the response state is always `queued` — with `run` + one `planned_execution` per manifest entry + one `producer_slot` per shard + one outbox row, all committed together |
| AC2 | A crash/exception after slot registration but before commit → **no** run row, **no** planned executions, **no** slots, **no** outbox row (single-transaction atomicity) |
| AC3 | Same `Idempotency-Key` + identical canonical payload → `201`/`200` with the **same** `run_id`, no new planned executions, no new slots |
| AC4 | Same `Idempotency-Key` + different canonical payload → `409 idempotency_conflict` |
| AC5 | Manifest referencing an environment/suite revision that does not resolve (already locked by 05.1.1/05.1.2 checks) → `422 manifest_invalid` before any write |
| AC6 | `execution_key = sha256(case_id ‖ variant_hash ‖ target_env)` is unique per `(org_id, run_id)`; a manifest with a colliding tuple → `422` at run create (not at reconcile) |
| AC7 | Producer slots are committed inside the create transaction → run state is `queued` immediately (T13), never left `created` |
| AC8 | A request naming `purpose: "replay"` without a valid, unexpired `replay_grant_id` issued by 08.4.3 and bound to this project → `422 replay_grant_invalid` (T67); `purpose` defaults to `regular`, is immutable, and is exposed on the run read model; a replay run never counts as regression |
| AC9 | `purpose: "replay"` combined with a `release` field → `422 replay_release_not_allowed` — a replay run is never bound to a release (T67) |
| AC10 | A request naming a `release` → the field is syntactically validated but at M1 resolves to `422 release_unresolvable` [DECISION]: the `release`/`release_component`/`release_run` tables land with 05.6.1 at M2, and 05.6.1-T2 owns the write-bind by digest match (T15; the area plan's task row says this story binds — see §3). Once 05.6.1 exists, naming a release delegates to its bind path; a non-matching digest is not bound |
| AC11 | The caller's OIDC claims are copied onto `run.ci_run_ref` (`provider`, `repository_id`, `run_id`, `run_attempt`) inside the create transaction; a caller whose token carries no CI claims (e.g. ingest-token exchange) → `ci_run_ref = null`. 04's `BindOrCheckAsync` compares `producer_slot.bound_ci_run_ref` against this stored reference (T88/T9) — a token from a different repository or workflow run can never claim the slot |
| AC12 | Deadlines are computed once at create and are immutable (T93): `collection_deadline_at` = `created_at + policy.collection_timeout` when a policy revision is pinned, else `created_at + EVIDGATE__Runs__DefaultCollectionTimeout` (default 2 h ⚠️ tuned ≈ p95 × 1.5); `late_window_minutes` is a snapshot copied from the pinned policy (default 24 h, T62) — no update path exists on either field |

`migrations/NNNN_orchestration_run.sql` (DbUp, owner role):

  id uuid primary key,
  org_id uuid not null,
  project_id uuid not null,
  manifest_id uuid not null,
  policy_revision_id uuid,               -- nullable: pinned by 07.1.1-T4 handshake when active
  suite_revision_id uuid not null,
  environment_revision_id uuid not null,
  test_commit text,
  ci_run_ref jsonb,                            -- T88: {provider, repository_id, run_id, run_attempt} from the caller's OIDC claims; null when absent
  components jsonb not null default '{}',
  parent_run_id uuid,

  purpose text not null default 'regular' check (purpose in ('regular','replay')),  -- T67

  version int not null default 0,        -- optimistic concurrency (C4)
  created_at timestamptz not null default now(),

  foreign key (org_id, manifest_id) references manifest (org_id, id),
  foreign key (org_id, suite_revision_id) references suite_revision (org_id, id),
  foreign key (org_id, environment_revision_id) references environment_revision (org_id, id),
  foreign key (org_id, policy_revision_id) references policy_revision (org_id, id),

create table planned_execution (
  id uuid primary key,
  org_id uuid not null,
  run_id uuid not null,
  execution_key text not null,

  unique (org_id, id),                                            -- T3
  unique (org_id, run_id, execution_key),                          -- AC6

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Notes |
|---|---|---|---|---|
| Command | `CreateRunCommand : ICommand<CreateRunResult>` → `CreateRunHandler` (EF Core 10 write model) | `POST /v1/projects/{p}/runs` | `run:create` | C2 pipeline (telemetry → validation → tenant tx → authorization → idempotency → handler → outbox → commit). Idempotency step reads/writes `idempotency_record (org_id, project_id, operation='run:create', key)` before the handler runs (§5.2.1-T2). Handler: lock manifest (by id, already immutable) + suite/environment/(policy) revisions by FK existence, compute `planned_execution` rows from the manifest's shard plan, call `IProducerRegistry.RegisterSlotsAsync` for one slot per shard, insert `run` (`state='queued'` when slots commit, T13) with `purpose`/`replay_grant_id` per T67, write the outbox row — all in the one transaction opened by C2. `release` is field-validated only (AC10, §3). 201 `{run_id, state: "queued", manifest_hash, purpose}` |

Create-time-only fields (T88, T93): `ci_run_ref`, `collection_deadline_at` and `late_window_minutes` are computed and written inside this handler and are never mutated afterward — no command other than create touches them (AC11, AC12).

Error codes (00 §9.2): `not_found` (404, other-tenant or unknown manifest), `manifest_invalid` (422, AC5), `execution_key_conflict` (422, AC6), `replay_grant_invalid` (422, AC8), `replay_release_not_allowed` (422, AC9), `release_unresolvable` (422, AC10), `idempotency_conflict` (409, AC4), `forbidden` (403 project-scope mismatch), `unauthenticated` (401).

Queries: none new — `GET /v1/runs/{r}` belongs to 05.3.1 (state machine story), not to run creation.

## 6. States and transitions

Implements only the entry of 00 §8.1: `created` (row committed) → `queued` when the manifest's producer slots are committed **inside the create transaction** (T13). `running`, `collecting`, `complete`, `incomplete`, `canceled` are out of scope (05.3.1, 05.3.2, 05.4.1). The `state` check constraint enumerates the full set now so no later migration widens it.

## 7. Jobs and integrations

- `Evidgate.Modules.Ingestion.Contracts.IProducerRegistry.RegisterSlotsAsync(runId, shardCount)` (04.1.2-T4) — in-process module call inside the same transaction (no network hop, P5).
- Outbox row (00 §5.3) — `run.created` integration event; consumed later by 05.3.1 (state watchers), 09 (UI list), 12 (usage/ledger via T50 batch metering — not triggered here, ingest owns metering).
- `idempotency_record` (01, T11) purge task (owner-owned `SECURITY DEFINER`) is out of scope; this story only reads/writes it.

- **Authorization:** `POST /v1/projects/{p}/runs` requires `run:create`, checked by the C2 authorization step after the tenant transaction opens (§5.5 C2/S2 row); a project-scope mismatch is `403 forbidden`, another tenant's manifest `404 not_found`.
- **Retention/deletion:** `run` and `planned_execution` rows hold no personal data and are deleted only with the tenant (Privacy/retention row); the `idempotency_record` row follows the ≥ 24 h idempotency retention of 01/T11.
- **Telemetry:** the C2 pipeline's telemetry step wraps the command (first in the order of the §5.5 C2/S2 row); the committed `run.created` outbox event (§7) is the durable trace of a create.
- **Failure path:** every write is in one transaction (§5.5 C1/C7/D2 row): any refusal (`manifest_invalid`, `execution_key_conflict`, `replay_grant_invalid`, `replay_release_not_allowed`, `release_unresolvable`, `idempotency_conflict`) or crash rolls back with no partial rows (AC2).
