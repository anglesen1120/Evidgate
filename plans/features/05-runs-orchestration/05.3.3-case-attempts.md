## 1. Goal and non-goals

**Goal.** Every executed attempt is persisted exactly once per `(org_id, run_id, execution_key, attempt_no)` with the raw status **as sent** plus the normalised status (00 §8.3); 04's event-batch commit writes the attempt row through 05's write interface inside the **same** transaction (T50 batch insert semantics); a failed setup marks dependant attempts `blocked`, never `passed` (FR-05-15).

**Non-goals.** The event batch/ingest transaction itself and its `unnest`/`ON CONFLICT` mechanics (04, T50 — this story only exposes the write interface 04 calls into); reconciliation/evidence-revision persistence (05.3.2); the suite dependency DAG's authored shape (03, `case_dependency` — this story only reads it to decide which attempts to block).

## 2. User stories and acceptance criteria

- As the reconciler, I read one immutable attempt row per executed case per run, so completeness comparison is deterministic.
- As a test author, a setup failure marks every case that depends on it `blocked` instead of silently missing, so a broken fixture never masquerades as a pass.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An event batch reporting a new `(run_id, execution_key, attempt_no)` → exactly one `case_attempt` row, `raw_status` stored verbatim, `normalized_status` computed per 00 §8.3 |
| AC2 | A second event reporting the same `(run_id, execution_key, attempt_no)` with a different payload → the whole batch rejected `422` at the event index (04's unique-key conflict), the attempt row **never rewritten** |
| AC3 | `normalized_status ∈ {passed, failed, skipped, timed_out, error, blocked}`; a raw status outside the known vocabulary still gets a row with `normalized_status = "error"` (unknown-status handling, never silently dropped) |
| AC4 | A failed setup attempt marks every dependant execution (per the suite's `case_dependency` DAG, 03) `blocked`; a dependant attempt is never marked `passed` after its setup failed |
| AC5 | `case_attempt` is visible only after 04's event batch commits (write-through-commit, no dirty read) |
| AC6 | Query by `(run_id, normalized_status)` and by `(case_id, started_at)` use their covering indexes (no sequential scan on the reconciler's completeness comparison) |

## 4. Data model and migrations

`migrations/NNNN_orchestration_case_attempt.sql` (DbUp, owner role):

```sql
create table case_attempt (
  id uuid primary key,
  org_id uuid not null,
  run_id uuid not null,
  job_id uuid,                      -- null in CI mode; set in agent mode (V2); FK deferred:
                                    -- `job` is created only by 05.7.2-T1 (V2, M4)
  execution_key text not null,
  case_id uuid not null,
  attempt_no int not null check (attempt_no >= 1),
  raw_status text not null,         -- verbatim as sent, never overwritten
  normalized_status text not null check (normalized_status in
    ('passed','failed','skipped','timed_out','error','blocked')),
  started_at timestamptz,
  finished_at timestamptz,
  duration_ms int,
  created_at timestamptz not null default now(),
  unique (org_id, id),                                                -- T3
  unique (org_id, run_id, execution_key, attempt_no),                 -- FR-05-15 identity
  foreign key (org_id, run_id) references run (org_id, id),
);
alter table case_attempt enable row level security;
alter table case_attempt force row level security;
create policy case_attempt_tenant on case_attempt
  using (org_id = evidgate.current_org_id()) with check (org_id = evidgate.current_org_id());
revoke update, delete on case_attempt from evidgate_app;  -- immutable per attempt (C6)

create index case_attempt_run_status_idx on case_attempt (org_id, run_id, normalized_status);  -- AC6 / reconciler
create index case_attempt_case_started_idx on case_attempt (org_id, case_id, started_at);       -- AC6 / history views
```

No update path exists: a corrected status is a **new** attempt row with the next `attempt_no` (retry), never an edit — consistent with T50's `ON CONFLICT DO NOTHING` semantics upstream in 04's event insert.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Notes |
|---|---|---|---|
| Internal command interface | `ICaseAttemptWriter.WriteAttemptAsync(runId, executionKey, attemptNo, rawStatus, timestamps)` — implemented by `WriteCaseAttemptHandler` | none (no public route; called by 04's `ProcessEventBatchHandler` inside its own tenant transaction) | Batch semantics inherited from the caller (04, T50): one `unnest`-array insert per batch, `ON CONFLICT (org_id, run_id, execution_key, attempt_no) DO NOTHING`, then a compare of returned ids vs requested ids to distinguish `accepted` from `duplicate_different_payload` (per-event ack, 00 §9.4) |
| Internal query | `IBlockedAttemptResolver.ResolveDependantsAsync(runId, failedExecutionKey)` | none | Reads `case_dependency` (03) for the failed case's dependants within the run's planned executions, returns the set to mark `blocked`; called by the same handler right after a `failed`-at-setup attempt commits |

No public endpoint in this story: `case_attempt` rows are read by 05.3.2 (reconciler, internal module call) and later by 09/07 through their own owned queries — out of scope here.

## 6. States and transitions

00 §8.3 (implemented exactly): raw status stored as sent; `normalized_status ∈ passed|failed|skipped|timed_out|error|blocked`; normalisation never overwrites the raw value. A failed setup marks dependants `blocked`, never `passed`. There is no per-row lifecycle beyond this one-shot classification at insert time — a "correction" is a new `attempt_no`, not a transition.

## 7. Jobs and integrations

- Called synchronously, in-process, from 04's event-batch commit handler (`ProcessEventBatchHandler`) — the write happens **inside** 04's transaction (FR-05-15's "same transaction" requirement), so `ICaseAttemptWriter` never opens its own connection/transaction (P5: no network call inside a DB transaction — this is a local method call, not a network hop).
- `Evidgate.Modules.Catalog.Contracts` (03) — read-only `case_dependency` DAG lookup for `blocked` propagation, same transaction.
- Consumed by 05.3.2 (reconciler completeness comparison), 06.5.1 (evidence freeze reads case-level outcomes), 07.4.1/07.4.2 (flaky-budget and retry policy read attempts).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| §5.4 T2, T3 | `org_id` + `unique (org_id, id)` + composite FKs to `run`/`job`, `FORCE RLS` | `CaseAttempt_CrossTenant_404`; 02.6.1-T2 lint |
| §5.5 C1/C7 | write happens only through the command interface inside the caller's transaction; no separate outbox (attempts are read synchronously by the reconciler, not event-driven) | architecture test: no public route for `case_attempt` writes |
| §5.5 C6 | immutable per attempt: no setters, `REVOKE UPDATE, DELETE`; corrections are new `attempt_no` rows | `CaseAttempt_UpdateDelete_Revoked` |
| §5.7 P2/T50 | attempt writes ride the same `unnest`-array batch insert as the event commit — no per-row loop; one statement per batch regardless of batch size | `WriteAttempt_BatchInsert_OneStatementPerBatch` (command counter) |
| §5.7 P3 | dependant-blocking lookup is one bounded query against `case_dependency` for the failed case's direct dependants (per suite DAG, not a graph walk over the whole suite) | `BlockedAttempt_CommandCounter_Bounded` |
| §5.7 P4 | `case_attempt_run_status_idx` and `case_attempt_case_started_idx` cover the two named query shapes (AC6) | query plan assertion in the integration test |
| §5.7 P5 | `ICaseAttemptWriter`/`IBlockedAttemptResolver` are in-process calls on the caller's connection (`Database.UseTransaction`), never a new network hop | code review + architecture test (no `HttpClient`/new `NpgsqlConnection` in the handler) |
| Privacy/retention | `raw_status`/timestamps are test-execution metadata, no personal data; deleted only with the tenant | RLS tests |
