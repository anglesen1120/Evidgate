## 1. Goal and non-goals

**Goal.** Every executed attempt is persisted exactly once per `(org_id, run_id, execution_key, attempt_no)` with the raw status **as sent** plus the normalised status (00 §8.3); 04's event-batch commit writes the attempt row through 05's write interface inside the **same** transaction (T50 batch insert semantics); a failed setup marks dependant attempts `blocked`, never `passed` (FR-05-15).

**Non-goals.** The event batch/ingest transaction itself and its `unnest`/`ON CONFLICT` mechanics (04, T50 — this story only exposes the write interface 04 calls into); reconciliation/evidence-revision persistence (05.3.2); the suite dependency DAG's authored shape (03, `case_dependency` — this story only reads it to decide which attempts to block).

## 2. User stories and acceptance criteria

- As the reconciler, I read one immutable attempt row per executed case per run, so completeness comparison is deterministic.
- As a test author, a setup failure marks every case that depends on it `blocked` instead of silently missing, so a broken fixture never masquerades as a pass.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An event batch reporting a new `(run_id, execution_key, attempt_no)` → exactly one `case_attempt` row, `raw_status` stored verbatim, `normalized_status` computed per 00 §8.3 |
| AC2 | A second event reporting the same `(run_id, execution_key, attempt_no)` with a different payload → the whole batch rejected `422` at the event index (04's unique-key conflict), the attempt row **never rewritten** |
| AC3 | `normalized_status ∈ {passed, failed, skipped, timed_out, error, blocked}`; a raw status outside the known vocabulary still gets a row with `normalized_status = "error"` (unknown-status handling, never silently dropped) |
| AC4 | A failed setup attempt marks every dependant execution (per the suite's `case_dependency` DAG, 03) `blocked`; a dependant attempt is never marked `passed` after its setup failed |
| AC5 | `case_attempt` is visible only after 04's event batch commits (write-through-commit, no dirty read) |
| AC6 | Query by `(run_id, normalized_status)` and by `(case_id, started_at)` use their covering indexes (no sequential scan on the reconciler's completeness comparison) |

## 4. Data model and migrations

`migrations/NNNN_orchestration_case_attempt.sql` (DbUp, owner role):

```sql
create table case_attempt (
  id uuid primary key,
  org_id uuid not null,
  run_id uuid not null,
  job_id uuid,                      -- null in CI mode; set in agent mode (V2); FK deferred:
                                    -- `job` is created only by 05.7.2-T1 (V2, M4)
  execution_key text not null,
  case_id uuid not null,
  attempt_no int not null check (attempt_no >= 1),
  raw_status text not null,         -- verbatim as sent, never overwritten
  normalized_status text not null check (normalized_status in
    ('passed','failed','skipped','timed_out','error','blocked')),
  started_at timestamptz,
  finished_at timestamptz,
  duration_ms int,
  created_at timestamptz not null default now(),
  unique (org_id, id),                                                -- T3
  unique (org_id, run_id, execution_key, attempt_no),                 -- FR-05-15 identity
  foreign key (org_id, run_id) references run (org_id, id),
);
alter table case_attempt enable row level security;
alter table case_attempt force row level security;
create policy case_attempt_tenant on case_attempt
  using (org_id = evidgate.current_org_id()) with check (org_id = evidgate.current_org_id());
revoke update, delete on case_attempt from evidgate_app;  -- immutable per attempt (C6)

create index case_attempt_run_status_idx on case_attempt (org_id, run_id, normalized_status);  -- AC6 / reconciler
create index case_attempt_case_started_idx on case_attempt (org_id, case_id, started_at);       -- AC6 / history views
```

No update path exists: a corrected status is a **new** attempt row with the next `attempt_no` (retry), never an edit — consistent with T50's `ON CONFLICT DO NOTHING` semantics upstream in 04's event insert.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Notes |
|---|---|---|---|
| Internal command interface | `ICaseAttemptWriter.WriteAttemptsAsync(runId, IReadOnlyList<CaseAttemptInput>)` (1..500 attempts) — implemented by `CaseAttemptWriter`; answers one `CaseAttemptWriteOutcome` per attempt (`Accepted`, `Duplicate`, `DuplicateDifferentPayload`, `UnknownExecution`, `Invalid`) | none (no public route; called by 04's event-commit handler inside its own tenant transaction) | Batch semantics inherited from the caller (04, T50): one statement per batch (`jsonb_to_recordset` expansion), `ON CONFLICT (org_id, run_id, execution_key, attempt_no) DO NOTHING RETURNING id`, then one bounded classification select only when some id was not returned, to tell a same-payload replay (`Duplicate`) from `DuplicateDifferentPayload` (per-event ack, 00 §9.4); the caller rolls back on any refusal outcome |
| Internal command interface | `IBlockedAttemptResolver.ResolveDependantsAsync(runId, failedExecutionKey)` → keys written | none | Reads the run's suite-revision dependency DAG through `ICatalogContracts.GetDependantsAsync` (transitive dependants of the failed member), keeps the dependants this run plans in the same `target_env` that have no attempt yet, and writes one `blocked` row (`attempt_no = 1`) for each in the caller's transaction; called by the same handler once it has decided a setup failed |

No public endpoint in this story: `case_attempt` rows are read by 05.3.2 (reconciler, internal module call) and later by 09/07 through their own owned queries — out of scope here.

## 6. States and transitions

00 §8.3 (implemented exactly): raw status stored as sent; `normalized_status ∈ passed|failed|skipped|timed_out|error|blocked`; normalisation never overwrites the raw value. A failed setup marks dependants `blocked`, never `passed`. There is no per-row lifecycle beyond this one-shot classification at insert time — a "correction" is a new `attempt_no`, not a transition.

## 7. Jobs and integrations

- Called synchronously, in-process, from 04's event-batch commit handler (`ProcessEventBatchHandler`) — the write happens **inside** 04's transaction (FR-05-15's "same transaction" requirement), so `ICaseAttemptWriter` never opens its own connection/transaction (P5: no network call inside a DB transaction — this is a local method call, not a network hop).
- `Evidgate.Modules.Catalog.Contracts` (03) — read-only `case_dependency` DAG lookup for `blocked` propagation, same transaction.
- Consumed by 05.3.2 (reconciler completeness comparison), 06.5.1 (evidence freeze reads case-level outcomes), 07.4.1/07.4.2 (flaky-budget and retry policy read attempts).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| §5.4 T2, T3 | `org_id` + `unique (org_id, id)` + composite FKs to `run`/`job`, `FORCE RLS` | `CaseAttempt_CrossTenant_404`; 02.6.1-T2 lint |
| §5.5 C1/C7 | write happens only through the command interface inside the caller's transaction; no separate outbox (attempts are read synchronously by the reconciler, not event-driven) | architecture test: no public route for `case_attempt` writes |
| §5.5 C6 | immutable per attempt: no setters, `REVOKE UPDATE, DELETE`; corrections are new `attempt_no` rows | `CaseAttempt_UpdateDelete_Revoked` |
| §5.7 P2/T50 | attempt writes are one batch insert (`jsonb_to_recordset` expansion of one `jsonb` parameter, see §10 T2 [DECISION] 2) in the caller's transaction — no per-row loop; one statement per batch regardless of batch size (a second bounded statement only classifies slots that were not inserted) | `WriteAttempt_BatchInsert_OneStatementPerBatch` (command counter) |
| §5.7 P3 | dependant-blocking lookup is one bounded recursive statement in 03 (`ICatalogContracts.GetDependantsAsync`: the transitive dependants of the failed member in the run's suite revision, `UNION` walk, cycle-safe, bounded by the revision's member count) plus one insert in 05; statement count is constant in plan size (§10 T2 [DECISION] 5) | `BlockedAttempt_CommandCounter_Bounded` |
| §5.7 P4 | `case_attempt_run_status_idx` and `case_attempt_case_started_idx` cover the two named query shapes (AC6) | query plan assertion in the integration test |
| §5.7 P5 | `ICaseAttemptWriter`/`IBlockedAttemptResolver` are in-process calls on the caller's ambient tenant scope (`ITenantDb`, §10 T2 [DECISION] 3), never a new connection, transaction or network hop | code review + `CaseAttempt_NotVisibleUntilBatchCommits` / `WriteAttempt_CallerRollbackLeavesNoRows` (the writer neither commits nor rolls back) |
| Privacy/retention | `raw_status`/timestamps are test-execution metadata, no personal data; deleted only with the tenant | RLS tests |

- **Authorization:** no public route exists for `case_attempt`; the only writer is 05.3.3-T2's internal `ICaseAttemptWriter`, called in-process by 04's event-commit handler inside the caller's tenant transaction, so every write carries the caller's tenant scope (`org_id` from the tenant scope, `FORCE RLS` on the table) and a producer can never write an attempt directly.
- **Retention/deletion:** rows are test-execution metadata with no personal data and are deleted only with the tenant (or by 06.4.6's partition drop); the app role holds no `DELETE` grant (`REVOKE UPDATE, DELETE`), so no application path removes an attempt.
- **Telemetry:** `evidgate_case_attempt_written_total{normalized_status}` and `evidgate_case_attempt_blocked_by_setup_total` land with T2 (the writer); no raw status value, case id or execution key is a metric label.
- **Failure path:** an unknown raw status still writes a row with `normalized_status = 'error'` (never dropped); a failed setup writes `blocked` rows for its dependants, never `passed`; a composite-FK or unique violation (`23503`/`23505`) is mapped by the 04 caller to a 422 per-event ack, and the whole batch rolls back with no partial rows.

### 05.3.3-T2 — Attempt write interface used by 04's event commit in the same transaction + `blocked` propagation (M)

| Sub-task | Work | Size | Done when |
|---|---|---|---|
| 05.3.3-T2.1 | `ICaseAttemptWriter.WriteAttemptsAsync`: batch insert riding 04's event-commit transaction (the ambient tenant scope's connection and transaction, `ITenantDb`), `ON CONFLICT DO NOTHING` + returned-id compare for duplicate detection (T50 semantics) | S | AC1, AC2, AC5 pass; `WriteAttempt_BatchInsert_OneStatementPerBatch` |
| 05.3.3-T2.2 | `IBlockedAttemptResolver.ResolveDependantsAsync`: read `case_dependency` (03) through `ICatalogContracts.GetDependantsAsync` for the failed case's dependants within the run's planned executions, write `blocked` rows for each, in the same transaction | S | AC4 passes; `WriteAttempt_FailedSetup_DependantsMarkedBlocked_NeverPassed` |

Notes (05.3.3-T2 delivery, S31): [DECISION] 1 — the writer is batch-shaped, `WriteAttemptsAsync(runId, attempts)`, not the scalar `WriteAttemptAsync` of the first §5 draft: T50 requires one statement per batch, and a one-attempt call is a batch of one. [DECISION] 2 — the batch travels as one `jsonb` text parameter expanded by `jsonb_to_recordset`, not `unnest` arrays: the tenant Dapper path refuses array parameters (precedent `OrchestratorSql.InsertPlannedExecutions`); the statement count is the same. [DECISION] 3 — "rides the caller's transaction" is `ITenantDb` on the ambient scope's connection and transaction (00 §5.5 C5, the Dapper path of every Orchestrator write), not an EF `Database.UseTransaction`; no connection, transaction, commit or rollback is ever opened by the writer. [DECISION] 4 — duplicate handling: the returned-id compare finds the slots that were not inserted, one select classifies them: same payload (`raw_status`, normalised status, timestamps, duration, `job_id`) is `Duplicate`, anything else is `DuplicateDifferentPayload`, a key with no planned row for a run visible to the scope is `UnknownExecution`; the same rule applies inside one batch (first occurrence wins). No unique violation is ever caught. A malformed attempt is `Invalid` with a closed `reason` token and a batch with an `Invalid`/in-batch conflicting attempt runs no statement; the caller MUST roll back on any `IsRefusal` outcome. [DECISION] 5 — `blocked` propagation (AC4, FR-05-15): transitive (every dependant of a failed setup, not only the direct ones; still one recursive statement in Catalog, cycle-safe through `UNION`, bounded by the revision's member count, so P3's "one bounded query" holds), only for dependants the run plans in the same `target_env` as the failed setup, only for dependants with no attempt yet, with `attempt_no = 1` and `raw_status = normalized_status = 'blocked'` (server-assigned, never a producer value); the resolver writes nothing unless the named execution has a `failed`, `timed_out` or `error` attempt in the run (which attempt of a retried setup is final is the caller's decision, 04.1.1/07.4.2); a repeated call writes nothing. A later producer attempt for a slot already holding a `blocked` row is `DuplicateDifferentPayload` (first writer wins, fail closed: a dependant never reads as passed after its setup failed). [DECISION] 6 — new read `ICatalogContracts.GetDependantsAsync(suiteRevisionId, caseRevisionId, variantHash)` (03's contract, additive) returns `DependantMember(CaseRevisionId, VariantHash)` pairs; Orchestrator maps them to its own `planned_execution` rows and never reads Catalog tables. Telemetry: `evidgate_case_attempt_written_total{normalized_status}` and `evidgate_case_attempt_blocked_by_setup_total` (no raw status, case id or execution key as label; counted when written inside the caller's transaction, a later rollback is not subtracted). Hand-overs from T1 (S29, security review): (a) `ext.xfail` — `CaseAttemptInput.Xfail` is documented as producer-asserted; the caller takes it only from the allow-listed `test.finished` `ext` — open for 04.1.1-T1 (04.1.1 plan §10 T1.4 Notes, "from S31"). (b) U+0000 in `raw_status` — met here: the writer refuses it (`Invalid`, `raw_status_invalid`, together with lone surrogates and values over 64 code points) before any statement; escaping control characters when rendering stays with the consumers (06/09). (c) first writer wins — met (`WriteAttempt_DuplicateDifferentPayload_422_NoRewrite`). (d) `case_id` equals the planned row's case — met (resolved from the planned row inside the insert); `job_id` still has no FK until 05.7.2-T1. (e) operator reads zero rows until 02.8.1's policy (T76) — unchanged. Open for 04.1.1-T1/T2: the caller must roll back on a refusal outcome, map `DuplicateDifferentPayload`/`UnknownExecution`/`Invalid` to the 422 per-event ack at the event index, and call the resolver once per setup it decides failed.

Notes (05.3.3-T2 review triage, S31): [DECISION] 7 — `ICaseAttemptWriter.MaxAttemptNo = 100`: the writer refuses a larger `attempt_no` (`Invalid`, `attempt_no_invalid`), so a producer cannot mint unlimited immutable slots per execution (the 0032 CHECK is only `>= 1`; this closes the bound that T1 hand-over (c) named).
