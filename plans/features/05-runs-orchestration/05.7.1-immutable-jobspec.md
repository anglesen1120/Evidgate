## 1. Goal and non-goals

**Goal.** Define the JobSpec — the single validated document an agent executes — as a JSON Schema in `contracts/`, a `job_spec` table addressed by `job_spec_hash` (`sha256:` over RFC 8785 canonical JSON), and a write path that can only insert identical-or-new rows: any change to repo/commit, suite revision, app digest, environment revision, engine family/version/image digest, timeouts, resource limits, secret references or artifact policy produces a different hash and a new row; no row is ever edited, and no field accepts a free-form command.

**Non-goals.** The `job`/`job_lease` tables and claim/heartbeat endpoints (05.7.2); capability matching and scheduling (05.7.3); the agent that executes the spec (05.7.4); job creation from a run (shipped with the claim path it feeds — 05.7.2-T1 wires `job.job_spec_hash`).

## 2. User stories and acceptance criteria

- As the platform, I address a job's instructions by content hash, so the spec an agent ran is exactly the spec that was approved — replayable and auditable.
- As a security reviewer, I can see that a `qa_engineer` can never smuggle a shell command, image or secret reference outside the declared adapter operations into execution.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `contracts/jobspec.schema.json` declares every field of FR-05-9/D6 (`repo`, `commit`, `suite_revision_id`, `app_digest`, `environment_revision_id`, `engine{family,version,image_digest}`, `queue_timeout_s`, `execution_timeout_s`, `limits{cpu_ms?/memory_mb,wall_clock_s}`, `secret_refs[]`, `artifact_policy{allow_paths[],max_bytes,kinds[],default_sensitivity}`, `run_namespace`); Corvus.Json.Validator accepts a valid spec and rejects each violated constraint with a schema path |
| AC2 | No field accepts a free-form command: `prepare`/`execute`/`collect`/`cleanup` entries are `{operation: enum, params: object constrained to typed fields}`; a spec containing `command`, `shell`, `script`, `cmd` or `args` string-arrays → validation 422 `jobspec_invalid` |
| AC3 | `IJobSpecWriter.WriteAsync(spec, run_id)` canonicalises (RFC 8785, `Evidgate.Canonicalization`), computes `job_spec_hash`, `INSERT … ON CONFLICT (org_id, job_spec_hash) DO NOTHING`; writing the identical spec twice yields one row and the same hash |
| AC4 | Any single-field mutation (repo, commit, suite revision, app digest, env revision, engine version, image digest, timeout, limit, secret ref, artifact policy) produces a different `job_spec_hash` and a new row — parameterised test covers all eleven field groups |
| AC5 | No UPDATE/DELETE path exists: the app role holds no UPDATE/DELETE grant and a domain aggregate has no mutator; an attempted `UPDATE`/`DELETE` as the app role fails |
| AC6 | `engine.version` is an exact pinned version (no `latest`, no semver range) and `engine.image_digest` is mandatory `sha256:` — both enforced by the schema (D6, DECISIONS §4) |
| AC7 | The schema file is the single source: server Corvus and CLI Ajv 8 run the same `fixtures/contracts/jobspec/` accept/reject corpus and any disagreement fails both builds (T42) |

## 4. Data model and migrations

Migration `migrations/NNNN_orchestration_job_spec.sql`:

- `job_spec` (`id uuid pk`, `org_id uuid not null`, `run_id uuid not null`, `job_spec_hash text not null`, `spec jsonb not null`, `created_at timestamptz not null default now()`): `unique (org_id, id)` (T3), `unique (org_id, job_spec_hash)` — content-addressed dedup; composite FK `(org_id, run_id) → run (org_id, id)`; index `(org_id, run_id)` serving "specs of a run".
- Immutability: `REVOKE UPDATE, DELETE ON job_spec FROM evidgate_app` (migrator owns the grants) — defence in depth alongside the no-mutator aggregate (C6).
- RLS policy via `evidgate.current_org_id()` (T2); rows are tenant-scoped even though the hash is content-derived (a spec references tenant revision ids).
- No `updated_at`/`version` columns — immutable rows need neither (00 §7).

## 5. API shapes (commands, queries, endpoints)

No public endpoint in this story (write path is internal, invoked by job creation in 05.7.2).

| Op | Type | Surface | Detail |
|---|---|---|---|
| `WriteJobSpecCommand` | `ICommand<string>` (returns hash) | internal handler, invoked by job creation | Validate spec against Corvus schema → canonicalise → hash → `INSERT … ON CONFLICT DO NOTHING` → `job_spec_hash`; schema failure maps to `Result` error `jobspec_invalid` (C8) |
| `GetJobSpecByHashQuery` | `IQuery<JobSpec>` | `IJobSpecReader.ByHashAsync` | Dapper, single indexed lookup by `(org_id, job_spec_hash)`; used by the claim handler (05.7.2) and the UI/operator detail view |
| spec validation at edge | endpoint filter | claim response serialisation | the served `job_spec` object is validated once more on write, so the read path returns bytes already proven valid |

## 6. States and transitions

`job_spec` rows are stateless and immutable: insert-only, addressed by hash. Identical content collapses to one row (dedup); different content is a different row. There is no draft/deprecate lifecycle — unreferenced rows are retained for audit under normal tenant retention.

## 7. Jobs and integrations

- Consumed by `ClaimJobsCommand` (05.7.2-T1): the claim response embeds the spec resolved via `IJobSpecReader` — no second schema validation on the hot path.
- `fixtures/contracts/jobspec/` corpus (accept + reject cases) is the T42 parity fixture shared with the CLI's Ajv validation.
- Engine image pull (05.7.4) keys on `engine.image_digest`; this story guarantees the digest is always present and pinned (D6).
