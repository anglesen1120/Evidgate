## 1. Goal and non-goals

**Goal.** Ship `packages/evidgate-agent` (Node 22+/TypeScript 6.0, Vitest): a service identity per tenant+pool that polls `POST /v1/agents/jobs/claim`, executes **exactly** the claimed JobSpec — validated adapter operations `prepare`/`execute`/`collect`/`cleanup` only — inside a disposable workspace under an unprivileged user with resource limits and no ambient credentials; collects only allow-listed artifacts with size caps and sensitivity; resolves secret references locally without ever logging or returning values; reports setup failure as `setup_error` separately from test failure; and heartbeats its epoch lease.

**Non-goals.** Server-side claim/lease/schedule logic (05.7.2/05.7.3); JobSpec schema (05.7.1, consumed); cleanup-confirmation gate (05.7.5); end-to-end engine scenario (05.7.6); agent registration token issuance (02.5.1); evidence upload pipeline semantics (06.1.x, 06.3.5 consumes the agent's uploads).

## 2. User stories and acceptance criteria

- As a tenant, I run Evidgate jobs on my own hosts with an agent that cannot exfiltrate secrets or exceed its sandbox.
- As the platform, I can trust that evidence labelled agent-produced came from the pinned JobSpec, executed under resource and egress limits.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The agent authenticates with a tenant+pool-scoped token (claims `org_id`, `pool`, permissions `job:claim`, `job:execute` only); it cannot claim another pool's jobs (403 `agent_forbidden`) or read project data |
| AC2 | Claim poll loop: GET-nothing → exponential backoff with jitter (base 1 s, cap 30 s); on lease grant, one heartbeat every 15 s ± jitter; on 409 `stale_lease`/`job_finished` the agent kills the process group and discards the workspace |
| AC3 | Executor creates a fresh workspace dir per job, runs the adapter child process as a configured unprivileged uid/gid, applies wall-clock/CPU/memory limits, and deletes the workspace (or keeps it quarantined on cleanup failure → 05.7.5) — verified by file-permission and uid assertions in tests |
| AC4 | Only `prepare`/`execute`/`collect`/`cleanup` operations declared in the JobSpec run; the JobSpec is re-validated against `contracts/jobspec.schema.json` (Ajv 8, T42 corpus) before any execution; a spec failing validation → job `failed` + `jobspec_invalid` report, zero side effects |
| AC5 | No ambient credentials: the child process env is an allow-list (proxy, locale, engine vars); the test asserts `AWS_*`, `GCP_*`, `AZURE_*`, `EVIDGATE_*` agent-token vars never appear in the child's environment, and egress is restricted to the target environment + Evidgate API (proxy/firewall config shipped + asserted by contract test) |
| AC6 | Secret references resolve inside the agent from its configured provider (env vars or mounted files — never values from the JobSpec); values are masked in logs (`***`), never sent upstream, never written into collected artifacts (log scrubber + test) |
| AC7 | `collect` copies only paths matching `artifact_policy.allow_paths`, each ≤ `max_bytes`, kinds mapped to the 00 §7 closed list (T20); a path outside the allow-list or an over-size file → the file is skipped with a `collect` violation entry; policy violations beyond the tolerance mark the job `failed` |
| AC8 | Setup failure (`prepare` non-zero) reports outcome `setup_error` (missing-reason code, 00 §8.5, T14) distinct from `execute` failure; attempts' dependants become `blocked`, never `passed` (00 §8.3) |
| AC9 | `execute` events stream to `POST /v1/runs/{r}/events` with the lease's `job_id` + `epoch`; events after losing the epoch are never sent (agent checks 409 paths) |

## 3. Contracts touched

- `packages/evidgate-agent`: new workspace package (Node 22+, TS 6.0 strict, Vitest). Consumes `packages/sdk` generated client (claim/heartbeat/events/artifact upload-url+complete) — no hand-written DTOs.
- `contracts/openapi.yaml`: agent auth expectations documented on claim/heartbeat (already defined 05.7.2); no new operations.
- `fixtures/contracts/jobspec/` reject corpus shared with 05.7.1 (T42 parity: Ajv 8 here, Corvus server side).
- `Evidgate.Modules.Orchestration.Contracts` unchanged — the agent speaks HTTP only.
- Config file `evidgate-agent.toml` (pool, token file path, workspace root, uid/gid, limits, egress allow-list, secret provider) — documented in `packages/evidgate-agent/README.md`.

## 4. Data model and migrations

None (agent holds no server-side tables). Agent-local state: an append-only job journal per workspace (`workspace/<job_id>/journal.jsonl`) recording claim, epoch, operations, collect manifest — disposable with the workspace, never authoritative.

## 5. API shapes (commands, queries, endpoints)

Agent-side module map (all I/O through the generated SDK):

| Module | Responsibility |
|---|---|
| `src/poller.ts` | claim loop: `POST /v1/agents/jobs/claim` (`job:claim`) with `{pool, capability}`; backoff/jitter; passes lease to executor |
| `src/lease.ts` | heartbeat timer (15 s ±20 % jitter) → `POST /v1/jobs/{j}/heartbeat` (`job:execute`); 409 handling → abort signal to executor |
| `src/spec.ts` | Ajv 8 validation of `job_spec` against `contracts/jobspec.schema.json`; refuses unknown fields (`additionalProperties:false` — invalid spec = `jobspec_invalid` report) |
| `src/executor.ts` | operation runner: `prepare`/`execute`/`collect`/`cleanup` as child processes of the engine image/command declared in the spec; unprivileged spawn, rlimits + wall-clock kill, env allow-list, process-group kill |
| `src/secrets.ts` | `secret_refs[]` resolution from the configured provider; scoped env injection per operation; log redaction (`ScrubbedLogger`) |
| `src/collect.ts` | artifact policy enforcement (allow-list glob, per-file + total size caps, kind map T20) → `upload-url`/`complete` via SDK (T17/T18 path) |
| `src/events.ts` | event batching → `POST /v1/runs/{r}/events` with `job_id`/`epoch`; `schema_version:1` envelope (00 §9.4) |
| `src/report.ts` | terminal job report (`finished`/`failed`/`setup_error`/policy violations) via heartbeat `status` payload |

## 6. States and transitions

Agent-side job lifecycle mirrors 00 §8.2 from the outside: `claimed → preparing → executing → collecting → reporting → done | failed | setup_error | aborted (stale lease)`. Aborts are forced transitions: `stale_lease` or lease expiry → SIGTERM → grace → SIGKILL on the process group → workspace disposal attempt. The server-side state machine stays authoritative; the agent never transitions a job directly except through heartbeat status payloads.

## 7. Jobs and integrations

- Server endpoints: `claim`, `heartbeat`, `events`, `artifacts/upload-url`, `artifacts/complete` — all existing contracts.
- Engine image: the agent runs the digest-pinned engine (`engine.image_digest`, D6) — either as the adapter's own runtime or by pulling an OCI image when the host has a container runtime; **both modes behind one `EngineRunner` interface**, container runtime optional ([INFERENCE] pilot hosts may be bare VMs; noted for DoR).
- Secret providers: `env:` and `file:` providers in V2 (agent-configured); cloud secret stores are a later adapter — out of scope.
- Cleanup operation dispatch → 05.7.5 (the `cleanup` op exists here; its confirmation gate is the next story).
- 06.3.5 consumes artifacts the agent uploads; 03.6.1 (draft dry-run) invokes the same executor path; 11.2.1 reviews the sandbox for the healing replay host.

## 11. Rollout

- Ships with agent mode (M4); registration requires an agent token from 02.5.1 — no token, no claim.
- Config-first rollout per tenant: pool declared (05.7.3) → token minted → agent deployed by the customer on their host; Evidgate never executes anything outside the customer's own infrastructure.
- Monitoring: agent logs stay customer-side; server-side signal = claim/heartbeat/`stale_lease` metrics (05.7.2) + `setup_error` rate.
- Rollback: revoke the agent token (02.5.1 rotation); jobs re-queue under new epochs and are claimed by remaining agents or time out as `queue_timeout` — nothing destructive.
