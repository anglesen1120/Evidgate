## 1. Goal and non-goals

**Goal.** Cancel returns `202` and records a **durable** request row — survivable across worker restarts (D7). Execution stops softly first (a cancel token visible to agents/CI), then is killed at a configured timeout. A canceled run never becomes `complete`: events arriving after cancel are accepted and stored with `after_cancel = true`, never refused (T12) — a leaked in-flight shard cannot resurrect a canceled run.

**Non-goals.** The run state machine's adjacency table itself (05.3.1 — this story only calls its `*→canceled` edge); agent-side cancel-token delivery and process-group kill mechanics for V2 agent mode (05.7.x — this story implements the CI-mode "no push channel, accept and mark" path per T12 and the durable request row that a future agent executor consumes); rerun after cancel (05.5.1).

## 2. User stories and acceptance criteria

- As a CI operator, I cancel a stuck run and get an immediate `202`, so I don't wait for the run to actually stop before knowing the cancel was accepted.
- As the platform, a race between cancel and a completing reconcile never lets a canceled run finish `complete`, so a cancel is a real guarantee, not a best-effort hint.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/runs/{r}/cancel` on a non-terminal run → `202`, `run_cancel_request` row inserted (`requested_by`, `reason`, `requested_at`, `soft_stop_deadline_at`, `kill_at`), run transitions toward `canceled` via 05.3.1's guard |
| AC2 | Cancel on an already-terminal run (`complete`/`incomplete`/`canceled`) → `202`, no-op (idempotent; no second cancel request row, no error) |
| AC3 | A run in `created`/`queued` cancels immediately (straight to `canceled`, no soft-stop window needed since nothing is executing) |
| AC4 | A run in `running`/`collecting` transitions to `canceled` **immediately** when the cancel request is accepted (plans/05:115); the soft-stop→kill window (`soft_stop_deadline_at`/`kill_at`) then acts on **execution** — the CI shard's producer stream or, in V2 agent mode, the agent job — never on `run.state`, which is already terminal |
| AC5 | An event batch arriving for a canceled run → accepted (never refused), each affected attempt/event row stamped `after_cancel = true`; the stamp is derived inside the ingest transaction from the `run` row taken `FOR SHARE` (T91), so a batch that serializes after the cancel commit can never miss it |
| AC6 | A reconciler verdict computed concurrently with a cancel commit never flips a `canceled` run to `complete`: whichever transition commits first wins and the run stays in its terminal state thereafter (05.3.1's terminal no-op rule) |
| AC7 | The cancel request row and its kill task survive a worker/API restart: the kill is a one-shot `task` row with `available_at = kill_at` (outbox-dispatched, durable per 00 §5.3), not an in-memory timer |
| AC8 | Cancel requires `run:cancel`; a caller without it → `403`; other-tenant run id → `404` |

## 4. Data model and migrations

`migrations/NNNN_orchestration_run_cancel.sql` (DbUp, owner role):

```sql
create table run_cancel_request (
  id uuid primary key,
  org_id uuid not null,
  run_id uuid not null,
  requested_by uuid not null,
  reason text,
  requested_at timestamptz not null default now(),
  soft_stop_deadline_at timestamptz not null,
  kill_at timestamptz not null,
  state text not null default 'requested' check (state in ('requested','soft_stopping','soft_stopped','killed')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  version integer not null default 1,        -- 00 §7 template; the shared update trigger moves both
  unique (org_id, id),                       -- T3
  unique (org_id, run_id),                   -- one active row per run (FR-05-6)
  foreign key (org_id, run_id) references run (org_id, id)
);
alter table run_cancel_request enable row level security;
alter table run_cancel_request force row level security;
create policy run_cancel_request_tenant on run_cancel_request
  using (org_id = evidgate.current_org_id()) with check (org_id = evidgate.current_org_id());

-- after_cancel marker lives on the rows it stamps, not here:
alter table case_attempt add column after_cancel boolean not null default false;
-- T91 lock discipline: cancel (this handler) and completion take the run row FOR UPDATE;
-- ingest takes the run row FOR SHARE inside the batch transaction and derives
-- after_cancel/late from it — a flag can never miss a committed cancel (AC5)
```

`run_cancel_request` is not itself a `task`-queue row, and the kill is **not** a Cronos schedule (Cronos is for recurring cron fires, 00 §5.3). The one-shot kill is an outbox-dispatched `task` row with `available_at = kill_at`: `FOR UPDATE SKIP LOCKED` claim, retried with backoff, durable across restarts (AC7, D7).

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Notes |
|---|---|---|---|---|
| Command | `CancelRunCommand : ICommand<CancelResult>` → `CancelRunHandler` | `POST /v1/runs/{r}/cancel` | `run:cancel` | C2 pipeline. Idempotent: terminal run → 202 no-op (AC2); non-terminal run → insert `run_cancel_request` (one row per run, `unique (org_id, run_id)`), compute `soft_stop_deadline_at`/`kill_at` from config, transition the run to `canceled` via 05.3.1 (`*` → `canceled`, accepted immediately per plans/05:115 — cancel is recorded, not "stopped"), write the kill `task` row (`available_at = kill_at`), write outbox + audit. `202` |
| Task (internal) | `CancelKillTask` (outbox-dispatched, `task` queue, `available_at = kill_at`) | — | — | Fires at `kill_at`: marks the cancel request `killed` and cancels the execution-side resources — the cancel token visible to agents/CI producers; in V2 agent mode, kills the job process group via the agent's cancel-token channel (05.7.x). It never touches `run.state`, which is already `canceled` since the request was accepted (plans/05:115) |

Errors: `forbidden` (403, AC8), `not_found` (404, AC8).
Lock discipline (T91): `CancelRunCommand` takes the `run` row `FOR UPDATE` (via 05.3.1's transition handler) before deciding; ingest's batch handler takes the same row `FOR SHARE` and derives `after_cancel`/`late` inside its transaction. An in-flight batch either waits out the cancel commit (and then sees `after_cancel = true`) or stamps first and the cancel's `FOR UPDATE` blocks on it — never a torn flag.


## 6. States and transitions

Drives the `*→canceled` edge of 00 §8.1 (owned by 05.3.1, this story is a caller only): the transition fires when the cancel **request** is accepted, not when execution actually stops (plans/05:115). `run_cancel_request.state` is a local sub-state machine for observability of the execution stop, not part of 00 §8.1: `requested → soft_stopping → soft_stopped | killed`. `soft_stopped` means execution confirmed stopped before the kill deadline (soft stop worked); `killed` means the `kill_at` task fired. Either way `run.state` was already `canceled` — a terminal state per 05.3.1, from which no further transition is ever accepted (AC6, T12: post-cancel events are stamped, never used to complete the run; a reconcile verdict may still persist a labelled `evidence_revision` on a canceled run).

## 7. Jobs and integrations

- Kill `task` row (00 §5.3): one-shot outbox task with `available_at = kill_at`; `FOR UPDATE SKIP LOCKED` claim and `dead_letter` after the retry cap give exactly-once firing semantics without a leader — the row itself is the durable schedule (not a Cronos cron fire).
- Calls 05.3.1's `TransitionRunStateCommand` — no duplicate transition logic (§6).
- 05.3.3's attempt writer and 04's event-commit handler take the `run` row `FOR SHARE` inside their own transaction and derive `after_cancel` (and `late`, T81) from it (T91, AC5) — serialized with cancel's `FOR UPDATE` on the same row, no coupling back into this story's write path.
- Outbox row `run.cancel_requested` / the existing `run.state_changed` (05.3.1) cover downstream consumers (09 UI, webhooks 00 §9.5).

## 11. Rollout

- No feature flag. Merge order: T1 → T2 → T3 in one PR series on `develop`, sequenced after 05.3.1 (state machine exists to call into).
- Monitoring: `evidgate_run_cancel_requested_total`, `evidgate_run_cancel_kill_forced_total` (soft-stop-failure signal), `evidgate_event_after_cancel_total` (post-cancel traffic volume, an operational health signal for CI shard cleanup).
- Rollback: revert the PR series; `run_cancel_request` is additive — a revert before any cancel is requested is lossless; after, in-flight cancel requests lose their kill schedule until the code is restored (operational pause, no data corruption — soft-stopped runs simply never reach the forced-kill step until re-deployed).
