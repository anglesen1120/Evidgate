## 1. Goal and non-goals

**Goal.** `POST /v1/runs/{r}/finalize` (producer/shard, `last_sequence`, `count`, `manifest_hash`) is accepted with `202`; the caller must be the identity bound to that producer slot (T9). The reconciler waits until the expected events are acknowledged, compares declared vs observed counts/ids and required-artifact readiness, takes 06's `FreezeAsync(FreezeRequest)` result and persists an `evidence_revision` (`completeness ∈ {complete, incomplete}`, `missing[]` reasons incl. `setup_error` — T14). Collection deadline + late window govern when a run is forced to a verdict and how late evidence is handled. All of this is idempotent under duplicate/out-of-order finalize (D3).

**Non-goals.** The `case_attempt` write path (05.3.3); cancel interaction beyond "canceled run still gets a labelled revision" (05.4.1); 06's `FreezeAsync` algorithm itself (06.5.1 — this story only calls it and persists its result, D4); rerun (05.5.1); release binding (05.6.1).

## 2. User stories and acceptance criteria

- As a CI shard, I finalize once my events are sent, so the platform knows to start reconciling instead of waiting for a deadline.
- As the platform, I never call a run `complete` on partial evidence, and I never lose a late event by silently dropping it.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Finalize from the identity bound to the shard's producer slot, matching `manifest_hash` → `202`, producer slot marked closed, run → `collecting` (if not already) |
| AC2 | Finalize from a non-bound identity → `403 producer_slot_taken`; finalize naming an unregistered producer → `422 unknown_producer` (T9) |
| AC3 | Finalize with a mismatched `manifest_hash` → `422`, run stays `collecting`, missing reason recorded — never treated as evidence against the wrong plan |
| AC4 | A fully-reported run (all shards closed, counts/ids match, required artifacts `ready`) → `evidence_revision.completeness = "complete"`, `missing[] = []`, run → `complete` |
| AC5 | Missing shard, count/id mismatch, unknown status, or `setup_error` → `evidence_revision.completeness = "incomplete"` with the matching `missing[]` reason, run → `incomplete` at the collection deadline (00 §8.6: never `PASS`) |
| AC6 | Duplicate finalize for an already-closed `(run, producer)` → `202`, no state change, no second `evidence_revision` row |
| AC7 | Finalize arriving before its events → producer marked closed, run stays `collecting`, reconciler retried until the deadline |
| AC8 | Late evidence is accepted, never silently dropped (T81): events for a run in `incomplete`, or in `complete` within its `late_window` since completion, are stored with `late = true` and a **new** `evidence_revision` is persisted (re-freeze on the new watermark) plus a re-evaluation outbox task (07.5.1) — an existing revision is never rewritten (AC9); events arriving after the late window are rejected by ingest with `409 run_closed` |
| AC9 | `evidence_revision` is append-only: unique `(org_id, run_id, revision_no)`, no update path |

**Deviation (D-S115-Q1, 05.3.2-T5, migration `0049`):** the shipped DDL is stricter than the snippet above, and the migration, not the reconciler, owns each item: `evidence_revision_missing_check` closes the code list with `<@` over the seven 00 §8.5 codes and additionally rejects a NULL element (`array_position(missing, null) is null`) and any multi-dimensional array (`array_ndims(missing) is null or array_ndims(missing) = 1`), so a duplicate code is tolerated while an unknown code or a NULL element fails `23514`; `evidence_revision_complete_has_no_missing_check` makes `complete` require `missing = '{}'`, while an `incomplete` row may keep an empty `missing[]` (the converse is the reconciler's rule); `evidence_revision_outcome_check` admits only `all_passed`, `has_failures`, `no_results` or NULL; `evidence_revision_revision_no_check` requires `revision_no >= 1`; `evidence_revision_watermark_check` requires `event_watermark >= 0` and the two hash columns carry 1–200 character bounds; the BEFORE INSERT trigger `evidence_revision_guard_insert` (`guard_evidence_revision_insert()`) takes the parent `run` row `for no key update` first and refuses any `revision_no` other than `max + 1` (1 for the first row) with `23514`, so the sequence is gap-free and the unique key is unreachable by a duplicate; `run_current_evidence_revision_fk` is the composite pointer FK `(org_id, current_evidence_revision_id) → evidence_revision (org_id, id)` (NULL still legal, MATCH SIMPLE) and `grant update (current_evidence_revision_id) on public.run to evidgate_app` is the only new write surface on `run`; `run_evidence_pointer_guard` (`guard_run_evidence_pointer()`, BEFORE UPDATE when the pointer changes) refuses any move that is not to the latest revision of the same run with `23514` and refuses clearing the pointer to NULL with `23514` except when `current_user = 'evidgate_owner'` — the erasure sweep, which the run↔`evidence_revision` FK cycle would otherwise block; `run_evidence_pointer_insert_guard` (`guard_run_evidence_pointer_insert()`, BEFORE INSERT on `public.run` when the new pointer is not NULL) refuses a run inserted with a non-NULL `current_evidence_revision_id` (`23514`), because a new run has no revisions yet; and both guard functions are `EXECUTE`-granted to `evidgate_app`.

## 6. States and transitions

Drives two edges of 00 §8.1 owned by 05.3.1's transition function: `running → collecting` (first finalize, AC1/AC7) and `collecting → complete | incomplete` (reconciler verdict, AC4/AC5). This story never re-implements the adjacency table — it calls `TransitionRunStateCommand` (05.3.1-T1) with the target state and lets the guard reject anything illegal (e.g. a duplicate finalize after the run is already `complete` is a no-op per 05.3.1's terminal-state rule, AC6).

## 7. Jobs and integrations

- `ReconcileRunTask` is a `task`-queue row inserted via the finalize command's outbox (00 §5.3): `FOR UPDATE SKIP LOCKED` claim, idempotent handler keyed by `run_id`, retried with backoff, `dead_letter` after the cap (visible to operators).
- `Evidgate.Modules.Evidence.Contracts.IEvidenceFreeze.FreezeAsync(FreezeRequest)` (06.5.1) — in-process module call; no network hop inside the reconcile transaction (P5).
- Late window / re-evaluation trigger (T81): an event batch stored `late = true` for a run in `incomplete` or `complete` within `late_window` enqueues `LateEvidenceRevisionTask` (new `evidence_revision` on the new watermark) and the re-evaluation outbox task consumed by 07.5.1 — outbox-triggered only (T26, no `/v1` re-evaluation endpoint). Batches past the late window are refused by ingest with `409 run_closed`; canceled runs keep the T12 accept-and-mark path (05.4.1).
- `05.10.1-T1` (stuck-run detector, M2) consumes this story's `ReconcileRunTask` as its single reconcile retry before alerting.

| T81 | late events on an `incomplete` run, or on a `complete` run within `late_window`, are stored `late = true` and produce a new `evidence_revision` + re-evaluation trigger — never an in-place rewrite; post-window → `409 run_closed` | AC8, `LateEvent_IncompleteOrWithinLateWindow_NewRevisionAndReevaluate`; `LateEvent_AfterLateWindow_409RunClosed` |
| Privacy/retention | no personal data in `evidence_revision`; deleted only with the tenant | RLS tests |

- **Authorization:** `POST /v1/runs/{r}/finalize` requires `event:write` through the C2 pipeline — a service-principal permission (`ci_producer` or agent), so a member session cannot hold it — and the caller's credential must name the project that owns the run (`403 project_scope_mismatch`); only the identity bound to the shard's slot may close it (T9); another tenant's run is `404 not_found` under RLS.
- **Retention/deletion:** the finalize writes only the slot's declared values (`producer_slot`, 04's table) and an outbox row; both hold no personal data, follow the run's retention and are deleted only with the tenant.
- **Telemetry:** a module activity tagged with the run and producer ids only, `evidgate_finalize_producer_slot_taken_total` (T9 abuse signal) and `evidgate_finalize_declaration_mismatch_total`; never a token, a jti or the manifest hash.
- **Failure path:** every refusal rolls the one tenant transaction back (slot stays open or unbound, run state unchanged, no outbox row); the outbox row commits with the close, so a crash before commit leaves nothing and a retry re-runs the whole request; a duplicate is a no-op `202`.

## Notes (05.3.2-T1, S51, 2026-10-23)

- [DECISION] Q1 (A, decided by the coordinator under the owner rule of 2026-10-23: panel choices take the recommended option; recorded for owner phase review as `D-S51-Q1`, non-blocking): a repeat finalize that declares a *different* `last_sequence`/`count` is still `202` with no state change — the first declaration wins and the stored pair stays authoritative for T2; one warning line naming the run, the shard and the two numbers sent, plus `evidgate_finalize_declaration_mismatch_total`. Option B (409 with a new 00 §9.2 code) would be a wire-contract change.
- [DECISION] Q2 (A, coordinator-ratified): `shard` must equal the bound slot's own 1-based `shard_index`; a mismatch is `422 request_invalid` with `ErrorDetail` pointer `/shard`.
- [DECISION] Q3 (A): one outbox trigger per **newly closed** slot — task type `orchestrator.run.reconcile` (`RunReconcileContract`), aggregate `run`/run id, payload `{run_id, producer_id, declared_last_sequence, declared_count}` (stored values), key `orchestrator:run:{run}:reconcile:{producer}`. A repeat closes nothing and enqueues nothing, so one finalize leaves exactly one row. No consumer is registered yet; the dispatcher's `left join unnest(@route_task_types, @route_queues)` sends it to the default queue and `TaskQueueSql.ClaimBatch`'s `task_type = any(@task_types)` never claims it, so it stays `queued` (no attempts, no `dead_letter`) until T2 registers its handler — the same posture as `orchestrator.run.state_changed`.
- [DECISION] Q4: a finalize arriving before any event of a still-`queued` run steps `queued → running → collecting` through 05.3.1; `queued → collecting` is an undeclared forward-skip in the 00 §8.1 machine and the transition command refuses forward-skips.
- [DECISION] Q5: the route **is** an `IIdempotentCommand` (00 §9.1 / `contracts/README.md`: every mutation not on the exemption list), operation `run:finalize`, so a byte-identical retry replays the stored bodiless `202` and a reused key with a different run, body or caller is 409 `idempotency_conflict` (`BodyHash` covers the body, the caller's credential id and the CI run reference, all excluded from the serialized command). The key is **required**: a missing, blank or over-128-character key is `400 request_invalid` at the C2 idempotency stage, before the body is read. The key is still **not** the arbiter of a duplicate finalize — `producer_slot.closed_at` is (D3) — so a repeat with a fresh key is the same no-op `202`, while a missing key is 400, not 202. The replay is bound to the caller's credential: the same key and body reused from a different credential (or from the same credential under another CI run attempt) is 409 and never replays another credential's `202`, because the stored identity is part of the request hash.
- AC3's hash half: a `manifest_hash` different from the run's `manifest.manifest_hash` is `422 manifest_invalid` (`/manifest_hash`), checked **after** the identity check and before any close, so nothing is recorded and no slot moves — a foreign caller never learns the expected hash, and the expected value is never echoed. The "missing reason recorded" half has nothing to write into until T2/T5: the reconciler owns `missing[]` and reports a shard whose slot never closed as the missing shard.
- Hand-overs to T2: read the declared values from `producer_slot` (`declared_last_sequence`, `declared_count`, the first close's values); consume `RunReconcileContract.OutboxTaskType` in `Evidgate.Modules.Orchestrator.Contracts`; the payload record `RunReconcilePayload` (snake_case) is the row's shape. The run row is locked `FOR NO KEY UPDATE OF r` when the call may transition the run and `FOR SHARE OF r` otherwise, and the lock order is run → slot, so the reconciler must not hold a slot lock before the run. The trigger is not evidence that the run is collectable: a finalize on a `complete`, `incomplete` or `canceled` run still enqueues `orchestrator.run.reconcile` (T12 accept-and-mark) while an event batch on such a run answers `409 run_closed`, so **the T2 consumer MUST ignore a trigger for a terminal or canceled run** and never append an `evidence_revision` after the run completed.
- Observability: `evidgate_finalize_producer_slot_taken_total` (T9 abuse signal, incremented on both the bind and the close refusal) and `evidgate_finalize_declaration_mismatch_total`, neither labelled; the module activity carries `evidgate.run_id` and `evidgate.producer_id` only.
