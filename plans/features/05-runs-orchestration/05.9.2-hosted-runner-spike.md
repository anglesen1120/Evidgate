## 1. Goal and non-goals

**Goal.** Produce a written options note on running customer-submitted test executions on Evidgate-hosted runner infrastructure (as opposed to today's model where the customer's own CI or the customer-run agent executes tests): isolation model, inbound-networking implications of executing potentially untrusted code from a customer's repo, and a cost comparison against the current agent-mode model — ending in a decision proposal for the Tech Lead.

**Non-goals.** Building a hosted-runner pool, a sandbox/VM orchestration layer, or any billing change (12 owns pricing); macOS/iOS hosting (05.9.1, a separate spike); any change to the existing CI-mode or agent-mode execution paths.

## 2. User stories and acceptance criteria

- As the Tech Lead, I need the security implications of running a customer's test code on Evidgate-owned compute stated explicitly before any commitment, because it inverts today's trust boundary (customer code currently only ever runs on the customer's own infrastructure).
- As the owner, I need a cost/isolation/networking comparison so a "build hosted runners" decision is made on evidence, not convenience.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A findings note exists at `docs/spikes/05.9.2-hosted-runner.md` covering: (a) isolation model options (gVisor/Firecracker microVM, per-job ephemeral container, per-job disposable VM) with the trust boundary each gives against a hostile test suite, (b) inbound-networking implications — a hosted runner executing a customer's suite may need to reach the customer's staging environment (VPN/tunnel) or may be sandboxed with no customer-network reachability, each option's SSRF/exfiltration exposure stated against 00 §5.7 S4, (c) a cost comparison table (hosted pool at 3 concurrency tiers vs the current customer-run-agent model, which carries zero Evidgate compute cost) |
| AC2 | Every external cost/capability claim (cloud microVM pricing, egress cost, a named isolation technology's security track record) is ⚠️-marked with source and date; no service/library version is invented |
| AC3 | The note ends with a decision proposal: recommended isolation model (or "no viable model without X precondition"), and the precondition/trigger for revisiting ("build when a pilot customer requires zero local CI footprint") |
| AC4 | The note is reviewed by the Tech Lead and the recommendation is recorded as a `[DECISION]` or `[OPEN]` line in this file's §3, not silently assumed |
