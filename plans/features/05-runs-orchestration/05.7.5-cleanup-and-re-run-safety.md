## 1. Goal and non-goals

**Goal.** After a side-effecting agent job finishes, its `cleanup` operation runs once per run namespace and records a durable result; a follow-up job (re-run, rerun, next attempt) on the same namespace cannot start until a cleanup/isolation confirmation exists; cleanup is idempotent (re-invocation is safe) and its failure is reported as a distinct `cleanup_failed` state — never silently swallowed as job failure or success.

**Non-goals.** The `cleanup` operation's adapter implementation details (05.7.4-T2 ships the operation); environment locks (05.7.3-T4); data-namespace cleanup of catalog fixtures (03's `data namespace` lifecycle — this story reuses the pattern, doesn't own that state machine); CI-mode cleanup (CI producers manage their own environments).

## 2. User stories and acceptance criteria

- As the platform, I never re-run a side-effecting job against a dirty namespace, so retries can't double-apply mutations.
- As an operator, I see cleanup failure separately from test failure, so I know whether the environment or the suite is at fault.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Every agent-mode `job` carries `run_namespace` (from its JobSpec); a job declared `side_effecting = true` (job field derived from the spec's cleanup policy) gets a `job_cleanup` row `pending` at job terminal state |
| AC2 | After the job's `cleanup` operation reports success, the row → `confirmed` with `confirmed_by` (agent or actor), `confirmed_at`, `evidence` (cleanup report hash); the confirmation is durable across restarts |
| AC3 | A new job targeting a namespace whose latest `job_cleanup` is `pending`/`failed` is blocked at enqueue: `EnqueueJobsCommand` skips it and records `blocked_cleanup_pending`; claim never leases it until `confirmed` |
| AC4 | An operator/member confirmation endpoint `POST /v1/jobs/{j}/cleanup` (`job:execute` agent self-report vs `job:cleanup` member override, T59 — both audited) records isolation evidence manually when the automated op can't run |
| AC5 | Cleanup is idempotent: running the `cleanup` op twice for the same `(org_id, namespace)` records `attempt` rows but never blocks/errors on the second success; duplicate confirmations are no-ops returning the existing row |
| AC6 | `cleanup` op failure → `job_cleanup.state = cleanup_failed` with the error detail; the job's own outcome stays `cleanup_failed` (distinct from `failed`/`setup_error`); surfaced on `GET /v1/jobs/{j}` |
| AC7 | Re-run of the *job* after `confirmed` proceeds normally (fresh lease, new epoch) — the gate binds to the confirmation record, not to a job retry counter |
| AC8 | Jobs with `side_effecting = false` bypass the gate entirely — no `job_cleanup` row, no added latency |

## 4. Data model and migrations

`migrations/NNNN_orchestration_job_cleanup.sql`:

- `job` addition: `side_effecting bool not null default false`, `run_namespace text` (already implied by spec; materialised for indexing).
- `job_cleanup` (`id`, `org_id`, `namespace`, `job_id`, `state text check (state in ('pending','confirmed','cleanup_failed'))`, `confirmed_by`, `confirmed_at`, `evidence text` (report hash), `failure_detail`, `version`, `created_at`): `unique (org_id, id)` (T3); composite FK `(org_id, job_id)`; index `(org_id, namespace, created_at desc)` serving `IsCleanAsync` (latest row per namespace); partial index `(org_id, state) WHERE state <> 'confirmed'` for the sweeper/blocked view.
- `job_cleanup_attempt` (`id`, `org_id`, `job_cleanup_id`, `attempt_no`, `outcome ('ok','failed')`, `detail`, `created_at`): `unique (org_id, job_cleanup_id, attempt_no)`; composite FK `(org_id, job_cleanup_id)` — idempotency/audit trail.
- RLS via `evidgate.current_org_id()` on both (T2). Confirmations audited (actor, timestamp, evidence).

## 5. API shapes (commands, queries, endpoints)

| Op | Type | Route / handler | Detail |
|---|---|---|---|
| `RecordCleanupPending` | domain call | job terminal transition (05.7.2 state machine hook) | if `job.side_effecting`: insert `job_cleanup (pending)` + outbox `cleanup.required` |
| `ConfirmCleanupCommand` | `ICommand` | `POST /v1/jobs/{j}/cleanup` · `job:execute` (agent) / member actor path | `{outcome: 'confirmed'|'failed', evidence}` → `pending → confirmed | cleanup_failed`; second identical call → 200 no-op (natural-key idempotency); on a `confirmed` row with `outcome: failed` → 409 `cleanup_state_conflict`; non-side-effecting job → 422 `cleanup_not_required` |
| `IsCleanAsync` | `ICleanupRegistry` query | called by `EnqueueJobsCommand` (05.7.3) | latest `job_cleanup` per namespace: `confirmed` → proceed; else block + `blocked_cleanup_pending` audit |
| agent report path | heartbeat/report payload (05.7.4) | `cleanup` op result attaches `job_cleanup_attempt` + transitions state | same idempotent transition, agent identity recorded |
| `GetJobQuery` (extend) | `IQuery` | `GET /v1/jobs/{j}` | adds `cleanup_state`, latest attempt detail |

## 6. States and transitions

`job_cleanup`: `pending → confirmed | cleanup_failed`; `cleanup_failed → confirmed` allowed only via a new explicit confirmation (operator re-check) — never by a blind retry (A9 spirit). Attempts are append-only per `attempt_no`. The job itself is unaffected: cleanup state is a sidecar gate, jobs stay `finished`/`failed`; the gate blocks **future** jobs, not the current one.

## 7. Jobs and integrations

- Outbox `cleanup.required` wakes nothing in V2 — cleanup runs inside the job's own `cleanup` operation immediately after `collect` (agent-side, 05.7.4-T2); the outbox row exists for audit/observability and a future reminder sweep.
- `EnqueueJobsCommand` (05.7.3-T2.1) calls `ICleanupRegistry.IsCleanAsync` before writing `job` rows for side-effecting specs — one indexed read per enqueue batch (P3).
- The 05.10.1 sweeper may list `state <> 'confirmed'` rows older than a threshold for operator alerts (hook only; sweep is that story's work).
- Namespace convention: `run_namespace` = `job_spec.run_namespace` (05.7.1); shared suites combine it with the `environment_lock` (05.7.3-T4) — lock serialises execution, cleanup confirms sanitation.
