## 1. Goal and non-goals

**Goal.** `POST /v1/projects/{p}/manifests` accepts a manifest — planned executions (case × variant × target env), the matrix, the shard plan and the environment needs — verifies it against the JSON Schema and the catalogue, stores it immutable under a stable `manifest_hash` (`sha256:` over RFC 8785 canonical JSON), and rejects anything unverifiable with 422 + indexed details (D1). A verified manifest is the locked plan every later reconcile is proven against (A8).

**Non-goals.** The `environment_revision` table the manifest references (05.1.2); run creation and manifest locking (05.2.1); suite/case revision authoring and `case_dependency` (03); the adapter capability document (04); any manifest update or delete path (none exists — immutability).

## 2. User stories and acceptance criteria

- As a CI pipeline, I upload the manifest my reporter will execute against, so the server holds a locked plan to reconcile evidence to.
- As the platform, I reject manifests that cannot produce complete evidence, so a run never starts against a broken plan.
- As the Tech Lead, the same schema validates in the server (Corvus) and the CLI (Ajv), so "verify locally then upload" cannot diverge (T42).

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A valid manifest → `201` with `{manifest_id, manifest_hash}`; the hash is `sha256:<hex>` over the RFC 8785 canonical form and identical across JSON field orderings and re-uploads (golden vector test) |
| AC2 | A JSON Schema violation → `422 manifest_invalid` with `details[]` carrying `index`/`path`/`reason` per violation; a body over the route limit → `413` |
| AC3 | A manifest naming a case revision that does not exist in the project → `422 manifest_invalid`, reason `unknown_case_revision`, one `details[]` entry per offending index |
| AC4 | Variant params containing a secret *value* (literal, not a `secret:` reference) → `422 manifest_invalid`, reason `secret_in_variant_params` |
| AC5 | A shard plan not covering the matrix exactly (uncovered tuple or double assignment) → `422 manifest_invalid`, reason `matrix_not_covered` |
| AC6 | Re-upload of a canonically identical manifest returns the existing `manifest_id` (dedupe on `unique (org_id, project_id, manifest_hash)`), no second row |
| AC7 | The stored manifest cannot be mutated: `REVOKE UPDATE`/`DELETE` for the app role + domain object with no setters (C6); `UPDATE` as the app role fails at the DB level |
| AC8 | A `manifest_id` of tenant B addressed by tenant A's principal → `404` (RLS fail-closed, §5.4.7) |

## 3. Contracts touched

- `contracts/manifest/manifest.v1.json` — **new** schema (planned executions, matrix, shard plan, env needs); one schema consumed by the server (Corvus.Json.Validator) and the CLI (Ajv 8) with the shared `fixtures/contracts/vectors/manifest.v1/` accept/reject corpus (T42). The file is named `manifest.v1.json` (key `manifest.v1`), not `manifest.v1.schema.json`: the 01.3.1 conventions gate requires every contract schema file to end in `.vN.json`, and both loaders key a schema by its file name without `.json` (the same rule the corpus directory name follows).
- `contracts/openapi.yaml` — new path `POST /v1/projects/{p}/manifests` (05-owned row of 00 §9.3).
- 00 §7 hash + naming rules — implemented, not changed.
- Ordering note: `manifest.environment_revision_id` is created here as a plain `uuid` column; the composite FK `(org_id, environment_revision_id) → environment_revision` is added by 05.1.2-T1's migration (the table does not exist at 05.1.1 time; 05.1.2 depends on 05.1.1-T4).
- No permission, state-machine or error-envelope change.

## 4. Data model and migrations

`migrations/NNNN_orchestration_manifest.sql` (DbUp, owner role, app role = `evidgate_app`):

```sql
create table manifest (
  id uuid primary key,
  org_id uuid not null,
  project_id uuid not null,
  manifest_hash text not null check (manifest_hash like 'sha256:%'),
  schema_version int not null,
  suite_revision_id uuid not null,
  environment_revision_id uuid,          -- FK added by 05.1.2-T1 (see §3)
  shard_plan jsonb not null,             -- versioned producer metadata (§5.4.5)
  matrix jsonb not null,
  env_needs jsonb not null,
  planned_count int not null check (planned_count >= 0),
  document jsonb not null,               -- canonical request payload
  verified_at timestamptz not null,
  verified_by uuid not null,             -- member id, audited
  created_at timestamptz not null default now(),
  unique (org_id, id),                   -- T3: composite-FK target
  unique (org_id, project_id, manifest_hash),
  foreign key (org_id, suite_revision_id)
    references suite_revision (org_id, id)
);
alter table manifest enable row level security;
alter table manifest force row level security;   -- §5.4.3
create policy manifest_tenant on manifest
  using (org_id = evidgate.current_org_id())     -- T2 helper, fail-closed
  with check (org_id = evidgate.current_org_id());
revoke update, delete on manifest from evidgate_app;  -- C6 immutability
```

No list/filter queries exist on `manifest` in V1 (lookup is by PK / by content hash), so no extra index is needed beyond the two uniques.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint / use | Notes |
|---|---|---|---|
| Command | `UploadManifestCommand : ICommand<UploadManifestResult>` → `UploadManifestHandler` (EF Core 10 write model) | `POST /v1/projects/{p}/manifests`, permission `run:create` | Corvus schema validation runs at the edge before binding; pipeline C2 (telemetry → validation → tenant tx → authorization → idempotency → handler → outbox → commit). Body ≤ 256 KiB → `413`. On `(org_id, project_id, manifest_hash)` conflict: return the existing row (201, same body — content-addressed dedupe). 201 response `{manifest_id, manifest_hash}`, `ETag: "<manifest_hash>"` |

Error codes (00 §9.2 envelope): `manifest_invalid` (422, indexed `details[]`), `unauthenticated` (401), `forbidden` (403 incl. project-scope mismatch), `rate_limited` (429 `Retry-After`); an oversized body returns 413.

Queries: none. There is no `GET /v1/manifests/…` in 00 §9.3; run create (05.2.1-T1) reads the manifest inside its own transaction.

## 6. States and transitions

None. A manifest exists only in its terminal `verified` form (`verified_at` set at insert); there is no draft state and no transition. Immutability is enforced by C6 (no setters) + `REVOKE UPDATE, DELETE` (§4).

## 7. Jobs and integrations

- `Evidgate.Modules.Catalog.Contracts` (03) — read-only existence checks for the named `suite_revision_id` and every referenced `case_revision_id`, executed as SQL inside the same tenant transaction (no network call, P5).
- `Evidgate.Canonicalization` — RFC 8785 canonicalisation for `manifest_hash`; golden vectors shared with the CLI's `canonicalize` 5.1 (stack mapping §4).
- `fixtures/contracts/vectors/manifest.v1/` — the accept/reject corpus both runtimes must agree on (T42); CI fails on any disagreement.
- Consumed by 05.2.1-T1 (manifest lock at run create) and 04.2.2 (reporter-side manifest fetch by hash).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| §5.4 rules 1–3, T2, T3 | `org_id` NOT NULL, `unique (org_id, id)`, composite FK to `suite_revision`, `FORCE RLS`, policy via `evidgate.current_org_id()` | `Manifest_CrossTenant_404` (AC8); 02.6.1-T2 lint sees the table |
| §5.5 C2/S2 | `run:create` permission attribute on the command; authz in the pipeline, never in the endpoint | architecture test + `UploadManifest_NoPermission_403` |
| §5.5 C6/C8 | immutable domain object + `REVOKE UPDATE`; domain errors are `Result` values mapped to the §9.2 envelope | `Manifest_UpdateRevoked`; AC2–AC5 envelope shape |
| §5.7 P5 | catalogue existence check is one SQL statement inside the same tx; no network call while the tx is open | `UploadManifest_CommandCounter` (bounded-statement assertion, P3) |
| §5.5 Edge (per-route body limits)/S5 | body cap 256 KiB [DECISION — 00/05 name no manifest limit]; Corvus validation before binding; JSON depth/size caps | AC2 (`413`, `422`) |
| S3 secrets | variant params must carry `secret:` references, never values; the rejection reason never echoes the offending value | AC4 + redaction assertion in the test |
| T42 validator parity | one schema, two runtimes, one fixtures corpus | `ManifestSchema_ParityCorpus` in CI |
| Privacy/retention | `document` may embed case names (business data, tenant-scoped); no personal data field; deleted only with the tenant (T16 operator path) | RLS tests; retention note |
| Authorization | `run:create` on `UploadManifestCommand`, enforced by the C2 pipeline (never in the endpoint); a principal without it gets 403 and a project-scope mismatch gets 403 — never 404-vs-403 leakage across tenants | `UploadManifest_NoPermission_403`; architecture test (row above) |
| Retention/deletion | The manifest row is deleted only with the tenant or its project (T16 operator path, cascade per 06.4.4); it is immutable until then (`REVOKE UPDATE, DELETE`), and there is no separate manifest retention policy | `Manifest_UpdateDelete_Revoked_ForAppRole`; RLS tests |
| Telemetry | `evidgate_manifest_rejected_total{reason}` on edge validation plus request_id/trace_id on every request; no manifest field value, case name or hash of a rejected body in a metric label or log line | monitoring note (§11); rejection-counter test |
| Failure path | Schema violation 422 `manifest_invalid` with indexed `details[]`, oversize 413, unknown case revision/secret/matrix reasons 422, and a hash conflict returns the existing row (201) — the row is written in one transaction or not at all | AC2–AC6 tests of §9 |

## 11. Rollout

- No feature flag (endpoint is new, harmless before 05.2.1 consumes it). Merge order: T1 → (T2 ∥ T3) → T4 in one PR series on `develop`.
- Monitoring: the edge-validation 422 rate gets an `evidgate_manifest_rejected_total{reason}` counter so a systematically broken reporter is visible.
