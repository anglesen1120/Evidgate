## 1. Goal and non-goals

**Goal.** Only the transitions of 00 §8.1 are accepted on the `run` row created by 05.2.1: `created → queued → running → collecting → complete`, side exits `incomplete` and `canceled`; `complete`/`incomplete`/`canceled` are terminal. Every transition writes the state change, an outbox row and an audit entry, guarded by optimistic `version` (a stale write fails `412`). `GET /v1/runs/{r}` exposes state + current evidence revision.

**Non-goals.** The `created`/`queued` transition itself (already implemented at 05.2.1-T1/T4); what drives `collecting → complete|incomplete` (the reconciler, 05.3.2); the cancel-specific race rules (05.4.1, though this story's guard mechanism is what 05.4.1 calls); evidence revision content (06/05.3.2-T5).

## 2. User stories and acceptance criteria

- As the platform, I never let a run skip a transition or move out of a terminal state, so run state is always trustworthy for policy decisions.
- As an operator, I can read a run's current state and evidence revision through one call, so dashboards never poll multiple endpoints.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Every transition in `{queued→running, running→collecting, collecting→complete, collecting→incomplete, queued→incomplete, running→incomplete, any-non-terminal→canceled}` is accepted when driven by its trigger (first event, first finalize, reconciler verdict, deadline without complete evidence, cancel accept) |
| AC2 | A request for a state the run **already holds or has passed** on the forward path is a no-op returning the current state, never an error (T82): `running→queued` on a `running` run, a duplicate `created→queued`, a second `collecting→complete` — all return `200`/the current state without writing. Terminal-source requests are the same no-op (AC3), so idempotent reconcile/cancel retries and concurrent first batches stay safe |
| AC3 | Only a **forward-skip** — an undeclared edge to a state the run has *not* passed (e.g. `running → complete`) — is rejected at the domain layer (a `Result` failure, never applied). `complete`, `incomplete`, `canceled` are terminal: a further transition request against a terminal run is a no-op returning the current state (D3, T82) |
| AC4 | A canceled run never becomes `complete` even under a race (concurrent reconciler verdict arriving after cancel): the transition function checks terminality **inside** the same transaction as the write, not before it |
| AC5 | Every transition writes: the new `state`, an outbox row (`run.state_changed`), and an audit entry (actor `system` for automatic transitions, the caller for cancel) — all in one transaction |
| AC6 | A transition attempted against a stale `version` (concurrent writer already moved the row) → `412` with the current revision id in `error.details` |
| AC7 | `GET /v1/runs/{r}` → `200 {state, current_evidence_revision_id, version}`; other-tenant id → `404` |

## 4. Data model and migrations

No new table. `run.version` (already added by 05.2.1's migration) is the optimistic-concurrency column (C4, `IsConcurrencyToken`); this story adds the transition guard and an index needed by its own read:

`migrations/NNNN_orchestration_run_state_index.sql`:

```sql
-- current_evidence_revision_id is a nullable pointer column on run, added here because
-- 05.2.1's run table predates evidence revisions (05.3.2 creates evidence_revision).
alter table run add column current_evidence_revision_id uuid;
alter table run add constraint run_current_evidence_rev_fk
  foreign key (org_id, current_evidence_revision_id)
  references evidence_revision (org_id, id);
-- composite FK target evidence_revision(org_id, id) exists once 05.3.2-T5 lands;
-- this migration is sequenced after 05.3.2-T5 in the deploy order (see §11 Rollout).
```

State transition audit uses the existing `audit_log` table (02); no schema addition beyond the pointer column above.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Notes |
|---|---|---|---|---|
| Command | `internal` `TransitionRunStateCommand : ICommand<TransitionResult>` (no public endpoint — invoked in-process by the ingest event handler for `queued→running`, by 05.3.2's reconciler for `collecting→complete\|incomplete`, by 05.4.1's cancel handler for `*→canceled`; the `created→queued` edge has no caller — 05.2.1-T4 inserts the run as `queued` in the create transaction, so `created` is never persisted) | none (internal module API on `Evidgate.Modules.Orchestration.Contracts`) | Guarded: loads the `run` row `FOR UPDATE` inside the caller's tenant transaction, checks the requested edge against the 00 §8.1 adjacency table, then classifies (T82): current/passed state or terminal source → no-op returning current state; declared forward edge → apply, bump `version`, write outbox + audit; forward-skip → reject — all before the caller's own commit (C1: only commands mutate) |
| Query | `GetRunQuery : IQuery<RunStateDto>` | `GET /v1/runs/{r}` | `run:read` | Dapper, read-only tx; returns `{state, current_evidence_revision_id, version}`; cross-tenant → `404` |

Errors: `not_found` (404), `forbidden` (403), `precondition_failed` (412, AC6, `ETag`/`If-Match` semantics via `version`).
Idempotency contract (T82): the command distinguishes three cases — same/passed state or terminal source → no-op returning the current state (no outbox/audit row, no version bump); declared forward edge → apply; forward-skip (AC3) → reject. Two racing first-event batches (04.1.1) therefore both succeed: the winner performs `queued→running`, the loser reads `running` under the same row lock and no-ops — no 409/412 surfaces to ingest.


## 6. States and transitions

Canonical adjacency (00 §8.1), enforced by an explicit table in the domain layer — the single source every caller consults:

| From | To | Trigger |
|---|---|---|
| `created` | `queued` | producer slots committed — 05.2.1-T4 inserts the run as `queued` in the same tx as create (no command call; `created` is never persisted) |
| `queued` | `running` | first accepted event (CI mode) / first claim (agent mode, V2) |
| `running` | `collecting` | first finalize received (05.3.2-T1) |
| `collecting` | `complete` | reconciler verdict `complete`, no block (05.3.2-T2) |
| `collecting` | `incomplete` | deadline passed without complete evidence (05.3.2-T3) |
| `queued`\|`running` | `incomplete` | collection deadline passed without complete evidence — a shard that never sends an event or finalize must not stick `queued`/`running` forever (plans/05:95 "incomplete (deadline passed without full evidence)"; 05.3.2-T3 and 05.10.1-T1 are the callers) |
| `created`\|`queued`\|`running`\|`collecting` | `canceled` | cancel request accepted (05.4.1-T1) |

`complete`, `incomplete`, `canceled` have no outgoing edges (terminal — a request out of them is a no-op, AC2/AC3). Requests for the current state or a state already passed on the forward path (`created → … → collecting`) are no-ops returning the current state (T82). Only an undeclared forward-skip between non-terminal states is rejected (AC3).

## 7. Jobs and integrations

- Outbox row `run.state_changed {run_id, from, to, evidence_revision_id?}` (00 §5.3) — consumed by 09 (UI live state), 12 (usage attribution on terminal states), webhooks (00 §9.5 `run.state_changed`).
- `audit_log` (02) — every transition recorded with actor + reason (system for automatic edges, caller identity for cancel).
- Called by: 04's event handler (`queued→running`), 05.3.2-T1/T2/T3 (`running→collecting`, `collecting→complete|incomplete`), 05.4.1-T1/T2 (`*→canceled`). The `created→queued` edge has no caller: 05.2.1-T4 inserts the run as `queued` in the create transaction, so `created` is never persisted.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| §5.4 T2, T3 | reads/writes stay inside the caller's tenant transaction; `run` already `FORCE RLS` from 05.2.1 | `GetRun_CrossTenant_404` |
| §5.5 C6 | the transition adjacency table + no-op classification is the only place edges are decided — no caller re-implements state logic | `RunStateMachine_RejectsForwardSkips` (property test over all pairs) |
| §5.5 C4 | `version` is the concurrency token; `IsConcurrencyToken` on the EF Core entity | AC6 (`TransitionRun_StaleVersion_412`) |
| §5.7 P3/P5 | one `FOR UPDATE` read + one `UPDATE` + one outbox insert + one audit insert per transition, all local (no network call) | `TransitionRun_CommandCounter_Bounded` |
| Terminal-state race (AC4) | terminality check happens under the same row lock as the write, not as a pre-check | `TransitionRun_CancelRaceWithReconcilerVerdict_StaysCanceled` |
| T82 | a request for a state the run already holds or has passed is a no-op returning the current state (no outbox/audit/version bump); the concurrent-first-batch race is a named test | `TransitionRun_ConcurrentFirstBatch_OneWinnerOneNoOp`; `TransitionRun_SameOrPassedState_NoOp` |
| Privacy/retention | no personal data in state/audit rows beyond actor id (already covered by 02's retention rules) | — |

- **Authorization:** `TransitionRunStateCommand` has no endpoint and runs in the caller's already-authorised tenant transaction (the callers named in §7 hold their own permission); `GET /v1/runs/{r}` requires `run:read`, and another tenant's run is `404 not_found`.
- **Retention/deletion:** state, version and audit rows hold no personal data beyond the actor id; they follow the `run` retention and are deleted only with the tenant (Privacy/retention row above).
- **Telemetry:** every applied transition writes one `run.state_changed` outbox row and one `audit_log` row (§7); a no-op writes neither.
- **Failure path:** a forward-skip is rejected, a stale `If-Match` is `412 precondition_failed`, and any failure rolls back with the caller's transaction, leaving the state and version unchanged (AC3, AC6).

## 11. Rollout

- No feature flag. Single-PR merge on `develop`, sequenced after 05.2.1-T1 (run table exists) and before 05.4.1 (cancel calls this transition function) and 09.3.1 (UI reads `GET /v1/runs/{r}`).
- The `current_evidence_revision_id` migration (§4) is deploy-ordered after 05.3.2-T5's `evidence_revision` table lands, even though this story's task work (the state machine itself) does not depend on it — the FK is added as a follow-up migration in the same PR series once the target table exists, or split into its own migration PR if 05.3.2 has not merged yet.
- Monitoring: `evidgate_run_transition_total{from,to}` and `evidgate_run_transition_rejected_total` counters; a spike in rejected transitions signals a caller bug.
- Rollback: revert the PR; the transition function has no external side effect beyond outbox/audit rows, which are additive and harmless to leave in place.
