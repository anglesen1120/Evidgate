## 1. Goal and non-goals

**Goal.** Make GitHub "Re-run jobs" and "Re-run failed jobs" first-class: GitHub keeps `run_id` and increments `run_attempt` on a re-run ✅ (DECISIONS §6 F10, [contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)). The bound CI identity becomes `(repository_id, run_id, run_attempt)`, so a re-run never trips `producer_slot_taken`; each higher attempt is a **new Evidgate run** with `parent_run_id` and `rerun_scope = ci_attempt`, and attempt 1's evidence stays immutable. Also: an optional Evidgate-initiated re-run through the GitHub App, a CLI cancel poll, and a per-shard maximum duration reported as `shard_timeout` (D8).

**Non-goals.** The Evidgate-side rerun flow and `failed_subset` selection (05.5.1); durable cancel and the soft-stop/kill ladder on the server (05.4.1); the GitHub App installation model (02.4.3); the check-run content shown for a re-run (07.6.1); merging evidence across attempts into one run (not done in V1, see [OPEN] below); agent-mode job timeouts (05.7.3).

## 2. User stories and acceptance criteria

- As a developer, when I press "Re-run failed jobs" in GitHub, my results appear as a new attempt of the same pipeline, not as a 403.
- As a release manager, I see which run is an attempt of which, and a partial attempt is never mistaken for a full regression.
- As a CI owner, a cancelled run stops my shards promptly and a hung shard is named, not discovered at the collection deadline.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Run create with claims `(repository_id=R, run_id=7, run_attempt=2)` while a run for `(R, 7, 1)` exists creates a new run with `parent_run_id = <attempt-1 run>`, `rerun_scope = ci_attempt`, `ci_run_ref.run_attempt = 2`; the attempt-1 run, its events and its evaluations are byte-identical before and after |
| AC2 | Each attempt-2 shard slot binds to `(jti, repository_id, run_id, run_attempt)`; a first write from attempt 2 on attempt 2's slots returns 200, never `producer_slot_taken` |
| AC3 | Partial re-run: attempt 2 with only shard `shard-1` executing creates a run labelled as a subset (`ci_attempt` + `shard_selection`); it is never accepted as full-regression evidence (00 §8.1) |
| AC4 | A stale attempt-1 token writing to an attempt-2 slot gets 403 `producer_slot_taken`; the same token writing to the attempt-1 run (now `incomplete` or `canceled`) is accepted with `late = true` / `after_cancel = true` and never completes it (T12, T81) |
| AC5 | Same run create request repeated for the same `(R, 7, 2)` returns the existing run (idempotent); a claim with a lower attempt than the highest existing one is refused 409 `stale_attempt` and creates no run |
| AC6 | With the per-project flag on and the App installed, `POST /v1/runs/{r}/rerun {mode: "ci"}` triggers one GitHub re-run, writes one audit row, and a repeated call for the same parent run returns the first result without a second trigger |
| AC7 | Flag off, App not installed or suspended, or missing GitHub permission: 409 `ci_rerun_unavailable` with a reason code; nothing is sent to GitHub |
| AC8 | After `POST /v1/runs/{r}/cancel`, the CLI observes `canceled` within one poll interval (default 10 s ± 20 % jitter) and stops its shard; a poll failure never cancels locally by itself |
| AC9 | A shard running longer than `shard_max_duration` (stored in the manifest) is stopped by the CLI and reported as a producer event with reason `shard_timeout`; the run's `missing[]` names that shard before the collection deadline |

## 6. States and transitions

No new run state (00 §8.1). Attempt N starts at `created → queued` when its slots commit (T13) like any CI run. A `canceled` or `incomplete` parent stays so; a new attempt never reopens it. Cancel on the parent does not cancel a child attempt and vice versa. A shard timeout is evidence of a missing/failed shard, not a run state; the run still ends `complete` or `incomplete` by the existing rules. Transitions are idempotent (T82).

## 7. Jobs and integrations

- GitHub App call (T3): installation token from 02.4.3-T2, `POST /repos/{owner}/{repo}/actions/runs/{run_id}/rerun-failed-jobs` (or `/rerun`); endpoint names and the `Actions: write` permission are ✅ (F13, ADR-0007), and a re-run increments `run_attempt` ✅ (F10). `workflow_dispatch` creates a **new** `run_id`, not an attempt ✅ (F13: the dispatch response returns the new run's `workflow_run_id`), so it is the fallback only for a full re-trigger and is labelled `rerun_scope = full` with `parent_run_id`. The outbound call runs from a task-queue job after commit, never inside the request transaction (00 §5.7 P5).
- CLI (T4): cancel poll goroutine-equivalent timer with jitter, spool-aware; per-shard watchdog from `shard_max_duration`; on timeout it sends a final `producer.heartbeat`/`run.log` event with `ext.reason = shard_timeout` and stops the engine.
- [OPEN] O-5.5.2-1: whether a V1 gate may combine attempt 1's passing shards with attempt 2's re-run of failed shards. This plan decides no: evaluation uses one run's own evidence; the owner confirms in the 07 policy plan.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Authorization | create/rerun need `run:create`, settings need `project:write`; a token's attempt claim is verified against the OIDC JWT (02.4.1), never trusted from the body | 403 tests, AC2, AC4 |
| T9 binding | all three CI fields must match; a foreign repository or lower attempt never binds | AC4 |
| Tenant isolation | the lookup of an existing attempt is by `(org_id, project_id, repo, run_id)` inside the tenant transaction | isolation test across two orgs with equal GitHub ids |
| GitHub secrets | installation token minted per call, never persisted or logged (02.4.3) | log-allowlist test |
| Audit | `run.ci_rerun_requested`, `project.ci_settings_changed` through the 02.7.1 writer | AC6 |
| P1/P4 | attempt lookup served by the partial unique index; poll is an indexed `GET` with ETag, 1 req per 10 s per shard process | EXPLAIN check, 304 test |
| Privacy/retention | rows are tenant data, deleted with the org or run retention; GitHub ids are not personal data; the audit row keeps the actor id only | retention job test |

DoR review answers:

- **Authorization:** as above, plus the App's own GitHub permission.
- **Retention/deletion:** parent and child runs follow the same run retention; deleting a parent must not break `parent_run_id` (composite FK `ON DELETE` restricted; retention deletes children first, 11.9.1 procedure).
- **Telemetry:** counters `ci_attempt_runs_created_total`, `ci_rerun_requests_total{result}`, `shard_timeout_total`, `cancel_observed_seconds` histogram; trace attribute `ci.run_attempt`.
- **Failure path:** GitHub 4xx/5xx or rate limit retries with backoff then an alert and an audit `failed` row, the user is told "re-run not triggered"; poll failure keeps the shard running until the shard max duration.
