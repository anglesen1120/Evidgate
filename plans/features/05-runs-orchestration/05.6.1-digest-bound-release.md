## 1. Goal and non-goals

**Goal.** A release is a named set of `release_component` rows (`component_key → sha256 digest` + `environment_revision_id`). A run is bound to a release **only** when the run's recorded `components` (jsonb, captured in the run-create request) match the release's digests — by explicit `POST /v1/releases/{id}/runs` or automatically at run create when the request names a release. Binding by recency ("latest run wins") is forbidden by construction; a digest mismatch surfaces to 07 as a `build_mismatch` reason.

**Non-goals.** Release aggregate decision (`GET /v1/releases/{id}/decision`, 07.5.3); the build-mismatch **reason catalogue** itself (07.2.1-T2 consumes the match data this story exposes); release lifecycle beyond `draft → active` (no archive flow); artifact digests of uploaded binaries (06).

## 2. User stories and acceptance criteria

- As a release approver, I define a release by exact build digests, so only runs that exercised those binaries count toward it.
- As a developer, I get an explicit mismatch error instead of a silent wrong-bind when my run's build doesn't match the release.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/releases` with `components[{component_key, digest, environment_revision_id}]` returns 201 + `release_id`; duplicate `component_key` in the request → 422 `release_invalid`; a digest not matching `sha256:<64 hex>` → 422 `release_invalid` |
| AC2 | `POST /v1/runs/{p}/runs` naming `release_id` binds `release_run` rows for every `component_key` whose digest equals the run's `components[component_key]` — inside the same run-create transaction (05.2.1-T1 hook); a component with a different digest writes **no** row and is recorded for the mismatch report |
| AC3 | `POST /v1/releases/{id}/runs` with `{run_id}` returns 201 + created `release_run` rows keyed `(release_id, run_id, component_key)`; every mismatch listed in `mismatched[]` of the response; a run whose digests match nothing → 422 `release_component_mismatch` |
| AC4 | Explicit bind is refused 409 `release_bind_closed` once any `live` `evaluation` row exists for the run (T15, T22); idempotent re-bind with the same `Idempotency-Key` returns the original rows |
| AC5 | `GET /v1/releases/{id}` returns components + bound `release_run` rows; listing never uses recency — `BoundRunsQuery` orders by `created_at, id` over the `(org_id, release_id)` index only |
| AC6 | The digest-match result (bound keys + mismatch reasons) is available to 07.2.1-T2 via `IReleaseBindingReader` in `Orchestration.Contracts`, feeding `build_mismatch` evaluation reasons (00 §8.5) |
| AC7 | A `draft` release accepts no binds (`422 release_not_active`); components are immutable once the release is `active` — no update endpoint exists and the app role holds no UPDATE grant (C6) |

## 3. Contracts touched

- `POST /v1/projects/{p}/releases`, `GET /v1/releases/{id}`, `POST /v1/releases/{id}/runs` — all already in 00 §9.3; this story adds request/response schemas + `x-permission` (T51) + error codes `release_invalid`, `release_component_mismatch`, `release_bind_closed`, `release_not_active` to `contracts/openapi.yaml`.
- `run` create request gains optional `release_id` (additive field on an existing operation; the bind writes inside the same transaction per FR-05-8).
- `Evidgate.Modules.Orchestration.Contracts` — `IReleaseBindingReader` (+ `ReleaseMismatch` record) consumed by 07.2.1-T2 and aggregated by 07.5.3; additive.
- `release_run` is the **only** run↔release binding (T15): `run.release_id` does not exist; no contract change needed, enforced by review + architecture test.

## 4. Data model and migrations

Two migrations (T1 creates, T2 adds the binding index set it needs — stated per task):

`migrations/NNNN_orchestration_release.sql` (T1):

- `release` (`id`, `org_id`, `project_id`, `name`, `state text not null default 'draft' check (state in ('draft','active'))`, `created_by`, `created_at`, `version`): `unique (org_id, id)` (T3), `unique (org_id, project_id, name)`; index `(org_id, project_id, created_at, id)` for the list keyset (P4). `draft → active` via a `activate` flag on create or `PATCH` omitted — see §6.
- `release_component` (`id`, `org_id`, `release_id`, `component_key`, `digest text check (digest ~ '^sha256:[0-9a-f]{64}$')`, `environment_revision_id`): `unique (org_id, id)` (T3), `unique (org_id, release_id, component_key)`; composite FKs `(org_id, release_id)`, `(org_id, environment_revision_id)`. No UPDATE/DELETE grant for the app role once `release.state = 'active'` (enforced by trigger; C6).
- `release_run` (`id`, `org_id`, `release_id`, `run_id`, `component_key`, `created_at`): `unique (org_id, id)` (T3), `unique (org_id, release_id, run_id, component_key)`; composite FKs `(org_id, release_id)`, `(org_id, run_id)`; index `(org_id, run_id)` serving "which releases is this run bound to" (P4).
- RLS policies on all three via `evidgate.current_org_id()`/`current_project_id()` (T2).

## 5. API shapes (commands, queries, endpoints)

| Op | Type | Route / handler | Detail |
|---|---|---|---|
| `CreateReleaseCommand` | `ICommand<Guid>` | `POST /v1/projects/{p}/releases` · `x-permission: run:create` · `Idempotency-Key` | Validate digests + duplicate keys + env-revision existence (composite FK); insert `release` + `release_component` in one tenant tx; `state` from request (`draft` default; `active` allowed at create) → 201 `{release_id}`; 422 `release_invalid` with `details[]` indices |
| `BindReleaseRunCommand` | `ICommand<ReleaseBindResult>` | `POST /v1/releases/{id}/runs` · `x-permission: run:create` · `Idempotency-Key` | Load release components + run `components` jsonb; compute match set; **guard**: exists `evaluation` with `mode='live'` for the run → 409 `release_bind_closed` (T22 unique `live` row is the guard target); insert matched `release_run` rows + audit + outbox → 201 `{bound[], mismatched[]}`; empty match → 422 `release_component_mismatch`; `draft` release → 422 `release_not_active` |
| run-create bind | inside `CreateRunCommand` (05.2.1-T1) | `POST /v1/projects/{p}/runs` `release_id` field | Same match function, same transaction as run + planned executions + slots; partial match binds matched keys and records `ReleaseMismatch` rows for 07 — never fails the run create |
| `GetReleaseQuery` | `IQuery<ReleaseDetail>` | `GET /v1/releases/{id}` · `run:read` | Dapper: release + components + bound runs (two statements, P3) |
| `IReleaseBindingReader` | contract | consumed by 07 | `BoundKeysAsync`, `MismatchesAsync(run_id)` — read-only |

## 6. States and transitions

`release.state`: `draft → active` (set at create or — scope note — no separate activation endpoint ships in this story; a release created `draft` is activated by re-creating or by a later story if needed → owner-open in §11). `active` is terminal for component edits (no update path, trigger + revoked grant). `release_run` rows are append-only; unbind does not exist in V1 (T15 says "bind before first live evaluation" — removal is not specified; omitted deliberately).

## 7. Jobs and integrations

- `CreateRunCommand` integration point: the release-bind step is a private method invoked inside the existing run-create transaction — no extra round trip, no listener (P5).
- Outbox `release.bound` integration event on each explicit bind, so 07.2.1-T2's reason catalogue can refresh `build_mismatch` context; consumed idempotently (C7).
- 07.5.3 (M3) aggregates per-release decisions over `release_run`; this story guarantees only digest-matching runs ever appear in that set.
- No background jobs; no cron.

**Notes (05.6.1-T1, S248, 2026-11-05):** T1 is delivered; T2 (binding) is open. (1) `migrations/0072_orchestration_release.sql` creates all three tables — `release_run` ships here with its FORCE RLS, `to evidgate_app` tenant policy, composite FKs `(org_id, release_id) -> release` and `(org_id, run_id) -> run`, `unique (org_id, id)`, `unique (org_id, release_id, run_id, component_key)` and `(org_id, run_id)` — but **nothing writes or reads it**: no bind command, no bind route, no `IReleaseBindingReader`, no run-create hook; that surface is 05.6.1-T2. (2) The create route is `POST /v1/projects/{p}/releases` (`run:create`, `Idempotency-Key` operation `release:create`), the read `GET /v1/releases/{id}` (`run:read`, components by `component_key`, no bound-runs section until T2). (3) Limits and codes, now also in the operation descriptions: body cap 64 KiB (413), at most **100** components per release (no earlier limit existed in 00/05, so 100 is the documented bound), name 1..128 trimmed printable characters (no Cc/Cf/Zl/Zp — the migration's `release_name_check` refuses a subset of them (Cc plus the common invisible and separator code points), so an accepted name can never fail the insert; supplementary-plane Cf such as U+E0001 is not yet refused by the app, carried), `component_key` `[a-z0-9][a-z0-9_-]{0,63}`, `digest` `sha256:<64 lower-case hex>`; semantic failures are 422 `release_invalid` with `details[]` (`/components/{i}/<member>`, index repeated), a duplicate name is 409 `release_name_conflict` (unique `(org_id, project_id, name)`), an unparseable body is the only 400 `request_invalid`, while a body that is not a JSON object, an unknown or repeated member and a declared member of the wrong JSON type are 422 `request_invalid` (the `RetentionPolicyBodyParser` split), and an unknown, soft-deleted, other-tenant or sibling-project target is the shared 404 `not_found`, answered by a one-statement project-visibility probe **before** any body rule so a refused caller cannot tell a recognised project id from an unrecognised one. The migration's component guard locks the parent release `for share` before reading its state (a concurrent `draft -> active` therefore cannot interleave with a component insert), refuses an environment revision of a sibling project, and the state trigger refuses `draft -> active` on a release with no component (the create inserts the release `draft`, its components, then activates, so a create naming `active` satisfies it). (4) `state` is set at create only (§6/§11 [OPEN] unchanged): `draft` by insert, `active` by one `update` in the same transaction, and the migration's transition trigger admits `draft -> active` and nothing else while `release_component` refuses UPDATE/DELETE for every role and INSERT once its release is `active`. (5) The create writes one audit row (`release.create`, object `release`, metadata `count`/`status`) and no outbox row; the `release.create` row in `docs/security/audit-taxonomy.md` is **not** updated by this lane (that path is out of its scope) and is carried for the owning lane.
