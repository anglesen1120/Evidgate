## 1. Goal and non-goals

**Goal.** `POST /v1/runs/{r}/rerun` creates a **new** run carrying `parent_run_id` and `rerun_scope ∈ {full, failed_subset}`; a `failed_subset` run contains only the planned executions whose latest attempt failed, errored, timed out or was blocked in the parent's current evidence revision; the scope label is exposed on every read surface and to the policy evaluator, so a subset run can never be mistaken for — or satisfy — a full regression.

**Non-goals.** Reprocess of a stored raw report (`POST /v1/runs/{r}/reprocess`, 04); release binding (05.6.1); cancel semantics (05.4.1); the evaluator's scope decision logic (07.4.1 consumes the input this story ships); the UI label (09.3.1 consumes the API fields).

## 2. User stories and acceptance criteria

- As a QA engineer, I re-run only the failed executions of a run so I get a verdict on a fix without paying for the whole suite again.
- As a release approver, I can see that a run is a subset rerun, so partial evidence is never presented as a full regression.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/runs/{r}/rerun` with `{"rerun_scope":"full"}` on a `complete`/`incomplete`/`canceled` parent returns 201; `GET /v1/runs/{new}` shows `parent_run_id = {r}`, `rerun_scope = full` and the parent's locked `manifest_id`, suite, environment and policy revisions |
| AC2 | `rerun_scope = failed_subset` writes `planned_execution` rows only for `execution_key`s whose latest `case_attempt.normalized_status` under the parent's current evidence revision is `failed`, `timed_out`, `error` or `blocked`; selected rows keep the parent's `shard_id` and `required` flags |
| AC3 | `failed_subset` with no qualifying keys → 422 `rerun_scope_empty`; a parent with no evidence revision yet (`created`/`queued`/`running`/`collecting` before first revision) → 422 `no_source_revision` |
| AC4 | Same `Idempotency-Key` + same canonical payload returns the original `run_id` with no second set of `planned_execution`/`producer_slot` rows; a different payload returns 409 `idempotency_conflict` (T11) |
| AC5 | `rerun_scope` and `parent_run_id` are returned by `GET /v1/runs/{r}` and by every item of `GET /v1/projects/{p}/runs` |
| AC6 | `RunScopeInfo` (contract type) exposes `rerun_scope` + `source_evidence_revision_id` to 07; a contract test proves a `failed_subset` run can never satisfy a policy requiring a full regression (evaluator resolves `INCONCLUSIVE` reason `subset_rerun`; decision logic owned by 07.4.1) |
| AC7 | Rerun registers exactly one `producer_slot` per distinct `shard_id` among the selected executions via `IProducerRegistry.RegisterSlotsAsync` (T9); a subset spanning fewer shards registers fewer slots |

- `POST /v1/runs/{r}/rerun` — already listed in 00 §9.3 (`run:create`); this story adds the request/response schema to `contracts/openapi.yaml` with `x-permission: run:create` (T51) and error codes `rerun_scope_empty`, `no_source_revision`, `invalid_scope`.
- Read models — `GET /v1/runs/{r}` and `GET /v1/projects/{p}/runs` gain `parent_run_id`, `rerun_scope` (additive, backward compatible).

- `run` table — realises the `parent_run_id`/`rerun_scope` columns the area plan §4 row already declares; no contract change.
- No change to `manifest` (the rerun reuses the parent's locked manifest) or to 00 §8.1 (the rerun rule is canonical there).

## 4. Data model and migrations

Migration `migrations/NNNN_orchestration_run_parent_scope.sql`:

- `run` additions (already in the area plan §4 `run` row): `parent_run_id uuid null`, `rerun_scope text not null default 'full' check (rerun_scope in ('full','failed_subset'))`, plus `source_evidence_revision_id uuid null` recording which revision the subset was selected from (auditability; later parent revisions do not re-cut the subset).
- Constraints: `unique (org_id, id)` already present (T3); composite FKs `(org_id, parent_run_id) → run (org_id, id)` and `(org_id, source_evidence_revision_id) → evidence_revision (org_id, id)`.
- Indexes: `(org_id, parent_run_id)` for "children of a run"; `(org_id, project_id, rerun_scope, created_at desc, id desc)` covering the list filter + keyset order (P4, C5).
- `planned_execution` rows of the new run are plain inserts under the existing `unique (org_id, run_id, execution_key)`; the subset query is read-only over the parent's `case_attempt` joined to its `evidence_revision` (latest attempt per `execution_key`).

## 6. States and transitions

The new run is an ordinary 00 §8.1 run: `created → queued` when its producer slots commit inside the create transaction (T13), `queued → running` at the first accepted event. `rerun_scope` is data, not a state; it never changes after insert. The parent's state is untouched — a rerun is a new run, never a mutation of the parent.

## 7. Jobs and integrations

- `IProducerRegistry.RegisterSlotsAsync` (04.1.2-T4, T9): one slot per selected shard; bound-identity rules (403 `producer_slot_taken`, 422 `unknown_producer`) apply unchanged.
- Outbox `run.created` row in the same transaction drives dispatch (00 §5.3); reconcile (05.3.2-T2) runs against the new run's own planned set.
- Webhook `run.state_changed` (00 §9.5) carries the new run's transitions; consumers read `rerun_scope` from the run payload.
- `RunScopeInfo` is read by 07.4.1's evaluator trigger (exceptions/input snapshot pattern, T24); this story ships the contract type + a stub-evaluator contract test, not the decision logic.
