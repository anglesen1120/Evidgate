## 1. Goal and non-goals

**Goal.** A run permanently records what it was created for: `ref_kind`, `ref_name`, `pr_number`, `head_sha`, `base_sha`, `trigger_event`, `is_fork`, and whether any of them is unverified (`unverified_ref`). Values come from the minted CI token's verified `ref` and `sha` claims when the caller is a `ci_producer` credential whose recorded `ci_token_issue` row is found, otherwise from caller-supplied values labelled `unverified_ref = true`; `trigger_event` and `base_sha` are always body-only. The run list filters by them; a fork run is labelled, advisory-only and never bound to a release or counted by a gating policy. None of the fields can change after creation.

**Non-goals.** Branch-scoped policy mode is decided (DECISIONS §8.1 D-A10: `gating_refs`) and implemented in 07 — this story supplies inputs only. Check-run content and the PR comment (07.6.1, review D2). The run row, idempotency and slots (05.2.1). Release bind (05.6.1). Token minting and the fork token path itself (02.4.1/02.4.2; this story only documents and enforces the consequence).

**D2 reading `[DECISION]`.** GitHub "Re-run failed jobs" keeps `run_id` and increments `run_attempt`. A re-run attempt is a **new Evidgate run** (new `run_id`) whose `ci_run_ref.run_attempt` differs; it never reuses the old run's producer slots. This story stores the identity; the binding rule is 05.2.1 AC11 / 04's `BindOrCheckAsync`.

**Verified-claim mapping `[DECISION]` D-S45-Q1 (coordinator, 2026-10-13; jev option C).** A caller is *verified* when its principal is a `ci_producer` credential carrying a CI run reference (`principal.CiRun != null`) **and** the Evidgate-recorded `ci_token_issue` row for that run reference (`repository_id`/`run_id`/`run_attempt`, scoped to the org and project) is found — the row 02.4.1 writes when it exchanges the verified GitHub OIDC token, read inside the run's C1 tenant transaction through `ITenantDb`. No Identity change, no `IRequestPrincipal` change, no token-claim change. **Lookup key `[DECISION]` D-S45-Q2 (S45 lane decision after review F1, coordinator-ratified 2026-10-14; owner review recorded in `docs/phase-review.md`).** The row is looked up by the run reference the minted token carries, **not** by the credential's `jti`: 02.4.1 stores the GitHub OIDC token's `jti` in `ci_token_issue.jti` while the `ci_producer` token Evidgate mints carries a fresh `jti`, so a `jti` lookup never matches in production. `ref` and `sha` are fixed per GitHub run attempt, so the newest row of the attempt (`order by created_at desc limit 1`) is authoritative and one attempt that exchanged several tokens does not throw. Migration `0037` adds the covering `ci_token_issue_run_idx` index for this read; Identity code and the token contract are unchanged. The mapped claim set is `ref` and `sha` only: `refs/heads/<n>` → `branch`/`<n>`; `refs/tags/<n>` → `tag`/`<n>`; `refs/pull/<N>/merge` → `pull_request`/`<N>/merge` with `pr_number = N` (digits only, > 0, fits `integer`); any other `ref` shape → `ref_kind`/`ref_name`/`pr_number` stay null. `head_sha` is the `sha` claim **only** for a `branch` or `tag` ref: for a `pull_request` ref that claim is GitHub's test-merge commit, so it is not stored as `head_sha`. `is_fork` is false for every verified caller (02.4.1 AC3 refuses a fork PR exchange with 403, so a verified caller is never a fork). `trigger_event` and `base_sha` have no verified source — the minted token carries no `event_name`, `ref_type`, base sha or fork flag — so they are body-only. A claim always wins over a conflicting body value, which is *ignored*, never rejected (AC3); every value taken from the body sets `unverified_ref = true`; and when `principal.CiRun != null` but the `ci_token_issue` row is missing the caller is treated as **not** verified (body values stored, `unverified_ref = true`) — fail toward advisory, never trust the body as verified.

## 2. User stories and acceptance criteria

- As a release approver, I see which branch, PR and commit a run belongs to, so I do not approve on a run built for something else.
- As a security owner, a fork PR can never influence a release decision.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/runs` from a verified CI caller — a `ci_producer` principal carrying a CI run reference whose recorded `ci_token_issue` row exists — stores `ref_kind`, `ref_name`, `pr_number`, `head_sha`, `is_fork = false` and `unverified_ref = false` from the minted token's `ref` and `sha` claims: `refs/heads/<n>` → `branch` + `ref_name = <n>`; `refs/tags/<n>` → `tag` + `<n>`; `refs/pull/<N>/merge` → `pull_request` + `ref_name = <N>/merge` with `pr_number = N`; any other shape → those fields stay null; `head_sha` is the `sha` claim only for a `branch` or `tag` ref; `trigger_event` and `base_sha` have no verified source and come from the body `[DECISION]` D-S45-Q1 |

## 4. Data model and migrations

`migrations/NNNN_run_identity.sql` (extends `run` from 05.2.1; `unique (org_id, id)`, composite FKs and RLS unchanged):

```sql
alter table run
  add column ref_kind text check (ref_kind in ('branch','tag','pull_request')),
  add column ref_name text check (char_length(ref_name) <= 255),
  add column pr_number integer check (pr_number > 0),
  add column head_sha text check (head_sha ~ '^[0-9a-f]{40}([0-9a-f]{24})?$'),
  add column base_sha text check (base_sha ~ '^[0-9a-f]{40}([0-9a-f]{24})?$'),
  add column trigger_event text check (trigger_event in ('push','pull_request','schedule','manual','dispatch')),
  add column is_fork boolean not null default false,
  add column unverified_ref boolean not null default false,
  add constraint run_pr_requires_number check (ref_kind <> 'pull_request' or pr_number is not null);
-- run_project_ref_idx (project_id, ref_name, created_at, id) is 05.2.2-T2.2's migration, not this one.
create index if not exists ci_token_issue_run_idx   -- D-S45-Q2: the verified-caller read's index
  on ci_token_issue (project_id, repository_id, run_id, run_attempt, created_at desc);
create trigger run_identity_immutable before update on run
  for each row execute function forbid_run_identity_update(); -- raises if any identity column differs
```

Existing rows: columns null, `is_fork = false`, `unverified_ref = false`. The migration creates no index on `run`; `run_project_ref_idx (project_id, ref_name, created_at, id)` is created by 05.2.2-T2.2's own migration (the next free number after `0037`). Its one index is `ci_token_issue_run_idx`, added to the Identity-owned `ci_token_issue` for the D-S45-Q2 run-reference lookup (no column, grant, policy or RLS change there). Retention: identity values are business metadata, deleted only with the run/tenant.

## 6. States and transitions

No new state machine. Identity columns are write-once at `created`; the run lifecycle (00 §8.1) is unaffected. Fork runs follow the same lifecycle but their evaluation input is flagged advisory (see 07).

## 7. Jobs and integrations

- The run-created outbox row (05.2.1) carries the identity block — the seven `ref` members plus `unverified_ref`, additive, existing members unchanged — so 07 and 09 need no extra lookup.
- 07.1.1: the policy engine reads `is_fork`; a fork run yields at most an advisory evaluation, never a binding decision.
- 05.6.1: bind validation rejects `is_fork = true` before the digest match.
- 02.4.1/02.4.2: documentation lists fork PRs as unsupported for gating.

- `05.2.2-T2 (S48)` — `[DECISION]` **the `head_sha` filter is an additive amendment of AC6.** AC6 listed `ref_name`, `pr_number`, `trigger_event` and `is_fork`; the list also accepts `head_sha` (full 40- or 64-hex lowercase sha, exact match) — the commit filter the S48 brief asked for — so AC6's text gains it too. All five filters are optional, AND-combined and exact-match; an unknown query parameter is ignored, like the other lists.
- `05.2.2-T2 (S48)` — `[DECISION]` **order, cursor and 422 shapes.** Order is `(created_at, id)` ascending (AC6 verbatim); the cursor is the `KeysetCursor` of the last row's `(created_at, id)` and a page is one `(created_at, id) > (…)` keyset statement, so a concurrent insert sorts after the cursor and no row is repeated or skipped. The cursor is opaque and not signed: it is bound to the filter set only by the client re-sending the same filters, so a garbled or tampered value is 422 `request_invalid` (`details[].path` `cursor`, reason `malformed`) while a well-formed one can only move the position inside the caller's own project/tenant rows (filters, `project_id` and RLS are always applied — it can leak nothing). Limit and envelope are the 00 §9.1 ones (default 50, max 200 → 422 `request_invalid`, `limit`/`out_of_range`; `{items, next_cursor}`); any ill-typed, blank or out-of-range filter value is 422 `request_invalid` with `details[].path` = the parameter name and reason `invalid_value` (a blank string is invalid, never "absent").
- `05.2.2-T2 (S48)` — `[DECISION]` **project scope: the list follows `GetRunQuery` only.** An unknown, soft-deleted or other-tenant project answers the same 404 `not_found` (never an empty 200 page, so a caller cannot probe another tenant's project), and a credential scoped to a sibling project maps exactly as `GetRunQuery` does (scope mismatch → 404) — NOT as `CreateRunCommand`, which answers 403 `project_scope_mismatch`. That scope-mismatch branch is defensive today and untested over HTTP: only a service credential carries a project scope and `run:read` is outside the service ceiling, so the permission stage answers 403 before the scope check runs.
- `05.2.2-T2 (S48)` — the list's item projection is `run_id`, `state`, `created_at`, `ref` (the existing `RunRef` block, all seven members, `null` where unknown) and `unverified_ref`, so a client can label body-only identity. The `RunSummary` members `decision`, `rerun_label`, `reprocess_label` and `parent_run_id` are neither projected nor filtered here: hand-over to 07 (decision), 05.5.1-T2 (`parent_run_id` and `rerun_scope`), 05.5.2-T2 (`rerun_label`) and 04's reprocess route (`reprocess_label`). 05.5.1-T2 adds `parent_run_id`, `rerun_scope` and the `?rerun_scope=` filter to this item and should reconcile its 05.5.1 §4 index `(org_id, project_id, rerun_scope, created_at desc, id desc)` with this ascending order (build it ascending, or record why the descending form is kept).
- `05.2.2-T2 (S48)` — hand-over: **`pr_number`/`head_sha` have no index.** `run_project_ref_idx (project_id, ref_name, created_at, id)` (migration `0038`) serves only the `ref_name` keyset path; `trigger_event` and `is_fork` filter after the scan. Measured on a Postgres 17 scratch instance at 100 000 runs per project `[INFERENCE]` (the fixture pins Postgres 18): the unfiltered ascending list reads ~52 rows per page through 0031's descending `run_project_created_idx (org_id, project_id, created_at desc, id)` via a backward scan plus an Incremental Sort, so it needs no new index; the `ref_name` path is a forward scan of `run_project_ref_idx` with no Sort; a `trigger_event`-only filter is cheap; `pr_number` or `head_sha` WITHOUT `ref_name` scans the whole project (~100 000 rows, ~6 600 buffers, 24–176 ms) — the real remaining gap. Receiver: a 05.2.2 follow-up, or 09.3.1-T1 when the run volume makes the scan measurable.
- `05.2.2-T2 (S48)` — migration lock note: `0038_run_project_ref_idx.sql` uses a plain `create index` inside the runner's one transaction per file (`WithTransactionPerScript`), because `create index concurrently` cannot run there (migrations/README.md, "Known limits"). The SHARE lock blocks run create and the `update … set state` writes for the build (reads unaffected); the table is the youngest orchestration table and no production tenant exists yet, so the build is sub-second and the same plain form as 0028-0034 is kept.
