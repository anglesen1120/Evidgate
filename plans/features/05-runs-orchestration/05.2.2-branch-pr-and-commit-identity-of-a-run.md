## 1. Goal and non-goals

**Goal.** A run permanently records what it was created for: `ref_kind`, `ref_name`, `pr_number`, `head_sha`, `base_sha`, `trigger_event`, `is_fork`. Values come from verified GitHub OIDC claims when present, otherwise from CLI-supplied values labelled `unverified_ref`. The run list filters by them; a fork run is labelled, advisory-only and never bound to a release or counted by a gating policy. None of the fields can change after creation.

**Non-goals.** Branch-scoped policy mode is decided (DECISIONS §8.1 D-A10: `gating_refs`) and implemented in 07 — this story supplies inputs only. Check-run content and the PR comment (07.6.1, review D2). The run row, idempotency and slots (05.2.1). Release bind (05.6.1). Token minting and the fork token path itself (02.4.1/02.4.2; this story only documents and enforces the consequence).

**D2 reading `[DECISION]`.** GitHub "Re-run failed jobs" keeps `run_id` and increments `run_attempt`. A re-run attempt is a **new Evidgate run** (new `run_id`) whose `ci_run_ref.run_attempt` differs; it never reuses the old run's producer slots. This story stores the identity; the binding rule is 05.2.1 AC11 / 04's `BindOrCheckAsync`.

## 2. User stories and acceptance criteria

- As a release approver, I see which branch, PR and commit a run belongs to, so I do not approve on a run built for something else.
- As a security owner, a fork PR can never influence a release decision.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/runs` from a verified GitHub OIDC caller stores `ref_kind`, `ref_name`, `pr_number`, `head_sha`, `base_sha`, `trigger_event`, `is_fork` derived from the claims (`ref`, `ref_type`, `sha`, `event_name`, PR payload fields ⚠️ exact claim and payload names to confirm against GitHub docs), `unverified_ref = false` |
| AC2 | A caller without CI claims (ingest-token exchange, CLI) supplying the fields gets them stored with `unverified_ref = true`; absent fields stay null; the run is still created |
| AC3 | When OIDC claims are present and the request body supplies conflicting values, the claim wins and the mismatch is ignored, never trusted (`unverified_ref = false`) |
| AC4 | Constraints reject invalid shapes: unknown `ref_kind`/`trigger_event` → 422 `validation_failed`; `ref_kind = pull_request` requires `pr_number`; `head_sha`/`base_sha` match `^[0-9a-f]{40}$` or 64 (SHA-256 repos); `ref_name` ≤ 255 chars |
| AC5 | No update path: a direct `UPDATE` of any identity column fails (DB trigger, SQLSTATE `P0001`); no API accepts a change; a re-run attempt creates a new run |
| AC6 | `GET /v1/projects/{p}/runs?ref_name=&pr_number=&trigger_event=&is_fork=` filters with cursor paging; result order `(created_at, id)`; the filtered query uses the `(project_id, ref_name, created_at, id)` index (plan asserted) |
| AC7 | A run with `is_fork = true` is labelled `fork` in the read model and `GET /v1/runs/{r}`, is never bound to a release (`release` field → 422 `fork_run_not_bindable`) and never satisfies a gating policy (reported to 07 as `advisory = true` input) |
| AC8 | A project cannot opt a fork run into gating: no setting or permission turns the rule off in V1 |
| AC9 | Identity values are the same on a replayed idempotent create (05.2.1 AC3); a different value under the same key → 409 `idempotency_conflict` |

## 4. Data model and migrations

`migrations/NNNN_run_identity.sql` (extends `run` from 05.2.1; `unique (org_id, id)`, composite FKs and RLS unchanged):

```sql
alter table run
  add column ref_kind text check (ref_kind in ('branch','tag','pull_request')),
  add column ref_name text check (char_length(ref_name) <= 255),
  add column pr_number integer check (pr_number > 0),
  add column head_sha text check (head_sha ~ '^[0-9a-f]{40}([0-9a-f]{24})?$'),
  add column base_sha text check (base_sha ~ '^[0-9a-f]{40}([0-9a-f]{24})?$'),
  add column trigger_event text check (trigger_event in ('push','pull_request','schedule','manual','dispatch')),
  add column is_fork boolean not null default false,
  add column unverified_ref boolean not null default false,
  add constraint run_pr_requires_number check (ref_kind <> 'pull_request' or pr_number is not null);
create index run_project_ref_idx on run (project_id, ref_name, created_at, id);
create trigger run_identity_immutable before update on run
  for each row execute function forbid_run_identity_update(); -- raises if any identity column differs
```

Existing rows: columns null, `is_fork = false`. Retention: identity values are business metadata, deleted only with the run/tenant.

## 5. API shapes (commands, queries, endpoints)

| Shape | Endpoint | Permission | Notes |
|---|---|---|---|
| Command `CreateRunCommand` (extended) | `POST /v1/projects/{p}/runs` | `run:create` | optional body `ref { kind, name, pr_number, head_sha, base_sha, trigger_event, is_fork }`; OIDC claims override; the response adds `unverified_ref`; errors 422 `validation_failed` (indices), 422 `fork_run_not_bindable` |
| Query `ListRunsQuery` (Dapper) | `GET /v1/projects/{p}/runs` | `run:read` | filters `ref_name`, `pr_number`, `trigger_event`, `is_fork`, cursor; returns `ref`, `is_fork`, `unverified_ref` |
| Query `GetRunQuery` | `GET /v1/runs/{r}` | `run:read` | adds the identity block and `advisory_only` |

`advisory_only = is_fork`, derived, never stored separately.

## 6. States and transitions

No new state machine. Identity columns are write-once at `created`; the run lifecycle (00 §8.1) is unaffected. Fork runs follow the same lifecycle but their evaluation input is flagged advisory (see 07).

## 7. Jobs and integrations

- The run-created outbox row (05.2.1) carries the identity block so 07 and 09 need no extra lookup.
- 07.1.1: the policy engine reads `is_fork`; a fork run yields at most an advisory evaluation, never a binding decision.
- 05.6.1: bind validation rejects `is_fork = true` before the digest match.
- 02.4.1/02.4.2: documentation lists fork PRs as unsupported for gating.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |

| Retention/deletion (DoR b) | Identity rows live and die with the run; no personal data (branch names may contain user names, treated as business data, not logged beyond the run id) | review note, log-scrub test |

| Failure path (DoR d) | A validation failure aborts before any write (422); the immutability trigger failing an update returns 500 with an alert, never a silent overwrite | AC4, AC5 |
| Performance P2 | Filtered list is one keyset query on the new index, no N+1 | query-plan test |

## 11. Rollout

- No flag: columns are nullable and additive; the old CLI keeps working (fields absent, `unverified_ref = false`, `is_fork = false`).
- Order: 00 §15 entry and OpenAPI, migration, handler, then list filters, then fork rules; the fork rule ships before 05.6.1 exposes release bind.
- Monitoring: share of runs with `unverified_ref = true`, fork run count; a spike of unverified runs signals a CLI or OIDC misconfiguration.
- Rollback: revert code; columns remain unused. The trigger is dropped only with the migration revert.
- Decided: `unverified_ref` and fork runs are advisory-only (DECISIONS §8.1 D-A11).
