## 1. Goal and non-goals

**Goal.** Extend agent-mode leasing with exclusive device leases for the Android pool: at most one active lease per device, a recorded app-and-data reset before the job starts, the app checksum captured with the run, and scheduling so a job waiting for a device never holds a web/API pool slot — reporting `unschedulable` instead of hanging when no device can serve it.

**Non-goals.** The Appium adapter implementation itself (04.5.1 builds on this contract); actual device provisioning, MDM or a device farm (V3+); iOS pool decisions (05.9.1 spike); environment locks for `data_isolation = shared` (05.7.3-T4 — a different table and trigger); cleanup re-run gating (05.7.5).

## 2. User stories and acceptance criteria

- As an Android agent, I claim a device exclusively for my job so a second job can never drive the same device mid-test.
- As an operator, I see a job waiting for a device as waiting in the device pool — not silently holding a web slot — and as `unschedulable` when the pool can never serve it.
- As a reviewer, I can prove which app binary ran because the lease records the app checksum that lands in the run's evidence.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Two concurrent device-lease acquisitions for the same `device_udid_hash` in one pool: exactly one succeeds; the loser waits or fails — `device_lease` never holds two active rows per device (enforced by a partial unique index, verified by a concurrency test) |
| AC2 | A lease row requires `reset_policy` and is acquired only after the reset is confirmed: a job whose `device_lease` shows no reset confirmation never leaves `leased` → `running` on the device path; the confirmation row is audited |
| AC3 | The recorded `app_checksum` (`sha256:`) is queryable with the run (`GET /v1/runs/{r}` device block) and survives lease release — evidence identifies the exact binary (05 §6) |
| AC4 | A job queued for a device holds no web-pool slot: web concurrency cap is untouched while N device jobs wait; the device wait uses its own `queue_timeout_at` and expires independently |
| AC5 | When every matching device is leased or offline, the claim path returns no lease and — if no pool can ever satisfy the capability — the job is set `unschedulable` with the unmet requirement, per 00 §8.2 |
| AC6 | Device lease expiry follows job-lease rules: `expires_at` passes without heartbeat → lease released, epoch bump, next acquirer sees a clean slate; late release/heartbeat from the dead epoch gets 409 |
| AC7 | Appium port allocation per device is bounded: the lease records the assigned port range and refuses a second claim on ports already in the active lease's range |

## 3. Contracts touched

- 00 §8.2 job states — implemented; `unschedulable` reuse for exhausted device pools is the existing state, not a new one.
- `device_lease` columns are already listed in 05 §4; this plan fixes the constraint and index details inside that contract (no new endpoint).
- Resolved (T59): device leases are acquired inside `POST /v1/agents/jobs/claim` (`job:claim`) — no `device:claim` permission exists; the lease is a second step inside the job claim for `pool` types declaring `requires_device`.

## 4. Data model and migrations

Migration `migrations/NNNN_orchestration_device_lease.sql` (DbUp; number assigned at implementation).

| Object | Definition |
|---|---|
| `device_lease` | `id uuid`, `org_id uuid not null`, `project_id uuid not null`, `pool text not null`, `device_udid_hash text not null`, `job_id uuid not null`, `epoch int not null`, `app_checksum text not null` (`sha256:`), `reset_policy text not null`, `reset_confirmed_at timestamptz`, `reset_confirmed_by uuid`, `appium_port_base int not null`, `leased_at timestamptz not null`, `heartbeat_at timestamptz`, `expires_at timestamptz not null`, `released_at timestamptz`, `outcome text` (`released`/`expired`/`failed`), `version int not null default 1`, `created_at`, `updated_at` |
| Constraints | `unique (org_id, id)` (T3); composite FK `(org_id, job_id)` → `job (org_id, id)`; `check (app_checksum ~ '^sha256:[0-9a-f]{64}$')`; `check (reset_policy in ('full_wipe','app_reset','keep_data'))`; `check (appium_port_base between 4700 and 6900)` ⚠️ Appium default range, exact bounds confirmed in 04.5.1 |
| Exclusivity | partial unique index `device_lease_active_uq` on `(org_id, pool, device_udid_hash) where released_at is null` — one active lease per device per pool |
| Indexes | `(org_id, pool, device_udid_hash)` covered by the partial unique; `(org_id, expires_at) where released_at is null` for the expiry sweep (05.10.1-T2); `(org_id, job_id)` for job-side lookup |
| RLS | `FORCE ROW LEVEL SECURITY`; policy `org_id = evidgate.current_org_id()` (T2, `missing_ok` helpers); devices are never addressed by raw UDID — only `device_udid_hash` (HMAC of UDID, keyed like T5 tokens, so cross-tenant correlation is impossible) |
| Immutability | app checksum + reset policy never update after `leased_at` (no update path on those columns; domain enforces, SQL `REVOKE UPDATE` is not granular enough so a `BEFORE UPDATE` trigger rejects changes to `app_checksum`, `reset_policy`, `device_udid_hash`) |

## 5. API shapes (commands, queries, endpoints)

Device lease rides inside the existing claim contract — no new `/v1` surface:

| Command / Query | Handler | Endpoint | Permission | Status / errors |
|---|---|---|---|---|
| `ClaimJobCommand` (extended) | Orchestration command, EF Core write + Dapper `FOR UPDATE SKIP LOCKED` inside `ITenantScope` | `POST /v1/agents/jobs/claim` | `job:claim` | 200 lease `{job_id, epoch, deadline, device: {udid_hash, appium_port_base, reset_required}}` when the pool declares `requires_device`; 200 empty claim otherwise; 409 `lease_lost` on stale-epoch re-claim; 403 wrong pool/token scope; 429 `rate_limited` |
| `RenewJobLeaseCommand` (extended) | heartbeat path now also renews the device lease row (`expires_at`) in the same tx, epoch-fenced | `POST /v1/jobs/{j}/heartbeat` | `job:execute` | 204; 409 `lease_lost` for a non-current epoch (AC6); 404 cross-tenant |
| `ConfirmDeviceResetCommand` | marks `reset_confirmed_at/by` on the active lease before `job` may transition `leased → running` | internal call from the claim flow / agent bootstrap message, not a new public route | `job:execute` (via the job's bound agent identity) | 409 `device_reset_required` if the job tries to report `running` events first |
| `ListDeviceLeasesQuery` (Dapper, read-only tx) | operator/support view of active + expired leases per pool | `GET /v1/projects/{p}/device-leases` ⚠️ route name provisional — if `contracts/openapi.yaml` gains it, `x-permission: run:read` per T51; otherwise this stays an operator `/internal` query (flag in §3 before build) | `run:read` | 200 cursor list `(created_at, id)` (00 §9.1) |

Idempotency: claim is naturally idempotent by epoch — a retried claim for the same job by the same agent returns the current lease (no `Idempotency-Key` needed since no resource is created twice; the partial unique guarantees it).

## 6. States and transitions

`device_lease` per row: `active (leased_at set, released_at null) → released | expired | failed`. A second `active` row for the same `(org_id, pool, device_udid_hash)` is impossible (partial unique). Job device sub-state is the existing `leased → running` transition gated on `reset_confirmed_at IS NOT NULL` for `requires_device` pools; the job itself still follows 00 §8.2 (`lost` on lease expiry re-queues it — the device lease expires with it).

## 7. Jobs and integrations

- `POST /v1/agents/jobs/claim` internally: pick job (`SKIP LOCKED`, capability match, fairness from 05.7.3) → if `requires_device`, pick a free device in the pool (`SKIP LOCKED` over `device_lease_active_uq` probe + device registry read) → write `job_lease` + `device_lease` in the **same** short transaction (one atomic handover; a device picked without a lease row is impossible).
- Expired device leases are swept by the expired-lease sweeper (05.10.1-T2) — this story registers the schedule name (`device_lease_sweep`) and the handler contract; the sweeper implementation lives there.
- Reset execution itself runs on the agent host via the adapter `prepare` operation (00 §10) — the server only records the confirmation; no network call inside the lease transaction (P5).
- Consumed by 04.5.1 (Appium adapter maps `appium_port_base` + `udid_hash` onto device targets) and 05.9.1 (iOS spike reuses this lease model for evaluation).

- Behind the existing V2 agent-mode flag (no separate flag): `requires_device` pools only accept claims once this lands; Android/V2-conditional scope per DECISIONS §3.
- Monitoring: new SLIs already covered by 00 §11 operational list — lease-loss rate and `unschedulable` count per pool; device-wait timeout rate added to the orchestration dashboard (10).
