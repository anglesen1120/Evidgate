## 1. Goal and non-goals

**Goal.** Prove, end to end, that an `evidgate-agent` (Node 22+, TS 6.0.x, `packages/agent`) claiming a web/API job against a real API + worker produces the same evidence shape as CI mode: same `case_attempt` rows, same `evidence_revision` structure, same finalize → reconcile → decision path. Also prove the two resilience scenarios: a claim storm double-claims nothing, and a dead agent's lease expires and re-queues under a new epoch.

**Non-goals.** The executor internals (05.7.4-T2/T3 already ship disposable workspace, artifact policy, secret resolution); claim/heartbeat endpoints (05.7.2); scheduler correctness beyond what the storm test needs (05.7.3); Android devices (05.8.1) and cleanup re-run gates (05.7.5); the Playwright adapter itself (04.3.1).

## 2. User stories and acceptance criteria

- As the Tech Lead, I need one deterministic test that runs the whole agent path so a regression in any of 05.7.x is caught in CI, not on a customer runner.
- As an operator, I need proof that 50 agents racing for one job get exactly one lease and that a crashed agent's job finishes under a new epoch, so leasing is safe before V2 ships.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A suite run claimed, executed and finalized by the agent yields an `evidence_revision` with `completeness = complete`, `missing[] = []`, and `case_attempt` rows identical in shape (same columns populated, same `normalized_status` mapping) to a CI-mode run of the same manifest — asserted by diffing the two evidence shapes field-by-field, excluding identity fields (`run_id`, `producer_id`, timestamps) |
| AC2 | The agent-mode run follows `created → queued → running → collecting → complete` exactly (00 §8.1); `job` follows `queued → leased → running → finished` with a committed `job_lease` row carrying `epoch = 1` |
| AC3 | 50 concurrent `POST /v1/agents/jobs/claim` calls from distinct agent identities for one queued job produce exactly one 200 lease; the rest get an empty claim; `job_lease` has exactly one active epoch row |
| AC4 | An agent that claims a job and dies (no heartbeat) sees its lease expire at 90 s; the job is re-leased to the next claimant with `epoch = 2`; events sent with `epoch = 1` are stored as stale evidence and never complete the job (FR-05-10); the run still reaches `complete` via the epoch-2 producer |
| AC5 | The end-to-end run emits a `producer.heartbeat`/event stream under the agent identity bound at first write (T9): a different `jti` posting to the same producer slot gets 403 `producer_slot_taken` |

## 3. Contracts touched

- None changed. This story exercises 00 §8.1/§8.2/§9.3/§9.4 and T9/T12/T13 as a consumer.
- Evidence-shape parity is asserted against the contract, not by copying CI-mode internals — if the diff finds a real divergence (e.g. `job_id`/`epoch` present in agent events, absent in CI), the event schema (00 §9.4 already includes `job_id`, `epoch`) covers it and the test compares only contract fields.

## 4. Data model and migrations

None. All tables (`job`, `job_lease`, `case_attempt`, `evidence_revision`, `producer_slot`) are created by 05.7.1/05.7.2/05.3.3/05.3.2 and owned there. Test fixtures seed them through the public API + `IProducerRegistry` path, never direct inserts that bypass invariants.

## 5. API shapes (commands, queries, endpoints)

No new endpoints or handlers. The test drives the existing surface:

| Endpoint | Role in test |
|---|---|
| `POST /v1/projects/{p}/manifests`, `POST /v1/projects/{p}/runs` | seed a web/API run (CI-created manifest, `run:create`) |
| `POST /v1/agents/jobs/claim` | `job:claim`; agent token scoped to tenant + pool |
| `POST /v1/jobs/{j}/heartbeat` | `job:execute`; epoch-fenced extension |
| `POST /v1/runs/{r}/events`, `POST /v1/runs/{r}/finalize` | `event:write`; the agent reports test events and closes its producer slot (T9) |
| `GET /v1/runs/{r}` | `run:read`; assert state + current evidence revision |

## 6. States and transitions

None new. The test asserts the canonical machines only: run `created → queued → running → collecting → complete` (00 §8.1); job `queued → leased → running → finished` and `lost → re-queued` under a new epoch on lease expiry (00 §8.2).

## 7. Jobs and integrations

- The e2e harness runs `Evidgate.Api` + `Evidgate.Worker` + real PostgreSQL (Testcontainers.PostgreSQL) in one xUnit collection; the agent under test is the real `evidgate-agent` package driving a fake engine (stubbed `prepare`/`execute`/`collect` per the adapter contract, 04.3.1-T1) — no real browser needed.
- The Playwright engine image digest is pinned in the JobSpec (D6) but the image itself is not pulled in tests; engine execution is stubbed at the adapter boundary.
- Consumes: `IProducerRegistry` slot binding at run create (04.1.2-T4/T9), `freeze(run_id)` result persisted by the reconciler (05.3.2-T5).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T9 producer binding | AC5: first accepted write binds the slot to the agent token `jti`; foreign identity gets 403 `producer_slot_taken` | `AgentE2E_Tests.ForeignIdentityOnBoundSlot` |
| FR-05-10 / F6 | claim is a short `FOR UPDATE SKIP LOCKED` tx; no DB lock held while the (stubbed) engine runs; epoch fencing | AC3, AC4 |
| 00 §5.7 P1 | claim/heartbeat are hot endpoints; the storm test doubles as the burst check — 50 claims complete inside the endpoint budget with exactly one winner | AC3 timing assertion |
| 00 §5.4 tenancy | the agent token is scoped to one tenant+pool (05.7.4-T1); the test asserts a second tenant's token gets 404/403 on claim and run reads | `AgentE2E_Tests.CrossTenantClaim` |
| Authz (C2/S2) | `job:claim` on claim, `job:execute` on heartbeat, `event:write` on events/finalize — all from the `agent` service identity; no member permissions | contract test asserting `x-permission` on the four routes |
| Secrets | JobSpec carries secret *references* only; the stubbed resolve path asserts no secret value appears in events or logs (05 §6) | log-scan assertion in T1.2 |
| Retention/PDPL | none new — test data only, Respawn resets the container schema | — |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Agent claim → execute → finalize → complete with full evidence parity vs CI mode | `AgentE2E_Tests.FullRunMatchesCiEvidenceShape` (xUnit v3 + Testcontainers.PostgreSQL + the real agent + stub engine) — AC1, AC2 |
| Claim storm: 50 concurrent claims, one job | `AgentE2E_Tests.ClaimStormSingleLease` — AC3 |
| Lease expiry: agent dies, epoch bump, stale events, run completes | `AgentE2E_Tests.LeaseExpiryRequeuesUnderNewEpoch` — AC4 |

| Cross-tenant claim/read isolation | `AgentE2E_Tests.CrossTenantClaim` |

Fixture note (05 §7): the fake engine double lives under `packages/agent` test utilities; it emits a deterministic `test.started`/`test.finished` stream with known `execution_key`s so evidence parity is comparable.

## 11. Rollout

- Test-only story: no feature flag, no runtime surface. Lands as one PR on `develop` after 05.7.4-T3 and 04.3.1-T1 are merged; becomes part of the standard CI suite (T48 dogfooding — the JUnit output feeds Evidgate itself once 01.10.1 lands).

- Rollback: revert the PR; no data or deployed state affected.
