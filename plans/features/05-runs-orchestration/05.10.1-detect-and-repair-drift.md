## 1. Goal and non-goals

**Goal.** Three periodic consistency jobs keep the orchestration state honest without ever re-running business logic: (1) a stuck-run detector that retries reconcile once then alerts when a run sits without a transition past its deadline, (2) an expired-lease sweeper that re-queues jobs (and device leases, 05.8.1) whose lease passed `expires_at` without a heartbeat, bumping the epoch so stale evidence is preserved, and (3) a hook interface other modules (06 orphan artifacts, 12 missing usage) can register against the same sweep cadence, plus an operator runbook note. Every repair is idempotent and audited.

**Non-goals.** The reconciler's own logic (05.3.2 owns it — this story only re-triggers it once on a stuck run); the environment-lock expiry path (05.7.3-T4 owns lock release on expiry — the same epoch-fencing pattern, different table); the actual 06 orphan-artifact sweep or 12 usage-roll-up sweep implementations (this story ships the hook contract they implement against, not their bodies); device-lease table creation (05.8.1 owns the table this sweeper reads).

## 2. User stories and acceptance criteria

- As an operator, I need a run that never transitioned past its deadline to be retried once automatically and then alerted, so a reconciler crash doesn't leave a customer's run silently `collecting` forever.
- As an operator, I need a dead agent's lease to release and re-queue automatically within one sweep interval, so a crashed runner never blocks a job indefinitely.
- As a module owner (06, 12), I need one registered sweep hook to attach my own idempotent repair to, instead of inventing a second schedule.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A run whose `collection_deadline_at` has passed with no state transition since creation is detected within one sweep interval; the detector triggers exactly one reconcile retry; if the run still has no transition after the retry, an alert-worthy audit row (`drift_detected`, reason `stuck_run`) is written and no further automatic retry happens for that run |
| AC2 | A `job_lease` (or `device_lease`, 05.8.1) whose `expires_at` has passed with no heartbeat is released within one sweep interval: the job is re-queued as a new lease with `epoch + 1`; events/evidence tied to the old epoch are preserved, never deleted or rewritten |
| AC3 | Both sweeps fire via a Cronos schedule row with a unique `(schedule_name, fire_at)` key (00 §5.3): a simulated double-fire (two workers racing the same tick) inserts exactly one `task` row per fire, verified by the unique-constraint conflict on the second insert (`ON CONFLICT DO NOTHING`) |
| AC4 | Repairs are idempotent: running the stuck-run repair twice on the same run produces no second reconcile-retry audit row and no duplicate outbox row; running the lease sweep twice on an already-released lease is a no-op |
| AC5 | The hook interface (`IConsistencySweepParticipant` or equivalent) is implemented by at least a stub registration test proving a second module's sweep body runs on the same schedule tick without a second Cronos entry; the operator runbook note documents how to register a new participant and how to read the audit trail |
| AC6 | No repair re-runs business logic beyond the single permitted reconcile retry (AC1) and the lease re-queue (AC2) — the runbook and the audit rows make every automatic action traceable to exactly one of the two repair kinds |

## 4. Data model and migrations

Migration `migrations/NNNN_orchestration_consistency_sweeps.sql` (DbUp; number assigned at implementation). No new business table beyond audit rows already emitted by the domains being repaired (`run`, `job`, `job_lease`, `device_lease` — all owned elsewhere); this story adds only the schedule registrations and a thin audit projection.

| Object | Definition |
|---|---|
| Schedule registrations | two rows via the existing `task`-schedule mechanism (01, 00 §5.3): `schedule_name = 'stuck_run_sweep'`, `schedule_name = 'expired_lease_sweep'`; interval configured per environment (⚠️ exact interval tuned after measurement — the area plan gives no fixed number; default proposed 60 s, confirmed in 10 load test) |
| `consistency_sweep_participant` (hook registry, read-only at runtime) | not a table — a compile-time registration (`IConsistencySweepParticipant` implementations discovered via DI) so no schema object is needed; the interface contract itself lives in `Evidgate.Modules.Orchestration.Contracts` |
| Audit rows | reuse the existing `audit` table (02-owned) with `action ∈ {drift_detected, lease_expired_requeued}`, `org_id`, `resource_type ∈ {run, job, device_lease}`, `resource_id`, `reason`; no new table, an additive insert path only |
| Indexes reused | `(org_id, expires_at) where released_at is null` on `job_lease`/`device_lease` (already defined by 05.7.2/05.8.1) serves the sweep's candidate-selection query — no new index needed here |

## 5. API shapes (commands, queries, endpoints)

No public `/v1` endpoint — these are internal scheduled tasks, not client-triggered commands.

| Command | Handler | Trigger | Notes |
|---|---|---|---|
| `DetectStuckRunsCommand` | `ICommand` handler, EF Core write (reads candidate runs via a bounded Dapper query first, then writes inside `ITenantScope` per org) | `task` row from `stuck_run_sweep` fire | idempotent by `(org_id, run_id, sweep_fire_at)` natural key; triggers `IMediator.Send(ReconcileRunCommand)` at most once per detection |
| `SweepExpiredLeasesCommand` | `ICommand` handler | `task` row from `expired_lease_sweep` fire | idempotent by `(org_id, lease_id, epoch)`; releases the lease, inserts the re-queued `job_lease`/`device_lease` row with `epoch + 1` |
| `IConsistencySweepParticipant.RunAsync(sweepFireAt, tenantScope)` | contract interface, no HTTP surface | invoked by the sweep dispatcher for every registered participant on the same fire | 06 and 12 implement it for orphan-artifact and missing-usage repairs respectively (their own commands, not owned here) |

Read side: `ListDriftEventsQuery` (Dapper, `SET TRANSACTION READ ONLY`) surfaces the audit rows above for the operator runbook — no new endpoint required if `GET /v1/orgs/{o}/audit` (00 §9.3, already `audit:read`) already lists these rows by `action`; this story adds no new permission.

## 6. States and transitions

No new state machine. The detector observes the existing `run` machine (00 §8.1: `created → queued → running → collecting → complete`) looking for "no transition since `collection_deadline_at` passed" and drives exactly one `ReconcileRunCommand` retry — the run's own transitions stay governed by 05.3.2. The sweeper observes the existing `job` machine (00 §8.2: `lost` — lease expired, epoch bumped, re-queued) and drives that existing transition; it does not invent a new job state.

## 7. Jobs and integrations

- `stuck_run_sweep` and `expired_lease_sweep` are Cronos schedules fired by any worker (no leader, 00 §5.3): the fire is one transaction inserting the `task` row with unique `(schedule_name, fire_at)`, `ON CONFLICT DO NOTHING` guarantees one task per fire (AC3).
- The stuck-run repair calls into 05.3.2's `ReconcileRunCommand` (already the reconciler's own entry point) — this story never re-implements reconcile logic, only re-triggers it once.
- The lease sweep reads both `job_lease` (05.7.2) and `device_lease` (05.8.1) via the same `(org_id, expires_at) where released_at is null` index shape, re-queuing each under its own epoch-bump rule.
- `IConsistencySweepParticipant` is implemented by 06 (orphan-artifact detection: an artifact `pending_upload`/`uploaded` past its lifecycle without reaching `ready`) and by 12 (missing-usage-roll-up detection: a metering gap for a closed billing period) — both are separate stories in their own area plans; this story ships only the interface + dispatcher + the runbook note.
- Terminal task rows (`done`, `dead_letter` after replay window) are swept per T11 (30-day retention) — unrelated to this story's own schedules, which fire continuously.

## 11. Rollout

- No feature flag: the two schedules are internal safety nets that can be disabled by not registering the Cronos schedule row if a rollback is needed, without touching the run/job/lease domain code they observe.
- T1/T3 (V1, M2) land first since they only need 05.3.2 (reconcile) and 12.3.1 (usage hook stub); T2 (V2, M4) lands with agent-mode leasing once 05.7.2 ships — matching the header's split Milestone/Version cells.
- Monitoring: `drift_detected` and `lease_expired_requeued` audit-row counts feed the 10 operations dashboard as new SLIs (00 §11 operational list already includes "lease-loss rate"); an unexpectedly high stuck-run rate is the alert trigger the runbook documents.
- Rollback: unregister the Cronos schedule rows (stop future fires); already-inserted `task` rows drain via the existing dead-letter/retention path (T11); no data loss since repairs only re-queue or retry, never delete.
