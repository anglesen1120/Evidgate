## 1. Goal and non-goals

**Goal.** Every unit of work — an HTTP request, a claimed `task` queue row, a scheduled job — runs inside exactly one database transaction whose first statement is the parameterised `set_config('evidgate.org_id', …)`/`set_config('evidgate.project_id', …)` (C3). No code path reaches the database without a tenant scope, and a missing scope fails closed (zero rows via 02.6.1 helpers, plus a hard error from the command interceptor).

**Non-goals.** The `ITenantScope` primitive itself (connection + `BEGIN` + `set_config`), the `DbCommandInterceptor` (01.4.2-T1) and the Mediator pipeline tenant-transaction behaviour at the C2 slot (01.4.2-T4) have shipped; no second scope implementation is written here; this story wires the tenant into every entry point and defines how the tenant is resolved per credential type. RLS policies are 02.6.1; the isolation suite is 02.9.1.

## 2. User stories and acceptance criteria

- As a developer writing a handler, I never think about `org_id`: the pipeline opened the scope and the interceptor throws if I somehow run a command without it.
- As the Tech Lead, I can list every entry point and point at the line that opens its scope.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Every Mediator `ICommand`/`IQuery` executes inside a scope opened (by the 01.4.2-T4 pipeline behaviour, fed by this story's entry-point resolution) at the C2 position (after validation, before authorization); the transaction is committed only on success and a denied request rolls back |
| AC2 | Session-cookie requests derive `(org_id, project_id)` from membership on the authenticated user + route values; bearer tokens derive them from token claims; `POST /v1/ci/token` and ingest-token auth resolve through `evidgate_resolve` first (T1) and then open the scope |
| AC3 | A `task`-queue handler receives `(org_id, project_id)` from the outbox/task row it claims and opens the same scope before its handler runs; a row missing `org_id` is dead-lettered, never run unscoped |
| AC4 | Any `DbCommand` executed on a connection where `evidgate.org_id` is unset throws `TenantScopeMissingException` before execution (interceptor from 01.4.2-T1, wired here); no request can serve data without the scope |
| AC5 | A request whose principal resolves to no active membership in the URL's org gets 403 `forbidden` (or 404 for cross-tenant ids per 00 §9.2); the scope is never opened with a tenant the principal is not a member of |
| AC6 | The service-principal claim path of `PermissionEvaluator` is bound to the service-kind roles (`ci_producer`, `agent`) and denies staff-only codes (`billing:*`, `support:grant`) (W7-SEC-06) |

## 4. Data model and migrations

None. The tenant GUCs (`evidgate.org_id`, `evidgate.project_id`) are transaction-local settings, not schema.

## 5. API shapes (commands, queries, endpoints)

No new endpoints. The story defines the resolution matrix applied to every existing route group:

| Caller credential | Tenant resolution | Scope |
|---|---|---|
| `__Host-` session cookie | session → user → membership on `{o}`/`{p}` route values; per-request membership re-read (no cache) | `BeginAsync(org, project?)` |
| `ci_producer` bearer | org/project from token claims; `{p}` must equal claim → else 403 `project_scope_mismatch` | `BeginAsync(org, project)` |
| Ingest token / GitHub OIDC JWT (pre-tenant) | `evidgate_resolve` resolver → `(org_id, project_id, binding_id, status)` (T1) | `BeginAsync(org, project)` after resolve |
| `task` queue row | `org_id`/`project_id` columns on the claimed row | `BeginAsync(org, project)` in the worker dispatcher |
| `/internal/*`, `/internal/operator/*` | no tenant scope (health/metrics) or grant-scoped operator context (02.8.1) | none / operator role |

## 6. States and transitions

None. (A scope is open → work → commit/rollback; it has no persisted state.)

## 7. Jobs and integrations

- The worker's `task` dispatcher (00 §5.3, `FOR UPDATE SKIP LOCKED` claim) is an entry point: after claiming a row it calls `BeginAsync(row.OrgId, row.ProjectId)` and runs the handler inside that scope; `org_id` missing → `dead_letter` with reason `missing_tenant`.
- Mediator behaviour registration happens in each module's DI (template from 01.4.2); the tenant behaviour is `internal` to BuildingBlocks and modules cannot bypass it (architecture test, T47).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.5 C3 / 00 §5.4.2 | one connection from the app-role `NpgsqlDataSource`, `BEGIN`, parameterised `set_config(…, true)`; EF Core shares it via `Database.UseTransaction`; Dapper uses the same `IDbTransaction` | AC1 + `Scope_EfCore_And_Dapper_ShareOneTransaction` |
| 00 §5.4.7 / T2 | unset GUC ⇒ helpers return NULL ⇒ zero rows; the interceptor additionally throws so bugs are loud, not silent-empty in writes | AC4 |
| T1 | pre-tenant entry points call `evidgate_resolve` only; the scope opens strictly after resolution | AC2 + resolver-call test |
| 00 §5.7 S2 | authorization runs after the scope opens (C2 order) so permission reads are tenant rows under RLS | AC5 |
| 00 §5.7 P3, P5 | scope adds exactly one `set_config` batch statement to an existing transaction — no extra round trip; no network call inside | command-counter assertion in AC1 test |
| Privacy/retention | `org_id`/`project_id` may appear in traces/logs (they are ids, not personal data); secrets never enter the scope | log-allowlist test (11) |
