## 1. Goal and non-goals

**Goal.** `contracts/permissions.json` is the single source of every `resource:action` string; `permission`, `role` and `role_permission` rows seed the 00 §2 built-in roles exactly; the Mediator authorization behaviour (C2) evaluates permission × project per request, denies by default, and treats service identities (`ci_producer`, `agent`) like members through the same path. Any permission referenced in code but missing from the catalogue fails the test suite.

**Non-goals.** The org-specific custom-role editor (open question Q3 — assumed deferred to V2; the schema already carries `role.org_id`); support-grant scope semantics (02.8.1); healing permission *semantics* (08 only consumes the strings); UI (09.7.1).

## 2. User stories and acceptance criteria

- As the Tech Lead, every role's permission set is a data row seeded from one JSON file shared by server, web and CLI — drift fails CI.
- As a `viewer`, any write endpoint returns 403 even if I craft a valid request.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Seeded built-in roles equal the 00 §2 matrix exactly (incl. `billing:read` on `billing_operator`, `project:read` on all member roles, `project:write` + `project:create` on `tenant_admin` — T21); a set-difference test fails on any divergence |
| AC2 | A command/query without a permission requirement fails `Architecture.Tests` (`EveryRequestHasPermission`); one with a permission missing from `contracts/permissions.json` fails `CatalogueTests.CodeRefsSubsetOfCatalogue` — and vice versa (every catalogue row is either referenced or explicitly tagged `reserved`) |
| AC3 | A member whose roles lack the required permission → 403 `forbidden`; unknown permission on a request → deny; a permission check for project B while holding project-A-only roles → 403 `project_scope_mismatch` or `forbidden` (per-project evaluation, FR-02-2) |
| AC4 | `ci_producer` token permissions `{run:create, event:write, artifact:write}` (FR-02-7) are evaluated through the same behaviour: a `ci_producer` calling `membership:write` → 403 |
| AC5 | No catalogue permission exposes secret values: every permission marked `sensitive` in `permissions.json` is asserted unreachable for roles that must not hold it, and `tenant_admin` responses never contain token/credential fields (area-plan test rule) |
| AC6 | `GET /v1/permissions` returns the catalogue to any member (`role:read`); `POST/PATCH /v1/roles` on a built-in role → 409 `builtin_role_immutable` |
| AC7 | `permission.tenant_assignable` (T79): a custom role containing a non-assignable code (`support:*`, `billing:*`, `platform:*`, agent-only) → 422 `permission_not_assignable`; the evaluator never returns a non-assignable code as granted for a member principal, even if a `role_permission` row were corrupted to contain it |

No existing row, permission string or schema changed; the write rows of §5 stay with T2.
- 00 §2: built-in role → permission seed data materialises the table; no role added or removed (catalogue rows for other plans' strings — e.g. `artifact:read_sensitive`, `healing:*` — are seeded as `permission` rows even before their consumers ship, so later stories only *grant* them). Seed note (T98): the seed needs no change for org creation — `tenant_admin` and `release_approver` are ordinary built-in roles this seed already carries; granting **both** to the org creator is 02.1.1's `POST /v1/orgs` behaviour, not a new role or permission string.
- C2: this story implements the authorization behaviour in the pipeline order telemetry → validation → tenant tx → **authorization** → idempotency → handler → outbox → commit.
- Resolved (RECOMMENDATIONS 02-Q3): built-in roles only in V1 — the write endpoints ship but the `custom_roles_enabled` flag stays off in V1, gating non-built-in creation.

**Recorded (T2, the shipped shape).** No 00 §2 / §9.3 row changes: the two write routes of §5 below are on the 02-owned endpoint list of `plans/02-identity-tenancy.md` §4.2, and every error code they use is a status 00 §9.2 already names.

- **The C2 seam keeps the 01.4.2-T4 shape, with a code-carrying verdict.** `IPermissionChecker`/`DenyAllPermissionChecker` become `IPermissionEvaluator`/`DenyAllPermissionEvaluator` returning a `PermissionDecision` (granted, or denied with the 00 §9.2 code the envelope must carry). A `bool` could not distinguish `forbidden` from `project_scope_mismatch` and `no_membership`, and the task requires the code per case. `PermissionAttribute` keeps its name — the plan's "RequirePermission" wording is descriptive, not a rename — and the handler carries `PermissionAttribute`; `[Permission]` metadata, the post-tenant-transaction position in `PipelineBehaviourOrder.C2` and the fail-closed default are unchanged.
- **Who resolves the caller.** The entry points resolve the credential and publish the caller (`IRequestPrincipal` + `IRequestPrincipalSetter`/accessor, next to `IRequestTenantContext`) — that is 02.6.2-T1.1's resolution step, which has since shipped (02.6.2-T1, direct commit on `develop` 1e31175); the pipeline reads the published principal only and denies when none was published (fail-closed). `RequestPrincipal.Member/Service/Operator` are the only constructors, so no stage has to guess which fields a kind carries. Tests stand in for the resolver.
- **The member path in V1 is org-level, not per-project.** FR-02-2 asks for per-project evaluation, but 02.1.2 §4's `membership`/`membership_role` carry no project scope, so a member's roles apply to every project of their org and the project dimension binds the service-identity path (whose token carries the single project claim of FR-02-7). A project-scoped member role would be a schema change; it is deferred, not silently assumed.
- **The operator path is a fail-closed stub.** `PrincipalKind.Operator` is denied outright (`PermissionEvaluator.OperatorWithoutSupportGrant`) until 02.8.1 ships the tenant-approved, expiring `support_grant` scope check; the interface `ISupportGrant`-style contract is 02.8.1's to define, and the denial is named in the code rather than an implicit fall-through.
- **Grants are additive in V1.** Migration 0010 deliberately revokes `DELETE` on `role_permission` from the app role ("a role is archived, never hard-deleted"), and 02 §6 keeps custom-role `active|archived` past V1, so `PATCH /v1/roles/{r}` cannot remove a grant in V1: its body field is `add_permissions`, not a replacement set, and a role's grants only grow. The V2 editor (with the archived state) is what makes the set replaceable; the asymmetry is stated in the contract DTO rather than hidden behind a `permissions` field that would silently ignore a removal.
- **Write model.** `role`/`role_permission` get EF Core entities, configurations and `IdentityDbContext` (00 §5.5 C4); the read side stays Dapper (C5). A duplicate code is the database's `unique (org_id, code)` verdict (409 `role_code_taken`), and the concurrency token (`version`, trigger-incremented) turns a racing PATCH into 412 `precondition_failed` — that branch is defensive (it needs a true race between the handler's load and its save) and has no deterministic test.
- **Shape validation and idempotency follow the module's command convention.** The two commands' shape rules (code and permission shapes, name length, "at least one field to change") live in `CreateRoleCommandValidator`/`UpdateRoleCommandValidator` at the C2 validation stage — the stage whose point is that a malformed body never opens a transaction — while the catalogue questions (does the code exist, is it `tenant_assignable`) stay in the handlers, where the catalogue is read. Both commands implement `IIdempotentCommand` with the client's `Idempotency-Key` (00 §9.1, TL T11; the routes' spec rows declare the header required), so a retried create replays its stored 201 instead of colliding with its own `unique (org_id, code)`, and a missing key is 400 `request_invalid` from that stage.
- **Story-level error codes** (no 00 §2/§9.3 change; 00 §9.2 already carries the statuses): 403 `project_scope_mismatch` / `no_membership` (00 §9.1, 02.1.2 AC2, 02.3.1 AC3), 409 `builtin_role_immutable` (AC6) and `role_code_taken` (`unique (org_id, code)`), 412 `precondition_failed`, 422 `unknown_permission` and `permission_not_assignable` (T79).
- **The flag is configuration, not code.** `EVIDGATE__IDENTITY__CUSTOMROLESENABLED` (`IdentityOptions.CustomRolesEnabled`, default false) is declared in `infra/config-matrix.json` and `infra/dev/environment.json` and bound by `AddIdentityModule` in both entry points, so V1 is a configuration state and the routes answer 403 `forbidden` rather than disappearing.
- **Served-document shape.** `POST /v1/roles` declares a bodiless 200 next to its `201 RoleView`, because the OpenAPI generator otherwise derives a phantom 200 from the delegate's `Result<RoleView>` return type and publishes the internal wrapper (`ResultOfRoleView`, plus `Result`/`Error`/`ErrorDetail`) as a served schema, which `tests/Contract.Tests`' served-document diff reports as an undocumented DTO. The declaration keeps the served document to wire shapes; the 200 itself is unreachable (the create always answers 201 or an envelope status), and it is the same one-line shape the membership routes use for their 201/204 answers.

### 3b. Recorded when the wave-7 security review shipped (2026-09-27)

Four changes to the shipped slice (0010 plus the T2 handlers and the evaluator), all inside the story's own surface: no 00 §2/§9.3 row, DTO or response code changed, and no new error code was invented (403 `forbidden` and 409 `unknown_role` are already on every route involved).

- **`role.kind` is a catalogue column (W7-SEC-03).** `kind text not null check (kind in ('member','service','staff'))`, seeded from `contracts/permissions.json` (the file already carried `kind` per role), and mapped by the write model. `member` is the only kind a membership may hold: `GrantRole`/`InviteMember` resolve member-kind roles only (any other visible id is the existing 409 `unknown_role`), custom roles are written with `kind = 'member'`, and the evaluator's member join requires `r.kind = 'member'`. Without it a `tenant_admin` could attach `platform_operator` (`support:read`) or `ci_producer` (`run:create`, `artifact:write`) to a human membership: the T79 filter removes non-assignable *codes*, and both of those codes are assignable, so the kind is the only thing that keeps a staff or service identity out of a member's role set.
- **A grant row is tied to its role's org (W7-SEC-05).** The app-role INSERT policy on `role_permission` — and, so the hole cannot move there instead, the UPDATE policy's WITH CHECK — now carries the tenant predicate followed by `and exists (select 1 from public.role r where r.id = role_id and r.org_id = evidgate.current_org_id())`; the tenant predicate stays the first top-level AND operand, which is what the 02.6.1-T2 isolation self-check recognises. The evaluator's member join adds `rp.org_id is not distinct from r.org_id` as the read-time half. An org-scoped row can therefore no longer be attached to a built-in role (`org_id is null`) and widen it for every member who holds it; the `role(id)` FK stays a single-column platform reference (the catalogue's deliberate exception, §4), so this is the tie that FK cannot express.
- **[DECISION] Self-escalation is blocked (W7-SEC-02, rationale 00 §2).** 00 §2 bounds `tenant_admin` by what it does not hold ("secret values are never readable: no `artifact:read_sensitive` and no `billing:*`"), but the role strings are data and `tenant_admin` holds `role:write` — so it could grant itself `release_approver` or write a custom role containing a sensitive code. The rule: **a caller may hand out only permissions it already holds.** `CreateRole` applies it to every submitted code and `UpdateRole` to every added code (a custom role is not scoped to anyone until it is granted, so the whole set must be checked); 02.1.2 §3b records the same rule for the two membership routes, where it fires only when the target is the caller's own membership. The refusal is 403 `forbidden` — the code both write routes already document — and the caller's set is resolved by this story's own evaluator (`ICallerPermissionSet`, one statement over the same join as the per-permission verdict), so the set a command checks and the set the next request is evaluated with cannot diverge. A second resolution path, or one evaluator call per candidate code, was rejected: the first is the bug the rule exists to prevent, the second is an N+1 with a 200-code input limit.
  - [OPEN] (owner): does the stricter *grantor-subset* rule apply to grants to **other** members — i.e. may a `tenant_admin` appoint a `release_approver` at all? Not applying it keeps delegation working (T98's creator holds both roles and is expected to appoint approvers); applying it means no role can widen a permission set except from above. Recorded here and in 02.1.2 §3b because it decides who can staff an approval pair.
- **Order of refusals (unchanged codes, sharper reasons).** `CreateRole`: flag 403 → catalogue 422 (`unknown_permission`, `permission_not_assignable`) → subset rule 403 → built-in code 409 → `unique (org_id, code)` 409. `UpdateRole`: 404 → built-in 409 → flag 403 → catalogue 422 → subset 403 → write. `GrantRole`: 404 → 409 `unknown_role` (invisible *or* non-member kind) → 403 subset (own membership only) → write.
- **Shipped tests.** `BuiltinRoleTests.Create_With_A_Permission_The_Caller_Does_Not_Hold_Is_403` and `Patch_With_A_Permission_The_Caller_Does_Not_Hold_Is_403` (the second also proves the rule is a subset check: a code the admin holds is added afterwards), `EvaluatorTests.Caller_Permission_Set_Matches_The_Per_Permission_Verdict` (the seam's set equals the verdicts, one statement, and the empty-set branches), `Org_Scoped_Grant_On_A_Builtin_Role_Grants_Nothing` (the read-time tie), `CatalogueRlsTests.AppRole_Cannot_Attach_An_Org_Grant_To_A_Builtin_Role` / `AppRole_Cannot_Move_A_Grant_Onto_A_Builtin_Role` (the write-time policies), and `SeedMatrixTests.Role_Kinds_Match_The_Catalogue_File` (the seeded kind column).

## 4. Data model and migrations
`migrations/0010_identity_permission_catalogue.sql` (owner role; all three are platform catalogue rows per §4.5 / T3):

- `permission`: `code text pk` (`^[a-z_]+:[a-z_]+$` check), `resource text`, `action text`, `description`, `sensitive boolean`, `reserved boolean` (catalogue-only strings awaiting a consumer), `tenant_assignable boolean not null default true` (T79 — `false` for `support:*`, `billing:*`, `platform:*`, agent-only; member principals can never hold them). No `org_id`; RLS `ENABLE` + policy `USING (true)` for read, `WITH CHECK (false)` for the app role — writable only by `evidgate_owner`.
- `role`: `id uuid`, `org_id uuid null` (null = built-in), `code`, `name`, `is_builtin`, `kind text not null` (`member|service|staff`, §3b — who may hold the role; only `member` is grantable to a membership), `version`; `unique (org_id, id)` (T3 — the lint exception applies to the null-org rows), `unique (code) where org_id is null`, `unique (org_id, code)` for future custom roles. RLS policy `USING (org_id IS NULL OR org_id = evidgate.current_org_id())`.
- `role_permission`: `id uuid`, `org_id uuid null`, `role_id`, `permission_code` → `permission(code)`; `unique (org_id, id)`, `unique (role_id, permission_code)`; FK to `role(id)` (platform row — single-column FK is correct here since built-in roles have `org_id IS NULL`). The app role's write policies add the org tie the FK cannot express — the row's org must be the referenced role's org (§3b, W7-SEC-05), so a grant can never be attached to a built-in role.
- Seed `INSERT … FROM jsonb` reading `contracts/permissions.json` embedded in the migration (migration must be self-contained; a test diffs the seed against the file). Seeded ids are `uuidv7()`; the block is idempotent (`on conflict` / `where not exists`) so re-applying the file re-syncs the catalogue instead of failing.
- The three tables pass the 02.1.1-T1 schema-convention scan without a blanket exemption: `role` and `role_permission` carry `unique (org_id, id)`, ENABLE + FORCE RLS and the shared `set_updated_at_and_version` trigger, and `role_permission`'s only excuse is its single-column FK to `role(id)` (`CompositeForeignKey`), because a built-in role carries `org_id IS NULL` and a composite tenant FK could never match one.

## 5. API shapes (commands, queries, endpoints)

| Command / Query | Endpoint | Permission | Codes |
|---|---|---|---|
| `ListPermissionsQuery` (Dapper) | `GET /v1/permissions` | `role:read` (any member) | 200 catalogue page |
| `ListRolesQuery` / `GetRoleQuery` | `GET /v1/roles`, `GET /v1/roles/{r}` | `role:read` | 200; 404 |
| `CreateRoleCommand` / `UpdateRoleCommand` (custom roles only, flagged) | `POST /v1/roles`, `PATCH /v1/roles/{r}` | `role:write` (`tenant_admin`) | 201/200; 403 `forbidden` (flag off, or a code the caller does not hold — self-escalation, §3b); 409 `builtin_role_immutable`, `role_code_taken`; 422 `unknown_permission`, `permission_not_assignable` (T79) |
| `IPermissionEvaluator.HasPermission(principal, orgId, projectId?, permission)` | — (module contract consumed by the pipeline) | — | bool |

**Shipped read shape (T1).** `GET /v1/permissions` returns the catalogue in `code` order — its primary key — because a platform catalogue has no `created_at`; that is a deliberate deviation from 00 §9.1's `(created_at, id)` ordering, stated in the 00 §9.3 row and in `contracts/openapi.yaml`. `GET /v1/roles` keeps `(created_at, id)` with an opaque keyset cursor. Both pages are `?cursor=&limit=` (default 50, max 200); an out-of-range `limit` or a cursor this service did not issue is 422 `request_invalid`. The routes live in the module's `Endpoints/` namespace and the entry point applies the C8 `ResultEndpointFilter` when it composes them (a module may not reference the host), so `ApiHost` is the one place that maps them.

**Authorization behaviour** (new, in `BuildingBlocks` + `Identity` implementation): reads the `RequirePermission` attribute/metadata on each `ICommand`/`IQuery`; resolves the caller — member → `membership_role` → `role_permission` inside the tenant tx (RLS-safe), filtered to `tenant_assignable` codes for member principals (T79); service principal → permission set carried in the token claims (bounded by the catalogue: a claim not in `permission` is denied); operator → only via a valid `support_grant` scope (02.8.1). Deny → `Result` error → 403 envelope (C8); `project` in the requirement is checked against the token's project scope → 403 `project_scope_mismatch` (00 §9.1).
