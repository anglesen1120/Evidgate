## 1. Goal and non-goals

**Goal.** Every permission-checked mutation appends exactly one `audit_log` row in the same database transaction as the business change, with actor, action, object, before/after content hashes, `request_id` and `trace_id`. Rows are append-only for the app role, chained per org (`prev_hash`/`entry_hash`/`seq`), serialised under concurrency, and continuously verifiable by a scheduled job.

**Non-goals.** Webhook/web delivery of audit events (none planned); the tenant-facing audit UI (09.7.1); PDPL reporting queries (11.5.1 consumes this API); retention pruning of audit rows (10 defines the policy; `audit_log` keeps the minimum per §5 failure table).

## 2. User stories and acceptance criteria

- As a tenant admin, I can page through every change in my org and export it, so I can answer "who did what, when" myself.
- As a security reviewer, I can detect any tampering: a modified, deleted or reordered row breaks the per-org hash chain, and the verification task reports it.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Every command that passes authorization writes one audit row in the same transaction: rollback of the business change removes the audit row too (no orphan audit), and commit writes both atomically |
| AC2 | The app role can `INSERT`/`SELECT` `audit_log` but `UPDATE`/`DELETE` is denied (`REVOKE`); an attempted update raises a permission error |
| AC3 | Concurrent writers in one org produce a single unbroken `seq` chain: `pg_advisory_xact_lock(hashtext('audit:' ‖ org_id))` is taken as the last statement before commit (T8), `unique (org_id, seq)` holds, and `entry_hash` covers `prev_hash` + row content |
| AC4 | `GET /v1/orgs/{o}/audit` (`audit:read`) returns cursor-paginated rows `(created_at, id)` desc per 00 §9.1; another org's rows are invisible (RLS) and a foreign `{o}` returns 404 |
| AC5 | `GET /v1/orgs/{o}/audit/export` streams JSONL (and `format=csv`) of the same filtered set; export itself writes an audit row (`action = audit.export`) |
| AC6 | A scheduled chain-verification task (Cronos, unique `(schedule_name, fire_at)`, 00 §5.3) walks `seq` per org and reports any gap or hash mismatch as a `security_event` + `dead_letter`-visible failure; a deliberately corrupted row is caught on the next run |

## 3. Contracts touched

- 00 §9.3 — implements `GET /v1/orgs/{o}/audit` + `/export` with `audit:read`; shape added to `contracts/openapi.yaml`.
- T8 — implements the serialised per-org chain exactly; no deviation.
- 02 §4.4 — "every transition writes an audit row" is realised through this writer.
- Recorded 2026-10-03 (as delivered, Stage A):
  - **Writer shape.** `IAuditTrail` (`Evidgate.BuildingBlocks.Persistence.Audit`) is an ambient per-unit buffer: the tenant stage opens a unit, the authorization stage queues one entry after a successful `[AuditedAction]` handler (actor from `AuditActorResolver`), handlers add object detail with `Describe`, and the tenant stage appends the buffer to the org's chain just before commit (`pg_advisory_xact_lock(hashtext('audit:' || org))`, then the chain tip, then the inserts). An idempotent replay calls `Suppress()`; a no-op success (e.g. removing an already-removed member) does too.
  - **Hash rule.** `entry_hash = sha256(prev_hash || RFC 8785 canonical(id, org_id, seq, actor, action, object, hashes, request_id, trace_id, metadata, created_at))`, one implementation (`AuditHashing`) for writer and verifier; `created_at` is set in the application at microsecond precision so a stored row re-hashes identically.
  - **Owner privileges.** The owner role has SELECT and INSERT policies only, no UPDATE/DELETE policy, so history cannot be rewritten even by migrations (tamper tests use the superuser).
  - **Export is a command.** `GET …/audit/export` runs as `ExportAuditCommand` with `[AuditedAction("audit.export")]` so the audit row and the read are one transaction; it materialises at most 100 000 rows (422 `export_range_too_large` beyond that or beyond 92 days).
  - **`security_event` (AC6).** The table exists since 11.5.1-T5.1 (`migrations/0053_security_security_event.sql`), but `security_event.org_id` is NOT NULL and the closed V1 type set carries no type for a broken chain (11.1.1-T4.1; carried row "G8 verifier fault has no `security_event` type (11.5.1-T5, S137)"), so a broken chain is still carried by an error log, the `audit_chain_verification_failures_total` counter and a dead-lettered `audit.verify_chain` task. Where a platform-scope (no-tenant) event is stored is the open owner decision D-S137-OWNER (nullable `org_id` or a separate platform table), never a settled shape.
  - **Schedule.** cron `7 */6 * * *` (minute 7, off the hour).
  - **Deferred.** The `evidgate_resolve` call-audit stubs of 02.6.1 AC6 (`member_orgs` etc.) are replaced by audited versions in a later migration; the 02.1.1 AC3 audit row (other-org project read) is not written because denied reads are not audited here.

## 4. Data model and migrations

| Table | Columns / constraints |
|---|---|
| `audit_log` | `id uuid pk`, `org_id uuid not null`, `seq bigint not null`, `actor_type text not null` (`user\|ci_producer\|agent\|platform_operator\|system`), `actor_id text not null`, `action text not null`, `object_type text`, `object_id text`, `before_hash bytea`, `after_hash bytea`, `request_id uuid`, `trace_id text`, `metadata jsonb`, `prev_hash bytea not null`, `entry_hash bytea not null`, `created_at timestamptz not null default now()` · `unique (org_id, id)` (T3), `unique (org_id, seq)` · `REVOKE UPDATE, DELETE, TRUNCATE FROM evidgate_app` · RLS `org_id = evidgate.current_org_id()` · index `(org_id, created_at, id)` serving the list cursor (P4); `(org_id, seq)` covered by the unique key for chain walks |

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint / trigger | Notes |
|---|---|---|---|
| Writer | `IAuditWriter.AppendAsync(entry)` | called inside the business transaction | resolves `seq = max(seq)+1` and `prev_hash` for the org under the advisory lock; computes `entry_hash`; used by the authorization behaviour (for the check itself) and by command handlers via a Mediator post-step before outbox flush |
| Query | `GetAuditPage : IQuery<AuditPage>` | `GET /v1/orgs/{o}/audit?cursor=&limit=&actor_type=&action=&object_type=&from=&to=` | `audit:read`; Dapper, read-only tx; keyset on `(created_at, id)` desc; index `(org_id, created_at, id)` |
| Query | `ExportAudit : IQuery<Stream>` | `GET /v1/orgs/{o}/audit/export?format=jsonl\|csv` + same filters | `audit:read`; streamed response; capped date range (default 30 d, max 92 d) → 422 `export_range_too_large`; writes its own audit row via an internal `RecordAuditExport` command after streaming starts |
| Task | `VerifyAuditChain` | Cronos `0 */6 * * *` ⚠️ cadence | per org: walk `seq`, recompute hashes, assert contiguity; mismatch → security event + alert |

`actor_type` values: `user`, `ci_producer`, `agent` (V2), `platform_operator`, `system` (tasks/resolvers). `action` is `permission:performed`-style strings (`membership.invite`, `ingest_token.rotate`, `audit.export`, …) matching `permissions.json` where applicable.

## 6. States and transitions

`audit_log` is append-only: no state machine, no update path. Rows are immutable by grant (app role) and by chain verification (tamper detection). Related transitions that produce audit rows (`ingest_token`, `session`, `support_grant`, `ci_binding`) are owned by their stories — this story only supplies the writer.

## 7. Jobs and integrations

- **Chain-verification task** — Cronos schedule `0 */6 * * *` fired idempotently via unique `(schedule_name, fire_at)` on the task row (00 §5.3); handler `VerifyAuditChain` iterates orgs, walks `seq`, recomputes `entry_hash`; failure → `security_event` row (11.5.1 surface) + alert.
- **Consumers**: 02.8.1 (grant + operator-read audit), 03.6.1 (catalog actions), 11.1.1/11.5.1 (security reporting), 09.7.1 (audit screen) — all read through this API/writer, never their own tables.
- The `evidgate_resolve` call-audit stubs (02.6.1-T3) are written by owner-owned functions, outside this writer — they are deliberately separate because they precede tenant scope.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T8 chain integrity | per-org `seq` + `prev_hash`/`entry_hash`; `pg_advisory_xact_lock(hashtext('audit:' ‖ org_id))` last statement before commit; verification walks `seq` | AC3, AC6 |
| 02 D10 / C7 | audit row in the same transaction — actor and `request_id` can't be lost to a crash or log pipeline | AC1 |
| Append-only | `REVOKE UPDATE, DELETE` from `evidgate_app`; no API mutates audit rows | AC2 |
| 00 §5.7 P4 | list query served by `(org_id, created_at, id)`; chain walk served by `(org_id, seq)` unique | AC4 + query plan in test |
| 00 §5.7 P3 | `GetAuditPage` is one SQL statement (asserted by command counter); export streams, no N+1 | AC4/AC5 tests |
| 00 §5.7 P5 | advisory lock is held only for the final insert — the lock statement is last before commit, so hold time ≈ one insert | lock-ordering test + code review |
| 00 §5.7 S2 | `audit:read` enforced in the pipeline; S3 — `metadata` carries no secrets (allowlist enforced at write; token bodies never logged) | AC4 + writer unit test |
| Privacy/retention | `actor_id`, `ip` in metadata are personal data; tenant deletion keeps the minimum `(actor, action, object hash)` per the 02 §5 retention rule — the deletion task strips other fields, never the row | deletion-path test in 10/11 |

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** reading and exporting the trail need `audit:read` (enforced by the C2 stage, S2); a foreign `{o}` is 404 and RLS hides other orgs' rows. Writing is not an API: rows are appended only by the pipeline after an authorized, successful `[AuditedAction]` command, and the database refuses UPDATE, DELETE and a non-extending INSERT from the app role.
- **Retention/deletion:** audit rows are kept for the life of the org and are never pruned by this story; tenant deletion keeps the minimum `(actor, action, object hash)` and strips other fields per the 02 §5 rule, owned by 10/11. `metadata` is allowlisted and secret-free by construction.
- **Telemetry:** the verifier logs an error per broken chain (event 2400) and counts `audit_chain_verification_failures_total`; lock timeouts surface as 503 `unavailable`; every row carries the `request_id` and `trace_id` of the request that wrote it. No row, log or metric carries a secret or request body.
- **Failure path:** the audit row and the business change are one transaction, so a failed flush rolls both back and a failed command writes nothing; a busy chain is a retryable 503 after a 2 s lock wait; a broken chain dead-letters `audit.verify_chain` where operators see it; export beyond 92 days or 100 000 rows is 422 `export_range_too_large`.

## 11. Rollout

- No flag. T1 → T2 → T3 in one PR series; the read API is additive. Consumers (02.8.1, 11) can build against `IAuditWriter`/`audit:read` immediately after T2.
- Monitoring: chain-verification failures are pages (possible tampering or a bug); export volume is metered.
- Rollback: revert the PR before other modules adopt the writer; `audit_log` data is append-only — a rolled-back writer never needs a data repair.

## 8a. Review (2026-10-03, security + performance, from the spec package)

| # | Finding | Severity | Resolution |
|---|---|---|---|
| 1 | The app role could INSERT rows with any `seq`/`prev_hash` | Medium | Fixed: `audit_log_chain_guard` trigger forces the next seq, the tip's hash and non-decreasing `created_at` (`AppRole_CanOnlyExtendTheChainHonestly`). | 2 | Tail deletion / truncate by owner or superuser is undetectable | Medium | Recorded as OI-02-32 (anchor outside the table, HMAC key). The owner keeps TRUNCATE because the shared test harness resets as the owner; it has no UPDATE/DELETE policy |
| 3 | The advisory lock had no timeout; a burst could park every pooled connection | Medium | Fixed: `lock_timeout` 2 s before the lock; a timeout is `AuditBusyException` → 503 `unavailable` with `Retry-After` |
| 4 | Verifier is O(total rows) every 6 h; no checkpoint | Medium | Accepted for V1 volumes; incremental verification from an anchor is part of OI-02-32 |
| 5 | Export buffered up to MaxRows + one page | Medium | Fixed: the row cap is checked before a page is added (at most 100 000 DTOs). Streaming from a reader is later work |
| 6 | `audit_org_ids` scanned the whole audit index per page | Low | Fixed: iterates `organization` with an `exists` probe |
| 7 | `created_at` could run backwards against `seq` across nodes | Low | Fixed: never earlier than the chain tip |
| 8 | Read-only requests opened an audit unit | Low | Fixed: queries skip it |
