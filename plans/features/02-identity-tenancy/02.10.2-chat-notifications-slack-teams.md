## 1. Goal and non-goals

**Goal.** An org admin adds a Slack or Microsoft Teams incoming-webhook channel, chooses which events go to it (blocked release, quota 80 %, candidate expiry), and receives one short message per event through the existing outbox-driven notification path. The webhook URL is itself a credential, so it is stored as a secret reference (11.3.1-T1), never as plain text in the database, logs or API responses, and is checked https-only and against private, loopback and link-local addresses before every send.

**Non-goals.** Two-way chat (slash commands, approvals from chat), a Slack/Teams app or OAuth install, per-user DMs, other event types (extend by adding templates later), email channel behaviour (02.10.1), generic outbound webhooks to customer systems (07.6.3), delivery to channels other than Slack/Teams incoming webhooks.

## 2. User stories and acceptance criteria

- As an org admin, I paste a Slack incoming-webhook URL, pick "release blocked" and "quota 80 %", send a test message, and see messages arrive in the channel.
- As a security reviewer, I know the URL cannot be read back, cannot point at an internal address and that messages carry no test content.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/notification-channels` (`notification_channel:write`, `Idempotency-Key`) creates a channel `{kind: slack\|teams, name, url, events[]}`; the URL is stored only as a secret reference, the response and every later read return only `url_hint` (host + last 4 characters) and never the URL |
| AC2 | URL validation: scheme must be `https`; host must match the kind's allow-list pattern (`hooks.slack.com` for Slack; Teams webhook hosts per config ⚠️ to be verified, see §7); userinfo, non-443 ports and IP literals are refused 422 `invalid_webhook_url`; the URL is capped at 2048 characters |
| AC3 | SSRF guard: before each send the host is resolved and every address must be public; private (RFC 1918), loopback, link-local, unique-local, multicast and cloud-metadata addresses are refused; redirects are not followed; the connection is made to the resolved, checked address (no re-resolution gap) |
| AC4 | Per-event opt-in: an event reaches a channel only if the channel lists it; no default subscription; an org with no channel generates no chat tasks |
| AC5 | A message is sent at most once per `(org_id, channel_id, event key)` (idempotency key on the `notification` row from 02.10.1-T2); a retry after a 5xx or timeout does not duplicate once delivery was acknowledged |
| AC6 | Failure handling: 429 honours `Retry-After`, 5xx/timeouts use the 02.10.1-T2 retry then dead-letter; 404/410 from the provider marks the channel `broken`, stops sending and notifies org admins by email (02.10.1) |
| AC7 | Messages (T2) for blocked release, quota 80 % and candidate expiry carry only: org and project display name, release or candidate identifier, decision label or percentage, and a deep link into the Evidgate UI; no test names, error text, artifact content, secrets, member emails; text is vi or en by org locale |
| AC8 | `POST /v1/notification-channels/{c}/test` sends one fixed test message and reports `ok` or the typed failure without echoing the URL; limited to 5 per channel per hour |
| AC9 | Rotating the URL (`PUT` with a new URL) replaces the secret reference; the old reference is deleted; disabling a channel stops delivery within one dispatch cycle; every create/update/disable/delete writes an audit row without the URL |

## 6. States and transitions

`active → disabled` (admin) · `disabled → active` · `active → broken` (provider 404/410, or repeated permanent failure) · `broken → active` only by updating the URL. Notifications follow the 02.10.1-T2 states (`pending → sent | dead_letter`). Each admin transition is audited.

## 7. Jobs and integrations

- `SendChatNotification` task from the outbox (02.10.1-T2 sender, new `channel` handler): read channel, resolve the secret reference (11.3.1-T1 path), run the SSRF guard (shared library with 07.6.3-T1), POST JSON through the allow-listed `HttpClient` (S4) with a short timeout, no redirects, max 64 KiB response read.
- Payload formats: Slack incoming webhook JSON (`text`/blocks) and Teams incoming webhook (message card or Workflows webhook) ⚠️ both to be verified against current vendor docs in T2.1; Microsoft has announced retirement of classic Office 365 connectors in favour of Workflows ⚠️ verify, `[OPEN]` which Teams shape V2 supports.
- Rate: a per-channel send cap (default 1 message/s ⚠️) to respect provider limits.
- No schedule; candidate-expiry events come from 08.6.1-T3 on the existing outbox path.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S3 | URL only as secret reference; `url_hint` shows host + last 4; never in logs, metrics, traces, audit or error messages | `ChannelUrl_NeverInLogsAuditOrResponses` |
| 00 §5.7 S4 / SSRF | https only, host allow-list per kind, resolve-then-check public addresses, pinned connection, no redirects, DNS-rebinding safe | `Ssrf_PrivateLoopbackLinkLocalMetadata_Refused`, `Ssrf_RedirectNotFollowed`, `Ssrf_DnsRebinding_Refused` |
| Data minimisation | templates carry names, identifiers, labels, percentage and a link only (PDPL, DECISIONS §7) | `Templates_ContainNoTestContentOrEmails` (snapshot over fixtures) |
| 00 §5.5 C2 | channel commands carry permission attributes; sender task opens a tenant scope per task | architecture test + pipeline test |
| Idempotent delivery | `notification` idempotency key | `Send_Retry_NoDuplicateAfterAck` |
| 00 §5.7 P5 | HTTP call outside any DB transaction; task row updated after | integration test |

Authorization: `notification_channel:write` (create/update/test/delete) and `notification_channel:read` (list), `tenant_admin` only; the sender task runs as `system` inside the org scope.
Retention/deletion: channel rows and `secret_ref` live until the admin deletes the channel or the org is deleted (the referenced secret is deleted with the row); `notification` rows follow 02.10.1 retention; message bodies are not stored beyond the template id and parameters.
Telemetry: audit `notification_channel.create/update/disable/delete/test` (no URL); metrics `chat_notification_sent_total{kind,outcome}`, `chat_notification_dead_letter_total`; `security_event` `ssrf_blocked` on a refused target.
Failure path: invalid URL gives 422 `invalid_webhook_url`; a provider failure retries then dead-letters (operator list from 01.5.1-T4) and 404/410 flips the channel to `broken` with an email to org admins; a failed test returns a typed result without the URL.
