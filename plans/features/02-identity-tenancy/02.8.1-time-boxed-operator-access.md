## 1. Goal and non-goals

**Goal.** A `platform_operator` has **zero** standing tenant access. To see a tenant's data they file a `support_grant` (scopes + reason + expiry); a `tenant_admin` of that org approves (and is never the requester); while the grant is valid the operator connects through the separate `evidgate_operator` DB role with the tenant context set; every read/write is audited with the grant id; expiry ends access automatically with no cleanup step.

**Non-goals.** The operator console UI (09); the security-event alerting rules engine (11.5.1 consumes the events this story emits); retention/deletion policy content (10/11); per-object-type vs per-project scope granularity is an open owner question (02 §11 Q5) — this plan implements **per-project scopes** as the contract default.

## 2. User stories and acceptance criteria

- As a tenant admin, I see who requested access to my org, why, and until when; I approve or revoke and my users can see the same audit.
- As a platform operator, I can help a customer without ever holding a credential that outlives the incident.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/support-grants` (`support:grant`, operator session) creates a `requested` grant with `scopes[]`, `reason`, `expires_at` (≤ 72 h ⚠️ product cap assumed); `Idempotency-Key` required |
| AC2 | `POST /v1/support-grants/{g}/approve` requires `support:approve` **and** an active `tenant_admin` membership in `{g}.org_id`; approver = requester → 422 `approver_must_differ`; any other role → 403 |
| AC3 | With an `approved` unexpired grant, the operator's request to the granted org runs as `evidgate_operator` with `evidgate.org_id` set **and** `evidgate.support_grant_id` set; reads/writes outside the grant's `scopes` are denied; without a grant the same request → 403 `no_support_grant` |
| AC4 | Expiry is enforced at request start and re-checked before each write (02 §5): a grant that expired mid-session lets the in-flight transaction finish, then the next request → 403 `support_grant_expired`; no sweeper needed to cut access |
| AC5 | `POST /v1/support-grants/{g}/revoke` (approver or tenant admin) ends access identically to expiry; both paths write audit rows with `actor_type = platform_operator` and the grant id; every operator read/write inside a grant also writes one (`support.read`/`support.write`, grant id in `metadata`) |
| AC6 | Grant creation and operator reads of `sensitive`-flagged objects emit `security_event` rows (feed 11.5.1 alerting); the tenant sees all grant activity in `GET /v1/orgs/{o}/audit` |
| AC7 | DB-level enforcement (T76): tenant tables carry `TO evidgate_operator` policies that call `evidgate.operator_grant_ok(org_id, project_id, action)`; as `evidgate_operator`, a query without a valid grant GUC → 0 rows, a write outside the grant's named write scopes → RLS violation; the app layer cannot bypass the check |

## 4. Data model and migrations

| Table | Columns / constraints |
|---|---|
| `support_grant` | `id uuid pk`, `org_id uuid not null`, `operator_user_id uuid not null` → `user`, `scopes text[] not null` (`resource:action` strings from `permissions.json` + `project_ids uuid[]`), `reason text not null`, `approved_by uuid`, `approved_at timestamptz`, `expires_at timestamptz not null`, `revoked_at timestamptz`, `created_at` · `unique (org_id, id)` (T3) · `check (approved_at is null or approved_by is not null)` · `check (expires_at > created_at)` · index `(operator_user_id, expires_at)` for the request-start lookup (P4); `(org_id, created_at, id)` for the tenant list · RLS: tenant sees own grants via `org_id = evidgate.current_org_id()`; the **operator** path reads its own grant through the `evidgate_resolve`-style owner function `resolve_active_grant(p_operator_user_id, p_org_id)` (T1) because the operator has no membership |

GUCs added to the scope contract: `evidgate.support_grant_id`, `evidgate.actor_role = operator`. Migration: `migrations/NNNN_identity_support_grant.sql` + `…_resolve_active_grant.sql`.
`evidgate.operator_grant_ok(p_org_id uuid, p_project_id uuid, p_action text)` — owner-owned `SECURITY DEFINER` (`SET search_path=''`, schema-qualified, audited per T80): validates `current_setting('evidgate.support_grant_id', true)` against an approved, unexpired, unrevoked `support_grant` for the calling operator whose `scopes` cover `(org_id, project_id, action)` (`project_id` NULL on org-scoped tables). Tenant tables additionally get `CREATE POLICY … TO evidgate_operator USING (evidgate.operator_grant_ok(org_id, NULL, 'read'))` — **read-only default**; `WITH CHECK`/`FOR UPDATE`-style write policies allow a write only when the grant scope names that write action (T76).

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `RequestSupportGrant : ICommand<uuid>` | `POST /v1/support-grants` | `support:grant` (operator session) | 201 `{id}` · 422 `schema_invalid`, `expires_at` > cap → 422 `grant_window_too_long` · 409 `idempotency_conflict` |
| Command | `ApproveSupportGrant : ICommand<Unit>` | `POST /v1/support-grants/{g}/approve` | `support:approve` + `tenant_admin` of `{g}.org_id` | 200 · 403 · 404 · 422 `approver_must_differ`, `grant_not_requested` |
| Command | `RevokeSupportGrant : ICommand<Unit>` | `POST /v1/support-grants/{g}/revoke` | `support:approve` or the org's `tenant_admin` | 204 · 404 |
| Query | `ListSupportGrants : IQuery<Page>` | `GET /v1/orgs/{o}/support-grants` | `support:read` (`tenant_admin`) | cursor page; operator sees own grants via `GET /v1/support-grants/mine` |
| Pipeline hook | `OperatorGrantScope` | authorization behaviour extension | valid grant for `(operator, org)` + permission ∈ `scopes` | 403 `no_support_grant` / `support_grant_expired` |

Operator request flow: operator session → `resolve_active_grant(operator_user_id, org_id)` → valid → open `ITenantScope` on the `evidgate_operator` connection + set `evidgate.support_grant_id` → pipeline → every handler writes its audit row with the grant id (02.7.1 writer reads the GUC). The GUC is re-validated inside every statement by the `TO evidgate_operator` RLS policies via `operator_grant_ok` (T76) — a revoked or expired grant fails closed even mid-session.

## 6. States and transitions

`support_grant`: `requested → approved → expired | revoked` (00 §8.9; approver ≠ requester). `expired` is computed from `expires_at` (no job); `revoked` is a write. `requested → revoked` is allowed (withdrawal). Every transition writes an audit row, and `approved` also notifies the org's `tenant_admin`s via outbox email/webhook row (00 §5.3).

## 7. Jobs and integrations

- **No expiry sweeper needed** — enforcement is per-request; an optional daily task `ExpireStaleGrants` marks rows `expired` for reporting only.
- **Notifications**: approve/revoke enqueue outbox rows → tenant-admin notification (the 00 §5.3 task pipeline).
- **Alerts**: grant creation + operator read of `sensitive` objects → `security_event` (11.5.1 consumes; alert rules live there).
- **02.6.2**: `OperatorGrantScope` extends the tenant-context matrix with the `evidgate_operator` connection + grant GUCs.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-02-13 / D11 | no standing access: `evidgate_operator` cannot open a tenant scope without a valid `support_grant` row; approver is a tenant admin ≠ requester | AC2, AC3 |
| Time-boxing | `expires_at` re-checked at request start and before each write; revocation identical path | AC4, AC5 |
| Audit (T8, FR-02-12) | every operator action writes `actor_type=platform_operator` + grant id; grants appear in the tenant's `GET /v1/orgs/{o}/audit` — PDPL "who saw my data" is answerable | AC5, AC6 |
| Separate DB role | `evidgate_operator` (02.6.1-T1), no `BYPASSRLS`, only reachable through the operator connection factory | `OperatorRole_HasNoBypassRls` + `Connect_WithoutGrant_CannotSetScope` |
| T76 operator RLS | `TO evidgate_operator` policies on tenant tables call `evidgate.operator_grant_ok(org_id, project_id, action)` — validates the `support_grant_id` GUC against an approved unexpired grant; read-only default, writes only where the grant scope names a write action; definer-function hygiene per T80 | `OperatorRls_*` tests (AC7) |
| 00 §5.7 S2/S3 | `support:grant`/`support:approve` in the pipeline; `reason` is free text but metadata-allowlisted in audit (no secrets) | 403 tests + writer allowlist test |
| 00 §5.7 P3 | grant check is 1 indexed select at request start (`operator_user_id, expires_at` index); no N+1 per handler — the grant id rides the scope | command-counter test |
| Privacy/retention | grants record operator id + reason — retained per 10's policy; tenant deletion keeps the audit minimum | — |
