## 1. Goal and non-goals

**Goal.** Record a single Evidgate GitHub App per environment class (production + non-production), not one App per feature, and bind one installation per organization. The installation id is stored per org; a short-lived installation token is minted on demand from an RS256 app JWT and cached in memory below expiry, never persisted. An uninstall or suspension disables every integration that uses the installation, and every change is audited. The single-App-per-environment decision (T1) covers 07.6.1-T1 (check runs), 03.4.1/03.4.2 (catalog webhooks, healing branch/PR), 08.6.x (healing PR approval flow, via 03.4.2-T1) and 05.5.2-T3 (re-run trigger).

**Non-goals.** OIDC exchange and `ci_binding` (02.4.1); check-run delivery (07.6.1), catalog sync and PR creation (03.4.x), re-run trigger logic (05.5.2); the webhook receiver and `webhook_delivery` dedupe (03.4.1-T2) — this story only supplies its lifecycle event handler; GitHub Enterprise Server (not in V1 [OPEN]); web UI for install (09.x).

## 2. User stories and acceptance criteria

- As a tenant admin, I install the Evidgate GitHub App on my GitHub organization and see its state and permissions in Evidgate.
- As a security reviewer, I know no installation token or private key is stored in the database or logs, and an uninstall stops all GitHub-dependent features.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `StartGitHubInstall : ICommand<{url}>` | `POST /v1/github/installations/start` | `ci_binding:write` | 200 · 409 `already_installed` |
| Command | `CompleteGitHubInstall : ICommand<InstallationDto>` | `GET /v1/github/installations/callback` | session + state binding + OAuth user authorization | 302/200 · 400 `state_invalid` · 403 `installation_not_owned` · 409 `installation_bound` |
| Query | `GetGitHubInstallation : IQuery<InstallationDto>` | `GET /v1/github/installations` | `project:read` | 200 `{installation_id, account_login, state, permissions}` · 404 |
| Command | `DisconnectGitHubInstall : ICommand<Unit>` | `DELETE /v1/github/installations/{i}` | `ci_binding:write` | 204 · 404 (does not uninstall at GitHub; disables bindings) |
| Command | `ApplyInstallationEvent : ICommand<Unit>` | internal, from 03.4.1-T2 receiver | system (post-resolver) | idempotent no-op on replay |

Internal service `IGitHubInstallationTokens.GetAsync(orgId, feature, repositoryIds, ct)` returns `{token, expires_at}`; `feature` is a feature enum, the permission set is a compiled static table keyed by that enum (callers cannot pass permissions; an empty map is a bug and throws), and repo-scoped features pass `repositoryIds` taken from the stored project/repo binding, never from request input (mandatory for those features); the cache key is `(org, installation_id, feature, permission set, repo set)`. Callers never receive the app JWT. Mutations carry `Idempotency-Key`; list fields exclude nothing sensitive (no secrets exist in the row).

## 6. States and transitions

`active → suspended` (event `suspend`) · `suspended → active` (`unsuspend`) · `active|suspended → deleted` (event `deleted` or admin disconnect). `deleted` is terminal; reinstall creates a new row. Dependent bindings are disabled on `suspended`/`deleted` and are **not** auto-re-enabled on `unsuspend` [OPEN] (admin re-enables, avoiding silent resume). Each transition writes audit and an outbox notification.

## 7. Jobs and integrations

- GitHub API via typed `HttpClient`, RS256 app JWT (`Microsoft.IdentityModel.JsonWebTokens`), 10 min max lifetime (✅ ADR-0007 §Evidence), no Octokit (T46); retry with jitter on 5xx/secondary rate limit ⚠️.
- Single-App permission matrix per feature, minimal — authoritative table in [ADR-0007](../../../docs/adr/0007-single-github-app.md) §Permission matrix: checks (07.6.1) `checks:write`, plus `statuses:write` for the T62 commit-status fallback only; catalog (03.4.1) `contents:read` (plus the App-level `metadata:read` every row carries, ADR-0007 matrix last row ⚠️); healing PRs (03.4.2/08.6) `contents:write`, `pull_requests:write`; re-run (05.5.2-T3) `actions:write`. Each feature requests only its subset when minting, and a missing grant yields `installation_unavailable`-style 409 `permission_not_granted`.
- Reconcile task (Cronos, unique fire key, 00 §5.3): daily `GET /app/installations` (✅ ADR-0007 §Evidence, app JWT) compares state to stored rows to repair missed webhooks.
- Upgrade of the App's permission set triggers GitHub re-consent; the `installation` `new_permissions_accepted` event (✅ ADR-0007 §Evidence) updates `permissions`.

**[DECISION] O12 — the ownership check is two-part.** The callback binds an installation only when both hold: (1) `GET /user/installations` with the OAuth user token lists the installation id, and (2) the user administers the account — a `User` account must equal `GET /user`'s id; an `Organization` account must answer `GET /user/memberships/orgs/{org}` with `state=active` and `role=admin`. Either failure is 403 `installation_not_owned`; `GET /app/installations/{id}` with the App JWT runs first and verifies the id exists for this App. Prior art read once: [Generating a user access token for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), [`GET /user/installations`](https://docs.github.com/en/rest/apps/installations#list-app-installations-accessible-to-the-user-access-token), [`GET /user/memberships/orgs/{org}`](https://docs.github.com/en/rest/orgs/members#get-organization-membership-for-a-user); ADR-0007's `request_oauth_on_install` is what makes the code present at the callback.

**What the routes do.** `POST /v1/github/installations/start` (`ci_binding:write`) draws a 256-bit nonce, stores **only** the SHA-256 of that nonce — never of the whole state — bound to `(org, user)` with a 10-minute expiry, and the callback re-hashes the same nonce out of the `<org>.<nonce>` state it receives (the envelope's shape is validated, its org prefix only used as a hint); answers `https://github.com/apps/{slug}/installations/new?state={org}.{nonce}`; an org that already has a live row is 409 `already_installed`, and a user holding 20 unspent states is 429 `install_flow_limited` (the store refuses the 21st live row per `(org, user)`). The org rides inside the state because the browser callback carries no tenant header of its own: the host's tenant filter parses the prefix and still proves the session user's membership of that org through the resolver, so the prefix is a hint and never a grant. `GET /v1/github/installations/callback` (`ci_binding:write`) runs **three steps, two units**: unit one consumes the nonce with one conditional `UPDATE` and commits — so a replay, an expired state and another org's state all answer 400 `state_invalid`, and an ownership refusal that follows cannot be retried with the same nonce; then GitHub verification runs with **no transaction, connection or row lock held** (`GET /app/installations/{id}` with the App JWT, one code exchange, the two-part ownership check, and the callback's user token revoked whatever the verdict); unit two inserts the row and its `github_installation.create` audit entry, re-reading the consumed nonce so the insert cannot escape the org and user that consumption proved. A suspension the App reports in the same lookup is recorded as `suspended` with its `suspended_at`, never as `active` (the row guard requires the two to agree), and any unique-key hit maps to 409 `installation_bound` (another org holds the installation id, or this org already has a live row — a deleted row keeps its `installation_id`, so rebinding that installation needs a fresh installation at GitHub; see the open items below). `GET /v1/github/installations` (`project:read`) answers the row with `id` (the disconnect's `{i}`), `installation_id`, `account_login`, `state`, `permissions`; 404 when there is none or when it is deleted (a deleted row is outside the read, and `github_installation.installation_id` stays taken), and 409 `installation_unavailable` when it is suspended, so a suspended binding never reads as healthy. `DELETE /v1/github/installations/{i}` (`ci_binding:write`, idempotent) marks the row deleted, flushes that installation's cached tokens, and leaves the App installed at GitHub.

**T2.3 seam.** `IGitHubInstallationTokens` + `GitHubAppTokenSource` + `GitHubInstallationTokenSource` moved from `Evidgate.Modules.Catalog/Infrastructure/GitHub` into its own project `src/BuildingBlocks/GitHub` (SharedKernel keeps only the Stream-based reader) so Catalog and Identity share one implementation (Catalog callers and `Catalog.UnitTests` updated, the Catalog copies deleted; no second JWT mint or cache exists). The three catalog-feature rows remain the ADR matrix's ceiling; the installation rows themselves live in `Identity`, whose store also implements `IGitHubInstallationResolver`, so the token source keeps no module SQL.

**Open items of the S410 fix round.** (1) **Refusal audit** — a callback refused by the ownership check, the state binding or the unique key writes no `security_event` row; the receiver for it is [T3 security events](../11-security-events) (a `github_installation.refused` event with reason `state_invalid` / `installation_not_owned` / `installation_bound`), and until then the refusal is observable only through the 00 §9.2 error code and the absence of a create row (the tests assert that absence). (2) **Deleted row keeps its `installation_id`** — the unique key is on `installation_id` alone while only `(org_id)` is partial-indexed by live state, so disconnecting does not free the id: re-binding the same GitHub installation needs a fresh installation at GitHub (uninstall then install), and the 409 `installation_bound` message says so. Relaxing the key (partial on live states like the org one) is a schema decision for T3 with the lifecycle webhooks, not a fix-round edit. (3) **Read of `suspended_at` in the DTO** — the row is inserted as `suspended` with its time from the App lookup, but the read DTO does not expose the time; a UI needs it from T3's lifecycle work. (4) **Audit chain integrity for the create row** — the tests assert the row, its action, actor, org and exactly-once count, not that the audit entry's hash chain is intact, and a *failed* create (409 `installation_bound`) writes no audit row of its own; both need the audit verifier wired into this suite. (5) **No real App key and no log sink** — the suite drives fakes (no `eyJ`/`PRIVATE KEY` ever exists to leak) and scans the database sinks only; a real-key canary and a captured-log scan belong to the deployed-shape suite. (6) **GitHub 401 mapping** — a 401 from GitHub (revoked or malformed App credential) answers `github_unavailable` through `GitHubResponseReader`; telling it apart from a transient failure is not modelled. (7) **Permission description** — the `permissions` map is stored as GitHub returns it and is not checked against the catalogue's feature map. (8) **Resolver after HMAC only** — `evidgate_resolve.installation_by_id(bigint)` cannot tell a verified caller: T3 must call it only after the webhook's signature check, and never from an unauthenticated path. (9) **Malformed-state ordering** — the envelope is parsed inside the permission-gated consume command, so a denied caller gets its denial (403 `forbidden` over a state naming its own org) and a permitted caller gets 400 `state_invalid` for a malformed nonce; a state naming no org leaves no tenant to authorize against, so AC1's missing case answers 401 `unauthenticated` (fail-closed, nothing parsed, nothing consumed). Another org's state, a replay and an expired state stay 400 `state_invalid`, and a state naming an org the caller does not belong to is 403 before the nonce is touched.

## 11. Rollout

- Flag `github_app_enabled` per environment (default off until the App is registered and the ADR key owner is named); additive tables and endpoints. 07.6.1, 03.4.x and 05.5.2-T3 consume `IGitHubInstallationTokens` and stay dark without an active installation.
- Monitoring: `github_token_mint_total{result="error"}` alert, installation `suspended` count, reconcile drift count.
- Rollback: disable the flag; rows are tenant data and remain. The key-compromise stop is **generate-then-delete**, not delete: GitHub forbids deleting an App's only key ("you must regenerate a new key before you can delete the existing key" ✅ [Managing private keys for GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)), so the order is (1) turn `github_app_enabled` off, (2) revoke every Evidgate-held installation token with `DELETE /installation/token` before any restart (a restart only discards them; they stay valid up to 1 h), (3) generate a new key at GitHub, (4) delete the compromised key at once (this is the revoke; it stops new app JWTs signed with it), (5) identify and close the exposure path before loading the new key, (6) load the new key and deploy/restart Api+Worker; tokens an attacker already minted stay valid up to 1 h. The full procedure is in the key-custody runbook [`docs/runbooks/github-app-key-custody.md`](../../../docs/runbooks/github-app-key-custody.md).
