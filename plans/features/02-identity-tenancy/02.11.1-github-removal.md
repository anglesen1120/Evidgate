> [DECISION] D-NO-GITHUB (D5), D-A3, plan 00 §§5.4, 8.1, 9 and 10. Priority P1; implementation lane S703, tier T3. This is a destructive cutover, not a disabled feature. `plans/removed-scope.md` identifies the historical tasks it replaces.

## 1. Goal and non-goals

Remove the product's three GitHub connections: interactive login, Actions OIDC exchange, and App installation/webhooks/catalog sync. A new customer needs only the staging URL and, for external CI, a project credential. Evidgate never contacts a customer's repository.

Keep Google Workspace OIDC, membership and invite checks, sessions, ingest-token exchange, customer-pushed results, `evidgate gate`, outbound decision webhooks and producer-declared ref metadata. Evidgate's own GitHub Actions pipeline remains; its dogfood producer uses an ingest token. OI-02-34 separately adds Microsoft Entra ID on the shared OIDC handler and email magic-link sign-in. The removal must preserve these methods when present.

## 2. User stories and acceptance criteria

| ID | Observable result |
|---|---|
| AC1 | A Google user with verified email and active membership can sign in, link according to the existing rules, accept an invite and use a session. GitHub is neither offered nor accepted; no automatic link by email replaces a deleted identity. |
| AC2 | A project ingest token exchanges for a short-lived `ci_producer` for that project. Revoked, rotated-out, malformed and wrong-project credentials do not authorize the operation. The OIDC exchange request shape is refused. |
| AC3 | With only that token, create a run with branch/commit/PR metadata. The stored run and its read model report producer-declared provenance (`ref_provenance = declared`; stored today as `unverified_ref = true`, see OI-02-37), never GitHub-verified. A non-fork run on the declared default branch or configured release-branch glob may gate. A declared fork remains advisory-only and cannot bind to a release, even when uploaded by a trusted job; missing evidence never yields PASS (OI-02-39). No token-issue or repository lookup is necessary. |
| AC4 | On a migrated, populated database no integration table, dedicated resolver/purger or removed permission survives. The retained ingest-token resolver still runs with its existing least-privilege grants. |
| AC5 | No GitHub route, client, secret option, login button, binding/installation control, generated SDK operation or CLI credential path remains. A known project can still ingest, finalize and read a decision via `evidgate gate`. |

## 5. API shapes (commands, queries, endpoints)

`contracts/openapi.yaml` paths are relative to the API base. Retire `/projects/{p}/ci-bindings`, `/ci-bindings/{b}`, `/github/installations/start`, `/github/installations/callback`, `/github/installations`, `/github/installations/{i}`, `/projects/{p}/git-repo-bindings`, and `/webhooks/github`. Retired operations have no handler or redirect. Prune unreferenced integration schemas, permission literals and fixtures.

Keep `/ci/token` for project ingest tokens only; retain the supported OIDC variants of `/auth/oidc/{provider}/start`, `/auth/oidc/{provider}/callback` and `/auth/link/{provider}`. Remove GitHub from provider/input enums. The run-create payload may declare a ref but cannot set its authenticated provenance: after the cutover every producer-supplied ref is declared. The existing run fields are the boolean `unverified_ref` (migration 0037, `RunCreated`/`RunState`/`ListRuns` DTOs, telemetry); `ref_provenance = declared` is the vocabulary of D-NO-GITHUB/OI-02-35. Default (OI-02-37): no new column or wire field; `unverified_ref = true` is the stored form and UI/report text reads "declared". Do not relabel historical evidence or invent a ref when none was supplied.

## 6. States and transitions

- Revoke/delete App install and binding setup flows, including pending-state callbacks; nothing transitions a repository to trusted. A pre-existing GitHub-only user has no automatic Google association. Arrange access through the normal membership/linking process before cutover.
- For a long job, expiry requires re-exchange and a fresh short-lived token; expiry is not an authorization bypass. OI-02-36 resolves how an existing slot recognizes that the renewed token belongs to the same authenticated producer.

## 7. Jobs and integrations

Remove the `ci_token_issue` and GitHub install-state purge schedules, inbound delivery dedupe/sync jobs and their DI/configuration. Drain in-flight integration jobs before schema removal. The normal ingest-token rotation/revocation, rate limiting, event collection and outbound webhooks remain. The App custody runbook was retired in this plan change. Remove obsolete secret names from deployment/configuration; retire credentials in the secret store during operator cutover, not by copying them into logs.

## 8. Security, privacy and performance

- **Authorization:** Google login still requires verified email and active membership. The exchange issues a least-privilege, single-project token; project scope and slot ownership are enforced on write and finalize. A declared ref, attempt or repository name never establishes caller identity.
- **Retention/deletion:** remove installation, binding, issue, delivery, sync and GitHub identity records with the migration; retain unrelated identities, run evidence and audit history under their normal retention. No new copy of removed provider data.
- **Telemetry:** retire GitHub exchange/sync/purge counters, keep outcome/status counts for token exchange and run creation. Never log a token, webhook body, provider subject or credential-store value.
- **Failure path:** invalid credentials fail closed; missing credentials never fall back to OIDC. A remaining FK/definer or failed survivor probe blocks cutover. Measure locks on a populated fixture; if maintenance limits are exceeded, stop before deployment rather than starting mixed-version writers.

## 11. Rollout

Start S703 only after this plan and P0 (S695/S696) merge; assign `<next free>` then. Inventory GitHub-only users and arrange alternative access without automatic linking. Switch dogfood CI to a project secret, take a restorable pre-cutover backup, stop old binaries/workers, drain jobs, apply migration and deploy compatible binaries together. Probe Google login and project-token ingest → finalize → gate before reopening traffic. Before destructive DDL, abort without changing the DB. After commit, an old binary alone is **not** a rollback: pause writes and restore the pre-cutover DB together with compatible binaries under the recovery procedure, reconciling post-backup writes, or roll forward. Do not silently re-enable GitHub or recreate deleted personal identity links.
