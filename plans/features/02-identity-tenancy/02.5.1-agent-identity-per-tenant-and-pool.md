## 1. Goal and non-goals

**Goal.** In V2 an `evidgate-agent` process authenticates as a `service_identity` enrolled into exactly one `(tenant, pool)`. It can claim and execute jobs only from that pool, upload artifacts only for its claimed jobs, and can never approve healing, change policy or read another project. Its credential is an asymmetric keypair with rotation and immediate revocation.

**Non-goals.** The job/pool data model and claim semantics (05.7.3, 05.7.4 — this story supplies only the identity and its enforcement hooks); the agent binary itself (Node 22+/TS, 05.7.4); healing approval logic (08); operator-side rotation runbook (10.7.1).

## 2. User stories and acceptance criteria

- As a tenant admin, I enrol an agent into pool "linux-docker" of my org, receive a one-time enrolment bundle, and the agent can only ever see that pool's jobs.
- As a security reviewer, I can revoke a compromised agent key and the agent's next claim or heartbeat fails.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/orgs/{o}/service-identities` (`service_identity:write`, tenant admin) creates an identity bound to one `pool_id`; the response carries the private key / enrolment token once — only the public key is stored |
| AC2 | The agent obtains a short-lived `agent` token by signing a server challenge with its private key (challenge-response enrolment) or exchanging an enrolment token; the minted token carries `service_identity_id`, `org_id`, `pool_id`, `jti`, expiry ≤ 60 min |
| AC3 | `POST /v1/agents/jobs/claim` (`job:claim`) accepts only a claim whose `pool_id` equals the token's pool; any other pool → 403 `pool_scope_mismatch`; a job outside the token's org is invisible (RLS) |
| AC4 | An `agent`-type principal calling a `healing:approve`, `healing:configure`, `policy:*` or `project:write` endpoint gets 403 regardless of grants — the permission catalogue contains no binding from `agent` to those permissions (deny-by-default, FR-02-2) |
| AC5 | `POST /v1/service-identities/{s}/rotate` issues a new keypair while the old key verifies until its `expires_at`; `DELETE` (revoke) sets `status=revoked` and the next claim/heartbeat/token exchange returns 401 |
| AC6 | Every claim, heartbeat, rotation and revocation writes an audit row with `actor_type = agent` |

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `EnrolServiceIdentity : ICommand<EnrolResult>` | `POST /v1/orgs/{o}/service-identities` | `service_identity:write` | 200 `{id, name, pool_id, enrolment_bundle (once)}` · 404 foreign `pool_id` · 409 `unique (org_id, name)` |
| Command | `MintAgentToken : ICommand<CiTokenResult>` | `POST /v1/agents/token` | none — credential exchange | 200 `{token, expires_at, pool_id}` · 401 `identity_revoked` / `identity_expired` / `challenge_failed` |
| Command | `RotateServiceIdentity` / `RevokeServiceIdentity` | `POST /v1/service-identities/{s}/rotate`, `DELETE /v1/service-identities/{s}` | `service_identity:write` | 200 / 204 · 404 |
| Query | `ListServiceIdentities : IQuery<Page>` | `GET /v1/orgs/{o}/service-identities` | `service_identity:read` | cursor page `{id, name, pool_id, status, last_seen_at}` — no key material |
| Guard hook | `AgentPoolScope` | applied to `job:claim`/`job:execute`/`artifact:write` in the authorization behaviour | token `pool_id` must equal request `pool_id` | 403 `pool_scope_mismatch` |

`MintAgentToken` is a pre-tenant path (T1): a `evidgate_resolve.resolve_service_identity(enrolment_key_hash)` resolver returns `(org_id, project_id, binding_id, status)` where `binding_id = service_identity_id`; then the scope opens and the signature/challenge is verified inside it.

## 6. States and transitions

`service_identity`: `active → rotated` (overlap via `expires_at` on the old key) `→ revoked`; `active → revoked`; `active → expired`. Mirrors `ingest_token` (00 §8.9 pattern extended to this V2 table). Every transition + every `MintAgentToken` writes an audit row (`actor_type = agent` for agent-initiated, `user` for admin actions).

## 7. Jobs and integrations

- **05.7.3-T1** supplies `pool` and the claim transaction; this story supplies the `pool_scope_mismatch` check inside the authorization behaviour (no extra round trip — `pool_id` is a token claim).
- **10.7.1-T4** runbook: rotation cadence + compromised-key drill; the kill-switch path = `RevokeServiceIdentity` + (org-wide) a bulk-revoke operator route under `/internal/operator/` (T16 shape) for mass compromise.
- **05.7.4** (agent side) consumes the enrolment bundle format — pinned in `contracts/` (versioned JSON bundle: identity id, public key fingerprint, enrolment token, API base URL).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-02-9 / 00 §2 deny-by-default | `agent` permissions are exactly `{job:claim, job:execute, artifact:write}` in `permissions.json`; no path to `healing:approve`/`policy:*`/`project:write` exists | AC4 + `PermissionsJson_AgentRole_ExactSet` |
| Pool scope | `pool_id` is a signed token claim compared in the authorization behaviour; DB additionally enforces org via RLS + composite FK `(org_id, pool_id)` | AC3 |
| T1 | token exchange resolves tenant via `resolve_service_identity`, audited, `EXECUTE`-only | resolver tests |
| Key hygiene (T5 analogue) | private key exists only client-side; server stores public key; enrolment token ≥ 128-bit, HMAC'd like ingest tokens, shown once | AC1/AC2 |
| 00 §5.7 S2/S3 | permissions in pipeline; secrets never logged (`service_identity_id` + `jti` only) | AC4 + log-allowlist test |
| 00 §5.7 P3/P5 | claim adds zero DB round trips (claim check is a claim compare); token exchange is 1 resolver + 1 verify + 1 issue-row insert | command-counter test |
| Privacy/retention | `name`, `last_seen_at` deleted with org; public keys are not personal data | — |
