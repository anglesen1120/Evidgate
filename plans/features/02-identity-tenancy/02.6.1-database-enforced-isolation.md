## 1. Goal and non-goals

**Goal.** PostgreSQL itself refuses cross-tenant access: every business table runs under `FORCE ROW LEVEL SECURITY` with a fail-closed `org_id` policy, the runtime role can never bypass it, and every credential-only entry point resolves its tenant through owner-owned `SECURITY DEFINER` functions before the tenant scope opens. A table that misses a policy, `org_id` or `unique (org_id, id)` fails CI and the boot self-check.

**Non-goals.** The tenant-scope transaction primitive (`ITenantScope`, C3 wiring into Mediator and the worker) is 02.6.2; the isolation test suite that exercises all of this is 02.9.1; the GitHub-webhook resolver function is 03.4.1; DbUp runner is 01.4.1.

## 2. User stories and acceptance criteria

- As the Tech Lead, I know a forgotten `WHERE org_id` can never leak rows, because the database enforces tenancy even if application code is wrong.
- As an attacker holding the app role's credentials, I cannot read another tenant: the role is not the table owner, has no `BYPASSRLS`, and every tenant GUC is unset until a scoped transaction sets it.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | For every business table migrated at M1: `pg_class.relrowsecurity` and `pg_class.relforcerowsecurity` are true and a policy exists with `USING (org_id = evidgate.current_org_id())` / `WITH CHECK (org_id = evidgate.current_org_id())` |
| AC2 | `SELECT rolbypassrls FROM pg_roles WHERE rolname='evidgate_app'` is false; `evidgate_app` owns no tables; `evidgate_operator` likewise has no `BYPASSRLS` |
| AC3 | With `evidgate.org_id` never set (or set to `''`), every tenant-table select through `evidgate_app` returns 0 rows, never an error and never foreign rows (helpers use `current_setting(…, true)` + `NULLIF(…, '')::uuid`, T2) |
| AC4 | A new migration adding a business table without `org_id`, without `unique (org_id, id)` or without a policy fails the CI lint, unless the table is on the §4.5 exception list (`user`, `user_identity`, `session`, `permission`, built-in `role`/`role_permission`, built-in `template`, `organization`) |
| AC5 | The API boots only when the self-check confirms every non-exception table has a policy; a dropped policy makes startup fail with a named error |
| AC6 | `evidgate_resolve` functions return only `(org_id, project_id, binding_id, status)`; `evidgate_app` has `EXECUTE` on them and zero direct privileges on the tables they read; every call writes an audit-row stub (function name + lookup-key hash, never the secret) |
| AC7 | Every `SECURITY DEFINER` function in any schema (`evidgate_resolve`, `evidgate`, `evidgate_ops`) is linted for `SET search_path = ''` + schema-qualified references, `EXECUTE` to a dedicated role only and a per-call audit row (T80); `evidgate_operator` reaches tenant tables only through the `evidgate.operator_grant_ok` policies owned by 02.8.1 (T76) — this story creates the role and the lint, not the operator policies |

- Recorded 2026-09-27 (T1.4 fail-closed hardening, the story's failure-path findings D3/D5/D7) — `ReadPoliciesAsync` now reads `pg_policy.polroles` (resolved to role names, `0` = PUBLIC), `polcmd` and `polpermissive`, so a policy is judged by who it applies to and which commands it governs, not by its expression alone. A tenant table needs a permissive `FOR ALL` policy that applies to `evidgate_app` (explicitly or via PUBLIC) and carries `org_id = evidgate.current_org_id()` in USING and in its WITH CHECK (absent is fine: PostgreSQL reuses USING as the check); every other permissive policy that reaches `evidgate_app` must be scoped too, because permissive policies are OR-ed and one unscoped sibling re-opens the table. A RESTRICTIVE policy only narrows, so it is not judged. The platform kind keeps the flags-and-presence rule except for the tenant root, whose name-to-predicate map (`public.organization` → `id = evidgate.current_org_id()`) is per table on purpose: a platform entry does not distinguish genuinely open platform data (`public.permission`, a `using (true)` read for every org plus one denial per write command) from org-scoped data that merely lacks an `org_id` column, so a new self-scoped platform table adds one map line and a new open-catalogue one stays out. Refusals now speak distinct codes — `tenant_policy_wrong_role`, `tenant_policy_using_not_scoped`, `tenant_policy_with_check_not_scoped`, `tenant_policy_not_all_commands` and `permissive_policy_unscoped`, with the `platform_policy_*` set for the root; `tenant_policy_missing` and `catalogue_read_policy_missing` are unchanged. `tenant_policy_missing` now means only "the predicate appears nowhere on the table", so a correct predicate on the wrong role reads as `tenant_policy_wrong_role` (D3: fail-closed, previously undiagnosed), a select-only policy as `tenant_policy_not_all_commands`, and `using (true)` as `tenant_policy_using_not_scoped` (D5). Every table at head 0011 (`rls_probe`, `organization`, `project`, `idempotency_record`, `membership`, `membership_role`, `role`, `role_permission`, `permission`) was checked against the tightened rules before they landed; the mechanism tables stay outside the rule set through the exception list, and the catalogue kind keeps its all-org read rule.
- Recorded 2026-09-27 (W7-SEC-01, the policy-clause matcher) — the scoping test on a clause is now structural, not textual. `IsolationSelfCheck.MatchesPredicate` normalises case and whitespace, strips parentheses only where they wrap a whole expression, splits the clause at the boolean operators of its own parenthesis depth and refuses any top-level `OR`; the clause is scoped when it is the predicate (allowing for redundant parentheses and for how a homogeneous `AND`/`OR` chain associates) or an `AND` chain one of whose operands — possibly a nested `AND` chain of its own — is the predicate. The matcher it replaces removed every parenthesis before anchoring on the predicate text, so PostgreSQL's own deparse of `using ((org_id = evidgate.current_org_id() and status is not null) or true)`, namely `(((org_id = evidgate.current_org_id()) AND (status IS NOT NULL)) OR true)`, read as `org_id = evidgate.current_org_id() AND …` and passed a policy that admits every org's rows — the shape `using (true)` is refused for. The T2.1 lint and `RlsPolicyCoverageTests` call the same public matcher (one implementation: the test project already references `Evidgate.BuildingBlocks.Persistence`), so the boot gate and the CI lint cannot disagree about a policy shape. Proven by `SelfCheck_TenantPolicyOrWidenedClause_Fails` (`(pred AND x) OR true` and `true OR (x AND pred)`, on USING and on WITH CHECK, each refused with its own code) and by `SelfCheck_TenantPolicyWithExtraAndedCondition_Passes` (a narrower policy is still a scoped one); every table at head 0011 still passes the whole boot suite, `RlsPolicyCoverageTests` and the Tenancy suite.
- Recorded 2026-09-27 (the pre-merge review of the W7-SEC-01 rule set) — the OR-combining guard is no longer a tenant-only rule: on a catalogue table, once a policy carries the all-org read shape, every applicable permissive policy that reaches `evidgate_app` must also be scoped for its commands, or it is refused as `permissive_policy_unscoped` (before this, `public.role`/`public.role_permission` accepted an extra `for all … using (true) with check (true)` sibling that re-opened every org's tenant-created rows, because permissive policies OR-combine). The tenant predicate counts as scoped there too — it is strictly narrower than the all-org read shape — which is what keeps 0010 green: `role_tenant_insert`/`role_tenant_update` and `role_permission_tenant_insert`/`_update` (their WITH CHECK is the tenant predicate `AND` the `EXISTS` tie on the referenced role) are not leaks just because they do not carry `org_id IS NULL`. The guard is one implementation (`IsolationSelfCheck.AddUnscopedPermissiveViolations`), shared by the tenant, platform and catalogue kinds. Separately, the independent half in `RlsPolicyCoverageTests` no longer accepts *either* side for the tenant rule: its tenant assertion requires the predicate in USING (`MatchesUsing`), because PostgreSQL reuses USING as the WITH CHECK of a policy that declares none, while the catalogue assertion keeps the OR (0010 writes the read shape in USING for the read policy and in WITH CHECK for the insert one). Proven by `SelfCheck_CatalogueTableWithExtraPermissiveUnscopedPolicy_Fails` plus the positive `SelfCheck_CatalogueTables_UnmodifiedSchema_Passes`, and by `CoverageRule_TenantPolicyScopedOnlyByItsWithCheck_IsRefused` plus `CoverageRule_CataloguePolicyScopedOnlyByItsWithCheck_IsAccepted`.

## 4. Data model and migrations

No new business tables; this story adds roles, the `evidgate` helper schema, the `evidgate_resolve` schema and policies over 02.1.1 tables.

| Object | Definition |
|---|---|
| Roles | `evidgate_owner` (owns tables, runs migrations, `NOINHERIT` targets audited); `evidgate_app` (`NOLOGIN`, `NOBYPASSRLS`, granted `SET ROLE` to the login user; CRUD on business tables, `EXECUTE` on `evidgate_resolve` only); `evidgate_operator` (`NOLOGIN`, `NOBYPASSRLS`, used only by the support path of 02.8.1 — its tenant-table access is enforced by `TO evidgate_operator` policies calling `evidgate.operator_grant_ok`, T76) |
| `evidgate.current_org_id()` / `evidgate.current_project_id()` | `STABLE` functions: `NULLIF(current_setting('evidgate.org_id', true), '')::uuid` (and `…project_id`); return NULL when unset/empty |
| Policy template | `ALTER TABLE … ENABLE ROW LEVEL SECURITY; ALTER TABLE … FORCE ROW LEVEL SECURITY; CREATE POLICY tenant_isolation ON … USING (org_id = evidgate.current_org_id()) WITH CHECK (org_id = evidgate.current_org_id());` + `unique (org_id, id)`; join tables use `EXISTS` on the parent; catalogue rows use `org_id IS NULL OR org_id = evidgate.current_org_id()`; `organization` uses `id = evidgate.current_org_id()` (T4) |
| `evidgate_resolve.member_orgs(p_user_id uuid)` / `…resolve_ci_binding(p_provider text, p_repository_id bigint)` / `…resolve_ingest_token(p_prefix text)` / `…invite_by_secret(p_secret_prefix text)` | `SECURITY DEFINER`, owner-owned, `SET search_path = ''`, schema-qualified references; each returns a single row `(org_id, project_id, binding_id, status)` (`invite_by_secret` returns `(org_id, membership_id)` for 02.1.2, T75); `resolve_ci_binding` is challenge-aware — returns the single `active` row, or a single `pending_verification` row when none is active so the exchange can attempt activation (T70); each inserts its own call-audit row (lookup key stored hashed, T1) |
| Indexes | policies add no new list queries; `member_orgs` is served by `membership (user_id, org_id)` where status = active |

Migrations: `migrations/NNNN_identity_db_roles.sql`, `migrations/NNNN_tenancy_rls_helpers.sql`, `migrations/NNNN_tenancy_rls_policies.sql`, `migrations/NNNN_identity_evidgate_resolve.sql` (all run as `evidgate_owner` through the 01.4.1 DbUp runner).

## 7. Jobs and integrations

- Boot-time self-check (01.1.2 host): at `Evidgate.Api`/`Evidgate.Worker` startup, a hosted service asserts each non-exception table has a policy + `relforcerowsecurity`; failure aborts startup (AC5).
- The CI lint (`scripts/check-rls.sql` + CI step, T2) is consumed by 01.7.1's pipeline; it parses each `migrations/*.sql` for new `CREATE TABLE` statements and reconciles against the exception list file `contracts/rls-exceptions.txt`.
- Every resolver call emits its audit stub through the same connection before the tenant scope exists — written by the `SECURITY DEFINER` function itself (owner role), so the app role never writes outside RLS.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** the policies are the authorization layer this story owns: every org-scoped table denies by default and `evidgate_app` reads only `org_id = evidgate.current_org_id()` (or, for `organization`, `id = …`), so a caller that forgets a predicate gets zero rows instead of another tenant's; `evidgate_app` is not the owner and holds no `BYPASSRLS`, and the operator's tenant access stays T76's grant-gated policy of 02.8.1. The boot self-check refuses to start a process when a table the exception list does not excuse is not under that policy, so a missing policy cannot be served. Pre-tenant resolution (`EXECUTE`-only resolvers) is 02.6.1-T3. Proven by `RlsPolicies_EveryBusinessTable_HasForcedRls`, `AppRole_HasNoBypassRls_AndOwnsNoTables` and `SelfCheck_MissingPolicy_FailsStartup`.
- **Retention/deletion:** this story stores no business data and deletes nothing — it creates roles, helpers and policies over tables other stories own. `DELETE` stays revoked from `evidgate_app` on the registry tables, and every retention or purge rule (idempotency expiry, task retention, tenant deletion) belongs to the owning story (10/11). `contracts/rls-exceptions.txt` holds table names and reasons only — no personal data and nothing to retain.
- **Telemetry:** three log events on the self-check path, all secret-free: 1211 Information when it passes (`{CheckedTables} table(s) under forced row level security, {ExemptTables} mechanism table(s) exempt`), 1210 Warning when the check is explicitly disabled (naming `EVIDGATE__ISOLATION__SELFCHECK`), 1212 Error with the refusal (table names and codes). No metric or span is added: RLS costs nothing per request and the check runs once per process. The refusal line is asserted to carry no credential (`SelfCheck_MissingPolicy_FailsStartup`).
- **Failure path:** a table without `ENABLE`/`FORCE ROW LEVEL SECURITY` or without the policy shape its kind requires → the boot is refused with `isolation_self_check_failed`, one named line and exit code 3 (the Api and the Worker both translate the hosted-service exception); a catalogue that cannot be read → `isolation_catalogue_unreadable` and the same refusal, because "cannot confirm" is not "confirmed". The policy shape includes who the policy applies to and which commands it governs: a predicate on another role refuses as `tenant_policy_wrong_role` (D3), `using (true)` with a correct WITH CHECK as `tenant_policy_using_not_scoped` (D5), a `for select`-only policy as `tenant_policy_not_all_commands`, and a second unscoped permissive policy that OR-combines with a correct one as `permissive_policy_unscoped`. A clause that merely *mentions* the predicate while OR-ing something else in is the same failure as `using (true)`: `(org_id = evidgate.current_org_id() and status is not null) or true` refuses as `tenant_policy_using_not_scoped`, and its WITH CHECK twin as `tenant_policy_with_check_not_scoped` (W7-SEC-01) — the clause is judged on its structure, so the predicate has to be a conjunct of the clause, not a substring of it; `public.organization` refuses an open policy as `platform_policy_using_not_scoped` (D7) while `public.permission`'s open read keeps passing. `EVIDGATE__ISOLATION__SELFCHECK=Disabled` is the explicit, Warning-logged opt-out for hosts that intentionally boot without a database — never for a process that serves tenant traffic. At request time the failure mode is the same shape: zero rows (or a `WITH CHECK` rejection), never foreign rows. Proven by `SelfCheck_MissingPolicy_FailsStartup`, `SelfCheck_TenantPolicyForAnotherRole_Fails`, `SelfCheck_TenantPolicyWithOpenUsing_Fails`, `SelfCheck_TenantPolicyNotForAllCommands_Fails`, `SelfCheck_ExtraPermissiveUnscopedPolicy_Fails`, `SelfCheck_TenantPolicyOrWidenedClause_Fails`, `SelfCheck_TenantPolicyWithExtraAndedCondition_Passes`, `SelfCheck_OrganizationPolicyWithOpenUsing_Fails`, `SelfCheck_UnreadableCatalogue_FailsStartup`, `SelfCheck_Disabled_IsAnnounced` and `TenantGuc_Unset_OrEmpty_ReturnsZeroRows`.

## 11. Rollout

- No feature flag — RLS is the base layer. Merge order: T1 → T3 → T2 (lint lands last so early migrations bootstrap cleanly); T2 is the M2-sized hardening step.
- Risk: an over-tight policy breaks a legitimate read → the 02.9.1 suite and each module's integration tests run as `evidgate_app` and catch it at M1.
- Rollback: revert migrations before any tenant data exists; after M1, policy changes ship as new migrations, never edits.
