## 1. Goal and non-goals

**Goal.** One outbound email channel in `Evidgate.Modules.Notifications`. A business change writes a `notification` row and an outbox event in the same transaction; the worker's task sends exactly one localized (vi/en) mail per `(org_id, notification key)`. Consumers: invite (02.1.2-T2), support grant (02.8.1-T1), quota 80 % warning (12.3.1-T4), candidate expiry (08.6.1-T3, wired in V2). A bounce or complaint suppresses later mail to that address. No mail carries a secret or customer test data, except the single-use invite link (see §8).

**Non-goals.** In-app notification centre, Slack/webhook channels, marketing mail, user-editable templates, SMS (all later or out of scope); the outbox dispatcher and `task` queue themselves (01.5.1); the consumers' business logic (their own stories).

## 2. User stories and acceptance criteria

- As an invitee, I receive one invite email in my language and can follow it to join.
- As a tenant admin, I am told when quota reaches 80 % and when a support grant is requested or expires, once each.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Invite, support grant, quota warning each produce exactly one `notification` row and one provider call; replaying the same outbox event or task twice leaves one row (`unique (org_id, notification_key)`) and one provider call (provider-side dedupe header ⚠️ if supported, else the row's `sent` state guards) |
| AC2 | No provider call happens inside a request or DB transaction: a test double asserts the send runs only from the task handler, after the business transaction committed (P5) |
| AC3 | Locale is chosen per recipient (`vi` or `en`, fallback `en`); each template exists in both languages and a missing key fails the build (resource-parity test) |
| AC4 | A provider 5xx/timeout retries with backoff to the 01.5.1 cap, then the notification is `dead_letter` and visible in the operator dead-letter list; a provider 4xx permanent reject goes straight to `failed` with a reason code |
| AC5 | A signed bounce or complaint webhook inserts a `suppression` row; the next send to that address is `suppressed` with no provider call; an unsigned or replayed webhook is 401/ignored |
| AC6 | Per-org opt-out stops non-transactional mail (quota warning) but never invite or support-grant mail |
| AC7 | Rendered bodies and every log line contain no token, password, ingest token, artifact URL, test name or DOM/response data; logs carry notification id, template id, org id, and recipient domain only (allowlist test) |
| AC8 | The sender domain passes SPF, DKIM and DMARC alignment checks in the staging runbook (T1) |

## 6. States and transitions

`pending → sending → sent` · `sending → pending` (retry, `available_at` backoff) · `sending → dead_letter` (cap exceeded) · `pending|sending → failed` (permanent 4xx) · `pending → suppressed` (address on list or category opted out). Terminal states are immutable. `sent → bounced` is recorded on the suppression row, not by mutating the sent notification.

## 7. Jobs and integrations

- Outbox event `notification.requested` (same transaction as the business change) → dispatcher (01.5.1-T3) → `task` `notification.send` with natural key `(org_id, notification_key)`; handler opens the tenant transaction, loads the row, checks suppression and preferences, renders, then calls the provider **outside** any open transaction (claim, commit, send, short second transaction records the result).
- Provider adapter `IEmailSender` (SMTP or HTTPS API) behind one interface so the provider stays swappable. Bounce/complaint webhooks feed `email_suppression`. Provider facts (rate limits, signature scheme, dedupe header) are ⚠️ until T1 fixes the provider.
- Consumers: 02.1.2-T2 (invite), 02.8.1-T1 (support grant request/approve/expiry), 12.3.1-T4 (80 % quota), 08.6.1-T3 (candidate expiry, V2). Each only enqueues; none sends.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Authorization | enqueue runs under the caller's existing permission; webhook is signature-authenticated; preference write needs a tenant-admin permission; the worker acts as the tenant scope of the row | 403 + signature tests |
| S3 no secrets / test data | templates take allowlisted params only; the sole credential in mail is the single-use invite link per T75 (02.1.2): its secret is passed sealed in the outbox payload, rendered at send time, never logged, wiped on terminal state; [OPEN] confirm sealing key owner with plan 11 | AC7 log/body allowlist test |
| PDPL (DECISIONS §7) | recipient address and org name are the only personal data; provider is a processor needing a processing contract (Art. 37.2.a ✅) and a transfer assessment if abroad (Art. 20.2 ✅); retention in §4 | T1 decision memo; retention purge test |
| Retention / deletion impact | org deletion (06.4.4) deletes the org's `notification` and preference rows; `email_suppression` holds only a hash and survives by design | org-deletion fixture |
| Telemetry | counters `notification_sent_total{template,result}`, `notification_dead_letter_total`, `email_suppressed_total`; log fields per AC7; alert on dead-letter growth via the 01.5.1-T4 sink | metric assertions |
| Failure path | provider down → retry then dead-letter; mail never blocks the business action (the invite exists even if mail fails; resend path in 02.1.2) | AC4 test |

## 11. Rollout

- Flag `notifications.email_enabled` per environment, off until T1 is decided and the domain is verified; with it off, rows stay `pending` and nothing is sent.
- Order: T1 and T2 in M2 (invite and support grant need it), T3 and T4 in M3; V2 adds candidate expiry.
- Rollback: disable the flag; unsent rows are retained and drain on re-enable; no schema rollback needed.
