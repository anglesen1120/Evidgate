## 1. Goal and non-goals

**Goal.** The `__Host-` session cookie is an opaque reference to a server-side `session` row: `HttpOnly; Secure; SameSite=Lax`, rotated on login and on privilege change, idle (`expires_at`, sliding) and absolute (`absolute_expires_at`) expiry enforced, revocation effective on the very next request. Cookie-authenticated mutations pass the ASP.NET Core antiforgery pair (`XSRF-TOKEN` cookie / `X-XSRF-TOKEN` header). Users can list and revoke their own sessions; admins can revoke a member's.

**Non-goals.** Login protocol handlers (02.3.1); SAML session specifics (02.3.3 reuses this model); step-up re-authentication policy (09/11 — hook only); bearer-token clients (CLI/CI/agent are not cookie-authenticated, T38 — out of scope).

## 2. User stories and acceptance criteria

- As a user, I see all my sessions (device, IP, last activity) and can kill any of them — including "all but this one".
- As a `tenant_admin`, removing a member (02.1.2-T3) kills their sessions instantly.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Cookie attributes: `__Host-` prefix, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`; value is a ≥128-bit opaque random, stored only hashed (HMAC-SHA256 + `pepper_version`, T5 pattern) |
| AC2 | Idle expiry: a request AT or AFTER `expires_at` → 401 `session_expired` (the comparison is inclusive, `expires_at <= p_now` at `migrations/0045_identity_session_hardening.sql:381`, [DECISION D-S85-D10], pinned by `SessionAuthTests.Idle_Expiry_Answers_Session_Expired_At_The_Deadline` (`tests/Identity.IntegrationTests/Sessions/Http/SessionAuthTests.cs:114`) and `ExpiryTests.A_Session_Past_Its_Idle_Deadline_Is_Expired` (`.../Store/ExpiryTests.cs:155`)); activity within the idle window slides `expires_at` (throttled write — at most one `last_seen_at` update per 60 s per session, so the deadline is measured from the LAST slide and lapses up to 60 s earlier than a per-request slide would allow; that is the AC2 trade-off and `ExpiryTests.Idle_Activity_Inside_The_Throttle_Window_Writes_Nothing` (`:32`) pins it) |

## 4. Data model and migrations

`session` (created by 02.3.1-T1; this story adds, in `migrations/NNNN_identity_session_hardening.sql`):

- `cookie_hmac bytea unique` + `pepper_version int` — the presented cookie value is never stored raw (T5 pattern).
- Indexes: `session_user_live_idx (user_id) where revoked_at is null` for the session list and every per-user path — it REPLACES the `(user_id, revoked_at, expires_at)` shape named here, so the sliding `expires_at` is in no index and a slide stays heap-only; the hot lookup is served by the FULL unique `session_cookie_hmac_key (cookie_hmac)`, NOT by the partial `(cookie_hmac) where revoked_at is null` this plan first named ([DECISION D-S85-D3]: a partial key serves live rows only, so a revoked or expired cookie would be indistinguishable from one never issued; `migrations/0045_identity_session_hardening.sql:224-229`).
- `absolute_expires_at timestamptz not null`, `expires_at` sliding; `rotated_from uuid` self-FK.
- Platform-scoped exception table (D12): no `org_id`, no org RLS; only the app role touches it, and only via session code paths.

## 6. States and transitions

`session`: `active → revoked` (`revoked_at` set — logout, user/admin revoke, member removal, rotation kills the predecessor) and `active → expired` (past `expires_at`/`absolute_expires_at`; no row update needed — expiry is derived, a daily sweeper may stamp it for reporting). No path back to `active`. Every transition writes an audit row (02.7.1) where an actor exists, except the self-service paths (logout, self revoke, revoke-all), which write a `security_event` row instead (D-S102-Q3 as changed by the owner 2026-10-27, 11.5.1-T5).

## 7. Jobs and integrations

- `session-cleanup` Cronos task (00 §5.3, unique `(schedule_name, fire_at)`): hard-deletes sessions expired > 30 days; stamps `expired_at` once on rows past their idle (`expires_at`) or absolute (`absolute_expires_at`) deadline (reporting only; no route reads it yet).
- `ISessions.Create/Rotate` consumed by 02.3.1 login; `ISessionRevocation` by 02.1.2-T3 and later by 02.8.1 grant expiry.
- Antiforgery filter registered once on the cookie-authenticated route group; bearer routes skip it (T38).

- **[DECISION D-S85-D1] the cookie is `__Host-evidgate_session`, `Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, `Max-Age` = the row's ABSOLUTE deadline.** The value scheme of 02.3.1-T1.4 is unchanged; the lifetime is absolute because the row — not the browser — slides, so a cookie that outlives its row costs one 401 while a cookie that dies early signs an active user out (`Sessions/Http/SessionCookieNames.cs:28,31,34,37`, `SessionCookieWriter.cs:49,98`).
- **[DECISION D-S85-D2] the outcome precedence is unknown → revoked → expired → disabled → active, each with its own code.** 401 `unauthenticated` / `session_revoked` / `session_expired`, 403 `account_disabled` for a non-active `user.status`, 503 `unavailable` when the store cannot answer (no pepper, database fault) — never a 401 that would sign a healthy user out. `SessionRequestAuthenticator.cs:114-126`, store mapping in `Sessions/SessionAuthenticationStore.cs:93-106,156-168`, errors `Sessions/SessionErrors.cs:25,34,43,54,78`, codes `src/BuildingBlocks/SharedKernel/Api/ErrorEnvelope.cs:300,307,314,320`.
