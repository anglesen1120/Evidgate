## 1. Goal and non-goals

**Goal.** The `__Host-` session cookie is an opaque reference to a server-side `session` row: `HttpOnly; Secure; SameSite=Lax`, rotated on login and on privilege change, idle (`expires_at`, sliding) and absolute (`absolute_expires_at`) expiry enforced, revocation effective on the very next request. Cookie-authenticated mutations pass the ASP.NET Core antiforgery pair (`XSRF-TOKEN` cookie / `X-XSRF-TOKEN` header). Users can list and revoke their own sessions; admins can revoke a member's.

**Non-goals.** Login protocol handlers (02.3.1); SAML session specifics (02.3.3 reuses this model); step-up re-authentication policy (09/11 — hook only); bearer-token clients (CLI/CI/agent are not cookie-authenticated, T38 — out of scope).

## 2. User stories and acceptance criteria

- As a user, I see all my sessions (device, IP, last activity) and can kill any of them — including "all but this one".
- As a `tenant_admin`, removing a member (02.1.2-T3) kills their sessions instantly.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Cookie attributes: `__Host-` prefix, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`; value is a ≥128-bit opaque random, stored only hashed (HMAC-SHA256 + `pepper_version`, T5 pattern) |
| AC2 | Idle expiry: a request after `expires_at` → 401 `session_expired`; activity within the idle window slides `expires_at` (throttled write — at most one `last_seen_at` update per 60 s per session) |
| AC3 | Absolute expiry: request after `absolute_expires_at` → 401 even with fresh activity |
| AC4 | `revoked_at` set → next request → 401 `session_revoked`, before any handler runs |
| AC5 | Cookie-authenticated `POST/PATCH/DELETE` without a matching `X-XSRF-TOKEN` → 403 `csrf_failed`; bearer-token requests are exempt (T38) |
| AC6 | `GET /v1/auth/sessions` lists the caller's sessions (current marked); `DELETE /v1/auth/sessions/{s}` revokes that row (self); `DELETE …/{s}` on another user's session → 404; admin revoke on member removal is immediate (02.1.2 AC3) |
| AC7 | Rotation: login and any role change issue a new session id (`rotated_from` points to the predecessor); the old cookie value is dead |
| AC8 | A logged-out session replayed with the old cookie → 401 (D9: revocation is a row state, not a key rotation) |

## 4. Data model and migrations

`session` (created by 02.3.1-T1; this story adds, in `migrations/NNNN_identity_session_hardening.sql`):

- `cookie_hmac bytea unique` + `pepper_version int` — the presented cookie value is never stored raw (T5 pattern).
- Indexes: `(user_id, revoked_at, expires_at)` for the session list; partial `(cookie_hmac) where revoked_at is null` for the hot lookup.
- `absolute_expires_at timestamptz not null`, `expires_at` sliding; `rotated_from uuid` self-FK.
- Platform-scoped exception table (D12): no `org_id`, no org RLS; only the app role touches it, and only via session code paths.

## 5. API shapes (commands, queries, endpoints)

| Command / Query | Endpoint | Permission | Codes |
|---|---|---|---|
| Session auth middleware (not a command): cookie → HMAC lookup → `session` row live check → set principal | all cookie-authenticated `/v1` routes | — | 401 `session_expired` / `session_revoked` / `unauthenticated` |
| `LogoutCommand` | `POST /v1/auth/logout` | session | 204; revokes current row |

`POST /v1/auth/logout`, `DELETE /v1/auth/sessions/{s}`, `POST …/revoke-all` require the XSRF header (AC5). `Idempotency-Key` not required (revocation is naturally idempotent).

## 6. States and transitions

`session`: `active → revoked` (`revoked_at` set — logout, user/admin revoke, member removal, rotation kills the predecessor) and `active → expired` (past `expires_at`/`absolute_expires_at`; no row update needed — expiry is derived, a daily sweeper may stamp it for reporting). No path back to `active`. Every transition writes an audit row (02.7.1) where an actor exists.

## 7. Jobs and integrations

- `session-cleanup` Cronos task (00 §5.3, unique `(schedule_name, fire_at)`): hard-deletes sessions expired > 30 days; stamps `expired` status on rows past absolute expiry (reporting only).
- `ISessions.Create/Rotate` consumed by 02.3.1 login; `ISessionRevocation` by 02.1.2-T3 and later by 02.8.1 grant expiry.
- Antiforgery filter registered once on the cookie-authenticated route group; bearer routes skip it (T38).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T38 / FR-02-5 / 00 §9.1 | cookie attributes exact; antiforgery pair enforced by endpoint filter on every cookie mutation | `CookieAttributeTests`, `XsrfTests.MissingHeader403` (AC1, AC5) |
| T5 | cookie secret ≥128-bit random, stored `HMAC-SHA256(pepper_vN, value)`; lookup constant-time | `SessionStoreTests.RawValueNeverPersisted` |
| D9 | server-side row → revocation is immediate, next request 401 | `RevocationTests.NextRequest401` (AC4) |
| S1 | session lookup is a parameterised Dapper call | S1 lint |
| P1/P3 | auth lookup = 1 statement on the `(cookie_hmac)` partial index per request; slide-write throttled to 1 update/60 s | `SessionAuthTests.SingleStatement`, statement counter |
| S3 | cookie values, UA strings never logged raw (UA truncated/hashed in logs) | `LogRedactionTests` |
| Privacy/PDPL | `ip` + `user_agent` are personal data — stored only on `session`, shown only to the owner, purged by `session-cleanup` | retention test + 11 rules |
| Retention/deletion impact | expired rows hard-deleted after 30 days; `user` survives for audit | — |

- **Authorization:** every session route needs an authenticated cookie session and resolves the user from it, never from the route; `DELETE /v1/auth/sessions/{s}` is limited to the row's owner or `membership:write` (admin on a member), and another user's id answers 404 (AC6).
- **Telemetry:** session-auth outcome counters by code (`session_expired`, `session_revoked`, `unauthenticated`, `csrf_failed`), revocation and rotation counters, and the slide-write throttle hit rate; no cookie value, user agent or IP in any metric attribute or log.
- **Failure path:** an expired, revoked or unknown cookie → 401 with its code before any handler runs; a missing or mismatched `X-XSRF-TOKEN` on a cookie mutation → 403 `csrf_failed`; another user's session id → 404; a revoked cookie replayed after logout stays 401 (AC4, AC8).

**Notes (hand-over from 02.3.1-T2 delivery, S81, 2026-10-25).**

- **T1.2 owns the XSRF enforcement of three routes that already declare it.** 02.3.1-T2 added the cookie-authenticated link mutations that reference `components/parameters/XsrfToken` (`contracts/openapi.yaml:373` on `POST /v1/auth/link/{provider}`, `:524` on `DELETE /v1/auth/link/pending`, `:592` on `POST /v1/auth/link/confirm`) and was out of scope for the filter, so `contracts/README.md` records that the header is required by contract and unenforced today. T1.2's validation filter must therefore cover `/v1/auth/link/*` together with the rest of the cookie mutations; `POST /v1/auth/invite-token` stays exempt, because it SETS a cookie rather than authenticating with one, and the routes' own `Origin` check is defence in depth on top of `SameSite=Lax`, not a substitute. Receiver row: STATUS §6 "`X-XSRF-TOKEN` is required by the contract on the three link mutations" (`STATUS.md:533`).
- **T1.1 inherits the `evidgate_resolve.session_user` lookup and two edge cases 02.3.1-T2 left open.** `migrations/0044_identity_login_linking.sql:194-212` is the read-only resolver the linking routes authenticate with (`src/Modules/Evidgate.Modules.Identity/Login/Linking/NpgsqlSessionUserReader.cs`): it resolves only an unrevoked session unexpired on BOTH clocks that belongs to an `active` user and writes nothing, so sliding expiry, rotation and revocation stay this task's writes. Two consequences are STATUS §6 rows with T1.1 as the receiver: a disabled account's link start answers 401 instead of 403 `account_disabled`, because the resolver filters inactive users (`STATUS.md:534`, [DECISION D-S81-M1]); and the staged `__Host-evidgate_link` confirm cookie has no server-side spent marker, so a replay converges on `already_linked` (`STATUS.md:535`, [DECISION D-S81-Q4]).
- **T1.1 also owns the session check `evidgate_resolve.login_link_identity` does not make (residual SEC2, 02.3.1-T2 S81 review).** The definer takes the target `p_user_id` from its caller and verifies no session of that user itself: `POST /v1/auth/link/confirm` resolves the acting user through `evidgate_resolve.session_user` first (`ISessionUserReader`) and then passes that id, so the only caller that could move an identity onto an arbitrary user is code already running as `evidgate_app` with an injection primitive. Defence in depth is to pass the session HMAC and pepper version INTO the function and let it resolve the target user itself, which is this task's credential-lifecycle work (same receiver as the `session_user` hand-over above); STATUS §6 row, notes this line.
