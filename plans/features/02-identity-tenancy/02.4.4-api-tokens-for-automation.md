## 1. Goal and non-goals

**Goal.** A project admin creates a long-lived but always-expiring bearer token (`evg_<prefix>_<secret>`) for scripts, dashboards and automation that only need read or limited automation calls (for example `run:read`, `decision:read`, `artifact:read`). The token is bound to one project, carries an explicit permission subset, can never hold more than its creator holds at creation time and can never hold an administrative permission. The plaintext is shown once; only prefix, `HMAC-SHA256(pepper_vN, secret)` and `pepper_version` are stored (T5, same approach as 02.4.2-T1). Authentication goes through the same permission evaluator as every other principal (02.2.1-T2), so a token has no private authorization path.

**Non-goals.** CI ingest (stays on 02.4.1 OIDC and 02.4.2 ingest tokens; an API token must not be exchangeable at `POST /v1/ci/token`); agent identity (02.5.1); user sessions (02.3.2); the web screen for token management (09.7.2 settings screens); per-token rate-limit tiers beyond the shared limiter (10.11.1); rotation with overlap (create-new then revoke-old is the V1 flow, `[INFERENCE]`).

## 2. User stories and acceptance criteria

- As a project admin, I create a read-only token for a dashboard that expires in 90 days, copy it once, and revoke it when the dashboard is retired.
- As a security reviewer, I know no API token can approve a release, manage members or roles, or exceed what its creator could do, even if the creator later gains more rights.
- As the owner, a database dump exposes no usable token.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/api-tokens` (`api_token:write`, `Idempotency-Key` required) with `{name, permissions[], expires_at}` returns the plaintext exactly once; the row stores `prefix` + `token_hmac` + `pepper_version`; list/get never return the secret or the HMAC |
| AC2 | `expires_at` is mandatory, in the future and at most the configured maximum lifetime (default 365 d ⚠️ product-set `[OPEN]`); a missing or out-of-range value returns 422 `schema_invalid` |
| AC3 | Creation is refused 403 `permission_escalation` when any requested permission is not held by the creator on that project; the check uses the creator's effective permissions at creation time |
| AC4 | Creation is refused 422 `forbidden_token_permission` for any permission in the deny set: `membership:*`, `role:*`, `organization:write`, `project:create`, `project:write`, `ci_binding:write`, `api_token:*`, `ingest_token:write`, `service_identity:*`, `sso:*`, `support:*`, `billing:*`, `healing:approve`, `healing:revoke`, `healing:configure`, `policy:write`, `artifact:read_sensitive`, `audit:read`, `security_event:read`, `webhook:write`; the deny set is data in `contracts/permissions.json` and covers every admin-flagged permission (generated test) |
| AC5 | Bearer `Authorization: Bearer evg_…` authenticates through the evaluator: only the token's stored permissions on its one project apply; a call to another project returns 403 `token_scope_mismatch` (404 for another org's object, per 02.9.1) |
| AC6 | An expired token returns 401 `token_expired`, a revoked token 401 `token_revoked` (effective on the next request, no cache), an unknown prefix or bad secret 401 `token_unknown`; failures are the uniform §9.2 envelope |
| AC7 | A permission the creator lost after creation is not usable: at use time the effective set is the intersection of the stored subset and the creator's current permissions on the project; a deactivated creator makes the token fail 401 `token_revoked` (`[INFERENCE]` fail closed) |
| AC8 | A pepper rotation keeps tokens on the previous `pepper_version` valid until the last such token expires, then they fail as unknown (T5) |
| AC9 | Audit rows (02.7.1) are written for `api_token.create`, `api_token.revoke`, and `api_token.use_denied` (permission denied, scope mismatch, expired/revoked use); successful use updates `last_used_at` (throttled to ≥ 60 s granularity) without an audit row per call |
| AC10 | An `evg_` token is refused on cookie-only surfaces, on `POST /v1/ci/token` and on every command whose handler declares a session-only attribute; it cannot call the token endpoints themselves (AC4 `api_token:*`) |

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `CreateApiToken : ICommand<CreateApiTokenResult>` | `POST /v1/projects/{p}/api-tokens` | `api_token:write` | 200 `{id, name, prefix, token (once), permissions, expires_at}` · 403 `permission_escalation` · 422 `forbidden_token_permission` / `schema_invalid` · 409 `idempotency_conflict` |
| Command | `RevokeApiToken : ICommand<Unit>` | `DELETE /v1/api-tokens/{t}` | `api_token:write` | 204 · 404 (foreign org or unknown) |
| Query | `ListApiTokens : IQuery<Page>` | `GET /v1/projects/{p}/api-tokens` | `api_token:read` | cursor page of `{id, name, prefix, permissions, status, expires_at, last_used_at, created_by}` |
| Auth | `ApiTokenAuthenticationHandler` | any `GET`/allowed command | evaluator over stored subset | 401 `token_unknown` / `token_expired` / `token_revoked` · 403 `token_scope_mismatch` / `permission_denied` |

Token form and verification as 02.4.2-T1: 32 random bytes, base64url secret, `HMAC-SHA256(pepper_vN, secret)`, `CryptographicOperations.FixedTimeEquals`. The prefix `evg_` lets secret scanners match leaked tokens (⚠️ registering the pattern with GitHub secret scanning is a follow-up, `[OPEN]` owner).

## 6. States and transitions

`active → revoked` (stored, `revoked_at`) · `active → expired` (computed from `expires_at`, no write). No un-revoke; a replacement is a new token. Each create/revoke writes one audit row in the same transaction.

## 7. Jobs and integrations

- No scheduled job: expiry is computed at verify time. A purge of long-expired rows follows the project retention sweep (`[INFERENCE]`, kept 90 days for audit joins, then deleted by the existing retention task; no new schedule).
- Authentication handler: prefix → `resolve_api_token` → open tenant scope from the resolved org/project → HMAC verify → load creator's current effective permissions (one query) → intersect → hand the principal to the evaluator. Cost target: one resolver call + one scoped read.
- Downstream: 09.7.2 renders create/list/revoke; 10.11.1 limiter keys on token id after authentication.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Self-escalation (02.2.1-T2) | creation refused for any permission the creator lacks; use-time intersection with the creator's current set | `Create_PermissionCreatorLacks_403`, `Use_CreatorLostPermission_Denied` |
| No admin permissions | deny set from `contracts/permissions.json` enforced at create and at use (stored rows are re-filtered, so a catalogue change tightens existing tokens) | `Create_AdminPermission_422`, `DenySet_CoversEveryAdminPermission` (generated) |
| T5 / D6 | ≥ 128-bit random, HMAC + `pepper_version`, constant-time compare, prefix lookup | `Verify_UsesConstantTimeCompare`, `Pepper_RotatedVersionStillVerifies` |
| 00 §5.7 S3 | plaintext only in the create response; logs carry `id`/`prefix` only; HMAC excluded from read models and exceptions | `ApiToken_NeverInLogsOrReadModels` (log-allowlist) |
| 00 §5.7 S2 / §5.5 C2 | handlers carry permission attributes; the bearer principal enters the same pipeline | architecture test (existing) + AC5 |
| T1 / T80 | pre-tenant resolver is `SECURITY DEFINER`, `search_path = ''`, audited | resolver test + 02.6.1-T2 lint |
| Uniform failure | unknown prefix and bad secret share one shape with a distinct code only where 02.4.2 already does | `Verify_Failures_UniformEnvelope` |
| 00 §5.7 P1/P3 | one resolver call + one scoped query for auth; no per-call audit write | command-counter assertion |

Authorization: `api_token:write` to create/revoke, `api_token:read` to list (`tenant_admin`); a token itself holds only its stored subset and never `api_token:*`.
Retention/deletion: token rows are tenant data kept while active and for the audit-join period after expiry, deleted with the project/org; revocation never deletes; plaintext is never stored.
Telemetry: audit rows `api_token.create`, `api_token.revoke`, `api_token.use_denied` (actor type `api_token`); counter `api_token_auth_total{outcome}` (no token or prefix label, S3); trace attribute `token.id`.
Failure path: invalid credential gives 401 with `token_unknown`/`token_expired`/`token_revoked`; a permission or scope miss gives 403; a creator mismatch fails closed; a lost token is fixed by revoke + create (runbook note in 10.7.1 for pepper loss: all tokens fail, recreate).
