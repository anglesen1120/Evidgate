## 1. Goal and non-goals

**Goal.** `POST /v1/ci/token` exchanges a GitHub Actions OIDC JWT for a short-lived `ci_producer` JWT scoped to exactly one project: signature via issuer JWKS, `iss`/`aud`/`exp`/`nbf` (≤ 60 s skew) validation, `jti` single-use via `ci_token_issue`, and a `ci_binding` match on the immutable `repository_id` + allowed `ref` patterns + allowed `job_workflow_ref`. Tenant resolution happens pre-tenant through `evidgate_resolve` (T1). A binding proves repository control before it can mint: it is created `pending_verification` with a one-time random challenge and becomes `active` only when an OIDC exchange from that repository presents it (`EVIDGATE_BINDING_CHALLENGE`, T70); at most one org may hold the `active` binding for a `repository_id` platform-wide. Admins manage bindings per project.

**Non-goals.** Non-GitHub ingest tokens (02.4.2); agent identities (02.5.1, V2); the producer-slot binding that consumes `jti`/`run_id` claims at ingest time (T9, owned by 04); the GitHub App / webhook path (03.4.1); UI (09.2.1).

## 2. User stories and acceptance criteria

- As a CI workflow author, I add `id-token: write` and exchange the OIDC JWT for a `ci_producer` token — no long-lived secret lives in my repo settings.
- As a `tenant_admin`, I bind repositories to projects and control which `ref`s and workflow files may mint tokens.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Happy path: workflow OIDC JWT (test JWKS, locally generated keypair) matching a bound `repository_id`, allowed `ref` and `job_workflow_ref` → 200 `{token, expires_at, project_id, permission_set}`; the token validates as `ci_producer` scoped to that project only |

## 3. Contracts touched

- 00 §9.3 `POST /v1/ci/token` — implemented; GitHub OIDC JWT branch (ingest-token branch lands in 02.4.2).
- `ci_producer` token format — new contract detail: our own JWT signed by the platform key via `Microsoft.IdentityModel.JsonWebTokens` (D7); `aud` = `evidgate`, `iss` = environment issuer; consumed by every ingest endpoint as a bearer credential.
- Permission strings used: `run:create`, `event:write`, `artifact:write`, `ci_binding:write` — seeded by 02.2.1-T1.
- Recorded 2026-10-03 (02.4.1 as delivered, Stage A):
  - **Migrations.** `0016` `ci_binding` (+ `resolve_ci_binding`), `0017` `ci_token_issue` (+ the T7 purge function), `0018` `ingest_token` (+ `resolve_ingest_token`).
  - **Resolver signature.** `resolve_ci_binding(provider, repository_id, challenge_hashes bytea[] default null)`: the third argument is additive. Several orgs may hold a pending binding for one repository, and only the proven challenge says which one is meant; an unproven pending binding is reported as one row `('pending_unproven')` with NULL ids, so the endpoint can answer `binding_pending` without naming a tenant. Priority: active, then the proven pending one, then the oldest disabled.
  - **Order of work.** The endpoint rate-limits (client address, then repository id), validates the OIDC token against the JWKS entirely outside any transaction (P6), resolves the binding pre-tenant, publishes tenant and a service principal, and only then lets the pipeline open the scope for `ExchangeGitHubTokenCommand`, a `[CredentialAuthenticated]` handler (third gate, closed by an architecture allowlist to the two exchange handlers).
  - **Token format.** The minted `ci_producer` is HS256 over `EVIDGATE:Ci:SigningKey` (D7) with the AC6 claims; `CiProducerAuthenticator` turns it back into a service caller (org, project and permissions from the claims; permissions must be inside the service-role ceiling).
  - **No `Idempotency-Key` on the secret-bearing creates.** `POST …/ci-bindings` returns the one-time challenge; the replay store persists response bodies, and a secret must never be stored (S3). A retried create answers 409 `binding_exists`.
  - **Rejections are not audited rows.** A refused exchange rolls back its transaction, so `token_replayed` / `binding_mismatch` rows and the `security_event` emission wait for 11.5.1 (OI-02-31); successes and the activation write `ci_token.exchange`.
  - **Rate limiter.** In-process fixed window per key (`ExchangeBurstLimit` per `ExchangeWindowSeconds`), 429 with `Retry-After`; a multi-node deployment gets a per-node limit until a shared limiter exists.
- Recorded — the task DAG gives T3 no explicit dependency on `02.6.1-T3` (which builds the `evidgate_resolve` ci-binding resolver); the exchange cannot run without it — a transitive need via the M1 plan, recorded here, not silently added.
- T88 — the minted `ci_producer` claims (`provider`, `repository_id`, `run_id`, `run_attempt`) are recorded verbatim on `ci_token_issue` and are the claims 05.2.1 copies into `run.ci_run_ref` at run create; 04.1.2 compares them with `producer_slot.bound_ci_run_ref` (T9).

## 4. Data model and migrations

`migrations/NNNN_identity_ci_binding.sql` + `NNNN_identity_ci_token_issue.sql`:

- `ci_binding`: `id uuid`, `org_id`, `project_id`, `provider text` (`github_actions`), `repository_id bigint` (immutable GitHub id), `repository_full_name text` (display only — D4), `allowed_ref_patterns text[]` (e.g. `refs/heads/main`, `refs/tags/v*`), `allowed_workflow_refs text[]` (`job_workflow_ref` allowlist incl. `.github/workflows/…`), `status text` (`pending_verification | active | disabled`, T70), `binding_challenge_hash bytea` (≥ 128-bit random challenge, shown once at create, stored HMAC-SHA256 per T5), `challenge_issued_at timestamptz`, `activated_at timestamptz`, `created_at`, `updated_at`, `version`. Constraints: `unique (org_id, id)` (T3), `unique (org_id, project_id, provider, repository_id)`, `unique (provider, repository_id) where status = 'active'` (T70 — at most one org holds the active binding for a repository platform-wide, so the resolver returns ≤ 1 row). Index `(provider, repository_id)` for the resolver lookup. RLS standard `org_id` policy (02.6.1-T1).
- `ci_token_issue`: `id uuid`, `org_id`, `project_id`, `jti text`, `repository_id`, `ref`, `sha`, `run_id`, `run_attempt`, `job_workflow_ref`, `expires_at`, `created_at`. Constraints: `unique (org_id, id)` (T3), `unique (jti)` — replay arbiter (FR-02-6). Index `(expires_at)` for the purge task. Retention: OIDC token lifetime + 10 min (T7).
- `evidgate_resolve.resolve_ci_binding(p_provider text, p_repository_id bigint)` → `(org_id, project_id, binding_id, status)` — shipped by 02.6.1-T3; challenge-aware (T70): returns the single `active` row, or a single `pending_verification` row when none is active so the exchange can attempt activation; never more than one row.

## 5. API shapes (commands, queries, endpoints)

| Command / Query | Endpoint | Permission | Codes |
|---|---|---|---|
| `CreateCiBindingCommand` / `UpdateCiBindingCommand` / `DisableCiBindingCommand` | `POST /v1/projects/{p}/ci-bindings`, `PATCH /v1/ci-bindings/{b}`, `DELETE /v1/ci-bindings/{b}` | `ci_binding:write` (`tenant_admin`) | create → 201 `{id, binding_challenge}` (challenge shown once, T70); 200/204; 404; 409 `binding_exists`; `Idempotency-Key`, `If-Match` |
| `ListCiBindingsQuery` (Dapper) | `GET /v1/projects/{p}/ci-bindings` | `ci_binding:write` or `project:read` (read of config) | 200 cursor page |
| `ExchangeCiTokenCommand` | `POST /v1/ci/token` | GitHub OIDC JWT (no session) | 200; 401 `token_invalid`/`token_replayed`; 403 `binding_mismatch`/`binding_pending`/`binding_disabled`; 409 `binding_conflict`; 429 `rate_limited` |

`ExchangeCiTokenCommand` flow (C8 errors, no `Idempotency-Key` — `jti` uniqueness is the natural idempotency, §4.2): validate JWT (T1 work) → `evidgate_resolve.resolve_ci_binding(p_provider => 'github_actions', p_repository_id => repository_id)` (pre-tenant, T1; `repository_id` is bigint) → open tenant scope → if the binding is `pending_verification`, the request body's `binding_challenge` must match `binding_challenge_hash` → set `status = 'active'` (the T70 partial unique rejects a second org's concurrent activation → 409 `binding_conflict`; its row stays `pending_verification` and both orgs' audit show it); a missing or wrong challenge → 403 `binding_pending` → check binding `active`, `ref` matches `allowed_ref_patterns`, `job_workflow_ref` ∈ `allowed_workflow_refs`, `repository_full_name` drift → audit warning (AC4) → insert `ci_token_issue` (`jti` unique — conflict ⇒ `token_replayed`; `provider`/`repository_id`/`run_id`/`run_attempt` recorded per T88) → mint `ci_producer` JWT (AC6 claims) → 200. All in one tenant tx; **no network call inside the tx** (JWKS fetch precedes it, P5).

## 6. States and transitions

`ci_binding`: `pending_verification → active → disabled` (T70, §8.9); `disabled` → exchanges return 403 `binding_disabled`; re-enable is a PATCH (audited, back to `active` — the challenge is not re-issued). `ci_token_issue` has no states — append-only replay cache rows purged by schedule. `ci_producer` is stateless (JWT); revocation is not offered in V1 (60 min TTL bounds exposure — recorded risk).

## 7. Jobs and integrations

- `ci-token-issue-purge` Cronos schedule (00 §5.3): daily task row with unique `(schedule_name, fire_at)` deletes `ci_token_issue` rows where `expires_at + interval '10 minutes' < now()` (T7).
- JWKS: cached `https://token.actions.githubusercontent.com/.well-known/jwks` with TTL + single-flight refresh on unknown `kid` (S4 allowlist, P6 resilience).
- Consumed by: `evidgate` CLI/adapter token exchange (04), `ci_producer` auth on ingest endpoints (04/05), audit writer (02.7.1).

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** the exchange is a pre-tenant path with no permission: the credential is the GitHub OIDC token, verified (signature, issuer, audience, lifetime, RS256 only) and matched to a binding by the immutable `repository_id`, `ref` and `job_workflow_ref`; the tenant is resolved only through `evidgate_resolve.resolve_ci_binding`. The binding admin routes need `ci_binding:write` (list: `project:read`). The minted `ci_producer` holds only `run:create`, `event:write`, `artifact:write` for one project and is checked by the same evaluator as every caller.
- **Telemetry:** the exchange runs in a module span; logs carry `binding_id`, `repository_id` and outcome codes, never a token, challenge or key. The JWKS fetch, rate-limit rejections and replay attempts are counted by outcome; `token_replayed`/`binding_mismatch` security events are emitted by 11.5.1 (OI-02-31).
- **Failure path:** an invalid token is 401 `token_invalid`, an unknown or unlisted repository/ref/workflow 403 `binding_mismatch`, a binding without proof 403 `binding_pending`, a disabled one 403 `binding_disabled`, a replayed `jti` 401 `token_replayed`, a rival activation 409 `binding_conflict`, a burst 429 with `Retry-After`; unreachable GitHub keys or an unconfigured signing key are 503 `unavailable` (retryable). Every refusal rolls the transaction back, so a refused exchange mints and records nothing.
