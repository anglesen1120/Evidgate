## 1. Goal and non-goals

**Goal.** A project on a non-GitHub CI (GitLab, Jenkins, local) gets a revocable, rotatable ingest token that exchanges at `POST /v1/ci/token` for the same short-lived `ci_producer` token GitHub OIDC produces. The secret is ≥ 128-bit random, shown once, stored only as `HMAC-SHA256(pepper_vN, secret)` + `pepper_version`, looked up by public prefix and compared in constant time (T5).

**Non-goals.** GitHub OIDC validation and `ci_producer` minting (02.4.1); pepper storage/rotation operations (secret store + runbook 10.7.1); the web token-management screen (09.7.1); per-token usage metering beyond `last_used_at` (12).

## 2. User stories and acceptance criteria

- As a tenant admin, I create an ingest token for my GitLab pipeline, see the plaintext once, and can rotate or revoke it without a support ticket.
- As a security reviewer, I know a database dump exposes no usable secret (HMAC + pepper) and a leaked token can be killed instantly.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/ingest-tokens` (`ingest_token:write`, `Idempotency-Key` required) returns the plaintext exactly once: the response body carries it, the row stores only `prefix` + `token_hmac` + `pepper_version`; a subsequent `GET`/list shows prefix and metadata, never the secret |
| AC2 | Exchange: `POST /v1/ci/token` with `{ "ingest_token": "…" }` resolves `(org_id, project_id, binding_id, status)` via `evidgate_resolve.resolve_ingest_token(prefix)` (T1), verifies the HMAC in constant time, and returns the standard `ci_producer` 200 body scoped to that project |
| AC3 | `POST /v1/ingest-tokens/{t}/rotate` mints a successor token; both old and new verify during the overlap window (24 h, DECISIONS §8.1 D-A5), after which the old token returns 401 `token_expired`; `rotated_to_id` links the pair |
| AC4 | `DELETE /v1/ingest-tokens/{t}` (revoke) sets `revoked_at`; the next exchange returns 401 `token_revoked`; revocation is effective immediately, no cache |
| AC5 | Verification failures are uniform: unknown prefix, bad secret, expired, revoked → 401 with distinct codes; a retired `pepper_version` verifies until its last token expires (T5) then fails like an unknown token |
| AC6 | A successful exchange updates `last_used_at` (throttled to ≥ 60 s granularity inside the same transaction — no extra write on the hot path) and writes an audit row `ingest_token.exchange` |

## 4. Data model and migrations

| Table | Columns / constraints |
|---|---|
| `ingest_token` | `id uuid pk`, `org_id uuid not null`, `project_id uuid not null`, `name text not null`, `prefix text not null` (first 12 chars of the public form `egt_<prefix>_<secret>`), `token_hmac bytea not null`, `pepper_version int not null`, `scopes text[] not null` (subset of `{event:write, artifact:write, run:create}`), `expires_at timestamptz`, `revoked_at timestamptz`, `rotated_to_id uuid`, `last_used_at timestamptz`, `created_by`, `created_at` · `unique (org_id, id)` (T3) · `unique (prefix)` · composite FK `(org_id, project_id)` → `project` · `check (revoked_at is null or rotated_to_id is null)` — a token is either rotated or revoked, not both · RLS `org_id = evidgate.current_org_id()` · index `(org_id, project_id)` for the token list (P4); `unique (prefix)` serves the resolver lookup |

Migration: `migrations/NNNN_identity_ingest_token.sql`. Pepper versions come from configuration (secret store reference), never the table.

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `CreateIngestToken : ICommand<CreateIngestTokenResult>` | `POST /v1/projects/{p}/ingest-tokens` | `ingest_token:write` | 200 `{id, name, prefix, token (once), expires_at}` · 422 `schema_invalid` · 409 `idempotency_conflict` |
| Command | `RotateIngestToken : ICommand<RotateResult>` | `POST /v1/ingest-tokens/{t}/rotate` | `ingest_token:write` | 200 `{id, token (once), overlap_ends_at}` · 404 foreign/revoked · 409 `token_revoked` |
| Command | `RevokeIngestToken : ICommand<Unit>` | `DELETE /v1/ingest-tokens/{t}` | `ingest_token:write` | 204 · 404 |
| Command | `ExchangeIngestToken : ICommand<CiTokenResult>` | `POST /v1/ci/token` (`grant_type=ingest_token`) | none — pre-tenant (resolver T1) | 200 standard `ci_producer` body · 401 `token_unknown` / `token_revoked` / `token_expired` |
| Query | `ListIngestTokens : IQuery<Page>` | `GET /v1/projects/{p}/ingest-tokens` | `ingest_token:read` | cursor page of `{id, name, prefix, status, last_used_at, expires_at}` — never `token_hmac` |

Secret generation: `RandomNumberGenerator.GetBytes(32)` (256-bit ≥ 128-bit), token `egt_<12-char-prefix>_<base64url-secret>`; verify = `HMAC-SHA256(pepper_vN, secret)` + `CryptographicOperations.FixedTimeEquals` against the stored `token_hmac`.

## 6. States and transitions

`active → rotated` (overlap: both old and new verify until `overlap_ends_at`, then old → `expired`) · `active → revoked` · `active → expired` (`expires_at` passed; no explicit transition write — expiry is computed, revocation is stored). Every transition writes an audit row (`ingest_token.create/rotate/revoke/exchange`) via the 02.7.1 writer.

## 7. Jobs and integrations

- **Overlap expiry sweep**: no dedicated job needed — `active` vs `expired` is computed at verify time from `overlap_ends_at`/`expires_at`; the token list shows the derived status.
- `evidgate_resolve.resolve_ingest_token(prefix)` (02.6.1-T3) returns `(org_id, project_id, binding_id, status)`; `status` distinguishes `unknown` / `revoked` / `expired` / `active` so the endpoint maps to the right 401 code without touching the table directly.
- Downstream consumers: 04's CLI `evidgate` accepts the token for non-GitHub flows; 09.7.1 renders create/rotate/revoke.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T5 / D6 | ≥128-bit random (256 used), `HMAC-SHA256(pepper_vN, secret)` + `pepper_version`, `FixedTimeEquals`, prefix lookup; pepper in secret store (10.7.1 runbook) | `Verify_UsesConstantTimeCompare` + AC5 |
| T1 / 00 §5.4.8 | exchange resolves tenant via `resolve_ingest_token` `SECURITY DEFINER`; app role never scans `ingest_token` unscoped | AC2 + resolver audit stub |
| 00 §5.5 C2 | create/rotate/revoke run the full pipeline; exchange skips authorization (pre-tenant) but still opens the resolved scope before minting | pipeline tests |
| 00 §5.7 S3 | plaintext returned once in the response only; never logged, never stored; logs carry `id`/`prefix` only; `token_hmac` excluded from every read model | log-allowlist test; AC1 |
| 00 §5.7 S2 | `ingest_token:write` on mutations; `ingest_token:read` on list — declared in `permissions.json` | 403 tests |
| 00 §5.7 P1/P3 | exchange = 1 resolver call + 1 scoped verify + optional throttled `last_used_at` update in the same tx; single round trip after resolve | command-counter assertion in exchange test |
| Privacy/retention | `name`, `created_by`, `last_used_at` are tenant data deleted with the org; no personal content beyond admin ids | — |

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** create, rotate and revoke need `ingest_token:write`, the list `ingest_token:read` (C2 stage). The exchange is pre-tenant: the public prefix is resolved by `evidgate_resolve.resolve_ingest_token`, then the secret is verified in constant time against `HMAC-SHA256(pepper_vN, secret)` inside the resolved tenant; the minted token carries only the token's scopes, inside the service-role ceiling.
- **Retention/deletion:** token rows are tenant configuration kept until revoked and the org is deleted; only the prefix and the HMAC are stored, never the secret, so a retained or exported row exposes nothing usable. `last_used_at` is rewritten at most once a minute.
- **Telemetry:** logs and audit rows carry the token id and prefix only (never the secret, HMAC or full token); the audit trail records create, rotate, revoke and every exchange with the exchanging token as the `ci_producer` actor.
- **Failure path:** unknown prefix and wrong secret are the same 401 `token_unknown` (a retired pepper version fails the same way), `token_revoked` and `token_expired` are distinct 401s, a burst is 429 with `Retry-After`, an unconfigured pepper is 503 `unavailable`; a refused exchange changes nothing.
