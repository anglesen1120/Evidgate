## 1. Goal and non-goals

**Goal.** `membership` and `membership_role` make a user a member of an org with roles; the invite flow creates a pending membership bound to an email address that activates only when the invite's **single-use secret** is presented (`evidgate_resolve.invite_by_secret`, T75) **and** a login arrives with a provider-verified matching email — email alone never binds except under the org's explicit opt-in for verified Google Workspace domains; member removal revokes sessions immediately; the last `tenant_admin` can never be removed.

**Non-goals.** The login flows themselves and `user`/`user_identity` (02.3.1); the `session` table and cookie mechanics (02.3.2) — this story calls the revocation contract; support grants (02.8.1); the members UI (09.7.1); SCIM/directory sync (out of V1).

## 2. User stories and acceptance criteria

- As a `tenant_admin`, I invite a colleague by email, and they become a member when they present the invite secret at login — only if the provider also reports that exact email as verified (T75).
- As a `tenant_admin`, removing a member ends their access immediately, including live sessions.
- As the platform, I never let an org remove or demote its last `tenant_admin`.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/orgs/{o}/memberships` with `email` creates a `pending` membership; a second invite for the same email in the same org → 409 `invite_exists` |
| AC2 | On login (02.3.1-T2 calls `BindPendingMemberships`), a pending membership activates only when the single-use invite secret resolves the row **and** the provider-verified email equals `invited_email` (T75); a login with a different or unverified email — or no secret — leaves it `pending` and yields 403 `no_membership` |
| AC3 | `DELETE …/memberships/{m}` sets `status = removed` and revokes all sessions of that user in the same transaction → next request with the old cookie → 401 |
| AC4 | Removing or demoting the last active `tenant_admin` → 409 `last_admin`; the org keeps at least one |
| AC5 | `POST …/{m}/roles` / `DELETE …/{m}/roles/{r}` change the member's permission set per-project on the next request (no permission cache) |
| AC6 | Invite resend keeps the same membership row (`idempotent` by `(org_id, invited_email)`); cancel sets `pending → revoked` and the invite can never bind afterwards |

### 3a. Recorded when 02.1.2-T1 shipped (2026-09-27)

Recorded deviations and deferrals of the schema/API task — none changes a 00 contract (the §9.3 rows it added are logged in 00 §15):

- **`membership_role.role_id` carries no declarative foreign key.** The composite `(org_id, role_id)` → `role (org_id, id)` written in §4 is not declarable: 0010 seeds every built-in role with `org_id IS NULL`, so that key could never match one — and the creator's `tenant_admin` (T98) and AC4's protected role are both built-ins — while a single-column key to `role` is refused structurally by 02.9.1-T2's composite-FK rule for any tenant table. `role_id` therefore references `role.id` by value, resolved under RLS by `GrantRoleCommand` (409 `unknown_role`); reasoning in `migrations/0011_identity_membership.sql`'s header and 00 §15.
- **`invited_email` is `text`, not `citext`.** The extension is not installed in this database and the isolation suite's auto-discovered row generator (02.9.1-T2) has no `citext` value rule, so a NOT NULL `citext` column would fail that gate for a reason unrelated to isolation. Normalisation is therefore enforced twice in the API/DB: `InviteEmail.Normalize` (trim + lowercase, ASCII-only shape so it agrees with PostgreSQL `lower()`) and the migration's `invited_email = lower(invited_email)` check.
- **`user_id` carries no foreign key** — there is no `user` table in this build (02.3.1); the column is an unconstrained uuid until then, exactly as §4 records.
- **`ISessionRevocation` is defined but not called.** The interface is exported (T1.3); 02.1.2-T3.2 wires `RevokeAllForUserAsync` into `RemoveMember`/`UpdateMembership` in the same transaction, and the `session` table behind it is 02.3.2-T1's. AC3's revocation is therefore **not** implemented by T1 — the removal path keeps no stub.
- **`UpdateMembership` changes `status` only.** §4's table has no display column (a display name belongs to `user`, 02.3.1), so the `PATCH` route performs `active → removed` (the disable path) and refuses anything else (409 `invalid_transition`); the §5 "(display/status)" wording is settled as status-only.
- **`invite_secret_prefix`, `invite_token_hash` and `invite_expires_at` are nullable in 0011** and stay NULL until 02.1.2-T2 mints the token; `unique (invite_secret_prefix)` still holds, because PostgreSQL treats NULLs as distinct.
- **`429 quota_exceeded` is not reachable from T1**: it needs 02.1.1-T3's `max_seats` column and its limit owner; the invite path has no seat check yet, which §5 already assigns to 02.1.2-T2.3.
- **`organization.invite_autobind_verified_domain` (AC8) is not added** — it is 02.1.2-T2.2's and 02.1.1's schema surface, and AC8 is T2's end-to-end; adding a column now with no reader would be dead schema.
- **`ResendInvite`, `CancelInvite`, `BindPendingMemberships` and the invite-expiry sweep remain 02.1.2-T2's**; the routes and states they need (partial unique on the pending address, `revoked`/`expired`, `invite_secret_prefix`) exist in 0011.

### 3b. Recorded when the wave-7 security review shipped (2026-09-27)

The two membership write routes gained one refusal each, both from the W7 security review; no contract row, DTO or response code changed (403 `forbidden` and 409 `unknown_role` are already on both routes), and no new error code was invented:

- **`GrantRole`/`InviteMember` resolve `member`-kind roles only (W7-SEC-03).** `role.kind` (0010) records who may hold a role: `member` for the five roles of 00 §2 and every custom role, `service` (`ci_producer`, `agent`) and `staff` (`platform_operator`, `billing_operator`) for identities that are not memberships. A role of another kind is visible to the tenant (the catalogue read policy is `org_id is null or …`) but is refused with the existing 409 `unknown_role`, exactly like an invisible id; the evaluator's member join additionally requires `r.kind = 'member'`, so a hand-written `membership_role` row cannot grant a staff code either. Before this, a `tenant_admin` could attach `platform_operator` (`support:read`) to a human, because the T79 `tenant_assignable` filter removes non-assignable codes and `support:read` is assignable.
- **[DECISION] Self-grant is blocked (W7-SEC-02, rationale 00 §2).** 00 §2's `tenant_admin` row is "secret values are never readable: no `artifact:read_sensitive` and no `billing:*`", yet `tenant_admin` holds `membership:write` and every built-in role that carries a sensitive code is grantable — so the role strings were a one-step escalation for the very role that row bounds. The rule: **a caller may hand out only permissions it already holds.** On these routes it applies when the target is the caller's own membership — its `user_id`, or its `invited_email` (normalised on both sides, §3a) — on both routes, so a `GrantRole` onto a pending row addressed to the caller is refused like the invite that would have carried the role (one shared `SelfEscalation.IsSelfTargetAsync` definition; pre-merge review of PR #12) — since a pending row's address is the only handle it has before a login binds it — and it answers 403 `forbidden`, the code both routes already document. The caller's set is resolved by the module's evaluator (`ICallerPermissionSet`, one statement over the same `membership_role → role → role_permission → permission` join as the per-permission verdict, so the set checked and the set the next request is evaluated with cannot diverge); a resolution that finds no active membership yields the empty set and refuses the grant rather than trusting it. A grant to **another** member is deliberately not covered: delegation stays, and 02.2.1 §3b records the same decision for the custom-role commands.
- **[OPEN] (owner): does the stricter *grantor-subset* rule apply to grants to other members?** Under it a `tenant_admin` could not appoint a `release_approver` at all (it holds neither `policy:write` nor `artifact:read_sensitive`), which would make approval pairs staffable only by an existing approver — or by the org creator, who holds both roles (T98). The shipped behaviour is delegation-permitted; tightening it changes who can staff an approval pair, so it is an owner call, not a code one. Recorded here and in 02.2.1 §3b.
- **Shipped tests.** `MembershipEndpointTests.Staff_And_Service_Roles_Cannot_Be_Granted_Or_Invited` (409 `unknown_role` on both routes, no row), `Tenant_Admin_Cannot_Grant_Release_Approver_To_Itself` (403, no `membership_role` row), `Tenant_Admin_May_Still_Grant_Release_Approver_To_Another_Member` (delegation, through the real evaluator with a seeded `tenant_admin`), `Inviting_The_Callers_Own_Address_To_A_Role_They_Do_Not_Hold_Is_403` (the invite half, no membership written), and `EvaluatorTests.Staff_Role_Attached_To_A_Membership_Grants_Nothing` (the read-time half of the kind rule).

## 4. Data model and migrations

`migrations/0011_identity_membership.sql` (**shipped**; the number is fixed):

`membership`: `id uuid`, `org_id uuid not null` → FK `(org_id)` → `organization(id)`, `user_id uuid null` (null while pending, **no FK**: no `user` table exists yet, §3a), `invited_email text not null` (**text**, not `citext` — §3a; stored normalised, enforced by a check constraint), `status text not null default 'pending'` (`pending|active|removed`, plus `revoked|expired` reachable only from `pending`), `invited_by uuid`, `invite_secret_prefix text null` (public lookup key for `invite_by_secret`, T75; NULL until T2), `invite_token_hash bytea null` (HMAC-SHA256 of the invite link secret, T5 pattern), `invite_expires_at timestamptz null`, `created_at`, `updated_at`, `version`. Constraints: `unique (org_id, id)` (T3), `unique (org_id, user_id)` where `user_id is not null`, partial unique `(org_id, invited_email) where status = 'pending'` (AC1), `unique (invite_secret_prefix)`. Indexes: `(org_id, status, created_at, id)` (the "active members of this org" path, §8 P3) and `(org_id, created_at, id)` (the documented 00 §9.1 keyset page, which has no status predicate and cannot use a status-leading index).

`membership_role`: `id uuid`, `org_id`, `membership_id`, `role_id`, `granted_by`, `granted_at`, `created_at`, `updated_at`, `version`; `unique (org_id, id)`, `unique (membership_id, role_id)`; composite FK `(org_id, membership_id)` → `membership(org_id,id)` — the key AC7 rests on. **`role_id` is a by-value reference, not a foreign key** (§3a): the composite `(org_id, role_id)` → `role(org_id,id)` this section originally asked for cannot match a built-in role (`org_id IS NULL`), and the single-column form is refused by the 02.9.1-T2 gate.
`organization` gains `invite_autobind_verified_domain boolean not null default false` (per-org opt-in for email-only auto-bind on DNS-verified Google Workspace domains, T75) — **not added by T1**; it is 02.1.2-T2.2's and 02.1.1's schema surface, and AC8 is T2's (§3a).

RLS: `ENABLE` + `FORCE` on both tables, the `org_id = evidgate.current_org_id()` tenant policy and the permissive owner policy, exactly as 0004/0005 (02.6.1-T1's helper; 0011 ships both).

## 6. States and transitions

`membership.status`: `pending → active` (invite secret + first verified-email login via `BindPendingMemberships`, or opt-in auto-bind, T75), `pending → revoked` (cancel), `pending → expired` (past `invite_expires_at`, swept daily by a `task` queue row — Cronos schedule `invite-expiry`, unique `(schedule_name, fire_at)`, 00 §5.3), `active → removed` (admin delete). `removed` is terminal; re-invite creates a new row once no `pending` row exists (partial unique allows it). Every transition writes an audit row via 02.7.1.

## 7. Jobs and integrations

- `invite-expiry` scheduled task (Cronos, e.g. hourly): `UPDATE membership SET status='expired' … WHERE status='pending' AND invite_expires_at < now()`; idempotent by the unique fire key.
- `BindPendingMemberships` is invoked inside the login transaction of 02.3.1-T2 (no outbox — binding must be atomic with the first session).
- `ISessionRevocation` (02.3.2-T1 contract) called synchronously on removal/disable (AC3).

**DoR review answers** (11.1.1-T2 / `plans/features/README.md` §6 — the four questions, answered for this story's shipped slice):

- **Authorization:** every handler carries `[Permission]` — `membership:read` on the two queries, `membership:write` on the five commands — checked by the C2 stage 4, which denies by default and never sees the URL's org (the tenant is the principal's; a `{o}` that is not the request tenant is 404). Another org's membership id is 404 through RLS and the composite tenant key (AC7), and the org's last active `tenant_admin` cannot be removed or demoted (409 `last_admin`, AC4).
- **Retention/deletion:** there is no hard delete on the membership path — `removed` is a soft delete kept as audit history, and only `membership_role` grants are deleted; `invited_email` is personal data, stored minimised (normalised, never logged, no provider profile copy) and purged with the org (T16); pending invites expire rather than accumulate, and the invite token columns stay NULL until 02.1.2-T2 mints a token that only ever travels in the notification email.
- **Telemetry:** a module activity span per command/query (`StartModuleActivity(ModuleName.Identity, …)`); the story's counters are invite/removal counts and `last_admin` rejections (02.1.2 §11); no email, invite secret, prefix or token hash is ever a log field, span attribute or metric label (00 §5.7 S3).
- **Failure path:** every refusal is a 00 §9.2 `Result`/`Error` value — 404 `not_found`, 409 `invite_exists`/`last_admin`/`unknown_role`/`invalid_transition`, 412 `precondition_failed`, 422 `request_invalid` from the validator before the tenant transaction opens — never an exception for an expected conflict; the C2 tenant transaction rolls the whole change back on a failure, so no partial invite or role grant can survive.
