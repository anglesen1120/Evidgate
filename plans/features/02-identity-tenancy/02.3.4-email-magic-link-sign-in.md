## 1. Goal and non-goals

**Goal.** A person who already has an active membership enters their email address, receives a single-use link valid for at most 15 minutes, opens it **in the browser that asked for it**, confirms, and lands in the same session model as an OIDC login (02.3.2): same `__Host-` cookie, rotation, idle/absolute expiry, revocation and audit. The mechanism never reveals whether an address is known, stores only hashes, and never creates an account, an identity or a membership.

**Non-goals.**

- Creating users, binding or accepting pending invites, linking identities (02.1.2, 02.3.1-T2): a magic link signs in an existing member only. Invite binding by magic link is out of scope (OI-02-41).
- Passwords, one-time codes typed by the user, passkeys, MFA/step-up (11 hook only).
- Session lifecycle (02.3.2), the notification outbox and bounce/suppression handling (02.10.1-T2/T3), the org-settings screen that exposes the `magic_link_enabled` switch (09).
- SAML (02.3.3, G4).

## 2. User stories and acceptance criteria

- As a member without Google or Microsoft sign-in, I type my email, open the mail in the same browser and I am signed in without a password.
- As an attacker enumerating addresses, I cannot tell a member from a stranger by response body, status, headers, cookies or timing.
- As a `tenant_admin`, I can switch magic-link sign-in off for my org.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/auth/magic-link/request {email}` answers an identical `202` (same body, headers and `Set-Cookie` shape) for: a member, an unknown address, a disabled user, a user with no active membership, an address shared by two users, and a per-email throttled request. Only a malformed address is a `422 request_invalid`. A timing test (median over ≥ 200 samples) shows no distinguishable difference between member and unknown address; the mail send never runs inside the request |
| AC2 | An eligible request (user `active`, ≥ 1 active membership in an active org with `magic_link_enabled`) produces exactly one mail through `IEmailSender`; the link carries a ≥ 256-bit random token in the URL **fragment** (never path or query), `expires_at ≤ created_at + 15 min` (DB `check`), single use |
| AC3 | Only `HMAC-SHA256(pepper_vN, value)` + `pepper_version` of the token and of the browser secret are stored; neither value, nor the link, appears in the database, logs, traces, metrics, audit rows or the notification tables |
| AC4 | `POST /v1/auth/magic-link/verify {token}` with the matching `__Host-evidgate_magic` cookie, before expiry and unconsumed → one `session` row, `__Host-evidgate_session` cookie set, magic cookie deleted, one `auth.login` row per active admitting org (`provider = email`), `ILoginCompletion` seam reused |
| AC5 | A missing or different browser cookie (link opened on another device, in a mail app's in-app browser, or by an attacker holding the link) → `401 token_invalid`, the challenge is **not** consumed and `failed_attempts` increments; the 5th failure kills the challenge. Unknown, expired, consumed and killed tokens answer the same `401 token_invalid` body |
| AC6 | Two concurrent verifies of one valid link yield exactly one session; the loser gets `401 token_invalid` (consume is one `UPDATE … WHERE consumed_at IS NULL AND expires_at > now() RETURNING`) |
| AC7 | Limits (defaults, config): per email 3 requests / 15 min counted on `HMAC(email)` for known **and** unknown addresses; per IP 10 requests and 20 verifies / 15 min. Per-email overrun is a silent `202` with no mail; per-IP overrun is `429 rate_limited` + `Retry-After` and reveals nothing about any address |
| AC8 | Membership or status is re-read at verify: user disabled → `403 account_disabled`; no active admitting org left → `403 no_membership`; in both the challenge is consumed and no cookie is set |
| AC9 | A magic-link sign-in creates no `user`, `user_identity` or `membership` row and binds no pending invite; an org with `magic_link_enabled = false` is never part of the admitted set (a user whose every org disabled it gets the AC1 generic `202` at request and `403 no_membership` if a link existed before the switch) |
| AC10 | `PATCH /v1/orgs/{o}` accepts `magic_link_enabled` only with `organization:write`, `If-Match` and `X-XSRF-TOKEN`; the change is audited (`organization.updated`, field name only); another org's value is never readable |
| AC11 | Web: request form, "check your inbox" and confirmation screens exist in vi and en, are keyboard-operable with visible focus, show the wrong-browser recovery message with a "send a new link" action, read the fragment once and remove it from the address bar and history (`history.replaceState`), and never place the token in a URL path or query |
| AC12 | Delivery failure (provider 5xx, timeout) never changes the response (still `202`), never retries with the secret persisted, increments a failure counter, and the user can request again after the throttle window |

## 3. Contracts touched

- New contract routes `POST /v1/auth/magic-link/request` and `POST /v1/auth/magic-link/verify` (anonymous, browser surface like `/v1/auth/invite-token`): `x-permission: none`, `security: []`, `Idempotency-Key` exemption (a replay is harmless: per-email throttle and single use), body bounded at 2 KiB, `application/json` required (a cross-site form post is a 422, as for the invite-token route), `Origin` must equal the app origin; added to `check-contract-conventions.mjs` EXPECTED rows, `contracts/README.md` browser-surface list, SDK regeneration, `apps/web/src/app/core/telemetry/api-path-template.ts`.
- Error codes: reuse `token_invalid` (401), `no_membership` and `account_disabled` (403), `rate_limited` (429, new only if absent from 00 §9.2 — verify at DoR), `request_invalid` (422).
- `organization.magic_link_enabled boolean not null default true` (expand-only) and its `PATCH /v1/orgs/{o}` member (`UpdateOrganizationRequest`).
- Platform-scoped exception list gains `magic_link_challenge` and `magic_link_throttle` (area plan D12/§4.5, `contracts/rls-exceptions.txt`, `scripts/check-rls.py`).
- New secret `EVIDGATE__MAGICLINK__PEPPER` (+ `__PEPPERVERSION`): `SecretNames`, config-matrix `secret: true` rows, resolved through `ISecretProvider` in an `IPostConfigureOptions` (precedent `SessionSecrets`, `CiSecrets`). A missing pepper answers the request route `503 unavailable`, never a weaker mode.
- Consumes `ISessions.CreateAsync`, `IMemberOrgResolver.MemberOrgsAsync`, `IIdentityAuditWriter`, the Data Protection cookie pattern of `InviteTokenCookie`, and `IEmailSender` (02.10.1-T2.3). It does **not** use the 02.10.1 `notification` table (§7).

## 4. Data model and migrations

`migrations/NNNN_identity_magic_link.sql` (expand-only; number assigned by the coordinator), platform scope, `ENABLE` + `FORCE ROW LEVEL SECURITY` with the owner-only policy and **no** `GRANT` to `evidgate_app` (0041 precedent); access through `SECURITY DEFINER` resolvers in `evidgate_resolve` (`EXECUTE` only):

- `magic_link_challenge`: `id uuid pk`, `user_id uuid not null → "user"(id)`, `token_hmac bytea not null` (32 bytes, `unique`), `browser_hmac bytea not null` (32 bytes), `pepper_version int not null check (>= 1)`, `created_at`, `expires_at timestamptz not null check (expires_at <= created_at + interval '15 minutes')`, `consumed_at timestamptz null`, `failed_attempts smallint not null default 0 check (between 0 and 5)`, `requested_ip inet null`. Index `(user_id, created_at)` for the sweep; challenges of one user older than the newest 3 are consumed at issue (a new link kills older ones).
- `magic_link_throttle`: `email_hmac bytea pk` (32 bytes), `window_started_at`, `attempts int` — one upsert per request: `insert … on conflict do update set attempts = case when window expired then 1 else attempts + 1 end … returning attempts`.
- `organization.magic_link_enabled boolean not null default true` ([DECISION] default, see OI-02-42).
- Resolvers: `evidgate_resolve.magic_link_issue(email_hmac, token_hmac, browser_hmac, pepper_version, ip, normalised_email, now, limits…)` (one statement path for known/unknown: counts the throttle, resolves the single eligible user, inserts the challenge only when eligible and within the limit, returns `{send: bool, user_id, locale}` — the same cost for both); `evidgate_resolve.magic_link_consume(token_hmac, browser_hmac, now)` returns `consumed | wrong_browser | gone`. Both carry `DEFINER_AUDIT_EXEMPT` entries like the 0042 resolvers (audit rows are written by the application per active org).
- Sweep: the existing `session-cleanup` job (02.3.2-T2) gains one statement deleting challenges consumed or expired for > 24 h and throttle rows older than 24 h.

## 5. API shapes (commands, queries, endpoints)

| Route | Handler | Notes |
|---|---|---|
| `POST /v1/auth/magic-link/request` | `RequestMagicLinkCommand` (pre-tenant, direct handler like `CompleteLoginCommand`, [DECISION D-S75-Q2] precedent) | normalise email (NFKC, lower-case, trim, exactly one `@`, reject quotes, commas and control chars, max 254 — Auth.js precedent); always sets a fresh `__Host-evidgate_magic` cookie (random 256-bit, `HttpOnly; Secure; SameSite=Lax; Path=/`, 15 min) and answers `202 {}`; the mail is handed to a bounded in-memory dispatcher after the response |
| `POST /v1/auth/magic-link/verify` | `VerifyMagicLinkCommand` + `ILoginCompletion` seam | needs the cookie and `{token}`; consume → membership/org/status re-check → `auth.login` per active org → `ISessions.CreateAsync` → session cookie; always deletes the magic cookie |
| `PATCH /v1/orgs/{o}` | existing `UpdateOrganizationCommand` | gains `magic_link_enabled`; `organization:write`, `If-Match`, audited |

The link is `{EVIDGATE__LOGIN__PUBLICBASEURL}/sign-in/magic#t=<base64url token>`. The web page reads the fragment, POSTs it, then clears it. A GET of that page never changes state, so mail scanners and link previewers that fetch the URL cannot consume the challenge (and they never see the fragment).

## 6. States and transitions

`challenge`: `issued → consumed` (verify with the matching browser) · `issued → expired` (`expires_at`) · `issued → killed` (5 failed verifies, or a newer link for the same user beyond 3 live). Terminal states are immutable and every transition except `expired` is application-audited where an org exists. A `consumed` challenge never reopens; replay is `401 token_invalid`.

Eligibility at request: `user.status = 'active'` **and** exactly one `user` row has that normalised address **and** `member_orgs` yields ≥ 1 active org with `magic_link_enabled`. Two users with the same address (D3 allows it) make the address ineligible; nothing is sent and the `ambiguous` counter increments. At verify the same checks run again (AC8).

## 7. Jobs and integrations

- **Mail.** `IEmailSender.SendAsync` (02.10.1-T2.3) is called directly from a bounded in-memory dispatcher, not through the 02.10.1 outbox: that pipeline is org-scoped, persists rendered rows and states that no email contains a secret, while a magic-link mail is pre-tenant and its only content is the secret. Consequences: no `notification` row, no stored link, no retry after a restart (the user asks again), no suppression read in G2 (bounces and complaints belong to 02.10.1-T3; the per-email throttle bounds repeat mail). T2.1 first checks that the `IEmailSender` contract accepts a pre-rendered message, never logs the body or recipient, and carries no delivery-tracking pixel or click rewriting; if it does not, T2.1 amends 02.10.1-T2.3's file by one line, it does not fork the sender.
- Templates vi/en (subject, text, HTML): link, "valid 15 minutes, single use, open it in the same browser", "ignore if you did not ask", product name. No org name, no IP/UA, no test data. Locale: the user's `preferred_locale`, else the request's `Accept-Language` (vi default) [INFERENCE].
- Outbound: only the email provider host(s) 02.10.1-T1 selects (S4 allowlist, no redirects).
- Per-IP limiter: a dedicated instance (not the CI exchange pool, 02.3.1 T1.2 hand-over vii); honest client IP needs forwarded headers (receiver 10.1.1-T3, same dependency as the login limiter).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| OWASP enumeration (Authentication cheat sheet: generic response, no timing discrepancy) | identical `202`, cookie always set, mail off the request path, one resolver path for known and unknown addresses | `EnumerationTests.*` (AC1) incl. timing |
| Token strength and storage (T5) | 256-bit CSPRNG token and browser secret; only `HMAC-SHA256(pepper_vN, …)` + version stored; constant-time compare in the resolver (`unique` lookup by HMAC) | `StorageShapeTests`, schema review (AC3) |
| Single use, short life | `consume` is one conditional `UPDATE … RETURNING`; DB `check` caps `expires_at`; newer link kills older | `ConsumeTests.Concurrent*`, `ExpiryTests.*` (AC2, AC6) |
| Login CSRF / link theft | browser-bound cookie (`__Host-`, HttpOnly); `application/json` + `Origin` check; a stolen link is useless without the cookie | `WrongBrowserTests.*`, `ContentTypeTests.*` (AC5) |
| Mail scanners / previews | fragment token, GET never consumes | `FragmentTests` (web unit) (AC11) |
| Brute force | 256-bit token makes guessing moot; 5 failed verifies kill a challenge; per-IP verify limit | `VerifyThrottleTests.*` (AC5, AC7) |
| Mailbomb / abuse | per-email DB throttle (3 / 15 min) on `HMAC(email)`, per-IP limiter, one mail per request, no org-controlled text in the mail | `ThrottleTests.*` (AC7) |
| Privacy/PDPL | the address is HMACed in the throttle, absent from logs and metric labels; `requested_ip` kept ≤ 24 h; audit rows carry `provider = email` only | `LogRedactionTests.MagicLink*`, `AuditMetadataTests` (AC3) |
| Tenant isolation | pre-tenant tables hold no tenant data; org admission uses `member_orgs` + `magic_link_enabled`; the PATCH is org-scoped | `ResolverTests` rows, `OrgSwitchTests.*` (AC9, AC10) |
| Performance | one resolver call per request; throttle upsert on a pk; challenge lookup on a unique key | query-plan check in `ConsumeTests` |

**DoR review answers** (00 §12, `plans/features/README.md` §6):

- **Authorization:** both routes are pre-tenant and need no permission; admission is the same gate as OIDC login (active user, active membership, active org) plus the per-org `magic_link_enabled` switch, re-read at verify (AC8, AC9). `magic_link_enabled` is writable only by `organization:write` through `PATCH /v1/orgs/{o}`; the two new tables have no `GRANT` to `evidgate_app` and are reachable only through definers.
- **Retention/deletion:** challenges and throttle rows are deleted 24 h after expiry/consumption by the session-cleanup sweep; no address is stored in either table; user erasure (11.9.2) removes the user's challenges by FK cascade, and audit rows keep no address.
- **Telemetry:** counters `magic_link_requests{outcome=accepted|throttled_ip|invalid}`, `magic_link_mail{result=sent|failed|dropped}`, `magic_link_verify{outcome=ok|wrong_browser|gone|no_membership|disabled}`, `magic_link_ambiguous`; latency histogram on request; never labelled with an address, token, user id or IP; `auth.login` rows (per active org) and `auth.magic_link_requested` rows (eligible requests only, per active org, no address).
- **Failure path:** invalid address → 422; unknown, ineligible and per-email throttled → the same 202; per-IP overrun → 429 `Retry-After`; unusable token or wrong browser → 401 `token_invalid`; membership/status lost → 403 with no cookie; provider outage → 202 plus a failure counter and a new request after the window; missing pepper → 503 `unavailable`.

## 11. Rollout

1. Land T1 + T3 behind the existing absent-pepper `503` (no pepper → the route answers 503, nothing is sent). 02.10.1-T1/T2 must have delivered a sender before T2 ships; until then the dispatcher binds the capture-only fake in dev.

5. Rollback: stop exposing the routes (feature routes removed from the web screen, 404 on the API); tables are additive and the sweep still clears them. No data migration to reverse.

## Notes, decisions and open items

**[DECISION D-02.3.4-1] the link is bound to the requesting browser by a cookie, not confirmed by a typed code.** Rejected: a 6-digit code typed on the same device (guessable without a strict attempt cap, phishable by relaying, extra friction). A browser cookie costs one click, defeats login CSRF and stolen-link use, and fails safe. The cost is the in-app mail browser and cross-device case; AC11 gives them an explicit recovery screen.

**[DECISION D-02.3.4-2] a mail send is not durable.** Rationale in §7. A lost mail costs the user one more request; a durable row would store a live secret.

**[DECISION D-02.3.4-3] token in the URL fragment.** The fragment never reaches server logs, proxies or `Referer`; the page posts it. Auth.js puts the token in the query string and stores `sha256(token + secret)`; this plan takes the idea of hashing at rest and uses an HMAC with a versioned pepper (T5) instead, and takes its NFKC email normalisation and quote/comma rejection for address-confusion defence.

**Prior art.** OWASP Authentication Cheat Sheet (generic responses and timing-equal paths for login/recovery) and Forgot Password Cheat Sheet (single use, short expiry, hashed token); Auth.js email provider (`sendToken`: normalise, hash at rest, adapter-stored challenge). Approach only; no code taken. Not followed: Auth.js's query-string token and its non-bound challenge.
