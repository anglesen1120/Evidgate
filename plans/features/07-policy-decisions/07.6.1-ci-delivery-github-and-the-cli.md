## 1. Goal and non-goals

**Goal.** Every stored evaluation is delivered to GitHub as a check run (commit status as fallback) with an auditable `ci_delivery` record and bounded retries, and `evidgate gate` gives CI pipelines a blocking wait on a run's decision with unambiguous exit codes — `0` PASS, `1` FAIL, `2` INCONCLUSIVE (incl. wait deadline), `3` error. A delivery failure never changes the stored decision.

**Non-goals.** The evaluation itself (07.2.2); advisory/enforcing mode semantics applied *on top of* these exit codes (07.7.1); outbound webhooks (07.6.2); the GitHub App registration (03.4.1-T1) and the project↔installation binding (02.4.1-T2) — this story consumes them; CLI scaffolding and auth (04.2.1-T1); UI surfaces (09).

## 2. User stories and acceptance criteria

- As a CI engineer, the decision appears on the PR/commit within a minute of evidence freeze, so the pipeline can gate without polling.
- As a CI engineer, `evidgate gate` has a distinct exit code for "no decision yet / inconclusive" and for "transport error", so my pipeline can never mistake either for a pass.
- As an operator, a re-delivered decision does not create a second check run, and a GitHub outage is retried, not dropped.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Decision → conclusion mapping: `PASS` → check-run `success`, `FAIL` → `failure`, `INCONCLUSIVE` → `neutral` (never `success`); commit-status fallback maps `PASS`/`FAIL`/`INCONCLUSIVE` → `success`/`failure`/`error` with `context: evidgate/decision` |
| AC2 | A re-post for the same `(org_id, run_id, evaluation_id, provider)` updates the existing `ci_delivery` row and PATCHes the stored `external_id` check run instead of creating a second one |
| AC3 | A GitHub 5xx or expired installation token leaves `ci_delivery.state = 'failed'` with `last_error` (sanitised), schedules a retry task with backoff, and the `evaluation` row is byte-identical before and after |
| AC4 | `evidgate gate --run {r}` exits `0`/`1`/`2` for `PASS`/`FAIL`/`INCONCLUSIVE`; `--wait 30s` against a run that stays `pending` exits `2` (never `0`); a transport/auth failure exits `3`; `--json` prints `{ decision, completeness, evaluation_id, mode, url }` matching `contracts/cli.md` |
| AC5 | `GET /v1/runs/{r}/decision` returning `pending` under `--wait` polls until a decision row exists or the deadline; the deadline path is covered by a fixture test |
| AC6 | An installation lacking the checks:write scope falls back to commit-status delivery automatically, with no error surfaced to the caller; a transient GitHub error (5xx, timeout) never triggers the fallback — it retries check-run delivery instead (T62) |

## 4. Data model and migrations

`migrations/NNNN_decisions_ci_delivery.sql` (DbUp, owner role):

```sql
create table ci_delivery (
  id uuid primary key default gen_random_uuid(),
  org_id uuid not null,
  run_id uuid not null,
  evaluation_id uuid not null,
  provider text not null,               -- github_check_run | github_commit_status
  target_ref text not null,             -- owner/repo + sha recorded at send
  external_id text,                     -- check-run / status id returned by GitHub
  state text not null default 'queued', -- queued | sending | delivered | failed | dead_letter
  attempts int not null default 0,
  next_attempt_at timestamptz,
  last_error text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (org_id, id),                                   -- 00 §5.4.6 / T3
  unique (org_id, run_id, evaluation_id, provider),      -- idempotent re-post (AC2)
  foreign key (org_id, run_id) references run (org_id, id),
  foreign key (org_id, evaluation_id) references evaluation (org_id, id)
);
alter table ci_delivery enable row level security;
alter table ci_delivery force row level security;
create policy ci_delivery_tenant on ci_delivery
  using (org_id = evidgate.current_org_id());
```

The `(org_id, run_id, evaluation_id, provider)` unique already covers reads by run for operator/debug queries; no extra list index is added (deliveries are driven by task rows, not scans — P4 satisfied by the unique's leading columns).

## 5. API shapes (commands, queries, endpoints)

- **Command `UpsertCiDeliveryCommand`** (`ICommand<Guid>`, EF Core write model): INSERT … `ON CONFLICT (org_id, run_id, evaluation_id, provider) DO UPDATE` returning the row + `external_id`; executed in its own short tenant transaction **before** the network call so the HTTP call is never inside a DB transaction (P5).
- **Command `RecordCiDeliveryResultCommand`**: writes `state`, `external_id`, `attempts`, `last_error` (sanitised: status code + first line only, S3); on retryable failure also enqueues the next `ci.deliver` task row (C7).
- **Task handler `CiDeliveryHandler`** (task type `ci.deliver`, `Evidgate.Worker`): claim → UpsertCiDelivery → GitHub call → RecordCiDeliveryResult.
- **Query**: none new. The CLI uses existing `GetRunDecisionQuery` → `GET /v1/runs/{r}/decision` (`decision:read`), which returns `pending` or the evaluation body.
- **Endpoint surface**: none new under `/v1`.

`evidgate gate` (packages/cli, Node 22+/TS 6.0, Vitest): `gate --run <id> [--wait <dur>] [--json]` — polls the decision endpoint with jittered backoff; exits per AC4.

## 6. States and transitions

`ci_delivery.state`: `queued → sending → delivered`; `sending → failed` on retryable error → re-`queued` by the backoff task; attempts cap exceeded → `dead_letter` (visible to operators, replayable by re-enqueueing `ci.deliver`). `delivered` and `dead_letter` are terminal for that `(run, evaluation, provider)` triple.

## 7. Jobs and integrations

- The evaluate handler (07.2.2) writes a `ci.deliver` outbox row in the same transaction as the `evaluation` INSERT (C7); the dispatcher moves it into the `task` queue (`FOR UPDATE SKIP LOCKED`, `available_at` backoff, capped retries, 00 §5.3).
- GitHub integration per T46: typed `HttpClient` `GitHubChecksClient` — RS256 app JWT via `Microsoft.IdentityModel.JsonWebTokens` (registered in ADR-0002 with the NuGet licence row), installation access token minted against the installation id from the project binding (02.4.1-T2) and the App registration (03.4.1-T1). No Octokit dependency.
- Check run: `POST /repos/{owner}/{repo}/check-runs` (or PATCH when `external_id` exists) with `head_sha` from the run's CI reference, `conclusion` per AC1, `details_url` linking to the run's decision. Commit-status fallback (T62) fires **only** when the installation's permission set lacks `checks:write` (checked once at binding time, cached on the delivery's chosen `provider`) — never as a fallback for a transient GitHub error, which instead retries the check-run path: `POST /repos/{owner}/{repo}/statuses/{sha}` with `context: evidgate/decision`.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 P5 | Two-phase delivery: upsert + commit first, GitHub HTTP outside any transaction, result written in a second transaction | `CiDeliveryHandler` structure + integration test asserting no open transaction during the stubbed HTTP call |
| 00 §5.7 P6 | `IHttpClientFactory` named client `github` with timeouts and resilience handlers; GitHub `Retry-After` honoured | Resilience-handler unit test |
| 00 §5.7 S3 | Installation token and app private key come from the secret store; `last_error` stores status code + sanitised message only | Redaction list test; fixture asserting token never appears in logs |
| 00 §5.7 S4 | Outbound allow-list: `api.github.com` only; owner/repo/sha come from the stored binding and run, never from request input | Allow-list test attempting a non-GitHub host |
| 00 §5.7 S1, S2 | Parameterised SQL; no new `/v1` endpoint, so authorization is the worker service identity inside the tenant scope; CLI callers need `decision:read` | Architecture test still green; CLI auth fixture |
| T46 | Typed `HttpClient` + RS256 JWT via `Microsoft.IdentityModel.JsonWebTokens`; no Octokit | Dependency list + ADR-0002 row check |
| T51 | Not applicable — no new `/v1` operation; `gate` polls an existing operation that already carries `x-permission: decision:read` | Contract test |
| Roles/permissions | Worker service identity writes `ci_delivery`; CLI/gate caller = `ci_producer` or member bearer with `decision:read` | CLI 403 fixture without the permission |
| Privacy / retention | `ci_delivery` holds ids, state, sanitised error; no evidence content, no personal data; retention open question 07-O6 flagged, rows kept until decided | — |

- **Authorization:** the `gate` CLI calls `GET /v1/runs/{r}/decision` with a bearer that carries `decision:read`; a 401/403 exits 3 and never 0.
- **Retention/deletion:** the CLI stores nothing beyond the existing token cache; delivery rows follow `ci_delivery` retention (07-O6).
- **Telemetry:** `gate` prints one result line (or one `--json` object) and no token; delivery counters are `evidgate_ci_delivery_attempts` and state counts.
- **Failure path:** pending past `--wait` and INCONCLUSIVE exit 2, transport or auth failure and any unknown decision value exit 3; only a literal `PASS` exits 0.
