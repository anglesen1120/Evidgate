## 1. Goal and non-goals

**Goal.** Late evidence is **accepted** (T81): events for a run in `incomplete`, or `complete` within the pinned policy revision's `late_window` since completion, are stored with `late = true` (04.1.1) and cause the reconcile path (05.3.2) to freeze a new evidence revision; the worker then produces evaluation *n+1* through the normal outbox task. Evaluation *n* remains byte-identical and queryable. After the `late_window` ingest rejects with `409 run_closed` — no revision, no evaluation; canceled runs keep accept-and-mark (`after_cancel`, T12) and never complete. No code path, endpoint or operator action may mutate an existing evaluation row.

**Non-goals.** The evidence-revision creation itself (05.3.2-T3 + 06.5.1); the operator UI (10/09); release-level aggregation of the new revision (07.5.3); automatic release re-gating on late evidence (owner decision, still open in area plan §11 — not built).

## 2. User stories and acceptance criteria

- As a `release_approver`, I can trust that the decision a release consumed is still exactly the row it saw, even after late evidence produced a newer evaluation.
- As a `platform_operator`, I can force a re-evaluation of a run for support purposes via the operator ingress without any tenant-facing endpoint existing.
- As the Tech Lead, I know a bug or hostile caller cannot `UPDATE`/`DELETE` an evaluation, because the database itself refuses it.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Given run R with evaluation `e_n` (evidence revision `v_n`), late evidence inside `policy.late_window` produces `v_{n+1}` and a *new* evaluation `e_{n+1}` with `evidence_revision = v_{n+1}`; `e_n` is unchanged and still returned when queried by its `evidence_revision` |
| AC2 | Late evidence arriving **after** `late_window` produces no new evaluation: ingest returns `409 run_closed` (T81/04.1.1), so no evidence revision is frozen and nothing reaches the evaluation queue |
| AC3 | `POST /internal/operator/runs/{r}/evaluations` (platform-operator role, audited) enqueues the same evaluation task; if inputs are unchanged the T22 unique key dedupes it to the existing row — no duplicate `live` row |
| AC4 | A direct `UPDATE` or `DELETE` on `evaluation` executed as the application role fails with `permission denied` (immutability guard) |
| AC5 | No `/v1` route performs or triggers re-evaluation — a route table inspection finds no re-evaluation mapping (T26) |
| AC6 | Events for a run in `incomplete` (or `complete` within `late_window`) carry `late = true` (T81) and still produce `v_{n+1}` + `e_{n+1}`; events for a **canceled** run are accepted-and-marked `after_cancel` (T12), never complete the run and never trigger re-evaluation — the run row taken in the ingest tx is the arbiter (T91) |

## 3. Contracts touched

- 00 §8.5 — evaluation immutability and one-`live`-row-per-`(org_id, run_id, evidence_revision)` partial unique (T22): enforced at DB level by this story, not changed.
- 00 §9.1 — the operator route `POST /internal/operator/runs/{r}/evaluations` is registered under the operator ingress with the platform-operator role (per area plan §4 endpoints line).
- T26 — no `/v1` re-evaluation endpoint is created; verified by AC5.
- Resolved (T81/T81a): late evidence inside `late_window` is accepted (`late = true` on the stored events) and drives a new evidence revision + re-evaluation; after the window ingest returns `409 run_closed`; canceled runs stay accept-and-mark (T12). The `late_window` is checked **once, at ingest** — every revision produced from accepted events is re-evaluated; evaluation never re-checks the window.
- Resolved (T62 / RECOMMENDATIONS 07-O5): the `late_window` default is 24 h in the default policy template. This story reads whatever the pinned policy revision carries and needs no default of its own — no code impact.

## 4. Data model and migrations

No new table. One guard migration on the existing `evaluation` table (owner 07):

- `migrations/NNNN_policy_evaluation_immutable.sql`: `REVOKE UPDATE, DELETE, TRUNCATE ON evaluation FROM <app_role>` (C6 immutability at SQL level; the insert path needs `INSERT`/`SELECT` only), plus a comment noting the same for any future table owning decisions.
- `evaluation` already carries `unique (org_id, run_id, evidence_revision, policy_revision_id, evaluator_version, mode)` + partial unique `WHERE mode='live'` (T22, created by 07.2.2-T1's migration).
- `webhook`/`task` rows for re-evaluation use the existing 01-owned queue tables — no new queue objects.

## 6. States and transitions

`evaluation` rows are append-only: each is born complete and immutable (00 §8.5). Late evidence moves the *run's* "latest evaluation" pointer implicitly — consumers read "latest live evaluation for the run" — while prior rows stay addressable by `evidence_revision`. No state machine added; `run`/`evidence_revision` states stay owned by 05.

## 7. Jobs and integrations

- **Late-evidence path:** 05.3.2's reconcile freezes `v_{n+1}` and emits its existing evidence-revision-frozen outbox event → 07.2.2-T1's task handler evaluates it (the T22 unique key makes redelivery harmless). The `late_window` is already checked at ingest (04.1.1: inside → `late = true`, after → `409 run_closed`); evaluation never re-checks the window — every late revision produced from accepted events triggers the task and is re-evaluated (T81a).
- **Operator path:** the `/internal/operator` route calls `EnqueueEvaluationCommand` directly — same task, same dedupe.
- **Immutability:** enforced by the migration in §4; verified by AC4 probe.

## 11. Rollout

- No feature flag: late-window re-evaluation is core semantics (00 §8.5); advisory mode keeps M2 non-blocking regardless.
- Merge order: T1.1 (enqueue path) can merge only after 05.3.2-T3 emits frozen-revision events — dependency already declared; T1.2's route is independent of the event path and may land in the same PR.
- Monitoring: the `task` queue's existing depth/age metrics cover the re-evaluation tasks (01.5.1); a count of late-evidence re-evaluations is logged, not alerted (out-of-window events never reach 07 — ingest rejects them with `409 run_closed`).
- Rollback: revert the PR; written evaluations are immutable and remain valid — rollback never repairs data, matching A3.
