## 1. Goal and non-goals

**Goal.** (V1/T1) The flaky facts computed by 07.4.1 reach every consumer of a decision — the stored evaluation's `reasons[]`, the `evaluation.created` webhook payload and `evidgate gate`'s CLI output — so flakiness is visible on every surface, not just the database row. (V2/T2) A `flaky_trend` read table aggregates each case's retry-fail→pass history across a project's recent runs and exposes a `flaky`/`stable` label for UI/reporting — a purely informational signal that changes no V1 gating semantics.

**Non-goals.** The flaky decision effects themselves (07.4.1); the webhook transport and signing (07.6.2); the CLI's gate loop/exit codes (07.6.1-T2, 04.2.1); UI pages rendering the trend (09); changing gating from the trend label.

## 2. User stories and acceptance criteria

- As a `qa_engineer` reading CI logs or a webhook consumer, I see *which* case flaked and that a budget was hit, without logging into the UI.
- As a `test_maintainer` (V2), I see which cases have been flaky across recent runs so I can prioritise stabilisation work, while knowing the label alone can never soften a gate.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An evaluation whose `reasons[]` includes `flaky_critical_retry_pass` / `flaky_within_budget` / `flaky_budget_exceeded` emits an `evaluation.created` webhook payload carrying those same reason strings plus a `flaky_facts[]` array (`execution_key`, `attempt_count`, `case_id`) |
| AC2 | `evidgate gate` (JSON output mode) prints the same `reasons[]` strings and `flaky_facts[]` for a run over-budget on flaky — exit code still `2` (07-CR-2), unchanged |
| AC3 | `GET /v1/runs/{r}/decision` (07.5.2) returns `flaky_facts[]` alongside `reasons[]` with no extra endpoint |
| AC4 | V2: after a case fail→passes in ≥ threshold of the project's last N runs, `flaky_trend` shows `label = flaky` for that case; a run with no retries never adds a row |
| AC5 | V2: an evaluation computed over a `flaky`/`stable` labelled case is byte-identical to one computed without the table existing — the label is never an evaluator input (T24 purity kept) |

## 3. Contracts touched

- 00 §9.5 / `contracts/openapi.yaml` — `evaluation.created` webhook payload gains `flaky_facts[]` + `reasons[]` passthrough; additive field, version-safe.
- `contracts/cli.md` — `gate` JSON output schema gains the same additive fields; exit codes 0/1/2/3 unchanged (07-CR-2).
- 00 §8.5 — `evaluation` row gains no column; `flaky_facts[]` is persisted inside the existing `reasons[]`/detail payload or, where needed, derived at read time from the same frozen attempt set. No schema drift on the immutable row.
- [OPEN] Area plan does not name the threshold N or the label vocabulary for the trend; this plan picks `last 20 runs`, `label ∈ {flaky, stable}` with a case flaky when ≥ 1 retry fail→pass appears in ≥ 20 % of its executed runs — flagged for Tech Lead confirmation at DoR.

## 4. Data model and migrations

One new read-side table (V2/T2 only), owned by `Evidgate.Modules.Policy`:

| Table | Columns | Constraints / indexes |
|---|---|---|
| `flaky_trend` | `id uuid`, `org_id uuid not null`, `project_id uuid`, `case_id uuid`, `runs_considered int`, `runs_with_flaky int`, `last_flaky_run_id uuid`, `label text` (`flaky`\|`stable`), `updated_at timestamptz` | `unique (org_id, id)` (T3); `unique (org_id, project_id, case_id)`; RLS policy `org_id = evidgate.current_org_id()` (T2); index `(org_id, project_id, label, updated_at desc)` serving the per-project "flakiest cases" list |

- Migration: `migrations/NNNN_policy_flaky_trend.sql` (DbUp, placeholder number per convention).
- V1/T1 writes nothing — flaky facts live inside the evaluation row's `reasons[]`/detail and are re-derivable from `case_attempt` (05.3.3) at read time.

## 5. API shapes (commands, queries, endpoints)

| Type | Name / route | Detail |
|---|---|---|
| Query | `GetFlakyTrendQuery : IQuery<FlakyTrendPage>` → Dapper handler, read-only tx (C1/C5) | `GET /v1/projects/{p}/flaky-trend` — permission `project:read` (T21, every member role); keyset cursor on `(updated_at, id)`; returns `{case_id, label, runs_considered, runs_with_flaky, last_flaky_run_id}`; V2 only |
| Internal write | `UpdateFlakyTrendCommand : ICommand<Unit>` (07 module handler, EF Core write model) | invoked from the `task` handler after a live evaluation commits; upsert keyed `(org_id, project_id, case_id)`; V2 only |
| No command (V1/T1) | payload + CLI changes are additive fields on existing `evaluation.created` serialization and existing `gate` output — no new endpoint or verb | |

## 6. States and transitions

`flaky_trend.label` toggles `flaky → stable` (and back) per recompute — a derived label, not a lifecycle; it carries no approval semantics and never gates. Trend rows are re-derived on each evaluation; no immutable history is kept in V2 (re-derivation source is `case_attempt`).

## 7. Jobs and integrations

- V1/T1: `evaluation.created` webhook (transport by 07.6.2-T1) and the CLI `gate` reader (07.6.1-T2) consume the additive payload fields — integration with those owners is a shared contract, not shared code.
- V2/T2: `UpdateFlakyTrendCommand` is enqueued as a `task` row by the evaluation handler's outbox flush (00 §5.3, C7); idempotent by natural key `(org_id, project_id, case_id)` — a re-delivered task recomputes the same upsert.

## 11. Rollout
