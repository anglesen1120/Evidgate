## 1. Goal and non-goals

**Goal.** A single, side-effect-free C# function turns three immutable inputs — a frozen evidence revision, a pinned policy revision, and an (already-resolved) exceptions snapshot — into `completeness`, `outcome` and `decision`, each populated independently (A8), such that calling it twice with the same inputs in two different processes produces byte-identical output, and `FAIL` is representable even when `completeness = incomplete`.

**Non-goals.** Persisting the `evaluation` row, the unique-key conflict/idempotency handling, and running the full M1–M18 golden matrix as an integration suite (07.2.2); resolving *which* waivers/quarantine ids are active or hashing the snapshot (07.3.1/07.2.2-T3); the concrete effect of a waiver or quarantine entry on the decision (07.3.2); flaky detection from attempt history and the flaky budget (07.4.1) — this story's decision computation only reaches the matrix rows that do not depend on flaky or waiver/quarantine input (M1–M9, M13, M16); the task handler that invokes this function from the `task` queue (07.2.2-T1).

## 2. User stories and acceptance criteria

- As the platform, I need the same evidence + policy + exceptions triple to always produce the same evaluation, in a fresh process, months later, so a stored decision can be explained and replayed.
- As a Tech Lead reviewing a matrix row, I need `completeness`, `outcome` and `decision` to vary independently, so "confirmed failure with missing evidence" is representable as `FAIL` + `incomplete`, never coerced into `INCONCLUSIVE`.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Calling `IPolicyEvaluator.Evaluate` twice with structurally-equal inputs (deep-equal records, not the same object reference), in two separate `xUnit` test-class instances (simulating separate processes), returns deep-equal output including `reasons[]` order |
| AC2 | A required-assertion failure with an unrelated missing shard yields `decision = FAIL` and `completeness = incomplete` with `missing = [missing_shard]` (never `INCONCLUSIVE`) |
| AC3 | `Architecture.Tests` fails the build if the evaluator project (or its dependency graph) references `Npgsql`, `System.Net.Http`, `DateTime.Now`/`DateTime.UtcNow`, or any other module's `Infrastructure` namespace |
| AC4 | Zero cases matched (`expected_count = 0`) without an "empty suite allowed" flag on the policy yields `outcome = no_results`, `decision = INCONCLUSIVE`, reason `expected_count_zero`; with the flag it yields `decision = PASS`, reason `empty_suite_allowed` |
| AC5 | A critical case reported `skipped` or `blocked` yields `decision` = not `PASS` (`INCONCLUSIVE`, reason `critical_not_executed`) even when every other required case passed |

- No API, schema or permission change — this story ships a library type (`IPolicyEvaluator`), not an endpoint.

## 4. Data model and migrations

None. The evaluator is a pure in-memory function; it owns no table. Its input records (`EvidenceRevisionInput`, `PolicyRevisionInput`, `ExceptionsSnapshotInput`) are plain C# `record` types constructed by 07.2.2's task handler from rows owned by 06 (evidence), 07.1.1 (`policy_revision`) and 07.2.2-T3 (resolved snapshot) — no new columns here.

## 5. API shapes (commands, queries, endpoints)

None — this story is consumed in-process, not over `/v1`. The library surface:

| Type | Shape |
|---|---|
| `IPolicyEvaluator` | `EvaluationResult Evaluate(EvidenceRevisionInput evidence, PolicyRevisionInput policy, ExceptionsSnapshotInput exceptions)` — no `async`, no `CancellationToken` (nothing to cancel in a pure computation) |
| `EvaluatorVersion` | a `const string` (e.g. `"1.0.0"`), bumped only when the computation's observable behaviour changes; stored verbatim on the persisted `evaluation` row by 07.2.2, never derived from the assembly version |
| `EvaluationResult` | `{ Completeness, Missing[], Outcome, Decision, Reasons[] }` — the four fields persisted by 07.2.2; this story returns them, does not write them |

Consumed by 07.2.2-T1 (`EvaluateRunCommand` handler calls `Evaluate` inside the task handler, then persists the result), 07.3.2-T1 (extends the reason catalogue and the decision branch for quarantine/waiver), 07.4.1-T1/T2 (extends the branch for flaky detection), 03.8.1 and 05.6.1 (read `EvaluationResult` shapes via 07.2.2's persisted row, not this story directly).

## 6. States and transitions

None. The evaluator has no state machine of its own; it reads `policy_revision.state` and evidence-revision completeness as *inputs*, never mutates either (00 §8.1–§8.5 state machines are owned by 05/06/07.1.1, not re-declared here).

## 7. Jobs and integrations

None — no background task in this story. Called synchronously, in-process, by 07.2.2-T1's task handler (00 §5.3 applies to the *handler*, not to this pure function).
