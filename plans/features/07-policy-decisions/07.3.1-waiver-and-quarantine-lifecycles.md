## 1. Goal and non-goals

**Goal.** Two independent, auditable exception mechanisms exist as their own tables: a `waiver` (human risk acceptance, never itself a test result, `approver ≠ requester`) and a `quarantine_entry` (excludes a case from gating while keeping its failure visible), and a case on the pinned policy revision's critical list can never be quarantined — the write is refused `422 critical_case_not_quarantinable` (T23), full stop, regardless of who asks.

**Non-goals.** How the evaluator *applies* an active waiver or quarantine entry to a decision (07.3.2); resolving the exceptions snapshot and hashing it onto an evaluation (07.2.2-T3); expiry sweeping (07.3.2-T2); the UI screens that list/manage these (09.3.1) — this story ships the tables and the `/v1` write/read surface they consume.

## 2. User stories and acceptance criteria

- As a `release_approver`, I request a waiver for a known failing case and a *different* `release_approver` approves it, so risk acceptance always has two people behind it.
- As a `test_maintainer`, I try to quarantine a case that is on the current policy's critical list and I am refused, so a critical gate can never be silently laundered into a pass.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/waivers/{w}/approve` where `approved_by == requested_by` returns `403 waiver_self_approval`; no state change to the `waiver` row (still `requested`) |
| AC2 | The same call by a different member with `release_approver` succeeds: `waiver.state = approved`, `approved_by` set |
| AC3 | A raw-SQL attempt to `INSERT` a `waiver` row with `approved_by = requested_by` (bypassing the API) fails the `CHECK (approved_by <> requested_by)` constraint |
| AC4 | `POST /v1/quarantine` for a `case_id` present in the active policy revision's critical-case list returns `422 critical_case_not_quarantinable`; no `quarantine_entry` row is written |
| AC5 | `POST /v1/quarantine` for a `case_id` not on the critical list succeeds: `quarantine_entry.state = active` |
| AC6 | `DELETE /v1/quarantine/{q}` transitions `state: active → removed`; a second `DELETE` on an already-`removed` entry returns `404` (not a silent no-op `200`) |

## 5. API shapes (commands, queries, endpoints)

**Commands:**

| Command | Handler does | Endpoint | Permission | Status / errors |
|---|---|---|---|---|
| `CreateWaiverCommand` | `INSERT` with `state = requested` | `POST /v1/waivers` | `policy:write` (`release_approver`) | `201` |
| `ApproveWaiverCommand` | checks `approved_by <> requested_by` (API-level, before the DB `CHECK` is even reached) then `state: requested → approved` | `POST /v1/waivers/{w}/approve` | `policy:write` (`release_approver`) | `200`, `403 waiver_self_approval` (AC1), `409` if not in `requested` state |
| `RevokeWaiverCommand` | `state: approved → revoked` (any state other than a terminal one) | `POST /v1/waivers/{w}/revoke` | `policy:write` (`release_approver`) | `200`, `409` if already terminal |
| `CreateQuarantineEntryCommand` | checks `case_id` against the project's active policy revision's critical-case list (07.1.1's `GetActivePolicyQuery`); refuses if present; else `INSERT` with `state = active` | `POST /v1/quarantine` | `policy:write` (`test_maintainer`) | `201`, `422 critical_case_not_quarantinable` (AC4, T23) |
| `RemoveQuarantineEntryCommand` | `state: active → removed`; `404` if not `active` (AC6) | `DELETE /v1/quarantine/{q}` | `policy:write` (`test_maintainer`) | `200`, `404` |

**Queries:**

| Query | Endpoint | Permission | Notes |
|---|---|---|---|
| `ListWaiversQuery` | `GET /v1/projects/{p}/waivers` | `policy:read` (every member role incl. `viewer`, T58) | cursor pagination `(created_at, id)`; consumed by 09.3.1 |
| `ListQuarantineEntriesQuery` | `GET /v1/projects/{p}/quarantine` | `policy:read` (every member role incl. `viewer`, T58) | cursor pagination `(created_at, id)`; consumed by 09.3.1, 07.2.2-T3's snapshot resolver reads the table directly (in-process), not through this endpoint |

Idempotency: `CreateWaiverCommand`/`CreateQuarantineEntryCommand` are `Idempotency-Key`-guarded per 00 §9.1 (side-effecting creates); a retried identical request returns the original `201` body, a differing payload with the same key returns `409 idempotency_conflict`.

## 6. States and transitions

`waiver.state`: `requested → approved | revoked`; `approved → expired | revoked`. `expired` and `revoked` are terminal — a waiver is never re-approved from either (a correction is a new `CreateWaiverCommand`). `revoked` is reachable from both `requested` and `approved` (a requester or approver can withdraw before or after approval).

`quarantine_entry.state`: `active → expired | removed`. Both terminal. `removed` is an explicit operator/maintainer action (`DELETE`); `expired` is set only by the time-driven sweeper (07.3.2-T2), never by this story's commands.

## 7. Jobs and integrations

- No background task in this story (expiry is 07.3.2-T2). All writes are synchronous, single-transaction commands.
- Consumed by 07.2.2-T3 (snapshot resolver reads active `waiver`/`quarantine_entry` ids), 07.3.2-T1 (evaluator layer reads the resolved snapshot's referenced rows for reason-code text, e.g. "approved by waiver"), 09.3.1 (waiver/quarantine management UI).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-07-8 (approver ≠ requester) | API check + DB `CHECK` constraint, belt-and-braces (S2 pipeline authorization is *who* may call the endpoint; the `CHECK` guards *data integrity* even from a future bug or a direct migration) | AC1, AC2, AC3 |
| T23 (critical case never quarantinable) | `CreateQuarantineEntryCommand` reads the active policy revision's critical-case list inside the same transaction as the write — no TOCTOU window, because both reads/writes are in one tenant transaction | AC4, AC5 |
| 00 §5.4.6/.7 (RLS, `unique(org_id,id)`) | both tables `FORCE ROW LEVEL SECURITY`, `evidgate.current_org_id()`, `UNIQUE (org_id,id)` | Testcontainers RLS test: no-org-set session reads zero rows |
| S1 (parameterised SQL) | EF Core LINQ writes, Dapper parameter reads | code review |
| S2 (pipeline authorization) | `policy:write` (create/approve/revoke/quarantine) is a Mediator behaviour (C2); `x-permission` set on every operation (T51) | `Architecture.Tests` permission-match check |
| Authorization | Writes: `release_approver` owns waivers (00 §2, §6 "Policy authority"); `test_maintainer` owns quarantine; `qa_engineer` cannot call either write command. Reads: `policy:read` is open to every member role incl. `viewer` (T58) — an exception is never hidden from someone who can already see the run | permission test: `qa_engineer` gets `403` on `POST /v1/waivers` and `POST /v1/quarantine`; `viewer` gets `200` on `GET /v1/projects/{p}/waivers` and `GET /v1/projects/{p}/quarantine` |
| Privacy | `reason` is free text supplied by staff, not customer data; no artifact content stored here | code review |
| Retention/deletion | waivers/quarantine entries are never hard-deleted by this story (audit trail); tenant deletion (T16) purges them only as part of the whole-org purge, out of scope here | — |
| P4 (index per filter) | `(org_id, project_id, state, expires_at)` on both tables serves the sweeper's "due" query and the list endpoints' filters | integration test `EXPLAIN` assertion |

- **Telemetry:** every waiver handler runs in a module span (`ModuleName.Policy`); create, approve and revoke each write one audit row (`waiver.create`, `waiver.approve`, `waiver.revoke`, object `waiver`/id) through the pipeline's `[AuditedAction]`; `reason` text is never logged.
- **Failure path:** a self-approval is 403 `waiver_self_approval` before any write and leaves the row `requested`; approve or revoke of a waiver that is not in a source state of §6, or whose `expires_at` has passed, is 409 `waiver_state_conflict` from one conditional `UPDATE … RETURNING`, so two concurrent approvals yield one 200 and one 409; an unknown or other-tenant id is 404; a direct app-role write outside the granted columns or transitions fails the grant (42501) or the `waiver_guard` trigger / `CHECK` (23514). A replayed `Idempotency-Key` returns the first answer; the same key with another body is 409.

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Self-approval refused at API and DB layer | AC1, AC3 |
| Legitimate approval by a different approver | AC2 |
| Critical-list quarantine refused | AC4 |
| Non-critical quarantine succeeds | AC5 |
| Double-removal is `404`, not a silent success | AC6 |
| Concurrent quarantine of the same case | two concurrent `CreateQuarantineEntryCommand` calls for the same `case_id` → the partial unique index lets exactly one succeed as `active`; the loser gets `409` |
| Cross-tenant read | a project in org B cannot list org A's waivers/quarantine entries (`404`/empty page, never leaking a row) |
| Viewer can read exceptions | `viewer` gets `200` (not `403`) on `GET /v1/projects/{p}/waivers` and `GET /v1/projects/{p}/quarantine` (T58) |
