## 1. Goal and non-goals

**Goal.** Persist the aggregate of a release's per-component decisions as an append-only `release_decision` row: every `release_component` is matched to the run whose evidence digest equals the release's declared digest for that component; a mismatch (or absent bound run) is reported as `missing`, never silently substituted by the newest run for that component by time. Aggregation runs as an **outbox task on `evaluation.created`** (T87); `GET /v1/releases/{id}/decision` is a **pure query** that returns the persisted row, or `pending` when none exists yet — it never writes or enqueues.

**Non-goals.** Mobile app digests in the aggregate (V2, 07.5.4); CI delivery of the release decision (07.6.1 is run-scoped); release/component creation itself (owned by 05.6.1); re-aggregation triggers beyond the `evaluation.created` outbox task (T87: no polling/scheduling, no read-time projection, no aggregation at request time).

## 2. User stories and acceptance criteria

- As a `release_approver`, I see one decision per release that never claims a component passed unless the exact build it evaluated matches the release's declared digest for that component.
- As a `qa_engineer`, I can tell exactly which component is missing or mismatched instead of guessing from a list of unrelated runs.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A release with 3 components, all bound to runs whose evidence digest matches the release's declared digest and all `PASS`, aggregates to `decision = PASS`, `completeness = complete` |
| AC2 | One component's bound run has a digest that does not match the release's declared digest for that component → that component reports `missing` (reason `component_digest_mismatch`) and the release decision is not `PASS` |
| AC3 | A component with no bound run at all reports `missing` (reason `component_run_unbound`) — the aggregate never falls back to "the newest run for that component" |
| AC5 | `GET /v1/releases/{id}/decision` returns `200` with per-component `{component_id, status, decision, reasons[]}` array matching the persisted aggregate; when no `release_decision` row exists yet it returns `200` with `decision = "pending"` (T87) |
| AC6 | A `FAIL` on any single component makes the release decision not `PASS`, mirroring 00 §8.6's run-level "a confirmed failure gates regardless of other missing evidence" logic at the release level |
| AC7 | `GET /v1/releases/{id}/decision` never writes or enqueues anything: a GET on a never-aggregated release performs one SELECT, leaves `release_decision` and the `task` queue untouched, and returns `pending` (T87, C1 read-only tx) |
| AC8 | A `replay`-purpose run (T67) is never bound to a release and never counted by the aggregation task — a release whose only matching run is a replay run reports that component `missing` |

## 3. Contracts touched

- 00 §7 hashing — `inputs_hash = sha256:<hex>` over RFC 8785 canonical JSON of `{release_id, policy_revision_id, component_evaluations[]}`, reusing the existing canonicalisation service (`Evidgate.Canonicalization`, owner 01).
- Area plan §4 `release_decision` table — implemented as designed, not changed.
- `release`/`release_component` — owned by 05 (`05.6.1-T1`); this story reads them through 05's exported view (00 §5.1 module boundary: `Evidgate.Modules.Orchestrator.Contracts`), never queries 05's tables directly.
- Endpoint `GET /v1/releases/{id}/decision` added to `contracts/openapi.yaml` with `x-permission: decision:read` (T51), matching the area plan's endpoint list. Per T87 the operation is documented as a pure read: `200` with the persisted aggregate, or `200` `{decision: "pending"}` when no row exists; aggregation is only ever triggered by the `evaluation.created` outbox event.

## 4. Data model and migrations

| Table | Key columns | Constraints |
|---|---|---|
| `release_decision` | `id`, `org_id`, `release_id`, `policy_revision_id`, `component_evaluations` (jsonb array of `{component_id, run_id, evidence_revision, status, decision, reasons[]}`), `completeness`, `decision`, `reasons[]`, `inputs_hash` | `unique (org_id, id)` (T3); `unique (org_id, release_id, policy_revision_id, inputs_hash)` (AC4); RLS `org_id = evidgate.current_org_id()` (T2); index `(org_id, release_id, created_at desc)` serving "latest decision for this release" |

- Migration `migrations/NNNN_policy_release_decision.sql` creates the table above (00 §5.2 `migrations/` convention, DbUp, placeholder number).
- `component_evaluations` is JSONB because its shape is a versioned array of per-component facts, not something filtered/joined/authorised directly (00 §5.4.5) — `component_id`/`decision` inside it are read-only projections for display, never queried by SQL predicate (list queries filter on `release_id`/`created_at` only, both typed columns).

## 5. API shapes (commands, queries, endpoints)

| Type | Name | Detail |
|---|---|---|
| Command | `AggregateReleaseDecisionCommand : ICommand<Guid>` → EF Core write handler (C1/C4) | Invoked **only** by the outbox task `policy.release_aggregate` on `evaluation.created` (T87 — never by the GET): reads `release`/`release_component` via 05's `IReleaseReader` contract interface, finds releases bound to the evaluation's run; for each component, resolves the bound run's `live` evaluation (07.2.2) — `run.purpose='replay'` runs (T67) are never counted — and compares its evidence digest against `release_component.declared_digest`; computes `inputs_hash`; `INSERT … ON CONFLICT (org_id, release_id, policy_revision_id, inputs_hash) DO NOTHING RETURNING id`, then selects the winner on conflict (mirrors T22's dedupe pattern) |
| Query | `GetReleaseDecisionQuery : IQuery<ReleaseDecisionResult>` → Dapper handler, read-only tx (C1/C5) | `GET /v1/releases/{id}/decision`, permission `decision:read` (T51); returns the latest persisted `release_decision` row for the release, or `decision = "pending"` when no row exists; `404 release_not_found` when the release itself does not exist (or is another tenant's). Pure query: no INSERT, no outbox write, no command dispatch (T87) |

## 6. States and transitions

`release_decision` rows are append-only like `evaluation` (no update path — a re-aggregation with a changed input set produces a new `inputs_hash` and therefore a new row; an unchanged input set returns the existing row via the unique-key conflict). `pending` is a **read projection** of "no row persisted yet", never a stored state. No new state machine; `release`/`release_component` states stay owned by 05.

## 7. Jobs and integrations

- Reads 05's release/component view (`05.6.1-T1`) and 07's own `evaluation` table (`07.2.2-T1`) — no cross-module table access, only the exported `.Contracts` interface (00 §5.1/§5.5 module boundary).
- **Aggregation job (T87):** the outbox consumer task `policy.release_aggregate` subscribes `evaluation.created` (the event the 07.2.2 evaluation writer emits on every persisted evaluation). For each live evaluation it resolves releases bound to the run and persists the `release_decision` row via `AggregateReleaseDecisionCommand` (deduped by the `inputs_hash` unique key). The GET endpoint is never a trigger.
- Feeds 07.5.4 (V2 mobile digests extend the same persisted aggregate — write-time, not a read-time projection, T87) and 09.3.1 (UI release view).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| S1 parameterised SQL | `unnest`/typed parameters for the component comparison query, no string-built SQL | Code review + Dapper parameter usage |
| C4 write model / optimistic concurrency | `release_decision` uses the standard `version` column (C4); no update path needed since rows are append-only | N/A — insert-only entity, no concurrency conflict surface |
| P5 no network in a transaction | Component digest comparison reads only already-persisted `evaluation`/`release_component` rows — no S3/GitHub/LLM call inside the aggregation transaction | Code review of the command handler |
| P3 no N+1 | Aggregation issues one bounded query per release (component count is small, ≤ dozens) via a single `unnest`-joined SELECT, not a per-component round trip | `ReleaseAggregationTests.BoundedQueryCount` |
| S2 / T51 authorization | `decision:read` on the query, permission match asserted by Architecture.Tests | `ArchitectureTests.EndpointPermissionsMatch` |
| Tenant isolation (T2) | RLS on `release_decision`; cross-org release id → `404`, never a row | `Isolation.Tests.ReleaseDecision_OtherOrg_404` |
| Digest-mismatch integrity | Comparison uses the exact declared digest from `release_component`, never "most recent run"; `replay`-purpose runs are never counted (T67) | AC2, AC3, AC8 |
| T87 pure query / persisted aggregate | The GET performs one SELECT (or returns `pending`); aggregation exists only as the `evaluation.created` outbox task — a query can never enqueue or write | AC7; `ReleaseDecisionApiTests.Get_NoRow_Pending_NoWrites` asserts zero rows in `release_decision` and `task` after the GET |
| Privacy/retention | No personal data; component ids, hashes and decision reasons only | — |

## 11. Rollout

- No feature flag: release aggregation is a read/compute path, safe to ship directly at M3; enforcing mode (07.7.1-T2) is independent and gates runs, not this endpoint.
- Merge order: T1 (aggregation task + storage) before T2 (endpoint) — the endpoint has nothing to read without T1, and returns `pending` until the first `evaluation.created` event aggregates.
- Monitoring: `release_decision` insert rate, `policy.release_aggregate` task depth/age and digest-mismatch reason counts are visible via existing evaluation-style logging; no new dashboard in this story.
- Rollback: revert the PR; `release_decision` rows are append-only and harmless to leave in place — no data repair needed.
