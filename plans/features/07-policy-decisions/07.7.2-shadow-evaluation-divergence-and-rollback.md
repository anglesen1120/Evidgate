## 1. Goal and non-goals

**Goal.** Before rolling out a changed policy revision or a new evaluator version, Evidgate runs it in `mode = shadow` over recent runs' already-frozen evidence, using the same pure evaluator as the live path (T24), and produces a per-run divergence report against the live decision — without ever writing to the live row or affecting delivery. The report feeds 10's deploy flow (10.2.2) as a gate before the shadow policy/evaluator is promoted to live; a promoted change that turns out wrong rolls back to `advisory` (07.7.1) with zero evidence or decision loss.

**Non-goals.** Healing-candidate shadow results (already out of scope for all of 07, per the area plan; distinct mechanism in 08); the live evaluation path itself (07.2.2); the advisory/enforcing mode toggle itself (07.7.1, this story's rollback target); a UI for the divergence report (09).

## 2. User stories and acceptance criteria

- As the Tech Lead, before I promote a new policy revision or evaluator version, I see exactly which recent runs would change decision, so I can judge blast radius before customers see it.
- As an operator, running a shadow evaluation never creates a second live decision or double-delivers a webhook/check-run, so shadow testing is risk-free.
- As a release approver, if a promoted policy turns out wrong, flipping the affected projects back to `advisory` is immediate and loses no evidence or decision history.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Triggering a shadow run over a set of recorded runs writes one `evaluation` row per run with `mode = 'shadow'`, `policy_revision_id`/`evaluator_version` = the candidate, and **never** collides with or updates the existing `live` row for that `(org_id, run_id, evidence_revision)` (T22) |
| AC2 | The divergence report lists, per run, `live.decision` vs `shadow.decision` and the differing `reasons[]`; a run with no evidence-content difference between live and shadow policy is reported as not-diverged; the report is non-empty when a rule change actually changes an outcome |
| AC3 | No webhook, CI delivery, or `policy_activation` write is triggered by a shadow evaluation — verified by asserting zero rows appended to `ci_delivery`/`webhook_delivery` after a shadow run |
| AC4 | Shadow evaluation reuses the exact evaluator function used for live (T24); a shadow run over the same evidence/policy/exceptions inputs as an existing live evaluation reproduces byte-identical `decision`/`reasons[]`/`exceptions_hash` |
| AC5 | Rolling an affected project back to `advisory` (07.7.1's `SetPolicyModeCommand`) after a bad promotion is a single audited call; all prior `live` evaluations, `ci_delivery` and `webhook_delivery` rows for that project remain unchanged and queryable |

## 3. Contracts touched

- No `/v1` public endpoint: shadow evaluation is an operator-triggered internal flow consumed by 10's deploy pipeline (00 §9.1: operator actions live under `/internal/operator/*`, `platform_operator`, audited support-grant style access).
- 00 §8.5's `evaluation.mode` and the T22 unique key are exercised exactly as specified — no schema change, this story is the first consumer that *writes* `mode = shadow` at scale (07.2.2 already defines the column and constraint).

## 4. Data model and migrations

- No new table. `evaluation` (owned by 07.2.2) already has `mode` and the compound unique `(org_id, run_id, evidence_revision, policy_revision_id, evaluator_version, mode)` plus the partial unique `… WHERE mode = 'live'` (00 §8.5, T22) — this story is a consumer, not a schema owner.
- New table `shadow_run` (owner: this story) to track a shadow *campaign* (a batch of runs evaluated against one candidate policy/evaluator, for reporting):

```sql
create table shadow_run (
  id uuid primary key default gen_random_uuid(),
  org_id uuid not null,
  project_id uuid not null,
  candidate_policy_revision_id uuid,      -- nullable: an evaluator-only shadow has no new policy
  candidate_evaluator_version text not null,
  triggered_by uuid not null,             -- platform_operator actor
  state text not null default 'running',  -- running | completed | failed
  run_count int not null default 0,
  diverged_count int not null default 0,
  created_at timestamptz not null default now(),
  completed_at timestamptz,
  unique (org_id, id)                     -- 00 §5.4.6 / T3
);
create table shadow_run_result (
  id uuid primary key default gen_random_uuid(),
  org_id uuid not null,
  shadow_run_id uuid not null,
  run_id uuid not null,
  evidence_revision int not null,
  live_evaluation_id uuid,                -- null if no live evaluation exists yet for that revision
  shadow_evaluation_id uuid not null,
  diverged boolean not null,
  live_decision text,
  shadow_decision text not null,
  created_at timestamptz not null default now(),
  unique (org_id, id),
  unique (org_id, shadow_run_id, run_id, evidence_revision),
  foreign key (org_id, shadow_run_id) references shadow_run (org_id, id),
  foreign key (org_id, shadow_evaluation_id) references evaluation (org_id, id)
);
create index shadow_run_result_by_run on shadow_run_result (org_id, shadow_run_id, diverged); -- P4: serves the divergence report query
alter table shadow_run enable row level security;
alter table shadow_run force row level security;
alter table shadow_run_result enable row level security;
alter table shadow_run_result force row level security;
create policy shadow_run_tenant on shadow_run using (org_id = evidgate.current_org_id());
create policy shadow_run_result_tenant on shadow_run_result using (org_id = evidgate.current_org_id());
```

Migration file: `migrations/NNNN_decisions_shadow_run.sql`.

## 5. API shapes (commands, queries, endpoints)

- **Command `TriggerShadowRunCommand`** → `POST /internal/operator/projects/{p}/shadow-runs` (`platform_operator`, operator ingress only, 00 §9.1): body names the candidate `policy_revision_id` and/or `evaluator_version` and the run selection (recent N runs, or an explicit run-id list); writes a `shadow_run` row + one `shadow.evaluate` task row per selected run (C7 outbox) in the same transaction.
- **Task handler `ShadowEvaluateHandler`** (task type `shadow.evaluate`): loads the run's frozen evidence revision + candidate policy revision + the **same exceptions-snapshot resolution logic** as live (T24, `exceptions_as_of` = the original trigger time of the run's live evaluation, so the comparison is apples-to-apples) → calls the shared pure evaluator function → INSERT `evaluation` with `mode = 'shadow'` (guarded by the existing unique constraint, T22) → INSERT `shadow_run_result` comparing against the existing `live` row for that `(run, evidence_revision)` → increments `shadow_run` counters; on completion of the last task, flips `shadow_run.state = 'completed'`.
- **Query `GetShadowRunReportQuery`** (`IQuery`, Dapper read-only tx) → `GET /internal/operator/shadow-runs/{id}/report` (`platform_operator`): per-run divergence rows from `shadow_run_result`, served by `shadow_run_result_by_run`.
- **Rollback**: reuses 07.7.1's `SetPolicyModeCommand` unchanged — no new command.
- Explicitly **no** write path from shadow evaluation into `ci_delivery`, `webhook_delivery`, or `policy_activation` (AC3) — the outbox row written by the evaluate handler for live delivery (07.6.1/07.6.2) is only ever written by the **live** evaluation path (07.2.2), never by `ShadowEvaluateHandler`.

## 6. States and transitions

`shadow_run.state`: `running → completed | failed` (terminal). Per-result `diverged` is a boolean fact computed once at insert (`live.decision <> shadow.decision` or differing `reasons[]`), never recomputed later — a `shadow_run_result` row is immutable once written, consistent with A3. Project delivery `mode` transitions (`advisory ↔ enforcing`) are unchanged and owned by 07.7.1; this story only *reads* the rollback path as its recovery mechanism.

## 7. Jobs and integrations

- 10's deploy flow (10.2.2-T3) calls `TriggerShadowRunCommand` before promoting a policy/evaluator change, polls `shadow_run.state`, and gates promotion on `GetShadowRunReportQuery`'s `diverged_count` against a threshold owned by 10's deploy runbook (not this story).
- `ShadowEvaluateHandler` reuses the exact evaluator function and exceptions-snapshot resolution code from 07.2.2 (T24) — no duplicated business logic, only a different trigger path and `mode` value, keeping the pure-function guarantee (FR-07-3) intact.
- On a bad promotion, the operator flips affected projects to `advisory` via 07.7.1's endpoint — that flow is entirely 07.7.1's; this story only states the invariant it must hold (AC5).

## 8. Security, privacy and performance

## 11. Rollout

- No feature flag: shadow evaluation is operator-triggered and additive; it never runs unless 10's deploy flow calls it.
- Merge order: T1 → T2 in one PR series on `develop`, after 07.2.2 and 07.7.1 land.
- Monitoring: `shadow_run` state/`diverged_count` visible to operators; a shadow campaign that never reaches `completed` (stuck tasks) alerts via the existing dead-letter/queue-lag SLIs (00 §11).
- Rollback: this story's own output *is* the rollback mechanism for a bad promotion (07.7.1's mode flip); rolling back the shadow-evaluation feature itself is a pure code revert — `shadow_run`/`shadow_run_result` rows are inert history with no downstream writer.
