## 1. Goal and non-goals

**Goal.** The pure evaluator (07.2.1) is extended with the two exception effects the area plan requires: an active quarantine excludes its case's failure from blocking the decision while keeping the failure visible (`quarantined_cases[]`, M14), and an active waiver is displayed beside a result ("approved by waiver") without ever flipping a confirmed failure to `PASS` (M15); a case whose write to quarantine was refused because it is on the critical list can never appear as an effective exclusion even if a stale snapshot somehow contains it (M18, defence in depth for T23). Separately, a time-driven sweeper (Cronos) transitions expired waivers/quarantine entries and records an audit row for each transition, so the *next* evaluation's exceptions snapshot excludes them automatically.

**Non-goals.** The waiver/quarantine tables and their write endpoints (07.3.1); resolving *which* ids go into a snapshot and hashing it (07.2.2-T3); the base completeness/outcome/decision computation (07.2.1); flaky detection and budget (07.4.1); any UI (09.3.1) — this story is the evaluator layer and the sweeper only.

## 2. User stories and acceptance criteria

- As a QA lead, I need a quarantined case's failure to stop blocking the release gate immediately, while still showing up as a known failure in the run's reasons, so quarantine hides gating impact, never the fact.
- As a `release_approver`, I need a waiver to never silently turn a `FAIL` into a `PASS` — it only annotates the result — so waivers cannot be used to launder a real defect.
- As the platform, I need an expired waiver or quarantine entry to stop affecting evaluations without anyone manually re-running anything.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An evaluation whose only failure is a case with an id present in the resolved exceptions snapshot's active-quarantine set yields `decision = PASS`, `quarantined_cases = [<case_id>]`, reason `quarantined_case_failed` (M14) |
| AC2 | An evaluation with a confirmed required-assertion failure that also has an approved, active waiver for that case yields `decision = FAIL` (never `PASS`), with `reasons` including `waiver_approved` alongside `required_assertion_failed` (M15) |
| AC3 | A property-based test generates hundreds of random combinations of active waivers over a failing required case; in every combination, `decision` is never `PASS` when the failure is not also quarantined |
| AC4 | A snapshot that (defensively, e.g. from a stale cache) contains a quarantine id for a case still on the pinned policy's critical list is ignored by the evaluator — the case's failure still gates (`decision = FAIL`, reason `required_assertion_failed`, M18) |
| AC5 | The expiry sweeper transitions exactly the `waiver`/`quarantine_entry` rows whose `expires_at <= now()` and current state is non-terminal, each exactly once even when two workers fire the same schedule concurrently (unique `(schedule_name, fire_at)`), and writes one audit row per transition |
| AC6 | After a waiver's `expires_at` passes and the sweeper runs, the *next* evaluation (new evidence revision or operator re-run) resolves a snapshot that excludes it — its `exceptions_hash` differs from the prior evaluation's — while the prior evaluation's stored row is unchanged |

## 4. Data model and migrations

None new. This story adds no table: it reads `waiver`/`quarantine_entry` (07.3.1) and writes to their existing `state`/`updated_at` columns (via the sweeper's `UPDATE`, which is the one legitimate `UPDATE` path on those tables — narrower than a full app-role grant: implemented as a `SECURITY DEFINER` function `evidgate_resolve.sweep_expired_exceptions(org_id)` so the app role's grants stay `SELECT, INSERT` and the sweeper's restricted `UPDATE` capability is auditable and scoped to the single transition, consistent with 00 §5.4.8's pattern for narrowly-scoped privileged functions) and one row per transition into the shared `audit` table (02).

## 5. API shapes (commands, queries, endpoints)

No new `/v1` endpoint. Internal extension + a scheduled command:

| Type | Shape |
|---|---|
| `IPolicyEvaluator.Evaluate` (07.2.1, extended) | same signature; the `ExceptionsSnapshotInput` (already accepted, resolved by 07.2.2-T3) now drives two branches: quarantine exclusion (before the "critical skip/blocked" and "confirmed failure" checks, but only for *non-critical* cases per T23/AC4) and waiver annotation (after the decision is computed, purely additive to `reasons[]`) |
| `SweepExpiredExceptionsCommand` | `ICommand` run by a Cronos schedule fire (`waiver_and_quarantine_expiry`); claims the fire via the `task` queue's unique `(schedule_name, fire_at)` row, calls the `SECURITY DEFINER` sweep function, writes one audit row per row transitioned | triggered by Cronos, never `/v1`; permission = worker service identity only |

## 6. States and transitions

`waiver.state`: this story adds the `approved → expired` transition (07.3.1 defined `requested`/`approved`/`revoked`; `expired` is written only here, never by a user command). `quarantine_entry.state`: adds `active → expired` (07.3.1 defined `active`/`removed`; `expired` is written only here). Both transitions are one-way and terminal, matching 00 §8.8.

## 7. Jobs and integrations

- **`waiver_and_quarantine_expiry` Cronos schedule** — fires on a fixed interval (e.g. hourly; exact cadence is an operational tuning knob, not a contract); each fire inserts a `task` row with `UNIQUE (schedule_name, fire_at)`, guaranteeing exactly one task per fire regardless of how many worker instances observe the due schedule (00 §5.3, no leader election). The claimed task calls `SweepExpiredExceptionsCommand`, which is idempotent by nature (re-running it against already-expired rows changes nothing further — the `WHERE state = 'active'/'approved' AND expires_at <= now()` guard makes a retry a no-op).
- Consumed by 07.2.2-T3 (the next snapshot resolution naturally excludes swept rows because it re-queries `state = 'active'`/`state = 'approved'`); 09.3.1 (UI shows the `expired` state and its audit trail).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T24 (evaluator stays pure) | the quarantine/waiver *effect* is computed from the already-resolved, already-immutable `ExceptionsSnapshotInput` — the evaluator still performs no DB read; only the *sweeper* (a separate command, not the evaluator) touches the database | `Architecture.Tests` (07.2.1-T1.2's purity rule) continues to pass unchanged after this story's evaluator extension |
| T23 (defence in depth) | even if a snapshot somehow carries a critical-list case's quarantine id, the evaluator's branch order checks "is this case currently on the pinned policy's critical list" (from `PolicyRevisionInput`, already an input) before honouring any quarantine entry for it | AC4 |
| 00 §5.4.8-style narrow privilege | the sweeper's `UPDATE` runs through a single `SECURITY DEFINER` function scoped to exactly the expiry transition, not a general app-role `UPDATE` grant, keeping 07.3.1's "no `UPDATE` for the app role" invariant intact | code review of the migration's grants; a raw app-role `UPDATE` attempt on `waiver`/`quarantine_entry` still fails |
| 00 §5.3 (no leader, exactly-once fire) | `UNIQUE (schedule_name, fire_at)` on the `task` row is the only serialisation mechanism | AC5 (concurrent-fire test) |
| S1 (parameterised SQL) | the sweep function and its caller use parameters throughout | code review |
| Authorization | `SweepExpiredExceptionsCommand` runs only under the worker's service identity, never behind a user-facing permission (mirrors 07.2.2's "decision integrity" pattern) | architecture test: no `/v1` route maps to it |
| Privacy | audit rows record actor (`system`), scope and the transitioned id only, no reason/content duplication beyond what 07.3.1 already stored | code review |
| Retention/deletion | none — expiry is a state change, not a deletion | — |

- **Telemetry:** the sweep command runs in a module span (`ModuleName.Policy`) and writes one audit row per transitioned row; sweep-run count and rows transitioned per run are the operational metric of §11 (built by 10); the evaluator branch adds `waiver_approved`/`quarantined_case_failed` to `reasons[]` and logs ids only.
- **Failure path:** a sweep that fails rolls back its transaction and the due rows wait for the next fire (idempotent by design, §11); a second fire at the same `fire_at` is refused by `UNIQUE (schedule_name, fire_at)` (AC5); a snapshot carrying a critical-list case's quarantine id still fails the case (T23 branch order); a raw app-role `UPDATE` to `expired` is refused by the 07.3.1 `waiver_guard` trigger.

Notes (from #PRNUM, 2026-10-08; from 07.3.1-T1, receiving task 07.3.2-T2): the `waiver` table (migration `0027`) does not keep the app role at `SELECT, INSERT` as §4/§8 assume: approve/revoke need `UPDATE (state, approved_by)`, granted column-level behind the `evidgate.waiver_guard` trigger. The guard refuses `→ expired` when `current_user = 'evidgate_app'`, so the T2.1 sweep must still be an owner-run `SECURITY DEFINER` function, and the §8 check becomes "a raw app-role `UPDATE` to `expired` (or of any column other than `state`/`approved_by`) still fails". `approved → expired` is the only expiry transition the guard allows; a due `requested` waiver needs a guard change in T2's own migration if the sweeper must expire it. `waiver_state_expiry_idx (org_id, project_id, state, expires_at)` serves a per-org/per-project due query; a cross-tenant sweep `where state='approved' and expires_at <= now()` without org/project predicates cannot range-scan it, so T2 either sweeps per org (as `sweep_expired_exceptions(org_id)` implies) or adds a partial index in its own migration (perf review P1 of 07.3.1-T1).

## 11. Rollout

- No feature flag: the evaluator extension only activates when a snapshot actually contains an active waiver/quarantine id (harmless no-op until 07.3.1 data exists in production); the sweeper is inert until its schedule's first fire.
- Merge order: T1 → T2 (the sweeper's correctness test in T2.2 exercises T1's evaluator branch, so T1 must land first).
- Monitoring: sweep-run count and rows-transitioned-per-run as an operational metric (owned by 10, not built here); audit rows are visible via `GET /v1/orgs/{o}/audit` (02.7.1). Rollback: revert the PR; the sweeper's idempotent design means a rollback mid-cycle leaves no partial state — due rows simply wait for the next deployed sweep.
