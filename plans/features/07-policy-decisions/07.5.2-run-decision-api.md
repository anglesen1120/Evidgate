## 1. Goal and non-goals

**Goal.** `GET /v1/runs/{r}/decision` returns the exact evaluation revision (with `decision`, `reasons[]`, `completeness`, hashes) currently attached to a run, or an explicit `pending` result before any evidence revision has been frozen — a single, cheap, read-only lookup gated by `decision:read`.

**Non-goals.** Writing or triggering an evaluation (07.2.2, 07.5.1); release-level decisions (07.5.3); CI delivery of the same data (07.6.1); flaky-fact detail beyond passthrough (07.4.2 defines the payload fields this endpoint surfaces).

## 2. User stories and acceptance criteria

- As a `qa_engineer` or CI script, I can poll one endpoint to learn a run's decision without knowing internal evaluation ids.
- As the Tech Lead, I know this read never triggers work — it is a pure query, safe to poll frequently.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A run with a `live` evaluation returns `200` with `{decision, completeness, outcome, reasons[], evidence_revision, policy_hash, evaluator_version, manifest_hash}` matching the stored row exactly |
| AC2 | A run with no evidence revision frozen yet returns `200 {status: "pending"}` (never `404`, never a fabricated decision) |
| AC3 | A caller without `decision:read` on the run's project gets `403` and no row is disclosed |
| AC4 | A run id in another org returns `404 run_not_found` (RLS makes it invisible, not merely forbidden) — never a cross-tenant row |
| AC5 | The endpoint issues exactly one SQL statement (no N+1) regardless of `reasons[]`/`flaky_facts[]` length |

## 4. Data model and migrations

No new table or column. Reads the existing `evaluation` table (owner 07.2.2-T1) filtered to the run's most recent `live` row (`mode = 'live'`, highest `evidence_revision`). No migration.

| Query source | Filter | Index used |
|---|---|---|
| `evaluation` | `org_id = current_org_id()` (RLS) AND `run_id = @r` AND `mode = 'live'` ORDER BY `evidence_revision` DESC LIMIT 1 | the existing partial unique `(org_id, run_id, evidence_revision) WHERE mode='live'` (T22) already serves this as a covering lookup — no new index needed |

### 5.1 Response body (reconciled proposal, S171; 07.5.2-T1 implements it in one pass)

`[DECISION]` S171 (accepted with this PR, S184; the coordinator's pick is recorded in the PR): one `200` body, one schema `Decision`, for both the evaluated and the pending case, so the three receivers (07.6.1-T2 `gate`, 09.3.1-T5 decision view, 09.3.1-T3 evidence panel) read one shape. Every member is **required** and nullable where a pending run has no value; a member is never omitted, because the `gate` CLI treats a body without a `decision` member as an error (exit 3, `packages/cli/README.md` Gate section). All members of an evaluated body are copied from ONE immutable `evaluation` row (the latest `live` row, §4; columns in 07.2.2 §4), except `status` and `url`, which are derived.

| Member | Type / null | Source row (immutable) | Value while `pending` | Receivers | Defined at |
|---|---|---|---|---|---|
| `status` | `pending` \| `evaluated`, not null | derived: no `live` `evaluation` row for the run → `pending` | `pending` | 09.3.1-T5, 07.6.1-T2 (exit 2 on `pending`) | AC2 here; 00 §9.3 (`GET /v1/runs/{r}/decision`, 00:354) |
| `decision` | `PASS` \| `FAIL` \| `INCONCLUSIVE` \| null | `evaluation.decision` | `null` — never `PASS`, never a default | 07.6.1-T2 (exit code), 09.3.1-T5 | 00 §8.5 (00:275), 00 §7 (upper case); `Decision.decision` in `contracts/openapi.yaml` |
| `evaluation_id` | uuid \| null | `evaluation.id` | `null` | 07.6.1-T2 (`--json`) | 07.2.2 §4 (`id`) |
| `evidence_revision` | integer \| null | `evaluation.evidence_revision` = `evidence_revision.revision_no` of the frozen revision (replaces the unserved `evaluation_revision`, a stale name from `docs/source/system-design-detailed.vi.md:206`; 00 §8.5 says `evidence_revision`) | `null` | 09.3.1-T5 ("evaluation revision"), 09.3.1-T3 (pins the selector to it) | 00 §8.5 (00:275); 07.2.2 §4 |

| `url` | absolute https URL string \| null | derived, **not a row**: the deployment's public base URL (the `PublicBaseUrl` option shape of `LoginOptions`) joined with the 09.3.1 run-detail route `projects/:projectId/runs/:runId` | the same URL (the run page exists before a decision) | 07.6.1-T2 (`--json`) | 09.3.1 §route table; new, defined here |

- **`missing` vocabulary (closed, eight codes, no invented code).** `missing_shard`, `count_mismatch`, `artifact_missing`, `build_mismatch`, `unknown_status`, `setup_error`, `stale_epoch`, `missing_result`. Sources: 00 §8.5 (00:275: "eight reasons, a closed list"), the DDL comment in `plans/features/05-runs-orchestration/05.3.2-finalize-and-reconciliation.md:53-54` for the first seven, and `migrations/0056_reconcile_missing_result.sql` for `missing_result` (that plan's CHECK note, line 196, still lists seven: it predates 0056 and is not changed here). A further code is a contract change (00 first, then a migration widening `evidence_revision_missing_check`). A body carrying any other literal is an evaluator defect: receivers render it as unavailable, never as a success.
- **`url` is null when the deployment has no public base URL** (never guessed from the API host, the CLI also derives nothing). It is a convenience link, not evidence, and is the one member with no immutable source row.
- **Pending never reads as PASS.** `status = pending` and `decision = null` together; every evaluation-derived member is `null`. The `gate` CLI keeps exiting 2 on `pending` and 3 on any `decision` outside the three upper-case values.
- **Dropped / not carried.** `exceptions_hash` and `exceptions_as_of` (00 §8.5) are not receivers' needs today and stay on the row (07.3.2 may add them); `flaky_facts[]` stays 07.4.2's additive field (§3). No member is added that has no receiver in the table.

### 5.2 Evidence revisions: a separate route (decided)

09.3.1-T3.2 needs to list a run's evidence revisions (immutable) to pin the panel and show "a newer revision exists". The decision body carries only the ONE evaluated revision (`evidence_revision`, `completeness`, `missing`), and an incomplete run can have a revision and no evaluation yet, so the list is not a field here. `[DECISION]` COORDINATOR-DECISION 171 (option A, owner review non-blocking): a separate read `GET /v1/runs/{run_id}/evidence-revisions` (`run:read`), owner task **05.3.2**, cursor-paged with the standard 00 §9.1 `cursor`/`limit`, newest first (`revision_no` descending); each item carries `revision_no`, `created_at`, `completeness`, `missing[]` (from `evidence_revision`, 05.3.2-T5.1) and the evaluation reference of that revision, `evaluation_id` (the coordinator's "evaluation revision"), `null` when no `live` evaluation exists yet. The decision body keeps only the one evaluated revision. Option B (embed `evidence_revisions[]` in `GET /v1/runs/{r}`) was rejected: unbounded array in a hot read. The task row was added by the S171 close-out as `05.3.2-T6` (S / 0.5 d, plan 05, no dependency on 07.5.2-T1 because `evaluation_id` is nullable). 09.3.1-T3.2 depends on it and stays held until it lands.

## 6. States and transitions

None new. Reads `evaluation.decision ∈ {PASS, FAIL, INCONCLUSIVE}` (00 §8.5) as-is; the `pending` result is an API-level state (no row exists yet), not a persisted enum value.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| S2 / C2 authorization in pipeline | `decision:read` permission checked by the pipeline before the handler runs; Architecture.Tests asserts the handler's declared permission matches the OpenAPI `x-permission` (T51) | `ArchitectureTests.EndpointPermissionsMatch` |
| 00 §5.4.7 / T2 tenant isolation | RLS via `evidgate.current_org_id()`; a foreign-org run id yields zero rows → `404`, never `403` leaking existence | AC4 |
| C1/C5 read-only | Handler runs in a read-only transaction, no outbox row, no write | Code review + `SET TRANSACTION READ ONLY` assertion in the handler's integration test |
| P3 no N+1 | Single parameterised SELECT; `reasons[]`/`flaky_facts[]` are JSONB/array columns returned in the same row | AC5, statement-count assertion |
| P1 hot-path budget | This is a polled endpoint (CI loops); latency budget taken from 00 §11's `decision` row, load-tested by 07.6.2-T3 | Referenced, not re-measured here (owned by 07.6.2-T3) |
| Privacy | No artifact content or secrets in the response; only ids, hashes and reason codes | — |

- **Authorization:** `GET /v1/runs/{r}/decision` requires `decision:read` inside the caller's tenant scope; another org's run is 404.
- **Retention/deletion:** read-only; the response persists nothing and holds only ids, hashes and reason codes.
- **Telemetry:** request latency and status on the route feed the 00 §11 hot-path budget; no artifact content or secret is logged.
- **Failure path:** a run without an evaluation answers `pending` (`decision: null`); unknown run 404, missing permission 403; the `gate` CLI maps pending to exit 2 and every error to exit 3.
