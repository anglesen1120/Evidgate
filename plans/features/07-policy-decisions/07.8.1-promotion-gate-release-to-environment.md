## 1. Goal and non-goals

**Goal.** A CD pipeline asks "may release R be promoted to target T?" and gets `allowed`, `blocked` or `pending` with machine-readable reasons. The answer comes from the release decision (07.5.3) evaluated under the target's policy (the target's pinned policy revision, else the project's active revision) and is stored as an immutable `promotion_check` row bound to the decision revision and the policy revision it used. A promotion is **never `allowed`** when any component is missing, when the aggregate is not complete, or when any required result is failed. A waiver is shown beside the result and cannot turn FAIL into `allowed`. Late evidence yields a new check row; old rows are never edited.

**Non-goals.** Performing the deployment or talking to a CD tool (Evidgate answers, the pipeline acts); approval workflows or manual override of `blocked` (`[OPEN]` O-promotion-override, V2 candidate, not designed here); environment health checks or post-deploy verification; per-target data isolation (05's environment revision is a different concept, `[OPEN]` whether `deploy_target` should reference it, see CR-07.8.1-3); web screens (09); healing.

## 2. User stories and acceptance criteria

- As a release manager, I define `staging` and `prod` targets, `prod` pinned to a stricter policy revision.
- As a pipeline author, one CLI call gates the deploy step and its exit code is the contract.
- As an auditor, I can list every promotion check for a release with the decision and policy revision it relied on.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `CreateDeployTarget` / `UpdateDeployTarget` / `DisableDeployTarget` | `POST …/deploy-targets`, `PATCH,DELETE /v1/deploy-targets/{t}` | `project:write` `[OPEN]` CR-07.8.1-1 | 201/200 · 412 · 409 `target_exists` · 422 |
| Query | `ListDeployTargets`, `GetDeployTarget` | `GET …` | `project:read` | 200 · 404 |
| Command | `CheckPromotionCommand` | `POST /v1/releases/{id}/promotions` body `{target}` | see CR-07.8.1-1 | 200 existing · 201 new · 404 · 409 `target_disabled` · 422 `unknown_target` |
| Query | `ListPromotionChecksQuery` | `GET /v1/releases/{id}/promotions?target=&cursor=` | `decision:read` | 200 · 404 |

`CheckPromotionCommand` flow (C1/C4): in one transaction read the latest `release_decision` (07.5.3 persisted row via its exported contract), load the target and its policy revision (pin or active), compute `status` with a pure function `PromotionRule.Evaluate(releaseDecision, policyRevision, exceptionsSnapshot)` (no clock, no I/O, T24 style), insert the `promotion_check` and the outbox row for `promotion.checked`, write audit. It never recomputes component evaluations and never enqueues aggregation (T87).

Rule order (first match wins): no decision → `pending`; any component `FAIL` on a required result → `blocked`; any component `missing` or `completeness != complete` → `blocked` (or `pending` while inside the late window and the policy allows waiting); INCONCLUSIVE → per policy; PASS under the target's policy → `allowed`. `allowed` is only reachable through the last branch.

## 6. States and transitions

`deploy_target`: `active ⇄ disabled` (disabled targets return 409 `target_disabled` on checks; history stays readable). `promotion_check` has no lifecycle: it is an immutable fact, `status` never changes. "Current answer" for a release and target is the newest row; a re-check after late evidence is a new row. `pending` is a stored answer for that decision revision, not a mutable state.

## 7. Jobs and integrations

- Outbox event `promotion.checked` `{check_id, release_id, target, status, release_decision_id, policy_revision_id}` committed with the row; delivered by 07.6.2-T1 to endpoints that list the type (07.6.3 `event_types`). A receiver gets at-least-once; `Evidgate-Event-Id` is the check id.
- CLI: `packages/cli` command `gate` reuses 07.6.1-T2's polling, deadline and exit mapping; `--target` selects the promotion form; `--wait` default deadline from config, ⚠️ default value `[INFERENCE]` 10 min, fixed in T3.1.
- Release aggregation arrives by the 07.5.3 task on `evaluation.created`; `--wait` therefore waits for a *new decision revision*, not for a recomputation triggered by the check.
- Metrics: `promotion_check_total{status}`, `promotion_check_latency_ms`; alert none in V1 (visible in 10.3.1 dashboards).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Missing evidence never yields PASS | `allowed` only from the explicit PASS branch; property test over generated component sets | AC3, T5 |
| Waiver is not a pass | waiver is a reason annotation only | AC5 |
| Immutability | no UPDATE/DELETE grant, refuse trigger | AC8 |
| Tenant isolation | RLS, composite FKs, 404 for foreign ids | AC12, isolation suite |
| Idempotency | unique key, conflict returns the winner | AC7 |
| Performance | one SELECT of the latest decision + one INSERT; p95 < 300 ms ⚠️ `[INFERENCE]` target to be measured in the M3 run | benchmark in T2.5 |
| Spoofing a target name | targets resolved by `(project, name)` inside the release's project only | `Promotion_TargetOfOtherProject_422` |

DoR review answers. **Authorization:** targets need `project:write`/`project:read`; the check needs the permission fixed by CR-07.8.1-1 (`[OPEN]`), history needs `decision:read`; every command re-checks tenant membership and project scope. **Retention/deletion impact:** `promotion_check` and `deploy_target` are tenant data kept with the release decision and erased only through the tenant/project deletion job (06.4.4-T1); no PII except `checked_by` (membership id). **Telemetry:** §7 metrics, trace attributes `release.id`, `target.name`, `promotion.status`, an audit row per check and per target change. **Failure path:** no release decision → `pending`; target disabled → 409; webhook or audit delivery failure never alters the committed row (AC13); CLI transport error exits 3, never 0.

## 11. Rollout

- Order: T1 → T2 → T4 and T3 in parallel (M3, V1) → T5. Depends on 07.5.3 (persisted release decision), 07.6.1-T2 (gate semantics) and 07.6.2-T1 (transport); 07.6.3 must list `promotion.checked` in its allow-list before T4 ships.
- Mode: the endpoint always answers; whether a pipeline treats `blocked` as stopping is the customer's CI choice. Advisory/enforcing (07.7.1) governs run decisions, `[OPEN]` whether a project in advisory mode returns `blocked` or `allowed-with-warning` for promotions (CR-07.8.1-2 follow-up, default: honest `blocked`, never rewritten by mode).
- Monitoring: `promotion_check_total{status}`; a sudden all-`pending` rate means the aggregation task (07.5.3) is lagging.
- Rollback: disable targets; rows are immutable and stay; additive migrations only.
