## 1. Goal and non-goals

**Goal.** Every project's delivery mode is `advisory` or `enforcing`, stored on `policy_activation`, resolved once per delivery and audited on every change. In `advisory` (the M2 default) decisions are computed, stored, shown and delivered — GitHub check runs are posted as informational and `evidgate gate` reports the real decision but exits 0 — so nothing blocks a customer release. In `enforcing` (M3) the same decision maps to the blocking exit codes and check-run conclusions defined in 07.6.1. Flipping the mode is a reversible, audited, one-field change.

**Non-goals.** The decision computation itself (07.2.2) and its raw exit-code/conclusion mapping (07.6.1) — this story applies the mode on top; shadow evaluation and rollback of a *policy* (07.7.2); the check-run/CLI plumbing (07.6.1); waiver/quarantine authority (07.3.x); UI (09).

## 2. User stories and acceptance criteria

- As a pilot lead, our projects start in `advisory` so Evidgate's decisions build trust for weeks before anything can block a release.
- As a release approver, flipping to `enforcing` is one audited action and rolling back to `advisory` is equally fast, so a bad policy revision never traps a customer release.
- As a CI engineer, the gate's exit code is still a real reflection of the decision in advisory mode (visible in JSON/logs), it just doesn't fail my build.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A project with no explicit mode resolves `advisory`; `evidgate gate` on a `FAIL`/`INCONCLUSIVE` decision exits `0` but the JSON/log output carries the real decision and a `mode: advisory` marker |
| AC2 | In `advisory`, GitHub delivery posts check runs with `conclusion: neutral` + a summary line naming the would-be conclusion (e.g. "advisory: would have failed"), never `success`/`failure` — so it informs without blocking |
| AC3 | `POST /v1/projects/{p}/policy-activation` (`release_approver`, `Idempotency-Key`, `If-Match`) sets `mode = 'enforcing'`; afterwards `gate` exits `1`/`2` on `FAIL`/`INCONCLUSIVE` and check runs post `failure`/`neutral` per the 07.6.1 mapping |
| AC4 | Every mode change writes an audited `policy_activation` row (actor, project, old mode, new mode, `activated_at`); flipping back to `advisory` is accepted and restores advisory behaviour |
| AC5 | A transport/auth failure in `gate` exits `3` in **both** modes — infrastructure errors are never masked by advisory |

## 3. Contracts touched

- `contracts/openapi.yaml`: `POST /v1/projects/{p}/policy-activation` gains the `mode` field in its body and response (`x-permission` = the activation permission already defined for this operation, exercised by `release_approver`; T51 asserts it).
- `contracts/cli.md`: `gate` documents the advisory behaviour — decision codes are *computed* identically in both modes, but the process exit is forced to 0 for policy decisions (codes 1/2) when `mode = advisory`; code 3 is unchanged.
- 00 §8.5's `evaluation.mode` (live/shadow) is **not** the same field — no contract change; this story's mode is per-project delivery policy, never stored on an evaluation row.

## 4. Data model and migrations

- `policy_activation` is already owned by 07 (07 §4: `org_id, project_id, policy_revision_id, mode, activated_by, activated_at`, `UNIQUE (org_id, project_id)`, audit row per change). This story uses the existing `mode` column — **no new table**.
- If the 07.2.x migrations created `mode` without an `'advisory'|'enforcing'` check or an audit trigger, `migrations/NNNN_decisions_activation_mode.sql` adds `CHECK (mode IN ('advisory','enforcing'))` and backfills `advisory` as the default for existing rows.
- RLS unchanged: table is already tenant-scoped (`unique (org_id, id)` per 00 §5.4.6/T3 asserted by the 02.6.1-T2 lint).

## 5. API shapes (commands, queries, endpoints)

- **Command `SetPolicyModeCommand`** → `POST /v1/projects/{p}/policy-activation` (role `release_approver`, `Idempotency-Key` required, `If-Match` on the activation row/ETag per 00 §9.1): validates `mode`, writes `policy_activation` + audit row in one tenant transaction; returns the new mode + `activated_at`. 422 `mode_invalid` on unknown values (00 §9.2); 412 on stale `If-Match`.
- **Query `GetPolicyModeQuery`** (`IQuery<string>`, Dapper read-only tx): resolved mode for a project; `advisory` when no row — used by the CI-delivery handler (07.6.1) and exposed to the CLI via a `mode` field on the existing `GET /v1/runs/{r}/decision` response (additive field, backward compatible).
- No new task-queue handler; `CiDeliveryHandler` and `evidgate gate` read the resolved mode and branch on it — mode resolution is a read, never a write.

## 6. States and transitions

Project delivery mode: `advisory → enforcing → advisory → …` — no terminal state, always reversible. Each transition is an audited `policy_activation` write, not a state machine row. `advisory` is the implicit initial state (no row = advisory).

## 7. Jobs and integrations

- No new jobs. Mode resolution joins the existing delivery path: `CiDeliveryHandler` (07.6.1-T1) calls `GetPolicyModeQuery` before posting and chooses `neutral`-informational vs real conclusion (AC2/AC3); `evidgate gate` (07.6.1-T2) reads `mode` from the decision response and forces exit 0 for policy codes under advisory.
- Audit rows flow into 02's audit surface (02.7.1) — actor, scope, hash per 07 §6.

## 11. Rollout

- M2 behaviour is advisory-by-default — no flag needed; absence of a `policy_activation` row *is* advisory.
- Enforcing ships in M3 per project only; 07-O2 (flip criteria: weeks of clean data? waiver rate?) must be closed by the Tech Lead + QA lead before the first enforcing flip — recorded at DoR, not coded.
- Monitoring: audit trail on `policy_activation`; metric `evidgate_policy_mode{mode}` gauge per project for ops visibility.
- Rollback: `POST …/policy-activation { "mode": "advisory" }` — one audited call; gate/check-run behaviour reverts on the next decision poll/delivery. No data is lost: evaluations and `ci_delivery` rows are untouched.
