## 1. Goal and non-goals

**Goal.** Let a project that has no automated suite for a release (or wants both kinds of evidence) get a release decision from manual evidence under the 00 §8.6 rules. A policy revision carries `release_evidence ∈ {automated, manual, both}` (default `automated`) and a manual required-case selector. Aggregation reads the immutable `manual_evidence_revision` rows bound to the release, writes a new append-only `release_decision` row and records every revision it used in the decision inputs, so `inputs_hash` covers them. A release with only manual evidence can PASS; missing, mismatched or non-passing manual evidence is never PASS.

**Non-goals.** Changing any consumed decision or evaluation row; counting an open or unbound run; an approval or override flow; per-case waivers (07.3.1 is unchanged); recording or closing runs (13.10.2); report layout (13.10.3); tracker issues (13.10.4). Existing policies keep `automated` and behave byte-for-byte as before.

## 2. User stories and acceptance criteria

- As a QA lead on a repository-less project, I close my manual run against release R and the release shows PASS, FAIL or INCONCLUSIVE with named reasons.
- As a release approver, I can see which manual evidence revisions a decision used and why a case did not pass.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A policy revision with `release_evidence` absent or `automated` is aggregated exactly as in 07.5.3: no manual input is read, and `inputs_hash` and decision rows equal those the 07.5.3 code produces for the same inputs |
| AC2 | Under `manual` or `both`, no closed manual run is bound to the release → INCONCLUSIVE, reason `manual_evidence_missing`; an open or unbound run never counts. This row is persisted **without any run or manual close**: a release that becomes `active` under a `manual`/`both` policy is aggregated on activation, so `GET` returns the INCONCLUSIVE row, not `pending`, while no run exists |
| AC3 | A required manual case whose latest result (from the most recently closed bound run containing it) is `failed` → FAIL, even if other required cases are missing |
| AC4 | A required case whose latest result is `blocked` or `skipped` → not PASS (decision INCONCLUSIVE), reason `manual_case_not_passed` |
| AC5 | At aggregation an explicit selector pins the versions of all required cases matching the selected requirements/cases, regardless of which cases any run selected. Compare closed bound evidence against that full set: a missing case or missing result gives `manual_case_not_executed` and, absent a required failure, INCONCLUSIVE. An empty selector still means all cases in closed bound runs. |
| AC6 | The release's component set differs from the set hashed at close → that revision is not evidence: INCONCLUSIVE, reason `manual_release_mismatch`; its results (including a failure) are not counted |
| AC7 | A release whose required manual cases all pass in closed bound runs, with `release_evidence = manual`, decides PASS with `completeness = complete` and no automated run |
| AC8 | Under `both`, PASS needs both sides PASS; a FAIL on either side is FAIL; otherwise INCONCLUSIVE. A manual PASS never hides an automated gap, and an automated PASS never hides a manual gap |
| AC9 | Every revision read is listed in the decision inputs (run id, revision id, `content_hash`, per-revision reasons) and covered by `inputs_hash`; the same inputs return the existing row, a newly closed run produces a new row, and no earlier row changes |

## 6. States and transitions

No new state machine. `release_decision` stays append-only; `pending` stays a read projection.

**Rule order (deterministic).** (1) `automated` → manual ignored. (2) Otherwise drop revisions whose stored components hash differs from the recomputed one (status `mismatch`, reason `manual_release_mismatch`). (3) No remaining closed bound revision → `manual_evidence_missing`. (4) For each pinned case version in the AC5 set, take the latest result from the most recently closed eligible run containing that version (order by close time, then revision id): `failed` → FAIL; `blocked`/`skipped` → `manual_case_not_passed`; no result or no matching version → `manual_case_not_executed`; `passed` → ok. (5) Manual outcome: FAIL if any required case failed, else PASS only when every required case passed, else INCONCLUSIVE. (6) Combine with the automated decision under `both`: FAIL if either FAIL, PASS only if both PASS, else INCONCLUSIVE. `superseded` marks a revision whose case results were all overridden by a later closed run; it is listed, not hidden.

## 7. Jobs and integrations

- `evaluation.created` (07.5.3), manual close (13.10.2-T5) and release activation enqueue `policy.release_aggregate`. For a newly active release with no runs, `manual`/`both` writes the AC2 INCONCLUSIVE row; `automated` still writes nothing before the first evaluation. `GET` stays read-only.
- On each policy activation to `manual` or `both`, sweep the project's active releases in bounded keyset pages. Enqueue each release with no decision or whose latest decision's `policy_revision_id` differs from the newly applicable revision (OI-07-24, OI-07-28). The handler rereads all eligible revisions; the unique key dedupes redelivery.
- The handler holds no lock across the read of revisions and the insert beyond the transaction the 07.5.3 command already uses; a revision committed after the read simply produces a later row on its own enqueue. No network or object-storage call is made.
- Policy for a manual-only release: the project's active policy revision at aggregation time, pinned in `policy_revision_id` (OI-07-24); `mixed_policy_revisions` keeps its 07.5.3 meaning for automated components.

## 8. Security, privacy and performance

- **Authorization:** the read stays `decision:read`; no new permission and no write endpoint. Policy revisions with the new fields need the existing `policy:write`. The reader contract returns only same-org, same-project revisions; a revision of another project's release is never loaded. Cross-org release id → 404.
- **Retention/deletion:** `manual_inputs` holds ids, hashes and reason codes only, no notes, labels or file data. A purged run or project removes its revisions through the 13.10.2/06 owner path; the decision row keeps its recorded hashes as history, and a re-aggregation after a purge yields `manual_evidence_missing`, never a stale PASS.
- **Telemetry:** the existing aggregation metrics, with closed labels (`policy_mode`, `reason_code`); no case, requirement or tenant text in labels. Audit and log lines carry release, revision and decision ids only.
- **Failure path:** a revision with a hash mismatch, missing reader data or an unknown status never yields PASS; the command fails closed to INCONCLUSIVE with a reason or leaves the task for retry. A redelivered task adds no row. If the migration is not applied the writer refuses to run for `manual`/`both` policies rather than dropping the inputs. One bounded set-based read per release, not one per case (P3).
