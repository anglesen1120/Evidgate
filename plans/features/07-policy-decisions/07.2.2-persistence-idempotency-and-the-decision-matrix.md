## 1. Goal and non-goals

**Goal.** The pure evaluator's output becomes exactly one durable `evaluation` row per `(org_id, run_id, evidence_revision, policy_revision_id, evaluator_version, mode)`, with at most one `live` row per `(org_id, run_id, evidence_revision)` (T22); two concurrent workers evaluating the same pair never produce two rows — the loser's `INSERT` fails on the unique constraint and the handler returns the winner's row instead; the resolved exceptions snapshot (active waiver/quarantine ids as of trigger time) is captured and hashed onto the row before the evaluator runs.

**Non-goals.** The evaluator's own computation (07.2.1); the waiver/quarantine tables themselves (07.3.1); late-evidence re-evaluation scheduling and the operator re-evaluation route (07.5.1); the `GET /v1/runs/{r}/decision` read endpoint (07.5.2); CI/webhook delivery (07.6.1/07.6.2); advisory/enforcing mode and shadow comparison (07.7.1/07.7.2).

## 2. User stories and acceptance criteria

- As the platform, when reconcile freezes an evidence revision, I need exactly one `evaluation` row to exist afterwards even if two worker instances race to process the same outbox event.
- As a Tech Lead, I need every row of the 00 §8.6 decision matrix (M1–M18) proven against the *persisted* evaluation, not just the in-memory function, so a stored decision is trustworthy.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Two concurrent calls to the evaluation task handler for the same `(org_id, run_id, evidence_revision, policy_revision_id, evaluator_version, mode)` result in exactly one row in `evaluation`; both callers receive the same row (`EvaluateRunCommand` result), proven with `Task.WhenAll` over two handler invocations against one Testcontainers.PostgreSQL instance |
| AC2 | A `mode = shadow` evaluation for the same `(org_id, run_id, evidence_revision, policy_revision_id, evaluator_version)` as an existing `live` row inserts a second row (T22) and never overwrites or is rejected by the `live` partial-unique constraint |
| AC3 | Every row of the 00 §8.6 matrix (M1–M18) has a passing xUnit test against the persisted-and-reloaded evaluation, not only the in-memory `EvaluationResult` |
| AC4 | Two evaluation runs with different active-waiver sets at trigger time produce different `exceptions_hash` values; two runs with the identical active set produce the identical hash |
| AC5 | A crash after the evaluator computes but before the `INSERT` commits is recovered by the outbox retry: the task is re-claimed (`FOR UPDATE SKIP LOCKED`), re-run, and produces the identical row (byte-identical `reasons[]`, `decision`, hashes) — proven by killing the handler mid-transaction in a test double and re-invoking it |
| AC6 | A run with `purpose = replay` (05.2.1-T5, granted via a server-issued replay grant) is evaluated with `mode = shadow` only (T67): the handler's INSERT writes `mode = shadow` even when no `live` row exists for the pair, no `live` row is ever produced for the replay run, and the resulting `evaluation` is never returned by 07.5.3's release-aggregation read |

## 5. API shapes (commands, queries, endpoints)

No public `/v1` endpoint in this story (the read endpoint is 07.5.2). Internal command, dispatched by the `task` queue (00 §5.3), running through the same Mediator pipeline as any other command (C2: telemetry → validation → tenant tx → authorization → idempotency → handler → outbox → commit — the worker's task dispatcher opens the tenant scope from the outbox row's `org_id`/`project_id` before invoking the command, so no pipeline step is skipped for background work):

| Command | Handler does | Trigger | Idempotency |
|---|---|---|---|
| `EvaluateRunCommand` | resolves exceptions snapshot (07.2.2-T3) → loads `EvidenceRevisionInput`/`PolicyRevisionInput` → calls `IPolicyEvaluator.Evaluate` (07.2.1) → `INSERT … ON CONFLICT (org_id, run_id, evidence_revision, policy_revision_id, evaluator_version, mode) DO NOTHING RETURNING id`; on conflict, `SELECT` the existing row and return it as the command result | outbox row written by 05's reconcile (05.3.2) claimed via the `task` queue's `FOR UPDATE SKIP LOCKED` | the unique constraint *is* the idempotency key (FR-07-4) — no separate `idempotency_record` row is needed, because this command has no external caller supplying an `Idempotency-Key` header |

No query in this story: reading a persisted evaluation is 07.5.2's `GetRunDecisionQuery`.

## 6. States and transitions

None new. `evaluation` rows are immutable once inserted (no `state` column — a row simply exists or does not, per the unique key). The `live`/`shadow` split is a value of `mode`, not a state transition (a `shadow` row never becomes `live`; a rerun that should be `live` is a distinct `INSERT`, never an `UPDATE` of a `shadow` row).

## 7. Jobs and integrations

- The task handler itself *is* the integration point: `task` queue row → `EvaluateRunCommand` → `evaluation` row → outbox row for `evaluation.created` (consumed by 07.6.1 CI delivery and 07.6.2 webhooks, out of this story's scope) — this story only guarantees the `evaluation` row is written correctly and exactly once per key; the outbound webhook/CI dispatch is a separate outbox row written in the same transaction (C7) but delivered by 07.6.x.
- Consumed by 07.5.1 (late-evidence re-evaluation reuses the same `EvaluateRunCommand`), 07.5.2/07.5.3 (read the persisted row), 07.6.1/07.6.2 (react to the `evaluation.created` outbox event), 07.7.1/07.7.2 (advisory/shadow comparison reads persisted rows), 08.3.3 (healing reads the live decision to know whether an incident's run gated).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T22 (unique key + one-live-row) | migration constraints exactly as specified; `ON CONFLICT DO NOTHING RETURNING` + fallback `SELECT` implements "loser returns the winner's row" | AC1, AC2 |
| 00 §5.3 (task queue, no leader) | claim via `FOR UPDATE SKIP LOCKED`; retries on outbox redelivery are idempotent because the unique constraint, not the handler's own logic, is the arbiter | AC5 |
| 00 §5.7 P2 (batch writes, one round trip) | the `INSERT … ON CONFLICT` is one statement; no per-row loop for the (single) evaluation row | code review |
| 00 §5.7 P5 (no network in a DB tx) | the evaluator call (07.2.1) is pure/in-memory; loading inputs is DB-only reads before the write transaction opens (or inside the same read-write tx, still DB-only) — no HTTP/S3/LLM call anywhere in this handler | code review; `Architecture.Tests` extends its evaluator-purity rule (07.2.1-T1.2) to assert the handler's transaction scope contains no `HttpClient` usage |
| 00 §9.4/T28 (decision latency) | this handler is the "stored evaluation" endpoint of the p95 < 60 s budget (00 §11); the histogram itself (`evidence_frozen_at → evaluation.created_at`) is emitted here and measured by 07.6.2-T3's load fixture | 07.2.2-T1.1: the handler emits an OpenTelemetry histogram metric at commit time |
| S1 (parameterised SQL) | Dapper parameters / EF Core for the single `INSERT`; no string-built SQL | code review |
| Authorization | no tenant-facing endpoint writes an `evaluation` row (00 §6 "Decision integrity"); the command runs only under the worker's service identity, never behind a user-facing permission check | Architecture test: no `/v1` route maps to `EvaluateRunCommand` |
| Privacy | `reasons[]`/`missing[]` carry ids and reason codes only, never artifact content (00 §9.2, §6) | code review of the persisted columns' types (`text[]`, no `jsonb` blob of raw report data) |
| Retention/deletion | evaluations reference artifact ids, not content; artifact deletion under 06's retention never breaks this row — a later read reports "artifact missing (deleted by retention)" (00 §6), not a foreign-key failure, because there is no FK from `evaluation` to `artifact` | out of this story's test scope (06 owns that read-time behaviour); no impact on this story's writes |
