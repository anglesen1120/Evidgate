## 1. Goal and non-goals

**Goal.** Given a frozen evidence revision containing one or more retried planned executions, the evaluator detects every "retry fail → pass" fact from the attempt history and applies the pinned policy revision's flaky budget so that: a critical case's retry fail → pass blocks the run (pilot default), a non-critical breach within budget only warns, and a non-critical breach beyond budget yields `INCONCLUSIVE` with `flaky_budget_exceeded` (T27) — never a silent `PASS`.

**Non-goals.** Cross-run history, trend labels and CLI/webhook surfacing of flaky reasons (07.4.2); waiver/quarantine interaction with flaky cases (07.3.2); release-level aggregation of flaky facts (07.5.3); changing the retry mechanics themselves (owned by 05/case_attempt).

## 2. User stories and acceptance criteria

- As a `release_approver`, I want a retried critical case's flip from fail to pass to still block the release, so retries can never quietly launder a real defect.
- As a `qa_engineer`, I want to see when a non-critical case flaked within the agreed budget without the run going red, so noisy environments do not block delivery unnecessarily.
- As the Tech Lead, I want an over-budget flaky run to come back `INCONCLUSIVE`, never `PASS`, so the gate never fabricates confidence it does not have.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An evidence revision with `execution_key` X having attempts `[failed, passed]` and X on the policy's `critical_ids` yields `decision = FAIL`, `reasons` includes `flaky_critical_retry_pass` (matrix M10) |
| AC2 | Same attempt shape as AC1 but X **not** critical and the run's total non-critical flaky count is within the policy's `flaky_budget` yields `decision = PASS` (all else passing), `reasons` includes `flaky_within_budget` (matrix M11) |
| AC3 | Same as AC2 but the non-critical flaky count exceeds `flaky_budget` yields `decision = INCONCLUSIVE`, `reasons` includes `flaky_budget_exceeded`, never `PASS` (matrix M17, T27) |
| AC4 | An execution_key with attempts `[passed]` (no retry) contributes no flaky fact and no flaky reason |
| AC5 | An execution_key with attempts `[failed, failed]` (never recovers) contributes no "retry fail → pass" fact — it is a plain failure, not flaky |
| AC6 | The evaluator run over the same evidence + policy + exceptions snapshot twice (fresh process) yields byte-identical `flaky_facts` ordering and reasons (determinism, T24) |

## 3. Contracts touched

- 00 §8.6 decision table rows M10/M11/M17 — implemented, not changed.
- 00 §8.5 `evaluation.reasons[]` — no new persisted column; this story adds the reason *codes* `flaky_critical_retry_pass`, `flaky_within_budget`, `flaky_budget_exceeded` to the existing array (already named in 00 §8.6 and enumerated in 07 §7's matrix). No OpenAPI schema change: `reasons[]` is already `string[]` (07.5.2-T1 exposes it read-only).
- The evaluator's purity contract (T24, FR-07-3) is extended, not broken: flaky detection reads only the frozen evidence revision's attempt list plus the pinned policy revision's `flaky_budget`/`critical_ids` fields — both already inside the evaluator's three immutable inputs. No new I/O.

## 4. Data model and migrations

None. No new tables or columns. This story reads existing rows only:

- `case_attempt` (owner 05, `05.3.3-T1`) — frozen into the evidence revision before the evaluator runs; read via the evidence-revision attempt set, never a live query, so freeze semantics (00 §8.5) are preserved.
- `policy_revision.body` (owner 07.1.1) — `critical_ids[]` and `flaky_budget` fields, already part of the 00 §8.6 policy fields.

No migration file for this story.

## 5. API shapes (commands, queries, endpoints)

No new endpoint or command/query. This story adds one pure, in-process service to the evaluator library used by `07.2.1-T1`:

| Type | Name | Shape |
|---|---|---|
| Pure function | `IFlakyDetector.Detect(IReadOnlyList<CaseAttemptSnapshot> attempts)` | groups by `execution_key`, orders by `attempt_no`, returns `IReadOnlyList<FlakyFact>` where `FlakyFact = { ExecutionKey, RetryCount, HadRetryFailToPass }` |
| Pure function | `FlakyBudgetPolicy.Apply(IReadOnlyList<FlakyFact>, PolicyRevisionBody, ISet<Guid> criticalExecutionKeys)` | returns `(DecisionEffect effect, IReadOnlyList<string> reasons)`, `DecisionEffect ∈ { none, force_fail, force_inconclusive }` consumed by `07.2.1-T2`'s decision computation |

Both are plain C# methods in `Evidgate.Modules.Policy` (internal), called synchronously inside the `07.2.2-T1` task handler's transaction — no separate round trip, satisfying P3/P5.

## 6. States and transitions

None new. `case_attempt` normalized status (`passed | failed | skipped | timed_out | error | blocked`, 00 §8.3) is read as-is; `evaluation.decision` stays within the existing `PASS | FAIL | INCONCLUSIVE` enum (00 §8.5) — this story only adds the *reasons* that justify a given decision, not new states.

## 7. Jobs and integrations

- Runs inline inside the existing `Evidgate.Worker` evaluation task handler (`07.2.2-T1`, 00 §5.3 `task` queue) — no separate schedule or job.
- Consumes `case_attempt` rows written by ingest (`05.3.3-T1`) once they are part of the frozen evidence revision (`06.5.1-T1` freeze interface).
- Feeds `07.4.1-T2`'s budget application, which feeds `07.2.1-T2`'s decision computation in the same call.

## 11. Rollout

- No feature flag: flaky detection and budgeting are part of the core evaluator (`evaluator_version` bump records the behaviour change, 00 §8.5) and take effect for every evaluation once deployed — advisory mode (07.7.1) already keeps M2 non-blocking regardless.
- Merge order: T1 (detection) before T2 (budget application) — T2 has no input without T1.
- Monitoring: flaky reason counts are visible via the existing `evaluation.reasons[]` (no new dashboard in this story; 07.4.2-T1 wires them into webhooks/CLI).
- Rollback: revert the PR; evaluations already written are immutable (00 §8.5) and keep their `evaluator_version`, so no historical row needs correction.
