## 1. Goal and non-goals

**Goal.** A policy revision, once written, is byte-identical forever: same body hashes to the same `sha256:<hex>` (RFC 8785 canonical JSON), a stored revision can never be updated, activating a new revision changes nothing for a run that already pinned an older one, and every later story (evaluator, waivers, quarantine, CI delivery) reads the pinned revision through one query.

**Non-goals.** The evaluator itself (07.2.1); waiver/quarantine tables (07.3.1); the decision matrix and persistence of `evaluation` rows (07.2.2); enforcing-mode blocking behaviour (07.7.1, M3); reusable cross-project policy templates (V3, `[OPEN]`).

## 2. User stories and acceptance criteria

- As a `release_approver`, I write a new policy revision and it is rejected if it repeats a byte-identical body already on file, so the catalogue of revisions never has duplicate content.
- As the platform, when a run is created I pin its evaluation to the currently active policy revision, and activating a different revision afterwards never moves that run's target.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/policies` with a body identical (after RFC 8785 canonicalisation) to an existing revision's body for the same `(org_id, project_id)` returns `200` with the existing revision (same `id` and `hash`), never a second row; a different body returns `201` with a new revision (2026-10-02: aligned with the command table and the idempotency note) |
| AC2 | Two calls that `INSERT`/`UPDATE` a `policy_revision` row directly via raw SQL from the app role both fail: the app role has no `UPDATE`/`DELETE` grant on the table (C6) |
| AC3 | A policy body with a field not in the 00 §8.6 schema is rejected `422` with `error.details[].path` pointing at the field (Corvus validation) before any row is written |
| AC4 | `POST /v1/projects/{p}/policy-activation` sets `policy_activation.policy_revision_id` for the project; a run created *before* the activation keeps its original `run.policy_revision_id` even after a second activation call (query the run's pin, assert unchanged) |
| AC5 | `GET /v1/policies/{id}/revisions` lists append-only in `revision_no` order; a stale `If-Match` on a draft returns `412` with the current revision id in `error.details` |

## 5. API shapes (commands, queries, endpoints)

**Commands** (`ICommand<TResult>`, EF Core write model, C1/C4):

| Command | Handler does | Endpoint | Permission | Status / errors |
|---|---|---|---|---|
| `CreatePolicyRevisionCommand` | canonicalise body, compute hash, `INSERT`; unique-hash conflict returns the existing revision instead of a new row | `POST /v1/projects/{p}/policies` | `policy:write` | `201` new revision, `200` with the existing revision on duplicate hash within the project, `422 policy_unknown_field` on schema violation |
| `ActivatePolicyCommand` | upsert `policy_activation` for `(org_id, project_id)`, write the audit row, in one transaction | `POST /v1/projects/{p}/policy-activation` | `policy:write` (`release_approver`) | `200`, `404` if the revision id does not exist in this project |

**Queries** (`IQuery<TResult>`, Dapper, read-only tx, C5):

| Query | Endpoint | Permission | Notes |
|---|---|---|---|
| `GetPolicyRevisionQuery` | `GET /v1/policies/{id}` | `policy:read` | includes `state`, `hash`, `body` |
| `ListPolicyRevisionsQuery` | `GET /v1/policies/{id}/revisions` | `policy:read` | cursor pagination on `(revision_no, id)`; `If-Match` on the caller's cached draft returns `412` with the current id (00 §9.1) if stale |
| `GetActivePolicyQuery` | internal (no `/v1` route) | called in-process | used by 05.2.1-T1's run-create handler to resolve the id to pin; also by 07.2.2's evaluation handler to confirm the pinned id still resolves to a `policy_revision` row |

Idempotency: `CreatePolicyRevisionCommand` needs no `Idempotency-Key` — the content hash is its own idempotency key (a retried identical POST returns the same revision via the unique-hash path, not a `409 idempotency_conflict`; a genuinely different body is a new revision, never a conflict).

## 6. States and transitions

`policy_revision.state`: `draft → active → retired`. A revision starts `draft` (mutable body only before the first successful `INSERT`, i.e. within the same transaction — once committed the row is immutable regardless of `state`); an `ActivatePolicyCommand` targeting a `draft` moves it to `active` and the previously active revision for the project (if any) to `retired`. `retired` is terminal; no revision returns to `draft` or `active` from `retired` (a correction is a new `CreatePolicyRevisionCommand`).

`policy_activation`: one row per project, `UPSERT`ed on every `ActivatePolicyCommand`; there is no "unset" state — a project without an activation row has no active policy and run-create at 05.2.1-T1 fails closed (`422 policy_not_active`, defined by 05, not re-declared here).

Run pinning (FR-07-2): `run.policy_revision_id` is written once at run creation (05.2.1-T1) by reading `GetActivePolicyQuery`; it is never updated by `ActivatePolicyCommand` — the column has no `UPDATE` path from this story's code, only from run-create's own transaction.

## 7. Jobs and integrations

- No background task in this story: activation and revision creation are synchronous, single-transaction writes (00 §5.3 applies to *async* work only).
- Consumed by 05.2.1-T1 (run create resolves and pins `policy_revision_id`), 07.2.2-T1 (evaluation handler loads the pinned revision's `body` as one of the evaluator's three inputs), 07.3.1-T2 (quarantine write checks the active revision's critical-case list), 09.2.1/09.7.1 (policy editor and revision-history UI read `ListPolicyRevisionsQuery`/`GetPolicyRevisionQuery`).

**Notes (07.1.1-T1 delivery, migration `0025_policy_add_policy_revision.sql`, branch `feature/07.1.1-T1-s4`):**

- Hand-over to 07.1.1-T4: the app role holds `SELECT, INSERT` only (§4), so the §6 `draft → active → retired` move needs an explicit write path (a column-level `UPDATE (state)` grant or an owner `SECURITY DEFINER` function); T4 decides and records it. The `policy_revision_immutable` trigger already allows exactly `draft → active` and `active → retired`, sets `version = old.version + 1` on each such move (a caller-supplied `version` is ignored), and refuses `DELETE` and any change to identity, `body` or `hash`, whoever issues it. `PolicyRevisionStore.AppendAsync` returns `Result<PolicyRevisionAppend>`: `404` project not found (missing or soft-deleted) and `503` busy on lock timeout, for T3's command to pass through.
- Hand-over to 07.1.1-T2/T3 (T1 security review): `PolicyRevisionStore.AppendAsync` takes the caller's `sha256:<hex>` hash and checks only its shape, and its dedupe path returns the stored row by hash without comparing bodies. T2's `IPolicyHasher` should become the only producer of that hash (the store computes it from the body, or requires a hasher-issued value type), so a stored `body` can never sit under another content's address.
- Hand-over to 07.1.1-T3 (T1 performance review): the `body` column has no size cap (§4: validated by Corvus at the edge, "not re-validated by a DB check"; precedents 0021/0022/0024 cap their jsonb columns). T3 sets the request-body limit for `POST /v1/projects/{p}/policies` (manifest precedent: raw body capped before parsing) and records the number in 00 §8.6 or this plan.
- Deviations: no separate `(org_id, project_id, revision_no desc)` index (the unique btree on `(org_id, project_id, revision_no)` serves the newest-first list by backward scan, P4; T3.2's `EXPLAIN` test confirms); `revision_no` is assigned under a lock on the parent `project` row (05.1.2 precedent), because locking "the last revision row" cannot serialise a project's first append; `created_by` has no foreign key (audit fact; a member may leave).
- Downstream references to 07.1.1-T1: 01.8.1-T4.1 (`seed-dev` sample policy "through the 07.1.1-T1 command") and 05.3.2 (`Evidgate.Modules.Policy.Contracts` read). T1 ships the table and the internal `PolicyRevisionStore`, not a command or a contracts interface: the write command is `CreatePolicyRevisionCommand` (07.1.1-T3) and the cross-module read is `GetActivePolicyQuery`/`GetPolicyRevisionQuery` (07.1.1-T3/T4), so both consumers wait for those tasks.
- `tests/Isolation.Tests/TenantRowFactory.cs` gained one value rule for `policy_revision.hash` (coordinator-approved additive touch of a Session 1 file).
