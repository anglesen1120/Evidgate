## 1. Goal and non-goals

**Goal.** A policy revision, once written, is byte-identical forever: same body hashes to the same `sha256:<hex>` (RFC 8785 canonical JSON), a stored revision can never be updated, activating a new revision changes nothing for a run that already pinned an older one, and every later story (evaluator, waivers, quarantine, CI delivery) reads the pinned revision through one query.

**Non-goals.** The evaluator itself (07.2.1); waiver/quarantine tables (07.3.1); the decision matrix and persistence of `evaluation` rows (07.2.2); enforcing-mode blocking behaviour (07.7.1, M3); reusable cross-project policy templates (V3, `[OPEN]`).

## 2. User stories and acceptance criteria

- As a `release_approver`, I write a new policy revision and it is rejected if it repeats a byte-identical body already on file, so the catalogue of revisions never has duplicate content.
- As the platform, when a run is created I pin its evaluation to the currently active policy revision, and activating a different revision afterwards never moves that run's target.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/policies` with a body identical (after RFC 8785 canonicalisation) to an existing revision's body for the same `(org_id, project_id)` returns `200` with the existing revision (same `id` and `hash`), never a second row; a different body returns `201` with a new revision (2026-10-02: aligned with the command table and the idempotency note) |

## 5. API shapes (commands, queries, endpoints)

**Commands** (`ICommand<TResult>`, EF Core write model, C1/C4):

| Command | Handler does | Endpoint | Permission | Status / errors |
|---|---|---|---|---|
| `CreatePolicyRevisionCommand` | canonicalise body, compute hash, `INSERT`; unique-hash conflict returns the existing revision instead of a new row | `POST /v1/projects/{p}/policies` | `policy:write` | `201` new revision, `200` with the existing revision on duplicate hash within the project, `422 policy_unknown_field` on schema violation |
| `ActivatePolicyCommand` | under the project row lock, move the named revision `draft → active` and the previous active one `active → retired`, upsert `policy_activation` for `(org_id, project_id)`, write the audit row, in one transaction (07.1.1-T4) | `POST /v1/projects/{p}/policy-activation` | `policy:write` (`release_approver`) | `200` (`changed=false` when the revision is already active), `404` if the revision id does not exist in this project or tenant, `409 invalid_transition` for a `retired` revision, `422` for a malformed body, `enforcing` mode (until 07.7.1), a non-UUID `critical_cases` entry, or `critical_case_quarantined` (a critical case has an active quarantine entry), `503` busy on the project-row lock timeout |

**Queries** (`IQuery<TResult>`, Dapper, read-only tx, C5):

| Query | Endpoint | Permission | Notes |
|---|---|---|---|
| `GetPolicyRevisionQuery` | `GET /v1/policies/{id}` | `policy:read` | includes `state`, `hash`, `body` |
| `ListPolicyRevisionsQuery` | `GET /v1/policies/{id}/revisions` | `policy:read` | cursor pagination on `(revision_no, id)`; `If-Match` on the caller's cached draft returns `412` with the current id (00 §9.1) if stale |
| `GetActivePolicyQuery` | internal (no `/v1` route) | called in-process | used by 05.2.1-T1's run-create handler to resolve the id to pin; also by 07.2.2's evaluation handler to confirm the pinned id still resolves to a `policy_revision` row |

Idempotency: `CreatePolicyRevisionCommand` needs no `Idempotency-Key` — the content hash is its own idempotency key (a retried identical POST returns the same revision via the unique-hash path, not a `409 idempotency_conflict`; a genuinely different body is a new revision, never a conflict).

## 6. States and transitions

`policy_revision.state`: `draft → active → retired`. A revision starts `draft` (mutable body only before the first successful `INSERT`, i.e. within the same transaction — once committed the row is immutable regardless of `state`); an `ActivatePolicyCommand` targeting a `draft` moves it to `active` and the previously active revision for the project (if any) to `retired`. `retired` is terminal; no revision returns to `draft` or `active` from `retired` (a correction is a new `CreatePolicyRevisionCommand`).

`policy_activation`: one row per project, `UPSERT`ed on every `ActivatePolicyCommand`; there is no "unset" state — a project without an activation row has no active policy, and run-create at 05.2.1 then writes `run.policy_revision_id = null` and uses the `EVIDGATE:Runs` defaults (07.1.1-T4 [DECISION] Q1, coordinator-decided 2026-10-11; supersedes the earlier `422 policy_not_active` draft).

Run pinning (FR-07-2): `run.policy_revision_id` is written once at run creation (05.2.1-T1) from `IPolicyContracts.GetActivePolicyAsync` (the in-module `GetActivePolicy` reader behind the `Evidgate.Modules.Policy.Contracts` interface); it is never updated by `ActivatePolicyCommand` — the column has no `UPDATE` path from this story's code, only from run-create's own transaction.

## 7. Jobs and integrations

- No background task in this story: activation and revision creation are synchronous, single-transaction writes (00 §5.3 applies to *async* work only).
- Consumed by 05.2.1-T1 (run create resolves and pins `policy_revision_id`), 07.2.2-T1 (evaluation handler loads the pinned revision's `body` as one of the evaluator's three inputs), 07.3.1-T2 (quarantine write checks the active revision's critical-case list), 09.2.1/09.7.1 (policy editor and revision-history UI read `ListPolicyRevisionsQuery`/`GetPolicyRevisionQuery`).
