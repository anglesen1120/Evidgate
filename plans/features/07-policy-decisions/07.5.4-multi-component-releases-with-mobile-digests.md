## 1. Goal and non-goals

**Goal.** A release whose components include a mobile app build aggregates its component decisions exactly like a web/service component: the app component's manifest digest is matched against the release's declared digest for that component, and a mismatch is reported as `missing`, never averaged or silently dropped. The extension lands in the **persisted** `release_decision` aggregate: the `evaluation.created` aggregation task (07.5.3, T87) resolves app components and writes `component_kind` into `component_evaluations[]` at aggregate-write time — never a read-time projection. Adding a mobile component to a release changes nothing about how existing (non-app) components are aggregated.

**Non-goals.** Single/uniform-component release aggregation logic itself (07.5.3, already built); the mobile adapter that produces the app manifest and digest (04.5.1); `release`/`release_component` schema ownership (05.6.1 owns the tables; 07 only reads them through 05's exported view, 00 §5.1); release-level UI (09); healing shadow results (08, out of scope for 07 entirely).

## 2. User stories and acceptance criteria

- As a release approver, I see one release decision that correctly includes the mobile app's result, so I never have to check the app run separately from the web/service runs.
- As a release approver, if the app build in the release does not match what actually ran, I see that component reported as missing evidence, not a stale pass carried over from a different build.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A release with one web component and one `app` component, both matching the release's declared manifest digests, aggregates to the same decision as if all components were non-app (`release_decision.decision` follows 00 §8.6 over all components) |
| AC2 | An `app` component whose run's `manifest_hash` does not match the release's declared digest for that component is reported in `release_decision.reasons[]` as `component_missing` for that component id, and the release decision is never `PASS` while a required component is missing |
| AC3 | `release_decision.component_evaluations[]` persists a `component_kind` field (`web` \| `service` \| `app`) per entry — written by the aggregation task at aggregate time (T87), not computed by the GET — so the UI (09, out of scope here) can label app components distinctly |
| AC4 | A release built entirely of non-app components (07.5.3's existing scope) aggregates identically before and after this story — golden fixture `release-no-app` is unchanged |

## 3. Contracts touched

- `contracts/openapi.yaml`: `release_decision.component_evaluations[]` item schema gains `component_kind` (additive, backward compatible — existing consumers ignore an unknown field only if declared `additionalProperties: false` is avoided for this array item; here the field is added to the documented schema so no consumer breaks, 00 §9.1).
- No new endpoint. `GET /v1/releases/{id}/decision` (`decision:read`, existing, 07.5.1/07.5.3) response body gains the field.
- No change to 00 §8.5/§8.6 decision rules; this story only extends *which* components the same rules run over.

## 4. Data model and migrations

- No table owned by 07 changes shape (`release_decision.component_evaluations` is already `jsonb[]`/`jsonb`; adding a key to its documented shape needs no migration).
- `release_component` (owned by 05, read by 07 through 05's exported view) must already carry `component_kind` and the declared `digest` for the app build — 04.5.1-T2 is the mobile-digest producer this story depends on, and 07.5.3-T1 is the aggregation query this story extends. If 05's `release_component` view does not yet expose `component_kind`, that is a 05-owned gap; this story only consumes the column.
- `[OPEN]` The area plan (§4) does not name the exact column that carries `component_kind` on 05's `release_component`; this feature plan assumes it exists per 04.5.1/05.6.1 and is exposed by 05's read view. If it is missing, 05.6.1 needs a follow-up migration — flagged here, not fixed in this file.
- No DbUp migration file is added by 07 for this story (read-only extension of an existing query + response shape).

## 5. API shapes (commands, queries, endpoints)

- **Command (existing, extended):** `AggregateReleaseDecisionCommand` (07.5.3-T1, invoked only by the `policy.release_aggregate` outbox task on `evaluation.created`, T87) — its component-resolution set now includes `component_kind = 'app'` rows from 05's `release_component` view in the same digest-match comparison used for web/service components, and each persisted `component_evaluations[]` entry carries `component_kind`. No separate code path.
- **Query (existing, unchanged semantics):** `GetReleaseDecisionQuery` (`IQuery<ReleaseDecisionDto>`, Dapper, read-only transaction, owner 07.5.3) stays a pure read — it projects the persisted row verbatim, including `component_kind`; it never aggregates, writes or enqueues (T87).
- **Endpoint (existing):** `GET /v1/releases/{id}/decision` (`decision:read`) — response shape gains `component_evaluations[].component_kind`; status codes and error codes unchanged (`404` other-tenant/unknown release, `200` with `pending`/decision body per 07.5.3/T87).

## 6. States and transitions

- No new states. An app component's contribution to `release_decision.decision` follows the same terminal states as any component (`PASS`/`FAIL`/`INCONCLUSIVE`, 00 §8.6); a digest mismatch is a `missing[]` reason on the release aggregate (07.5.3's existing state shape), not a new component state.

## 7. Jobs and integrations

- No new background job: this story extends the existing `policy.release_aggregate` task's input set (07.5.3, `evaluation.created` trigger, T87) — the GET read path stays a synchronous pure query and no new outbox row type is introduced.
- Consumes 04.5.1's mobile adapter output (manifest + digest) indirectly, through 05's run/evidence pipeline — 07 never talks to the mobile adapter directly.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 P3 (no N+1) | The app-component rows are folded into the aggregation task's same single input read (one `UNION` branch) as web/service components — one bounded round trip, not a per-component query; the GET remains a single SELECT | Integration test asserting the command counter for the aggregation task's input read is unchanged after adding an app component |
| 00 §5.7 P4 (indexed filters) | The task's input query filters/joins on `release_component.component_kind` and `run.manifest_hash`, both already indexed by 05.6.1's migration (05 owns the index; 07 verifies it is used) | `EXPLAIN` assertion in the integration test shows an index scan, not a sequential scan, on `release_component` |
| 00 §5.4 rule 6/7 (tenancy) | The query stays inside the existing `org_id`/RLS-scoped transaction; no new table, no new RLS policy needed | Reuses 07.5.1's tenant-isolation integration test with an app component added to the fixture |
| T22 / T87 (immutability, persisted aggregate) | `component_kind` is written by the aggregation task as part of the input set feeding `inputs_hash` — an unchanged input set keeps its existing row; an app-component release produces a new append-only row, never an UPDATE | AC4 regression fixture (unchanged decision for the existing non-app case) |
| Privacy / retention | No personal data; app component digests carry no evidence content, only hashes | — |
