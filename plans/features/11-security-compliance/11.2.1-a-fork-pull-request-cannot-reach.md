## 1. Goal and non-goals

**Goal.** Make "untrusted CI is untrusted" provable: a published customer CI recipe that never puts a long-lived Evidgate credential in a workflow (FR-11-2); a fixture repository where a fork pull request demonstrably cannot reach any Evidgate credential and an attempted misuse fails authorisation and is logged (FR-11-3); a security review of the ingest-token design (T5) and the `evidgate_resolve` resolvers (T1); and the sandbox isolation specifications for the V1 shadow-replay path, the V2 agent/healing surfaces, and the V3 hosted-execution decision (FR-11-4).

**Non-goals.** Building the CI binding/token machinery (02.4.1/02.4.2), the `evidgate_resolve` functions themselves (02.6.1-T3, 03.4.1-T2), the replay/sandbox implementation (08.4.3, 05.7.4), supply-chain scanning (11.6.1), CodeQL (11.7.1-T2).

## 2. User stories and acceptance criteria

- As a customer's repo maintainer, I paste the published recipe and get a workflow that is safe by construction against fork PRs, so I never have to reason about `pull_request_target` myself.
- As the Tech Lead, a CI fixture proves a fork workflow reaches no Evidgate credential, so the claim is tested, not asserted.
- As the security reviewer, the token design and the pre-tenant resolvers have a written abuse review, so decisions are recorded.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `docs/security/customer-ci-recipe.md` + `fixtures/ci-recipes/github-fork-safe.yml` encode all five FR-11-2 rules: no `pull_request_target` checking out untrusted code, actions pinned to full commit SHA, `GITHUB_TOKEN` read-only by default with per-job elevation, `::add-mask::` on derived secrets, no long-lived Evidgate credential; `scripts/lint-ci-recipe.sh` exits 0 on it and exits 1 on each negative fixture (one fixture per rule) |
