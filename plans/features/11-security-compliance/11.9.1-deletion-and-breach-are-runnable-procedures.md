## 1. Goal and non-goals

**Goal.** Deletion and breach response are executable runbooks, not essays: a tenant/project/artifact/log deletion request runs through the existing deletion machinery, is verified by probes, and emits a checksummed customer-facing report; a breach triggers a documented path — detect, triage, prompt processor→controller notice, 72 h regulator support, evidence pack — rehearsed end-to-end against the clock.

**Non-goals.** The deletion state machine and artifact storage plumbing (06.4.4, 06.4.5); the operator deletion endpoint itself (00 §9.1 / T16, owned by the identity/operations stories that build `/internal/operator/*`); the audit log that feeds the evidence pack (11.5.1); the DPA clauses these procedures fulfil (11.8.1); restore drills (10.6.1).

## 2. User stories and acceptance criteria

- As a customer data owner, I request deletion and receive a report I can file with a regulator: what was deleted, when, from which stores, and how it was verified.
- As the on-call engineer, I open the breach runbook at 02:00 on a Saturday and complete the processor→controller notice inside the documented target without improvising.

## 7. Jobs and integrations

- `deletion-report` worker task (outbox → `task` queue, 00 §5.3): enqueued by the deletion completion path; re-runs the verification probes, writes the report, emits an audit row so the tenant sees it (11.5.1). Idempotent on `(deletion_request_id)` — a replay reproduces the same report hash.
- `scripts/breach-drill.sh`: seeds a fixture security event, walks the runbook checklist with timestamps, produces the drill record (AC7) — the same script drives the tabletop and the timed rehearsal.
- Sub-processor change path: notification template + version bump of `docs/compliance/sub-processors.md`, cross-referencing the DPA annex (11.8.1-T1).
- Consumed by: 12.2.1 pilot pack (deletion SLA + breach runbook are contractual artifacts), 11.5.1 (audit feed carries deletion/report/breach rows), 10 on-call rota (named breach path).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-11-15 / D8 (verified deletion, no cached-URL reads) | AC2 evidence lines + AC3 URL probe; report is generated, not asserted | AC2, AC3 |
| T60 (no fabricated claims) | report quotes backup retention window verbatim instead of claiming backup deletion | AC4 |
| Art. 23.1 ✅ (72 h / prompt notice) | runbook's processor→controller step is timed (4 h ⚠️) well inside the customer's own 72 h clock | AC5, AC6 |
| 00 §9.1 / T16 (operator-only destructive routes) | deletion requests never appear under `/v1`; every operator action is audited | AC2 audit line |
| T19 / T57(b) (scan/secret edges) | report records `pending`-scan artifacts as held (`sensitive` until clean) and `secret_rejected` deletions with their reason | AC2 evidence lines |
| Authz | operator role for deletion execution; `audit:read`/`security_event:read` (`tenant_admin`) for evidence; report delivery audited | AC2, AC5 |
| Privacy | report contains object ids/counts only — never artifact content or secret material (S3) | report schema review |
| Secrets | drill uses fixture tokens only; a real credential never appears in the drill record | AC7 review |
| Hot-path performance | report task is off-path (outbox, 00 §5.3); probes are bounded point lookups, one statement each, no N+1 (P3) | task handler review |
| Retention/deletion impact | this story *is* the retention/deletion verification surface | — |

- **Authorization:** the breach runbook is executed by the Tech Lead and the named clock owner (owner, per OI-11-08 `[INFERENCE]`); evidence is read with `audit:read` on `GET /v1/orgs/{o}/audit` and `/audit/export` by a tenant principal of the affected org, because the platform operator principal carries no permissions today (`src/Modules/Evidgate.Modules.Identity/Authorization/PermissionEvaluator.cs:63`); the runbook adds no route, role or permission, and `security_event:read` (`tenant_admin`) stays planned (11.5.1-T5.2).
- **Retention/deletion:** the runbook creates no stored data class; the incident clock record and evidence pack are versioned documents holding ids, counts, timestamps and hashes only, never artifact content, tenant payload or secrets; their retention and the clock-record location are `[OPEN OI-11-08]`, and a breach-related deletion request is routed to the deletion runbook (T1), never executed from this one.
- **Telemetry:** the procedure consumes existing signals only: the five V1 security-event types (`docs/security/security-event-baseline.md`), `audit_chain_verification_failures_total` and log event 2400 for a broken audit chain, and the `audit.export` row the export writes; it emits nothing new, and the clock record's own timestamps are the measurement T3's drill reads.
- **Failure path:** channel to the controller down or counsel/on-call unreachable (T2.4, open): try the next channel in the notice-contact list T2.4 will define, log each attempt and its time, and never delay the notice for a missing detail; the security-events extract is planned, not shipped, so the pack falls back to the audit page, the export and the chain-check result, with the gap logged; a lost clock record is rebuilt from audit timestamps and flagged `[OPEN OI-11-08]`.

## 11. Rollout

- Order: T1 and T2 in parallel once their deps land, then T5 (depends on T1's report machinery), T4, and T3 last — the rehearsal needs the finished runbook.
- The deletion SLA windows and the 4 h notice target are ⚠️ proposed values pending owner/counsel sign-off; they are written in the runbook and DPA, so any change is a coordinated edit of both, never one-sided.
- Gate: the M3 pilot exit requires one completed drill record (AC7) and one real verified deletion report — produced in rehearsal on a fixture tenant before the pilot, then exercised live when the first pilot tenant offboards.
- Rollback: runbook/report changes are versioned files; an in-flight deletion is never rolled back — a failed report task retries from the outbox, and a `verification_failed` report page-blocks the on-call rather than shipping a false clean bill.
