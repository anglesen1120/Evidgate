## 1. Goal and non-goals

**Goal.** Turn "a person asks us about their data" into a runnable operator procedure with a recorded outcome: intake, identity verification, scope lookup across tables and artifacts, a response template, a deadline tracker whose duration comes from counsel, and one rehearsal in staging with an attached report. It also settles the standing conflict between **immutable, hash-chained audit rows** (T8, 11.5.1, 11.5.2) and **deletion/erasure**: audit chain payloads never contain personal data, rows carry only a pseudonymous subject id, and erasing a person removes the link, not the row (T2). The four request kinds are access, correction, deletion and restriction (names per the acceptance; their legal definition and scope ⚠️ counsel).

**Non-goals.** The legal analysis of which rights exist, their conditions, exemptions or response times (counsel, 11.8.1; each ⚠️ here); the deletion engine and its customer report (11.9.1-T1, reused, not rebuilt); breach notification (11.9.1-T2); the audit chain mechanics and checkpoints (11.5.1-T1, 11.5.2); a self-service data-subject portal (not in V1; requests arrive through the controller/customer or a mailbox and are entered by an operator); consent management (customer-side, 11.8.1-T6); any LLM-provider side data (V2, 11.4.1-T3/T4).

## 2. User stories and acceptance criteria

- As a data subject (via the customer controller), I get an answer about my data, or a correction, restriction or deletion, inside the deadline that counsel set.
- As the Tech Lead / operator, I follow one written procedure with a tracker, so no request is lost or answered late by accident.
- As a customer admin (controller), I receive Evidgate's findings and can confirm or reject the action before it is executed on my tenant.

## 4. Data model and migrations

Migration `migrations/NNNN_dsr_request.sql` (placeholder, additive):

```sql
create table dsr_request (
  id            uuid primary key,                 -- UUIDv7
  org_id        uuid not null,                    -- the controller customer
  kind          text not null,                    -- access | correction | deletion | restriction
  state         text not null,                    -- opened | identity_pending | identity_verified | identity_failed | in_progress | closed
  outcome       text,                             -- completed | partially_completed | refused | refused_immutable_evidence | withdrawn
  subject_id    uuid,                             -- pseudonymous internal id; null until resolved
  received_at   timestamptz not null,
  due_at        timestamptz not null,             -- received_at + configured deadline (counsel)
  closed_at     timestamptz,
  identity_check jsonb,                           -- method, verifier id, time; never documents
  report_ref    text,                             -- artifact id of the checksummed report (11.9.1 style)
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now(),
  version       int not null default 1,
  unique (org_id, id)                             -- T3 composite-FK target
);
alter table dsr_request enable row level security;
alter table dsr_request force row level security;   -- DECISIONS F5
```

The table deliberately holds **no** name, email, free-text description of the person or request content; the request text lives with the controller/mailbox and is referenced by an external ticket id kept in `report_ref`/audit only if it contains no personal data (`[OPEN]` O-11.9.2-2: where the request correspondence is stored and its retention — counsel). Operator policies (cross-org operator read) are deferred to 02.8.1 like the other platform tables; until then the routes run a tenant transaction per `org_id`. `dsr_deadline_days` is a platform setting (`infra/config-matrix.json`, check-env-matrix entry), unset by default.

## 6. States and transitions

`opened → identity_pending → identity_verified → in_progress → closed`; `identity_pending → identity_failed → closed (outcome refused)`; `opened`/`identity_pending → closed (outcome withdrawn)`. No data release or scope execution before `identity_verified`; `closed` is terminal and immutable (AC11); reopening is a new request linked by the audit row. Restriction has its own reversible flag on the subject record, outside this state machine. Transitions are idempotent (T82).

## 7. Jobs and integrations

- Deadline tracker (T1): a scheduled task (Cronos runner, 01.5.1) computes `due_soon`/`overdue` and raises an alert via 10.3.1-T5; it never changes a request's state.
- Scope lookup (T1): `PersonalDataRegistry` (table, column, subject key, tenant filter, artifact class, deletion path) feeds export, correction, restriction and deletion; deletion calls into 11.9.1-T1 and 06.4.4/06.4.5 machinery; artifact bytes follow `pending_delete → deleted` (00 §8.4).
- Immutable evidence interplay: manifests and evaluations are immutable (invariant); personal data inside artifacts (for example screenshots, logs) is removed by artifact deletion, which leaves a hash tombstone; the effect on a past evaluation's completeness is recorded, not hidden — `[OPEN]` O-11.9.2-3 owner/counsel decision on whether a customer must be warned that deleting artifacts can turn a past PASS evidence set into "evidence deleted" (never silently rewritten).
- Audit reconciliation (T2): the rule in AC9, enforced by the audit payload schema and the registry; crypto-erasure is not used (the chain stays verifiable without keys of the subject).
- Rehearsal (T3): staging tenant with synthetic data only (no real person), run through the operator CLI, timings read from the tracker.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Authorization | operator routes behind a fail-closed `IOperatorGate`; every act is an audit row; the controller's confirmation is a recorded step for deletion and correction | AC11, gate test |
| Identity | no data release before `identity_verified`; identity documents are never stored; release goes only to the controller or the verified channel | AC3, AC5 |
| Tenant isolation | all lookups run in the tenant transaction of the controller org; a subject with the same email in two orgs yields two separate scoped lookups | isolation test across two orgs |
| Privacy by design | `dsr_request` holds ids and states only; exports are encrypted at rest and expire; the report has no raw payloads | schema + report tests |
| Audit/chain | audit payloads carry no personal data; erasure leaves the chain valid | AC9, AC10 |
| Completeness | the registry test guards against a new personal-data column that no procedure covers | AC4 |
| P1/P4 | scope lookup is per-subject indexed queries (subject id keyed); exports paged; no full-table scans in production paths | EXPLAIN checks |
| Legal | no legal fact is stated as verified; all duties and the deadline are ⚠️/`[OPEN]` until counsel review | doc lint: every legal sentence tagged |

DoR review answers. **Authorization:** operator-only (T16) with the customer controller's confirmation recorded; no data-subject login in V1. **Retention/deletion impact:** this story is the deletion path for personal data of a person; the request record itself is kept for a period set by counsel (`[OPEN]` O-11.9.2-2), contains no personal data, and the closed outcome is immutable; audit rows survive by design (AC9) and checkpoints never hold personal data (11.5.2). **Telemetry:** `dsr_requests_open`, `dsr_requests_overdue`, `dsr_request_duration_seconds{kind,outcome}`, `dsr_scope_registry_gap_total` (always 0 in CI); trace attribute `dsr.kind`; alert on overdue. **Failure path:** identity check fails → `identity_failed`, no release; deletion partially fails → `partially_completed` with the verified-deletion report listing what remained and a retry via 11.9.1-T5; deadline not configured → request cannot open (fail closed); deadline passed → `overdue` alert and escalation to the Tech Lead, never silent.
