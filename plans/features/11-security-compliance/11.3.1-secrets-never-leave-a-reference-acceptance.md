## 1. Goal and non-goals

**Goal.** Prove the secrets lifecycle of area plan §4.2 end-to-end: secret *values* live only in the customer's vault/CI or our secret manager; the database stores references; resolution is per-job, narrow-scoped, audited and value-free in every observable surface (DB, logs, artifacts, error `details`, traces, metric labels). Ship the leak runbook and rehearse it; make secret scanning fail-closed over CI and ingested artifacts; review the encryption/key lifecycle; and verify redaction-at-source is documented, toggleable and provably applied.

**Non-goals.** Building the ingest pipeline or artifact scanner (04.1.1, 06.2.3), the redaction implementation (06.2.2), the environments/secrets infrastructure (10.1.1, 10.5.1), the rotation runbook itself (10.7.1-T4). This story reviews, lints, scans and rehearses on top of those.

## 2. User stories and acceptance criteria

- As a tenant admin, no Evidgate database row, log line, error response or metric label ever contains my secret — only a reference — so a leaked artifact or log export cannot leak the value.
- As the on-call engineer, the leak runbook tells me exactly what to purge, rotate and notify, and I have rehearsed it.
- As the Tech Lead, scanning is fail-closed: a secret that slips through stops the pipeline, not the customer's trust.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A schema lint (`scripts/check-no-secret-values.sh` over `migrations/`) fails any column named `*secret*`, `*token*`, `*password*`, `*key*` that is not one of the allow-listed reference/hash columns (`secret_ref`, `secret_ciphertext`, `token_hash`, `hash`, `prefix`, `pepper_version`); run over the full migration set it exits 0 |
| AC2 | Canary test: a planted canary secret is injected into (a) a runtime log line, (b) an uploaded artifact body, (c) an API error `details`; the hygiene suite detects all three — (a) is caught by the log scanner, (b) by the artifact scan task, (c) the error envelope carries no secret and the envelope test asserts `details` does not match the canary (NFR-11-2) |
| AC3 | `secret_ref` resolution events appear in the tenant audit feed (`GET /v1/orgs/{o}/audit`) with scope and actor, and **without** the value |
| AC4 | Leak runbook `docs/runbooks/secret-leak.md` exists: mask-before-upload rule, log purge procedure, rotation order per system (ingest tokens → pepper → session → webhook secrets → data-protection keys), customer-notice criteria; a timed tabletop rehearsal is recorded with named roles |
| AC5 | Secret scanning is fail-closed: a seeded secret in a CI commit fails the pipeline job; a seeded secret in an ingested artifact moves `scan_state` to `flagged`, and with `reject_on_secret` on the artifact moves `ready → pending_delete` (reason `secret_rejected`, T57b); an exception process (documented, expiring, tenant-visible) exists |
| AC6 | Encryption/key-lifecycle review written: TLS in transit, at-rest encryption for database/object storage/backups, presigned-URL TTL + checksum binding (T18), token rotation (T5), data-protection key custody (S8) and backup keys — every row has an evidence link or a `[OPEN]` |
| AC7 | Redaction-at-source verified: documented patterns applied by the CLI before upload; the tenant toggle flips behavior; an uploaded artifact carries a `redaction_applied` record the hygiene suite can verify (06.2.2-T1 contract) |

## 6. States and transitions

Reviewed, not changed: `scan_state pending → clean | flagged` (T19); flagged + `reject_on_secret` ⇒ `ready → pending_delete` (T57b); ingest token `active → rotated → revoked | expired` (00 §8.9). The leak runbook adds a process state only: `detected → contained (purge+rotate) → notified → closed`, recorded in the incident log, not in the database.

## 11. Rollout

- Lint and scanners land as repo/CI checks (fail-closed from day one — no soak mode for the repo job; artifact scan `pending ⇒ sensitive` is already the safe default per T19).
- Order: T1 → T2 in M2; T3–T5 in M3 after 04.1.1/06.2.x/10.x land.
- Monitoring: `secret_scanner_alert` security events (11.1.1-T4 baseline) feed 11.5.1-T3 alerting.
- Rollback: lint/scanners can be scoped down per-pattern via the exception process; never disabled wholesale — an emergency disable needs a written owner approval.
