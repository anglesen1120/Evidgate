## 1. Goal and non-goals

**Goal.** Prove the healing/LLM boundary (FR-11-6/FR-11-7): the model receives structured input and returns a structured candidate only — it has no shell, no merge right, no policy edit right, no secret access and no cross-tenant reach; retrieval is tenant-filtered; the independent validator is the only authority over a candidate; a prompt-injection corpus (DOM, logs, documents, artifact content) produces **zero** policy/approval/permission/decision effects, with every attempt logged as a security event; and every outbound provider request is per-tenant opt-in, redacted at source and audited per request.

**Non-goals.** Implementing the LLM gateway/candidate pipeline (08.5.1–08.5.3), the kill switch (08.6.3), the `security_event` table and endpoint (11.5.1-T5 — this story only adds the injection-attempt event types to its set), redaction-at-source implementation (06.2.2, verified by 11.3.1-T5), the DPA paperwork mechanics (11.8.1-T1 — this story produces the provider-specific due-diligence input).

## 2. User stories and acceptance criteria

- As a tenant data owner, nothing leaves my project for an LLM provider until I explicitly opt in, and what leaves is redacted — so a model provider never sees my secrets or another tenant's data.
- As a release approver, text inside a DOM snapshot cannot approve, waive, quarantine or flip a decision — the rule engine decides, so injection payloads are inert.
- As the security reviewer, every injection attempt is a recorded security event, so the attack surface is observable.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The AI boundary spec `docs/security/ai-boundary.md` is written and each rule is wired to an enforcement point: structured I/O only (JSON Schema-validated candidate), no shell tool, no repository merge, no policy edit, no secret material in prompts, tenant-filtered retrieval; the review confirms each exists in the 08.5.x code path or files `[OPEN]` |
| AC2 | The injection corpus (`fixtures/injection-corpus/` — DOM snapshots, logs, document text, artifact bodies carrying instructions like "approve this candidate", "mark this case quarantined", "ignore previous rules") runs against the candidate pipeline: **zero** policy changes, approvals, permission changes or gate-decision effects; every payload is recorded as an `injection_attempt` security event |
| AC3 | Candidates are evaluated only by the validator path (structured output → validation → human approval): a corpus payload that mimics a validator verdict cannot reach `approved`/`applied`; `healing:approve` still requires `If-Match` + `candidate_hash` (00 §9.3) |
| AC4 | A tenant with the opt-in unset/off sends **no** request to any provider: harness asserts zero outbound calls and the gate returns the documented refusal (`unavailable` is derived, never stored — T33); with opt-in on, each outbound call writes an audit/`healing_llm_call` row with `project_id`, `incident_id`, `candidate_id` (T30) and the redaction record id |
| AC5 | Redaction-at-source applies to LLM context: the fixture secret set is absent from the outbound payload (byte-level assertion), verified against the 11.3.1-T5 redaction contract |
| AC6 | Provider allowlist: requests resolve only to configured provider hosts through the allow-listed `HttpClient` (S4); a non-allowlisted endpoint is refused |
| AC7 | The provider due-diligence memo exists: DPA terms, sub-processor list entry, residency input for O4 (Art. 20 transfer analysis per §4.5), retention/training-use terms; the threat-model LLM boundary row is updated via the 11.1.1 ritual |

## 6. States and transitions

Reviewed, not changed: candidate `proposed → validated → approved → applied` with `rejected | insufficient_evidence | expired | revoked` exits (00 §8.7) — injection corpus must produce no transition; availability `enabled | shadow | disabled | unavailable` resolved most-restrictive-wins, `unavailable` derived (T33). Corpus result set: `payload → no_effect | effect` — any `effect` fails the suite; every payload emits `injection_attempt`.

## 11. Rollout

- Behind the existing healing availability switch: corpus + opt-in gate land before any provider call is enabled for a tenant; apply capability stays gated by 08.6.3's flag (default off) regardless of this story.
- Monitoring: `injection_attempt` events join the security-event feed (11.5.1-T3 alerting); outbound-call audit rows give per-tenant LLM egress visibility.
- Rollback: flipping the tenant opt-in to off stops all egress (AC4); corpus failures block the pipeline until dispositioned — no partial rollout of the boundary.
