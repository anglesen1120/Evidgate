## 1. Goal and non-goals

**Goal.** Before the first pilot customer uploads a single event or artifact, the complete PDPL paperwork set exists, is versioned in the repository, has been through counsel review, and can be handed to a customer's legal reviewer as a bundle: DPA, privacy notice, data map/record of processing, processing impact dossier, cross-border transfer dossier process, sub-processor list, and the consent/redaction stance document.

**Non-goals.** Executing deletion or breach procedures (11.9.1 — but it consumes the DPA/SLA clauses defined here); the LLM provider's own due-diligence record (11.4.1-T4 consumes this story's DPA template and sub-processor list); pilot-contract commercial terms (12.2.1 consumes this paperwork); any product code — this story produces documents, a manifest and a gate check, not endpoints.

## 2. User stories and acceptance criteria

- As a customer's legal reviewer, I receive a complete, dated, versioned PDPL bundle and can accept the pilot without inventing clauses myself.
- As the Tech Lead, I have a single data map that tells me — per store, field, and sub-processor — what personal data exists, where it lives, how long it is kept and whether it leaves Vietnam, so dossier answers are lookups, not archaeology.

## 3. Contracts touched

- DECISIONS §7 legal position (processor role, redaction defaults, LLM opt-in) — documented, not changed.
- T64 opt-in mechanics are *described* by the stance document; the product enforcement lands in 08.5.3/08.6.1 (V2) and the V1 default is simply "no provider calls".
- `[OPEN]` The area plan requires dossier "filing" (Art. 20.2 ✅ 60-day clock) but residency (O3/O4) is undecided at M1: T5 therefore produces the filing-ready process + per-provider dossier shells and records the residency input for O3/O4; whether an actual filing is needed before pilot depends on the O3 deployment decision — flagged for owner confirmation at the M2 exit.
- No schema, API or permission change.

## 4. Data model and migrations

None. All artifacts are versioned markdown/YAML under `docs/compliance/` in the git repository — versioning is git history plus the explicit `version`/`changelog` header per document; no database objects.

## 5. API shapes (commands, queries, endpoints)

None. Maintainer-facing files and one check script only:

| Artifact / command | Effect |
|---|---|
| `docs/compliance/*.md` + `manifest.yaml` | the versioned paperwork set (AC1, AC2) |

## 6. States and transitions

Artifact lifecycle only, tracked in `manifest.yaml`: `draft → counsel_review → approved` (`approved` rows also carry `review_due` for the per-milestone re-review; a milestone exit checklist step re-runs the gate). No product state machine.

## 7. Jobs and integrations

- Inputs consumed: retention/deletion windows and artifact-state detail from 06.4.1 (data-map retention column), backup topology/region from 10.8.1 (data-map residency column), the security-events/audit surfaces from 11.5.1 (referenced by the breach-cooperation clause), the opt-in mechanics from T64 (stance document).
- Outputs consumed downstream: 11.4.1-T4 (LLM provider due diligence) reuses the DPA template + sub-processor annex; 11.9.1 implements the deletion SLA + breach clauses contractually promised here; 12.2.1 attaches the approved bundle to the pilot agreement.
- `check-compliance-manifest.sh` runs in CI on any `docs/compliance/**` change and as a step in the first-pilot-upload checklist.

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Required artifacts exist with the fixed filenames | `check-compliance-manifest.sh` enumerates the AC1 list |
| Un-approved artifact blocks the gate | set any required row to `draft`, expect exit 1 naming it |
| Missing manifest row for a real file fails | add a stray `docs/compliance/extra.md` without a manifest row, expect exit 1 |
| DPA section coverage | `check-compliance-manifest.sh --lint-dpa` greps the required clause headings (roles, sub-processors, breach, audit, deletion, cross-border); missing heading → exit 1 |
| Data-map store coverage | lint asserts every store class named in AC4 (database, object storage, backups, logs/traces, providers) appears with retention + residency columns filled |
| Stale review date flagged | a `review_due` in the past makes the gate warn (exit 2) rather than silently pass |

No product tests; the runnable checks are the manifest gate and the clause/coverage lints.

## 11. Rollout

- Order: T1 and T2 first (M1, no dependencies — counsel lead time is the schedule risk), T6 right after T1 (it references the DPA wording), T3 in M2 once 06.4.1/10.8.1 facts exist, T4/T5 in M3 on top of the data map.
- Gate: `check-compliance-manifest.sh` is part of the first-pilot-upload checklist in 12.2.1 — the bundle is contractually required *before* data arrives (Art. 37.2.a ✅), so "paperwork after the fact" is a failed rollout, not a delay.
- Review cadence: every manifest row carries `review_due`; milestone exits re-run the gate, and any product change touching personal-data stores reopens the data map.
- Rollback: documents are versioned in git; a withdrawn clause is a new version, never an edit of history.
