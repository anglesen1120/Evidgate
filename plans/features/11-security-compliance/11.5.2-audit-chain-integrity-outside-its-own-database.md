## 1. Goal and non-goals

**Goal.** Close review finding S1: today the audit hash chain (T8, 11.5.1-T1) lives in the same PostgreSQL database it protects, so anyone able to rewrite `audit_event` can also recompute every `row_hash` and no one would notice. This story (1) decides in an ADR that the chain is keyed (HMAC), where the key lives, how it rotates and how often a checkpoint is cut; (2) exports a **signed periodic checkpoint** (per org: last `seq`, last `row_hash`) to storage the application database role cannot modify, under a write-once policy; (3) ships a **verification job** that runs with its own identity, reads the chain and the checkpoints, and alerts on a broken link, a truncated tail, a missing checkpoint or a bad signature. "Does not trust the database" means: the verifier recomputes hashes itself with a key the database never sees, and compares to evidence held elsewhere.

**Non-goals.** The audit core tables and writer (02.7.1) and the base chain mechanics (T8, 11.5.1-T1); the event taxonomy and retention (11.5.1-T1); alert routing machinery and on-call (10.3.1-T5, 10.7.2); the general key-rotation runbook (10.7.1-T4 — this story adds one row to it, not a second runbook); tamper-**prevention** against a fully compromised platform operator with access to both the signing key and the storage account (out of scope, stated in the ADR as residual risk); reconciling deletion requests with the chain (11.9.2-T2); external timestamping or a public transparency log (`[INFERENCE]` possible V2).

## 2. User stories and acceptance criteria

- As the Tech Lead, I can prove to a customer that the audit log was not edited or shortened after the fact, even if the database was compromised.
- As a security reviewer, I can verify the chain from the checkpoint store and a read-only database login without trusting application code paths.
- As the on-call engineer, a mismatch pages me with the org, the first bad `seq` and the failure class.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | ADR `docs/adr/NNNN-audit-chain-keyed-hash-and-external-checkpoints.md` records: keyed chain (HMAC-SHA-256 over the T8 canonical input), key custody (secret store reference only, key never readable by the app DB role or the app database), key id on every row, rotation without rewriting history, checkpoint cadence, signature algorithm, the residual-risk statement, and rejected alternatives (unkeyed chain only, DB-side trigger only, external anchoring service) |
| AC2 | Every new `audit_event` row carries `chain_key_id`; rows written before the change keep the unkeyed `row_hash` and are covered by the first checkpoint (`legacy_unkeyed_through_seq` per org); a mixed-version chain verifies end to end |
| AC3 | A checkpoint job cuts a signed checkpoint at the ADR cadence: canonical JSON (RFC 8785) of `{checkpoint_seq, cut_at, key_id, prev_checkpoint_hash, prev_trusted_checkpoint_seq, orgs[{org_id, last_seq, last_row_hash, legacy_unkeyed_through_seq, deleted_at_seq, first_suspect_seq}]}` (field meanings per ADR-0010 Decision 7, which owns them), signed ECDSA P-256/SHA-256 over the IEEE P1363 64-byte `r\|\|s` form (ADR-0010 Decision 9); written to the checkpoint bucket as a new object under a write-once policy; a second `PutObject` to an existing checkpoint key is refused by the store where the store enforces Object Lock or deny-overwrite (ADR-0010 Decision 11, F21/F22), and where it does not, the replacement is detected as `checkpoint_link_broken` / `checkpoint_signature_invalid` instead of blocked |
| AC4 | The application database role and the application's storage credential **cannot** delete a checkpoint object, and cannot overwrite one where the store enforces Object Lock or deny-overwrite (ADR-0010 Decision 11); where it does not, an overwrite by that credential is detected by the signature and link checks (negative test against the dev store; production policy is a recorded config check) |
| AC5 | The verifier (separate process identity, read-only DB access, read-only checkpoint access) recomputes the chain per org from `seq` 1 or from the last verified checkpoint, and reports `ok` on an untouched chain |
| AC6 | Tamper: editing any field of a row, or recomputing the unkeyed hash after editing, is detected as `row_hash_mismatch` at the edited `seq` (the attacker without the key cannot forge the HMAC) |
| AC7 | Truncation: deleting the newest N rows (so tail `seq` < checkpointed `last_seq`), or deleting an interior row (gap in `seq`), is detected as `truncated_tail` / `seq_gap` |
| AC8 | Checkpoint store attacks: a deleted checkpoint object (gap in `checkpoint_seq`), a modified object (bad signature) and a reordered/replaced object (broken `prev_checkpoint_hash`) are each detected as `checkpoint_missing` / `checkpoint_signature_invalid` / `checkpoint_link_broken` |
| AC9 | On any mismatch the job exits non-zero, emits a `audit_chain_mismatch` alert through the 10.3.1-T5 rule set with `{org_id, failure_class, first_bad_seq, checkpoint_seq}`, and never includes row payloads; a verifier that cannot reach the store or the DB alerts `audit_verify_unavailable` and is never reported as green |
| AC10 | Key rotation: after rotating `audit_chain_key` to a new `key_id`, new rows use the new id, old rows still verify with the old (verify-only) key, and checkpoints signed under either id verify; no history is rewritten |
| AC11 | A legitimate org deletion (11.9.1) does not read as truncation: the chain ends with an `org_deleted` tombstone row and the next checkpoint records `deleted_at_seq` for that org; the verifier treats it as `ok` and flags rows missing without a tombstone |

## 6. States and transitions

Checkpoint: `cut → exported → verified | failed`. `exported` is terminal for the object (immutable); `verified`/`failed` are properties of verifier runs, recorded in the job's own log and metrics, not mutations of the checkpoint. A verifier run is `started → ok | mismatch | unavailable`. No new tenant-visible state. Idempotence: the job derives `checkpoint_seq` from the highest object in the bucket + 1; two concurrent runs race on a conditional create (`If-None-Match`-style, ⚠️ support per store verified in T2.1) so only one wins.

## 7. Jobs and integrations

- **Checkpoint job (T2).** Under the T8 advisory lock discipline it does **not** take the writer lock; it reads each org's tail in a repeatable-read snapshot, so a checkpoint is a consistent point and never blocks audit writes (00 §5.7 P1). Cadence from the ADR (`[INFERENCE]` default: every 15 min, matching RPO 15 min in 00 §11; the cadence bounds — it does not eliminate — the window in which rows can be added and removed again with no evidence left, ADR-0010 Decisions 10 and 13). Export to the write-once bucket; failure retries with backoff then alerts via 10.3.1-T5.
- **Write-once policy (T2).** ⚠️ Object Lock / WORM semantics and retention modes differ per S3-compatible store and are unverified for SeaweedFS and for the O3 production provider (10.8.1-T3). T2.1 verifies against the store docs and records the result in DECISIONS §6; if the production store cannot enforce write-once, the fallback in the ADR is a second account/bucket whose policy grants the platform `PutObject` on the checkpoint prefix plus the exporter's `ListBucket`/`GetObject` and nothing else, plus versioning. `[OPEN]` O-11.5.2-1 residency of the checkpoint bucket (O3/O4) — it holds only hashes and org ids.
- **Verifier (T3).** Runs on a schedule (`[INFERENCE]` hourly, plus on demand after a restore) in a separate workload identity from the API/Worker, with no write access to anything but its own metrics, its high-water store and its append-only backup target (ADR-0010 Decision 3). Per org: verify checkpoint signatures, the `prev_checkpoint_hash` link and the monotone `prev_trusted_checkpoint_seq` trusted chain, advance the high-water only to the highest **signature-verified** `checkpoint_seq` in its own store, backed up append-only outside the bucket and the database (ADR-0010 Decision 8), then recompute `row_hash` from the last trusted checkpoint's `last_seq` forward (full re-walk weekly, `[INFERENCE]`), comparing to the checkpointed `last_row_hash` at each checkpoint `seq`. Cost is bounded by rows added since the last checkpoint (P1); the weekly full walk is paged by `seq` ranges.
- **Alerting (T3).** Metrics `audit_chain_verify_runs_total{result}`, `audit_chain_mismatch_total{class}`, `audit_chain_verified_through_age_seconds`; alert rules in 10.3.1-T5. After a restore from backup (RPO), a legitimate truncated tail is expected: the restore runbook (10.5.x) triggers the owner-authorised re-seed of ADR-0010 Decision 8 (verifier identity, recorded as `restore_epoch`) and never re-cuts, rewrites or deletes a checkpoint — `[OPEN]` O-11.5.2-2 owner decision whether a restore may rewind the chain at all (default: no, alert and investigate).
- Dev stack: SeaweedFS bucket `audit-checkpoints` with a deny-delete policy for the app credential (01.8.1).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Key custody | HMAC key and checkpoint signing key come from the secret store (00 §11), never in the DB, image, config or logs; the verifier holds only what it needs (verify key, and the HMAC key read-only) | log-allowlist test, `check-env-matrix` entry, AC1 |
| Separation of duties | writer, exporter and verifier use three identities; no one of them can both forge and hide | AC4, role-grant test |
| Tamper evidence limits | the ADR states what is not defended (attacker holding the key and the store admin) | AC1 review |
| Tenant isolation | verifier iterates orgs with `SET LOCAL evidgate.org_id`; no `BYPASSRLS` | RLS assertion 02.6.1, boot self-check |
| Privacy | checkpoints and alerts hold org ids, seq numbers and hashes only; no actor, no payload | schema test: checkpoint schema forbids additional properties |
| Audit | a verification failure is an operator alert, not a tenant security event; operator reads of results use the 02.8.1 path | AC9 |
| P1/P4 | checkpoint reads a snapshot, never the writer lock; verify cost proportional to new rows | EXPLAIN + 1M-row timing check on the dev stack |
| Availability | an unavailable verifier or store alerts; the API never blocks on the checkpoint store | AC9 failure test |

DoR review answers (four labelled lines; `docs/adr/0010-audit-chain-keyed-hash-and-external-checkpoints.md` decides the same content):
- **Authorization:** no tenant API; three non-human identities with least privilege (above); human access to the key goes through 10.7.1-T4 break-glass; the key is never readable by the application DB role or the application database (ADR-0010 Decision 2).
- **Retention/deletion impact:** checkpoints and chain retention follow the audit retention rule in 11.5.1-T1; checkpoint objects contain no personal data, so they are never part of a data-subject deletion (11.9.2-T2), and the retention of the write-once bucket must be at least the audit retention (`[OPEN]` the audit retention period itself is counsel-reviewed in 11.8.1, ⚠️ no legal minimum is asserted here).
- **Telemetry:** the three metrics in §7, trace attribute `audit.checkpoint_seq`, alert rules `audit_chain_mismatch` and `audit_verify_unavailable`; alarm when `audit_chain_verified_through_age_seconds` is older than 2 cadences.
- **Failure path:** export failure retries then alerts and the gap in cadence is itself visible (`verified_through_age_seconds`); verification mismatch pages, the on-call follows the 11.9.1-T2 evidence-pack steps if tampering is suspected; signer failure fails the request closed (no unsigned audit rows).

- **(N1, HIGH — owner decided option A on 2026-10-29; the code fix in 02.7.1-T2 stays open).** ADR-0010 Decision 1 (with the new Context fact bullet naming `migrations/0050_identity_session_revoke_audit.sql:274-279` and `0051_identity_session_revoke_audit_ids.sql:285-290`) states the rule: option **A (decided 2026-10-29, DECISIONS §8.2 `D-S131-N1`)** moves the revoke path's audit append into the application writer before the keyed cutover, option **B** keeps the definer and adds an authenticated signer round trip inside the same transaction. The **code fix is 02.7.1-T2**, not this story; carried row `ADR-0010 N1: SQL definer audit writer (S131, #270)` stays open with the same receiver.
- **(N2/N3 — verifier-owned high-water).** ADR-0010 Decision 8 now states: the store's value is the highest **signature-verified** `checkpoint_seq` (an object with a missing, invalid or untrusted signature never raises it, and a number read from the bucket listing, the database or the exporter's local index never does either); the store is verifier-owned, atomic-write, not derived from the bucket or the database; every advance is backed up outside both with at least the checkpoint retention; a restore may only reinstall the highest backed-up value, never lower it, and treats every seq at or below it as consumed; a missing or stale backup, measured against the highest **signature-verified** `checkpoint_seq` and never against an unproven object, makes the verifier fail closed (`audit_verify_unavailable`, never green) until an owner-authorised `restore_epoch` re-seed (O-11.5.2-2) that runs under the verifier identity, appends its audited act to the backup target and may set the value only to the highest signature-verified checkpoint in the bucket. Continuation across revoked or unproven checkpoints: `prev_checkpoint_hash` always hashes the immediately preceding document whatever its status (no hole, no re-cut), while the new `prev_trusted_checkpoint_seq` is monotone and is what the verifier follows; the rows an unproven checkpoint covered are re-established by the recompute from the last trusted checkpoint, and a disagreeing `prev_trusted_checkpoint_seq` is `checkpoint_link_broken`. An unproven object never blocks verification: the verifier alerts (`checkpoint_signature_invalid`/`checkpoint_link_broken`), keeps walking and keeps verifying the database against the highest trusted checkpoint, so a bucket-write attacker with no keys cannot silence it (Decision 8, and the new residual-risk row for exactly that attacker). **Receiver 11.5.2-T3.1/T3.2**: implement and cover with `Verifier_UnsignedObject_DoesNotAdvanceHighWater`, `Verifier_RestoreFromBackup_NeverLowersHighWater`, `Verifier_ReseedAfterOwnerAct_SetsOnlyHighestVerified`, `Checkpoint_RevokedSignature_LinkBrokenOrUnproven`, `Verifier_LostBackup_AlertsUnavailable_NeverGreen`, `Checkpoint_BogusHigherNumber_DoesNotBlockVerification`. **Receiver 11.5.2-T2.2**: emit `prev_trusted_checkpoint_seq` and derive `checkpoint_seq` only from objects whose own `.sig` verifies and whose link holds (ADR-0010 Decision 7), never from a listing entry.
- **(N4 — exporter bucket permissions).** ADR-0010 Decision 3 now gives the exporter `PutObject` + `ListBucket` (prefix `audit-checkpoints/v1/`) + `GetObject` on that prefix and nothing else, with `DeleteObject`, `PutObjectAcl`, `DeleteBucket` and any key outside the prefix denied, because `checkpoint_seq` is derived from the highest object whose own `.sig` verifies (ADR-0010 Decision 7) and `prev_checkpoint_hash` needs the previous document. Consistent with §4: with no local index the exporter lists the prefix, and the verifier never trusts a listing. **Receiver 11.5.2-T2.1**: assert the policy (list works, get works, delete and out-of-prefix writes are denied) and that a second `PutObject` to an existing checkpoint key is refused (or reported `checkpoint_link_broken` where the store cannot refuse it) next to the existing AC4 negative test; AC4 itself is unchanged.
- **(N5 — detection wording).** ADR-0010 Decision 13 and the residual-risk table are corrected: detection always requires a checkpoint that already attested the fact; tail truncation **between** two checkpoints leaves no evidence at all (rows appended and deleted before the next cut were never recorded anywhere), and **pinning a forged row does not detect it** — the checkpoint attests that history was not rewritten after the cut, not that it was true then. Decision 10's cadence claim was softened to match (cadence bounds the exposure window, it does not remove it). AC7 keeps its meaning, because it only claims detection when the tail `seq` falls below a checkpointed `last_seq`; **receiver 11.5.2-T3.2** must not add a test that claims otherwise, and the game-day notes must say which attacks are out of reach.
- **(N6 — checkpoint shape, ADR half).** ADR-0010 Decision 7 now carries `deleted_at_seq` (the tombstone seq, terminal per org, AC11) and `first_suspect_seq` (first unproven seq after an HMAC-key compromise, set by Decision 6, never cleared), both per org, plus `prev_trusted_checkpoint_seq` top-level; `legacy_unkeyed_through_seq` is defined for an org absent from the first checkpoint: it is recorded in the checkpoint where the org first appears and is `0` for an org created after the keyed cutover, so a null `chain_key_id` on any of its rows fails; a listed org with no bound is a schema failure and the bound never increases. AC3 was updated to this shape. The `key_id`-prefix half of N6 (`HMAC(chain_key[key_id], key_id || prev_hash || canonical)`) belongs to the 02.7.1 plan note, another lane; `contracts/schemas/audit-checkpoint.v1.json` (T2.1) must encode the new fields as required-or-null, never additional-only.
