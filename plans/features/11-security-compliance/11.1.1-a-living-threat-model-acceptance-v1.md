## 1. Goal and non-goals

**Goal.** A versioned threat model (`docs/security/threat-model-v1.md`) covers every module and every trust boundary of the system; each STRIDE threat maps to a named control or a written owner acceptance; a machine-checked completeness lint keeps it that way; the milestone-exit ritual re-reviews it; and the ASVS verification level and the V1 security-event baseline are decided and published before the pilot.

**Non-goals.** Implementing controls (owned by the module plans), the tenant-isolation red-team suite (11.7.1-T1), the pen test (11.7.1-T3), CI/sandbox specifics (11.2.1), ASVS evidence walkthrough (11.7.1-T5, V2). This story produces documents, lints and ritual — not product code.

## 2. User stories and acceptance criteria

- As the Tech Lead, I can point a customer's security reviewer at one file where every threat is dispositioned, so the "we thought about it" claim is provable.
- As a later-feature author, the DoR checklist forces me to answer authz/retention/telemetry/failure questions before my story is "ready".
- As the owner, I accept or fix each risk in writing, so nothing is silently open.

## 3. Contracts touched

- 00 §11 ASVS target — this story owns the level decision (11-CR-1); outcome is written back via the existing CR mechanism, not by editing 00 here.
- 00 §9.3 `security_event` row — this story defines only the V1 event-type taxonomy; the endpoint itself is 11.5.1-T5.

- `[OPEN]` The area plan's residual-risk register (§4.1) and open question 4 (container-only isolation, owned by 11.2.1-T4/T5) are carried into the threat model as written items; if the owner later decides differently, the threat model changes, not this plan.

## 4. Data model and migrations

None. The story produces `docs/security/threat-model-v1.md`, `docs/security/asvs-l2-mapping.md`, `docs/security/security-event-baseline.md` and `scripts/check-threat-model.sh`. The event taxonomy is materialised as the `security_event` table by 11.5.1-T5 (its feature plan owns the migration).

## 5. API shapes (commands, queries, endpoints)

None (no endpoints in this story). The threat model enumerates the endpoint surface it reviews — `/v1/auth/*`, `POST /v1/ci/token`, ingest-token auth, `POST /v1/webhooks/github`, `POST /v1/support-grants`, `/internal/operator/*` — each under its trust boundary (pre-tenant resolvers per T1, cookie+CSRF browser path per T38, operator ingress per 00 §9.1).

## 6. States and transitions

None (no runtime states). Document lifecycle: `draft → reviewed (milestone gate) → reviewed-again at next gate`; a threat row is `mitigated | accepted | open`, and `open` rows block the milestone gate checklist.

## 7. Jobs and integrations

- Inputs consumed: 02.1.1 (org/project model), 02.6.1 (RLS + `evidgate_resolve` resolver contract, T1/T2), 02.7.1 (audit core the T4 baseline feeds).
