## 1. Goal and non-goals

A project can use documents alone, or import work from Jira Cloud or Linear. Imports create versioned requirements for stories, epics and acceptance criteria (AC); bugs remain tracker items that a user can link to cases or use as regression-test input. P1 delivers T1–T8. P2 adds one optional write in T9: a user can file one bug from a failed result.

[DECISION] D-REALIGN and D-NO-GITHUB: no customer repository connection, automatic bug filing, bidirectional edits, upstream deletion, attachment upload or general-purpose tracker API. A sync, report, generated draft or failed run is never an instruction to write to a provider.

## 2. User stories and acceptance criteria

| ID | Given / when | Then |
|---|---|---|
| AC1 | A project owner chooses documents only during onboarding | Onboarding finishes without OAuth, a tracker or an ingest token; sending results from the customer's CI is a separate, optional choice. |
| AC2 | A user with `project:write` connects a tracker | Consent requests only the read set in §3. Enabling create-bug requires fresh consent; refusal never enables writes. No OAuth token appears in the browser. |
| AC3 | A user previews issues from a selected Jira site or Linear team | Stories become `user_story` requirements, epics become `epic` requirements parent to their stories, and AC become `acceptance_criterion` children of a story. Bugs and unclassified items do not become requirements. |
| AC4 | A sync repeats after a title/body change, an unchanged item or an interrupted page | Only changed requirement content appends a version. Provider identity survives renames; neither a retry nor an incomplete scan marks an unseen item removed. |
| AC5 | A user links an open bug to a manual case or automated case identity | The case and its report show the linked open bug. Choosing to generate a regression case produces a draft through the existing authoring flow; issue text cannot authorize provider calls or enable tools. |
| AC6 | An authorized user explicitly files a bug from a failed manual result or failed automated attempt | The selected connection gets one issue with the allowed fields and an Evidgate evidence link. The action records the local mapping and `tracker.issue.created`; a retry returns the existing issue. |
| AC7 | A user lacks the grant, uses another project's result, chooses a non-failure, or the connection is disabled or disconnected | The server refuses before provider I/O. A double-click or second user acting on the same connection and source cannot create a second issue. |

## 3. Contracts touched

- Plan 13 FR-13-12; overview §2 (permissions), §3 (glossary), §5.4 (tenant boundary), §8.12 (connection states), §9 (API conventions). During implementation publish the operations and permission metadata in OpenAPI and the generated SDK; never include token columns in a returned model.
- Jira read consent: `read:jira-work offline_access`. OI-13-702 is decided: recheck `offline_access` at T1 DoR against [Atlassian's 3LO documentation](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/). Optional write consent **adds** `write:jira-work` (classic, OI-13-705); do not silently substitute or add granular scopes.
- Linear read consent: `read`. Optional write consent **adds** `issues:create` ([Linear OAuth scopes](https://linear.app/developers/oauth-2-0-authentication)). That provider grant allows more than this product does: adapters expose only issue creation and attaching an evidence URL, not arbitrary mutations, edits or file uploads.
- Requirements use the 13.10.1 version writer; regression drafts use 13.3.1, including its tenant opt-in, redaction, schema validation and review. Issue creation reads the source result, not the release verdict; it cannot revise a result, report or decision.

## 4. Data model and migrations

| Owner | Record and invariant |
|---|---|
| T1 | `tracker_connection`: project, provider (`jira_cloud` or `linear`), selected upstream resource, filter, grant scopes, state and `create_issue_enabled` default false. Encrypt access and refresh tokens with the existing ASP.NET Data Protection key ring; restrict token access to the server-side connector. |
| T1 | `tracker_item`: stable provider ID, provider key/identifier, `kind`, display URL, content hash, last seen and removal marker. Unique `(connection_id, provider_id)`; the display URL is never a request destination. Add `requirement.tracker_item_id` and its composite tenant FK here, after the requirement migration. |
| T2/T3 | Attach the imported requirement to its item; retain the upstream key as `external_ref`. Match on stable provider identity, not a mutable display key. Canonicalize requirement content before hashing; a new `requirement_version` is append-only, with `source=tracker`. |
| T8 | `tracker_item_link` points from one bug item to exactly one `manual_test_case_id` or `test_case_id`; composite FKs keep both ends in the same project. Refuse a duplicate pair. Open-bug display on a report follows the report's snapshot boundary, not a rewrite of an old report. |
| T9 | `tracker_issue_created`: connection, exactly one immutable source (`manual_result_id` or complete `case_attempt` key), and resulting bug `tracker_item_id`. Enforce uniqueness separately for each non-null source shape to avoid SQL NULLs defeating deduplication. Reserve the operation durably before sending (§6); persist the confirmed provider identity so a link retry cannot repeat the create. |

All new tables carry `org_id`, use FORCE RLS and enforce tenant/project ownership at references, including the source of a creation. Index the connection/item identity, source uniqueness and case-to-open-bug lookup. Provider I/O runs outside database transactions.

## 5. API shapes (commands, queries, endpoints)

The operations below are project-scoped. Derive tenant and user from the authenticated context; accept neither a tenant override nor an upstream base URL.

| Operation | Input and result |
|---|---|
| Connect / consent / callback / disconnect | Choose a provider enum and read or create-bug consent intent. Use authorization code, one-use `state` bound to initiating user/project/provider/intent, a registered callback and PKCE where supported. Exchange the code on the server. Return connection ID, provider, status and effective capabilities only. |
| Select filter / preview / import / sync now | Jira: select an accessible `cloudId`, then JQL or project/epic filter. Linear: select team/project/cycle. Preview bounded plain-text items with mapped kind; explicit import or scheduled sync goes through the same writer. Status reports last completed sync, counts and a safe failure category. |
| Link bug / generate regression test case | Accept a scoped bug ID plus a typed target case ID for a link. Generation takes the bug ID; the server reads normalized text as untrusted input and returns the existing generation/draft reference. No tracker mutation. |
| Create bug | With `Idempotency-Key`, submit connection ID and exactly one typed failed-source identifier. Resolve the source and build a preview of title, steps, expected, actual, environment, release/build label and authenticated Evidgate evidence URLs. Send only those fields on explicit confirmation; no artifact bytes, signed download links, raw logs or file upload. Return existing or newly created tracker item and issue link, or the pending/reconciliation status if still unresolved. |

## 6. States and transitions

- `active ↔ needs_reauth`; either may move to terminal `disconnected`. Reject other transitions in the database. Re-consent only to the same authorized project and upstream resource; a new connection is required after disconnect. Denied write consent leaves `create_issue_enabled=false`. Stop writes immediately on disable; discard the write-capable credentials and require read-only consent before further sync if a narrower valid grant is not available.
- Re-sync by provider ID. A normalized content hash equal to the current version updates last-seen metadata only. Append changed content through the requirement writer; 13.10.1 owns stale-link detection. Resolve parent relationships by provider identity even when a child arrives before its epic. Mark removed upstream items only on positive removal evidence or a complete authoritative scan; absence from a changed filter is not proof of deletion.
- Create-bug checks permission, source failure, scope, active connection, write consent and capability before dispatch. Reserve one operation per `(connection, typed source)`; concurrent callers attach to it even with different idempotency keys. Reusing a key for a different command is refused per overview §9. Only the reservation owner calls create. On success, persist provider ID and local bug mapping, and audit the creation once; the provider-specific link step targets only that ID.
- A lost create response is not proof of failure. Keep the reservation, reconcile to the original issue before completing, and do not resend while the outcome is unknown (OI-13-741). A failed link does not undo an already created issue: an explicit retry repairs the missing link after checking for its presence. A completed replay returns the original issue without any upstream write.

## 7. Jobs and integrations

- Cronos schedules sync per connection (daily by default). Coalesce overlapping sync-now and scheduled work; page with bounded batches and resume after `429 Retry-After`. OI-13-703 proposes 5,000 items per connection: reaching the cap means partial, not deleted. Serialize token refresh and atomically replace the encrypted pair; an expired/revoked refresh grant stops the job and moves the connection to `needs_reauth`.
- Route OAuth and API calls by provider enum to fixed HTTPS endpoints only. Jira: auth/token on `auth.atlassian.com`, accessible resources and cloud-ID-qualified API on `api.atlassian.com`. Linear: consent on `linear.app`, token/GraphQL on `api.linear.app`. Browser consent redirects contain no bearer tokens. Never follow upstream redirects with credentials; do not fetch issue URLs, embedded content, custom domains or pagination links on unapproved hosts.
- Jira maps Atlassian Document Format to plain text/Markdown; choose an AC custom field or the description section headed “Acceptance criteria” (OI-13-701). Linear uses Markdown AC sections or labelled sub-issues. Its bug label defaults to a case-insensitive “Bug” or the team's selected label (OI-13-706). Map remaining non-story/non-epic types to `other` tracker items, not requirements.
- Only the T9 command invokes Jira create issue + remote link, or Linear `issueCreate` + `attachmentCreate` **link**. Read-sync workers have no mutation dispatcher. Target project/team and issue type come from the consented, selected resource, never from imported text.

## 8. Security, privacy and performance

- **Authorization:** `project:write` controls connect, consent, configure, import, sync-now and disconnect; `project:read` permits scoped status. Use existing authoring grants for case linkage and generation. `tracker:create_issue` belongs to `qa_engineer`, `test_maintainer` and `tenant_admin`; it grants only explicit filing, not configuration. Check source visibility and scope, not just permission on the connection. Foreign tenant IDs give no disclosure; a sibling project's connection or source cannot be used.
- **Retention/deletion:** disconnect erases locally stored tokens and invalidates pending consent and sync; copied requirements and bug references remain project content under normal project retention/purge. Disconnect or local purge never deletes a provider issue. Audit follows the existing audit retention policy.
- **Personal data:** treat descriptions, AC, bug text and evidence as customer data. Normalize and truncate imported bodies at 20,000 NFC code points; render as escaped text. No prompt instructions, remote media fetches or raw HTML. On write-back show what will leave Evidgate, redact secrets and omit credentials from environment details and links. Provider access is not permission to read linked Evidgate evidence.
- **Telemetry:** audit actor, project, connection, provider, operation, scoped IDs and outcome, including `tracker.issue.created` once. Log sync counts, throttling and reauth with bounded labels. Exclude tokens, auth codes, `state`, PKCE verifiers, callback queries, issue bodies, evidence URLs and provider payloads from logs, errors, metrics and audit.
- **Failure path:** reject expired/replayed consent or PKCE mismatch before storing credentials. Stop on unapproved egress or revoked consent; retry only safe reads on throttling. Do not count an incomplete scan as success or dispatch another create on an ambiguous response. Present actionable status to an authorized user without exposing upstream secrets.

## 11. Rollout

1. P1/G1: migrate T1 after its prerequisites; deliver provider imports, sync, isolation, optional onboarding and linked bugs with remote writes disabled. Read-only projects must not need a new consent screen when P2 ships.
2. P2/G2: enable T9 only after failed manual results exist and both provider paths pass the one-issue and lost-response checks. Each connection remains read-only until an administrator explicitly completes additional consent and an authorized user confirms a particular filing.
3. To stop write-back, disable the capability and block dispatch, retaining mappings for reconciliation. For compromised credentials disconnect and reauthorize through a new connection; do not delete already-created upstream issues or historical local evidence.
