## 1. Goal and non-goals

**P1 · G2.** An Evidgate operator can find an organization by its platform identifier, check its operational status, see authorized usage totals and request support access. When the tenant has confirmed erasure, the operator can submit and track the existing deletion job. The directory is not a way to browse tenant content.

No impersonation, export, member search, project or evidence browser, ledger drill-down, quota adjustment, grant approval by staff, or synchronous erase. This story changes no platform settings. A support-grant transition or deletion request is an audited domain command, not a configuration revision that can be rolled back to restore access or data. Setting changes remain append-only, conditional on `If-Match` and effective without redeploy under 13.12.1-T3.

## 2. User stories and acceptance criteria

| ID | Actor and action | Observable outcome |
|---|---|---|
| 13.12.5-AC1 | A provisioned operator with a verified workforce MFA session pages through the directory. | Only opaque organization IDs and platform lifecycle status are returned (no support grant is involved, and none is needed for these fields); no names, contact details, customer-supplied labels, tenant records or nested payload appear anywhere in the response. Billing role alone cannot open the directory. |
| 13.12.5-AC2 | The operator opens usage for one organization and period. | Usage is the existing 12.3.1-T6 `GetUsageSummary` (`usage:read`, organization taken from the tenant context), so it needs an approved, unexpired support grant for that organization whose scopes include `usage:read`, checked on each request. The console shows only the organization-wide metric counters (`used`, `limit`, `warned_at`, `blocked_at`, unavailable reason); it never shows the per-project rows or ledger lines. Without a grant the screen says "grant required" and nothing is fetched. Every read is audited with the grant ID. Revocation or expiry removes access on the next request. Denied, unavailable and measured zero are distinguishable. The directory and status paging work without any grant. |
| 13.12.5-AC3 | The operator requests named scopes for a target and reason, for up to 72 hours. | The request starts pending. Only a different actor who is the target's tenant admin can approve; until then there is no tenant scope. Revoke or expiry stops further reads, including refreshes in an already open console. |
| 13.12.5-AC4 | An operator starts deletion for a selected organization. | The deletion domain requires both an approved, unexpired grant for this operator, target and `tenant_deletion` scope **and** the tenant-admin confirmation token for this target. Acceptance yields a job ID, not an erasure receipt. Two submissions while one is open cannot enqueue two jobs; the second is shown as refused. |
| 13.12.5-AC5 | The operator revisits an accepted request. | Authorized status follows the actual job (`queued`, `running`, `done` or `failed`); no step in the console deletes data. With a revoked grant, the next poll is denied rather than disclosing an outcome. |

## 3. Contracts touched

- FR-13-14 / 13.12.1: staff app and API live only at `/internal/operator/*` on the operator ingress. Require the provisioned `platform_operator`, verified MFA and live operator session; use the shell's antiforgery protection on mutations. No public or `/v1` console alias. Tenant admins continue to approve in the tenant flow, not in the staff app.
- FR-02-13 / 02.8.1: the directory's thin platform projection is the only tenant-related data available without a grant; every other tenant read, usage included, and every tenant write requires the 02 grant check (`operator_grant_ok`) and a tenant context equal to the route organization. A session or route parameter is never authority. 12.3.1-T6 `GetUsageSummary` is a tenant-context `usage:read` query; the `billing:read` routes (ledger, reconciliation) are a different surface this story does not use, and 12-CR-1 gives no grant-free path over T6. No new grant-free definer is added over usage (OI-13-864).
- 06.4.4-T3 owns deletion authorization, admission, tenant notice and the job contract. 11.5.2-T1 supplies the chain ADR; 02.7/02.8 own grant audit and 11.5.1 owns support-access verification. Preserve domain permissions and audit rather than introducing an administrator shortcut.

## 4. Data model and migrations

| Read or command source | Allowed shape and storage |
|---|---|
| Platform directory | A bounded projection of organization ID and operational status. The `organization` base table is restricted to the current org ID even for `evidgate_app`, and `evidgate_operator` has no policy on it without a grant, so the console reads the projection only through an owner-owned `SECURITY DEFINER` function (`SET search_path=''`, schema-qualified, audited, `EXECUTE` granted to `evidgate_operator` only, precedent: `evidgate_resolve`) that returns the allowlisted columns and page. No arbitrary columns, joins or filters; no tenant rows copied into a shadow directory. |
| Usage | The selected organization's existing 12.3.1-T6 summary for one period, called with the grant's tenant context and `usage:read` scope on the `evidgate_operator` connection. The console projects only the organization-wide metric rows (`scope: tenant`) from the response and drops `projects[]` and its cursor before returning. No second ledger, invoice lines, source IDs or raw events; no usage cache persisted by the console. |
| `support_grant` | 02.8.1 owns requester, org/project scope, reason, approver, expiry and revocation. Read only the requesting operator's permitted grant metadata; never copy it as an editable console ACL. |
| `deletion_job` | 06.4.4 owns job identity, target, state and terminal report. Return only the permitted job reference, state and safe outcome; never expose raw report object keys or backup locations. No parallel deletion table or worker. |

## 5. API shapes (commands, queries, endpoints)

All paths below are on the operator ingress. New console contracts are narrow adapters over the named owners; tenant-admin approval is not an operator command.

| Operation | Inputs, successful result and refusal |
|---|---|
| `GET /internal/operator/orgs` | Accept a bounded page size and opaque cursor. Use keyset ordering by immutable unique org ID; enforce a positive size up to the API cap, reject malformed cursors, and omit the next cursor on the last page. An empty page is a valid result. The list does not bulk-read usage or grant tenant context. |
| `GET /internal/operator/orgs/{o}/usage` | Resolve the caller's approved grant for `{o}` (scope `usage:read`) and open the tenant context before calling the T6 query; refuse `403 no_support_grant` / `support_grant_expired` otherwise, with no data and no T6 call. Return the period and organization-wide metric counters only. An unknown organization and an organization without a grant give the same refusal; do not infer another tenant's usage from a denial. |
| Request / revoke support access | Target org, selected scopes/projects, reason and expiry go to the existing request command, with its idempotency key. Return own request reference and state. An operator may withdraw/relinquish their **own** request or grant through the domain's narrowly authorized revoke transition; preserve the tenant admin's independent revoke path. No staff approve, extend, reassign or revoke-another-operator endpoint. |
| `POST /internal/operator/orgs/{o}/deletion` | Use the 06.4.4-T3 route, not a replacement. Submit explicit tenant-admin confirmation in the body, never the URL. Verify the live grant and the confirmation independently of browser state; do not derive confirmation merely from the selected grant. Return `202` and job reference on first admission. A competing/new request while a job is open is refused without enqueuing work. |
| Deletion status for `{o}` and job | Return only the matching job's authorized operational state. Recheck auth and scope on every poll; deny an org/job mismatch without exposing the other org. A successful POST, timeout or empty response must never produce a `done` result. |

## 6. States and transitions

- Directory pages belong to the platform session. Selecting another target resets usage, grant, job and confirmation state before fetching anything for the new target; late responses for the previous selection cannot repopulate it.
- `requested → approved → revoked | expired`; a pending request can be withdrawn. Approval belongs to the target tenant admin, never the requester. Apply the 72-hour ceiling and exclude `now == expires_at` from validity. Revocation takes effect without waiting for sign-out or a cleanup job.
- An authorized deletion goes `queued → running → done | failed` under 06.4.4. An open job suppresses a second submission on the server even from another tab. A lost response leads to an authorized status lookup, not automatic resubmission. `failed` is not erased; the existing recovery procedure owns retries.

## 7. Jobs and integrations

Use 02.8.1's approval notifications, tenant-visible grant trail and alerts on sensitive reads. Use 12.3.1-T6 rather than querying raw usage events. Use 06.4.4 for the deletion task, open-job admission guard, tenant-visible notice, report and upload/ingest refusal (`409 tenant_deleting`). The console cannot cancel an admitted job by revoking the grant: revocation ends operator access, not the tenant's accepted erasure process.

## 8. Security, privacy and performance

- **Authorization:** no standing tenant access. Every console read and command runs on the dedicated `evidgate_operator` connection (not `evidgate_owner`, not a broadened `evidgate_app`; no `BYPASSRLS`). The directory is cross-tenant by nature, so it goes through the owner-owned definer function of §4, which returns only the allowlisted columns; nothing else on `evidgate_operator` can see a tenant row. Usage and every other tenant read or write resolve the caller's grant and scope first, then set the transaction-local org, applicable project and `evidgate.support_grant_id`; preserve `ENABLE` + `FORCE ROW LEVEL SECURITY` and the `TO evidgate_operator` policies using `evidgate.operator_grant_ok(org_id, project_id, action)`. Missing context yields no tenant rows; the default is read-only and writes need their named scope. Never reuse another request's GUCs.
- **Retention/deletion:** grant, deletion job and audit records follow their domain retention policies; no duplicate console records. Do not cache scoped responses across sessions or persist confirmation tokens in browser storage, URLs, logs, traces, audit, history or responses. Discard the write-only field after submit, denial or target change.
- **Telemetry:** audit directory reads on the platform chain with `actor_type = platform_operator`, operator, action and request ID; each grant-scoped read (usage included) or write adds the grant ID, target and period per 02.8.1. Record state transitions with before/after hashes of canonical nonsecret data in the command transaction. Do not log raw reasons, request bodies, tokens or token-derived hashes. Metrics use bounded operation/outcome labels, not org or grant IDs.
- **Failure path:** if grant resolution, RLS context, the T6 call or the audit write fails, return no data and perform no mutation; usage fails closed. A support grant is not an exemption from deletion confirmation or from any other permission the underlying query requires. On session expiry, denial or revoked/expired scope, clear previous data and stop polling. A summary outage is not zero usage; an unavailable deletion service is not a queued or completed request.
- **Performance:** keyset pages use an indexed, fixed order; fetch at most the allowed page plus one lookahead. No offset scan, unbounded export, per-row billing queries or audit of tenant content as a side effect of listing platform metadata.

## 11. Rollout

1. Enable the directory and scoped usage on the operator ingress only after verifying projection privileges, two-tenant RLS isolation and read auditing with the real host and database roles. Keep the customer app unchanged.
2. Enable support/deletion actions after the domain owners resolve the contract handoffs below. Exercise independent tenant approval, refusal, concurrent deletion and job-status tracking on disposable fixture organizations. A migration or seed must never pre-authorize staff.
3. Enable the approved console screens only after both locale and accessibility passes. On failure disable the affected console surface; do not loosen grants, interrupt accepted deletion work or rewrite either audit chain.
