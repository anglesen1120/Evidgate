## 1. Goal and non-goals

**Goal.** Inside the one label that already exists — 08.2.2's `test_drift` — decide **deterministically, from stored data only**, whether a broken bound step is *locator drift* (the element is still there, its markup or position moved) or *UI change* (the element or its meaning changed on purpose), and turn that decision into exactly one reviewable artefact: a candidate locator for drift, a test-case review proposal for UI change, or nothing at all. The decision is arithmetic over element profiles captured on green runs (13.6.1): no browser, no origin fetch, no model, no repository write. Every row carries the `rule_version` and `similarity_version` that produced it, so a rule change is auditable and re-derivable rather than a silent reinterpretation of old incidents.

**Area-plan acceptance (quoted).** "within the 08.2.2 label `test_drift`, profile rules separate locator drift from UI change; locator drift yields a candidate locator and a matching test case edit; UI change yields a test case review proposal and no script repair; other labels yield nothing; a per-project shadow window measures before PRs are offered" (`plans/13-product-phases.md:226`). The governing requirement is FR-13-7 verbatim: "Within the 08.2.2 label `test_drift`, a rule set separates locator drift (same role and accessible name) from UI change; only locator drift yields a script repair candidate; `product_defect`, `environment`, `data_issue` and `unknown` yield none" (`plans/13-product-phases.md:25`). The flow this story implements is plan 13 flow 4: "**Repair:** failed run → incident (08.1) → 08.2.2 label → within `test_drift`, profile rules → locator drift: candidate (08.3) → validation (08.4) → review (08.6.1 + 13.8.2); UI change: test case review proposal" (`plans/13-product-phases.md:59`).

**Partial against that acceptance — "a matching test case edit" (`OI-13-551`).** The acceptance names two outputs for locator drift. The **candidate locator** is delivered in full (AC2, AC4). The **matching test case edit** is delivered as a *proposed, human-applied* edit and never as an applied write: the classification emits the exact edit payload (step number, the case's current element description for that step, the proposed description, the reason and the evidence refs), the review surface shows it beside the candidate, and a human with `authoring:write` turns it into one immutable authoring version: by default the reviewable text rides a `comment` `authoring_change` on the case's parent checklist item (13.1.2-T1's existing change type, no schema change) and the content edit is the human's own 13.1.1 `PATCH` under `If-Match`. Nothing in this story writes a case, a version or a script by itself. The delivery channel is not free: 13.1.2-T1's `authoring_change` table accepts `target_kind in ('checklist_item')` and `change_type in ('comment','delete','merge','split')` (`plans/features/13-product-phases/13.1.2-batched-review.md:120-121`) and `:341` keeps every case or item edit on 13.1.1's `PATCH`, so a *case-content* edit has no legal row shape there today. `OI-13-551` therefore fixes the default — a `comment` change on the case's parent checklist item carries the reviewable text, and the content edit is the human's own 13.1.1 `PATCH` — and leaves the optional `manual_test_case`/`update` extension to the 13.1.2 owner. Either way the edit is a proposal, never an automatic consequence of a rule.

**Second honesty note — the input this story does not build (`OI-13-552`).** Plan 13 says for 13.6.1: "similarity is a versioned function with stability tests" (`plans/13-product-phases.md:204`), delivered inside 13.6.1-T3 at L size. This story **consumes** that one versioned function and ships no second fingerprint and no second similarity implementation (§3, §7). If 13.6.1-T3 ships without a citable spec v1 (inputs, distance, thresholds, tie/ambiguity) and its stability tests, this story's rule set has no legal input: a classification whose `similarity_version` is unsupported records class `unknown` and produces nothing (`OI-13-552` is the cross-plan pointer, and the receiver is 13.6.1-T3, not this plan).

**Phase and scope (CR-D-2).** G3 only, index wave 23 (`scripts/plan_graph.py`, 2026-10-28). Multimodal locate (13.7.2), candidate validation (08.4), PR creation and approval binding (08.6.1), review-screen additions (13.8.2-T2) and the G3 gate report (13.9.1-T3) are separate stories.

**Non-goals.** Any model or gateway call — plan 13 Q1/Q2 (`plans/13-product-phases.md:257-258`) do not reach this story, and 13.7.2 is the only multimodal path; capturing profiles (13.6.1-T1/T2); the similarity function itself (13.6.1-T3); the incident record, its context capture and its fingerprint (08.1.1, 08.1.2); the five incident labels and their precedence (08.2.2); the candidate model, its states, `candidate_hash` and the 3-candidate cap (08.3.1); the validator and the negative control (08.4); the shadow result store and its reporting (08.3.3-T2/T3); approval, PR creation and the two-person rules (08.6.1); before/after screenshots and the a11y/DOM diff (13.8.2-T1); every screen and its visual design (13.8.2-T2 owns review-screen additions; this plan designs no UI); any new permission, and any migration this document could number (§4).

## 2. User stories and acceptance criteria

- As a QA engineer, when an incident already carries `test_drift` I see one deterministic class for each broken bound step — locator drift, UI change, ambiguous or unknown — with the rule and similarity versions that produced it, instead of a black-box suggestion.
- As a test maintainer, a locator-drift incident hands me one candidate locator and the exact case-text edit it implies, and a UI-change incident hands me a review proposal for the case and explicitly *no* script repair.
- As a project admin, I can see that nothing was offered for approval until this project's shadow window closed with measured classification quality, and I can see those measurements.
- As the platform, I can prove that classification read only stored profiles, sent nothing to a provider, fetched no origin, wrote no repository and never classified a local run as evidence.

Every criterion has a named proof in §9 and an owning sub-task in §10. Numeric defaults marked `[INFERENCE]` are build defaults pending the OI row named beside them, never measured product facts.

**Prior art.** Three public sources, read for approach only. (1) *Erratum*, "Leveraging Flexible Tree Matching to Repair Broken Locators in Web Automation Scripts" (`https://arxiv.org/abs/2106.04916`): taken — relocating an element and regenerating a locator are two separate stages, and reducing the candidate search space by tree context beats scanning the whole DOM; not followed — its tree-matching algorithm and its scoring, because this story classifies from an already-stored profile pair and never re-reads a page. (2) *Similo*, "Similarity-based web element localization for robust test automation" (`https://arxiv.org/abs/2208.00677`): taken — a weighted multi-attribute similarity is more robust than one attribute, and abstention beats a forced pick when candidates are indistinguishable; not followed — its per-attribute weight training, because the weights and thresholds belong to 13.6.1-T3's versioned spec, not here. (3) Shadow-testing practice as documented for a managed inference service (`https://docs.aws.amazon.com/sagemaker/latest/dg/shadow-tests.html`): taken — duplicate live inputs into the candidate path with **all** candidate side effects suppressed, log versioned decisions plus adjudicated labels, and promote only on a predefined gate where **missing evidence is hold, not pass**; not followed — traffic mirroring and infrastructure shadowing, because this story classifies after the fact from stored rows, so its "shadow" is a state on the proposal plus a per-project window, not a second live path.

**What this story must not store.** No DOM, no accessibility subtree, no accessible-name *text* beyond the one normalised, redacted value 13.6.1's profile already holds — the classification keeps `profile_id` references and numbers, and `evidence` holds step keys, hashes, scores and reason codes only. No second latest-green table: "the latest green profile per step is queryable" is 13.6.1-T2's view (`plans/13-product-phases.md:204`), read here and never duplicated. No second fingerprint and no second shadow-result store (08.1.2-T3's fingerprint and 08.3.3-T2's storage stay theirs); this plan's window stores a *computed snapshot at close*, not per-attempt shadow rows.

**Traceability chain.** `incident → run → case_attempt` and `case_revision_id` stay 08.1's and 05's; the classification adds `step_key` (13.6.1's key: `case_revision_id` + bound step, per plan 13 §4.1 `element_profile` "(append-only per run and bound step; `case_revision_id`, `step_no`, …)", `plans/13-product-phases.md:49`), and the proposal adds `target_version` — the `authoring_version` the case sat on when the class was computed — so an accepted edit can be refused as stale instead of applied to a moved case (§5, §6).

**Retention and deletion.** Classification and proposal rows follow the incident's retention via 08.1.2-T2's hooks, not a second mechanism; window rows follow project retention. Tenant erasure removes all three tables' rows for the org; the append-only guard allows exactly that path under `evidgate_owner`, as 13.1.2 does for its own lineage table.

A human dismissal is the same route 4 command with `decision: "dismiss"` and a required reason; the **system** dismissal of AC4 (`reason = relabelled`) runs inside the label-change handler, writes no authoring change and is audited as a system actor.

**Refusal matrix** (code is always an existing envelope code; the reason is `details[0].reason`):

| Refusal | Decided where | Code |
|---|---|---|
| accept while the project's window is open | route 4, state check | `409 invalid_transition` `window_open` |
| accept/dismiss of an already-decided proposal | route 4, state check | `409 invalid_transition` `proposal_not_open` |
| accept when the case moved (`target_version` stale) or the hash changed | route 4, inside the transaction | `412 precondition_failed` |

**What is deliberately absent.** No route classifies on demand: classification is driven by the label event and a sweep, so a caller cannot mint a class by calling an endpoint. No route creates a candidate directly; 08.3.1 owns that. No route writes a case or a version.

## 6. States and transitions

**`drift_classification` has no state machine — it is append-only with precedence.** Every run of the rule table appends rows; a human override appends one more. A read returns, per `(case_revision_id, step_key)`, the human row if any exists, else the newest rule row. There is no mutable "current" column, exactly as the shared vocabulary requires ("latest-green per step = a VIEW or documented query, not a mutable row" applies to profiles; the same reasoning applies to a class). `unknown` is a recorded value that enables nothing (AC4).

**`drift_proposal` — one small machine, and it is not 00 §8.7's candidate machine.** The candidate states `proposed → validated → approved → applied` with their exits belong to 08.3.1 and are only *referenced* here (`plans/00-overview.md:295`); this story adds a review artefact that has no approval power over a script.

| From | To | Allowed when | Refused |
|---|---|---|---|
| — | `shadow` | a classification completes while the project's window is open (or the case is sensitive, AC8) | a window row missing on a project that has never measured — the first classification opens nothing by itself; the window is opened by the operator/task (§7) and until then the proposal stays `shadow` |
| `shadow` | `open` | the window closes with the `OI-13-553` gates met, by the closing task | a window closed on inconclusive evidence — it does not close at all |
| `open` | `accepted` | route 4 with a fresh hash and target version; queues the 13.1.2 change | window reopened, hash changed, case moved (`412`), already decided (`409`) |
| `open` | `dismissed` | a human decision with a reason | already decided (`409`) |
| `shadow`/`open` | `dismissed` | system, `reason = relabelled`, when the incident label leaves `test_drift` (AC4) | never by deletion |
| `shadow`/`open` | `expired` | `expires_at` passed, or the `case_revision_id` is superseded by a new revision (a classification for the new revision supersedes it) | `accepted` rows never expire |
| `shadow`/`open` | `superseded` | a newer classification for the same `(case_revision_id, step_key, proposal_kind)` — a higher `rule_version` or `similarity_version`, or another incident on the same step — written in the same transaction before the new row is inserted (the partial unique index of §4 is the guard) | `accepted`/`dismissed` rows are terminal |

**`drift_shadow_window`.** `open → closed` only, one `open` row per project (partial unique index); a new `(rule_version, similarity_version)` pair starts a **new** row. Closing is a computation over stored rows and writes the metric snapshot; nothing reopens it (AC5).

**`generated_script` is never moved by this story.** The four states and the `draft → active · flaky → retired` edges are 00 §8.11's verbatim (`plans/00-overview.md:315`); activation counts CI-verified runs only (13.5.1-AC20, `…13.5.1-bound-playwright-scripts.md:59`), and this story touches no script row at all — a candidate that a human later approves still needs 08.6.1's approval and its own canary.

## 7. Jobs and integrations

- **Trigger (outbox) — hand-over.** `ClassifyDriftCommand` is dispatched by an outbox row written in 08.2.2's label-write transaction, so a label and its classification cannot diverge. 08.2.2 is **not built** (`STATUS.md` §2/§5 carry no 08.2.2 row on `d54349e5`), and its outbox event name is that story's to fix; this plan therefore names the **shape** ("a label-change event carrying incident id, previous and new label, actor and `label_source`") and records the exact name as a review question for 08.2.2's owner, not a dependency edge.
- **Fallback sweep — idempotent, and the reason this story is buildable before 08.2.2 emits events.** A Cronos schedule (`plans/00-overview.md:177`) selects incidents whose current label is `test_drift`, whose `context_state = complete` and the run not `origin = local`, and which have no classification row for the current `rule_version`; it dispatches the same command with the handler's natural key. A duplicate fire writes no second row (unique natural key + `ON CONFLICT DO NOTHING` at the task row, 00 §5.3).
- **Shadow-window close schedule.** One fire per project per window computes the `OI-13-553` gates from `drift_classification`, `drift_proposal` and the 08.8.1-T1 corpus adjudications and either closes the window (writing the snapshot) or leaves it open with the failing gate recorded in the run's log. Nothing is offered while it is open (AC5).
- **Consumed, not built:** profile capture and the latest-green view (13.6.1-T1/T2); the similarity function (13.6.1-T3); the candidate model, cap and expiry (08.3.1-T1); the corpus and holdout (08.8.1-T1/T3); the pending-change model (13.1.2-T1); the healing switch's `disabled` state, which suppresses *offering* while classification may still record evidence (08.6.3-T1 is merged, `STATUS.md:194`).
- **No new outbox consumer besides these two, and no event emitted by this story**: 13.9.1-T3 reads the window snapshot and the classification rows directly as a query; nothing waits on an event that does not exist (A10/C7 apply only where work must cross a transaction).
- **No model call anywhere.** No 08.5.1 client, no prompt, no credit, no redaction-pipeline call: the classification is arithmetic over stored numbers and short strings. Plan 13 Q1/Q2 (`plans/13-product-phases.md:257-258`) are not consumed, and 13.7.2's multimodal path is the only place a model may ever propose for an ambiguous class.

**Trust boundaries and five abuse cases.** (1) A forged or replayed label event cannot invent a class: the handler is idempotent on its natural key and writes rows only for a current `test_drift` label read inside the transaction. (2) A crafted accessible name cannot steer a match into the wrong element: equality is exact after normalisation, an ambiguous pair abstains, and no rule may pick by position. (3) A tenant cannot read another tenant's class or proposal: `404` on every route and RLS beneath it. (4) A caller cannot mint a candidate or a class by calling an endpoint — there is no such route, and 08.3.1's cap is enforced in its own mint. (5) A sensitive case cannot receive an offerable repair: the branch is proposal-only and the rule is asserted by test, not by prompt or policy wording.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** four routes, two existing permissions — `healing:triage` (`qa_engineer`, `contracts/permissions.json:422`; `plans/00-overview.md:60`) for all reads and the override, `authoring:write` (`contracts/permissions.json:278`) for accepting a proposal that queues an authoring change; no new permission, no operator path, and a candidate's approval stays `healing:approve` (08.6.1); the healing set is the four shipped strings (`plans/08-healing-learning.md:353`). Because `qa_engineer` holds `healing:triage`, `authoring:write` and `healing:approve` today (`contracts/permissions.json:422`, `:278`), the split is capability-based, not a role wall: separation of duty on a sensitive case is 08.6.1-T2's approver rule (T35) and AC8's proposal-only form, never a claim that these two permissions keep different people apart. Another org's id is `404`; a credential scoped to a sibling project is `403 project_scope_mismatch` as elsewhere; the sweep runs as the worker under its own role and writes only inside tenant scope.
- **Retention/deletion:** classification and proposal rows inherit the incident's retention via 08.1.2-T2 (no second mechanism); window rows inherit project retention; the append-only guard on `drift_classification` allows deletes only from `evidgate_owner`, so tenant erasure and retention sweeps can run while the app role cannot rewrite history; nothing here outlives the case revision it references by design — an expired proposal is a state, not a deletion.
- **Telemetry:** `evidgate_drift_classification_total{drift_class, class_source, rule_version, reason}`, `evidgate_drift_proposal_total{proposal_kind, state}`, `evidgate_drift_window_close_total{outcome}` and `evidgate_drift_skipped_total{reason}` (labels are closed sets: class, source, state, rule version, reason code — `reason` is set only on `drift_class="unknown"` and on `skipped`, never an incident id, project name, case title, locator or accessible name); no new dashboard is required; a jump in `ambiguous` is a similarity-threshold signal and a jump in `skipped{reason="origin_local_not_evidence"}` is a local-run habit.
- **Failure path:** fail closed and leave evidence intact. Missing or unsupported `similarity_version`, `context_state != complete`, no profile or a stale case revision → class `unknown`, no proposal, no candidate, one counter; a run with `origin = local` is never classified at all and only increments its skipped counter (AC7). A worker crash mid-transaction writes nothing (one transaction per classification). A window close that cannot compute its gates leaves the window `open` (hold, not pass). A stale accept is `412` with nothing written. No failure path retries a classification into a different class, and no failure path deletes a row.
