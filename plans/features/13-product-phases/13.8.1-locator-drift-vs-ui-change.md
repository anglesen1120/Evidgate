## 1. Goal and non-goals

**Goal.** Inside 08.2.2's existing `test_drift` label, separate locator drift from UI change deterministically from stored profile pairs, producing a gated candidate and review proposal, or nothing. The latest-green baseline and a resolved failed-step profile come from 13.6.1; failed-step observations remain self-asserted and never eligible for latest-green. No browser, origin fetch, model or repository write occurs here. Each row carries both `rule_version` and `similarity_version`; absent or unsafe input abstains rather than inferring that a missing element changed meaning.

**Area-plan acceptance (quoted).** "within the 08.2.2 label `test_drift`, profile rules separate locator drift from UI change; locator drift yields a candidate locator and a matching test case edit; UI change yields a test case review proposal and no script repair; other labels yield nothing; a per-project shadow window measures before PRs are offered" (`plans/13-product-phases.md:226`). The governing requirement is FR-13-7 verbatim: "Within the 08.2.2 label `test_drift`, a rule set separates locator drift (same role and accessible name) from UI change; only locator drift yields a script repair candidate; `product_defect`, `environment`, `data_issue` and `unknown` yield none" (`plans/13-product-phases.md:25`). The flow this story implements is plan 13 flow 4: "**Repair:** failed run → incident (08.1) → 08.2.2 label → within `test_drift`, profile rules → locator drift: candidate (08.3) → validation (08.4) → review (08.6.1 + 13.8.2); UI change: test case review proposal" (`plans/13-product-phases.md:59`).

**Partial against that acceptance — "a matching test case edit" (`OI-13-551`).** The output is a human-applied proposal, not an applied case write: its bounded payload contains `step_no`, closed changed-field flags (`role_changed`, `name_changed`, `region_changed`), a reason code and evidence refs. The rendered statement says only that role/name/region changed for step N; there is no `before_description`/`after_description` sourced from a content-free profile. By default (OI-13-551), `comment` on the parent checklist item carries that statement through 13.1.2-T1; the human independently applies content through 13.1.1's `PATCH` under `If-Match`. No handler here writes a case, version or script. A `manual_test_case`/`update` schema extension belongs to the 13.1.2 owner, not this plan.

**Input hand-over (`OI-13-552`) and dominant partial (`OI-13-558`).** The 13.6.1 plan exists: its §10 T3.1 row in `plans/features/13-product-phases/13.6.1-element-profiles.md` specifies the versioned inputs, weights, distance, thresholds, tie rule and tests (cited by label). Consume it once; unsupported versions yield `unknown`. 13.6.1 also captures a failed bound step only when its element resolved, with `outcome` and self-asserted provenance, excluded from latest-green; that row is what 13.8.1 reads back through 13.6.1 §5 read 3 (`IElementProfileReader.FailedStepAsync`) and its id is what `drift_classification.failing_profile_id` stores. If a broken locator no longer resolves, **there is no failing profile**: AC1–AC3 are **PARTIAL against plan 13 `:226` clauses 1–3**, returning `unknown/no_profile`, no proposal and no candidate in this dominant case. `OI-13-558` hands candidate-profile input to 13.7.2 and consumption to 13.8.1-T1; this plan does not pretend to solve it.

**Phase and scope (CR-D-2).** G3 only; wave: see `scripts/plan_graph.py` (ordering is computed, not pinned here). Multimodal locate (13.7.2), validation (08.4), PR approval (08.6.1), screens (13.8.2-T2) and G3 reporting (13.9.1-T3) are separate stories. **Not buildable until** 13.5.1-T1/T4 supply bound steps and `generated_script_run`, 13.6.1-T1/T2/T3 supply profiles/view/similarity, and 08.3.1-T1 supplies a real rule-only mint seam; mocks are not a substitute.

**Non-goals.** Any model or gateway call — plan 13 Q1/Q2 (`plans/13-product-phases.md:257-258`) do not reach this story, and 13.7.2 is the only multimodal path; capturing profiles (13.6.1-T1/T2); the similarity function itself (13.6.1-T3); the incident record, its context capture and its fingerprint (08.1.1, 08.1.2); the five incident labels and their precedence (08.2.2); the candidate model, its states, `candidate_hash` and the 3-candidate cap (08.3.1); the validator and the negative control (08.4); the shadow result store and its reporting (08.3.3-T2/T3); approval, PR creation and the two-person rules (08.6.1); before/after screenshots and the a11y/DOM diff (13.8.2-T1); every screen and its visual design (13.8.2-T2 owns review-screen additions; this plan designs no UI); any new permission, and any migration this document could number (§4).

## 2. User stories and acceptance criteria

- As a QA engineer, when an incident already carries `test_drift` I see one deterministic class for each broken bound step — locator drift, UI change, ambiguous or unknown — with the rule and similarity versions that produced it, instead of a black-box suggestion.
- As a test maintainer, a locator-drift incident hands me one candidate locator and the exact case-text edit it implies, and a UI-change incident hands me a review proposal for the case and explicitly *no* script repair.
- As a project admin, I can see that nothing was offered for approval until this project's shadow window closed with measured classification quality, and I can see those measurements.
- As the platform, I can prove that classification read only stored profiles, sent nothing to a provider, fetched no origin, wrote no repository and never classified a local run as evidence.

Every criterion has a named proof in §9 and an owning sub-task in §10. Numeric defaults marked `[INFERENCE]` are build defaults pending the OI row named beside them, never measured product facts.

**Prior art.** Three public sources, read for approach only. (1) *Erratum*, "Leveraging Flexible Tree Matching to Repair Broken Locators in Web Automation Scripts" (`https://arxiv.org/abs/2106.04916`): taken — relocating an element and regenerating a locator are two separate stages, and reducing the candidate search space by tree context beats scanning the whole DOM; not followed — its tree-matching algorithm and its scoring, because this story classifies from an already-stored profile pair and never re-reads a page. (2) *Similo*, "Similarity-based web element localization for robust test automation" (`https://arxiv.org/abs/2208.00677`): taken — a weighted multi-attribute similarity is more robust than one attribute, and abstention beats a forced pick when candidates are indistinguishable; not followed — its per-attribute weight training, because the weights and thresholds belong to 13.6.1-T3's versioned spec, not here. (3) Shadow-testing practice as documented for a managed inference service (`https://docs.aws.amazon.com/sagemaker/latest/dg/shadow-tests.html`): taken — duplicate live inputs into the candidate path with **all** candidate side effects suppressed, log versioned decisions plus adjudicated labels, and promote only on a predefined gate where **missing evidence is hold, not pass**; not followed — traffic mirroring and infrastructure shadowing, because this story classifies after the fact from stored rows, so its "shadow" is a state on the proposal plus a per-project window, not a second live path.

**What this story must not store.** Profile names contain ONLY `name.hash` (`sha256:` hex64) plus `length_class`, never name text; this story compares hash equality and never re-normalises. Collector first checks RAW name/test id/id for registered secrets and secret shapes; a match omits the field and records `dropped_fields:["name"]` for a dropped name, never a hash of a secret. Only then collector normalises once (NFC, trim, collapse, truncate 80 code points) and hashes. Reporter validates leaves as closed enums, bounded integers or `sha256:` hex64; no second redaction/hash pass. Classification evidence stores references, numbers and closed reason codes; proposals only say role/name/region changed for step N. No DOM/subtree/name text in either `evidence` or `payload`. Latest-green is 13.6.1-T2's view: key includes `target_env`/`variant_hash`, eligible OIDC CI green runs on project baseline refs only, ordered by server ingest timestamp/sequence, never `finished_at`; source `generated_script_run` requires `script_id NOT NULL`. No second fingerprint or per-attempt shadow store.

**Traceability chain.** `incident → run → case_attempt` and `case_revision_id` stay 08.1's and 05's; the classification adds `step_key` (13.6.1's key: `case_revision_id` + bound step, per plan 13 §4.1 `element_profile` "(append-only per run and bound step; `case_revision_id`, `step_no`, …)", `plans/13-product-phases.md:49`), and the proposal adds `target_version` — the `authoring_version` the case sat on when the class was computed — so an accepted edit can be refused as stale instead of applied to a moved case (§5, §6).

**Retention and deletion.** Classification and proposal rows follow the incident's retention via 08.1.2-T2's hooks, not a second mechanism; window rows follow project retention. Tenant erasure removes all three tables' rows for the org; the append-only guard allows exactly that path under `evidgate_owner`, as 13.1.2 does for its own lineage table.

**Internal commands (no route).** `ClassifyDriftCommand` natural key is `(org_id,project_id,incident_id,run_id,step_key,rule_version,similarity_version)`, enforced by the rule-only unique index. It writes a rule row and supersedes old open proposals before new `shadow` insertion. `MintDriftCandidateCommand` calls only `IRuleOnlyCandidateMint` (08.3.1-T1, no model/repository path), exclusively inside eligible `shadow → open` promotion. Store candidate ids on a proposal link, not by updating append-only classification. Open/close/supersede window commands run tenant-scoped as §6. Relabel handler dismisses proposals, records audit/retraction and leaves classification history immutable. A human override never invokes mint.

**Refusal matrix** (code is always an existing envelope code; the reason is `details[0].reason`):

| Refusal | Decided where | Code |
|---|---|---|
| accept while the project's window is open | route 4, state check | `409 invalid_transition` `window_open` |
| accept/dismiss of an already-decided proposal | route 4, state check | `409 invalid_transition` `proposal_not_open` |
| accept when the case moved (`target_version` stale) or the hash changed | route 4, inside the transaction | `412 precondition_failed` |

**What is deliberately absent.** No route classifies on demand: classification is driven by the label event and a sweep, so a caller cannot mint a class by calling an endpoint. No route creates a candidate directly; 08.3.1 owns that. No route writes a case or a version.

## 6. States and transitions

**`drift_classification` is append-only.** Read precedence is newest human override, else newest rule row, per org/project/case-revision/step, with relabelled incidents excluded by current label/retraction audit. No state mutation. Overrides are display decisions only: they never create/promote proposals or mint, and are measured separately from rule precision.

**`drift_proposal` — one small machine, and it is not 00 §8.7's candidate machine.** The candidate states `proposed → validated → approved → applied` with their exits belong to 08.3.1 and are only *referenced* here (`plans/00-overview.md:295`); this story adds a review artefact that has no approval power over a script.

| From | To | Allowed when | Refused |
|---|---|---|---|
| — | `shadow` | a rule classification has sufficient input and yields a proposal, whether window is missing, open or already passed | unknown/ambiguous/non-drift label, override-only or missing input writes no proposal |
| `shadow` | `open` | the exact version-pair project's window is passed/closed, current label and target/hash still valid, healing enabled; close command or post-close classification invokes the same guard. Mint here only for non-sensitive rule-sourced locator drift | window missing/open/superseded, stale input or override cannot mint; sensitive proposal can open for second-person review but never mints |
| `open` | `accepted` | route 4 fresh hash/target, exact passed window, all capabilities, sensitive second-person guard met | open window `409`; stale `412`; terminal `409`; sensitive guard `403`; unknown actors dismiss-only |
| `shadow`/`open` | `dismissed` | human decision with reason (shadow dismiss is allowed), or system relabel with `relabelled` | terminal rows `409`; never delete |
| `shadow`/`open` | `expired` | TTL passed or case revision superseded, independently of classification of a new revision | accepted rows never expire |
| `shadow`/`open` | `superseded` | newer incident/classification for same kind/step, or either version bump; atomically retire previous row before insertion | terminal rows immutable; existing candidate ids retained for audit but no longer approval-eligible |

**Single offering invariant.** `drift_shadow_window` has exactly three states — `open → closed | superseded` — and at most one window is `open` per `(org_id, project_id)` across ALL version pairs; an offer/approval is eligible only while its exact pair has a `closed` (passed) window and no replacement window is open. `open → closed` requires that project's RLS-scoped adjudicated gates; missing evidence stays `open`. Either version bump atomically moves an open old window to `superseded` (or supersedes a previously `closed` one) and sets `superseded_by_id`, invalidates old shadow/open proposals and their candidate approval eligibility, then opens the new pair. Only this supersede command force-closes; it never marks quality passed. New classifications after a passed close create shadow rows then immediately attempt guarded promotion; no missing post-close transition. 08.3.1/08.6.1 approval rechecks this window and proposal linkage and returns `409 window_open` while a window is open, including for a previously minted candidate.

**`generated_script` is never moved by this story.** The four states and the `draft → active · flaky → retired` edges are 00 §8.11's verbatim (`plans/00-overview.md:315`); activation counts CI-verified runs only (13.5.1-AC20, `…13.5.1-bound-playwright-scripts.md:59`), and this story touches no script row at all — a candidate that a human later approves still needs 08.6.1's approval and its own canary.

## 7. Jobs and integrations

- **Trigger (outbox) — hand-over.** `ClassifyDriftCommand` is dispatched by an outbox row written in 08.2.2's label-write transaction, so a label and its classification cannot diverge. 08.2.2 is **not built** (`STATUS.md` §2/§5 carry no 08.2.2 row on `d54349e5`), and its outbox event name is that story's to fix; this plan therefore names the **shape** ("a label-change event carrying incident id, previous and new label, actor and `label_source`") and records the exact name as a review question for 08.2.2's owner, not a dependency edge.
- **Fallback sweep — idempotent.** Select tenant/project-scoped `test_drift` incidents with complete context and non-local runs lacking a rule classification for the **current `(rule_version, similarity_version)` pair** per bound step. Dispatch the same natural key including both versions; unique rule index + conflict-do-nothing makes replay harmless, while a similarity-only bump is never skipped.
- **Shadow close schedule.** Computes gates only over this project's own independently adjudicated rule rows under FORCE RLS, not the global corpus. Missing/inconclusive gates hold the window `open`; a pass moves it to `closed` and promotes eligible shadow proposals atomically; either version bump runs the supersede path of §6 instead of a quality close. Candidate mint occurs only on eligible promotion.
- **Consumed, not built:** 13.5.1-T1/T4 bound steps and `generated_script_run` (outcome/CI provenance/timestamps; script-less rows ineligible); 13.6.1-T1/T2/T3 profiles/view/similarity and its failed-step read (§5 read 3, `IElementProfileReader.FailedStepAsync`, the read whose returned id this plan stores as `drift_classification.failing_profile_id`; it answers `no_profile` when the locator never resolved, `OI-13-558`); 08.3.1-T1 rule-only candidate mint; 13.1.2-T1 pending changes; 08.6.3 healing switch. Platform-release measurement additionally awaits 08.8.1-T3 holdout (V2) and 08.8.2-T2 false-repair definition (`OI-13-553`), not added silently to task graph edges.
- **13.9.1-T3 read tenancy.** Its project gate query reads only the requesting org/project's window snapshots/classifications under that project's RLS scope and triage authorization. Platform corpus release reports are a separate privileged aggregate with no cross-project raw rows exposed by these routes.
- **No new outbox consumer beyond the classification trigger, and no event emitted by this story:** 13.9.1-T3 reads the window snapshot and the classification rows directly as a query, so nothing waits on an event that does not exist (A10/C7 apply only where work must cross a transaction).
- **No model anywhere, including downstream mint.** Narrow 08.3.1 to `IRuleOnlyCandidateMint`; traverse classify+mint assembly dependencies and calls in Architecture.Tests. `IElementProfileReader` is prohibited from prompt builders, gateway and 13.7.2; 13.7.2 receives only class/step ids here, never profiles, hashes or reader access.

**Trust boundaries and five abuse cases.** (1) Replay uses the full version-pair natural key and current label. (2) Raw secret/name text is rejected before hashing; exact hash equality cannot bypass missing/dropped/truncated/uncontrolled-input abstention. (3) RLS and capability pairs protect verdict/payload and project adjudications. (4) Override never mints and open-window promotion/approval is blocked, including previously minted ids. (5) Metadata-default-sensitive cases never mint, and both proposal kinds need an independent second person to accept.

- **Authorization:** four routes, three existing capabilities: triage for derived verdicts/override; proposal payload additionally authoring-read; decisions additionally authoring-write (default, `OI-13-555`). No route returns profile content/hash. Catalogue roles: QA triage/read/write, no approve (`contracts/permissions.json:24-52`); maintainer approve/read/write, no triage (`:54-91`); tenant admin neither healing capability (`:112-151`). Foreign id `404`; sibling-project scoped credential `403 project_scope_mismatch`; worker scoped per tenant/project.
- **Retention/deletion:** classification and proposal rows inherit the incident's retention via 08.1.2-T2 (no second mechanism); window rows inherit project retention; the append-only guard on `drift_classification` allows deletes only from `evidgate_owner`, so tenant erasure and retention sweeps can run while the app role cannot rewrite history; nothing here outlives the case revision it references by design — an expired proposal is a state, not a deletion.
- **Telemetry:** `evidgate_drift_classification_total{drift_class, class_source, rule_version, reason}`, `evidgate_drift_proposal_total{proposal_kind, state}`, `evidgate_drift_window_close_total{outcome}` and `evidgate_drift_skipped_total{reason}` (labels are closed sets: class, source, state, rule version, reason code — `reason` is set only on `drift_class="unknown"` and on `skipped`, never an incident id, project name, case title, locator or accessible name); no new dashboard is required; a jump in `ambiguous` is a similarity-threshold signal and a jump in `skipped{reason="origin_local_not_evidence"}` is a local-run habit.
- **Failure path:** missing/unsupported similarity, incomplete context, no profile, stale revision, dropped fields, truncation or capture_controlled=false → unknown with closed AC1 reason, zero proposal/candidate. Local run skipped entirely. Crash rolls back. Missing/inconclusive project or platform-release evidence holds the applicable gate. Window replacement supersedes old offers and blocks approval; stale accept `412`, open-window accept/approve `409`, sensitive actor violation `403`. Never retry into a guessed class or delete history.
