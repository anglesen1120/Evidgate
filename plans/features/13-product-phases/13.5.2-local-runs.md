## 1. Goal and non-goals

**Goal.** One command, `evidgate run`, executes already-generated tests on the developer's own machine and pushes the results through **the same machine as CI**: the shipped 04.3.1 Playwright reporter writes the same 00 §9.4 envelopes into the same spool layout, `events send` batches and keyed-retries them with the same rules, `runs finalize` closes the producer slot the same way, and snapshots travel the same presigned `upload-url` → `complete` path. Parity is achieved by *reusing* the four shipped pieces verbatim (`packages/adapter-playwright`, `packages/cli/src/sender.ts`, `finalize`, `attachmentUpload`) and adding exactly one command plus a manifest builder and a child-process launcher. Nothing about the event, artifact or run contract changes.

**Area-plan acceptance.** `evidgate run` executes selected generated tests on a developer machine and ingests results and redacted snapshots exactly like CI (`plans/13-product-phases.md:196`).

**Partial against that acceptance (`OI-13-530`).** The *results* half is delivered in full: payload shape, batch and idempotency behaviour, tenant binding and the exit-code registry are byte-for-byte the CI path (§2 AC2–AC4, §9). The *redacted snapshots* half is **not** deliverable by this story, for a reason this plan can cite rather than a gap it invents: the shipped reporter declares `supports.capture_control: false` (`packages/adapter-playwright/README.md:234-240`) because it does not yet read `capture_enabled`, `redaction_rules` or per-kind `max_bytes` from the run-create configuration document (`contracts/adapter/config.v1.json:22-62`), and the task that delivers that reading — 06.2.2-T1 "adapter capability + per-project options (disable kinds, allowlisted redaction rules)" — is still queued, not merged (`STATUS.md:226`). So **no** capture gating or source-side redaction exists today for CI runs either: a local run is labelled `capture_uncontrolled` by the server exactly when a CI run of the same reporter is (`contracts/adapter/capability.v1.json:74-77`), and every byte it uploads is then subject to the server's `scan_state`/sensitivity path (`plans/00-overview.md:352`, ruling T19). This plan therefore claims structural parity and the *same* redaction posture as CI; it claims no source-side redaction of snapshots, and `OI-13-530` records 06.2.2-T1 as the receiver that closes the remaining half. A **second** conjunct of the same acceptance is blocked and is recorded in that one row: the shipped reporter emits the all-zero placeholder `execution_key` (`packages/adapter-playwright/src/identity.ts:8-15`, "the reporter never hashes it") and the server refuses a key outside the run's plan with `422 unknown_execution_key` (ruling T10, `plans/features/README.md:60`), so the *ingest* half cannot succeed on a developer machine until 05.2.1-T3 ships the real key (`plans/05-runs-orchestration.md:183`, partial at `STATUS.md:278`). That blocks a CI run of the same reporter identically, which is why the parity claim itself stays true; the failure path is named in §5 (exit 3, server code verbatim, no retry, spool kept).

**Non-goals.** Generating or repairing scripts (13.5.1, 13.8.x); element profiles and their capture (13.6.1-T1); drift classification; release decisions, gate verdicts and `release_decision` (07); the reporter itself, the envelope schema, the spool format and the send/finalize commands (04.3.1, 04.2.3); artifact upload, its journal and its allow-list (04.2.4); the capture/redaction configuration document and per-project capture flags (06.2.2); the secret-scan task (06.2.3); any server-side execution of generated code — the platform never runs it (`plans/13-product-phases.md:101`, architecture rule A5); the CI quickstart workflow (04.2.4-T2, `contracts/cli.md:599-723`); and any new permission, endpoint, table or migration.

**Prior art.** Playwright's own CLI (`https://playwright.dev/docs/test-cli`) and custom-reporter API (`https://playwright.dev/docs/api/class-reporter`): taken — delegate *selection* to the engine (`--grep`, `--project`) rather than re-implement matching, and attach a reporter by configuration, never by patching the user's tests. Deliberately not followed: `--reporter` **replaces** the configured reporter list and `--add-reporter` only exists in newer releases, so the command must compose a config that appends the Evidgate reporter instead of overwriting a developer's own reporters (`§10 13.5.2-T1.3`; whether the installed Playwright release offers `--add-reporter` is a build-time `[INFERENCE]` check recorded in the Notes, not an open item); and no "local mode" branch is added to the reporter — a second code path in the emitter is exactly how local and CI payloads drift apart.

## 2. User stories and acceptance criteria

- As a developer, I run the scripts I generated for one test case on my laptop and see Evidgate results — pass/fail, retries, steps, attachments — without pushing a branch or waiting for CI.
- As a developer, I discover *why* a local run did not reach Evidgate from one stderr line: a closed `error.code`, a `request_id` and a hint, never a token.
- As a QA engineer, I re-run the same local command after an outage and it resumes instead of duplicating: no second event, no second artifact, no second run.
- As a release approver, I can tell a local run apart from a CI run and I know a local result never moves a release decision or a script's stability state.

Every criterion has a named proof in §9. Numeric defaults marked `[INFERENCE]` are build defaults, not measured product facts. All refusal codes below are either existing `contracts/cli.md` §5 codes or the closed set this plan adds to the T2 documentation (`AC14`); none of them is a new exit code.

## 4. Data model and migrations

**No new table, no migration, no column.** A local run *is* a run: it writes the shipped `run`, `producer_slot`, `event`, `case_attempt` and `artifact` rows through the shipped routes. What this story must prove is that it adds no *row shape*: the `SchemaConventionScan` exemptions, `rls-exceptions.txt` and the composite-FK lint stay untouched because nothing new is created.

Rows the path touches, and what binds them (`plans/00-overview.md:181-190`): every one carries `org_id` (business FKs composite `(org_id, <id>)`, `:183`), sits under `FORCE ROW LEVEL SECURITY` with the app role neither owner nor `BYPASSRLS` (`:185`), and is scoped only by `evidgate.current_org_id()`/`current_project_id()`, so an unset tenant context yields zero rows (`:189`). No `org_id` or `project_id` is ever read from the request body or from a flag.

| `artifact` | `upload-url` + `complete` | composite FK through the run | `ready` with `scan_state` per T19 (`plans/features/README.md:68`); `pending/` objects expire in 24 h (T18) |
| `run` | `runs create` (05.2.1) | composite `(org_id, project_id)` | retained; `origin=local` is **derived**, not stored (`OI-13-535`) |

**`origin=local` has no column (default, `OI-13-535`).** Nothing in 00 §8.1 or plan 13 §4.1 lists such a column (`plans/13-product-phases.md:41-50`), and a column would be a schema change with its own RLS/retention review for one boolean. The plan therefore derives the label from data that already exists: no `--ci-ref`, no CI claims, and a slot whose `bound_ci_run_ref` is null. If 13.9.1-T2 later needs the label as a queryable filter, that is a 05.2.2 read-model decision, recorded in the same OI. It is also **not** a wire field: no contract under `contracts/` carries an `origin`, `trigger` or `provenance` member (repo-wide grep, 2026-10-28) and the adapter documents are closed (`"additionalProperties": false`, e.g. `contracts/adapter/capability.v1.json:8`, `contracts/adapter/config.v1.json:8`), so adding one would be a schema change for one label. If the owner prefers it explicit rather than derived, the cheap form is a **run-level** member on the run-create request — one place, one review, no envelope change — and never a per-event member, which would ship an event-envelope version bump before any local run works. That trade-off is `OI-13-535`.

**Retention split.** Retained: the run, its events, attempts and artifacts, under the project's retention policy. Deleted: the spool, and only by `runs finalize` after a 202 (`contracts/cli.md:1013-1020`) — a spool holding unacked events is never deleted, and no CLI command sweeps the spool root (`:1032-1042`). The upload journal is removed with the producer directory at that purge (`:1293-1296`). Playwright's own output directories (`test-results/`, `playwright-report/`) are the developer's local files: Evidgate never copies them, never keeps a second copy, and the docs say the developer owns them.

**No new endpoint, no new DTO, no new permission.** One command on top of four shipped ones.

| # | Command | Required configuration | Behaviour → exit |
|---|---|---|---|
| 1 | `evidgate run --grep <pattern> --script <uuid>… --playwright-project <name> --config <path> --json` | `EVIDGATE_API_URL`/`--api-url`, `EVIDGATE_PROJECT`, one token source (`contracts/cli.md:71-87`, `:152-156`) | validates every flag (`usage`), resolves the token (`missing_config`/`invalid_config`/`dev_token_refused`/`exchange_failed`), builds + uploads a manifest (`manifest_invalid_local`, server `manifest_invalid`), creates the run (`run_not_created` on a 2xx body that fails validation), spawns Playwright (`playwright_missing`/`config_missing`/`script_not_selected`), drains (`transport_failed`/`deadline_exceeded`/`ack_mismatch`/`spool_*`), finalizes (`unsent_events`/`spool_missing`/`spool_corrupt`), prints a summary → `0`, or `3` on any refusal |

Internal sequence (observable order, no transaction spans a subprocess):

1. flag + config validation, then `getToken()` (`contracts/cli.md:160-162`, `:499-512` is the precedent: every flag before any request).
2. select the test set: `--grep` and/or `--script` markers, `--playwright-project`; empty intersection is `script_not_selected` (AC11).
3. build the manifest for exactly that set and `POST /v1/projects/{p}/manifests` (raw bytes, ≤ 256 KiB, `Idempotency-Key` = SHA-256 of the bytes; `contracts/cli.md:428-473`).
4. consult the run pointer built in step 3's key space (AC9): if it names an **open** run this spool owns, adopt it as a resume — no create call, no new key, same `run_id`; otherwise `POST /v1/projects/{p}/runs` with `manifest_id`, **no** `ref` (a local machine has no verified ref; `contracts/cli.md:477-521`) and an explicit nonce-bearing `--idempotency-key` (`:478`, `:489`), then write the pointer and export `EVIDGATE_RUN_ID`/`EVIDGATE_SPOOL_DIR` for the child. A create response naming a run this spool did not create, or one already finalized, is `run_mismatch`.
5. spawn the child: the developer's Playwright CLI with the composed config, the `evidgate` reporter appended, and an allow-listed environment (AC13).
6. `events send --run <id>` — the shipped drain (AC3).
7. `runs finalize --run <id> --producer <slot> --shard <n> --manifest-hash <sha256:…>`, whose `last_sequence`/`count` are read from the spool, never from flags (`contracts/cli.md:993-1000`).
8. print: text mode one line `evidgate: run <id> tests=<n> passed=<p> failed=<f> events=<e> duplicates=<d> artifacts=<a>` — prefixed `resumed ` when the invocation adopted an open run — or `--json` exactly one object `{"run_id":…,"tests":…,"passed":…,"failed":…,"events":…,"duplicates":…,"artifacts":…,"origin":"local","resumed":true|false}` with those nine keys and no others, no title, no path and no token.

## 6. States and transitions

**No state machine is added.** The run lifecycle is 00 §8.1's and is driven by the same ingest calls as CI, so a local run moves exactly like a CI run and nothing in this story introduces an edge: `run` create puts the run where 05.2.1 puts it, the first accepted batch moves it where ingest moves it, and `finalize` declares the slot done with asynchronous reconcile (`contracts/cli.md:1008-1012`). Cancelling a local run is `POST /v1/runs/{r}/cancel` by whoever holds `run:cancel`; the command offers no cancel flag (out of scope, no new surface).

`generated_script` is **not moved by a local run** (default, `OI-13-534`): §8.11 fixes the list — `draft` is the PR candidate, `active` needs 3 of 3 green runs on one build after merge, `flaky` is set or cleared by the run policy, `retired` is terminal (`plans/00-overview.md:315`). This plan and 13.5.1 now state the same rule: **activation counts CI-verified runs only** (13.5.1-AC20, `plans/features/13-product-phases/13.5.1-bound-playwright-scripts.md:59`: a run counts toward the three greens only with a non-null, OIDC-verified `bound_ci_run_ref`), so an `origin=local` run never contributes to it. The reason is not only provenance: the manifest identity and `execution_key` are **client-supplied** (`contracts/manifest/manifest.v1.json:9-18`, `:126`), so a locally forged manifest could otherwise claim a case/variant identity and mint activation. A developer-machine run may inform a human; the flip authority stays 13.5.1-T4's and only on CI-verified runs.

**Abandoned local run — `[OPEN]`, owner decision, `OI-13-544` (taken outside this plan's first range because that range was full).** A run whose child died or whose drain never finished stays open server-side. The command cannot cancel it: `POST /v1/runs/{r}/cancel` needs `run:cancel` (`plans/00-overview.md:348`, `contracts/openapi.yaml:1159`) and the producer credential's closed set is `{run:create, event:write, artifact:write}` (`contracts/permissions.json:167-171`). Recommended default: do not add a permission — the run is closed by the server's own lease/expiry (`[INFERENCE]`: no run reaper was found in the tree on 2026-10-28, so this must be confirmed by 05.2.1's owner) or by a human with `run:cancel` in the UI, and the local pointer records `state: closed` after any `run_closed` refusal so the next invocation creates a fresh run instead of adopting a corpse. `[OPEN]` alternative: grant `run:cancel` to a local-only credential, which this plan does not propose.

**Progress is the spool, not a new state.** The command's observable progress is `cursor.json` (`next_unacked_sequence`, `last_acked_sequence`, `acked_count`; `contracts/cli.md:787-796`) and the per-attempt upload journal (`put_done`, `complete_done`, `mint_no`; `:1235-1248`). Partiality is an exit code plus that on-disk record, never an invented `partial` state in the API.

## 7. Jobs and integrations

- **No new outbox task, no new job, no schedule.** Ingest writes whatever the shipped ingest writes (T50's one statement, `usage` rows via 04.8.1's path), `complete` writes the shipped `artifact_secret_scan` and `artifact_staging_delete` rows (T86/T19, `plans/00-overview.md:352`), and reconcile is the shipped async step.
- **Integrations consumed:** `@evidgate/playwright-reporter` in-process (04.3.1-T1) with `spool_dir`/`run_id` from the environment it already reads (`packages/adapter-playwright/src/reporter.ts:110-114`); `evidgate manifests upload` (04.2.2-T1); `evidgate runs create` (04.2.2-T2); the spool + `events send` + `runs finalize` trio (04.2.3-T1/T2); `evidgate artifacts upload` and its journal (04.2.4-T1); the attachment drain (04.3.3-T2).
- **Consumers of a local run:** the run detail/list reads (05.2.2) show it like any run; 13.9.1-T2 must be able to *exclude* it from the 3-of-3 metric (`OI-13-534`); 13.6.1-T1's profile capture is a green-run consumer and therefore only counts local runs if its own contract says so (`[OPEN]` pointer, no edge added); 13.8.x consumes failures as incidents exactly as it does for CI runs, but its intake must **exclude or explicitly flag `origin=local`** before it classifies drift or opens a repair — a laptop failure is not a production signal (`[OPEN]` hand-over, no edge; recorded in `OI-13-535`).
- **Hand-overs (no design here):** 12.4.1-T4 (the G2 credit offer) is untouched — this story consumes no credits and calls no model; 13.9.1-T2 (G2 metric) needs the "70 % of generated scripts pass 3 of 3 on one build" definition (`plans/13-product-phases.md:66`) to state its origin filter; 13.5.1-T4/T5 own the script state and the marker; 06.2.2-T1 owns capture gating; 05.2.1-T3 owns the reporter's real `execution_key` (`plans/05-runs-orchestration.md:183`, partial per `STATUS.md:278`) — until it lands, a local run's ingest is refused exactly as a CI run's is, which is `OI-13-530` conjunct (b), not a local-only defect.
- **Failure isolation:** the command never leaves a half-created run silently — if the child fails to start, the run exists but nothing is sent, and the message says so with the run id and the next command to run (`events send`/`runs finalize` by hand); if the child runs and the drain fails, the spool keeps everything and a re-run resumes (AC9).

**Trust boundaries and five abuse cases.** Developer machine → CLI validation → token exchange → manifest → run → child Playwright → spool → drain → object store → server scan. (1) A hand-edited spool or a forged `execution_key` cannot invent results: the server refuses a key outside the plan and a reused sequence (AC4, §9). (2) On a laptop the secret that matters is the **long-lived `egt_` project ingest token**, not a short-lived CI bearer: it is issued per project to an owner/admin in the project's settings (a producer credential carrying `{run:create, event:write, artifact:write}`, `contracts/permissions.json:167-171`), shown once, and must live in the developer's secret store or a shell profile outside the repo — the docs say so, and the command never writes it to the token cache (that file holds the *exchanged short-lived bearer*, never the plaintext ingest token: `packages/cli/src/auth/getToken.ts:38-51`, `packages/cli/src/commands/authLogin.test.ts:141-145`), nor to the spool, the journal or any log (`contracts/cli.md:326-333`). It is project-scoped and slot-bound, so a leaked copy cannot read another project's runs, approve anything or hold `authoring:read`; **same-user** filesystem isolation is *not* provided — a process running as the same account can read whatever that account can, which is why the child gets an allow-listed environment and no cache directory (AC13). (3) A malicious `--config` executes on the developer's own machine with a stripped environment, so it cannot exfiltrate the Evidgate credential (AC13). (4) A snapshot cannot become an uncontrolled egress path beyond what CI already does — the run is labelled `capture_uncontrolled` while the adapter declares `capture_control: false` (AC6). (5) A foreign-org run id is a 404 and a sibling-project credential a 403 `project_scope_mismatch`, never an existence oracle (AC4). Nothing in this story is an enforcement authority the server relies on: the CLI is a convenience, the server stays the judge.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** no permission is added and no route is called with a new code: the local credential is the existing producer identity `{run:create, event:write, artifact:write}` (`contracts/permissions.json:167-171`) and `event:write` is service-only (`:376-380`), which is exactly why `--script` resolves locally instead of reading `authoring:read` (AC11). `POST /v1/runs/{r}/events` and `/finalize` need `event:write`, `upload-url`/`complete` need `artifact:write`, `manifests`/`runs` create need `run:create` (`plans/00-overview.md:345-352`). Another org's run id is `404`; a credential scoped to a sibling project is `403 project_scope_mismatch`; an unset tenant context yields zero rows; the command's own flags grant nothing and are validated before any request.
- **Retention/deletion:** no table and no column is added, so nothing new is retained: the run/event/attempt/artifact rows keep the project's retention and are erased with the project; the local spool is deleted only by a successful `runs finalize` and never while it holds unacked events (`contracts/cli.md:1032-1042`), the upload journal goes with the same purge (`:1293-1296`), and Playwright's own output directories stay the developer's files — Evidgate never copies them. `pending/` objects expire in 24 h (T18).
- **Telemetry:** the CLI emits no metric and adds no label; its only output is the fixed text line or the fixed `--json` object of §5 (no title, path, id-of-file or token). Server-side, the shipped ingest/upload telemetry is unchanged and already content-free (T50's batch row, T19's `scan_state`, 04.8.1's usage row). A new metric label would need a DoR contract edit and is explicitly not part of this story.
- **Failure path:** every refusal in §5's matrix is a closed stderr `error.code` with exit `3` from the registry (`contracts/cli.md:54-64`); the story-local codes are `script_not_selected`, `config_missing`, `playwright_missing`, `run_not_created`, `manifest_invalid_local`. Server refusals keep their own codes verbatim (`project_scope_mismatch`, `producer_slot_taken`, `unknown_execution_key`, `sequence_reused`, `run_closed`, `idempotency_conflict`, `upload_*`), a 401 purges the cached token, a 403/422 keeps it, and a failed drain leaves the spool intact so a re-run resumes rather than duplicates. No failure path prints a token, a presigned URL or a file's contents (`contracts/cli.md:1267-1268`, `:1298-1306`).

## 11. Rollout

1. **Contract proposals first (DoR):** the `contracts/cli.md` §1 command row and the §2 sentence about a completed local run exiting `0` (`OI-13-532`), and the flag-naming decision `--playwright-project` (`OI-13-531`). Nothing else in `contracts/` moves, so a wrong proposal costs one table row, not a migration. The `origin` marker of `OI-13-535` is **not** proposed here: that wire change belongs to the run-create owner, and this story ships against whatever form it lands in.
2. **Then the code in sub-task order:** T1.1 (registry) → T1.2 (selection + manifest + run create) → T1.3 (child + reporter) → T1.4 (drain/close/exit codes) → T1.5 (output contract) → T2 (docs). The server is not deployed for this story: every call it makes already exists.
3. **Rollout shape:** the command ships dark by being add-only — no existing command, route, table or config key changes behaviour, so there is no flag, no migration order and no data backfill. A tenant that never runs `evidgate run` sees nothing new.
4. **Monitoring:** the shipped ingest metrics and the run list are the observability (a local run is a run); the CLI's own signal is its exit code and its one summary line. No new dashboard and no new alert; a spike of `403 project_scope_mismatch` or `unknown_execution_key` on the ingest route is the signal that a local setup is misconfigured, and the T2 troubleshooting table is the runbook.
5. **Rollback:** delete the registry row (or ship the package without it). Because the story adds no server-side change and no stored state beyond ordinary runs, rollback is instant and loses nothing; a spool left behind is purged by the developer or by the next successful `runs finalize` (`contracts/cli.md:1032-1042`).
