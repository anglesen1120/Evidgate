## 1. Goal and non-goals

**Goal.** Make a green run leave behind **one structural record per bound step** — no text, no input values, no credentials, no pixels — so that a later failure can be reasoned about as *locator drift* or *UI change* without asking a model and without re-opening a browser. Three pieces: capture on the customer side at the bound step with the allow-list and redaction applied **before** anything is hashed and before the profile is encoded into the step's `ext` member (T1), an append-only `element_profile` store with a latest-green derivation and tenant isolation (T2), and a versioned similarity function over the stored profiles with stability tests (T3).

**Area-plan acceptance.** "each green run records a profile per bound step, keyed to the case revision and step; profiles hold structure, not content; the latest green profile per step is queryable; similarity is a versioned function with stability tests" (`plans/13-product-phases.md:204`). The four clauses are AC1, AC2, AC3 and AC4 respectively.

**Partial against that acceptance, clause 4 (`OI-13-549`, proposed, owner confirmation pending).** "Similarity is a versioned function with stability tests" is delivered in the *deterministic* sense: one implementation, a pinned `similarity_version`, a documented input/distance/threshold rule set, stability tests over dynamic ids, locales, reorder and duplicate names, and a verdict that replays byte-for-byte on the same rows.
It is **not** delivered in the *validated* sense: no accuracy claim, no tuned threshold, and no measurement on real breaks — those need the labelled corpus (08.8.1-T1/T3) and the shadow window (13.8.1-T4), neither of which exists on this base. The two thresholds in AC4 are `[INFERENCE]` build defaults, not measured product facts.

**Second partial, clause 1 (`OI-13-546`, proposed, owner confirmation pending).** "each green run records a profile" holds for every run the adapter *can* capture. The shipped adapter declares `supports.capture_control: false` (`packages/adapter-playwright/README.md:234-240`), so per-project capture flags and redaction patterns from the run-create configuration document are not read; the precedent label is 13.5.2's `capture_uncontrolled` (`OI-13-530`), which this plan consumes and **does not re-decide**.
A step whose page context is gone — the element never resolved, the run is `ingest_only`, the step is `not_applicable` — records **`capture_unavailable` with a closed reason instead of a profile**, and the run keeps its state: capture never fails a run and never edits a `generated_script` (`plans/00-overview.md:315`).
A bound step that **did** resolve its element and then failed is captured, and its row carries the run's `outcome` (`red`) with `provenance = self_asserted`, so it can support a diagnosis but is never eligible for latest-green (`R1(c)` of the review; decision (c) shared with 13.8.1, which reports `unknown/no_profile` for the unresolved case).

**Adopted, not invented.** Plan 13's rule for a profile-spec change is adopted verbatim: "`spec_version` stored; similarity only compares equal versions; backfill job re-derives" (`plans/13-product-phases.md:96`). Two versions are **stored** on the row — `spec_version` (document shape) and `capture_version` (capture implementation) — and compared for equality only; `similarity_version` is **computed at read time** from the pinned matcher, because it describes the query, not the fact (`R4` of the review: storing it would need it in the unique key and in the view for no gain, and every matcher bump would make every stored row `requires_backfill`). A row whose `spec_version` the pinned matcher cannot read is skipped as `requires_backfill`; the backfill is a documented re-derivation query, not a mutable row (name: `OI-13-550`'s receiver owns the job row if one is ever needed).

**Non-goals.** Drift classification, its rules and its proposal paths (13.8.1); the multimodal fallback (13.7.2); any repair, candidate, validator or PR (08.3, 08.4, 08.6); the incident fingerprint — profiles are **not** a second fingerprint and never replace 08.1.2-T3's versioned one; DOM/accessibility **artifact** capture, artifact kinds, uploads, secret scan and screenshot policy (08.1.2-T1/T2, 06.2.2, 06.2.3, 13.5.1-T1.7); the generated script's emitted code, its PR payload and its stability window (13.5.1-T1/T4/T5); `evidgate run` and local-run labelling (13.5.2); every screen and design file (13.8.2-T2 owns the review additions; no screen is designed here).
Also out of scope: the document rejection corpus (08.8.1), gate metrics (13.9.1-T3), and any model, gateway, provider or credit path — plan 13's Q1/Q2 (`plans/13-product-phases.md:257-258`) do not reach these stories, and 12.4.1-T4 consumes no credits here.

**Prior art (owner rule, 2026-10-27; vendor-neutral, approach only).**
(1) *Playwright `Locator.ariaSnapshot()`* (`https://playwright.dev/docs/aria-snapshots`, `https://playwright.dev/docs/api/class-locator`): taken — the accessible subtree of a **scoped locator** (roles, optional accessible names, states, nesting by indentation) is the right capture primitive, because it exists in the page context where the reporter has no DOM handle.
Deliberately not followed: storing the YAML text (it carries accessible names and `text:` lines, i.e. content) and using `toMatchAriaSnapshot()` as the product matcher (an order-sensitive assertion with partial-match templates, not a versioned score).
(2) *Healenium property weighting* (`https://www.healenium.io/`) and *NIST's threshold/margin* argument (`https://www.nist.gov/blogs/taking-measure/tale-two-errors-measuring-biometric-algorithms`): taken — weight signals (semantic identity strongest, container/neighbours supporting, position weakest) and accept only when **best ≥ threshold AND best − runner-up ≥ margin**, else abstain; a score is never a probability.
Deliberately not followed: healing or promoting anything because a run went green, and Healenium's proxy/DOM-diff capture — a profile is promoted only by a CI-verified green run with an attributable build identity (AC8), and capture is in-process at the bound step. Budget: 2 searches, 3 sources.

## 2. User stories and acceptance criteria

- As a test maintainer, after my case's steps run green I can see the structure each step bound to, so a later break has something to be compared against that is not a screenshot and not a page dump.
- As a security reviewer, I can point at one allow-list and one redaction point and say no page text, input value, cookie, header, token or storage state ever left the customer's machine in a profile.
- As the drift classifier (13.8.1), I read one latest-green row per step and get a versioned verdict — match, ambiguous or no claim — that replays identically next month on the same rows.
- As a project owner, a local `evidgate run` never becomes the memory my repair decisions are made from.

Every criterion has a named proof in §9. Numeric defaults flagged `[INFERENCE]` are build defaults. All refusals are existing codes or the closed set §5 names.

## 3. Contracts touched

This story **edits no contract in this PR**. Everything below is a proposal for the owning task's DoR review, or a consumption of a shipped contract. Nothing here is applied by this document.

- **`contracts/adapter/element-profile.v1.json` — new file (proposal, `OI-13-545`):** the closed profile document of AC2 plus the `capture_version` enum and the caps. Strictness is part of the proposal, not an afterthought: every enum is an explicit member list ending in `other` (so an unrecognised page value stays content-free instead of being dropped into free text), every integer states its bounds (`depth` 0–64, `node_count` 0–2000, `region_ordinal` 0–255), every object level is `additionalProperties: false`, and the vector set carries one canary per page-controlled field (text, accessible name, `value`, placeholder, `href`, cookie, header, storage, `data-*` value, XPath) that must be refused or omitted. It is a *new* file rather than a member of `capability.v1.json`, whose `supports` object is closed and already carries `capture_control` (`packages/adapter-playwright/README.md:234-240`).
- **`packages/adapter-playwright/README.md` §"`ext` allow-list" (`:242-270`) — proposal (`OI-13-545`):** add exactly one `test.step` key, `element_profile`, plus one reserved attachment name (`evidgate.element-profile`) that the reporter consumes and never forwards. The guard rail is welcome and stays: the reporter builds a candidate from raw Playwright objects and drops every undeclared key, and a step envelope must never *carry* an attachment — `stepExt` deletes the raw `TestStep.attachments` list on purpose (`.ts:944-948`). The reporter still **holds** that list in hand, so the payload rides in as a step-scoped attachment the reporter reads, caps, redacts and converts into the single `ext.element_profile` member. This is the one seam the earlier draft got wrong: forwarding an attachment is forbidden, reading one is what the reporter already does with the rest of the step.

**Latest green is a view, not a mutable row.** `element_profile_latest_green` selects, per `(org_id, project_id, case_revision_id, step_key, target_env, variant_hash)`, the row with the greatest **`ingest_seq`** (server-assigned, monotone per tenant; `finished_at`, `created_at` and `run_id` are deliberately *not* the ordering key, because the first two are client-supplied and the third is a random UUIDv7 that only agrees with time by accident) among rows that are eligible on **every** condition of AC3: `provenance = 'run_verified'`, `outcome = 'green'`, joined to a `generated_script_run` row with `ci_verified = true` and a complete build identity, `script_id` present, `origin_local = false`, and the run's git ref inside the project's **baseline ref set**. That set is project configuration owned by the run policy (13.5.1-T4 reads it for the stability window); if it is undefined the view returns nothing rather than falling back to "any ref", so a feature branch can never become the baseline by default. It is a plain view over immutable rows, so a re-derivation (the `plans/13-product-phases.md:96` backfill) is a `select`, never an `update`, and a wrong promotion cannot be "fixed" by editing memory. A materialised table was rejected: it would need its own write path, its own RLS story and its own chance to drift from the rows.
The view is created `with (security_invoker = true)` and granted `select` to `evidgate_app`, so it reads with the caller's privileges and the base table's tenant policy — and because `tests/Isolation.Tests/Rls/RlsIsolationTests.cs:85-91` fails any `v`/`m`/`f` relation the app role can SELECT that is not in its (today empty) `SelectableRelationAllowlist`, T2.1 adds exactly one allowlist row citing this migration, with the `security_invoker=true` assertion of `:534-540` already enforced by that suite.
The alternative — one Dapper statement in the repository and no view object, the shape 13.1.1 chose for its uncovered read model and justified there ("why it is not a SQL view", `plans/features/13-product-phases/13.1.1-feature-tree-and-manual-test-cases.md:237`) — was rejected because the area plan names a view (`plans/13-product-phases.md:208`) and the allowlist mechanism exists for exactly this case; if the owner prefers it, the change is local to T2.1/T2.3, drops the allowlist row, and costs no contract edit.

**Retention split, stated once — and bounded, because "as long as the case revision" is not a bound.** Profiles are small structural facts and are retained as long as the case revision they describe (and purged with it or with the project); `dom_snapshot`, `a11y_snapshot` and `screenshot` artifacts keep the retention their own kind promises (06, 13.5.1-T1.7) and are **not** referenced from this table — no `evidence_artifact_id`, no copy, no orphan. On top of the lifecycle bound, three limits keep the store from growing without end (defaults `[INFERENCE]`, `OI-13-559`): the **newest 20 eligible rows per `(project, case revision, step_key)`**, a **pin** on any row referenced by an open classification (13.8.1's verdict or an open candidate — pinned rows survive the bound while the reference is open), and a **180-day TTL** on unpinned rows. Deletion is `REVOKE DELETE` for the app role plus one named purge job (`element_profile_retention`) that runs under the **owner role** in 08.1.2-T2's hook set (`plans/08-healing-learning.md:152`), re-used and not re-implemented: 13.6.1 contributes one hook registration row, and `ElementProfileRetentionTests.hook_covers_table` fails when that hook set stops covering `element_profile`, so the dependency cannot decay silently.

**Why the similarity lives here and not in the Worker.** The 08.2.2 rule triage runs in the Worker over an incident's context; profiles are different input: they are *many small immutable rows already in PostgreSQL*, the verdict must be a pure function of `(rows, similarity_version)`, and 13.8.1 must be able to re-run it after a backfill without touching a job queue. Putting it in the Worker would (a) need a second tenant-scoped read path with its own WLM/RLS story, (b) hide a versioned derivation behind a queue retry, and (c) make "same rows, same version, same verdict" depend on which worker ran. It is therefore an application-layer query over the store, computed server-side, never in a browser and never by a model.

## 6. States and transitions

**No state machine is added.** A profile row is an immutable fact; the only things that look like states are derivations, and each is computed from rows rather than stored as a column that could go stale:

- `capture_state` per step per run ∈ `recorded | unavailable(reason)`, derived from the presence of a row and the capture reason the envelope carried (AC5). It never blocks a run, a case result or a script transition.
- The latest-green selection of AC3 is a view over append-only rows (§4). Nothing "moves" a profile to latest; a newer eligible green row wins because its server-assigned `ingest_seq` is higher (never the client `finished_at`), and a bad row is superseded by rows, never repaired by an `update`.
- A row's **`spec_version`** is compared for equality and nothing else (`plans/13-product-phases.md:96`); `similarity_version` is not a row state at all, it is the matcher's constant returned with the verdict (AC4). A `spec_version` the matcher cannot read is `requires_backfill`; the re-derivation writes new rows, because the store has no update path at all.
- `origin=local` rows are stored and readable, and are **excluded** from the derivation and from every similarity input. This is 13.5.2's decision (`OI-13-535`) consumed here; the reason it matters is that a laptop run's manifest identity is client-supplied (`plans/features/13-product-phases/13.5.1-bound-playwright-scripts.md:390`), so a local "green" would otherwise become the memory repair decisions are made from.
- **A failing run's row is not a state either:** a bound step whose element resolved and then failed is stored with `outcome = 'red'` and `provenance = 'self_asserted'`, is readable for diagnosis, and is never eligible for latest-green (AC1, AC3, AC8). A bound step whose element never resolved has no row at all, and 13.8.1 reports `unknown/no_profile` for it — the 13.8.1-side partial this plan hands over (decision (c)).
- The verdict vocabulary is closed and borrowed, not invented: `match` (profile similarity says this is the same element), `ambiguous` (best below threshold **or** best − runner-up below the margin), `no_claim` (no eligible row, unreadable `spec_version`, or the rule the caller applies refuses). `ambiguous` is exactly the hand-off to 13.7.2 and `no_claim` is exactly "the rules decide nothing" — 13.8.1-T1 turns these into `test_drift` / UI change / nothing, and this story does not decide a drift class.
- `generated_script` states are untouched: capture cannot activate, retire, set or clear `flaky` (`plans/00-overview.md:315`), and no row here is an input to activation.

- **Authorization:** no route, no permission and no principal in this story: all three reads are repository calls with no HTTP surface. Any later surface must obey three rules (`OI-13-547`, decision (e)): it returns **ids, scores and classes only — never a profile body and never a hash**; reading **derived verdicts** needs `healing:triage` (`contracts/permissions.json:422`); a **proposal payload** needs `authoring:read` as well (`:269`). The receiver is 13.8.2-T2 (and 13.8.1-T1 if it ever needs an HTTP read). Nothing is added, widened or moved: the producer set `{run:create, event:write, artifact:write}` (`:167-171`) is what writes profiles, through the shipped ingest route it already holds, and `event:write` stays service-only. The similarity entry point is a module call with no route and no principal, so it cannot be used to read another tenant, and the `Architecture.Tests` rule keeps it out of every prompt/gateway path. Isolation expectations: an unset tenant context yields zero rows, a case revision or script outside the caller's tenant yields zero rows from all three internal reads, the composite FK refuses a cross-tenant parent at insert, and the classify query filters by project before scoring.
- **Retention/deletion:** `element_profile` is retained as long as its case revision and purged with it and with the project, **and bounded on top of that** (AC10, `OI-13-559`): newest 20 eligible rows per `(project, case revision, step_key)`, pins while a referenced classification is open, a 180-day TTL on unpinned rows, and one named job (`element_profile_retention`) running under the owner role inside 08.1.2-T2's hook set rather than a second scheduler — **hook coverage of this table is a DoR dependency**, and `ElementProfileRetentionTests.hook_covers_table` fails the build when it is missing. The app role has `REVOKE UPDATE, DELETE`, so no request can erase history mid-promotion. The split against artifacts is explicit and is the point of §4: a profile is a few hundred bytes of structure and outlives nothing, while `dom_snapshot`/`a11y_snapshot`/`screenshot` keep their own shorter promise and are never referenced from this table. The step attachment is consumed in memory (an inline `body`) so no new file enters `test-results/`; when an engine path form is used instead, the reporter reads it once and the file is Playwright's own test result, retained by the customer's CI and never by us. A sidecar in the `OI-13-545` fallback follows §11.8 and is deleted on successful send.
- **Telemetry:** counters and no content: `evidgate_element_profiles_total{capture_state, capture_controlled}` on the client side (counted, not exported by the CLI) and `evidgate_element_profile_verdicts_total{verdict}` plus `evidgate_element_profiles_stripped_total{reason}` server-side (`element_profile_invalid`, `element_profile_unknown_step`, `element_profile_run_cap`); all label-only, with no case, step, project or name in a label. Nothing new is logged: a stripped or rejected profile logs its reason code and nothing else, and the existing ingest/upload telemetry is unchanged.
- **Failure path:** every failure is a labelled absence, not an edge. Client side: `capture_unavailable` (`no_page_context`, `ingest_only`, `engine_unsupported`, `attachment_missing`, `capture_error`) and `profile_size_exceeded`, counted, never fatal to the run. Server side: an invalid, oversized, unbound or over-cap profile is **stripped from its envelope** (`element_profile_invalid`, `element_profile_unknown_step`, `element_profile_run_cap`) and the envelope is stored as if the key were absent — the profile key never turns a valid envelope into a 422 — while a row whose stored `spec_version` the matcher cannot read degrades to `no_claim` + `requires_backfill` rather than an error. All three internal reads answer zero rows outside the caller's tenant and never leak existence; a damaged jsonb row is skipped and counted (`corrupt_row`) instead of failing the page.

1. **Contract proposals first (DoR):** the new `contracts/adapter/element-profile.v1.json`, the single `ext.element_profile` allow-list row and the reserved attachment name in the reporter README (`OI-13-545`), and the FR-13-6 name-hash wording (`OI-13-548`). 2. **Then the code in sub-task order:** T1.1 (schema) → T1.2 (collector + step attachment, with the engine assertion) → T1.3 (reporter filter + redaction) → T1.4 (reasons + posture + failing-run capture) → T2.1 (migration + view + allowlist row) → T2.2 (projector: validation, strip, counters) → T2.3 (reader + retention wiring) → T3 (spec → implementation → classify query → stability corpus). The server deploy for T2 is one forward-only migration; nothing else in the API changes.
3. **Dark by construction:** capture is additive on `test.step` envelopes and the store is write-only until a read surface ships (13.8.2-T2's screen or 13.8.1's classifier), so a project that never reads it sees nothing new. No new CLI flag is added: the off-switch is shipping the package without the collector call (13.5.1-T1's emit), plus the adapter's own `supports.step_events`/`mode` handling, and neither costs a migration.
4. **Monitoring:** `evidgate_element_profiles_total{capture_state, capture_controlled}`, `evidgate_element_profile_verdicts_total{verdict}` and `evidgate_element_profiles_stripped_total{reason}` (labels only, no tenant data). Watch the `capture_state` mix first: a jump in `attachment_missing` means T1.2 and T1.3 disagree about the reserved name or about step scoping, a jump in `no_page_context` usually means a case whose steps fail before the element exists — a case-quality signal, not a profile bug — and a rise in `stripped{reason="element_profile_invalid"}` means client and server canonicalisation have drifted apart (they must compute the same RFC 8785 bytes). A `profile_size_exceeded` cluster means a subtree shape the caps did not anticipate.
5. **Rollback:** forward-only migration; the levers are (a) stop emitting the collector call from the generated script (T1's data stops growing, stored rows stay readable and harmless), (b) stop the projector with a feature switch that leaves the envelopes valid and merely drops the new key (the strip path already behaves that way, so the switch and the failure mode are the same code), (c) pin `similarity_version` back if a matcher regression appears — the version rule makes this safe, because the matcher version is not stored and the backfill writes new rows. No rollback path deletes profile rows; they are purged by the retention path only.
