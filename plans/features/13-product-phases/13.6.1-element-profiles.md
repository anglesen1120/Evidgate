## 1. Goal and non-goals

**Goal.** Make a green run leave behind **one structural record per bound step** — no text, no input values, no credentials, no pixels — so that a later failure can be reasoned about as *locator drift* or *UI change* without asking a model and without re-opening a browser. Three pieces: capture on the customer side at the bound step with the allow-list and redaction applied **before** the profile is encoded into the step's `ext` member (T1), an append-only `element_profile` store with a latest-green derivation and tenant isolation (T2), and a versioned similarity function over the stored profiles with stability tests (T3).

**Area-plan acceptance.** "each green run records a profile per bound step, keyed to the case revision and step; profiles hold structure, not content; the latest green profile per step is queryable; similarity is a versioned function with stability tests" (`plans/13-product-phases.md:204`). The four clauses are AC1, AC2, AC3 and AC4 respectively.

**Partial against that acceptance, clause 4 (`OI-13-549`, proposed, owner confirmation pending).** "Similarity is a versioned function with stability tests" is delivered in the *deterministic* sense: one implementation, a pinned `similarity_version`, a documented input/distance/threshold rule set, stability tests over dynamic ids, locales, reorder and duplicate names, and a verdict that replays byte-for-byte on the same rows.
It is **not** delivered in the *validated* sense: no accuracy claim, no tuned threshold, and no measurement on real breaks — those need the labelled corpus (08.8.1-T1/T3) and the shadow window (13.8.1-T4), neither of which exists on this base. The two thresholds in AC4 are `[INFERENCE]` build defaults, not measured product facts.

**Second partial, clause 1 (`OI-13-546`, proposed, owner confirmation pending).** "each green run records a profile" holds for every run the adapter *can* capture. The shipped adapter declares `supports.capture_control: false` (`packages/adapter-playwright/README.md:234-240`), so per-project capture flags and redaction patterns from the run-create configuration document are not read; the precedent label is 13.5.2's `capture_uncontrolled` (`OI-13-530`), which this plan consumes and **does not re-decide**.
A step whose page context is gone (the step failed before its element existed, the run is `ingest_only`, the step is `not_applicable`) records **`capture_unavailable` with a closed reason instead of a profile**, and the run keeps its state: capture never fails a run and never edits a `generated_script` (`plans/00-overview.md:315`).

**Adopted, not invented.** Plan 13's rule for a profile-spec change is adopted verbatim: "`spec_version` stored; similarity only compares equal versions; backfill job re-derives" (`plans/13-product-phases.md:96`). This plan adds the *versions* the rule needs — `spec_version` (document shape), `capture_version` (capture implementation) and `similarity_version` (matcher) — and compares nothing across unequal values; the backfill is a documented re-derivation query, not a mutable row (name: `OI-13-550`'s receiver owns the job row if one is ever needed).

**Non-goals.** Drift classification, its rules and its proposal paths (13.8.1); the multimodal fallback (13.7.2); any repair, candidate, validator or PR (08.3, 08.4, 08.6); the incident fingerprint — profiles are **not** a second fingerprint and never replace 08.1.2-T3's versioned one; DOM/accessibility **artifact** capture, artifact kinds, uploads, secret scan and screenshot policy (08.1.2-T1/T2, 06.2.2, 06.2.3, 13.5.1-T1.7); the generated script's emitted code, its PR payload and its stability window (13.5.1-T2/T4/T5); `evidgate run` and local-run labelling (13.5.2); every screen and design file (13.8.2-T2 owns the review additions; no screen is designed here).
Also out of scope: the document rejection corpus (08.8.1), gate metrics (13.9.1-T3), and any model, gateway, provider or credit path — plan 13's Q1/Q2 (`plans/13-product-phases.md:257-258`) do not reach these stories, and 12.4.1-T4 consumes no credits here.

**Prior art (owner rule, 2026-10-27; vendor-neutral, approach only).**
(1) *Playwright `Locator.ariaSnapshot()`* (`https://playwright.dev/docs/aria-snapshots`, `https://playwright.dev/docs/api/class-locator`): taken — the accessible subtree of a **scoped locator** (roles, optional accessible names, states, nesting by indentation) is the right capture primitive, because it exists in the page context where the reporter has no DOM handle.
Deliberately not followed: storing the YAML text (it carries accessible names and `text:` lines, i.e. content) and using `toMatchAriaSnapshot()` as the product matcher (an order-sensitive assertion with partial-match templates, not a versioned score).
(2) *Healenium property weighting* (`https://www.healenium.io/`) and *NIST's threshold/margin* argument (`https://www.nist.gov/blogs/taking-measure/tale-two-errors-measuring-biometric-algorithms`): taken — weight signals (semantic identity strongest, container/neighbours supporting, position weakest) and accept only when **best ≥ threshold AND best − runner-up ≥ margin**, else abstain; a score is never a probability.
Deliberately not followed: healing or promoting anything because a run went green, and Healenium's proxy/DOM-diff capture — a profile is promoted only by a CI-verified green run with an attributable build identity (AC8), and capture is in-process at the bound step. Budget: 2 searches, 3 sources.

## 2. User stories and acceptance criteria

- As a test maintainer, after my case's steps run green I can see the structure each step bound to, so a later break has something to be compared against that is not a screenshot and not a page dump.
- As a security reviewer, I can point at one allow-list and one redaction point and say no page text, input value, cookie, header, token or storage state ever left the customer's machine in a profile.
- As the drift classifier (13.8.1), I read one latest-green row per step and get a versioned verdict — match, ambiguous or no claim — that replays identically next month on the same rows.
- As a project owner, a local `evidgate run` never becomes the memory my repair decisions are made from.

Every criterion has a named proof in §9. Numeric defaults flagged `[INFERENCE]` are build defaults. All refusals are existing codes or the closed set §5 names.

## 4. Data model and migrations

**One new table, one migration, one view — and no new artifact kind.** The migration is `migrations/NNNN_element_profile.sql`, created by T2.1 with **the next free number assigned at build time** (migrations end at `0052_healing_switch.sql`; `STATUS.md:8` names `0053` as next free, and 0053 belongs to another lane — re-check at build). Plan 13 §4.1 already lists the table at high level (`plans/13-product-phases.md:49`); this plan refines its columns, and the refinement is written back to §4.1 by the plan-13 edit, not by this file.

| Column | Rule |
|---|---|
| `project_id` | its own column with a composite FK `(org_id, project_id)` → `public.project (org_id, id)` (`migrations/0005_identity_project.sql:39`, the key that comment `:14` exists for); it joins the FKs whose target carries it (`run`, `generated_script`), so no cross-project hop is expressible there |

| `step_no` | int, the case step number — the area plan's `step_no` (`plans/13-product-phases.md:49`) kept for ordering, with `step_key` its text identity |
| `run_id`, `attempt_no`, `execution_key` | composite FK `(org_id, project_id, run_id)` → `run`; `attempt_no` int ≥ 1; `execution_key` the shipped hex key (00 §7 `:246`); `green` and `ci_verified` are read from the run/attempt projection, not re-derived here |
| `script_id` | nullable composite FK `(org_id, project_id, script_id)` → `generated_script`; null when the run came from a hand-written script |
| `origin_local` | `boolean not null default false`; true for a run 13.5.2 derived as `origin=local` (`OI-13-535`) — stored so the derivation can exclude it, never used to promote |
| `profile` | jsonb, the closed document of AC2; `check (octet_length(profile::text) <= 4096)` |
| `profile_hash` | `sha256:<hex>` over the RFC 8785 canonical document (00 §7 `:247`); the identity a duplicate insert compares |
| `spec_version`, `capture_version`, `similarity_version` | `spec_version` = document shape (area plan's `spec_version`, `:49`), `capture_version` = capture implementation, `similarity_version` = the matcher that vectorised this row; all three `text not null`, all three compared for equality only (`plans/13-product-phases.md:96`) |
| `capture_controlled` | `boolean not null`; false while the adapter declares `capture_control: false` (AC5) |
| `created_at` | `timestamptz not null default now()`; the store is append-only, so there is no `updated_at` and no `version` column — nothing is ever updated |

Append rules: the app role holds `select, insert` only (`REVOKE UPDATE, DELETE`); a duplicate `(run_id, case_revision_id, step_key)` is resolved by `ON CONFLICT DO NOTHING` on the unique key, which is what makes a replayed envelope idempotent (AC1). Indexes: `(org_id, project_id, case_revision_id, step_key, created_at desc)` for the derivation, `(org_id, project_id, run_id)` for the per-run read, `(org_id, project_id, profile_hash)` for duplicate detection.
`FORCE ROW LEVEL SECURITY` with policies on `evidgate.current_org_id()`/`current_project_id()` per 00 §5.4 (`:181-190`); `unique (org_id, id)` so the row can be the target of a composite FK. No `rls-exceptions.txt` entry is needed and no `SchemaConventionScan` exemption is requested, because both blanket suites cover the table the moment it lands with **no list to edit**: `CompositeFkTests` auto-discovers every table carrying `org_id` and fails the missing composite FK with the table's own name (`tests/Isolation.Tests/CompositeFkTests.cs:13-19`), and `SchemaConventionTests` asserts `unique (org_id, id)`, composite tenant FKs, ENABLE + FORCE RLS and the 00 §7 columns (`tests/Persistence.IntegrationTests/SchemaConventionTests.cs:7-16`).

**Latest green is a view, not a mutable row.** `element_profile_latest_green` selects, per `(org_id, project_id, case_revision_id, step_key)`, the row with the greatest `(finished_at, run_id)` among rows whose run is `green`, `ci_verified`, `origin_local = false` and whose build identity is complete. It is a plain view over immutable rows, so a re-derivation (the `plans/13-product-phases.md:96` backfill) is a `select`, never an `update`, and a wrong promotion cannot be "fixed" by editing memory. A materialised table was rejected: it would need its own write path, its own RLS story and its own chance to drift from the rows.
The view is created `with (security_invoker = true)` and granted `select` to `evidgate_app`, so it reads with the caller's privileges and the base table's tenant policy — and because `tests/Isolation.Tests/Rls/RlsIsolationTests.cs:85-91` fails any `v`/`m`/`f` relation the app role can SELECT that is not in its (today empty) `SelectableRelationAllowlist`, T2.1 adds exactly one allowlist row citing this migration, with the `security_invoker=true` assertion of `:534-540` already enforced by that suite.
The alternative — one Dapper statement in the repository and no view object, the shape 13.1.1 chose for its uncovered read model and justified there ("why it is not a SQL view", `plans/features/13-product-phases/13.1.1-feature-tree-and-manual-test-cases.md:237`) — was rejected because the area plan names a view (`plans/13-product-phases.md:208`) and the allowlist mechanism exists for exactly this case; if the owner prefers it, the change is local to T2.1/T2.2, drops the allowlist row, and costs no contract edit.

**Retention split, stated once.** Profiles are small structural facts and are retained as long as the case revision they describe (and purged with it or with the project); `dom_snapshot`, `a11y_snapshot` and `screenshot` artifacts keep the retention their own kind promises (06, 13.5.1-T1.7) and are **not** referenced from this table — no `evidence_artifact_id`, no copy, no orphan. Deletion is `REVOKE DELETE` for the app role plus the purge path; the hook itself is 08.1.2-T2's (`plans/08-healing-learning.md:152`), re-used and not re-implemented.

A route would cost 00 §9.3 + §15 rows, openapi, SDK regeneration, a permission pair, contract-convention rows, served-route and isolation route cases, and an `apps/web` `KNOWN_API_SEGMENTS` row (`api-path-template.spec.ts:143-158` fails in both directions) — inside a 1.0 d sub-task with no consumer.

**Why the similarity lives here and not in the Worker.** The 08.2.2 rule triage runs in the Worker over an incident's context; profiles are different input: they are *many small immutable rows already in PostgreSQL*, the verdict must be a pure function of `(rows, similarity_version)`, and 13.8.1 must be able to re-run it after a backfill without touching a job queue. Putting it in the Worker would (a) need a second tenant-scoped read path with its own WLM/RLS story, (b) hide a versioned derivation behind a queue retry, and (c) make "same rows, same version, same verdict" depend on which worker ran. It is therefore an application-layer query over the store, computed server-side, never in a browser and never by a model.

## 6. States and transitions

**No state machine is added.** A profile row is an immutable fact; the only things that look like states are derivations, and each is computed from rows rather than stored as a column that could go stale:

- `capture_state` per step per run ∈ `recorded | unavailable(reason)`, derived from the presence of a row and the capture reason the envelope carried (AC5). It never blocks a run, a case result or a script transition.
- The latest-green selection of AC3 is a view over append-only rows (§4). Nothing "moves" a profile to latest; a newer eligible green row wins because it is newer, and a bad row is superseded by rows, never repaired by an `update`.
- A row's `similarity_version` is compared for equality and nothing else (`plans/13-product-phases.md:96`). An unequal version is `requires_backfill`; the re-derivation writes new rows, because the store has no update path at all.
- `origin=local` rows are stored and readable, and are **excluded** from the derivation and from every similarity input. This is 13.5.2's decision (`OI-13-535`) consumed here; the reason it matters is that a laptop run's manifest identity is client-supplied (`plans/features/13-product-phases/13.5.1-bound-playwright-scripts.md:390`), so a local "green" would otherwise become the memory repair decisions are made from.
- The verdict vocabulary is closed and borrowed, not invented: `match` (profile similarity says this is the same element), `ambiguous` (best below threshold **or** best − runner-up below the margin), `no_claim` (no eligible row, unequal version, or the rule the caller applies refuses). `ambiguous` is exactly the hand-off to 13.7.2 and `no_claim` is exactly "the rules decide nothing" — 13.8.1-T1 turns these into `test_drift` / UI change / nothing, and this story does not decide a drift class.
- `generated_script` states are untouched: capture cannot activate, retire, set or clear `flaky` (`plans/00-overview.md:315`), and no row here is an input to activation.

## 7. Jobs and integrations

- **No new outbox task, no new schedule, no new worker.** The projector of T2.2 runs inside the shipped ingest path's existing transaction for the `test.step` envelope: one insert per bound step with the unique-key `ON CONFLICT DO NOTHING` above. If the ingest transaction rolls back, no profile row exists — there is no second write and no compensation. Idempotency follows the pattern 06.1.2-T2 established for `complete` (natural key + one statement + no update), which is what this story's plan-13 edge to 06.1.2-T2 actually consumes; **no artifact is created by this story**, so no kind, scan or staging path is involved.
- **Integrations consumed:** `@evidgate/playwright-reporter` in-process (04.3.1-T1) and its closed `ext` filter; the CLI's registered-secret redaction (`contracts/cli.md` §6, `:324-365`); the event ingest route (`POST /v1/runs/{r}/events`, `event:write`) and its batch validation; 08.1.2-T2's masking rule set and retention hooks (`plans/08-healing-learning.md:152`); the run/attempt projection that carries `outcome`, `attempt_no`, `ci_verified` and the build identity. No spool layout is consumed or changed: the profile payload never becomes a file unless `OI-13-545` falls back to the sidecar.
- **Consumers:** 13.8.1-T1 reads the classify entry point inside the `test_drift` label and decides drift vs UI change; 13.8.1-T2 turns a `match` into a candidate for the 08.3.1-T1 model (candidate_hash, ≤ 3, expiry — not duplicated here); 13.7.2 consumes `ambiguous`; 13.9.1-T3 and 13.8.1-T4 read counts, never profile content; 13.8.2-T2 adds whatever the review screens show.
- **Hand-overs (no design here):** 13.5.1-T2 must emit the per-bound-step capture call into the generated script and 13.5.1-T5's PR payload carries it — without both, T1 captures nothing in practice (`OI-13-545`); 13.5.1-T4 owns the green/`flaky` policy this story reads; 13.5.2-T1 owns `origin=local`; 08.1.2-T2 owns masking and retention hooks; 08.1.2-T3 owns the fingerprint (this story invents no second fingerprint); 08.1.2-T4 owns the stability-test *shape* this story mirrors; 08.2.2-T2 owns the label the classify runs inside; 08.3.1-T1 owns the candidate model; 08.4.1-T2 owns the validator (never called here); 08.8.1-T1/T3 own the real corpus and holdout; 13.1.1 owns the case revision identity and 13.1.2-T1 owns `authoring_change`.
- **Failure isolation:** capture and similarity are both non-blocking by construction — a missing step attachment, a schema violation or an unreadable row degrades to a labelled absence, and ingest keeps its own atomic batch rule (a rejected batch is the *ingest* contract's 422, not a new code). A failed migration is forward-only, so the rollback lever is a code switch (§11) rather than a down-migration.

No rollback path deletes profile rows; they are purged by the retention path only.
