## 1. Goal and non-goals

**P1 · G1 · FR-13-14.** An MFA-authenticated, provisioned platform operator can select a supported Claude model from the Anthropic adapter’s versioned catalog, rotate its credential, set a daily global spend ceiling and stop AI calls. A successful change governs the next gateway call without restarting the API or worker. The console shows which revision is active, not just what an operator last entered.

This is platform configuration, not a tenant opt-in, credit adjustment, provider onboarding project or model evaluation. OI-08-01 fixes the V1 provider to the direct Anthropic API. Operators select a supported Claude model from the adapter's versioned catalog without redeploying. Reject any other provider or unsupported model. A later provider adapter requires a new decision. No operator-entered provider URL or automatic fallback to another provider.

## 2. User stories and acceptance criteria

| ID | Action | Observable outcome |
|---|---|---|
| AC1 | A staff operator publishes an installed provider, a compatible model and a valid credential. | The revision and audit commit together; the next eligible 08.5.1 gateway request uses that adapter, model and credential version without redeploy. An unsupported pair makes no change. |
| AC2 | An operator rotates the active key. | The replacement stays staged until validated for that Anthropic model. An invalid, timed-out or stale rotation leaves the active tuple untouched. Success changes the opaque version reference; only configured status and last-rotated time are exposed. |
| AC3 | An operator with `billing:write` lowers the daily cap. | The next credit reservation obeys the new ceiling without resetting today's spend, reservations or alert state. At exhaustion the provider receives zero requests. The 80% alert still fires at most once per day; tenant/project limits and credit checks still apply independently. |
| AC4 | An operator confirms the system kill switch. | New gateway dispatches, including retries, stop; no model call or new credit reservation. The incident runbook still works. Restoring a permitted system mode does not override tenant/project restrictions, missing opt-in, caps or an unhealthy dependency. |
| AC5 | An unauthorized caller submits a change, or a second operator saves an outdated view. | Public ingress has no console route. Unauthorized staff writes leave config, switch and active key unchanged. A stale `If-Match` returns 412 with the current public revision metadata, never the key. |
| AC6 | An operator inspects the screen, history or an error after a key change. | en/vi views distinguish saved, refused and stale changes. The key field is never prefilled or echoed; no key value, key-derived digest or provider response body survives in an API response, browser storage, telemetry or audit. |

## 3. Contracts touched

- FR-13-14 and 13.12.1-T2/T3 supply the operator principal, ingress and revision protocol. Use the platform audit scope: global changes need no impersonation, tenant grant or artificial `org_id`.
- 08.5.1-T1 owns the provider adapter and gateway; 08.5.3 owns redaction and tenant opt-in. Pilot terms allow customer **test/staging data only**, never production data or real personal data. Secret scanning, redaction and the redaction report hash remain mandatory for each customer model request. A DPA, transfer assessment or zero-retention attestation is **not** a gate to the first real call (OI-08-01).
- 08.5.5-T3/T5 own spend enforcement and billing permissions; 08.6.3-T1 owns switch resolution and the system switch definer. Configure these paths rather than creating a second spend ledger, switch or public administration API. No tenant grants/adjustments here; their existing two-person rule above the threshold is unchanged.

## 4. Data model and migrations

| State | Ownership and invariant |
|---|---|
| Published configuration | Use the 13.12.1-T3 append-only revision and current pointer for the fixed provider ID (Anthropic API), model ID and opaque credential version. Cap and switch changes also append revisions linked to their authoritative domain writes. Store actor, UTC time, request ID, old/new non-secret values or opaque references and before/after hashes of the canonical redacted records, never hashes of secret bytes. |
| Secret versions | The deployed versioned secret store owns candidate and active key material. Configuration points to a specific provider-bound version, never a mutable “latest” key. Keep write/rotate/retire authority separate from the gateway's read capability. The operator cannot read a secret back or supply an arbitrary secret-store reference. |
| Spend and availability | Retain the existing `ai_spend_global` day record, its spent amount and alert marker; use integer micro-units and existing reserve/settle semantics. `healing_switch` system state is authoritative, including changes made by the incident runbook. Do not implement the switch as an independent config Boolean. |

## 5. API shapes (commands, queries, endpoints)

All routes below are under `/internal/operator/*` on the operator ingress only. Reads require the operator session; mutations also require antiforgery protection and `If-Match` from the current read. Reject a missing precondition without writing. On a mismatch return 412 plus the current safe revision. Each accepted command returns a safe revision and fresh ETag, never the input body.

| Operation | Request and response contract |
|---|---|
| Read AI settings | Return the fixed provider (Anthropic API) and the supported model IDs from the adapter catalog, active selection, configured/last-rotated metadata, daily cap with units, current system mode and edit permissions. Version the view against the authoritative values; an incident change must invalidate an old switch edit. Do not list environment values or credentials. |
| Publish model or rotate key | Accept model ID (the provider is fixed to Anthropic API; reject any other provider value) and optional **new** write-only credential over TLS. Omit the credential to retain the current current-provider version, not to clear it. Check the model against the installed adapter's capabilities; stage and validate any replacement server-side before atomically publishing the new tuple. Return safe field errors or a transient validation failure, not provider diagnostics. |
| Set daily global cap | Use `PUT /internal/operator/ai-spend/global-cap` with the existing `billing:write` check in addition to the staff gate. Validate integer micro-units in the domain range; no float, negative, overflow or implicit unlimited value. Apply to spend admission and record the revision and audit together. |
| Set system switch | Use the operator-ingress-only `POST /internal/operator/healing/switch` command with an explicit supported system mode. Confirm disable/restore in the UI; do not allow writing the derived `unavailable` state. Call the existing `evidgate.healing_switch_set_system` definer through a narrowly privileged operator path, not generic app/worker credentials. |

## 6. States and transitions

1. **Stage:** authenticate, authorize and check revision before accepting a candidate. A staged version is not active; gateway readers cannot discover it through the published config. For initial setup without an active tuple, the gateway makes no model requests.
2. **Validate:** reject unknown adapters/models locally. Use the installed adapter's credential/access check for the selected model; it carries no customer content and is not a model invocation. If an adapter can verify access only by invoking a model, that check is a model call: refuse it while the system switch is disabled and do not publish the candidate until it can be verified (OI-13-831).
3. **Publish:** recheck the precondition after validation. Append revision, update the current pointer or underlying cap/switch state, and write the audit record in one database transaction. An audit failure rolls it all back. A failed/losing candidate is retired under 10.7.1-T4; its existence in the secret store does not imply a published change.
4. **Consume/retire:** the next admitted call resolves the published tuple as a unit. Never mix a new model with an old provider's key. Retire the superseded version per the rotation procedure after existing borrowers are finished; an operator rollback publishes a fresh, validated revision rather than editing history or reviving a retired key.

## 7. Jobs and integrations

The gateway resolves the published tuple (provider, model, credential version) once, at admission, and uses that same tuple for the reservation price and for every dispatch and retry of that call. A publish never changes the tuple of a call that already holds a reservation; it applies to calls admitted after it commits. Re-resolving at send time is forbidden: a pricier replacement could exceed the reserved amount and the hard cap. The gateway checks the authoritative switch before any new provider dispatch, including retries. Preserve 08.6.3's in-flight stop behavior; a cached enabled mode cannot override an incident disable. Reuse the 08.5.5 gate for global/tenant caps, reservations, refunds, metering and alert deduplication. A cap change is not a fresh day or a ledger adjustment. A stricter cap below today's spend immediately blocks additional spend; previously recorded costs remain visible.

CR-19 / migration 0105 withdrew the generic application's ability to change the system switch. T1 must retain that restriction and the existing privileged `psql` incident path. Only the operator-ingress command may acquire the narrowly scoped database capability for this web operation. Test the actual deployment roles; neither the public API identity nor a worker may execute the definer. Separate provider config edits never rewrite system mode.

## 8. Security, privacy and performance

- **Authorization:** workforce session with verified MFA and provisioned `platform_operator`; enforce existing additional permissions on the server, including `billing:write` for cap changes. Public ingress, a customer session, bare billing role, CI token, revoked session or forged principal is insufficient. Routine settings do not require a second operator.
- **Retention/deletion:** keep redacted revision/audit history under the platform audit policy. Clear input on submit, rejection, navigation or session expiry; no form replay from browser storage. Retire abandoned/superseded secret versions using 10.7.1-T4. Do not retain raw requests, upstream bodies, tokens or secret-derived fingerprints in any store, cache, log, trace or history.
- **Telemetry:** reuse the once-per-day 80% alert and bounded counters for spend refusal, disabled operation and credential validation outcome. Record actor and revision only in restricted audit where needed. Never emit authorization headers, credentials, prompt text, upstream errors or tenant data in diagnostics.
- **Failure path:** rejected writes preserve the last valid revision and working key. If current switch/cap safety cannot be established at dispatch, or the active credential cannot be resolved, refuse without calling the provider; do not route to an older provider, a default key or a more permissive cap. Do not hold a database transaction open during credential validation.

## 11. Rollout

1. Keep the public host unchanged and retain the incident runbook. Install the narrow operator role and confirm both host isolation and the public/worker database denials before exposing the settings screen.
2. Exercise rotation, stale writes, disable/restore and cap exhaustion with synthetic test data. Leave a missing adapter or unvalidated credential unavailable. Before any real call, select a catalog model informed by the 08.5.5-T4 evaluation corpus and OI-13-401.
3. Enable eligible opt-in pilot traffic only after verifying the chosen adapter, alert and absence of secret markers. To stop traffic, use the existing system switch; restore a working tuple only through a new conditioned and audited revision. Do not roll back consumption records.
