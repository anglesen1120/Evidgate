## 1. Goal and non-goals

**P1 · V2 · G2.** An Evidgate operator can change how many hosted jobs each tenant may run concurrently, how long a job may run and which approved browser images may start. One platform setting applies the concurrency cap **separately to each tenant**; the operator does not select a tenant or inspect any tenant's jobs, and there is no per-tenant override (non-goal; per-tenant differences come only from the plan in 13.12.4). The next new job uses the published settings without a redeploy. A running job is not restarted, reimaged or given a different deadline.

The console consumes the hard envelope recorded by 13.11.1-T1; it cannot edit that envelope. The owner accepted starting defaults of **two concurrent jobs per tenant and a 15-minute wall-clock timeout**, with a scanned, approved image pinned by digest. The defaults do not substitute for the spike's evidence or identify a production image. Isolation, egress, tenant script approval, quota, billing and emergency kill remain with their existing owners. This is not a registry browser or an image approval pipeline.

## 2. User stories and acceptance criteria

| ID | Actor and action | Observable outcome |
|---|---|---|
| 13.12.6-AC1 | A signed-in operator publishes a valid change against the current revision. | One immutable revision becomes current, with one corresponding audit event. Reading the settings returns its ETag. A stale edit gets 412 and the current revision; validation or audit failure changes neither settings nor job behavior. |
| 13.12.6-AC2 | The operator proposes an out-of-bounds number, a floating tag or a digest without approval or passing scan evidence. | The entire publish is refused, even if the other fields are valid. No tag resolution, registry fetch or partial update takes place. The API refuses the same inputs the screen disallows. |
| 13.12.6-AC3 | Two jobs for tenant A are running. The operator lowers the cap from two to one, reduces the timeout and removes their image from the selected list. | Both jobs keep their admitted revision, digest and deadline. With two, then one active, A receives no further slot. Once A has zero active, its next eligible admission pins the new revision; tenant B with headroom remains eligible throughout. |
| 13.12.6-AC4 | A hosted worker starts a newly admitted job. | Only a current lease with a valid admission, pinned deadline and approved digest can start a guest. The executor uses the pinned digest, not a tag or a worker-selected alternative, and stops the guest at its deadline. | 13.12.6-AC5 | Staff open the runner settings screen on the operator ingress in English or Vietnamese. | They can distinguish active values from read-only hard bounds, see eligible image digests and understand that a save affects new jobs only. ## 3. Contracts touched

- FR-13-14 and 13.12.1 provide the isolated operator origin, workforce session, configuration history, conditional publish and audit. This setting contains no secret fields. No public `/v1` route, customer role or tenant support grant is added.
- 13.11.1-T1 records the hard limits from 05.9.2-T1. 13.11.1-T8 owns approved image digests and their scan and licence evidence; only that source can supply eligible images. An operator can select a subset, not promote a new image.
- 13.11.1-T12 owns per-tenant slots, fairness and the live kill switch; 13.11.1-T5 owns the disposable executor and teardown. FR-13-13's approved script revision, isolation and network rules do not change. Keep 13.11.1-T11's reservation and settlement of included minutes, including refusal at exhaustion and no overage.

## 4. Data model and migrations

| Record | Change and invariant |
|---|---|
| Platform configuration revision | Store the per-tenant concurrency cap (jobs), wall-clock timeout (minutes), selected set of approved image digests and the identity of the hard envelope used for validation. Reuse the configuration framework's immutable revision and current pointer; do not create another mutable limits table. Canonicalize the digest set before hashing. |
| Admission on the existing hosted job | Persist the settings revision, cap used, chosen image digest and timeout; record the absolute deadline from the execution start and the pinned timeout. Bind these to the tenant's existing slot and leased job. A duplicate claim must not allocate a second slot, pick a different image, or reset an existing deadline. |
| Platform audit | In the same transaction as revision append and pointer update, record operator, UTC time, request ID, previous/new nonsecret settings and before/after hashes of their canonical representation. No request bodies, credentials, job payloads or tenant data. |

## 5. API shapes (commands, queries, endpoints)

**Read:** on the operator origin only, `GET /internal/operator/hosted-runner/settings` returns current revision and ETag, active values, hard numeric bounds with units and the catalog of eligible immutable image references. Distinguish an unavailable envelope or catalog from an intentionally selected value. Do not return tenant IDs, usage or live jobs.

**Publish:** a conditional `PUT` on the same resource accepts only the cap, timeout and selected digest set. Require a valid operator session, antiforgery protection and `If-Match`. Validate positive bounded integers against the recorded envelope, and a nonempty subset against the approved, scanned digest catalog. Reject unsupported fields (including registry credentials, image tags, network rules, quota or kill overrides). Neither the browser nor the request chooses the hard bounds. Missing precondition is refused; a stale ETag yields 412 with the current revision. Success returns the committed revision, never a draft. No routine second-operator approval is needed.

## 6. States and transitions

| Transition | Rule |
|---|---|
| Edited → published | Validate against trusted envelope and catalog; compare expected revision and atomically append, activate and audit. Failure leaves the last valid revision untouched. Recovery republishes valid settings as a new revision; history is never rewritten. |
| Waiting → admitted | Admission is the slot reservation before dispatch, not enqueue time. Requests still waiting when publication commits use the new revision when admitted. Order concurrent publication and reservation so each admission sees one complete revision; do not admit using an unverified stale cache. |
| Admitted → executing | The worker verifies the job's admission and live lease, checks the pinned digest and approval, and starts only the authorized guest. A later routine edit does not replace a successful admission's pin. If the admission or image cannot be verified, refuse launch and release the reservation; never substitute another image. |
| Executing → terminal | Enforce the pinned wall-clock deadline outside tenant code and tear down on timeout, cancel, lease loss or kill. Return slots and settle actual minutes through the existing owners. A routine edit is not a kill and does not grandfather future admissions. |

## 7. Jobs and integrations

Use the scheduler's existing tenant slot reservation, including leases admitted but not yet running. Compare the tenant's occupied slots to the effective cap atomically before granting one. At capacity, follow the existing queue/fairness policy without dispatch; lowering a cap below current occupancy drains naturally. Do not take away a slot from one tenant to enforce a limit on another.

Read the active revision without restarting workers. Carry its identity across dispatch rather than asking the executor to reconstruct a job from the latest values. The executor verifies the immutable image content against the admitted digest before launch. A removed selection prevents future admissions on that image; **loss of upstream security approval** is different from routine deselection and must not authorize a new launch. Settings publication does not create jobs, revalidate running guests, reserve minutes, or change the emergency stop path.

## 8. Security, privacy and performance

- **Authorization:** require the 13.12.1 operator gate (real workforce identity, verified MFA, provisioned `platform_operator`, valid operator-only session). Enforce ingress for reads and writes and antiforgery on writes. Tenant, billing-only and CI identities are not operators. This platform setting neither needs a fabricated tenant grant nor confers access to tenant payloads.
- **Retention/deletion:** configuration revisions and platform audit follow the existing platform retention rules; never delete a revision to undo a setting. Retain job pins with the ordinary hosted job record and tear down temporary guest state on normal or interrupted exit. Do not retain registry credentials; secrets belong only in the write-only secret-store path, never in these settings, API responses, UI, logs or audit.
- **Telemetry:** count successful publications and refusals by bounded reason (stale, invalid bound, image ineligible, unavailable policy), admission refusals and timeouts. Keep actor and request/revision identity in authorized audit/history, not metric labels; no request bodies, session values or tenant job details in diagnostics.
- **Failure path:** refuse a publish if the envelope or image evidence is missing or if its audit cannot be written. Preserve the last valid settings; if a consumer cannot establish the effective revision, lease, image approval or applicable admission guards, do not dispatch or launch a new guest. Keep live kill and quota checks independent of config refresh.

## 9. Test plan

| Acceptance | Evidence required |
|---|---|

Try zero, a negative, a fraction, one above each cap, an empty selection, a tag, an unknown digest and a digest lacking scan approval. Submit two edits based on one ETag and force an audit-write failure. Inspect active settings, revision count and audit: only valid, winning commits changed them. |
| AC3: scheduler | Run the two-tenant drain scenario while a request waits before the edit. Race two eligible requests for A's last slot: exactly one wins. Observe admitted revision/slot per tenant; demonstrate old jobs undisturbed and the first subsequently admitted job using the new revision without restart. |
| AC4: executor and independent gates | Start a short fixture job with the approved digest and observe deadline teardown. Compare the old job's deadline and image across a publish. Missing pin, substituted digest or expired lease starts no guest. Exercise exhausted quota with spare slots and live kill with queued/running work: no unauthorized start, no overage and no surviving killed guest. |
| AC5: web and ingress | Exercise a valid read/save, stale 412 after another edit, invalid selection, denied write and session expiry. Verify hard bounds, units, digest identity, active revision and prospective-only explanation in en/vi. Check the actual public ingress serves neither the screen nor command; tenant-admin, CI and billing-only sessions produce no mutation. |

## 11. Rollout

1. Before enabling publish, bind the documented envelope and the approved digest catalog to the real read path. If the spike evidence or the initial approved image is missing, keep publication unavailable; P1 does not move the upstream gates.
2. On the operator ingress, run the two-tenant admission test and timeout/kill drill against a fixture executor, verify operator-only access and audited revisions, then enable the screen from the approved design. No customer ingress change is part of rollout.
3. To undo a bad selection, publish a previously working set through `If-Match` after checking it against today's envelope and catalog. This affects new admissions only. If jobs must stop immediately, use the existing hosted kill switch, not a limit of zero or an empty image list.
