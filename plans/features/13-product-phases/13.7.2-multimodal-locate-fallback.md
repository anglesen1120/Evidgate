## 1. Goal and non-goals

**Goal.** When — and only when — 13.8.1's profile similarity returns `ambiguous` for one broken bound step, build a **bounded, closed candidate set** from the stored accessibility snapshot (`a11y_snapshot`), read page text with a local OCR engine, and, if the tenant has opted in and the per-incident budget allows, ask a vision model through the 08.5.1 gateway to choose **one index** from a set it did not author. The chosen candidate is a *proposal*: it must pass **every** 08.4 check before anyone sees it, and this story never decides the drift class. Three tiers, cheapest first — accessibility (no model, no egress), OCR (local, no egress), visual (gateway, opt-in, budgeted) — and a refusal at any tier is a normal outcome.

**Area-plan acceptance (quoted).** "when profile similarity is ambiguous, an accessibility + OCR + visual locator may propose a candidate that still passes all 08.4 validation; it never decides the class" (`plans/13-product-phases.md:218`). The governing decisions are verbatim: plan 13 §3 — "profile similarity classifies; a model or the multimodal locator only proposes, and every proposal passes 08.4 validation" (`:32`); plan 13 §5 — "Class `unknown` → no repair; the multimodal locator may propose, and the proposal still needs 08.4 validation" (`:97`); CR-D-2 §7 — "used only when element-profile similarity is ambiguous … Calls go through the gateway with a per-incident budget, and screenshots stay opt-in (`docs/decisions/CR-D-2-direction-a.md:171`).

**Three partials, stated here rather than discovered at build.** (1) **No profile is read** (`OI-13-570`): 13.6.1's architecture rule fails the build if the profile module, `IElementProfileReader` or `IElementProfileSimilarity` is referenced from 13.7.2 (`13.6.1-AC11` and its §9 row, `plans/features/13-product-phases/13.6.1-element-profiles.md:193`, which names 13.7.2's module as a receiver and `:266` says this story owes a receiver row), so ambiguity must arrive *pushed* by 13.8.1 as a command carrying the verdict, `rule_version` and `similarity_version` — never re-computed here. 13.8.1's plan defines no such command yet (its §5/§6 name only classification, proposals and windows), so AC1 is met against a hand-off shape this plan states and that story names. (2) **The "visual" tier has no legal wire shape today** (`OI-13-565`): `HealingLlmRequest.Payload` is a `string` (`src/Modules/Evidgate.Modules.Healing.Contracts/IHealingLlmProvider.cs:79-90`) and the shipped adapter posts `{model, prompt_version, prompt, response_schema}` (`src/Modules/Evidgate.Modules.Healing/Application/HttpHealingLlmProvider.cs:74-90`); a bounded image part is a proposed contract edit, not an existing capability, and the gateway's consumer validator refuses any purpose outside the shipped three before the provider is reached (`src/Modules/Evidgate.Modules.Healing/Application/HealingLlmGateway.cs:50-58`). (3) **The visual tier has no opt-in to read either** (`OI-13-524`): a screenshot exists only when the project carries an **explicit** row enabling that kind, because the table default `capture_enabled` is `true` (`migrations/0028_evidence_artifact.sql:141`) and a bare default is not consent (13.5.1-AC12); a missing or default-only row denies `screenshot_not_enabled`, and the mask that lets a pixel leave needs 08.1.2-T2's rules (unbuilt), so `mask_unavailable` sends no image at all.

**Phase and scope (CR-D-2).** G3 only, V1; wave order is computed by `scripts/plan_graph.py`, not pinned here. Validation (08.4), candidate states and minting (08.3.1), approval and PR (08.6.1), screens (13.8.2-T2), the class decision (13.8.1) and G3 reporting (13.9.1-T3) are other stories. **Not buildable until** 08.5.1-T1.4 supplies the out-of-transaction call and the budget hard stop, 08.5.3-T1/T3 supply the redaction pipeline and the tenant/provider approval, 08.1.2-T1/T2 supply the incident context artifacts and their masking, 08.3.1 supplies the `healing_candidate` row and its `proposed` state (the replay job and `candidate_validation` are keyed by `candidate_id`, so validation cannot run before the row exists: `plans/features/08-healing-learning/08.4.3-sandbox-replay.md:45`, `:54`), 08.4.x supplies the validator, 13.5.1-T1.7 supplies the `a11y_snapshot` and `screenshot` artifacts plus the project's explicit screenshot row (`OI-13-524`), 13.6.1-T3 produces `ambiguous` at all, and 13.8.1-T1 emits the hand-off. Mocks are not a substitute for any of them.

**Non-goals.** Any class, verdict or `drift_classification` write (13.8.1); profiles, capture or similarity (13.6.1); the validator, the sandbox, the negative control and the replay comparability gate (08.4); candidate states, `candidate_hash`, the 3-candidate cap and minting (08.3.1); PR creation, approval, canary and rollback (08.6.1/08.6.2); before/after screenshots and the a11y/DOM diff (13.8.2-T1); every screen and its design (13.8.2-T2); the provider/model choice, pricing and region (08.5.5-T4); the eval corpus itself (08.8.1); mobile (`adapter-mobile`, 04.5.1-T1, G4); any new permission, route, state machine or migration number; any change to `plans/13-product-phases.md` or an estimate.

**Prior art (owner rule, 2026-10-27; approach only).** (1) *Set-of-Mark prompting* (`https://arxiv.org/abs/2310.11441`, abstract read 2026-11-09 ✅): taken — overlay numbered marks on region candidates and make the model answer with a mark, which converts an open-ended "find the element" into a closed choice; deliberately not followed — its segmentation model and its free-form answers, because the candidate set here is built deterministically and the answer schema permits one index only. (2) *Tesseract* (`https://github.com/tesseract-ocr/tesseract`, `LICENSE` read 2026-11-09 ✅ Apache-2.0; release `5.5.4`, 2026-10-28 ✅ GitHub releases API): taken — a local, offline OCR pass whose word boxes can be matched against the expected accessible name; deliberately not followed — sending the image to a provider for text, which would turn a free, zero-egress step into a paid cross-border transfer. (3) Internal precedent, not prior art but the binding shape: 13.5.1-AC8 already has a model choose **a candidate index from a list the client built** and re-check the choice live; this story reuses that pattern instead of inventing a second one.

## 2. User stories and acceptance criteria

- As a QA engineer, when the profile rules cannot decide where a broken step's element went, I get an explicit proposal or an explicit refusal with a reason — never a guessed locator.
- As a test maintainer, I can see which tier produced a candidate (accessibility, OCR or visual), what it cost, and that it still had to pass the full validator before I was asked to review it.
- As a data owner, I can prove no pixel left the tenant unless my project enabled screenshots and I approved that provider, and that a refused or over-budget call placed zero calls.

Proposal: `scope_kind ('project','incident')` + nullable `incident_id` + `CHECK ((scope_kind = 'project' and incident_id is null) or (scope_kind = 'incident' and incident_id is not null))`, with the unique key written **NULL-safe** as `unique nulls not distinct (org_id, project_id, scope_kind, incident_id, period, period_start)` — or, below PostgreSQL 15, as two partial unique indexes (`… where incident_id is null` and `… where incident_id is not null`) — because a plain unique key treats every NULL `incident_id` as distinct and would allow two project rows for one period; the project row stays the outer cap. - **`healing_llm_call.incident_id` — consumed as-is, no FK today.** It is a plain `uuid` by deliberate deferral (`0054:50-55`); this story resolves the incident under RLS before writing, exactly as 0054's note requires, and adds no second resolution rule.

## 4. Data model and migrations

**Two tables, one migration, number "next free at implementation"** (this plan pins no number; it is read from the migration ledger at implementation time, not stated as a current maximum). Conventions are the shipped ones: `unique (org_id, id)`, composite FKs over the tenant column, `ENABLE` + `FORCE ROW LEVEL SECURITY`, `timestamptz`, `version` (`plans/00-overview.md:181-190`, `:243-249`), and the append-only pattern 13.6.1-T2 and 13.1.2 use — applied here as *append-only* for `locate_candidate` and *claim-then-freeze* for `locate_attempt`.

| Table | Purpose | Key columns | Bounds and indexes |
|---|---|---|---|
| `locate_attempt` | one attempt per `(incident, step, versions)` | `org_id`, `project_id`, `incident_id`, `step_key`, `rule_version`, `similarity_version`, `locate_version`, `tier` (`accessibility\|ocr\|visual`), **`state` (`claimed`\|`done`)**, **`lease_until`**, `claim_owner`, `attempt_count`, `outcome` (§6, null while `claimed`), `reason`, `call_id` (→ `healing_llm_call`), **`screenshot_artifact_id`** (→ `artifact`, same project, chosen tier only), **`candidate_set_hash`** (SHA-256 over the canonical set, no names), `cost`, `tokens`, `input_hash`, `ingest_seq` | unique `(org_id, project_id, incident_id, step_key, rule_version, similarity_version, locate_version, tier)` — the claim key; composite FK `(org_id, screenshot_artifact_id)` → `artifact (org_id, id)` with the same-project rule enforced by the writer and a test; **partial index `(lease_until) where state = 'claimed'`** for the recovery sweep (the sweep never reads `done` rows, so the index stays small and the sweep cannot be slowed by history); `(org_id, project_id, incident_id, created_at)`, `(org_id, project_id, created_at)` for retention |
| `locate_candidate` | the bounded set and the choice; row sensitivity class **`sensitive`** | `org_id`, `project_id`, `attempt_id`, `index`, `source`, `role`, `bbox` (4 × `int4`), `test_id?`, `name?` and `rendered_locator` (bounded 512) — **written only on the chosen row**, `chosen`, `validation_outcome`, `reason` | unique `(org_id, attempt_id, index)`; non-chosen rows keep only `index`, `source`, `role` and `bbox`, so no accessible name of an unpicked element is stored, and the set stays re-verifiable against `locate_attempt.candidate_set_hash`; any read of a name needs `healing:triage`; ≤ 40 rows per attempt enforced by the writer and re-asserted by a test; index `(org_id, project_id, attempt_id)` |

**The attempt row is the spend boundary — claim before the paid step.** The row is inserted `state = claimed` with `lease_until = now() + lease` **before** the budget reserve and the provider call, and its unique key is what makes a duplicate delivery or a concurrent worker lose: the loser re-reads the existing row, compares `input_hash`, exits `duplicate_delivery` when it matches or `input_hash_mismatch` when it does not, and in either case reserves nothing and places no call. The lease exceeds the worst-case handler time — the storage read cap, the 2 s OCR child and two 60 s provider attempts, plus margin (`[INFERENCE]`, `OI-13-568`) — and the handler's cancellation token is linked to that lease, so a worker that stalls is not renewed by a later delivery. The append-only guard allows exactly two writes to a claimed row — a `lease_until` renewal by the same `claim_owner`, and the single `claimed → done` transition that carries the terminal `outcome`; a `done` row is immutable. Recovery never re-calls on the same key: a sweeper loops per tenant with the tenant scope open — `evidgate_worker_sched` holds no rights on the ledger tables (`migrations/0006_platform_outbox.sql:100`, `migrations/0007_platform_idempotency_record.sql:127`), so there is no owner-function shortcut here — finds expired `claimed` rows through the partial index, and closes each one `provider_outcome_unknown`, copying the spend of the `healing_llm_call` rows that name the claim and placing no call; no answer is reconstructed, because the ledger never stored content (`0054:149-156`). A positive-control test proves the sweeper does see a recorded call row for a claim and still places no call. A re-run of the same step is a new `locate_version`, so it needs a fresh command — never a second paid call under an existing key.

**Traceability chain.** `incident → run → case_attempt` stays 08.1's and 05's; this story adds `step_key` (13.6.1's bound-step key) and records the four versions it consumed, so a later reviewer can say which tier and which similarity version produced a proposal. `call_id` is the single link to the gateway ledger — no second cost store. **`locate_version` is owned here:** the consumer mints it as the smallest integer above every version already stored for the same `(incident, step_key, similarity_version)`, so a re-run is a new version and a late duplicate of an old event keeps the old one; no other story writes it.

**What this story must not store.** No image bytes, no object key, no presigned URL, no full OCR transcript, no page URL, no cookie, no header, no storage value. `name` and `rendered_locator` are stored **only for the chosen candidate**, and only because the bound step already carries that name (`generated_script_step.locator_name`, the amendment `OI-13-548` asks for): a name is what makes a locator a locator, it is never copied into a profile, and every row that holds one is class `sensitive` and read-gated behind `healing:triage`. `screenshot_artifact_id` is a reference, not a copy: the artifact keeps its own tenant, project, retention clock and sensitivity class, and this table never holds pixels. A secret-shaped value is dropped before the row with the same `dropped_fields` treatment 13.6.1 uses.

**Retention and deletion.** Attempt and candidate rows follow the incident's lifecycle and are purged by 08.1.2-T2's hook set, not a second mechanism: one hook registration row **naming `locate_attempt` and `locate_candidate` explicitly**, and `LocateRetentionTests.hook_covers_tables` fails when the hook set stops covering them. A candidate referenced by an open 08.3.1 candidate or an open 08.6.1 approval is pinned while that reference is open. Tenant erasure removes both tables' rows for the org; the append-only guard allows exactly that path under `evidgate_owner`.

## 6. States and transitions

**`locate_attempt` has one transition and then freezes: `claimed → done`.** `claimed` carries the lease and no `outcome`; `done` carries a closed `outcome` — `proposed` (a candidate was chosen and handed to validation), `refused` (a reason above, including `mask_unavailable`, `screenshot_unavailable` and `input_hash_mismatch`), `no_candidate`, `budget_exceeded`, `provider_error`, `unavailable`, `provider_outcome_unknown` — and is immutable. There are no terminal-to-terminal transitions: a re-run writes a new attempt with a new `locate_version` or a different tier, and the newest `done` row per natural key is the current answer. The single mutable window is the claim, which is what makes a duplicate delivery or a crash unable to spend twice. Nothing in this vocabulary can move an incident, a run, a `case_attempt`, a `generated_script` or an 08.3.1 candidate.

**The candidate machine is 08.3.1's, driven but never written here.** `proposed → validated → approved → applied` and their exits belong to `plans/00-overview.md:299`; this story triggers 08.3.1's minting with the chosen index, so the `healing_candidate` row exists in `proposed` before 08.4 runs (AC6), and it writes no state itself — so no state can be skipped by a fallback path. `generated_script`'s four states (`plans/00-overview.md:315`) are untouched: a proposal that a human later merges still needs 08.6.1's approval and its own canary.

**Availability is read, never written — and re-read at the call.** `IHealingAvailabilityResolver.ResolveAsync(projectId)` returns the most restrictive persisted mode (`src/Modules/Evidgate.Modules.Healing.Contracts/HealingAvailability.cs:145-156`); `unavailable` is a runtime observation 08.6.3-T2 produces, so a provider outage is mapped by this module to `outcome = unavailable` without writing a switch row. The same read, the delivered opt-in row and the provider approval are repeated immediately before the provider call, after the reserve, because revocation takes effect before the next call (T64, `plans/features/README.md:123`); a denial at that point releases the reserve and closes the attempt `refused` with that reason and zero calls.

## 7. Jobs and integrations

- **Trigger (outbox) — hand-over, `OI-13-570`.** 13.8.1 writes an event in the transaction that stores the `ambiguous` classification, and **only 13.8.1 registers that outbox type** — this story registers no producer. The consumer re-reads the stored classification through 13.8.1's read contract before it acts, so a stale or forged payload cannot make it spend. The event **name and payload shape are 13.8.1-T1's to fix** (that story is unbuilt, `STATUS.md:350`); this plan names only the shape — incident, step key, verdict, both versions, both scores. A missing, stale or non-ambiguous classification is a no-op, so the trigger can ship before the producer and the fallback stays dark.
- **One queue, one consumer, no schedule — and the claim, not the row, is what stops a second spend.** The work runs in `Evidgate.Worker`; the API never decodes an image, runs OCR or calls a provider. The paid path is preceded by a committed claim: `insert … (state = 'claimed', lease_until = now() + lease, input_hash = …) on conflict (natural key) do nothing`; the insert that returns a row proceeds, the insert that returns none re-reads the row, compares `input_hash` and exits `duplicate_delivery` or `input_hash_mismatch` — so a concurrent delivery cannot reserve twice, and a crash after payment cannot buy a second call because the claim already exists (the sweeper closes it `provider_outcome_unknown`, §4). The terminal write is `update … set state = 'done', outcome = …, call_id = …` guarded by `state = 'claimed'` and `claim_owner`, so a stale worker cannot overwrite a recovered row. `on conflict do nothing` on the *terminal* row alone would not bound spend — the claim does. No Cronos schedule is added for retries (a retry is a new event with a new `locate_version`); the only timer is the per-tenant recovery sweep, which never places a call and needs no `evidgate_worker_sched` grant (§4).
- **Order of operations, forced by P5 and by cost.** The cheap gates come first: module flag, `IHealingAvailabilityResolver`, the project's explicit screenshot opt-in, the remaining-budget read and the **claim insert (committed)** — then candidate building from the stored `a11y_snapshot` (one bounded object read, `IObjectStorage.GetAsync`, `src/BuildingBlocks/ObjectStorage/IObjectStorage.cs:108`, cap from `artifact_kind_policy.max_bytes`) **outside** any transaction → header check of the crop's dimensions → OCR in the child → mask and re-encode → re-check of approval, switch and opt-in (T64) → budget reserve for the **worst case of two paid attempts** → provider call outside the transaction → `claimed → done` with the outcome, the candidate rows, `call_id` and `candidate_set_hash` on one connection. A denial after the reserve releases it and places zero calls. No storage read, decode or OCR happens before the cheap gates, so a disabled project or an exhausted budget costs no I/O and no pixels; the imaging and the call never hold a connection.
- **Child process, not in-process, and closed by construction.** OCR — and every decode, crop and annotate step — runs as a child of the Worker over JSON stdin/stdout with an empty environment allowlist, an empty working directory, no network, rlimits, a pinned `tessdata` and one concurrency semaphore: T36's shape, the same one 08.4.1-T3 uses for the validator and 08.4.2-T1 for heavy checks, so a malformed image or a decoder bug cannot take the Worker down and the child cannot reach the network, the filesystem or a credential.
- **Cost accounting: one row per paid attempt, two ledger keys that must not collide.** Every paid attempt writes one `healing_llm_call` row (`0054:143`) through the existing recorder, with `purpose = locate_fallback` and its `claim_id`; cost is metered once per logical invocation as `ai_credit` under 08.5.5-T2's `ai:<call_id>` key (`plans/12-pilot-commercial.md:101`, 08.5.5-AC1 — that key is the credit dedupe key, one row however many attempts), and tokens are metered **separately** as `ai_tokens` under `tokens:<call_id>:<attempt>` (`[DECISION] proposed, owner to confirm`), because reusing `ai:<call_id>` for a token row would collide with the credit dedupe. `locate_attempt.cost` and `.tokens` are a copy for reporting only — no second meter and no second cost store.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** no route, no permission and no principal: the only entry point is the Worker consumer of 13.8.1's event, so authorization is 13.8.1's and the tenant scope's. Any future read must obey three rules (`OI-13-570`): ids, tiers, outcomes and scores only — never an image, a key, a profile value or a name that is not already on the bound step; reading a verdict needs `healing:triage` (`contracts/permissions.json:469`); a proposal payload additionally needs `authoring:read` (`:299`). Role reality checked against the file: `qa_engineer` holds `healing:triage` and `authoring:write`, not `healing:approve` (`:25-52`); `test_maintainer` holds `healing:approve` and `authoring:write`, not `healing:triage` (`:55-91`); `tenant_admin` holds neither (`:113-168`). No worker credential gains a permission; the composite FKs and RLS are the only isolation controls and are the ones the isolation suite already covers.
- **Retention/deletion:** both tables are append-only for the app role and purged with the incident through 08.1.2-T2's hook set (§4), whose registration row names `locate_attempt` and `locate_candidate`; a row is pinned while an open candidate or approval references it; no pixels, no object copies, no second clock; `screenshot_artifact_id` is a reference, so the artifact's own retention and sensitivity govern it; tenant erasure reaches both tables and leaves no candidate without its attempt (composite FK, enforced).
- **Telemetry:** counters and one audit row per **paid attempt**, carrying ids, tier, outcome, reason, cost, tokens, `call_id` and `claim_id` — never page text, a name, a URL or a box; metric labels come from closed sets (`tier`, `outcome`), and no label carries an id; the gateway's own `llm_calls_total{status}` keeps its meaning.
- **Failure path:** every refusal in §5 places **zero** calls and leaves the incident exactly as 13.8.1 wrote it; a provider failure or timeout maps to `unavailable`/`provider_error` on the attempt row and never fails a run; a crash after payment leaves a `claimed` lease that the per-tenant sweeper closes `provider_outcome_unknown` — spend copied from that claim's call rows, never re-called — so spend is bounded by the key and not by luck; a gate that turns false after the reserve releases the reserve before any call (T64); an OCR child crash yields `no_candidate` with a reason; budget exhaustion, a missing cap and an unparsable cap are refusals, not alert storms; a kill switch at `disabled` short-circuits before any read of the image. The runbook entry is 10.7.1's, with this module's counters named there.

**Trust boundaries and five abuse cases.** (1) A replayed or concurrently delivered event cannot double-spend: the committed claim precedes the reserve and the call (§4, §7), so the loser places no call and a crash-orphaned claim is settled rather than retried; a forged event cannot name another tenant's incident (RLS + composite FK). (2) Page text is untrusted: the closed-index answer plus 08.4 validation is the containment, not prompt wording. (3) An image bomb is bounded by `artifact_kind_policy.max_bytes`, pixel caps and the child process's memory cap. (4) Cost abuse is bounded by the per-incident cap and the project's daily row; a caller cannot start a call. (5) A secret in a name or in OCR text is dropped before serialisation, and the run continues with one fewer candidate.

2. **Flag and default:** `Healing:Locate:Enabled` defaults **off**; `Healing:Locate:VisualTier` defaults **off** even when the module is on, so the OCR tier can ship and be measured without a paid call. Enabling either tier per project requires the project's **explicit** screenshot row (a default-true kind default is not consent, `OI-13-524`) **and** the 08.5.3-T3 approval; a project that never enabled screenshots never reaches the visual tier.
3. **Migration order:** the two tables, the NULL-safe incident budget key and its CHECK in one migration, after 08.1.1's `incident` exists (or with the FK deferred exactly as `0054:50-55` does); no backfill — the tables start empty, and a missing cap row denies rather than defaulting to unlimited.

5. **Rollback:** flip the flag off — no row is mutated, no proposal is retracted from a reviewer, and the incident keeps the class 13.8.1 gave it; deleting the feature's rows is the tenant-erasure path, never a hand-run `delete`.
