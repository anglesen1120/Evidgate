## 1. Goal and non-goals

**Goal.** When — and only when — 13.8.1's profile similarity returns `ambiguous` for one broken bound step, build a **bounded, closed candidate set** from the stored accessibility snapshot (`a11y_snapshot`), read page text with a local OCR engine, and, if the tenant has opted in and the per-incident budget allows, ask a vision model through the 08.5.1 gateway to choose **one index** from a set it did not author. The chosen candidate is a *proposal*: it must pass **every** 08.4 check before anyone sees it, and this story never decides the drift class. Three tiers, cheapest first — accessibility (no model, no egress), OCR (local, no egress), visual (gateway, opt-in, budgeted) — and a refusal at any tier is a normal outcome.

**Area-plan acceptance (quoted).** "when profile similarity is ambiguous, an accessibility + OCR + visual locator may propose a candidate that still passes all 08.4 validation; it never decides the class" (`plans/13-product-phases.md:218`). The governing decisions are verbatim: plan 13 §3 — "profile similarity classifies; a model or the multimodal locator only proposes, and every proposal passes 08.4 validation" (`:32`); plan 13 §5 — "Class `unknown` → no repair; the multimodal locator may propose, and the proposal still needs 08.4 validation" (`:97`); CR-D-2 §7 — "used only when element-profile similarity is ambiguous … Calls go through the gateway with a per-incident budget, and screenshots stay opt-in (`docs/decisions/CR-D-2-direction-a.md:171`).

**Two partials, stated here rather than discovered at build.** (1) **No profile is read** (`OI-13-570`): 13.6.1's architecture rule fails the build if the profile module, `IElementProfileReader` or `IElementProfileSimilarity` is referenced from 13.7.2 (`13.6.1-AC11` and its §9 row, `plans/features/13-product-phases/13.6.1-element-profiles.md:193`, which names 13.7.2's module as a receiver and `:266` says this story owes a receiver row), so ambiguity must arrive *pushed* by 13.8.1 as a command carrying the verdict, `rule_version` and `similarity_version` — never re-computed here. 13.8.1's plan defines no such command yet (its §5/§6 name only classification, proposals and windows), so AC1 is met against a hand-off shape this plan states and that story names. (2) **The "visual" tier has no legal wire shape today** (`OI-13-565`): `HealingLlmRequest.Payload` is a `string` (`src/Modules/Evidgate.Modules.Healing.Contracts/IHealingLlmProvider.cs:79-90`) and the shipped adapter posts `{model, prompt_version, prompt, response_schema}` (`src/Modules/Evidgate.Modules.Healing/Application/HttpHealingLlmProvider.cs:74-90`); a bounded image part is a proposed contract edit, not an existing capability.

**Phase and scope (CR-D-2).** G3 only, V1; wave order is computed by `scripts/plan_graph.py`, not pinned here. Validation (08.4), candidate states and minting (08.3.1), approval and PR (08.6.1), screens (13.8.2-T2), the class decision (13.8.1) and G3 reporting (13.9.1-T3) are other stories. **Not buildable until** 08.5.1-T1.4 supplies the out-of-transaction call and the budget hard stop, 08.5.3-T1/T3 supply the redaction pipeline and the tenant/provider approval, 08.1.2-T1/T2 supply the incident context artifacts and their masking, 08.4.x supplies the validator, 13.6.1-T3 produces `ambiguous` at all, and 13.8.1-T1 emits the hand-off. Mocks are not a substitute for any of them.

**Non-goals.** Any class, verdict or `drift_classification` write (13.8.1); profiles, capture or similarity (13.6.1); the validator, the sandbox, the negative control and the replay comparability gate (08.4); candidate states, `candidate_hash`, the 3-candidate cap and minting (08.3.1); PR creation, approval, canary and rollback (08.6.1/08.6.2); before/after screenshots and the a11y/DOM diff (13.8.2-T1); every screen and its design (13.8.2-T2); the provider/model choice, pricing and region (08.5.5-T4); the eval corpus itself (08.8.1); mobile (`adapter-mobile`, 04.5.1-T1, G4); any new permission, route, state machine or migration number; any change to `plans/13-product-phases.md` or an estimate.

**Prior art (owner rule, 2026-10-27; approach only).** (1) *Set-of-Mark prompting* (`https://arxiv.org/abs/2310.11441`, abstract read 2026-11-09 ✅): taken — overlay numbered marks on region candidates and make the model answer with a mark, which converts an open-ended "find the element" into a closed choice; deliberately not followed — its segmentation model and its free-form answers, because the candidate set here is built deterministically and the answer schema permits one index only. (2) *Tesseract* (`https://github.com/tesseract-ocr/tesseract`, `LICENSE` read 2026-11-09 ✅ Apache-2.0; release `5.5.4`, 2026-10-28 ✅ GitHub releases API): taken — a local, offline OCR pass whose word boxes can be matched against the expected accessible name; deliberately not followed — sending the image to a provider for text, which would turn a free, zero-egress step into a paid cross-border transfer. (3) Internal precedent, not prior art but the binding shape: 13.5.1-AC8 already has a model choose **a candidate index from a list the client built** and re-check the choice live; this story reuses that pattern instead of inventing a second one.

## 2. User stories and acceptance criteria

- As a QA engineer, when the profile rules cannot decide where a broken step's element went, I get an explicit proposal or an explicit refusal with a reason — never a guessed locator.
- As a test maintainer, I can see which tier produced a candidate (accessibility, OCR or visual), what it cost, and that it still had to pass the full validator before I was asked to review it.
- As a data owner, I can prove no pixel left the tenant unless my project enabled screenshots and I approved that provider, and that a refused or over-budget call placed zero calls.

## 4. Data model and migrations

**Two tables, one migration, number "next free at implementation"** (the ledger's highest today is `0089`, `STATUS.md:8`; the number is taken at build). Conventions are the shipped ones: `unique (org_id, id)`, composite FKs over the tenant column, `ENABLE` + `FORCE ROW LEVEL SECURITY`, `timestamptz`, `version` (`plans/00-overview.md:181-190`, `:243-249`), and the append-only pattern 13.6.1-T2 and 13.1.2 use — applied here as *append-only* for `locate_candidate` and *claim-then-freeze* for `locate_attempt`.

| Table | Purpose | Key columns | Bounds and indexes |
|---|---|---|---|
| `locate_attempt` | one attempt per `(incident, step, versions)` | `org_id`, `project_id`, `incident_id`, `step_key`, `rule_version`, `similarity_version`, `locate_version`, `tier` (`accessibility\|ocr\|visual`), **`state` (`claimed`\|`done`)**, **`lease_until`**, `claim_owner`, `attempt_count`, `outcome` (§6, null while `claimed`), `reason`, `call_id` (→ `healing_llm_call`), `cost`, `tokens`, `input_hash`, `ingest_seq` | unique `(org_id, project_id, incident_id, step_key, rule_version, similarity_version, locate_version, tier)` — the claim key; index `(state, lease_until)` for the recovery sweep, `(org_id, project_id, incident_id, created_at)`, `(org_id, project_id, created_at)` for retention |
| `locate_candidate` | the bounded set and the choice | `org_id`, `project_id`, `attempt_id`, `index`, `source`, `role`, `name`, `test_id`, `bbox` (4 × `int4`), `rendered_locator` (bounded 512), `chosen`, `validation_outcome`, `reason` | unique `(org_id, attempt_id, index)`; ≤ 40 rows per attempt enforced by the writer and re-asserted by a test; index `(org_id, project_id, attempt_id)` |

**The attempt row is the spend boundary — claim before the paid step.** The row is inserted `state = claimed` with `lease_until` **before** the budget reserve and the provider call, and its unique key is what makes a duplicate delivery or a concurrent worker lose: the loser reads the existing row and exits `duplicate_delivery` without reserving and without calling. The append-only guard allows exactly two writes to a claimed row — a `lease_until` renewal by the same `claim_owner`, and the single `claimed → done` transition that carries the terminal `outcome`; a `done` row is immutable. Recovery never re-calls on the same key: a lease that expires while `claimed` is settled by a sweeper that asks whether a `healing_llm_call` row exists for the claim — if one does, the outcome is recoverable from the gateway record; if none does **but the call may still have been placed** (the gateway writes call rows inside the caller's transaction today, `src/Modules/Evidgate.Modules.Healing/Application/HealingLlmGateway.cs:129-132`), the row is closed `provider_outcome_unknown` and the spend is recorded as unknown, not retried. A re-run of the same step is a new `locate_version`, so it needs a fresh command — never a second paid call under an existing key.

**Traceability chain.** `incident → run → case_attempt` stays 08.1's and 05's; this story adds `step_key` (13.6.1's bound-step key) and records the four versions it consumed, so a later reviewer can say which tier and which similarity version produced a proposal. `call_id` is the single link to the gateway ledger — no second cost store.

**What this story must not store.** No image bytes, no object key, no presigned URL, no full OCR transcript, no page URL, no cookie, no header, no storage value. `name` and `rendered_locator` hold the accessible name **only because the bound step already carries it** (`generated_script_step.locator_name`, the amendment `OI-13-548` asks for): a name is what makes a locator a locator, and it is never copied into a profile. A secret-shaped value is dropped before the row with the same `dropped_fields` treatment 13.6.1 uses. Candidate rows never carry a screenshot reference, so there is no copy of an artifact and no second retention clock.

**Retention and deletion.** Attempt and candidate rows follow the incident's lifecycle and are purged by 08.1.2-T2's hook set, not a second mechanism: one hook registration row, and `LocateRetentionTests.hook_covers_tables` fails when the hook set stops covering them. A candidate referenced by an open 08.3.1 candidate or an open 08.6.1 approval is pinned while that reference is open. Tenant erasure removes both tables' rows for the org; the append-only guard allows exactly that path under `evidgate_owner`.

## 5. API shapes (commands, queries, endpoints)

All work runs in the existing pipeline shape (`plans/00-overview.md:203`, C2): telemetry → validation → tenant transaction → handler → outbox flush → commit, with the storage read and the provider call **outside** the transaction (P5, `src/BuildingBlocks/ObjectStorage/IObjectStorage.cs:82-100`).

## 6. States and transitions

**`locate_attempt` has one transition and then freezes: `claimed → done`.** `claimed` carries the lease and no `outcome`; `done` carries a closed `outcome` — `proposed` (a candidate was chosen and handed to validation), `refused` (a reason above), `no_candidate`, `budget_exceeded`, `provider_error`, `unavailable`, `provider_outcome_unknown` — and is immutable. There are no terminal-to-terminal transitions: a re-run writes a new attempt with a new `locate_version` or a different tier, and the newest `done` row per natural key is the current answer. The single mutable window is the claim, which is what makes a duplicate delivery or a crash unable to spend twice. Nothing in this vocabulary can move an incident, a run, a `case_attempt`, a `generated_script` or an 08.3.1 candidate.

**The candidate machine is 08.3.1's, referenced only.** `proposed → validated → approved → applied` and their exits belong to `plans/00-overview.md:299`; this story writes no candidate row, so no state can be skipped by a fallback path. `generated_script`'s four states (`plans/00-overview.md:315`) are untouched: a proposal that a human later merges still needs 08.6.1's approval and its own canary.

**Availability is read, never written.** `IHealingAvailabilityResolver.ResolveAsync(projectId)` returns the most restrictive persisted mode (`src/Modules/Evidgate.Modules.Healing.Contracts/HealingAvailability.cs:145-156`); `unavailable` is a runtime observation 08.6.3-T2 produces, so a provider outage is mapped by this module to `outcome = unavailable` without writing a switch row.

## 7. Jobs and integrations

- **Trigger (outbox) — hand-over, `OI-13-570`.** 13.8.1 writes an event in the transaction that stores the `ambiguous` classification; this consumer reads it with the tenant scope open. The event **name and payload shape are 13.8.1-T1's to fix** (that story is unbuilt, `STATUS.md:350`); this plan names only the shape — incident, step key, verdict, both versions, both scores. A missing or non-ambiguous event is a no-op, so the trigger can ship before the producer and the fallback stays dark.
- **One queue, one consumer, no schedule — and the claim, not the row, is what stops a second spend.** The work runs in `Evidgate.Worker`; the API never decodes an image, runs OCR or calls a provider. The paid path is preceded by a committed claim: `insert … (state = 'claimed', lease_until = now() + lease) on conflict (natural key) do nothing`; the insert that returns a row proceeds, the insert that returns none re-reads the row and exits `duplicate_delivery` — so a concurrent delivery cannot reserve twice, and a crash after payment cannot buy a second call because the claim already exists (the sweeper settles it as recoverable or `provider_outcome_unknown`, §4). The terminal write is `update … set state = 'done', outcome = …, call_id = …` guarded by `state = 'claimed'` and `claim_owner`, so a stale worker cannot overwrite a recovered row. `on conflict do nothing` on the *terminal* row alone would not bound spend — the claim does. No Cronos schedule is added for retries (a retry is a new event with a new `locate_version`); the only timer is the recovery sweep, which never places a call.
- **Order of operations, forced by P5.** resolve → read the snapshot bytes with `IObjectStorage.GetAsync` (`src/BuildingBlocks/ObjectStorage/IObjectStorage.cs:108`, cap from `artifact_kind_policy.max_bytes`) **outside** any transaction → build candidates → OCR in a child process → [gate: opt-in, switch] → **claim insert (committed)** → budget reserve → provider call outside the transaction → `claimed → done` with the outcome, candidates and `call_id` on one connection. The imaging and the call never hold a connection; the reserve and the outcome rows are the only database work around them.
- **Child process, not in-process.** OCR runs as a child of the Worker over JSON stdin/stdout with CPU, memory and wall-clock limits — T36's shape, the same one 08.4.1-T3 uses for the validator and 08.4.2-T1 for heavy checks — so a malformed image or a decoder bug cannot take the Worker down.
- **Cost accounting.** Every placed call writes one `healing_llm_call` row (`0054:143`) through the existing recorder and is metered once under `08.5.5-T2`'s `ai:<call_id>` key into the `ai_tokens` ledger metric (`plans/12-pilot-commercial.md:101`); no second meter, no second cost column outside `locate_attempt.cost` as a copy for reporting.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** no route, no permission and no principal: the only entry point is the Worker consumer of 13.8.1's event, so authorization is 13.8.1's and the tenant scope's. Any future read must obey three rules (`OI-13-570`): ids, tiers, outcomes and scores only — never an image, a key, a profile value or a name that is not already on the bound step; reading a verdict needs `healing:triage` (`contracts/permissions.json:469`); a proposal payload additionally needs `authoring:read` (`:299`). Role reality checked against the file: `qa_engineer` holds `healing:triage` and `authoring:write`, not `healing:approve` (`:25-52`); `test_maintainer` holds `healing:approve` and `authoring:write`, not `healing:triage` (`:55-91`); `tenant_admin` holds neither (`:113-168`). No worker credential gains a permission; the composite FKs and RLS are the only isolation controls and are the ones the isolation suite already covers.
- **Retention/deletion:** both tables are append-only for the app role and purged with the incident through 08.1.2-T2's hook set (§4), pinned while an open candidate or approval references a row; no pixels, no object copies, no second clock; tenant erasure reaches both tables and leaves no candidate without its attempt (composite FK, enforced).
- **Telemetry:** counters and one audit row per call, carrying ids, tier, outcome, reason, cost, tokens and `call_id` — never page text, a name, a URL or a box; metric labels come from closed sets (`tier`, `outcome`), and no label carries an id; the gateway's own `llm_calls_total{status}` keeps its meaning.
- **Failure path:** every refusal in §5 places **zero** calls and leaves the incident exactly as 13.8.1 wrote it; a provider failure or timeout maps to `unavailable`/`provider_error` on the attempt row and never fails a run; a crash after payment leaves a `claimed` lease that is settled `provider_outcome_unknown` rather than re-called, so spend is bounded by the key and not by luck; an OCR child crash yields `no_candidate` with a reason; budget exhaustion is a refusal, not an alert storm; a kill switch at `disabled` short-circuits before any read of the image. The runbook entry is 10.7.1's, with this module's counters named there.

**Trust boundaries and five abuse cases.** (1) A replayed or concurrently delivered event cannot double-spend: the committed claim precedes the reserve and the call (§4, §7), so the loser places no call and a crash-orphaned claim is settled rather than retried; a forged event cannot name another tenant's incident (RLS + composite FK). (2) Page text is untrusted: the closed-index answer plus 08.4 validation is the containment, not prompt wording. (3) An image bomb is bounded by `artifact_kind_policy.max_bytes`, pixel caps and the child process's memory cap. (4) Cost abuse is bounded by the per-incident cap and the project's daily row; a caller cannot start a call. (5) A secret in a name or in OCR text is dropped before serialisation, and the run continues with one fewer candidate.
