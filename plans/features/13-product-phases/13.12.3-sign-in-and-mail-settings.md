## 1. Goal and non-goals

**P1.** A provisioned Evidgate operator can rotate either customer OIDC client without restarting Identity (G1). In G2, the same operator can change the magic-link default for future organizations, rotate the outbound mail credential, and check that the active sender accepts a test message. A configuration error must not disable an already working login or sender.

These controls are platform settings, not tenant impersonation. They neither configure workforce sign-in nor issue operator sessions. They cannot add arbitrary identity providers or mail endpoints, modify existing organizations' authentication policies, send invitations or magic links as a diagnostic, or turn a customer magic link into staff MFA.

## 2. User stories and acceptance criteria

| ID | Operator action | Observable outcome |
|---|---|---|
| AC1 | Change Google Workspace or Microsoft Entra ID client ID and rotate that provider's secret. | The next customer sign-in for that provider uses the validated pair without redeploy. A member of an allowed organization succeeds; the other provider and workforce sign-in are unaffected. |
| AC2 | Supply a wrong credential or race another editor. | Validation failure leaves the working revision, secret reference and login intact. A stale `If-Match` returns 412 with the current revision; it cannot overwrite a later edit. Neither case creates an active change. |
| AC3 | Change the platform magic-link default from true to false, then back to true. | Each newly created organization receives the default in force at creation. Existing values, including an explicit false set by a tenant admin, are unchanged. Sign-in still checks the organization's own value. |
| AC4 | Change the supported mail provider settings or credential. | The next ordinary dispatch through `IEmailSender` uses the validated revision without a restart. An invalid provider, sender or credential leaves the old sender in service. |
| AC5 | Request a test send under the active revision. | A fixed diagnostic message, not a login link, goes through the same sender to an approved operations mailbox. The result distinguishes queued, provider-accepted and terminal failure; accepted does not mean delivered. |
| AC6 | Open a settings screen, save, encounter a refusal or revisit history. | Only an MFA-authenticated operator on the operator origin can do this. Safe revision and rotation metadata are visible; no secret is prefilled, echoed or retained by the screen, even on failure. |

## 3. Contracts touched

- FR-13-14 and 13.12.1 supply the separate operator host, workforce session/gate, approved UX design, append-only revisions, audit and write-only secret storage. No second-person approval for these settings. No customer `/v1` alias for an operator command.
- 02.3.1 owns customer OIDC: keep the verified email, membership, redirect allowlist, state/nonce/PKCE, signature, audience, issuer and organization-policy checks. For Entra (02.3.1-T4), `iss` must match `tid`; retain `xms_edov`, `(tid, oid)` identity and the allowed-tenant check. Changing a client ID changes the expected audience, not the trust policy.
- 02.3.4 owns the customer magic-link challenge, non-enumerating responses, rate limits and existing tenant-admin switch. OI-02-42 sets its initial platform default to **true**; it is not a global runtime override.
- 02.10.1-T2.3 supplies `IEmailSender`; 02.10.1 owns suppression, retry/deduplication and dispatch outside the request transaction. OI-02-17 selects Resend for the pilot, not arbitrary SMTP or HTTP endpoints; external sends remain subject to its DNS and transfer/retention release gate.

## 4. Data model and migrations

| Setting scope | Active revision data | Consumer |
|---|---|---|
| One customer OIDC provider | Fixed provider key, client ID, opaque reference to that provider's versioned client secret | Existing 02.3.1 handlers read a matching ID/secret pair. A change to one provider cannot replace the other's reference. |
| Platform magic-link default | Boolean, initially true | Organization creation writes a concrete `organization.magic_link_enabled`. Do not implement this with a fallback joined at sign-in or an update across existing rows. |
| Platform transactional mail | Supported provider, verified sender address on the approved sending domain, opaque version reference for the credential | The existing sender resolves one validated configuration per dispatch. Do not copy credentials into a notification or outbox payload. |

Use the 13.12.1-T3 revision store, not new plaintext provider tables. Stage replacement credentials in the secret store; validate the entire candidate, including unchanged fields. Append the revision, advance the pointer conditionally and write its audit entry in one transaction. Only committed revisions may be loaded. Settings reads return configured/last-rotated metadata, never a retrievable secret handle. Imports of existing working settings seed the first validated revision without copying secret bytes into the database.

## 5. API shapes (commands, queries, endpoints)

All queries, commands and test results below live under `/internal/operator/*` on the operator ingress. The operator session and antiforgery conventions come from 13.12.1. Customer-facing login routes and the existing org-admin switch remain unchanged.

| Operation | Input | Result or refusal |
|---|---|---|
| Read current setting or history | Fixed setting key; for OIDC, one of the two supported providers | Current `ETag`, safe values, configured/last-rotated status and revision metadata. Never serialize a credential field, request body or credential-validation response. |
| Publish OIDC configuration | Current `If-Match`, provider, client ID, optional write-only replacement secret | Omitted secret retains that provider's active version; explicit empty input is invalid. An initial configuration needs a valid pair. Return a new revision only after validation, commit and audit. |
| Publish platform default | Current `If-Match`, boolean | Return the new revision. No target organization parameter and no batch update. |
| Publish mail configuration | Current `If-Match`, supported provider and allowed sender, optional write-only replacement credential | Reject an unsupported provider, unverified sender or invalid credential. Blank is not a command to erase the working key. No caller-supplied provider URL. |
| Test active sender / read result | Observed active mail revision; fixed diagnostic template and the deployment-configured operations recipient (OI-13-843), neither editable by the caller | Authorize, check the revision and enqueue one diagnostic. Return an operation ID/status; stale revision means no enqueue. The worker refuses a changed revision before dispatch rather than reporting a test of the wrong configuration. No new setting revision, login challenge or tenant notification is created. |

## 6. States and transitions

A candidate is **staged**, then **validated**, then **active**. Discovery metadata or correct string format does not prove a client secret works: require a provider-authenticated check of the candidate pair, not a test of the old active client (OI-13-841). Similarly, mail validation must establish that the candidate can use the approved sender. Inconclusive results are failures to validate, not permission to publish.

A validation failure, revision conflict or failed audit commit leaves the previous pointer untouched. Retire unused staged secret versions through the 10.7.1-T4 process. A rotation must not mix an old client ID with a new secret within a login; complete an in-flight callback against the revision pinned at login start, or require a fresh sign-in if that revision can no longer be used (OI-13-842). Never weaken token validation to complete an old callback. A rollback is a new conditional, validated revision, not mutation of history.

## 7. Jobs and integrations

- Customer OIDC handlers load the committed provider revision on the next login. Exercise the actual 02.3.1 handlers, not only a configuration read model. Workforce authentication uses neither these keys nor the customer magic-link switch.
- At organization creation, resolve the default and persist the org switch in the creation transaction. Concurrent creation and publication must produce an org with one committed value. At login, read only that org's value; the tenant admin keeps the independent right to disable or enable magic links.
- The mail worker resolves the active sender at dispatch, not when business mail was originally enqueued. Preserve suppression, retries, provider idempotency where supported and terminal outcome handling. Diagnostics use a platform-scoped job via the existing queue and `IEmailSender`, not a fictitious customer `org_id` or a second transport. No provider send occurs in the API transaction. Local evidence uses the existing capture-only channel; external provider acceptance needs the release prerequisites in §11.

## 8. Security, privacy and performance

- **Authorization:** require an explicitly provisioned `platform_operator` with a live workforce session and verified MFA. Reject wrong host, expired/revoked session, missing antiforgery on writes, tenant admin, CI token or billing-only role before secret staging, publication or test enqueue. No support grant or tenant identity is needed for a platform setting. Never mint a workforce session from customer sign-in.
- **Retention/deletion:** keep redacted configuration/audit history under the platform retention policy; retire unused or superseded credential versions per 10.7.1-T4. Never store secret text or a secret-derived hash in revisions, caches, diagnostics, browser storage, logs, traces or audit. Test messages contain no personal or customer content, sign-in URL or token; do not retain their body in the console.
- **Telemetry:** audit actor, UTC time, setting key, old/new safe values or opaque version references, before/after hashes of canonical redacted data and request ID. Record safe failure categories and test outcome by operation ID, not credential bytes, provider response bodies, recipient addresses or OIDC tokens. No raw request capture on these routes.
- **Failure path:** refuse absent preconditions, stale edits (412), validation timeouts, secret-store errors or audit failure without replacing a working revision. If no validated setting exists, refuse that affected operation; do not silently borrow another provider's or staff credential. Check request limits and suppression for diagnostic dispatch; a failed or suppressed mail reports that outcome, never success. Provider checks run outside the publish transaction; recheck `If-Match` at commit.

## 11. Rollout

1. In G1, bootstrap validated customer registrations and demonstrate independent workforce access before rotating either one. Enable the operator sign-in settings screen only after design approval and the real-handler checks for both providers. Leave G2 controls absent.
2. In G2, bring up the initial platform default of true without writing existing organizations. Rehearse create-before/after and mail rotation against capture-only local dispatch. A captured message is evidence of wiring, not external delivery.
3. Before any external mail, meet the OI-02-17 Resend account, dedicated sending-domain SPF/DKIM/DMARC and counsel transfer/retention prerequisites. Exercise a test dispatch to the approved operations mailbox and an ordinary staged notification with the live sender. On failure, keep or republish the last validated settings as a new revision; do not replay delivered mail or roll back tenant switches.
