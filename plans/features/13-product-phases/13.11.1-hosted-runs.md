## 1. Goal and non-goals

**P4 · G2.** A project that has approved a Playwright script in Evidgate can run it against its declared staging origin without operating a CI runner. The result is ordinary automated evidence. A reviewer can follow the resulting evaluation and, for a run bound to a release, the release decision back to the script revision that ran.

`[DECISION]` D-HOSTED-RUN narrows A5 only for hosted script generation and execution. Neither the API host nor the ordinary worker executes tenant scripts. Healing replays stay customer-side. FR-13-13 (reworded): a hosted run executes only an approved script revision pinned by hash, and the hosted executor never fetches from a repository (D-NO-GITHUB). The sole executable input is the Evidgate script revision hash; there is no repository URL, branch, commit or pasted-script path.

## 2. User stories and acceptance criteria

| ID | Actor and action | Observable outcome |
|---|---|---|
| 13.11.1-AC1 | A user with `hosted_run:create` selects an approved revision and one of the project's declared staging origins and presses Run. | One request creates one `mode=hosted` run with the selected hash; retrying the same intent returns that run. A missing grant, foreign revision or undeclared origin starts no job. |
| 13.11.1-AC2 | A hosted worker claims the run. | Only the current lease holder can finalize its job; one disposable VM/microVM executes only the verified revision. The next tenant cannot see its disk, browser profile or credentials. |
| 13.11.1-AC3 | A case tries to contact a destination outside policy. | The executor refuses the connection, including on redirects and after DNS changes. The case attempt fails with `egress_refused`; the run continues with the remaining cases. |
| 13.11.1-AC4 | A case needs a staging login and produces an artifact. | Only an in-executor, tenant-scoped reference resolves to the secret. Neither log nor published artifact contains it; an artifact that cannot safely be redacted is withheld. |
| 13.11.1-AC5 | A reviewer opens results from a release-bound run. | Ordinary case attempts and authorized artifacts feed the existing evaluation and release aggregation. A finished job with failing cases is not a PASS; missing evidence never supplies a passing result. |
| 13.11.1-AC6 | Two tenants request work; one exhausts its slots or minute budget. | Capacity is bounded per tenant; the other tenant can start. Retried finalization does not double-meter minutes. A kill stops admission, dispatch and active hosted execution. |
| 13.11.1-AC7 | A project has an approved case but no script or customer-owned tests. | Hosted `evidgate generate` returns a candidate for the existing authoring review. Nothing executes as an approved test until that review produces an immutable revision. |

## 3. Contracts touched

- 00 §2: `hosted_run:create` for `qa_engineer`, `test_maintainer`, `tenant_admin`; §3: hosted run and script revision; §5.4: tenant isolation. FR-13-13 (approved revision pinned by hash; no repository fetch) and its egress rules apply to every executor connection, not just the initial browser navigation.
- 13.5.1 owns script identity, annotation, approval and immutable hash. 05.2.1 creates the run; 05.7 owns job, lease, claim and finalization. Hosted mode neither invents another run identity nor gives the browser access to those APIs.
- 06.1.3 receives artifacts through its existing upload path. Evaluations, release aggregation (07.5.3) and reporting consume ordinary run evidence. 12.3.1 owns the usage ledger and quota gate; 13.11 supplies `runner_minutes`, not a new invoice or price.
- 05.9.2-T1 and 11.2.1-T4/T5 supply the isolation decision, threat review and boundary. This plan describes acceptance before the spike; it does not select a production executor or image.

## 4. Data model and migrations

| Record | Write and constraint |
|---|---|
| `hosted_run_request` | One request references the ordinary run, project, immutable script revision hash, selected staging origin and request state. Bind the idempotency key and input fingerprint to the project and operation. Never persist raw credentials or replace the pin on a retry. |
| `hosted_egress_origin` | A project declares a normalized origin (scheme, host, effective port), not a path, wildcard or arbitrary redirect target. Enforce uniqueness within the project and enforce the configured maximum atomically. The fixed artifact-upload destination is platform-owned, not a user-editable origin. |
| Existing ownership | Both new records carry `org_id`, project-scoped composite foreign keys and FORCE RLS. Reuse the run, script store, `job`/`job_lease`, artifact and usage records through their owners. Use a unique usage identity for each metered execution so replay is harmless. |

## 5. API shapes (commands, queries, endpoints)

**Create** (T2): project-scoped hosted request with `Idempotency-Key`, approved script revision hash and declared origin reference. App credentials, when required, are references only. The result supplies request id, ordinary run id and state. Check permission, scope, approval, declared origin, kill switch and quota before dispatch. The same key and body returns the original ids; reusing a key with different inputs is a conflict. A denial cannot leave a runnable job.

**Progress and result** (T13): the authorized run view reads request state, a safe refusal reason if applicable and a link to the ordinary run. Do not return the staging credentials, lease token or upload capability. The origin picker lists project declarations, not a free-form navigation field.

**Claim and finalize** (T3): worker service identity, scoped job and current lease are required. Finalize accepts the normal result/evidence references for that run only. Duplicate delivery is safe; an expired holder cannot write over its successor. The human create grant is not a worker grant.

## 6. States and transitions

| Transition | Condition and effect |
|---|---|
| `requested` → `queued` | Persist the run/request association and submit the eligible job without exposing a partly created runnable request. A pre-admission rejection need not create a request row. |
| `queued` → `running` | The hosted worker obtains the current lease and a tenant slot. Re-check kill switch, quota and applicable policy before execution. |
| `running` → `done` | The current lease holder finalizes through the ordinary run path; `done` means execution finished, not that all cases passed. |
| `requested` / `queued` / `running` → `refused` | A stop, cancellation, timeout or policy failure that prevents completion records a safe reason. Tear down any executor and release the slot. Preserve actual partial evidence without synthesizing pass results. |

Loss of a lease revokes that executor's authority; destroy it before work is reassigned. An individual navigation refusal is a failed **attempt**, not a request-wide refusal. Terminal requests cannot be restarted by a late heartbeat, duplicate claim or duplicate finalize.

## 7. Jobs and integrations

The control-plane worker claims from the existing queue and stages the verified script and image into a fresh guest. The guest has no scheduler, database, tenant-store or upload credential. A scoped secret delivery mechanism resolves only the requested staging secrets inside the executor; it does not open general egress to a secret service. **Artifacts never leave the guest by the guest's own network path:** the guest hands raw output over a one-way channel to the trusted worker, which runs outside tenant-controlled code, redacts it, withholds what cannot be made safe, and only then uploads the result to the platform-issued destination via plan 06. The worker finalizes evidence, settles usage and destroys guest resources on normal and interrupted exits.

Hosted generation runs `evidgate generate` inside the same boundary. Hand candidate output to the script store through the trusted worker; use the approved generation gateway path outside the guest when needed. Do not add provider hosts to browser egress. Generation cannot approve or run its own output.

**Prior art (approach only).** [Selenium Grid's queue and distributor](https://www.selenium.dev/documentation/grid/components/) separate waiting requests from available browser slots. Use that distinction for fair admission and lease assignment; do not adopt Grid's node or slot as the tenant security boundary. Evidgate uses its own job ledger and a disposable guest per job.

## 8. Security, privacy and performance

- **Authorization:** check `hosted_run:create` in the selected project. Recheck tenant/project ownership of revision, origin, secret references, run and artifacts. Worker identity and a current lease authorize only the assigned job. Neither user nor guest may choose a worker identity, broader tenant scope or arbitrary image.
- **Retention/deletion:** destroy the guest, disks, browser profile and temporary secret material on success, failure, lease loss, cancel, timeout or kill. Project requests and origins follow project deletion; published artifacts follow plan 06 retention/deletion, and usage records follow the ledger policy. Do not retain raw material for later redaction.
- **Personal data:** staging pages, screenshots, traces, network captures and application logins may contain tenant data. Inject only scoped secret references' values inside the executor. Redact before persistence or upload, and omit artifact classes that cannot be made safe. Never place a value in request records, URLs, telemetry or audit.
- **Telemetry:** record lifecycle, safe reason, duration and metered minutes. Keep IDs in authorized audit records; use bounded labels for run state and refusal class. Do not record page contents, credential values, raw URLs/query strings or upload capabilities.
- **Failure path:** enforce FR-13-13 at the network boundary independently of tenant code. Guest egress permits only the project's declared staging origins; the fixed artifact upload host is reachable only from the trusted worker's post-redaction upload and never from the guest, the browser or any script process, so tenant code cannot publish an unredacted artifact or use the upload capability. Validate scheme/host/port and the actual address used at connect time for every connection, including subresources, redirects and DNS re-resolution. Refuse private, loopback, link-local and metadata addresses in both address families, even behind an allowed hostname. Default deny on unresolved or ambiguous policy; no browser-only check, ambient network path or arbitrary outbound proxy. Record `egress_refused` on the affected attempt and continue the run.

`[OPEN]` Proposed operating envelope for the spike, not a production authorization: HTTPS only, at most 10 staging origins per project, two concurrent jobs per tenant and 15 minutes per job. Fair scheduling, a wall-clock deadline and admission against remaining quota bound use even before a runner-minute price exists.

## 9. Test plan

| Acceptance | Evidence required before enabling hosted runs |
|---|---|
| AC1, AC2 | Exercise concurrent identical creates, payload mismatch, unauthorized actor, foreign org/project inputs, stale and duplicate finalizers. Observe one run for a valid intent, no unauthorized lease and no changes by a stale worker. Verify actual guest destruction and a clean next job. |
| AC3 | In a controlled network fixture, cover a permitted destination, undeclared destination, non-public address classes, redirect targets and changed DNS answers. Assert the refused connection never reaches the fixture sink and a subsequent allowed case still executes. |
| AC4 | Use synthetic secret markers; inspect persisted requests, logs, audit, errors and every published artifact type. Also attempt a guest-originated upload and a guest connection to the artifact host. Expected: the fixture can authenticate, no marker is observable in any retained output, both guest attempts are refused, and only the trusted worker's post-redaction upload reaches the artifact host. Withhold unsafe output rather than failing open. |
| AC5 | Bind an approved fixture-app run to a release. Follow its revision hash, case attempts and artifacts into evaluation and release decision. Repeat with a failing case and missing evidence; compare to the ordinary evidence path, not to a hosted-specific decision. |
| AC6 | Compete for limited slots with two tenants; fill one tenant's quota, replay finalization, cancel and activate the kill switch with work both queued and active. Assert fair progress, bounded minutes, no double debit, no live guest after shutdown and no new claims. |
| AC7 | Generate against the fixture without a repository; a candidate without approval cannot run. After review, the executor verifies the approved revision's hash rather than using draft bytes. |

## 11. Rollout

1. Keep hosted admission off. Complete the isolation spike, review the image, measure the fixture cost and record the threat decision. An unresolved boundary blocks T5; a container-only fallback does not qualify.
2. Exercise one fixture project under explicit origin, slot, minute and timeout limits. Before pilot, require ordinary release evidence, clean secret-marker checks, two-tenant isolation/fairness and a successful kill drill. Hosted generation must pass the same boundary checks before enabling it.
3. Enable eligible pilot projects with metering and caps from the first run. If a gate fails, stop hosted execution and reconcile outstanding jobs; customer CI, local runs and previous evidence remain available. Meter unpriced until the owner resolves OI-13-806.
