## 1. Goal and non-goals

**Goal.** Make every **§4.3 gate** measurable from rows the platform already stores, and readable by the operator: one append-only, platform-scope snapshot per metric and period, computed by a scheduled job from stored rows, plus an operator-ingress read that returns the numbers, their numerators and denominators, the period they cover and their `metric_version` — never a hand-entered value, never a number the read path invented.

**Area-plan acceptance (quoted).** "each §4.3 gate metric is computed from stored data and readable by the operator; the G1 free trial also reports the measured model cost per AI action" (`plans/13-product-phases.md:241`). The metric definitions are not this plan's to invent; §4.3 says (`:63-68`):

| Phase | Go when | Stop / pivot signal |
|---|---|---|
| G1 Author | At least 5 external teams use authoring for at least 3 weeks and export or use the test cases | Fewer than 3 teams return after week 1 |
| G2 Run | At least 70 % of generated scripts pass 3 of 3 runs on one build without manual edits; at least 3 teams agree to pay | Most scripts need manual repair |
| G3 Learn and repair | 0 adjudicated false repairs on the 08.8.1 corpus over at least 300 proposals, with the rule-of-three caveat (08.8.2-T2); acceptance rate reported, not gated; threshold stays O6 `[OPEN]` | Any false repair whose cause is not understood and fixed |
| G4 Expand | Paying demand per item | — |

**What is fixed and what is open.** Three of the words in that table are not defined anywhere in the plans, and this document says so instead of choosing silently: **"external team"** (the `organization` row has no internal/external marker — `0004:34-55`), **"use authoring"** (reads are not recorded anywhere, so only writes can be counted), **"return after week 1"** (no window or cohort rule exists), and **"export"** (13.1.1's export route writes no audit row — its `[DECISION]` note lists an audit row for import only, `13.1.1` §Notes `:557`). Those four are `OI-13-576`–`OI-13-578`; the plan ships `[INFERENCE]` definitions behind them so the metric is computable, and every snapshot names its `metric_version` so a changed definition is a new measurement, never a rewritten one.

**Two definitions are not this story's at all, and are quoted verbatim rather than re-invented.** (1) **G2** — 13.5.1-T4.2 owns the metric wording and hands it over (`OI-13-515`, `plans/features/13-product-phases/13.5.1-bound-playwright-scripts.md:389`, `:411`): numerator = scripts that reached three greens on one build after merge **whose merged PR contains exactly the one generated commit** (a human-added commit is a manual edit); denominator = scripts that reached `pr_state = open` in the measurement window. (2) **G3** — 13.8.1-T4.4 fixes the wording (`plans/features/13-product-phases/13.8.1-locator-drift-vs-ui-change.md:273`, quoted in §2 AC6). Both are partial until their owner confirms them (`OI-13-515` is `owner decision`, open in `plans/open-items/05-product-phases-g1.md`), and this story computes what those rows say, not a rival definition.

**What "measured model cost" means, and what it does not.** The G1 clause asks for **measured** cost, not the credited price: `healing_llm_call.cost_micro` is the provider-measured value, while `authoring_generation.cost_micro` is the **settled credit** value (`13.3.1-AC19`, `plans/features/13-product-phases/13.3.1-generation-pipeline.md:120`) — 0 on a cache hit or a blocked call, which would report a cost of 0 for exactly the actions that cost nothing and a misleading average for the rest. This plan therefore divides **provider-measured micro-cost** by the number of **actions that actually placed a call** (`ai_run_id` non-null), reports `no_call_actions` and `unmetered_calls` separately, and answers `null` + `incomplete_cost` when a counted call has no measured cost (T60) — never a partial average.

**Non-goals.** Any threshold, verdict or go/stop decision: §4.3's numeric bars are quoted as data, the G3 threshold is O6's (owner, `DECISIONS §8`), and the V2/V3 **gate mechanism** with its stored pass/fail result is 08.8.3's (`plans/features/08-healing-learning/08.8.3-phase-gates.md:11-13`), which this story does not extend, call or duplicate. The pilot's own M1–M7 metrics and their frozen `metric-definitions.md` (12.2.1); the evaluation corpus, holdout split and adjudication themselves (08.8.1, 08.8.1-T3); the per-project shadow window and its `drift_shadow_window.metrics` (13.8.1-T4); the stability check and the script states (13.5.1-T4); authoring CRUD, import/export and coverage (13.1.1); dashboards, charts and any screen (none here — the read is an operator JSON route, and a rendered view is not in this story's rows); any tenant-facing route (there is none: no tenant may read a cross-tenant aggregate); every new permission string, error code, 00 §9.3 row and `plans/13-product-phases.md` edit; any change to an estimate or to the §4.3 table.

**Prior art (owner rule, 2026-10-27; approach only).** (1) *DORA-style metric definitions* (`https://dora.dev/guides/dora-metrics-four-keys/`, read 2026-11-11 ⚠️ — a documentation page, not a normative spec): taken — one written definition per metric with an explicit numerator, denominator and window, and the rule that a definition change is a new measurement rather than an edited history; deliberately not followed — its performance-band labels, because plan 13's §4.3 bars are the only thresholds this product has. (2) *`pg_stat_statements`-style cumulative counters* (PostgreSQL documentation ⚠️ general knowledge, not re-read here): taken — the instinct that a metric row is an immutable observation with a timestamp, so a recompute appends; deliberately not followed — cumulative-since-start counters, because a gate needs a **period** to be comparable. (3) The repository's own two precedents are the primary source and win over both: `platform_sweep_audit` (`0088`) for the platform-scope table and its one-writer posture, and `evidgate.usage_ledger_org_ids` (`0076:126-146`) for the org enumerator a cross-tenant read needs.

## 2. User stories and acceptance criteria

- As the owner, I open one read and see each §4.3 gate's numbers with their window, their numerator and denominator, and a plain `null` plus a reason where the platform has not measured enough yet — so a phase decision cites data, not an impression.
- As the Tech Lead, I can tell whether "3 of 3 without manual edits" was actually met, because the report names the build identity and says how many merged PRs carried a commit other than the generated one.
- As a data owner, I can confirm that nothing on that read identifies my tenant: the snapshot holds counts and rates, and no route returns a per-tenant row.

## 4. Data model and migrations

One new table, one migration. The number is "next free number at build time" (the tree ends at `0097_identity_membership_role_fk.sql` on this base, so the lane re-checks before it creates the file); this plan names no number.

**`gate_metric_snapshot`** — one immutable observation of one metric over one period.

| Column | Rule |
|---|---|
| `id` | `uuid` UUIDv7, app-generated, primary key |
| `gate` | `text check (gate in ('g1','g2','g3'))` |
| `metric` | `text check` against the **closed v1 vocabulary** (§4.3-derived): `g1_active_teams`, `g1_teams_three_weeks`, `g1_weekly_return`, `g1_usage_share`, `g1_exports`, `g1_cost_per_ai_action`, `g2_three_of_three_share`, `g3_drift_class_precision`, `g3_proposal_acceptance_rate`, `g3_false_repair_rate`, `g3_adjudicated_false_repairs` |
| `period_start`, `period_end` | `date not null`, half-open ISO week/month as the metric's definition states; `check (period_start <= period_end)` |
| `numerator`, `denominator` | `numeric null` — the two numbers the definition divides, published so a reader can re-derive `value`; `null` where the metric is a count |
| `value` | `numeric null` — the metric; `null` with a reason rather than `0` (AC2, T60) |
| `unavailable_reason` | `text null`, closed: `insufficient_sample`, `incomplete_cost`, `export_not_recorded`, `not_computed`, `corpus_unbuilt`, `adjudication_missing`, `threshold_owner_decision_open` |
| `sample_counts` | `jsonb` ≤ 4 KiB: the per-clause counts (`teams`, `teams_returning`, `weeks`, `no_call_actions`, `unmetered_calls`, `commits_in_merged_pr`, `within_300_floor`, `unknown_class`, `overrides`, `rule_of_three_bound`), each a bounded integer or a closed string — never a free-text note and never an id |
| `metric_version` | `int not null check (metric_version >= 1)`; v1 is the set written down here, and a definition change bumps it instead of editing rows (§1, §6) |
| `computed_at` | `timestamptz not null default now()` |
| `recorded_by` | `text not null check (recorded_by in ('gate_metrics_snapshot'))` — stamped inside the writer, never accepted from the caller |

**Why it is one table and not eleven.** Every metric has the same five facts (period, numerator, denominator, value-or-reason, version); eleven tables would multiply the policies, the grants and the guard by eleven, and a metric added later would need a migration and a policy review for a row shape that has not changed. The closed `metric` enum is the gate.

**Constraints, indexes, append-only.** `unique` is deliberately **not** on `(gate, metric, period)`: a recomputation is a new measurement with a new `computed_at` (the "re-running the matrix is a fresh measurement" rule 13.7.1 states for its own rows), and the read takes the newest row per metric; an edit history that cannot be rewritten is the point. Indexes: `(gate, metric, computed_at desc)` for the read and `(period_end desc, computed_at desc)` for the retention sweep. A guard trigger refuses UPDATE and DELETE with `23514` and TRUNCATE is revoked for every runtime role (the `0088:74-95` shape).

**Row level security and grants.** ENABLE + FORCE; `for insert to evidgate_owner with check (true)` and `for select to evidgate_owner using (true)` — the two policies the owner-owned definers need under FORCE, exactly as `0088:97-111` explains. **No runtime role holds a table privilege and no policy names one:** `revoke all` from `public`, `evidgate_app`, `evidgate_operator` and `evidgate_worker_sched`. **The `grant select` + no-policy posture is deliberately not copied from 0088** `[DECISION]`, and 0088 says why in as many words: "the grant is in place and the operator reads zero rows until 02.8.1's operator scope lands" (`0088:33-36`, the same note `0052:196-199` carries for `healing_switch`). This story's acceptance is "readable by the operator" **now**, so that grant would be a dead privilege that makes both routes answer `[]` forever — the letter of AC1/AC8 with none of its purpose. The read is a definer (§ "The three definers" below) and **no `TO evidgate_operator` policy is written**, so there is also nothing for `OPERATOR_GATE_EXEMPT` (`scripts/check-rls.py:226`) to judge: that list accepts one operator predicate on a tenant column, and this table has no tenant column.

**The three definers.** (1) `evidgate.gate_metric_org_ids(p_from date, p_to date, p_after uuid, p_limit integer) returns setof uuid` — `SECURITY DEFINER`, owner-owned, `set search_path = ''`, keyset over `(org_id)` for the orgs with any in-scope activity in the window; the caller's only input is the window and the cursor, and the return is org handles, never business rows (the shape `evidgate.usage_ledger_org_ids` already uses, `0076:126-146`). `EXECUTE` to `evidgate_worker_sched` only. (2) `evidgate.record_gate_metric_snapshot(...)` — `SECURITY DEFINER`, stamps `recorded_by = 'gate_metrics_snapshot'` and `computed_at`, inserts one row, returns the new id. Its `EXECUTE` goes to **`evidgate_worker_sched` only**, because the job's write is a platform write and `evidgate_app` must stay outside this table entirely (AC1); the job therefore holds two connections' worth of work — a tenant-scoped read leg and a schedule-scoped write leg — exactly as `evidgate.usage_ledger_org_ids` + the rollup task already split theirs (`12.3.1-T1`/`T5`). (3) **`evidgate.read_gate_metric_snapshots(p_gate text, p_metric text, p_from date, p_to date, p_latest_only boolean, p_after_ts timestamptz, p_after_id uuid, p_limit integer) returns setof public.gate_metric_snapshot`** — `SECURITY DEFINER`, owner-owned, `set search_path = ''`, **the only read path in the system**: it validates `p_gate` against the closed enum and `p_metric` against the vocabulary, clamps `p_limit` to 1–200, filters `period_end` by the date range and, when `p_latest_only`, returns one row per `metric` by `computed_at desc` (`distinct on (metric)` inside the function, so route 2 is not a read-path aggregate). `EXECUTE` to **`evidgate_app` only** — the role every request path already runs as (`UsageLedgerReader` reads inside `ITenantScopeFactory`, `src/Modules/Evidgate.Modules.Usage/Application/Queries/UsageLedgerRead.cs:85-115`, and no runtime code anywhere in `src/` connects as `evidgate_operator`). The function returns aggregate rows that carry no tenant dimension, so the grant cannot hand a caller a tenant row; the residual risk is that any app-role code path could call it, which is bounded by an `Architecture.Tests` call-graph rule naming the gate-metrics reader as the definer's only caller and by AC8's seeded, non-empty route test.

**Why the aggregation is per-org then merged, not one owner-wide `select`.** A single definer `select ... from authoring_version, generated_script, drift_shadow_window` across every tenant would need the house `_owner_backfill` policy on each table (`0046:141`, `0054:269` — present today) and would put business logic for four modules into one SQL body. The org-enumerator shape keeps every read inside the **app** role's own tenant scope (`ITenantScope`, the rollup precedent), where the RLS policy is the one that already governs that table, and leaves only aggregates to cross the boundary — which is also why the platform table can hold no tenant row.

**Retention and deletion.** Snapshots carry counts, not tenant data, so tenant or project erasure has nothing here to remove and does not touch the table (stated once, in §8). The table itself is bounded by a retention sweep that keeps the newest **24** months of rows per `(gate, metric)` (`[INFERENCE]`, one row per period per gate, so ~120 rows in total) and runs as the owner through 08.1.2-T2's hook set rather than a second scheduler; until the sweep exists the bound is a documented owner purge, never a silent `delete` by the app role.

**What this story must not store.** No `org_id`, `project_id`, `case_revision_id`, `script_id`, `incident_id`, `run_id`, `membership_id`, `email`, `name`, `code`, selector, URL, prompt, output or cost line item; no per-tenant row anywhere, even transiently on disk. The strongest guarantee is structural: the insert path has no column that could carry one (AC1).

## 6. States and transitions

**This story owns no state machine.** A snapshot row is an immutable observation: it is inserted once and is never updated, superseded or deleted by a runtime role (§4), so there is no `draft → final` or `open → closed` edge to write down. A recomputation **appends** a newer row for the same `(gate, metric, period)`, and the read resolves "the latest" by `computed_at`; an older row stays readable, which is what makes a changed definition or a late-arriving corpus auditable.

**The one lifecycle-like rule, stated so nobody invents a state column.** A **period** is either open or closed *in the calendar*, not in a row: the job computes the last closed period on every fire, and a metric whose sources can still change — the G3 corpus, a late adjudication — is reported twice (two `computed_at` values) rather than mutated. `metric_version` is the only "state" of a definition: v1 is what this plan writes down, and a change bumps it, so a row is always read with the definitions it was computed under.

**The job's own runs** have `queued | running | succeeded | failed` and a dead-letter path, but that is the task queue's mechanism (`00 §5.3`, the `task` table), inherited and not re-declared here; a failed run writes no snapshot and leaves the previous row as the answer.

**No consumer state.** 08.8.3's V2/V3 gate results (`healing_phase_gate_result`) are that story's rows and are untouched; nothing in this story reads or writes a gate result, and no consumer of this report is blocked by a state.

## 7. Jobs and integrations

## 8. Security, privacy and performance

- **Authorization:** two operator-ingress routes, admitted by `RequireOperatorFilter`/`IOperatorGate` and by nothing else — "the `billing:read`/`billing:write` semantics therefore ride on `IOperatorGate`, which is what admits the request before any handler runs" is the shipped comment this story follows for its own surface (`UsageOperatorEndpoints.cs:21-27`), and `platform_operator` is the principal 00 §9.3 (`:333`) names. **No `to evidgate_operator` policy is written and `OPERATOR_GATE_EXEMPT` is not used** (`scripts/check-rls.py:226`): the table has no tenant column, so there is no operator predicate to judge. **The read path is `evidgate.read_gate_metric_snapshots`, a `SECURITY DEFINER` reader `EXECUTE`d by the ingress role, and not a table grant** — the 0088 grant-gated posture is rejected on 0088's own evidence that it reads zero rows (`0088:33-36`), so a route under it would answer `[]` forever and "readable by the operator" would be false (AC8 proves both directions: two seeded rows come back through the route, and a direct `select` as `evidgate_app` is refused). The definer returns aggregate rows with no tenant dimension and takes no parameter that names a tenant, and an `Architecture.Tests` call-graph rule keeps its only caller the gate-metrics reader. **No support grant is involved and none may be implied:** 00 §9.3 describes operator actions that read tenant rows, and this route reads none; a per-tenant drill-down is a non-goal of V1 precisely because it would need the 02.8.1 grant and an attributed audit row. No tenant principal holds any code, route or table privilege here.
- **Retention/deletion:** snapshots are counts and rates with a period, a `metric_version` and a timestamp; they hold no tenant data, so tenant, project or case deletion has nothing here to remove and the table is untouched by an erasure (contrast the org-scoped rows it summarises, whose own retention is 13.1.1's, 13.5.1's, 13.8.1's and 08.1.2-T2's). The table itself is bounded at the newest 24 months per `(gate, metric)` (`[INFERENCE]`) by an owner purge inside 08.1.2-T2's hook set; rows are append-only for every runtime role, and the migration's rollback note drops the table, all three definers and the `rls-exceptions.txt` row in one change.
- **Telemetry:** counters only — `gate_metric_snapshot_written_total{gate,metric,state}` and `gate_metric_read_total{gate}` — no span label, log line or metric label carries an org, project, case, script or incident id, a name, a code, an email, a selector or a URL. One audit-shaped record exists and it is the row itself: `recorded_by` is stamped inside the definer, so a snapshot cannot be attributed to a caller who did not compute it. There is **no `audit_log` row for a gate-metrics read**: `audit_log.org_id` is NOT NULL and hash-chained per org (`0015:25-54`), and a cross-tenant aggregate has no org to name — the gap is `OI-13-579`, and until it is decided the read is attested by `gate_metric_read_total` and by the operator ingress's own request-level attributions, never by a fabricated per-org row.
- **Failure path:** a metric that cannot be sourced is `value: null` with a closed `unavailable_reason`, never `0` and never an omitted row, so a reader can never mistake "not measured" for "measured and bad" (T60; §4.3's G3 caveat is the same discipline). A job failure writes no snapshot, leaves the previous row as the answer, retries through the task queue with its dead-letter path, and increments the written-counter's `state = failed` variant; a source that is unbuilt (`08.8.1-T3`'s corpus, `08.8.2-T2`'s definition) produces `corpus_unbuilt`/`adjudication_missing`, not a guess. On the route, a bad filter is `422`, an unmeasured gate is `200` with an empty list, and a reader can always see `computed_at` — stale data is visible as stale, never presented as current.
