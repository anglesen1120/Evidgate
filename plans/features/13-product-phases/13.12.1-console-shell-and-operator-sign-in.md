## 1. Goal and non-goals

**P1 · G1 · FR-13-14.** An explicitly provisioned Evidgate staff member signs in to the operator origin with workforce MFA, can see which platform settings are current, and can trace a change to its author and previous revision. Changing a setting does not require restarting its consumers. Staff cannot retrieve a stored secret, even if they entered it themselves.

This story delivers the design for the whole console, the staff authentication boundary, the shared publication contract, and the Angular shell and history screens. The AI, customer sign-in/mail, plans/quotas, tenant operations and runner stories own their typed settings, validation and domain-specific enforcement. The shell is neither a tenant impersonation tool nor a generic editor for environment variables or arbitrary secret names. No changes here to customer sign-in, grants, billing authority or incident runbooks.

## 4. Data model and migrations

| Logical record | Fields and constraints |
|---|---|
| Operator provisioning and session | Bind a provisioned active staff actor to the verified workforce `(issuer, subject)`; session references that actor, verified MFA context/time, expiry and revocation. Use the plan 02 server-side session primitives with a distinct operator scheme and credential namespace. A tenant session row or cookie is never convertible into an operator session. |
| `platform_setting_revision` | Immutable per setting group: revision ID, predecessor ID, typed schema version, previous and new canonical nonsecret snapshots (or opaque version references for secret slots), before/after hashes, actor, UTC timestamp and request ID. Reject unregistered fields/groups. Constrain predecessor and revision to the same group; no update/delete permission for application principals. The hash input contains no secret bytes or secret-derived digest. |
| `platform_setting_current` | One row per registered setting group, with a group-bound foreign key to its active revision. Bootstrap a documented safe baseline with explicit system provenance, using an unconfigured/disabled state where no valid value exists. The initial read has a concrete ETag so even the first operator edit is conditional. Never manufacture a secret or an enabled provider as a default. |
| Audit and delivery | Link exactly one successful platform audit event to each publish. In the same transaction append the revision and audit, move the current pointer and persist a durable change notice (group and revision ID only). Index history by group and revision order for cursor paging. No tenant-config table doubles as the platform store. |

Migrations grant the operator command path only the rights needed to publish; registered runtime consumers read their own effective settings, not history for all groups or the capability to change them. A privileged migration is not a runtime identity. Do not reserve a migration number in the plan.

## 5. API shapes (commands, queries, endpoints)

All routes below are relative to `/internal/operator/` on the operator origin. Route names describe this story's contract; settings screens call their own domain commands, not a generic privileged JSON or secret-store proxy.

| Operation | Contract |
|---|---|
| `auth/login`, `auth/callback`, `session`, `auth/logout` | Start the workforce authorization-code flow with PKCE and one-use state/nonce; validate the signed response, issuer, audience, expiry, MFA context and active provisioning before issuing a new session ID. Accept only registered same-origin return locations. Return minimal actor/expiry information, never provider tokens. Logout is a protected POST and revokes the server record. |
| `GET settings/{group}` | Authenticated read returns the typed nonsecret values, revision ID, configured/rotation metadata for credential slots, and a strong `ETag` bound to the current group revision. Do not expose a secret ref usable as a retrieval capability. Return `Cache-Control: no-store` for session and settings/history responses. |
| `GET settings/{group}/history` | Cursor-paged, deterministic newest-first summaries with revision/predecessor, actor, timestamp, nonsecret before/after values and hashes. Secret fields show that they changed and when, never their value, storage locator or revertable browser token. Do not return a tenant payload or multipart request body. |
| Typed publish command | Require a concrete `If-Match` from the group read and antiforgery proof. Missing precondition → 428; mismatched current revision → 412 with current ID/ETag; invalid typed settings → validation refusal. On success return only the committed revision and new ETag. Refuse wildcard/unconditional edits. Keep the winner when equal preconditions race. |

Use an operator-specific host-only `__Host-` session cookie (`Secure`, `HttpOnly`, `Path=/`, no `Domain`), SameSite policy compatible with the registered OIDC callback, and separate ASP.NET authentication/protection purposes from the tenant app. Apply plan 02's same-origin antiforgery cookie/header pair to authenticated mutations (including logout); validate OIDC state/nonce on the callback instead. Enforce absolute/idle expiry server-side and rotate on login and entitlement change. Browser-side expiry banners are not authorization.

## 6. States and transitions

- **Signed out → workforce challenge → verified staff session:** an invalid callback, insufficient MFA, unknown subject, disabled operator or expired challenge stops before session issuance. Revocation, logout or expiry invalidates the session on the next request, regardless of an open console tab.
- **Current R → candidate → current R+1:** authorize first, validate the candidate and any staged secret against the typed group's rules. Lock/compare the current pointer and require the submitted strong ETag still matches. Append revision and audit, update the pointer and record delivery in one database transaction. No success response before commit; no partial writes on failure. Restore an earlier nonsecret configuration by publishing a **new** validated revision against the current ETag, never by editing history.
- **Credential rotation:** the command takes write-only material over TLS, stages a fresh version under a server-selected secret slot, validates it, then publishes only its opaque version reference. Vault operations are not part of the SQL transaction: a losing or failed publish leaves the old reference active. Retire unreferenced staged versions via 10.7.1-T4, checking active references before retirement; do not release the old working version prematurely. A blank/omitted secret field means keep the existing version, not clear or rotate it.
- **Applied vs committed:** each consumer identifies its loaded revision separately from the current pointer. A duplicate, missed or out-of-order notification cannot make it regress. An application failure preserves the last validated snapshot and raises an alert; when freshness is required to authorize work, refuse that work until the current revision is available rather than use stale permission or limit data.

## 7. Jobs and integrations

10.1.1-T2's `ISecretProvider.GetSecretAsync(name)` is read-only. Add a distinct, least-privileged **server-side** capability to stage/write, rotate and retire versioned secrets. Use a durable deployment secret store that can resolve a specific version without process restart. Runtime consumers only resolve the slots/versions they need. Do not turn the existing environment-injection path (D-A2) into a writable file, put plaintext in SQL or require an environment refresh. OI-13-822 names the pilot adapter/provisioning decision for dynamically managed console secrets, not a wholesale replacement of bootstrap secrets.

A committed change notice wakes consumers to read the authoritative pointer and load the entire validated revision, including secret resolution where required. Replace each local snapshot atomically, never field by field. On startup, notification loss or reconnect, reconcile against the current pointer. For the next operation whose behavior depends on the setting, check the effective revision before admission/use; notifications alone are not proof that every process has applied the change. Only registered business consumers read values; notices and operational metrics carry no payloads.

The T1 `design-ui` deliverable covers (1) shell, workforce sign-in/MFA, session and current/history; (2) AI provider/model, credential, cap and kill; (3) customer OIDC, magic-link default and mail; (4) plans, quotas and assignments; (5) tenant directory, usage, grants and deletion status; (6) runner limits and allowed images. For each, identify data, authorized actions, default/loading/empty/error/success and refusal/stale/expired-session states. Include credential entry, configured/last-rotated feedback, keyboard/focus and screen-reader behavior, vi + en, narrow/wide and light/dark, using 09.10.1 tokens/components and WCAG 2.2 AA. The owner approves the artifact before **any** screen build. T4 owns only the shell/sign-in/history implementation, not the other stories' controls.

## 8. Security, privacy and performance

- **Authorization:** enforce the operator ingress, live MFA-backed staff session and explicit provisioning on every protected read/write; apply antiforgery to mutations. Do not trust a Host or forwarded identity header as proof of staff identity. An operator is not a standing tenant administrator; grant-bound reads and writes use plan 02's grant ID and audit. No generic config path can route around domain approvals.
- **Retention/deletion:** bound session/challenge lifetime per plan 02 and invalidate on revocation. Keep immutable redacted history/audit under the platform audit retention policy. Retire orphaned and superseded secret versions on the 10.7.1-T4 rotation schedule; discard submitted credential material on success, refusal, conflict, navigation and session expiry. Do not persist it in browser storage, caches or diagnostics.
- **Telemetry:** record request ID and bounded outcome/reason, publish/apply counts, revision lag and refresh failures; keep actor/time and redacted before/after hashes in authorized audit. No tokens, cookies, secret-derived hashes, raw inputs, bodies, vault locators or provider error payloads in logs, traces, browser diagnostics or history exports.
- **Failure path:** deny on unverified MFA, wrong ingress, expired session, failed antiforgery, failed validation, unavailable store or audit write failure. Do not switch current revision on pre-commit failure. After commit, distinguish consumer convergence failure from a rolled-back publish; alert, re-read current, and fail closed for freshness-sensitive work. Never automatically replay a rejected mutation from a browser draft.

Page history with a bounded cursor/limit; avoid reading the whole revision stream on the settings hot path. Validate staged credentials before taking a pointer lock. The short DB transaction performs the precondition check, revision, audit, pointer and delivery writes; no external call while holding its lock.

## 11. Rollout

1. Obtain the T1 design approval and establish the workforce registration/MFA policy. Release T2 on the operator host; keep public routing unchanged. Hand the verified identity to the plan 02 grant remainder.
2. Bootstrap safe baseline revisions, provision the limited vault identities, prove rotation and exercise a publish/rollback on the pilot deployment. Do not expose editable credentials against an env-only or fake backend. Record the committed and applied revision separately during rollout.
3. Enable the Angular shell/history only after the operator path and grant integration pass the §9 checks. Add the other screens as their domain stories land; do not display a successful save for unsupported settings. If a bad revision must be withdrawn, publish a validated replacement with a fresh precondition; if the operator surface is unsafe, close its ingress and revoke its sessions, retaining audit history.
