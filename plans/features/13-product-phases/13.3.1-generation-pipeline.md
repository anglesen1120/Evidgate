## 1. Goal and non-goals

**Goal.** Turn requirement input into reviewed authoring content through one governed path. A requirement arrives as text, as a DOCX/PDF whose text is extracted under hard caps, or as an image stored as an artifact; the pipeline then produces a **prioritised checklist** and, from selected checklist items, **manual test cases**, plus `rebuild` and `translate` actions on existing drafts. Every call runs through the 08.5.1 gateway with 08.5.3 redaction and per-tenant opt-in and 08.5.5 credits; output is validated against a platform JSON schema before anything is written; the platform records provenance (`AiSettingsRef`, `RoleProfileRef`, prompt/schema/model versions) and a cost per action; and the author accepts drafts explicitly.

**Area-plan acceptance.** Requirement text, documents or images produce a prioritised checklist and then test cases through the gateway with redaction, opt-in and credits; output is schema-validated; provenance and cost are stored per action (`plans/13-product-phases.md:161`).

**Partial against that acceptance (owner decision `OI-13-402`).** Plan 13's line reads "requirement text, documents **or images** produce a prioritised checklist"; G1 delivers text and DOCX/PDF-extracted text end to end, while an image is stored as an artifact and shown next to the draft as a human reference and its bytes are **never** sent to a provider (AC4). Image bytes cannot pass `IRedactionPipeline` and 08.5.3's opt-in has no multimodal form, so "images produce a checklist" is **not** delivered by this story: it is `OI-13-402`, an owner decision with the same story recorded as the receiver for the later multimodal story that closes the gap. Until then this story claims text and document input only, and no section of this plan may be read as delivering image generation.

**Phase (CR-D-2).** G1. This story is the only story in the area plan whose tasks are consumed by the G1 critical chain: `06.1.2-T1 → 06.1.2-T3 → 13.3.1-T1 → 13.3.1-T2 → 13.3.1-T3 → 13.2.2-T2 → 13.2.2-T5 → 13.2.2-T6` (`plans/features/README.md:276`).

**Non-goals.** Generating Playwright scripts (13.5.1), element profiles (13.6.1), drift repair (13.8.x); the authoring UI and the generation screen (13.4.1-T4 consumes this story's routes); project AI settings authoring (13.2.1) and role-profile authoring (13.2.2); the gateway itself, its provider adapter, its budget hard stop and its metering (08.5.1); the credit ledger and its administration routes (08.5.5); redaction rules, the opt-in request/approve flow (08.5.3); the artifact upload protocol (06.1.2).

Also out of scope: parser hardening in a resource-limited child process, per-tenant parse concurrency and the hostile-input suite (06.3.1, 06.3.6 — both **G2**, `plans/06-evidence-artifacts.md:193-194`, `:221-223`); `test_plan` and `integration_scenario` output kinds (OI-13-305); billing, pricing and the G2 credit offer (12.4.1); and any model name, provider choice or cost value in code.

## 2. User stories and acceptance criteria

- As a QA engineer, I paste a requirement or upload a specification document and get a prioritised checklist draft I can edit and accept.
- As a QA engineer, I select checklist items and get draft manual test cases with steps I can review; I can rebuild a weak draft and translate drafts into another project language.
- As a tenant admin, I see what each AI action cost, which settings version and role profile produced it, and I can prove that nothing was sent when the tenant had not opted in or had run out of credits.
- As the platform, I never trust a document, an image or model output: extraction runs under fixed caps, output is schema-validated, and a failure leaves no partial authoring content.

Every criterion has a named proof in §9. Numeric defaults marked `[INFERENCE]` are build defaults pending OI-13-403, not measured product facts.

## 6. States and transitions

`authoring_intake`: `[*] → received → extracting → ready | rejected`; `rejected` is terminal (a new intake is a new row, never a repair); a stuck `extracting` is re-driven by the same idempotent task (at-least-once, one terminal write); `ready` is terminal for editing but the row is purged with the project (AC27). Inline text intakes take `received → ready` in one request when the text passes validation; the job path is the same command.

`authoring_generation`: `[*] → queued → running → succeeded | failed | blocked | canceled`. `queued → canceled` and `running → canceled` are the only cancel edges (AC21); `blocked` is reserved for pre-send refusals that happen inside the job (leak, opt-in revoked between preflight and dispatch, kill switch, a credit reserve refused before any transport — AC22), while preflight refusals in the request write **no** generation row and return an HTTP error. A `blocked` row that never obtained a `healing_llm_call` row keeps `ai_run_id` null and pins on its own ref snapshots (AC20, OI-13-412). `succeeded` is terminal for the call even if the later accept is partial. No retry edge exists: a retry is a new generation row bound to the same idempotency key only when it is the same request, and a `rebuild` action otherwise.

Draft publishing (owned here, executed by the writer): `checklist_item` `draft → active` and `manual_test_case` `draft → approved` on accept; `draft → retired` on discard/rebuild supersession with a reason. `13.1.2`'s apply never flips a state (`…13.1.1…:298`, `13.1.2-AC…`/OI-13-126), so this accept step is the single flip owner; a human may still flip through 13.1.1 route 9/17.

Cache rows have no state: a row either exists for a key (hit) or it does not. `hits`/`last_hit_at` are counters, not transitions.

Progress: `authoring_generation.progress.stage` is closed and monotonic — `queued → redact → generate → validate` (`redact` covers the envelope build plus the in-adapter `IRedactionPipeline` pass, `generate` the provider call including its one retry, `validate` the Corvus check and the draft write) — with `eta_class ∈ {short, long}` (the single vocabulary AC5 uses for the intake read too: `short` = expected within 60 s, `long` = otherwise, `[INFERENCE]`) and no percentage, ever. A screen's end-to-end strip is composed from the linked intake row's `state` (`received`/`extracting`/`ready`) followed by these stages; no client derives a stage the row does not have, and a client never maps `state` into `eta_class` or the reverse.

## 7. Jobs and integrations

- **Outbox tasks** written in the creating transaction (C7): `authoring_intake_extract {intake_id}` (AC5) and `authoring_generation_run {generation_id}` (dispatch). Both are idempotent on their row id and their terminal write is guarded by `where state = <expected>`, so a duplicate delivery is a no-op.
- **Concurrency:** extraction and generation each take a per-tenant slot from the existing task queue configuration; the queue's per-tenant cap (the 06.3.6-T2 shape, arriving in G2) is configured now through `ITenantLimits`, so the G1 default is a bounded value rather than unbounded parallelism (OI-13-403).

**Trust boundaries and five abuse cases.** Browser/client → intake validation/RLS → immutable artifact + capped extraction → provenance pin → redaction and prompt envelope → external provider → schema validator → drafts → human accept. (1) A hostile document (zip bomb, macro, external reference, entity expansion, encrypted PDF) is refused before parse or dies under the cap (AC2/AC3). (2) A foreign-org or sibling-project id is stopped by scope/RLS/composite FKs (AC23).

(3) Prompt text inside the requirement cannot change the schema, priority mapping or permissions (AC11 + `AuthoringGenerationInjectionTests`). (4) An image cannot silently become an egress path (AC4). (5) A credit/opt-in/leak refusal cannot leave a debit, a partial draft or a provider send (AC7/AC19/AC22). The model is never the enforcement authority.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** `POST intakes`, `POST generations/estimate`, `POST generations` and `cancel` require `authoring:generate`; `GET intakes/{i}`, `GET generations`, `GET generations/{g}` require `authoring:read`; `accept` requires `authoring:write`. All three codes already exist (13.1.1-T2.1); no new permission is seeded, no role-profile selection grants anything, and permission evaluation never reads request text. Foreign org/project ids are `404`; a scoped credential addressing a sibling project is `403 project_scope_mismatch`; unset tenant GUC yields zero rows; handler permission equals `x-permission` on every operation (T51).
- **Retention/deletion:** intake text and extracted text, generation rows and cache rows are project content erased with the project/tenant by 06.4.4-T1 through the owner purge path (app role keeps `REVOKE DELETE`); cache rows never survive their project, so a purged project cannot be revived by a cache hit; artifacts follow 06.2.1/06.4.1 sensitivity and retention rules; audit rows follow 11.5.1 and carry no text; `authoring_version` stays append-only (13.1.1-AC6) and a generation row is immutable in its identity columns.
- **Personal data:** requirement and extracted text are tenant content and may contain personal data; they are redacted by 08.5.3 before egress, stored protected under RLS, never logged or metered by content, and erased with the project. `run_note` is NFC, ≤ 500 code points, redacted before persistence and attached to one generation only (13.2.2's rule). No image byte leaves Evidgate in G1 (AC4). DECISIONS §7 and 08.5.3 opt-in/transfer controls apply unchanged.
- **Telemetry:** audit exactly one entry per generation batch, accept and cancel, with ids, action, tier, state, outcome, cost and hashes — never text. Counters use closed labels: `authoring_generation_total{action,state,outcome_code,tier}`, `authoring_intake_total{kind,state,failure_code}`, `authoring_extraction_seconds{kind}` histogram, `authoring_generation_cost_micro{action}` histogram. No requirement id, tenant prose, profile name or free-text reason in a metric label; per-action cost by project is an authorized aggregate over `authoring_generation`, not a metric label.
- **Failure path:** preflight refusals return `ai_credit_exhausted` (status class per 08.5.5, whose 402-class mapping is still `[OPEN]` at `08.5.5…:33`), `403 healing_provider_not_approved`, `503 healing_unavailable`, `422 request_invalid`/`413 payload_too_large` and write no row, no reserve and no send. In-job failures land on the row as `outcome_code` = the seven `healing_llm_call.status` values copied verbatim (`ok`, `timeout`, `schema_violation`, `budget_exceeded`, `error`, `blocked_no_optin`, `blocked_leak`) or one of the three generation-only values that exist because no call row can (`cache_hit`, `blocked_kill_switch`, `canceled`) — ten values in total, the same vocabulary §4 and 13.4.1 use — with the internal code in `error.code` (AC22's mapping) plus exactly one refund or settle by the gateway, and the detail route shows both. Sends are per AC22's two families: zero before dispatch, one per attempt after it (at most two, the single bounded retry), and never a second call. Internal codes never appear as a `/v1` error (`08.5.1…:53`); the client-facing codes are the envelope ones in §3. Stale accept is `412 precondition_failed` with current versions; a wrong-state target is `409 invalid_transition`; a missing idempotency key is `400` and a replay conflict is `409`.
  - **Extraction refusals are two different surfaces, not one HTTP answer.** A refusal raised **in the request**, before `201` — an unknown/unsupported media type, empty text, a declared byte count above the cap — is `422 request_invalid` with `details[].path` and `details[].reason ∈ {empty_input, media_type_not_allowed, size_limit_exceeded}` (or `413`), and writes nothing. Once `POST intakes` has answered `201`, extraction failures are **not** HTTP errors: the job writes `rejected` + `failure_code` on the intake row, and that row is what `GET /intakes/{i}` returns, what `authoring_intake_total{kind,state,failure_code}` counts and what 13.4.1 renders — there is no later 422 to observe. The closed `failure_code` set has ten values: `container_mismatch`, `macro_present`, `encryption_unsupported`, `external_reference_present`, `archive_limit_exceeded`, `page_limit_exceeded`, `char_limit_exceeded`, `no_extractable_text`, `extraction_timeout`, `extraction_failed`. One token per condition: `unsupported_media_type` is **not** a `failure_code` (the request-time `media_type_not_allowed` reason owns that condition), and a declared type that disagrees with the sniffed container is `container_mismatch`.
