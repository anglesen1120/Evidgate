## 1. Goal and non-goals

**Goal.** Ship the G1 authoring workspace in `apps/web` on the existing shell: a feature tree with a dense, filterable manual-case table; the manual test case editor with an immutable timeline; the pending-changes panel that applies one batch with `If-Match`; the credit-aware generation flow; the project AI-settings and import/export screens; a sidebar regrouped by product phase in which later-phase entries are **hidden and unmatched**; and the AI credit balance and usage-by-action region on the usage page. Every screen is vi + en, WCAG 2.2 AA, zoneless/signal-based, consumes only the generated SDK, and renders server text as text.

**Area-plan acceptance:** an approved design (`design-ui` agent) precedes build; tree, table with filters, test case editor, batched changes panel, generation flow, timeline, settings and export work in vi + en and meet WCAG 2.2 AA; the navigation hides items of a later phase and the usage page shows the AI credit balance and usage by action.

**Phase (CR-D-2).** G1 only. Servers, memory and repair screens are G2–G3 (13.5–13.8) and are not designed here; the sidebar already encodes that (`apps/web/src/app/shell/nav/nav-registry.ts:123-221`).

**Non-goals.** Any backend route, migration, table or command — this story adds **none** (a missing read shape is an `[OPEN]` handed to its owning plan, §5.3). Implementing 13.1.1, 13.1.2, 13.2.1, 13.2.2 or 13.3.1 behaviour: the screens call their routes and render their answers. The role-profile editor itself (13.2.2-T6) — this story designs the selector and the editor in T1 (plan 13 `:182`) and leaves the implementation to 13.2.2. Quota, retention and storage regions of the usage page (09.7.1-T5, G2) and the quota warning badge (09.7.1-T11). Release verdicts, script/run routes, repair apply buttons, mobile UI, a client-side phase switch, optimistic caching/sync or any invented credit price (`00-delta-brief.md:100-104`).

## 2. User stories and acceptance criteria

- As a QA author, I browse the project's hierarchy, filter manual cases by priority, status, source, coverage and owner, and open one case — without the page losing my filters when I come back.
- As a QA author, I edit a case and save a new immutable version; when someone else saved first, I keep my draft and see exactly what changed.
- As a reviewer, I queue comments, merges, splits and deletes and apply the whole queue as one version — or, when the batch moved, as nothing at all.
- As a BA, I take a requirement through an estimate I can see, an explicit confirmation, honest progress, a reviewable checklist and test cases I approve one by one.
- As a project admin, I change AI settings as a new version and see which version a past case was generated with.
- As a limited-grant user, I see every screen that my permissions allow, with the actions I lack explained rather than silently missing.

### 5.2 Shapes the screens rely on

- **Keyset paging everywhere** (W4/W7): the store keeps `next_cursor` and the rows it already showed; a repeated cursor is a thrown contract violation rendered as a failure, the same refusal as `features/settings/audit/audit.store.ts:13-23`.
- **Path prefix is not a screen decision.** Every path in §5.1 is relative to the authoring group; whether it is the shipped `/v1/projects/{p}/authoring/…` (13.1.1 §5) or the org-nested `/v1/orgs/{o}/projects/{p}/authoring/…` is `OI-13-410`, whose recommendation is the shipped group (`13.3.1-generation-pipeline.md:149,355`). The screens call generated SDK operations and never build a path string, so the choice changes no page or store code.
- **The 202 body is the preflight's own receipt:** `POST …/generations` answers `{generation_id, state, model_tier, cache_hit, credit_estimate_micro}` and reserves nothing (`13.3.1-generation-pipeline.md:156`); the store keeps `credit_estimate_micro` beside the confirmed estimate, and `post` is a POST-redirect-to-detail: the detail read is the only source of truth afterwards.
- **`If-Match` sources:** case `ETag` from route 14; batch etag from `GET changes?ids=…` (`13.1.2:336`); settings `version_no` (`13.2.1:185`); role profile `"N"` (`13.2.2:201`); generation row `ETag` on accept (`13.3.1:160`). A missing tag is the server's 422, never a client-side 428.
- **412 `details[]` are pointers, not snapshots:** `{index?, path?, reason?}` with the current revision identifier in `reason` (`packages/sdk/src/errors.ts:12-13`). `conflictFromError` today matches only the bare names `revision_id`, `version`, `order` (`apps/web/src/app/shared/ui/conflict/conflict-details.ts:27-31`), while the authoring routes answer the pointer form `/version` and `/order` (`STATUS.md:660`). T3 widens that match and adds the spec case; it keeps the bare-name matches for the routes that still emit them.
- **Null is not zero:** an absent balance, an unmetered cost or an unavailable estimate renders "unavailable" with its reason, never `0` (`08.5.5:48`; `00-delta-brief.md:94`).

## 6. States and transitions

**Request state per load (shared, `apps/web/src/app/shared/ui/states/request-state.component.ts:26-97`):** `idle → loading → ready | error(code)`. `ready` carries `empty`; `error` carries the typed `ApiError` and renders one of `forbidden` (403), `not_found` (404), `rate_limited`/`unavailable` (429/503 with `Retry-After`), or the generic error with a retry that is disabled while the retry is in flight. **`stale`** is not an error state: a 412 on save/apply opens the shared conflict dialog and leaves the form in `dirty`, and a long-open reader marks its data `stale` after a failed refresh rather than clearing the screen. **`offline-ish`** means the `unavailable` pattern with the local draft preserved — the app ships no service worker and no optimistic cache, so there is no fake offline mode and no queued write.

| Surface | States the screens must render |
|---|---|
| Tree + table | loading (tree and table independently); empty project; category without cases; no filter matches (distinct from empty); tree error with table still usable; 403 on the entry; stale page after a failed refresh; deep hierarchy and longest-vi overflow; restricted creation/selection (permission explained, not hidden silently) |
| Editor | new case; missing required field; unsaved draft; save in progress/success/failure; 412 with draft preserved; read-only history; restore confirm/success; queued checklist edit; AI action not allowed (opt-in off / credits exhausted / gateway unavailable / schema-invalid output — no version created) |
| Pending changes | empty queue; one of each operation; long comment; invalid merge/split preview with apply blocked and a reason; applying/success/error; duplicate intent; 412 stale batch (queue kept, nothing applied); permission revoked |
| Generation | empty/oversized/unsupported/scanning/rejected attachment; extraction failure; opt-in off; credits exhausted; estimate unavailable; gateway unavailable; schema invalid (no version, refund shown only when supplied); partial test-case generation; review pending; cases ready for review |
| Timeline | first page; paging; empty history for a new case; restore confirmation; restored (new version appended); read-only |
| AI settings | no settings yet (defaults, `"0"`); dirty draft; counter below/at/above each limit; template preview and cancelled replacement; save loading/error/success; 412; read-only version; opt-in off |
| Import/export | no file; unsupported/malformed; preview loading; row errors; duplicate ids; mixed valid/invalid; import denied; success; no selection; empty export scope; export unavailable |
| Usage credits | balance present; zero balance (confirmed) vs unavailable balance; no usage vs no matches for the period; opt-in off (the state comes from the estimate read / `OI-13-505`, never from a second route); no `usage:read`: the sidebar entry is hidden and a typed URL lands on the `/forbidden` pattern — no region and no partial page |

**Generation progress** (`authoring_generation.state`, `13.3.1-generation-pipeline.md:185`): `queued → running → succeeded | failed | blocked | canceled`. `progress` is `{stage, eta_class?}` with a closed monotonic stage set `queued → redact → generate → validate` and `eta_class ∈ {short, long}` (`:120`) — never a percentage: the four-step strip renders the linked intake row's `state` (`received|extracting|ready`) as its first step and the generation row's `progress.stage` for the rest, and derives no stage that is not on a row. `blocked` and `failed` render the row's `outcome_code`, which is the linked `healing_llm_call.status` copied verbatim — `ok`, `cache_hit`, `timeout`, `schema_violation`, `budget_exceeded`, `error`, `blocked_no_optin`, `blocked_leak`, `blocked_kill_switch`, `canceled` (`:121`; `13.3.1-AC22`) — each with vi + en copy; a gateway status outside that list is displayed **as-is**, never translated and never folded into a synonym. The internal `error.code` (`llm_schema_violation`, `llm_timeout`, `llm_provider_error`, `healing_provider_not_approved`, `healing_unavailable`, `ai_credit_exhausted`, `ai_spend_cap_reached`, or an unmapped gateway code kept verbatim) is shown as detail under the sentence, never as the outcome (`:122`). `canceled` is user-visible; `succeeded` reveals `output_refs[]` with their provenance — the UTC time and duration come from the detail read's `created_at`/`started_at`/`finished_at` (`:159`) — and enables the accept step. Intake states are `received|extracting|ready|rejected`, and the 11 canonical extraction `failure_code` values each need their own vi + en sentence. No state and no percentage is inferred from elapsed time.

## 7. Jobs and integrations

- **No scheduler, no background job in the app.** Progress is client polling of `GET …/generations/{g}`: first read immediately, then 1 s → 2 s → 4 s → 8 s → 15 s (cap), stopped at a terminal state, on route leave (`DestroyRef`), when the tab is hidden (resumed with one immediate read on `visibilitychange`), after 15 minutes (states "still running, refresh") and on any 401 (the session store's expiry path takes over). `Retry-After` on 429/503 replaces the delay. This cadence is a UI decision; it needs nothing from the server beyond the documented route.
- **Idempotency per intent:** the SDK call carries the `Idempotency-Key` the UI generated once per user intent (`api-client.ts:56-65`); a retry after a transport failure reuses it, a second confirmation creates a new one. A duplicate-intent 409 renders the first answer, not a second generation.
- **Data services:** thin wrappers over `@evidgate/sdk` functions (`provideApi()`/`API_CLIENT`, `api-client.ts:45-85`) returning `SdkResult` through `ApiGateway.call` (`api-gateway.ts:108-113`); no wire types in `apps/web`, no hand-written DTOs (W5).
- **Fixtures:** every screen is developable before the API exists through the `fixtures` build configuration (`provideFixtureBackend()`, `09.1.1-app-scaffold-and-build-acceptance-npm.md:243-248`), answering by `operationId` from `fixtures/web-api/<name>/`; the authoring corpus is added per screen and validated against `contracts/openapi.yaml` by `fixture-contract.spec.ts`.
- **Telemetry:** the existing facade only (`core/telemetry/telemetry.service.ts`); authoring screens add **no** new event. Route templates and API path templates drop query strings, so filter values never leave the page (`core/telemetry/route-template.ts`, `core/telemetry/api-path-template.ts`).
- **i18n:** `@angular/localize` with explicit `@@` ids; `vi` is the product default and `en` the source locale (`apps/web/README.md:560-598`); `npm run i18n:check -w apps/web` gates a missing or empty translation.
