## 1. Goal and non-goals

**Goal.** Give the reviewer of a repair candidate the two things the candidate's own fields cannot carry: **what the page looked like before and after the failure**, and **what actually changed in the page structure**, computed once at build time, bounded, content-free, and rendered only through 06's isolated viewer. Concretely: when a 08.3.1 candidate reaches `validated` and 08.6.1's read `GET /v1/healing/candidates/{c}` is served, that response gains **one additive member** `review_evidence` that names the before/after screenshot references (only where the project enabled that artifact kind), names the accessibility and DOM snapshot references, and carries a server-computed **structural diff** between the two sides. Nothing in the reviewer's flow changes: no new route, no new permission, no new error code, and every 08.6.1 field keeps its current meaning.

**Three subheads, because the story's own words hide three things.**

1. **"Capture" means resolve, never capture.** This story takes no pixel and opens no browser. The before/after artifacts belong to the capture pipeline that already writes them (06.1/06.2.2 and 13.5.1 for exploration sessions), and this story resolves an artifact by its existing coordinate — `(org_id, project_id, run_id, execution_key, attempt_no, kind)` on `public.artifact` (`migrations/0028_evidence_artifact.sql:45-53`). A project that never enabled a kind therefore never gets that part of the evidence, and says so in a labelled reason rather than in an empty frame. **An artifact's existence is not consent, though.** A kind that still has a shipped static default resolves `capture_enabled = true` with **no project row at all** — `ArtifactKindDefaults.Resolve` returns `CaptureEnabled: true` for a defaulted kind (`src/Modules/Evidgate.Modules.Evidence/Domain/ArtifactKindDefaults.cs:200-210`) and the shipped `ICaptureOptionsReader` documents that a project without a policy row answers that kind's static default (`src/Modules/Evidgate.Modules.Evidence.Contracts/ICaptureOptionsReader.cs:63-72`) — so a `screenshot` artifact can exist under a fallback rather than under a declared decision. Screenshots are therefore shown only when the project has an **explicit** `artifact_kind_policy` row for `screenshot` with `capture_enabled = true`, read through the narrow Evidence-contracts reader of §3, and the rule is evaluated at read time: the platform stores no capture-time policy snapshot, so this is a display-consent check rather than a provenance proof (`OI-13-571`).
2. **"Before/after" is a decision this plan has to make explicit**, because two readings are defensible and they are not the same pair: *baseline green versus failing observation* (both exist whenever the project captured those kinds; the failing attempt is the incident's own, 08.1.1 §4), or *failing observation versus repaired candidate*. The second needs the candidate's replay leg to upload a screenshot, an a11y snapshot and a DOM snapshot — 08.4.3's sandbox replay plan promises none of that, and its job is to prove assertions, not to photograph. `[DECISION]` **baseline green → failing observation**, with the candidate's failing step named in the row so the reviewer knows which step the pair is about; the post-repair capture is 08.6.2's applied-canary evidence on its own path. The residual (which baseline coordinate is authoritative, and who exposes it) is `OI-13-572`.
3. **"Accessibility/DOM diff" is a summary, not a document.** Storing or returning either snapshot's content would put page text and accessible names on a review path that today carries no hash at all (13.6.1-AC9/§3, and FR-13-6 forbids input values and user content). `[DECISION]` the diff is a **closed, bounded structure over role paths and ordinals** plus booleans derived from name equality and a node count — never text, never an accessible name, never a `name.hash` (13.6.1 §3's three rules for any human-facing surface, recorded as `OI-13-547`). A reviewer reads "one button was added at `main[0]/button[3]`, three nodes changed role, the accessible name of the form field at `main[0]/form[1]/input[0]` changed" and opens the snapshots in the viewer when they want the page itself.

**Non-goals.** No capture, no screenshot, no replay, no OCR, no model and no network call (§8) · no classification, rule, score or proposal-state change — 13.8.1 owns every verdict, and this story **reads** refs it did not produce · no new HTTP route, permission, error code, webhook or 00 §9.5 event · no pixel manipulation: screenshots are never decoded, cropped, masked or compared here (a pixel diff is the visual tier's masked-crop concern (§5 of 13.7.2), and a visual-diff product is not in this plan) · no artifact retention change, no second retention clock (§8) · no UI decision: T2 states surfaces, states and acceptance and stops at the `design-ui` gate.

**Prior art.** One public source, read this session for approach only. Playwright's own aria-snapshot model documents what an accessibility tree "snapshot" is and how it is compared: a **YAML tree of roles, attributes and names** where indentation is nesting, the accessible name is a first-class field, and comparison is **order-sensitive** — "the order of elements in the snapshot template must match the order in the page's accessibility tree" (`https://playwright.dev/docs/aria-snapshots` ✅, read 2026-11-11; the page also documents partial matching per node, so a diff can speak about role and hierarchy while ignoring a name). Taken: the **order-sensitive tree walk** and the role/attribute vocabulary as the shape of the comparison — the diff addresses a node as `role[ordinal]` among its siblings, which is `[INFERENCE]` derived from that order rule rather than a rule the page states, and it compares two sides rather than one template against one tree. Not followed: the name and text fields (this wire carries neither), the YAML serialisation (the diff is JSON behind a contract test, not a debug string), the template/pattern matching model (`contain`/`equal`/`deep-equal`), and its single-side assertion shape, because this story never compares a live page. Deliberately skipped: DOM-tree patch libraries (jsondiffpatch and friends) — an ordered walk over two redacted snapshots, with hard caps, is smaller and testable, and a general patch library would emit paths and values this plan is not allowed to store.

## 2. User stories and acceptance criteria

- As a `test_maintainer`, I open a validated candidate and see the page before the failure next to the page at the failure, plus what changed in its structure, so I can tell a moved element from a redesigned one without leaving the review.
- As a `qa_engineer`, I see *why* a piece of evidence is absent (capture not enabled for this project, artifact already deleted, snapshot unreadable) instead of an empty panel, and I am never asked to guess.
- As a security reviewer, I can prove this story stores no page content, copies no bytes, decodes no image and adds no route that a `healing:triage` holder could not already call.
- As a `tenant_admin`, the screenshots I enabled for regulated projects are governed by that project's artifact kind policy, and the review never bypasses the sensitivity gate I configured.

The product question — which pair the acceptance means (this plan reads baseline-green → failing observation) — is the owner decision carried by `OI-13-572`.
- **Hand-over 2 — the drift class on incident reads (blocks T2.4, `OI-13-574`):** the inbox chip needs an additive, nullable `drift_class` object on `GET /v1/projects/{p}/incidents` and `GET /v1/incidents/{i}`, resolved from the newest `drift_classification` for `(org_id, project_id, incident_id)` — receivers are 08.2.2 (the incident read model) and 09.4.1-T1/T2 (the two surfaces). The server side is 08.2.2's read model and has no table read of ours, so it cannot be silently bundled into T1.

## 4. Data model and migrations

**One new table, one migration.** Migrations end at `0097_identity_membership_role_fk.sql` on this base; the number is "next free number, assigned at build time", never guessed in this document. Conventions are the shipped ones: `unique (org_id, id)`, composite FKs **including `project_id`** where the target carries it, `FORCE ROW LEVEL SECURITY`, `timestamptz`, `version` for optimistic concurrency (`plans/00-overview.md:185-191`), a `BEFORE UPDATE` guard function with `set search_path = ''` (`migrations/0095_evidence_artifact_state_guard.sql:24-41`), and no new grant beyond `select, insert, update (state, reasons, version, updated_at)`.

| Table | Purpose | Key columns | Bounds and indexes |
|---|---|---|---|
| `review_evidence` | Append-only-per-candidate evidence row: the before/after artifact refs and the bounded structural diff for one 08.3.1 candidate | `org_id`, `project_id`, `id` (UUIDv7), `candidate_id`, `incident_id`, `before_run_id`, `before_attempt_no`, `after_run_id`, `after_execution_key`, `after_attempt_no`, `before_screenshot_artifact_ids uuid[]`, `after_screenshot_artifact_ids uuid[]`, `before_a11y_artifact_id`, `after_a11y_artifact_id`, `before_dom_artifact_id`, `after_dom_artifact_id`, `state`, `reasons text[]`, `diff jsonb`, `diff_version smallint`, `diff_hash`, `truncated boolean`, `recorded_at`, `updated_at`, `version` | **One row per candidate:** `unique (org_id, candidate_id)`; `unique (org_id, id)`. **Foreign keys.** `(org_id, project_id)` → `project`; `(org_id, candidate_id)` → `healing_candidate (org_id, id)` (the shipped 2-column form — 08.3.1 carries `project_id` denormalised for filtering and quota joins, `…08.3.1-candidate-model-and-rule-based-generation.md:43`, and 08.6.1's history table references the candidate exactly this way, `…08.6.1…:46`); `(org_id, incident_id)` → `incident (org_id, id)`; `(org_id, before_run_id)`/`(org_id, after_run_id)` → `run (org_id, id)` (the 08.1.1 form, `…08.1.1…:44`); the six single-ref columns (`before_a11y_artifact_id`, `after_a11y_artifact_id`, `before_dom_artifact_id`, `after_dom_artifact_id` and the two scalar screenshot refs) carry **no foreign key**, so 06's retention can delete an artifact without touching this row: a `BEFORE INSERT` trigger validates at write time that each ref is an `artifact` row of the expected kind in this project, and afterwards the ref is a plain uuid — a deleted artifact is detected **at read time** by the missing artifact row and reported as `artifact_deleted`. A foreign key here would either block 06 retention or cascade an `UPDATE` into a terminal row, and the terminal-state guard forbids exactly that update. `project_id` stays a plain column with its own `(org_id, project_id)` FK and RLS predicate; `after_execution_key` is the 00 §7 `sha256` hex, matching `migrations/0028_evidence_artifact.sql:74`.

**Why its own table and not columns on `healing_candidate`.** `candidate_hash` is the approval binding (08.6.1-AC2, `approved_head_sha`), so nothing may join the hashed row's mutable surface after validation; and 06 retention may delete an artifact, which must never be an `UPDATE` on a candidate that a reviewer is approving concurrently. A separate row also makes "one evidence row per candidate" a unique key instead of a nullable-quad convention. `[DECISION]`.

**Retention and erasure.** The row is content-free and small: purged with the candidate/project through 08.1.2-T2's hook set (registration row names `review_evidence`), **never** on the artifact clock — an artifact's deletion sets the ref NULL and is reported, it never deletes the evidence row. Tenant/project erasure cascades. Row states are `pending → complete | partial | unavailable`; terminal rows are immutable (guard trigger), which is what makes `diff_hash` reproducible a year later.

**No second clock, no copy.** Nothing here duplicates bytes, mime types, sizes or checksums; every content fact is resolved through `artifact` at read time, which is also why a sensitivity change (`normal → sensitive`) takes effect on the next read with no backfill (`[DECISION]`).

**Read rules (each is a test in §9).**

1. **Ref gating mirrors 06.2.1**, not a new vocabulary: `content_gated` is true when the artifact is `sensitive` and the caller lacks `artifact:read_sensitive`, or when `scan_state = pending` (06.2.1-AC6); then `bytes_declared` is omitted exactly as `object_key`/`checksum` are omitted from metadata (`06.2.1…:47`). No download URL is minted by this read — the viewer asks per artifact, and that call is the audited one. **Screenshots additionally require the project's explicit opt-in; see rule 7.**
2. **Screenshot arrays are ordered** by `(attempt_no, id)` ascending and capped at 4 per side; the UI shows the first and offers the rest, and the cap is a read rule rather than a silent drop (`truncated` covers the diff, `reasons` covers availability).
3. **`state` derivation:** `complete` when both sides produced every ref the project's enabled kinds allow **and** at least one diff side is `available`; `partial` when some refs exist and a diff side is unavailable; `unavailable` when no ref exists at all; `pending` only while the row is leased. The derivation lives in one function, not in the UI.
4. **Reasons are additive, not exclusive:** a project with screenshots enabled but no `a11y`/`dom` rows yields `state = unavailable` (or `partial` if screenshots exist) with `capture_kind_disabled`, and the panel shows the screenshot pair it can.
5. **`null` vs absent:** a snapshot kind the project never enabled is `null` with the reason; a snapshot that exists but cannot be parsed is `{state: "unavailable", reason: "snapshot_invalid"}` inside the diff and keeps its ref. A reviewer can therefore still open the raw snapshot.
6. **No pagination.** The diff is capped at 64 KiB, so the member is a fixed-size member of a single-object response; a future need for more is a new endpoint, not a cursor on this one.
7. **Screenshot consent is an explicit project row, re-checked per read.** `capture.before.screenshots` and `capture.after.screenshots` are populated (and the artifact refs are returned) only when the project has an explicit `artifact_kind_policy` row for `screenshot` with `capture_enabled = true`, read through `IArtifactKindPolicyReader` in the ambient tenant transaction (§3). No row, or a row with `capture_enabled = false`, yields `reasons: ["capture_kind_disabled"]` and empty screenshot arrays **even when `screenshot` artifacts exist**, because a static default is not a decision (§1.1). Removing the row hides screenshots on the next read without touching stored artifacts or this row; a kind with no default and no row (a11y/DOM) is already unrepresentable, since no artifact can have been completed under `422 kind_disabled`.

**The build command's input shape** (internal, not wire): `{org_id, project_id, candidate_id}` plus the resolved failing coordinate; it re-reads the candidate and the classification inside the tenant transaction (C2), resolves refs through a read-only `IReviewEvidenceSource` query (Dapper, `SET TRANSACTION READ ONLY`), reads the two snapshot documents through `IObjectStorage` **outside** the transaction (P5: no network or object IO inside a transaction), then writes/updates the row. Idempotency key: `review-evidence:<candidate_id>` (00 §9.1), so a redelivery is a no-op.

## 6. States and transitions

**The evidence row** (`review_evidence.state`, canonical here and exposed only inside the review member):

- `pending` — written by the task's first attempt, before any storage read; a reviewer sees "collecting" and a retry notice, never an empty panel (this mirrors 09.4.1's incident context `pending` semantics).
- `complete` — every enabled kind resolved on both sides and ≥ 1 diff side `available`.
- `partial` — some refs resolved; at least one side cannot produce a diff or a kind is disabled.
- `unavailable` — no ref resolved on either side (or the candidate's failing coordinate is unknown).
- Terminal states are `complete | partial | unavailable`; the guard refuses any other move (`pending` re-entry, terminal → terminal, terminal → `pending` on redelivery) with `23514`. A retry re-runs the **same** `pending` row, never a new one.
- **The candidate is untouched:** no candidate state transition, no `candidate_hash` change, no approval invalidation. `validated → approved` stays 08.6.1's, and a late evidence write after approval never demotes anything (there is nothing to demote — the evidence is not an input to the hash).

**Rendered states (for the T2 design gate; no visual decision is taken here):** `pending` (collecting), `complete`, `partial` + reason list, `unavailable` + reason list, `content_gated` per ref, `artifact_deleted`, `truncated diff`, and "screenshots are not enabled for this project" with the project-policy pointer for a `project:write` holder. Absence never renders as a zero-size image or an empty diff table.

**Incident classification display (AC11):** `drift_class ∈ {locator_drift, ui_change}` with `class_source ∈ {rule, override}` and `recorded_at`; no classification renders as "not classified"; a classification older than the incident's last attempt is shown with its own timestamp rather than silently refreshed. Rendered only — 13.8.1 owns every write.

## 7. Jobs and integrations

**One internal task, no integration.** `healing.review_evidence` is a task-queue job (00 §5.3, `:179-181`), registered in the worker's task-type routing like every other type; the queue it lands in comes from the routing list, not from the producer (the dispatcher's own rule, `OutboxDispatcher.cs:99-102`).

**How it is enqueued — the seam that must be built, not assumed (`OI-13-573`).** The dispatcher maps **one outbox row to exactly one task row** and sets `task_type = outbox.task_type` (`OutboxDispatchSql.cs:70-87`), so "another consumer of the same event" is not a thing this system supports: 08.6.1's `validated` transition already writes one outbox row for `healing.build_pr` (`08.6.1…:56`, `:69`). The build therefore needs a **second outbox row** with `task_type = 'healing.review_evidence'`, written in the same transaction that sets the candidate `validated` (08.6.1-T1.1's validation command). Receiver: 08.6.1-T1.1 for the extra row; this story owns the task type, the handler and its routing entry. An alternative — chaining the evidence command at the tail of `healing.build_pr` — is rejected: a PR-build failure (GitHub outage) would then silently suppress evidence that has nothing to do with GitHub, and 08.6.1-AC1 already separates PR mechanics from review data.

**Task body, in order (each step a test):** (1) open the tenant transaction, re-read the candidate and the newest classification inside it, and **refuse a candidate that is not `validated`** with no row, one counter and no retry (the enqueue only fires on `validated`, so this is a guard against a stale or forged row, not a retryable failure); (2) in the same transaction, claim the work by inserting `state = 'pending'` with `ON CONFLICT (org_id, candidate_id) DO NOTHING` and stop unless a row is now `pending` — which is what makes a redelivery a no-op and keeps a terminal row immutable; (3) resolve refs with a read-only query over `artifact` for both sides (AC2); (4) outside the transaction, read the two snapshot objects through the bounded reader — screenshots are never opened (AC9); (5) compute both diffs with the caps and the canonical `diff_hash`; (6) one `UPDATE … SET state = terminal … WHERE state = 'pending'` that writes the refs, reasons, `diff`, `diff_hash` and `version` in a single statement (the guard refuses any other move); (7) emit the metric. Retries: 3 attempts with the queue's backoff, then the same step-5 write with `unavailable`/`build_failed` so a reviewer is never left in `pending` forever; a stale `pending` older than 2× the task lease renders as "collecting" and is visible to the sweeper (no silent stall).

**Backfill.** One ops-run `task` row (`review_evidence_backfill`, bounded batch, logs a count) for candidates that reached `validated` while the flag was off — the 08.1.2 `BackfillFingerprints` shape. It is idempotent by the same key and writes no second row.

**Integrations:** none. No GitHub call, no provider call, no webhook, no emailed notification. The only external surface touched is object storage, read-only, through `IObjectStorage`'s read-only members — `HeadAsync` for the declared size, then `GetAsync`/`ReadPrefixAsync` under the byte cap (`src/BuildingBlocks/ObjectStorage/IObjectStorage.cs:51`, `:79`, `:109`); `CopyAsync`/`DeleteAsync` are never called.

**Why 13.2 and 13.3 are not the source here, checked rather than assumed.** 13.2.1's non-goals list the gateway call, the provider, redaction and the tenant opt-in as 08.5.1–08.5.3's (`…13.2.1-versioned-project-ai-settings.md:15`), and 13.3.1's image intake stores the artifact and sends no bytes to any provider (13.3.1-AC4, `…13.3.1-generation-pipeline.md:41`); neither governs evidence capture or artifact sensitivity, so this plan takes the opt-in from 06.2.1/06.2.2 and 13.5.1-AC12 and says so instead of borrowing a rule from a plan that disclaims it.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** read = `healing:triage` on the existing route (`contracts/permissions.json:469`); build = no principal, tenant scope opened from the task row (RLS, 00 §5.4); capture opt-in = `project:write` (`:609`); sensitive bytes = `artifact:read_sensitive` (`:259`) on 06's `download-url` only. No new string, route or role. Role reality: `qa_engineer` reads both evidence and sensitive snapshots; `test_maintainer` can read the candidate's sensitive artifacts but not the candidate itself without `healing:triage`; `tenant_admin` gets 403 on the review read and never sees a review, because it holds neither `healing:triage` nor `artifact:read_sensitive`. The content-gating branch is asserted with a triage-holding principal **without** `artifact:read_sensitive` (a custom role — no built-in triage role lacks it). All of this is asserted in `ReviewEvidenceAuthorizationTests`, not described.
- **Retention/deletion:** the row is content-free and lives on the candidate/incident clock, purged through 08.1.2-T2's hook set; an artifact deletion **never touches this row** (no FK on a ref, no cascade, no `SET NULL`) and is derived at read time as `artifact_deleted`, so 06 retention is never blocked and a terminal row stays byte-identical; tenant/project erasure cascades; no second retention clock, no byte copy, no object-store write; the row stays immutable so `diff_hash` is verifiable a year later.
- **Telemetry:** `review_evidence_build_total{outcome, reason}` and `review_evidence_diff_bytes` (histogram) with closed label sets and **no** candidate/artifact/org id in a label; one span around the build tagged with node counts and the truncation flag, never with an id; availability is aggregated per project for the G3 adjudication read. No audit row from this read — the audited events (sensitive download grant/denial) remain 06.2.1's, so evidence is not double-audited.
- **Failure path:** a missing kind, a deleted or unscanned artifact, an unparsable or oversized snapshot, a missing baseline coordinate and an exhausted retry each map to a **closed reason** on the row and a `200` review response; nothing fails the candidate, the approval, the run or the review read, and nothing is retried on a permanent condition (an unknown schema is not retried). A storage outage is transient: retries, then `unavailable`/`build_failed`, and the sweeper surfaces the stale row. An approval that happens while evidence is still `pending` stays valid — evidence is not part of `candidate_hash`. A project that turns capture off keeps its old artifacts' refs and gains `capture_kind_disabled` only on the **next** candidate, never by rewriting history.

**Trust boundaries and abuse cases.** (1) *A crafted artifact cannot widen the read:* every ref is resolved by coordinate and tenant from the artifact table, and the diff parser is a closed grammar that fails to `snapshot_invalid` rather than echoing unknown keys. (2) *A page cannot smuggle content through a role path:* roles and ordinals come from the snapshot's own structure; `changes[]` values are a closed enum, so an attacker-chosen role string is either an allowed member or `other`. (3) *A reviewer cannot use this path to read a project they cannot triage:* the read is scoped by the candidate's own project and RLS, and a cross-project candidate id is a 404. (4) *A noisy page cannot blow up the response:* caps and truncation, with the reason recorded. (5) *A deleted artifact cannot resurrect content:* `ON DELETE SET NULL` plus `artifact_deleted`, and no copy exists.

## 11. Rollout

**Order.** (1) 08.6.1-T1.1 lands `validated` and its outbox rows (including the second row of `OI-13-573`); (2) 13.8.2-T1 lands the table, task, diff and the additive read; the build keys on a candidate existing rather than on `Healing:Apply` (that flag decides whether a candidate can be approved and applied, 08.6.1-AC6/§11), and the read returns `review_evidence` absent for pre-existing candidates until the backfill runs; (3) 09.4.1-T1/T2 and 09.5.1-T1/T2 land the surfaces; (4) 13.8.2-T2's design gate, then the panel and the chips. A deployment out of order is safe: an older web build ignores the unknown member (SDK types are additive), and the read never requires the task to have run.

**Availability, not apply.** The build task is registered for every environment and produces a row for every candidate that reaches `validated` — `shadow` included, because a shadow candidate is reviewed the same way. It does **not** read `Healing:Apply`: that flag governs approve and apply (08.6.1-AC6), and 08.6.1's own rollback keeps already-approved candidates reviewable with the flag off (`:143`), so no flag may make review evidence disappear. A deployment that wants no evidence work removes the task-type routing entry and no outbox row is enqueued; it never gates the read, and the read has no switch of its own because it is a member of 08.6.1's review read.

**Measurement (reported, never a gate).** Budget per plan 13 §4.3 G3 (`:67`): the adjudication needs before/after evidence; report per project the share of reviewed candidates with `state = complete`, the reason histogram, the diff truncation rate and the p50/p95 build duration and `diff_bytes`. A project whose evidence is mostly `capture_kind_disabled` is a **configuration** finding for the pilot, not a defect of this story, and the plan is explicit that a missing a11y/DOM kind is a labelled absence rather than a claim of "no structural change" (the failure mode this story must never have).

**Rollback.** Drop the task-type routing entry and the outbox producer (one config change, one line in 08.6.1's transaction); the read then returns `review_evidence: null` (or the last row, if the field stays served), the panel hides itself, and the table is inert. No migration rollback is required: the table is additive and no other object references it. `diff_version` exists so a grammar change ships as `diff_version = 2` with both shapes readable for one release rather than a rewrite of stored rows.

**Owner decisions to close before the first build step.** `OI-13-571` (the grammar is the contract T1.2 implements) and `OI-13-572` (the pair is the acceptance the reviewer sees); `OI-13-573`/`OI-13-574` are hand-overs with named receivers; `OI-13-575` is measured at each task's start and never silently absorbed.
