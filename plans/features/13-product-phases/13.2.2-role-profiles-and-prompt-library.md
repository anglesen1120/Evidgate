## 1. Goal and non-goals

**Goal.** Give each generation one explicit, versioned role profile without making a role name an authorization role. The three layers are platform-owned seed templates → project-defined, immutable profile versions → one per-generation selection, optionally accompanied by a short run note. A profile changes emphasis, content and tone within the selected output kind, never the output JSON schema, gateway safety rules or caller permissions.

**Area-plan acceptance:** a tenant picks or defines a role profile (seeded BA, QA, PM, Dev templates in vi + en, cloneable and editable) and chooses one per generation; the profile changes the content and tone of the generated output for that role at that phase, never its output JSON schema, never the gateway safety rules, never the caller's permissions; role text is untrusted data, length-capped, normalised, delimited, redacted and covered by an injection corpus; provenance and cache keys carry profile id + version.

**Phase (CR-D-2).** G1 delivers BA and QA seeds in vi + en, clone-and-edit, project-scoped custom profiles, and selection for `checklist` (requirement → checklist/AC, 13.3.1-T2) and `test_case` (checklist item → manual test case, 13.3.1-T3). T8 delivers PM `release_summary` and Dev `failure_triage` in G2, after run results exist. BA, QA, PM and Dev are seed data, not a closed role enum; tenants may name their own profiles. The **output-kind** set is closed and phase-gated.

**Non-goals.** Editing base prompts, JSON schemas, gateway policies or RBAC through a profile; a new permission string or an “AI-settings admin” role; changing models, credit accounting or safe-healing rules; org-level profiles; cross-project sharing; persisting a run note as reusable guidance. `test_plan` and `integration_scenario` have no owned generation/schema task today: OI-13-305 recommends a separate G2 story after the G1 pilot, not sized here. T1 names future research and its method only; this plan contains no GitHub research result.

## 2. User stories and acceptance criteria

- As a QA engineer, I select a BA or QA seed or a saved project profile for one generation and see the exact version used afterwards.
- As a tenant admin, I clone a seed or define project guidance, edit it as a new version and preserve the earlier versions for provenance.
- As the platform, I treat role text and the run note as untrusted data; a profile called “admin” has no more authority than any other profile.
- As a prompt-library maintainer, I can trace every seed to reviewed ideas, licence evidence and an evaluation fixture, without importing prohibited source text.

Every criterion refines the story acceptance in §1 and has a named proof in §9. Numeric defaults below are `[INFERENCE]` recommendations pending OI-13-302; they are enforceable defaults for build, not measured product facts.

## 4. Data model and migrations

`migrations/NNNN_authoring_role_profiles.sql` — **SQL sketch, not an executable migration**; NNNN is allocated at build, never reserved here. UUIDv7 ids, UTC timestamps, canonical `sha256:<64 hex>` hashes and composite tenant FKs follow 13.2.1 §4. All business rows are project-scoped (`project_id not null`); the platform seed catalogue is the sole no-`org_id` exception.

**Canonical content.** `content` is the closed role-profile document from §3; instructions combine style and priority in one capped field. NFC/end-trim precede schema validation, SecretShape refusal and RFC 8785 canonicalization. Hash `{content, retired}` so all effective profile changes change the hash; ids, version numbers, seed-copy metadata, author and reason are provenance, not content. `retired` is a typed column, not mutable JSON lifecycle text. Reason is optional, capped at 500 code points, SecretShape-checked and never copied to audit. JSON type/length CHECKs supplement, never replace, edge schema validation.

```sql
-- Platform seed catalogue: no org_id; migration-written, app select-only.
create table public.role_prompt_template (
  id uuid primary key,
  seed_code text not null,
  seed_version integer not null check (seed_version >= 1),
  output_kind text not null check (output_kind in ('checklist', 'test_case')),
  locale text not null check (locale in ('vi', 'en')),
  body text not null,                       -- trusted, reviewed platform seed material
  profile_defaults jsonb not null check (jsonb_typeof(profile_defaults) = 'object'),
  content_hash text not null check (content_hash ~ '^sha256:[0-9a-f]{64}$'),
  provenance text not null,                 -- source/licence/review disposition, AC19
  created_at timestamptz not null default now(),

-- content_hash addresses {content: profile_defaults, retired: false};
-- body + its seed binding are separately covered by prompt_version.

  project_id uuid not null,

  org_id uuid not null,
  project_id uuid not null,
  ai_run_id uuid not null,
  profile_id uuid not null,                  -- externally visible selected id
  version_no integer not null check (version_no >= 1),
  content_hash text not null check (content_hash ~ '^sha256:[0-9a-f]{64}$'),
  source text not null check (source in ('seed', 'custom')),
  custom_profile_id uuid,
  seed_template_id uuid,
  run_note text check (run_note is null or char_length(run_note) <= 500),
  run_note_hash text not null,               -- hash of normalized redacted note/null
  created_at timestamptz not null default now(),
  unique (org_id, id),
  unique (org_id, ai_run_id),
  foreign key (org_id, project_id) references public.project (org_id, id),
  foreign key (org_id, project_id, custom_profile_id, version_no, content_hash)
    references public.role_profile_version
      (org_id, project_id, profile_id, version_no, content_hash),
  foreign key (seed_template_id, version_no, content_hash)
    references public.role_prompt_template (id, seed_version, content_hash),
```

**Direct seeds versus custom ids.** A generation may choose a platform seed directly: its `profile_id` is the catalogue row id, `version_no` its seed version, `source = seed`. A clone or from-scratch profile always has a project identity and `source = custom`, even when its content still matches a seed. The two nullable backing FKs and exclusive CHECK above make this union enforceable without a fake tenant profile or a nullable project. Direct seed selection never writes a custom profile or bypasses save authorization. The seed row is version-pinned and immutable like a custom version.

**Policies, guard and grants.** All four tables ENABLE + FORCE RLS and have an explicit permissive owner policy `for all to evidgate_owner using (true) with check (true)`. Each tenant table uses `evidgate.current_org_id()` and project scope through `evidgate.current_project_id()` where set, in both USING and WITH CHECK (T2/T3); unset org yields zero rows. Catalogue SELECT to the app uses `true`; no tenant INSERT/UPDATE/DELETE policy or grant exists for seeds. Tenant app grants are SELECT + INSERT, explicitly revoking UPDATE + DELETE; `role_profile_use` INSERT waits for the T5 FK. Operator access is grant-gated under 00 §5.4, never a blanket cross-tenant policy.

The immutable guard rejects **UPDATE for every role**, raises `23514`, and rejects DELETE except when `current_user = 'evidgate_owner'`. This applies to the identity, versions, use rows and immutable seed versions. Owner DELETE is for authorized retention/erasure, not an API delete; an FK prevents deleting a seed or version still referenced by a run. 06.4.4-T1's owner sweep removes use rows, then versions, then identities, never shared seeds. Its `SECURITY DEFINER` function must meet T80 (`search_path = ''`, qualified names, dedicated EXECUTE, audit). No guard is disabled to make deletion work.

**Limits and save algorithm.** Server/DB checks enforce AC1, closed locales/kinds, schema depth/body caps and the reason limit; field CHECKs use `char_length` on normalized JSON members where applicable. Serialize custom-profile saves with a transaction-scoped advisory lock keyed by `(org_id, project_id, profile_id)`; read the head, compare If-Match, then canonical no-op or one append, then audit. The unique version key is the final race guard, not a substitute for the lock. Create serializes org/project quota checks in a fixed order using the `ITenantLimits` pattern; bounded counts stop at the cap. Default 20 custom identities includes retired profiles; seed catalogue rows do not consume that quota. ## 6. States and transitions

**No new lifecycle machine.** Identity and version rows are immutable. The typed version flag `retired` is a versioned availability property, not a new mutable `active|retired` enum or a change to 00 §8.11's authoring states. A change of that flag is a new version and a new hash. No DELETE endpoint, hard-delete workflow or reusable run-note resource is introduced.

| Existing fact | Operation | Result | Invariant |
|---|---|---|---|
| no custom identity | create/clone | identity + v1, `retired = false` | one version, no shared-seed mutation |
| vN current | changed save with current tag | vN+1 | old version unchanged |
| vN current | identical save with current tag | vN unchanged | no audit/version append |
| vN current | stale tag | 412 | nothing changed |
| vN selectable | save `retired = true` | vN+1 marks profile unavailable | no new generation silently substitutes another profile |
| retired head | explicit save with current tag and `retired = false` | new version | history retained, no in-place restore |
| run pinned to vN | ordinary vN+1 edit | pinned vN retained | exact resolve, not latest-head substitution |
| run pinned to vN | head retired before dispatch/publication | stop/discard | OI-13-307 default no in-flight use; pin retained for explanation |

The retirement check is separate from exact-version content resolution. Recheck under the profile serialization discipline before dispatch authorization and before publication/cache write; do not hold a DB transaction across provider HTTP. A retirement committed after dispatch cannot recall provider bytes: cancel where possible, refuse publication when the result returns and use the existing once-only failed-generation refund. Reactivation never revives a previously stopped run; it needs an explicit new generation.

**Trust boundaries and five abuse cases.** Browser/client → Authoring validation/RLS → immutable provenance → redaction and prompt envelope → external provider → schema validator/publication. (1) A foreign-org id is stopped by scope/RLS and composite FKs (AC13). (2) “Act as admin” or schema-replacement text cannot affect RBAC or the platform schema (AC5/AC6). (3) Closing delimiters, nested JSON and Unicode tricks remain opaque or are refused (AC7/AC8). (4) A pasted credential is refused; PII-like prose is redacted and residual leaks block egress (AC9). (5) An overlong profile, profile-create race or cache/pin replay cannot bypass caps, mix tenants or replace provenance (AC1/AC10/AC11/AC20). The model is never the enforcement authority; deterministic validation and permissions are.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** `ListRoleProfiles`, `GetRoleProfile`, `ListRoleProfileVersions` and `ListRolePromptTemplates` require `authoring:read`; `CreateRoleProfile` (including clone) and `SaveRoleProfile` require `project:write` — recommended default `[INFERENCE]`, `tenant_admin` only, OI-13-301. Selecting an existing seed/custom profile inside generation requires `authoring:generate`, not `project:write`. A `qa_engineer` reads/selects but cannot save. A viewer/release approver cannot generate; service identities without these codes are refused. Handler permission equals `x-permission` (T51), evaluated on principal/project only; profile text is never permission input. Foreign org/project resource ids are 404; a scoped credential addressing another project is 403. Platform seeds remain read-only shared data after member authorization.
- **Retention/deletion:** identity/version text is project content and provenance, retained while generated artifacts cite it; no app hard delete or per-version rewrite. `role_profile_use`, including its redacted `run_note`, is retained and erased with the associated generation/run, never longer merely because the profile survives. 06.4.4-T1's owner sweep removes use rows before versions/identities; retained references constrain deletion, and erasure must remove dependent run links consistently. Owner-only DELETE plus owner RLS policy makes the sweep possible under FORCE; UPDATE is always forbidden. Shared seeds are platform data, not erased per tenant. If selective profile-text erasure is required before project deletion, the erasure owner must define the dependent-provenance treatment, not bypass the guard.
- **Personal data:** name/description/instructions/reason may contain personal data; SecretShape is not a PII detector. Stored profile versions therefore remain protected tenant content. The optional run note is NFC-normalized, scanned, redacted before persistence, capped at 500 code points and stored only in the run's use row (OI-13-304 default yes). Egress redacts profile/settings/context again; hashes prove which immutable source was used without exposing its text. Neither idempotency response bodies nor audit/log/telemetry copy text. DECISIONS §7 and 08.5.3 opt-in/transfer controls apply unchanged.
- **Telemetry:** audit exactly one create/changed-save action with ids/version/hash/seed reference, never text or free-text reason. Counters `profile_selected_total{source,output_kind}`, `role_text_refused_total{reason}` and `injection_blocked_total` use closed low-cardinality labels only. Generation-by-profile is an authorized, project-scoped aggregate over `role_profile_use` joined to call outcomes/cost, not an unbounded profile-id/name metric label. No raw profile id, note, name or tenant prose in metric labels; no invented quality score for custom profiles.
- **Failure path:** known project, missing/retired/wrong-kind selection → 422 `request_invalid`, `details[].path = /role_profile_ref`, reason `profile_not_found|profile_retired|output_kind_not_allowed`; unknown/foreign org/project resources → 404 `not_found`. Never silently choose another profile. Bad text/secret/limit → 422 with machine reason; oversized body → 413; stale save → 412 with draft preserved, no auto-merge; missing idempotency key → 400 and conflicting replay → 409. Pre-dispatch refusal spends no credit. Model output failing the fixed schema follows 13.3.1 + 08.5.5-T2's existing reject/refund path, no partial authoring version. Retirement after dispatch discards publication with the same failed-generation settlement. Existing opt-in, switch, budget, provider and leak failures keep their gateway outcomes. No additional retry policy is introduced.

## 11. Rollout

- **Migration order:** expand-only four-table schema/policies/guards/exemptions first, independent of a live model; reviewed T2 seed rows are installed by owner migrations once the tables exist. Then management API/SDK, T4 safety, T5 call FK + pin/cache integration, approved T6 UI and T7 evaluation gate. No runtime seed editing or silent seed replacement; a changed seed is a new migration/version (OI-13-306).
- **No flag for tables.** New storage/routes are additive and inert until selected. Existing generation paths without a role-aware contract are not silently assigned a profile: update both clients and generation contract together before enabling the selector; older callers receive an explicit validation/compatibility response once explicit selection is required. Management and manual authoring remain available with generation off.
- **Per-tenant kill/opt-in:** reuse 08.6.3's **Kill switches and degradation** (`healing_switch`, most restrictive system/tenant/project resolution) and 08.5.3's **Redaction and per-tenant opt-in** (`healing_optin`, active provider/project scope, two distinct tenant-admin signatories, revocation before next send). 08.5.5-T3 explicitly makes the switch halt **all model calls**; no role-profile-specific safety switch or opt-in bypass. These gates and credits must be live before the first role-selected real call, not deferred by this story's task dependencies.
- **Compatibility:** schema/permission/error changes are additive except the coordinated generation selection requirement; schemas remain fixed by output kind. Regenerate SDK alongside OpenAPI, preserve pinned old versions and old prompt bindings, and keep the old reader until retained runs no longer require it. Roll back clients/routes/integration first; leave immutable provenance tables in place. Forward migrations, not destructive drops of referenced evidence. No new permission aliases or deprecated profile APIs.
- **Evaluation gate:** ship BA/QA only after T7 passes the existing rubric across vi/en/kinds; block a seed/prompt/model revision that fails. Custom profiles are not quality-gated, but never bypass schema, authorization, redaction, opt-in, switch or credit checks. T8 has its own G2 fixture evidence before enabling PM/Dev kinds.
