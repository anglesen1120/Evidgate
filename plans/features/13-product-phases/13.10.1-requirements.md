## 1. Goal and non-goals

A QA engineer starting with a document can answer: **which tests cover this exact acceptance criterion, and what evidence, if any, do they have?** Store a stable requirement identity, preserve each version and let reviewers follow the links without relying on a matching title or an external issue key.

This story owns authoring, import, generation input and the coverage read model. It does not generate a verdict, execute tests, implement a tracker connector or publish reports. Story 13.10.2 supplies manual results, 13.10.3 snapshots reports, and 13.10.4 imports tracker content. A link or an approval is not execution evidence.

## 2. User stories and acceptance criteria

| ID | Acceptance criterion |
|---|---|
| AC1 | In a documents-only project, an author creates an epic, a story beneath it and two acceptance criteria beneath the story; a standalone spec section need not have a parent or a feature node. Reading a requirement returns its stable id and current version. |
| AC2 | A writer changes a criterion, then restores its first version: history shows three versions, their source, author, reason and content hash. The original two rows are unchanged. Two edits based on the same ETag cannot both succeed. |
| AC3 | Given two criteria with the same title but different ids, opening the first shows every manual case it reaches **either** by a direct link **or** through a linked checklist item (`manual_test_case.checklist_item_id`), with approval states, the path (direct, via item, or both) and any automated `test_case` identities reachable via `manual_case_link`. A requirement linked only to a generated checklist item still lists that item's child cases and their automated identities; adding a direct link to one of those cases leaves the distinct-case count unchanged. The second criterion does not inherit any of these. |
| AC4 | The coverage page distinguishes an unlinked requirement, a linked draft, an approved case and a case with an observed result. Before the manual-result source exists it says “not available”; after it exists a case without a result is “not executed”. Neither a missing result nor an approved case is shown as PASS. |
| AC5 | CSV, XLSX and Markdown fixtures representing a story with two ACs import as a parent and two children. In Markdown a heading starts a story, a list item is an AC, and a Given/When/Then block remains one AC with its lines intact. Extracted spec text can be saved as a `spec_section` without invoking generation. |
| AC6 | Generation from selected requirements records the exact versions read before dispatch. A subsequent edit does not change the input used by a queued job; each generated checklist item links to the input requirement version(s) that support it, not indiscriminately to every selected requirement. |
| AC7 | Editing a requirement or syncing changed tracker content makes **every** link to an older version `requirement_changed`. Reviewers see old and current versions and stale counts. Relinking one target clears staleness only for that target. Dismissal requires a reason, is audited, and never silently repins the link or increases current coverage. |
| AC8 | An author can navigate the tree, inspect history, compare link pins and review stale coverage by keyboard in vi or en. Empty, loading, inaccessible and unavailable-result states are distinguishable without colour. |

## 3. Contracts touched

- Keep `authoring:read` and `authoring:write` for requirement queries and commands respectively; selecting requirements as generation input does not replace the existing `authoring:generate` gate. Publish operations, permission metadata, concurrency headers and response shapes in OpenAPI with the generated SDK.
- `requirement_version` is append-only, including on restore. `external_ref` is optional and uses the catalog's 03.1.4 `requirement_ref` character rule; it is neither a foreign key to a tracker nor a join key for coverage.
- Reports consume stable ids and pins plus explicitly available result data. Generated items carry the actual input pins in provenance. Historical reports and consumed release decisions are never rewritten when a link or requirement changes.

## 4. Data model and migrations

| Record | Invariant |
|---|---|
| `requirement` | Project-scoped identity; `kind` is `user_story`, `acceptance_criterion`, `epic`, `spec_section` or `other`; `title`, optional `external_ref`, optional `feature_node_id` and optional `parent_requirement_id`. Parent belongs to the same project; reject a cycle on reparent. The nullable `tracker_item_id` column and FK arrive with 13.10.4-T1, **not** with the first migration. |
| `requirement_version` | One immutable row per `(requirement_id, version_no)` with NFC body ≤ 20,000 Unicode code points, `content_hash`, `source` (`manual`, `import`, `tracker` or `ai`), `author_membership_id` and `reason`. Allocate the next version under the head concurrency check. A restore appends even if the restored body hash already exists. |
| `requirement_link` | Pin `requirement_id` and `requirement_version_id` and exactly one of `checklist_item_id` or `manual_test_case_id`. Composite FKs enforce that the version belongs to this requirement and all endpoints belong to the same tenant/project. Coverage reaches a case by a direct link or through a linked item's child cases (`manual_test_case.checklist_item_id`) and counts each case once; a duplicate pin to the same target must not inflate counts. |

Include `org_id`, scoped composite keys, FORCE RLS and least-privilege grants on each new table. Index scoped history by requirement/version and links by requirement and target. Retain the version history on ordinary deletion of a requirement; use the project purge path for erasure. Read automated case identity through the existing `manual_case_link`, not a second copy of catalog data.

## 5. API shapes (commands, queries, endpoints)

Proposed operations under the existing `/v1/projects/{p}/authoring` group; reuse its error, idempotency and pagination conventions. `r` below is a requirement id, not an external reference.

| Operation | Input and observable result |
|---|---|
| `POST /requirements`; `GET /requirements`, `GET /requirements/{r}` | Create with kind, title, body, reason and optional parent, feature node or external ref. Return id, version and ETag. List by project, including parent ids for the tree. |
| `PATCH`, `DELETE /requirements/{r}`; `GET /requirements/{r}/versions`; `POST /requirements/{r}/restore` | Mutations of existing state take `If-Match`. Restore takes a prior version id and reason, verifies ownership, and returns the new head; delete removes the item from the live list, not its historical pins. |
| `GET /requirements/{r}/coverage` | Return the revision being viewed, pinned targets and version ids, linked/approved distinct-case counts (cases reached directly or under a linked checklist item, each counted once, with its link path), automated identities, stale count and the availability of the latest manual result per case. Do not overload a count of zero to mean the result source is unavailable. |
| Link and review commands under `/requirements/{r}/links` | Name one target and an exact version pin. Relink names the old pin and new head; dismissal names the stale link, reviewed head and reason. A stale review must not overwrite a concurrent review or an edit. |
| Import and generation | Extend the existing import/intake paths; do not add another upload service. Extend the generation request with `requirement_ids[]`: resolve each id to a scoped version before dispatch; store and subsequently read those pins (§7). |

## 6. States and transitions

A requirement has a stable identity and successive immutable versions, not a pass/fail lifecycle. For a link, **current** means its pin equals the current version; **stale** means they differ. A newer version flags old pins even when it restores a previously seen body. Do not mark neighbouring requirements stale. Dismissing a notice records who reviewed which old/new pair and why. It acknowledges that change only: another version requires review again. Relinking is an explicit write, preserving the prior pin in the audit trail. No transition changes a test result.

## 7. Jobs and integrations

- Import uses the 13.1.1-T5 preview/commit pipeline for parent-child validation; 13.3.1-T1 supplies extracted text only when intake is ready. Text is input data, never a command. Tracker sync uses the same version writer: unchanged content produces no revision and no new stale links.
- At generation request acceptance, capture each authorized `(requirement_id, requirement_version_id, content_hash)` and preserve attribution through 13.3.1 checklist materialization. Before saving links, verify every attributed pin is among the captured inputs. Editing while the job runs therefore produces correctly stale links, not generation against an unrecorded head.
- Consume latest manual results only where the 13.10.2 read model supplies them. A report can snapshot the resulting trace, but only the release decision path can issue a release verdict. No background re-linking, repository fetch or automatic provider call on edit.

## 8. Security, privacy and performance

- **Authorization:** project-scoped reads need `authoring:read`; edits, imports, links, restore and dismiss need `authoring:write`; generation retains its own permission and opt-in checks. Check every nested id under the same scope. Return `404` for a foreign resource; the normal scoped-credential mismatch remains `403 project_scope_mismatch`. Unset tenant context reads no rows.
- **Retention/deletion:** authoring removal hides the requirement without deleting immutable versions or breaking historical pins. Project/tenant erasure uses the privileged purge path, with link and version dependants included. Audit follows the existing audit retention policy.
- **Personal data:** titles, bodies, imported prose, refs and reasons may contain personal data. Protect them as tenant content; never place them in logs, spans or metric labels. Keep the dismissal reason in protected review history. Only explicit generation uses the existing redaction/opt-in gateway; CRUD and import do not send text externally.
- **Telemetry:** audit create, edit, delete, restore and review by actor, scoped ids, operation, previous/new pin and outcome; correlate the dismissal with its protected reason. Metrics use closed operation/outcome labels, not requirement ids or text. Use paged, set-based coverage reads, not one query per linked test.
- **Failure path:** stale `If-Match` returns `412 precondition_failed` without another version; invalid kind, excessive normalized body, wrong version/target combination or blank dismissal reason cannot change persisted state. Failed import preview cannot create a partial trace. Missing result data remains unavailable, never PASS.

## 9. Test plan

| Fixture or action | Required observation |
|---|---|
| Schema and isolation (AC1–AC3) | Migrate a project with no connector; store all five kinds. Accept exactly 20,000 NFC code points including non-BMP text; reject 20,001. Reject an invalid ref, foreign parent, parent cycle, foreign version/target and both/neither link targets. Direct app-role version UPDATE/DELETE fails. |
| API and audit (AC1–AC2, AC7) | Exercise reader, writer, no grant, sibling project and foreign tenant on each route. Race two PATCH requests with one ETag: one append, one 412. Restore the first version and compare all three stored rows. Record one audit per accepted write; failed writes leave no mutation. |
| Trace and result availability (AC3–AC4) | Seed same-title requirements R1 and R2, an item I1 with an approved case C1 (with an automated identity) and a draft case C2, plus an unrelated item. Link **only I1** to R1: assert R1 lists C1 and C2 with their approval states, the automated identity and path "via item", while R2 lists nothing. Then add a direct link R1 → C1: C1 shows path "both", the distinct-case count stays 2 and the automated identity is listed once. A direct-links-only implementation fails the first assertion. Also test no links, no result producer, a producer without a result, and an actual failed result; none of the first three implies PASS. |
| Import and provenance (AC5–AC6) | Preview/commit each supported format, a multiline Given/When/Then case, a rejected input and a ready extracted document. Queue a two-requirement generation; edit one source before materialization. Verify each item points only at its contributing pinned versions and the original source remains readable. |
| Change review (AC7) | Seed two old pins, advance head manually and via a changed sync; unchanged sync does nothing. Relink one and dismiss the other: one current and one stale, with actor/reason recorded. A later version reopens review. Replaying a stale review cannot lose a newer edit. |
| UI (AC4, AC8) | In vi/en, traverse list → history → links → coverage with keyboard and screen-reader labels. Inspect no links, draft/approved/stale cases, failed load and unavailable result without relying on badges or colour alone. |

## 11. Rollout

1. Land the schema and isolation fixtures before exposing the authoring API. No connector, provider credentials or test result producer is required to start T1.
2. Expose versioned links and coverage to an authoring-enabled project; seed a story, two criteria and two cases. Inspect pins before and after editing one criterion. Confirm the other criterion's coverage does not move.
3. Enable imports, generation input and the reviewed vi/en surfaces when their dependencies land. Until manual results are available, retain the explicit unavailable state. If an authoring rollout must be withdrawn, stop exposing new actions; keep immutable versions and pins readable for existing consumers.
