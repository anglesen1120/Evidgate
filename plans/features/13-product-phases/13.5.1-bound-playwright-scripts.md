## 1. Goal and non-goals

**Goal.** Turn one **approved** manual test case into a TypeScript Playwright script whose every step is either bound to a real element on the customer's own running application, with a live pre-action target check, or recorded as unbound with a closed reason that keeps the script `draft`. The generated code is produced on the customer's machine by `evidgate generate` (architecture rule A5, `plans/13-product-phases.md:31`), never on Evidgate hosts; the browser session is bounded to the project's approved environment origin; the emitted locators obey one policy (role → label → test id → text → CSS, never absolute XPath, never `nth()`); a model is asked **only** for steps the rules cannot bind and may only pick one candidate from a closed list the client extracted; the code reaches the repository **only** as a pull request through 03.4.2; and a script becomes `active` only after three green runs on one build after that merge. The story also ships the per-project testability score and the scripts screen that shows status, stability, unbound steps, lint results, PR state and the score.

**Area-plan acceptance.** An approved test case with an environment URL and a seed test yields a TypeScript Playwright script whose every step is bound to an element found on the live page; the locator policy holds; forbidden patterns are never emitted; the script reaches the repository only as a PR and becomes `active` after 3 of 3 green runs on one build; a scripts screen shows status, stability, unbound steps, lint results, PR state and testability (`plans/13-product-phases.md:186`).

**Partial against that acceptance (owner decision `OI-13-510`, proposed, owner confirmation pending).** "Every step is bound to an element found on the live page" cannot hold for every approved case: some steps need no element (open a URL, wait for a response, assert that something is absent, set up data), some target an element the session cannot reach (behind a one-time code, a captcha, a third-party origin outside the allowlist, a destructive action the plan never executes), and some pages are refused by the origin allowlist. This story therefore delivers a weaker but testable guarantee: **every step is accounted for** — either `bound` with a locator and a passed pre-action check, `not_applicable` with a recorded reason, or `unbound` with a closed reason — and **any** `unbound` step keeps the script `draft` and is never guessed. "Every step bound" is true only of scripts that reach `active`. No section of this plan may be read as promising that generation always produces a complete script, and no code path may invent a binding to make a script look whole.

**Second honesty note (no decision needed, `[INFERENCE]` on the ordering).** Plan 13's task order is T4 (stability) before T5 (PR), while 00 §8.11 (`plans/00-overview.md:315`) says `active` is reached "after merge". Both hold here: T4 builds the recorder, the pure policy and the `activate` gate; the three greens that **activate** a script are post-merge runs, and any pre-merge greens are evidence only. This plan never flips a script to `active` on pre-merge runs.

**Phase (CR-D-2).** G2 only, index wave 21 (`plans/features/README.md:560`). Servers, memory and repair screens are G3 and are not designed here; the `scripts` navigation entry already exists at `phase: 'G2'` (`apps/web/src/app/shell/nav/nav-registry.ts:125-134`), so this story adds no navigation row.

**Non-goals.** Any server-side browser, host, sandbox or execution of the generated code, now or later (A5, `plans/13-product-phases.md:31`); element profiles and the accessibility-subtree capture (13.6.1); locator-drift classification, repair candidates, replay (13.8.x, 08.3, 08.4.3); `evidgate run` and local execution (13.5.2); the catalog's draft/dry-run/merge machinery (03.6.1) — this story calls 03.4.2's writer, not 03.6.1's draft lifecycle; the annotation **format** (`03.1.1`, 00 §7) and its read path (`04.3.2-T1`), both consumed; the reporter (04.3.1-T1, merged); the gateway, its provider, its budget and its metering (08.5.1); redaction, opt-in and the credit ledger (08.5.3, 08.5.5); the artifact upload protocol, sensitivity classification and the secret scan (06.1.2, 06.2.1–06.2.3); mobile scripting (G4); and any model id, provider name, price or credit amount in code — every one of those reaches this plan only as a config key (§7, `OI-13-513`).

**Prior art (owner rule, 2026-10-27; vendor-neutral, approach only).** (1) *Locator strategy*: the Playwright locator and best-practice documentation, read for the ordering that keeps a locator resilient to DOM churn — role and accessible name first, test id next, visible text next, CSS last, XPath and positional selectors discouraged — and for the rule that a locator must match exactly one element (strict mode). Taken: the policy order of §2 AC4 and the "an ambiguous match is a failure, not a tie-break" rule. Deliberately not followed: the code-generator's recorded-selector defaults, because this story must not emit positional selectors even as a fallback. (2) *Browsing scope*: an agent-driven browser's origin allowlist/blocklist options are documented as **guardrails, not a security boundary**, and explicitly do not constrain redirect destinations or alternative loopback/metadata addresses. Taken: the allowlist is checked on every navigation **and** every redirect hop, private/loopback/link-local/metadata ranges are refused, and the real boundary is that the session runs on the customer's infrastructure — never a server-controlled browser. Deliberately not followed: wildcard-port forms (`http://localhost:*`), which are wider than an approved environment, and any design that treats a blocklist alone as sufficient. (3) *Stability gating*: no third source was needed; 00 §8.11 and FR-13-5 fix the rule, so the "3 of 3 on one build, green-on-retry is flaky" wording is the area plan's, not an outside convention.

## 2. User stories and acceptance criteria

- As a test maintainer, I take an approved manual case, point `evidgate generate` at the project's approved environment, and get a draft Playwright script whose steps are bound with checks I can see — plus an explicit list of the steps that could not be bound and why.
- As a test maintainer, I know that nothing the generator emits uses absolute XPath, `nth()` or any other forbidden pattern, and that the lint that proves it runs on my machine before anything is uploaded.
- As a project admin, I can see which scripts are draft, active or flaky, how each of the three stability runs went on which build, where the pull request stands, and whether a model was ever asked to help bind a step.
- As the platform, I can prove that no page content, cookie, token or captured pixel left the customer's machine unless the tenant had opted in, that a model was only ever asked to choose from a list I built, and that a refusal left no send, no debit and no partial script.

Every criterion below has a named proof in §9 and an owning sub-task in §10. Numeric caps, thresholds and vocabularies marked `[INFERENCE]` are build defaults pending the OI row named beside them, never measured product facts.

## 6. States and transitions

`generated_script` — the canonical sentence of 00 §8.11 (`plans/00-overview.md:315`) is adopted verbatim: `draft → active | flaky → retired`, with `draft` the PR candidate, `active` needing 3 of 3 green runs on one build **after** merge, `flaky` "set or cleared by the run policy", and `retired` terminal and never run again. Read as edges with `[*] → draft`: `draft → active` (only through route 8 or 7, with merge evidence and three greens on one build), `active ↔ flaky` (run policy only, `OI-13-516`), `flaky → retired` (terminal). **No edge returns to `draft`** — a re-generation is a new row for the same case, so the old row's history stays readable — and **no `draft → retired` or `active → retired` edge is claimed today** — `OI-13-516` proposes exactly those two as an 00 §8.11 refinement (so a superseded `active` script and an abandoned `draft` have a way out instead of accumulating), and until the owner signs it off the code implements the canonical set only, an abandoned `draft` staying `draft` and being superseded by a newer row. The platform writes `flaky` when the last three attributable runs of one build contain a green-on-retry or a red, and clears it when three consecutive greens on one build arrive; a human never types `flaky` and no route accepts it.

**Closed reason vocabulary (one list, used by §2, §4, §5 and §9 — finding S7):** `binding_state = bound` carries no reason; `not_applicable` reasons are `navigation_only`, `data_setup`, `assertion_on_absence`; `unbound` reasons are `ambiguous_match`, `no_candidate`, `element_not_reached`, `origin_refused`, `model_unmapped`, `pre_check_failed`, `capture_unavailable`. **Aborting the whole generation** (CLI exit `3`, nothing uploaded, no script row) is reserved for the CLI `error.code` values of §3/§8 — `seed_unreadable`, `playwright_unavailable`, `origin_not_allowed` (AC3/AC19), `exploration_failed`, `locator_policy_violation`, plus the existing `usage`/`missing_config`/`invalid_config`/`transport` — and **no step reason ever aborts**. `origin_refused` is a step-level reason, not that abort code: it marks exactly one step whose target element sits on an origin outside the allowlist (a third-party embed, an iframe or a payment widget the step needs), so the session refuses that element, records the reason and continues with the remaining steps; `origin_not_allowed` is the session-level abort, raised when the session itself would navigate or request off-origin. Every other step reason marks **one step** and keeps the script `draft` (AC7). `retire_reason` (route 9) is its own closed set: `superseded`, `obsolete_case`, `replaced_by_new_generation`, `withdrawn`.

Steps have no lifecycle machine: `binding_state` is an outcome of one generation and is immutable afterwards; a re-bind is a new script row. The projection rows `generated_script_run` have no transitions either — `outcome` is what the run was, and the "window" is computed by ordering, never stored as a moving state.

`pr_state`: `not_created → open → merged | closed`. A `closed` PR without a merge leaves the script `draft`; the next request opens a **new** PR on a new ref (never a force-push over a reviewed branch). A `merged` PR whose script content later changes is a new script row, so `pr_state` never moves back from `merged`.

`project_testability_snapshot` has no state: one append-only measurement per score, the latest wins for reads (`unavailable` is a value with a reason, never a `0`).

Progress for the caller: the CLI reports its own phases (`resolve → explore → bind → lint → upload`) on stderr as `evidgate: …` lines and, with `--json`, one line at the end (AC6); the server has no progress route for this story because generation is not a server job.

**Trust boundaries and five abuse cases.** Browser (customer machine) → origin allowlist → bounded exploration → locator candidates → [optional] redaction + gateway → index-only answer → live re-validation → emitted file → lint → server-side lint → artifact store (opt-in) → PR. (1) A hostile page tries to make the model emit a malicious selector: the model cannot emit a selector at all, only an index, and the chosen index is re-checked live (AC8). (2) A page tries to make the session walk into `169.254.169.254`, a private range or a redirect to another host: refused per hop, with no alternative-address retry (AC3). (3) A page or a case step carries a credential: the locator scan and the capture redaction refuse it before storage, and storage state is never written (AC12). (4) A foreign-org or sibling-project id in any route: scope + RLS + composite FKs make it `404`; a scoped credential naming another project is `403 project_scope_mismatch` (AC14). (5) A credit, opt-in or kill-switch refusal must leave no send, no debit and no binding: preflight refusals write no row, and in-job refusals are asserted by a counting provider stub (AC13). The model is never the enforcement authority — the pre-action check and the policy are.
