## 1. Goal and non-goals

**Goal.** Replace a vendor claim with a measurement for the one question the G4 mobile decision cannot be made without: **does an exploration that a model performs through `mobile-mcp` become a determinism-preserving `mobilewright` script that runs with no model in the loop, and at what repeatability and cost?** Two days buy a pinned environment, a pre-registered 10-task matrix on one Android emulator and one iOS simulator, an honest measurement record, a per-package licence and transfer inventory, and a go / no-go memo.

**Area-plan acceptance.** "10 real tasks on one Android emulator and one iOS simulator, each run twice: first driven by a model through mobile-mcp, then replayed as a mobilewright script without a model; pass rate, time per step, model cost and repeatability are recorded; a memo states whether a model-driven run converts to a deterministic mobilewright script, the licence status of every driver in the dependency tree (the `mobilecli` driver is FSL-1.1-ALv2, CR-D-2 §7), and what `DECISIONS.md` §7 and ADR-0002 / ADR-0005 would need" (`plans/13-product-phases.md:213`). The clauses are AC1–AC7 below.

**What this story is.** A measurement whose artefact is a document. T1 installs, pins, runs and records; T2 analyses, inventories licences and transfers, and writes the memo.

**What this story is not — and cannot become.** No production code, no `packages/adapter-mobile` (the workspace holds `adapter-playwright`, `adapter-junit`, `cli`, `sdk`, `test-fixtures` and nothing mobile — verified by listing `packages/`), no new dependency in any repo `package.json` (so no ADR-0002 row and no licence-gate change is caused by this story), no contract file, no migration, no endpoint, no permission, no tenant path, no artifact kind, no Worker job. The mobile producer stays G4 and is decided by the memo, not by this plan (`plans/04-ingestion-adapters.md:228`, `:307`; `docs/decisions/CR-D-2-direction-a.md:186`; `plans/00-overview.md:123`). `adapter-mobile`'s shape appears here **only** as a proposal carried inside the memo (§3), because a shape proposed in a 2-day spike that is then treated as agreed is exactly the failure mode 00 §12's DoR exists to prevent.

**Adopted, not invented.** (a) The web precedent for "a run is green" and for stability counting is 3-of-3 on one build (`plans/13-product-phases.md:66`), so a script is called *deterministic* here only when it passes **3 of 3** replays on the same build with no model — one replay cannot distinguish deterministic from lucky. (b) Metrics are never fabricated: a leg that cannot run is recorded `not_measured` with a reason, never `0` and never a pass (T60, `plans/features/README.md:119`). (c) The engine version is pinned, never `latest` (`plans/05-runs-orchestration.md:51`; `docs/decisions/CR-D-2-direction-a.md:160`). (d) Nothing of the customer's is touched: no tenant, no token, no customer app, no customer data (`docs/decisions/CR-D-2-direction-a.md:168`; DECISIONS §7, `:140-144`).

**Verified starting facts (read 2026-11-09, primary sources linked in §7).** Four findings shape the protocol, and one of them corrects the plan's working assumption:

1. **There is no "export the MCP session as a script" feature.** The vendor documents the conversion as a *prompted* workflow: the agent explores through Mobile MCP, then the same agent writes the test in the same session ("An agent session is not a test", `https://mobilewright.dev/guides/mobile-ui-testing-with-claude-code/`, updated 2026-11-01; full guide `https://mobilewright.dev/docs/guides/mobile-mcp`). The recorder (`npx mobilewright codegen`) records **human** clicks on a live screenshot, not an agent's session (`https://mobilewright.dev/docs/guides/codegen.md`). The agent CLI prints the exact test call for every action it runs ("Collect these lines and you have a test", `https://mobilewright.dev/docs/agent-cli/introduction.md`). So the measurable question is not "is there a converter" but **"does an agent-authored script, written from the session, replay deterministically, with how much repair, at what cost"** — and the memo must name which of the three paths it measured (AC5).
2. **`mobilecli` (FSL-1.1-ALv2) is in the default tree and cannot be avoided by installing fewer packages:** `mobilewright@0.0.68` depends on `@mobilewright/driver-mobilecli@^0.0.68` **and** `@mobilewright/driver-mobilenext@^0.0.68`, the mobilecli driver pins `mobilecli@1.0.22` exactly, and `@mobilewright/cli@0.0.68` also pulls the mobilecli driver. The Apache-2.0 alternative (`driver-mobilenext`) targets the paid Mobile Next Cloud (⚠️ terms unread; `docs/decisions/CR-D-2-direction-a.md:157`).
3. **The pin is exact where it matters and caret where it does not:** `@mobilenext/mobile-mcp@1.0.16` depends on `mobilewright` **`0.0.68`** (exact) and `playwright` **`1.63.0`** (exact, inside mobilewright); but mobilewright ranges its own `@mobilewright/*` packages as `^0.0.68`, so **only a committed lockfile** makes the tree reproducible. The spike keeps that lockfile outside the repo and records the resolved tree instead (AC6).
4. **Engines are compatible but untested at our version:** mobilewright, its drivers and its CLI require Node ≥ 22.12.0, mobile-mcp requires ≥ 20, and the repo pins `node >=26 <27` (`package.json` `engines`), while the publisher built and tested these versions on Node 24.22.1 (registry `_nodeVersion`). That is a ⚠️ to record, not a blocker.

**Prior art (owner rule, 2026-10-27).** Mature-project sources read, approach only, no text copied: (1) *mobilewright* (Apache-2.0) — taken: the agent-explores-once / script-runs-without-a-model split as the hypothesis to test, and the accessibility-tree-first locator priority (`getByTestId` > `getByRole` > `getByLabel` > `getByText`) as the locator census this spike counts; deliberately not followed: treating the vendor's own reports as evidence (no pass-rate numbers are published) and codegen as the primary conversion path, because it records a human, not the model. (2) *mobile-mcp* (Apache-2.0) — taken: it is the driver the plan fixes and its tool list defines what a model-driven step can be (element list, tap by ref, screenshot, logs); deliberately not followed: the screenshot-first fallback as a default, because every image-bearing call is a data-transfer event to be counted, not a convenience (T57). (3) *Mobile Next's Milliways app* — taken: one cross-platform app with intentionally placed bugs is a fairer matrix than two unrelated apps; not followed: redistributing its binaries (its licence is unstated, §3). Budget: 6 sources, 3 projects; no further searches in T1/T2 unless a pin disagrees with the registry at install time.

**Non-goals.** Any mobile product work (real devices, device farms, cloud providers, CI wiring, app signing, store builds); `adapter-mobile` implementation, its capability document, artifact kinds, device lease or port limits (`04.5.1`, `06.3.5`, `05.8.1`); mobile healing (`08.9.1`); the 13.7.2 fallback (OCR, visual locators, gateway budget, corpus evaluation); drift classification (13.8.1); web/Playwright behaviour; the platform gateway, credits or metering code (`08.5.1` is partial, `STATUS.md:282`); every screen and design file.

## 2. User stories and acceptance criteria

- As the owner, I can decide G4 mobile go / no-go from numbers produced on one machine in two days, and I can see which numbers are missing instead of reading a vendor's claim as one of mine.
- As the tech lead, I can point at a pre-registered task list, prompts and thresholds frozen **before** the first run, so a favourable result cannot come from quietly dropping the tasks that failed.
- As the security and legal reviewer, I can see every package in the installed tree with its licence verdict, every host the harness contacted, and how many model calls carried an image — and whether that is enough for DECISIONS §7 and ADR-0005, or not.
- As the G4 implementer, I read one memo section and know which `adapter-mobile` capability fields the execution surface can actually supply (`step_events`, `capture_control`, element tree, video, per-step timing) and which it cannot.

Every criterion has a named proof in §9. Thresholds marked `[DECISION]` are proposals for the owner (OI-13-560); `[INFERENCE]` marks a build default. No refusal code is invented: the spike emits no wire response.

## 4. Data model and migrations

**No table, no migration, no artifact, no bucket, no spool, no index.** The mobile spike writes nothing into the platform: there is no tenant, no `org_id`, no run, no producer slot, no evidence revision. **No migration number is reserved or implied**; if a later G4 lane needs one it takes the next free number at implementation, never a number named here.

**The two documents are the deliverable, and they are docs, not data.** Both live in the `decisions/` folder that `docs/README.md:13` already defines for a story-scoped owner-facing decision input ("the criteria document and, later, the decision memo for the same story id"), so this story introduces **no new documentation path** and no row is owed to `docs/README.md`'s table (`:3`):

| File | Content | Bound |
|---|---|---|
| `docs/decisions/13.7.1-mobile-spike-memo.md` | the go / no-go memo: the answer to the conversion question, the pre-registered metric and the measured value, cost per deterministic test, the `adapter-mobile` capability evidence, the DECISIONS §7 / ADR checklist, conditions and what would flip the verdict | ≤ 400 lines, one decision, every number carries the measurement row id it comes from |
| `docs/decisions/13.7.1-mobile-spike-measurements.md` | the raw record: pin table, app commit + checksums, the frozen 10-task list and prompts, 40 model rows, 60 script rows, per-script locator census, dependency/licence inventory with verdicts and integrity, egress hosts, image-bearing call count, cleanup evidence | machine-checkable tables; one row per run; no customer identifier, no secret, no token, no email address |

**Retention, stated plainly.** The measurements are aggregates over an Evidgate-owned app and a public sample app; they contain no personal data, so their retention is the repo's own (they stay with the decision they support and are edited or reverted like any document — 00 §11 governs platform data, not documentation). The **scratch** data — lockfile, `node_modules`, app builds, screenshots, videos, logs — is deleted at T2.3 and never committed: screenshots and videos are `sensitive` by default even when they show a sample app (T57), so committing one would be a policy violation with no upside. If a review asks to see one, it is attached to the PR discussion out of band, not committed.

**Idempotency/replay.** Re-running the matrix is a fresh measurement with a new date stamp; rows are never overwritten, so a second run appends and the memo cites the run it used. This mirrors the append-only instinct of the profile store without borrowing its schema (nothing is stored).

## 5. API shapes (commands, queries, endpoints)

**Zero endpoints, zero commands, zero queries, zero permissions, zero wire errors.** The spike runs on a developer machine outside the platform: no route, no handler, no principal, no tenant scope, no `openapi.yaml` change, no SDK regeneration, no `apps/web` segment. The only interfaces are local: an MCP server over stdio (`@mobilenext/mobile-mcp`), the `mobilewright` CLI, and one throwaway harness script in the scratch directory.

The **measurement record is the one shape a reviewer can check**, so it is fixed here (it is a document schema, not a wire contract):

```json
{"run_id":"13.7.1/2026-11-10/r03","platform":"android|ios","task_id":"T01..T10",
 "leg":"model_a|model_b|script_r1|script_r2|script_r3",
 "outcome":"green|red|harness_error|not_measured","reason":null,
 "started_at":"<ISO-8601>","wall_ms":0,"steps":[{"n":1,"action":"tap|fill|swipe|press|assert",
 "locator":"testid|role|label|text|coords|none","locator_value":"<redacted>","ms":0}],
 "model":{"provider":"<name>","model":"<pinned>","tool_calls":0,"tokens_in":0,"tokens_out":0,
 "usd":0.0,"rate_card_ref":"<url + read date>","image_bearing_calls":0},
 "script":{"path":"tests/t03.spec.ts","repairs":0,"replay_of":"model_a|model_b"},
 "capability_evidence":{"step_events":true,"element_tree":true,"engine_version":"0.0.68",
 "cancel":true,"capture_control":false},
 "egress_hosts":["registry.npmjs.org"],"device":{"name":"<avd|simulator>","wiped_at":"<ISO-8601>"}}
```

A row must be present for **every** cell of the matrix (20 pairs × 5 legs = 100 rows); `not_measured` rows exist precisely so the shape is complete without a fabricated number. Locator values are redacted to their kind and length class in the committed document (a test id or a label of a public sample app is not personal data, but the rule is stated once and applied to every row so no future run can leak a customer's string by accident).

**Refusals.** There is no 4xx: the harness is not a service. The only negative outcome is an outcome value — `not_measured` with a closed reason: `toolchain_missing`, `app_build_failed`, `device_unavailable`, `model_refused`, `harness_error`, `clock`. A pair that errors twice is recorded `red`, not retried again (no unbounded retries, DECISIONS §5.2 `:105`).

## 6. States and transitions

**No platform state machine is added or touched.** `run`, `case_attempt`, `generated_script`, `incident`, `healing_switch`, `element_profile` all keep their 00 §8 shapes; nothing here reads or writes one. Three closed vocabularies live in the documents and nowhere else:

- **Per-run outcome** ∈ `green | red | harness_error | not_measured(reason)`, with `not_measured` never counted as a pass and never converted to `0` (T60). A run that is green under the model but red under the script is two rows, not one verdict — collapsing them is how a spike lies.
- **Per-script determinism** ∈ `3/3 | 2/3 | 1/3 | 0/3 | not_measured`; the memo's threshold applies to this value, not to a mean of replays.
- **Memo verdict** ∈ `go | no-go | conditional`, where `conditional` **must** name the condition, the measurement that would clear it, and the receiver task. There is no "probably" state, and `[DECISION] proposed` marks every recommendation.

**The decision chain, so no reader mistakes the memo for a decision.** spike run → measurement rows → memo (findings + proposal) → **owner decision** (OI-13-560/562/563) → G4 tasks (`04.5.1`, `06.3.5`, `05.8.1`) — or nothing. `healing_switch` (`08.6.3-T1`) is not involved because no apply path exists and no runtime capability ships (T33, `plans/features/README.md:88`).

## 7. Jobs and integrations

**No outbox task, no schedule, no Worker job, no queue, no database.** Everything runs synchronously on one machine in one scratch directory; if the machine dies the measurement is lost and re-run, which is acceptable for a two-day measurement and would not be for a product.

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** none. There is no route, handler, command, query, permission or principal: the spike runs on a developer machine outside the platform, issues no token, opens no tenant scope and cannot read or write a tenant's data. The nearest platform surface is the future producer identity, which already exists as `ci_producer` `{run:create, event:write, artifact:write}` (`contracts/permissions.json:169-173`) — no permission is added, widened or moved by this story or by the memo. If a later surface ever exposes spike data over HTTP it must obey the usual rule (no new permission without a catalogue row).
- **Retention/deletion:** the spike writes **no platform data** — no row, no artifact, no bucket object, no spool file, no migration. The two documents of §4 are repo documentation retained with the decision they support and edited or reverted like any doc; they contain aggregates and public-app locators only, never a customer identifier or a secret. The scratch directory, app builds, screenshots, videos and logs are deleted at T2.3, and the devices are erased and deleted; deletion of the memo is a normal docs revert and leaves nothing behind on any device or bucket.
- **Telemetry:** none is emitted by the spike — no metric, no trace span, no audit record, no `security_event`, because there is no platform process to emit from. The measurements file **is** the record, and it is deliberately shaped like the numbers the platform will later meter: device wall-clock minutes (`device_minutes`, `plans/12-pilot-commercial.md:101`) and tokens per exploration (the `healing_llm_call` columns of T30, `plans/features/README.md:85`). That is a data sample for `12.3.1`, not a second telemetry path.
- **Failure path:** there is no caller and no operator surface, so failure is a recorded outcome, never an envelope: `not_measured` with a closed reason (`toolchain_missing`, `app_build_failed`, `device_unavailable`, `model_refused`, `harness_error`, `clock`), a step that exceeds its timeout recorded `harness_error`, and a pair that errors twice recorded `red` rather than retried. The reader's failure path is the memo: a partial matrix produces a `conditional` verdict that names the missing measurement and what would clear it — never a `go` on absent data, and never a wordless silence.

## 11. Rollout

1. **Nothing ships, so there is no flag, no migration order and no rollback lever in the product sense.** The "rollout" is a sequence of commits on one docs branch: freeze (T1.3) → measurements (T1.4) → inventory (T2.1) → memo (T2.2) → cleanup + hand-over (T2.3). The freeze commit must be an ancestor of the measurement commit; that ancestry is the audit trail that stops a later reader from believing the protocol was written after the results.
2. **Monitoring during the spike:** the harness writes one line per run to its own log and one row to the record; a run that exceeds its timeout is killed and recorded `harness_error`. There is no dashboard, no metric and no alert because there is no service; the memo's "what would flip this" section is the operator note.
3. **Rollback:** delete the branch or revert the two documents. Nothing else exists to unwind — no device, no bucket, no table, no dependency. If a leak is suspected (a screenshot with a credential, a log with an API key), the rule is the same as for any incident: delete the artefact, record what was exposed in the PR, rotate the key (10.7.1's runbook pattern) — the measurements and the memo are aggregates and never contain the key by construction.
