## 1. Goal and non-goals

**Goal.** A tenant-scoped, append-only usage ledger where each metered metric yields exactly one deduplicated row carrying quantity, applied price and amount; a versioned rate card with per-pilot overrides; quota counters that warn at 80 % and block at 100 % with an explicit error; and an idempotent roll-up feeding statements and the quota screen.

**Non-goals.** Emitting metering events in ingest (04.8.1-T1) and storage metering (06.5.2-T1/T2) — this story owns the *schema they write into* and the shared `IQuotaGate`, not their emitters; invoicing (12.4.1-T2); the quota UI (09.7.1 — this story supplies the data contract); automated billing, dunning, payment gateway (V3); published prices (O5 stays `[OPEN]`).

## 2. User stories and acceptance criteria

- As the `billing_operator`, I re-run a closed period's roll-up and get identical totals, and every invoice reconciles to ledger rows + adjustments, so the ledger is the only billing source (D3).
- As ingest (04.8.1), I ask one `IQuotaGate` call per batch whether to proceed, and a retried batch never double-counts (T50/T53).
- As a `tenant_admin`, I see my usage per metric against limits, with unmetered metrics shown as "unavailable", never 0 (T60).

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Inserting two metering events with the same `(org_id, billing_key)` yields exactly one `usage_ledger_entry` row; the second attempt reports `duplicate` |
| AC2 | A correction is an adjustment row with `adjustment_of` pointing at the original; the original row is byte-identical afterwards and both appear in the period statement |
| AC3 | `UPDATE`/`DELETE` on `usage_ledger_entry` by the app role raises a permission error (append-only enforced in SQL, C6) |
| AC4 | At 80 % of a project quota the counter sets `warned_at` and the gate returns `warn`; at 100 % new writes get `block` → 429 `quota_exceeded` + `Retry-After`, while a run whose upload already committed completes normally |
| AC5 | Two concurrent batches racing the last unit of quota leave `quota_counter.used ≤ limit` (atomic conditional increment) |
| AC6 | Re-running `usage_rollup` for a closed period reproduces identical totals (NFR-12-1); the reconciliation query reports gaps (known usage, no rows) and duplicate `billing_key` attempts |
| AC7 | Price resolution picks the org override row before the `org_id IS NULL` rate-card row; changing a price never mutates amounts on already-issued rows (T44) |
| AC8 | A metric with no metering source yet returns `null` in `GetUsageSummary` with `unavailable_reason` (T60) |

## 4. Data model and migrations

All in module `Evidgate.Modules.Usage`; DbUp scripts, run as the owner role:

**`usage_ledger_entry`** — `id uuid` (UUIDv7, app-generated), `org_id uuid not null`, `project_id uuid null` (org-level rows: support hours), `metric text not null check (metric in ('results','artifact_gb_month','egress_gb','ai_tokens','support_hours','runner_minutes','device_minutes'))`, `quantity numeric not null`, `unit text not null`, `period text not null` (`YYYY-MM`), `billing_key text not null`, `occurred_at timestamptz not null`, `price_ref uuid null` → `(org_id, id)` on `usage_price`, `amount numeric null`, `currency text null`, `adjustment_of uuid null` → composite FK `(org_id, adjustment_of)` → `usage_ledger_entry (org_id, id)`, `reason text not null when adjustment_of is not null`, `created_at`, `updated_at`, `version`.
Constraints: `unique (org_id, id)` (T3), `unique (org_id, billing_key)` (T43), `check (amount is not null or price_ref is null)` optional — unpriced rows allowed while O5 is open (amount `null`, not 0, per T60). Indexes: `idx_ledger_period (org_id, project_id, period, metric)` serving every roll-up/summary filter (P4); `idx_ledger_billing_key` is covered by the unique. Append-only: migration issues `REVOKE UPDATE, DELETE ON usage_ledger_entry FROM <app_role>`; inserts via `ON CONFLICT (org_id, billing_key) DO NOTHING` in one statement (P2).

**`usage_price`** — `id uuid`, `org_id uuid null` (NULL = global rate card, non-NULL = per-pilot override; T44), `metric text not null`, `unit_price numeric not null`, `currency text not null`, `effective_from timestamptz not null`, `effective_to timestamptz null`, `included_quota numeric null`, `version`, `created_at`, `updated_at`; `unique (org_id, id)` (T3); index `idx_price_lookup (metric, effective_from) include (org_id, unit_price)`; resolver query: `WHERE metric=@m AND (org_id=@o OR org_id IS NULL) AND effective range contains @t ORDER BY org_id NULLS LAST, effective_from DESC LIMIT 1` (override-first).
RLS: `org_id IS NULL OR org_id = evidgate.current_org_id()` (built-in catalogue pattern, T46); writes only via the internal command.

**`quota_counter`** — `id uuid`, `org_id uuid not null`, `project_id uuid null` (NULL = tenant-level limit; T45), `period text not null`, `metric text not null`, `used numeric not null default 0`, `limit numeric not null`, `warned_at timestamptz null`, `blocked_at timestamptz null`, `created_at`, `updated_at`, `version`; `unique (org_id, id)` (T3) + `unique (org_id, project_id, period, metric)` where the project-scoped row uses a non-null `project_id` (enforced by a `check` + the unique index `ON (org_id, coalesce(project_id,'00000000-0000-0000-0000-000000000000'), period, metric)`).

**`usage_rollup`** — `id uuid`, `org_id`, `project_id null`, `period`, `metric`, `total_quantity`, `total_amount`, `currency null`, `row_count`, `gap_flag boolean`, `computed_at`, `created_at`, `updated_at`, `version`; `unique (org_id, id)` + `unique (org_id, project_id, period, metric)` (upsert target for idempotent recompute, T43).

Migrations: `migrations/NNNN_usage_ledger.sql`, `migrations/NNNN_usage_price.sql`, `migrations/NNNN_usage_quota_counter.sql`, `migrations/NNNN_usage_rollup.sql` (NNNN = next free numbers at build). Every table gets the standard RLS policy `org_id = evidgate.current_org_id()` via the helpers (T2) + `FORCE ROW LEVEL SECURITY`.

## 6. States and transitions

`quota_counter` per `(org, project, period, metric)`: `used < 0.8·limit` → `warned_at` set on first crossing of 80 % (notification row via outbox) → `blocked_at` set at 100 %; a raise clears `blocked_at` and is audited. The ledger itself has no lifecycle: rows are immutable once inserted (C6); corrections are new rows pointing at the corrected one.

## 7. Jobs and integrations

- **Roll-up schedule**: Cronos daily + on-close-of-period; the fire inserts one `task` row keyed `unique (schedule_name, fire_at)` (00 §5.3) — `usage_rollup.compute`. Handler recomputes `usage_rollup` upserts for open periods; closed periods are recomputed but must produce identical totals (AC6, NFR-12-1). Reports `gap_flag` when the source stream shows usage with no ledger rows.
- **Warn notification**: `quota_counter` crossing 80 % enqueues an outbox row in the same transaction → notification task (email/web UI badge feed for 09.7.1).
- **Emitters**: 04.8.1-T1 calls `RecordUsageBatch` inside the accepted-batch transaction with `batch:<event_batch_id>:<metric>` keys (T50/T43); 06.5.2-T2 emits `artifact_gb_month`/`egress_gb` period rows (`egress_gb` rows stay `null`-quantity until `IObjectStore` exposes egress — T60); `ai_tokens` rows are written by the healing LLM gateway (08.5.x, V2) — the contract is ready, no V1 emitter; `support_hours` rows come from 12.2.1-T5.
- **Consumers**: `IQuotaGate` is referenced only via `Evidgate.Modules.Usage.Contracts` (C-module boundary); 09.7.1 consumes `GetUsageSummary`; 12.4.1/12.5.1 consume reconciliation and ledger reads.

## 11. Rollout

- Merge order: T1 (schema + contracts) first — the M2 bundle (04.8.1 + 06.5.2 + 12.3.1) is sequenced "ledger schema first, then emitters" (README §5.3). Emitters (T2) merge only behind the same release that ships `RecordUsageBatch`; `IQuotaGate` defaults to `ok` when no `quota_counter` row exists (limits land via `RaiseQuotaLimit`/seeded pilot rows — enforcement starts when a limit row exists).
- Monitoring: roll-up reports `gap_flag` and duplicate counts into the weekly review (12.2.1-T4); `blocked_at` events feed the quota screen.
- Rollback: migrations are forward-only; a deploy rollback leaves the tables (append-only, inert without callers); disabling `IQuotaGate` is a config flag returning `ok` — recorded in the runbook.
