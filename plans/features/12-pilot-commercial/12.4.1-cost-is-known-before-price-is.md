## 1. Goal and non-goals

**Goal.** Measure what a tenant actually costs (API/DB share, object GB-month, egress, AI tokens, support hours), turn that into a pricing hypothesis pack with an explicit cost floor, and run manual monthly invoicing that provably reconciles to the ledger — so the O5 decision lands on data, not guesses.

**Non-goals.** Publishing prices (D4 — forbidden until O5 closes); automated billing, dunning, tax handling, payment gateway (V3+); the ledger/quota mechanics themselves (12.3.1); runner-minute billing — customer CI pays its own in V1–V2 (FR-12-10).

## 2. User stories and acceptance criteria

- As the `billing_operator`, I generate a monthly invoice from a documented ledger query, have it checked by a second person, and send a statement the customer can reconcile row by row.
- As the owner, I get an O5 decision pack: measured cost floor per tenant, margin scenarios and willingness-to-pay evidence — and a contract template update once I choose.
- As a reviewer, I can recompute any invoice from `usage_ledger_entry` + adjustments and get the same total.

| # | Acceptance criterion (testable) |

| AC1 | `docs/commercial/cost-per-tenant.md` per pilot shows API/DB share, object GB-month, egress, AI tokens and support hours with the query for each; any unmetered input shows `null`/unavailable with a reason (T60) — never 0 |
| AC2 | `docs/commercial/pricing-hypothesis.md` contains every §4.5 component (onboarding, per-project subscription, concurrency, included quota, AI/artifact overage, support) with a number `[OPEN] O5` and the cost-floor derivation; no invented price appears anywhere (grep check finds no currency figures outside the cost floor and O5 placeholders) |

## 3. Contracts touched

- DECISIONS §8 O5 — this story produces the pack; the *decision* is the owner's and is recorded in DECISIONS §10.
- 00 §2 — invoice/statement reads ride the audited `billing:read` permission (`billing_operator` only); tenant-facing statements are documents, not API surface (V1 manual).
- Rulings T43/T44 — invoice amounts come from `usage_ledger_entry` rows priced at write time; a price change never rewrites an issued row.
- T60 — cost inputs without a source are `null` with a reason.
- Resolved (T69): the append-only `billing_statement` table is accepted; statement issue and adjustments are two-person acts (approver ≠ author, enforced by the `prepared_by <> checked_by` CHECK on `billing_statement` and the audited `billing:write` route on `AdjustUsageEntry`). Writes use `billing:write` on `/internal/operator/billing/*`.

## 4. Data model and migrations

One append-only table in `Evidgate.Modules.Usage` (accepted, T69), migration `migrations/NNNN_usage_billing_statement.sql`:

`billing_statement` — `id uuid`, `org_id uuid not null`, `period text not null`, `statement_no text not null`, `ledger_amount numeric not null`, `adjustment_amount numeric not null`, `total_amount numeric not null`, `currency text not null`, `line_count int not null`, `prepared_by text not null`, `checked_by text not null`, `check (prepared_by <> checked_by)` enforcing the two-person rule (D7), `issued_at timestamptz`, `created_at`, `updated_at`, `version`; `unique (org_id, id)` (T3), `unique (org_id, period, statement_no)`; `REVOKE UPDATE, DELETE` for the app role (corrections are new statements); RLS `org_id = evidgate.current_org_id()` (T2). Index `idx_statement_period (org_id, period)` serves reconciliation (P4).

All other cost data is *read* — no further tables: the cost model is a set of documented Dapper queries over `usage_ledger_entry`, `usage_rollup`, object-usage facts (10.6.1-T3) and capacity counters (10.3.1-T3), with results committed to `docs/commercial/`.

## 5. API shapes (commands, queries, endpoints)

| Operation | Kind | Endpoint | Permission | Behaviour |
|---|---|---|---|---|
| `GetInvoiceWorksheet` | `IQuery<InvoiceWorksheet>` | `GET /internal/operator/orgs/{o}/invoice-worksheet?period=` | `billing_operator` `billing:read`, audited | returns every ledger row + adjustment for the period with `price_ref` context, and the reconciliation sum; deterministic for a closed period (AC4) |
| `IssueStatement` | `ICommand<uuid>` | `POST /internal/operator/billing/orgs/{o}/statements` | `billing:write` (`billing_operator`), audited; two-person (T69) | validates `total = ledger_amount + adjustment_amount` server-side against the worksheet recompute (mismatch → 422 `validation_failed`); inserts `billing_statement`; `Idempotency-Key` via `idempotency_record` (T11) |
| `GetCostPerTenant` | `IQuery<TenantCost>` | `GET /internal/operator/orgs/{o}/cost?period=` | `billing_operator` `billing:read`, audited | five cost lines with `source` and `unavailable_reason` where unmetered (T60) |

No `/v1` customer-facing billing endpoint in V1 (manual invoicing, D7); the customer statement is a generated document attached to email.

## 6. States and transitions

`billing_statement` rows are immutable once inserted; a disputed invoice is resolved by a new adjustment ledger row + a corrected re-issued statement (new `statement_no`), never an edit (area plan §5). Draft → issued is just `issued_at` set at insert time — statements are written only after the two-person check.

## 7. Jobs and integrations

- Inputs: `usage_ledger_entry`/`usage_rollup` + `GetPeriodReconciliation` (12.3.1-T5); per-unit cost counters (10.3.1-T3); object-storage usage facts (10.6.1-T3); support hours already metered (12.2.1-T5); AI-token rows when the V2 gateway emits them (T60 until then).
- Output feeds: O5 decision pack → agreement template update (12.2.1-T1 fill-in) → `usage_price` rows loaded via `LoadUsagePrice` (12.3.1-T3) once O5 closes; margin numbers → 12.5.1-T1 contribution-margin metric.
- No new schedules: invoicing is monthly-manual by design (D7); the worksheet query is deterministic so a re-run at statement time cannot drift.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Audited billing reads (00 §2) | every `billing:read` query writes `audit_log`; no customer artifact/test data is reachable from these queries | `BillingRead_IsAudited`; query column whitelist |
| D7 (two-person rule) | `check (prepared_by <> checked_by)` on `billing_statement`; AC3 requires two named sign-offs | constraint test tries same-name → rejected |
| S1/C1 | all reads parameterised Dapper in `SET TRANSACTION READ ONLY` (C5); no writes from queries | `Queries_RunReadOnly` |
| T60 | unmetered cost lines (`egress_gb`, `ai_tokens` before their emitters exist) are `null` + `unavailable_reason` | `CostPerTenant_UnmeteredLine_IsNull` |
| NFR-12-1 | `GetInvoiceWorksheet` is deterministic for a closed period | AC4 test runs it twice |
| P3/P4 | worksheet = bounded statements over `idx_ledger_period` + `idx_statement_period`; single round trip for the sum | command-count assertion |
| S3 | statements carry amounts and row refs, never secrets; customer names appear only inside the tenant-scoped doc | redaction review |
| Retention | `billing_statement` and ledger rows are accounting records retained per law; excluded from artifact retention/deletion, split recorded in the data map (11.8.1-T3) | data-map row |

## 11. Rollout

- Order: T3 (measurement) → T1 (hypothesis on the floor) → T2 (invoicing live) → T4 (O5 pack) → T5 (V2, M4). The area plan lists T1 before T3 by id, but T1's dependency is T3 — the task `Depends on` cells govern (README §5).
- Monitoring: reconciliation gaps from 12.3.1-T5 are checked before every statement; a `gap_flag` blocks issuing until explained.
- Rollback: statements are immutable documents; a wrong issued statement is corrected by a new adjustment + re-issue, never by deletion.
