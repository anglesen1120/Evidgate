## 1. Goal and non-goals

**Goal.** Turn a letter of intent into a running, paying, measurable pilot: signed agreement + DPA before any upload, a baseline measured for ≥ 2 sprints under frozen definitions, weekly reviews, metered support hours, and a mid-point health check.

**Non-goals.** The ledger schema and quota mechanics (12.3.1); invoice generation (12.4.1-T2); the exit review (12.5.1-T3); automating the agreement or billing (V3); hosted runners/device farm — explicitly in the agreement's "not included" list.

## 2. User stories and acceptance criteria

- As the founder, I sign a paid agreement with a DPA annex before the customer's first upload, so billing and PDPL duties exist before data does.
- As the Tech Lead, I measure the pilot's baseline with definitions frozen before enablement, so the M3 comparison is auditable.
- As the pilot owner's `tenant_admin`, I hit a warned-then-blocked quota with an explicit error and a raise path, never a silent drop.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | For each pilot, `docs/pilots/<pilot>/` contains a signed agreement (scope, price or `[OPEN] O5` marker, payment terms, DPA annex reference, data-handling/deletion terms, success metrics, exit criteria, support expectations, "not included" list) dated **before** the earliest `artifact.created_at` for that org; `scripts/check-pilot-gate.sh <org>` exits 1 otherwise |
| AC2 | `baseline/sprint-1.md` and `baseline/sprint-2.md` per pilot hold raw measurements (triage times per failure, maintenance hours) under the definitions frozen in `metric-definitions.md` v1; `metric-definitions.md` is not edited after the first baseline row (git history check) |
| AC3 | `reviews/week-NN.md` files exist for every week between onboarding and review date; each lists usage, failures, customer labels collected, blockers and next actions |
| AC4 | `support-log.md` rows each carry `hours`, `severity`, `issue`, `started_at`; every row produces a `usage_ledger_entry` with `metric = 'support_hours'` and `billing_key = support:<org>:<issue>` via `RecordUsageBatch` — a retried log entry dedupes to one ledger row |
| AC5 | At 80 % of a pilot quota the warn notification fires (recorded in the review notes); at 100 % new uploads get 429 `quota_exceeded` naming metric, period and raise path, while a committed run finishes (12.3.1-T4 provides the mechanism) |
| AC6 | `reviews/midpoint.md` records continue/adjust/stop with reasons and an owner |

## 3. Contracts touched

- 00 §9.2 — the pilot faces `quota_exceeded` (429 + `Retry-After`) exactly as specified; no new code added here.
- 00 §2 — pilot customer users are ordinary members (`tenant_admin` signs, `qa_engineer`/`viewer` consume); `billing_operator` reads their ledger rows internally.
- DECISIONS §8 O5 — the agreement carries the agreed pilot fee; public pricing stays `[OPEN]` until 12.4.1-T4.
- Rulings T11, T60, T63 — intake dedupe via `idempotency_record`; absent metrics shown as `null`/"unavailable"; onboarding uses the 09.2.1 wizard (progress derived, no wizard-state table).
- Resolved (T69): `RecordUsageBatch` for `support_hours` (12.3.1 §5) runs on `POST /internal/operator/billing/usage` under `billing:write` (`billing_operator` only); the tenant usage read uses `usage:read` (`tenant_admin`, 00 §9.3). The intake contract is unchanged.

## 4. Data model and migrations

None owned. This story *emits* rows owned elsewhere: `usage_ledger_entry` rows for `support_hours` (schema in 12.3.1-T1), and onboarding-time rows created by the product itself (project, CI binding, first run — 02/05). The pilot pack is files under `docs/pilots/<pilot>/`.

## 5. API shapes (commands, queries, endpoints)

| Operation | Kind | Endpoint | Permission | Notes |
|---|---|---|---|---|
| `RecordUsageBatch` | `ICommand<int>` → handler (EF Core write model) | module-contract call; `POST /internal/operator/billing/usage` for manual support-hours entry | `billing:write` (`billing_operator`), audited | body `{entries[]:{billing_key, project_id, metric, quantity, unit, occurred_at}}`; `Idempotency-Key` on the request; dedupe by `unique (org_id, billing_key)`; returns `{inserted, duplicates[]}` |
| `GetUsageSummary` | `IQuery<T>` → Dapper, read-only tx | `GET /v1/projects/{p}/usage-summary` | `usage:read` (`tenant_admin`, T69) | per-metric `used`/`limit`/`warned`/`blocked` for the current period; unmetered metrics return `null` (T60) |
| `GetPilotBaselineReport` | `IQuery<T>` → Dapper | `GET /internal/operator/orgs/{o}/pilot-report` | operator ingress, audited | read-only; joins ledger + run/label data for the weekly review packet |

Status/error codes follow 00 §9.2: 401/403/404 (cross-tenant ids are 404), 422 `validation_failed` per-entry with indices, 429 `quota_exceeded` on a blocked write path.

## 6. States and transitions

None owned. Pilot lifecycle is a documented checklist (`letter of intent → agreement+DPA → onboarded → baseline ≥2 sprints → collection enabled → weekly reviews → midpoint → M3 exit`), not a database state machine.

## 7. Jobs and integrations

- Consumes: `usage_ledger_entry` + `IQuotaGate` (12.3.1), onboarding wizard (09.2.1, T63), DPA/privacy notice/data map (11.8.1-T1…T3), deletion SLA on exit (11.9.1).
- Feeds: the frozen metric definitions and baseline into 12.5.1-T1; support severity expectations into the agreement; friction log into 09.
- No scheduled tasks are created here; the weekly review is a ritual, not a cron.

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Upload before signature | `check-pilot-gate.sh` exits 1 on a seeded fixture (agreement date > first artifact) |

| Support-hours double-log | `RecordUsageBatch` retried with same `billing_key` → `{inserted:0, duplicates:[…]}`, exactly one `usage_ledger_entry` (xUnit `RecordUsageBatch_DuplicateKey_IsIdempotent`, 12.3.1) |

| PDPL | any PD finding in customer material is filed back to the customer (area plan §6) and noted in the review log |

## 11. Rollout

- Sequence: T1/T2 in M1 (agreement template waits on the 11.8.1-T1 DPA); T3–T6 in M3 once 09.2.1 onboarding and 12.3.1 metering exist. A pilot never uploads before AC1's date check passes.
- Monitoring: weekly review files are the operational record; quota warns are re-checked in each review.
- Rollback: a stopped pilot follows the agreement's exit path — artifact deletion per 11.9.1, ledger/statement retained for accounting; no code rollback applies.
