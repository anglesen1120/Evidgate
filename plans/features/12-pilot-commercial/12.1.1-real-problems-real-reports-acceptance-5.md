## 1. Goal and non-goals

**Goal.** Produce evidence, not opinion, about what real QA teams struggle with: ≥ 5 recorded structured interviews, a register of real failure reports collected with provenance and written permission, a pain-to-feature map, a signed-off O1 record (CI + engines), and a screened pilot pipeline with ≥ 2 letters of intent.

**Non-goals.** Signing or onboarding pilots (12.2.1); the usage ledger (12.3.1); pricing (O5, 12.4.1); trademark (12.6.1); any product code — this story ships documents, checklists and decision records only.

## 2. User stories and acceptance criteria

- As the founder, I want proof that pilot candidates have the problem we solve, so V2 is built on measured demand, not enthusiasm.
- As the Tech Lead, I want O1 decided from what pilot teams actually run, so the V1 scope (00 §1.3) is confirmed or corrected before adapter work starts.
- As the compliance owner (11.8.1), I want every borrowed artifact redacted and permitted in writing, so discovery cannot create a PDPL incident.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `docs/discovery/interviews/` holds ≥ 5 interview records, each with date, role (QA lead/engineer), team size, current gate process, triage/maintenance cost answers and consent flag; `scripts/check-discovery.py` exits 0 only when 5 complete records exist |
| AC2 | `docs/discovery/artifact-intake.md` rows total ≥ 1 per interviewed team; every row has `source`, `format` (playwright_json/playwright_html/junit_xml/other), `received_at`, `permission_ref` pointing to a written grant, `redaction_state ∈ none|pending|done`, and `provenance` (who sent it, original system); no row with `redaction_state ≠ done` has a file under `fixtures/discovery/` |
| AC3 | `docs/discovery/pain-map.md` links every pain to ≥ 1 interview id and to the 00 §1.3 scope item it confirms or challenges; a pain with no scope item is marked `[OPEN]` |
| AC4 | `docs/discovery/O1-ci-engine.md` records O1 (GitHub Actions + Playwright TypeScript + one JUnit producer) as confirmed or amended, signed with the names of ≥ 2 pilot-candidate teams whose CI matches it |
| AC5 | `docs/discovery/pilot-pipeline.md` lists 8–10 screened teams with one FR-12-2 verdict (pass/fail per criterion) each, a ranking, and ≥ 2 attached letters of intent |

## 3. Contracts touched

- 00 §1.3 — the interview evidence confirms or challenges the V1 scope decisions; the story produces input to O1, it does not edit 00.
- DECISIONS §8 O1 — closed by AC4; the record names the teams.
- DECISIONS §8 O5 — surfaced pricing signals are captured in the interview register for 12.4.1; no price is committed here.
- [OPEN] If interviews show the assumed JUnit producer is wrong for the pilot pool, a CR against 00 §1.3 is raised from AC3's `[OPEN]` list — the discovery story flags it, it does not decide it.

## 4. Data model and migrations

None. Discovery outputs are files under `docs/discovery/` and redacted fixtures under `fixtures/discovery/` (only after written permission + redaction); no database objects exist before the product schema lands (02.1.1).

## 5. API shapes (commands, queries, endpoints)

None. Tooling is a checker, not a service:

| Command | Effect |
|---|---|
| `scripts/check-discovery.py` | validates AC1 (5 complete interview records), AC2 (intake register fields, no unredacted fixture) and AC5 (8–10 rows, ≥ 2 letters of intent); exits 1 with the failing row ids |

## 6. States and transitions

None. The intake register uses a per-row `redaction_state ∈ none|pending|done` as a checklist field (not a database state machine); `pending|done` is the only allowed path before fixture reuse.

## 7. Jobs and integrations

- Outputs feed: O1 → 04.3.x/04.4.x adapter scope and 05 planning; artifact intake → 04 ingest fixtures and the 08 healing evaluation set; pain map → 09 screen priorities; pilot pipeline → 12.2.1.
- Received artifacts sit in a restricted workspace outside the repo until redacted; only `redaction_state = done` files are copied to `fixtures/discovery/` with the permission reference.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Area plan §6 (pre-DPA handling) | All received material is handled under production-artifact rules before any DPA exists: restricted workspace, redaction before reuse, never uploaded to a third-party tool, deleted on request | AC2 check; register column `permission_ref` |
| PDPL / FR-12-14 | Personal data found in a shared report is reported to the sender as a finding; fixture reuse requires written permission + `redaction_state = done` | AC2; privacy finding log in `interviews/` |
| Retention/deletion | Intake register records `deletion_requested_at` when a sender asks; artifacts are deleted and the register keeps the provenance row only | T2.2 register field |
| 00 §5.7 S3 | Interview notes contain no credentials/secrets; customer secrets in samples are part of the redaction pass | `check-discovery.py` secret-pattern scan on `fixtures/discovery/` |
| Performance | n/a — no runtime code | — |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Fewer than 5 complete interviews | `check-discovery.py` fails naming the missing fields |
| Artifact without written permission or unredacted | register row rejected; fixture file present while `redaction_state ≠ done` → exit 1 |
| Pipeline < 8 screened or < 2 LOIs | check fails; M0 exit gate does not pass |
| O1 not named-team-backed | AC4 review: the O1 file must list ≥ 2 team names whose CI matches the decision |
| Process review | interview guide walked through once on a friendly team before the real series (T1.2) |

- Deliverables are files on `develop`; the M0 exit review reads them directly. Order: T1 and T2 run in parallel from week 1; T3 follows T1; T4 needs both T1 and T2; T5 runs in parallel after T1 starts.
- Monitoring: none (no runtime). `check-discovery.py` is re-run in the M0 gate review.
- Rollback: delete the docs; nothing else depends on them yet. Interviews and permissions, once collected, are kept under the retention rule even if the plan changes.
