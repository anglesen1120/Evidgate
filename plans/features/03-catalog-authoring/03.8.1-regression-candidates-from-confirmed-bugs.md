## 1. Goal and non-goals

**Goal.** From an incident a human labelled `product_defect` (08.2.2, the only ground truth), generate a regression-candidate draft that explains why its assertion matches the observed failure — then prove it with the available run evidence: the candidate must **fail on the buggy build and pass on the fixed build** when both exist as evidence; when a control build is missing, the candidate records an explicit limitation and can never be marked `verified`.

**Non-goals.** Incident creation and labelling (08.1/08.2); the AI generation mechanics and LLM provenance (03.7.1, reused here); artifact storage and download (06.1.2); evidence-revision mechanics (07.2.1); UI surfaces (09.6.1); any auto-merge path — the candidate is still a `draft` that reaches the repo only via 03.6.1's PR flow.

## 2. User stories and acceptance criteria

- As a `test_maintainer`, I click "generate regression test" on a confirmed product-defect incident and get a draft whose assertion is traceable to the actual failure evidence.
- As an auditor, a `verified` mark on a regression candidate is impossible without recorded fail-on-buggy **and** pass-on-fixed evidence.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/incidents/{i}/regression-candidates` on an incident whose `label = product_defect` and `label_source = human` creates one `regression_candidate` + one `draft` (`kind='regression'`, provenance → incident) → 202; on any other label/source → 422 `incident_not_product_defect` |
| AC2 | The generated draft's `content` carries `assertion_rationale`: which evidence fields (`case_attempt` status, assertion message hash, page/artifact refs) the assertion encodes — stored on the candidate row |
| AC3 | When buggy-build and fixed-build evidence revisions both exist, the proof harness dry-runs the candidate against each: fail-on-buggy + pass-on-fixed ⇒ `proof_state = verified`; any other combination ⇒ `failed` with recorded reasons |
| AC4 | When either control build's evidence is missing, `proof_state = limited` and `limitation` names the missing side; a `limited` candidate transitions to `pr_open` like any draft but the PR body carries the limitation and the candidate can never reach `verified` |
| AC5 | Re-requesting generation on the same incident returns the existing candidate (idempotent by `(org_id, incident_id)`), never a second draft |
| AC6 | Candidates whose incident is re-labelled away from `product_defect` by a human are marked `withdrawn` and excluded from lists marked verified |

## 4. Data model and migrations

`migrations/NNNN_catalog_regression_candidate.sql` (T1):

```sql
create table regression_candidate (
  id uuid primary key,
  org_id uuid not null, project_id uuid not null,
  incident_id uuid not null,                  -- resolved via 08 Contracts; not a cross-module FK
  draft_id uuid not null, foreign key (org_id, draft_id) references draft (org_id, id),
  buggy_evidence_revision uuid null,          -- refs resolved via 07 Contracts
  fixed_evidence_revision uuid null,
  assertion_rationale jsonb not null,         -- evidence fields the assertion encodes (AC2)
  proof_state text not null default 'pending'
    check (proof_state in ('pending','verified','limited','failed','withdrawn')),
  limitation text null,                        -- required when proof_state='limited'
  buggy_result text null, fixed_result text null,   -- 'passed'|'failed'|'error'
  created_at timestamptz not null default now(), updated_at timestamptz not null default now(),
  unique (org_id, id),
  unique (org_id, incident_id)                 -- one candidate per incident (AC5)
);
create index regression_candidate_project
  on regression_candidate (org_id, project_id, proof_state, created_at, id);
alter table regression_candidate enable row level security;
```

Invariant enforced twice: the `verified` transition requires `buggy_result='failed'` **and** `fixed_result='passed'` — checked in the domain service and by a `check (proof_state <> 'verified' or (buggy_result='failed' and fixed_result='passed'))` constraint.

## 5. API shapes (commands, queries, endpoints)

| Shape | Type | Endpoint | Permission · codes |
|---|---|---|---|
| `CreateRegressionCandidate` | `ICommand<Guid>` | `POST /v1/incidents/{i}/regression-candidates` | `ai_draft:request` · 202; 422 `incident_not_product_defect`; 409 on a second live candidate for the same incident · `Idempotency-Key` |
| `GetRegressionCandidate`, `ListRegressionCandidates` | `IQuery` (Dapper) | `GET /v1/regression-candidates/{c}`, `GET /v1/projects/{p}/regression-candidates` | `case:read` · cursor pagination |
| `RecordCandidateProof` | internal `ICommand` | invoked by the proof task only (no route) | — · writes `proof_state`, results, `limitation` |
| `WithdrawRegressionCandidate` | `ICommand` | `POST /v1/regression-candidates/{c}/withdraw` | `test_maintainer` (`draft:write` scope) · audited |

Generation delegates to the 03.7.1-T1 pipeline with context = incident evidence allowlist (`case_attempt` statuses, assertion messages, artifact references — never raw artifact bytes; 06 download is not on this path).

## 6. States and transitions

`regression_candidate.proof_state`: `pending → verified | failed | limited | withdrawn`. `verified` is reachable only from `pending` and only with both control results present per the CHECK constraint; `limited` needs a non-empty `limitation`; `withdrawn` is terminal and set by a human or by incident relabelling (AC6). The linked `draft` follows the normal 00 §8.10 machine; `verified` is *not* required for `pr_open`, but the PR body must render `proof_state` + `limitation`.

## 7. Jobs and integrations

- `catalog.regression_candidate_generate` task: calls the 03.7.1 AI pipeline with the incident-evidence allowlist; writes `draft` (kind `regression`) + `assertion_rationale`.
- `catalog.regression_candidate_proof` task: resolves buggy/fixed evidence revisions via 07.2.1's contract (`EvidenceRevisionContract`), fetches `case_attempt` outcomes for the incident's `execution_key`; if both builds present, submits two sandbox dry-runs (03.6.1 `catalog.dry_run_dispatch` reused) and settles `proof_state`.
- Reads `incident` state via `Evidgate.Modules.Healing.Contracts` (08.2.2); artifact **references** only via 06.1.2's contract — no byte downloads on the proof path.
- Webhook/event integration: none new; `withdrawn` propagation rides a reconcile task fired when 08 reports a label change (consumed idempotently by natural key `(org_id, incident_id)`).
