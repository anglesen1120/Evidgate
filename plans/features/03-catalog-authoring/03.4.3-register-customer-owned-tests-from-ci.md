## 1. Goal and non-goals

**Goal.** A customer who keeps tests in their own repository runs `evidgate catalog push` from their own CI with a project credential. The command finds `evidgate.id` annotations and `evidgate.cases.yaml` sidecars in the working tree, and any suite definitions the customer declares, sends them to Evidgate, and the catalog gets stable case identities and appended revisions plus the declared suites with a revision that pins their members. Pushing the same tree again changes nothing. Evidgate never has any access to the repository; the customer's CI decides what leaves it.

**Non-goals.** Any Evidgate-side repository read, webhook or pull request (removed by D-NO-GITHUB); generating tests (13.5.1); resolving provisional import identities (03.1.2); suite authoring in the UI (09); creating a new catalog domain model.

## 2. User stories and acceptance criteria

| ID | Criterion |
|---|---|
| AC1 | `evidgate catalog push` with a valid project credential registers a new annotated case once, assigns no new identity to a renamed/moved file, and appends a revision when the test content changed. |
| AC2 | The second identical push returns an all-`unchanged` report, writes no case, revision or audit-visible change, and exits 0. |
| AC3 | A duplicated id, or an annotation and sidecar that disagree, is reported as a conflict; that file writes no revision and the rest of the tree is still processed (the 03.1.1 rules). |
| AC4 | The report lists registered, renamed, unchanged, missing, conflicts and warnings. A push that looks truncated (no test files, or most active cases vanished) is refused and changes nothing. |
| AC5 | A token without the registration scopes, a token of another project, a malformed or over-cap payload each fail without partial writes. |
| AC6 | `--dry-run` discovers locally and prints which files and how many bytes would be sent, and which suites would be registered; nothing is sent and the exit code is 0. |
| AC7 | The first push of a tree that declares a suite creates the suite and one suite revision pinning its members (the case revisions just registered). An identical second push keeps the same suite id and the same revision (the existing 200 `created: false` answer) and appends no suite, revision, member or edge row. Changing the member set appends exactly one new revision. |
| AC8 | Suite registration needs `suite:write` on the credential; a token holding only `case:write` registers cases but creates no suite, and a suite naming a case of another project is refused (`cross_project_member`, 422) with nothing written. |

## 3. Contracts touched

- `evidgate catalog push` is a new subcommand of `packages/cli` (alongside `gate`, `events send`, `artifacts upload`); register it in the CLI's command table and `contracts/cli.md`. The CLI keeps reading CI environment variables for the declared commit.
- The case and suite surface today is read/patch for cases and create for suites and suite revisions in `contracts/openapi.yaml`. There is **no** HTTP route that registers discovered cases: the only entry point is the in-process `ICaseIdentityService.RegisterDiscoveredAsync` (used by the dev seed and tests). OI-03-17 records the new route this story must add.
- Project credentials: a CI token menu holds only run, event, artifact, decision and suite-plan scopes (migration 0111). Registration scopes `case:write` and `suite:write` are new; OI-03-17.
- Unchanged: the identity rules, sidecar schema `contracts/catalog/sidecar.v1.json`, revision hashing, the `case_import_identity` mapping rules (03.1.2).
- Dependency on 02.11.1: the removal must keep `ICaseIdentityService`, the parsers and the revision hasher. It deletes only the GitHub sync code and routes that called them.

## 4. Data model and migrations

No new table. The registration scope widens the ingest-token scope check, additive and idempotent, in one migration numbered `<next free>` at launch (precedent: migration 0111). Older migrations are not edited.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command (new, OI-03-17) | `RegisterDiscoveredCases` | `POST /v1/projects/{p}/case-registrations` (name `[OPEN]`) | `case:write` | 200 report · 400 · 403 · 404 · 413 · 422 `empty_tree` / `incomplete_tree` / invalid commit |
| Command (existing) | `createSuite`, `createSuiteRevision` | `POST /v1/projects/{p}/suites` (201; 409 `suite_slug_taken` on replay), `POST /v1/suites/{s}/revisions` (201 new, 200 `created: false` for identical content; `members[].case_revision_id`) | `suite:write` | unchanged; called by the CLI for each declared suite |
| CLI | `evidgate catalog push [--dry-run] [--commit <sha>] [--json]` | wraps the first row, then the suite calls | token holding `case:write` (and `suite:write` when suites are declared) | exit 0 · 2 usage · 3 conflicts or refused tree |

Request: commit sha plus the files the CLI chose (path, text, framework). The body reuses the server's `SourceFile` shape and the platform payload caps (00 §5.7) [INFERENCE: exact caps are fixed in T1.1]; a file over the cap fails the call with 413 and names the file. The response is the existing `CaseSyncReport` (registered, renamed, unchanged, conflicts, warnings, missing, reactivated, revisions) plus per-file results, and each registered or unchanged case carries its `case_id` and head `case_revision_id` so the CLI can pin suite members. Suite flow in the CLI, after a successful case registration: for each declared suite, resolve it by slug (create it; a 409 `suite_slug_taken` means it exists, so read it from `GET /v1/projects/{p}/suites`), then post the revision with members resolved from `evidgate.id` to `case_revision_id`. Identical content makes the replay a no-op. The suite manifest format is OI-03-19.

## 6. States and transitions

Case status `active ↔ missing` and rename history are unchanged from 03.1.1. A push is stateless on the client; on the server one registration per project runs at a time under the existing project lock, so two concurrent pushes serialise or the loser reports busy. Replays of the same tree are no-ops. Revision append is idempotent by revision hash.

## 7. Jobs and integrations

No background job. The CLI is the only integration: it walks the working tree, applies ignore rules and caps locally, and uploads over the existing client with retry (the spool used by the other commands may be reused). The customer's CI runs it with a project secret; the quickstart example workflows (09.2.1, 04.2.4) gain one line once this lands. Commit ordering: an older commit applied after a newer one is not prevented by the server today (OI-03-15 a); OI-03-20 records the default.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Untrusted input (DECISIONS F4) | Annotation and sidecar text is parsed with size/type limits, never executed, never used to build SQL or paths | parser tests from 03.1.1 re-run through the new route |
| Least privilege | `case:write` and `suite:write` are separate opt-in scopes, never on a results-only token; the project comes from the token, not the body; a case-only token cannot create suites | `Push_WithoutScope_403`, `Push_OtherProjectToken_403`, `Push_CaseWriteOnly_NoSuiteCreated` |
| Customer source leaving CI | Only files the CLI selects (annotated test files and sidecars) are sent, text only, size-capped; `--dry-run` shows the list before anything leaves | `DryRun_ListsFiles_SendsNothing` |
| Performance (P1/P8) | Server parses before taking the project lock; payload and file-count caps; CLI streams discovery | cap tests, large-tree fixture |

DoR review answers (labelled):

- **Authorization:** `case:write` for cases and `suite:write` for suites, both on a project-scoped credential that is explicitly granted those scopes; tenant and project from the token; cross-tenant ids are 404, other-project tokens 403, a suite member from another project 422. A fork-PR job must not receive this secret (11.2.1 rules).
- **Retention/deletion:** pushed file text is parsed and the derived case rows and revisions follow normal catalog retention; the raw file bodies are not stored beyond what the revision record already keeps (confirm in OI-03-18). Cases are archived, not deleted, when files vanish.
- **Telemetry:** a counter of registrations by result and a histogram of files and bytes per push; no file text, token or customer path in logs; trace attribute for the project id.
- **Failure path:** a refused tree, cap or scope error writes nothing; the CLI prints the code and exits 2 or 3; a transient network error retries and the replay is a no-op, so a retry cannot duplicate.
