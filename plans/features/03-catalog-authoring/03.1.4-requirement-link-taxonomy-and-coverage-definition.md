## 1. Goal and non-goals

**Goal.** Three small definitions that later screens and policies depend on, fixed before their schema exists: (1) an optional `requirement_ref` on `test_case`, or a recorded decision to drop it; (2) `platform`, `level`, `purpose` stored as enum-catalogue fields on suite and template, where mobile *emulation* in a browser counts only as `web`; (3) a single definition of **UI coverage** as *declared executions*: the ratio of declared case × variant executions that have an accepted result, never code coverage, so a Chromium pass never masks a Firefox failure.

**Non-goals.** Requirement management itself, requirement import or sync from Jira or similar (V2 AI drafts in 03.7.1 consume *approved* requirements, not this field); code-coverage tooling; the coverage UI (09, which reads the definition); policy rules that use platform or level (07); changing the 03.2.1 `variant` hash rules.

## 2. User stories and acceptance criteria

- As a QA lead, I can tag a case with an external requirement reference so a failing case points to what it protects.
- As a release manager, I can filter suites by platform, level and purpose.
- As a release manager reading "coverage 80 %", I know it means "80 % of declared case × variant executions have an accepted result", not lines of code.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The decision on `requirement_ref` is recorded in DECISIONS/00 §15 before any migration; if kept, `test_case.requirement_ref` is nullable `text`, max 200 chars, trimmed, no control characters; a case without it behaves exactly as before |
| AC2 | `requirement_ref` is metadata only: changing it never creates a `test_revision`, never changes `revision_hash` or the assertion hash, and never changes a decision |
| AC3 | `suite` and `template` carry `platform ∈ {web, api, unit, mobile}`, `level ∈ {unit, integration, e2e, smoke}`, `purpose ∈ {regression, smoke, release_gate, exploratory}`; a value outside the catalogue returns 422 `schema_invalid` naming the field; defaults are `[INFERENCE]` and listed in section 3 |
| AC4 | A web run whose variant declares a mobile viewport or touch emulation is stored with `platform = web`; `mobile` is accepted only when the runner capability document (00 §10) declares a mobile platform |
| AC5 | The coverage definition appears once in 00 §3 and once in the 09 plan; the read model computes `accepted_executions / declared_executions` over `(case_id, variant_hash)` pairs of the suite revision and returns both numerators and denominators |
| AC6 | A case × `chromium` variant that passed and a case × `firefox` variant with no accepted result give coverage 1/2, never 1/1; an execution that is `missing` or only from an `import` run (03.9.2) is not accepted |
| AC7 | Taxonomy columns are changeable on a suite head only through a new `suite_revision` (immutability, 03.2.1); a template change is a new template `version` |

## 4. Data model and migrations

Migration `migrations/NNNN_catalog_taxonomy.sql`, additive, two parts (T1 part first, T2 part later):

| Change | Detail |
|---|---|
| `test_case.requirement_ref` | `text null`, `check (char_length(requirement_ref) <= 200)`; excluded from the revision hash input; the app role may update it (not an immutable column) |
| `suite.platform`, `suite.level`, `suite.purpose` | `text not null` with default and `check (... in (...))`; stored on the suite head and copied into the `suite_revision` content hash input (so a taxonomy change is a new revision) |
| `template.platform`, `template.level`, `template.purpose` | same checks; templates are content-addressed (03.5.1), so a change is a new version |
| Index | `(org_id, project_id, platform, level)` on `suite` for the list filter (00 §5.7 P4) |

Existing rows get defaults in the same migration; no rewrite of immutable rows (`suite_revision` rows created before this migration keep their old hash; the taxonomy enters the hash input only from `revision_no` created after it, with the hash input version bumped, see section 6). All tables keep `org_id`, `unique (org_id, id)`, composite FKs, FORCE RLS (T3).

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `SetCaseRequirementRef` | `PATCH /v1/projects/{p}/cases/{c}` (`requirement_ref` only) | `catalog:write` | 200 · 422 `schema_invalid` · 404 foreign case |
| Command | `CreateSuite` / revision (03.2.1, extended) | `POST /v1/projects/{p}/suites` | `catalog:write` | 201 · 422 `schema_invalid` on a bad enum |
| Query | `ListSuites` (filters) | `GET /v1/projects/{p}/suites?platform=&level=&purpose=` | `catalog:read` | 200 cursor-paged |
| Query | `GetExecutionCoverage` | `GET /v1/projects/{p}/suites/{s}/coverage?revision=` | `catalog:read` | 200 `{declared, accepted, ratio, by_variant[]}` |

The coverage query is read-only Dapper over the suite revision's members and `evidence_revision` results; it is added in T3 for M2 and is `[INFERENCE]` as an endpoint (the contract change to 00 §9.3 is [OPEN] O-03.1.4-3 until the 09 plan confirms it needs a server-side number).

## 6. States and transitions

No new state. Suite/template states come from 00 §8.10 (T46). Taxonomy fields are part of the revision content: changing one on a suite creates `revision_no + 1` (D4) and the `revision_hash` input version increments so older hashes stay valid and comparable only within the same input version. `requirement_ref` edits are plain updates of a mutable catalogue attribute, audited, with no state change.

## 7. Jobs and integrations

None at runtime. T3 adds a documentation and read-model definition only. The `evidgate.id` annotation and sidecar parser (03.1.1-T1) accepts an optional `requirement` key; a missing key means null, an invalid value is a parse warning on the case, not a conflict. ⚠️ Whether Playwright/JUnit annotations can carry this key without adapter changes is unverified; the sidecar is the guaranteed path.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Authorization | writes need `catalog:write`; reads `catalog:read`; no new permission string | 403 test |
| Tenant isolation | all columns are on tenant tables under FORCE RLS; the coverage query runs in the tenant transaction | isolation test with two orgs |
| Free-text safety | `requirement_ref` is length-capped, rendered as text (never HTML), never fetched or linked automatically | length and control-character tests, web escape test in 09 |
| Privacy | the field must not hold personal data or secrets; the docs say "an id or URL", and the log allowlist excludes it | log-allowlist test |
| P1/P4 | list filter served by the new index; coverage is bounded by suite size | EXPLAIN check, statement-count assertion (P3) |

DoR review answers. **Authorization:** `catalog:write` / `catalog:read`, tenant-scoped. **Retention/deletion impact:** columns live and die with the case/suite rows; no new table; org deletion removes them. **Telemetry:** counter `catalog_taxonomy_rejected_total{field}`; the coverage query is traced with `suite.id` and `variants.count`. **Failure path:** an invalid enum or an over-long reference is a 422 with the field name and nothing is written; a missing evidence revision yields denominator-only coverage (accepted 0), never an error and never a PASS signal.
