## 1. Goal and non-goals

**Goal.** Fixtures are versioned, immutable-on-create `fixture_revision` rows referenced by `suite_revision` — secrets by **name only**, never values (D7). Every run gets its own `(org, project, run)` data namespace with `expires_at`, and a scheduled sweeper cleans expired/orphaned namespaces idempotently, surfacing failures as `cleanup_failed` instead of leaking test data between runs.

**Non-goals.** Seed-data authoring UX and fixture *content* format (Q6, QA Lead); the executor that actually consumes a namespace (05.7.4); secret resolution/vault (11 owns; we store references); the V2 dry-run sandbox namespace consumer (03.6.1 reuses this contract).

## 2. User stories and acceptance criteria

- As a test maintainer, I declare a fixture once and reference a pinned revision from suite revisions, so every run sees the same data definition.
- As an operator, expired and orphaned namespaces are cleaned automatically and failures are visible, so tenant test data never accumulates or leaks across runs.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/fixtures` creates a fixture (`fixture_key`, unique per project); `POST /v1/fixtures/{f}/revisions` appends `revision_no` with `revision_hash`, `seed_version`, `timeout_s`, `cleanup_policy`, `resource_prefix`; create is idempotent by `Idempotency-Key` |
| AC2 | UPDATE/DELETE on `fixture_revision` fails at trigger + `REVOKE` (immutable on create — 00 §8.10); fixture *body/seed* content lives under `body_ref` (artifact or repo path), never inline |
| AC3 | A fixture revision or suite `environment_requirements` field containing a secret-shaped key or value → 422 `secret_value_rejected` (same rule list as variants) |
| AC4 | `IDataNamespaceService.AllocateAsync(run_id)` (contract in `Evidgate.Modules.Catalog.Contracts`, called by 05's run create in the same transaction) inserts `data_namespace` with `expires_at = run_deadline + grace` and `unique (namespace_key)` |
| AC5 | The sweeper (`Cronos` schedule `catalog.namespace-ttl`, one `task` row per fire via `unique (schedule_name, fire_at)`, 00 §5.3) marks expired namespaces `cleaned` after deleting the prefixed resources; a namespace whose run never reached terminal state but is past `expires_at` is still cleaned (orphan rule) |
| AC6 | After N sweeps fail to delete a namespace's resources it becomes `cleanup_failed` and appears on the operator dead-letter view with the attempt count; retries are idempotent (re-running a sweep over the same namespace is a no-op) |
| AC7 | A suite revision referencing a `fixture_revision` of another project (or a non-existent revision) → 422 `cross_project_member` |

## 4. Data model and migrations

`migrations/NNNN_catalog_fixtures.sql`:

```sql
create table fixture_revision (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  fixture_key text not null, revision_no int not null, revision_hash text not null,
  seed_version text not null, timeout_s int not null default 60,
  cleanup_policy text not null default 'drop' check (cleanup_policy in ('drop','truncate','none')),
  resource_prefix text not null,               -- e.g. 'fx_<hash>' namespace prefix the sweeper targets
  body_ref text not null,                      -- repo path or artifact id; content never inlined
  created_by uuid not null, created_at timestamptz not null default now(),
  primary key (org_id, id), unique (org_id, id),            -- T3
  unique (org_id, project_id, fixture_key, revision_no),
  unique (org_id, project_id, fixture_key, revision_hash),  -- dedupe identical content
  foreign key (org_id, project_id) references project (org_id, id)
);
revoke update, delete on fixture_revision from evidgate_app;
create trigger fixture_revision_immutable … raise 'revision_immutable';

create table data_namespace (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  run_id uuid,                                 -- null while orphaned-unknown
  namespace_key text not null, expires_at timestamptz not null,
  cleanup_state text not null default 'active' check (cleanup_state in ('active','cleaned','cleanup_failed')),
  cleanup_attempts int not null default 0,
  cleaned_at timestamptz, last_cleanup_error text,
  created_at timestamptz not null default now(),
  primary key (org_id, id), unique (org_id, id),
  unique (namespace_key),                      -- 03 §4.1
  foreign key (org_id, project_id) references project (org_id, id)
);
create index data_namespace_expiry on data_namespace (cleanup_state, expires_at)
  where cleanup_state = 'active';              -- the sweeper's hot index (P4)
```

- RLS on both: `FORCE ROW LEVEL SECURITY`, `org_id = evidgate.current_org_id()`.
- `resource_prefix` is generated server-side (`fx_<org_prefix>_<namespace_key>`), never client-supplied, so cleanup can only target our own prefixed objects (S4 analogue).
- The sketch above is superseded where the header's recorded deviations say so: the identity table `fixture` precedes `fixture_revision` (a revision's composite key pins org, fixture, project and key), and both tables are persisted with Dapper statements rather than an EF entity; `data_namespace` is unchanged.

## 5. API shapes (commands, queries, endpoints)

| Shape | Endpoint / caller | Permission | Behaviour |
|---|---|---|---|
| `CreateFixtureCommand` | `POST /v1/projects/{p}/fixtures` | `fixture:write` | `Idempotency-Key`; creates fixture_key shell + revision 1 in one tx |
| `ListFixturesQuery` | `GET /v1/projects/{p}/fixtures` | `suite:read` | cursor list (fixture_key, head revision) |
| `GetFixtureQuery` | `GET /v1/fixtures/{f}` | `suite:read` | metadata only; `body_ref` is returned as a pointer, never content |
| `CreateFixtureRevisionCommand` | `POST /v1/fixtures/{f}/revisions` | `fixture:write` | `Idempotency-Key`; secret-shape check → 422 `secret_value_rejected`; `revision_hash` dedupe returns existing revision |
| `IDataNamespaceService.AllocateAsync` | called by 05.1.1 run create (same tx) | internal contract | computes `namespace_key = sha256(org_id‖project_id‖run_id‖counter)`; inserts row; conflict → 409 `namespace_collision` (caller retries with next counter) |
| `FixtureLint` (domain + repo lint) | invoked from `CreateSuiteRevisionCommand` (03.2.1) and fixture paths | — | rejects secret values in suites/fixtures/variants (AC3) |

`namespace_cleanup` task handler (`worker`): claims expired `active` rows `FOR UPDATE SKIP LOCKED` in batches of 100, deletes `resource_prefix` resources, sets `cleaned`/`cleanup_failed`.

## 6. States and transitions

`data_namespace`: `active → cleaned | cleanup_failed` (00 §8.10). `cleanup_failed → cleaned` only by a later successful sweep or operator action; after `cleanup_attempts ≥ 5` the row stays `cleanup_failed` and emits a dead-letter-style operator signal. `fixture_revision`: immutable on create — no transitions.

## 7. Jobs and integrations

- **Sweeper**: Cronos schedule `catalog.namespace-ttl` (every 5 min, jitter); the fire inserts a `task` row with `unique (schedule_name, fire_at)` — the constraint, not a leader, guarantees one task per fire (00 §5.3); handler idempotent by `(namespace_id, cleanup_attempt)` natural key.
- Resource deletion calls the project's storage/database through 05's executor contract — **never inside the DB transaction that marks the row** (P5): the task handler first deletes resources (idempotent by prefix), then commits `cleaned`.
- 05.1.1 allocates namespaces at run create; 03.6.1's sandbox dry run allocates with a tighter TTL (V2).

## 11. Rollout

- Expand-only; sweeper schedule registered but harmless until namespaces exist (05.1.1 lands before runs need them). Order T1→T2→T3, all M2.
- Migration order: `fixture_revision` before any suite referencing it — enforced because suite `environment_requirements` fixture refs are validated at write time (03.2.1-T4).
- Monitoring: `cleanup_failed` count feeds the operator dead-letter view (01.5.1-T4 alert hook); storage growth tracked by 10.
- Rollback: stop the schedule (delete schedule row), revert PR; namespaces remain `active` and cleanable later.
