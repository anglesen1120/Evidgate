## 1. Goal and non-goals

**Goal.** A `suite_revision` fully pins what a run must execute: members (`case_revision` × `variant`), the dependency DAG, shard strategy, retry policy and secret-free `environment_requirements` — content-hashed, immutable once a run references it, superseded by `revision_no + 1` (D4). Variants are content-addressed normalised parameter hashes and never carry secrets (D5).

**Non-goals.** Locking a suite revision into a manifest and allocating namespaces (05.1.1); fixture revisions referenced by `environment_requirements` (03.3.1); the diff *UI* (09.6.1 consumes `GET /v1/suite-revisions/{r}/diff`); quarantine/critical-list semantics (07).

## 2. User stories and acceptance criteria

- As a test maintainer, I evolve a suite by creating new revisions with a visible diff, so runs pinned to old revisions stay reproducible.
- As the platform, a suite definition that is cyclic, cross-project, or contains a secret never becomes a revision.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/suites/{s}/revisions` writes members + variants + edges + strategies in **one** transaction; the response is `(suite_revision_id, revision_no, revision_hash)` and `GET /v1/suite-revisions/{r}` returns the full pinned content |
| AC2 | A member `case_revision_id` belonging to another project (or non-existent) → 422 `cross_project_member`; composite FK is the backstop |
| AC3 | A dependency cycle → 422 `dependency_cycle` with the offending path in `error.details[]`; a self-edge is a cycle of length 1; no revision row is written |
| AC4 | A variant whose params contain a secret-shaped key (`api_token`, `password`, `secret`, `key`, `credential`, `bearer` — case-insensitive) or a secret-shaped value (token patterns, ≥ 20-char high-entropy strings) → 422 `variant_not_secret_free`; identical params after normalisation (key order, defaults, case of enum values, non-identifying keys dropped) map to the **same** existing `variant` row |
| AC5 | Two concurrent `POST /v1/suites/{s}/revisions` produce `revision_no` n and n+1, never a conflict-lost revision (server allocates `revision_no` via `next` per-suite sequence enforced by `unique (org_id, suite_id, revision_no)`) |
| AC6 | Once a run references a revision (05.1.1 sets `status='published'`), any attempt to update/delete it fails (`revision_immutable` trigger + `REVOKE`); edits go to a new revision; a run referencing attempt returns 409 `revision_frozen` where the API would mutate the head |
| AC7 | `GET /v1/suite-revisions/{r}/diff?against={other}` returns member add/remove, variant changes, edge changes and strategy deltas; `GET /v1/suites/{s}` returns `ETag: <head revision_no>` and `If-None-Match` honours 304 |
| AC8 | `environment_requirements` accepts only the declared schema (base URLs, dependency versions, warm-up, `data_isolation: isolated|shared`, `secrets[]` as **names**); a secret value or unknown key → 422; `shared` is stored verbatim for 05.7.3-T4's lock |

## 4. Data model and migrations

`migrations/NNNN_catalog_suites.sql`:

```sql
create table suite (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  name text not null, slug text not null, status text not null default 'active',
  head_revision_id uuid,                      -- filled after first revision
  created_at timestamptz not null default now(), updated_at …, version int not null default 1,
  primary key (org_id, id), unique (org_id, id),
  unique (org_id, project_id, slug),
  foreign key (org_id, project_id) references project (org_id, id)
);

create table suite_revision (
  id uuid not null, org_id uuid not null, suite_id uuid not null,
  revision_no int not null, revision_hash text not null,
  status text not null default 'draft' check (status in ('draft','published')),
  shard_strategy jsonb not null, retry_policy jsonb not null,
  environment_requirements jsonb not null default '{}',
  created_by uuid not null, created_at timestamptz not null default now(),
  primary key (org_id, id), unique (org_id, id),
  unique (org_id, suite_id, revision_no), unique (org_id, revision_hash),
  foreign key (org_id, suite_id) references suite (org_id, id)
);

create table variant (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  variant_hash text not null, params jsonb not null,
  created_at …,
  primary key (org_id, id), unique (org_id, id),
  unique (org_id, project_id, variant_hash),
  foreign key (org_id, project_id) references project (org_id, id)
);

create table suite_member (
  id uuid not null, org_id uuid not null, suite_revision_id uuid not null,   -- T46 surrogate id
  case_revision_id uuid not null, variant_id uuid not null,
  ordinal int not null, required boolean not null default true,
  primary key (org_id, id), unique (org_id, id),
  unique (suite_revision_id, case_revision_id, variant_id),
  foreign key (org_id, suite_revision_id) references suite_revision (org_id, id),
  foreign key (org_id, case_revision_id) references test_revision (org_id, id),
  foreign key (org_id, variant_id) references variant (org_id, id)
);

create table case_dependency (
  id uuid not null, org_id uuid not null, suite_revision_id uuid not null,
  parent_member_id uuid not null, child_member_id uuid not null,
  primary key (org_id, id), unique (org_id, id),
  unique (suite_revision_id, parent_member_id, child_member_id),
  foreign key (org_id, suite_revision_id) references suite_revision (org_id, id),
  foreign key (org_id, parent_member_id) references suite_member (org_id, id),   -- T46 composite FKs
  foreign key (org_id, child_member_id) references suite_member (org_id, id)
);
```

- `suite.head_revision_id` composite FK `(org_id, head_revision_id) → suite_revision` added as a deferred `alter table` in the same file (circular pair resolved by deferring the constraint).
- Immutability: trigger on `suite_revision`/`suite_member`/`case_dependency`/`variant` raises `revision_immutable` once `suite_revision.status='published'`; `REVOKE update, delete` on `suite_member`, `case_dependency`, `variant` for the app role; the `draft→published` transition itself is a one-way UPDATE executed by the run-lock path (05.1.1) — the trigger permits exactly `status: draft→published` and nothing else.
- Indexes: `suite_member` on `(suite_revision_id, ordinal)`; `case_dependency` on `(suite_revision_id)`; `suite_revision` on `(org_id, suite_id, revision_no desc)` for head lookup + diff (P4).
- All tables RLS `org_id = evidgate.current_org_id()`, `FORCE ROW LEVEL SECURITY`.

## 5. API shapes (commands, queries, endpoints)

| Shape | Endpoint | Permission | Behaviour |
|---|---|---|---|
| `CreateSuiteCommand` | `POST /v1/projects/{p}/suites` | `suite:write` | `Idempotency-Key`; slug conflict → 409 `suite_slug_taken` |
| `ListSuitesQuery` | `GET /v1/projects/{p}/suites` | `suite:read` | cursor list incl. head `revision_no` |
| `GetSuiteQuery` | `GET /v1/suites/{s}` | `suite:read` | 200 + `ETag: "<head_revision_no>"`; `If-None-Match` → 304; 404 cross-tenant |
| `CreateSuiteRevisionCommand : ICommand<SuiteRevisionHead>` | `POST /v1/suites/{s}/revisions` | `suite:write` | `Idempotency-Key`; validates everything (AC2/AC3/AC4/AC8) then inserts revision + members + edges in one tx; computes `revision_hash` = `sha256:` of canonical `{members sorted by (case_revision_id, variant_id), edges sorted, shard_strategy, retry_policy, environment_requirements}`; identical content → returns the existing revision (dedupe on `unique (org_id, revision_hash)`), no new `revision_no` |
| `GetSuiteRevisionQuery` | `GET /v1/suite-revisions/{r}` | `suite:read` | full pinned content |
| `GetSuiteRevisionDiffQuery` | `GET /v1/suite-revisions/{r}/diff?against=` | `suite:read` | member/variant/edge/strategy delta (AC7) |

All writes go through the C2 pipeline (authorization → idempotency → handler); `Idempotency-Key` via `idempotency_record` (T11), no permanent unique on client keys.

## 6. States and transitions

`suite_revision`: `draft → published` only (00 §8.10); published = referenced by a run (05.1.1 performs the flip inside its run-create transaction by calling `ICatalogContracts.PublishSuiteRevisionAsync`). `suite.status`: `active | archived`. `variant`, `suite_member`, `case_dependency`: no lifecycle — rows live and die with their revision.

## 7. Jobs and integrations

- No jobs. 03.4.1-T3 registers suite revisions discovered in repo suite-definition files via `CreateSuiteRevisionCommand`'s handler directly (same validation path as the API).
- 05.1.1 locks `suite_revision_id` into the manifest; 05.7.3-T4 reads `environment_requirements.data_isolation`; 07 reads `required` members and quarantine references.
