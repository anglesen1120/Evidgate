## 1. Goal and non-goals

**Goal.** A producer result that arrives with no `evidgate.id` gets a provisional identity keyed by `(producer, suite, name)` so runs still attribute evidence, while no provisional row ever silently merges with an annotated case. Collisions and ambiguous renames stay `conflicted`/`unmapped` until a human (or the single unique-match rule) binds them through the mapping API that 09's UI consumes.

**Non-goals.** The annotated identity itself (03.1.1); revision storage (03.1.3); the UI screens rendering `unmapped`/`conflicted` lists (09.2.1); decision semantics of unmapped evidence (07).

## 2. User stories and acceptance criteria

- As a test maintainer, an imported run with unnamed tests lists them as provisional identities, so evidence is not lost while I decide where they belong.
- As a test maintainer, a same-name collision in a monorepo blocks auto-mapping, so two distinct tests are never merged by a name guess (D2).

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A run reporting test `(producer_id, suite_key, name)` with no annotation creates one `case_import_identity` row `state='unmapped'`; the same key from a later run updates no row (dedupe on `unique (org_id, project_id, producer_id, suite_key, name_hash)`) |
| AC2 | When a commit adds exactly one annotation whose classified name matches a pending key and no other candidate matches in the commit-range, the sync proposes a mapping (`state` stays `unmapped`, `proposed_case_id` set); 0 or ≥2 candidates leave the row untouched |
| AC3 | Two new same-name annotations in one commit → the pending key becomes `conflicted`; `POST /v1/case-import-mappings/{m}/resolve` with `case_id` maps it and returns 200; resolving against a case already bound to a different import key returns 409 `mapping_conflict` |
| AC4 | `resolve` on a `mapped` row is idempotent (same `case_id` → 200 with existing state; different `case_id` → 409 `mapping_conflict`) |
| AC5 | A mapped identity never absorbs an annotated case: resolve does not rewrite `test_case.annotation_id`, historical `test_revision.case_id` re-pointing happens only through this endpoint and is audited |
| AC6 | `GET /v1/projects/{p}/case-import-mappings?state=unmapped|conflicted` lists pending rows with cursor pagination for 09.2.1 |

## 4. Data model and migrations

`migrations/NNNN_catalog_case_import.sql` (appended to the catalog migrations):

```sql
create table case_import_identity (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  producer_id text not null, suite_key text not null, name_hash text not null,
  display_name text not null,                 -- raw name for UI; hash is the key
  case_id uuid,                               -- null while unmapped/conflicted
  proposed_case_id uuid,                      -- unique-match proposal, not binding
  state text not null default 'unmapped'
    check (state in ('unmapped','mapped','conflicted')),
  first_seen_run_id uuid, last_seen_run_id uuid,
  resolved_by uuid, resolved_at timestamptz,
  created_at timestamptz not null default now(), updated_at timestamptz not null default now(),
  version int not null default 1,
  primary key (org_id, id), unique (org_id, id),              -- T3
  unique (org_id, project_id, producer_id, suite_key, name_hash),
  foreign key (org_id, project_id) references project (org_id, id),
  foreign key (org_id, case_id) references test_case (org_id, id),
  foreign key (org_id, proposed_case_id) references test_case (org_id, id)
);
create index case_import_pending on case_import_identity (org_id, project_id, state, created_at, id); -- P4 list index
```

- `name_hash = sha256:<hex>` of the producer-supplied suite+name after trimming (00 §7 hashing convention); `display_name` keeps the raw string for the UI only.
- RLS: `FORCE ROW LEVEL SECURITY`, policy `org_id = evidgate.current_org_id()`; lint-checked by 02.6.1-T2.
- `resolve` writes an audit row (02.7.1) and a `case_identity_source` row with `source='imported'` on the target case so the bind is explainable later.

## 5. API shapes (commands, queries, endpoints)

| Shape | Endpoint / caller | Rule |
|---|---|---|
| `ListCaseImportMappingsQuery` | `GET /v1/projects/{p}/case-import-mappings?state=` · `case:read` | Dapper read-only; cursor on `(created_at, id)`; covers AC6 |
| `CreateCaseImportMappingCommand : ICommand<ImportMapping>` | `POST /v1/projects/{p}/case-import-mappings` · `case:write` | Manual pre-registration of a binding (`producer_id, suite_key, name, case_id`); `Idempotency-Key` required; key already mapped to another case → 409 `mapping_conflict` |
| `ResolveCaseImportMappingCommand : ICommand<ImportMapping>` | `POST /v1/case-import-mappings/{m}/resolve` · `case:write` | body `{case_id}` or `{action:'dismiss'}`; state guard per AC3/AC4; writes audit + `case_identity_source` |
| `ICaseImportRegistry.RecordObservedAsync` | called by 04.3.2/04.4.1 ingest mapping in the event-batch transaction | `INSERT … ON CONFLICT (org_id, project_id, producer_id, suite_key, name_hash) DO NOTHING` (single statement, P2) |
| `ICaseImportMatcher.ProposeAsync(commit_range)` | called by 03.4.1-T3 sync | unique-match rule of AC2 only; never binds |

Permissions per 03 §4.5: `case:write` = `test_maintainer`, `tenant_admin`; `case:read` all member roles.

## 6. States and transitions

`case_import_identity`: `unmapped → mapped | conflicted`; `conflicted → mapped` only via `resolve` (00 §8.10). `dismiss` is a terminal *resolution* recorded as `mapped` with `case_id` staying null and `resolved_by`/`resolved_at` set — the row then dedupes future imports without surfacing as pending (kept out of reports as intentionally unmapped).

## 7. Jobs and integrations

- No jobs of its own: `RecordObservedAsync` runs inside the 04 ingest transaction; `ProposeAsync` inside the 03.4.1-T3 sync transaction — both callers, no new queue types.
- The mapped key keeps working for future imports (D2), so resolve results feed `RecordObservedAsync` lookups.
