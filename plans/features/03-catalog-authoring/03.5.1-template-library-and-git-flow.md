## 1. Goal and non-goals

**Goal.** A versioned template catalogue (built-in rows, `org_id NULL`) whose web, API, unit and mobile templates each emit a runnable customer test that registers a stable `evidgate.id` case id and passes the template's own conformance checks; `evidgate init` wires a repo to use them; the API template emits request skeletons plus schema-conformance checks only — it never invents business assertions.

**Non-goals.** Draft editor integration (03.6.1 consumes templates to seed drafts); AI generation (03.7.1); the JUnit/Appium mappers themselves (04.4.1); runner pools and capability matching (05.7.3); custom per-org templates (V3+; the `org_id` column is reserved for it).

## 2. User stories and acceptance criteria

- As a `qa_engineer`, I run `evidgate init` in my repo and get a first test that already carries an `evidgate.id`, so catalog sync registers it on the first push.
- As an API tester, the generated spec skeleton checks status and schema conformance and clearly marks where I must write the business assertion.
- As a mobile tester (V2), the Appium template keeps its own framework, fixtures and locators and declares the platform capability document.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `evidgate init --template web` in a fixture repo writes a Playwright TypeScript test containing a unique `evidgate.id`; after commit + push, the catalog sync registers exactly one `test_case` with `source = annotation` |
| AC2 | The API template applied to `fixtures/catalog/openapi-skeleton` emits request construction + response status/schema-conformance checks only; every business assertion appears as an explicit `TODO(author)` marker — zero inferred assertions |
| AC3 | The unit template emits Vitest tests whose JUnit report maps `producer + suite + name` keys exactly like 04.4.1's mapper, so evidence binds to the registered case id |
| AC4 | `evidgate init --conformance-check` (or the CI recipe it writes) fails the build when the emitted test lacks an `evidgate.id` or violates a `conformance_rules` entry |
| AC5 | `GET /v1/templates` returns active built-ins (`org_id IS NULL`) to every member role; a non-active or another org's row is invisible (catalogue RLS policy, T46) |
| AC6 | (V2) The mobile template produces an Appium project with its own fixture/locator layout and a capability document declaring `platforms`/`engine` per 00 §10, never reusing the web template's structure |

## 4. Data model and migrations

`migrations/NNNN_catalog_template.sql` (DbUp):

```sql
create table template (
  id uuid primary key,                -- application-generated UUIDv7
  org_id uuid null,                   -- null = built-in catalogue row
  kind text not null check (kind in ('web','api','unit','mobile')),
  name text not null,
  version integer not null,
  body_ref text not null,             -- content-addressed: sha256:<hex> → packaged template files
  conformance_rules jsonb not null,
  active boolean not null default true,
  created_at timestamptz not null default now(),
  unique (org_id, kind, name, version)
);
-- catalogue exception policy (T46), no unique (org_id, id) needed for org-scoped FK targets:
alter table template enable row level security;   -- + FORCE
create policy template_catalogue on template
  using (org_id is null or org_id = evidgate.current_org_id());
```

Index `template (kind, active)` serves the list query (P4). Seed inserts ship in the same migration (`seed` DbUp script class); a body file under `templates/<kind>/<name>/<version>/` is hashed into `body_ref` so content is tamper-evident.

## 5. API shapes (commands, queries, endpoints)

| Shape | Type | Endpoint / notes |
|---|---|---|
| `ListTemplates` | `IQuery<IReadOnlyList<TemplateDto>>` (Dapper, read-only) | `GET /v1/templates?kind=` — permission `case:read` (all member roles); active rows only |
| `GetTemplate` | `IQuery<TemplateDetailDto>` | `GET /v1/templates/{t}` — `case:read`; 404 for unknown/inactive ids |
| — | CLI | `evidgate init --template <kind>/<name>` fetches the body via `packages/sdk`, renders params (role/name preference), writes files; `--conformance-check` runs the rules locally |

No commands: built-in templates are write-once catalogue data; a new version is a new row via migration.

## 6. States and transitions

None. Templates are immutable catalogue rows; `active` flips only via migration (deprecation = new version + old `active=false`).

## 7. Jobs and integrations

- Consumed by `evidgate init` (CLI, Node 26/TS 6.0) and by 03.6.1's draft creation (server-side render into `draft.content`).
- Conformance runs in customer CI via the recipe `evidgate init` writes (JUnit output flows through the normal 04 ingest path).
- Mobile template (V2) declares its capability document so 05.7.3 pool matching accepts it.

## 11. Rollout

- V1 slice (T1–T4) ships at M2; T5 is a separate V2/M4 PR. No flag needed — inactive templates are invisible, so rollout is `active=true` per row.
- Monitoring: template-fetch failures on `evidgate init`, conformance-check failure rate (telemetry event, no content).
- Rollback: set `active=false` on a bad template version via migration; already-generated customer tests are unaffected (content is copied, not linked).
