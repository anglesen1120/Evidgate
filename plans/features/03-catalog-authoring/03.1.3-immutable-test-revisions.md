Recorded choices: (1) `revision_hash` is `sha256:` over the canonical `{content_sha256, framework, language, assertion_hash, metadata}`, metadata being only `assertion_count` and `assertions_extracted`; (2) a descriptor keeps the matcher, negation, modifiers and expected-value arguments but not the subject, so healing a locator keeps the `assertion_hash` while a removed, weakened or re-targeted assertion changes it; (3) the hash-skip is the unique key itself — one `insert … on conflict do nothing` for the whole tree — rather than a read of each case's latest hash; (4) "newest first" orders by first appearance of a distinct content: reverting to old content reuses the old row and does not make it newest; (5) the table keeps `created_at` only (append-only exemption, like `audit_log`); (6) `ITestRevisionStore.AppendAsync` takes the source text and hashes it, so a caller cannot supply a hash that does not match.

## 1. Goal and non-goals

**Goal.** Every version of a test that was ever synced or run is stored as an append-only `test_revision` identified by `(case_id, revision_hash)`: same content → same hash → same row; any change is a new revision; referenced revisions can never be updated or deleted, so evidence (06/07) and healing (08) always point at a reproducible input.

**Non-goals.** Who walks the repo and calls the append path (03.4.1); suite revisions (03.2.1); content byte storage — Git is the content store (A2), the row stores `content_sha256` + metadata; `GET /v1/cases/{c}/revisions` was wired in 03.1.1 and starts returning rows here.

## 2. User stories and acceptance criteria

- As a release approver, the exact test version a run executed is retrievable forever by hash, so a FAIL decision is reproducible from the pinned commit.
- As the platform, a retry or re-sync of unchanged code reuses the existing revision row, so storage does not grow on no-op syncs.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `INSERT` of identical `(org_id, case_id, revision_hash)` twice yields one row (`ON CONFLICT DO NOTHING` returns existing id); the same test content always computes the same `revision_hash` |
| AC2 | `UPDATE` or `DELETE` on `test_revision` as the app role raises `revision_immutable` (trigger) / permission denied (`REVOKE`) regardless of whether a run references it |
| AC3 | `revision_hash` = `sha256:` over the RFC 8785 canonical JSON of `{content_sha256, framework, language, assertion_hash, metadata}`; `file_path` is **excluded** so a rename-only commit reuses the revision (AC1 of 03.1.1 holds) |
| AC4 | `assertion_hash` = `sha256:` over canonical extracted assertion metadata per framework; a change in assertions alone produces a new `revision_hash` |
| AC5 | `GET /v1/cases/{c}/revisions` returns revisions newest-first with `commit_sha`, `file_path`, `assertion_hash`; cross-tenant case id → 404 |

## 4. Data model and migrations

`migrations/NNNN_catalog_test_revision.sql`:

```sql
create table test_revision (
  id uuid not null, org_id uuid not null,
  case_id uuid not null, revision_hash text not null,        -- 'sha256:<hex>'
  commit_sha text not null, file_path text not null,          -- path at first sync of this content
  framework text not null, language text,
  content_sha256 text not null, assertion_hash text not null,
  metadata jsonb not null default '{}',
  created_at timestamptz not null default now(),
  primary key (org_id, id), unique (org_id, id),              -- T3
  unique (org_id, case_id, revision_hash),                    -- D3
  foreign key (org_id, case_id) references test_case (org_id, id)
);
create index test_revision_case on test_revision (org_id, case_id, created_at desc, id); -- serves GET revisions (P4)

revoke update, delete on test_revision from evidgate_app;
create trigger test_revision_immutable … raise exception 'revision_immutable';
```

- Trigger + `REVOKE` are the SQL enforcement (C6); the domain record additionally has no setters and no EF tracking path that issues UPDATE (handler never attaches a mutable copy).
- RLS policy `org_id = evidgate.current_org_id()`; lint-checked.

No new HTTP endpoints in this story.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T3 / 00 §5.4.6 | `unique (org_id, id)` + composite FK to `test_case (org_id, id)` | `RevisionSchemaTests` |
| T2 / C3 | RLS + tenant tx | `RevisionRlsTests` |
| C6 / D3 (integrity) | no setters + `REVOKE UPDATE, DELETE` + trigger | `RevisionImmutabilityTests` (both enforcement layers) |
| P2 | append is batched with the sync upsert set; hash-skip avoids inserts on unchanged files | `SyncRevisionTests` (2 000-case fixture, unchanged subset inserts 0 rows) |
| P4 | `test_revision_case` serves the revisions list | covering index asserted in test |
| S3 | content bytes never leave the repo; only hashes + metadata stored — secret values cannot enter the row (ties to D5 for params in 03.2.1) | schema review + test asserting no `content` column |
| Retention | revisions persist with case history; tenant deletion removes them (11); metadata must not contain secrets (schema allows only extracted assertion descriptors) | stated; lint in 03.3.1-T3 covers the write path |

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** `GET /v1/cases/{c}/revisions` needs `case:read` and answers 404 for another org's case and for a case outside the credential's project scope; there is no write route — revisions are appended only by `ITestRevisionStore` and the sync, in-process inside a tenant transaction, so no caller can name a revision to create.
- **Retention/deletion:** a revision row holds hashes, a path, a commit id and a two-member metadata object, never the test source (S3), so a secret cannot enter it. Rows persist with the case history and leave with the project or tenant (plan 11); because the table is append-only for every role, tenant deletion uses the owner path of 11.2.1.
- **Telemetry:** the store and the query run in module spans; the sync report counts the revisions appended; hashes and counts are the only content that is logged.
- **Failure path:** appending identical content is a no-op that returns the existing row; a case of another tenant fails the composite foreign key; a malformed hash fails its check constraint; `UPDATE` or `DELETE` raise `revision_immutable` (owner) or are denied (app role). A conflict between two syncs cannot occur: they queue behind the per-project lock of 03.1.1.

## 8a. Review (2026-10-03, security + performance, from the spec package)

| # | Finding | Severity | Resolution |
|---|---|---|---|
| 1 | `assertion_hash` was a constant for any unsupported framework (and for a file with no assertions), so removing every assertion of such a file was invisible to the healing tamper check | Medium-high | Fixed, fail closed: an unsupported framework or a scan that could not finish hashes `["unreliable", content_sha256]`, so any edit changes it; `assertions_extracted` / `assertions_reliable` are stored in `metadata`, hashed, and returned by the API (`FailClosed_*`, `Revisions_FlagFilesWhoseAssertionsCouldNotBeTrusted`) |
| 2 | Assertions inside an `expect(...)` subject (`expect(async () => { expect(a)… }).toPass()`) were invisible | Medium | Fixed: the subject is scanned for nested `expect` and reported as `in:` descriptors |
| 3 | Regex literals, unterminated strings or comments and nested templates could desync the scanner and hide later assertions | Medium | Mitigated: whatever the scanner cannot follow marks the extraction unreliable (fail closed, finding 1); a full JavaScript lexer is not built (OI-03-15) |
| 4 | A comment inside a multi-line Python `assert` dropped the clauses after it | Medium | Fixed: comments are stripped per physical line; line-comment line breaks survive normalisation in arguments, so a comment cannot swallow the next argument |
| 5 | Common forms missed: Chai chains, `assert.*`, Python one-line blocks, pytest-playwright `expect`, scanner chosen by framework only | Medium-low | Fixed: Chai filler words, `assert(...)`/`assert.x(...)`, `if c: assert x`, `expect` in Python, `language=python` selects the Python scanner |
| 6 | Silent truncation at 2 MiB / 20 000 descriptors | Low-medium | Fixed: either marks the extraction unreliable |
| 7 | `created_at` was the transaction start, so "newest first" could be wrong across overlapping syncs | Medium-high | Fixed: revisions are stamped with `clock_timestamp()` after the project lock |
| 8 | The project lock and the open transaction were held across parsing and hashing; waiters had no timeout | Medium-high | Fixed: discovery and hashing (parallel) run before the lock; `lock_timeout` 10 s, a timeout answers `sync_busy` |
| 9 | Per-file allocation churn in the extractor and four JSON parses in the hasher | Medium | Fixed: keyword pre-checks, no identifier substrings on the hot path, metadata written raw into the hash document, pooled UTF-8 buffer for the content hash |
| 10 | A lone surrogate in a test file could fail the whole sync | Low | Fixed: such a file is a warning (`Sync_AFileWithBrokenText_IsAWarning…`); `ITestRevisionStore.AppendAsync` validates commit, path, framework, language and source |
| 11 | `AppendOne` could not see a concurrent winner's row in the same statement | Low | Fixed: a second read statement |
| 12 | `held_dirs` grew with the number of broken sidecars | Low | Fixed: past 200 the root is held |
| 13 | The listing is "first appearance of a distinct content", not "current revision"; no record of which revision a commit had; storage grows with churny content; no override for `incomplete_tree`; hashes of low-entropy secrets are readable by `case:read`; erasure needs the owner path | Low | Recorded as OI-03-15 and in the 03.4.1 / 08 / 11 hand-offs: the tamper check must refuse when `assertions_reliable` is false and must also compare skip/conditional structure and subject retargeting, which `assertion_hash` deliberately does not cover |

- Expand-only migration; deploy with 03.1.1 (same PR series) or right after — the revisions endpoint returns `[]` until the first sync appends rows.

- Rollback: revert; orphaned `test_revision` rows are harmless (no run can have referenced them in-window).
