## 1. Goal and non-goals

**Goal.** Every version of a test that was ever synced or run is stored as an append-only `test_revision` identified by `(case_id, revision_hash)`: same content → same hash → same row; any change is a new revision; referenced revisions can never be updated or deleted, so evidence (06/07) and healing (08) always point at a reproducible input.

**Non-goals.** Who walks the repo and calls the append path (03.4.1); suite revisions (03.2.1); content byte storage — Git is the content store (A2), the row stores `content_sha256` + metadata; `GET /v1/cases/{c}/revisions` was wired in 03.1.1 and starts returning rows here.

## 2. User stories and acceptance criteria

- As a release approver, the exact test version a run executed is retrievable forever by hash, so a FAIL decision is reproducible from the pinned commit.
- As the platform, a retry or re-sync of unchanged code reuses the existing revision row, so storage does not grow on no-op syncs.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `INSERT` of identical `(org_id, case_id, revision_hash)` twice yields one row (`ON CONFLICT DO NOTHING` returns existing id); the same test content always computes the same `revision_hash` |
| AC2 | `UPDATE` or `DELETE` on `test_revision` as the app role raises `revision_immutable` (trigger) / permission denied (`REVOKE`) regardless of whether a run references it |
| AC3 | `revision_hash` = `sha256:` over the RFC 8785 canonical JSON of `{content_sha256, framework, language, assertion_hash, metadata}`; `file_path` is **excluded** so a rename-only commit reuses the revision (AC1 of 03.1.1 holds) |
| AC4 | `assertion_hash` = `sha256:` over canonical extracted assertion metadata per framework; a change in assertions alone produces a new `revision_hash` |
| AC5 | `GET /v1/cases/{c}/revisions` returns revisions newest-first with `commit_sha`, `file_path`, `assertion_hash`; cross-tenant case id → 404 |

## 3. Contracts touched

## 4. Data model and migrations

`migrations/NNNN_catalog_test_revision.sql`:

```sql
create table test_revision (
  id uuid not null, org_id uuid not null,
  case_id uuid not null, revision_hash text not null,        -- 'sha256:<hex>'
  commit_sha text not null, file_path text not null,          -- path at first sync of this content
  framework text not null, language text,
  content_sha256 text not null, assertion_hash text not null,
  metadata jsonb not null default '{}',
  created_at timestamptz not null default now(),
  primary key (org_id, id), unique (org_id, id),              -- T3
  unique (org_id, case_id, revision_hash),                    -- D3
  foreign key (org_id, case_id) references test_case (org_id, id)
);
create index test_revision_case on test_revision (org_id, case_id, created_at desc, id); -- serves GET revisions (P4)

revoke update, delete on test_revision from evidgate_app;
create trigger test_revision_immutable … raise exception 'revision_immutable';
```

- Trigger + `REVOKE` are the SQL enforcement (C6); the domain record additionally has no setters and no EF tracking path that issues UPDATE (handler never attaches a mutable copy).
- RLS policy `org_id = evidgate.current_org_id()`; lint-checked.

## 5. API shapes (commands, queries, endpoints)

| Shape | Endpoint / caller | Rule |
|---|---|---|
| `ITestRevisionStore.AppendAsync` | inside `RegisterDiscoveredAsync` (03.1.1) during sync | one `INSERT … ON CONFLICT (org_id, case_id, revision_hash) DO NOTHING RETURNING id` per changed file — unchanged files are skipped before the insert by hash compare, so the sync stays proportional to changed files (P2) |
| `GetCaseRevisionsQuery` | `GET /v1/cases/{c}/revisions` (endpoint already registered in 03.1.1-T1.4) · `case:read` | Dapper on `test_revision_case`; now returns data |
| `AssertionExtractor` (domain service, `Domain/`) | used by `AppendAsync` | per-framework assertion extraction → `assertion_hash`; unknown framework → `assertion_hash` over empty set, flag `assertions_extracted=false` in `metadata` |

No new HTTP endpoints in this story.

## 6. States and transitions

None. `test_revision` is append-only with no lifecycle column; existence is the state.

## 11. Rollout

- Expand-only migration; deploy with 03.1.1 (same PR series) or right after — the revisions endpoint returns `[]` until the first sync appends rows.
- No flag, no monitoring of its own; sync surfaces append failures through `catalog_sync.error` (03.4.1).
- Rollback: revert; orphaned `test_revision` rows are harmless (no run can have referenced them in-window).
