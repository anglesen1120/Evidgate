## 1. Goal and non-goals

**Goal.** A minimal V1 history model so that a case shows its recent results per variant, and a failure is classified as **new** (it passed on the baseline branch before) or **already failing on main**. A read table `case_result_history` is projected from accepted evidence revisions by an outbox consumer, queried with Dapper, and rebuildable from revisions alone. It also yields a flake-rate input (pass/fail flips over a window) for 07, without deciding any policy.

**Non-goals.** Flaky policy and quarantine decisions (07, 08); trend charts and the V2 trend label beyond the raw input; cross-project history; the investigation UI (09.4.1-T4 consumes the endpoint); import of past reports (03.9.2); retention of `event`/`case_attempt` themselves (06.4.6) and artifacts (06).

## 2. User stories and acceptance criteria

- As a developer, I see for a failing case whether it also fails on `main`, so I know if my change broke it.
- As a release manager, I see the last N results per variant of a case, newest first.
- As an operator, I can rebuild history from stored revisions and get identical rows.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | When an `evidence_revision` is accepted for a run, one history row per `(case_id, variant_hash, target_env)` is written within one consumer cycle; rows carry run id, `revision_no`, outcome, branch, `head_sha`, run purpose, `finished_at` and `attempt_count`; a duplicate outbox delivery writes nothing new (unique `(org_id, evidence_revision_id, execution_key)`) |
| AC2 | Only accepted revisions project; a late revision (new `revision_no`) supersedes the earlier row of the same run in the **read** view (`is_latest`), the earlier row stays |
| AC3 | `GET /v1/projects/{p}/cases/{c}/history?variant=&branch=&limit=&cursor=` returns newest first, keyset-paged, default 20, max 100; ordering is `(finished_at desc, id desc)` and stable across pages |
| AC4 | Classification: failed on a non-baseline run and the latest baseline-branch result for the same case × variant × env is `passed` → `new_failure`; baseline latest is `failed` → `failing_on_baseline`; no baseline row → `unknown_baseline`; passed → `passing`; the baseline branch is the project's configured branch (default branch) |
| AC5 | A retry pass (fail → pass inside one run) is stored with `attempt_count > 1` and counted as one flip-input row `flaky_signal = true`; the flake-rate query over a window returns flips / runs and never mutates a decision |
| AC6 | Runs with purpose `replay` are projected but excluded from baseline and flake input; runs with purpose `import` (03.9.2) are projected, flagged, and used as baseline seed only |
| AC7 | A user of org A never reads org B history (404 for a foreign case); the consumer and the table obey FORCE RLS; a history row cannot reference a case of another org (composite FK) |
| AC8 | Retention: rows older than the history window (default 90 d `[INFERENCE]`, [OPEN] O-03.9.1-1) are purged by the 01.5.1 purge job in batches; rows of a deleted run (06.4) are removed with it; the endpoint returns an explicit `window_start` |
| AC9 | Rebuild: truncating the table and replaying all accepted revisions gives byte-identical rows (excluding surrogate `id` order), checked by a row-hash comparison |

## 4. Data model and migrations

Migration `migrations/NNNN_case_result_history.sql` (new table, read model owned by 03):

| Column / constraint | Detail |
|---|---|
| `case_result_history` | `id` UUIDv7, `org_id`, `project_id`, `case_id`, `variant_hash`, `target_env`, `execution_key`, `run_id`, `evidence_revision_id`, `revision_no`, `outcome` (`passed`/`failed`/`skipped`/`errored`/`missing`), `attempt_count`, `flaky_signal bool`, `branch`, `head_sha`, `run_purpose`, `is_import bool`, `finished_at`, `projected_at` |
| Keys | `unique (org_id, id)`; `unique (org_id, evidence_revision_id, execution_key)`; composite FKs `(org_id, case_id)` → `test_case`, `(org_id, run_id)` → `run`, `(org_id, evidence_revision_id)` → `evidence_revision` |
| Indexes | `(org_id, case_id, variant_hash, finished_at desc, id desc)` for history; partial `(org_id, case_id, variant_hash, target_env, finished_at desc) where branch_is_baseline` for the baseline lookup (baseline flag computed at projection from the project's branch setting) |
| `is_latest` | not a column; the read view picks the highest `revision_no` per `(run_id, execution_key)` |
| RLS | FORCE, standard tenant policy; app role has `SELECT/INSERT/DELETE` (purge, rebuild), no `UPDATE` except the consumer's idempotent upsert path |
| Projection checkpoint | row in the existing outbox consumer offset table (01.5.1); no new table |

Branch is read from `run.branch` (review D1, contract change owned by 05.2.1 and ⚠️ not yet merged); until D1 lands the baseline classification returns `unknown_baseline` and the T2 branch tests are skipped with a tracked reason.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Query | `GetCaseHistory` | `GET /v1/projects/{p}/cases/{c}/history` | see O-03.9.1-2 | 200 `{items[], next_cursor, window_start}` · 404 foreign case · 422 bad cursor |
| Query | `GetCaseFlakeInput` | `GET /v1/projects/{p}/cases/{c}/history/flake?window=` | same | 200 `{runs, flips, rate}` |
| Internal | `RebuildCaseHistory` | `POST /internal/operator/case-history/rebuild` behind `IOperatorGate` | operator | 202 · 403 |

Item shape: `{run_id, revision_no, variant_hash, outcome, classification, attempt_count, branch, head_sha, finished_at, run_purpose}`. Classification is computed at read time from the baseline index (not stored), so a baseline change never needs a rewrite.

## 6. States and transitions

No new state machine. Projection per evidence revision: `pending → projected` is implicit in the consumer offset. History rows are append-only (a late revision adds rows; superseded rows stay and are hidden by `is_latest`). Purge deletes whole rows by age; it never edits one. Rebuild is a truncate-and-replay run as an operator task with a lock (one at a time).

## 7. Jobs and integrations

- Outbox consumer `CaseHistoryProjector` (01.5.1 consume contract): reads the accepted-revision event, loads the revision's results with one set-based query and writes with a single batch insert (`unnest`, 00 §5.7 P2), inside the tenant transaction; acknowledged only after commit.
- Purge: the 01.5.1 purge job gains a history rule (batch delete by `finished_at`, retention from config).
- Rebuild task: reads all `evidence_revision` rows of the tenant in id order and re-runs the projector logic; never reads raw events.
- No network calls inside the transaction (P5).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Authorization | endpoint permission per O-03.9.1-2; rebuild is operator-only and fail-closed | 403 tests |
| Tenant isolation | FORCE RLS, composite FKs, consumer sets `evidgate.org_id` per event | `History_CrossOrg_404`, isolation suite entry |
| Evidence integrity | history only copies fields from immutable accepted revisions; it never feeds back into evidence, manifests or evaluations | rebuild equality test (AC9) |
| Missing evidence never PASS | `missing` is a stored outcome and never rendered as passing; baseline `passed` requires a stored `passed` | `Baseline_MissingIsNotPassed` |
| Privacy | no test output text, only ids/hashes/outcome/branch/sha; author names are not stored | schema review, log allowlist |
| P1/P3/P4 | history query is one indexed keyset page, p95 budget from 00 §11 `[INFERENCE]` 150 ms at 100k rows per case-variant window; statement counter asserts 2 statements | EXPLAIN + counter test, k6 row in 10 |
| Volume | projector batch size capped; a 100k-test run projects streaming in chunks (review D5) | 100k fixture test in 10.6.1 |

DoR review answers. **Authorization:** as above; history needs the same read scope as the runs it summarises. **Retention/deletion impact:** window purge plus cascade from run deletion (06.4); org deletion removes the table's rows; the table is derived data, so rebuild restores it within the window. **Telemetry:** `case_history_rows_projected_total`, `case_history_projection_lag_seconds`, `case_history_purged_total`, trace attribute `case.id`; alert on lag above 5 min. **Failure path:** a projector failure retries with backoff and goes to the task dead-letter after N attempts with an alert (01.5.1-T4); a missing branch yields `unknown_baseline`, never a guess; an unreadable revision is skipped with an audit-visible error row and counted.
