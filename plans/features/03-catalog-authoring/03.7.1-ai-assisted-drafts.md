## 1. Goal and non-goals

**Goal.** `POST /v1/projects/{p}/ai-drafts` produces a `kind='ai'` draft from an **approved requirement** only: context is assembled from an allowlist, redacted, sent to the LLM over an allow-listed egress, and the result lands as a normal draft carrying full provenance (`ai_run_id`, model id, prompt hash). Unapproved AI drafts can only ever run in the sandbox capability. A separate evaluation task measures Playwright's planner/generator agents against a fixture set before any adoption.

**Non-goals.** The draft/dry-run/PR mechanics themselves (03.6.1); regression candidates built from incident evidence (03.8.1 consumes this pipeline); the secret store and outbound-context control implementation (11.4.1-T3 provides the egress rules); the healing LLM call ledger (08 owns `healing_llm_call`; this story records its own `ai_draft_run`); UI (09.6.1).

## 2. User stories and acceptance criteria

- As a `qa_engineer`, I point the system at an approved requirement and get a draft I can review, dry-run and PR — never code that silently lands in the repo.
- As a security auditor, I can trace every AI-produced draft back to its requirement, prompt hash and model id, and prove that no tenant secrets or non-allowlisted context left the platform.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/projects/{p}/ai-drafts` without a `requirement_approved_by` membership (≠ requester, holding `test_maintainer`/`tenant_admin`) → 422 `requirement_not_approved`; with a valid approver → 202 + `draft_id` + `ai_run_id` |
| AC2 | The dispatched LLM payload contains only allowlisted fields (requirement text, template skeleton ids, target framework) and passes through the redaction list; a context field outside the allowlist is dropped and recorded in `ai_draft_run.context_dropped[]` |
| AC3 | Provenance is complete: `draft.provenance` + `ai_draft_run` store `model_id`, `prompt_hash` (sha256 over RFC 8785 canonical prompt), `requirement_hash`, approver and requester — re-hashing the stored prompt reproduces `prompt_hash` |
| AC4 | An unapproved AI draft (state before `dry_passed` + human review) requesting any capability beyond the sandbox is refused with 403 `permission_denied`; the only offered execution is `POST /v1/drafts/{d}/dry-run` |
| AC5 | LLM call failure (timeout, 5xx, refusal) leaves the draft in `draft` state with `ai_draft_run.state = failed` and a retryable task; no partial content is committed |
| AC6 | The Playwright planner/generator evaluation (T3) produces a report over `fixtures/ai-drafts/` with validity rate, no-skip compliance, review effort and cost per draft; generator output never lands in `draft` until the report is adopted in DECISIONS |

## 4. Data model and migrations

`migrations/NNNN_catalog_ai_draft_run.sql` (T1):

```sql
create table ai_draft_run (
  id uuid primary key,
  org_id uuid not null, project_id uuid not null,
  draft_id uuid null,                       -- set when generation succeeds
  requested_by uuid not null,               -- membership id
  requirement_text text not null,
  requirement_hash text not null,           -- sha256:<hex> RFC 8785 canonical
  approver_membership_id uuid not null,     -- ≠ requested_by; permission checked
  context_allowlist jsonb not null,
  context_dropped jsonb not null default '[]',
  model_id text not null, prompt_hash text not null,
  cost_usd numeric null, tokens_in integer null, tokens_out integer null,
  state text not null check (state in ('requested','running','done','failed')),
  error text null,
  created_at timestamptz not null default now(), finished_at timestamptz null,
  unique (org_id, id),
  foreign key (org_id, draft_id) references draft (org_id, id),
  check (approver_membership_id <> requested_by)
);
create index ai_draft_run_project on ai_draft_run (org_id, project_id, created_at, id);
alter table ai_draft_run enable row level security;
```

`draft.provenance` gains `{ "ai_run_id", "requirement_hash", "approver" }` for `kind='ai'` rows (columns already owned by 03.6.1-T1's migration).

## 5. API shapes (commands, queries, endpoints)

| Shape | Type | Endpoint | Permission · codes |
|---|---|---|---|
| `RequestAiDraft` | `ICommand<Guid>` | `POST /v1/projects/{p}/ai-drafts` | `ai_draft:request` · 202 `{ draft_id? , ai_run_id }`; 422 `requirement_not_approved`; `Idempotency-Key` required |
| `GetAiDraftRun` | `IQuery` | `GET /v1/ai-draft-runs/{r}` | `case:read` · provenance view for the 09 screen |

`RequestAiDraft` validates the approver (exists in the project org, holds `test_maintainer`/`tenant_admin`, ≠ requester) inside the tenant transaction, writes `ai_draft_run` + `draft` (`kind='ai'`, status `draft`, empty content) + outbox row in one transaction; the LLM call itself runs in `catalog.ai_draft_generate` task (P5). On success the task writes `draft.content` + provenance and marks the run `done`.

## 6. States and transitions

`ai_draft_run`: `requested → running → done | failed` (retryable while `running`; terminal on `done`/`failed` after retry cap). The draft itself follows the 00 §8.10 machine unchanged — AI produces content only; `dry_running` onward is identical to a template draft. "Approval" of the AI draft is expressed by a human driving it to `pr_open`; there is no separate approved flag on `draft`.

## 7. Jobs and integrations

- `catalog.ai_draft_generate` task: builds the allowlisted context, redacts, calls the LLM via allow-listed `HttpClient` (S4, P6; timeouts + bounded retries → `dead_letter`), validates the returned structured content (JSON Schema via Corvus; a schema-invalid completion → `failed`), writes `draft.content`.
- Egress/context rules from 11.4.1-T3 (denylist-free allowlist of fields + redaction list applied before send).
- Usage metering (12): `tokens_in`/`tokens_out`/`cost_usd` recorded per run for the usage ledger; no per-LLM-call client input is trusted.
- Playwright planner/generator evaluation (T3) runs as a script + fixture corpus, not a shipped path.

## 11. Rollout

- Rollback: revoke `ai_draft:request` + remove the egress allow-list entry; existing drafts stay readable; no migration rollback (additive table).
