## 1. Goal and non-goals

**Goal.** A GitHub push delivery is signature-verified, resolved to a tenant *before* any business table is touched (T1), deduped by `delivery_id`, and turned into a `catalog_sync` task that walks the commit tree and applies 03.1.x/03.2.x writers — idempotently. A suspended installation disables sync without deleting history.

**Non-goals.** Branch/commit/PR creation (V2, 03.4.2); other providers (GitLab/Bitbucket not in V1); the V2 draft reconciliation (03.6.1-T4); Git credentials of users — the App installation token is never persisted (03 §6).

## 2. User stories and acceptance criteria

- As a test maintainer, pushing a commit syncs my catalog once and only once, so revisions reflect the repo without manual refresh.
- As a security reviewer, the webhook endpoint cannot be spoofed and learns nothing about tenants before signature verification and scoped resolution.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/webhooks/github` with a valid `X-Hub-Signature-256` → 202; with a forged/missing signature → 401, **no** row written, no tenant resolution attempted |
| AC2 | The tenant is resolved only through `evidgate_resolve.github_repo(org lookup by installation_id + repository_id)` returning `(org_id, project_id, binding_id, status)`; the function is owner-owned `SECURITY DEFINER`, app role has `EXECUTE` only, and every call writes an audit row (T1) |
| AC3 | A second delivery with the same `(provider, delivery_id)` → 200 no-op; exactly one `webhook_delivery` row and at most one `catalog_sync` row per commit per repo |
| AC4 | A push on a bound repo enqueues `catalog_sync` `state='queued'`; the worker task walks the commit tree via the App installation (read-only), applies `ICaseIdentityService`/`ITestRevisionStore`/`CreateSuiteRevisionCommand` handlers, and ends `done` with `counts jsonb` (registered/renamed/conflicts/warnings) |
| AC5 | Installation `suspend`/`deleted` events set `git_repo_binding.sync_state='disabled'`; later pushes → 200 recorded, `catalog_sync` not enqueued; catalog keeps serving last state; `unsuspend` re-enables |
| AC6 | GitHub API 5xx/429 mid-sync → task retries with `available_at` backoff; the sync is resumable/idempotent (re-running the same commit inserts nothing); after retry cap → `catalog_sync.state='failed'` + dead-letter |
| AC7 | A scheduled reconcile (Cronos `catalog.reconcile`, unique `(schedule_name, fire_at)`) enqueues a sync for bindings whose `head_commit != last_synced_commit`, repairing missed webhooks |
| AC8 | `GET /v1/projects/{p}/catalog-syncs` lists syncs newest-first (drives the 09 "catalog is stale" badge) |

## 3. Contracts touched

- 00 §9.3 `POST /v1/webhooks/github` — owned; signature auth, not session.
- 00 §5.4.8 + T1 — this story owns the **GitHub resolver function** `evidgate_resolve.github_repo(...)` (the fourth resolver beside 02's login/ci-token/ingest ones).
- New endpoints (additive): `POST /v1/projects/{p}/git-repo-bindings` (`project:write`) records a binding after the customer installs the App; `GET /v1/projects/{p}/catalog-syncs` (`suite:read`) — recorded for `contracts/openapi.yaml`.
- ✅ verified 2026-11-13 (legend: ✅ = verified with an official link) — this story's own token row is **Contents: read** (`GET /repos/{owner}/{repo}/git/trees/{tree_sha}`, `GET /repos/{owner}/{repo}/git/blobs/{file_sha}`) plus **Metadata: read** (`GET /repos/{owner}/{repo}`, the binding verify): [Contents](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-contents), [Metadata](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-metadata). The App-level registered set stays ADR-0007's union, not this row: this verification adds and removes no permission, and a sync token never exceeds the row. No `pull_requests` permission until 03.4.2.
- ✅ Metadata read is the requested registration expectation, **not doc-verified as mandatory or automatically granted**: [Choosing permissions for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app) states apps have no permissions by default, so request it explicitly; ADR-0007 keeps the same ⚠️ until someone reads the registration UI.
- ✅ Events: [push](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push) is the only subscription this story needs, and its docs require at least read-level Contents and name no further permission for subscribing; [installation](https://docs.github.com/en/webhooks/webhook-events-and-payloads#installation) (`created`, `deleted`, `suspend`, `unsuspend`, `new_permissions_accepted`) and [installation_repositories](https://docs.github.com/en/webhooks/webhook-events-and-payloads#installation_repositories) (`added`, `removed`, needed to see repository access taken away) need none — every App receives both by default and cannot subscribe manually, so `default_events` lists `push` only.
- ✅ Manifest ([parameters](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest#github-app-manifest-parameters)): `{"name":"Evidgate","url":"https://<origin>","public":true,"hook_attributes":{"url":"https://<origin>/v1/webhooks/github","active":true},"default_permissions":{"metadata":"read","contents":"read","checks":"write","statuses":"write","actions":"write"},"default_events":["push"],"request_oauth_on_install":true,"callback_urls":["https://<origin>/v1/github/installations/callback"]}`.
- ✅ OAuth during install follows ADR-0007 `## Decision` §Install binding (lines 25-27: both Apps "registered with Request user authorization (OAuth) during installation"). The callback URL value is owned by 02.4.3-T2; this lane stays sync-only — no callback endpoint, no user-token code, the client authenticates with installation tokens only.
- ✅ `public: true` is required for customer installs: a private App "can only be installed on the user or organization account of the app owner" ([Making a GitHub App public or private](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/making-a-github-app-public-or-private)), which matches ADR-0007's public production App; `public: false` stays the non-production App's setting only.
- ✅ Auth: [App JWT](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app) signed RS256 with the App private key, `iss` = client ID (or App ID; client ID recommended), `iat = now - 60s` for clock skew, `exp` at most 10 minutes ahead, sent as `Authorization: Bearer`; [installation token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app) = `POST /app/installations/{id}/access_tokens` with that JWT, expires after 1 hour, and cannot exceed the installation's repositories or permissions.
- ✅ Webhook secret ([validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)): `sha256=` + HMAC-SHA256 of the raw payload (UTF-8, unmodified) keyed by the App's webhook secret, compared in constant time against `X-Hub-Signature-256` before parsing; the App private key is never the HMAC key.
- Rejected over-broad scopes — each sits outside this row's ceiling or has no caller in this story. ADR-0007 keeps its own rows for `checks: write` (07.6.1-T1), `statuses: write` (T62) and `actions: write` (05.5.2-T3): registered at App level, never requested by a sync token.

| Rejected for 03.4.1 | Reason |
|---|---|
| `pull_requests: write` | PR creation is 03.4.2 only (ADR-0007 V2 amendment). |
| `contents: write` | Sync reads trees, blobs and repository metadata; it never writes a commit, ref or file. |
| `checks: write` | No check run is created or read; that row belongs to 07.6.1-T1. |
| `statuses: write` | No commit status is read or published; T62 owns it. |
| `actions: write` | No workflow run is triggered or read; 05.5.2-T3 owns it. |
| `administration` | No repository settings, webhook administration or collaborator changes; ADR-0007 registers none. |
| `workflow` (repository permission or OAuth scope) | No `.github/workflows` file is read or edited. |
| `members` | No organization membership or team lookup. |
| User access token on the sync path | Installation tokens cover every sync call; the user token exists only for 02.4.3's install handshake. |

- Resolved (RECOMMENDATIONS 03-Q8) — one repo per project in V1 (`unique (org_id, project_id, provider, repository_id)` allows N rows but the UI/binding flow assumes one). The tenant-less resolver also needs a single answer, so `unique (provider, installation_id, repository_id)` makes a repository bindable by one org only, and `catalog_sync` pins its binding with the composite `(org_id, project_id, binding_id)` FK.

## 4. Data model and migrations

`migrations/NNNN_catalog_git.sql` + resolver functions:

```sql
create table git_repo_binding (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  provider text not null default 'github',
  installation_id text not null, repository_id text not null,
  default_branch text not null default 'main',
  head_commit text, last_synced_commit text,
  sync_state text not null default 'active' check (sync_state in ('active','disabled')),
  webhook_secret_ref text not null,            -- secret-store reference, never the value (S3)
  created_at …, updated_at …, version int not null default 1,
  primary key (org_id, id), unique (org_id, id),
  unique (org_id, project_id, id),                 -- the sync row's three-column FK target
  unique (org_id, project_id, provider, repository_id),
  unique (provider, installation_id, repository_id), -- one binding per repository across the installation
  foreign key (org_id, project_id) references project (org_id, id)
);

create table webhook_delivery (
  id uuid not null, org_id uuid not null,          -- org learned only after resolve; delivery rows are tenant-scoped
  provider text not null, delivery_id text not null, event text not null,
  payload_hash text not null, state text not null default 'accepted',
  created_at timestamptz not null default now(),
  primary key (org_id, id), unique (org_id, id),
  unique (provider, delivery_id)                   -- A10 dedupe
);

create table catalog_sync (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  commit_sha text not null, binding_id uuid not null,
  state text not null default 'queued' check (state in ('queued','running','done','failed')),
  counts jsonb, error text,
  started_at timestamptz, finished_at timestamptz, created_at …,
  primary key (org_id, id), unique (org_id, id),
  unique (org_id, binding_id, commit_sha),          -- at most one sync row per commit per repo (AC3)
  foreign key (org_id, project_id) references project (org_id, id),
  foreign key (org_id, project_id, binding_id) references git_repo_binding (org_id, project_id, id)
);
create index catalog_sync_list on catalog_sync (org_id, project_id, created_at desc, id); -- P4 for AC8
create index catalog_sync_binding on catalog_sync (org_id, project_id, binding_id); -- the binding FK's child side

-- T1 resolver (owner-owned, SECURITY DEFINER; app role gets EXECUTE only)
create function evidgate_resolve.github_repo(p_installation_id text, p_repository_id text)
returns table(org_id uuid, project_id uuid, binding_id uuid, status text)
security definer … -- SELECT on git_repo_binding bypassing RLS, writes resolver-audit row
```

- RLS on all three tables (helpers, FORCE). `webhook_delivery`/`catalog_sync`/`git_repo_binding` all carry `unique (org_id, id)` (T3).
- The `unique (provider, delivery_id)` is global by design (03 §4.1): dedupe must catch a delivery even when re-issued against the same repo.

## 5. API shapes (commands, queries, endpoints)

| Shape | Endpoint / caller | Behaviour |
|---|---|---|
| `ReceiveGithubWebhookCommand` (pre-tenant entry) | `POST /v1/webhooks/github` — **no session** | 1) verify `X-Hub-Signature-256` HMAC against `webhook_secret_ref`-resolved secret (401 on fail, before anything else) 2) `evidgate_resolve.github_repo` → tuple or 404-as-202 (unknown repo: record nothing, return 200 to stop GitHub retries) 3) open tenant scope (C2 pipeline resumes with principal = service identity `github-webhook`) 4) `webhook_delivery` dedupe insert 5) route `push` → enqueue `catalog_sync` task + `catalog_sync` row `queued`; `installation.suspend/delete` → `sync_state='disabled'`; `unsuspend` → `active` |
| `RegisterGitRepoBindingCommand` | `POST /v1/projects/{p}/git-repo-bindings` · `project:write` | `Idempotency-Key`; stores ids + `webhook_secret_ref`; verifies installation is reachable (single GitHub call, outside the tx per P5) |
| `ListCatalogSyncsQuery` | `GET /v1/projects/{p}/catalog-syncs` · `suite:read` | cursor list newest-first (AC8) |
| `CatalogSyncTaskHandler : ITaskHandler` | worker `task` queue | tree walk → discovery → per-commit writers → `done`/`failed`; idempotent by `(binding_id, commit_sha)` |
| `GitHubClient` (typed `HttpClient`, T46) | sync task + binding verify | RS256 app JWT via `Microsoft.IdentityModel.JsonWebTokens`, cached installation tokens (short-lived, never persisted), `IHttpClientFactory` + resilience handlers (P6), allow-listed base URL `api.github.com` (S4) |

## 6. States and transitions

- `git_repo_binding.sync_state`: `active ↔ disabled` (installation events only — operators don't flip it).
- `catalog_sync`: `queued → running → done | failed` (00 §8.10); `failed` is retried by the reconcile schedule creating a *new* sync row for the same commit only if no row exists — retry of a `failed` row is via dead-letter replay (01.5.1-T4), state goes `queued` again.
- `webhook_delivery.state`: `accepted | duplicate | processed` (informational).

## 7. Jobs and integrations

- **`catalog_sync` task**: claimed by the worker `FOR UPDATE SKIP LOCKED`; natural idempotency key `(binding_id, commit_sha)`; runs the §4.3 flow — tree fetch (network, outside DB tx) → compute per-file actions → one tenant transaction running `ICaseIdentityService` + `ITestRevisionStore` + suite-revision writes + `case_rename_history` + `missing` status + `catalog_sync.counts` → commit. Network and DB phases never overlap (P5).
- **Reconcile schedule** `catalog.reconcile` every 15 min (Cronos): fire = one `task` row via `unique (schedule_name, fire_at)`; handler finds `active` bindings where `head_commit IS DISTINCT FROM last_synced_commit` and enqueues syncs.
- **Propose step**: sync calls `ICaseImportMatcher.ProposeAsync` (03.1.2) for pending import keys.
- Emits `catalog.sync_completed` outbox event (C7) for 09 staleness badge + usage metering (12).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T1 / 00 §5.4.8 | tenant learned only via `evidgate_resolve.github_repo` (SECURITY DEFINER, EXECUTE-only, audited); no BYPASSRLS role on the API | `WebhookResolverTests` + resolver audit assertion |
| Signature auth | HMAC-SHA256 constant-time compare, 401 before tenant resolution; body read with 1 MiB cap (P8) | `WebhookApiTests` AC1 |
| A10 / dedupe | `unique (provider, delivery_id)` → replay = 200 no-op | `WebhookApiTests` AC3 |
| S3 | `webhook_secret_ref` is a reference; secret resolved per-call from the secret store (11.3.1 model), never stored/logged | secret never in logs assertion |
| S4 | `GitHubClient` pinned to `api.github.com`; no user-supplied URLs | client test asserting host allowlist |
| S5 | webhook payload + tree JSON parsed with depth/size caps; file content never executed at sync (03 §6) | parser tests |
| P5 | all GitHub calls outside DB transactions (fetch-then-write split) | `CatalogSyncTests` transaction-ordering assertion |
| P2 / P3 | per-file actions computed in memory, applied via batched `unnest` upserts; sync of 2 000-case repo bounded statements | `CatalogSyncTests` on golden repos + statement counter |
| P6 | `IHttpClientFactory` + timeouts + retry; 429 honoured via `Retry-After` | `GitHubClientTests` (stub server) |
| C2 / S2 | `project:write`/`suite:read` on the HTTP endpoints; service-identity principal inside the webhook path | `WebhookApiTests`, `SyncApiTests` |
| Retention/PDPL | file paths/commit shas may carry personal data; history kept on suspend (FR-03-8); tenant deletion removes rows (11) | stated |

- **Authorization:** the binding and sync-list endpoints use `project:write` / `suite:read`; the webhook path has no session and is authorised by the HMAC signature plus the audited `evidgate_resolve.github_repo` resolver; the GitHub client calls GitHub with installation tokens only, never a user token.
- **Telemetry:** the client logs call outcomes through source-generated log messages that carry no installation token, JWT or key material; the standard resilience handler supplies retry and timeout telemetry; sync and webhook metrics belong to T2/T3.
- **Failure path:** GitHub 5xx, timeout and 429 map to a retryable `github_unavailable` / rate-limited result honouring `Retry-After`; 401 on a cached installation token evicts it and retries once; an unconfigured App key answers `github_not_configured` with no outbound call.

## 11. Rollout

- Order: T1 → T2 → T3, all M2. The webhook endpoint may ship before the sync handler (deliveries dedupe, syncs queue up) — actually required order is T2 before T3 since the handler consumes what T2 enqueues.
- Feature flag: none; the endpoint is harmless without bindings (unknown repo → 200). GitHub App must be registered with the verified V1 scopes before customers bind.
- Monitoring: `catalog_sync` `failed` count + task-queue lag feed 10's SLIs; dead-letter replay via 01.5.1-T4 operator route.
- Rollback: set `sync_state='disabled'` per binding (ops) or revert; deliveries already deduped can be re-fired by GitHub's redeliver safely (idempotent).
