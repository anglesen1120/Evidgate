## 1. Goal and non-goals

**Goal.** A GitHub push delivery is signature-verified, resolved to a tenant *before* any business table is touched (T1), deduped by `delivery_id`, and turned into a `catalog_sync` task that walks the commit tree and applies 03.1.x/03.2.x writers — idempotently. A suspended installation disables sync without deleting history.

**Non-goals.** Branch/commit/PR creation (V2, 03.4.2); other providers (GitLab/Bitbucket not in V1); the V2 draft reconciliation (03.6.1-T4); Git credentials of users — the App installation token is never persisted (03 §6).

## 2. User stories and acceptance criteria

- As a test maintainer, pushing a commit syncs my catalog once and only once, so revisions reflect the repo without manual refresh.
- As a security reviewer, the webhook endpoint cannot be spoofed and learns nothing about tenants before signature verification and scoped resolution.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /v1/webhooks/github` with a valid `X-Hub-Signature-256` → 202; with a forged/missing signature → 401, **no** row written, no tenant resolution attempted |
| AC2 | The tenant is resolved only through `evidgate_resolve.github_repo(org lookup by installation_id + repository_id)` returning `(org_id, project_id, binding_id, status)`; the function is owner-owned `SECURITY DEFINER`, app role has `EXECUTE` only, and every call writes an audit row (T1) |
| AC3 | A second delivery with the same `(provider, delivery_id)` → 200 no-op; exactly one `webhook_delivery` row and at most one `catalog_sync` row per commit per repo |
| AC4 | A push on a bound repo enqueues `catalog_sync` `state='queued'`; the worker task walks the commit tree via the App installation (read-only), applies `ICaseIdentityService`/`ITestRevisionStore`/`CreateSuiteRevisionCommand` handlers, and ends `done` with `counts jsonb` (registered/renamed/conflicts/warnings) |
| AC5 | Installation `suspend`/`deleted` events set `git_repo_binding.sync_state='disabled'`; later pushes → 200 recorded, `catalog_sync` not enqueued; catalog keeps serving last state; `unsuspend` re-enables |
| AC6 | GitHub API 5xx/429 mid-sync → task retries with `available_at` backoff; the sync is resumable/idempotent (re-running the same commit inserts nothing); after retry cap → `catalog_sync.state='failed'` + dead-letter |
| AC7 | A scheduled reconcile (Cronos `catalog.reconcile`, unique `(schedule_name, fire_at)`) enqueues a sync for bindings whose `head_commit != last_synced_commit`, repairing missed webhooks |
| AC8 | `GET /v1/projects/{p}/catalog-syncs` lists syncs newest-first (drives the 09 "catalog is stale" badge) |

## 4. Data model and migrations

`migrations/NNNN_catalog_git.sql` + resolver functions:

```sql
create table git_repo_binding (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  provider text not null default 'github',
  installation_id text not null, repository_id text not null,
  default_branch text not null default 'main',
  head_commit text, last_synced_commit text,
  sync_state text not null default 'active' check (sync_state in ('active','disabled')),
  webhook_secret_ref text not null,            -- secret-store reference, never the value (S3)
  created_at …, updated_at …, version int not null default 1,
  primary key (org_id, id), unique (org_id, id),
  unique (org_id, project_id, provider, repository_id),
  foreign key (org_id, project_id) references project (org_id, id)
);

create table webhook_delivery (
  id uuid not null, org_id uuid not null,          -- org learned only after resolve; delivery rows are tenant-scoped
  provider text not null, delivery_id text not null, event text not null,
  payload_hash text not null, state text not null default 'accepted',
  created_at timestamptz not null default now(),
  primary key (org_id, id), unique (org_id, id),
  unique (provider, delivery_id)                   -- A10 dedupe
);

create table catalog_sync (
  id uuid not null, org_id uuid not null, project_id uuid not null,
  commit_sha text not null, binding_id uuid not null,
  state text not null default 'queued' check (state in ('queued','running','done','failed')),
  counts jsonb, error text,
  started_at timestamptz, finished_at timestamptz, created_at …,
  primary key (org_id, id), unique (org_id, id),
  unique (org_id, binding_id, commit_sha),          -- at most one sync row per commit per repo (AC3)
  foreign key (org_id, project_id) references project (org_id, id),
  foreign key (org_id, binding_id) references git_repo_binding (org_id, id)
);
create index catalog_sync_list on catalog_sync (org_id, project_id, created_at desc, id); -- P4 for AC8

-- T1 resolver (owner-owned, SECURITY DEFINER; app role gets EXECUTE only)
create function evidgate_resolve.github_repo(p_installation_id text, p_repository_id text)
returns table(org_id uuid, project_id uuid, binding_id uuid, status text)
security definer … -- SELECT on git_repo_binding bypassing RLS, writes resolver-audit row
```

- RLS on all three tables (helpers, FORCE). `webhook_delivery`/`catalog_sync`/`git_repo_binding` all carry `unique (org_id, id)` (T3).
- The `unique (provider, delivery_id)` is global by design (03 §4.1): dedupe must catch a delivery even when re-issued against the same repo.

## 5. API shapes (commands, queries, endpoints)

| Shape | Endpoint / caller | Behaviour |
|---|---|---|
| `ReceiveGithubWebhookCommand` (pre-tenant entry) | `POST /v1/webhooks/github` — **no session** | 1) verify `X-Hub-Signature-256` HMAC against `webhook_secret_ref`-resolved secret (401 on fail, before anything else) 2) `evidgate_resolve.github_repo` → tuple or 404-as-202 (unknown repo: record nothing, return 200 to stop GitHub retries) 3) open tenant scope (C2 pipeline resumes with principal = service identity `github-webhook`) 4) `webhook_delivery` dedupe insert 5) route `push` → enqueue `catalog_sync` task + `catalog_sync` row `queued`; `installation.suspend/delete` → `sync_state='disabled'`; `unsuspend` → `active` |
| `RegisterGitRepoBindingCommand` | `POST /v1/projects/{p}/git-repo-bindings` · `project:write` | `Idempotency-Key`; stores ids + `webhook_secret_ref`; verifies installation is reachable (single GitHub call, outside the tx per P5) |
| `ListCatalogSyncsQuery` | `GET /v1/projects/{p}/catalog-syncs` · `suite:read` | cursor list newest-first (AC8) |
| `CatalogSyncTaskHandler : ITaskHandler` | worker `task` queue | tree walk → discovery → per-commit writers → `done`/`failed`; idempotent by `(binding_id, commit_sha)` |
| `GitHubClient` (typed `HttpClient`, T46) | sync task + binding verify | RS256 app JWT via `Microsoft.IdentityModel.JsonWebTokens`, cached installation tokens (short-lived, never persisted), `IHttpClientFactory` + resilience handlers (P6), allow-listed base URL `api.github.com` (S4) |

## 6. States and transitions

- `git_repo_binding.sync_state`: `active ↔ disabled` (installation events only — operators don't flip it).
- `catalog_sync`: `queued → running → done | failed` (00 §8.10); `failed` is retried by the reconcile schedule creating a *new* sync row for the same commit only if no row exists — retry of a `failed` row is via dead-letter replay (01.5.1-T4), state goes `queued` again.
- `webhook_delivery.state`: `accepted | duplicate | processed` (informational).

## 7. Jobs and integrations

- **`catalog_sync` task**: claimed by the worker `FOR UPDATE SKIP LOCKED`; natural idempotency key `(binding_id, commit_sha)`; runs the §4.3 flow — tree fetch (network, outside DB tx) → compute per-file actions → one tenant transaction running `ICaseIdentityService` + `ITestRevisionStore` + suite-revision writes + `case_rename_history` + `missing` status + `catalog_sync.counts` → commit. Network and DB phases never overlap (P5).
- **Reconcile schedule** `catalog.reconcile` every 15 min (Cronos): fire = one `task` row via `unique (schedule_name, fire_at)`; handler finds `active` bindings where `head_commit IS DISTINCT FROM last_synced_commit` and enqueues syncs.
- **Propose step**: sync calls `ICaseImportMatcher.ProposeAsync` (03.1.2) for pending import keys.
- Emits `catalog.sync_completed` outbox event (C7) for 09 staleness badge + usage metering (12).

## 11. Rollout

- Order: T1 → T2 → T3, all M2. The webhook endpoint may ship before the sync handler (deliveries dedupe, syncs queue up) — actually required order is T2 before T3 since the handler consumes what T2 enqueues.
- Feature flag: none; the endpoint is harmless without bindings (unknown repo → 200). GitHub App must be registered with the verified V1 scopes before customers bind.
- Monitoring: `catalog_sync` `failed` count + task-queue lag feed 10's SLIs; dead-letter replay via 01.5.1-T4 operator route.
- Rollback: set `sync_state='disabled'` per binding (ops) or revert; deliveries already deduped can be re-fired by GitHub's redeliver safely (idempotent).
