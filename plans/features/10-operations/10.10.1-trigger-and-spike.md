## 1. Goal and non-goals

**Goal.** Define and measure the trigger under which Temporal would replace our own `task`/outbox queue (DECISIONS A7): the count of workflows with long human waits, the recovery incidents caused by queue/outbox limitations, and the manual work each costs. If the trigger is not met, the queue stays and the measurement is recorded; if it fires, a bounded spike answers whether Temporal reduces operational risk for the healing PR flow.

**Non-goals.** Adopting Temporal (the spike is a throwaway evaluation, never a migration); building the healing PR/approval flow itself (08 owns it); evaluating any other orchestrator (A7 names Temporal specifically as the alternative to our queue); changing the queue (the trigger measurement feeds a future decision, it does not alter 00 §5.3 now).

## 2. User stories and acceptance criteria

- As the Tech Lead, I know objectively — from measured workflow counts and recovery incidents, not gut feel — whether our own queue is still sufficient or whether Temporal would reduce operational risk.
- As the owner, a "trigger fired" outcome comes with a bounded spike memo I can use to decide, without a vendor commitment made inside this plan.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The trigger is defined as measurable inputs — number of workflows with long human waits, recovery incidents attributable to queue/outbox limitations, and the manual work each costs — computed from 10.3.1-T3's metrics and the incident log; a verdict (met / not met) is recorded with the numbers |
| AC2 | If the verdict is "not met", the queue+outbox design (00 §5.3) is confirmed to stay, and the measurement artefact records the inputs and date so the trigger can be re-evaluated later |
| AC3 (V3, conditional) | Only if the trigger fires: a bounded spike models the healing PR flow (candidate → validated → approved → applied waits, 00 §8.7) under Temporal, measures the cost of running one more system and sketches the migration path; output memo goes to plan 08 and 00 |

## 3. Contracts touched

- DECISIONS A7 — this story owns the trigger's definition and measurement; no contract change (the trigger firing opens a future decision, it does not auto-adopt Temporal).
- 00 §5.3 — measured as the incumbent design, not modified.
- T60 — trigger inputs are measured from real metrics/incidents, never asserted.
- No schema, permission or API change.

## 4. Data model and migrations

None. Trigger inputs are read from the existing metrics catalogue (10.3.1-T3) and incident log; the verdict is a document, not a row.

## 5. API shapes (commands, queries, endpoints)

None. Internal measurement only; no endpoint is added.

## 6. States and transitions

None. The verdict is a recorded conclusion (`met`/`not met`), not a persisted state machine.

## 7. Jobs and integrations

- Trigger measurement (T1) reads 10.3.1-T3's metrics and the incident log — a one-off/recurring report, not a standing job.
- The conditional spike (T2) stands up a throwaway Temporal instance (devcontainers/local, never production), models the healing PR flow's waits, and is torn down afterward; its memo is consumed by plan 08 and recorded against A7.
- If the trigger never fires by the time the V3 review happens (M5), T2 is recorded as "not executed — trigger not met" rather than silently dropped.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T60 (no fabricated metrics) | The three trigger inputs are computed from real metrics/incidents; a missing input is recorded as unavailable, not zeroed | AC1 |
| No production data in the spike | The throwaway Temporal instance runs synthetic workflow definitions only; nothing tenant-scoped is migrated or replayed | AC3 review |
| A7 (no Kubernetes/Temporal in V1–V2) | Temporal only ever runs inside the bounded spike; production keeps the own-queue design unless a later decision changes it | AC2 |
| P-rules / S-rules | No hot-path or tenant-facing code is added; spike infra is isolated and torn down | — |

- No feature flag. T1 is a measurement deliverable landing in M2; T2 (V3, M5) only runs if T1's recorded verdict (or a later re-evaluation) is "met".
