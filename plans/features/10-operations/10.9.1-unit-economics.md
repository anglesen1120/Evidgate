## 1. Goal and non-goals

**Goal.** Cost per 1 000 events, per artifact GB-month and per run is measured, tagged and reported monthly per environment, and the unit-cost model is handed to plan 12 for pricing and quota decisions — so unit economics are visible before pricing locks (area-plan §8).

**Non-goals.** Setting prices, quota values or the pilot contract (12.2.1/12.3.1 own them); choosing the LLM provider (O4); building the usage ledger tables themselves (12.3.1/04.8.1/06.5.2 emit the metering; this story consumes their counters). T2 is V2 and only extends the model to LLM + healing-replay cost once those paths exist (08.5.x, M4).

## 2. User stories and acceptance criteria

- As the Tech Lead, a monthly cost report per environment and per unit tells me whether artifact storage is growing faster than revenue before pricing locks.
- As plan 12's pricing owner, I get a unit-cost model whose numbers are measured, with unavailable sources flagged, so I never price against a fabricated zero.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Every environment's resources carry a consistent tag set (`env`, `service`) so cost is attributable; a budget alert per environment is configured and fires on a staged threshold breach |
| AC2 | The V1 baseline unit-cost model computes cost per 1 000 events, per artifact GB-month and per run from the provider bill (by tag) + the per-unit counters exposed by 10.3.1-T3; a monthly report per environment is produced |
| AC3 | Any unit metric whose source does not exist yet is reported as `null`/"unavailable" with a reason — never as 0 (T60); e.g. egress per tenant stays unavailable until `IObjectStore` exposes egress (06.5.2) |
| AC4 (V2) | The model adds LLM token cost and healing-replay cost per tenant (from 08's `healing_llm_call` accounting, T30) and the result is handed to 12.3.1 for pricing/quota |

## 3. Contracts touched

- T60 — governs how unavailable metrics render; no new contract introduced.
- 00 §9.1 — usage metering stays an internal read; no public write endpoint is added.
- No schema, permission or API change; this story reads 10.3.1-T3's counters plus provider billing/tag data.

## 4. Data model and migrations

None. The unit-cost report is a computed document (`docs/cost/` monthly artefacts); it reads the metrics catalogue counters (10.3.1-T3) and the provider's tag-scoped billing export — no new business table or migration.

## 5. API shapes (commands, queries, endpoints)

No new endpoint. Reporting is an internal scheduled computation; its output is consumed by 12's pricing work as a document/dataset, not a `/v1` route (consistent with 00 §9.1: usage metering is internal, quantities never from a client).

## 6. States and transitions

None. The monthly report is a snapshot artefact, not a stateful resource.

## 7. Jobs and integrations

- A scheduled `task` (Cronos schedule, unique `(schedule_name, fire_at)`, 00 §5.3) runs monthly per environment: pulls the tag-scoped billing export, joins the 10.3.1-T3 per-unit counters, emits the unit-cost report.
- Consumed by plan 12 (12.3.1/12.4.1) for pricing and quota; the V2 extension additionally consumes 08's `healing_llm_call` per-tenant rows (T30).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T60 (no fabricated metrics) | Unavailable sources render `null`/"unavailable" + reason, never 0 — the defining constraint of this story | AC3 |
| 00 §5.7 S3 | Billing-export credentials come from the environment secret store; the report carries numbers only, no secrets or tenant-identifying fields beyond `org_id` | review of report artefact |
| Tenant isolation | Per-tenant cost attribution reads already-tenant-scoped counters; the report is operator-facing only, never a tenant-visible write path | AC2/AC4 scope review |
| Privacy | Cost rows aggregate to `(env, unit)` or `(org_id, unit)`; no content, no PII | AC2 |
| P-rules | The monthly job is off the hot path; it issues a bounded set of reads (P3 spirit) and never runs a network billing call inside a DB transaction (P5) | AC2 job review |

## 11. Rollout

- No feature flag; the monthly scheduled task is the rollout. T1 lands in M2 (tagging + alerts before pilot spend grows); T2 is a separate V2 PR in M4 once 08's LLM accounting exists.
- Monitoring: the budget alert per environment is itself the monitor; a failed monthly job surfaces through the dead-letter alert (10.3.1-T5) and the dead-letter runbook (10.7.1-T1).
- Rollback: disable the schedule; no data or production state is affected — the report is read-only output.
