## 1. Goal and non-goals

**Goal.** Every alert rule in 10.3.1-T5 reaches a named destination and a person, including out of hours (review S2). With one operator there is no rota, so the design is explicit about it: one paging tool with a routing table (severity to destination), a primary (the owner), a secondary or an auto-acknowledge fallback that records "nobody answered" and escalates to a second channel, and a monthly test page. The 72 h breach clock (Art. 23.1 ✅ per plan 11) has a named owner and a start event that the paging path records.

**Non-goals.** Alert thresholds and rule content (10.3.1-T5); the incident severity ladder and postmortem process (10.7.1-T6); the breach runbook content (11.9.1-T2); status page for customers; a staffed 24/7 rota (not available to a solo operator, `[OPEN]` for the first hire).

## 2. User stories and acceptance criteria

- As the operator, a P1 alert wakes or reaches me within minutes, and I am told when a page went unanswered.
- As the operator, I know before an incident that my paging path works because I test it monthly.
- As a compliance owner, I can show who owned the 72 h clock and when it started.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A route table `infra/alerts/routing.yml` maps every alert in 10.3.1-T5 (by severity label) to a destination; a lint fails when any alert lacks a route or a destination is undefined |
| AC2 | In the dev/staging compose stack a synthetic firing alert is delivered to the receiver stub within one evaluation interval, carrying alert name, severity, environment, runbook URL and no secrets |
| AC3 | P1/P2 alerts reach the paging destination (push/phone-level); P3 goes to chat/email only; the severity-to-channel mapping is documented in the decision record |
| AC4 | Unacknowledged page: after the escalation timeout (default 15 min `[INFERENCE]`) the secondary destination is notified and an `alert_unacknowledged` record is written; with no secondary, the auto-ack fallback marks it, sends a second-channel message and raises the repeat interval |
| AC5 | A monthly test page is scheduled (Cronos schedule or CI cron), delivered, and its acknowledgement time recorded; a missed test raises an alert |
| AC6 | Out-of-hours: quiet-hours policy is explicit (P1 always pages; P2 pages 07:00–23:00 local, else queued to the first morning, `[INFERENCE]` for the owner to confirm) and covered by a routing test that uses a fake clock |
| AC7 | The breach runbook (11.9.1-T2) links to the paging path and names an owner for the 72 h clock; a "suspected breach" page type starts a clock record (timestamp, owner) |
| AC8 | The decision record states the chosen tool, why, cost, what runs without internet access to it (fallback), and which parts are `[OPEN]` on O3 |

## 4. Data model and migrations

No business tables (plan 10 owns none). Alert state lives in the paging tool. The monthly-test and breach-clock records are files under `docs/runbooks/records/` (`[INFERENCE]` sufficient for a single operator); if the 72 h clock needs a durable app record it is a 11.9.1 table, not here (`[OPEN]` 11.9.1).

## 5. API shapes (commands, queries, endpoints)

No public API. Integration surface: alert rules in OTel/Prometheus-style rule files evaluated per 10.3.1 (⚠️ backend choice is 10.3.1's) and a webhook receiver contract: `POST <paging-tool-webhook>` with fields `name`, `severity`, `env`, `summary`, `runbook_url`, `fired_at`. A stub receiver in `infra/dev/` implements it for tests.

## 6. States and transitions

Alert lifecycle in the paging tool: `firing → acknowledged → resolved`, with `firing → unacknowledged_escalated` after the timeout. Transitions are the tool's; this story records and tests them. No application state machine changes.

## 7. Jobs and integrations

- Tool choice (T1.1) compares by criteria: works for one person, phone-level push/call, free or low cost, no dependency on O3's provider, a webhook API, acknowledgement tracking. Candidates `[INFERENCE]`: a hosted on-call product with a free tier, or a self-hosted notification gateway plus a mobile push app. ⚠️ Pricing and free-tier limits are unverified and must be cited when T1.1 runs.
- Single-operator cover: primary = owner; secondary = a trusted second contact if one exists, else the auto-ack fallback (record, repeat page, second channel). Honest statement in the decision record: with one operator an unanswered P1 may stay unanswered; the mitigations are redundancy of channels and the monthly test, not a guarantee.
- Fire drill: part of 10.7.1's "second person executes a runbook" rule applies to the breach path in T3.
- Provider-specific (`[OPEN]` on O3): provider-native alarms (cloud monitoring) may feed the same tool later; V1 on compose uses the OTel collector rules only.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| No secrets or personal data in notifications | payload fields limited to the list in §5; tenant data excluded (org id only if needed) | AC2 payload test |
| Webhook secret | stored in the secret store; rotated per 10.7.1-T4 key-rotation runbook | rotation checklist includes it |
| Reliability | monthly test, repeat paging, second channel | AC4, AC5 |
| Alert fatigue | severity mapping and quiet hours documented; P3 never pages | AC3, AC6 |
| Breach timing | clock owner named, start recorded | AC7 |

DoR review answers. **Authorization:** only the operator can acknowledge or change routes; the tool account has MFA. **Retention/deletion impact:** alert history in the tool may contain org ids; retention set to the minimum the tool allows (⚠️ per tool); no personal data of customers. **Telemetry:** `alert_notifications_total{severity,result}`, `alert_unacknowledged_total`, `paging_test_ack_seconds`; a dead-man's-switch alert fires if the alert pipeline itself goes silent. **Failure path:** tool outage — a second channel (email) is configured; the dead-man's switch is checked by the monthly test; the runbook lists "check the dashboard by hand every morning" as the degraded mode.
