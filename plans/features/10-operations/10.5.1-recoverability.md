## 1. Goal and non-goals

**Goal.** A restore into a clean environment reproduces a run, its evidence and its decision within RPO 15 min / RTO 4 h (FR-10-8, 00 §11): managed-PostgreSQL-18 backup with PITR and a documented recovery-point expectation; object-storage protection (versioning, lifecycle, orphan-object sweep hook, integrity verification); restore-drill automation that restores a PITR backup into a clean project, applies the migration head, runs the tenant-isolation + smoke suites and records duration against the RTO; and a DR runbook covering failover decision, communication, a data-loss statement at the measured RPO and recovery order. The drill evidence attaches to the M2 exit gate — a failed drill is a P1 that blocks the pilot (area plan §5).

**Non-goals.** Choosing the provider (10.8.1/O3 — this story consumes whatever managed-PostgreSQL-18 + object-store the O3 memo lands on); the artifact-retention *policy values* (06 owns retention rules; this story owns the bucket-level protection mechanisms); the reconcile job's business logic (06 owns it; this story wires the orphan-sweep hook into it); cross-region/multi-region DR (A7, out of scope for V1).

## 2. User stories and acceptance criteria

- As an operator, I can state exactly how much data a disaster loses (the measured RPO), not "we have backups".
- As the Tech Lead, the M2 gate cannot be claimed without a recorded restore drill whose duration and verification output are attached.
- As a second responder, the DR runbook tells me the recovery order and what to say about data loss without paging the author.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | PITR/continuous backup is enabled on the managed PostgreSQL 18 instance per environment, and a script returns the most recent restorable point ≤ 15 min old |
| AC2 | Object storage has versioning enabled and lifecycle rules applied (incl. `pending/` 24 h expiry, T18); the orphan-sweep hook is wired to 06's reconcile job; an integrity-verification pass checksums a sample of `ready` objects and reports mismatches |
| AC3 | The restore-drill automation (one command) restores a PITR backup into a clean environment, applies migrations to head via `Evidgate.Migrator`, runs the tenant-isolation + smoke suites, and records duration; a seeded run + its artifacts + its decision are present after restore |
| AC4 | The recorded drill duration is ≤ 4 h and the drill evidence (start time, restored point, duration, suite results) is attached to the M2 exit-gate record |
| AC5 | `docs/runbooks/dr.md` contains failover decision criteria, the communication plan, a data-loss statement template at the measured RPO, and the recovery order database → object storage → queues → app; a second person executes a dry run in staging |
| AC6 | Simulated drift (e.g. an object deleted after backup) is surfaced by the integrity verification, not silently passed over |

## 3. Contracts touched

- 00 §11 RPO/RTO row — implemented; the numbers (15 min / 4 h) are the contract, unchanged.
- 00 §8.4 — consumed: restored artifacts must land in a valid artifact state; the drill asserts no `ready` artifact references a missing object and no object claims `ready` without a row.
- 00 §4 M2 exit gate — the drill record is the gate evidence.
- `[OPEN]` PITR capability and exact mechanism depend on the O3 provider decision (area plan §11); this plan scripts against the provider-agnostic interface (provider backup API) and parameterises the provider calls.

## 4. Data model and migrations

None owned. Plan 10 owns no business tables (area plan §4). The drill *applies* existing migrations to head via `Evidgate.Migrator` (DbUp journal verification included), which validates the module-owned schema is restorable; no new table, column or migration is introduced here. Drill records (duration, point restored, suite results) are stored as `infra/drills/` artifacts and attached to the M2 gate record.

## 5. API shapes (commands, queries, endpoints)

None. No `/v1` surface and deliberately no restore endpoint (restore is an operator procedure, never a tenant-reachable action; 00 §9.1 keeps operator paths on the operator ingress). Mechanisms:

| Mechanism | Effect |
|---|---|
| Provider PITR API call (`infra/scripts/pitr-restore.*`) | create a restored instance/snapshot at the requested point (⚠️ provider-specific call until O3 lands; wrapped behind a single script interface) |
| `Evidgate.Migrator --status` / apply | bring the restored DB to the expected journal head; mismatch aborts the drill |
| Object-store versioning + lifecycle configuration | bucket-level config applied per environment (`infra/`) |
| Orphan-sweep hook | invokes 06's reconcile job entry point over a restored bucket listing |
| Integrity verification | checksum pass over a `ready`-object sample; mismatches reported in the drill record |
| Drill orchestrator (`infra/scripts/restore-drill.*`) | end-to-end: restore → migrate → isolation + smoke suites → duration/evidence capture |

## 6. States and transitions

None introduced. Consumed states a restore must respect, unchanged: artifact lifecycle (00 §8.4 — a restored `ready` row whose object is missing becomes an integrity failure, not a silent pass), run terminal states (00 §8.1), `task`/`outbox` queue state (00 §5.3 — in-flight tasks replay idempotently after restore; no manual queue surgery in the DR order).

## 7. Jobs and integrations

- Consumes 10.1.1-T3's bootstrap (roles, buckets, network) to stand up the clean drill environment — task dependency.
- Orphan sweep calls 06's reconcile job (its entry point, not reimplementation).
- Drill evidence feeds the M2 exit gate (00 §4) and the pilot review.
- The DR runbook's recovery order aligns with 10.7.1's runbook set (dead-letter, stuck run, orphan artifact) — queue recovery steps reference those runbooks rather than duplicating them.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §11 RPO 15 min / RTO 4 h; durability | PITR config + measured restorable point + timed drill | AC1, AC3, AC4 |
| Tenant isolation after restore | the isolation suite runs against the restored DB before the drill is a pass | AC3 (isolation suite leg) |
| Least privilege (area plan §6) | restore automation runs under the deploy identity's restore scope only; no human prod console steps scripted | IAM-policy check in T3 |
| Secrets not in drill artifacts | drill record carries timestamps/durations/results, never credentials | record inspection |
| T18 / object protection | `pending/` lifecycle + versioning configured, consistent with the artifact contract | AC2 |
| Data-loss honesty (NFR-10-1 spirit) | DR runbook's data-loss statement is computed from the *measured* RPO, not the nominal one | AC5 |
| Performance | integrity verification samples objects (bounded set), never a full-bucket scan on the hot path; sweep runs as a scheduled task (00 §5.3) | verification bounds asserted in T2.2 |
| Retention/deletion impact | lifecycle rules are the enforcement mechanism 06's retention policies rely on; no retention *values* set here beyond the `pending/` 24 h rule already contracted | AC2 + 06's tests |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Restorable point ≤ 15 min | script asserts `now - latest_restorable_time <= 15m` (AC1) |
| Versioning + lifecycle applied | bucket config assertion incl. `pending/` expiry (AC2) |
| Orphan sweep finds a planted object | seed an object with no `ready` row; sweep/reconcile reports it (AC2) |
| Integrity verification catches drift | delete/corrupt a `ready` object post-backup; verification flags it (AC6) |
| Full drill reproduces run + evidence + decision | seeded fixture restored into clean env; fixture assertions pass; duration recorded (AC3, AC4) |
| Migration head enforced on restore | restore an older backup; Migrator applies to head or the drill aborts (AC3) |
| Drill failure blocks the gate | a failed suite leg marks the drill record failed; M2 gate evidence absent (area plan §5 P1 path) |
| DR runbook executable by a second person | staging dry run with communication + data-loss statement produced (AC5) |

## 11. Rollout

- No feature flag. Merge order: T1 → T3 (drill needs PITR) with T2 in parallel, T4 after the first real drill; all M2.
- The drill is scheduled to re-run quarterly after the pilot-gate pass (area plan §8 risk: RTO unproven until the first real drill) — cadence recorded in the DR runbook.
- Monitoring: drill success/failure and measured RPO/RTO feed 10.3.1's operational SLI view; a failed drill is a P1 (area plan §5).
- Rollback: disable the scheduled drill and bucket-policy changes via `infra/` config revert; PITR itself stays on (disabling backup is never a rollback).
