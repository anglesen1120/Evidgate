## 1. Goal and non-goals

**Goal.** A compromised application credential cannot destroy evidence (review S5). Three separate S3 principals: the app credential (put/get/head, no delete, no version delete, no policy change), a deletion-only retention credential used by the retention sweeper only, and an owner/admin credential held by the operator offline. Bucket versioning stays on (10.5.1-T2); where the backend supports object lock or an equivalent policy, evidence objects are protected against version deletion for a retention window. An automated test deletes an object, restores it from a version or copy, verifies its checksum and that the artifact row returns to `ready`. Everything is specified and tested on the compose stack with SeaweedFS first; managed-provider mechanics are `[OPEN]` on O3.

**Non-goals.** Versioning, lifecycle and the sweep hook (10.5.1-T2); the restore-drill harness and DR runbook (10.5.1-T3/T4); retention and deletion semantics (06 retention, 11.9.1-T5); database backup (10.5.1-T1); choosing the provider (10.8.1); customer-managed keys.

## 2. User stories and acceptance criteria

- As the operator, a leaked app credential cannot erase evidence or its history.
- As the operator, I can restore a deleted artifact object and know it is byte-identical.
- As a compliance owner, I can state where replicas live and whether an offshore replica is a cross-border transfer.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | With the app credential, `DeleteObject`, `DeleteObjectVersion`, `PutBucketVersioning`, `PutBucketPolicy` and `PutLifecycleConfiguration` against the evidence bucket return an access-denied error; `PutObject`, `GetObject`, `HeadObject` on allowed prefixes succeed |
| AC2 | The retention credential can delete (create a delete marker) under the evidence prefixes but cannot `GetObject`, `PutObject` or change bucket configuration |
| AC3 | A version of an evidence object cannot be permanently deleted with either runtime credential; only the operator credential can, and doing so is outside the application (documented) |
| AC4 | The retention sweeper deletes with the retention credential and the artifact row goes `pending_delete → deleted` only after the delete succeeded; with the app credential the same job fails closed and writes nothing |
| AC5 | Restore test: after deleting an object (delete marker or hard removal), restore from the previous version or the copy yields an object whose `sha256` equals the artifact row's checksum and the artifact is `ready` again; the test fails if checksum or state differs |
| AC6 | A restore of a version whose checksum does not match is refused and the artifact is marked for operator attention (alert), never silently `ready` |
| AC7 | Credential split is verified at startup: the API refuses to start in `staging`/`prod` profiles if the app credential has delete permission (self-check by a harmless probe against a sentinel key) |
| AC8 | The runbook entry names the steps, the drill date, duration and the attached result; the drill result is stored beside the 10.5.1-T3 restore evidence |

## 4. Data model and migrations

No new tables. If the retention sweeper needs a record of which principal deleted, it reuses the audit writer (02.7.1) with action `artifact.object_deleted`. No migration expected; if T2 needs a `last_restored_at` column it is added additively (`[INFERENCE]` not needed in V1; restore evidence lives in the drill result file).

## 5. API shapes (commands, queries, endpoints)

No public API. Internal only: the storage abstraction (06) gains two named clients, `IEvidenceStoreWriter` (app credential) and `IEvidenceStoreRetention` (retention credential), registered separately in Api and Worker; the Api host cannot resolve the retention client. Operator surface is a script `scripts/ops/object-restore.sh` (T2/T3), not an endpoint (00 §9.1).

## 6. States and transitions

Artifact states unchanged (00 §8.4). Restore moves `deleted-object-but-row-ready` back to a consistent `ready` row; it never reopens `deleted` rows (a deleted artifact stays deleted). A checksum mismatch after restore leaves the row `ready → rejected` is not allowed; the artifact is flagged `needs_attention` in the alert only (no new state, `[INFERENCE]`). Retention transitions are idempotent.

## 7. Jobs and integrations

- Compose stack: SeaweedFS identities in `infra/seaweedfs/s3-config.json` split into `app`, `retention`, `admin` with per-action grants. ⚠️ SeaweedFS action granularity (for example `Write` covering delete, bucket-level versioning, object lock) must be verified in T1.1; if it cannot deny delete to a writer, the compromise is recorded as a parity gap and covered by a proxy/policy test instead.
- Retention sweeper (06) switches client to the retention credential.
- Restore script: list versions, copy a chosen version to a new key, verify `sha256`, `HEAD` and update/verify the artifact row through the reconcile hook from 10.5.1-T2.
- Provider specifics `[OPEN]` on O3: bucket policy / IAM conditions, object lock modes, MFA delete, cross-account or cross-region replica. Note for 11: ⚠️ an offshore replica is a cross-border transfer (PDPL Art. 20.2 ✅ per plan 11); any replica outside the chosen residency requires the 11 transfer dossier before it is enabled. Default: no offshore replica until the owner decides.
- Single operator: the admin credential lives in the operator's password manager, not in CI; restore uses it by hand.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Least privilege | three principals; app cannot delete; retention cannot read | AC1, AC2 |
| Compromise containment | version deletion denied to runtime credentials | AC3 |
| Secrets | credentials from env/secret store, never logged or in metric labels | log-allowlist test |
| Audit | every retention delete and every restore writes an audit row | AC4, AC5 |
| Tenant isolation | restore tool takes `org_id` and verifies the key prefix matches the artifact's org | test with two orgs |
| Privacy | replica location documented; no offshore copy by default | AC8 |
| Performance | restore of one object is O(object); drill uses a ≥ 20 MB object | AC5 |

DoR review answers. **Authorization:** no new `/v1` permission; credential split replaces it. **Retention/deletion impact:** all deletes route through the retention credential; versions persist after a delete marker until a lifecycle rule for noncurrent versions expires them, so the deletion SLA of 11.9.1-T1 must count version expiry (`[OPEN]` noncurrent-version retention window, owner/counsel). **Telemetry:** `object_delete_denied_total{principal}`, `object_restore_total{result}`, `object_restore_seconds`; alert on any denied delete from the app principal. **Failure path:** restore with checksum mismatch aborts and alerts; sweeper with wrong credential fails closed.

## 11. Rollout

- Order: T1 (compose, M3 start) → T2 → T3. Per DECISIONS O3 the provider run of the suite waits for the provider choice; compose is the gate until then.
- Monitoring: alert on `object_delete_denied_total{principal="app"}` > 0 and on a failed restore test.
- Rollback: re-merge identities into one (dev only); never in staging/prod, where the startup self-check blocks it. Restored objects are plain objects, nothing to roll back.
