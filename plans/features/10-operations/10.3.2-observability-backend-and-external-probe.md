## 1. Goal and non-goals

**Goal.** Close review S11: (1) decide the observability backend in an ADR before the collector lands (10.3.1-T2 depends on this story's T1): a compose-local stack that works today and a managed-OTLP exit after O3, both behind the OpenTelemetry collector so the application never changes; with retention and cost limits stated per signal; (2) measure availability from outside the service network with a scheduled synthetic probe that checks health and runs a canary ingest-to-decision path on a dedicated tenant; (3) tie log and trace retention to the deletion promises and prove that no customer content, only ids, is in telemetry and that a tenant deletion purges what it must.

**Non-goals.** Instrumentation and the metrics catalogue (10.3.1-T1/T3); the collector deployment itself (10.3.1-T2, unblocked by T1 here); SLI definitions and targets (10.4.1-T1); alert rules and paging (10.3.1-T5, 10.7.2); deletion mechanics for tenant data (11.9.1-T1, this story only verifies telemetry stores against it); a status page for customers.

## 2. User stories and acceptance criteria

- As the owner, the backend choice, its cost ceiling and its exit path are written down before any collector is deployed.
- As the owner, I learn the service is down from a check that does not run inside the service network.
- As a customer's DPO, telemetry holds ids, never test content, and it ages out or is purged inside the promised windows.

## 4. Data model and migrations

No migrations in V1. The canary data uses ordinary rows of a dedicated organization/project seeded by the environment bootstrap (10.1.1-T3) and removed by the normal retention path. Backend storage is outside PostgreSQL (volumes named in the ADR). `[OPEN]` CR-10.3.2-2 above if a `synthetic` column is chosen.

## 5. API shapes (commands, queries, endpoints)

No new endpoints. The probe is a client of existing routes:

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Query | liveness | `GET /health/live` | none | 200 / 503 |
| Query | readiness | `GET /health/ready` | none | 200 / 503 |
| Command | canary ingest | existing ingest endpoint (00 §9.3) | probe token, ingest scope on the canary project | 202 / 4xx, never 429 by design (quota set above probe rate) |
| Query | canary decision | existing run/decision read | `run:read` on the canary project | 200 with decision / 404 until ready |

Probe script: `scripts/probe/synthetic.mjs` (Node, no new runtime dependency beyond the workspace), exit code and metric push per check.

## 6. States and transitions

Probe check: `scheduled → running → succeeded | failed(reason)`; a missing run (the scheduler did not fire) is `absent`, not `failed`, and the SLI treats `absent` as unknown. Canary run lifecycle is the ordinary run/evaluation lifecycle (00 §8) on the canary tenant; the probe never alters or reads other tenants. Backend retention: `ingested → retained → expired (purged)` per signal.

## 7. Jobs and integrations

- Backend options (decision in T1): ⚠️ candidates for a compose-local stack built from Apache-2.0/MIT-compatible components, for example the OpenTelemetry Collector (Apache-2.0), Prometheus (Apache-2.0), Grafana Tempo and Loki (⚠️ AGPL-3.0 at the time of writing, which the DECISIONS §4 rule excludes from the shipped stack unless the owner accepts it), Jaeger (Apache-2.0), VictoriaMetrics (Apache-2.0), SigNoz or ClickHouse-based stores (⚠️ licences verified). The ADR picks and cites; managed OTLP (provider tier) is the post-O3 exit `[OPEN]` O3.
- Cost and retention limits: stated per signal as numbers with `[INFERENCE]` marks (starting point: traces 7 days sampled per 10.3.1-T1, logs 30 days, metrics 13 months at reduced resolution, backend storage ceiling in GiB) and revised after 10.6.1-T1 load numbers; these are the default, not a customer promise.
- Probe locations: `[OPEN]` O3. Until a provider exists the options are a scheduled GitHub Actions workflow (⚠️ cron minimum interval and best-effort scheduling documented by GitHub, so the interval is at least 5 minutes and delays are expected) or a second, separately networked host owned by the operator; on compose the probe is a container on an isolated network that reaches only the public hostname. The ADR names the dev default and the staging choice.
- Probe frequency and canary load are tiny by design; canary rate must stay far under the 04.1.2 per-project quota and under 10.11.1 per-IP limits (the probe uses an allowed-listed token, not an exemption from limits).
- Deletion link: telemetry deletion checked against 11.9.1-T1's verified-deletion procedure (T3.2).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| No secrets in telemetry (S3) | collector redaction from 10.3.1-T2 plus allow-listed log fields | AC9 |
| No customer content in logs beyond ids | content test on the live pipeline | AC9 |
| Deletion promises hold for telemetry | retention ≤ deletion window; purge check | AC8, AC10 |
| Availability measured honestly | probe outside the network, absent ≠ up (T60) | AC4, AC7 |
| Least privilege | probe token scoped to the canary project | AC6 |
| Cost bounded | per-signal retention and a storage ceiling | AC3 |
| Copyleft avoided | licence rule applied in the ADR | AC1 |

DoR review answers.

- **Authorization:** the probe token is an ingest/run-read credential on one project; no new permission; backend access is operator-only and not exposed on public ingress.
- **Retention/deletion:** this story defines it for telemetry; per-signal windows must not exceed the deletion promise (AC8) and tenant deletion is verified (AC10); the canary tenant's own data follows normal retention.
- **Telemetry:** the probe metrics `probe_success`, `probe_duration_seconds`; absence of probe data is itself a signal consumed by 10.3.1-T5 (alert owner and runbook link required).
- **Failure path:** see below.

Failure paths: backend down or full → the collector buffers within its memory limit then drops (app unaffected, never blocks requests); a drop counter is exposed; probe location unreachable → `absent`, not `up`, and an alert for "probe silent" after 3 missed intervals; canary decision mismatch → failure with reason and no retry storm (single retry then fail); canary tenant data grows → retention purge test (AC6); the owner is the only recipient of alerts until 10.7.2 (the probe works without paging).

## 11. Rollout

- Order: T1 (M1, before 10.3.1-T2 lands) → T2 (M2, after 10.4.1-T1 and 10.3.1-T3 supply the SLI and metrics) → T3 (M3, after 10.3.1-T2 and 11.9.1-T1). The compose profile ships first; managed OTLP and the staging probe location follow O3.
- Monitoring: `probe_success` by check, "probe silent" alert owned in 10.3.1-T5, backend storage use against the ceiling.
- Rollback: the backend is swapped by changing collector exporters (no application change); the probe is disabled by its schedule with the SLI showing "unavailable" rather than "up"; the canary tenant remains and ages out by retention.
- `[OPEN]` O3: probe location, managed OTLP provider and its retention/cost tiers; revisit in 10.8.1.
