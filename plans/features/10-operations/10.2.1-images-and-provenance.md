## 1. Goal and non-goals

**Goal.** One immutable artifact per deployable unit, built once and promoted unchanged dev → staging → prod (FR-10-2): multi-stage `dotnet publish` images for `Evidgate.Api`, `Evidgate.Worker` and `Evidgate.Migrator` on a pinned SDK builder, running on a digest-pinned chiseled non-root `aspnet:10.0` base; a CycloneDX SBOM per image; registry hosting with image signing and provenance attestation; and a deploy workflow that resolves digests only — `latest` can never appear in a deploy file. `apps/web` is an Angular static bundle on object storage + CDN, not a container.

**Non-goals.** The deploy pipeline, expand gate, canary and rollback (10.2.2); the CDN/edge header values for the app origin, which T63 assigns to this story's edge config while 09.1.1's E2E test verifies them — this story ships the mechanism, 09.1.1 proves the headers; vulnerability and licence *policy* (scan results go to 11.6.1; the scan tooling itself is 01.7.1-T2/01.9.1-T2); environment bootstrap (10.1.1-T3); the viewer-origin hosting (10.1.1-T4).

## 2. User stories and acceptance criteria

- As a deployer, I promote a digest, never a tag, so what passed staging is bit-identical in prod.
- As a security reviewer, every image carries a signature, a provenance attestation and an SBOM, so I can verify what it contains and who built it.
- As an incident responder, I can rebuild the exact image from the pinned build inputs (pinned builder digest, lock files) when investigating a supply-chain question.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `dotnet publish` for Api and Worker on the pinned `mcr.microsoft.com/dotnet/sdk:10.0` builder produces an image whose runtime base is the digest-pinned chiseled non-root `aspnet:10.0`; `docker inspect` shows a non-root `User` |
| AC2 | `grep -R ':latest' infra/` finds no mutable tag in any deploy file, and a `scripts/check-no-mutable-tags.sh` lint fails on an injected one |
| AC3 | A CycloneDX SBOM exists per image; every NuGet package version in it matches `Directory.Packages.props` / `packages.lock.json` (diff script exits 0) |
| AC4 | The pushed image carries a signature and a provenance attestation verified by the registry tooling (`cosign verify` / `cosign verify-attestation` or provider-native equivalent, ⚠️ tool choice confirmed at build against the DECISIONS §4 licence rule) |
| AC5 | `dotnet publish` for `Evidgate.Migrator` produces its own image (separate Dockerfile), not a tag of the Api or Worker image |
| AC6 | `apps/web`'s build produces a static bundle artifact (index + hashed assets) published to object storage + CDN — no `apps/web` container image exists in the registry |

## 3. Contracts touched

- Ruling T41 — implemented: builder/runtime pins, separate Migrator image, `apps/web` static-bundle mechanism.
- Ruling T63 — implemented for the mechanism: the CDN/edge layer this story stands up emits the app-origin CSP + Trusted Types headers; their correctness is verified by 09.1.1's E2E header test, not re-asserted here.
- Ruling T40 — consumed: `dotnet restore --locked-mode` inside the build uses the committed `packages.lock.json`; SBOM output feeds 11.6.1's scan.
- 00 §11 supported runtimes — images target Linux x64 + arm64 per the runtime row; a single-arch build that breaks the arm64 lane fails AC1.
- `[OPEN]` The exact chiseled `aspnet:10.0` tag/digest is unverified upstream (area plan marks it ⚠️); the build task must record the resolved digest in the registry metadata and in the deploy workflow's digest file.

## 4. Data model and migrations

None. Plan 10 owns no business tables (area plan §4). SBOM, signature and attestation artifacts live as registry metadata and files under `infra/`; no PostgreSQL objects are introduced.

## 5. API shapes (commands, queries, endpoints)

None. No `/v1` command, query or endpoint. Build/release commands:

| Command | Effect |
|---|---|
| `dotnet publish src/Evidgate.Api -c Release /t:PublishContainer` | produces the Api image (ReadyToRun, `InvariantGlobalization`, Server GC per 00 §5.7 P7) |
| `dotnet publish src/Evidgate.Worker -c Release /t:PublishContainer` | produces the Worker image with the pinned Node runtime layer for `packages/healing-validator` (ruling T36) |
| `dotnet publish src/Evidgate.Migrator -c Release /t:PublishContainer` | produces the separate Migrator image (AC5) |
| `dotnet-cyclonedx` / SBOM step (⚠️ licence checked like 11.6.1's tool choice) | emits CycloneDX JSON per image, attached as registry artifact |
| `cosign sign` / `cosign attest` (or provider-native signing) | signature + provenance attestation on the pushed digest (AC4) |
| `scripts/check-no-mutable-tags.sh` | AC2 lint: no `:latest` or untagged reference in `infra/` or the deploy workflow |
| `npm run build --workspace apps/web` + bundle publish | static bundle → object storage + CDN (AC6, T41/T63) |

## 6. States and transitions

None. Images are immutable, digest-addressed build artifacts; the artifact lifecycle of 00 §8.4 (`pending_upload → uploaded → ready → …`) applies to tenant evidence objects, not to release images. Promotion state is an emergent property of which digest the deploy workflow references (10.2.2), not a stored state here.

## 7. Jobs and integrations

- The deploy pipeline (10.2.2-T1) consumes the promoted digest references this story produces.
- The Worker image carries the pinned Node runtime that `packages/healing-validator` runs under (ruling T36) — its version pin is set here, exercised by 08.
- SBOM and provenance feed 11.6.1's vulnerability/licence review (this story is listed as blocking it).
- The `apps/web` bundle publish is consumed by 09.1.1's E2E tests (ruling T63 header check, bundle integrity).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S6 / ruling T40 (lock files, locked-mode restore, supply chain) | image build restores with `--locked-mode` against committed `packages.lock.json`; SBOM per image | AC1, AC3 |
| 00 §5.7 S3 (secrets never baked into images or logged) | runtime secret injection only (10.1.1-T2); image layer history scanned for secret-like strings | `scripts/check-no-secret-literals.sh` extended to image layers in T1.4 |
| Chiseled non-root runtime (ruling T41) | no shell, no package manager, non-root UID in the runtime base | `docker inspect` User field in AC1 |
| Immutable artifacts (FR-10-2, digest pinning) | deploy files reference digests; `latest` lint | AC2 |
| Provenance/attestation | signed image + build-provenance attestation in the registry | AC4 |
| 00 §5.7 P7 (ReadyToRun, Server GC, `InvariantGlobalization`) | publish properties set in the image-build profiles | image startup smoke: invariant-globalization check + R2R headers |
| Retention/deletion impact | none — build artifacts follow registry retention policy, not tenant-data retention | — |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Runtime base is the pinned chiseled non-root image | AC1: `docker inspect` base-digest and `User` checks |
| Mutable tag can never reach a deploy file | AC2: inject `:latest`, expect lint exit 1 |
| SBOM complete and consistent with lock files | AC3: SBOM↔`packages.lock.json` diff script |
| Signature and attestation verify | AC4: `cosign verify` / `verify-attestation` against a pushed digest |
| Migrator is its own image | AC5: registry listing shows a distinct `evidgate-migrator` repository/digest |
| `apps/web` is not a container | AC6: registry has no `apps-web` image; bundle exists on the object store |
| No secret in any image layer | layer-history scan fails on an injected secret literal |

No product/business-logic tests (no business tables or `/v1` surface in this story).

## 11. Rollout

- No feature flag. Merge order: T1 → T2 (signing needs an image to sign). The digest-promotion contract lands with T2 so 10.2.2-T1 can build against it in the same milestone.
- Monitoring: none directly; image pull/startup failures surface through the readiness probe (`/internal/health/ready`, implemented by 01.1.2-T1, configured per environment by 10.1.1-T1) and later through 10.3.1 telemetry.
- Rollback: keep the previously promoted digest referenced in the deploy workflow; an image itself is never mutated or re-tagged.
