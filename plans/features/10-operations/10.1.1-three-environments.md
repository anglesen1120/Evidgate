## 1. Goal and non-goals

**Goal.** Dev, staging and prod exist as three environments with separate credentials and data (FR-10-1): a per-environment `EVIDGATE_*` configuration matrix, validated at process boot by 01.1.2-T1's options mechanism (a missing or malformed value stops the boot non-zero before any port binds); secrets resolved behind one provider-agnostic interface with no value ever committed to the repo or baked into an image; environment bootstrap automation (database + owner/app/operator roles, object-storage buckets and policies, secret placeholders, network rules); and an isolated, separately-hosted artifact-viewer origin (domain, DNS, TLS, static hosting, CSP/CORS headers) that never carries the app's session cookie.

**Non-goals.** Container image build/promotion (10.2.1); the deploy pipeline and canary (10.2.2); OpenTelemetry instrumentation and alerting (10.3.1); backup/PITR (10.5.1); the cloud-provider choice itself (10.8.1, O3 — this story's bootstrap automation is provider-agnostic and is re-targeted once O3 closes); the artifact viewer's own CSP directives and iframe/postMessage behaviour, which stay owned by 06.3.3-T1 (this story only stands up the origin's infrastructure); `apps/web`'s own static-hosting pipeline, which is T41/10.2.1's concern.

## 2. User stories and acceptance criteria

- As an operator, I cannot accidentally point staging at prod's database or object-storage bucket, because the two environments have no shared credential or network path.
- As a developer, a typo in an environment variable fails the process at boot with a clear message, not a runtime 500 three requests later.
- As a security reviewer, artifact content only ever renders on a domain that never receives the app's session cookie, so a hostile artifact cannot ride an authenticated session.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A required `EVIDGATE_*` variable missing from `infra/<env>/` fails the environment-config lint before deploy; at boot, 01.1.2-T1's validated options exit non-zero naming the offending key before `GET /internal/health/live` becomes reachable |
| AC2 | `/internal/health/live` and `/internal/health/ready` (implemented by 01.1.2-T1) are unreachable on the public ingress in every environment, and reachable on the internal path with the configured per-environment probe behaviour (200/503 as dependency state dictates) |
| AC3 | `scripts/check-no-secret-literals.sh` exits 0 on a clean tree/built image and exits 1 when a dummy secret literal is added to a config file, Dockerfile or `infra/` compose file |
| AC4 | A connection attempt from staging's database credentials against the prod database host is refused (network-level, not just auth-level) |
| AC5 | A fresh bootstrap of a clean environment leaves exactly the owner, app and operator PostgreSQL roles, with the app role's `pg_roles.rolbypassrls = false` and `FORCE ROW LEVEL SECURITY` on every non-exception table |
| AC6 | `curl -v https://<viewer-domain>` completes a valid TLS handshake, and the viewer origin's response headers never include a `Set-Cookie` for the app's `__Host-` session cookie |

## 3. Contracts touched

- 00 §9.1 — the operational-endpoint constraints (outside `/v1`, tenant-free, never on the public ingress) are enforced here via per-environment ingress configuration; no contract change.
- 00 §5.4.1/§5.4.6 — this story's bootstrap creates the owner/app/operator roles the tenancy contract requires; it does not change the contract.
- No `contracts/openapi.yaml` change (these endpoints are explicitly excluded from it by 00 §9.1).
- Ownership (Tech-Lead ruling): `GET /internal/health/live`, `GET /internal/health/ready` and `GET /metrics` are **implemented by 01.1.2-T1** (ASP.NET Core health checks: Npgsql + migration-journal head; see `plans/features/01-foundation/01.1.2-two-process-skeleton.md`). This story only **consumes** them: per-environment probe configuration (liveness/readiness paths and thresholds), the ingress rule keeping `/internal/*` off the public ingress, and the per-environment smoke test.
- Recorded 2026-09-27 (T1.1 as delivered, the declared-value rules) — a matrix row may carry `forbiddenValues`, a map from environment to the values that environment must not set, and the lint of `scripts/check-env-matrix.mjs` now checks every `value` an `infra/<env>/environment.json` declares against the row's `forbiddenValues[env]` and against the row's `constraints.enum` (the enum is derived from the option's `[EnumDataType]`, so the matrix cannot name a value the code refuses). A declared `value` must also be the row's declared `type` (a string, or an integer/boolean row's own JSON value), so `null` or `12345` on a string row fails instead of drifting past the lint; the enum a row's `constraints.enum` is derived from is collected for the whole `src/**/*.cs` tree before any class is parsed, so the enum may be declared after the options class that names it. `EVIDGATE__ISOLATION__SELFCHECK` is the first user: `forbiddenValues: {staging: ["Disabled"], prod: ["Disabled"]}`, which turns "a deployable environment never sets Disabled" (02.6.1-T1.4's switch) from prose into a failing lint. The host still accepts `Disabled` in any environment on purpose — the contract-surface and shutdown suites boot a Production host without a database — so the rule belongs to the environment description, not to a boot refusal. Proven by the lint's `--self-test` cases `forbidden-value-in-prod`, `value-outside-the-enum` and `forbidden-value-outside-the-enum`, and by a temporary `prod` declaration of `Disabled` failing the lint on this tree (docs/runbooks/environments.md §5.1).

## 4. Data model and migrations

None. Plan 10 owns no business tables (area plan §4). Environment inventory, secret-provider wiring, bootstrap scripts and the viewer origin's DNS/TLS records are configuration/infrastructure objects under `infra/` and `docs/`, not PostgreSQL rows. The bootstrap task (T3) provisions the owner/app/operator roles used by 01.4.1-T2's RLS setup but adds no table of its own; `schema_migration`/`task` are platform-exception tables owned by 01 (ruling T3).

## 5. API shapes (commands, queries, endpoints)

No `/v1` command or query. Operational surface (00 §9.1):

| Endpoint / mechanism | Behaviour |
|---|---|
| `GET /internal/health/live` | Implemented by 01.1.2-T1 (always 200 when the host is up); this story configures the probe path per environment (`infra/<env>/`) |
| `GET /internal/health/ready` | Implemented by 01.1.2-T1 (Npgsql + journal-head checks, 503 while failing); this story configures the probe path/thresholds per environment and, via T3, the object-store it probes |
| Boot validation | Mechanism owned by 01.1.2-T1 (`IOptions<T>` + `IValidateOptions<T>`, `.ValidateOnStart()`); this story owns the per-environment `EVIDGATE_*` matrix the validation binds to |
| Ingress rule | `/internal/*` and `/metrics` never reachable on the public ingress (00 §9.1); configured per environment |
| `ISecretProvider.GetSecretAsync(name)` | Internal interface only, no HTTP surface; env-injection implementation for V1, a managed-secret-store implementation is a documented future swap point (O3) |

## 6. States and transitions

None. This story introduces no domain state machine; a boot either succeeds or the process exits non-zero, and `/internal/health/ready` is a stateless 200/503 probe (00 §9.1 defines no state machine for operational endpoints).

## 7. Jobs and integrations

- T3's owner/app/operator roles are consumed by 01.4.1-T2 (RLS setup) and by every module's migrations.
- T2's `ISecretProvider` is consumed by every module that needs a connection string, the ingest-token pepper (T5) or an OIDC client secret; T3 provisions the placeholder entries it resolves at first boot.
- T4's viewer origin is consumed by 06.3.3-T1 (viewer application, CSP/iframe behaviour, its own header test) — this story owns only the origin's domain/DNS/TLS/hosting/edge headers, per the area plan's explicit note distinguishing the two tasks.
- `/internal/health/ready` is the post-deploy verification signal consumed by 10.2.2-T1.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §11 tenant isolation | staging and prod share no credential and no network path (T3.4) | AC4 |
| 00 §5.7 S3 (secrets never in logs/metric labels, only from environment/secret store) | `ISecretProvider` abstraction; no literal in repo, config files or built images (T2) | AC3 |
| 00 §5.4.1/§5.4.3 (owner role separate from app role; app role has no `BYPASSRLS`, `FORCE ROW LEVEL SECURITY`) | bootstrap creates exactly the three roles with the correct privilege split (T3.1) | AC5 |
| Ruling T63 (viewer-origin CDN/edge emits its own headers, separate from the app origin) | dedicated domain/TLS/hosting with edge-configured CSP/CORS and no app cookie scope (T4) | AC6, cross-checked by 06.3.3-T1's header test |
| Least-privilege deploy identity (area plan §6) | bootstrap scripts run under the CI deploy identity only; no human runs them against prod directly | IAM-policy test in T3 |
| A switch that must never be off where tenant traffic is served (02.6.1-T1.4's `EVIDGATE__ISOLATION__SELFCHECK`) | the matrix row forbids `Disabled` in staging and prod (`forbiddenValues`), and the lint fails an `environment.json` that declares it — the host itself stays permissive, because the contract-surface and shutdown suites run Production without a database | lint `--self-test` cases `forbidden-value-in-prod`, `value-outside-the-enum`, `forbidden-value-outside-the-enum` |
| Retention/deletion impact | none — no business or personal data is created by this story | — |

- **Authorization:** no caller-facing surface; `/internal/*` and `/metrics` stay off the public ingress (00 §9.1, AC2, enforced by the `check-env-matrix.mjs` ingress rule), and the bootstrap scripts run under the CI deploy identity only.
- **Telemetry:** none added here; instrumentation and alerting belong to 10.3.1. The config lint names the offending key (and, for an enum knob, the declared and allowed values); secret-sourced keys carry no value in the matrix or `environment.json`, so none can be printed.
- **Failure path:** a missing, malformed, out-of-enum or environment-forbidden `EVIDGATE_*` value fails the config lint before deploy; at boot 01.1.2-T1's validated options exit non-zero naming the key before `/internal/health/live` is reachable (AC1).

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Missing/malformed `EVIDGATE_*` value | AC1: delete a required var from `infra/<env>/` → config lint fails pre-deploy; boot exits non-zero naming the key (01.1.2 mechanism) |
| A declared value the option cannot take, or one the environment forbids | config lint: an `environment.json` value outside the row's `constraints.enum`, a value whose JSON type is not the row's declared `type` (`null` or `12345` on a string row), or a value on the row's `forbiddenValues[env]` (`EVIDGATE__ISOLATION__SELFCHECK=Disabled` in staging/prod) fails; the lint's `--self-test` pins each through the real CLI |

| Staging cannot reach prod | AC4: network-policy test, staging credentials against the prod host |
| Bootstrap produces exactly the expected roles | AC5: `pg_roles` inspection after a clean bootstrap run |
| Viewer origin never carries the app cookie | AC6: TLS handshake + header inspection against the viewer domain |

No product/business-logic tests (this story has no business tables or `/v1` surface).

## 11. Rollout

- No feature flag (no runtime product behaviour). Merge order: T1 → T2 → T3 in one series; T4 (viewer-origin infra) has no dependency on T1–T3 and may land in parallel, but 06.3.3-T1 cannot proceed until T4 is live.
- Monitoring: `/internal/health/live` and `/internal/health/ready` (implemented by 01.1.2-T1, configured per environment here) become dashboard signals once 10.3.1's collector exists; until then the deploy pipeline (10.2.2-T1) is the first consumer.
- Rollback: revert the bootstrap scripts/config; no data or deployed application state is affected (infrastructure-only story).
