## 1. Goal and non-goals

**Goal.** Every operational runbook needed to keep the pilot alive — dead-letter triage, stuck run, orphan artifact, key rotation, kill switch, incident process — exists in `docs/runbooks/` and has been executed at least once in staging by a person who did not write it, so the pilot does not depend on one operator (the bus-factor risk in the area plan §8).

**Non-goals.** Building the operator tooling each runbook calls (dead-letter replay CLI is 01.5.1-T4, the healing switch is 08, token rotation is 02); the on-call schedule itself (owner decision O2); DR failover design (10.5.1-T4 covers the DR runbook — this story's incident process references it, it does not rewrite it).

## 2. User stories and acceptance criteria

- As a second operator, I can take the pilot on-call and resolve a dead-letter row, a stuck run or a false-positive healing incident by following the runbook alone, without asking the person who built the feature.
- As the Tech Lead, every alert in 10.3.1-T5 links to a runbook that has been exercised once, so alerts are actionable rather than tribal knowledge.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Each of the six runbooks (dead-letter, stuck run, orphan artifact, key rotation, kill switch, incident process) has been executed once in staging by a person who did not write it, and the executor's corrections are committed to the runbook |
| AC2 | Dead-letter drill: a deliberately dead-lettered `task` row is triaged via the runbook's query, classified, and replayed exactly once through 01.5.1-T4's operator path — the handler's natural idempotency key prevents a double side effect |
| AC3 | Stuck-run drill: a run whose worker is killed mid-run past the collection deadline is detected via the runbook's query, its lease/epoch state inspected (00 §5.3), and settled to `incomplete` or `canceled` — the runbook never produces evidence or fabricates a result |
| AC4 | Orphan-artifact drill: an object stuck in `pending_upload` past TTL and an object without `ready` are swept via the retention/orphan reconciler path; an object without `ready` is never treated as evidence (00 §8.4) |
| AC5 | Key-rotation drill: ingest token, JWT signing key, webhook secret, database credential and the ingest/API token HMAC pepper (T5) are each rotated in staging with no downtime and no lost acknowledged event; a new `pepper_vN` signs new tokens while old versions verify until their last token expires |
| AC6 | Kill-switch drill: healing availability is flipped `enabled → shadow → disabled` at system, tenant and project level while ingest, runs and gates continue (T33, DECISIONS §5.9); `unavailable` is never settable by hand |
| AC7 | Every alert rule in 10.3.1-T5 links to one of these runbooks; an alert without a link fails the dashboard review (NFR-10-2); the incident-process runbook includes a severity ladder, the on-call expectation and a postmortem template with a follow-up-task rule |

## 4. Data model and migrations

None. The runbooks operate on tables owned elsewhere: `task`/`outbox` (01), `run`/`job`/`job_lease` (05), `artifact` (06), `healing_switch` (08), token/pepper tables (02). No migration.

## 5. API shapes (commands, queries, endpoints)

No new endpoint. The runbooks call existing surfaces:

| Runbook | Operator action invoked (owner) |
|---|---|
| Dead-letter | `POST /internal/operator/…` dead-letter replay via 01.5.1-T4 operator CLI |
| Stuck run | reconcile/cancel tasks enqueued via `POST /internal/operator/…`; queries read `run`/`job`/`job_lease` state |
| Orphan artifact | retention-sweep/orphan-reconcile trigger + `pending_upload` TTL check (06) |
| Key rotation | rotation admin calls/CLI per secret kind (02, 10.1.1-T2 secret-store interface) |
| Kill switch | `PUT /v1/healing/switch` (T33, `healing:configure`) at system/tenant/project scope |
| Incident | process only — severity ladder, postmortem template, no endpoint |

## 6. States and transitions

None introduced. Runbooks describe operating on the canonical states: `task` lifecycle `queued → active → retry → dead_letter → replayed` (00 §5.3), run terminal states `complete | incomplete | canceled` (00 §8.1), artifact `pending_upload → uploaded → ready → pending_delete → deleted` (00 §8.4), healing availability `enabled | shadow | disabled` settable / `unavailable` derived (00 §8.7, T33), ingest token `active → rotated → revoked | expired` (00 §8.9).

## 7. Jobs and integrations

- Deliverable: `docs/runbooks/<name>.md` files, linked from the 10.3.1-T5 alert rules and dashboards.
- Each runbook's first drill is executed by a non-author (area-plan story acceptance); drill evidence is recorded next to the runbook.
- Consumed downstream by 02.5.1 (rotation support), 08.6.3 (kill-switch story's apply path) and 11.3.1 (security-incident process), which list this story as a blocker — the runbook ids above are the hand-off surface.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S3 (secrets never in logs) | The key-rotation runbook contains no secret value; every step goes through the environment secret store / audited rotation path | AC5 + runbook review |
| T5 (pepper rotation, no scrypt) | Rotation runbook covers `pepper_vN` introduction: new tokens signed with the new version, old versions verify until their last token expires | AC5 |
| DECISIONS §5.9 (kill switch before apply) + T33 | The kill-switch runbook/drill proves the switch reaches system/tenant/project scope before any apply capability is live; `unavailable` is never settable | AC6 |
| 00 §9.1 (operator routes) + tenant-visible support access (00 §8.9) | Every runbook action is meant to go through `/internal/operator/*` with an audited support grant (target; today the gate denies every caller, see the Authorization line below); the runbook explicitly forbids ad-hoc `psql` writes outside the operator path | AC1–AC5 drill review |
| Performance rules P1–P8 | None apply: this is an operations-process story with no hot-path endpoint; the runbooks must never tell an operator to run a network call inside a live DB transaction (P5 is a build rule, not an ops action) | — |
| Privacy/retention | Runbooks contain no customer data; drill artifacts are synthetic-tenant ids only | AC1 |

- **Authorization:** runbook actions are meant to run through `/internal/operator/*` with an audited support grant (target); today the operator gate denies every caller and list/replay write no audit row (dead-letter.md §5.4); read-only SQL runs under the roles each runbook names, never BYPASSRLS on the app role.
- **Retention/deletion:** runbooks are versioned files holding no customer data; drill records use synthetic tenants only.
- **Telemetry:** each runbook links from its alert (10.3.1-T5) and records the drill date; no new metric is introduced.
- **Failure path:** where an operator path does not exist (carried S152 CR-10 gaps), the runbook states it and escalates; it never prescribes a hand-written write.
