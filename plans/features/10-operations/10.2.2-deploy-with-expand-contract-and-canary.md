## 1. Goal and non-goals

**Goal.** A deploy never takes traffic on a version whose migrations have not run (FR-10-3), and no rollout — code or policy — can change a decision silently (FR-10-4). The pipeline runs the `Evidgate.Migrator` job as the owner role, gates on the DbUp checksum journal head, refuses a non-expand-only migration set while the old version is live, rolls out the promoted digest behind a readiness check, canaries with automatic rollback on SLI breach, and runs a shadow decision compare that replays a fixed evidence set under the incoming policy revision and blocks promotion on an unexplained diff. A release runbook makes the sequence executable by a second person.

**Non-goals.** Building/signing the images (10.2.1); the telemetry catalogue, alert thresholds and routing the canary consumes (10.3.1); SLI definitions (10.4.1); backup/restore (10.5.1); the evaluator and policy-revision semantics themselves (07); environment provisioning (10.1.1).

## 2. User stories and acceptance criteria

- As a deployer, I cannot push a version whose schema isn't ready, because the expand gate fails before traffic moves.
- As a release approver, a policy revision that would change any stored decision is blocked until I approve the diff per project, with the diff attached.
- As an operator, a bad canary rolls itself back on an SLI breach without me paged, and the rollback never touches the schema.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A deploy whose pending migration set contains a non-expand (destructive/contract) migration while the old version is live is refused before any replica change; the refusal message names the offending `migrations/NNNN_*.sql` file |
| AC2 | After the Migrator job runs, the expand gate compares the DbUp checksum journal head to the release's expected head; a mismatch stops the deploy and the old version keeps serving |
| AC3 | The canary step puts one new-version replica behind the load balancer; a synthetic SLI breach (error rate, latency or readiness) triggers automatic rollback to the previous digest within one alert-evaluation window, and the rollback performs no schema change |
| AC4 | Replaying the fixed evidence set under an incoming policy revision produces `mode = 'shadow'` evaluations; an empty diff promotes, a non-empty diff blocks until a per-project approval is recorded with the diff attached |
| AC5 | A rollback executed after an expand migration succeeded leaves the expanded schema in place and the old code version serving (schema rollback is never attempted) |
| AC6 | The release runbook is executed end-to-end in staging once by someone who did not write it, with each checklist step matching an actual pipeline step |

## 3. Contracts touched

- 00 §8.5 — consumed, not changed: shadow compare writes only `mode = 'shadow'` evaluation rows; the partial unique (one `live` row per `(org_id, run_id, evidence_revision)`, T22) guarantees a replay cannot collide with live rows. ## 4. Data model and migrations

None owned. Plan 10 owns no business tables (area plan §4). This story *reads* the `schema_migration` DbUp journal (platform table owned by 01) to gate deploys, and *reads/writes* `evaluation` rows only through 07's evaluator in `shadow` mode — no new column, table or migration is introduced here. The per-project approval record for a non-empty diff is stored in the deploy workflow's release record (an `infra/` artifact/audit entry), not a new business table.

## 5. API shapes (commands, queries, endpoints)

No `/v1` commands or queries. Pipeline operations (CI/deploy workflow):

| Step | Mechanism | Refusal semantics |
|---|---|---|
| `migrate` | run `Evidgate.Migrator` image as owner role; DbUp applies pending `migrations/NNNN_*.sql` | job non-zero → deploy aborts, old version untouched |
| `expand-gate` | classify pending migrations expand-only vs contract/destructive (filename + content lint); verify journal head = expected head | non-expand while old version live → refuse (AC1); journal mismatch → refuse (AC2) |
| `rollout` | start new-version replicas at the promoted digest; require `/internal/health/ready` = 200 on each before traffic | readiness timeout → abort, no traffic shift |
| `canary` | shift traffic to 1 new replica (parameterisable %, default per RECOMMENDATIONS) for the watch window | SLI breach signal from 10.3.1-T5 → auto-rollback (AC3) |
| `shadow-compare` | replay fixed evidence set under incoming `policy_revision` via 07 evaluator (`mode = 'shadow'`) | unexplained diff → block promotion (AC4) |
| `promote` / `rollback` | repoint load balancer to new / previous digest | rollback never invokes a migration step (AC5) |

Diff approval is an operator-recorded pipeline input (`--approve-diff <report-id> --project <p>`), audited in the release record — not a public endpoint.

## 6. States and transitions

None introduced. Consumed states, unchanged: `task`/`outbox` lifecycle (00 §5.3) keeps draining across a deploy; `evaluation.mode` `live` vs `shadow` (00 §8.5, T22) is the compare's isolation mechanism. The release-record lifecycle (`pending → gated → canary → promoted`, or `rolled_back`) is a deploy-workflow artifact under `infra/`, not a domain state machine.

## 7. Jobs and integrations

- `Evidgate.Migrator` image (10.2.1-T1.2) is the job unit of the migrate step; journal head read comes from 01.4.1's schema/journal setup.
- The canary's SLI inputs are the alert rules/metrics of 10.3.1-T5 (task dependency `10.3.1-T5`); the rollback trigger is that alert firing, consumed via the same channel, per area plan §4.
- Shadow compare calls 07's evaluation pipeline in shadow mode; the fixed evidence set fixture is co-owned with 05/06 (area plan §7 fixtures).
- The runbook's rollback drill reuses 10.1.1's environments; deploy verification uses the readiness probe (`/internal/health/ready`, implemented by 01.1.2-T1, per-env config from 10.1.1-T1).

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Destructive migration in the pending set while old version is live | staging drill: add a `DROP`-class migration, deploy refused naming the file (AC1) |
| Journal head mismatch | corrupt/rollback the journal fixture, gate refuses (AC2) |
| Deploy fails after expand migration ran | kill the rollout after migrate; old version keeps serving, expanded schema intact (area plan §5) |
| SLI breach during canary | inject error-rate breach synthetically; automatic rollback within one evaluation window, no schema action (AC3) |
| Shadow compare blocks a decision-changing revision | fixture policy revision with a deliberately different rule → non-empty diff blocks promotion (AC4; area-plan §7 shadow-compare test) |
| Shadow compare passes an equivalent revision | empty diff → promote |
| Per-project approval path | non-empty diff + recorded approval for project A only → promotion proceeds for A, still blocked for B |
| Rollback never rewrites schema | static lint: rollback path contains no migration invocation; drill confirms journal head unchanged (AC5) |
| Runbook correctness | second-person staging execution (AC6, shared acceptance method with 10.7.1) |

## 11. Rollout

- No feature flag for the pipeline itself; the canary percentage and watch window are deployment parameters (defaults 1 replica / 30 min per RECOMMENDATIONS 10-canary).
- Monitoring: the pipeline emits its own step telemetry into 10.3.1 (deploy events as logs/metrics); the canary's health is the alert set of 10.3.1-T5.
- Rollback: repoint to the previous promoted digest (never a schema rollback, AC5); contract migrations ship at least one release later per FR-10-3, so an expanded schema is always safe for the previous version.
- Merge order: T1 (M1) → T2/T3 (M2, T2 needs 10.3.1-T5) → T4 after the first real drill.
