## 1. Goal and non-goals

**Goal.** The 00 §11 targets become measurable facts (FR-10-7): recording rules produce ingest p95 (< 1 s per batch within limits), decision p95 (< 60 s from complete evidence) and availability (99.5 %/month on core endpoints) per environment and per tenant class; web-vitals SLIs (LCP, INP) are recorded from 09's browser telemetry against the W7 budgets; a monthly report makes the numbers reviewable; and an error budget with burn-rate alerts enforces the rule that a breach pauses feature rollout — it never lowers the target.

**Non-goals.** Raw metric emission and dashboards (10.3.1 — this story adds recording rules over that catalogue); the load test that exercises the targets (10.6.1); RPO/RTO measurement (10.5.1); the decision to act on a budget breach (the rule, not the call); the availability SLI's expansion to non-core endpoints.

## 2. User stories and acceptance criteria

- As the Tech Lead, I can query "did we meet ingest p95 last month in prod" with one recorded metric, not a hand-rolled query.
- As a release owner, a burn-rate breach blocks the next promotion automatically instead of becoming a meeting topic.
- As the QA lead, the availability number can never be gamed by the test pass rate — it measures core endpoints only.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Recording rules emit `sli:ingest_p95_seconds`, `sli:decision_p95_seconds` and `sli:availability_ratio` per environment and per tenant class, queryable in the telemetry backend |
| AC2 | The availability rule's numerator/denominator cover only the core-endpoint set named in the rule file; a request to a non-core path is excluded (unit test on the rule's endpoint filter) |
| AC3 | Web-vitals recording rules emit `sli:lcp_seconds_p75` and `sli:inp_ms_p75` from 09.1.1-T9's vitals events, compared against W7 budgets (LCP ≤ 2.5 s p75); while the vitals source is absent the SLI reads unavailable-with-reason (T60) |
| AC4 | A monthly report artifact (generated per environment) lists each SLI value vs target for the period and is checked into `docs/reports/` or attached to the release record |
| AC5 | A synthetically injected error/latency streak triggers the burn-rate alert in staging within its evaluation window, and the recorded breach sets the rollout-pause flag consumed by the deploy pipeline's promote step (10.2.2) |
| AC6 | The rollout-pause rule's definition file states the resume condition (budget recovered or explicit owner override recorded) — verified by lint on the rule file |

## 4. Data model and migrations

None. Plan 10 owns no business tables (area plan §4). Recording rules, the monthly-report job definition and error-budget state live as `infra/` configuration plus telemetry-backend data; no PostgreSQL objects are introduced. The rollout-pause flag is a deploy-workflow input (a recorded release-gate state in `infra/deploy/`), not a domain table.

## 5. API shapes (commands, queries, endpoints)

None. No `/v1` surface; this story adds no endpoint. Outputs are recording-rule definitions and one scheduled report job:

| Artifact | Mechanism |
|---|---|
| `infra/rules/sli-*.yaml` | recording rules evaluated by the telemetry backend per environment |
| Monthly SLI report | scheduled job (Cronos-fired `task` per 00 §5.3 `unique (schedule_name, fire_at)` — one fire per period) rendering SLI values vs targets to a report artifact |
| Burn-rate rules | `infra/alerts/<env>/burn-rate-*.yaml` feeding the 10.3.1-T5 routing; breach writes the rollout-pause flag for 10.2.2's promote gate |
| Rollout-pause flag | `infra/deploy/` gate file read by the pipeline's promote step; explicit override requires a recorded owner entry |

## 6. States and transitions

None introduced. The error budget is a derived value (SLI vs target over a rolling window); the rollout-pause flag has two operational positions (clear, paused) recorded in the release-gate state — an ops artifact, not a domain state machine.

## 7. Jobs and integrations

- Consumes the 10.3.1-T3 metrics catalogue (histograms and counters) — task dependency `10.3.1-T3`.
- The rollout-pause flag is consumed by 10.2.2's promote step; 10.2.2 does not reimplement the rule.
- Burn-rate alerts reuse 10.3.1-T5's routing and the runbook-link requirement (runbook entry points at the incident process, filled by 10.7.1-T6).
- Web-vitals events arrive from 09.1.1-T9 (T39); the SLI stays unavailable-with-reason until they exist (T60).
