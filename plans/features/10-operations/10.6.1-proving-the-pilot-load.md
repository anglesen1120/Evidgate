## 1. Goal and non-goals

**Goal.** Prove on staging, with a synthetic tenant, that the pilot's ingest and artifact-upload load pass within the 00 §9.3/§11 limits, and produce a capacity model that names the next bottleneck so 12 can plan pricing/quota and 10 can plan the next capacity step.

**Non-goals.** Production load testing (never the target, per the area-plan "Load tests run against staging only" decision); choosing the cloud provider (10.8.1); building the ingest or artifact endpoints themselves (04, 06 own them — this story only exercises them under load); LLM/healing-replay cost modelling (10.9.1-T2).

## 2. User stories and acceptance criteria

- As the Tech Lead, I need proof that 50 000 events in 60 s and the pilot's artifact profile pass on staging before the M2 exit gate, so the pilot is not the first place we discover a bottleneck.
- As an operator, I need a capacity model that tells me which resource runs out first, so I know what to scale before it becomes an incident.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A load generator sends 50 000 valid events in 60 s to staging as batches within 00 §9.3 limits (≤ 500 events, ≤ 1 MiB before decompression) at a sustained ≈ 833 events/s; the run completes with no unexpected 5xx and every batch is `accepted` or `duplicate` |
| AC2 | The generator's measurement run captures, per batch, the single `INSERT … SELECT … FROM unnest(@arrays) ON CONFLICT (org_id, run_id, event_id) DO NOTHING RETURNING` statement (T50) and the per-org `pg_advisory_xact_lock(hashtext('audit:' ‖ org_id))` wait (T8); ingest p95 per batch < 1 s (00 §11) |
| AC3 | An artifact upload harness sustains the pilot profile (2 GB/day, ≥ 20 MB objects) via presigned-URL concurrency; one smoke test against the real provider's S3-compatible endpoint confirms the presigned PUT signs `Content-Length` and the checksum header (T18), closing the emulator-parity gap left open by 01.8.1-T1 |
| AC4 | `docs/capacity-model.md` is updated with the recomputed source §9 numbers (100 000 results/day ≈ 98 MiB/day ≈ 8.6 GiB/90 d; 2 GB/day artifacts, 28 GB/14 d; 833 events/s burst), Npgsql pool sizes/connection counts, container memory limits, .NET GC settings (`DOTNET_GCServer`, heap hard-limit), thread-pool headroom and growth triggers, and names the next bottleneck |
| AC5 (V2) | A soak/back-pressure run sustains multi-hour ingest; 429/503 responses carry `Retry-After` once quota is exceeded (00 §9.2); queue growth stays bounded and the system recovers after the overload window ends |

## 3. Contracts touched

- 00 §9.3 batch limits and 00 §9.4 event envelope — exercised, not changed.
- T8, T18, T50 — measured as implemented by 04/06; this story adds no new rule.
- 00 §11 burst/ingest-latency targets — this story is the proof.

## 4. Data model and migrations

None. This story exercises the existing 04 `event`/`producer_slot` tables and 06 artifact tables under load; it owns no business table. The synthetic tenant/org load-test fixture is seed data (owned jointly with 05 and 06 per area-plan §7), not a migration. Capacity numbers are recorded in `docs/capacity-model.md`, not the database (consistent with T60: a number with no measured source is never written as a fact).

## 5. API shapes (commands, queries, endpoints)

No new command, query or endpoint. Existing endpoints exercised at load:

| Endpoint exercised | Harness | What is measured |
|---|---|---|
| `POST /v1/runs/{r}/events` | `scripts/load/ingest-burst` (T1) | Throughput, error rate, batch-insert (T50) and audit-lock (T8) timings |
| `POST /v1/artifacts/upload-url`, `POST /v1/artifacts/{a}/complete` | `scripts/load/artifact-profile` (T2) | Presigned-URL concurrency, provider parity (T18) |
| `docs/capacity-model.md` update | `scripts/capacity/recompute` (T3) | Pool/GC/thread-pool sizing vs measured load |

## 6. States and transitions

None. No new state is introduced; runs and events reach the same 00 §8.1/§8.4 terminal states as any other batch.

## 7. Jobs and integrations

- Ingest load generator (T1) is a standalone script, not a deployed job; it targets staging only.
- Artifact load harness (T2) runs a real-provider smoke test once the O3 candidate is reachable (10.8.1); until then it runs against the staging provider.
- Capacity model (T3) consumes 10.3.1-T3's metrics catalogue (Npgsql pool occupancy, GC/thread-pool counters) recorded during the T1/T2 runs.
- Soak test (T4, V2) is scheduled after the pilot to validate sustained back-pressure behaviour ahead of 12.4.1 (pricing/quota planning, which this story blocks until the capacity model lands).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 P1 (hot-endpoint budget + load-test row) | `events` and `upload-url` get their load-test row here | AC1, AC3 |
| 00 §5.7 P2 (batch writes, one round trip) | T50's single `unnest`/`ON CONFLICT` statement is measured directly, not inferred | AC2 |
| 00 §5.7 P5 (no network call inside a DB transaction) | The audit-lock measurement (T8) confirms the advisory lock is the last statement before commit, with no S3/GitHub/LLM call inside the transaction | AC2 |
| Tenant isolation | Load runs use a synthetic tenant only; the "load tests run against staging only" decision keeps production evidence trustworthy | AC1 harness config review |
| S3 (secrets never in logs/metrics) | Load-generator credentials come from the environment secret store; the collector redaction rule (10.3.1-T2) is verified under load, not bypassed | AC1 run log review |
| T60 (no fabricated metrics) | Capacity numbers are the measured T1–T3 results, not assumptions; a number with no run behind it is not written to the model | AC4 |

**DoR review answers** (00 §12, `plans/features/README.md` §6):

- **Authorization:** load runs use a synthetic tenant and a staging-only CI token minted for the run; the story adds no endpoint and widens no permission.
- **Retention/deletion:** none; load-run evidence is synthetic and deleted with the staging tenant after the run.
- **Telemetry:** the measured SLI/latency series of 10.3.1; the story adds no new telemetry surface.
- **Failure path:** a run that misses a budget is recorded as a failed measurement with its numbers, never rounded; a harness or staging failure leaves the capacity model unchanged.

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Sustained 833 events/s for 60 s | AC1: `scripts/load/ingest-burst --events 50000 --window 60s` against staging |
| Batch at the exact limit (500 events / 1 MiB) | Boundary case in the generator's batch shaper; batch 501 or > 1 MiB is rejected client-side before send, confirming the limit is honoured |
| Batch insert + audit lock timing | AC2: generator emits a per-batch timing histogram; p95 asserted < 1 s |
| Quota exceeded mid-burst | Generator deliberately exceeds the tenant quota once; expects 429 with `Retry-After`, never a silent drop |
| Artifact upload at pilot profile | AC3: `scripts/load/artifact-profile --rate 2GB/day --min-size 20MB` |
| Presign parity on the real provider | AC3: one-off smoke test comparing SeaweedFS (staging) and the O3 candidate provider's signed headers |
| Soak / back-pressure (V2) | AC5: multi-hour sustained run; 429/503 + `Retry-After` observed; queue depth bounded; recovery timed after the window ends |
