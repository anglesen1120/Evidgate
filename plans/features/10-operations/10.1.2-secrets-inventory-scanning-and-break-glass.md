## 1. Goal and non-goals

**Goal.** Close review S8 without a cloud provider: (1) one machine-readable secret inventory (`infra/secrets-inventory.json`) naming for every secret its owner, store, rotation cadence and break-glass holder, with a CI check that every `secret: true` key in `infra/config-matrix.json` is listed (and no listed secret is unknown to the matrix); (2) repository secret scanning and push protection switched on, with the setting and the bypass roles recorded; (3) a break-glass procedure (sealed offline copy, who may open it, forced rotation after every use, an audit record) that works with a single human operator; (4) a CI vulnerability scan of the three built images with a severity gate and a reviewed exception list.

**Non-goals.** The secret provider interface and resolution (10.1.1-T2); rotation steps per secret (10.7.1-T4 — this story links to them and owns only the cadence column); a managed secret store or HSM (`[OPEN]` O3); vulnerability triage SLA and base-image refresh cadence (11.6.1-T4); SBOM and signing (10.2.1); secret-in-log redaction (10.3.1-T2); customer-side secret handling.

## 2. User stories and acceptance criteria

- As the owner (the only operator), I can list every secret, who holds it, where it lives and when it is next due for rotation.
- As the owner, a secret pasted into a commit is blocked before it reaches the remote.
- As the owner, if I lose access to the normal secret path I can recover with a documented offline procedure, and the use leaves a trace and forces rotation.
- As a reviewer, a vulnerable base image or dependency fails the build unless a dated exception exists.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `infra/secrets-inventory.json` validates against `infra/secrets-inventory.schema.json`; every entry has `name`, `owner`, `store` (`env-injection` \| `secret-store` \| `sealed-offline`), `rotationDays` (integer > 0), `lastRotated` (date or `null` with reason), `breakGlassHolder`, `runbook` (link into 10.7.1-T4 sections), and no field holds a value |
| AC2 | The check fails when a key with `secret: true` in `infra/config-matrix.json` has no inventory entry, and fails when an inventory entry names a key absent from the matrix (except entries flagged `external: true`, e.g. the repo-level CI secrets); a rotation overdue by the entry's own cadence is reported as a warning in dev and an error for `staging`/`prod` rows |
| AC3 | `inventory.owner` and `breakGlassHolder` are named people or the literal role `owner`; an empty or placeholder value fails the check; with one operator the same person may hold both and the file states it explicitly (`soleOperator: true`) |
| AC4 | Secret scanning and push protection are enabled on the repository; `docs/runbooks/secrets.md` records the setting names, the date, who can bypass (roles), and the bypass review step; a committed canary pattern is rejected by a documented drill |
| AC5 | A repository-local secret scan (pre-commit and CI) runs over the working tree with an allowlist file; a synthetic fake token committed to a scratch branch fails it, and the real allowlist contains only fixture values listed with a reason |
| AC6 | `docs/runbooks/break-glass.md` defines: what the sealed offline copy contains (inventory of recovery material, never the live secrets of staging/prod beyond what recovery needs), how it is encrypted and stored, who may open it, the steps, and the forced rotation of every secret read; a drill reaches a recorded "rotated" state for a dev secret |
| AC7 | Every break-glass use writes an audit record (who, when, why, which secret names, rotation done) in the break-glass ledger; the ledger entry has no secret value; closing the use is refused until each named secret shows a `lastRotated` after the opening time |
| AC8 | CI scans the Api, Worker and Migrator images; a finding at or above the gate severity (default `HIGH`, fixed in T4.1) fails the job unless it is on `infra/vuln-exceptions.json` with `id`, `package`, `reason`, `expires` (≤ 90 days) and an approver; an expired exception fails the job |
| AC9 | The scanner's licence and the database terms are recorded and pass `licence-scan.sh` policy (DECISIONS §4); the scan runs offline-capable or states its network egress and uses a pinned version/digest |
| AC10 | No secret value (matrix values, scan findings with matched strings) appears in CI logs or the uploaded scan report |

No HTTP endpoints. Command-line surface:

| Kind | Name | Where | Result |
|---|---|---|---|
| Check | `scripts/check-secrets-inventory.mjs` | `verify.sh --stage secrets-inventory`, CI | exit 1 with the offending key names (names only) |

## 6. States and transitions

Break-glass use: `closed → open → rotated → closed`. `open` is entered by `break-glass.sh open` (ledger line with `closedAt: null`); `rotated` when every named secret has `lastRotated` after `openedAt`; `closed` only from `rotated`. No path from `open` to `closed` without rotation; an abandoned `open` older than 24 h is surfaced by the inventory check as an error. Exception entries: `active → expired` by date; expired fails the build.

## 7. Jobs and integrations

- GitHub secret scanning and push protection: ⚠️ availability of both features depends on the repository's visibility and plan (free for public repositories, a paid add-on for private ones at the time of writing); verify and cite in T2.1. If push protection is unavailable on the plan, the local scanner (AC5) is the compensating control and this is recorded, not hidden. Bypass is limited to repository admins ⚠️ setting name "delegated bypass" to be verified.
- Repository-local scanner: ⚠️ candidate `gitleaks` (MIT) run pinned in pre-commit and CI; licence verified in T2.1 against `licence-policy.json`. Not a runtime dependency.
- Image scanner: ⚠️ candidates `Trivy` (Apache-2.0) and `Grype` (Apache-2.0); choose in T4.1 by licence, offline database support, .NET chiseled-image coverage and SBOM input (10.2.1 emits CycloneDX per image, so scanning the SBOM is preferred where supported). The scanner database download is the only new egress and is allowed-listed for CI only.
- Sealed offline copy: ⚠️ tool for encryption (`age`, BSD-3 / `gpg` GPL as a process, not linked) to be chosen in T3.1; storage is a physical or cloud-independent medium held by the owner and a named second location. A managed secret store replacing it is `[OPEN]` O3 (10.8.1).
- Works on the compose stack: the inventory covers dev `.env.dev` secrets (`source: env-file`) so the check runs locally; staging/prod rows reference `secret-store`.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Secrets never in repo, images or logs (00 §5.7 S3) | inventory holds names only; scanner output redacted; push protection and local scan | AC1, AC4, AC5, AC10 |
| Every secret has an owner and cadence | schema + matrix cross-check | AC2, AC3 |
| Recovery without weakening security | offline copy, forced rotation, audit record | AC6, AC7 |
| Supply chain | image scan gate + expiring exceptions | AC8, AC9 |
| Sole-operator risk | explicit `soleOperator` flag and second storage location, reviewed at 10.8.1 | AC3, AC6 |
| Performance | both checks add ≤ 2 min to CI (scan DB cached) | CI timing noted in T4.2 |

DoR review answers. **Authorization:** no tenant permission; repository admin and the owner role only; bypass rights recorded in AC4; ledger and exceptions files under CODEOWNERS. **Retention/deletion impact:** no customer data; ledger is retained for the life of the repository (audit), contains names and dates only. **Telemetry:** CI job results; `[INFERENCE]` an inventory-overdue count is exposed as a metric only once 10.3.1 lands (alert owner and runbook link required by 10.3.1-T5). **Failure path:** see below.

Failure paths: a secret reaches the remote despite protection → treated as compromised, `break-glass.sh` rotation path without opening the sealed copy, rotation per 10.7.1-T4, and a ledger line of kind `leak`; the scanner database cannot be fetched → job fails closed (no silent pass) with a documented one-time cached-DB override recorded in the exceptions file; a critical CVE with no fix → exception with expiry and a compensating-control note; the owner is unavailable → no second human exists, so the sealed copy has a named recovery contact `[OPEN]` O1/10.8.1 (who that is cannot be decided here).

## 11. Rollout

- Order: T1 and T2 (M1, no runtime impact) → T3 (M2, after 10.7.1-T4 rotation steps exist) → T4 (M2, after 10.2.1-T1 images). Gate severity starts at `CRITICAL` for one week if the first scan is noisy, then `HIGH`; the change is a one-line config and is recorded.
- Monitoring: CI job status; inventory overdue rows reported by the check; break-glass ledger `open` older than 24 h.
- Rollback: disabling the image-scan stage is a CI config change that needs an exception-file entry with an expiry (never silent); push protection is not rolled back. Nothing in the runtime path changes.
- `[OPEN]` O3: managed secret store, managed key custody and provider-native image scanning replace the compose-era equivalents; revisit in 10.8.1.
