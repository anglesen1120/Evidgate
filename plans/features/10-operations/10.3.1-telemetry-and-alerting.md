## 1. Goal and non-goals

**Goal.** An operator can reconstruct what happened to any run, decision or dead-letter row from telemetry alone (NFR-10-1): `Evidgate.Api` and `Evidgate.Worker` emit OTel traces, metrics and logs correlated by `request_id`/`run_id`/`job_id`/`trace_id` (FR-10-5); one collector is the only egress and redacts secrets before export; a metrics catalogue covers the queue/outbox/lease/artifact/healing signals plus .NET runtime health and per-unit cost counters; dashboards and alert rules carry severity, numeric thresholds, owners and runbook links — and every alert fires in staging when synthetically triggered (NFR-10-2, FR-10-6).

**Non-goals.** SLI/SLO recording rules and error budgets (10.4.1); the load test that generates the measured values (10.6.1); backup/restore telemetry beyond existing job signals (10.5.1); the web-vitals *emission* (09.1.1-T9 owns it, T39); healing availability switch semantics (00 §8.7); the per-unit cost model (10.9.1 consumes the counters); the observability backend selection (resolved: RECOMMENDATIONS 10 — managed OTLP backend or Apache-2.0 components, licences ⚠️ checked when chosen).

## 2. User stories and acceptance criteria

- As an operator, I can follow one `trace_id` from an HTTP request through the outbox task to a dead-letter, without reading logs by hand.
- As an on-call responder, every page links a runbook and names a numeric threshold I can sanity-check.
- As a security reviewer, a secret-looking value sent through the system never reaches the telemetry backend in a label or field.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A `POST /v1/runs/{r}/events` request produces one trace whose spans and correlated logs carry `request_id`, `run_id`, `trace_id`, and the resulting outbox/task processing carries `job_id`; the W3C `traceparent` is propagated end to end |
| AC2 | A synthetic log/trace containing `authorization`, a `__Host-` cookie value or an `EVIDGATE_*` secret is exported by the collector with those attributes dropped/redacted |
| AC3 | The metrics catalogue exposes, per environment: task-queue age, outbox dispatch lag, lease-loss rate, dead-letter depth, incomplete rate, parser-error rate, artifact-failure rate, healing false-positive rate, ingest p95, decision p95, plus .NET runtime metrics (GC heap/gen-2/LOH, thread-pool counts and starvation, Npgsql pool occupancy/wait, EF Core command durations) and per-unit cost counters |
| AC4 | Four dashboards exist and render: service health, ingest/decision SLI, queue and lease state, tenant-neutral cost view |
| AC5 | Each alert rule in `infra/alerts/` carries a numeric threshold, a named owner and a runbook URL; a synthetically triggered breach fires the alert with its severity in staging within one evaluation window; `scripts/check-alerts.sh` fails on any rule missing threshold/owner/runbook |
| AC6 | A catalogue metric whose source does not exist yet reads `null`/unavailable with a reason label, never 0 (T60) |

## 4. Data model and migrations

None owned. Plan 10 owns no business tables (area plan §4). Metrics are emitted at runtime and recorded in the telemetry backend; dashboards, alert rules and collector config are versioned files under `infra/`. The catalogue queries `task`/`outbox` and the domain state columns of 00 §8 — read-only, no new columns or tables.

## 5. API shapes (commands, queries, endpoints)

No `/v1` commands or queries. Operational surface:

| Surface | Mechanism |
|---|---|
| `GET /metrics` | scrape endpoint on Api and Worker (00 §9.1: outside `/v1`, tenant-free, not public) |
| OTLP export | Api/Worker → collector over the internal network; collector → backend (⚠️ backend per RECOMMENDATIONS 10 — managed OTLP or Apache-2.0) |
| Correlation | `X-Request-Id` + W3C `traceparent` middleware (00 §9.1) feeding trace/log/span attributes; `job_id` stamped by the task handler on claim |
| Alert rules | `infra/alerts/<env>/*.yaml`: metric, numeric threshold, severity, owner, runbook URL |
| Alert routing | collector/backend routing to the on-call channel; consumed by 01.5.1-T4 (dead-letter hook) and 10.2.2-T2 (rollback trigger) |

## 6. States and transitions

None introduced. This story only *measures* existing states: `task` lifecycle `queued → active → retry → dead_letter → replayed` and `outbox` dispatch (00 §5.3), job `epoch`/lease (00 §8.2), artifact `ready`/`rejected` (00 §8.4), evaluation `mode` (00 §8.5), healing availability `enabled`, `shadow` or `disabled` (00 §8.7, T33).

## 7. Jobs and integrations

- Queue/lease metrics are computed from `task`/`outbox`/`job_lease` tables (00 §5.3, §8.2) by a scheduled reader in the Worker (Cronos schedule via `unique (schedule_name, fire_at)`, no leader).
- Alert outputs are consumed by: 01.5.1-T4 dead-letter runbook hook, 10.2.2-T2 canary rollback trigger, 10.7.1-T1/T2/T5 runbooks (each alert names its runbook).
- Web-vitals ingestion point for 09.1.1-T9's LCP/INP events (T39) — recording rules for them land in 10.4.1-T1. Shape delivered by 09.1.1-T9.1 (#153): OTLP/HTTP trace spans named `web_vital` with attributes `web_vital.name` (`LCP`/`INP`/`CLS`), `web_vital.value`, `web_vital.rating`, `web_vital.navigation_type`, `evidgate.route` (a route template, never a URL), resource `service.name`; LCP is final-only, INP/CLS are page-cumulative; head sampling follows `evidgate-telemetry-sample-ratio`. The collector receiver must accept browser CORS (`OPTIONS` + `Access-Control-Allow-Origin`, `content-type`).
- Cost counters feed 10.9.1-T1's unit-economics roll-up.

| T60 (no fabricated metrics) | missing-source metrics emit `null`/unavailable with reason | AC6 |

| Tenant scope | `/metrics` is tenant-free by contract (00 §9.1); tenant-class aggregation is cardinality-bounded and neutral in dashboards | AC3 + dashboard review |

| Telemetry | this story defines the telemetry: metric label allowlist and collector redaction as in the rows above, correlation ids per NFR-10-1, no customer identifiers in any label | AC1, AC2 |
| Failure path | an unreachable or slow collector must never affect a request or a job: export is asynchronous and bounded and drops rather than blocks, and the browser exporter is a no-op or fails silently (09.1.1-T9.1); `[OPEN]` the T1 test plan (§9) lists no collector-down case yet | T1 test plan (§9), to be extended |

**T1 notes (delivered S91):** correlation ids (`request_id`, `run_id`, `job_id`, `trace_id`) are carried on **spans and log records only, never as metric tags** — a tag is a series, so an id in one is one series per request (cardinality, §8) — which refines T1.2's "metric tags" wording; `job_id` is set on the `task.execute` consumer span (and on the claim span for a single-row claim; the claim span otherwise carries only the bounded `task.queue`/`task.claimed`), and the head sampler deliberately keeps a dropped trace recorded in-process so its errors can still be exported, so `EVIDGATE__TELEMETRY__SAMPLERATIO` saves backend volume and network, not local CPU (collector-side tail sampling is 10.3.1-T2's; the trade-off and the honoured inbound `traceparent` are recorded in `docs/runbooks/telemetry.md` for owner review).

## 11. Rollout

- No feature flag for instrumentation itself; sampling rate and batching are per-env config. Merge order: T1 → T2 → T3 (M1), T4 → T5 (M2); T5 depends on runbook stubs that 10.7.1 fills in — stub files are created here so links are never dead.
- Monitoring: this story *is* the monitoring; until T5 lands, staging relies on dashboards only.
- Rollback: reduce sampling to 0 or remove the exporter — telemetry loss must never break the app (collector absence degrades gracefully: export failure is logged once, not retried into the request path).
