## 1. Goal and non-goals

**Goal.** One Settings surface where a `tenant_admin` (and role-scoped delegates: `release_approver` for policy, `test_maintainer`/`tenant_admin` for agent pools) manages members and roles, secret *references*, policy revisions, quota/retention, audit, integrations (webhook endpoints, V1) and agents (V2) — and at no point does any Settings screen fetch, store or render a secret's plaintext value. The server is the only place a secret is ever generated or verified; the UI shows metadata (name, scope, prefix/last-4, rotation state, expiry) and triggers rotation, never displays the rotated value on an ongoing screen.

**Non-goals.** Creating the *first* ingest token or CI binding during onboarding (09.2.1-T2 owns the one-time reveal-at-creation dialog reused here for rotation, §3); computing any decision/gate logic client-side (09.3.1 owns decision rendering, FR-09-1); SSO/SAML enterprise settings (V3, `[OPEN]`); billing/invoice UI (12, out of 09 scope entirely); healing kill-switch UI (09.5.2-T3).

## 2. User stories and acceptance criteria

- As a `tenant_admin`, I open Settings and see only the tabs my permissions allow, so I never see a control I cannot use.
- As a `tenant_admin`, I invite/remove members and see their effective per-project role before I save, so I do not lock myself out.
- As a `tenant_admin`, I see which secrets exist, their scope and rotation state, and can rotate them — without ever seeing the current plaintext value.
- As a `release_approver`, I review a policy revision diff and publish a new one, and a concurrent edit shows me a conflict, not a silent overwrite.
- As a `tenant_admin`, I see quota usage against limits and change retention with a clear warning of what gets deleted sooner.
- As a `tenant_admin`, I filter and export the audit log, and see clearly which rows are platform-operator support access.
- As a `tenant_admin`, I see security events (auth failures, cross-tenant probes, flagged support access) filtered by project/type/severity/time.

## 6. States and transitions

No new state machine; this story renders existing ones read-only (plus the transitions its actions trigger through existing endpoints):

| Object | States rendered (00 §8.9/§8.10, 07) | UI rule |
|---|---|---|
| Membership | `pending → active → removed` | Last-admin guard error shown verbatim (AC2), never a client-side pre-check that could drift from the server |
| Invite | `pending → accepted \| revoked \| expired` | Pending invites shown with a resend/revoke action |
| Ingest token | `active → rotated → revoked`, `active → expired` | Rotation shows state transition + reminder chip; never re-fetches the old or new plaintext |
| `policy_revision` | `draft → active → retired` (07 §4) + `policy_activation.mode ∈ {advisory, enforcing}` | Advisory-vs-gating indicator is a direct render of `mode`, never inferred |
| `webhook_delivery` | `state`, `attempts`, `next_attempt_at` (07 §4) | Delivery log row shows retry state and next attempt time as-is |
| Job/lease (V2, agents page) | `queued → leased → running → finished`, `lost`, `unschedulable` (00 §8.2) | `unschedulable` reasons rendered verbatim from the server, never paraphrased |

## 7. Jobs and integrations

- No background job is owned by this story. It reads outputs of jobs owned elsewhere: `storage_usage_daily` roll-up (06.5.2-T1), the usage ledger roll-up (12.3.1-T5/T6), the webhook delivery dispatcher's retry state (07.6.2), the security-events baseline collector (11.5.1-T5).
- CSV export (T6) is client-side: repeated cursor fetches of `GET /v1/orgs/{o}/audit` up to a bounded row cap (10,000, matching AC7); no server export endpoint is added — this keeps the story contract-free per §3.
- Rotation actions (secrets, integrations) are plain mutations on existing endpoints; the resulting one-time plaintext reveal is delegated to the shared `ConnectStepRevealComponent` (09.2.1-T2) so exactly one component in the codebase is ever allowed to hold a secret value in memory, and only for the duration of that dialog.

|---|---|---|

| T60 (no fabricated metrics) | Quota counters render `null`/"unavailable" with the server's reason when `storage_usage_daily.egress_bytes` is not yet populated, never `0` | Vitest test feeding a `null` egress field and asserting "unavailable" text, not "0" |
| Authz per action | Invite/remove requires `membership:write`; policy publish requires `policy:write` (`release_approver`); retention save requires `project:write`; agent pool write requires `agent_pool:write` (`tenant_admin`, V2); webhook endpoint create/rotate/redeliver requires `webhook:write` (`tenant_admin`) | Route-guard + button-disabled Vitest tests per role fixture |

| Secrets from environment/secret store (S3) | The UI never has an environment/secret-store credential of its own; the browser only ever holds the `__Host-` session cookie + XSRF token (T38) | Existing 09.1.1-T5 contract, unchanged here |
| Hot-path performance (W7, NFR-09-1) | Every list (members, audit, security events) is cursor-paginated and CDK-virtual-scrolled past 200 rows; no "load all" button anywhere in this story | `angular.json` budget check on the settings lazy chunk (≤ 150 kB gzip) |
| PDPL/retention impact | Retention-change flow is the only control in this story that changes a deletion timeline; it always shows AC6's impact warning before submit and audits the change (06.4.1's `GET/PUT /v1/projects/{p}/retention`) | AC6; Playwright spec |

**DoR review answers** (00 §12, `plans/features/README.md` §6):

- **Authorization:** each tab and action follows the per-action permissions in the table above; the support access tab (T10) needs `support:read` to list and `support:approve` to approve/revoke; the quota badge (T11) needs `usage:read`. The server pipeline is the authority.
- **Retention/deletion:** the retention change flow is the only control here that changes a deletion timeline; it shows the AC6 impact warning and is audited by 06.4.1.
- **Telemetry:** 09.1.1-T9 vitals on the Settings chunk; audit export cap hits logged as an error-funnel event with ids only.
- **Failure path:** server errors show verbatim; a `null` usage summary shows "unavailable" and no badge (T60); a revoked or expired support grant removes the banner on the next response.

- Monitoring: 09.1.1-T9 web telemetry (LCP/INP) covers the Settings lazy chunk; audit export cap hits are logged as an error-funnel event (ids only, no row content, per §8).
- Rollback: revert the PR; no server data or migration is touched by this story.
