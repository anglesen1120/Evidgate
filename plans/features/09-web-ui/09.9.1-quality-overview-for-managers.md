## 1. Goal and non-goals

**Goal.** A manager opens one project page and sees, from stored history only: pass rate over time, the most flaky cases, time to decision (p50/p95) and the incomplete-run rate, for a chosen date range and branch, with every number linking to the runs behind it. The numbers are produced by a server read model (`GET /v1/projects/{p}/overview`, T1) over the 03.9.1 `case_result_history` projection and 07.5.2 evaluations; the browser renders them and computes nothing (FR-09-1). Permissions match run pages: whoever can read runs of the project can read the overview.

**Non-goals.** Cross-project or org-wide dashboards; export; custom metrics or user-defined charts; alerts and notifications; the history projection itself (03.9.1); flake classification rules (07.4.1); a quality "score" or ranking of people; any metric that mixes outcome and completeness into one number. Pass rate is never presented as a release verdict.

## 2. User stories and acceptance criteria

- As a QA manager, I see whether pass rate is rising or falling over the last 30 days and click a bad day to see its runs.
- As a manager, I see which cases are most flaky so I can assign owners.
- As a release manager, I see how long decisions take (p50/p95) and how often runs end incomplete, so I can find collection problems rather than blaming tests.
- As a screen-reader user, I get the same information as a table, not only a chart.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `GET /v1/projects/{p}/overview?from=&to=&branch=` returns `pass_rate_trend[]` (per day: passed, failed, other counts and rate), `top_flaky[]` (case id, name, flake rate, runs observed, last flaked at), `decision_latency` (`p50_seconds`, `p95_seconds`, sample size) and `incomplete_rate` (incomplete runs / terminal runs, counts included); every figure is derived from stored history and carries its sample size |
| AC2 | The endpoint requires the same permission as run pages (`run:read`/`decision:read` `[OPEN]`), is project-scoped under RLS (a foreign project id returns 404, no enumeration), and excludes `import`-marked runs (03.9.2) and runs of other branches when `branch` is set |
| AC3 | The screen renders the four panels from the response only; it computes no rate, percentile or classification client-side, and shows "no data" with the sample size (never `0%`) when the denominator is 0 |
| AC4 | The date range defaults to the last 30 days, is bounded (max 366 days `[INFERENCE]`, from the server error), and both range and branch live in URL query params so a link reproduces the view; an invalid range surfaces the server's validation error verbatim |
| AC5 | Every trend point, flaky case and latency/incomplete figure links to the run list (09.3.1-T1) or case history prefiltered by the same range/branch/state; the pass-rate trend never uses colour alone to separate passed from failed/other |
| AC6 | Outcome, completeness and decision stay separate: the pass-rate panel counts outcomes of complete runs only and states the exclusion; incomplete runs appear only in the incomplete-rate panel; no panel is labelled "quality score" or implies PASS |
| AC7 | A large history (366 days, 5 000 flaky candidates server-side) renders within the W7 budgets: top-N is capped by the server (N ≤ 50), the chart series is ≤ 366 points, the lazy chunk ≤ 150 kB gzip and the response p95 meets the read-model target `[OPEN]` set with 03.9.1 |
| AC8 | Empty state (new project, no runs in range), partial data (some days missing), 403/404, 429 with `Retry-After` and a slow response (skeleton, cancel on range change) each render a defined state; stale data is labelled with the server's `as_of` time |
| AC9 | Keyboard and screen reader: charts have a text-table alternative toggle, all controls are operable by keyboard, focus order is logical, axe is clean, and every label, unit and error exists in `vi` and `en` |

## 4. Data model and migrations

No new table. The read model is Dapper SQL over `case_result_history` (03.9.1) and evaluation/run rows (05, 07), executed in the request's tenant transaction (`SET LOCAL evidgate.org_id`) so RLS applies. Aggregation is by UTC day `[INFERENCE]`; the response states the timezone. Percentiles use `percentile_cont` ⚠️ (PostgreSQL 18 behaviour to verify against docs in T1.1). Pass-rate trend is computed from complete runs only (AC6); incomplete runs are counted separately.

Client structure under `apps/web/src/app/features/quality/` (a feature never imports another feature, W1):

| Path | Contents |
|---|---|
| `quality.routes.ts` | lazy route `/projects/:p/quality`, `CanMatchFn` on the run-read permission |
| `overview.store.ts` | `@ngrx/signals` `OverviewStore`: `range`, `branch`, `overview` (response as returned), `status`, `asOf` — no derived metrics |
| `overview.service.ts` | `rxResource` over the SDK call, cancelled on range/branch change |
| `pass-rate-trend.component.ts`, `flaky-cases.component.ts`, `decision-latency.component.ts`, `incomplete-rate.component.ts`, `range-filter.component.ts`, `data-table-toggle.component.ts` | standalone, `OnPush`, signal inputs, `@defer` for the chart panel |

Chart library: ⚠️ not chosen. `[OPEN]` choose in T2.1 with licence and bundle-size check against the W7 budget (candidate: a small SVG renderer written in-repo; or a licence-checked library through `licence-scan.sh`), following DECISIONS §4.2 rather than adding an unvetted dependency.

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Query (Dapper) | `GetProjectOverviewQuery` | `GET /v1/projects/{p}/overview?from=&to=&branch=` | run/decision read `[OPEN]` | 200 · 400/422 `validation_failed` · 404 · 429 |
| SDK data service | `overviewService.get(projectId, range, branch)` | same | same | typed error envelope |

Response sketch ⚠️ (confirmed in T1.1): `{ project_id, from, to, branch, timezone: "UTC", as_of, pass_rate_trend: [{ day, passed, failed, other, runs }], top_flaky: [{ case_id, name, flake_rate, runs_observed, last_flaked_at }], decision_latency: { p50_seconds, p95_seconds, sample_size }, incomplete_rate: { incomplete_runs, terminal_runs } }`. Rates are included as numbers computed server-side; the UI never derives them. Cursor pagination is not used (bounded top-N); `from`/`to` bounds and top-N are server-enforced. ETag/`If-None-Match` ⚠️ optional for cheap refresh `[INFERENCE]`.

## 6. States and transitions

No new domain state. Renders existing run states (00 §8.1: `complete`, `incomplete`, `canceled` terminal) and evaluation outcomes; `canceled` runs are excluded from both pass-rate and incomplete-rate denominators and the exclusion is stated. Screen state: `idle → loading → ready | empty | error`, with `loading` re-entered on range/branch change (previous request cancelled, last good data kept dimmed with `as_of`).

## 7. Jobs and integrations

No job owned here; the overview reads on demand. Freshness depends on the 03.9.1 projection consumer lag (outbox, 05) — `as_of` shows the projection's watermark `[OPEN]` field from 03.9.1. If the query exceeds the read-model budget at scale, a daily roll-up table would be a follow-up decision in 10.6.1 terms `[OPEN]`, not added silently. Telemetry: endpoint latency histogram and the web vitals from 09.1.1-T9 for the route; ids only, no case names in telemetry.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| S2 / tenant isolation | Server pipeline authorizes; RLS scopes the query; foreign project is 404 | AC2; `Overview_ForeignProject_404` isolation test |
| No fabricated metrics (T60, FR-09-1) | Zero denominators render "no data" with sample size; the UI computes no figure | AC3 |
| Untrusted text | Case names are bound by interpolation only; no `[innerHTML]`/`bypassSecurityTrust*` | lint rule; component test with markup-like case name |
| Input limits (S5) | `from`/`to` max span, `branch` length and charset validated by the server; top-N capped | AC4, AC7 |
| Privacy | Aggregates only; no per-person metric, no author names in the overview (avoids ranking people, PDPL-minimal) `[INFERENCE]` | response schema test: no user fields |
| Performance (W7) | Single request per range; chart `@defer`; series ≤ 366 points; server top-N ≤ 50; query uses indexed range scans, `EXPLAIN`-checked in T1.2 | AC7; budget gate; read-model perf test |
| a11y / i18n (W8) | Text-table alternative, no colour-only encoding, `$localize` for all labels, number/date formatting by locale | AC9 |

DoR review answers. **Authorization:** run-page permission, server-enforced; hidden route is a convenience. **Retention/deletion impact:** the overview shows only what history retention keeps (03.9.1 follows 06 retention); after history is purged the range shows fewer days and the empty/partial state says so, it never invents past values. **Telemetry:** endpoint latency/error counters and web vitals; no case or branch content in telemetry. **Failure path:** projection lag or missing days show `as_of` and "partial data"; query timeout returns 503/`Retry-After` and a retry control; 429 shows `Retry-After`; a failed panel does not blank the others.
