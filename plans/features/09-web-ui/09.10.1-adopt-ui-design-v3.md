## 1. Goal and non-goals

**Goal.** `apps/web` looks and navigates as the approved v3 mockups: one token set (light and dark), two self-hosted fonts (Manrope, Public Sans, SIL OFL), one shell built from a single navigation manifest, and shared components with fixed status semantics, so each product screen is a migration of an existing screen, not a rewrite.

**Non-goals.** New behaviour or endpoints (each screen's behaviour stays with its own 09.x task; where a mockup shows something no contract specifies, §3 lists it as a question); a v3 of the landing page; deleting the v2 mockups (kept as history); mockup 39 (a localization review page, not a product screen); implementation is not claimed by this document.

## 2. User stories and acceptance criteria

- As a user, I see the same navigation, project selector and account menu on every signed-in screen, in light or dark, in Vietnamese or English.
- As a reviewer, I can tell a waiting item from a validated or approved one without relying on colour.
- As a keyboard or screen-reader user, nothing is lost by the new look.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Tokens and fonts load from `apps/web` assets only (no external font request); light and dark both pass AA contrast (4.5:1 text, 3:1 large text and essential controls) on every migrated screen. |
| AC2 | The shell reads one manifest: sidebar membership and order, breadcrumb parent and screen search come from it; no page copies navigation markup. |
| AC3 | Status semantics: status is never conveyed by colour alone (icon + text); pending / awaiting review is neutral; "Validated" and "Approved" are separate chips and Approved needs a recorded human decision; over-SLA is the only amber in review queues. |
| AC4 | Missing evidence never renders as PASS; completeness, outcome and decision stay three separate fields on run, release and decision screens. |
| AC5 | Healing screens never hide the original failure: the pre-healing failure stays visible next to any shadow result, validation or approval. |
| AC6 | Body text ≥ 12 px; vi and en complete (no hard-coded strings, longest-string layout checked); every screen fits at 900 px without sideways scroll and keeps focus visible and unobscured. |
| AC7 | One primary action per view or active dialog; destructive confirmation only for destructive actions; unavailable actions are natively disabled with the reason beside them. |
| AC8 | Each migrated screen cites its mockup file and passes the visual-regression baseline at 1440 and 900 px, light and dark, vi and en (T13). |

## 3. Contracts touched

No contract change: no endpoint, schema, permission string or migration. Open questions the mockups raise (answers belong to the owning story; the screen must not invent one):

- **[OPEN] Token secret shown once (37, 09.7.2-T1):** whether the plaintext is returned only in the create response and never retrievable; owner 02.4.4. Until answered the screen shows prefix and metadata only.
- **[OPEN] Token maximum expiry (37):** the mockup requires an expiry; the cap is not specified (owner 02.4.4).
- **[OPEN] Policy tab read permission (30, 09.7.1-T4):** which permission lets a non-approver read revisions (owner 07.1.1 / 02.2.1).
- **[OPEN] Retention change 412 (31, 09.7.1-T5):** the response shape when a retention change races a deletion-impact preview (owner 06.4.1).
- **[OPEN] Waiver decline (06, 09.3.1-T11):** the mockup previews a decline; no decline endpoint is specified (owner 07.3.1). The decline control stays preview-only until it exists.

No new domain state. Screen states reuse 09.1.1-T8 (loading, empty, error, 403, 404, 412, 429). The mockups' "prototype state" selector is design-only and is not shipped.

## 7. Jobs and integrations

None. Fonts are self-hosted files (SIL OFL; licence texts ship beside them, see §8).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Untrusted text | The restyle keeps interpolation-only binding; no `[innerHTML]` | existing lint rule, unchanged |
| CSP and Trusted Types (09.1.1-T10) | Fonts and CSS are same-origin files; no inline-style or script additions | CSP check in the web gate |
| Third-party assets | Both fonts are SIL OFL 1.1 variable files, OFL text kept beside them; recorded in the licence inventory by T1 | licence gate stage green |
| Performance (W7) | Fonts preloaded with `font-display: swap`, subset to vi + latin; bundle budgets unchanged | `angular.json` budget check; LCP in 09.1.1-T9 |
| a11y / i18n (W8) | AC6, AC7; vi and en keys complete | axe (09.8.1-T2), key-completeness gate |

DoR review answers.

- **Authorization:** unchanged; route guards and server checks stay the only enforcement, and a screen hides nothing as security.
- **Failure path:** a failed font or token load falls back to system fonts and the existing 09.1.1-T8 error states; no data is at risk.
- **Retention/deletion:** none; the story stores and removes no data.
- **Telemetry:** the 09.1.1-T9 vitals (LCP/INP) per route are the before/after measure; no new event.
