## 1. Goal and non-goals

**Goal.** A new tenant walks a resumable five-step wizard — create project → connect repo/CI → run a sample suite → compare with the original report → enable regular collection — and reaches an enabled, collecting project. No step is skipped silently; each step shows the run/evidence it produced, and reopening the wizard resumes at the correct step from persisted server state.

**Non-goals.** Project/catalog list screens beyond what the wizard needs inline (full catalog browsing is 09.2.1-T6's own screen, in scope here as a task but not general catalog editing — see 03); run detail beyond the sample-run live view (09.3.1 owns the full run/evidence page, T3 here reuses its data service); policy authoring (07 owns policy edit, this story only previews advisory mode); GitHub App installation UI beyond the OIDC/token connect step (03.4.1/03.6.1 own the App flow, V2).

## 2. User stories and acceptance criteria

- As a new tenant admin, I create a project and connect my CI in a few guided steps, so the first green (or red) signal reaches Evidgate without reading documentation first.
- As a QA engineer resuming later, I reopen the wizard and land on the step I left off, with the run/evidence each prior step produced still visible.
- As the Tech Lead, the wizard never claims a gate is enabled before the tenant explicitly enables collection, and never conflates "collection complete" with "policy passed" (FR-09-1/FR-09-2 apply inside the wizard too).

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Completing step 1 (create project) creates the project and advances to step 2; reloading the wizard mid-flow (any step) resumes exactly at the first incomplete step, reading resumable state from the server, not local storage |
| AC2 | Step 2 offers both connect paths (GitHub OIDC exchange, hashed project ingest token shown once and copyable); completing either advances to step 3 and step 2's panel shows the created `ci_binding`/`ingest_token` metadata (never the raw token again) |
| AC3 | Step 3 shows the sample run live (state transitions `created → queued → running → collecting → complete\|incomplete`, per-attempt table) sourced from 09.3.1's run detail data service; the run reaching a terminal state advances the "next" control, it does not skip the step automatically |
| AC4 | Step 4 renders the normalised-vs-original comparison (counts, ids, statuses, digests) with discrepancies listed as per-case reasons, from `GET /v1/runs/{r}/reports/{report_id}/comparison`; zero discrepancies is shown as an explicit "matches" state, not a blank panel |
| AC5 | Step 5 shows the policy's advisory-mode preview and an explicit "not gating yet" statement; a user holding `policy:write` (`release_approver`) can confirm — and the lone org creator does hold it via the T98 grant, so a single-person tenant completes this step unaided; confirm activates the project's policy in `advisory` mode via an audited `policy_activation` row; a user without the permission (i.e. when the `release_approver` role was moved to someone else) sees the step disabled with "ask your release approver"; the wizard's terminal screen shows the project as enabled and collecting once activation exists |
| AC6 | At no step does any element render a PASS/FAIL verdict computed client-side; the sample run's decision panel shows `pending` until `GET /v1/runs/{r}/decision` returns one, per FR-09-1 |
| AC7 | Abandoning the wizard after step 2 and returning within the token's still-valid window resumes at step 3 without re-issuing a new ingest token |
| AC8 | The mapping screen lists `unmapped` and `conflicted` import mappings from `GET /v1/projects/{p}/case-import-mappings?state=`; resolving binds the row to a chosen `case_id` or dismisses it via `POST /v1/case-import-mappings/{m}/resolve`; a state-guard refusal (row already resolved by someone else) renders the server error verbatim and reloads the row; step 4 links every `unmapped`/`conflicted` discrepancy reason to this screen filtered to that row |

- No new permission string; the wizard uses `project:create`, `ci_binding:write`, `ingest_token:write`, `run:create`, `run:read`, `decision:read`, `policy:write` already in 00 §2 (T58/T59 catalogue); the catalog and mapping screens (T6, T8) use `case:read`/`case:write`.
**Resolved (T63, README §3):** wizard progress is **derived** from existing resource state — project, CI binding/token, first run, first evidence revision — never a new wizard-state table or endpoint. Step 5 ("enable collection") activates the project's policy in `advisory` mode via `POST /v1/projects/{p}/policy-activation` (07.1.1-T4, `policy:write`/`release_approver`, audited); there is no `collect_mode` column on `project` (T63).

## 4. Data model and migrations

None (no new database objects; the wizard derives all state from existing project/binding/token/run/evidence-revision/`policy_activation` resources per the §3 T63 note). Web structure:

```
apps/web/src/app/features/onboarding/
  onboarding.routes.ts          lazy route "/onboarding/:projectId?"
  onboarding.store.ts           SignalStore: currentStep, project, binding/token,
                                 sampleRun, comparison, enableState
  steps/
    create-project.page.ts
    connect-ci.page.ts
    sample-run.page.ts
    compare-report.page.ts
    enable-collection.page.ts
  data/onboarding-progress.service.ts   derives resumable step from GET calls,
                                         never a local-only flag
```

## 5. API shapes (commands, queries, endpoints)

| Step | Command / query | Endpoint | Permission | Idempotency / concurrency |
|---|---|---|---|---|
| 1 Create project | command | `POST /v1/orgs/{o}/projects` | `project:create` | `Idempotency-Key` per submit |
| 2 Connect (OIDC path) | command | `POST /v1/projects/{p}/ci-bindings` | `ci_binding:write` | `Idempotency-Key`; response never re-returns a prior binding's secret |
| 2 Connect (token path) | command | `POST /v1/projects/{p}/ingest-tokens` | `ingest_token:write` | `Idempotency-Key`; plaintext returned once, stored only in-memory in the store for the copy action, cleared on navigation away |
| 3 Sample run | query (poll/stream) | `GET /v1/runs/{r}` via 09.3.1's run detail service | `run:read` | none (read) |
| 3 Trigger sample run | command | `POST /v1/projects/{p}/runs` | `run:create` | `Idempotency-Key` per "run sample" click |
| 3 Decision | query | `GET /v1/runs/{r}/decision` | `decision:read` | none; renders `pending` until present |
| 4 Comparison | query | `GET /v1/runs/{r}/reports/{report_id}/comparison` | `run:read` | none |
| 5 Enable collection | command | `POST /v1/projects/{p}/policy-activation` (07 §4) | `policy:write` (`release_approver`) | `Idempotency-Key` per confirm; disabled control (not hidden) when the user lacks the permission |
| Mapping list | query | `GET /v1/projects/{p}/case-import-mappings?state=unmapped\|conflicted` (03.1.2) | `case:read` | cursor `(created_at, id)`, default 50 |
| Mapping resolve | command | `POST /v1/case-import-mappings/{m}/resolve` body `{case_id}` or `{action:'dismiss'}` (03.1.2) | `case:write` | `Idempotency-Key` per submit; controls disabled (not hidden) without `case:write` |

All calls go through the `OnboardingDataService` (W5) over `@evidgate/sdk`; no hand-written DTOs (FR-09-10).

## 6. States and transitions

- Wizard step derivation (no new state machine; reuses 00 §8, resolved T63): `step1_done = project exists`; `step2_done = ci_binding or ingest_token exists`; `step3_done = sampleRun.state ∈ {complete, incomplete}` (terminal collection state, 00 §8.1); `step4_done = the sample run's first evidence revision exists` (00 §8.5) — not "comparison fetched": the comparison panel is a read-only view over that revision, so a reload never loses the signal; `step5_done = a `policy_activation` row exists for the project` (07 §4). Current step = first not-done step; all five done → wizard shows the terminal "project enabled" screen.
- Sample run rendering follows 00 §8.1 exactly (`created → queued → running → collecting → complete\|incomplete\|canceled`); `canceled` in the wizard shows a retry control, never treated as `complete`.
- Evidence/decision rendering follows 00 §8.5: `pending` until an evaluation exists; FAIL/PASS/INCONCLUSIVE only from `GET .../decision`.

## 7. Jobs and integrations

- Step 2's OIDC path calls into 02.4.1/02.4.2 (CI token exchange, GitHub OIDC); the token path calls 02's ingest-token issuance.
- Step 3 reuses 09.3.1's run detail data service and `09.1.1`'s shared components (`EvidenceBadge`, `DecisionChip`, attempts table) rather than re-implementing run rendering.
- Step 4 consumes 04.4.1-T6's comparison endpoint and 06.1.2's evidence-revision read path.
- Step 5 activates the project's policy in `advisory` mode via 07.1.1-T4's `POST /v1/projects/{p}/policy-activation` (`policy:write`/`release_approver`); no policy authoring happens in this story.
- No background task is introduced by this story; the sample run and comparison are computed by the endpoints it calls, not by the web app.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-09-1 (decision never computed) | Step 3's decision panel renders only `GET .../decision` output, `pending` shown until present; step 5's advisory preview renders only the policy's mode/rules from 07's read endpoint, never a computed verdict | AC6, `decision-chip` reuse from 09.1.1 |
| FR-09-2 (complete ≠ passed) | Step 3's terminal state uses `EvidenceBadge` (collection) separate from `DecisionChip` (verdict); wizard copy never says "passed" for a completed collection | AC3, AC6 |
| T38 / 00 §9.1 CSRF | every wizard mutation is a cookie-authenticated call carrying `X-XSRF-TOKEN` via the shared interceptor from 09.1.1-T3 | reused interceptor test + `onboarding.e2e.spec.ts` |
| Secret handling (ingest token) | plaintext token held only in the in-memory store slot for the single "copy" action, cleared on navigation/unmount, never logged, never re-displayed after leaving step 2 | AC2, `connect-ci.page.spec.ts` asserts store slot cleared on `ngOnDestroy` |
| Authz | `project:create`/`ci_binding:write`/`ingest_token:write`/`run:create`/`policy:write` are all permission-checked server-side; a role lacking one sees the corresponding step's action disabled, not hidden silently (server remains the authority) | E2E with a scoped-down role fixture |
| T98 | the org creator holds `release_approver` from org creation, so step 5 is confirmable by a lone creator; the "ask your release approver" disabled state appears only when the user lacks `policy:write` (e.g. the role was reassigned away) | `enable-collection.page.spec.ts` |
| 00 §9.1 idempotency | project/binding/token/run creation each carry `Idempotency-Key` generated once per click, reused on retry | `idempotency.interceptor.spec.ts` (shared from 09.1.1), wizard-specific retry test |
| 00 §9.1 idempotency | step 5 confirm is an audited `POST .../policy-activation` with `Idempotency-Key`; a repeat submit writes the same audited outcome (unique `policy_activation` per project), never a silent double-activation | AC5 idempotent-submit test |
| Performance (W7/T39) | wizard is a lazy `features/onboarding` chunk ≤ 150 kB gzip (09.1.1 budgets apply); step 3's run polling uses the same bounded interval as 09.3.1, no busy-poll | bundle-size check in CI, polling-interval test |
| Retention/PDPL | no additional personal data stored; audit of the enable action (step 5) goes through the existing audit log (02, 00 §9.3 `GET /v1/orgs/{o}/audit`) | enable-audit E2E assertion |

**DoR review answers** (00 §12, `plans/features/README.md` §6):

- **Authorization:** every step's mutation is checked server-side (`project:create`, `ci_binding:write`, `ingest_token:write`, `run:create`, `policy:write`); the mapping screen (T8) needs `case:read` to list and `case:write` to resolve, and its controls are disabled, not hidden, without it.
- **Retention/deletion:** no new stored data; wizard progress is derived from existing resources (T63), and mapping resolutions are 03.1.2's rows.
- **Telemetry:** completion-funnel drop-off per step through 09.1.1-T9, ids only.
- **Failure path:** each mutation reuses its `Idempotency-Key` on retry; server errors (403, 409, 422, 429) show verbatim with a retry; a reload resumes at the derived step.

## 11. Rollout

- No feature flag (the wizard is new UI reached only from a fresh project's empty state; existing enabled projects never see it). Merge order: T1 (shell) → T2/T3 in parallel (both consume T1's store) → T4 → T5 → T6 (catalog screen is reusable independent of the wizard, can land in parallel with T2–T5) → T7 last (depends on T2's binding/token); T8 after T6 and 03.1.2-T2.
- Monitoring: Playwright E2E (09.2.1-T1.4, T3.2, T5.2) makes AC1–AC7 permanent in CI; plan 10 records completion-funnel drop-off per step once telemetry (09.1.1-T9) is wired.
- Rollback: revert the PR; no destructive server-side effect beyond the projects/bindings/tokens/runs already created through normal endpoints during testing, cleaned up by existing tenant-deletion tooling.
