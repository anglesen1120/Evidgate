## 1. Goal and non-goals

**Goal.** A new tenant walks a resumable five-step wizard — create project → connect repo/CI → run a sample suite → compare with the original report → enable regular collection — and reaches an enabled, collecting project. No step is skipped silently; each step shows the run/evidence it produced, and reopening the wizard resumes at the correct step from persisted server state.

**Non-goals.** Project/catalog list screens beyond what the wizard needs inline (full catalog browsing is 09.2.1-T6's own screen, in scope here as a task but not general catalog editing — see 03); run detail beyond the sample-run live view (09.3.1 owns the full run/evidence page, T3 here reuses its data service); policy authoring (07 owns policy edit, this story only previews advisory mode); GitHub App installation UI beyond the OIDC/token connect step (03.4.1/03.6.1 own the App flow, V2).

## 2. User stories and acceptance criteria

- As a new tenant admin, I create a project and connect my CI in a few guided steps, so the first green (or red) signal reaches Evidgate without reading documentation first.
- As a QA engineer resuming later, I reopen the wizard and land on the step I left off, with the run/evidence each prior step produced still visible.
- As the Tech Lead, the wizard never claims a gate is enabled before the tenant explicitly enables collection, and never conflates "collection complete" with "policy passed" (FR-09-1/FR-09-2 apply inside the wizard too).

| # | Acceptance criterion (testable) |

## 5. API shapes (commands, queries, endpoints)

| Step | Command / query | Endpoint | Permission | Idempotency / concurrency |
|---|---|---|---|---|
| 1 Create project | command | `POST /v1/orgs/{o}/projects` | `project:create` | `Idempotency-Key` per submit |
| 2 Connect (OIDC path) | command | `POST /v1/projects/{p}/ci-bindings` | `ci_binding:write` | `Idempotency-Key`; response never re-returns a prior binding's secret |
| 2 Connect (token path) | command | `POST /v1/projects/{p}/ingest-tokens` | `ingest_token:write` | `Idempotency-Key`; plaintext returned once, stored only in-memory in the store for the copy action, cleared on navigation away |
| 3 Sample run | query (poll/stream) | `GET /v1/runs/{r}` via 09.3.1's run detail service | `run:read` | none (read) |
| 3 Trigger sample run | command | `POST /v1/projects/{p}/runs` | `run:create` | `Idempotency-Key` per "run sample" click |
| 3 Decision | query | `GET /v1/runs/{r}/decision` | `decision:read` | none; renders `pending` until present |
| 4 Comparison | query | `GET /v1/runs/{r}/reports/{report_id}/comparison` | `run:read` | none |
| 5 Enable collection | command | `POST /v1/projects/{p}/policy-activation` (07 §4) | `policy:write` (`release_approver`) | `Idempotency-Key` per confirm; disabled control (not hidden) when the user lacks the permission |
| Mapping list | query | `GET /v1/projects/{p}/case-import-mappings?state=unmapped\|conflicted` (03.1.2) | `case:read` | cursor `(created_at, id)`, default 50 |
| Mapping resolve | command | `POST /v1/case-import-mappings/{m}/resolve` body `{case_id}` or `{action:'dismiss'}` (03.1.2) | `case:write` | `Idempotency-Key` per submit; controls disabled (not hidden) without `case:write` |

All calls go through the `OnboardingDataService` (W5) over `@evidgate/sdk`; no hand-written DTOs (FR-09-10).

## 6. States and transitions

- Wizard step derivation (no new state machine; reuses 00 §8, resolved T63): `step1_done = project exists`; `step2_done = ci_binding or ingest_token exists`; `step3_done = sampleRun.state ∈ {complete, incomplete}` (terminal collection state, 00 §8.1); `step4_done = the sample run's first evidence revision exists` (00 §8.5) — not "comparison fetched": the comparison panel is a read-only view over that revision, so a reload never loses the signal; `step5_done = a `policy_activation` row exists for the project` (07 §4). Current step = first not-done step; all five done → wizard shows the terminal "project enabled" screen.
- Sample run rendering follows 00 §8.1 exactly (`created → queued → running → collecting → complete\|incomplete\|canceled`); `canceled` in the wizard shows a retry control, never treated as `complete`.
- Evidence/decision rendering follows 00 §8.5: `pending` until an evaluation exists; FAIL/PASS/INCONCLUSIVE only from `GET .../decision`.

## 7. Jobs and integrations

- Step 2's OIDC path calls into 02.4.1/02.4.2 (CI token exchange, GitHub OIDC); the token path calls 02's ingest-token issuance.
- Step 3 reuses 09.3.1's run detail data service and `09.1.1`'s shared components (`EvidenceBadge`, `DecisionChip`, attempts table) rather than re-implementing run rendering.
- Step 4 consumes 04.4.1-T6's comparison endpoint and 06.1.2's evidence-revision read path.
- Step 5 activates the project's policy in `advisory` mode via 07.1.1-T4's `POST /v1/projects/{p}/policy-activation` (`policy:write`/`release_approver`); no policy authoring happens in this story.
- No background task is introduced by this story; the sample run and comparison are computed by the endpoints it calls, not by the web app.

**DoR review answers** (00 §12, `plans/features/README.md` §6):

- **Authorization:** every step's mutation is checked server-side (`project:create`, `ci_binding:write`, `ingest_token:write`, `run:create`, `policy:write`); the mapping screen (T8) needs `case:read` to list and `case:write` to resolve, and its controls are disabled, not hidden, without it.
- **Retention/deletion:** no new stored data; wizard progress is derived from existing resources (T63), and mapping resolutions are 03.1.2's rows.
- **Telemetry:** completion-funnel drop-off per step through 09.1.1-T9, ids only.
- **Failure path:** each mutation reuses its `Idempotency-Key` on retry; server errors (403, 409, 422, 429) show verbatim with a retry; a reload resumes at the derived step.
