## 1. Goal and non-goals

**Goal.** A `test_maintainer`/`qa_engineer` can inspect every V1 shadow healing candidate — patch diff, validation results, negative control, lineage, risk flags — and compare the original failure against the shadow result, with an unmissable "proposal only" banner and **no control anywhere in the UI that can apply, approve or reject a patch** in V1 (T29: approval ships behind a flag that defaults off; 09.5.2 owns the V2 approval controls).

**Non-goals.** Approve/reject/apply actions and `If-Match`/`candidate_hash` conflict handling (09.5.2, V2); candidate generation, validation execution, AST allowlisting (08.4.x, server); kill-switch configuration (09.7.1); incident triage (09.4.1, though this story consumes its original-failure rendering pattern for the comparison block).

## 2. User stories and acceptance criteria

- As a test maintainer, I open the Healing Review queue and see every shadow candidate with its validation and sample outcome, so I can judge quality before V2 approval exists.
- As a QA engineer, I open a candidate and see the patch diff, negative control result and lineage, with validation evidence I can trust because the UI cannot have altered it.
- As anyone with `healing:triage`, I see the shadow result next to the original failure and I can verify the official run is untouched.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The Healing Review queue lists shadow candidates with status (`proposed, validated, approved, applied, rejected, insufficient_evidence, expired, revoked`), label source, sample counts and the availability chip (`enabled, shadow, disabled, unavailable`) (Vitest `healing-queue-store.spec.ts`) |
| AC2 | Candidate detail renders patch diff, validation results (including the negative-control outcome), lineage (source incident, knowledge record if any) and risk flags, all read-only, with a persistent "proposal only" banner on every view of the page |
| AC3 | No element in `apps/web` under this story's routes renders an approve, reject or apply control; a repo-wide grep/lint check (`scripts/check-no-v1-apply-control.sh`) scoped to `features/healing-review/` finds zero matches for approve/reject/apply action bindings |
| AC4 | The shadow-comparison view shows the original failure (raw status, evidence revision) and the shadow result as two separate blocks; the official run's decision is unchanged and rendered from `GET /v1/runs/{r}/decision` exactly as in 09.3.1, never overwritten by the shadow outcome |
| AC5 | When healing availability resolves to `unavailable`, the queue shows the derived banner and disables review controls without implying an operator disabled it (T33) |

## 3. Contracts touched

- 00 §9.3 endpoints consumed: `GET /v1/projects/{p}/healing/candidates` (`healing:triage`), `GET /v1/healing/candidates/{c}` (`healing:triage`). No mutation endpoint is called by this story — `POST /v1/healing/candidates/{c}/approve|revoke|reject` and the kill-switch `PUT /v1/healing/switch` belong to 09.5.2/09.7.1 and are explicitly out of scope (T29).
- 00 §8.7 candidate lifecycle rendered only: `proposed → validated → approved → applied`, exits `rejected, insufficient_evidence, expired, revoked`; every transition's actor/reason/hashes shown when present; knowledge record `active → revoked` shown as lineage context; availability `enabled | shadow | disabled | unavailable`, most-restrictive-wins, `unavailable` always derived (never operator-set, T33).
- T29 (kill switch before apply): this story's queue and detail pages contain zero apply/approve/reject bindings; the approval capability itself is not merely hidden by a flag inside this component tree — it does not exist in the V1 build of `features/healing-review/`, satisfying "no control can apply a patch in V1" literally, not just by default-off flag.

## 4. Data model and migrations

None — no database objects. Client structure (W1/W4):

- `apps/web/src/app/features/healing-review/` — lazy route `projects/:projectId/healing/candidates` (queue) and `projects/:projectId/healing/candidates/:candidateId` (detail, read-only); `HealingQueueStore`, `CandidateDetailStore` (`@ngrx/signals`); `HealingDataService` over `@evidgate/sdk` exposing only the two `GET` calls of §3.
- Shared components added: `AvailabilityChip` (`enabled|shadow|disabled|unavailable`), `PatchDiffView` (read-only diff, `@defer`), `ValidationResultsPanel` (negative control highlighted), `LineagePanel`, `RiskFlagsList`, `ProposalOnlyBanner`.
- Reuses `FlakyBadge`/`HealedBadge` pattern and evidence-revision rendering from 09.3.1-T4/T3 for the shadow-comparison block; no new store duplicates run/evidence state — the comparison view reads the run's existing decision via the same `RunDetailStore` query used by 09.3.1.

## 5. API shapes (commands, queries, endpoints)

| Route | Guard (`CanMatchFn`) | Store | Page |
|---|---|---|---|
| `projects/:projectId/healing/candidates` | `healing:triage` | `HealingQueueStore` | shadow-candidate queue |
| `projects/:projectId/healing/candidates/:candidateId` | `healing:triage` | `CandidateDetailStore` | read-only candidate detail + shadow comparison |

| Endpoint consumed | Permission | UI semantics |
|---|---|---|
| `GET /v1/projects/{p}/healing/candidates` | `healing:triage` | shadow (V1) candidates only; `?cursor=&limit=50`, filters status/availability |
| `GET /v1/healing/candidates/{c}` | `healing:triage` | patch diff, validation set (incl. negative control), lineage, risk flags, hashes |

No commands (no `ICommand`/mutation) are issued by this story; the entire surface is `IQuery`-backed reads consumed through the generated SDK, matching D3/D5 (rendered, never computed; SDK-only types).

## 6. States and transitions

Rendered only (00 §8.7, no new states): candidate `proposed → validated → approved → applied`, exits `rejected, insufficient_evidence, expired, revoked` — in V1 only `proposed`/`validated` (and terminal `insufficient_evidence`/`expired`) are reachable in practice since nothing in this UI approves; `approved`/`applied`/`rejected`/`revoked` states, if present from other tenants' data or future migration, are still rendered as read-only history, never as an actionable state. Knowledge record `active → revoked` shown as lineage context only. Availability `enabled | shadow | disabled | unavailable`, most-restrictive of system/tenant/project wins; `unavailable` is always derived, never stored by an operator (T33) — the UI never offers a control that would contradict that.

## 7. Jobs and integrations

- No client-triggered background jobs; candidate generation/validation is entirely server-owned (08.3.x/08.4.x).
- Shadow comparison reuses the run detail's existing `DecisionView`/`AttemptsTable` query path (09.3.1-T4/T5) to guarantee the official run's decision is never re-derived or shadowed by this screen — it is the same read, not a copy.
- Consumed by: none listed (story blocks none per header); a leaf node feeding only 09.5.2 (V2) by component reuse (`PatchDiffView`, `ValidationResultsPanel`, `LineagePanel` are extended, not replaced, when 09.5.2 adds approval controls in a later PR).

## 11. Rollout

- Order: T1 → T2 → T3 (T3 depends on 09.3.1-T4's attempts rendering, already delivered).
- Feature flag: none required for V1 — the absence of apply/approve/reject controls is structural (not present in the build), not flag-gated, satisfying T29 more strongly than a default-off flag would. When 09.5.2 (V2) adds approval, it introduces its own flag defaulting off per T29, in a separate route/component, without modifying this story's read-only components beyond composition.
- Monitoring: web-vitals telemetry (09.1.1-T9) on the queue/detail routes.
- Rollback: revert the PR; no data or deployed state is affected (read-only surface).
