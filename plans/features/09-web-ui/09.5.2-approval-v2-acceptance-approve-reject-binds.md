## 1. Goal and non-goals

**Goal.** On the Healing Review screen, a member holding `healing:approve` can approve or reject a validated healing candidate; every decision is bound to the exact `candidate_hash` and base commit that were reviewed (`If-Match`), the server re-checks permission at write time, a stale hash returns 412 rendered as a visible conflict with a reload path, and sensitive cases enforce a different reviewer (T35). The story also delivers the knowledge-record/revocation panel and the resolved kill-switch availability controls (system → tenant → project), and keeps healing approval visibly separate from release/policy approval (FR-09-8).

**Non-goals.** The approve/reject/revoke and switch server handlers (08.6.1, 08.6.3, 08.7.2 — contracts are consumed, not defined here); the V1 shadow queue and shadow comparison blocks (09.5.1, 09.3.1); candidate generation, validation and LLM plumbing (08.2–08.5); release/waiver/policy approval UI (09.7.1); applying an approved candidate (08.6.2, V2 follow-on — the UI shows `applied` as a read-only state and the no-V1-apply-control check covers the shared `features/healing-review/` root, T96).

## 2. User stories and acceptance criteria

- As a `healing:approve` holder, I approve or reject a candidate after seeing its patch, validation evidence, `candidate_hash` and base commit, so my decision can never silently apply to a different patch.
- As a tenant admin (`healing:configure`), I can see where the healing switch is effectively set and change it per scope, so approval controls match the real availability.
- As a reviewer of a sensitive case, I am told when I am not an eligible approver (T35), so the four-eyes rule is legible instead of a bare 403.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Approve opens a dialog showing `candidate_hash` and base commit and requiring a reason; submit issues `POST /v1/healing/candidates/{c}/approve` with `If-Match: <ETag>` and the hash in the body; on success the candidate chip renders `approved` and the approve control is gone |
| AC2 | If the candidate changed between render and submit (another reviewer acted, a new validation set landed), the API returns 412; the UI shows a conflict dialog containing the current revision id from `error.details` and a Reload action; after reload the dialog shows the new `candidate_hash`; no auto-retry or merge happens |
| AC3 | Reject with an empty reason has a disabled submit control; a forced request without a reason returns 422 (code per `contracts/openapi.yaml`, T52) and the dialog stays open with the error rendered |
| AC4 | On a sensitive case where the current member triggered/edited the candidate or gave the human `test_drift` label, approve returns 403; the UI renders the "a different reviewer must approve" notice with the reason; a different eligible approver succeeds (T35) |
| AC5 | A member whose `healing:approve` was revoked after page load gets 403 on submit; the UI re-reads the session permissions, disables approve/reject and shows a "permissions changed" notice — the hidden/disabled control is never the security check |
| AC6 | When the resolved healing switch is `disabled` or `unavailable` at any scope (system → tenant → project), the approval panel shows a banner naming the restrictive scope and every mutating control is disabled; the `unavailable` value is rendered read-only (T33); changing a scope requires `healing:configure` |
| AC7 | Revoking an `approved`/`applied` candidate requires a reason, shows the knowledge-record effect preview (dependent candidates, where the heal applies), and ends with the candidate rendered `revoked` and absent from active-heal lists |
| AC8 | No healing approve/reject control appears on release/policy screens and no release/waiver approval control appears on healing screens; an E2E spec asserts both directions (FR-09-8) |
| AC9 | The lazy feature root `apps/web/src/app/features/healing-review/` (T96) is shared by 09.5.1 (V1) and this story (V2); the repo check that no V1 apply control ships covers that whole root, and the V2 additions — panels, dialogs, routes — introduce no apply control (apply stays a read-only `applied` state render) |

None — no database objects in this web story. Client structure instead (W1/W4):

- Lazy feature `apps/web/src/app/features/healing-review/` (T96 — one root shared by 09.5.1 V1 and this V2 story; created by 09.5.1) gains:
  - `pages/candidate-detail/approval-panel.component.ts` — approve/reject dialogs, hash + base-commit block, expiry, sensitive-case notice, conflict dialog; heavy diff panel stays behind `@defer`.
  - `pages/candidate-detail/knowledge-record-panel.component.ts` — lineage chain, dependent candidates, effect preview, revoke action.

- Routes: `projects/:projectId/healing/candidates/:candidateId` (existing, panel added), `projects/:projectId/healing/settings` (new), each behind a `CanMatchFn` permission guard.
- `HealingReviewStore` (`@ngrx/signals`, extended from 09.5.1): signals `candidate`, `candidateEtag`, `knowledgeRecord`, `switchResolution`, `conflict`, `actionPending`; methods `loadCandidate`, `approve`, `reject`, `revoke`, `loadSwitch`, `setSwitch`. The ETag from the last GET is kept in the store and sent as `If-Match`; server state is never copied into a global store (W4).

## 5. API shapes (commands, queries, endpoints)

Web story — routes, guards and SDK calls (no server endpoints added):

| UI route | Guard (`CanMatchFn`) | Store method → SDK call (endpoint, permission) | Rendered outcomes |
|---|---|---|---|
| `…/healing/candidates/:id` | `healing:triage` | `loadCandidate` → `GET /v1/healing/candidates/{c}`; stores `ETag` | candidate states per §8.7; `proposed`/`validated` offer approve/reject |
| `…/healing/candidates/:id` (approve) | `healing:approve` re-checked in panel | `approve` → `POST /v1/healing/candidates/{c}/approve`, `If-Match`, `Idempotency-Key` | 200 → `approved`; 403 → AC4/AC5; 412 → AC2; 422 → AC3; 429 → `Retry-After` notice |
| `…/healing/candidates/:id` (reject) | `healing:approve` | `reject` → `POST /v1/healing/candidates/{c}/reject` | as above, minus hash binding |
| `…/healing/candidates/:id` (revoke) | `healing:revoke` | `revoke` → `POST /v1/healing/candidates/{c}/revoke` | 200 → `revoked`; effect preview shown before submit |
| `…/healing/settings` | `healing:configure` for PUT, `healing:triage` to view | `loadSwitch`/`setSwitch` → `GET`/`PUT /v1/healing/switch` | resolved scope banner; settable `enabled`/`shadow`/`disabled` only (T33) |

Interceptors (09.1.1, W5) add `X-XSRF-TOKEN` (T38), `X-Request-Id`, and `Idempotency-Key` once per user intent; the 00 §9.2 envelope maps to typed UI errors. Foreign-tenant ids render "not found" (404), never a tenant hint (§5 failure table).

## 6. States and transitions

- Candidate (00 §8.7): `proposed, validated, approved, applied, rejected, insufficient_evidence, expired, revoked` rendered verbatim; UI actions only offer the transitions the server allows: `proposed|validated → approved|rejected`, `approved|applied → revoked`. `expired` candidates show expiry and no actions.
- Switch availability: `enabled | shadow | disabled` settable, `unavailable` derived and rendered read-only (T33); most restrictive scope wins, and the banner names that scope.
- Conflict is a UI-only state entered on 412 (dialog + revision id); it is not a server state and is cleared by reload.

## 7. Jobs and integrations

- None server-side. The client refetches `GET /v1/healing/candidates/{c}` on route enter, after each action, and on visibility regain (bounded poll while `actionPending`); server-side `healing.candidate_changed` webhooks (00 §9.5) are not consumed by the SPA.
- T29 rollout dependency: the server approve route ships behind a flag that defaults off (DECISIONS §5.9); when approve/reject endpoints respond as unavailable the UI renders a "healing approval is not enabled" empty state instead of erroring.
