## 1. Goal and non-goals

**Goal.** The Test Studio surface where a `draft:write` holder creates a case draft from a template, edits intent/assertions/variants with the inline forbidden-change lint, reviews the change as a diff against its base revision with the assertion hash highlighted, runs a bounded dry run, reviews AI-suggested candidates as untrusted text, and submits the draft for merge — with approval by a different person surfaced end-to-end.

**Non-goals.** All server behaviour: template and draft CRUD, `evidgate.id` assignment, the forbidden-change linter, diff and assertion-hash computation, the dry-run executor, the GitHub draft-PR flow and merge (03.2.1, 03.5.1, 03.6.1, 03.7.1); healing approval (09.5.2); catalog browsing outside the studio context (09.x project/catalog screens). The UI never computes diffs, hashes or lint results itself.

## 2. User stories and acceptance criteria

- As a QA engineer, I create a draft from a template and fill the required assertion fields, so a new case starts from a reviewed shape instead of a blank file.
- As a reviewer, I see exactly what changed — diff versus base revision and whether the assertion hash changed — and who approved, so merging a different test than reviewed is impossible.
- As the author, I cannot satisfy the approval alone: the approver identity shown is server-provided and the merge path enforces approver ≠ author.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The gallery lists templates with name, description and required assertion fields; Create issues `POST` create-draft with `Idempotency-Key`; on success the draft editor opens in state `draft`; built-in (platform) templates are labelled and not editable |
| AC2 | The editor shows the server-assigned `evidgate.id`, edits intent/assertion text and variant parameters, and renders the forbidden-change lint inline; save sends `If-Match`; a concurrent edit returns 412 rendered as the conflict dialog with a reload path (no auto-merge) |
| AC3 | The review screen renders the server-provided diff versus the base revision, highlights hunks that change the assertion hash, and shows the hash values plus approver identity verbatim; state gates: actions available only in `draft`/`dry_passed` per server state |
| AC4 | Dry run enters `dry_running` with the action disabled (no double submit), polls the bounded result list, then renders `dry_passed`/`dry_failed`; a failed run shows the pre-healing failure block with original raw status + evidence revision and links to run/attempt artifacts (FR-09-3) |
| AC5 | AI-suggested candidates render labelled as AI-generated, through interpolation/`[innerText]` only; Accept inserts the text as a normal draft edit (author remains the human user); Reject dismisses the item; each accept is an attributed edit |
| AC6 | The suite composition view renders case revision × variant per entry plus shard strategy, and shows DAG/coverage-gap warnings verbatim from the server; the UI computes no coverage itself |
| AC7 | Submit-for-review/merge opens the draft-PR flow (`POST /v1/drafts/{d}/pull-request`, `draft:merge_request`, `Idempotency-Key`); the PR link and status are shown; when the server reports the PR approved, the merge affordance appears with approver name ≠ author; the end state renders `merged` |

## 4. Data model and migrations

None — no database objects in this web story. Client structure instead (W1/W4):

- New lazy feature `features/studio/` (a feature never imports another feature — lint-enforced):
  - `pages/template-gallery/template-gallery.page.ts` — template list, built-in badge, create-draft dialog with required assertion fields.
  - `pages/draft-editor/draft-editor.page.ts` — intent/assertion form, `evidgate.id` read-only chip, variant parameter editor, inline forbidden-change lint markers, save with `If-Match` + conflict dialog.
  - `pages/draft-review/draft-review.page.ts` — `@defer`ed diff viewer vs base revision, assertion-hash highlight + values, approver identity, submit-for-review action.
  - `pages/dry-run-panel.component.ts` — bounded dry-run result list, `dry_running` progress, failure block with evidence links.
  - `pages/ai-suggestions-panel.component.ts` — AI-labelled candidates, accept/reject.
  - `pages/suite-composition.component.ts` — case revision × variant matrix, shard strategy, warning list.
- Routes under `projects/:projectId/studio/` (`templates`, `drafts/:draftId`, `drafts/:draftId/review`), each behind a `CanMatchFn` permission guard.
- `StudioStore` (`@ngrx/signals`): signals `templates`, `draft`, `draftEtag`, `diff`, `dryRuns`, `aiCandidates`, `composition`, `conflict`, `actionPending`; methods `loadTemplates`, `createDraft`, `loadDraft`, `saveDraft`, `loadDiff`, `startDryRun`, `pollDryRuns`, `acceptSuggestion`, `rejectSuggestion`, `loadComposition`, `submitPullRequest`. ETag from the last GET is sent as `If-Match`; no server state duplicated into a global store (W4).

## 6. States and transitions

- Draft (00 §8.10): `draft → dry_running → dry_passed | dry_failed → pr_open → merged | closed`; UI action gating follows the server state verbatim: edit in `draft`/`dry_failed`, dry-run from `draft`/`dry_failed` (re-run allowed), submit for review from `dry_passed` (or `draft` where the server allows), withdraw `pr_open → draft` shown as "PR withdrawn" when the API reports it.
- Suite revision `draft → published`: published revisions are rendered read-only (immutable, 00 §8.10); fixture revisions immutable on create (T46) — no edit affordance.
- Conflict is a UI-only state entered on 412 (dialog + current revision id), cleared by reload; it is not a server state.

## 7. Jobs and integrations

- None server-side. Dry-run progress is polled via `GET /v1/drafts/{d}/dry-runs` (bounded poll while `dry_running`, stop on terminal or route leave — no push channel); the draft-PR status comes back with `loadDraft` refetches.
- Sidecar note for authoring UX only: `evidgate.id` originates in `evidgate.cases.yaml` per T55; the UI only displays the assigned id, never generates one.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.6 W5 + T51/T59 | All calls through `StudioDataService` over the generated SDK; route guards check session permissions; server remains the authority (S2) | AC1/AC7 permission-gated flows; fixture contract tests |
| 00 §9.1 + FR-09-13 | `If-Match` on every draft update; `Idempotency-Key` on create/dry-run/PR; 412 → conflict dialog with reload, never auto-merge | AC2, AC7 |
| T38 / 00 §9.1 CSRF | `withXsrfConfiguration` sends `X-XSRF-TOKEN` on every mutation; 403 `csrf_failed` surfaces as session error | interceptor unit test |
| 00 §5.6 W6 + §6 untrusted content | AI-generated draft text, assertion text and linter messages render via interpolation/`[innerText]` only; no `[innerHTML]`, no `bypassSecurityTrust*` outside the artifact-viewer bridge; AI items carry the AI label (source §8) | AC5 + eslint rule + component test |
| 00 §8.10 integrity | The UI never computes diffs/hashes/lint — all are server values rendered verbatim (FR-09-5 identity headers carry revision + assertion hash) | AC3 |
| T60 | Dry-run and coverage numbers the server does not provide render as "unavailable" with reason, never 0 | component spec |
| 00 §5.6 W7 + NFR-09-1 | `studio` is a lazy chunk ≤ 150 kB gzip; diff viewer behind `@defer`; lists cursor-paginated (00 §9.1), CDK virtual scroll > 200 rows | `angular.json` budgets on the built app |
| 00 §5.6 W8 + T37 | All studio copy keyed in `vi` + `en`; dialogs and editor keyboard-operable; axe-clean | i18n CI check; axe in `studio.spec.ts` |
| Privacy | Dry-run/AI panels show ids and hashes; artifact content stays behind `artifact:read`/`artifact:read_sensitive` links on the isolated viewer origin; telemetry carries ids only | §6 rules; telemetry attribute check |

- **Authorization:** the studio read and write routes are gated by session permissions through route guards (`suite:read` for the suite composition view); the server stays the authority and a 403 renders its own state.
- **Retention/deletion:** the web app keeps no draft, revision or evidence content beyond the page; server retention rules of 03 apply and the UI adds no client-side persistence.
- **Telemetry:** the studio routes emit the 09.1.1-T9 web-vitals and route telemetry with ids only; no suite, member or warning text is sent.
- **Failure path:** 401, 403, 404, 412, 422, 429 and 503 map to typed UI states with a retry or reload action; a server value the API does not provide renders as `unavailable`, never as zero.
