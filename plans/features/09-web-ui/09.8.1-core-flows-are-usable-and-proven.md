## 1. Goal and non-goals

**Goal.** Make the six core flows of FR-09-12 — login, project switch, run detail, failure triage, evidence viewer, onboarding — provably accessible (WCAG 2.2 AA, keyboard-complete, axe-clean) and provably working end to end: a Playwright suite runs green in Evidgate's own CI on every change, and its results are ingested into Evidgate itself (D7, R10), so the product gates on the same evidence format a customer would produce.

**Non-goals.** Accessibility remediation of non-core flows (V2 Test Studio, agents page get their own pass when built); visual-regression review (V3); performance/load testing (plan 10 owns load tests; web budgets stay enforced by `angular.json` from 09.1.1-T1); translating content — the i18n QA here is a coverage/layout review of existing `vi`/`en` strings, not new copy.

## 2. User stories and acceptance criteria

- As a keyboard-only user, I complete login → project switch → open a run → triage a failure → open its evidence without touching a mouse, and focus is never lost or invisible.
- As a screen-reader user, every form error announces itself and every icon-only control has a name.
- As the QA lead, axe runs as part of component tests and E2E; a new violation fails the build, and every accepted exception is a documented, owned entry — not a config-level rule disable.
- As the Tech Lead, the E2E suite's JUnit output flows through the Playwright reporter/CLI into Evidgate's own ingest, so a broken E2E shows up as a FAIL decision on our own project like any customer's.
- As a Vietnamese user, every core-flow screen renders fully in `vi`, including the longest translations, without clipped or concatenated text.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `axe` reports **zero** new violations on the six FR-09-12 flows in `npm run test:e2e:a11y` (Playwright + axe) and `npm run test:a11y` (Vitest + axe on components); the exception list in `e2e/a11y-exceptions.json` is empty or each entry carries rule id, selector, reason, owner, and review-by date — entries without all five fields fail CI |
| AC2 | A scripted keyboard-only walkthrough (Playwright with `page.keyboard` only, no mouse) completes each core flow; focus is visible at every step and never escapes the focused dialog/flow |
| AC3 | The Playwright suite is a blocking CI job (01.7.1's pipeline); a failing spec fails the build; retries are allowed only for infrastructure flakes tagged in the spec, never for product assertions |
| AC4 | A green run publishes results via the Evidgate ingest path (Vitest JUnit → JUnit mapper → manifest + evidence → decision, T48/D7) and produces a PASS decision on the `evidgate-e2e` project; a forced spec failure in a demo branch produces a FAIL decision with the spec named as a failed case |
| AC5 | `npm run i18n:check` fails on a missing `vi` or `en` key (already from 09.1.1-T6); this story adds the layout check: a snapshot review page renders the 20 longest `vi` strings on the core flows at the narrowest supported viewport with no overflow or clipping |

## 7. Jobs and integrations

- **CI integration**: the Playwright job runs on Evidgate's CI on every PR to `develop` and on `main`; sharded (Playwright `--shard` matching the manifest's shard plan so producer slots bind 1:1, T54's `shard-<index>` convention applies to our own ingest too).
- **Dogfooding integration (T3)**: the job ends by invoking `evidgate` CLI: `evidgate run` (manifest from the shard plan) → Playwright emits JUnit per shard → CLI posts events/finalizes → `evidgate gate` exits 0/1/2/3 on the resulting decision (00 §9.3 note). The `evidgate-e2e` project's policy is advisory during the ramp (07 FR-07-15) and switched to enforcing once the suite is stable — a flaky suite must not block its own fix loop.
- **a11y tooling**: axe-core runs (a) in Vitest component tests via `axe()` on the rendered fixture DOM and (b) in Playwright via `@axe-core/playwright` on each core-flow page after navigation — both read the same `a11y-exceptions.json` (AC1).
- Telemetry: each E2E spec carries a `test.title`-level tag for known-infra-flake retries (AC3); the suite's own pass/fail is the Evidgate decision, not CI job colour alone.

| S4-adjacent (test isolation) | Specs run against a seeded fixture tenant; the `evidgate-e2e` ingest writes to its own project only; E2E never runs against a customer tenant | Fixture-seeding script is the only setup path; spec teardown asserts no cross-project rows were touched |

- **Authorization:** T1.1 + T1.2 change only Angular markup, focus handling and specs plus a findings document; no guard, permission, token, session or tenant code is touched, so no authorization change.
- **Retention/deletion:** the findings list `docs/a11y/findings-09.8.1-T1.md` holds file paths and spec names only, no customer data; it is deleted or archived when 09.8.1-T2 closes the exception list.
- **Telemetry:** none added; focus handoff adds no span, event or attribute.
- **Failure path:** a handoff target that is missing leaves focus where the browser put it (no throw, no focus trap); each walkthrough spec fails if focus lands on `body` or escapes the flow.

## 11. Rollout

- The suite is additive: enabling the CI job is the rollout. Ramp order: T3's job starts **non-blocking** for one sprint while the seeded fixture stabilises, then flips to blocking per AC3 (the flip is a one-line pipeline change, explicitly gated by the QA lead).
- The `evidgate-e2e` project's policy starts `advisory` (07 FR-07-15); switching to `enforcing` is a `POST /v1/projects/{p}/policy-activation` by a `release_approver` once the suite has two weeks of green history — a flaky suite must never block the pipeline it measures.
- Monitoring: the dogfooded decision itself is the monitor (a red `evidgate-e2e` decision is the first alert); 10's dashboards can also read the CI job duration trend.
- Rollback: flip the CI job back to non-blocking or disable it; no data or deployed state is affected. Axe/component-test additions are pure checks and roll back by reverting the PR.
