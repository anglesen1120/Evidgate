## 1. Goal and non-goals

**Goal.** Two more Settings tabs, inside the shell 09.7.1-T1 builds: (a) **API tokens**, where a project admin lists project-scoped automation tokens, creates one with a mandatory expiry and a permission subset, sees the secret exactly once, revokes it and reads `last_used_at`; (b) **Deploy targets**, where an admin lists a project's targets (`staging`, `prod`, order, optional pinned policy revision) and reads the promotion-check history per release with each `allowed | blocked | pending` result and its server-given reasons. No screen renders a secret after the creation dialog closes, and no screen computes a promotion verdict.

**Non-goals.** The token model, HMAC/pepper handling, bearer authentication and escalation refusal (02.4.4); the promotion evaluation, `promotion_check` rows and the `evidgate gate` CLI (07.8.1); ingest tokens and CI bindings (09.7.1-T3, 09.2.1-T2); webhook endpoints (09.7.1-T8); release-level decision view (09.3.1-T10, V2). Editing a target's policy pin from the UI beyond what 07.8.1-T1 exposes is `[OPEN]` (CRUD may be read-only in the first cut).

## 2. User stories and acceptance criteria

- As a project admin, I create an API token for a script with a short expiry and only the permissions it needs, copy it once, and later see when it was last used.
- As a project admin, I revoke a leaked token and see it stop being usable immediately.
- As a release manager, I open a target and see which releases were checked against it, the result and why a release was blocked.
- As a member without token or target permissions, I do not see these tabs.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The API tokens tab and the Deploy targets tab are absent from the DOM for a member without the matching read permission; direct navigation renders "not found" (`CanMatchFn` returns `false`, same rule as 09.7.1 AC1) |
| AC2 | The token list shows `name`, `token_prefix`, permission subset, `expires_at`, `state` (`active`/`expired`/`revoked`) and `last_used_at` ("never" when null); no list row, store signal or network body bound to a template contains a full token value |
| AC3 | Create requires an expiry: the submit control stays disabled and the form shows an error until `expires_at` is set within the server's maximum (read from the server error, not hard-coded); the permission picker only offers permissions the caller holds and none of the admin-class permissions (member/role/support/billing); the server's 422 on escalation is rendered verbatim |
| AC4 | After a successful create the secret is shown once in the shared one-time reveal dialog with a copy action and the warning that it cannot be shown again; closing the dialog clears it from memory; reopening the list, reloading the page or navigating back never shows it; it is absent from `localStorage`, `sessionStorage`, router state, URL, telemetry and console output |
| AC5 | Revoke asks for confirmation, sends one `Idempotency-Key` per press, and the row changes to `revoked` from the server response; a double-click produces one request; a 404/409 is shown verbatim |

## 3. Contracts touched

- Consumer only. No new endpoint, schema, migration or permission is introduced by this story.
- **[OPEN] 02.4.4-T1** (not built): `api_token` create/list/revoke API. Assumed shape ⚠️: `GET/POST /v1/projects/{p}/api-tokens`, `DELETE`/`POST …/revoke` on one token, fields `id`, `name`, `token_prefix`, `permissions[]`, `expires_at`, `state`, `last_used_at`, `created_by`, and the secret only in the create response. Exact paths, field names, maximum expiry and the permission string (⚠️ e.g. `api_token:read`/`api_token:write`) are confirmed when 02.4.4 publishes its OpenAPI; until then the screens run against `fixtures/` recordings.
- **[OPEN] 07.8.1-T1/T2/T4** (not built): `deploy_target` CRUD with ETag, `POST/GET /v1/releases/{id}/promotions` history, and the `promotion_check` row shape (`result`, `reasons[]`, decision and policy revision). There is no project-level "all promotions" list in the area plan; if the history must be browsed per target rather than per release, a list endpoint is a contract request to 07 `[OPEN]`, logged via a 00 §15 change request, not invented here.
- **[OPEN]** Whether 02.2.1 seeds a distinct permission for target administration and which roles hold it (⚠️ not verified; the route guards read whatever the server declares).
- Error codes consumed: 00 §9.2 envelope (`validation_failed`, 412, 422, 429); no UI-specific codes.
- SDK: regenerated `@evidgate/sdk` types (D5); no hand-written DTOs (W5).

## 4. Data model and migrations

None (web story). Client structure under `apps/web/src/app/features/settings/` (never imports another feature, W1):

| Path | Contents |
|---|---|
| `.../settings/api-tokens/` | `api-tokens.store.ts` (`@ngrx/signals` `ApiTokensStore`: `tokens` (metadata rows), `cursor`, `createState`, `revokeState`), `api-token-list.component.ts`, `api-token-create-dialog.component.ts`, `permission-picker.component.ts`, `api-tokens.service.ts` |
| `.../settings/deploy-targets/` | `DeployTargetsStore` (`targets`, `selectedTargetId`, `promotions`, `cursor`), `deploy-target-list.component.ts`, `promotion-history.component.ts`, `blocked-reasons.component.ts`, `deploy-targets.service.ts` |
| `.../settings/api-tokens/` routes | `api-tokens.routes.ts`, `deploy-targets.routes.ts` registered by the 09.7.1-T1 settings shell with `CanMatchFn` guards |

All components are standalone, `OnPush`, signal `input()`/`output()`, built-in control flow with `track` (W2); the stores are zoneless-safe, RxJS only at the I/O edge via `rxResource`/`toSignal` (W3/W4). `ApiTokensStore` has **no** field named `token`, `secret`, `value` or `plaintext`; the `no-secret-field-in-store` lint rule from 09.7.1-T1.1 covers these folders and the rule's path list is extended in T1.1 below. The one-time secret lives only in the local state of the shared `ConnectStepRevealComponent` (09.2.1-T2), reused through its input; it is never written to a store.

## 5. API shapes (commands, queries, endpoints)

No new endpoints. Routes, guards and the calls behind each data service:

| Route | Guard (`CanMatchFn`) | Data service → SDK call | Endpoint `[OPEN]` | Permission ⚠️ |
|---|---|---|---|---|
| `/settings/api-tokens` | `hasPermission('api_token:read')`; create/revoke additionally `api_token:write` | `apiTokensService.list/create/revoke` | 02.4.4-T1 create/list/revoke | `api_token:read` / `api_token:write` |
| `/settings/deploy-targets` | `hasPermission('deploy_target:read')`; edits additionally `deploy_target:write` | `deployTargetsService.list/get` (+ `update` with `If-Match` if exposed) | 07.8.1-T1 `deploy_target` CRUD | `deploy_target:read` / `deploy_target:write` |
| `/settings/deploy-targets/:id/promotions` | same as the list | `deployTargetsService.promotions(releaseId?, targetId)` | 07.8.1-T4 `GET /v1/releases/{id}/promotions` | `deploy_target:read` + `decision:read` |

Rules: create and revoke send `Idempotency-Key` generated once per button press and reused on retry of the same intent (FR-09-13, 00 §9.1); target edits send `If-Match` with the last-read ETag and a 412 renders the shared conflict dialog (09.1.1-T8); lists use the URL cursor (`?cursor=&limit=`, default 50, max 200); filters are URL state so links are shareable.

## 6. States and transitions

No new state machine; the UI renders server states read-only.

| Object | States rendered | UI rule |
|---|---|---|
| `api_token` (02.4.4) | `active`, `expired`, `revoked` | `expired` is shown from `expires_at`/server state, never computed from the browser clock alone; revoke is irreversible and shown as such |
| `promotion_check` (07.8.1) | `allowed`, `blocked`, `pending` + `reasons[]` | Direct render; `pending` has its own non-success style; a later check for the same release/target is a new row, never an edit of an old one |
| `deploy_target` | exists with `order` and optional `policy_revision_id` | A pin is shown with its revision hash chip (09.1.1-T7); "no pin" means the active policy, stated in words |
| Create dialog | `idle → submitting → revealed → closed`, `error` | `revealed` is the only state holding the secret, and leaving it (close, route change, session expiry) clears it |

## 7. Jobs and integrations

No background job. The tab data is refetched on route entry and after each mutation; `last_used_at` is whatever the server last wrote (02.4.4 may debounce it, ⚠️ so the UI labels it "last seen at, approximate"). No client polling for promotion history in V1 `[INFERENCE]`; the user refreshes. Telemetry: the 09.1.1-T9 API-error funnel records route and error code with ids only; the create flow emits a `api_token_created` event with project id and no token, name or prefix.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| S3 (secrets never in logs/UI) | Show-once secret held only in the reveal component, cleared on close; no store/field/URL/storage/telemetry/console path; error interceptor strips request bodies so a failed create never echoes the request or response | AC4; Vitest state-shape test and a Playwright check that the secret string appears nowhere in storage, URL or console after close |
| S2 (authz in the pipeline) | Guards are convenience; the server enforces creator-ceiling and refuses admin-class permissions (02.4.4-T2); the picker narrows choices but the 422 is rendered verbatim | AC1, AC3 |
| Untrusted text | Token names, target names and `reasons[]` are bound by interpolation only; no `[innerHTML]`, no `bypassSecurityTrust*` (W6) | lint rule; component test with an HTML-like name asserting it renders as text |
| Tenant isolation | `{p}` comes from the active project switcher; a stale tab from another project never shows rows | E2E project-switch test (09.1.1-T4 contract) |
| Input limits | Name length and expiry bounds mirrored from the server error; promotions list cursor `limit` ≤ 200; no "load all" | AC7, AC3 |
| PDPL/retention | Token `created_by` is a member id shown with the member's display name from membership data; the UI keeps no copy of tokens or their prefixes beyond the loaded page | AC2 |
| Hot-path performance (W7) | Lazy chunk per tab; lists virtual-scrolled past 200 rows; promotion history `@defer` loaded | `angular.json` budget gate |
| Copy action | Uses `navigator.clipboard.writeText` inside the reveal component only, with a visible "copied" confirmation and no fallback that writes the secret to the DOM outside the dialog (⚠️ browser clipboard permission behaviour to verify in T1.2) | AC4 |

DoR review answers. **Authorization:** tab visibility from server-declared permissions; creation limited to the caller's own permissions by the server; no new permission here `[OPEN]` names above. **Retention/deletion impact:** the UI stores nothing durable; revoked tokens stay listed per 02.4.4's retention (⚠️ confirmed there). **Telemetry:** ids-only web telemetry; `api_token_created`/`api_token_revoked` events without values; server-side audit rows (02.4.4-T3) are the audit trail. **Failure path:** 422 escalation, 429, expired session during the reveal (secret cleared, user told to create a new token), network failure after create (the response may have been lost: the UI never retries create with a new key silently, it offers "check the list" and revoke of an unseen token).

## 11. Rollout

- Order: 09.7.1-T1 (settings shell) → T1 (tokens) and T2 (targets) in parallel; both are blocked on their backends (02.4.4-T1, 07.8.1-T2) `[OPEN]` — until then they merge behind the permission guard against `fixtures/` recordings and stay unreachable because the server declares no matching permission.
- No feature flag; the guard is the gate. Milestone M3 with the backend stories.
- Monitoring: 09.1.1-T9 error funnel on these routes (create/revoke failures by code, ids only); no token data in any event.
- Rollback: revert the PR; no server data or migration is touched. A token created through the UI stays valid until its expiry or revoke, so rollback of the UI never affects issued tokens.
