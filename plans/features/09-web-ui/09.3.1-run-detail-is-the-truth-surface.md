## 1. Goal and non-goals

**Goal.** The run list and run detail pages render exactly what the server stored — manifest, release components and build digests, per-producer finalize state, every attempt with raw and normalised status, evidence completeness with `missing[]` reasons, and the stored evaluation — with zero client-side verdict computation (FR-09-1, D3). The release view aggregates components → digests → runs → decisions the same way (V2, T10).

**Non-goals.** Onboarding wizard (09.2.1); failure-inbox triage actions (09.4.1); healing candidate review (09.5.1/09.5.2); policy/waiver authoring screens (09.7.1); admin/settings (09.7.1); any new server endpoint (all reads exist in 00 §9.3, writes in 05).

## 2. User stories and acceptance criteria

- As a QA engineer, I open a run and see exactly what ran (manifest hash, suite/policy revision, environment, build digests) so I can reproduce or dispute it.
- As a release approver, I see the gate verdict with its reasons and the evidence revision it was computed on, knowing the UI cannot have made it up.
- As an engineer, I see why a run is `incomplete` — which producer shard is missing or stale — with a deep link, so I can fix CI instead of re-running blindly.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | On a run with a missing shard and one failed assertion, the page shows collection `incomplete`, decision `FAIL` with the missing-shard reason naming the absent shard, and no element renders `PASS` (Playwright `run-detail-missing-shard.spec.ts`) |
| AC2 | While no evaluation exists, the decision area shows `pending` and the evidence badge shows only collection completeness; screenshot fixture `run-no-evaluation` |
| AC3 | The attempts table shows raw and normalised status side by side for every attempt; a retry fail→pass chain shows both attempts; a `blocked` dependant never renders `passed` (Vitest `attempts-table.spec.ts`) |
| AC4 | The decision view is byte-equivalent to `GET /v1/runs/{r}/decision`: verdict, `reasons[]`, `policy_hash`, `evidence_revision`, `evaluator_version`, `mode` are rendered from the SDK response only — grep-based lint finds no verdict arithmetic in `apps/web` (`scripts/check-no-client-verdict.sh`) |
| AC5 | `POST /v1/runs/{r}/rerun` with `rerun_scope: failed_subset` creates a run labelled `failed_subset` that never counts as full regression; `POST /v1/runs/{r}/reprocess` produces a revision labelled `reprocessed`, never `rerun`; copy and labels differ visibly (E2E) |
| AC6 | Create run sends one `Idempotency-Key` per button intent, reused on retry; cancel sends `POST /v1/runs/{r}/cancel` and shows 202 "cancel recorded" — a terminal `canceled` wins over in-flight `collecting` on next poll |
| AC7 | An active waiver renders the banner "approved by waiver: <approver>, expires <date>" next to the still-failing results; a quarantine chip shows reason and expiry; results are never suppressed (T58) |
| AC8 | Flaky and healed are separate labels: a healed attempt shows the pre-healing failure plus the candidate hash and shadow/official distinction in two blocks (FR-09-3/FR-09-4) |
| AC9 | Run list filters (state, completeness, decision, rerun-scope label) live in the URL and restore on reload; pagination is `?cursor=` keyset, never offset |
| AC10 | Release view (V2) renders the components → digests → runs → decisions matrix from `GET /v1/releases/{id}/decision` and marks stale components when runs predate the recorded digest, with freshness/late-window warnings |

## 3. Contracts touched

- 00 §9.3 endpoints consumed: `GET /v1/projects/{p}/runs` (`run:read`), `GET /v1/runs/{r}` (`run:read`), `GET /v1/runs/{r}/decision` (`decision:read`), `GET /v1/runs/{r}/reports/{report_id}/comparison` (`run:read`), `POST /v1/projects/{p}/runs` (`run:create` + `Idempotency-Key`), `POST /v1/runs/{r}/cancel` (`run:cancel`), `POST /v1/runs/{r}/rerun` (`run:create`), `POST /v1/runs/{r}/reprocess` (`run:create`), `GET /v1/releases/{id}` and `GET /v1/releases/{id}/decision` (`run:read` / `decision:read`), `GET /v1/artifacts/{a}/download-url` (`artifact:read`, `+ artifact:read_sensitive`). No endpoint invented.
- Wire types: generated SDK `@evidgate/sdk` only (FR-09-10, W5); no hand-written DTOs.
- Error codes surfaced: `pending` decision (200 body), 404 for other-tenant runs (rendered "not found"), 409 `idempotency_conflict`, 412 with current revision id in `error.details`, 429 `rate_limited`/`quota_exceeded` with `Retry-After`.
- Immutability observed: manifests, evidence revisions, evaluations are never re-requested for overwrite; the UI keeps the superseded revision viewable (A3).
- Resolved (T66): per-producer slot state (bound, last sequence, finalized, `after_cancel` count) is part of the `GET /v1/runs/{r}` payload — no `/producers` endpoint exists; the UI consumes the slot/finalize fields from the run detail response only (05.3.2).

## 4. Data model and migrations

None — no database objects. Client structure instead (W1/W4):

- `apps/web/src/app/features/runs/` — lazy routes `projects/:projectId/runs` and `projects/:projectId/runs/:runId`; `RunListStore`, `RunDetailStore` (`@ngrx/signals`); `RunDataService` over `@evidgate/sdk`.
- `apps/web/src/app/features/releases/` — lazy route `projects/:projectId/releases/:releaseId`; `ReleaseViewStore`.
- `apps/web/src/app/shared/ui/` additions: `MissingReasonsList`, `ProducerStatusTable`, `AttemptsTable` (retry-chain cell), `WaiverBanner`, `QuarantineChip`, `FlakyBadge`, `HealedBadge`, `ReprocessVsRerunDialog`; reuses `EvidenceBadge`/`DecisionChip` from 09.1.1 (D4).
- Store state: cursor + filter signals synced to the URL; run detail keyed by `(run_id, evidence_revision)`; server state never duplicated into a global store; polling only for non-terminal runs.

## 6. States and transitions

Rendered only (00 §8, no new states): run `created → queued → running → collecting → complete | incomplete | canceled` (a canceled run never becomes complete; `after_cancel` events shown informational, T12); attempt raw + normalised `passed | failed | skipped | timed_out | error | blocked` (blocked never passed); artifact `ready` gate for evidence offers; evidence `complete | incomplete` + `missing[]`; evaluation `pending` until a stored row; candidate chip `proposed | validated | …`; waiver `approved/expired/revoked`, quarantine `active/expired/removed`; subset reruns labelled `failed_subset`.

## 7. Jobs and integrations

- Client polling: `RunDetailStore` polls `GET /v1/runs/{r}` while state is non-terminal (backoff, `traceparent` propagated); polling stops on terminal state, route change or logout (09 §6).
- `run.state_changed` / `evaluation.created` webhooks (00 §9.5) are server→customer events; the UI learns via polling, not push.
- Artifact deep links resolve `GET /v1/artifacts/{a}/download-url` lazily at view time on the isolated viewer origin (FR-09-14); expired-URL refresh retries once.
- Reuses `EvidenceBadge`/`DecisionChip`, SDK and interceptors from 09.1.1; supplies `ProducerStatusTable`, `AttemptsTable` and the evidence-revision selector consumed by 09.4.1-T4 and 09.5.1-T3.

## 11. Rollout

- Order inside the story: T1 → T2 (skeleton) → T3/T4/T5/T6 in parallel → T7/T8/T9 → T10 at M4 after 07.5.3-T1. T10 is V2-gated and must not delay the M2/M3 gates.
- Feature flag: none for reads; the V2 release route is lazy and reachable only when releases exist (data-driven, no flag). Rerun/reprocess controls render only when the API returns them available for the run.
- Monitoring: web-vitals telemetry (09.1.1-T9) on the run list/detail; error surfaces report typed SDK errors with `request_id`.
- Rollback: revert the PR; no data or deployed state is affected.
