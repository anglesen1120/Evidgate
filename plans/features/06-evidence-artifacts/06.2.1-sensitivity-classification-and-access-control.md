## 1. Goal and non-goals

**Goal.** Every artifact kind has a default sensitivity (project-overridable); any path that can return `sensitive` content — read, list, metadata, `download-url` — requires `artifact:read_sensitive` and audits a denial, so a member without the permission can never see or fetch sensitive bytes or their descriptive metadata.

**Non-goals.** The secret scan that can *raise* sensitivity at runtime (06.2.3, `scan_state=pending` also serves as `sensitive`, T19 — this story only wires the enforcement path the scan result flows through); redaction/capture-disable at source (06.2.2); the isolated viewer origin itself (06.3.3, a dependency here only for the audited-issuance endpoint); retention (06.4.x).

## 2. User stories and acceptance criteria

- As a `viewer` role member, I can list and open `normal` artifacts but a `sensitive` one is hidden from me and any attempt to fetch it is denied and logged.
- As a `tenant_admin`, I can override an artifact kind's default sensitivity per project (e.g. force `screenshot` to `sensitive` for a project with regulated data, or lower a default-`sensitive` kind like `trace` to `normal` for a project that needs it, audited either way, T57(a)).

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `GET /v1/artifacts/{a}` for a `sensitive` artifact, called by a principal without `artifact:read_sensitive`, returns metadata with content-bearing fields (`object_key`, `checksum`, download affordance) omitted/redacted, not 403 — only *content* is gated (FR-06-5 "reading… a sensitive artifact requires…") |
| AC2 | `GET /v1/artifacts/{a}/download-url` for the same artifact + principal → 403 `sensitivity_forbidden`, one `audit` row written (actor, artifact, run, request id) |
| AC3 | The same request with `artifact:read_sensitive` → 200 with a short-lived per-view URL on the viewer origin (06.3.3) |
| AC4 | A list query (`GET /v1/projects/{p}/runs` artifact summaries, or any future artifact-list read) never leaks a sensitive artifact's `object_key` to a caller lacking the permission — asserted by a Dapper read-model test, not just the endpoint |
| AC5 | An `artifact_kind_policy` row with `default_sensitivity=sensitive` for `(org, project, screenshot)` makes every new `screenshot` artifact in that project `sensitive`, overriding the kind's global default |
| AC6 | An artifact with `scan_state=pending` is served as `sensitive` regardless of its resolved kind default (T19) — proven by a query that forces `pending` and asserts the read-model marks it sensitive |
| AC7 | Lowering a default-`sensitive` kind (`trace`, `dom_snapshot`, `a11y_snapshot`, `patch`) to `normal` for a project is only possible through `PUT /v1/projects/{p}/artifact-kind-policy/{kind}` (`project:write`); the change writes an `audit` row and never happens by omission (T57(a)) |

## 3. Contracts touched

- 00 §2 — `artifact:read_sensitive` is already listed; this story is the sole enforcement point for it across every artifact-content path (§6 "checked on every path that can return content").
- 00 §9.3 `download-url` row — implemented; `x-permission` composite (`artifact:read` AND `artifact:read_sensitive` for sensitive rows) recorded per T51 (the architecture test asserts the base permission; the conditional escalation is asserted by AC2/AC3 integration tests since `Architecture.Tests` cannot express "permission X unless resource is sensitive").
- 06 §4 `artifact_kind_policy.default_sensitivity` — read here; the write endpoint for per-kind overrides is this story's `PUT /v1/projects/{p}/artifact-kind-policy/{kind}` (`project:write`, audited). TL ruling T57(a) (README §3) accepts this endpoint as the sole path to lower a default-`sensitive` kind to `normal`, closing 06-O4 and the area plan's silence on an override endpoint.

## 4. Data model and migrations

No new table (`artifact`, `artifact_kind_policy` already exist from 06.1.1-T1). This story adds:

- A resolver: `ResolveDefaultSensitivity(org, project, kind)` — reads `artifact_kind_policy` by `(org_id, project_id, kind)`; falls back to a static in-code kind→sensitivity map per TL ruling T57(a) (06-O4 resolved: yes): `trace`, `dom_snapshot`, `a11y_snapshot`, `patch` → `sensitive`; `video`, `screenshot`, `raw_report`, `ui_hierarchy` → `normal`; when no policy row exists. Lowering a default-`sensitive` kind to `normal` is only possible via the override endpoint (AC7), audited, never by omission.
- Migration `migrations/NNNN_evidence_artifact_kind_policy_endpoint.sql`: no schema change — adds a partial index to serve the new endpoint's read: `create index artifact_kind_policy_lookup_idx on artifact_kind_policy (org_id, project_id, kind);` (already implied by the `unique (org_id, project_id, kind)` constraint from 06.1.1, so this migration is a no-op placeholder unless the constraint is missing — confirmed present, migration file is dropped from scope after re-check; see §10 re-estimate note).

## 5. API shapes (commands, queries, endpoints)

| Endpoint | Command / Query | Notes |
|---|---|---|
| `GET /v1/artifacts/{a}` | `GetArtifactMetadata : IQuery<Result<ArtifactMetadataView>>` | `artifact:read`. Dapper read-only tx. Response omits `object_key`/`checksum`/`bytes` when `sensitivity=sensitive` and the caller lacks `artifact:read_sensitive`; a `content_gated: true` flag is set instead |
| `GET /v1/artifacts/{a}/download-url` | `IssueArtifactDownloadUrl : ICommand<Result<DownloadUrlResponse>>` | `artifact:read` + `artifact:read_sensitive` when sensitive. Modeled as a command (not a query) because it writes an `audit` row on both grant and denial (C1: anything that writes is a command) |
| `PUT /v1/projects/{p}/artifact-kind-policy/{kind}` | `SetArtifactKindPolicyOverride : ICommand<Result<Unit>>` | `project:write` (`tenant_admin`, T21). Upserts `default_sensitivity`/`max_bytes`/`media_types`/`capture_enabled`/`reject_on_secret` for `(org, project, kind)` |
| — | `ResolveDefaultSensitivity` | pure resolver used by `CreateArtifactRecord` (06.1.1) at mint time and by this story's read paths |

Errors: `sensitivity_forbidden` 403 (audited), `artifact_not_found` 404 (cross-tenant or missing), `kind_unknown` 422 (policy override with an out-of-list kind).

## 6. States and transitions

None new. `sensitivity` is set at mint (06.1.1, using this story's resolver) and can only be *raised* by the scan (06.2.3, T19); this story does not add a transition, only read-time gating plus the write-time resolver.

## 7. Jobs and integrations

- Consumed by 09 (UI gating, `content_gated` flag drives a "request access" affordance) and 06.3.3 (the download-url's viewer-origin URL is only issued after this story's check passes).
- Audit rows go through 02's `audit` core (`02.7.1-T1`/`T2`, referenced by the area plan §10; not a new dependency here since the story already depends on `02.2.1`).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-06-5 | `artifact:read_sensitive` required for read/list/download-url content; enforced identically at all three paths via one shared resolver + guard, not duplicated per-endpoint logic | AC1, AC2, AC4 |
| S2 | authorization in the C2 pipeline for the base permission (`artifact:read`); the sensitivity escalation is a second explicit in-handler check (necessary since it is data-dependent, not route-dependent) — both are asserted, never trusted to the endpoint | AC2/AC3 integration tests |
| Audit (00 §6, source §8) | every denial and every grant of sensitive content writes an `audit` row with actor/artifact/run/request id | AC2 |
| T21 | `project:read` (all roles) / `project:write` (`tenant_admin`) on the new policy-override endpoint | `Architecture.Tests` permission assertion |
| T57(a) | `trace`, `dom_snapshot`, `a11y_snapshot`, `patch` default `sensitive`; lowering to `normal` only via the audited override endpoint, never by omission | AC7 |
| Tenant isolation | resolver and both queries scoped by `org_id` inside the tenant transaction; cross-tenant artifact id → 404 | integration test `GetArtifact_CrossTenant_404` |
| P3 | metadata/download-url reads are single-statement Dapper queries; no N+1 across the sensitivity + policy lookup (one join) | command-counter test |
| PDPL | sensitivity gating is the technical control backing the DPA's "controller-approved access" clause (06 §6) | — |
| Retention/deletion impact | none directly; sensitivity does not change retention timing (06.4.1 owns that) | — |

## 11. Rollout

- No feature flag: sensitivity gating is correctness, not optional behavior — it ships enabled from the first artifact.
- Monitoring: `sensitivity_forbidden` 403 rate is worth a dashboard row once 10's metrics catalogue exists; audit-row volume feeds 11's security-event review.
- Rollback: revert the endpoints/resolver; existing `artifact.sensitivity` values are unaffected since they were already written correctly by 06.1.1's fallback (`normal`) — a rollback only removes the override capability and re-tightens list gating to "not implemented" (fail-closed is preserved because `artifact:read_sensitive` checks predate this story in the 00 §2 catalogue).
