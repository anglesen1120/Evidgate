## 1. Goal and non-goals

**Goal.** `ui_hierarchy` (native view-tree dump) — the one kind 00 §7 actually tags "(V2 mobile)" — gets its first `media_types`/`max_bytes` default entry (extending 06.1.2-T3.1's static per-kind defaults mechanism; its `default_sensitivity` is already resolved to `normal` by 06.2.1-T1's `ResolveDefaultSensitivity`, no change needed there). `video` (device screen recording) and `a11y_snapshot` (accessibility tree dump) are already-defined V1 kinds with existing defaults from 06.1.2-T3.1/06.2.1-T1 — this story's job for them is *serving*, not defaults: `video` gets HTTP range-request streaming in the viewer, and `a11y_snapshot`/`ui_hierarchy` get tree-rendering serving through 06.3.1's parser profile. All three render in the existing isolated viewer (06.3.3/06.3.4) without a new registrable origin.

**Non-goals.** Mobile adapter/reporter capture itself (04.5.1, a dependency); the mobile run/orchestration side (05.7.4, a dependency); a new viewer origin (reuses 06.3.3 unchanged — though per-kind CSP/sandbox header rows, the pattern 06.3.4 already established for `raw_report`/`trace`, are in scope if `video`/tree-dump serving needs them); redaction rules specific to mobile capture (06.2.2 covers redaction generically); redefining `video`'s or `a11y_snapshot`'s `default_sensitivity` (06.2.1-T1 already owns and has resolved both); resolving 06-O3 (`video`'s exact size ceiling remains an open owner decision this story consumes, not closes).

## 2. User stories and acceptance criteria

- As a mobile QA engineer, I want to scrub through a device-screen recording and inspect the view hierarchy at the point of failure, in the same viewer used for web traces, so mobile debugging needs no new tool.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The static per-kind defaults mechanism (06.1.2-T3.1) gets a new `ui_hierarchy` entry (`media_types = [application/xml, application/json]`, `max_bytes` sized for a tree dump); `06.2.1-T1`'s `ResolveDefaultSensitivity` already maps `ui_hierarchy → normal` and needs no change (confirmed against 06.2.1's static map: `trace`, `dom_snapshot`, `a11y_snapshot`, `patch` → `sensitive`; `video`, `screenshot`, `raw_report`, `ui_hierarchy` → `normal`). `video` and `a11y_snapshot` already have both a `media_types`/`max_bytes` default (06.1.2-T3.1) and a sensitivity default (06.2.1-T1); this story reads, does not redefine, those |
| AC2 | A `ready` `video` artifact opened on the viewer origin responds to `Range` requests (`Accept-Ranges: bytes`, `206 Partial Content`) so the player can seek without downloading the whole file |
| AC3 | A `ready` `ui_hierarchy` or `a11y_snapshot` artifact is parsed through `IParsing` (06.3.1 profile: depth/size caps, no external entity resolution for the XML variant) and rendered as a collapsible tree in the viewer; a hostile/oversized dump is rejected the same way any other kind is at `complete` |
| AC4 | No new registrable origin is introduced; all three kinds render through the existing 06.3.3 origin. `video` and the tree-dump kinds may still need their own per-kind CSP/sandbox header row on top of 06.3.3's baseline — following the override pattern 06.3.4 already established for `raw_report`/`trace` — evaluated here rather than assumed to need none |

## 3. Contracts touched

- 00 §7 artifact `kind` list — `ui_hierarchy` is the only kind of the three actually new/"(V2 mobile)"; `video` and `a11y_snapshot` are existing V1 kinds this story serves for the first time in a mobile context, not defines.
- FR-06-9 — extended to these kinds' rendering, not changed in shape.
- No new endpoint, permission, or table: `ui_hierarchy`'s `media_types`/`max_bytes` default is added to 06.1.2-T3.1's existing static-defaults mechanism (a code-level per-kind fallback, not a migration — `artifact_kind_policy` is `org_id`/`project_id`-scoped with no platform-default row concept, 06 §4). `ResolveDefaultSensitivity` (06.2.1-T1) needs no change, since its static map already lists `ui_hierarchy → normal`.

## 4. Data model and migrations

No new table, no migration. `ui_hierarchy`'s `media_types`/`max_bytes` entry is added to whatever code-level static defaults 06.1.2-T3.1 established (per that story's own task: "Static per-kind defaults (media types + `max_bytes`) seeded as `artifact_kind_policy` fallback when no project row exists") — this story extends that same fallback table with one more row, for the one kind it did not yet cover at M2 (V1). No change is made to `ResolveDefaultSensitivity`'s map (06.2.1-T1), which already resolves all eight closed-list kinds including `ui_hierarchy`.

**Notes (from 06.1.2-T3, S46):** T1.1's `ui_hierarchy` default is NOT supplied by DECISIONS §8.1 D-A9 — D-A9 caps only `screenshot`, `log`, `trace`, `html_report`, `video` and `raw_report` (`DECISIONS.md:167`), and `log`/`html_report` themselves are unmapped/folded (06.1.2 plan §10 T3 Notes item 2). The owner must therefore decide `ui_hierarchy`'s `max_bytes` and `media_types` before T1.1 writes the entry (open owner decision D-S46-Q1, recorded in the 06.1.2 plan §10 T3 Notes item 3 and STATUS.md §6). AC1's provisional `media_types = [application/xml, application/json]` is a proposal, not a decided default; it does pass the hard rule that a default media type must be one `MediaSniffer.HasSignature` accepts (06.3.1-T2.2 — the XML family is `application/xml`/`text/xml`/`application/*+xml`, the JSON family `application/json`/`application/*+json`). Until the owner decides, a `ui_hierarchy` upload with no project policy row stays 422 `kind_disabled` (`contracts/evidence/artifact-kind-defaults.v1.json` `no_default`). `video` is unaffected (its 200 MiB / `video/mp4` default lands with 06.1.2-T3), and `a11y_snapshot` stays in `no_default`.
