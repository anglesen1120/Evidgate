## 1. Goal and non-goals

**Goal.** A tenant- or project-scoped deletion removes all evidence — objects, artifact rows, metadata, masking events, usage pointers — within the published period, produces a per-item deletion report, and leaves storage provably empty for the target. It is the only path allowed to delete evidence outside retention (FR-06-13). The deletion mechanics (T1) are separate from the operator-facing entry point and its guards (T3): T1 is the job that does the work once queued; T3 is how, and under what controls, it gets queued.

**Non-goals.** Non-evidence tenant data (memberships, catalog, runs metadata — orchestrated by 02/10's tenant-deletion flow); backup restore mechanics (10.5.1 supplies coverage evidence); retention (06.4.2); healing-record internals (T2 calls 08.7.1's contract, it does not implement it); the `support_grant` model itself (02.8.1-T1 owns request/approve/revoke/expiry — T3 only consumes an approved grant).

## 2. User stories and acceptance criteria

- As a platform operator with an approved support grant confirmed by the target org's `tenant_admin`, I trigger tenant or project deletion once and get a job I can watch to completion.
- As a departing customer, I receive a deletion report listing what was removed and proof that nothing remains within the published period (PDPL erasure, DECISIONS §7), and I see the deletion in my own audit/notice feed before it starts.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `POST /internal/operator/orgs/{o}/deletion` (org-scoped) and `POST /internal/operator/orgs/{o}/projects/{p}/deletion` (project-scoped) → 202 + `deletion_job` id, only when the caller holds an `approved` `support_grant` (02.8.1-T1) scoped to `tenant_deletion`/`project_deletion` for that target, passed as `confirmation_token = grant_id`; missing/unapproved/expired/wrong-scope grant → 403 `support_grant_required`; route absent from the public ingress and from `contracts/openapi.yaml`; unauthenticated → 401 |
| AC2 | While a `deletion_job` (`scope in ('tenant','project')`) targeting an org or one of its projects is not `done`, new `upload-url` calls for that scope return 409 `tenant_deleting`; in-flight uploads may finish but are deleted with the rest |
| AC3 | On completion: every object under the target's key prefix is absent (verified by listing), all `artifact`, `masking_event`, `artifact_kind_policy`, `retention_policy` and `storage_usage_daily` rows in scope are gone, and `deletion_job.state='done'` with a report (`counts per class`, `bytes`, `object_key` list persisted) |
| AC4 | An object-store failure mid-job leaves `state='running'` with `last_error`; retry resumes from where it stopped (objects already gone are skipped); after the attempt cap → `dead_letter` task + `state='failed'` |
| AC5 | A second `POST` for the same target returns the existing job (200) — `unique (org_id, scope, target_id)` |
| AC6 | The backup-coverage step queries 10.5.1's register before reporting: the report names the snapshots containing the target's data and their expiry dates; a backup horizon beyond the published period is surfaced in the report, not hidden |
| AC7 | (T2, V2) Deletion also invokes `IHealingTenantErasure.EraseAsync(orgId)` (08.7.1-T1); knowledge records and candidate context for the org are gone and the report includes their counts |
| AC8 | (T3) A project-scoped deletion (`scope='project'`) removes only that project's evidence and leaves sibling projects in the same org untouched; the target org's `tenant_admin`s and the requesting operator both receive an audited, tenant-visible notice when the job starts and when it completes |

## 4. Data model and migrations

`migrations/NNNN_evidence_tenant_deletion.sql` (DbUp; placeholder number):

- `alter table deletion_job add column report jsonb, add column started_at timestamptz, add column confirmation_grant_id uuid;` — plain `ADD COLUMN` (no `CHECK`-expression change needed here since `deletion_job.scope` already accepts `'project'` from 06.4.2-T1.1's migration).
- Composite FK `(org_id, confirmation_grant_id)` → `support_grant (org_id, id)` (02.8.1-T1's table), nullable until T3 populates it.
- `organization`/`project` (02's tables) get no deleting marker **via this plan** — the `upload-url` guard checks `deletion_job` existence (`scope in ('tenant','project')` + matching `target_id` + `state != 'done'`), already in 06's schema; a first-class `deleting` flag for the wider cutover — if 02 wants one — is for the orchestrator plan, not this one.
- No other new tables: the report lives on `deletion_job.report` (jsonb, append-frozen on `done`).

## 5. API shapes (commands, queries, endpoints)

| Endpoint | Permission | Behaviour |
|---|---|---|
| `POST /internal/operator/orgs/{o}/deletion` | `platform_operator` + `approved` `support_grant` (scope `tenant_deletion`) as `confirmation_token` (00 §9.1, T16) | 202 `{deletion_job_id}` on first call, 200 same body on repeat; 403 `support_grant_required` if the grant is missing/unapproved/expired/wrong-scope; creates `deletion_job(scope='tenant', target_id=org_id)` + `tenant.delete` task in one transaction |
| `POST /internal/operator/orgs/{o}/projects/{p}/deletion` | same, grant scope `project_deletion` | identical shape with `deletion_job(scope='project', target_id=project_id)` + `tenant.delete` task carrying the project scope |

Command `QueueTenantDeletion(orgId, projectId?, confirmationGrantId)` (`ICommand<DeletionJobResult>`) — validates the grant (state, scope, expiry, target match) before creating the job row; runs through the C2 pipeline minus the tenant behaviour (the operator ingress principal carries no tenant; the command executes under the audited operator role, T11 precedent, 00 §5.4.3).

Internal task `tenant.delete` `{ org_id, project_id?, job_id }` — natural idempotency key `tenantdelete:<org>[:<project>]`; the handler (T1) does all per-target work inside `ITenantScope.BeginAsync(org_id)` per C3.

Query `GetDeletionJob(jobId)` (`IQuery<DeletionJobStatus>`) — operator-only status read for the report download in 11.9.1's audit pack; read-only tx (C1).

## 6. States and transitions

`deletion_job` (scope `tenant`/`project`): `queued → running → done | failed`; `failed` may be re-queued by an operator replay (a new `tenant.delete` task; the job row itself is terminal-`failed` for audit, replay creates a `task` retry).

`artifact` rows under deletion reuse the 06.4.2 pipeline: `ready → pending_delete → deleted`, then rows are hard-deleted. Blocking guard: upload-url refuses while the matching job is active (AC2).

## 7. Jobs and integrations

- `tenant.delete` handler steps (T1): mark `running` → `UPDATE artifact SET state='pending_delete'` for all non-deleted rows in scope (org-wide or one project) → run the 06.4.2 delete+verify loop over the scoped prefix (bounded batches) → list-and-delete residual `pending/` objects in scope → verify listing empty → hard-delete scoped artifact-side rows → call `10.5.1` backup register + (T2) `IHealingTenantErasure` when scope is `tenant` → write `deletion_job.report` + `done`.
- Backup integration (10.5.1-T1/T2): read-only query of the snapshot register; no deletion of backups here — the report records snapshot names + expiry so 11.9.1 can prove the published period end-to-end.
- Operator route + guard integration (T3): reads `support_grant` (02.8.1-T1) to validate the confirmation token; writes an audited notice (`tenant.deletion_requested`, `tenant.deletion_completed`) visible to the target org's `tenant_admin`s via the existing audit feed; the `upload-url` guard is one indexed read against `deletion_job`.
- Metrics: `evidgate_tenant_delete_jobs_total{result,scope}`, `evidgate_tenant_delete_duration_seconds`, `evidgate_tenant_delete_objects_removed_total`.
- Alerting handoff: `dead_letter` `tenant.delete` task pages the operator (00 §5.3 dead-letter visibility; wiring in 10).

## 11. Rollout

- T3's routes are manual/operator-triggered only; no schedule. First real invocation is a rehearsal on the dogfood org before any pilot offboarding (links to 10's restore/deletion drill).
- Monitoring: `deletion_job` stuck in `running` > 1 h and any `dead_letter` `tenant.delete` alert the on-call; report retained as an internal record (it is org-scoped metadata, not tenant data).
- Rollback: a `running` job can be paused by dead-lettering its task; partial deletion cannot be un-deleted — the two-key control (operator role + tenant-admin-approved grant, T3) is the guard, not a rollback path.
