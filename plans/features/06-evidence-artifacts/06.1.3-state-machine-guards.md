## 1. Goal and non-goals

**Goal.** Every transition on an `artifact` row is checked against the 00 §8.4 state machine both in the domain type (no setters, C6) and in SQL (a trigger denies an illegal `UPDATE` for the app role), so `rejected` and `ready` are terminal for their branches and an illegal transition returns 409 instead of silently overwriting a row.

**Non-goals.** The transitions themselves (already implemented by 06.1.2's `complete` and by 06.4.x's retention/sweeper jobs, which are the only other writers); sensitivity/scan-state changes (orthogonal to `state`, not covered by this guard, per 06 §4).

## 2. User stories and acceptance criteria

- As the Tech Lead, I know a bug or a replayed request can never move a `rejected` or `ready` artifact backward, so evidence integrity holds even under handler mistakes.
- As an on-call engineer, an illegal transition attempt fails loudly (409) instead of silently corrupting the row, so it shows up in monitoring immediately.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An attempt to move a `rejected` artifact to `ready` (or any other state) is rejected: the domain method throws `InvalidOperationException` in-process and, independently, the SQL trigger raises an exception if attempted by raw `UPDATE`, leaving the row unchanged |
| AC2 | An attempt to move a `ready` artifact back to `pending_upload`/`uploaded` fails the same way; only `ready → pending_delete` (retention, 06.4.2) and `ready → rejected` (a parse verdict, 06.3.6, recorded in 00 §8.4 and §15) are legal |
| AC3 | Every edge in the 00 §8.4 table is covered by a positive test (allowed) and every non-edge from the same source state has a negative test (blocked) |
| AC4 | The mapped endpoint-level error for a blocked transition triggered through a public command (e.g. a duplicate/late `complete` call racing a sweeper `rejected`) is 409 `artifact_state_conflict` (00 §9.2), not 500 |
| AC5 | The SQL trigger denies the illegal `UPDATE` even when issued by the app role directly (bypassing the C# domain layer), proving the guard is not solely an application-layer discipline |

## 4. Data model and migrations

Migration `migrations/0095_evidence_artifact_state_guard.sql` (shipped as an explicit edge allow-list, which is the §6 matrix; the sketch below is the deny-list form) adds a trigger to the existing `artifact` table (created by 06.1.1-T1); no new table.

```sql
create function evidgate.artifact_guard_transition() returns trigger as $$
begin
  if old.state = 'rejected' or (old.state = 'ready' and new.state not in ('ready','rejected','pending_delete')) then
    raise exception 'artifact_illegal_transition: % -> %', old.state, new.state
      using errcode = '23514';
  end if;
  if old.state = 'pending_delete' and new.state not in ('pending_delete','deleted') then
    raise exception 'artifact_illegal_transition: % -> %', old.state, new.state
      using errcode = '23514';
  end if;
  if old.state = 'deleted' and new.state <> 'deleted' then
    raise exception 'artifact_illegal_transition: % -> %', old.state, new.state
      using errcode = '23514';
  end if;
  return new;
end;
$$ language plpgsql;

create trigger artifact_guard_transition_trg
  before update of state on artifact
  for each row
  when (old.state is distinct from new.state)
  execute function evidgate.artifact_guard_transition();
```

The function runs as the migration-owner role (`SECURITY DEFINER` not needed — it only raises, never bypasses RLS) so the app role cannot `ALTER`/`DROP` it (00 §5.4.3 "no `BYPASSRLS`").

## 5. API shapes (commands, queries, endpoints)

No new endpoint. The guard is exercised transitively by existing commands:

| Command (owner story) | Guard interaction |
|---|---|
| `CompleteArtifactUpload` (06.1.2) | catches the Postgres `23514` from the trigger and maps it to `Result.Conflict("artifact_state_conflict")`, surfaced as 409 by the C8 endpoint filter |
| Retention job handler (06.4.2, not yet built) | relies on the same trigger for `ready → pending_delete → deleted` |
| Sweeper handler (06.4.3, not yet built) | relies on the same trigger to refuse re-marking a `ready` row `rejected` |

Domain-layer guard: `Artifact.TransitionTo(ArtifactState next)` in the EF Core entity throws `InvalidOperationException` for the same illegal edges *before* the SQL statement is even sent, so the common path never reaches the trigger; the trigger is the defense-in-depth layer for AC5.

## 6. States and transitions

Guard matrix (00 §8.4 is the source; this table is the complete allow-list enforced by both layers):

| From | Allowed to | Blocked (examples) |
|---|---|---|
| `pending_upload` | `uploaded`, `ready`, `rejected` | `pending_delete`, `deleted` |
| `uploaded` | `ready`, `rejected` | `pending_upload`, `pending_delete`, `deleted` |
| `ready` | `ready` (idempotent no-op), `rejected` (parse verdict only), `pending_delete` | `pending_upload`, `uploaded` |
| `rejected` | `rejected` (idempotent no-op) | every other state — terminal |
| `pending_delete` | `pending_delete`, `deleted` | every state before `ready` |
| `deleted` | `deleted` (idempotent no-op) | every other state — terminal |

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| C6 domain invariants | state machine enforced in the C# aggregate (no setters) and in SQL (trigger, `REVOKE`-equivalent via exception) | AC1, AC2, AC5 |
| 00 §5.4.3 no `BYPASSRLS` | guard trigger runs under the same RLS-forced table; it adds a constraint, not a privilege escape | migration review |
| S1 | trigger body has no dynamic SQL, no string-built statements | code review |
| P5 | guard check is in-transaction, in-database, zero network calls | trigger definition |
| 00 §9.2 | illegal transition surfaces as 409 `artifact_state_conflict`, never 500 | AC4 |
| Authz | none added — the guard applies regardless of caller permission, closing the "commands with the right permission but a stale/racing view of state" gap | AC4 replay test |

## 11. Rollout

- No feature flag: the trigger is additive protection with no user-visible behavior change on the happy path.
- Monitoring: a spike in `artifact_state_conflict` responses (00 §11 operational SLIs) signals a racing-writer bug and is worth its own alert once 10's metrics catalogue exists.
- Rollback: drop the trigger and revert the domain guard; no data migration needed since the guard only ever blocks writes, never transforms data.
