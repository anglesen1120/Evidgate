## 1. Goal and non-goals

**Goal.** A project can view and set its artifact and metadata retention days within a bounded range via `GET/PUT /v1/projects/{p}/retention`; a project with no explicit row uses the platform defaults (14 days artifacts, 90 days metadata); the stored value is exactly what 06.4.2's deletion job later enforces.

**Non-goals.** The deletion job itself that acts on the policy (06.4.2, blocked by this story); the sweeper (06.4.3); tenant-wide deletion (06.4.4); publishing the defaults to customers as a contractual commitment (11.8.1, blocked by this story, consumes the value this story stores); **setting the actual floor/ceiling numbers** — flagged `[OPEN] owner` (the 14 d/90 d defaults themselves are Resolved (RECOMMENDATIONS 06-O1)); this story implements them as configurable values, not values it invents.

## 2. User stories and acceptance criteria

- As a tenant admin, I want to raise my project's retention window within the allowed range, so evidence needed for a longer audit cycle is not deleted early.
- As the Tech Lead, I want a floor and a ceiling enforced server-side, so no project can set a window too short for compliance/decision-integrity, nor unboundedly long (defeating "deleted on a date we can prove", 06 §1, and the storage cost model).

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `GET /v1/projects/{p}/retention` with `project:read` returns `{artifact_days, metadata_days}`; for a project with no row, it returns the platform defaults (14, 90) without creating a row |
| AC2 | `PUT /v1/projects/{p}/retention` with `project:write` (`tenant_admin`, T21) upserts `retention_policy` for `(org_id, project_id)`; a value outside the configured range (below `RetentionLimits.MinArtifactDays`/`MinMetadataDays`, above `RetentionLimits.MaxArtifactDays`/`MaxMetadataDays`, or `metadata_days < artifact_days`) returns 422 `retention_out_of_range` (details: which field), and no row is written. **`[OPEN] owner`** the concrete numbers for `RetentionLimits` are not set anywhere in 00/06 — 06-O1 confirms only the 14/90 *defaults* — so this story ships them as named, owner-configurable constants (conservative placeholders until Tech Lead confirmation) rather than inventing a number |
| AC3 | `PUT` without `project:write` (e.g. a `member` role) returns 403 |
| AC4 | Two concurrent `PUT`s upsert without a duplicate-row error (`UNIQUE (org_id, project_id)` + a parameterised `INSERT … ON CONFLICT DO UPDATE`), and the last committed write wins |
| AC5 | Cross-tenant project id on either verb returns 404, never 403 or another tenant's policy |

## 4. Data model and migrations

`migrations/0NNN_evidence_retention_policy.sql`:

```sql
CREATE TABLE evidgate.retention_policy (
    id             uuid PRIMARY KEY,
    org_id         uuid NOT NULL,
    project_id     uuid NOT NULL,
    artifact_days  int  NOT NULL,
    metadata_days  int  NOT NULL,
    created_at     timestamptz NOT NULL DEFAULT now(),
    updated_at     timestamptz NOT NULL DEFAULT now(),
    version        int  NOT NULL DEFAULT 0,
    CONSTRAINT uq_retention_policy_org_id UNIQUE (org_id, id),
    CONSTRAINT uq_retention_policy_org_project UNIQUE (org_id, project_id),
    CONSTRAINT fk_retention_policy_project FOREIGN KEY (org_id, project_id)
        REFERENCES evidgate.project (org_id, id),
    CONSTRAINT ck_retention_policy_sane CHECK (artifact_days > 0 AND metadata_days >= artifact_days)
);
ALTER TABLE evidgate.retention_policy FORCE ROW LEVEL SECURITY;
CREATE POLICY retention_policy_tenant_isolation ON evidgate.retention_policy
    USING (org_id = evidgate.current_org_id());
```

- Columns are the area plan's `retention_policy` row (06 §4) plus `created_at`/`version`, which 00 §7's DB naming contract requires on every table and which wins over the area plan's shorter "key columns" cell (README §0 authority order). `version` exists per that contract but AC4 deliberately does not expose `If-Match`/conditional-write semantics on it (see §5) — it is present for the naming contract and available to a future story, not exercised by any acceptance criterion here.
- `UNIQUE (org_id, id)` (T3) for composite-FK targeting; `UNIQUE (org_id, project_id)` is the upsert key (AC4).
- `ck_retention_policy_sane` is a loose DB-level sanity invariant only (positive artifact window, metadata window at least as long as the artifact window) — it is **not** the compliance floor/ceiling from AC2. The actual business `RetentionLimits` (floor + ceiling, `[OPEN] owner`) live in application configuration (`SetRetentionPolicyCommand`'s FluentValidation), not as a hardcoded SQL literal, so the owner can tighten or loosen them without a migration once 06-O1's sibling decision closes.
- No index beyond the two unique constraints is needed: the only read path is by `(org_id, project_id)`, already covered.
- RLS policy uses `evidgate.current_org_id()` per T2, never raw `current_setting`.

## 5. API shapes (commands, queries, endpoints)

| Operation | Kind | Endpoint | Permission | Status / error codes |
|---|---|---|---|---|
| `GetRetentionPolicyQuery` | `IQuery<T>` (Dapper, read-only tx) | `GET /v1/projects/{p}/retention` | `project:read` | 200 `{artifact_days, metadata_days}` (row value or platform default if absent); 404 cross-tenant/unknown project |
| `SetRetentionPolicyCommand` | `ICommand<T>` (EF Core write, upsert) | `PUT /v1/projects/{p}/retention` | `project:write` (`tenant_admin`) | 200 `{artifact_days, metadata_days}` on success; 422 `retention_out_of_range` (details: which field, and against which `RetentionLimits` bound) when a value is outside the configured range; 403 forbidden; 404 cross-tenant/unknown project |

- `SetRetentionPolicyCommand` runs through the standard CQRS pipeline (C2): telemetry → validation (FluentValidation checks against `RetentionLimits`, `[OPEN] owner` values, before the handler; the SQL `ck_retention_policy_sane` CHECK is a second, looser fence) → tenant tx → authorization (`project:write`) → idempotency (not required — `PUT` is naturally idempotent, no `Idempotency-Key` needed per 00 §9.1's idempotency being for side-effecting non-idempotent operations) → handler (parameterised raw SQL `INSERT (id, org_id, project_id, artifact_days, metadata_days, created_at, updated_at, version) VALUES (@id, @org_id, @project_id, @artifact_days, @metadata_days, now(), now(), 0) ON CONFLICT (org_id, project_id) DO UPDATE SET artifact_days = excluded.artifact_days, metadata_days = excluded.metadata_days, updated_at = now(), version = retention_policy.version + 1`, executed via `DbContext.Database.ExecuteSqlInterpolated` inside the EF Core `DbContext`'s tenant-scoped connection/transaction — LINQ has no native upsert, so this is the standard EF Core pattern for one, still parameterised per S1) → outbox flush (none needed, no downstream event) → commit.
- No `If-Match`/conditional write: `version` is carried per the DB naming contract (§4) and bumped on every upsert, but this story does not expose it on the API — AC4's "last committed write wins" is the intended concurrency behaviour for a project settings row with no observed multi-writer contention risk; `version` remains available for a future conditional `PUT` (`If-Match` → 412, 00 §9.2) without a migration.
## 6. States and transitions

None. `retention_policy` has no state machine; it is a single mutable settings row per project (upsert, no lifecycle).

## 7. Jobs and integrations

- No outbox row, no task, no webhook: setting the policy is a pure settings write with no downstream async effect from this story.
- Consumed by 06.4.2 (deletion job reads `artifact_days`/`metadata_days` to compute what is due) and 11.8.1 (published customer-facing retention commitment cites the same value) — both are blocked on this story, neither is built here.

## 11. Rollout

- No feature flag: the endpoint activates on merge; every project without an explicit row transparently uses the existing defaults, so no migration of existing data is needed. `RetentionLimits` ships with conservative placeholder values pending the Tech Lead closing the `[OPEN] owner` floor/ceiling decision — changing them later is a config change, not a migration.
- Merge order: T1.1 → T1.2 (the table and read path must exist before the write path's tests can assert the upsert against it).
- Monitoring: none beyond standard request-rate/error-rate on the two new routes.
- Rollback: revert the PR and the migration (`retention_policy` table drop); no other table references it yet (06.4.2 depends on this story but has not shipped), so rollback is clean.
