## 1. Goal and non-goals

**Goal.** A CI producer obtains a short-lived presigned `PUT` for a server-chosen `pending/` staging key — validated against the run scope, its bound producer slot, the manifest's planned `(execution_key, attempt_no)` and the kind policy — then `complete` verifies the object (size + checksum via `HEAD`), promotes it to the final key, marks the row `ready` and enqueues the async secret scan. Verified bytes only ever become evidence (FR-06-4).

**Non-goals.** The state-machine guard layer that makes illegal transitions 409 (06.1.3); sensitivity enforcement on download (06.2.1); the scan task itself (06.2.3); the orphan sweeper and `pending/` bucket-expiry reconciliation (06.4.3); freeze resolution to `case_attempt` (06.5.1).

## 2. User stories and acceptance criteria

- As a CI reporter, I ask for an upload URL per planned artifact and `PUT` bytes straight to storage, so the API never proxies upload bandwidth (DECISIONS §9 arithmetic).
- As the Tech Lead, only bytes that match the declared size and checksum become `ready`, so a tampered or truncated upload can never back a release decision.

| AC7 | Objects under `pending/` carry the 24 h bucket lifecycle expiry (asserted via bucket policy in the SeaweedFS container) |

## 3. Contracts touched

- 00 §9.3 `upload-url` / `complete` rows — implemented exactly; `x-permission: artifact:write` added to both operations in `contracts/openapi.yaml` (T51) and the full error-code list added there (T52).
- 00 §8.4 — the `pending_upload → uploaded → ready|rejected` transitions are the only ones written by these handlers; T86 fixes the `complete` commit order (verify → copy → commit `ready` → outbox-task staging delete) so a crash never leaves a `ready` row pointing at an uncommitted object nor loses a committed final object.
- `artifact.object_key` — this story uses two key forms: staging `pending/<org_id>/<artifact_id>` (T18/FR-06-2) and the final FR-06-1 key minted by 06.1.1; `UNIQUE (org_id, object_key)` covers both.
- ⚠️ verified in 01.8.1-T1 — FR-06-2 signs the checksum header but does not pin the header name; this plan assumes the provider-neutral `x-amz-checksum-sha256`, confirmed against the SeaweedFS parity check.

## 4. Data model and migrations

None — no new tables. `upload-url` inserts `artifact` rows (`state=pending_upload`, `object_key=pending/…`); `complete` updates `state`, `object_key` (final key), `bytes`, and bumps `version`. `artifact_kind_policy` (created in 06.1.1-T1) is read for `max_bytes`, `media_types`, `capture_enabled`.

## 5. API shapes (commands, queries, endpoints)

| Endpoint | Command / Query | Notes |
|---|---|---|
| `POST /v1/artifacts/upload-url` | `RequestArtifactUploadUrl : ICommand<Result<UploadUrlResponse>>` | `artifact:write`, `Idempotency-Key` **required** (T92). Body `{run_id, producer_id, execution_key, attempt_no, kind, media_type, bytes, sha256}` (T85: `producer_id` names the slot). Handler: (1) run exists + belongs to project + project not deleting; (2) `producer_slot` for `(run_id, producer_id)` — the first accepted write binds it to the caller's token identity, a different identity → 403 `producer_slot_taken`, unknown `producer_id` → 422 `unknown_producer` (04.1.2-T4, T9/T85); (3) `(execution_key, attempt_no)` in the run's manifest plan (T17); (4) `artifact_kind_policy` kind/media/size/`capture_enabled`; (5) mint row + presign. Returns `{artifact_id, object_key, upload_url, required_headers, expires_at}` |
| `POST /v1/artifacts/{a}/complete` | `CompleteArtifactUpload : ICommand<Result<CompleteResponse>>` | `artifact:write`, `Idempotency-Key` **required** (T92). T86 order: `HEAD` the `pending/` object → verify size vs declared + kind cap + checksum → idempotent storage copy `pending/…` → final key → **commit** `state=ready` with the final key, `bytes` from `HEAD` + outbox rows `artifact_secret_scan` (T19) and `artifact_staging_delete` in one tenant transaction; the outbox task deletes the staging object **after** commit. Retry path (T86): staging absent → `HEAD` the final key; if its checksum matches the declared one, proceed to commit. The `HEAD`/copy calls happen *before* the transaction opens (P5: no network inside a DB transaction) |
| — | `GetArtifactPolicy` + `GetProducerSlotBinding` : `IQuery<…>` (Dapper, read-only tx) | single-statement reads used by the command's validation steps (P3: bounded statement count) |

Errors (00 §9.2): `unknown_execution_key`/`unknown_producer` 422, `producer_slot_taken` 403, `idempotency_conflict` 409, `not_found` (unknown run, 06.1.2-T1) / `artifact_not_found` 404, `project_deleting`/`artifact_state_conflict` 409, `payload_too_large` 413 (the existing code; no `too_large`), `media_type_not_allowed`/`checksum_invalid`/`kind_disabled` 422.

Presign detail: expiry ≤ 15 min; signed headers `Content-Length` (= declared `bytes`) and the checksum header (⚠️ parity per T18); the returned `required_headers` must be sent verbatim by the client. `complete` requires the artifact be `uploaded` or `pending_upload` (object may exist); the reporter marks `uploaded` via the same call path — an explicit "PUT finished" marker is the reporter's first `complete` call, which simply fails verification if the object is absent.

## 6. States and transitions

`pending_upload → uploaded` (reporter finished PUT; verified only at `complete`) · `uploaded|pending_upload → ready` (verified) · `uploaded|pending_upload → rejected` (mismatch/absent; reason in `failure_code`). `scan_state=pending` written with `ready`. Illegal transitions (e.g. `rejected → ready`) are impossible here and guarded in 06.1.3.

## 7. Jobs and integrations

- Outbox rows written in the `complete` transaction (C7): `artifact_secret_scan {artifact_id}` (T19; task handler is 06.2.3-T1) and `artifact_staging_delete {artifact_id, staging_key}` (T86; the handler deletes the staging object after commit and is idempotent on a missing key — a no-op when the 24 h lifecycle already collected it).
- `IObjectStorage` adapter (`AWSSDK.S3` presign + `HeadObject`/`CopyObject`/`DeleteObject`): configured region/bucket from env (`EVIDGATE_OBJECT_*`, S3); no credentials in code.
- Bucket `pending/` prefix lifecycle rule = 24 h expiry (T18), applied in infra config and asserted in tests.
- Produces `ready` artifacts consumed by reconcile/freeze (06.5.1) and lists (09.2.1).

## 8. Security, privacy and performance

| 00 §5.7 P1 | `upload-url`/`complete` are hot endpoints: single-digit statement count, presign is CPU-only; `complete`'s `HEAD`+copy run before the tx (P5) | `UploadUrl_Issues_BoundedStatements` command-counter test; load-test row registered for 10 |

| S3 | presigned URLs and checksums never logged or put in metric labels/exception messages | log-redaction unit test on the endpoint filter |
| S4 | storage calls go through the allow-listed `IHttpClientFactory` client; no user-supplied URLs (keys are server-minted) | code review + `HttpClient` registration test |

| Tenant isolation | run scope check inside the tenant transaction; cross-tenant run id → 404 | AC6 |
| Bearer-credential risk | short expiry, per-request issuance, checksum binding makes silent overwrite detectable; rotation = signing-credential rotation (runbook 10.7.1) | AC1 expiry assertion |
| PDPL | artifact bytes may contain personal data; redaction/capture controls are 06.2.2, masking 06.2.3 | — |

**DoR review answers** (00 §12, `plans/features/README.md` §6; restating the rows above and §11):

- **Authorization:** both commands need `artifact:write` (`ci_producer` for CI uploads, members for manual), checked in the C2 pipeline, not the endpoint; a cross-tenant run id → 404 inside the tenant transaction (AC6).
- **Retention/deletion:** `pending/` objects expire after 24 h (T18); the outbox `artifact_staging_delete` row removes the staging object after commit (T86); rows left `pending_upload`/`uploaded` are rejected by the sweeper (06.4.3); artifact bytes may hold personal data, governed by 06.2.2/06.2.3.
- **Telemetry:** the artifact-failure-rate SLI (00 §11) gets its `failure_code` dimension here; outbox lag on `artifact_secret_scan` once 06.2.3 lands; presigned URLs and checksums never appear in logs, metric labels or exception messages (S3).
- **Failure path:** a failed `complete` commit leaves recoverable staging plus a final object the sweeper removes, and the retry path HEADs the final key (T86, AC4/AC5); an idempotency payload drift → 409 `idempotency_conflict` (AC8); a size or checksum mismatch fails the signed `Content-Length` + checksum or `complete`'s size re-check (T18, AC1/AC3).
