## 1. Goal and non-goals

**Goal.** Every parse of untrusted artifact bytes inside the server — XML/JUnit reports, JSON payloads, zip archives (Playwright trace, report bundles) — goes through one enforced safe-parser profile in `Evidgate.Modules.Evidence`: external entities and DTDs are impossible, depth/size/entity/time caps are hard limits, archive extraction never writes outside its root, and the sniffed signature must match the declared media type. A hostile artifact costs bounded CPU and memory and ends `rejected`, never `ready`.

**Non-goals.** The hostile fixture corpus and fuzz run (06.3.2); the isolated viewer origin and per-kind serving (06.3.3, 06.3.4); the JUnit event mapping and report comparison logic itself (04.4.1); secret scanning of content (06.2.3); adapter-side parsing in the Node CLI (04, separate runtime).

## 2. User stories and acceptance criteria

- As the Tech Lead, I want every code path that opens untrusted XML/JSON/zip bytes to be physically unable to resolve external entities, so XXE and SSRF-via-parser are structurally excluded.
- As a reviewer, I want the caps enumerated and tested, so a regression in any guard fails the build.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An XML body containing `<!DOCTYPE`/`<!ENTITY` is rejected: `XmlReader` is created with `DtdProcessing.Prohibit` and `XmlResolver = null`; a counting `XmlResolver` spy in the test proves zero external-resolution calls and zero file/HTTP access |
| AC2 | Depth, size and wall-time caps are enforced: input deeper than the profile depth (default 64), larger than the kind's `max_bytes` from `artifact_kind_policy`, or slower than the parse timeout returns `Result` failure (`artifact_invalid` / `too_large`, 00 §9.2), never an unhandled exception |
| AC3 | A zip with more than the entry cap (10 000), total expanded size above the cap (512 MiB), a per-entry compression ratio above 100:1, or a nested-archive depth above 2 is rejected before any entry is written to disk |
| AC4 | Archive entry names are normalized and entries containing `..`, an absolute path, a drive letter or `\` separators are rejected; no byte lands outside the extraction root |
| AC5 | The sniffed magic bytes must match the declared `media_type`; a mismatch at `complete` leaves the artifact `rejected` with `failure_code = media_type_mismatch` and is never counted as evidence |
| AC6 | Parsing is streamed and bounded: a guard test parses the largest allowed fixture while asserting peak managed allocation stays under the per-kind cap ×2 |

## 3. Contracts touched

- 00 §5.7 S5 — implemented by this story (the rule names 06 as owner).
- FR-06-8 — implemented, not changed.
- `Evidgate.Modules.Evidence.Contracts` gains a public `IParsing` surface (`ParseXmlReport`, `EnumerateArchive`, `SniffMediaType`) so 04's raw-report parsing and 06.3.4's trace serving use the same guards — allowed by 00 §5.5 (Contracts projects hold public service interfaces).
- Rejection reasons reuse the codes the area plan already defines (`media_type_mismatch`, `too_large`); the new parse-failure code `artifact_invalid` is registered in `contracts/openapi.yaml` (the only error-code source, T52) at DoR.
- No schema, endpoint or permission change.

## 4. Data model and migrations

None. The profile reads `artifact_kind_policy.max_bytes` / `media_types` (table owned by 06.1.1, unchanged) and stores rejections in `artifact.failure_code` (existing column). Cap defaults that are not per-kind live as module constants (`ParsingLimits`: `MaxDepth = 64`, `MaxZipEntries = 10_000`, `MaxExpandedBytes = 512 MiB`, `MaxCompressionRatio = 100`, `MaxNesting = 2`, `ParseTimeout = 30 s`).

## 5. API shapes (commands, queries, endpoints)

No new endpoint. The profile is invoked inside existing command/handlers:

| Consumer | Use |
|---|---|
| `CompleteArtifactCommand` handler (06.1.2) | sniffs magic bytes vs declared `media_type` on the `pending/` object stream before `ready`; mismatch → `rejected` (`media_type_mismatch`) |
| `IParsing.ParseXmlReport` (04.4.1 raw-report parse, `reprocess`, comparison) | `XmlReader` profile over a capped stream |
| `IParsing.EnumerateArchive` (06.3.4 trace/report serving, 06.4.3 sweeper) | entry allowlist + path normalization + caps |
| `IParsing.ParseJson` | `JsonDocument` with `MaxDepth` and a pre-read size cap |

Failures are `Result` values mapped once to the 00 §9.2 envelope (C8); no `ProblemDetails`, no parser exception escaping a handler.

## 6. States and transitions

None new. The story only writes `artifact.state = rejected` + `failure_code` through the existing `uploaded → rejected` transition (00 §8.4, 06 §4 states). `rejected` remains terminal.

## 7. Jobs and integrations

- `CompleteArtifactCommand` (06.1.2-T2) calls the sniffer inside its handler; the `HEAD`/object read is a storage call and stays outside the DB transaction (P5): open the object stream, sniff the first bytes, then run the state update in the tenant transaction.
- `IParsing` is consumed by 04.4.1 (report parse at `reprocess` and comparison), 06.3.4-T2 (trace zip serving) and 06.2.3's scanner (bounded readers for content scan).
- The Node-side CLI/reporter does its own validation in TypeScript (04); this story covers the server runtime only — the wire contract is unchanged.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S5 | `XmlReaderSettings` `DtdProcessing.Prohibit` + `XmlResolver = null` + entity/depth/size/time caps; zip entry/ratio/nesting caps; `JsonDocument.MaxDepth` | `SafeXmlReaderTests`, `SafeZipArchiveTests`, `SafeJsonTests` (AC1–AC4) |
| 00 §5.7 S3 | parse errors return `artifact_invalid` + a generic reason; parser output never includes artifact bytes or paths in logs/messages | `ParseErrorRedactionTests` asserts message content |
| 00 §5.7 S4 | `XmlResolver = null` and no fetch API in the profile make outbound requests impossible, not just disallowed | AC1 spy resolver |
| 00 §5.7 P1 | `complete` is a listed hot endpoint; sniffing reads a bounded prefix (≤ 4 KiB) and archive walks abort at first cap | AC6 allocation/timing guard test |
| 00 §5.7 P5 | storage `HEAD`/stream reads run before/outside the tenant transaction; no DB tx is held while bytes are walked | `CompleteArtifactCommandTests` ordering assertion |
| 00 §5.5 C8 | all rejection paths are `Result` → 00 §9.2 envelope (422/413) | endpoint tests in 06.1.2 re-run against hostile fixtures |
| Tenant isolation | no new reads/writes; runs under the caller's tenant transaction like any handler code | existing RLS integration suite |
| Privacy | parses bytes but extracts nothing to logs or to disk outside the extraction root | AC4 |
| Retention/deletion impact | none | — |

| Behaviour / boundary / failure | Test |

## 11. Rollout

- No feature flag: the profile is enforced unconditionally on merge (parse paths that bypass it do not exist — `Architecture.Tests` asserts `XmlReader`/`ZipArchive` are constructed only inside `Infrastructure/Parsing`).
- Merge order: T1 → T2 in one PR series on `develop`; 06.3.2's corpus then hard-gates the profile in CI.
- Monitoring: `artifact-failure rate` SLI (00 §11) already counts `failure_code`; watch `media_type_mismatch`/`artifact_invalid` share after rollout.
- Rollback: revert the PR; rejected artifacts stay `rejected` (terminal), no data repair needed.
