## 1. Goal and non-goals

**Goal.** An HTML `raw_report` artifact and a Playwright `trace` artifact open correctly on the isolated viewer origins (06.3.3, T71) using a short-lived, token-verified URL: the HTML report — a self-contained single file with inline script and embedded (data-URI) assets, per Playwright's HTML reporter format — renders interactively from `viewer-content` while being unable to exfiltrate anything over the network; the trace zip's index + resources render through the pinned `playwright-core` trace-viewer bundle served from `viewer-app`, via the parser-hardened archive reader (06.3.1), with no path-traversal write and no unbounded expansion.

**Non-goals.** Establishing the viewer origins, their default headers, sandbox and the token primitive (06.3.3, a dependency here); the parser caps themselves (06.3.1, a dependency here); mobile kinds (`video`, `ui_hierarchy`, `a11y_snapshot`, 06.3.5); report *comparison* logic (`GET /v1/runs/{r}/reports/{report_id}/comparison`, owned by 04.4.1-T6); the `download-url` endpoint and its authorization/audit (06.2.1-T2) — this story only serves bytes for a token 06.3.3's `ViewerTokenService.Verify` already accepted, after re-reading the artifact under the claims-derived tenant scope (T74).

## 2. User stories and acceptance criteria

- As a QA engineer, I want to open a Playwright trace or an HTML report from a run directly in the browser, so I can debug a failure without downloading and unzipping anything locally.
- As a security reviewer, I want the trace viewer's file-serving path to be immune to the same archive attacks 06.3.1 already blocks, so trace serving cannot become a second, unguarded path into the same bug class.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A `ready` `raw_report` (kind = HTML) artifact, once its token is verified by `ViewerTokenService.Verify` (06.3.3) **and** re-read under `ITenantScope.BeginAsync(org_id, project_id)` opened from the token claims (T74), is served from `viewer-content` under the T71 header floor: `Content-Security-Policy: sandbox; default-src 'none'` (the `sandbox` directive gives the response document a unique opaque origin; inline script still executes so the report's own charts/filters work; `default-src 'none'` with no `connect-src`/`form-action` allowance blocks every network call the report script could attempt), a server-chosen allow-listed `Content-Type`, `X-Content-Type-Options: nosniff`. A hostile fixture's `fetch`/`XHR`/form-post attempt fails |
| AC2 | A `ready` `trace` artifact's zip is enumerated through `IParsing.EnumerateArchive` (06.3.1); the trace index (`trace.json`/equivalent) and each referenced resource inside the zip render in the pinned `playwright-core` trace-viewer bundle served from `viewer-app` (T71 — the bundle and its Service Worker live on the trusted origin, only the zip's bytes come from `viewer-content`) (⚠️ version pinned, licence row added to ADR-0002 at 01.1.1-T1, Apache-2.0 ⚠️ (ADR-0002 records `@playwright/test` as Apache-2.0; add a `playwright-core` row before 06.3.4-T1)); a resource path that normalizes outside the archive root is refused with the same `artifact_invalid` behaviour as 06.3.1 |
| AC3 | Requesting a resource by a path not present in the trace's own index (path guessing) returns 404, never a raw filesystem/zip listing |
| AC4 | A token that fails `ViewerTokenService.Verify` (expired or tampered claims) results in no report/trace bytes being returned on either serving route, fails closed; after `Verify`, the handler re-reads `artifact` inside `ITenantScope` opened from the claims and serves only `state = ready` rows (T74) — a token for a since-deleted/downgraded artifact 404s |
| AC5 | Serving is streamed: the largest legitimate fixture within the `artifact_kind_policy.max_bytes` budget for `raw_report`/`trace` renders without loading the whole expanded archive into memory at once |
| AC6 | A report/trace whose declared `media_type` does not match its sniffed signature (06.3.1 AC5) was already rejected at `complete` and is never `ready`, so no additional media-type check is needed at serve time — confirmed by a test that only `ready` artifacts are servable; the response `Content-Type` is still server-chosen from the allow-list, never from client input (T71) |

## 3. Contracts touched

- FR-06-9 — implemented (the "opens correctly" half of isolated serving; the origin/header mechanics are 06.3.3).
- No schema, endpoint-permission or state change; this story implements the viewer-origin document/resource-serving routes 06.3.3 §5 names but leaves to per-kind ownership — report documents and trace resources on `viewer-content`, the trace-viewer bundle + Service Worker on `viewer-app` (T71).
- Reuses `IParsing.EnumerateArchive`/`SniffMediaType` (06.3.1 §5) and `ViewerTokenService.Verify` (06.3.3 §5) unchanged; `Verify` itself touches no database — after it returns the verified claims, each serving handler opens `ITenantScope.BeginAsync(org_id, project_id)` from those claims and does its own Dapper read of `artifact` under RLS (T74, 00 §5.4.8).
- **CSP/header boundary with 06.3.3:** 06.3.3-T1.3 sets both origins' header floors — `viewer-content` already serves `CSP: sandbox; default-src 'none'`, `Content-Disposition: attachment` unless the kind is an allow-listed inline type (`raw_report` documents and `trace` resources are on that allow-list and go inline), allow-listed server-chosen `Content-Type`, `nosniff` (T71). This story's `raw_report` route relies on that floor and adds no relaxation; the `trace` route keeps `viewer-app` serving only Evidgate's own reviewed, version-pinned bundle, not untrusted content (§4).
- New dependency: `playwright-core`'s trace-viewer static bundle, added to DECISIONS §4 / ADR-0002 at 01.1.1-T1 (⚠️ licence check, same gate as every other package).
- **Iframe sandbox boundary with 06.3.3:** when the app embeds either kind, 06.3.3-T1.4 defines the iframe `sandbox` value per kind — `raw_report` gets `sandbox="allow-scripts"` only; `trace` gets `sandbox="allow-scripts allow-same-origin"`, required because the pinned trace-viewer bundle (§4) registers a Service Worker on `viewer-app`, which needs a non-opaque origin. This is distinct from, and in addition to, the response-level CSP `sandbox` directive on `viewer-content`: the iframe attribute governs what the parent app grants the framed document, the CSP header governs what the document's own response permits.

## 4. Data model and migrations

None new. Reads existing `artifact` columns (`state`, `kind`, `object_key`, `media_type`, `bytes`) from 06.1.1; no new table, no migration.

**Trace-viewer hosting (T71).** Unlike the raw-report route (which streams untrusted artifact bytes directly as the response document on `viewer-content`), the trace route serves two distinct things on two origins: (a) Evidgate's own pinned, reviewed `playwright-core` trace-viewer static bundle (JS/CSS) and its Service Worker, deployed once to `viewer-app` under 06.3.3's baseline CSP — it is not untrusted content, so no opaque-origin sandbox is needed and its Service Worker can register (Service Worker registration requires a non-opaque origin, which the `viewer-content` CSP `sandbox` directive would prevent); and (b) the trace zip's own resources, served from `viewer-content` under the T71 header floor, which the bundle's Service Worker fetches via `ServeTraceResourceQuery` and treats purely as data (network-log JSON, screenshots, DOM snapshots) rendered into the viewer UI.

## 5. API shapes (commands, queries, endpoints)

Server story:

| Operation | Kind | Endpoint | Permission | Status / error codes |
|---|---|---|---|---|
| `ServeReportDocumentQuery` | `IQuery<T>` (Dapper, read-only tx for metadata + streamed storage read outside the tx, P5) | `GET https://viewer-content…/{artifact_id}` (`?t=<token>` only on the first load — a one-time token exchanged server-side and stripped by a 302 to the clean URL (T99); subsequent loads are authorized by `Authorization: Viewer <token>` sent by the `viewer-app` Service Worker — `viewer-content` reads no browser credentials and answers CORS only to `viewer-app`) | token-scoped (`ViewerTokenService.Verify`, no session/permission header — the token already encodes the authorization decision made by 06.2.1-T2 at issuance) + post-verify `ITenantScope` re-read (T74) | 200 (HTML body, streamed, T71 `viewer-content` headers, AC1); 403 invalid/expired token or a token bound to a different `artifact_id`; 404 artifact not `ready` or kind mismatch |
| `ServeTraceResourceQuery` | `IQuery<T>` | `GET https://viewer-content…/{artifact_id}/resource/{resource_path}` (same viewer token — `Authorization: Viewer <token>` attached by the `viewer-app` Service Worker on its cross-origin fetches (T99); no browser credentials are sent or read) | same token scope + RLS re-read; `resource_path` matched against the trace's own index only | 200 (resource bytes, streamed, T71 `viewer-content` headers); 404 unknown resource path or path normalizes outside the archive |
| Trace-viewer bundle serving | static asset route, no token | `GET https://viewer-app…/trace-viewer/*` (viewer-app origin) | none (public static assets, Evidgate's own reviewed code, no artifact data) | 200; served under 06.3.3's `viewer-app` baseline headers |

Both queries are queries (C1): they read `artifact` + stream storage bytes, never mutate. No `Idempotency-Key` (GET, no side effect).

## 6. States and transitions

None new. Both queries guard on `artifact.state = ready` and `artifact.kind ∈ {raw_report, trace}` under the claims-derived tenant scope (T74); any other state or kind is 404 (00 §8.4).

## 7. Jobs and integrations

- Consumes 06.3.3 (viewer origins, headers, `ViewerTokenService.Verify`, the one-time `?t=` exchange + `Authorization: Viewer` verification) and 06.3.1 (`IParsing.EnumerateArchive`, `SniffMediaType`) directly; no new integration surface of its own.
- No outbox/task involvement: serving is synchronous, streamed, read-only.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S5 | trace zip resources are enumerated exclusively through `IParsing.EnumerateArchive` (06.3.1 caps + traversal guard); no direct `ZipArchive` use in the serving handler | `Architecture.Tests` forbidding direct `System.IO.Compression` use outside `Infrastructure/Parsing`, and `ServeTraceResourceQuery` calling only `IParsing` |
| T71 | `raw_report` bytes serve only from `viewer-content` under `CSP: sandbox; default-src 'none'` + allow-listed `Content-Type`/`nosniff`; the trace-viewer bundle + Service Worker serve only from `viewer-app`; tenant bytes never land on `viewer-app` | AC1, AC2 |
| T74 + T99 | after `Verify` the handler opens `ITenantScope.BeginAsync` from the token claims and re-reads `artifact` under RLS (`ready`, sensitivity, scan state) before streaming a byte; the viewer token is bound to the requested `artifact_id` and arrives only as `Authorization: Viewer <token>` (held in memory on `viewer-app`, T99 — never in browser credential storage), so a token minted for artifact A is rejected for artifact B | AC4 |
| 00 §5.7 P5 | metadata read (Dapper, tx) and storage byte streaming (network) are separate steps; no storage call inside the DB transaction | `ServeReportDocumentQueryTests` ordering assertion |
| 00 §5.7 P2/P3 | one Dapper read of `artifact` per request (no N+1), streamed storage read (no full-buffer read into memory) | AC5, command-counter test |
| Authz | delegated to the token verified by 06.3.3's `Verify` plus the T74 RLS re-read (which encodes the decision 06.2.1-T2 already made); this story never re-derives authorization from a session, so a stolen token cannot escalate beyond what it was minted for | AC4, token-scope test |
| Tenant isolation | `org_id`/`project_id` come only from inside the verified HMAC claims; RLS on the re-read guarantees a cross-tenant artifact id 404s | `ServeReportDocumentQueryTests.CrossTenantTokenIs404` |
| Privacy | resource paths inside a trace are matched against the trace's own index, never against the filesystem/zip listing, so no directory-enumeration leak | AC3 |
| Supply chain (T40) | `playwright-core` trace-viewer bundle version-pinned + licence row in ADR-0002 (01.1.1-T1) | ADR-0002 row |
| Retention/deletion impact | none; a deleted/expired artifact is already `!= ready` and 404s at the T74 re-read | — |

## 11. Rollout

- No feature flag: serving activates once both dependencies (06.3.3 origins, 06.3.1 parser) are live; the Angular bridge that links to these URLs (09.4.1) can flag its own rollout independently.
- Merge order: T1 and T2 can land in parallel PRs once 06.3.3 and 06.3.1 are merged (no shared code path between report and trace serving beyond the token/parser dependencies).
- Monitoring: 404 rate on resource requests (a spike indicates a broken trace index or a scraping attempt); CSP-violation reports from the `viewer-content` route (a violation there is expected background noise from `default-src 'none'`, monitored for unexpected patterns); streamed-response latency/memory on the largest fixtures.
- Rollback: revert the PR; no persisted state (read-only serving), no cleanup needed.
