## 1. Goal and non-goals

**Goal.** Artifact viewing runs on a separate registrable domain split into **two origins** (T71): `viewer-app` serves only Evidgate's own trusted viewer bundle and its Service Worker, while `viewer-content` serves tenant bytes exclusively under `Content-Security-Policy: sandbox; default-src 'none'`; `Content-Disposition: attachment` unless the kind is an allow-listed inline type, a server-chosen `Content-Type` from an allow-list and `X-Content-Type-Options: nosniff`; neither origin carries app credentials or shared browser storage, and every view URL is short-lived. A malicious report cannot read app credentials, call authenticated app APIs, or persist beyond its view.

**Non-goals.** Parsing/serving the specific HTML report or trace content itself (06.3.4, which builds on this origin); the mobile artifact kinds (06.3.5); redaction/masking of artifact content (06.2.2/06.2.3); the app-origin CSP and session mechanics themselves (owned by 10.1.1 infra and 11.1.1 security baseline — this story consumes both, does not define them); **the `GET /v1/artifacts/{a}/download-url` endpoint, its `artifact:read`/`artifact:read_sensitive` authorization check and the sensitive-issuance audit row — all owned by 06.2.1-T2, which depends on this story's T1 and calls the token primitive this story exposes.**

## 2. User stories and acceptance criteria

- As a security reviewer, I want an XSS in a rendered report to be unable to read app session credentials or call authenticated app endpoints, so a hostile artifact cannot pivot into account takeover.
- As a tenant admin, I want every artifact view token to expire quickly and to be unmintable except through an authorized request, so a leaked link has bounded value and cannot be forged.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The viewer is served from a separate registrable domain from the app, split into `viewer-app` and `viewer-content` origins (e.g. `app.evidgate.<tld>` vs `viewer-app.evidgate-content.<tld>` / `viewer-content.evidgate-content.<tld>`, confirmed against 10.1.1's DNS/CDN setup); a document served on either viewer origin has no access to app-origin credentials or storage and `document.domain` cannot be widened to the app's eTLD+1 (public-suffix distinct) |
| AC2 | Response headers on every `viewer-content` response (T71): `Content-Security-Policy: sandbox; default-src 'none'`, `Content-Disposition: attachment` for every kind **except** the allow-listed inline types (`raw_report`, `trace` resources) which are served inline, a server-chosen `Content-Type` from an allow-list (never client-supplied), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (T74); `viewer-app` responses carry the 11.1.1-T1 baseline CSP. A Playwright test loading a hostile HTML fixture (06.3.2) asserts an injected `<script>` never reaches the app or another tenant (06.3.4 may apply a stricter, kind-specific override for `raw_report` — this story defines the defaults and the header-application mechanism, not every per-kind variant) |
| AC3 | Neither viewer origin is ever issued the app's session credential or any XSRF token, and `viewer-content` reads **no** browser credential transport at all (00 §5.6 W6, T71, T99): the only credential on the viewer surface is the T74 HMAC viewer token, held **in memory** by the `viewer-app` Service Worker and sent as `Authorization: Viewer <token>` on every `viewer-content` request; `viewer-content` answers CORS preflights only for the `viewer-app` origin. A request carrying app session credentials by accident (cross-site leakage test) still gains nothing — they are never shared to the viewer domain and never read |
| AC4 | `ViewerTokenService.Mint(…)` produces a T74 token `HMAC-SHA256(viewer_key_vN, canonical(v, org_id, project_id, artifact_id, kind, expires_at))` signed with a dedicated viewer key (not the ingest pepper), `v` carried in the token, TTL ≤ 5 min; `Verify` fails closed on expiry, signature or canonical-fields mismatch. On first load `viewer-app` verifies the token and 302s to `viewer-content/{artifact_id}?t=…`, where `viewer-content` treats `?t=` as a **one-time** token (T99): it verifies it server-side and 302s to the clean URL, stripping the parameter; the `viewer-app` Service Worker then sends `Authorization: Viewer <token>` on every subsequent content request. A token minted for artifact A is rejected for artifact B (scoping by value, not path) |
| AC5 | The iframe embedding contract is per kind, matching the two-origin split (T71): `raw_report` gets `sandbox="allow-scripts"` only (no `allow-same-origin`, `allow-top-navigation`, `allow-popups`, `allow-forms`) and renders bytes from `viewer-content`; `trace` gets `sandbox="allow-scripts allow-same-origin"` because its pinned trace-viewer bundle + Service Worker are served from `viewer-app`, which needs a non-opaque origin — safe because `allow-same-origin` grants only the iframe's own `viewer-app` context, never the app's (AC1/AC3). A sandbox-escape smoke test per kind (top-navigation/popup/same-origin-storage-of-the-*app*-origin attempt from a hostile fixture) is blocked for both |
| AC6 | After `Verify` succeeds, the serving handler opens `ITenantScope.BeginAsync(org_id, project_id)` on the app role **from the token claims** and re-reads the artifact under RLS, returning bytes only when the row is `ready` and passes the sensitivity + scan-state checks (T74); a tampered `org_id`/`project_id`/`artifact_id`/`kind` claim fails `Verify`, and a since-deleted/downgraded artifact 404s |

- Depends on infra facts owned elsewhere: 10.1.1-T4 (domain/DNS/CDN provisioning for the second registrable domain) and 11.1.1-T1 (security baseline: CSP/header policy source of truth) — this story consumes those, does not redefine them.
- No new database table; no permission catalogue change (`artifact:read`, `artifact:read_sensitive` already exist, T21, enforced by 06.2.1).

## 4. Data model and migrations

None new. `ViewerTokenService` reads nothing from the database: `Mint` takes an already-authorized claims record `{v, org_id, project_id, artifact_id, kind, expires_at}` from its caller (06.2.1-T2's `IssueArtifactDownloadUrl` command handler, which has already read `artifact.state`/`sensitivity`, checked permission and written its audit row) and returns a T74 token `HMAC-SHA256(viewer_key_vN, canonical(v, org_id, project_id, artifact_id, kind, expires_at))`; `Verify` recomputes over the presented claims in constant time (`CryptographicOperations.FixedTimeEquals`), accepts any known `viewer_key_vN` version, and checks `expires_at` against the current clock. The signing material is a **dedicated viewer key** from the secret store — never the ingest pepper; rotation mints a new key version while `Verify` still accepts the previous version until outstanding tokens expire. The tenant-scope re-read after `Verify` (T74, AC6) is performed by 06.3.4's serving handler — `Verify` itself stays stateless; no database row backs the token, so exposure is bounded by TTL alone, not by a revocation list.

Web-side structure (component/route, consumed by 09.4.1, not built here): the viewer app itself is a minimal static bundle deployed to the `viewer-app` origin (own build, not part of `apps/web`), with a single route that accepts the signed token as a query parameter and never reads any other query/hash state as trusted input; after `Verify` its Service Worker keeps the token **in memory only** and hands off to `viewer-content`, which performs the one-time `?t=` exchange and strip-redirect (T99); from then on the Service Worker attaches `Authorization: Viewer <token>` to every `viewer-content` fetch — no browser credential storage is written or read on the viewer surface, which serves all tenant bytes (T71/T74/T99).

## 6. States and transitions

None new. `ViewerTokenService` has no state of its own; 06.2.1-T2 (not this story) guards `artifact.state = ready` before minting, and the serving handler's post-`Verify` RLS re-read (AC6/T74) re-checks `ready` + sensitivity + scan state at serve time (00 §8.4).

## 7. Jobs and integrations

- Consumes 10.1.1-T4 (second registrable domain provisioned, DNS + CDN/static hosting) and 11.1.1-T1 (org-wide CSP/security-header policy baseline) as inputs; this story's headers are the artifact-viewer specialization of that baseline, not a competing policy.
- Exposes the `Mint`/`Verify` primitive consumed by 06.2.1-T2 (issuance + authorization + audit) and 06.3.4 (per-kind serving on `viewer-app`/`viewer-content`, verifies before returning bytes).
- Blocks 06.3.4 (which serves actual report/trace bytes on these origins), 06.2.1 (whose T2 needs this story's T1 primitive), 09.4.1 (Angular embedding bridge), 11.7.1 (security evidence walkthrough cites this origin's isolation).
- No task-queue/outbox involvement: the primitive is synchronous and stateless.

## 11. Rollout

- No feature flag for the origins/headers/primitive themselves (infrastructure, always on once provisioned); the Angular embedding bridge that consumes it (09.4.1) ships behind its own feature flag if needed.
- Merge order: T1.1 (origins must exist before headers/tokens can be tested end-to-end) → T1.2 and T1.3 in parallel → T1.4 last (needs both the token service and the headers).
- Monitoring: `Verify` failure rate (expired/tampered) surfaced once 06.2.1/06.3.4 wire it into their handlers; CSP-violation reports (`report-to`) from the viewer origins surfaced to 10's dashboards.
- Rollback: revert the DNS/CDN config and the primitive together; no persisted data (tokens are stateless, HMAC-verified) so rollback has no cleanup step.
