## 1. Goal and non-goals

**Goal.** A scheduled consistency sweep finds and repairs every divergence between the `artifact` table and object storage: rows past the upload window, rows stuck in `pending_delete` beyond the retry budget, `ready` rows whose object vanished, and storage objects with no row. Every repair is idempotent and writes an audit row.

**Non-goals.** The normal retention path (06.4.2 — the sweeper only re-drives what retention could not finish); tenant deletion (06.4.4); alerting rules and the independent verification cycle (06.4.5); the 24 h bucket lifecycle policy itself (06.1.2-T1, T18).

## 2. User stories and acceptance criteria

- As the platform, storage and the catalog converge automatically after crashes, lifecycle deletions or failed jobs, so evidence claims and billing both stay truthful.
- As an operator, every repair is auditable and repeatable, so I can trust the sweep instead of hand-fixing rows.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A `pending_upload`/`uploaded` row older than the upload window becomes `rejected` with `failure_code='upload_expired'`; the object, if present under `pending/`, is deleted best-effort |
| AC2 | A `pending_delete` row whose last attempt exceeded the retry budget is re-driven through the normal delete+verify pipeline and escalated to a `deletion_job` row (`scope='artifact'`) after the attempt cap |
| AC3 | A `ready` row whose object is absent becomes `rejected` with `failure_code='object_missing'` — evidence never claims an object it cannot fetch (FR-06-4, §5 invariant) |
| AC4 | A storage object under `pending/` or the final prefix with no matching `ready` artifact row is deleted after a grace period — this includes a T86 leftover: a final-key object whose `complete` copy succeeded but whose `ready` commit never landed; each deletion writes an audit row |
| AC5 | Re-running the sweep on the same divergence performs no second repair (state guard + audit dedup) |
| AC6 | Each repair writes one `audit_event` row (`artifact.swept_orphan`, org, artifact id or key, repair kind); a sweep that touches org A never touches org B |

## 4. Data model and migrations

`migrations/NNNN_evidence_sweeper.sql` (DbUp; placeholder number):

- Index `artifact_stale_pending_idx on artifact (created_at) where state in ('pending_upload','uploaded')` (P4).
- Index `artifact_repair_due_idx on artifact (org_id) where state = 'pending_delete'` (already partially covered by 06.4.2's index; kept for the escalation scan ordered by `org_id`).
- No new tables. The sweep watermark is derived from `created_at`/`expires_at`, not persisted state, so a skipped run simply catches up next cycle.
- `evidgate_ops.sweep_due_orgs()` owner `SECURITY DEFINER` function returning orgs needing a sweep — same T11 precedent as `retention_due_projects`, hardened per T80: `SET search_path = ''`, schema-qualified references, `EXECUTE` granted to `evidgate_worker_sched` only, one audit row per call; covered by the 11.2.1-T7 review and the 02.6.1-T2 lint.

## 5. API shapes (commands, queries, endpoints)

None — internal tasks only:

| Task type | Payload | Idempotency key |
|---|---|---|
| `sweep.scan` | `{ }` (schedule `evidgate.orphan-sweep`, hourly) | `(schedule_name, fire_at)` |
| `sweep.org` | `{ org_id }` | `sweep:<org>:<yyyy-mm-ddThh>` → `ON CONFLICT DO NOTHING` |

`sweep.org` opens `ITenantScope.BeginAsync(org_id)` and runs, in order: stale-upload pass → stuck-`pending_delete` pass → row-vs-object check (`HEAD` sampled + full check on entries flagged by storage listing) → object-vs-row pass (prefix listing). Storage calls happen between transactions (P5), exactly like 06.4.2-T1.3.

## 6. States and transitions

| From | Event | To | Guard |
|---|---|---|---|
| `pending_upload`/`uploaded` | upload window elapsed | `rejected` (`upload_expired`) | `created_at < now() - upload_window` |
| `ready` | object absent at sweep | `rejected` (`object_missing`) | `HEAD` 404, audited |
| `pending_delete` | sweep re-drive | `deleted` or stays `pending_delete` | reuses 06.4.2 delete+verify |
| `pending_delete` | attempt cap exceeded | `deletion_job(scope='artifact') queued` | unique `(org_id, scope, target_id)` dedups |
| — (object only) | orphan older than grace — `pending/` key with no row, or final-prefix key with no `ready` row (T86 failed-commit leftover) | object deleted | grace ≥ 48 h covers in-flight uploads *and* commits racing the copy; audit row |

## 7. Jobs and integrations

- Schedule `evidgate.orphan-sweep`, Cronos `17 * * * *` UTC (hourly; distinct fire key from retention), unique `(schedule_name, fire_at)`, never a leader (00 §5.3).
- `IObjectStore` operations: `ListObjects` by prefix (`pending/<org>/`, `org/<org>/`), `HEAD`, delete; all outside DB transactions (P5), paginated at 1000 keys.
- Metrics: `evidgate_sweep_orphans_repaired_total{kind}`, `evidgate_sweep_orphans_open` gauge, `evidgate_sweep_escalations_total`.
- Consumed/verified by 06.4.5 (verification cycle asserts convergence and alerts on `evidgate_sweep_orphans_open > 0` persisting).

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|

## 11. Rollout

- Ships enabled alongside retention (same M2 wave); the orphan-object grace (48 h) is config `Sweep:OrphanGraceHours` and is never set below the `pending/` lifecycle window plus a margin.
- Monitoring: `evidgate_sweep_orphans_open` gauge trend; a non-zero plateau for > 1 cycle is what 06.4.5's alerting consumes.
- Rollback: remove the schedule; divergences then require manual repair — no destructive rollback step exists because repairs are forward-only.
