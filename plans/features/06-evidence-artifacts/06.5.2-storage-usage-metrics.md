## 1. Goal and non-goals

**Goal.** Per org/project, the day's stored bytes (GB-month basis), object count, egress bytes and artifact-failure counts are computed daily from `artifact`, exposed as queryable rows that reconcile with the live table, fed into 10's metrics catalogue as per-unit cost counters, and handed to 12's `usage_ledger_entry` as a dedicated `artifact_gb_month`/`egress_gb` metering point with a unique `billing_key` per source event.

**Non-goals.** The `usage_ledger_entry`/`usage_price` schema and enforcement (12.3.1-T1/T3/T4 own them); the metrics catalogue/dashboards themselves (10.3.1-T3/T4 own the exporter and panels — this story only emits the counters); egress *measurement at the storage layer* (this story reads egress bytes reported by `IObjectStore`, it does not instrument the CDN/provider).

## 2. User stories and acceptance criteria

- As the platform, I can see each org/project's daily storage footprint and egress, so cost trends are visible before pricing locks (10's monthly cost-spike risk).
- As 12's ledger, I receive one deduplicated usage event per org/project/day/metric, so double-counting a re-run job never inflates a bill.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | For a fixture org/project with N `ready` artifacts of known `bytes`, the nightly job writes one `storage_usage_daily` row with `bytes_stored = sum(bytes)` for `ready` artifacts as of that day and `objects = count(*)` |
| AC2 | `artifact_failures` counts artifacts that reached `rejected` that day (any `failure_code`), matching a direct `count(*) from artifact where state='rejected' and updated_at::date = @day` |
| AC3 | Re-running the roll-up for the same `(org_id, project_id, day)` is idempotent: `unique (org_id, project_id, day)` upsert produces the same row, never a duplicate |
| AC4 | GB-month average is computed as bytes × fraction-of-day-held, matching the area-plan §5 rule ("GB-month is computed from actual stored bytes × time, from the retention states in 06") — verified against a hand-computed fixture |
| AC5 | The daily roll-up emits exactly one usage event per `(org_id, project_id, day, metric)` to 12's `usage_ledger_entry` via a `billing_key` of the form `storage:<org_id>:<project_id>:<day>:<metric>`; a re-emit after a crash produces zero duplicate ledger rows (T43, `unique (org_id, billing_key)`) |
| AC6 | `storage_usage_daily` counts reconcile with `artifact`: a query joining both for the same day and org/project returns zero discrepancy rows on the test fixture |

## 4. Data model and migrations

`migrations/NNNN_evidence_storage_usage.sql` (DbUp; placeholder number):

- `storage_usage_daily`: `id uuid pk`, `org_id uuid not null`, `project_id uuid not null`, `day date not null`, `bytes_stored bigint not null`, `objects int not null`, `egress_bytes bigint null` (T60: `NULL` means "not measurable this day", never a false `0`), `egress_unavailable_reason text null` (set to `'unavailable'` when `IObjectStore` cannot report egress for the provider, cleared once it can), `artifact_failures int not null default 0`, `created_at timestamptz not null default now()`; `unique (org_id, id)` (T3); `unique (org_id, project_id, day)`; RLS `org_id = evidgate.current_org_id()` with `FORCE ROW LEVEL SECURITY`.
- Serving index: covered by the `unique (org_id, project_id, day)` constraint itself (used both for the upsert and for range queries by 09.7.1's usage screen and 12.3.1-T6's summary).
- Source-side index reuse: the roll-up's `bytes_stored`/`objects` query reuses `artifact (org_id, run_id)` is not sufficient (it needs `(org_id, project_id, state)`); add `artifact_project_state_idx on artifact (org_id, project_id, state)` for the daily scan (P4) — `project_id` is already a column on `artifact` (via `run_id`'s project scope, joined once, not per row; see §5 query).

## 5. API shapes (commands, queries, endpoints)

None — internal task + internal module call:

| Task type | Payload | Idempotency key |
|---|---|---|
| `usage.storage_rollup` | `{ }` (schedule `evidgate.storage-usage-rollup`, daily 02:00 UTC) | `(schedule_name, fire_at)` |
| `usage.storage_rollup.project` | `{ org_id, project_id, day }` | `storage-rollup:<org>:<project>:<day>` |

`usage.storage_rollup.project` handler, inside `ITenantScope.BeginAsync(org_id)`:

```sql
-- one statement, aggregated per project for the day (P2/P3)
select r.project_id, sum(a.bytes) as bytes_stored, count(*) as objects
from artifact a
join run r on r.org_id = a.org_id and r.id = a.run_id
where a.org_id = @org_id and r.project_id = @project_id and a.state = 'ready'
group by r.project_id;
```

then upserts `storage_usage_daily` (`ON CONFLICT (org_id, project_id, day) DO UPDATE`), reads `artifact_failures` with the sibling query from AC2, and (06.5.2-T2) calls `IUsageMeter.RecordAsync(orgId, projectId, "artifact_gb_month", quantity, billingKey)` and the equivalent for `egress_gb`.

## 6. States and transitions

None owned here — `storage_usage_daily` rows are append/upsert, not a state machine. The one behavioural rule: a row for `(org_id, project_id, day)` is only ever upserted by that day's own task run, never backfilled by a later day's run (idempotency key is day-scoped).

## 7. Jobs and integrations

- Schedule `evidgate.storage-usage-rollup`, Cronos `0 2 * * *` UTC (before retention's 03:00 fire, so the day's numbers reflect pre-deletion state for that day — deleted artifacts already excluded next day since they leave `state='ready'`), unique `(schedule_name, fire_at)` (00 §5.3).
- Egress bytes are read from `IObjectStore.GetDailyEgressBytes(orgId, day)` (01.8.1's storage adapter, ⚠️ provider-specific metric availability — some providers require a separate billing-export read). **T60 [DECISION]:** when the provider cannot report egress for a day, `egress_bytes` is written as `NULL` with `egress_unavailable_reason = 'unavailable'` — never a false `0` that would understate cost or silently zero out a metered event. Once `IObjectStore` gains the method (01.8.1) the same column starts recording real values; no migration is needed to flip the meaning.
- Handoff to 12: `IUsageMeter.RecordAsync` (defined by 12.3.1-T1/T2 in `Evidgate.Modules.Usage.Contracts`) is called once per metric per project per day, after the `storage_usage_daily` row commits (separate transaction, since it crosses module write boundaries — each module owns its own write per C4, no cross-module EF `DbContext` sharing). When `egress_bytes` is `NULL` (T60, provider cannot report it), the `egress_gb` metering call is skipped entirely for that day rather than emitting a false zero-quantity ledger row.
- Metrics (10.3.1-T3 catalogue): `evidgate_storage_bytes_stored{org_id,project_id}` ⚠️ — per-tenant label cardinality is flagged for 10.3.1-T3's review (S3 redaction list covers *values*, not org-id cardinality, which is 10's call), `evidgate_storage_objects`, `evidgate_storage_egress_bytes`, `evidgate_storage_rollup_failures_total`.

## 11. Rollout

- Ships enabled with `StorageUsageRollup:Enabled` (default on); until 01.8.1 adds `GetDailyEgressBytes`, every day's row carries `egress_bytes = NULL` + `egress_unavailable_reason = 'unavailable'` (T60) and no `egress_gb` ledger row is emitted — pricing (12) sees an explicit gap, never a silent zero.
- Monitoring: `evidgate_storage_rollup_failures_total` and the three storage gauges feed 10's per-unit cost report (10.9.1-T1) and monthly cost-spike review (10 risk table).
- Rollback: disable the schedule; `storage_usage_daily` simply stops advancing — no destructive state, and 12's ledger keeps its already-recorded rows untouched (append-only per D3).
