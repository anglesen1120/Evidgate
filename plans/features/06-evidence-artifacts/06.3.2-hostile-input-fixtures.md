## 1. Goal and non-goals

**Goal.** A committed, versioned corpus of hostile artifact bytes — XXE, billion-laughs, zip-bomb, path-traversal archive, truncated artifact — runs in CI against the 06.3.1 parser profile on every build and fails the build when any guard regresses; a separate coverage-guided fuzz harness runs the same entry points nightly, promoting any crash/timeout it finds into the committed corpus.

**Non-goals.** Building the parser guards themselves (06.3.1, already done); browser-level viewer isolation tests (06.3.3); trace/report serving (06.3.4); adapter-side (Node/TypeScript) fixture reuse beyond placing files where 04/11 can read them (their CI wiring is out of scope here).

## 2. User stories and acceptance criteria

- As the Tech Lead, I want a standing hostile-input corpus in CI, so a future refactor of the parser profile cannot silently regress a guard.
- As a security reviewer, I want coverage-guided fuzzing over the same entry points, so inputs outside the hand-written corpus are also covered without hand-authoring every case.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `fixtures/hostile/` contains at minimum: `xxe.xml`, `billion_laughs.xml`, `traversal.zip` (entry `../../etc/passwd`), `truncated_trace.zip`, `planted_secret.txt` (fixture reused by 06.2.3) — each with a one-line manifest entry naming the guard it exercises. `zipbomb.zip` and `oversized.bin` are generated at test time by a small script (`GenerateBombFixture`, `GenerateOversizedFixture`) rather than committed as binaries, since their only property that matters (entry ratio, declared size) is reproducible from a seed |
| AC2 | A CI job (`fixtures-hostile`) runs `HostileFixtureTests` against every file in `fixtures/hostile/` plus the two generated fixtures, through `IParsing`/`CompleteArtifactCommand`, asserting each is rejected with its documented `failure_code` and that none ever reaches `ready` |
| AC3 | Removing or weakening a guard (e.g. raising `MaxZipEntries` above the corpus's bomb size) makes at least one `HostileFixtureTests` case fail — proven by a mutation smoke: a deliberately weakened build variant makes the test run fail |
| AC4 | A nightly coverage-guided fuzz run (06.3.2-T2) seeded from the corpus runs the `IParsing` entry points for a 10-minute budget and reports zero unhandled exceptions/timeouts beyond the documented rejections; any crash/timeout it finds is promoted into `fixtures/hostile/` as a new fixture, not silently ignored |
| AC5 | The corpus directory is the single source fixture set: 04 (report parsing) and 11 (security test suite) reference `fixtures/hostile/` by path rather than keeping a second copy |

## 4. Data model and migrations

None. Fixtures are static files under `fixtures/hostile/` with a `manifest.json` (`{file, guard, expected_failure_code}`) plus two generator scripts for the large/ratio-based fixtures; no database objects.

## 5. API shapes (commands, queries, endpoints)

None new. The test suite drives the existing `IParsing` methods and `CompleteArtifactCommand` handler from 06.3.1 directly (in-process, no HTTP):

| Fixture | Driven through | Expected result |
|---|---|---|
| `xxe.xml`, `billion_laughs.xml` | `IParsing.ParseXmlReport` | `Result.Failure(artifact_invalid)` |
| `zipbomb.zip` (generated), `traversal.zip`, `truncated_trace.zip` | `IParsing.EnumerateArchive` | `Result.Failure(too_large \| artifact_invalid)` |
| `oversized.bin` (generated) | `CompleteArtifactCommand` (declared-size vs cap) | `rejected` / `too_large` |
| `planted_secret.txt` | 06.2.3 scanner (separate story; referenced, not re-tested here) | `masking_event` written |

## 6. States and transitions

None new; asserts the existing `uploaded → rejected` transition (00 §8.4) is reached for every corpus entry, never `ready`.

## 7. Jobs and integrations

- CI job `fixtures-hostile` (T1) runs on every PR; a separate nightly job `fixtures-fuzz` (T2) runs the fuzz harness on its own budget — wired into the pipeline owned by 01.7.1, this story only adds the job definitions and the xUnit/fuzz projects, not the CI platform itself.
- Fixture directory is a dependency surface for 04 (raw-report parsing reuse) and 11 (security test suite); both read, neither owns.
- Crash/timeout promotion from T2 writes new files into the same `fixtures/hostile/` directory T1 asserts against, so a promoted crash immediately becomes a permanent regression test once merged.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S5 | corpus + fuzz harness exercise exactly the guards S5 requires (DTD/entities off, depth/size/entry caps, timeout) with a fail-closed CI gate | AC2, AC4 |
| Regression safety | mutation smoke proves the gate actually fails on a weakened guard, not just on the guard's absence | AC3 |
| Coverage beyond hand-written cases | nightly coverage-guided fuzzing over the same `IParsing` entry points, findings promoted into the permanent corpus | AC4 |
| Supply chain (T40) | the fuzz tool (`SharpFuzz` ⚠️ licence checked in 01.1.1-T1) or its seeded-mutation fallback is licence-cleared before use, same gate as every other dependency | ADR-0002 row (01.1.1-T1) |
| Privacy | fixture bytes are synthetic (no real customer data); `planted_secret.txt` uses a recognizably fake key pattern, never a real credential shape reused elsewhere; generated fixtures (`zipbomb.zip`, `oversized.bin`) contain only deterministic filler bytes | fixture review at DoR |
| Retention/deletion impact | none (fixtures are source-controlled test data, not tenant data) | — |
| Authz | none — this story runs entirely in-process test code with no permission surface | — |

- **Authorization:** none; this story runs only in-process test code with no permission surface (see the Authz row above).
- **Retention/deletion:** none; fixtures are source-controlled synthetic test data, not tenant data.
- **Telemetry:** none beyond the CI result of the fixture and fuzz jobs; no runtime metric is added.
- **Failure path:** a fixture that is not rejected with its documented `failure_code` fails the gate; the mutation smoke proves a weakened cap turns the gate red.

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Every corpus fixture (committed + generated) rejected with its documented code | `HostileFixtureTests.RejectsAllCorpusFixtures` (AC2) |
| No fixture reaches `ready` | same test, assert final `artifact.state` |
| Guard weakening breaks the gate | `HostileFixtureMutationSmokeTests` (CI-only, runs the corpus against a build with one cap deliberately raised) (AC3) |
| Nightly fuzz budget finds no unreported crash | `fixtures-fuzz` job report (AC4) |
| A seeded crash is promoted into the corpus, not swallowed | `FuzzPromotionTests` (smoke-injects a crash, asserts a new fixture file + manifest row appear) (AC4) |
| 04/11 reuse the same corpus, not a duplicate | directory-reference check (`fixtures/hostile/` path exists, no second `xxe*.xml` copy elsewhere) (AC5) |

## 11. Rollout

- No feature flag: CI gates are enforced on merge to `develop` once `fixtures-hostile` (T1) and `fixtures-fuzz` (T2) are green.
- Merge order: T1.1 → T1.2 (blocking PR gate) → T1.3 (hardens the gate, same PR series) → T2 (separate PR once T1 is merged, since the fuzz harness seeds from the corpus T1 establishes).
- Monitoring: nightly fuzz job failure count; a crash/timeout triages into a new corpus fixture within one cycle (AC4).
- Rollback: revert the PR; no data or deployed state affected (test-only change).
