## 1. Goal and non-goals

**Goal.** A nightly scheduled job expires every artifact whose `expires_at` has passed under its project's `retention_policy`, deletes the storage object first, verifies absence, and only then marks the row `deleted`; a later pass hard-deletes the metadata row once `metadata_days` has elapsed. Every step is idempotent and survives a crash halfway.

**Non-goals.** The retention policy endpoint/table (`06.4.1-T1`); repair of orphans or stuck rows beyond the normal retry (06.4.3); tenant deletion (06.4.4); verification/alerting cycle (06.4.5); the `task` queue and Cronos scheduler themselves (01.5.1).

## 2. User stories and acceptance criteria

- As the platform, I delete expired evidence within the published retention period, so storage cost and PDPL exposure stay bounded.
- As an operator, a job that dies halfway leaves rows in `pending_delete` that the next run clears, so nothing silently lingers.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A `ready` artifact whose `expires_at` is past ends one run with its object absent in storage (`HEAD` → 404) and `state='deleted'` |
| AC2 | With an injected object-store failure on part of a batch, those rows stay `pending_delete` with `failure_code` set; the next task run deletes them and total object count converges |
| AC3 | A row is never deleted before its object: `deleted` is written only after a successful delete + `HEAD` verify; a crash between delete and verify leaves `pending_delete`, re-verified next run |
| AC4 | A second schedule fire for the same slot inserts no duplicate task (`unique (schedule_name, fire_at)`); a reprocessed `retention.project` task performs no second delete (idempotent) |
| AC5 | `deleted` rows remain readable until `created_at + metadata_days`; past that, the row and its `masking_event` children are hard-deleted |
| AC6 | Per-project values above the floor are honoured; a project with no `retention_policy` row uses defaults 14/90 (FR-06-10) |
| AC7 | Cross-tenant enumeration goes through the owner function only; each per-project task runs inside `ITenantScope` for that org (no `BYPASSRLS`) |
| AC8 | `evidgate_ops.retention_due_projects()` satisfies T80: `SET search_path = ''`, all references schema-qualified, `EXECUTE` granted to `evidgate_worker_sched` only (revoked from the app role), and every call writes an audit row |

## 5. API shapes (commands, queries, endpoints)

None — no endpoint. Internal task types only:

| Task type | Payload | Idempotency key |
|---|---|---|
| `retention.scan` | `{ }` (fired by schedule `evidgate.retention-scan`) | `(schedule_name, fire_at)` unique constraint |
| `retention.project` | `{ org_id, project_id }` | natural key `retention:<org>:<project>:<yyyy-mm-dd>` → `ON CONFLICT DO NOTHING` |

`retention.scan` calls `evidgate_ops.retention_due_projects()` and enqueues one `retention.project` per pair. `retention.project` runs inside `ITenantScope.BeginAsync(org_id)` (C3) and performs the select→mark→delete→verify→mark loop in bounded batches of 500.

## 6. States and transitions

| From | Event | To | Guard |
|---|---|---|---|
| `ready` | retention run, `expires_at` past | `pending_delete` | row claimed `FOR UPDATE SKIP LOCKED` |
| `pending_delete` | object deleted + `HEAD` 404 | `deleted` | verify inside the confirming transaction |
| `pending_delete` | delete/verify failed | `pending_delete` | `failure_code` set; retried next run |
| `deleted` | `created_at + metadata_days` past | row removed | metadata purge; children deleted first |

`deletion_job.state`: `queued → running → done | failed` (used only for escalations, §3).

## 7. Jobs and integrations

- Schedule `evidgate.retention-scan`, Cronos `0 3 * * *` UTC; any worker fires it; the unique `(schedule_name, fire_at)` insert (`ON CONFLICT DO NOTHING`) guarantees one task per fire — never a leader (00 §5.3).
- Object operations go through `IObjectStore` (01.8.1): delete, then `HEAD` verify. Per P5 no S3 call runs inside a DB transaction: **tx A** claims rows and marks `pending_delete`; **network** deletes + verifies; **tx B** marks `deleted`. Batch loop caps 500 rows per claim.
- Metrics (labels: none carrying tenant ids per S3 — org id only as metric attribute allowlisted by 10.3.1): `evidgate_retention_objects_deleted_total`, `evidgate_retention_pending_delete_backlog`, `evidgate_retention_failures_total`.

## 11. Rollout

- Config flag `Retention:Enabled` (default on) plus `Retention:DryRun` for the first deploy in each environment: dry-run logs the would-be deletions without touching storage; flip after one observed cycle.
- Monitoring: `evidgate_retention_pending_delete_backlog` and `dead_letter` depth on the `task` table (10's dashboards); 06.4.5 adds the independent verify pass.
- Rollback: disable the schedule — `pending_delete` rows simply resume when re-enabled; no data migration needed.
