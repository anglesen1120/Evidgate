## 1. Goal and non-goals

**Goal.** Prove, with re-run tests, that 06.4.2's retention job and 06.4.3's sweeper are idempotent and converge after a half-failure; wire alert rules onto their existing failure/backlog metrics so a stuck cycle is surfaced within one cycle instead of discovered later; assert that every repair and deletion path they take writes the audit row it claims to. This story adds **no new runtime job** — it is a test suite plus alerting configuration on top of 06.4.2/06.4.3's already-built mechanisms.

**Non-goals.** Performing any deletion or repair itself (06.4.2/06.4.3 own the repairs); a new convergence-checking task, schedule or query contract (deliberately not built here — the re-run tests are the proof, and alerting reuses the metrics 06.4.2/06.4.3 already emit); tenant deletion reporting (06.4.4 owns its own report); the alerting transport/routing itself (10.3.1-T5 owns notification channels — this story defines the two threshold rules and hands them to that pipeline).

## 2. User stories and acceptance criteria

- As the Tech Lead, I have a re-run test that proves idempotency end-to-end (retention half-fail → next run clears it; sweeper half-fail → next run clears it) before trusting the 14/90-day defaults with real customer data (06-O1).
- As the on-call operator, a persisting retention or sweeper backlog pages me within one cycle instead of silently growing.
- As an auditor, every repair 06.4.2/06.4.3 perform has a matching audit row, proven by an assertion, not by inspection.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Re-running 06.4.2's `retention.project` handler twice against a fixture with an injected half-failure leaves the second run with zero further changes and the object/row count converged (reuses 06.4.2's own fixtures, driven twice) |
| AC2 | Re-running 06.4.3's `sweep.org` handler twice against the same fixture set (stale upload, stuck `pending_delete`, missing object, orphan object) leaves the second run with zero further repairs and zero remaining orphans |
| AC3 | An alert rule fires when `evidgate_retention_pending_delete_backlog` stays > 0 across two consecutive scheduled fires (i.e. retention did not clear its own backlog in one cycle) |
| AC4 | An alert rule fires when `evidgate_sweep_orphans_open` stays > 0 across two consecutive hourly fires |
| AC5 | Every repair path in 06.4.2 (delete, metadata purge) and 06.4.3 (stale-upload reject, stuck-`pending_delete` redrive/escalate, `ready`-row-missing-object reject, orphan-object delete) is asserted to write its documented audit row; a path with no audit row fails the assertion |

- No new schedule. The re-run tests drive 06.4.2's `retention.project` handler and 06.4.3's `sweep.org` handler directly (in-process, via their existing command/handler types) inside the test harness, twice in a row against the same Testcontainers.PostgreSQL + SeaweedFS fixture.
