## 1. Goal and non-goals

**Goal.** After `complete` writes `ready` and an outbox row, an async `task` handler fetches the object, scans it against a secret-pattern set, sets `scan_state ∈ clean | flagged`, writes a `masking_event` for each match, raises the artifact's `sensitivity` to `sensitive` on any flag, and rejects the artifact only when the project has `reject_on_secret=true` — all without ever delaying `ready` (T19, FR-06-7).

**Non-goals.** Redaction/capture-disable at source (06.2.2, first line of defense); parser hardening for the scan's own file reading (06.3.1 supplies the safe XML/archive readers this task reuses, not re-implemented here); the secret taxonomy itself beyond a starter pattern set (11's `11.3.1-T3`/`T5` depend on this story's `masking_event` shape, not the other way — per 06 §10 "no 11 task defines the masking secret taxonomy").

## 2. User stories and acceptance criteria

- As a `tenant_admin`, a planted API key in an uploaded trace is detected shortly after upload, the artifact becomes `sensitive`, and I see a `masking_event` — without the upload ever being slowed down waiting for the scan.
- As a `tenant_admin` who set `reject_on_secret=true`, a matching artifact is moved out of evidence (`pending_delete`, reason `secret_rejected`) instead of merely flagged, so it never counts as evidence and the next evidence revision reports it missing.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `complete` returns `ready` immediately; the `artifact_secret_scan` outbox row exists but the scan has not necessarily run yet — `ready` is never blocked on the scan (T19, timing asserted by *not* awaiting the task in the `complete` test) |
| AC2 | The task handler scans the final object; a fixture containing a planted key (`AKIA[0-9A-Z]{16}`-shaped and a generic `-----BEGIN PRIVATE KEY-----` pattern) sets `scan_state=flagged`, writes one `masking_event` per distinct pattern class with `hit_count`, and raises `artifact.sensitivity` to `sensitive` |
| AC3 | A clean fixture sets `scan_state=clean`, writes no `masking_event`, and leaves `sensitivity` unchanged |
| AC4 | While `scan_state=pending` (task not yet run, or mid-run), the artifact is served as `sensitive` by every read path (06.2.1's resolver), regardless of its kind default |
| AC5 | With `artifact_kind_policy.reject_on_secret=true` for the artifact's `(org, project, kind)`, a flagged scan additionally transitions `state: ready → pending_delete` with `failure_code=secret_rejected` (the existing legal `ready → pending_delete` edge from 06.1.3, T57(b)) and a `masking_event{action='rejected'}` row; 06.4.2's deletion job then deletes the object as it would for any `pending_delete` row, and the next evidence freeze (06.5.1) reports `artifact_missing` for it. With `reject_on_secret=false` (default), the artifact stays `ready` and `sensitive` with `masking_event{action='flagged'}` |
| AC6 | The task is idempotent: replaying the same outbox row (retry after a transient failure) never writes a duplicate `masking_event` for the same `(artifact_id, pattern_class)` scan pass and never re-raises an already-flagged artifact twice |
| AC7 | A scan that cannot fetch the object (deleted out of band) leaves `scan_state=pending` and the task row moves to retry-then-`dead_letter` per 00 §5.3, without crashing the worker |

## 3. Contracts touched

- 06 §4 `masking_event` — implemented exactly (`id`, `org_id`, `artifact_id`, `pattern_class`, `hit_count`, `action`, `created_at`; append-only, `T3` unique).

## 4. Data model and migrations

Migration `migrations/NNNN_evidence_masking_event.sql`:

```sql
create table masking_event (
  id            uuid primary key,
  org_id        uuid not null,
  artifact_id   uuid not null,
  pattern_class text not null,        -- e.g. 'aws_access_key', 'private_key_pem', 'generic_bearer_token'
  hit_count     int not null check (hit_count > 0),
  action        text not null check (action in ('flagged','rejected')),
  created_at    timestamptz not null default now(),
  unique (org_id, id),                -- T3
  unique (org_id, artifact_id, pattern_class),  -- idempotent replay: one row per (artifact, pattern) scan outcome
  foreign key (org_id, artifact_id) references artifact (org_id, id)
);
alter table masking_event enable row level security;
alter table masking_event force row level security;
create policy masking_event_tenant on masking_event
  using (org_id = evidgate.current_org_id())
  with check (org_id = evidgate.current_org_id());
create index masking_event_artifact_idx on masking_event (org_id, artifact_id);
```

No change to `artifact` (columns `scan_state`, `sensitivity`, `state`, `failure_code` already exist from 06.1.1).

## 5. API shapes (commands, queries, endpoints)

No public endpoint — this is a background `task` handler.

| Type | Name | Shape |
|---|---|---|
| `ICommand<Result<Unit>>` (invoked by the task dispatcher, not HTTP) | `RunArtifactSecretScan` | input `{artifact_id}` from the outbox payload; handler fetches the object (`IObjectStorage.GetAsync`, before the tx per P5), runs the pattern set, then in one tenant transaction: upserts `masking_event` rows (`ON CONFLICT (org_id, artifact_id, pattern_class) DO NOTHING` for idempotent replay, AC6), sets `scan_state`, conditionally raises `sensitivity`, and — only when `reject_on_secret=true` and a match was found — transitions `state: ready → pending_delete` with `failure_code=secret_rejected` (T57(b); the existing legal 06.1.3 edge, never an illegal `ready → rejected`) |
| domain service | `SecretPatternScanner` | pure function `Scan(bytes) -> IReadOnlyList<(string PatternClass, int HitCount)>`; unit-tested against the starter pattern set, no I/O |

Natural idempotency key for the `task` row: `artifact_id` (00 §5.3); retries capped, then `dead_letter` visible to operators (AC7).

## 6. States and transitions

`scan_state`: `pending → clean` (no matches) or `pending → flagged` (≥1 match), written once per artifact (idempotent re-runs are no-ops via AC6's unique constraint plus a `scan_state` guard: the handler skips the scan-and-write step if `scan_state` is already `clean`/`flagged`).

`state`: this story's only effect on `state` is, when `reject_on_secret=true` and the scan flags a match, `ready → pending_delete` with `failure_code=secret_rejected` (TL ruling T57(b), README §3) — the same edge 06.1.3's guard already allows for retention, so no guard-table change is needed and no illegal `ready → rejected` transition is attempted. 06.4.2's deletion job then deletes the object exactly as it would for any `pending_delete` row (it does not distinguish *why* a row reached that state); the next evidence freeze (06.5.1) reports the artifact `artifact_missing` since it is no longer `ready`. Without `reject_on_secret`, the scan never touches `state`.

## 7. Jobs and integrations

- Consumer of the `artifact_secret_scan` outbox row written by 06.1.2-T2's `complete` handler.
- Depends on `IObjectStorage.GetAsync` (06.1.2's adapter) to fetch bytes; reuses 06.3.1's safe-parsing readers only if the scan needs to decompress an archive artifact before pattern-matching (e.g. a zipped trace) — plain byte/text scanning for other kinds needs no parser.
- Produces `masking_event` rows consumed by 11's security-event review (`11.3.1`) and by 09's UI (sensitivity badge).
- 06.4.2's retention deletion job (not owned by this story) is the sole executor of `pending_delete → deleted` for rows reaching that state via T57(b) as much as via normal retention aging — no separate deletion path is added here.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-06-7/T19 | scan is async via outbox+task, `ready` never delayed; `scan_state` gates sensitivity while `pending` | AC1, AC4 |
| P5 | object fetch happens before the tenant transaction opens; the transaction only does row writes | code review + `RunScan_NoNetworkInsideTransaction` (command-counter/interceptor test) |
| P1 | not a hot synchronous endpoint (it's a background task) — no latency budget from 00 §11's hot-endpoint list applies, but task queue lag is an operational SLI (00 §11) | 10's future dashboard; out of this story's proof surface |
| C7 | idempotent consumer via `ON CONFLICT DO NOTHING` on `(org_id, artifact_id, pattern_class)` and a `scan_state` short-circuit guard | AC6 |
| S1 | pattern matching is in-process regex/byte scanning, no SQL built from scan content; `masking_event.pattern_class` is an enum-like string from a fixed code list, never raw matched text (secret values never stored) | code review; `MaskingEvent_NeverStoresMatchedSecretValue` test |
| S3 | matched secret *values* are never persisted, logged or put in `masking_event` (only class + count) — the redaction list (00 §5.7 S3) extends to scan output | same test as above |
| T57(b) | `reject_on_secret` rejection is `ready → pending_delete` (`failure_code=secret_rejected`), the pre-existing 06.1.3 legal edge — never an illegal `ready → rejected` transition | AC5 |
| Authz | no endpoint; handler runs as the worker's own module-internal identity, not a request principal | — |
| PDPL | this is the "second line" masking control referenced in 06 §6's DPA rationale | — |
| Retention/deletion impact | `masking_event` rows are project-scoped, append-only, deleted by tenant deletion (06.4.4) alongside their artifact | — |

## 11. Rollout

- No feature flag beyond the existing per-project `reject_on_secret` (defaults `false`, per 06-O6's open question — alert-and-classify is the safe default until QA confirms V1 need).
- Monitoring: `masking_event` volume and `scan_state=flagged` rate are operational SLIs worth a 10 dashboard row (parser-error-adjacent "artifact-failure-rate" family, 00 §11).
- Rollback: revert the task handler registration; artifacts already `scan_state=pending` stay `pending` (served `sensitive`, safe fail-open-to-caution) until the handler is restored.
