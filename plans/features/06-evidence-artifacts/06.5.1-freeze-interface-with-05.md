## 1. Goal and non-goals

**Goal.** 06 exposes exactly one call, `Evidgate.Modules.Evidence.Contracts.IEvidenceFreeze.FreezeAsync(FreezeRequest)`, that 05's reconciler (05.3.2-T2) uses to get a snapshot of the run's `ready` artifacts grouped by requirement, with `(execution_key, attempt_no)` resolved to `case_attempt` (unresolved pairs reported as `artifact_missing` orphans), the required-artifact gaps and the completeness input. Resolving a pair persists `artifact.attempt_id` at freeze time (FR-06-1, the area plan's own column comment: "null until resolved at freeze, T17") — this is a small, idempotent, in-transaction write, not a side channel outside the call. 05 alone persists `evidence_revision` (FR-06-14) and a frozen revision is never mutated by a later call; on 06's side, once `artifact.attempt_id`, `object_key` and `checksum` are set on a `ready` row they are guarded against further change by a DB trigger (§4, §10 T3).

**Non-goals.** The `evidence_revision` table and its persistence (owned by 05.3.2-T5); the reconciler's event-count/producer comparison (05.3.2-T2); required-artifact *policy* definition — this plan resolves gaps against whatever requirement set 05/03 declares, it does not define which artifacts are required per case (03/07); late-evidence re-evaluation triggering (07.5.x, 05.3.2-T3).

## 2. User stories and acceptance criteria

- As 05's reconciler, I call one function and get back a complete, internally-consistent picture of a run's evidence, with the attempt link already resolved and durable, so I can decide `complete`/`incomplete` without touching `artifact` rows myself.
- As the platform, a `ready` artifact's evidentiary fields (`object_key`, `checksum`, resolved `attempt_id`) never change once set, so a decision made against them stays reproducible forever.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `FreezeAsync(FreezeRequest)` returns the set of `ready` artifacts for the run grouped by `(execution_key, attempt_no)`, each with `attempt_id` resolved via `case_attempt` when a matching row exists |
| AC2 | An artifact whose `(execution_key, attempt_no)` has no matching `case_attempt` row is returned as an orphan entry and contributes `artifact_missing` to the gap list, never silently dropped and never resolved to a wrong attempt; its `attempt_id` stays null |
| AC3 | A required artifact per the caller-supplied requirement set with no `ready` artifact at all appears in `missing[]` with a requirement-specific reason, distinct from `artifact_missing` (unresolved-orphan case) |
| AC4 | `attempt_id` resolution is idempotent: a `ready` artifact whose `attempt_id` was already set by a prior `FreezeAsync` call is never rewritten (`WHERE attempt_id IS NULL` guard); two consecutive calls with no new `ready` artifacts in between produce identical `FreezeResult` and issue no second `UPDATE` |
| AC5 | Once `attempt_id`, `object_key` or `checksum` is set on a `ready` artifact, a direct `UPDATE` attempting to change any of the three fails at the database (trigger), independent of any application-level guard — proving the invariant does not rely solely on 05 never re-calling `FreezeAsync` for a settled revision |
| AC6 | `FreezeAsync` runs entirely inside the caller's existing tenant transaction (no new transaction opened) and issues a bounded number of SQL statements regardless of artifact count (no N+1 per case): one read + one conditional `UPDATE`, never one per artifact |

## 4. Data model and migrations

`migrations/NNNN_evidence_freeze_immutability.sql` (DbUp; placeholder number) — owned by T3, no new table or column (attempt_id/object_key/checksum already exist on `artifact` per 06.1.1-T1):

```sql
create or replace function evidgate.artifact_ready_immutable_fields() returns trigger as $$
begin
  if OLD.state = 'ready' then
    if NEW.object_key is distinct from OLD.object_key
       or NEW.checksum is distinct from OLD.checksum
       or (OLD.attempt_id is not null and NEW.attempt_id is distinct from OLD.attempt_id) then
      raise exception 'artifact % : object_key/checksum/attempt_id are immutable once ready', OLD.id
        using errcode = 'integrity_constraint_violation';
    end if;
  end if;
  return NEW;
end;
$$ language plpgsql;

create trigger artifact_ready_immutable_fields
  before update on artifact
  for each row execute function evidgate.artifact_ready_immutable_fields();
```

The one exception the trigger allows is the initial `NULL → value` fill of `attempt_id` on a `ready` row — this is what `FreezeAsync`'s `UPDATE` performs (T2), guarded application-side by `WHERE attempt_id IS NULL` and now also guarded at the database once set.

Query shape used by `FreezeAsync` (single round trip per statement, P2/P3):

```sql
-- T1: one statement, ready artifacts for the run left-joined to case_attempt by (execution_key, attempt_no).
-- org_id and project_id come from the ambient tenant scope, never from a caller value. artifact's RLS policy is
-- org-only (migrations/0028_evidence_artifact.sql:106-111), so the project predicate is the only thing that
-- honours a project-scoped caller — IEvidenceFreeze.cs:32-33 promises another project's run yields no artifacts.
select a.id as artifact_id, a.execution_key, a.attempt_no, a.kind, a.object_key, a.checksum, a.sensitivity,
       a.attempt_id as current_attempt_id, ca.id as resolved_attempt_id
from public.artifact a
left join public.case_attempt ca
  on ca.org_id = a.org_id and ca.run_id = a.run_id
 and ca.execution_key = a.execution_key and ca.attempt_no = a.attempt_no
where a.org_id = @org_id
  and a.run_id = @run_id
  and (@project_id::uuid is null or a.project_id = @project_id::uuid)
  and a.state = 'ready'
order by a.execution_key, a.attempt_no, a.kind, a.id;   -- cosmetic: the service re-orders in C# (ordinal)

-- T2: at most one statement, resolving and persisting attempt_id for the rows newly matched (idempotent).
-- The batch travels as ONE jsonb text parameter — the tenant Dapper path refuses array parameters
-- (precedent CaseAttemptSql.cs) — and is expanded server-side. The same org/project/run guards here mean a
-- forged id in the batch reaches no row.
update public.artifact as a set attempt_id = r.resolved_attempt_id
from jsonb_to_recordset(@rows::jsonb) as r(id uuid, resolved_attempt_id uuid)
where a.org_id = @org_id
  and a.run_id = @run_id
  and (@project_id::uuid is null or a.project_id = @project_id::uuid)
  and a.state = 'ready'
  and a.attempt_id is null
  and a.id = r.id;
```

The T2 statement is issued only when at least one read row has a null current `attempt_id` and a resolved `case_attempt`, so a fully resolved re-freeze writes nothing, and `attempt_id is null` keeps it idempotent. Two stored-value cases are integrity violations refused application-side with `InvalidOperationException` and nothing rewritten, because the composite FK `(org_id, attempt_id)` does not pin the attempt to the run: a stored `attempt_id` that differs from the resolved `case_attempt`, and a stored `attempt_id` on a row whose pair resolves to **no** `case_attempt` at all — fail-closed, since reporting that row as an orphan would leave a non-null `attempt_id` on an orphan.

Existing index `artifact (org_id, run_id)` (06.1.1-T1) covers the run-scoped scan; `case_attempt (org_id, run_id, execution_key, attempt_no)` unique index (05.3.3-T1) covers the join; the `UPDATE` targets by primary key (`org_id, id`), covered by `artifact`'s own `unique (org_id, id)`.

## 5. API shapes (commands, queries, endpoints)

No HTTP endpoint. Internal service contract only:

| Call | Kind | Notes |
|---|---|---|
| `IEvidenceFreeze.FreezeAsync(FreezeRequest)` | internal `.Contracts` service call (C7), not a Mediator query/command | runs inside the caller's ambient tenant transaction; T1's read is one statement, T2's `attempt_id` persistence is one bounded `UPDATE … FROM jsonb_to_recordset(…)` statement — two statements total regardless of artifact count (P2/P3) |

Request/result member shapes the caller binds to:

| Type | Shape | Notes |
|---|---|---|
| `FreezeRequest` | `record FreezeRequest(Guid RunId, IReadOnlyList<RequiredArtifactSpec> Required)` | `MaxRequired = 10 000`; the request and every element are validated before the tenant-scope guard and before any SQL (§8 Failure path) |
| `RequiredArtifactSpec` | `record RequiredArtifactSpec(string ExecutionKey, string Kind, string ReasonCode, int? AttemptNo = null)` | `ExecutionKey` is the 64-char lowercase hex key of T17; `Kind` is one of the `artifact` table's closed kinds (`trace`, `video`, `screenshot`, `raw_report`, `dom_snapshot`, `a11y_snapshot`, `patch`, `ui_hierarchy`); `ReasonCode` matches `^[a-z][a-z0-9_]{0,63}$` and is forwarded verbatim into `MissingReason.Code`; a null `AttemptNo` matches any attempt of the pair |
| `MissingReason` | `record MissingReason(string Code, MissingSource Source, string ExecutionKey, string Kind, int? AttemptNo, Guid? ArtifactId)` | `Source` is `Orphan` (a `ready` artifact with no `case_attempt` for its pair; `ArtifactId` set, `Code` = `artifact_missing`) or `Requirement` (a declared spec with no matching resolved artifact; `ArtifactId` null, `Code` = the spec's own `ReasonCode`) — this is how AC2 and AC3 stay distinct even when the caller declares `artifact_missing` itself |

A requirement is met iff at least one **resolved** (`case_attempt`-bound), `ready` artifact has the same `ExecutionKey`, the same `Kind` and, when the spec names one, the same `AttemptNo`. An orphan never satisfies a requirement: it is reported only as its own `MissingSource.Orphan` gap, so a run whose only artifact for a pair has no `case_attempt` carries that artifact in `Orphans` (not in `Ready`) and also gets the `Requirement` gap for that pair. Duplicate specs collapse to one gap.

`ArtifactSetHash` is `sha256:<hex>` (00 §7) of the RFC 8785 canonical JSON of the **whole ready set — resolved and orphaned artifacts together** — as an array of `{"artifact_id", "object_key", "checksum"}` objects in the order of `(execution_key, attempt_no, kind, artifact id)`, hashed with `CanonicalHash.Compute` (`src/BuildingBlocks/Canonicalization`, the same canonicalization `manifest_hash`/`policy_hash` use, 00 §3 glossary). It is independent of DB row order and excludes `attempt_id`: that is resolved metadata about the artifact, not part of what makes the artifact itself, so resolving an orphan later never changes the hash. The empty set hashes the canonical JSON of `[]`.

`MissingReason` values used here: `artifact_missing` (T17 orphan case) and pass-through of requirement-declared reasons (e.g. a caller-declared required kind absent) — the *reason vocabulary itself* is 00 §8.5's, this call only classifies against it.

## 6. States and transitions

None owned here (`artifact` states are 06.1.3's; `evidence_revision` states are 05.3.2-T5's). This story adds one behavioural guarantee, enforced two ways: application-side (`WHERE attempt_id IS NULL` on the resolving `UPDATE`, plus an `InvalidOperationException` when a `ready` row already holds an `attempt_id` while its pair resolves to no `case_attempt` — an orphan may never keep a non-null `attempt_id`) and database-side (the T3 trigger rejecting any further change to `object_key`/`checksum`/a once-set `attempt_id` on a `ready` row) — mirroring C6's "immutability... enforced both in the domain type (no setters) and in SQL (trigger or `REVOKE UPDATE`)" pattern already used for manifests/revisions.

## 7. Jobs and integrations

- Called synchronously by 05's reconciler (05.3.2-T2) inside the reconcile transaction, after 05 has already resolved acknowledged events and closed producer slots; 06 does not open its own transaction (C3 — one tenant transaction per request/task, shared here with the caller).
- No outbox row is written by this call — the `attempt_id` resolution is a local, single-module write with no external consumer of its own; 05 is responsible for the outbox row that later triggers evaluation off the persisted revision.
- Late-artifact path: when a `ready` artifact lands after 05 has already frozen and persisted revision N, 05's late window (05.3.2-T3) calls `FreezeAsync` again to produce the input for a *new* revision N+1 — the new artifact's `attempt_id` resolves for the first time (still idempotent, `WHERE attempt_id IS NULL`); already-resolved artifacts from revision N are untouched (both by the `WHERE` guard and by the T3 trigger). 06.5.1-T3 documents this boundary explicitly.

| 00 §5.7 P2 | both the join and the resolution `UPDATE` are single statements (no per-artifact lookup/write loop) | code review + P3 test above |
| 00 §5.7 P5 | no network call inside the transaction (pure DB read + DB write, no S3/HTTP) | code review |

| Retention/deletion impact | none — reads/writes only `ready` rows; a retention-deleted artifact simply stops appearing (already excluded by `state='ready'` filter); the trigger only guards `ready` rows, so retention's own `ready → pending_delete → deleted` transition is unaffected | code review |

- **Authorization:** no endpoint in this story, so no new permission or route: `FreezeAsync` is an internal `.Contracts` call that runs under the ambient tenant scope its caller already opened (implementation inside `Evidgate.Modules.Evidence`) — it has no principal, permission or scope of its own, and the reconcile task that calls it is outbox-dispatched, so the finalize request's `event:write` authorization stays 05.3.2's (§8); a missing ambient scope is refused with `InvalidOperationException` before any statement.
- **Telemetry:** none added by T1/T2 — no metric, activity or log record is emitted from this call; the path is covered by 05's reconcile-latency histogram (T28) and the caller's own module span, and the only durable trace of a freeze is the `attempt_id` resolution it persists plus the `evidence_revision` 05 writes.
- **Failure path:** invalid request (null, empty `RunId`, more than 10 000 specs, a malformed `ExecutionKey`/`Kind`/`ReasonCode`, `AttemptNo < 1`) is an `ArgumentException`/`ArgumentNullException` raised before the scope guard and before any statement; no ambient tenant scope is `InvalidOperationException`; a stored `attempt_id` is `InvalidOperationException` and nothing is rewritten in either integrity case — it disagrees with the resolved `case_attempt`, or its pair resolves to no `case_attempt` at all (fail-closed: an orphan may not keep a non-null `attempt_id`). Every refusal leaves the resolution unwritten, and 05 rolls its transaction back, so a retry re-freezes from the same `ready` rows; a run invisible to the ambient scope (org-only RLS plus the explicit org and project predicates) returns no artifacts, so every requirement is missing — never complete.

1. **[DECISION] D-S57-Q1 — `FreezeAsync(FreezeRequest request, CancellationToken ct)` returning `Task<FreezeResult>`, not `Freeze(runId)`.** Decided by the coordinator (owner rule 2026-10-23), recorded for owner review. The name and the request object follow this plan (§3, §5) over 05.3.2's shorthand `Freeze(runId)`, which the 05.3.2 plan now spells correctly; `Task` (not `ValueTask`) matches the module's other `.Contracts` services.
2. **[DECISION] D-S57-Q2 — `RequiredArtifactSpec(ExecutionKey, Kind, ReasonCode, AttemptNo?)` with the caller's `ReasonCode` forwarded verbatim.** Decided by the coordinator (owner rule 2026-10-23), recorded for owner review. 06 does not own the required-artifact vocabulary: it echoes the spec's own `ReasonCode` into `MissingReason.Code`, and keeps AC2/AC3 distinct through `MissingReason.Source` (`Orphan` vs `Requirement`) even when 05 itself declares `artifact_missing` for a requirement gap.
3. **[DECISION] An orphan never satisfies a requirement.** A requirement is met only by a resolved (`case_attempt`-bound), `ready` artifact with the same `execution_key`, kind and (when the spec names it) `attempt_no`; an unresolved pair is reported once as an orphan gap, and a spec covering that pair adds its own `Requirement` gap. Duplicate specs collapse to one gap.
4. **[DECISION] `Ready` and `Orphans` are flat lists ordered `(execution_key, attempt_no, kind, artifact id)`, ordinal.** Decided by the coordinator; this is the "grouped by `(execution_key, attempt_no)`" of AC1 — the caller groups, 06 guarantees a deterministic order that does not depend on DB collation or physical row order (`attempt_no` and id compared as their invariant string forms).
5. **[DECISION] `ArtifactSetHash` covers all `ready` artifacts (resolved and orphans).** Canonical JSON array of `{"artifact_id","object_key","checksum"}` in the order of item 4, hashed with `CanonicalHash.Compute` (RFC 8785) as `sha256:<hex>` (00 §7); `attempt_id` is excluded; the empty set hashes the array `[]`.
6. **[DECISION] Both statements carry explicit org, run and project predicates.** §4's snippet plus `run_id`, `state = 'ready'` and — on both the T1 read and the T2 `UPDATE` — `(@project_id::uuid is null or a.project_id = @project_id::uuid)`, all taken from the ambient scope, never from a caller value. `artifact`'s RLS policy is org-only (`migrations/0028_evidence_artifact.sql:106-111`), so the project predicate is the only thing honouring a project-scoped caller, which the contract promises (`IEvidenceFreeze.cs:32-33`: another project's run yields no artifacts); it is load-bearing, not decoration. The T2 statement keeps `attempt_id is null`, takes its batch as one jsonb text parameter expanded with `jsonb_to_recordset` (the tenant Dapper path refuses array parameters; precedent `CaseAttemptSql.cs`), and is skipped entirely when nothing is newly resolved — two statements per call regardless of artifact count (P3). No `attempt_id` that is already set is ever rewritten.
7. **[DECISION] A stored `attempt_id` that disagrees with the resolution throws `InvalidOperationException`, in both integrity cases.** (a) It differs from the resolved `case_attempt`; (b) its `(execution_key, attempt_no)` resolves to **no** `case_attempt` at all — fail-closed, because reporting such a row as an orphan would leave a non-null `attempt_id` on an orphan. The composite FK `(org_id, attempt_id)` does not pin the attempt to the run, so neither case may be overwritten or reinterpreted; nothing is written and nothing else on the row changes.
8. **[DECISION] A run invisible to the ambient scope yields no artifacts, so every requirement is missing.** The read is `org_id`-scoped from the tenant scope of the caller (as `ArtifactCompletionVerifier`/`CaseAttemptWriter` do); an unknown or foreign run id returns no rows and therefore a not-ready result, never an error that would let a caller probe for another tenant's runs.
9. **[DECISION] `MaxRequired = 10 000` and request validation runs before the scope guard and before any statement.** Empty `RunId`, more than `MaxRequired` specs, an `ExecutionKey` not matching `^[0-9a-f]{64}$`, a `Kind` outside the artifact table's closed list, a `ReasonCode` not matching `^[a-z][a-z0-9_]{0,63}$` or `AttemptNo < 1` is an `ArgumentException`; a null request or element is `ArgumentNullException`.
10. **[DECISION] No migration is added by T1/T2.** Migration 0028 already grants `update (attempt_id, …)` on `artifact` to the app role and 0032 added the `artifact → case_attempt` FK; the existing `artifact_run_idx` (`org_id, run_id` where `state <> 'deleted'`) and the `case_attempt (org_id, run_id, execution_key, attempt_no)` unique index cover both statements.
11. **The immutability trigger and its two tests stay with 06.5.1-T3.** `Freeze_TriggerRejectsDirectUpdate_BypassingApplication` and `Freeze_LateArtifact_ResolvesOnlyNewRows_LeavesFrozenRowsUntouched` need T3's migration and 07.5.1's late-evidence policy, so T1/T2 do not claim them; the application-side `where attempt_id is null` guard is the only protection until T3 lands.

Hand-overs:

- **05.3.2-T2.4** calls `FreezeAsync(new FreezeRequest(runId, required))` and owns resolving `required` from the run's manifest and the policy in force (06 does not derive the requirement set, §1); it maps `MissingReason.Code` into `evidence_revision.missing[]` and `FreezeResult.ArtifactSetHash` into `evidence_revision.artifact_set_hash` (05.3.2 plan §10 T2 Notes).
- **07.2.1** reads `missing[]` only through 05's persisted `evidence_revision`; it never calls `IEvidenceFreeze` and never queries `artifact` rows.

## 11. Rollout

- No feature flag: this is a pure internal contract consumed only by 05's reconciler, which itself gates evidence-freeze usage behind its own M2 rollout (05.3.2-T2).
- Monitoring: `Freeze_BoundedQueries_NoNPlus1`'s statement-count assertion and the T3 trigger are the permanent guards against regression; no runtime metric owned here (05's reconcile-latency histogram, T28, covers the end-to-end path).
- Rollback: revert the PR; 05.3.2-T2 cannot function without this interface, so rollback of 06.5.1 implies rollback of 05.3.2-T2 in the same release train (bundle noted in `plans/features/README.md` §5.3). The T3 trigger is additive-only (rejects writes it would not otherwise allow), so it can be dropped independently without breaking T1/T2.
