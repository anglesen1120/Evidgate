## 1. Goal and non-goals

**Goal.** 06 exposes exactly one call, `Evidgate.Modules.Evidence.Contracts.IEvidenceFreeze.FreezeAsync(runId)`, that 05's reconciler (05.3.2-T2) uses to get a snapshot of the run's `ready` artifacts grouped by requirement, with `(execution_key, attempt_no)` resolved to `case_attempt` (unresolved pairs reported as `artifact_missing` orphans), the required-artifact gaps and the completeness input. Resolving a pair persists `artifact.attempt_id` at freeze time (FR-06-1, the area plan's own column comment: "null until resolved at freeze, T17") — this is a small, idempotent, in-transaction write, not a side channel outside the call. 05 alone persists `evidence_revision` (FR-06-14) and a frozen revision is never mutated by a later call; on 06's side, once `artifact.attempt_id`, `object_key` and `checksum` are set on a `ready` row they are guarded against further change by a DB trigger (§4, §10 T3).

**Non-goals.** The `evidence_revision` table and its persistence (owned by 05.3.2-T5); the reconciler's event-count/producer comparison (05.3.2-T2); required-artifact *policy* definition — this plan resolves gaps against whatever requirement set 05/03 declares, it does not define which artifacts are required per case (03/07); late-evidence re-evaluation triggering (07.5.x, 05.3.2-T3).

## 2. User stories and acceptance criteria

- As 05's reconciler, I call one function and get back a complete, internally-consistent picture of a run's evidence, with the attempt link already resolved and durable, so I can decide `complete`/`incomplete` without touching `artifact` rows myself.
- As the platform, a `ready` artifact's evidentiary fields (`object_key`, `checksum`, resolved `attempt_id`) never change once set, so a decision made against them stays reproducible forever.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `FreezeAsync(runId)` returns the set of `ready` artifacts for the run grouped by `(execution_key, attempt_no)`, each with `attempt_id` resolved via `case_attempt` when a matching row exists |
| AC2 | An artifact whose `(execution_key, attempt_no)` has no matching `case_attempt` row is returned as an orphan entry and contributes `artifact_missing` to the gap list, never silently dropped and never resolved to a wrong attempt; its `attempt_id` stays null |
| AC3 | A required artifact per the caller-supplied requirement set with no `ready` artifact at all appears in `missing[]` with a requirement-specific reason, distinct from `artifact_missing` (unresolved-orphan case) |
| AC4 | `attempt_id` resolution is idempotent: a `ready` artifact whose `attempt_id` was already set by a prior `FreezeAsync` call is never rewritten (`WHERE attempt_id IS NULL` guard); two consecutive calls with no new `ready` artifacts in between produce identical `FreezeResult` and issue no second `UPDATE` |
| AC5 | Once `attempt_id`, `object_key` or `checksum` is set on a `ready` artifact, a direct `UPDATE` attempting to change any of the three fails at the database (trigger), independent of any application-level guard — proving the invariant does not rely solely on 05 never re-calling `FreezeAsync` for a settled revision |
| AC6 | `FreezeAsync` runs entirely inside the caller's existing tenant transaction (no new transaction opened) and issues a bounded number of SQL statements regardless of artifact count (no N+1 per case): one read + one conditional `UPDATE`, never one per artifact |

## 3. Contracts touched

- New public contract: `Evidgate.Modules.Evidence.Contracts.IEvidenceFreeze` — `Task<FreezeResult> FreezeAsync(FreezeRequest request, CancellationToken ct)`; `FreezeRequest { Guid RunId, IReadOnlyList<RequiredArtifactSpec> Required }`; `FreezeResult { IReadOnlyList<FrozenArtifact> Ready, IReadOnlyList<OrphanArtifact> Orphans, IReadOnlyList<MissingReason> Missing, string ArtifactSetHash }`. Consumed by `Evidgate.Modules.Runs` (05) only, referenced via the `.Contracts` project per 00 §5.5 module-shape rule (C7 — no cross-module `Domain`/`Infrastructure` reference). `FreezeAsync` is **not** itself a Mediator `IQuery`/`ICommand`: it is an internal cross-module service call, invoked from inside 05.3.2-T2's own command handler, sharing that handler's already-open tenant transaction and write authorization — the same pattern 06.5.2 uses for `IUsageMeter.RecordAsync`. C1's "queries never write" split applies to Mediator-pipeline handlers; it does not forbid a `.Contracts` service invoked by one handler from performing a small, in-transaction, idempotent write of its own module's data.
- 05.3.2-T5's `evidence_revision.artifact_set_hash` — sourced directly from this call's `FreezeResult.ArtifactSetHash`; hash algorithm and canonical ordering are this plan's responsibility (§5).
- 00 §8.5 `missing[]` codes — this call emits only `artifact_missing` for unresolved orphans and forwards requirement-declared reason codes (00 §8.5 owns the code list; this plan does not invent new codes beyond `artifact_missing`, already named in T17).
- `artifact.attempt_id`, `object_key`, `checksum` — a new immutability trigger (T3) guards all three once a `ready` row has them set; this is new SQL enforcement, not a contract change to the columns themselves (both already exist per 06.1.1-T1's migration).
- No endpoint, no permission change (internal module call, not `/v1`).
- Resolved (area plan authoritative): `plans/06-evidence-artifacts.md:252` lists 06.5.1-T3's dependencies as `06.5.1-T1, 07.5.1` — the `07.5.1` (late-evidence policy) dependency is real for T3's late-artifact-path behaviour, and §10 below follows the area plan.

## 4. Data model and migrations

`migrations/NNNN_evidence_freeze_immutability.sql` (DbUp; placeholder number) — owned by T3, no new table or column (attempt_id/object_key/checksum already exist on `artifact` per 06.1.1-T1):

```sql
create or replace function evidgate.artifact_ready_immutable_fields() returns trigger as $$
begin
  if OLD.state = 'ready' then
    if NEW.object_key is distinct from OLD.object_key
       or NEW.checksum is distinct from OLD.checksum
       or (OLD.attempt_id is not null and NEW.attempt_id is distinct from OLD.attempt_id) then
      raise exception 'artifact % : object_key/checksum/attempt_id are immutable once ready', OLD.id
        using errcode = 'integrity_constraint_violation';
    end if;
  end if;
  return NEW;
end;
$$ language plpgsql;

create trigger artifact_ready_immutable_fields
  before update on artifact
  for each row execute function evidgate.artifact_ready_immutable_fields();
```

The one exception the trigger allows is the initial `NULL → value` fill of `attempt_id` on a `ready` row — this is what `FreezeAsync`'s `UPDATE` performs (T2), guarded application-side by `WHERE attempt_id IS NULL` and now also guarded at the database once set.

Query shape used by `FreezeAsync` (single round trip per statement, P2/P3):

```sql
-- T1: one statement, ready artifacts for the run left-joined to case_attempt by (execution_key, attempt_no)
select a.id, a.kind, a.execution_key, a.attempt_no, a.object_key, a.checksum, a.sensitivity,
       a.attempt_id as current_attempt_id, ca.id as resolved_attempt_id
from artifact a
left join case_attempt ca
  on ca.org_id = a.org_id and ca.run_id = a.run_id
 and ca.execution_key = a.execution_key and ca.attempt_no = a.attempt_no
where a.org_id = @org_id and a.run_id = @run_id and a.state = 'ready'
order by a.execution_key, a.attempt_no, a.kind;

-- T2: one statement, resolves and persists attempt_id for rows newly matched (idempotent)
update artifact set attempt_id = v.resolved_attempt_id
from (values (@ids, @resolved_ids)) as v(id, resolved_attempt_id)
where artifact.org_id = @org_id and artifact.id = v.id and artifact.attempt_id is null;
```

Existing index `artifact (org_id, run_id)` (06.1.1-T1) covers the run-scoped scan; `case_attempt (org_id, run_id, execution_key, attempt_no)` unique index (05.3.3-T1) covers the join; the `UPDATE` targets by primary key (`org_id, id`), covered by `artifact`'s own `unique (org_id, id)`.

## 5. API shapes (commands, queries, endpoints)

No HTTP endpoint. Internal service contract only:

| Call | Kind | Notes |
|---|---|---|
| `IEvidenceFreeze.FreezeAsync(FreezeRequest)` | internal `.Contracts` service call (C7), not a Mediator query/command | runs inside the caller's ambient tenant transaction; T1's read is one statement, T2's `attempt_id` persistence is one bounded `UPDATE … FROM (VALUES …)` statement — two statements total regardless of artifact count (P2/P3) |

`ArtifactSetHash` = `sha256` over the canonically-ordered (by `execution_key`, `attempt_no`, `kind`, `id`) list of `(artifact_id, object_key, checksum)` tuples — deterministic regardless of DB row physical order, matching the canonicalization approach already used for `manifest_hash`/`policy_hash` (00 §3 glossary; `Evidgate.Canonicalization`). `attempt_id` is intentionally excluded from the hash: it is resolved metadata about the artifact, not part of what makes the artifact itself; two freezes that resolve the same orphan differently (impossible under T17's unique-pair rule, but kept out of the hash on principle) would not spuriously change `ArtifactSetHash`.

`MissingReason` values used here: `artifact_missing` (T17 orphan case) and pass-through of requirement-declared reasons (e.g. a caller-declared required kind absent) — the *reason vocabulary itself* is 00 §8.5's, this call only classifies against it.

## 6. States and transitions

None owned here (`artifact` states are 06.1.3's; `evidence_revision` states are 05.3.2-T5's). This story adds one behavioural guarantee, enforced two ways: application-side (`WHERE attempt_id IS NULL` on the resolving `UPDATE`) and database-side (the T3 trigger rejecting any further change to `object_key`/`checksum`/a once-set `attempt_id` on a `ready` row) — mirroring C6's "immutability... enforced both in the domain type (no setters) and in SQL (trigger or `REVOKE UPDATE`)" pattern already used for manifests/revisions.

## 7. Jobs and integrations

- Called synchronously by 05's reconciler (05.3.2-T2) inside the reconcile transaction, after 05 has already resolved acknowledged events and closed producer slots; 06 does not open its own transaction (C3 — one tenant transaction per request/task, shared here with the caller).
- No outbox row is written by this call — the `attempt_id` resolution is a local, single-module write with no external consumer of its own; 05 is responsible for the outbox row that later triggers evaluation off the persisted revision.
- Late-artifact path: when a `ready` artifact lands after 05 has already frozen and persisted revision N, 05's late window (05.3.2-T3) calls `FreezeAsync` again to produce the input for a *new* revision N+1 — the new artifact's `attempt_id` resolves for the first time (still idempotent, `WHERE attempt_id IS NULL`); already-resolved artifacts from revision N are untouched (both by the `WHERE` guard and by the T3 trigger). 06.5.1-T3 documents this boundary explicitly.

## 11. Rollout

- No feature flag: this is a pure internal contract consumed only by 05's reconciler, which itself gates evidence-freeze usage behind its own M2 rollout (05.3.2-T2).
- Monitoring: `Freeze_BoundedQueries_NoNPlus1`'s statement-count assertion and the T3 trigger are the permanent guards against regression; no runtime metric owned here (05's reconcile-latency histogram, T28, covers the end-to-end path).
- Rollback: revert the PR; 05.3.2-T2 cannot function without this interface, so rollback of 06.5.1 implies rollback of 05.3.2-T2 in the same release train (bundle noted in `plans/features/README.md` §5.3). The T3 trigger is additive-only (rejects writes it would not otherwise allow), so it can be dropped independently without breaking T1/T2.
