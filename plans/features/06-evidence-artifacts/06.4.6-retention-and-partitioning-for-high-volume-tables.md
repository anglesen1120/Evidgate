## 1. Goal and non-goals

**Goal.** Decide, before the first production row exists, how `event`, `event_batch`, `case_attempt` and `evaluation` are retained and whether they are partitioned, without losing the dedupe guarantee. T1 is the ADR (this plan fixes the chosen default, §3). T2 builds the partitioned schema plus a job that creates and drops partitions with audit rows. T3 proves dedupe across a partition boundary, that a retention drop leaves the run readable, and that backup/restore keeps the partitions.

**Non-goals.** Artifact and object retention (06.4.1/06.4.2); the deletion verification suite (06.4.5); tenant deletion (06.4.4, which still deletes rows of partitioned tables by `org_id`); read-model tables such as `case_result_history` (03.9.1, derived and rebuildable); audit-log retention (02.7.1); archiving to cold storage (not V1).

## 2. User stories and acceptance criteria

- As an operator, ingest stays fast and old event data is removed by a cheap metadata operation, not a billion-row `DELETE`.
- As a release manager, an old run still shows its decision and evidence summary after raw events are gone.
- As an engineer, a retried batch is deduplicated whether it lands before or after a month boundary.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | The ADR `docs/adr/NNNN-event-table-partitioning.md` records the options in §3, the chosen default, the retention windows per table and the consequences; `scripts/check-adr.sh` passes |
| AC2 | After the migration, `event`, `event_batch` and `case_attempt` are range-partitioned by `run_created_at` (monthly); the dedupe key `(org_id, run_id, event_id, run_created_at)` is unique on the partitioned table and `(org_id, run_id, event_id)` uniqueness holds globally because `run_created_at` is determined by `run_id` |
| AC3 | A batch whose `event_id`s were first committed in month M and are retried after the month boundary (received month M+1) returns `duplicate` for same-hash and 409 `duplicate_different_payload` for a different hash; no second row exists |
| AC4 | An insert whose `run_created_at` differs from the run row's `created_at` is impossible: the composite FK `(org_id, run_id, run_created_at)` → `run (org_id, id, created_at)` rejects it |
| AC5 | The maintenance job keeps partitions for the current month plus the next 3 present (idempotent re-run creates nothing new) and writes one audit row per create/drop; if fewer than 2 future partitions exist the alert `partition_runway_low` fires; a row that would land in no partition goes to the `DEFAULT` partition and raises `partition_default_nonempty` |
| AC6 | A partition is dropped only when its upper bound is older than the retention ceiling for that table (§3 table), no run in it is non-terminal, and 06.4.2's artifact deletion for those runs has completed; otherwise the job skips it, writes a `skipped` audit row with the reason, and alerts after 2 cycles |

| AC8 | `evaluation` is not partitioned and never deleted before its decision's metadata window: its retention is `max(metadata_days of its project, the life of the release record that references it)`; an evaluation referenced by a release decision is never dropped by any job |

## 3. Contracts touched

**The constraint.** PostgreSQL requires a unique constraint on a partitioned table to include every partition-key column (⚠️ to re-verify against the PostgreSQL 18 docs in T1.1: ddl-partitioning "Limitations"). So `(org_id, run_id, event_id)` cannot stay unique across time partitions if the partition key is `received_at`.

**Options (T1 decides; default chosen).**

| Option | Partition key | Dedupe after change | Cost / risk | Verdict |
|---|---|---|---|---|
| A. Partition by `received_at`, unique `(org_id, run_id, event_id, received_at)` | receive time | **lost across boundary**: a retry received next month inserts a second row | breaks A10 at-least-once dedupe exactly when retries are slowest (spool replay) | rejected |
| B. Keep global dedupe in a side table `event_dedupe(org_id, run_id, event_id)` unpartitioned, insert first | receive time | kept | extra write per event on the hot path (T50 one-statement insert becomes two); the side table grows without partition drop and needs row deletes | fallback if C cannot be built |
| **C. Partition by `run_created_at`** (immutable, denormalised from `run.created_at`), unique `(org_id, run_id, event_id, run_created_at)` | run creation time | **kept**: all events of a run carry the same `run_created_at`, enforced by composite FK to `run`, so the extra column cannot make two rows of one `(run_id, event_id)` distinct | one extra 8-byte column; `ON CONFLICT` target gains the column; partition boundaries follow run age so drops align with retention | **chosen default** |
| D. No partitioning; batch `DELETE` by age | none | kept | bloat, vacuum load, long locks at pilot scale (≈ 100k results/day, 00 §11 numbers; the real growth is a ⚠️ measurement, 10.6.1) | kept as the zero-risk fallback if the partition job is not ready; retention still enforced |
| E. Hash partition by `run_id` | `run_id` | kept (key contains `run_id`) | no cheap retention drop, so it solves nothing for D4 | rejected |

[DECISION] default = C, monthly ranges, `DEFAULT` partition as a safety net. Late events for an old run (late window, T12/05.3.2-T3) land in that run's partition, which exists until retention drops it.

**Retention windows (default; all `[INFERENCE]` until the owner confirms).**

| Table | Window (ceiling for partition drop) | Rule |
|---|---|---|
| `event`, `event_batch` | `metadata_days` platform ceiling (default 90 d, same as the project default; V1 cap on a project's `metadata_days` = 365 d, `[OPEN]`) | partition dropped when the whole range is older than the largest `metadata_days` of any project whose rows it holds (never below the 90 d default, never above the 365 d cap), i.e. the ceiling; rows of a project with a *shorter* window than the ceiling stay until the ceiling (never deleted early); a project with a longer window than the ceiling is not allowed (hence the cap) |
| `case_attempt` | same as `event` | same drop rule; the summary needed for the run page is `evidence_revision` + counts, which are not partitioned |
| `evaluation` | not partitioned; `max(project metadata_days, referencing release record)` | row-level delete by the 06.4.2 job, child-first; never before the decision it supports |
| `evidence_revision`, `run` | unchanged (05, 06.4.1) | |

## 6. States and transitions

Partition lifecycle: `planned → attached → eligible → detached → dropped`, or `skipped` (guard failed). Only the job transitions it; each step is idempotent (T82) and logged. Run, artifact and evidence-revision states are unchanged. A `DETACH CONCURRENTLY` interrupted by a crash leaves a detached partition that the next cycle drops (state recovered from the catalog, not memory).

## 7. Jobs and integrations

- **Partition maintenance job.** Daily Cronos fire → `task`. Steps: (1) ensure runway; (2) compute eligible partitions per table (upper bound older than ceiling); (3) guard: no non-terminal run (`run.created_at` in range), 06.4.2 reports artifact deletion complete for those runs, no open legal-hold/deletion job; (4) detach concurrently, drop, audit. Lock timeout short (≤ 5 s) so it never blocks ingest; retry next cycle on timeout.
- **Evaluation retention.** A new step in the 06.4.2 handler (or its own handler registered there): deletes evaluation rows past `max(metadata_days, release reference)`, child rows first (`decision_reason`, delivery rows; 07 owns the names), in batches.
- **Reads.** Event-level query handlers detect "partition gone" by comparing `run.created_at` to `expired_before` rather than catching SQL errors.
- **Backup (10.5.1).** Partitioned tables restore as ordinary tables; the restore drill adds the AC9 check. ⚠️ Whether managed-PostgreSQL PITR preserves detached-then-dropped partitions as "dropped" at the restore point is expected but unverified; T3.2 records the result.
- **Tenant deletion (06.4.4).** Deletes by `org_id` across partitions (partition pruning cannot help; acceptable for the rare operation); `partition_maintenance_log` is platform data, not tenant data, and is not touched.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Tenant isolation | RLS FORCE on parent and partitions, grants on parent only, composite FK keeps `org_id` in every key; isolation suite runs against partitioned tables | `Isolation.Tests` extended, 02.6.1 assertions |
| Evidence immutability | dropping is the only removal path and it is time + guard based; no UPDATE path is added; evaluations and revisions are never partitioned away before their window | AC6, AC8 |
| Dedupe invariant | key includes `run_created_at` which the FK pins to the run | AC3, AC4 |
| P1/P2 | ingest stays a single `unnest` insert; partition pruning by `run_created_at` is available for run-scoped reads because queries always carry `run_id` → join/lookup of `run.created_at` (the handler passes it as a parameter) | EXPLAIN check shows pruning, 10.6.1-T1 compares p95 before/after |
| Audit | every create/drop/skip recorded (platform-scope audit row + log table) | AC5 |
| Privacy/retention | event payloads hold producer `ext` data; dropping partitions makes the retention window real, not a flag | AC6, AC7 |
| Operations | runway alert, default-partition alert, skip alert, operator runbook entry | AC5 |

DoR review answers.

- **Authorization:** the job runs as the maintenance role (owner of partitions, not the app role); operator list is behind `IOperatorGate`; no tenant-facing permission change.
- **Retention/deletion impact:** this story defines it: windows table in §3; interaction with 06.4.2 (artifacts first), 06.4.4 (tenant deletion deletes across partitions), 06.4.5 (verification suite gains partition cases).
- **Telemetry:** `partition_runway_months{table}`, `partition_default_rows`, `partition_drop_total{result}`, `partition_skipped_total{reason}`, job duration; trace `partition.maintain`.
- **Failure path:** missing future partition → rows land in `DEFAULT` + alert (ingest never fails); drop guard failure → skip + alert; detach timeout → retry; restore anomaly → drill fails the M2 exit gate.
