## 1. Goal and non-goals

**Goal.** Untrusted bytes are never parsed inside the shared `Evidgate.Worker` process. Each parse (XML/JSON report, zip index, secret-scan reader) runs in a short-lived child process with hard memory, CPU and wall-time limits and no network, started by a task-queue handler; a crash, OOM kill or timeout becomes a `rejected` artifact with a stable reason and never takes the worker down. A per-tenant concurrency cap with fair scheduling stops one tenant from occupying every parse slot.

**Non-goals.** The parser profile itself — DTD off, depth/entity caps, zip-slip rules (06.3.1, reused inside the child); streaming consumption of report entries (04.1.3); the viewer origin and rendering (06.3.3/06.3.4); a general code-execution sandbox for customer code (not a product feature); container-level isolation per tenant (rejected, see §3).

## 2. User stories and acceptance criteria

- As an operator, a memory bomb or a pathological file costs one failed parse, not a worker restart.
- As a tenant, my 10 000 queued parses do not delay another tenant's single parse beyond the fair-share bound.
- As a CI owner, a rejected report tells me why (`parse_oom`, `parse_timeout`, ...) without exposing internals.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Every parse call site reaches the parser only through `IParseRunner`; an `Architecture.Tests` rule fails if `XmlReader`/`ZipArchive`/`JsonDocument.Parse` over artifact bytes is used outside the child entry point and `Infrastructure/Parsing` |
| AC2 | The child runs with a memory limit (default 512 MiB), CPU time limit (default 20 s CPU), wall-time limit (default 30 s, same as `ParseTimeout`) and no network; limits are configuration with those defaults `[INFERENCE]` |
| AC3 | Exit mapping: normal result → parsed output; exit by memory limit → `rejected` `parse_oom`; wall/CPU limit → `rejected` `parse_timeout`; non-zero or signal exit → `rejected` `parse_crashed`; malformed output on the pipe → `rejected` `parse_crashed`; none leaves the artifact `ready` or `uploaded` |
| AC4 | A parse attempting any outbound connection (DNS or TCP) fails inside the child and the attempt is logged as a security event; the artifact is `rejected` |
| AC5 | With per-tenant cap `N` (default 2 concurrent parses per org, global slots `G`), tenant A with 50 queued parses never holds more than `N` slots; tenant B's parse starts within one scheduling interval when a slot is free, and waits at most `ceil(parses_ahead / G)` rounds under load |
| AC6 | Wait time is observable: histogram `parse_queue_wait_seconds{tenant_tier}` (no tenant id label) and gauge of slots in use; an alert fires when p95 wait exceeds the target for 10 minutes |
| AC7 | Hostile-input suite (06.3.6-T3): memory bomb, deep nesting, huge attribute, billion-laughs, zip bomb — the worker process pid and uptime are unchanged, each hostile artifact ends `rejected` with the mapped reason, and a parallel parse from another tenant completes within its normal time |
| AC8 | A worker killed while a child runs leaves no orphan child (child exits when the parent pipe closes) and the task is retried by the queue visibility timeout; the artifact is parsed once (idempotent result write) |

## 6. States and transitions

Artifact states per 00 §8.4 are unchanged: `uploaded → ready | rejected`. The parse step sits inside the `complete` → `ready` path (sniff, then parse where the kind needs it). New: a parse task is `claimed → running → done | retry | dead_letter` under the 01.5.1 task machine; limit hits are *results* (`rejected`), not retries, because a retry of a hostile file cannot succeed. Infrastructure failures (cannot spawn the child, queue lease lost) retry with backoff then dead-letter with the alert sink (01.5.1-T4). Transitions idempotent (T82).

## 7. Jobs and integrations

- **Spawn.** The `parse` handler writes nothing before the child finishes; it opens the object read stream with a byte cap and pipes it to the child's stdin. The child applies the 06.3.1 profile (defence in depth), emits NDJSON entries and a final `{"done": true, "count": n}` line; a missing final line = `parse_crashed`.
- **Limits.** Memory via cgroup v2 where available, else `RLIMIT_AS` (⚠️ behaves differently for a managed runtime heap; verify in T1.1) plus `DOTNET_GCHeapHardLimit` as the first line; CPU via `RLIMIT_CPU`; wall via parent timer that kills the process group. Child runs as an unprivileged uid with read-only root filesystem and an empty temp dir deleted after exit.
- **Fairness.** Claim query selects the oldest runnable task per `fair_key` round-robin, skipping orgs at their cap `N` (counted from `running` tasks); global slots `G` come from per-queue concurrency (01.5.1-T1). Alternative considered: one sub-queue per tenant — rejected, unbounded queue count. Starvation bound documented in the runbook.
- **Callers.** `CompleteArtifact` (06.1.2) enqueues `parse` for kinds that need parsing; 04.4.1 raw-report parse and 06.2.3 content scanner use the same queue and runner. [INFERENCE] interactive callers (a user waiting on a comparison) share the queue in V1; a priority lane is deferred.
- **Streaming.** The NDJSON pipe is the hand-off that lets 04.1.3 stream entries to the mapper in bounded pages.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| S5 untrusted parsers | memory/CPU/time limits, unprivileged uid, read-only FS, no network; hardened profile still enforced inside | AC2, AC4, AC7 |
| Blast radius | child crash cannot corrupt worker state; no shared mutable state across parses; temp dir wiped | AC7, AC8 |
| Tenant isolation | child receives one artifact's bytes only; fair scheduling keyed on `org_id`; metrics carry no tenant id; claim query returns task payload only | isolation test, AC5 |
| S3 no leakage | stderr of the child is captured, truncated and never stored or logged verbatim; tenant-visible reasons are code-only: `parse_*`, the validated child-reported reason (D-S125-Q4), or `too_large` for an over-cap object | `ParseErrorRedactionTests` extended |
| Audit | repeated `parse_crashed` for one project raises a security event (`artifact.parse_rejected`) through 02.7.1/11.5.1 | event test |
| Performance | spawn cost measured; a small-report fast path is allowed only if measured spawn overhead exceeds a budget (`[INFERENCE]` 50 ms p95) — default is always out-of-process | spawn benchmark in T1.4 |

DoR review answers.
- **Authorization:** internal handler, no new permission; callers already hold `artifact:write` paths (06.1.2).
- **Retention/deletion impact:** no persistent data beyond `artifact.failure_code`; temp files removed per parse; parse tasks purged by the 01.5.1 task purge.
- **Telemetry:** `parse_queue_wait_seconds`, `parse_runs_total{result}`, `parse_child_peak_rss_bytes`, `parse_slots_in_use`, trace span `parse.child` with exit class; alert on wait p95 and on `parse_crashed` rate.
- **Failure path:** limit hit → `rejected` with reason; spawn failure → retry with backoff → dead letter + alert; worker kill → child dies with pipe, task reclaimed.

**Notes (06.3.6-T1.1+T1.2 hand-over, S117, #243; STATUS.md:803 "Parse child hand-overs (06.3.6-T1.1+T1.2, S117, #243)"):** the child's NDJSON protocol and the limits measured in this session are handed to 06.3.6-T1.3 (parent runner: spawn, byte-capped stdin, stdout cap, limits, process group) and 06.3.6-T1.4 (exit mapping, handler); every figure below was measured by the author on this host in this session and is not re-run in CI:

- **Output cap in bytes and records.** 06.3.6-T1.3 must cap the child's stdout by **bytes and by record count**, because the child's amplification is not bounded by its input: measured up to 18.6x input bytes and about 10M records from a 16 MiB input, and non-ASCII JSON values escape to about 3x — receiver 06.3.6-T1.3, tests `Child_AppliesConfiguredLimits` (AC2) plus the byte/record cap test T1.3 adds; a breach must end as a `rejected` record with a documented reason, never as a truncated success (AC3).
- **Marker.** Accept the final marker only as the top-level `done` key of the **last** record, with `count` equal to the number of records written before it — a `rejected` record is counted too, because `NdjsonWriter.WriteRejected` goes through `BeginRecord`/`EndRecord` (`NdjsonWriter.WriteRejected` in `src/Evidgate.Parser/NdjsonWriter.cs`: the `string` overload both callers funnel through, and the `Error` overload that delegates to it); a missing, duplicate, non-last or miscounted marker is `parse_crashed` — receiver 06.3.6-T1.4, test `ExitMapping_Oom_Timeout_Crash_Garbage_AllReject` (AC3); the child side already asserts framing in `ChildProtocolTests.AssertFramed`.
- **Stdin overflow.** On the first byte past `--max-bytes` the child writes its rejection, writes the marker and exits **without draining** stdin (the `content.Overflowed` branch of `Program.Run` in `src/Evidgate.Parser/Program.cs`), so 06.3.6-T1.3 must treat an `EPIPE` on a stdin write that follows a marker as normal completion, not as a child fault — receiver 06.3.6-T1.3, covered by `Input_Over_The_Cap_Is_A_Size_Rejection_And_The_Cap_Itself_Is_Accepted` (AC2).
- **XML emit wall time.** The parent's wall-clock kill is the only bound on the emit pass, because attribute handling scales quadratically (800k attributes 5 s, 1.4M attributes 14.6 s, 1154 MB RSS for a 16.3 MiB dense-attribute input); 06.3.6-T3.1 must add those shapes to the hostile suite, and 06.3.6-T1.3 must size the default 512 MiB limit from the dense-JSON (about 19x input RSS) and huge-attribute (about 68x) shapes — receivers 06.3.6-T1.3 (limit value, AC2) and 06.3.6-T3.1 (fixtures, AC7).
- **Heap OOM versus crash.** Exhausting `DOTNET_GCHeapHardLimit` surfaces as an unhandled `OutOfMemoryException` and exits **3**, the same code as an internal crash; 06.3.6-T1.4 decides whether `parse_oom` gets a distinct exit code or the heap-limit death is documented as `parse_crashed` (AC3 requires the memory-limit exit to map to `parse_oom`), and a `SIGKILL`/signal death is already distinguishable from exit 3 — receiver 06.3.6-T1.4, test `ExitMapping_Oom_Timeout_Crash_Garbage_AllReject`.
- **Environment.** 06.3.6-T1.3 must pass a scrubbed, minimal environment: the runtime reads `DOTNET_*` variables itself (`DOTNET_STARTUP_HOOKS`, the `DOTNET_gc*` family), so the allow-list holds only what this chain needs (`DOTNET_GCHeapHardLimit`) — receiver 06.3.6-T1.3, test `Child_AppliesConfiguredLimits` (AC2).

- **Process-group kill, deviation from the T1.3 row wording (COORDINATOR-DECISION S121, panel pick (a)).** The runner kills the child's whole process TREE with `Process.Kill(entireProcessTree: true)` on wall-clock timeout, cap breach, malformed output, cancellation and disposal, not a process group. - **No orphan on parent death (AC8, first half).** No new child P/Invoke: parent death closes the child's stdin (read ends) and stdout (write fails with EPIPE, exit 3); a child already CPU-bound inside a parse is bounded by `RLIMIT_CPU` (20 s) and the profile's 30 s timeout. Proof: `ParseRunnerParentDeathTests` kills a separate host process mid-run and asserts the child pid is gone (Unix; Linux CI job is queue F57). The queue-retry and parsed-once half of AC8 (`WorkerKilledMidParse_NoOrphanChild_TaskRetried_ParsedOnce`, §9) needs the `parse` handler and the idempotent result write — receiver 06.3.6-T1.4 (task row T1.4, :115).
- **Limits and sizing (AC2).** Defaults: `RLIMIT_CPU` 20 s, `RLIMIT_FSIZE` 0, `RLIMIT_CORE` 0 (child, one allow-listed import), `DOTNET_GCHeapHardLimit` 512 MiB (parent env), wall clock 30 s. At 512 MiB the child streams: dense JSON up to 20 MiB (≈16.7x RSS; 24 MiB dies with an unhandled `OutOfMemoryException`, exit 3), dense-attribute XML up to 12 MiB (≈44x; from 14 MiB the 30 s profile timeout, not memory, binds), text-heavy XML at least 128 MiB (≈2.4x), a zip index 64 MiB (bounded by `MaxZipEntries` 10 000). Inputs beyond these shapes end as `parse_oom`/`parse_timeout` by design (T1.4 maps). The earlier 68x huge-attribute figure (Notes :149) is the 16 MiB shape that exceeds the limit.
- **Output caps.** Defaults derive from `--max-bytes`: bytes `min(256 MiB, max(8 MiB, 24 x max-bytes))` (24x clears the measured 18.6x only up to ≈10.7 MiB of input; above ≈13.8 MiB an 18.6x stream breaches by design), records `min(2 000 000, max(4096, max-bytes / 8))` (the measured ≈10M-record shape is refused), one line at most `min(byte cap, max(1 MiB, 6 x max-bytes))`, nesting depth at most the profile's 64 + 4. A breach is a failure result (`OutputBytesExceeded` / `OutputRecordsExceeded`), never a truncated success; T1.4 maps it to a documented `rejected` reason. Invalid UTF-8 in a record is `MalformedOutput`.
