## 1. Goal and non-goals

**Goal.** A project can disable capture of a whole artifact kind (no such artifact is ever uploaded) and can declare allowlisted redaction rules (headers, cookies, form fields, query params) that the reporter/CLI applies *before* upload, so personal data never reaches Evidgate storage for a disabled kind and is stripped for an enabled one — first-line defense ahead of the server-side secret scan (06.2.3).

**Non-goals.** The secret-scan task that runs after upload (06.2.3, second line of defense per FR-06-7); the adapter protocol schema itself, owned by 04 (`04.7.1-T1` owns `contracts/adapter/config.v1.json`; this story supplies the redaction/capture-control *content* for the run-create configuration document per T97 and the server-side read path — the `capture_control` capability flag itself is 04's schema); sensitivity classification (06.2.1).

## 2. User stories and acceptance criteria

- As a `tenant_admin`, I disable `video` capture for a project handling regulated user data, so no `video` artifact is ever uploaded for that project, not merely hidden after the fact.
- As a `tenant_admin`, I configure a redaction rule stripping the `Authorization` header and a `password` form field from captured `dom_snapshot`/`raw_report` artifacts, so the reporter removes them before any byte leaves the CI runner.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `GET /v1/projects/{p}/capture-options` returns `{kind: {capture_enabled, redaction_rules[]}}` per artifact kind, readable by the adapter capability negotiation (00 §10) |
| AC2 | `PUT /v1/projects/{p}/capture-options/{kind}` (`project:write`) sets `capture_enabled=false` for a kind; a subsequent `upload-url` request for that kind on that project returns 422 `kind_disabled` (reusing 06.1.2's `artifact_kind_policy.capture_enabled` gate — no new enforcement point) |
| AC3 | Redaction rules are restricted to an allowlist of rule types (`header`, `cookie`, `form_field`, `query_param`) each with a name pattern; a rule outside the allowlist is rejected at write time (422 `redaction_rule_type_unknown`) |
| AC4 | The adapter protocol v1 **configuration document** returned at run create (04.7.1, `contracts/adapter/config.v1.json`) carries the project's redaction rules and disabled kinds so the reporter applies them client-side before capture (T97); an adapter that cannot honour them declares `capture_control: false` in its capability document and the run is labelled `capture_uncontrolled`; the server never receives the pre-redaction bytes for a disabled kind (proven by the adapter contract test asserting the reporter skips capture, not merely skips upload)
| AC5 | Changing capture options takes effect for the *next* run only; an in-flight run's already-issued `upload-url`s are unaffected (no retroactive rejection of an artifact already staged) |

## 4. Data model and migrations

Migration `migrations/NNNN_evidence_redaction_rule.sql`:

```sql
create table redaction_rule (
  id            uuid primary key,
  org_id        uuid not null,
  project_id    uuid not null,
  kind          text not null check (kind in ('trace','video','screenshot','raw_report','dom_snapshot','a11y_snapshot','patch','ui_hierarchy')),
  rule_type     text not null check (rule_type in ('header','cookie','form_field','query_param')),
  name_pattern  text not null,             -- exact name or glob, applied client-side by the reporter
  created_at    timestamptz not null default now(),
  unique (org_id, id),                     -- T3
  unique (org_id, project_id, kind, rule_type, name_pattern)
);
alter table redaction_rule enable row level security;
alter table redaction_rule force row level security;
create policy redaction_rule_tenant on redaction_rule
  using (org_id = evidgate.current_org_id())
  with check (org_id = evidgate.current_org_id());
create index redaction_rule_project_idx on redaction_rule (org_id, project_id);  -- serves the configuration-document read
```

`artifact_kind_policy.capture_enabled` (existing column from 06.1.1) is the sole source for the disable-kind check; no duplicate flag is added.

**Notes (06.2.2-T1, landed in this wave) — [DECISION]s, recorded for owner review.**

1. **Path deviation (coordinator decision, superseding §5's shape).** The read ships as `GET /v1/projects/{p}/artifact-kind-policy` and the write stays `PUT /v1/projects/{p}/artifact-kind-policy/{kind}`. No `/capture-options` path is added: the capture switch it reports is the one `artifact_kind_policy` already holds, and a second path family for one row would be a second vocabulary for the same resource. AC1's `{kind: {capture_enabled, redaction_rules[]}}` is served as `{kinds: [{kind, capture_enabled, redaction_rules}]}` — one entry per contract kind in contract order — so every kind appears exactly once with the members AC1 names.
2. **Rules are written through the existing override route.** `PUT .../artifact-kind-policy/{kind}` gains an optional `redaction_rules` member: a list replaces the kind's declared set, `[]` clears it, and an omitted member leaves it untouched — chosen so a client that only toggles `capture_enabled` can never delete a privacy control it never sent. An unknown `rule_type` is the new 422 `redaction_rule_type_unknown`, judged before any statement; a malformed `name_pattern`, a `null` rule entry, more than 64 rules or a repeated pair is `422 request_invalid`; a non-object rule entry or a rule object carrying a member it does not declare is the documented closed-body `400 request_invalid`. Neither refusal writes a row or appends an audit entry. `name_pattern` is 1..128 characters of `[A-Za-z0-9._~%+:*?/-]`, the CHECK, the validator and `contracts/adapter/config.v1.json`'s `redactionRule.name_pattern` all at the same bound, so a stored rule always fits the delivery document.
3. **AC4 and AC5 are carried, not delivered here.** They move to `05.2.1`/`04.7.1` with the configuration-document assembler; this task ships the contract surface they consume (`ICaptureOptionsReader` in `Evidgate.Modules.Evidence.Contracts`) and proves it answers disabled kinds and rules per project with nothing cross-org.
4. **No `redaction_rule_project_idx`.** `redaction_rule_kind_key` starts `(org_id, project_id, kind, …)`, so it already serves both reads; a separate `(org_id, project_id)` index would duplicate that prefix (recorded in the migration header).
5. **The audit row counts the rules on either side.** The existing `artifact_kind_policy.set` row keeps `previous_default_sensitivity`/`status` and adds `redaction_rule_count` (what the write left) and `redaction_rule_count_before` (what it replaced, read under the same advisory lock) when the write sent the declared set, so a clear, a replacement or an identical replay is visible in the chain. Both are counts, never patterns.
6. **The route's body cap is its own, 32 KiB.** The write no longer shares upload-url's 8 KiB cap: 64 rules of a 128-character `name_pattern` cost 11,073 bytes of JSON and the 64 media types the same body may carry at most 16,448, so 32 KiB holds the largest documented body (`CapturePolicyLimits.MaxBodyBytes`, mirrored in §9.3's route text) and still answers 413 before parsing.
7. **The read is one statement.** `GET /v1/projects/{p}/artifact-kind-policy` and `ICaptureOptionsReader` read the policy rows and the declared rules in one `union all` statement, so the switch and the rules beside it come from one snapshot instead of two reads that a concurrent write could split.

## 11. Rollout

- No feature flag: capture options default to `capture_enabled=true`, no redaction rules — fully backward compatible until a `tenant_admin` configures them.
- Monitoring: `kind_disabled` 422 rate on `upload-url` is a useful signal that a project's config and its CI adapter version have drifted (adapter still trying to capture a disabled kind); worth a dashboard row in 10 once available.
- Rollback: revert the endpoints; `artifact_kind_policy.capture_enabled` reverts to always-true behavior since 06.1.2's gate treats a missing/true value as enabled by default.
