## 1. Goal and non-goals

**Goal.** `scripts/verify.sh` fails on a module-boundary violation, an unformatted file, an un-awaited task, a nullable warning and a TypeScript `strict` error — so code-quality invariants are machine-enforced from the first real module PR.

**Non-goals.** The CI workflow that invokes `verify.sh` (01.7.1); the licence/vulnerability scan jobs (01.7.1-T4, 11.6.1); test conventions and fixtures (01.6.1); any product rule beyond the five violations above.

### 01.2.1-T6 — Review-blocker diff gate (M)

Owner decision 2026-10-30: the review-blocker scan that lives coordinator-side as `.omp/coordinator/check-review-blockers.py` becomes a repo stage, so a blocked pattern on an added line fails the build and the U1 comment-id count cannot grow unnoticed. **Merged** in PR #310 as `26d6070e` (2026-10-30).

**Review integrity.** The `check-review-blockers` stage runs the checkout's own copy — that is what local and smoke runs need. On `pull_request` a second step, `Review-blocker gate from the base revision`, archives `git archive "$BASE_SHA" -- scripts/check-review-blockers.py scripts/review_blockers scripts/check-review-blockers.baseline.json | tar -x -C "$RUNNER_TEMP/crb-base"` and runs **that** copy; `scripts/review_blockers` joins the archive only when the base has it (`git cat-file -e "$BASE_SHA:scripts/review_blockers/__init__.py"`), so a base that predates the split still extracts the self-contained entry file and `git archive` never asks for a path the base lacks. The two shas have separate jobs: the payload base sha names the trusted copy, because the scanner and the baseline must be a commit of the base branch and checking that commit exists first keeps the choice stable; the range comes from the merge commit's first parent, so a branch that has merged develop cannot re-scan base-side changes as its own, and only a checkout without a second parent falls back to the payload sha (with a `::warning::`). So the step runs the diff scan `"$scanner" HEAD^1 HEAD`, then the ratchet as `"$scanner" --baseline "$baseline" --u1-ratchet HEAD`. Because that copy carries the base's own rules and the base's own number, a pull request cannot buy headroom for new violations: a head that adds one comment-id line and raises its own baseline to 9999 still fails there (`BLOCK U1 ratchet 1932 > 1931`, measured, exit 1) while the same head judged with its own baseline exits 0, and a head that relaxes a rule *and* adds a line that rule would block also fails. Editing the gate's own scanner or its baseline is not a CI failure: it stays the non-failing `WARN gate-file`, so a rule change or a new ceiling is the coordinator's decision at merge, measured against the task file that names the change (the `WARN gate-file` line's own rule) and with the merge check running the `origin/develop` copy (`docs/engineering/omp-setup.md` Step 5a). A base revision with no scanner (the change that introduced the gate, while `origin/develop` does not carry it yet) runs the checkout's copy with a `::warning::`, and that bootstrap disappears as soon as develop carries the scanner; a base that has a scanner but no baseline fails the step instead of borrowing the pull request's number. A base commit missing from the clone fails the step first, with its sha in the message, before any copy is chosen. The diff scan runs only for a landing on develop (a pull request to develop, or a push to develop, which scans `github.event.before`): a pull request to main or a push to main runs the stage with `EVIDGATE_REVIEW_DIFF=off`, so only the ratchet runs, because develop's own debt that the scan tolerates (the `0053`/`0054` D1 policies) is not a promotion's change set and would fail every promotion for it. The base copy protects the scanner and its baseline only — a pull request's `ci.yml` and `scripts/verify.sh` are the pull request's own too — so the workflow's copy is the coordinator's `origin/develop` check plus the `gate-file` WARN, never this step. Both the CI step and the hand check therefore judge a pull request's added lines with rules and a ceiling the pull request did not write.

### 01.2.1-T7 — Path-scoped verify.sh gate tiers (M)

Owner decision 2026-10-30: a full `scripts/verify.sh` run costs about 50 minutes, almost all of it in the .NET restore, build, test, isolation and fixture stages, so a change that touches no .NET-relevant file pays for nothing it needs — and a change that touches one must never be able to skip those stages.

**Tiers.** A tier is chosen only when `verify.sh` runs with no `--stage`; an explicit `--stage` list behaves exactly as today, because every caller that names its stages has already decided what to run.

- `review-infra` (added by S194) — every judged path is `infra/review/**` or `scripts/review/**` (never a Dockerfile or its `.dockerignore`, which stay `full`) or in the docs set. Runs prettier, every `check-*` stage including `check-review-infra`, `eslint` and `image-pins`; the `docs` tier does not run `check-review-infra`.
- `docs` — every judged path is Markdown under `docs/`, `plans/`, or a root `*.md` (`AGENTS.md`, `STATUS.md`, `DECISIONS.md`, `REVIEW.md`, …). Runs prettier and every `check-*` stage (`check-layout` … `check-gate-scope`), and nothing else. Three exceptions widen it, each because a .NET or script stage reads that file: `docs/security/audit-and-deletion-rule.md` is `full` (`AuditRuleDocumentTests` reads it), `docs/adr/**` is `no-dotnet` (`licence-scan`/`audit-deps` resolve ADR files), and a path under `plans/features/` that the change deletes or renames away is `full` (`CatalogueTests` reads only the stories `PendingV1Consumers` names, so judging every removed story path `full` over-approximates, the safe direction).
- `no-dotnet` — every judged path is in the docs set or in the safe set: `apps/web/`, `packages/`, `scripts/` — except the gate's own files (`scripts/verify.sh`, `scripts/locked-run.sh`, `scripts/gate_scope.py`, `scripts/tests/test_gate_scope.py`, `scripts/tests/test_verify_scope.py`, `scripts/build-images.sh`, `scripts/smoke-clean-build.sh`, `scripts/tests/review_blockers_fixtures.py`, `scripts/review_blockers/**`, `scripts/dev/**`), which force `full` — plus the root `package.json`, `package-lock.json`, `.prettierignore`, `tsconfig*.json`, `eslint.config.*` and `.prettierrc*`. `fixtures/web-api/` is not safe: `FixtureLoaderTests` walks every directory under `fixtures/`, so a fixture change is `full`. Runs every stage except restore, build, format, test, isolation, fixtures-hostile, fixtures-fuzz and images.
- `full` — anything else: `src/`, `tests/`, `fixtures/`, `migrations/`, `contracts/`, `infra/`, `.github/`, `.config/`, any path outside the narrowed allow-lists — and, wherever it sits, a .NET file (`*.cs`, `*.csproj`, `*.fsproj`, `*.vbproj`) or a build or tool configuration (`*.sln`, `*.slnf`, `*.slnx`, `*.props`, `*.targets`, `Directory.*`, `global.json`, `nuget.config`, `packages.lock.json`, `.globalconfig`, `*.ruleset`, `Dockerfile*`, `.editorconfig`) — or a committed `.omp/` path, or a base that cannot be resolved, or `EVIDGATE_GATE_SCOPE=full`. Untracked `.omp/` harness state is skipped rather than counted, because it is never committed; a `.omp/` path that is committed is judged like any other and selects `full`.

**Inputs.** The changed paths are `git diff --name-only --no-renames <base>...HEAD` plus the uncommitted and untracked paths of `git status --porcelain`, so an uncommitted `.cs` edit forces `full` instead of letting a local run pick the cheap tier. The base is the first of `origin/develop`, `develop`, `origin/main`, `main` that resolves, using the same helper as `scripts/review_blockers/gitio.py`, reused rather than copied, so the gate scope and the review-blocker scan cannot disagree about which base they mean. `EVIDGATE_REVIEW_BASE`, when it is set and resolves, adds a second diff and the change set is the union of both: the variable can only widen the change set, never hide a path the default base sees, and an unresolvable base is `full`.

**Override.** `EVIDGATE_GATE_SCOPE=full|no-dotnet|docs|auto` (default `auto`) widens only: a request narrower than the computed tier is refused and the wider tier runs, with a message naming both. A gate never gets cheaper because someone asked it to.

**Output.** One line before the first stage, `== gate scope: <tier> (<reason>, N changed path(s), base <sha>)`, where `N` counts the judged paths (skipped untracked `.omp/` entries excluded), and at the end `all stages passed` only when every `ALL_STAGES` entry ran, otherwise `selected stages passed:` listing what ran, so a reviewer reading a local log or a PR comment can see exactly which stages did not run.

**CI.** The workflow sets `EVIDGATE_GATE_SCOPE: full` for every job: a runner clone is often shallow or detached, a merge commit's diff is not the change set, and a CI verdict that skipped the .NET stages because a change looked web-only is not one to merge on. Every job also passes `--stage` explicitly, so the workflow-wide variable is the second lock on the same door.
