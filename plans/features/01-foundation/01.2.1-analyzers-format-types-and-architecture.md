## 1. Goal and non-goals

**Goal.** `scripts/verify.sh` fails on a module-boundary violation, an unformatted file, an un-awaited task, a nullable warning and a TypeScript `strict` error — so code-quality invariants are machine-enforced from the first real module PR.

**Non-goals.** The CI workflow that invokes `verify.sh` (01.7.1); the licence/vulnerability scan jobs (01.7.1-T4, 11.6.1); test conventions and fixtures (01.6.1); any product rule beyond the five violations above.

## 2. User stories and acceptance criteria

| Privacy / retention | no data | — |

DoR answers (00 §12 four review questions, `scripts/check-dor-security.sh`), written for this story and for its newest task 01.2.1-T6, the only one here that reads a diff and the head tree:

- **Authorization:** no endpoint, command or query — the gate reads `git diff` output and the head tree only, so it declares no permission and holds no tenant scope.
- **Retention/deletion:** nothing to retain or delete; the single committed artefact is `scripts/check-review-blockers.baseline.json`, an integer count with no customer data.
- **Telemetry:** the stage prints its counts on stdout like every other `verify.sh` stage; no metric, no exported identifier, no org or project value.
- **Failure path:** a missing base ref, a shallow clone or a git error exits 2 with a message instead of passing, and the ratchet fails closed when its baseline file is absent.

### 01.2.1-T6 — Review-blocker diff gate (M)

Owner decision 2026-10-30: the review-blocker scan that lives coordinator-side as `.omp/coordinator/check-review-blockers.py` becomes a repo stage, so a blocked pattern on an added line fails the build and the U1 comment-id count cannot grow unnoticed.

**Review integrity.** The `check-review-blockers` stage runs the checkout's own copy — that is what local and smoke runs need. On `pull_request` a second step, `Review-blocker gate from the base revision`, materialises `git show "$BASE_SHA:scripts/check-review-blockers.py"` and `…baseline.json` into `$RUNNER_TEMP` and runs **that** copy: diff scan `"$scanner" "$BASE_SHA" HEAD`, then the ratchet as `"$scanner" --baseline "$baseline" --u1-ratchet HEAD`. Because that copy carries the base's own rules and the base's own number, a pull request cannot buy headroom for new violations: a head that adds one comment-id line and raises its own baseline to 9999 still fails there (`BLOCK U1 ratchet 1548 > 1547`, measured, exit 1) while the same head judged with its own baseline exits 0, and a head that relaxes a rule *and* adds a line that rule would block also fails. Editing the gate's own scanner or its baseline is not a CI failure: it stays the non-failing `WARN gate-file`, so a rule change or a new ceiling is the coordinator's decision at merge, taken with that warning in view and with the merge check running the `origin/develop` copy (`docs/engineering/omp-setup.md` Step 5a). A base revision with no scanner (this PR, because `origin/develop` does not have one yet) runs the checkout's copy with a `::warning::`; a base that has a scanner but no baseline fails the step instead of borrowing the pull request's number. Both the CI step and the hand check therefore judge a pull request's added lines with rules and a ceiling the pull request did not write.
