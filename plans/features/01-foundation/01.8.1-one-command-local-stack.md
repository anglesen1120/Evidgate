## 1. Goal and non-goals

**Goal.** `scripts/dev/up.sh` on a clean machine (Docker, .NET 10 SDK, Node 26) brings up PostgreSQL 18 + the S3 emulator in compose, runs migrations and the dev seed, and starts Api (`dotnet watch`), Worker and web (`ng serve`) — with a presigned PUT/GET round-trip succeeding through the exact code path plan 06 uses. Dev roles mirror production (owner/app/operator) so an RLS mistake fails locally first.

**Non-goals.** Production-grade compose for deploy (10.2.1); HTTPS termination; seeding real business fixtures beyond the minimal org/project/roles/policy (02–07 own richer seeds); Kubernetes anything.

## 2. User stories and acceptance criteria

- As a new developer, one script gives me a working stack with seeded data, so day-one productivity is measured in minutes.
- As a backend developer on 06, the local S3 emulator honours the same SigV4 presigned-URL contract (checksum + signed `Content-Length`, oversize rejected) as the provider, so local green means something.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | On a clean checkout: `scripts/dev/up.sh` exits 0 with Api, Worker, web, PostgreSQL 18 and SeaweedFS healthy; `GET /internal/health/ready` returns 200 (db + migration head checks pass) |
| AC2 | SeaweedFS parity via `AWSSDK.S3`: presigned PUT with checksum header and signed `Content-Length` uploads; a PUT with a `Content-Length` larger than signed is rejected; presigned GET returns the bytes — the same assertions 10.6.1-T2 will run against the real provider (T18) |
| AC3 | `Evidgate.Migrator seed-dev` creates one org, one project, memberships from the 02 roles catalogue and one sample policy revision; running it with a non-dev `EVIDGATE__Environment` exits non-zero without writing |
| AC4 | Data survives `down`/`up` via named volumes; `scripts/dev/up.sh --reset` wipes them deterministically |
| AC5 | The seeded app role cannot bypass RLS locally (`evidgate_app` has no `BYPASSRLS`, policies `FORCE`d) — proven by re-running the 01.6.1-T4 isolation suite against the compose database |

## 4. Data model and migrations

No new tables. `seed-dev` inserts into existing tables only (org, project, memberships, one policy revision) — all through the owner role in one transaction, idempotent by natural keys (`seed_dev` marker in a `meta` table or `on conflict do nothing` per row). The compose Postgres initialises the three roles via `infra/postgres/init-dev-roles.sql` (mirroring 01.4.1-T2's production role DDL with dev passwords from `.env.dev`).

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** the seed runs as the owner role against the local compose database only; `seed-dev` refuses unless `DOTNET_ENVIRONMENT=Development` and the host is local or a bare compose service name, so it cannot touch a shared database. The application roles keep no `BYPASSRLS`; the seeded dev user holds `tenant_admin` and `release_approver` and has no credential until login exists.
- **Telemetry:** none beyond the script output: `seed-dev` prints what it wrote (a count, never a secret) and `db-init.sh` never prints a password.
- **Failure path:** a refusal exits 1 and writes nothing; an unreachable database exits 4, a failed statement exits 3 and the single transaction rolls back; rerunning is always safe because every row has a fixed id and `on conflict do nothing`.

**AC1 closed (2026-10-31, S167, PR pending): Api and Worker start in Development.**

- **Cause:** Mediator 3.0.2's source generator registers handlers and `IMediator` as Singleton by default; handlers consume scoped stores, `ICatalogContracts`, `IRunStateTransition` and so on, so the Development default host (`ValidateScopes` + `ValidateOnBuild`) refused to build. The Production-pinned test hosts never validated, which is why no test caught it ([Mediator README](https://github.com/martinothamar/Mediator/blob/main/README.md): `ServiceLifetime` option, compile-time).
- **Fix:** both hosts call `AddMediator((MediatorOptions options) => options.ServiceLifetime = ServiceLifetime.Scoped)` (the option is read at compile time per generating assembly, so each host sets it); the C2 pipeline behaviours are `AddScoped` instead of `AddSingleton`, because they look handlers up through their injected `IServiceProvider`, which a singleton gets as the root provider.
- **Regression tests:** `DevelopmentScopeValidationTests` (Hosts.IntegrationTests) builds the real Api and Worker compositions with `ValidateScopes` and `ValidateOnBuild`; both failed on base with `Cannot consume scoped service ... from singleton ...` and pass on head. `PipelineOrderTests.Behaviours_Are_Scoped_So_Handler_Lookups_Use_The_Request_Scope` pins the behaviour lifetime.
- **Rerun evidence (clean worktree on `develop` 674fecbd plus the fix, `scripts/dev/up.sh` under `locked-run.sh`, own compose project `evidgate-s167`, ports 55432/58333, the owner's containers renamed aside and restored):** `up.sh` exit 0; `GET /internal/health/ready` Api 200 and Worker 200; web `GET /` 200; `Cannot consume scoped` count 0 in api.log, worker.log and web.log.
