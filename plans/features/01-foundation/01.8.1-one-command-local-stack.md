## 1. Goal and non-goals

**Goal.** `scripts/dev/up.sh` on a clean machine (Docker, .NET 10 SDK, Node 26) brings up PostgreSQL 18 + the S3 emulator in compose, runs migrations and the dev seed, and starts Api (`dotnet watch`), Worker and web (`ng serve`) — with a presigned PUT/GET round-trip succeeding through the exact code path plan 06 uses. Dev roles mirror production (owner/app/operator) so an RLS mistake fails locally first.

**Non-goals.** Production-grade compose for deploy (10.2.1); HTTPS termination; seeding real business fixtures beyond the minimal org/project/roles/policy (02–07 own richer seeds); Kubernetes anything.

## 2. User stories and acceptance criteria

- As a new developer, one script gives me a working stack with seeded data, so day-one productivity is measured in minutes.
- As a backend developer on 06, the local S3 emulator honours the same SigV4 presigned-URL contract (checksum + signed `Content-Length`, oversize rejected) as the provider, so local green means something.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | On a clean checkout: `scripts/dev/up.sh` exits 0 with Api, Worker, web, PostgreSQL 18 and SeaweedFS healthy; `GET /internal/health/ready` returns 200 (db + migration head checks pass) |
| AC2 | SeaweedFS parity via `AWSSDK.S3`: presigned PUT with checksum header and signed `Content-Length` uploads; a PUT with a `Content-Length` larger than signed is rejected; presigned GET returns the bytes — the same assertions 10.6.1-T2 will run against the real provider (T18) |
| AC3 | `Evidgate.Migrator seed-dev` creates one org, one project, memberships from the 02 roles catalogue and one sample policy revision; running it with a non-dev `EVIDGATE__Environment` exits non-zero without writing |
| AC4 | Data survives `down`/`up` via named volumes; `scripts/dev/up.sh --reset` wipes them deterministically |
| AC5 | The seeded app role cannot bypass RLS locally (`evidgate_app` has no `BYPASSRLS`, policies `FORCE`d) — proven by re-running the 01.6.1-T4 isolation suite against the compose database |

## 4. Data model and migrations

No new tables. `seed-dev` inserts into existing tables only (org, project, memberships, one policy revision) — all through the owner role in one transaction, idempotent by natural keys (`seed_dev` marker in a `meta` table or `on conflict do nothing` per row). The compose Postgres initialises the three roles via `infra/postgres/init-dev-roles.sql` (mirroring 01.4.1-T2's production role DDL with dev passwords from `.env.dev`).

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** the seed runs as the owner role against the local compose database only; `seed-dev` refuses unless `DOTNET_ENVIRONMENT=Development` and the host is local or a bare compose service name, so it cannot touch a shared database. The application roles keep no `BYPASSRLS`; the seeded dev user holds `tenant_admin` and `release_approver` and has no credential until login exists.
- **Telemetry:** none beyond the script output: `seed-dev` prints what it wrote (a count, never a secret) and `db-init.sh` never prints a password. The one exception is `--with-token`: on the mint it prints the dev token secret once, to the caller's terminal and to no other sink, and a rerun prints the recovery note instead.
- **Failure path:** a refusal exits 1 and writes nothing; an unreachable database exits 4, a failed statement exits 3 and the single transaction rolls back; rerunning is always safe because every row has a fixed id and `on conflict do nothing`.

**T4 dev ingest token and sample policy (2026-10-31, S172, PR pending): implemented; the `runs create` 201 check is open by design.**

- **Design.** The seed composes an in-process service provider with the real module registrations (the composition `tests/Persistence.IntegrationTests/PipelineTestHost.cs` uses) and sends the real `CreateIngestTokenCommand` and `CreatePolicyRevisionCommand` through the mediator. `Evidgate.Migrator` references the Identity and Policy modules and the mediator package, and both modules carry an `InternalsVisibleTo` for it the way they name the Api and the Worker. No token row, hash or policy row is written by hand, and there is no second copy of the credential logic.
- **Datasource and principal (coordinator ruling 172).** The token and policy commands run on the app-role datasource (`EVIDGATE__DATABASE__CONNECTIONSTRING`, `evidgate_app`) inside a tenant scope for the dev org, with a synthetic principal = the seeded dev user (`DevSeed.UserId`, `tenant_admin`, project `dev-project`). The tenant rows stay on the owner role. `scripts/dev/db-init.sh` therefore runs `seed-dev --with-token` in step 3b, after the app-role `LOGIN` grants, instead of at 2b; it hands the seed both connection strings and `EVIDGATE__CI__PEPPER` as environment variables on the `dotnet run` — never as arguments, never printed. Without `--with-token` the seed stays at 2b and nothing changes.
- **Token.** Name `dev-seed`, bound to the dev project, scopes `artifact:write`, `event:write`, `run:create` (the `CreateIngestTokenCommand` default), no expiry (it dies with the volume). The pepper is resolved through `ISecretProvider` (`EVIDGATE:CI:PEPPER`) exactly as in the Api; with no pepper the seed exits non-zero before any write, the base seed included. The full secret goes to the `output` writer only, as one `EVIDGATE_DEV_TOKEN=egt_...` line; it never reaches a logger, an exception message, the `error` writer, a file or `.env.dev`.
- **Sample policy.** One `policy-revision.v1` body for the dev project through `CreatePolicyRevisionCommand`; a rerun returns the same revision and the same content hash (`sha256:<hash>`) and adds no revision. The command appends a **draft** revision (activation is `ActivatePolicy`, a separate command), and a run create falls back to the `EVIDGATE:Runs` defaults while the project has no active policy, so the sample does not by itself change run behaviour.
- **Rerun and concurrency.** A rerun that finds a live `dev-seed` token exits 0, mints nothing and prints no secret; the note names the one recovery exactly: `a live 'dev-seed' ingest token already exists; its secret was shown once and cannot be shown again. To get a new one run: scripts/dev/down.sh && scripts/dev/up.sh --reset --with-token`. That reset is the only recovery in dev: the dev user has no login, so no session exists to revoke a token with, and a stored secret cannot be shown a second time. Before the lookup and the minting, `seed-dev --with-token` takes a session-level PostgreSQL advisory lock (`pg_advisory_lock` on a 64-bit key derived from `sha256('evidgate.dev-seed.ingest-token')`) on a dedicated app-role connection, held until both commands have run; a second concurrent first run therefore blocks, then finds the live `dev-seed` token and mints nothing. Residual risk: any writer outside this path (`ingest_token` has no unique key on `(project_id, name)`) and, once a login exists, a revoke that races the check-and-mint window. A crashed run releases the lock with its connection.
- **Opt-in in the dev flow.** `scripts/dev/up.sh --with-token` (header, usage text and final summary updated) preflights `EVIDGATE__CI__PEPPER` before compose starts and passes `--with-token` to `scripts/dev/db-init.sh`. The token-bearing `dotnet run` writes straight to the caller's terminal: not captured in a variable, not tee'd, not appended to `.local/dev/logs/*`, and never exported, so `logs.sh` and the host logs cannot show it. `EVIDGATE_DEV_TOKEN` is documented as a shell-only export and deliberately absent from `.env.dev`, which every host process inherits.

**AC1 closed (2026-10-31, S167, merged #358, d8ed83b3): Api and Worker start in Development.**

- **Cause:** Mediator 3.0.2's source generator registers handlers and `IMediator` as Singleton by default; handlers consume scoped stores, `ICatalogContracts`, `IRunStateTransition` and so on, so the Development default host (`ValidateScopes` + `ValidateOnBuild`) refused to build. The Production-pinned test hosts never validated, which is why no test caught it ([Mediator README](https://github.com/martinothamar/Mediator/blob/main/README.md): `ServiceLifetime` option, compile-time).
- **Fix:** both hosts call `AddMediator((MediatorOptions options) => options.ServiceLifetime = ServiceLifetime.Scoped)` (the option is read at compile time per generating assembly, so each host sets it); the C2 pipeline behaviours are `AddScoped` instead of `AddSingleton`, because they look handlers up through their injected `IServiceProvider`, which a singleton gets as the root provider.
- **Regression tests:** `DevelopmentScopeValidationTests` (Hosts.IntegrationTests) builds the real Api and Worker compositions with `ValidateScopes` and `ValidateOnBuild`; both failed on base with `Cannot consume scoped service ... from singleton ...` and pass on head. `PipelineOrderTests.Behaviours_Are_Scoped_So_Handler_Lookups_Use_The_Request_Scope` pins the behaviour lifetime.
