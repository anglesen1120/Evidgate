## 1. Goal and non-goals

**Goal.** One contract, three consumers, zero drift: `packages/sdk` is a committed, deterministic TS client generated by `@hey-api/openapi-ts`; `Evidgate.Contracts.Validation` (Corvus.Json.Validator) and the CLI's Ajv 8 validate the same `contracts/` schemas against a shared `fixtures/contracts/` accept/reject corpus; contract tests pin implemented responses to the spec and diff the served OpenAPI document against `contracts/openapi.yaml`; `Evidgate.Canonicalization` and `canonicalize` produce identical RFC 8785 hashes. Any hand-edit, served-document drift or validator disagreement fails CI.

**Non-goals.** The spec and schemas themselves (01.3.1); the endpoints being validated (02–08); the CLI's command surface (04); healing-validator (08, T36); the `evidgate gate` exit codes (07.5.2).

## 2. User stories and acceptance criteria

- As a CLI/web developer, `import { … } from '@evidgate/sdk'` gives typed calls matching the spec — no hand-written DTOs (W5).
- As a backend developer, ingest payloads are rejected by Corvus before binding, with per-item indices matching the §9.2 `details[]` shape.
- As the Tech Lead, the spec is the only thing I edit; the generated SDK, both validators and the served document are pinned to it.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Editing a generated file under `packages/sdk/gen/` then running `npm run codegen && git diff --exit-code` fails; a spec edit without re-running codegen fails identically |
| AC2 | `packages/sdk` compiles under `tsc -b` with `strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` (TS 6.0.x) and is consumed by both `packages/cli` and `apps/web` builds |
| AC3 | Every vector in `fixtures/contracts/` (accept + reject, incl. per-event `index`/`path` rejections of 00 §9.4) produces the **same verdict** in the Corvus suite (xUnit) and the Ajv suite (Vitest); a deliberately divergent vector fails both builds (T42) |
| AC4 | `Contract.Tests` validates a sample implemented response against the spec, and the normalised diff of `Microsoft.AspNetCore.OpenApi`'s served document against `contracts/openapi.yaml` is empty (⚠️ 3.1 output confirmed here; fallback = response validation only, recorded in the test name/comment) |
| AC5 | The RFC 8785 reference vectors plus the Evidgate golden vectors (manifest/policy/candidate/evidence) hash identically as `sha256:<hex>` in `Evidgate.Canonicalization` (xUnit) and `canonicalize` 5.1 (Vitest) (⚠️ reference-vector licence checked in ADR-0002) |

| 00 §5.7 S3 | golden fixtures contain no real secrets; synthetic tokens only | fixture review |
| 00 §5.7 S5 depth cap, CLI side (01.3.2-T4 QA DEF-3) | the CLI rejects a document nested deeper than `JsonCanonicalizer.MaxDepth` (64 levels) instead of returning a digest for a payload the ingest edge answers 400 for; the level is counted as the server's reader counts it, containers from the root down, so 64 is accepted and 65 rejected in both runtimes | CLI spec "caps container nesting at 64 levels, exactly as the server does" and `CrossRuntimeParityVectorTests.Depth_Cap_Is_Exact` (accept 64, reject 65, arrays and objects); the walk itself is pinned by "walks a shared-reference DAG once instead of once per path" and "still rejects a shared subtree that only exceeds the cap on its deep path" (see the §9 notes) |

| CLI digest determinism on Node 26.10.0 (01.3.2-T4 QA DEF-1) | a warm process can mis-decode an escaped member name, so `canonicalizeJson` re-parses its own canonical text and withholds the digest when the runtime cannot reproduce it; the `canonicalize` row in ADR-0002 carries the matching `[WARN]` | CLI spec "withholds a digest when the runtime cannot reproduce its own canonical text"; macro reproduction recorded in the §9 notes |
| Performance: server-side canonical hashing | every object is re-emitted from its sorted member names: `WriteObject` decodes and sorts the names, then re-reads each member's value fragment out of the input (`Utf8JsonReader.Skip()` plus a second pass), so the bytes of an object are scanned once per enclosing level — O(object depth × size). | Performance: CLI round-trip guard (01.3.2-T4 QA DEF-1) | `canonicalizeJson` pays for the determinism guard with one extra `JSON.parse` + `canonicalize` of its own output: 2.8–3.2× the bare `canonicalize` measured on this host. | Privacy / retention | fixtures are synthetic; no customer data | — |

### 9.1 Notes from the 01.3.2-T4 QA pass (2026-09-26)

- The RFC 8785 reference pairs were moved from `tests/Canonicalization.UnitTests/TestData/rfc8785/`
  to `fixtures/rfc8785/` so the xUnit suite and the CLI Vitest suite read the same bytes; the README
  next to them carries the Apache-2.0 attribution, and `.prettierignore` keeps `input/` and `output/`
  byte-exact. The two files named before — `canonicalize.spec.ts` and `*.sha256` sidecars — never
  existed: the spec is `canonical.test.ts` (01.6.1-T1 convention reserves `*.spec.ts` for Playwright)
  and each golden file carries its `sha256` field inline.
- DEF-1 macro reproduction (throwaway, not committed — it needs a warm Node process and a large
  corpus): the harness at `/tmp/canonfuzz` — `gen.mjs` (seeded generator run 5 times), `min.mjs
  rand154 20000` (one process, two distinct canonical texts for the same input), `quantify.mjs`.
  Measured there on Node 26.10.0: the self-consistency guard fires on 64–78 of the 27,146
  generated documents in a warm process (0.24–0.29%), while the isolated single-document
  processes of `spawn.mjs` were 20/20 RFC-correct and a small text stayed stable over 200,000
  parses, so the instability is process-history dependent and could not be reduced to a minimal
  text — which is why no permanent test pins the corruption itself, only the guard's firing path.
  The guard is a mitigation, not a fix: it converts most, not all, silent wrong digests into a
  hard failure (some affected documents still return inside it), so the ADR-0002 `[WARN]` stands
  until Node is upgraded and re-measured.
- DEF-4 asymmetry, deliberately unpinned on the CLI side: a duplicate-name document is rejected by
  `JsonCanonicalizer` and silently collapsed by `JSON.parse`, so the CLI digest is only meaningful
  for documents the server accepts. The shared parity table therefore uses documents without
  duplicate names; the server-side verdict is covered by `Rfc8785VectorTests`.
- `CrossRuntimeParityVectorTests.Depth_Cap_Is_Exact` originally wrapped 64 nested objects in one
  more object, which is not JSON at all, so its object case passed for a parse error rather than for
  the depth cap; it now nests a 65th member and asserts the reader's depth message.

### 9.2 Notes from the wave-3 review fixes (2026-09-26)

- Performance measurements (throwaway harnesses on this host — .NET 10.0.12 Release, Node 26.10.0 —
  recorded as the evidence for the §8 performance rows, not as a gate; no perf test is committed):
  - `CanonicalHash.Compute` on a 4.65 MiB flat events array (20,000 objects × 4 members): 111 ms,
    12.7 MB allocated — 2.6× the input.
  - The same call on a 1.41 MiB document dense in short member names (20,000 objects × 10 members):
    80 ms, 25.3 MB (17.1×), so the allocation tracks the member-name count, not only the byte size
    (the decoded names plus the caller's output buffer).
  - The same call on a 4.00 MiB nested tree (262,144 objects, about 36 levels): 406 ms, 96.5 MB
    (23.0×). This is where the O(object depth × size) fragment rescan of `WriteObject` shows up, and
    it is the deliberate CPU-for-memory trade of the §8 row.
  - `canonicalizeJson` versus the bare `canonicalize` over the four golden vectors and a 1 MiB
    document: 2.8–3.2×, which is the DEF-1 guard's second `JSON.parse` + `canonicalize`.
- The CLI depth walk (`assertWithinCanonicalDepth`) memoises each container's subtree depth. The
  walk runs before `canonicalize`, and a shared reference is a cycle for neither of them
  (`canonicalize` releases a container from its `seen` set once its subtree completes), so the old
  ancestors-as-path-set walk was O(k^depth) on a DAG: 40 shared levels — 41 containers, 2^40 paths —
  had not finished after 90 s, while the memoised walk reaches `canonicalize`'s "Circular reference
  detected" in about 1 ms. A memo hit is still re-checked against the 64-level cap, which is the only
  way a shared subtree can exceed it; `canonical.test.ts` pins both the DAG case and the deep-path
  rejection.

## 11. Rollout

- No runtime feature flag. Merge order: T1 → T2 → T3 → T4 (T4 independent of T1–T3, may parallelise). Spec edits after T1 must re-run codegen in the same PR (drift gate enforces).
- AC2 deviation, recorded 2026-09-27 (wave 6, QA-W6-T1-2): `packages/sdk/gen/` compiles with `strict` and `noUncheckedIndexedAccess` but with `exactOptionalPropertyTypes` **off** (`packages/sdk/tsconfig.gen.json`; the hand-written `src/` project keeps the flag, and `tsc -b` still type-checks `gen/` through that composite reference). Forcing the flag on the generated tree fails with real TS2379 errors inside `@hey-api/openapi-ts`'s bundled fetch client (it emits `T | undefined` actuals into `T?` parameters). AC2's "compiles under ... `exactOptionalPropertyTypes`" therefore holds for everything we write and for the generated tree's type-check, minus that one flag; revisiting needs a generator-side fix, not a local patch.
- The drift gate's precondition (recorded after QA-W6-T1-1): `scripts/check-codegen-drift.sh` regenerates before diffing, so it compares the regenerated tree against the git index — it catches committed/staged drift (CI, pre-commit) and not an unstaged local hand-edit. Merge-order rule above assumes the tree is committed when the gate runs, which CI guarantees.
- Monitoring: none; drift/parity/contract checks are permanent via `verify.sh` → CI (01.7.1).
- Rollback: revert; generated and fixture files are regenerated, never hand-patched.
