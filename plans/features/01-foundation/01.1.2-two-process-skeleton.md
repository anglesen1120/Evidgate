## 1. Goal and non-goals

**Goal.** `Evidgate.Api` and `Evidgate.Worker` start from the same solution and the same module projects, each with validated `EVIDGATE__*` options, redacted structured logging, OpenTelemetry and graceful shutdown; `/internal/health/ready` is green only when the database is reachable **and** the migration journal head is at or ahead of the build's expected head; a vertical skeleton slice (manifest → run → planned execution → event batch → completeness stub → decision stub) crosses real module boundaries so a handler change is visible in both processes (removed; see Notes at the end of this file).

**Non-goals.** The real tenant scope, RLS and EF/Dapper data access (01.4.2); the Mediator pipeline behaviours (01.4.2-T4); the outbox and `task` queue (01.5.1); analyzers enforcing the boundaries (01.2.1, only referenced); real business rules of manifests/runs (04/05); container images (10.2.1); CI (01.7.1).

## 2. User stories and acceptance criteria

- As a developer, I run `dotnet run --project src/Evidgate.Api` and `dotnet run --project src/Evidgate.Worker` side by side and watch the skeleton slice flow through real module calls, so I can trust the module boundaries before real code lands (removed; see Notes at the end of this file).
- As an operator, `/internal/health/ready` tells me the process can serve work (database + schema at or ahead of the expected head), while `/internal/health/live` only says the process is alive.
- As the Tech Lead, a missing `EVIDGATE__*` variable fails startup with a named error, and a leaked connection string can never reach the logs.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | With the dev database up and migrations applied, `Evidgate.Api` and `Evidgate.Worker` both start and exit 0 on `SIGTERM` within the shutdown timeout |
| AC2 | Unsetting one required `EVIDGATE__*` option (e.g. `EVIDGATE__DATABASE__CONNECTIONSTRING`) makes `ValidateOnStart` fail startup with an error naming that key |
| AC3 | `GET /internal/health/ready` returns 503 while PostgreSQL is down or the `schema_migration` head is behind the build's expected head, 200 when both are met (a head at or ahead of the expected head counts as met: the expand/contract rollback state, 01.4.1 §11); `GET /internal/health/live` returns 200 in all these states |
| AC4 | A log line carrying the connection string or an `authorization` value is emitted with the secret redacted (golden-file log test) |
| AC5 | A unit test calls the same Mediator command handler resolved from the Api composition and from the Worker composition and gets the same result, proving handler code is shared, not copied (the slice-handler instance of this test was removed; see Notes at the end of this file) |
| AC6 | Handling the slice command produces an OTel trace with spans tagged `evidgate.module` per module crossed (removed; see Notes at the end of this file) |
| AC7 | `/internal/*` routes are absent from the served OpenAPI document (00 §9.1) and the skeleton `/v1` endpoints return the 00 §9.2 error envelope on a bad request, not `ProblemDetails` |

## 3. Contracts touched

- 00 §5.1 — the two-entrypoint component diagram is implemented as written; no change.
- 00 §9.1 — `GET /internal/health/live`, `GET /internal/health/ready`, `GET /metrics` implemented here as the first operational endpoints; mapped outside `/v1` and excluded from `contracts/openapi.yaml` and the served document (AC7). ## 4. Data model and migrations

None. ## 6. States and transitions

None. Slice results are fixed stubs (`incomplete`, `pending`) (removed; see Notes at the end of this file); real run/job/artifact states are 00 §8, owned by 04–07.

## 7. Jobs and integrations

- `Evidgate.Worker` is a `Generic Host` with hosted services only; the outbox dispatcher and queue consumers plug in at 01.5.1-T1/T3 without touching the host wiring.
- PostgreSQL 18 via Npgsql is the only external dependency for health; no S3, GitHub or LLM call exists yet.
- The journal-head check queries the `schema_migration` table that 01.4.1-T1 creates — until then `ready` stays 503, which is the intended deploy gate for 10.2.2-T1.

## Notes (CR-02/CR-01 skeleton removal)

- The sprint-1 skeleton slice was removed from the Api and Worker composition: the anonymous `/v1/slice/run` and `/internal/slice/run` routes, `SliceRunConsumer`, the in-memory run/catalog/manifest/event stores, the six slice handlers and the `ICatalog`/`IIngestion` seams are gone.
- No `/v1/slice` path is served any more; the real routes of plans 04 and 05 replace the slice, and the Worker no longer runs a demo on boot.
- T3 therefore describes history, not live behaviour. The hosts, health endpoints and `/metrics` from T1/T2 are unchanged.
- Acceptance statements above that mention the slice flowing through module calls no longer apply and are not re-verified.
