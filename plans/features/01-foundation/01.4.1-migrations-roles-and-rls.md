## 1. Goal and non-goals

**Goal.** `Evidgate.Migrator` (DbUp 7) applies ordered plain-SQL files from `migrations/` as the **owner** role — one transaction per file, forward-only, checksum-guarded, with `--status`/`--dry-run` and deploy-gate exit codes; four roles exist (owner/app/operator + the dedicated EXECUTE-only sweep role `evidgate_worker_sched` for T80 `SECURITY DEFINER` sweeps) with least privilege; the RLS baseline (`evidgate.current_org_id()`/`current_project_id()`, `FORCE ROW LEVEL SECURITY` template, empty `evidgate_resolve` schema) is in place so the app role provably cannot bypass tenancy; and an expand/contract playbook with a proven rename pair sets the schema-change discipline.

**Non-goals.** Any module's business tables (02–08 create theirs against this baseline); the `evidgate_resolve` resolver *functions* (02.6.1-T3, 03.4.1 — this story creates only the schema + grant pattern); the `02.6.1-T2` convention lint itself (01.4.2-T2 ships the equivalent schema test); the deploy pipeline consuming the exit codes (10.2.2-T1).

## 2. User stories and acceptance criteria

- As a developer, `dotnet run --project src/Evidgate.Migrator` takes a fresh database to head in one command, and `--status` shows pending files.
- As the Tech Lead, editing an already-applied migration is impossible: the Migrator refuses to start and `--status` names the drifted file.
- As a security reviewer, the app role demonstrably cannot read another tenant's rows and cannot bypass RLS.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | On a scratch PostgreSQL 18 container, the Migrator applies all pending files in lexical order, one transaction each, recording `name`, `checksum`, `applied_at`, `duration_ms` in `schema_migration`; `--status` prints applied/pending; exit 0 |
| AC2 | Failing migration (syntax error in file `NNNN`) rolls back its transaction completely, writes **no** journal row, exits non-zero — verified by `information_schema` absence of the half-created object |
| AC3 | Editing an applied file makes the Migrator exit non-zero with a checksum-mismatch message naming the file; `--status` shows the drifted row |
| AC4 | `--dry-run` lists pending files and applies nothing (journal unchanged) |
| AC5 | As the **app** role: `SET LOCAL evidgate.org_id` to org A cannot read org B rows on a fixture business table; `RESET ROLE`-free bypass attempts (`SET row_security = off`, table-owner tricks) fail — app is not owner and `FORCE ROW LEVEL SECURITY` is on |
| AC6 | `evidgate.current_org_id()` returns the set UUID when `evidgate.org_id` is configured and `NULL` (not an error, not all rows) when unset or empty — same for `current_project_id()` |
| AC7 | The expand/contract fixture pair (add `new_col`, dual-write, backfill, drop `old_col` in a later file) applies cleanly through the Migrator and the old code path still works mid-sequence |

## 4. Data model and migrations

Owned objects (all created by migrations `0001`–`0003` run as owner):

| Object | Definition |
|---|---|
| `schema_migration` | `name text PK`, `checksum text not null`, `applied_at timestamptz not null default now()`, `duration_ms int`; custom DbUp `IJournal` writes here; sequential, never re-run |
| schema `evidgate` | owned by owner; holds helper functions |
| `evidgate.current_org_id()` / `evidgate.current_project_id()` | `stable` SQL functions: `nullif(current_setting('evidgate.org_id', true), '')::uuid` (same for `project_id`); `EXECUTE` granted to app + operator |
| schema `evidgate_resolve` | empty; owned by owner; `USAGE`/`EXECUTE` grant pattern scripted for later `SECURITY DEFINER` resolver functions (T1); app has `EXECUTE` only, never `CREATE` |
| fixture `rls_probe` (test-only table, `0003`) | `org_id uuid not null`, `id uuid`, `unique (org_id, id)`, `FORCE ROW LEVEL SECURITY`, policy `org_id = evidgate.current_org_id()` — the template the tests and later tables copy |
| roles | `evidgate_owner` (DDL, migration runner), `evidgate_app` (CRUD, no `BYPASSRLS`, not owner), `evidgate_operator` (audited read path; used by 10/11), `evidgate_worker_sched` (dedicated sweep role: EXECUTE-only target for owner `SECURITY DEFINER` purge/sweep functions such as 01.5.1's `evidgate.purge_expired_idempotency`, T80; no table privileges of its own) |

## 5. API shapes (commands, queries, endpoints)

None. CLI surface of `Evidgate.Migrator`:

| Command | Exit code contract (consumed by 10.2.2-T1) |
|---|---|
| (default) apply pending | 0 all applied · 2 checksum mismatch · 3 migration failure · 4 unreachable DB |
| `--status` | prints applied/pending/drifted; 0 clean, non-zero on drift |
| `--dry-run` | lists pending; always exit 0 unless DB unreachable |

## 6. States and transitions

`schema_migration` is append-only; a file's lifecycle is `pending → applied`, with `failed` never journaled (transaction rollback). Drift (applied file edited) is detected, not a state.

## 7. Jobs and integrations

- `Evidgate.Api`/`Evidgate.Worker` boot check (01.1.2-T1.3) reads the journal head; the Migrator is the only writer.
- Local bootstrap script `scripts/dev/db-init.sh` creates the roles + database for the dev stack (01.8.1 consumes it).
- No scheduled jobs; purge/sweeper schedules belong to 01.5.1.

## 11. Rollout

- No feature flag; migrations run in every environment before app rollout (deploy gate 10.2.2-T1 consumes the exit codes).
- Order: T1 → T2 → T3 → T4 (T4 independent of T2/T3 content-wise but lands after them in the same PR series).
- Monitoring: Migrator exit codes surface in CI/deploy logs; journal drift is a `--status` check.
- Rollback: forward-only — a bad migration is fixed by a new migration, never by editing history (AC3 enforces).
