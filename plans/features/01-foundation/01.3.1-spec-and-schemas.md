## 1. Goal and non-goals

**Goal.** `contracts/` becomes the single source of truth for wire formats: an OpenAPI 3.1 `contracts/openapi.yaml` that lints clean at warn severity, carries every 00 §9.1/§9.2 convention and documents every V1 endpoint of 00 §9.3 as a stub; versioned JSON Schemas for the event envelope (00 §9.4) and adapter protocol (00 §10); and a written versioning/deprecation policy.

**Non-goals.** Generating the SDK or wiring validators (01.3.2); implementing any endpoint (02–08); the `contracts/cli.md` gate-exit-code document body beyond the section it already owns in 00 §9.3 (detailed in 07.5.2); webhook payload schemas (07/08).

## 2. User stories and acceptance criteria

- As an SDK/CLI consumer, the spec plus generated client compile and describe every endpoint before it is coded.
- As a backend developer, the conventions (envelope, cursor, idempotency, ETag, XSRF) are expressed once in `components/` and reused, so no endpoint invents its own shape.
- As a producer implementer, the event envelope and capability document schemas are versioned files I can validate against locally.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `spectral lint contracts/openapi.yaml` (Apache-2.0, ruleset committed) exits 0 at warn severity; a seeded lint violation fails it |
| AC2 | `components/schemas` contains the 00 §9.2 error envelope (`error.code/message/request_id/retryable/details[]`) and the cursor list envelope (`items`, `next_cursor`); `components/parameters` contains `cursor`, `limit` (default 50, max 200), `Idempotency-Key`, `If-Match`, `X-XSRF-TOKEN`; every V1 stub operation references them |
| AC3 | Every endpoint row of 00 §9.3 (V1 and V2-tagged) appears in the spec as a documented stub operation with its permission in `x-permission` (or an equivalent committed extension naming rule); `/internal/*` routes are absent |
| AC4 | `contracts/schemas/event-envelope.v1.json` validates the 00 §9.4 example and rejects a batch over the §9.3 caps (500 events / 1 MiB declared bounds); `contracts/adapter/capability.v1.json` validates the 00 §10 capability document (`protocol.major/minor`, `engine`, `platforms[]`, `supports`, `mode`) |
| AC5 | `contracts/README.md` states the versioning/deprecation policy: breaking change ⇒ new major (`/v2`) or a `*.vN.json` file bump; adapter `protocol.major` incompatible ⇒ rejected; deprecations announced in-field before removal |
| AC6 | All schema files are JSON Schema 2020-12, snake_case fields, enums lower_snake except `decision` values upper case (00 §7) — checked by a conventions test script |

## 3. Contracts touched

- 00 §9.1/§9.2/§9.3/§9.4/§10 — expressed as artifacts, not changed. Any spec fact that diverges from 00 must be raised as a CR, not resolved in the file.
- Resolved (T51): every operation in `contracts/openapi.yaml` carries its permission as the `x-permission` extension — the convention is fixed for AC3 and propagated by 01.3.2 codegen.
- Adapter schemas live in `contracts/adapter/` (00 §10, 04 D6); every schema file follows the `*.vN.json` rule of AC5, so the adapter plans (04.3.1, 04.5.1, 04.7.1, 06.2.2) name `capability.v1.json` / `config.v1.json`.
- No table or runtime contract change.

## 5. API shapes (commands, queries, endpoints)

The spec defines (stubs only, no implementation): the full 00 §9.3 table — `POST /v1/ci/token`, `POST /v1/projects/{p}/manifests`, `POST /v1/projects/{p}/runs`, `GET /v1/runs/{r}`, `POST /v1/runs/{r}/cancel`, `POST /v1/runs/{r}/events`, `POST /v1/runs/{r}/finalize`, `POST /v1/artifacts/upload-url`, `POST /v1/artifacts/{a}/complete`, `GET /v1/runs/{r}/decision`, `GET /v1/projects/{p}/runs`, `POST /v1/runs/{r}/rerun`, environment-revision, comparison, reprocess, releases, download-url, orgs/projects/memberships, ci-bindings/ingest-tokens, audit, support-grants, security-events, catalog reads/suite versioning, `POST /v1/webhooks/github`, V2 dry-run/PR/incidents/usage/jobs/healing routes — each with permission, status codes from 00 §9.2, and idempotency/ETag markers where §9.1 requires them.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §9.1 (XSRF, idempotency, ETag) | conventions are shared `components` — endpoints can't silently omit them | AC2, AC3 + Spectral custom rule |
| T38 | `X-XSRF-TOKEN` documented on every cookie-authenticated mutation; bearer routes excluded | AC2 + spec review |
| 00 §9.2 (error codes, no secrets in details) | error envelope schema + the fixed status/code list per operation | AC2, AC3 |
| 00 §5.7 P8 (payload caps) | §9.3 batch caps encoded as `maxItems`/`maxLength`/declared `maxBytes` in the event-envelope schema | AC4 |
| Input limits | schema `maxLength`/`pattern` on all string ids (`uuid`, ≤ 128-char idempotency key per 00 §7) | AC6 conventions script |
| Authz | permissions recorded per operation (`x-permission`), not implemented here | AC3 |
| Privacy / retention | spec describes contracts only; no data | — |
