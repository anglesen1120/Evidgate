## 1. Goal and non-goals

**Goal.** `BuildingBlocks.Persistence` delivers the single data-access path: `ITenantScope.BeginAsync(orgId, projectId?)` opens one app-role `NpgsqlConnection`, `BEGIN`s and sets `evidgate.org_id`/`evidgate.project_id` via parameterised `set_config(…, true)`; EF Core 10 write models and Dapper read queries share **that** connection+transaction; a `DbCommandInterceptor` throws on any command without the tenant setting; `FOR UPDATE SKIP LOCKED` claim + composite-FK/`unique (org_id,id)`/column conventions are enforced by schema tests; and the Mediator 3 pipeline runs the C2 order with an architecture test asserting it.

**Non-goals.** The `outbox`/`task`/`idempotency_record` tables and dispatcher themselves (01.5.1 — this story consumes 01.5.1-T2's outbox flush and 01.5.1-T6's idempotency store through their interfaces); the authorization permission catalogue (02 — the behaviour calls `ITenancyAuthorizer`-style interface resolved before the pipeline); the resolver functions (02.6.1); module `DbContext` contents (02–08).

## 2. User stories and acceptance criteria

- As a module developer, I cannot accidentally query outside a tenant scope — the interceptor throws, in tests and production.
- As a reviewer, the C2 pipeline order is a build assertion, not a comment.
- As the Tech Lead, schema conventions (`org_id` FKs, `unique (org_id,id)`, UUIDv7, `version` token) are tested against the live database, not documented hopes.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Any SQL executed on an `ITenantScope` connection without a prior `BeginAsync` throws `TenantScopeMissingException` — proven for EF Core and Dapper paths |
| AC2 | Inside `BeginAsync(orgA)`, a select on the `rls_probe`-style fixture returns only org A rows; after `Dispose`, the connection is reset (no `set_config` bleed into the pool — verified by reusing the pooled connection) |
| AC3 | EF Core write and Dapper read inside one scope see each other's uncommitted rows (same transaction); the scope's `CommitAsync`/`Dispose` maps to `COMMIT`/`ROLLBACK` |
| AC4 | `Architecture.Tests` fails when the Mediator behaviour registration order deviates from C2: telemetry → validation → tenant transaction → authorization → idempotency → handler → outbox flush → commit |
| AC5 | `SchemaConventionTests` (xUnit + Testcontainers, against the real DB) fail a table missing `unique (org_id, id)` and a business FK lacking the `org_id` composite column (T3, §5.4.1/§5.4.6) |
| AC6 | `IQuery<T>` handlers open their scope with `BEGIN READ ONLY` — the read-only mode is set as the transaction's first statement and the tenant `set_config` runs inside it, so no statement of a query path runs writable (probe on the pinned `postgres:18.6`: a late `SET TRANSACTION READ ONLY` is accepted and takes effect, while `READ WRITE`/`ISOLATION LEVEL` after the first statement are rejected with 25001) (T95); a write attempt inside one errors; a command's `Result` maps once to the 00 §9.2 envelope by the endpoint filter (C8) |
| AC7 | `FOR UPDATE SKIP LOCKED` claim helper, exercised by two concurrent claimers on a fixture queue, hands each row to exactly one claimer (F6, consumed by 01.5.1-T1) |

## 3. Contracts touched

- 00 §5.4.2/§5.4.7 — `set_config(…, true)` parameterised call + helper functions: implemented, not changed.
- 00 §5.5 C1–C8 — the pipeline, scope, EF/Dapper split and error mapping are implemented exactly; no deviation.
- Authorization behaviour depends on 02's permission contract — until 02.6.2 lands, the behaviour resolves the permission interface with a stub that fails closed (denies) unless a test registers a fake; flagged so no one wires a permissive default.
- Recorded — 01.4.2 is listed as depending on 01.5.1 (for T4's outbox/idempotency interfaces) **and** blocking 01.5.1 (T1's scope is a prerequisite of 01.5.1-T1/T2). The area plan resolves this by task-level deps (01.5.1-T1 ← 01.4.2-T1; 01.4.2-T4 ← 01.5.1-T2/T6) — i.e. the stories interleave. Noted so schedulers don't read the story edge as a cycle defect.
- Recorded — the interceptor's reach is the EF Core command pipeline only (M1W3-04): `TenantCommandInterceptor` sees the `DbCommand`s EF builds, batched ones included, and nothing else, so `COPY`, `NpgsqlBatch`, a command built directly on the scope's connection and the large-object API run outside it by design. The tenant boundary is row level security, which applies to every statement of the scope's transaction whatever sent it; the interceptor is the earlier, more legible failure for the ordinary path, and `ITenantDb`'s per-call scope accessor is the Dapper half of the same guard.
- Recorded — the scope's open path issues the read-only mode and both `set_config` calls as ONE command after `BEGIN` (M1W3-F3): Npgsql splits a multi-statement command with named parameters into an implicit batch, so a query scope opens in two round trips instead of four and the tenant values stay bound parameters. The mode is still the transaction's first statement.
- Recorded — `AddEvidgateTenancy` is also where Dapper's process-wide read prerequisites are set (M1W3-02): `DefaultTypeMap.MatchNamesWithUnderscores`, a `DateTimeOffset` type handler (`timestamptz` arrives as `DateTime`) and a `string[]` type handler (`text[]` arrives as `System.Array`). Dapper selects a positional record's constructor only when every parameter matches the reader's field type or carries a handler, so a host that registered Dapper itself would lose the whole read path.

## 4. Data model and migrations

No new business tables (the mechanism tables land in 01.5.1). This story contributes:

- `tests/fixture` schema objects used only by `SchemaConventionTests`/`TenantScopeTests` (a deliberately compliant table + deliberately violating tables created inside the test transaction, never migrated).
- EF Core conventions committed in `BuildingBlocks.Persistence`: snake_case singular table names, `version` `IsConcurrencyToken`, `created_at`/`updated_at` `timestamptz` UTC defaults, UUIDv7 id generation via `Guid.CreateVersion7()`. The token is store-generated on update (`ValueGenerated.OnUpdate`): the database owns the increment through the shared `set_updated_at_and_version` BEFORE UPDATE trigger a business-table migration attaches (0004/0005 are the first two, M1W3-01), and EF reads the new value back so a second tracked update in the same scope still matches its row.

## 5. API shapes (commands, queries, endpoints)

No endpoint. The pipeline surface:

| Element | Shape |
|---|---|
| `ITenantScope` | `BeginAsync(orgId, projectId?, readOnlyTransaction, ct) → IAsyncDisposable` scope; exposes `Connection`, `Transaction`, `IsReadOnly`, `CommitAsync()`; nested calls throw (one scope per request/task) |
| `ICommand<T>` / `IQuery<T>` | Mediator 3 markers; commands write, queries read (C1); a query scope opens `BEGIN READ ONLY` before `set_config` (T95) |
| Behaviours (C2 order) | `TelemetryBehaviour` → `ValidationBehaviour` (FluentValidation) → `TenantTransactionBehaviour` (opens `ITenantScope` from the pre-resolved principal) → `AuthorizationBehaviour` (permission × project via 02 interface, inside the scope) → `IdempotencyBehaviour` (commands with `Idempotency-Key`, via 01.5.1-T6 store) → handler → outbox flush (01.5.1-T2) → commit |
| `IClaimNext<T>` helper | `FOR UPDATE SKIP LOCKED` batch claim over Dapper for queue-style tables (F6) |
| Endpoint filter | `Result` → 00 §9.2 envelope; exceptions → 500 envelope with `request_id`, never `ProblemDetails` on `/v1` (C8) |

## 6. States and transitions

None (mechanism only). Scope lifecycle: `opened → committed | rolled-back`, enforced by disposal rules.

## 7. Jobs and integrations

- Consumed by every module (02–08), 01.5.1 (dispatcher/consumers open scopes from `task.org_id`), 02.6.2 (principal→tenant resolution feeds `BeginAsync`), 05.1.2 (environment revisions under the scope).
- The worker dispatcher/consumers reuse the same `ITenantScope` — no second data-access path (§5.4.2 covers request **and** task).

## 11. Rollout

- No feature flag; the pipeline is the permanent dispatch path. Merge order: T1 → T2/T3 → T4 (T4 waits on 01.5.1-T2/T6 interfaces per the task deps).
- Monitoring: `TelemetryBehaviour` emits per-handler spans/metrics (consumed by 10 dashboards).
- Rollback: revert; modules written against `ITenantScope`/C2 remain valid because the contract is unchanged — only its enforcement is new.
