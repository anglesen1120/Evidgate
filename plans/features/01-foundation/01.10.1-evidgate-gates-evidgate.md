## 1. Goal and non-goals

**Goal.** Evidgate uses itself: our CI produces test results in exactly the ingest format a customer produces (through the same adapter/mapper code, T48), pushes them to a real Evidgate project via the real `POST /v1/ci/token` OIDC exchange (F3), and — from M3 — the Evidgate decision becomes a required check that can block our own PRs. From M4, the friction found while dogfooding loops back as `fixtures/` cases and 04 issues.

**Non-goals.** The ingest API itself (02 tokens, 04 adapters/mappers, 05 run orchestration, 07 decision engine — those stories deliver the server side this story *consumes*); the web dashboard usage (09); the load test (10).

## 2. User stories and acceptance criteria

- As the Tech Lead, our own xUnit/Vitest/Playwright results appear in an Evidgate project as runs, proving the ingest path works for a real producer before any customer touches it.
- As a developer, a failing Evidgate decision blocks my PR exactly as it would a customer's, so the gate is exercised weekly by real usage.
- As QA, parser warnings or mapping gaps found on our own output become fixture cases, so dogfooding hardens 04 continuously.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A `main` build publishes a run whose artifact set is produced by the same adapter/mapper code shipped to customers (04): xUnit v3 → JUnit XML (⚠️ format verified in T1), Vitest → JUnit, Playwright → JUnit — each report parses through Evidgate's own JUnit mapper with zero errors |
| AC2 | The CI job exchanges a GitHub OIDC token at `POST /v1/ci/token` for a short-lived `ci_producer` token scoped to the Evidgate dogfood project (F3, T1 pre-tenant resolution) and pushes `manifest → events → finalize` for both `main` and PR builds; no static token is stored in repo secrets |
| AC3 | From M3, a required check `evidgate/decision` reads `GET /v1/runs/{r}/decision`; a FAIL blocks merge, `pending`/INCONCLUSIVE never yields PASS (00 §8.6), and a weekly exercised "missing evidence ⇒ not PASS" path is logged |
| AC4 | A real run appears in the dogfood project with the same fixture classes a customer uses; visible fields (state, decision, reasons) match what 09 renders |
| AC5 | Every parser error/warning or mapping gap observed on our own reports has either a merged `fixtures/` case + regression test, or an open issue in 04 — enforced by a `dogfood-findings.md` ledger reviewed at M4 |

## 4. Data model and migrations

## 5. API shapes (commands, queries, endpoints)

Consumed (never redefined here):

| Call | Purpose |
|---|---|
| `POST /v1/ci/token` | GitHub OIDC JWT → `ci_producer` token (02; T1 resolver) |
| `POST /v1/projects/{p}/manifests` | dogfood manifest describing our CI shards (xunit, vitest, playwright producers) |
| `POST /v1/projects/{p}/runs` | create run bound to the commit/PR (`Idempotency-Key` = `gh:<repo>:<run_id>:<run_attempt>`) |
| `POST /v1/runs/{r}/events` | mapped JUnit → event batches (04 mapper output) |
| `POST /v1/runs/{r}/artifacts/upload-url` + `complete` | raw reports uploaded as `raw_report` artifacts (T18 presign path — also dogfoods 01.8.1 parity) |
| `POST /v1/runs/{r}/finalize` | producer finalize with `last_sequence`, `count` |
| `GET /v1/runs/{r}/decision` | gate check reads decision + reasons |

Client = `packages/cli` (`evidgate` CLI) or `packages/sdk` — never curl, so the customer path is exercised.

## 6. States and transitions

None new. The runs exercise the canonical 00 §8.1 machine (`created → queued → running → collecting → complete`, `incomplete` when evidence is missing) — the "missing evidence never yields PASS" weekly exercise drives runs into `incomplete`/INCONCLUSIVE deliberately.

## 7. Jobs and integrations

- `dogfood.yml` runs after the main CI stages on `main` and PRs (M2): collects JUnit artifacts from xUnit v3, Vitest, Playwright jobs → invokes the 04 mapper path → ingest sequence above.
- Weekly scheduled workflow (`missing-evidence.yml`): creates a run, uploads only part of the evidence, asserts decision ≠ PASS — keeps AC3's negative path live.
- M3: `evidgate/decision` becomes required via branch protection update (01.7.1-T3 mechanism).
- M4: findings → `fixtures/reports/own-ci/` + `docs/dogfood-findings.md` → issues filed against 04 with reproducer fixtures.
- The GitHub OIDC binding for the dogfood project is provisioned by the 02 ci-binding endpoint (admins set it once); the token path is T1/T5 (HMAC-hashed, short-lived).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| F3 / 00 §5.7 S3 | OIDC exchange, no long-lived ingest token in repo secrets; `ci_producer` token lives only in job memory | AC2; workflow audit shows no `secrets.*` for ingest |
| T9 | producer slots bind on first accepted write; a second producer identity is rejected (exercises `producer_slot_taken`) | AC2 + a deliberate conflicting-producer step in the weekly job |
| T48 | same mapper code path as customers, not a bespoke pusher | AC1 code review + mapper version pin |
| 00 §9.1 idempotency | run create carries `Idempotency-Key` `gh:…` so retried CI jobs don't duplicate runs | retry test in T2 |
| 00 §5.7 S5 | our JUnit files go through the same capped/DTD-off XML parser as customer input | mapper already enforces; verified by fixture corpus |
| Privacy | reports contain our own test names only — internal repo, no customer data; artifacts marked `normal` sensitivity | review |
| Performance | ingest adds ≤ 2 min to pipeline; events ≤ 500/batch per 00 §9.3 limits | run timing in workflow summary |
| Retention | dogfood project data lives on the dev/staging deployment, retained per its normal policy; `dogfood-findings.md` is permanent repo history | — |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| JUnit XML format valid for our mapper | `Dogfood_XunitReport_Parses` — real xUnit v3 output fed to the mapper ⚠️ format verified, else mapper/emitter fixed (T1) |
| End-to-end ingest | `Dogfood_Run_Appears` — workflow run on `main` yields a queryable run with decision (AC2, AC4) |
| OIDC path | job uses `id-token: write`; no static token present (AC2) |
| Gate blocks FAIL | a PR with a deliberately failing test → `evidgate/decision` = FAIL → merge blocked (AC3) |
| Missing evidence ⇒ not PASS | weekly job asserts `incomplete` run ⇒ decision INCONCLUSIVE/`pending`, never PASS (AC3) |
| Idempotent re-run | same `Idempotency-Key` retry → single run (T2 test) |
| Fixture promotion | each ledger entry links a merged fixture or an open 04 issue (AC5, ledger check) |
