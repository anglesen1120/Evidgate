## 1. Goal and non-goals

**Goal.** Every piece of background work in Evidgate — outbox dispatch, reconciles, evaluations, webhooks, retention sweeps, usage roll-ups — runs through one durable mechanism: a transactional `outbox` row committed with the business change, a dispatcher that moves it into the `task` queue, and `Evidgate.Worker` consumers that claim rows with `FOR UPDATE SKIP LOCKED` and run idempotent handlers with a capped retry then `dead_letter`. Cron schedules fire through Cronos with the unique `(schedule_name, fire_at)` constraint — never a leader. The story also delivers `idempotency_record`, the only arbiter for `Idempotency-Key` on mutating endpoints (T11).

**Non-goals.** Runner `job`/`job_lease` leasing (05, V2 — 00 §5.3 keeps it separate); the concrete task payloads of modules 03–08; webhook signing/delivery content (00 §9.5, owner 03/06); alert sink implementation (10.3.1-T5 consumes the hook); the `job`/`job_lease` tables.

## 2. User stories and acceptance criteria

- As a module developer, I write one outbox row inside my command's tenant transaction and the work is guaranteed to run later, so I never wire a queue myself.
- As an operator, I can list and replay dead-lettered tasks, so a poisoned task is visible and recoverable instead of silently lost.
- As the Tech Lead, duplicate dispatch, worker crashes and concurrent schedule fires each produce exactly one side effect, proven by tests.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | An outbox row committed, then the worker killed before dispatch, is still dispatched after restart — `CrashAfterCommit_TaskStillDispatched` shows the handler ran exactly once |
| AC2 | Running the dispatcher twice over the same undispatched outbox rows yields exactly one `task` row per outbox row (`unique (idempotency_key)`) and one recorded side effect |
| AC3 | Two workers computing the same Cronos occurrence insert with `ON CONFLICT DO NOTHING` — exactly one `task` row exists for `(schedule_name, fire_at)` |
| AC4 | A handler that always throws is retried with exponential backoff + jitter until `max_attempts`, then `state = dead_letter` with `last_error` set; `GET /internal/operator/tasks/dead-letter` returns it |
| AC5 | `POST /internal/operator/tasks/dead-letter/{id}/replay` on a `dead_letter` row sets `state = queued`, `attempts = 0`, `available_at = now()`; on a non-dead-letter row it returns 409 `task_not_dead_letter` |
| AC6 | A mutating request with an `Idempotency-Key`: same key + same canonical request hash replays the stored status/body; same key + different payload returns 409 `idempotency_conflict`; the record's `expires_at ≥ created_at + 24 h`; the purge task deletes expired rows; `project_id` is NULL for org-scoped operations and the key still dedupes via `unique nulls not distinct (org_id, project_id, operation, key)` (T94) |
| AC7 | With N=4 concurrent consumers on one queue, a batch of claimed tasks is executed by exactly one consumer each (`FOR UPDATE SKIP LOCKED`); a task whose `locked_until` expires without completion is claimable again |

## 3. Contracts touched

- 00 §5.3 — implemented exactly (outbox → dispatcher → `task` queue → idempotent handler; schedules via unique fire key, no leader).
- 00 §5.4 — `task.org_id` is nullable for platform tasks; handlers open `ITenantScope` from the row's `org_id`. `task` and `outbox` are mechanism tables: they carry `org_id` but hold no RLS policy (the dispatcher and claim queries scan across orgs by design — area §4). `idempotency_record` is tenant data and gets RLS + `FORCE` (T2 helpers).
- 00 §7 / T11 — `idempotency_record` is the only arbiter; no business table gets a permanent unique on the key.
- T94 — `idempotency_record.project_id` is nullable (org-scoped operations carry NULL); the composite PK becomes a surrogate `id` PK plus `unique nulls not distinct (org_id, project_id, operation, key)` (PostgreSQL 15+, we run 18).
- T80 — every `SECURITY DEFINER` function ships `SET search_path = ''` with schema-qualified references, `EXECUTE` granted only to a dedicated role (`evidgate_worker_sched` for sweeps/purges), and every call audited — applied here to `evidgate.purge_expired_idempotency` and covered by the 11.2.1-T7 review.
- 00 §9.1 — dead-letter list/replay lives under `/internal/operator/*` on the operator ingress, never in `/v1`, never in `contracts/openapi.yaml` (T16, CR-01-4).
- Resolved (T11): terminal `task` rows (`done`, `dead_letter` after the replay window) are kept 30 days, then swept by a schedule — the 30-day sweep this story adds is the ruled value.


```sql
-- migrations/NNNN_platform_task_queue.sql
create table task (
  id              uuid primary key,
  org_id          uuid,                              -- null for platform tasks
  queue           text not null,
  task_type       text not null,
  payload         jsonb not null,
  idempotency_key text not null,
  schedule_name   text,
  fire_at         timestamptz,
  state           text not null default 'queued'
                  check (state in ('queued','active','retry','dead_letter','done')),
  attempts        int  not null default 0,
  max_attempts    int  not null default 8,
  available_at    timestamptz not null default now(),
  locked_until    timestamptz,
  last_error      text,
  created_at      timestamptz not null default now()
);
create unique index task_idem_uq      on task (idempotency_key);
create unique index task_fire_uq      on task (schedule_name, fire_at) where schedule_name is not null;
create index        task_claim_idx    on task (queue, available_at) where state in ('queued','retry');
create index        task_dead_idx     on task (created_at, id)         where state = 'dead_letter';
create index        task_terminal_idx on task (created_at)             where state in ('done','dead_letter');
```

```sql
-- migrations/NNNN_platform_idempotency_record.sql
create table idempotency_record (
  id              uuid primary key,                 -- Guid.CreateVersion7()
  org_id          uuid not null,
  project_id      uuid,                              -- NULL for org-scoped operations (T94)
  operation       text not null,
  key             text not null check (length(key) <= 128),   -- 00 §7
  request_hash    text not null,                              -- 'sha256:<hex>' over RFC 8785 canonical request (01.3.2-T4)
  response_status int,                                        -- null until the command commits
  response_body   jsonb,
  created_at      timestamptz not null default now(),
  expires_at      timestamptz not null check (expires_at >= created_at + interval '24 hours')
);
create unique index idempotency_record_uq on idempotency_record
  (org_id, project_id, operation, key) nulls not distinct;   -- T94: NULL project_id still dedupes
alter table idempotency_record enable row level security;
alter table idempotency_record force row level security;
create policy idempotency_record_org on idempotency_record
  using (org_id = evidgate.current_org_id());
create index idempotency_expiry_idx on idempotency_record (expires_at);
-- owner-owned purge used by the scheduled task (T80: SET search_path = '', schema-qualified references,
-- EXECUTE only to the dedicated sweep role evidgate_worker_sched, every call audited):
create function evidgate.purge_expired_idempotency(p_limit int) returns int
  language sql security definer set search_path = '' as
$$ delete from public.idempotency_record r where r.expires_at < now()
     and r.ctid in (select ctid from public.idempotency_record where expires_at < now() limit p_limit);
   select count(*) ... $$;  -- exact body finalised at build; audited like evidgate_resolve functions (T1/T80 pattern)
revoke all on function evidgate.purge_expired_idempotency(int) from public;
grant execute on function evidgate.purge_expired_idempotency(int) to evidgate_worker_sched;
```

`outbox_undispatched_idx` serves the dispatcher scan; `task_claim_idx` serves the claim query; `task_dead_idx` serves the operator list (keyset `(created_at, id)`, 00 §9.1); `task_terminal_idx` serves the retention sweep.

## 5. API shapes (commands, queries, endpoints)

Internal service surface (not HTTP): `OutboxWriter.Enqueue(taskType, payload, aggregateType, aggregateId, idempotencyKey)` — called only by the C2 outbox-flush behaviour inside the tenant transaction; `ITaskHandler<TPayload>` (`TaskType` string const, `HandleAsync(TPayload, ITenantScope, CancellationToken)`); `IScheduleRegistry` mapping `schedule_name` → Cronos expression, queue, `task_type`, payload factory; `IIdempotencyStore` (`TryBeginAsync`/`CompleteAsync`/`Replay`) used by the C2 idempotency behaviour.

| Endpoint | Shape | Auth | Codes |
|---|---|---|---|
| `GET /internal/operator/tasks/dead-letter?queue=&cursor=&limit=` | `ListDeadLetterTasksQuery` → Dapper on `task_dead_idx`, keyset `(created_at,id)`; `{ items, next_cursor }` | `platform_operator` on the operator ingress + audited support grant (00 §9.1) | 200, 401, 403 |
| `POST /internal/operator/tasks/dead-letter/{id}/replay` | `ReplayDeadLetterTask : ICommand` → `update task set state='queued', attempts=0, available_at=now(), locked_until=null where id=@id and state='dead_letter'` | same | 200; 404 `task_not_found`; 409 `task_not_dead_letter` |

No `ETag`/`Idempotency-Key` needed: replay is naturally idempotent through the `state` guard.

## 6. States and transitions

`task.state`: `queued → active → done`; `active → retry` (handler threw, `attempts < max_attempts`, `available_at = now() + backoff(attempts) + jitter`, `locked_until = null`); `active → dead_letter` (`attempts >= max_attempts`, `last_error` redacted); `dead_letter → queued` (operator replay). `locked_until` expiry while `state = active` makes the row claimable again (visibility timeout) — the crashed-worker path. Internal mechanism state only; no business state machine (area §4).

## 7. Jobs and integrations

- **Dispatcher loop** (Worker): batch-claims undispatched `outbox` rows (`FOR UPDATE SKIP LOCKED`, batch 200), inserts `task` rows (`idempotency_key = 'outbox:' || outbox.id`) and marks `dispatched_at` in the same transaction — crash anywhere in it is safe by construction.
- **Schedule runner** (Worker): every minute computes due Cronos occurrences per registered schedule, inserts `task` rows `ON CONFLICT (schedule_name, fire_at) DO NOTHING`; `pg_try_advisory_xact_lock(hashtext(schedule_name))` short-circuits concurrent fire attempts but the unique index is the guarantee.
- **Consumers**: per-queue polling with concurrency limits, `SELECT … FOR UPDATE SKIP LOCKED` claim setting `state='active'`, `locked_until = now() + visibility_timeout`.
- **Schedules registered by this story**: `idempotency.purge` (daily, calls `evidgate.purge_expired_idempotency`) and `task.sweep` (daily, deletes terminal rows older than 30 d (T11)).
- **Alert hook**: `ITaskAlertSink` notified on each `dead_letter` transition; OTel counters `task_dead_letter_total`, `task_dispatch_lag_seconds`, `outbox_undispatched` gauge — consumed by 10.3.1-T5 and the 00 §11 SLIs.

Authz: operator routes use `platform_operator`, not a tenant permission — tenant-scope pipeline does not apply (routes are outside `/v1`).

- **Authorization:** the consumer carries no request identity — it opens the row's `org_id` tenant scope from `task.org_id`, and a tenant handler never runs unscoped (it dead-letters instead); dead-letter list and replay ride the operator ingress under `platform_operator` outside `/v1`, never a tenant permission.
- **Retention/deletion:** payloads reference aggregates by id and hold no personal data; terminal `task` rows are swept after 30 d and `idempotency_record` rows are purged at `expires_at` by the audited owner function, so neither a retry nor a shutdown release outlives the retention window.
- **Telemetry:** `task_dead_letter_total`, `task_dispatch_lag_seconds` and the `outbox_undispatched` gauge carry queue and `task_type` only, and a shutdown release is marked `task.released=shutdown` on the consumer span — no org, project, payload or customer value is exported.
- **Failure path:** a lease-deadline cancellation becomes a `TimeoutException` and takes the ordinary retry/dead-letter path with the attempt counted; a host-shutdown cancellation releases the row (`queued`, `locked_until` null, attempt given back) instead of failing it; a handler that ignores its token cannot complete a superseded attempt, because every transition is guarded by `state = 'active' and locked_until = @lease and version = @version`; and a queue whose `Concurrency` is outside 1..64 fails `ValidateOnStart` at boot rather than killing the Worker inside its `BackgroundService`.

## Notes from the CR-04/CR-05 fix (#TBD, 2026-10-30)

- A handler runs under a token linked to the host stopping token and to its lease deadline. The deadline is the database-stamped `claim.locked_until` minus a margin of `min(5 s, lease/10)`, measured with the injected `TimeProvider` rather than a local clock, so a handler is cancelled before another consumer can reclaim the row and run the same work a second time.
- A cancellation caused by the lease deadline is reported as a `TimeoutException`, so it takes the ordinary failure path: the attempt is counted and the row moves to `retry` or `dead_letter` with a redacted `last_error` that names the overrun instead of showing a bare `OperationCanceledException`.
- A cancellation caused by host shutdown releases the row instead of failing it: `task` returns to `queued` with `locked_until` null, `available_at = now()` and the attempt given back (`attempts = attempts - 1`), so a deploy neither burns a retry nor dead-letters healthy work and `attempts` is unchanged.
- Cooperative cancellation is not a fence: a handler that ignores its token can still run past the lease, and its completion is then refused, because every transition is guarded by `state = 'active' and locked_until = @lease and version = @version`. The queue stays at-least-once, and the idempotency key of the enqueuing operation absorbs the replay.
- The claim itself is unchanged: `SELECT … FOR UPDATE SKIP LOCKED` with `locked_until = now() + visibility_timeout`, which still stamps one deadline for the whole batch, so two consumers never claim the same row.
- Every `QueueOptions` item is validated at start (`Concurrency` 1..64, the queue name, the routes, the default dispatch queue and the backoff ordering), so `Concurrency = 0` now fails `ValidateOnStart` with a message naming the configuration key instead of throwing inside the `BackgroundService` and killing the Worker.
