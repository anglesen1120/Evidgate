## 1. Goal and non-goals

**Goal.** The `@evidgate/cli` package exists (skeleton, config, exit codes and a dev-token path at M1 via 04.2.1-T2, so 04.2.2/04.2.3 have a base) as a Node 22+/TypeScript 6.0 binary `evidgate` that exchanges either a GitHub OIDC JWT (`ACTIONS_ID_TOKEN_REQUEST_*`) or a project ingest token for a short-lived `ci_producer` token at `POST /v1/ci/token`, caches it per CI job, refreshes before expiry, and exits with a loud, distinct code on auth failure.

**Non-goals.** Minting/validating `ci_producer` tokens (02.4.1/02.4.2 — this is the client side and the failure paths only); any other CLI command (04.2.2–04.2.4); the generated SDK internals (01.6.1); `evidgate gate` exit-code semantics (07.6.1 consumes them).

## 2. User stories and acceptance criteria

- As a CI pipeline, I add two env vars and the CLI authenticates itself — no long-lived secret in the workflow.
- As a developer debugging CI, an auth failure names the cause and exits non-zero instead of hanging.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | With `EVIDGATE_OIDC_TOKEN` (or `ACTIONS_ID_TOKEN_REQUEST_URL`/`_TOKEN` env pair) present, `evidgate auth login` exchanges the OIDC JWT at `POST /v1/ci/token` and caches the returned `ci_producer` token + expiry |
| AC2 | With `EVIDGATE_INGEST_TOKEN`, the same exchange path works; plaintext ingest token is never written to disk, logs or metrics (T5: server stores HMAC, client keeps it only in memory/env) |
| AC3 | A second CLI invocation in the same job reuses the cached token while `exp - now > 60 s`, and refreshes silently when within the margin |
| AC4 | A 401/403 from `/v1/ci/token` exits code 3 with the server's `error.code` printed to stderr (never retried blindly); a 429 honours `Retry-After` once then fails |
| AC5 | `EVIDGATE_API_URL`, `EVIDGATE_PROJECT`, token source — all configurable via env or `--flag`, env wins over flag defaults, missing config exits 3 with the missing names |
| AC6 | The CLI never prints a bearer token (T78): `auth login --json` outputs `{ok, expires_at, project_id}` only; the token reaches CI via the `0600` cache file or is appended to `$GITHUB_ENV` after an `::add-mask::<token>` line (`--github-env`) |
| AC7 | With `EVIDGATE_BINDING_CHALLENGE` set (the challenge of a `pending_verification` `ci_binding`, stored as a repository variable by the repo owner — T70), `resolveConfig` reads it and `auth login` includes `binding_challenge` in the `/v1/ci/token` body; a 403 `binding_pending` or 409 `binding_conflict` exits 3 with `error.code` + `request_id` on stderr and a remediation hint (never retried) |
| AC8 | Dev path (amended 2026-11-01, D-S177-Q1: the dev token is now exchanged like an ingest token and cached; the text below is the original M1 wording): with `EVIDGATE_DEV_TOKEN` set (an ingest token minted by `seed-dev`, 01.8.1-T4; until 02.4.2-T1 lands, integration tests use a test principal) and no OIDC/ingest source, `getToken()` returns it as the bearer without calling `/v1/ci/token`; it is redacted like any token, never written to the cache, and refused when `EVIDGATE_ENV` is `staging` or `prod`; superseded by the T1 exchange at M2 |

## 3. Contracts touched

- 00 §9.3 `POST /v1/ci/token` — consumed as specified (request `{ oidc_jwt } | { ingest_token }` + project, plus the optional additive field `binding_challenge` when `EVIDGATE_BINDING_CHALLENGE` is set, T70; response `ci_producer` token + `expires_at`); no other change.
- `contracts/cli.md` — auth env vars (including `EVIDGATE_BINDING_CHALLENGE`), the `binding_pending` / `binding_conflict` error rows, cache location, and exit-code 3 definition are written down here (file owned across 04.2.x stories; this story adds the auth section).
- No API, schema or permission change; the CLI is a bearer-token client, not cookie-authenticated (T38 — no XSRF handling needed).
- Resolved (T78): the CLI never prints a bearer token — `--json` emits `{ok, expires_at, project_id}`; the token is delivered through the `0600` cache file or `$GITHUB_ENV` behind `::add-mask::` (EVG-SEC-01).
- Resolved (T70): `EVIDGATE_BINDING_CHALLENGE` is forwarded as `binding_challenge` on the exchange when present; the server answers 403 `binding_pending` (challenge not yet presented by that repository) or 409 `binding_conflict` (repository already bound `active` in another org) — both are terminal for the step and echo `error.code` verbatim.

## 4. Data model and migrations

None (no database objects — customer-side CLI). On-disk footprint is the token cache file only, §5.

## 5. API shapes (commands, queries, endpoints)

Client-side command surface (`packages/cli`, TS 6.0, ESM, Node 22+; SDK calls via `packages/sdk` generated from `contracts/openapi.yaml`):

| Command / module | Behaviour |
|---|---|
| `evidgate auth login [--json] [--github-env]` | resolves token source (env `EVIDGATE_OIDC_TOKEN` → `ACTIONS_ID_TOKEN_REQUEST_*` fetch → `EVIDGATE_INGEST_TOKEN`), POSTs to `/v1/ci/token` — adding `binding_challenge` when `EVIDGATE_BINDING_CHALLENGE` is set (T70) — writes the token only to the `0600` cache file (or appends it to `$GITHUB_ENV` after emitting `::add-mask::<token>` when `--github-env` is passed); stdout and `--json` output `{ok, expires_at, project_id}` — the token is never printed (T78) |
| `auth/token-cache.ts` | cache file `${EVIDGATE_CACHE_DIR:-$XDG_CACHE_HOME/evidgate}/ci-token.<sha256(api_url+project)>.json`, mode `0600`, fields `{token, expires_at}` |
| `auth/refresh.ts` | `getToken()` used by every later command: returns cached token if `exp - now > 60 s`, else re-exchanges; wraps 401/403/409 → exit 3 echoing `error.code` verbatim (incl. `binding_pending` / `binding_conflict`, T70), 429 → one retry after `Retry-After`, network error → exit 3 `transport` |
| `auth/dev-token.ts` | `EVIDGATE_DEV_TOKEN` guard (env `dev` + loopback, refused on staging/prod); the token is then exchanged like an ingest token (D-S177-Q1) |
| `config.ts` | `EVIDGATE_*` env + flag parsing — `EVIDGATE_API_URL`, `EVIDGATE_PROJECT`, token envs, `EVIDGATE_BINDING_CHALLENGE`; single `resolveConfig()` used by all commands; redacts token and challenge values in `--verbose` logs |

Exit codes (from `contracts/cli.md`, shared with 07.6.1's `gate`): `0` ok, `3` tool/transport/auth error; auth-specific subcodes appear only in the stderr message, not the exit code.

## 6. States and transitions

Cached token: `absent → valid → expiring (≤ 60 s) → re-exchanged`; `401/403` deletes the cache entry so the next run re-authenticates cleanly. Ingest-token server states (`active/rotated/revoked/expired`, 00 §8.9) surface to the CLI only as 401/403 bodies — the CLI never distinguishes them beyond echoing `error.code`.

## 7. Jobs and integrations

- `POST /v1/ci/token` resolves the tenant via `evidgate_resolve` `SECURITY DEFINER` functions server-side (T1, owned by 02.6.1); the CLI only transports credentials.
- GitHub OIDC acquisition uses the documented `ACTIONS_ID_TOKEN_REQUEST_URL` + `ACTIONS_ID_TOKEN_REQUEST_TOKEN` request with `audience=evidgate` ⚠️ (standard Actions OIDC flow; verified against GitHub docs in 02.4.1's server work — client mirrors it).
- No background jobs; no retries of side-effecting calls (token exchange is safe to retry — it is a read-equivalent mint, and the server keys `ci_token_issue.jti` per T7).
