## 1. Goal and non-goals

**Goal.** Authenticate a trusted CI job using its project ingest token, cache the short-lived producer credential privately, renew it before expiry, and surface auth failures distinctly.

**Non-goals.** Minting/validating `ci_producer` tokens (02.4.1/02.4.2 — this is the client side and the failure paths only); any other CLI command (04.2.2–04.2.4); the generated SDK internals (01.6.1); `evidgate gate` exit-code semantics (07.6.1 consumes them).

## 2. User stories and acceptance criteria

- As a CI pipeline, I add two env vars and the CLI authenticates itself — no long-lived secret in the workflow.
- As a developer debugging CI, an auth failure names the cause and exits non-zero instead of hanging.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A valid project ingest token exchanges for a scoped producer bearer. No external issuer or CI provider call. |
| AC2 | With `EVIDGATE_INGEST_TOKEN`, the same exchange path works; plaintext ingest token is never written to disk, logs or metrics (T5: server stores HMAC, client keeps it only in memory/env) |
| AC3 | A second CLI invocation in the same job reuses the cached token while `exp - now > 60 s`, and refreshes silently when within the margin |
| AC4 | A 401/403 from `/v1/ci/token` exits code 3 with the server's `error.code` printed to stderr (never retried blindly); a 429 honours `Retry-After` once then fails |
| AC5 | `EVIDGATE_API_URL`, `EVIDGATE_PROJECT`, token source — all configurable via env or `--flag`, env wins over flag defaults, missing config exits 3 with the missing names |
| AC6 | `auth login --json` emits only `{ok, expires_at, project_id}`; credentials stay in memory or a private `0600` file. |
| AC7 | A missing project credential fails closed; no repository challenge or provider login fallback. |
| AC8 | Dev path (amended 2026-11-01, D-S177-Q1): with `EVIDGATE_DEV_TOKEN` set (an ingest token minted by `seed-dev`, 01.8.1-T4) and no OIDC/ingest source, `getToken()` exchanges it at `POST /v1/ci/token` like an ingest token and returns the minted `ci_producer` token as the bearer (source `dev`); only the minted token is cached, the dev token is redacted like any token and never persisted, and it is refused unless `EVIDGATE_ENV=dev` and the API host is loopback (`staging`/`prod` always refused) |

## 3. Contracts touched

- 00 §9.3 `POST /v1/ci/token` — consumed as specified (request `{ oidc_jwt } | { ingest_token }` + project, plus the optional additive field `binding_challenge` when `EVIDGATE_BINDING_CHALLENGE` is set, T70; response `ci_producer` token + `expires_at`); no other change.
- `contracts/cli.md` — auth env vars (including `EVIDGATE_BINDING_CHALLENGE`), the `binding_pending` / `binding_conflict` error rows, cache location, and exit-code 3 definition are written down here (file owned across 04.2.x stories; this story adds the auth section).
- No API, schema or permission change; the CLI is a bearer-token client, not cookie-authenticated (T38 — no XSRF handling needed).
- No bearer material in stdout, JSON, command arguments, job artifacts or logs.
- No repository challenge is forwarded; a job without an eligible project credential cannot exchange.

## 4. Data model and migrations

None (no database objects — customer-side CLI). On-disk footprint is the token cache file only, §5.

## 5. API shapes (commands, queries, endpoints)

Client-side command surface (`packages/cli`, TS 6.0, ESM, Node 22+; SDK calls via `packages/sdk` generated from `contracts/openapi.yaml`):

| Command / module | Behaviour |
|---|---|
| `evidgate auth login [--json]` | Exchange the project ingest token, cache the producer credential in a private file, and emit only `{ok, expires_at, project_id}`. |
| `auth/token-cache.ts` | cache file `${EVIDGATE_CACHE_DIR:-$XDG_CACHE_HOME/evidgate}/ci-token.<destination>.<binding>.json` (both 64-hex SHA-256 digests: destination over `[v2, api_url, project]`, binding over `[v2, source kind, credential]`), mode `0600`, fields `{token, expires_at}` |
| `auth/refresh.ts` | `getToken()` used by every later command: returns cached token if `exp - now > 60 s`, else re-exchanges; wraps 401/403/409 → exit 3 echoing `error.code` verbatim (incl. `binding_pending` / `binding_conflict`, T70), 429 → one retry after `Retry-After`, network error → exit 3 `transport` |
| `auth/dev-token.ts` | `EVIDGATE_DEV_TOKEN` guard (env `dev` + loopback, refused on staging/prod); the token is then exchanged like an ingest token (D-S177-Q1) |
| `config.ts` | `EVIDGATE_*` env + flag parsing — `EVIDGATE_API_URL`, `EVIDGATE_PROJECT`, token envs, `EVIDGATE_BINDING_CHALLENGE`; single `resolveConfig()` used by all commands; redacts token and challenge values in `--verbose` logs |

Exit codes (from `contracts/cli.md`, shared with 07.6.1's `gate`): `0` ok, `3` tool/transport/auth error; auth-specific subcodes appear only in the stderr message, not the exit code.

## 6. States and transitions

Cached token: `absent → valid → expiring (≤ 60 s) → re-exchanged`; `401/403` deletes the destination's cache entries so the next run re-authenticates cleanly. Ingest-token server states (`active/rotated/revoked/expired`, 00 §8.9) surface to the CLI only as 401/403 bodies — the CLI never distinguishes them beyond echoing `error.code`.

## 7. Jobs and integrations

- `POST /v1/ci/token` resolves the tenant via `evidgate_resolve` `SECURITY DEFINER` functions server-side (T1, owned by 02.6.1); the CLI only transports credentials.
- No provider credential request; a trusted job reads its protected project ingest token.
- No background jobs; no retries of side-effecting calls (token exchange is safe to retry — it is a read-equivalent mint, and the server keys `ci_token_issue.jti` per T7).

**Notes (CLI-CACHE-FOLLOWUPS, S181, 2026-11-01; merged #381, 450b1a65):** the token cache directory is now refused when it is a symlink, foreign-owned or group/world-writable (write: `token_cache_error`; read: no cache), and a successful write deletes the destination's entries bound to another credential (bound-name shape only, symlinks unlinked not followed, failure never fails the write). `contracts/cli.md` §7 updated; specs in `packages/cli/src/auth/tokenCache.test.ts` and `getToken.test.ts`.
