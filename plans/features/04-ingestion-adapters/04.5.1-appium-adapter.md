## 1. Goal and non-goals

**Goal.** A UiAutomator2 (Android) Appium run maps to protocol v1 events with device identity carried in the variant (never a web locator field), registers a capability document declaring its engine/platform/`supports`, honours the device exclusive-lease client before starting, and produces golden fixtures the conformance harness (04.6.1) can diff. XCUITest is explicitly declared unsupported on non-macOS hosts rather than silently attempted.

**Non-goals.** The device lease server/allocation logic itself (05.8.1 — this story is a client of it); the protocol schemas and negotiation rules (04.7.1 — this story is an adapter conforming to them); the conformance harness engine (04.6.1 — this story only adds fixtures into it); Appium's own driver internals or device-farm provisioning (customer-operated); healing/validator use of Appium evidence (08.9.2 consumes this story's output, not vice versa).

## 2. User stories and acceptance criteria

- As a mobile QA engineer, I run my UiAutomator2 suite through the `evidgate-appium` adapter and see per-test events with the device model/OS version attached to the variant, distinguishable from a web run on the same case id.
- As the platform, an XCUITest run submitted from a non-macOS host is refused with a clear "unsupported on this host" signal rather than producing wrong or partial data.
- As the device fleet operator, no two concurrent runs claim the same physical/emulated device without the lease client enforcing exclusivity and a reset-by-policy before start.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `@evidgate/adapter-appium` registers a capability document (`engine.family: "appium"`, `engine.version`, `platforms: ["android"]` for V2, `supports.cancel: true`, `mode: "full"`) at first send; it validates against `contracts/adapter/capability.schema.json` (04.7.1) |
| AC2 | A UiAutomator2 session's test results map to events whose `ext.schema = "adapter-appium/1"` and whose variant carries `{ platform: "android", device_model, os_version, app_checksum }`; case identity never falls back to a web CSS/XPath locator field |
| AC3 | Submitting an XCUITest capability document on a non-macOS host (`platforms` reports the host OS) is refused before any event write: 422 `unsupported_platform_host` naming the required host platform, with `mode` reported as declared-but-refused, never silently degraded to `ingest_only` |
| AC4 | Before `execute`, the adapter calls the device exclusive-lease client (05.8.1-T1); a lease denial (device already held) aborts the run attempt with a clear CLI error and no events are sent; a granted lease triggers reset-by-policy before the first `prepare` step |
| AC5 | The adapter's golden fixtures live in `fixtures/appium/` per the 04.6.1 layout; the conformance harness (04.6.1-T1 runner) diffs them with zero unexplained differences; XCUITest fixtures are present but marked ⚠️ pending a macOS host and excluded from the CI-required set until then |
| AC6 | Retries and step events reuse the same normalisation contract as other adapters (00 §8.3: raw status preserved, normalised status separate, retries become `attempt_no` 1..n) — device-specific steps never invent a new status vocabulary |

## 4. Data model and migrations

No new tables (this is a `packages/adapter-appium` TypeScript story; server-side event/producer tables are owned by 04.1.1/04.7.1 and unchanged). Component/package structure instead:

```text
packages/
  adapter-appium/
    src/
      capability.ts        # builds + registers the capability document (04.7.1 client)
      session.ts           # wraps the Appium WebDriver session (UiAutomator2 client)
      mapping.ts           # test result → event envelope (variant, status, attempt_no)
      lease-client.ts      # calls IDeviceLeaseClient (05.8.1-T1) before prepare
      unsupported.ts       # host-platform gate for XCUITest (macOS-only)
      index.ts             # discover/prepare/execute/collect/cleanup entrypoints
    test/                  # Vitest: mapping.spec.ts, unsupported.spec.ts, lease-client.spec.ts
    package.json            # Node 22+, TypeScript 6.0.x (T36-adjacent: this is a customer-side adapter package, not the healing-validator, but same runtime line)
fixtures/appium/
  uiautomator2-happy-path/  case.json + session.log + expected.json
  uiautomator2-retry/       case.json + session.log + expected.json
  xcuitest-macos-only/      case.json + session.log + expected.json   # ⚠️ excluded from required CI set
```

No DbUp migration in this story: `adapter_capability` (04.7.1) and `event`/`producer_slot` (04.1.1) already accept any conformant capability document/producer without a schema change.

## 5. API shapes (commands, queries, endpoints)

This is a client-side adapter package; it calls existing server endpoints and internal clients, defining no new `/v1` route:

| Shape | Detail |
|---|---|
| Capability registration | adapter builds the document per §2 AC1 and sends it via the first `POST /v1/runs/{r}/events` batch (04.7.1's `RegisterAdapterCapability` path) — no separate call |
| Event mapping | `mapping.ts` produces the 00 §9.4 envelope: `type: test.started|test.step|test.finished`, `status` = raw Appium/W3C WebDriver test outcome, `ext.schema = "adapter-appium/1"`, `ext.variant = { platform, device_model, os_version, app_checksum }` |
| Device lease call | `IDeviceLeaseClient.AcquireAsync(deviceSelector, runId)` (05.8.1-T1 contract, consumed as a typed client over its documented transport) before `prepare`; `ReleaseAsync` in `cleanup` |
| Unsupported-host gate | pure function `checkHostSupport(capability, hostPlatform): { supported: boolean, reason?: "unsupported_platform_host" }` called before any network call; on failure the CLI exits non-zero with the reason, no batch is ever sent |
| Errors surfaced to the user | CLI-level: `unsupported_platform_host` (local, pre-send), `device_lease_denied` (from 05.8.1), plus the standard 04.1.1/04.7.1 server error codes (`unsupported_protocol_major`, `unknown_producer`, etc.) passed through unmodified |

## 6. States and transitions

- Adapter session (client-local, not persisted server-side): `discovering → leased → preparing → running → collecting → cleaned_up` mirrors the protocol's five operations; a lease denial short-circuits at `discovering → leased` and the session never reaches `preparing`.
- Case attempt status still follows 00 §8.3 (`passed | failed | skipped | timed_out | error | blocked`); device disconnects mid-test map to `error`, never a silent `blocked` unless a setup step genuinely failed.
- Capability `mode` is fixed `full` for UiAutomator2 in V2 (no `ingest_only` variant planned for this adapter).

## 7. Jobs and integrations

- Consumes: 04.7.1's `IProtocolNegotiator`/capability schema (registration must pass or the adapter refuses to start), 05.8.1-T1's device lease client, 04.6.1's fixture layout + harness (for its own golden set), 04.1.1's event ingest endpoint (transport).
- Consumed by: 06.3.5 (evidence — device video/screenshot artifacts tagged with the mobile variant), 07.5.4 (policy — decisions over mobile cases use the same evaluator, no special-casing needed if variant/status mapping is correct), 08.9.2 (healing — incident creation keys on `execution_key`, which already encodes the mobile variant per §3).
- No outbox/task ownership in this story (client package); server-side task handling for the events it sends is 04.1.1's.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S5 / NFR-04-3 | Session logs/W3C responses are parsed defensively (bounded size, no `eval`, JSON.parse only); device identifiers are allow-listed fields, never free-text injected into `ext` without a schema | `mapping.spec.ts` fuzz cases (oversized session log, malformed WebDriver response) |
| T9 (producer binding, unaffected) | The adapter is a normal CI/agent producer — it registers under the run's existing `producer_slot` binding rules; no special exemption | integration smoke: adapter batch rejected 403 `producer_slot_taken` when replayed under a different token, same as any producer |
| T42 | `adapter-appium` runs the shared `fixtures/contracts/adapter/` corpus (Ajv) exactly like other adapters — no separate validator | CI job reuses 04.7.1-T3's harness |
| Device/app privacy | `app_checksum` (not the binary) travels in the variant; device identifiers are hardware model/OS version only, never IMEI/serial/user account data (DECISIONS §7 personal-data caution) | fixture review + `mapping.spec.ts` assertion that no PII-shaped field name is emitted |
| Lease safety (05.8.1 rule, consumed) | Adapter never starts `execute` without a granted lease; `cleanup` always releases even on failure (`finally` block) | `lease-client.spec.ts`: forced exception in `execute` still calls `ReleaseAsync` |
| Host-platform honesty (D7 spirit) | XCUITest on non-macOS is refused pre-send, never silently downgraded to `ingest_only` | AC3 test |
| Performance | Client-side only; no server hot path added. Session log parsing is O(events) single pass, no N+1 (there is no DB here) | `mapping.spec.ts` timing on a 2 000-step session log stays under 1 s (informal budget, no server SLA) |

## 11. Rollout

- Feature-gated by milestone: 04.5.1 ships in M4 (V2); no runtime flag needed since Appium producers simply don't exist in customer traffic until this adapter is distributed.
- Merge order: T1 → T2 → T3 (can run in parallel with T2 once T1 lands, per the task deps: T3 depends only on 05.8.1-T1, not on T2) → T4 last (needs T1–T3 working to capture real session logs for fixtures).
- Distribution: published as `@evidgate/adapter-appium` alongside the other adapter packages (01.1.1's `packages/` workspace); documented in the quickstart alongside Playwright/JUnit (04.2.4).
- Monitoring: adapter version + `unsupported_platform_host` counts surface in ingest metrics (04.1.2-T1 namespace) once traffic exists.
- Rollback: revert the package publish; no server-side schema or state is adapter-specific, so rollback has no data migration.
