## 1. Goal and non-goals

**Goal.** Protocol v1 exists as machine-readable JSON Schemas under `contracts/adapter/` — the capability document, the five operations (`discover`, `prepare`, `execute`, `collect`, `cleanup`), and the run-create **configuration document** (`config.v1.json`, T97) — and the server enforces the documented negotiation rules: an incompatible `protocol.major` is rejected at registration/claim with a clear error, minor versions negotiate per a written matrix, unknown `supports` flags are ignored, and `mode: ingest_only` results are viewable but never gate-eligible.

**Non-goals.** The ingest endpoints themselves (04.1.x); the Playwright/JUnit/Appium adapters that *produce* capability documents (04.3.x, 04.4.x, 04.5.1); agent job claiming semantics beyond the protocol check (05.7.x); evidence use of `ingest_only` results (06.2.2); the OpenAPI surface of `/v1` (01.3.x).

## 2. User stories and acceptance criteria

- As an adapter author (any language), I can implement against `contracts/adapter/` JSON Schemas alone, without reading TypeScript or C# source.
- As the platform, I reject adapters speaking an incompatible protocol major before any event is accepted, so a version skew never corrupts a run.
- As a customer with an unsupported engine, my `ingest_only` results are stored and viewable but can never produce a gating PASS (D7).

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `contracts/adapter/capability.v1.json`, `contracts/adapter/config.v1.json` (run-create configuration document, T97) plus one schema per operation (`discover`, `prepare`, `execute`, `collect`, `cleanup`) exist, are valid JSON Schema (2020-12), and every vector of the `fixtures/contracts/vectors/` corpus for those schema keys validates against them |
| AC2 | A capability document with `protocol.major` different from the server's supported major is rejected at capability registration and at job claim with 422 `unsupported_protocol_major`; the error names the adapter's major and the supported major(s) |
| AC3 | Same major, adapter minor higher than the server: registration succeeds and `supports` flags unknown to the server are ignored (recorded verbatim in `adapter_capability.supports` jsonb; the document root stays closed per 00 §10, so an undefined root member is 422 `capability_invalid`); same major, adapter minor lower: accepted for the operations the minor declares |
| AC4 | A capability document declaring `mode: ingest_only` registers successfully; results from that producer are stored and viewable, and the run's evaluation is never gate-eligible unless the manifest is proven complete (00 §10) — asserted by a test that a decision for such a run is `INCONCLUSIVE` when the manifest is incomplete |
| AC5 | Both validators agree: the Corvus.Json.Validator (server) and Ajv 8 (CLI) accept/reject verdicts on the shared `fixtures/contracts/vectors/` corpus (the `capability.v1`, `config.v1` and operation schema keys) are identical; any disagreement fails both builds (T42) |
| AC6 | The compatibility matrix test enumerates (server major, adapter major, adapter minor) × (accept, reject) and documents each expected outcome; a behaviour change in negotiation fails the test |
| AC7 | A capability document declaring `capture_control: false` registers successfully and runs produced by it carry the `capture_uncontrolled` label (set at run create by 05.2.1); otherwise the configuration document — per-project capture flags, redaction patterns, max sizes per kind, decided server-side by 06.2.2 — is delivered to the adapter at run create and must be honoured (T97) |

- Recorded (04.7.1-T2, 2026-10-08): the natural-key `name` is taken from the `ext.schema` prefix (`<adapter-name>/<protocol-major>`); the capability document itself carries no `name`.
- Recorded (04.7.1-T2, 2026-10-08): the 409 rule follows `contracts/adapter/README.md` — §6's "registers as a new row" sentence is superseded: the same natural key with a different `mode`/`supports` set is 409 `capability_conflict`.

## 4. Data model and migrations

One table (owned by this module per area plan §4):

```sql
-- migrations/NNNN_ingestion_adapter_capability.sql
create table adapter_capability (
  id              uuid primary key,           -- UUIDv7, app-generated (00 §7)
  org_id          uuid not null,
  name            text not null,              -- adapter identity, e.g. "evidgate-junit"
  protocol_major  int  not null,
  protocol_minor  int  not null,
  engine_family   text not null,
  engine_version  text not null,
  platforms       text[] not null,
  supports        jsonb not null default '{}',-- discovery, step_events, retry, cancel, capture_control (+ unknown keys kept)
  mode            text not null check (mode in ('full','ingest_only')),
  first_seen_at   timestamptz not null default now(),
  unique (org_id, id),                                        -- T3
  unique (org_id, name, protocol_major, protocol_minor, engine_version)  -- area plan §4
);
-- RLS: org_id = evidgate.current_org_id(); app role cannot UPDATE (capability rows are first-write facts).
```

No `project_id`: capability documents are producer-level metadata, not project data; tenant isolation is by `org_id` + RLS (00 §5.4.1–2).

## 5. API shapes (commands, queries, endpoints)

| Shape | Detail |
|---|---|
| `RegisterAdapterCapability` command (`ICommand<RegisterCapabilityResult>`) | Handler in `Evidgate.Modules.Ingestion`; invoked by the ingest pipeline on first send and by job claim (05.7.x); validates the document with Corvus against `capability.v1.json` before binding (edge validation per 00 §5.5 Edge), then applies negotiation rules; upserts by the natural unique key — a repeated identical document is a no-op |
| `ValidateAdapterCapability` — internal service (`Evidgate.Modules.Ingestion.Contracts.IProtocolNegotiator`) | Pure function over (document, server protocol version) → `accept | reject { code, details }`; used by registration now and by `jobs/claim` in 05.7.x so both paths share one negotiation rule |
| No new `/v1` endpoint | Registration piggybacks on `POST /v1/runs/{r}/events` (first send) and `POST /v1/agents/jobs/claim` (V2, owner 05); a rejected capability returns the 00 §9.2 envelope with `unsupported_protocol_major` and `retryable: false` |
| Errors | 422 `capability_invalid` (schema failure, `details[].path` points at the offending field), 422 `unsupported_protocol_major` (major mismatch, `details` names both majors) |
| Run-create configuration document (T97) | `contracts/adapter/config.v1.json` is owned by T1; 05.2.1 fills it from 06.2.2's per-project capture flags/redaction patterns/per-kind size caps and returns it at run create; a producer whose capability declares `capture_control: false` may ignore it — its runs carry the `capture_uncontrolled` label |

## 6. States and transitions

- Protocol negotiation outcome per document: `accepted` (row upserted) | `rejected` (no row; error returned). No stored state for rejections beyond the request log.
- `mode` is immutable per capability row (`full | ingest_only`); an adapter that changes `mode` for the same natural key registers as a new row (different `supports`/fields change the unique tuple — a genuine conflict is rejected 409 `capability_conflict`).

## 7. Jobs and integrations

- Consumed by: 04.3.1/04.4.1/04.5.1 (adapters emit the capability document at first send), 05.7.1/05.7.3 (claim-time validation via `IProtocolNegotiator`), 06.2.2 (gate-eligibility flag on the revision derived from `mode` + manifest completeness).
- `ingest_only` → gate-eligibility is enforced where the freeze result is evaluated (06/07); this story exports the `mode` field and its semantics, not the freeze logic.

## 11. Rollout

- No feature flag needed (V1 has no live adapter traffic before 04.3.x/04.4.x land); merge order T1 → T2 → T3.
- The schemas are additive contract files; consumers merge against them by task dependency, not release gate.
- Monitoring: `adapter_capability` rejections surface as `unsupported_protocol_major` counts in ingest metrics (04.1.2-T1 counters).
- Rollback: revert the PR; capability rows already stored stay valid (schema changes are additive; a breaking change is a new protocol major, not an edit).
