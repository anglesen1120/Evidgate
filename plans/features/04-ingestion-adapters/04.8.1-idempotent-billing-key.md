## 1. Goal and non-goals

**Goal.** Every accepted event batch emits exactly one `usage_ledger_entry` row per metric, with `billing_key = batch:<event_batch_id>:<metric>` (T43, T50), so that a redelivered batch (`duplicate` re-ack) and a reprocess of the same acceptance never produce a second billing row. Quantity is the event count from the batch, never a client-supplied number (00 §9.1).

**Non-goals.** The `usage_ledger_entry` table schema and the per-period roll-up (owned by 12.3.1 — this story is an emitter against that contract, per the README bundle ordering: ledger schema first, then emitters); pricing/rate cards (12.2.1/T44); the usage read API (`GET /v1/orgs/{o}/usage/*`, owned by 12); metering for artifacts or agent jobs (out of this plan's FR-04-9 scope, which is batch/event metering only).

## 2. User stories and acceptance criteria

- As the billing system, I trust that one accepted batch bills once per metric, regardless of how many times the client resent it or how many times its report was later reprocessed.
- As a customer, my invoice never double-counts an ACK my CI lost and retried.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A batch accepted by `IngestEventBatch` writes exactly one outbox row that, once dispatched, inserts exactly one `usage_ledger_entry` per distinct metric in that batch, with `quantity = event count` for that metric and `billing_key = batch:<event_batch_id>:<metric>` |
| AC2 | Resending the identical batch (same `event_id`s, same payload hash → all `duplicate` per T50) never triggers a second ledger emission: the batch is recognised as already-billed via `event_batch.id` (the batch row itself is idempotent — same request under the same `Idempotency-Key`/hash returns the original `event_batch`, so no second outbox row is even queued) |
| AC3 | A reprocess of the same raw report (04.4.2) writes new `event` rows under a synthetic producer but **no** new `event_batch` row and **no** `usage_ledger_entry` — reprocess is metering-invisible, asserted by an integration test spanning both stories' contracts |
| AC4 | A retry sequence fail → pass (05's retry semantics) meters once per accepted batch per metric, not per retry attempt — quantity reflects accepted event count of that batch only |
| AC5 | Redelivering a batch whose first attempt's ledger insert crashed mid-task (task retried by the queue) still yields exactly one ledger row: the emitter's own insert is idempotent on `billing_key` (`ON CONFLICT (org_id, billing_key) DO NOTHING`) |
| AC6 | The `usage_ledger_entry` insert never runs inside the same DB transaction as any outbound network call (P5); the emitter is a pure DB-to-DB task step |

## 4. Data model and migrations

No new tables owned by this story. `usage_ledger_entry` (columns, unique `(org_id, billing_key)`, `unique (org_id, id)` per T3) is owned and migrated by 12.3.1; this story's migration only adds the emission wiring:

```sql
-- migrations/NNNN_ingestion_usage_emission_outbox.sql
-- No new table: this migration only ensures the outbox payload shape is registered
-- (outbox rows are polymorphic per 00 §5.3; no schema change needed if 01's outbox
-- table is already generic). If the outbox requires a typed discriminator column
-- migration, it is a one-line addition to the existing outbox check constraint
-- listing valid `kind` values, adding 'ingestion.usage_batch_metered'.
alter table outbox
  drop constraint if exists outbox_kind_check,
  add constraint outbox_kind_check check (kind in (
    'ingestion.event_batch_committed',
    'ingestion.reprocess_report',
    'ingestion.usage_batch_metered'
  ));
```

Read path: none added here (no query in this story reads `usage_ledger_entry` — that is 12's `GET /v1/orgs/{o}/usage/ledger`).

## 5. API shapes (commands, queries, endpoints)

No new `/v1` endpoint (usage writes are internal-only per 00 §9.1). Internal contract:

| Shape | Detail |
|---|---|
| Emission trigger | `IngestEventBatch` command handler (04.1.1-T1), on successful commit, writes one outbox row `ingestion.usage_batch_metered { event_batch_id, org_id, project_id, metrics: [{ metric: "event", quantity }] }` in the **same transaction** as the batch commit (C7 — outbox row in the same tx as the business change) |
| `MeterEventBatchTaskHandler` (worker) | Claims the outbox-derived task row (`SKIP LOCKED`); for each `metric` in the payload calls `IUsageLedger.RecordAsync(org_id, project_id, billing_key: $"batch:{event_batch_id}:{metric}", quantity, occurred_at)` — one call per metric, each independently idempotent via `ON CONFLICT (org_id, billing_key) DO NOTHING` (owned inside 12.3.1's handler, called here) |
| `IUsageLedger` (consumed, owned by `Evidgate.Modules.Ledger.Contracts`, delivered by 12.3.1) | `Task<RecordResult> RecordAsync(Guid orgId, Guid? projectId, string billingKey, long quantity, DateTimeOffset occurredAt)` — this story is a caller only, no interface change |
| Errors | Task-level only (no public endpoint): dead-letter after capped retries with the batch id in the dead-letter payload for operator replay (`/internal/operator/*`, owned by 10) |

## 6. States and transitions

- Per-batch metering state: `queued (outbox row) → dispatched → recorded | dead_letter` (standard 00 §5.3 task lifecycle) — no new state machine.
- `usage_ledger_entry` rows are append-only facts; no transition once inserted (owned by 12.3.1).

## 7. Jobs and integrations

- Outbox task `ingestion.usage_batch_metered`, natural idempotency key = the `billing_key` itself (T43); capped retries → `dead_letter`, replay via the operator dead-letter-replay route (00 §9.1, owned by 10).
- Upstream trigger: `IngestEventBatch` (04.1.1-T1) commit. Downstream consumer: 12.3.1's roll-up reads `usage_ledger_entry` on its own schedule — this story does not call the roll-up directly.
- Reprocess (04.4.2) explicitly does **not** enqueue this task (AC3) — verified by a cross-story integration test living in this story (it asserts the *absence* of the outbox row after a reprocess).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §9.1 (internal-only metering) | No public write endpoint; quantity computed server-side from `event_batch.event_count` (owned by 04.1.1), never client-supplied | code review + architecture test (no `[HttpPost]`/minimal-API route touches `IUsageLedger`) |
| T43/T50 | `billing_key = batch:<event_batch_id>:<metric>`; one row per batch per metric; quantity = count | AC1, AC2, AC5 |
| 00 §5.5 C7 | Outbox row written in the same transaction as the `event_batch`/`event` commit — never a separate write that could be lost on crash | integration test: kill the process after commit, before dispatch → task still fires on restart (outbox durability) |
| 00 §5.7 P5 | `IUsageLedger.RecordAsync` is a DB call inside the task's own short transaction; no outbound network call anywhere in this path | code review; P5 is trivially satisfied (no HTTP client involved) |
| 00 §5.7 P2 | One `RecordAsync` call per metric (V1 has one metric, `event`) — no per-row loop over individual events | command-counter assertion |
| Authorization | No commands/queries exposed publicly; the task handler runs under the worker's tenant scope (`ITenantScope.BeginAsync(org_id, project_id)`), not a user principal | integration test with RLS on |
| Privacy/retention | Ledger rows carry counts only, no event bodies; retention/deletion of usage rows is 12.3.1's responsibility (tenant deletion cascades per 02) | — |

## 11. Rollout

- No feature flag: emission is transactionally tied to batch commit from day one; there is no meaningful "off" state once 12.3.1's ledger table exists (bundle ordering, README §5.3).
- Merge order: 12.3.1's `usage_ledger_entry` table + `IUsageLedger` lands first (bundle), then this story's T1/T2 in one PR series.
- Monitoring: dead-letter count for `ingestion.usage_batch_metered` alongside other outbox kinds (10's operations dashboards); a per-org daily reconciliation (12) cross-checks ledger rows against `event_batch` count as a backstop, not part of this story.
- Rollback: revert the PR; no ledger rows are lost (they are append-only facts already committed) — only future emission stops.
