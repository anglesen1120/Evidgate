## 1. Goal and non-goals

**Goal.** Every producer format Evidgate parses has a golden fixture set under `fixtures/<producer>/<case>/` — the original report plus the expected normalised events — and a diff harness that runs each fixture through the real parser and fails the build on any unexplained difference between expected and produced output. The first fixture is Evidgate's own CI run (R10), so our adapter bugs are caught by us, not by a customer (D5).

**Non-goals.** The mappers themselves (04.3.x, 04.4.1, 04.5.1 — they consume the harness); the protocol schemas (04.7.1-T1 ships `contracts/adapter/`); the CLI end-to-end test that uses the fixture run (04.2.4-T3); CI pipeline construction (01.7.1 — this story only adds a job to it); production ingestion code paths beyond what the harness needs to invoke the mapper in-process.

## 2. User stories and acceptance criteria

- As a developer changing a mapper, the golden suite immediately shows the exact event-level difference my change caused — or proves there is none.
- As the QA lead, the fixture corpus includes real customer-shaped data (our own CI), malformed input, and a shard-merged set, so the three riskiest paths (D5, §8 risk table) are covered before release.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `fixtures/<producer>/<case>/` layout is defined and enforced: each case directory contains the original report file(s), `expected.json` (normalised events + declared counts + expected `raw_report.status`), and `case.json` metadata (producer id, parser version the expectation was captured against, rationale); a fixture missing any file fails the harness with a named error |
| AC2 | The harness replays each fixture through the actual parser entry point (same code the ingest path calls, in-process) and diffs produced vs expected normalised events field-by-field after RFC 8785 canonicalisation; ordering is compared by `(producer_id, sequence)` per 00 §9.4 |
| AC3 | Any unexplained difference fails the suite with a diff that names fixture, event index and field; differences classified as expected (e.g. a truncation yielding `malformed`) must be declared in `expected.json`, never suppressed silently |
| AC4 | The dogfood fixture exists and passes: Evidgate's own CI artifacts (Playwright reporter output, a pytest `junitxml` file, one deliberately malformed file, one shard-merged set) are ingested through the harness and produce zero unexplained diffs (R10) |
| AC5 | A CI job runs the conformance suite for every registered adapter with fixtures only — no network, no database, no credentials; the job fails fast and prints the per-fixture diff summary |
| AC6 | Adding a deliberately wrong expectation (flip a normalised status) makes the suite fail with that case named; reverting restores green |

## 3. Contracts touched

- `fixtures/` top-level directory from 00 §5.2 — the `<producer>/<case>` sub-layout is created here; `fixtures/contracts/` (04.7.1-T1.3) is a sibling namespace owned by the protocol story.
- No API, schema or permission change; fixtures are build-time test data.
- Expected-event JSON uses the §9.4 envelope field names (snake_case) so fixture files double as wire-format documentation.
- Recorded — the area plan gives T3 (CI conformance job) milestone M1 with dependency only on 04.6.1-T1, but a CI job needs the pipeline from 01.7.1 (M1 wave 4); sequencing risk noted, no contract change.

## 4. Data model and migrations

None. (No database objects; fixtures are files in the repository. The harness runs parsers in-process and never touches PostgreSQL — AC5 keeps it network- and DB-free.)

Directory contract instead:

```text
fixtures/
  junit-pytest/           # producer id = parser registry key (report_parser.parser_id)
    happy-path/case.json + report.xml + expected.json
    truncated/case.json + report.xml + expected.json      # status: malformed
    shard-merged/case.json + shard-1.xml + shard-2.xml + expected.json
  playwright-reporter/
    …same shape…
  evidgate-ci/            # dogfood corpus (T2), same layout
```

`expected.json` shape: `{ "declared": {tests, failures, …}, "events": [ {envelope fields} ], "raw_report_status": "parsed|malformed|unsupported", "notes": "…" }`.

## 5. API shapes (commands, queries, endpoints)

None. No `/v1` surface. The harness is a library + runner:

| Artefact | Detail |
|---|---|
| `Evidgate.Ingestion.Conformance` (test-only project under `tests/`, or a `dotnet run` target) | loads `fixtures/`, resolves `parser_id` via the same per-producer mapping registry used by `IngestEventBatch` (04.1.1-T1/04.4.1-T1), replays, diffs |
| Fixture runner exit codes | 0 all diffs explained or empty; 1 any unexplained diff or missing fixture file (names printed) |
| Adapter-side hook | each `packages/adapter-*` / reporter package exposes a `--self-check <fixture-dir>` (or Vitest suite) invoking the same expected.json contract, so TypeScript adapters share the corpus (T42 spirit; the CLI/JUnit mappers run it in CI from 04.2.x) |

## 6. States and transitions

None. Fixtures are immutable once merged (a changed expectation is a reviewed diff, versioned in git; `case.json.parser_version` records which parser produced the expectation).

## 7. Jobs and integrations

- Consumed by: 04.4.1 (JUnit mapper verification), 04.3.x (Playwright reporter), 04.5.1-T4 (Appium golden fixtures are added by that story into this layout), 04.2.4-T3 (CLI end-to-end against the fixture run), 01.10.1 (dogfooding pipeline emits JUnit/XML that lands back here — T48).
- The malformed + shard-merged dogfood fixtures are the regression corpus for §5 failure modes (`malformed` → `unknown` statuses, never PASS).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §5.7 S5 / NFR-04-3 | Fixtures exercise the hardened parser path: DOCTYPE/entity payloads live in the `truncated`/negative cases and must be rejected by the parser, not by the harness | AC4 corpus + a DOCTYPE fixture case |
| Secrets/privacy (DECISIONS §7) | Dogfood fixtures contain only Evidgate's own CI output — no customer data; a fixture-review checklist bans real credentials or user data in `fixtures/` | PR checklist + T2.4 review step |
| 00 §5.7 P1/P3 (budget spirit) | Conformance suite runs in < 60 s in CI and holds no DB/network dependency (AC5) — measured, and a budget assertion fails the job if the whole suite exceeds it | CI job timing output |
| T48 dogfooding | The dogfood corpus is generated by our own pipeline emitting JUnit through the JUnit mapper — the same reports customers send | AC4 |
| Retention/deletion | Fixtures are repo files; deleted with the repo; no runtime retention impact | — |
| Authorization | No runtime surface: the harness reads committed fixtures and calls mappers in process; no token, tenant or route is involved | AC5 (no network, no DB) |
| Telemetry | No runtime telemetry; the suite reports pass/fail and its own duration in the CI job output | CI job timing output |
| Failure path | A mapper discrepancy fails the suite with the fixture name and the diff against `expected.json`; fixtures are never edited to hide it (T2.2 rule) | AC4 corpus |

## 9. Test plan

| Behaviour / boundary / failure | Test |
|---|---|
| Layout enforcement | harness test `Fixture_MissingExpected_FailsNamed` (AC1) |
| Happy-path fidelity per producer | `Golden_<producer>_<case>_NoUnexplainedDiff` auto-generated per directory (AC2, AC3) |
| Malformed input stays honest | `junit-pytest/truncated` case asserts `raw_report_status: malformed` and `unknown` normalised statuses (04 §5) |
| Shard-merged ordering | `junit-pytest/shard-merged` asserts per-`producer_id` sequence ordering, not arrival order (00 §9.4) |
| Unicode/emoji names | a case with surrogate pairs + 4-byte emoji in test names (04 §7 boundary list) |
| Harness self-detection | negative meta-test flips one expected field → suite fails with the fixture + field named (AC6) |
| No-network CI conformance | CI job manifest asserts zero socket use; suite runs from fixtures only (AC5) |

Server-side harness tests are xUnit v3 (no Testcontainers needed — no DB); adapter-side Vitest suites consume the same directories.

| Sub-task | Work | Size | Done when |

Notes (04.3.3-T1 merge-reports limitation, S56 — receiving task): the "one shard-merged set" that T2.2 captures cannot be produced by the reporter. A v1 Playwright reporter never receives the per-blob shard config — Playwright wraps it in `ReporterV2Wrapper`, which has no `onReportConfigure` (`@playwright/test` `lib/runner/index.js:1705-1774`) — so a `playwright merge-reports` replay emits **nothing** and logs one stderr line rather than guessing an id (decision D-S56-Q11, recorded in `contracts/adapter/playwright-mapping.md` § "Known limitation (D-S56-Q11)" and in the 04.3.3-T1 Notes). Customers ingest per-shard runs, where each shard's original `producer_id`/`sequence` is preserved. T2 therefore has two acceptable shapes: ingest the merged set **per shard** (capture each shard's own events, merge them into the fixture as separate producers) or drive a v2 reporter once one exists. It must not expect events from a merged replay.

Notes (04.3.2-T1 sidecar number spellings, S56 — receiving task `04.6.1-T2`): the reporter and the server can hash three raw-text number spellings in `metadata.evidgate.params` differently (documented in `contracts/adapter/playwright-mapping.md`; 04.3.2 plan §10 "Notes (04.3.2-T1, S11 review outcomes)" item 4). The dogfood corpus is the first place a fixture can hit it: T2.2 runs the harness until the corpus diffs clean, so a mismatch there is filed as a mapper bug against the reporter or the server mapper, not worked around in the fixture. Decided by the coordinator (owner rule 2026-10-23), recorded for owner phase review; `STATUS.md` §6 carries the row.
