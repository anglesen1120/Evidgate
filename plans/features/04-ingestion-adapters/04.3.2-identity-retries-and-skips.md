## 1. Goal and non-goals

**Goal.** The Playwright reporter resolves every emitted `test.finished`/`test.started` to a stable case identity — `evidgate.id` annotation or sidecar manifest, else a derived id with a visible warning — computes `variant_hash` from project name + normalised parameters, and maps Playwright outcomes (pass, fail, `timedOut`, interrupted, `skip`, `fixme`, retries) to raw + normalised statuses so that retries become `attempt_no` 1..n and `fixme`/`skip` are distinguishable and never become `passed`.

**Non-goals.** Reporter skeleton and spool writer (04.3.1-T1); shard→producer mapping (04.3.3-T1); server-side status storage and completeness reasons (04.1.x, 06); the `evidgate.id` annotation format itself (03.1.1) and sidecar filename (03.1.1-T1).

## 2. User stories and acceptance criteria

- As a QA engineer, I annotate a test with its catalog id once, and every retry and shard reports against the same `execution_key`, so attempts line up.
- As the Tech Lead, I want unmapped or conflicting identities to fail loudly in the CI log, so silent mis-attribution never reaches the decision engine.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A test with `test.annotations` entry `{ type: "evidgate.id", description: "<uuid>" }` produces events whose `ext.case_id` is that UUID; the same id in two different tests emits a conflict warning event (`run.log`, `reason: "duplicate_case_id"`) naming both locations |
| AC2 | Annotation and sidecar manifest disagreeing for the same test location → conflict per 00 §7 (never a silent pick): the test's events carry `ext.identity_conflict = true` and no `case_id`; the reporter exits non-zero on `onEnd` unless `EVIDGATE_ALLOW_UNMAPPED=1` (mirrors 03's `allow_unverified` flag, T46) |
| AC3 | `variant_hash` = `sha256(rfc8785({project, params}))` where `params` is the normalised (sorted-key, code-point-normalised) parameter set of a `test.describe`/parameterised project; two runs of the same suite on different machines produce identical `variant_hash`es |
| AC4 | `execution_key` is computed by the server from the manifest (00 §7); the reporter sends `ext.case_id` + `ext.variant_hash` + `ext.target_env`; an event the server cannot resolve rejects the batch 422 `unknown_execution_key` (T10) — the reporter emits the keys, it does not hash `execution_key` itself unless the contract stub says so |
| AC5 | Retry N (Playwright `result.retry`) maps to `attempt_no = retry + 1`; a flaky pass (fail then pass) yields `attempt_no` 1 `failed` + 2 `passed` — never a merged status |
| AC6 | Status map: `passed→passed`, `failed→failed`, `timedOut→timed_out`, `interrupted→error`, `skipped`(annotation `skip`)→`skipped`, `skipped`(`fixme`)→`skipped` with `ext.skip_reason="fixme"`; `expectedStatus:"failed"`×`failed` outcome → `passed` with `ext.xfail=true`; raw status string preserved verbatim in `status` |
| AC7 | A test whose `fixme`/`skip` annotation appears only on a retry keeps `attempt_no` sequence contiguous (1..n, no gap) |

- No endpoint/schema/state change; `unknown_execution_key` behaviour is server-side (04.1.2-T5) and asserted here only at the client boundary.
- Recorded (04.3.1-T1, 2026-10-07): `execution_key` is not derived by the reporter. 04.3.1-T1 ships an injectable identity resolver option on `EvidgateReporter` (ctor option; default is the exported constant `PLACEHOLDER_EXECUTION_KEY` = 64 × `'0'`, valid per the schema pattern `^[0-9a-f]{64}$`) applied to every envelope including `run.log`; the envelope schema requires the field while 00 §7 says the server computes it from the manifest and AC4 says the reporter does not hash it. 04.3.2-T1 must replace the default with the real value or obtain a contract change (00 §9.4 / `contracts/schemas/event-envelope.v1.json`, logged in 00 §15). The gap is open, not resolved.
- Recorded (04.3.1-T1, 2026-10-07): `attempt_no` is already emitted as `result.retry + 1` in 04.3.1-T1; 04.3.2-T2 owns the status/retry semantics (AC5–AC7) on top of that field.
- Recorded (04.3.1-T1, 2026-10-07): the OI-04-01 Playwright 1.63 type facts (`TestResult.retry`, `result.steps`, attachment field names) are confirmed against the installed package in 04.3.1-T1 — see `packages/adapter-playwright/README.md` §"Verified Playwright 1.63 API"; this story consumes those names and does not re-verify them.
- Recorded (04.3.1-T1, 2026-10-07): the capability document is carried by the first spooled envelope (sequence 1), a `run.log` envelope with the document under `ext.capability`; this story's `ext` allow-list additions (bullet above) must be added to the same allow-list module and recorded in that capability flow.

## 4. Data model and migrations

None server-side. Reporter-local: `sidecar` manifest file (filename fixed by 03.1.1-T1) parsed once at `onBegin` into an in-memory `location → case_id` map; conflicts resolved per AC2 at emit time.

## 5. API shapes (commands, queries, endpoints)

Library internals only (no HTTP):

| Function | Signature | Notes |
|---|---|---|
| `resolveIdentity(test)` | `TestCase → { case_id?, variant_hash, target_env, conflict? }` | annotation first, sidecar second, both → conflict |
| `mapStatus(result, annotations)` | `TestResult → { raw, normalized, skip_reason?, xfail? }` | pure function, table-driven (AC6) |
| `attemptOf(result)` | `TestResult → attempt_no` | `retry + 1` |
| Warning channel | `run.log` envelopes with `ext.warn` codes | warnings are data, not stderr-only |

## 6. States and transitions

Identity resolution state per test file: `unmapped → mapped | conflicted` (mirrors 00 §8.10 case-import identity states). Transitions are computed per test at `onTestBegin`; once `conflicted`, never re-mapped within the run. `attempt_no` strictly increments per `execution_key` within the process; a restarted shard reuses the same deterministic `producer_id` and resumes `sequence` from the checkpoint (04.3.3, T84), so a `(run, producer, sequence)` is never re-emitted and attempts never collide.

## 7. Jobs and integrations

- Consumes the annotation vocabulary and sidecar filename owned by 03.1.1-T1/03.1.3; if the sidecar spec changes, only `resolveIdentity` changes.
- Emits through the 04.3.1 spool writer; consumed by the CLI pipeline unchanged.
- Server side, `unknown_execution_key` batches (T10) are surfaced by the CLI as exit 3 with the failing indices — the reporter itself is offline.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| FR-04-6 / 00 §8.3 | `status` raw verbatim; `ext.normalized` carries the mapped value; normalisation table is data-driven, versioned in `playwright-mapping.md` | AC6 table test |
| T10 | Reporter forwards identity fields; server rejects unknown keys — client treats 422 `unknown_execution_key` as exit 3 | boundary test in CLI e2e (04.2.4-T3 fixture) |
| 00 §7 conflict rule | annotation+sidecar mismatch is `conflicted`, never a silent pick | AC2 |
| S3 / 04 §6 | Annotation values are UUIDs; `test.title`/`location` may carry user text — allow-listed into `ext`, secret-pattern keys dropped | `ext-filter.test.ts` (shared with 04.3.1) |
| NFR-04-2 | Pure string/hash work; no platform-specific code | matrix CI |
| Performance | Identity map built once at `onBegin` (O(files)); per-callback lookup O(1); `variant_hash` memoised per `(project, params)` key | `perf.test.ts`: 5k parametrised cases < 500 ms |
| Retention/deletion | None — no persistence beyond the shared spool | — |
| Authorization | No endpoint and no token in the reporter (no network, 04.3.1 S3); the CLI posts under its `ci_producer` token and the server enforces T9/T10 | 04.1.2-T5 (server side) |
| Telemetry | Identity warnings (`identity_conflict`, unmapped count, unknown status) are `run.log` envelopes with `ext.warn` codes, visible in run evidence (§5, §11) | AC1, AC2 |
| Failure path | Annotation/sidecar conflict → `conflicted` + warning event; unmapped without `EVIDGATE_ALLOW_UNMAPPED` → visible warning; unknown future status → `error` + warning; server 422 `unknown_execution_key` → CLI exit 3 with indices | AC1, AC2, AC7 |
