## 1. Goal and non-goals

**Goal.** `POST /v1/runs/{r}/events` accepts one batch of ≤ 500 events (≤ 1 MiB before decompression), validates, canonicalises and commits it in **one** transaction, and acknowledges each event as `accepted` or `duplicate`. No partial commit exists: a schema error, an unknown `execution_key`, an unknown `producer_id`, a same-`event_id`-different-payload conflict or a reused `(run, producer, sequence)` rejects the whole batch with the failing indices.

**Non-goals.** Producer-slot table + token binding enforcement (04.1.2-T4/T5 — this story builds the insert path; the binding check is wired by 04.1.2-T5), quota/rate limits and epochs (04.1.2), the CLI that produces batches (04.2.3), `finalize` semantics (05.3.2-T1; CLI in 04.2.3-T2), usage ledger rows (04.8.1 — this story only emits the outbox row), adapters (04.3/04.4).

## 2. User stories and acceptance criteria

- As a CI producer, I send one batch and get a deterministic per-event ack, so a lost response is retried safely by resending the same `event_id`s.
- As the platform, I never store a partial batch or bill twice, so count reconciliation in 05 stays reliable.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | A valid batch of N events commits all N `event` rows + one `event_batch` row + one outbox row in a single transaction and returns 200 with per-event `accepted` acks in request order |
| AC2 | Resending the identical committed batch returns 200 with every event `duplicate`; `event`, `event_batch` (a new audit row is allowed, with `duplicate = N`) and the usage ledger gain no new business rows and no new billing row — usage is metered only for accepted events, so a resend with `accepted = 0` emits no `usage.batch_accepted` outbox row at all (T83) |
| AC3 | A batch with one schema-invalid event returns 422 `event_invalid` with that event's `index`/`path` in `error.details` and commits nothing (zero `event` rows, zero `event_batch` row) |
| AC4 | A batch containing an `execution_key` absent from the run's planned executions returns 422 `unknown_execution_key` with all failing indices (T10) and commits nothing |
| AC5 | Same `event_id` with a different canonical payload hash → 409 `duplicate_different_payload` with `index`; whole batch rejected (T50) |
| AC6 | Two batches reusing `(run, producer_id, sequence)` → the second returns 422 `sequence_reused` and commits nothing |
| AC7 | 501 events, body > 1 MiB raw, or gzip expanding over the expanded-size/ratio cap (8 MiB / 20:1, DECISIONS §8.1 D-A8) → 413 `batch_too_large` before any write; exactly 500 events and exactly 1 MiB pass (FR-04-2) |
| AC8 | An ack is returned only after commit: killing the API between insert and commit leaves zero rows, and the client retry then gets `accepted` acks |
| AC9 | Events for a run in `incomplete`, or `complete` within `late_window` since completion, are stored with `late = true` and acked `accepted`; only after the late window does the batch return 409 `run_closed` (T81). A canceled run still accepts-and-marks (`after_cancel = true`, T12) |

## 6. States and transitions

- `event`: append-only; no lifecycle. `after_cancel`/`late` are derived inside the ingest transaction from the run row read `FOR SHARE` (T91): `after_cancel = true` when the run is `canceled` (T12); `late = true` when the run is `incomplete` or `complete` within its stored `late_window` since completion (T81). Cancel and completion take the run row `FOR UPDATE`, so a flag can never miss a committed cancel/close; enforcement tests land with 04.1.2-T5.
- Run transition `queued → running` on first accepted event (T13) is invoked through 05's run interface in the same transaction. After `late_window` the run is closed: further batches return 409 `run_closed`. Stored `late = true` rows drive the new evidence revision + re-evaluation downstream (05.3.2, 07.5.1) — ingest never reopens a run.
- Out-of-order `sequence` values are stored as sent; no reordering by `received_at` ever (D3).

## 7. Jobs and integrations

- **Outbox → usage metering:** the handler writes one outbox row `usage.batch_accepted { event_batch_id, metric, quantity }` per metric with `quantity = accepted` — only non-duplicate events are metered and no row is written when `accepted = 0`, so a resent batch never bills again (T83, T43, T50). The worker handler (04.8.1-T1) writes `usage_ledger_entry` with `billing_key = batch:<event_batch_id>:<metric>` — once per batch per metric, never per event.
- **05 contract callouts** (in-transaction, same tenant scope): planned-`execution_key` membership probe (`= ANY(@keys)`, T90), `case_attempt` upsert (05.3.3-T2), run-state `FOR SHARE` read (T91) + `queued → running` transition.
- **Corvus/Ajv parity (T42):** the same `fixtures/contracts/` accept/reject corpus runs against Corvus (server, xUnit) and Ajv 8 (`packages/sdk`/`cli`, Vitest); disagreement fails CI.
