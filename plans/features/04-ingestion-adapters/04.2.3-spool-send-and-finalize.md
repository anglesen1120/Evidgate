## 1. Goal and non-goals

**Goal.** The CLI's send path: an append-only on-disk spool keyed by `(run_id, producer_id, sequence)` buffers envelopes produced between adapter output and the API; a batcher posts them to `POST /v1/runs/{r}/events` within the 500-event/1 MiB limits; retries with deadline + jittered backoff survive a 10-minute outage and a process restart; and `evidgate runs finalize` reports `(producer, shard, last_sequence, count, manifest_hash)` to `POST /v1/runs/{r}/finalize`, surfacing 403/422 verbatim.

**Non-goals.** The reporter/adapter that emits envelopes (04.3), artifact uploads (04.2.4), server-side dedupe/finalize semantics (04.1.1, 04.1.2, 05.3.2-T1), `evidgate gate` (07.6.1), reprocess (04.4.2).

## 2. User stories and acceptance criteria

- As a CI job on a flaky network, my results queue on disk and all arrive exactly once — a lost ACK or a CLI crash mid-send never duplicates or loses an event (A9, A10).
- As a developer, a full spool or a permanent rejection tells me the run, the unsent sequence range and the server's error code.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | With the API down for 10 minutes, the CLI keeps spooling under its size cap, then delivers every event; resent events get `duplicate` acks which are ignored without error |
| AC2 | Killing the CLI mid-send and restarting it resumes from the first unacked sequence — no event is sent twice under different identity, and none is skipped |
| AC3 | Spool reaching the configured cap stops intake and exits 3 naming the run and the unsent sequence range; never a silent drop (04 §8 risk) |
| AC4 | Batches respect ≤ 500 events and ≤ 1 MiB pre-compression; gzip is applied when it helps; a single event over the limit fails the file with its `event_id` named |
| AC5 | Retries use the same `event_id`s and deadline-bounded exponential backoff with jitter; 429 honours `Retry-After`; a mid-batch 500 retries the same batch (04 §7) — business logic is never re-run (FR-04-5) |
| AC6 | `evidgate runs finalize` sends `producer_id`, `shard`, `last_sequence`, `count`, `manifest_hash`; on 403 `producer_slot_taken` / 422 `unknown_producer` it exits 3 with `error.code` + `request_id` (T9); on 202 it prints the reconcile-accepted state |

## 4. Data model and migrations

None (no database objects — customer-side CLI). Spool layout on disk (owned by this story; amended S54 to the reporter layout, D-S54-Q1):

```
$EVIDGATE_SPOOL_DIR/<run_id>/<producer_id>/
  000001.jsonl         # append-only JSONL: one 00 §9.4 envelope per line, \n-terminated
  000002.jsonl         # next chunk; rotate at 1 MiB or 1000 lines, never reuse (highest + 1)
  checkpoint.json      # reporter-owned: { producer_id, next_sequence }
  cursor.json          # CLI-owned: { producer_id, next_unacked_sequence,
                       #   last_acked_sequence, acked_count, updated_at }
  spool.lock           # CLI-only exclusive lock while a command holds it: { pid, started_at }
```

No `<org_hash>` level and no `journal.seq` (D-S54-Q1). Directories are `0700`, files `0600`; ids are single safe path segments and the resolved path must stay inside `EVIDGATE_SPOOL_DIR` (`invalid_spool_id`). Every chunk the cursor claims is durable before ack-advance — each chunk is fsynced once by the process, the highest chunk (the only one a writer may still append to) on every ack, then the directory, so a send costs O(chunks) syncs, not O(batches × chunks) — and `cursor.json` is write-tmp-fsync-rename (+ directory fsync) for crash atomicity. Cap enforced on the summed size of the `<run_id>` directory, all producers included. Contract: `contracts/cli.md` §11.1.

## 5. API shapes (commands, queries, endpoints)

| Command / module | Endpoint | Behaviour |
|---|---|---|
| internal `spool.ts` | — | `append(events)` writes chunk lines keyed `(run, producer, sequence)`; `unacked()` replays from `cursor.json`; `advance(last_acked)` commits the cursor; `purge()` removes the producer directory after a finalize (D-S54-Q1/Q2) |
| internal `batcher.ts` | `POST /v1/runs/{r}/events` | packs ≤ 500 events / ≤ 1 MiB raw per request, gzip when it shrinks the body; Ajv envelope validation before send (an oversized single event fails with its `event_id`); `Idempotency-Key: batch:<sha256(versioned [version, run, producer, [[sequence, event_id]…])]>` as belt-and-braces on top of event-level dedupe |
| internal `sender.ts` | same | retry loop: exponential backoff + full jitter, deadline `EVIDGATE_SEND_DEADLINE` (default 30 min), 429/408/5xx/transport only, `Retry-After` honoured as a floor under the jittered backoff and a wait that would reach the deadline failing `deadline_exceeded`; 401 purges the cached token, other 4xx fails the batch immediately with `error.code` + `request_id`; on the first fatal failure no new batch is dispatched, in-flight batches settle (their acks still advance the cursor) and unstarted ones retry nothing; the error names the full unsent range from `unsentRange()`; `duplicate` acks are success; max 4 batches in flight per run |
| `evidgate events send --run <uuid> [--producer <p>] [--from <file\|->] [--json]` | `POST /v1/runs/{r}/events` (`event:write`) | requires `EVIDGATE_SPOOL_DIR`; drains unacked envelopes (every producer of the run unless `--producer`), holding `spool.lock`; `--from` is the only local intake and the only cap-enforcing write: streamed with a running byte total that fails `spool_cap_exceeded` (nothing written) as soon as total + current run directory bytes would cross the cap, all-or-nothing across producers (`spool_cap_exceeded` names run + unsent range); never deletes spool data, only advances `cursor.json`; prints `sent run=… producer=… batches=… accepted=… duplicate=…` per producer or one JSON object (`producers`, `batches`, `accepted`, `duplicates`) |
| `evidgate runs finalize --run <uuid> --producer <p> --shard <1..256> --manifest-hash <sha256:64hex> [--keep-spool] [--json]` | `POST /v1/runs/{r}/finalize` (`event:write`) | body is exactly `{producer_id, shard, last_sequence, count, manifest_hash}`; `last_sequence`/`count` come from `cursor.json` under `spool.lock` (unacked events → `unsent_events`, no spool → `spool_missing`); `Idempotency-Key` = sha256 hex of `['evidgate.finalize-key.v1', run, producer, shard, last_sequence, count, manifest_hash]`; 202 → reconcile-accepted line/JSON then purge the producer directory unless `--keep-spool` (a purge failure after 202 is a stderr warning, exit 0); 403 `producer_slot_taken` / 422 `unknown_producer` / `manifest_invalid` / 409 → exit 3 echoing `error.code` + `request_id`, exactly one request. Server side is idempotent via `IProducerRegistry.CloseSlotAsync` (T68): a repeat returns the same 202, so the CLI may resend after a lost response |

## 6. States and transitions

Per `(run, producer)` spool cursor: `spooled → sent → acked(accepted|duplicate)`. A 4xx stops the pipeline for that run: the CLI exits 3 with the server's `error.code` and `request_id`, the cursor takes only the acks that settled (never the failing batch) and **no `failed` marker is persisted**; the batch is never silently retried, and a later explicit rerun re-sends from the first unacked sequence — never silent, because the operator ran it (D-S54-Q4). Process death at any point resumes from `cursor.json`'s `next_unacked_sequence`; a partial chunk line at EOF is truncated — the reporter writes no per-line checksum (D-S54-Q3), so a line is trusted when it ends with `\n`, parses as JSON, passes the envelope schema and carries the next contiguous `sequence`, and a bad line anywhere but the torn tail is exit 3 `spool_corrupt` naming the chunk and line. Acked chunks are retained until a successful finalize purges the producer directory (D-S54-Q2), so a restart can never reuse a chunk name.

## 7. Jobs and integrations

- Consumes `POST /v1/runs/{r}/events` (04.1.1/04.1.2 server side: dedupe acks, `sequence_reused`, `unknown_execution_key`, slot binding, quota) and `POST /v1/runs/{r}/finalize` (05.3.2-T1 semantics + `IProducerRegistry` binding and `CloseSlotAsync` idempotent close from 04.1.2-T5, T68).
- Called by 04.3's reporter integration and by `evidgate runs send` for raw-report-derived events; the finalize command is invoked last in the CI recipe produced by 04.2.4-T2's `quickstart`.
- No server jobs; no in-process scheduler. Delivery is at-least-once; server `event_id` dedupe + per-batch `Idempotency-Key` provide exactly-once effect (A10, T11, T50).
