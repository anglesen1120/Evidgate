## 1. Goal and non-goals

**Goal.** The CLI's send path: an append-only on-disk spool keyed by `(run_id, producer_id, sequence)` buffers envelopes produced between adapter output and the API; a batcher posts them to `POST /v1/runs/{r}/events` within the 500-event/1 MiB limits; retries with deadline + jittered backoff survive a 10-minute outage and a process restart; and `evidgate runs finalize` reports `(producer, shard, last_sequence, count, manifest_hash)` to `POST /v1/runs/{r}/finalize`, surfacing 403/422 verbatim.

**Non-goals.** The reporter/adapter that emits envelopes (04.3), artifact uploads (04.2.4), server-side dedupe/finalize semantics (04.1.1, 04.1.2, 05.3.2-T1), `evidgate gate` (07.6.1), reprocess (04.4.2).

## 2. User stories and acceptance criteria

- As a CI job on a flaky network, my results queue on disk and all arrive exactly once — a lost ACK or a CLI crash mid-send never duplicates or loses an event (A9, A10).
- As a developer, a full spool or a permanent rejection tells me the run, the unsent sequence range and the server's error code.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | With the API down for 10 minutes, the CLI keeps spooling under its size cap, then delivers every event; resent events get `duplicate` acks which are ignored without error |
| AC2 | Killing the CLI mid-send and restarting it resumes from the first unacked sequence — no event is sent twice under different identity, and none is skipped |
| AC3 | Spool reaching the configured cap stops intake and exits 3 naming the run and the unsent sequence range; never a silent drop (04 §8 risk) |
| AC4 | Batches respect ≤ 500 events and ≤ 1 MiB pre-compression; gzip is applied when it helps; a single event over the limit fails the file with its `event_id` named |
| AC5 | Retries use the same `event_id`s and deadline-bounded exponential backoff with jitter; 429 honours `Retry-After`; a mid-batch 500 retries the same batch (04 §7) — business logic is never re-run (FR-04-5) |
| AC6 | `evidgate runs finalize` sends `producer_id`, `shard`, `last_sequence`, `count`, `manifest_hash`; on 403 `producer_slot_taken` / 422 `unknown_producer` it exits 3 with `error.code` + `request_id` (T9); on 202 it prints the reconcile-accepted state |

## 4. Data model and migrations

None (no database objects — customer-side CLI). Spool layout on disk (owned by this story):

```
$EVIDGATE_SPOOL_DIR/<org_hash>/<run_id>/<producer_id>/
  journal.seq          # append-only JSONL: {sequence, event_id, line_bytes, event}
  cursor.json          # {next_unacked_sequence, last_acked_sequence, updated_at}
```

Files are fsynced before ack-advance; `cursor.json` is write-then-rename for crash atomicity. Cap enforced on the directory size of `<run_id>`.

## 5. API shapes (commands, queries, endpoints)

| Command / module | Endpoint | Behaviour |
|---|---|---|
| internal `spool.ts` | — | `append(events)` writes journal rows keyed `(run, producer, sequence)`; `unacked()` replays from `cursor.json`; `advance(last_acked)` commits the cursor |
| internal `batcher.ts` | `POST /v1/runs/{r}/events` | packs ≤ 500 events / ≤ 1 MiB raw per request, optional `Content-Encoding: gzip`; applies per-event Ajv validation before send; sends `Idempotency-Key: batch:<sha256(canonical batch)>` as belt-and-braces on top of event-level dedupe |
| internal `sender.ts` | same | retry loop: exponential backoff + jitter, deadline `EVIDGATE_SEND_DEADLINE` (default 30 min), 429 honours `Retry-After`, 4xx other than 409/429 fails the batch immediately with `error.code`; `duplicate` acks are success |
| `evidgate runs finalize --run <id> --producer <p> --shard <i> [--json]` | `POST /v1/runs/{r}/finalize` (`event:write`) | sends `producer_id`, `shard`, `last_sequence` (from cursor), `count` (acked total), `manifest_hash`; 202 → print state; 403/422 → exit 3 echoing `error.code`. Server side is idempotent via `IProducerRegistry.CloseSlotAsync` (T68): a repeat finalize with the same identity/values returns the same 202, so the CLI may resend after a lost response |

## 6. States and transitions

Per `(run, producer)` spool cursor: `spooled → sent → acked(accepted|duplicate)`; a 4xx event goes to `failed` (stops the pipeline for that run, error reported) — never silently retried. Process death at any point resumes from `cursor.json`'s `next_unacked_sequence`; a partial journal line at EOF is truncated (checksum per line detects torn writes).

## 7. Jobs and integrations

- Consumes `POST /v1/runs/{r}/events` (04.1.1/04.1.2 server side: dedupe acks, `sequence_reused`, `unknown_execution_key`, slot binding, quota) and `POST /v1/runs/{r}/finalize` (05.3.2-T1 semantics + `IProducerRegistry` binding and `CloseSlotAsync` idempotent close from 04.1.2-T5, T68).
- Called by 04.3's reporter integration and by `evidgate runs send` for raw-report-derived events; the finalize command is invoked last in the CI recipe produced by 04.2.4-T2's `quickstart`.
- No server jobs; no in-process scheduler. Delivery is at-least-once; server `event_id` dedupe + per-batch `Idempotency-Key` provide exactly-once effect (A10, T11, T50).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T9 surfacing | finalize/send failures print `producer_slot_taken`/`unknown_producer` verbatim with `request_id`; no client-side retry on 403/422 | AC6 test |
| S3 analogue | journal stores event envelopes (may carry `ext`); spool dir mode `0700`, files `0600`; token never in journal or logs | file-mode + content tests |
| Payload caps | 500/1 MiB enforced client-side before send (matches FR-04-2 so a well-formed CLI never trips 413) | AC4 boundary test |
| Backoff discipline | jittered exponential + `Retry-After` honoured + deadline; max concurrency 4 sends/run | AC5 + concurrency test |
| NFR-04-2 | POSIX + Windows paths; atomic rename resume | platform path tests |
| Resource safety | spool cap default 256 MiB/run configurable; memory bounded — journal is streamed, never fully loaded | cap test (AC3) |
| Retention/PDPL | spool is deleted on finalize success (`--keep-spool` opt-out); it may hold test names — treated as sensitive local data | deletion test |
