## 1. Goal and non-goals

**Goal.** Close review finding P3: V1 shadow healing needs a replay executor, and A5 forbids a hosted runner. `evidgate replay --grant <replay_grant_id>` runs inside the customer's own CI job, fetches the server-issued job spec, checks out the candidate patch, runs the pinned Playwright version against the customer's staging host, and sends the outcome as a `purpose = replay` run through the existing send path (04.2.3). The server never executes customer code; customer secrets never leave the customer's CI. A replay result is evidence for the candidate only and can never affect a release decision.

**Estimate status.** The 4.5 d is `[INFERENCE]`. DECISIONS §8 O10 sized the whole replay path (including 08 work) at 12–20 days, so 08.4.3 **must be re-sized at its DoR**; this story only sizes the customer-side CLI step, template and conformance tests.

**Non-goals.** Replay grant issuance, job-spec content and the comparability gate (08.4.3-T1); validation report and rejection taxonomy (08.4.3-T3); server-side grant check (05.2.1-T5); hosted or runner-job execution (05.7.x, V2, A5); runtime auto-apply of any patch (off in V1–V2, DECISIONS §5); LLM calls (08.5.x).

## 2. User stories and acceptance criteria

- As the healing validator, I receive a replay result bound to one candidate and cannot be fooled into a regression or incident.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `evidgate replay` without `--grant`, with an unknown, expired, other-project or other-candidate grant exits non-zero before any checkout or test execution; the server answers 422 `replay_grant_invalid` and the CLI prints the code verbatim |
| AC2 | The grant is bound to project, candidate and expiry (05.2.1-T5); the CLI sends a `replay` run only for the grant's own project and candidate hash, and a grant reused for a second candidate is refused |
| AC3 | A `purpose = replay` run creates no incident, no `incident_attempt`, and no regression entry; asserted by a fixture whose replay run fails every case |
| AC4 | A replay run is never bound to a release (`POST /v1/releases/{id}/runs` refuses it) and is absent from release evaluation inputs; it appears only on the run read model with `purpose = replay` |
| AC5 | No customer secret leaves the CI: the only credential sent to Evidgate is the OIDC-derived token; the job spec carries no secret values; env vars outside an allowlist are neither read into events nor uploaded; a canary secret planted in the CI env never appears in any request body or log of the conformance run |
| AC6 | The Playwright version pinned in the job spec is compared with the installed one; a mismatch stops the run with a `engine_pin_mismatch` report (no test executed) and a distinct exit code |
| AC7 | Grant expiry mid-run, CI timeout and a partial upload each end with a documented exit code and a run marked `incomplete`, never `complete` with missing cases |
| AC8 | The patch is applied to a scratch checkout of the customer's working copy only; the CLI never pushes, commits or opens a PR, and the original failing attempt is never overwritten (DECISIONS §5) |

## 4. Data model and migrations

None. No table or migration is owned here; `run.purpose` and the grant table belong to 05.2.1-T5 and 08.4.3-T1. The CLI keeps only a local, ephemeral replay workspace (scratch checkout and spool) deleted at exit.

## 5. API shapes (commands, queries, endpoints)

| Shape | Detail |
|---|---|
| CLI | `evidgate replay --grant <id> [--workdir <dir>] [--timeout <s>]`; token from the CI OIDC exchange (04.2.1), never a long-lived secret |
| Fetch | `GET` job spec by grant: `{ candidate_hash, patch, app_digest, fixture_ref, env_ref, playwright_version, case_ids[], expires_at }` (08.4.3-T1 shape, ⚠️ unverified until that plan lands) |
| Send | `POST /v1/runs` with `purpose = replay`, `replay_grant_id`; then `events`/`finalize` as in 04.2.3 |
| Errors | 422 `replay_grant_invalid`, 409 `run_closed`, 429 `Retry-After`, surfaced verbatim in the §9.2 envelope |
| Exit codes | to be listed in the CLI docs (T4): 0 completed, one code each for grant refused, pin mismatch, timeout, partial upload; numbering reserved after 04.2.3's existing codes [OPEN] |

## 6. States and transitions

Client flow: `grant_fetched → workspace_ready → patch_applied → running → uploading → finalized | failed(reason)`. The run follows the 00 §8.1 machine (`created → queued → running → collecting → complete`, exit `incomplete`); `purpose` is immutable. Candidate states (§8.7) change only through 08.4.3, never from this story.

## 7. Jobs and integrations

- Runs as one job in the customer's CI; no Evidgate-side job, task or runner lease (A5).
- Calls Evidgate only through the CLI send path; Playwright and the app under test run on the customer's side against the customer's staging host.
- Egress and workspace rules follow 11.2.1-T6 as stated to the customer in the template (T2); Evidgate cannot enforce them on customer infrastructure `[INFERENCE]`.

## 8. Security, privacy and performance

Rules named: 00 §5.7 S-rules on secrets and least privilege, P5 (no network call inside a DB transaction, server side), §5.5 C-pipeline unchanged (no new handler); DECISIONS §5 (no assertion weakening, no skip, original failure kept), A5.

| Rule | How this story meets it | Proven by |
|---|---|---|
| No secret egress | OIDC-only credential; env allowlist; redaction before spool | AC5, T3.1 canary test |
| Grant binding | Project, candidate, expiry checked server-side (05.2.1-T5) and re-checked by CLI before each upload batch | AC1, AC2 |
| Replay isolation from decisions | `purpose` immutable; excluded from regression, release, incident | AC3, AC4 |
| Safe healing | Patch applied to scratch copy; CLI refuses a patch that removes or weakens an assertion or adds skip/fixme (defence in depth with 08.4.3) | T1.3 test |

Authorization: the CI token must carry a `ci_producer` scope for the grant's project; no user permission is used; operators have no route here.
Retention/deletion: the CLI writes only a local scratch workspace deleted at exit; the replay run and its artifacts follow the normal run/artifact retention (00 §11, 06) and are deleted with the tenant; the grant's retention is 08.4.3's.
Telemetry: CLI prints a structured summary (grant id, candidate hash, exit reason); server side reuses ingest metrics tagged `purpose=replay`; a refused grant records a `security_event` (05.2.1-T5) [OPEN: confirm owner].
Failure path: the CLI exits with a documented code and the §9.2 error code; an expired grant or timed-out CI yields an `incomplete` replay run, which 08.4.3-T3 maps to `insufficient_evidence`; runbook note in the customer quickstart (T2/T4).
