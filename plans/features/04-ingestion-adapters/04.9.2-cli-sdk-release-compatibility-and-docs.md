## 1. Goal and non-goals

**Goal.** A tagged release publishes `@evidgate/*` (CLI, SDK, adapters) with provenance, a changelog and a signed tag; the server rejects clients outside the written N-1 window with an actionable 426; a customer can reach a first accepted run from the docs site alone; the vulnerability-disclosure channel exists.

**Non-goals.** Server release/deploy (10.2.x); the CLI commands themselves (04.2.x, 04.9.1); a hosted status page build (only the product choice is recorded); marketing site; localisation of docs beyond `en` at M3 [OPEN: vi docs timing].

## 2. User stories and acceptance criteria

- As a customer engineer, I want to pin and verify a published CLI version, so I trust what runs in my CI.
- As a customer on an old CLI, I want a clear upgrade message, so my pipeline failure is fixable in minutes.
- As a security researcher, I want a disclosure contact and policy, so I can report responsibly.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Pushing a signed tag `vX.Y.Z` runs `release.yml`, which re-runs `verify.sh` (including the licence and audit gates) and publishes every `@evidgate/*` workspace package with npm provenance; `npm audit signatures` on the installed package verifies the attestation ⚠️ (npm provenance behaviour to confirm against the npm docs at T1.1) |
| AC2 | The release workflow uses no long-lived npm token: auth is registry trusted publishing/OIDC (`id-token: write`) ⚠️, `check-no-npm-token.sh` fails CI if `NPM_TOKEN`/`_authToken` appears in workflows or `.npmrc`; every `uses:` is pinned by commit SHA (`check-action-pins.sh` covers `release.yml`) |
| AC3 | A release without a matching `CHANGELOG.md` entry, with a non-semver tag, or with an unsigned tag fails before publish; the changelog is generated from conventional commits and lists breaking changes under a heading |
| AC4 | `docs/compat.md` states the window "server supports clients N and N-1 minor" and `contracts/compat.json` holds `{min_supported, latest}`; a unit test asserts docs and JSON agree |
| AC5 | A request with `X-Evidgate-Client: evidgate-cli/<v>` below `min_supported` receives 426 in the 00 §9.2 envelope, code `client_unsupported`, with `min_supported`, `latest` and an upgrade URL; a supported or absent header (non-CLI callers) passes; the CLI maps 426 to exit 3 with that message |
| AC6 | `npm run docs:build` is a `verify.sh --stage docs` stage wired into `ci.yml` (parity checked by `check-ci-parity.sh`); it fails on a broken link, a missing glossary term, or API reference drift against `contracts/openapi.yaml` |
| AC7 | The docs site has a quickstart per CI (GitHub Actions from 04.2.4-T2, generic) and an error-code catalogue generated from the error enum in `contracts/openapi.yaml`; a scripted walk of the quickstart on the local stack reaches an accepted run (04.2.4-T3 script reused) |
| AC8 | `/.well-known/security.txt` (RFC 9116 fields `Contact`, `Expires`, `Policy`) is served by the docs host with `Expires` < 12 months away; a CI check fails when fewer than 30 days remain; the disclosure page names scope, safe harbour wording [OPEN: legal review] and response targets |

## 5. API shapes (commands, queries, endpoints)

| Surface | Shape |
|---|---|
| Request header | `X-Evidgate-Client: <name>/<semver>` (`evidgate-cli`, `evidgate-sdk`, `evidgate-adapter-<x>`); sent by the CLI/SDK/adapters on every call |
| Endpoint filter | Pipeline filter on `/v1/**` (Api host) compares header to `compat.json`; absent header never blocks (browser/web, curl) |
| 426 response | `{ "error": { "code": "client_unsupported", "message": "evidgate-cli 0.3.1 is no longer supported; upgrade to >= 0.5.0", "details": { "client": "0.3.1", "min_supported": "0.5.0", "latest": "0.6.2", "upgrade_url": "https://docs.evidgate.example/upgrade" } }, "request_id": "..." }` + `Upgrade-Info` not used; `Retry-After` absent (not retryable) |
| Docs build | `npm run docs:build` → static site artefact; API reference rendered from `contracts/openapi.yaml`, glossary from 00 §3, catalogue from the error enum |

## 6. States and transitions

Release: `tag pushed → verify → build → publish (provenance) → GitHub release + changelog`; a failed publish step leaves no partial set (publish order: SDK → CLI → adapters; rerun is idempotent, already-published versions are skipped, never overwritten). Client skew: `supported → deprecated (within N-1, CLI prints a warning to stderr) → unsupported (426)`. Dependency pin: adapters declare an exact-minor SDK range.

## 7. Jobs and integrations

- `release.yml` GitHub Actions workflow (npm registry, OIDC trusted publishing ⚠️, `git tag -v` signature check, release notes upload); Dependabot/audit gates from 01.7.1-T4 run in the same verification.
- Docs site: static generator [OPEN: tool choice, ⚠️ licence check by `licence-scan.sh`]; hosted on the pilot-approved static host.
- Status page: candidate products (hosted status-page services, or a static self-hosted page) are ⚠️ unverified; T3.2 compares them and records one `[DECISION]` (ADR in `docs/adr/`).

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Authorization (DoR 1) | Publishing is limited to the protected `release` environment with required reviewers (01.7.1-T3 CODEOWNERS); the 426 filter and `/v1/compat` need no permission and expose no tenant data | AC2, T4.1 test |
| Retention/deletion impact (DoR 2) | None for customer data: no table; release artefacts and changelog are public, immutable on the registry (unpublish policy: deprecate, never delete) | review note |
| Telemetry (DoR 3) | Counter `client_version_requests_total{client,major_minor}` and `client_unsupported_total` (bounded labels: parsed version only, malformed header → `unknown`); release workflow emits run summary | T4.2 test |
| Failure path (DoR 4) | Missing/garbled header passes (fail-open for compat, logged once); a failed publish leaves registry consistent and is rerunnable; docs build failure blocks merge | AC3, AC6 |
| Supply chain (00 §5.7, 01.7.1-T4) | SHA-pinned actions, no stored token, provenance, `npm audit signatures`, licence gate in release path (answers 01 §11 [OPEN]) | AC1, AC2 |
| Performance | Header check is an in-memory semver compare, < 0.05 ms p99; docs build < 3 min | T4.1 benchmark-free assertion, CI timing |

## 11. Rollout

- Flag: none; the 426 filter ships with `min_supported` equal to the lowest published version, so nothing is rejected until a deliberate bump. Merge order: T1 → T4 → T2 → T3.
- Monitoring: `client_unsupported_total` alert on a spike after a bump; release run summary; security.txt expiry check in CI.
- Rollback: deprecate a bad npm version and publish a patch (never unpublish); lower `min_supported` in config to stop 426s.
