## 1. Goal and non-goals

**Goal.** Each Playwright shard is its own producer with its own contiguous sequence, surviving Playwright's blob-merge report model; every `result.attachments` entry (trace, video, screenshot) is classified, policy-checked and uploaded through the CLI artifact path so `test.finished` envelopes can reference real `artifact_ids`.

**Non-goals.** The server-side producer-slot table and binding check (04.1.2-T4/T5); the upload mechanics themselves (04.2.4-T1 — this story consumes `uploadFile()`); artifact viewing/scanning (06); merging shard reports for the customer's own dashboard (Playwright's `merge-reports` stays a customer-side choice).

## 2. User stories and acceptance criteria

- As a CI author running `playwright test --shard=k/n` (or a matrix of jobs), I get one producer per shard with independent sequences, so the server sees the manifest's planned shards and no sequence collides.
- As a reviewer, I see traces/videos/screenshots attached to the right attempt, so evidence is complete without manual upload.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Two shards of the same run emit under distinct `producer_id`s (`shard-<k>` derived from the blob filename / `--shard` index ⚠️ confirm `--shard` env surface per area plan §4), each with sequence 1..m contiguous; the union covers the manifest's shard slots and matches one `producer_slot` per shard (T9) |
| AC2 | A restarted shard process reuses the **same** deterministic `producer_id` (the manifest `shard-<index>` slot, T54/T84) and resumes `sequence` from the spool/`shards.json` checkpoint — it never mints a restart suffix; a `producer_id` the manifest did not declare is a client bug that the server rejects 422 `unknown_producer`; a reused `(run, producer, sequence)` is never emitted client-side (04 §5 restart rule superseded by T84) |
| AC3 | In `merge-reports` mode the per-shard origin is preserved: each event keeps its original shard's `producer_id`/`sequence`; no renumbering at merge (D3 order rule). **Follow-up (S56):** met as *no renumbering, refusal instead of guessing* — a merged replay emits nothing and logs one stderr line, because a v1 reporter never sees the per-blob shard config (see T1 Notes "Known limitation (D-S56-Q11)") |
| AC4 | `result.attachments` map by content-type/path: `trace*.zip→trace`, `video*.(webm|mp4)→video`, `*.(png|jpeg)→screenshot` (T20 kinds); unknown types → `raw_report` bucket refused — attachments with unmapped types are skipped with a `run.log` warning, never uploaded under a guessed kind |
| AC5 | Each attachment is uploaded with run scope + this shard's manifest `producer_id` + planned `(execution_key, attempt_no)` and the deterministic `Idempotency-Key` = `sha256(run_id ‖ producer_id ‖ execution_key ‖ attempt_no ‖ kind ‖ file_sha256)` exactly as 04.2.4-T1 (T17, T85/T92); the emitted `test.finished` carries the returned `artifact_ids`; a rejected `upload-url` (422 unplanned attempt) leaves the event emitted **without** that id plus a warning — the test result is never lost to an artifact failure |
| AC6 | Files outside the allowed directory set (Playwright `outputDir` + `test-results` + explicit `--dir`) or over the per-kind size cap are refused pre-upload with a filtered reason (04 §5 traversal row; §6 allow-list); path traversal names (`../`) in `attachment.path` are rejected and logged as warnings |
| AC7 | Sensitivity is decided at `upload-url` time (§6): reporter marks `sensitive` when the suite/case opts in via annotation `evidgate.sensitive`; default `normal` |

## 3. Contracts touched

- 00 §9.4 `(run, producer_id, sequence)` uniqueness — producer naming is client-side; the contract it must satisfy is fixed.
- T9/T54 producer slots: `producer_id` values equal the manifest shard producer names agreed with 05's manifest schema — the deterministic scheme `shard-<index>`; the reporter derives them so `RegisterSlotsAsync` (04.1.2-T4) writes matching rows. **Contract note:** the manifest↔producer naming rule is shared with 05.1.1 manifest work — `shard-<index>` is documented in `contracts/adapter/playwright-mapping.md`; if 05's manifest uses different names, this story conforms to that file.
- T84 restart contract: a restart keeps the same `producer_id` (no new id is minted) and resumes `sequence` after the stored checkpoint; any `producer_id` outside the manifest is rejected 422 `unknown_producer` (04.1.1-T4.2), so a misconfigured producer fails loudly instead of splitting the slot stream.
- T17/T18/T85/T92: attachment upload passes `producer_id` + `(execution_key, attempt_no)` + the deterministic `Idempotency-Key` + signed headers exactly as 04.2.4-T1 implements.
- No schema or endpoint change.
- Recorded (04.3.1-T1, 2026-10-07): the reporter's capability document declares only the four AC3 `supports` flags. Per `contracts/adapter/capability.v1.json`, an absent `capture_control` means the run-create configuration document (`config.v1.json`, T97) is honoured, which the reporter does not read yet. When attachments land here, either honour `config.v1.json` or declare `capture_control: false`. Open gap.
- Recorded (04.3.1-T1, 2026-10-07): `producer_id` is a required reporter option with no env fallback (no contract defines `EVIDGATE_PRODUCER_ID`) and must match `^[A-Za-z0-9._-]{1,128}$` (spool path safety); the `shard-<index>` scheme fits. The reporter's `checkpoint.json` (`{ producer_id, next_sequence }`, 04.3.1 §4) already gives T84 resume; reconcile it with the `shards.json` of §4 instead of keeping two sequence stores.

## 4. Data model and migrations

None server-side. Reporter-local: `shards.json` in the spool dir records `{ producer_id, shard_index, sequence_next, last_restart_at? }` — on restart the same `producer_id` is kept and `sequence` resumes from `sequence_next` (T84), proving continuity; artifact references are envelope fields only.

## 5. API shapes (commands, queries, endpoints)

Client-side additions to `packages/adapter-playwright` (no new server endpoints):

## 6. States and transitions

Producer slot view (04 §4 states): `open → closed` via `finalize`; this story only chooses `producer_id` — slot state is server-owned. Attachment per-file flow: `classified → uploaded → referenced (artifact_id in event)`; exits: `skipped` (unmapped type, cap exceeded, disallowed path) and `failed` (upload error → warning event, result preserved). No transitions are retried into a different kind.

## 7. Jobs and integrations

- Playwright blob reporter writes `report-<shard>.zip` — relied on only for shard *identity*, never parsed for results (D3/D8: results flow through callbacks).
- Uploads happen between `onTestEnd` and a bounded drain in `onEnd`; attachments stream via `uploadFile()` — no whole-file buffering.
- Consumed downstream by 06 evidence freeze (T17: link resolved server-side at freeze; unresolved ⇒ `artifact_missing`, not this story's failure path).

Notes (04.3.3-T1 shard identity, S56): the area plan §4 `[WARN]` on the shard surface is confirmed and recorded in `contracts/adapter/playwright-mapping.md` §`shards` with the installed `@playwright/test@1.63.0` sources: `FullConfig.shard` is `null` or `{ current, total }` with `current` one-based (`types/test.d.ts:1675,1691-1698`; default `null` at `lib/runner/index.js:581`), the CLI flag is `--shard <current>/<total>` (`lib/program.js:216`), there is **no** `PLAYWRIGHT_SHARD` environment variable (no match in `node_modules/playwright/{lib,types}`), and the blob file is `report[-<commandHash>]-<current>.zip` with `current` zero-padded to the width of `total` (`lib/runner/index.js:3151-3161`). Decisions: the index base is **1-based** so slot `i` of the manifest is producer `shard-i` (T9/T54) and an unsharded run is `shard-1` with `shard_index: 1` and no `shard_total` (the manifest owns the count); `resolveProducerId(config)` reads `config.shard` only (never a blob filename or an env var); the reporter option `producer_id` is honoured only when it equals the derived id, otherwise `onBegin` buffers a refusal that `onEnd` throws with zero envelopes written (a wrong id would be 422 `unknown_producer` or two shards interleaved on one sequence), and without a shard config an explicit id still wins and claims no slot. Restart (T84) is the same id and the same directory, resuming `sequence` from the chunk scan / `shards.json`; `shards.json` is written at rotation, close and restart detection only (D-S56-Q1) and never per flush. Merge mode (AC3): the merged config is `shard: null` (`lib/runner/index.js:8211-8219`) and a custom reporter is wrapped in `ReporterV2Wrapper` (`lib/runner/index.js:1703-1715`), so it never sees the per-blob shard config (`onReportConfigure` is dispatched at `:8012` to built-in reporters only); the replay therefore emits **nothing** and logs one stderr line, which preserves each shard's original identity instead of guessing or renumbering. **Closed, Note from #32:** the sidecar lookup root is pinned to `FullConfig.rootDir` (`sidecar.ts` `SidecarLoadOptions.rootDir`, passed by `reporter.ts`), so every shard reads the same manifests and maps the same `case_id`; a file outside the root contributes only its own directory, nothing above it is read, and the traversal/symlink hardening is unchanged (`sidecar-root.test.ts`). **Closed, Note from #49:** `identity-perf.test.ts` no longer asserts wall-clock time; it measures process CPU time (`process.cpuUsage`, min of 3 samples) and asserts complexity — 4x the input may cost at most 8x the CPU and the cost per item may not grow, which a quadratic regression (16x) still fails — plus a deterministic count that each manifest is read once; it stays in the default `vitest` run.

Notes (04.3.3-T1 spool, S56): the reporter-side spool contract is settled and closes the three S54 leftovers recorded above. (1) `shards.json` replaces the writer-side `checkpoint.json` (D-S56-Q1): one record per producer directory, written atomically at chunk rotation, at close and at restart detection only — never per flush — with a read-only legacy `checkpoint.json` fallback and a leftover `shards.json.tmp`/`checkpoint.json.tmp` cleaned rather than trusted. (2) Resume is `max(record, last chunk sequence + 1)`, i.e. the record is a floor (D-S56-Q9), because the only server sequence refusal is reuse (`422 sequence_reused`, `contracts/events/ordering.md` §1) while a hole is accepted (§3); a value that is not a safe integer is dropped on read. (3) The reporter takes `<producer_dir>/writer.lock` for the life of a writer and the CLI refuses a live one with exit 3 `spool_locked` naming the pid (D-S56-Q8, `contracts/cli.md` §11.2) — a dead lock is ignored by the CLI and broken only by the reporter's own verified takeover, and the CLI's upload journal is deliberately not gated by it. (4) The write-time cap `EVIDGATE_SPOOL_MAX_BYTES` is per RUN directory, checked before the first byte of a batch (all-or-nothing, error `spool_cap_exceeded`), so the cap is a write-time refusal as well as a CLI pre-flight. With these, the three S54 items — no single-writer lock, no write-time cap, per-flush `checkpoint.json` rewrite — are closed. Proven by `packages/adapter-playwright/src/spool.test.ts`, `spool-hardening.test.ts`, `spool-lock.test.ts`, `shards-store.test.ts`, `restart.test.ts` and `packages/cli/src/spoolLock.test.ts`, `commands/eventsSend.test.ts`, `commands/runsFinalize.test.ts`.

Known limitation (D-S56-Q11): the reporter cannot attribute merged events to shards. A v1 reporter never receives the per-blob shard config — Playwright wraps it in `ReporterV2Wrapper` (`@playwright/test` `lib/runner/index.js:1705-1774`) and dispatches `onReportConfigure` to built-in reporters only — so a `merge-reports` replay emits nothing and logs one stderr line instead of guessing an id (AC3's "no renumbering, refusal instead of guessing"). Customers therefore ingest **per-shard** runs, and the merged-report path is not usable for event production until a v2 reporter exists. Receiving task `04.6.1-T2` (dogfood fixture "one shard-merged set", `plans/04-ingestion-adapters.md:241`) must either ingest the merged set per shard or drive a v2 reporter; see the matching note in `plans/features/04-ingestion-adapters/04.6.1-per-producer-golden-set.md`.
