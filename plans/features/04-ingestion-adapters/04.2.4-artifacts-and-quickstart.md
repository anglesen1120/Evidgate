## 1. Goal and non-goals

**Goal.** The `evidgate` CLI can ship a file to evidence storage end to end — `upload-url` → presigned PUT → `complete` — with retry, checksum verification and correct surface of 06's rejections; `evidgate quickstart` emits a working CI recipe; a scripted end-to-end test runs the whole CLI path (token → manifest → run → events → artifacts → finalize) against the local stack with the dogfood fixture.

**Non-goals.** Artifact lifecycle, object storage, scan and retention on the server (06.1.x, 06.3.x); reporter-side attachment collection (04.3.3-T2 consumes this story's upload function); the conformance harness itself (04.6.1); web artifact viewing (09).

## 2. User stories and acceptance criteria

- As a CI author, I want `evidgate artifacts upload` to reliably deliver traces and screenshots, so evidence is attached to my run.
- As a new customer, I want `evidgate quickstart` to print a working GitHub Actions workflow using OIDC, so I never handle a long-lived secret.
- As the Tech Lead, I want one reproducible e2e run of the CLI against the local stack, so CLI regressions are caught before release.

## 3. Contracts touched

- 00 §9.3 `POST /v1/artifacts/upload-url` and `POST /v1/artifacts/{a}/complete` — consumed as specified by 06; the CLI never picks the object key (04 §6).
- T17/T85: the CLI supplies `(run_id, producer_id, execution_key, attempt_no)` in the `upload-url` body — `producer_id` is the manifest `shard-<index>` of this producer, so the first accepted write binds the right `producer_slot` (T9); the attempt↔artifact link is resolved server-side at evidence freeze — the CLI stores only the returned artifact id.
- T18: presigned PUT signs `Content-Length` and the checksum header — the client must send exactly the signed values, byte-identical.
- Resolved (T85/T92): `upload-url` carries `producer_id` plus a **required** `Idempotency-Key` (00 §9.1 — every resource-creating mutation takes one); the CLI derives it deterministically as `sha256(run_id ‖ producer_id ‖ execution_key ‖ attempt_no ‖ kind ‖ file_sha256)`, so a step retry after a lost response replays the stored artifact row instead of minting a duplicate. [S56: T85/T92 require only those two; the request body has no sensitivity member — sensitivity is server-resolved from the kind policy.]
- `contracts/cli.md` gains the `artifacts upload` and `quickstart` commands and their exit codes (00 §9.3: 0 pass-through success, 3 tool/transport error; upload commands exit 0/3), plus §3's `EVIDGATE_UPLOAD_DEADLINE` and the §12 upload contract [S56: the deadline row and §12 were added by the T1 delivery].
- No schema, permission or endpoint change.

## 4. Data model and migrations

None server-side. Client-side state only: the upload journal lives in the CLI spool directory (04.2.3-T1) as `uploads/<identity>-<artifact_id>.json` `{ artifact_id, file_sha256, size, kind, execution_key, attempt_no, media_type, put_done, complete_done, mint_no }`, where `<identity>` is the first 16 hex of a SHA-256 over the length-prefixed `upload-url` identity so a lookup parses only its own candidates [S56: the record carries the whole identity, not just (`file_sha256`, size)} — a resume requires every field to match. Another execution, kind or attempt is a different `upload-url` key (so a different server row); a changed `--media-type` keeps the key and changes the body, so the server's `409 idempotency_conflict` surfaces verbatim. In both cases the CLI restarts at mint `0` rather than resuming the other record [S56: `uploads/<artifact_id>.json` in `contracts/cli.md` §11.1/§11.8 is left to the §11 owner (FixReporter), not edited by this task]. [S56: `mint_no` is the 0-based `upload-url` mint it belongs to, so an expired presigned URL renews without replaying a dead row], so a restarted CLI resumes an interrupted upload without minting a duplicate artifact row.

## 5. API shapes (commands, queries, endpoints)

Client commands (Node 22+/TS 6.0, `packages/cli`):

| CLI command | Server call | Behaviour |
|---|---|---|
| `evidgate artifacts upload --run <r> --file <f> --kind <k> --execution-key <64-hex> [--producer <slot>] [--attempt <n>] [--media-type <t>] [--dir <root>]` | `POST /v1/artifacts/upload-url` (`artifact:write`) → presigned PUT → `POST /v1/artifacts/{a}/complete` | kind allow-list per 00 §7 (T20); body carries `producer_id` (manifest `shard-<index>`) + `(execution_key, attempt_no)` scope and header `Idempotency-Key` = `sha256(run_id ‖ producer_id ‖ execution_key ‖ attempt_no ‖ kind ‖ file_sha256)` (T85/T92); SHA-256 computed while streaming once; honours `Retry-After` on 429 [S56 supersedes: `--execution-key` is **required**, not optional — `contracts/openapi.yaml` `createArtifactUploadUrl` marks `execution_key` required; the body has no sensitivity member] |
| `evidgate quickstart [--format github|generic] [--write <path>]` | none (local template) | renders a workflow pinned to the published CLI version; the GitHub template uses `id-token: write` + OIDC exchange |

Error mapping follows 00 §9.2: 401 → "run `evidgate auth` refresh"; 403 scope mismatch / `producer_slot_taken` → exit 3 with server code; 409/412/422 → exit 3, never retried; 413 → exit 3 naming the cap; 429/5xx → jittered backoff inside the per-upload deadline.

## 6. States and transitions

Client view of the artifact lifecycle (00 §8.4): `upload-url` accepted → `pending_upload` (object under `pending/` prefix, 24 h expiry, T18) → PUT done → `uploaded` → `complete` accepted → `ready`, or `rejected` on size/checksum/MIME mismatch. Journal states `put_done` / `complete_done` mirror this so a restart resumes at the right step. A replayed `complete` for an already-ready artifact is a `200` (openapi) and the journal answers `ready` without a request; a `complete` **409** is a real state conflict, terminal and never retried [S56 supersedes: "a `complete` that returns 409/already-ready is treated as success (idempotent)" — the wire contract resolves the replay as `200`, so a 409 is not a replay].

## 7. Jobs and integrations

- Object storage: presigned PUT to the store chosen in 06 (SeaweedFS/provider parity for signed `Content-Length` + checksum headers verified by 01.8.1-T1 / 10.6.1-T2, T18 ⚠️ client relies on the headers returned).
- Secret scan is async (T19): `complete` returns `ready` without waiting; the CLI never polls `scan_state`.
- Consumed by 04.3.3-T2 (reporter attachments call the same `uploadFile()` library function, not a subprocess) and by the 04.6.1 dogfood fixture.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| T18 / 00 §8.4 | PUT sends exactly the signed `Content-Length` + checksum; `complete` re-check happens server-side; client treats `pending/` expiry as "re-request upload-url" | AC2, AC3 |
| 04 §6 allowed directories / DECISIONS §7 | CLI resolves `--file` to an absolute path and refuses files outside the configured allow-list (default: test output dir + explicit `--dir`), preventing accidental upload of home/secret files | T1.3 test with a disallowed path |
| 00 §9.1 | Bearer `ci_producer` token only (no cookie/XSRF path); token from the 04.2.1 cache, refreshed before expiry | AC6 run log |
| S3 | File names and artifact ids may be logged; file contents, presigned URLs (bearer credentials, 04 §6) and tokens are redacted from logs | redaction unit test `redact.test.ts` |
| 00 §9.2 retry rule | Retries only on 429/5xx/network with jittered backoff; same artifact id; deterministic 4xx never retried | AC3; T1.2 test |
| Performance | Single streaming pass computes SHA-256 while uploading; no double read of multi-GB traces; concurrency cap (default 4) for batch uploads | T1.1 test asserts one `fs.read` pass |
| Retention/deletion | None owned: the CLI holds only the journal file, deleted on `finalize` success; server retention is 06's | — |

DoR review answers (00 §12, `plans/features/README.md` §6) for this story:

- **Authorization:** `artifacts upload` (T1) is a bearer `ci_producer` client: `upload-url` and `complete` need `artifact:write` on the token's project (server-side, 06.1.2); the CLI holds no permission logic. `quickstart` (T2) calls no endpoint and reads no token or cache; the workflow it renders grants only `contents: read` and `id-token: write`, and the job's OIDC JWT is exchanged at `POST /v1/ci/token` under the project binding (02.4.1).
- **Telemetry:** the CLI prints file names, artifact ids and the server `error.code` + `request_id` on stderr (`contracts/cli.md` §5); presigned URLs and tokens are redacted (S3 row above); server-side counters belong to 06 and 04 §6. `quickstart` emits only the rendered template or `wrote <path>`.
- **Failure path:** every CLI failure exits 3 with a stable `error.code` (`contracts/cli.md` §2/§5): deterministic 4xx are never retried, 429/5xx/network retry inside the per-upload deadline, and the journal resumes an interrupted upload (§6). `quickstart` refuses an unknown `--format` (`usage`), a project that is not renderable (`invalid_config`, value not echoed) and a `--write` path outside the working directory or an existing file (`usage`), writing nothing.
