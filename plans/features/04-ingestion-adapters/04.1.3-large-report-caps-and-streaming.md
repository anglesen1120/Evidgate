## 1. Goal and non-goals

**Goal.** A 100 000-test report is either accepted within documented caps or refused with a stable code, and nothing on the server holds a whole report in memory. Three parts: (T1) published caps on manifest size/cases/variants and raw-report size, enforced at the edge, plus cursor pages on every list that can grow with test count; (T2) the reconciler reads one grouped SQL aggregate over acked events (no event rows in memory; decision 468 A) and the raw-report parsers stream report entries; (T3) a 100 000-test fixture and a memory/time budget test that fails the build when a budget is exceeded, and feeds the 10.6.1-T1 load generator.

**Non-goals.** The per-batch limits (500 events, 1 MiB pre-decompression, gzip bomb guard) — already 04.1.1-T3; XML/zip safe-parser profile and the child-process sandbox (06.3.1, 06.3.6); time partitioning of `event` (06.4.6); quota/rate limits (04.1.2); the web table virtualisation (09 plans consume the page shape only); streaming *upload* of artifacts (06.1.2 uses presigned PUT, bytes never pass the API).

## 2. User stories and acceptance criteria

- As a CI owner with a 100 000-test suite, I get a clear 413/422 with the limit named if my manifest or report is over the cap, and success if it is under.
- As an operator, a large run does not push the worker past its memory limit or stall other tenants' reconciliation.
- As a release manager, run detail and report comparison open with the first page fast, however many cases the run has.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | Manifest with `executions <= MaxManifestExecutions` and bytes `<= MaxManifestBytes` is accepted; one execution over → 422 `cap_exceeded` with `details {cap: "manifest_executions", limit, actual}`; bytes over (before decompression or after, whichever trips first) → 413 `too_large` with `details {cap: "manifest_bytes"}`; neither creates a run or any row |
| AC2 | A raw report over the `raw_report` kind's `max_bytes` or declaring more than `MaxReportCases` entries ends `rejected` with `too_large` / `cap_exceeded` and the `missing[]` reason `report_unparseable`; the stored raw bytes are kept until retention (04.4.1-T3) |
| AC3 | Caps are published: `contracts/openapi.yaml` lists the codes and `x-evidgate-limits` values; `GET /v1/capabilities` (if present) or the docs page states the same numbers; a drift test fails when code constant and OpenAPI value differ |
| AC4 | Every list that grows with test count (`GET /v1/runs/{r}` executions section, comparison, case-attempt list) returns `{items, next_cursor}` ordered `(created_at, id)`, default 50, max 200; `limit > 200` → 422 `schema_invalid`; paging through 100 000 items returns each exactly once with no duplicate or gap while rows are being appended |
| AC5 | `GET /v1/runs/{r}` stays O(1) in test count: it returns summary counts (by normalised status) and the first page only, p95 under 300 ms on the 100k fixture (budget `[INFERENCE]`, confirmed by 10.6.1-T1) |

## 4. Data model and migrations

No new table. One additive migration `migrations/NNNN_ingestion_large_report_indexes.sql`:

| Change | Detail |
|---|---|
| Index `event (org_id, run_id, producer_id, sequence)` | already the unique key from 04.1.1; the reconciler aggregate uses it (EXPLAIN-asserted by `ObservedEventsAggregate_UsesRunProducerSequenceIndex_NoSeqScanOnEvent`, no new index) |
| Index `case_attempt (org_id, run_id, created_at, id)` | keyset order for the paged list; the existing `(run_id, normalized_status)` index does not serve `(created_at, id)` order |
| ~~Table `reconcile_progress`~~ | struck (decision 468 A, 2026-11-20): not created. The attempt and its finish run in ONE transaction that rolls back on a crash, so a cursor written in it would never survive one, and the read is already a single aggregate, so there is no page to resume |

## 5. API shapes (commands, queries, endpoints)

| Kind | Name | Endpoint | Permission | Codes |
|---|---|---|---|---|
| Command | `CreateRun` (cap check, 05.2.1) | `POST /v1/projects/{p}/runs` | `run:create` | 201 · 413 `too_large` · 422 `cap_exceeded` / `manifest_invalid` |
| Query | `GetRun` (counts + first page) | `GET /v1/runs/{r}` | `run:read` | 200 · 404 foreign run |
| Query | `ListCaseAttempts` | `GET /v1/runs/{r}/case-attempts` | `run:read` | 200 page · 422 bad `limit` / `cursor` |
| Query | `GetReportComparison` (paged) | `GET /v1/runs/{r}/reports/{report_id}/comparison` | `run:read` | 200 page · 404 |

Cursor is opaque (base64 of `(created_at, id)`), tamper-evident via HMAC so a forged cursor is 422, never an SQL error. List queries are Dapper over a module view (C5).

## 6. States and transitions

No new state. A cap violation at run create produces no run. A cap violation on a raw report is an artifact/report outcome (`rejected`, 00 §8.4) and a completeness reason (`report_unparseable`, 00 §8.5), never a run state. A reconcile attempt is one transaction: a crash rolls it back and the redelivered attempt re-runs whole and yields one revision (T82); there is no reconcile cursor.

## 7. Jobs and integrations

- Reconciler (05.3.2-T2): reads observed evidence as one grouped SQL aggregate over `event` per producer (counts, min/max sequence, flag counts, unfinished attempts); no event row is materialised, the gap check compares declared last sequence/count with the aggregate, and a crash re-runs the attempt (05.3.2 retry, one revision). No `ReconcilePageSize` and no persisted cursor.
- Parsers (04.4.1): consume `IParsing` streaming readers (06.3.1) and emit entries to the mapper one at a time; the mapper never builds the full `testsuite` DOM. Where 06.3.6's child process runs the parse, results return as NDJSON over the pipe in pages. [INFERENCE] the NDJSON hand-off is decided in 06.3.6-T1; this story only requires that the consumer is a stream.
- Fixture generator (T3): a deterministic script `scripts/dev/gen-large-report` writes the 100k fixture from a seed so the repo stores the generator and a loader-shaped fixture directory (`meta.json`, `input.json` parameters, `expected.json` checksums), not 100 MiB of XML. [INFERENCE] if CI cannot afford generation time, a gzip-compressed copy is stored with Git LFS; decided in T3.1.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| Authorization | list endpoints need `run:read`; cap checks run after authentication so unauthenticated callers learn nothing about limits beyond the public docs | 403 test |
| Tenant isolation | page queries run in the tenant transaction (RLS), cursor holds no tenant data, and a cursor from another run/org is 422 | isolation test with two orgs |
| DoS | caps are enforced before parse/allocate (Content-Length and streaming byte counter, 413 early); a cap error returns no body echo | AC1, AC2 |
| P1/P4 | keyset pages over covering indexes, no OFFSET; memory bounded by page size | AC4, AC6, AC8, EXPLAIN check |
| Privacy | pages return ids and statuses, no raw report bytes or paths in errors (S3) | log-allowlist test |
| Telemetry | counter `ingest_cap_exceeded_total{cap}` (the `reconcile_page_seconds` and `reconcile_peak_events_in_memory` instruments are struck with the page loop, decision 468 A) | metric visible in dev stack |

- **Retention/deletion:** no reconcile cursor table exists (struck, decision 468 A); the 100k fixture is test data, not tenant data.
- **Failure path:** cap exceeded → documented 413/422 and counter; reconcile crash → the attempt rolls back and is redelivered (one revision); cursor invalid or minted for another run → 422 `request_invalid` at `cursor`.

DoR review answers. **Authorization:** `run:read` for lists, `run:create` for manifest caps; no new permission string. **Retention/deletion impact:** none for the reconciler (no cursor table); the 100k fixture is test data, not tenant data. **Telemetry:** as above plus trace attribute `ingest.cap` on rejected requests. **Failure path:** cap exceeded → documented 413/422 and counter; reconcile crash → the attempt rolls back and is redelivered (one revision); cursor invalid → 422.
