## 1. Goal and non-goals

**Goal.** `evidgate` gains the two commands that open a run: `evidgate manifests upload` (upload + verify a manifest, print `manifest_hash`) and `evidgate runs create` (create a run with a client-supplied `Idempotency-Key`, `--json` output, release/ci-ref flags). Both are thin, deterministic clients over the generated SDK.

**Non-goals.** Manifest verification and `execution_key` derivation (server, 05.1.1-T4), run-create orchestration and slot registration (05.2.1-T1), event sending (04.2.3), artifact upload (04.2.4), `evidgate gate` (07.6.1).

## 2. User stories and acceptance criteria

- As a CI pipeline, I upload the manifest once and create the run idempotently, so re-running the workflow step after a network blip returns the same run instead of a duplicate.
- As a developer, `--json` gives me `run_id` and `manifest_hash` I can feed into later steps.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `evidgate manifests upload --file m.json` POSTs to `/v1/projects/{p}/manifests` and prints `manifest_id` and `manifest_hash`; a manifest that fails server verification exits 3 with `error.code` |
| AC2 | `evidgate runs create --manifest-id <uuid> --manifest-hash h [--idempotency-key k]` POSTs `/v1/projects/{p}/runs` with the `Idempotency-Key` header and prints `run_id` (amended 2026-10-14 (D-S47-Q1, coordinator): `--manifest-id` is required in addition to `--manifest-hash`, because the merged `CreateRunRequest` resolves the manifest by `manifest_id` — `contracts/openapi.yaml` `createRun`, `additionalProperties: false`) |
| AC3 | Repeating `runs create` with the same key and same payload returns the same `run_id` (server replay); the same key with a different payload exits 3 on 409 `idempotency_conflict` (T11) |
| AC4 | When `--idempotency-key` is omitted, the CLI derives a stable key ≤ 128 chars, so an accidental step-retry stays idempotent: `sha256` (lowercase hex) of the UTF-8 JSON array `["evidgate.run-key.v1", manifest_hash, manifest_id, release ?? null, ci_ref ?? null]`, fixed field order and JSON `null` for an absent optional (amended 2026-10-14 (D-S47-Q1, coordinator): a JSON array is unambiguous — no separator can collide — and every value sent in the body feeds the key, replacing `sha256(manifest_hash + policy + suite + env + ci_ref)`) |
| AC5 | `--manifest-id`, `--manifest-hash`, `--release` (release binding at create, T15) and `--ci-ref` flags map to the documented request fields (`--manifest-hash` and `--manifest-id` are never a substitute for each other; the hash is never sent); `--json` prints `{run_id, manifest_hash, state}` and nothing else on stdout (amended 2026-10-14 (D-S47-Q1, coordinator): `--policy`/`--suite`/`--env` are dropped — `CreateRunRequest` has no such member, the server pins suite/environment from the manifest (05.2.1 plan line 11) and policy from the project's active revision (07.1.1-T4, 05.2.1 plan line 193)) |

## 3. Contracts touched

- 00 §9.3 `POST /v1/projects/{p}/manifests` and `POST /v1/projects/{p}/runs` — consumed as specified; no shape change.
- `contracts/cli.md` — adds the two commands, their flags, the derived-key rule (AC4) and `--json` output shape.
- Idempotency (T11): the CLI supplies the key; `idempotency_record` arbitration stays server-side. No permanent unique on business tables is implied by the client.

## 4. Data model and migrations

None (no database objects — customer-side CLI). Manifest files are read-only inputs; no local persistence beyond the 04.2.1 token cache.

## 5. API shapes (commands, queries, endpoints)

| Command | Endpoint | Behaviour |
|---|---|---|
| `evidgate manifests upload --file <path> [--json]` | `POST /v1/projects/{p}/manifests` (`run:create`) | streams the file, prints `manifest_id`, `manifest_hash`; 422 `manifest_invalid` → exit 3 with `error.details` verbatim |
| `evidgate runs create --manifest-id <uuid> --manifest-hash <h> [--release r] [--ci-ref ref] [--idempotency-key k] [--json]` | `POST /v1/projects/{p}/runs` (`run:create`) | body `{manifest_id, release?, ref?}` and the `Idempotency-Key` header (derived per AC4 when the flag is omitted); prints `run_id`, `manifest_hash` and `state`; 409 `idempotency_conflict` → exit 3 echoing `error.code`; 202-style async fields absent — run create is synchronous per 00 §9.3 (amended 2026-10-14 (D-S47-Q1, coordinator): `--policy`/`--suite`/`--env` dropped and no `manifest_hash` request member — the merged `CreateRunRequest` has `manifest_id` plus optional `release`/`components`/`ref`/`purpose`/`replay_grant_id` only, `additionalProperties: false`) |

Both commands reuse 04.2.1's `resolveConfig()`, token provider and exit codes; HTTP goes through `packages/sdk` (no hand-written DTOs, W5 analogue for the CLI).

## 6. States and transitions

None locally — the CLI is stateless between invocations. Server-side it triggers: manifest `verified` (05.1.1), run `created` (and `created → queued` when 05 commits the producer slots, T13). The CLI observes only the returned `state`.

## 7. Jobs and integrations

- Consumes `POST /v1/projects/{p}/manifests` (05.1.1-T4's verification result is what prints `manifest_hash`) and `POST /v1/projects/{p}/runs` (05.2.1-T1 — whose committed `producer_slot` rows are later bound by 04.1.2-T5 when events arrive).
- `--release` feeds the run↔release binding at create (T15); a missing/ambiguous release name surfaces the server's 422.
- No background jobs; `runs create` is safe to retry only with the same `Idempotency-Key` — AC4 makes that automatic.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §9.1 idempotency | header sent on every create; derived key is deterministic per identical intent | AC3, AC4 tests |
| Token scope | `ci_producer` project scope matches `--project`/`EVIDGATE_PROJECT`; mismatch → server 403 → exit 3 | integration test |
| S3 analogue | manifest content is user data — echoed only under `--verbose` to stdout files the user owns; secrets in manifests are rejected server-side (05) and never logged by the CLI | stderr redaction test |
| Input limits | manifest file size capped at the server's documented limit (256 KiB: openapi `createManifest` "Body ≤ 256 KiB → 413", 05.1.1 §8 transport cap; this row said 1 MiB before 04.2.2-T1 and the contract wins); a larger file exits 3 `manifest_too_large` locally before any request, including the token exchange | boundary test |
| NFR-04-2 | Node 22+ cross-platform paths only | Vitest path tests |
| Retention/PDPL | CLI stores nothing; manifest may name suites/envs but carries no credentials | stated |
| Authorization | the CLI holds no permissions of its own: it presents the `ci_producer` bearer from `getToken()` (04.2.1) and the server decides scope; a project mismatch is the server's 403 → exit 3 | integration test (token scope row) |
| Telemetry | none client-side (no metrics, no phone-home); `--verbose` prints the resolved config with every secret `[REDACTED]` (04.2.1) | stderr redaction test |
| Failure path | every failure exits 3 with `evidgate: error <code>` on stderr: a file over the cap exits before any request, `manifest_invalid` details and `idempotency_conflict` are passed through with the server's `error.code` and `request_id`, and a 401 purges the cached CI token (hand-over from 04.2.1-T1); codes in `contracts/cli.md` §5 | AC1–AC5 tests, boundary test |
