## 1. Goal and non-goals

**Goal.** `evidgate` gains the two commands that open a run: `evidgate manifests upload` (upload + verify a manifest, print `manifest_hash`) and `evidgate runs create` (create a run with a client-supplied `Idempotency-Key`, `--json` output, release/ci-ref flags). Both are thin, deterministic clients over the generated SDK.

**Non-goals.** Manifest verification and `execution_key` derivation (server, 05.1.1-T4), run-create orchestration and slot registration (05.2.1-T1), event sending (04.2.3), artifact upload (04.2.4), `evidgate gate` (07.6.1).

## 2. User stories and acceptance criteria

- As a CI pipeline, I upload the manifest once and create the run idempotently, so re-running the workflow step after a network blip returns the same run instead of a duplicate.
- As a developer, `--json` gives me `run_id` and `manifest_hash` I can feed into later steps.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `evidgate manifests upload --file m.json` POSTs to `/v1/projects/{p}/manifests` and prints `manifest_id` and `manifest_hash`; a manifest that fails server verification exits 3 with `error.code` |
| AC2 | `evidgate runs create --manifest-id <uuid> --manifest-hash h [--idempotency-key k]` POSTs `/v1/projects/{p}/runs` with the `Idempotency-Key` header and prints `run_id` (amended 2026-10-14 (D-S47-Q1, coordinator): `--manifest-id` is required in addition to `--manifest-hash`, because the merged `CreateRunRequest` resolves the manifest by `manifest_id` — `contracts/openapi.yaml` `createRun`, `additionalProperties: false`) |
| AC3 | Repeating `runs create` with the same key and same payload returns the same `run_id` (server replay); the same key with a different payload exits 3 on 409 `idempotency_conflict` (T11) |
| AC4 | When `--idempotency-key` is omitted, the CLI derives a stable key ≤ 128 chars, so an accidental step-retry stays idempotent: `sha256` (lowercase hex) of the UTF-8 JSON array `["evidgate.run-key.v1", manifest_hash, manifest_id, release ?? null, ci_ref ?? null]`, fixed field order and JSON `null` for an absent optional (amended 2026-10-14 (D-S47-Q1, coordinator): a JSON array is unambiguous — no separator can collide — and every value sent in the body feeds the key, replacing `sha256(manifest_hash + policy + suite + env + ci_ref)`) |
| AC5 | `--manifest-id`, `--manifest-hash`, `--release` (release binding at create, T15) and `--ci-ref` flags map to the documented request fields (`--manifest-hash` and `--manifest-id` are never a substitute for each other; the hash is never sent); `--json` prints `{run_id, manifest_hash, state}` and nothing else on stdout (amended 2026-10-14 (D-S47-Q1, coordinator): `--policy`/`--suite`/`--env` are dropped — `CreateRunRequest` has no such member, the server pins suite/environment from the manifest (05.2.1 plan line 11) and policy from the project's active revision (07.1.1-T4, 05.2.1 plan line 193)) |

## 3. Contracts touched

- 00 §9.3 `POST /v1/projects/{p}/manifests` and `POST /v1/projects/{p}/runs` — consumed as specified; no shape change.
- `contracts/cli.md` — adds the two commands, their flags, the derived-key rule (AC4) and `--json` output shape.

## 4. Data model and migrations

None (no database objects — customer-side CLI). Manifest files are read-only inputs; no local persistence beyond the 04.2.1 token cache.

## 5. API shapes (commands, queries, endpoints)

| Command | Endpoint | Behaviour |
|---|---|---|
| `evidgate manifests upload --file <path> [--json]` | `POST /v1/projects/{p}/manifests` (`run:create`) | streams the file, prints `manifest_id`, `manifest_hash`; 422 `manifest_invalid` → exit 3 with `error.details` verbatim |
| `evidgate runs create --manifest-id <uuid> --manifest-hash <h> [--release r] [--ci-ref ref] [--idempotency-key k] [--json]` | `POST /v1/projects/{p}/runs` (`run:create`) | body `{manifest_id, release?, ref?}` and the `Idempotency-Key` header (derived per AC4 when the flag is omitted); prints `run_id`, `manifest_hash` and `state`; 409 `idempotency_conflict` → exit 3 echoing `error.code`; 202-style async fields absent — run create is synchronous per 00 §9.3 (amended 2026-10-14 (D-S47-Q1, coordinator): `--policy`/`--suite`/`--env` dropped and no `manifest_hash` request member — the merged `CreateRunRequest` has `manifest_id` plus optional `release`/`components`/`ref`/`purpose`/`replay_grant_id` only, `additionalProperties: false`) |

Both commands reuse 04.2.1's `resolveConfig()`, token provider and exit codes; HTTP goes through `packages/sdk` (no hand-written DTOs, W5 analogue for the CLI).

## 6. States and transitions

None locally — the CLI is stateless between invocations. Server-side it triggers: manifest `verified` (05.1.1), run `created` (and `created → queued` when 05 commits the producer slots, T13). The CLI observes only the returned `state`.

## 7. Jobs and integrations

- Consumes `POST /v1/projects/{p}/manifests` (05.1.1-T4's verification result is what prints `manifest_hash`) and `POST /v1/projects/{p}/runs` (05.2.1-T1 — whose committed `producer_slot` rows are later bound by 04.1.2-T5 when events arrive).
- `--release` feeds the run↔release binding at create (T15); a missing/ambiguous release name surfaces the server's 422.
- No background jobs; `runs create` is safe to retry only with the same `Idempotency-Key` — AC4 makes that automatic.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §9.1 idempotency | header sent on every create; derived key is deterministic per identical intent | AC3, AC4 tests |

| Retention/PDPL | CLI stores nothing; manifest may name suites/envs but carries no credentials | stated |

**T3.1 mapping design (decided 2026-11-20, coordinator, option B)**

- **Finding (existing contract).** No existing suite-revision member read is reachable by `ci_producer`: `GET /v1/suite-revisions/{r}` requires `suite:read` (`contracts/openapi.yaml:5655-5663`), while the service role has only `artifact:write`, `decision:read`, `event:write`, `run:create` (`contracts/permissions.json:169-174`). Its member DTO exposes `case_revision_id` and `variant_hash`, but no `case_id` (`contracts/openapi.yaml:12129-12138`), so that response cannot supply the proposed annotation match key.
- **Route proposal — DRAFT, not in contracts/openapi.yaml.** Add `GET /v1/suite-revisions/{r}/execution-plan`, proposed operationId `getSuiteRevisionExecutionPlan`, returning exactly `{suite_revision_id, members: [{case_id, variant_hash, case_revision_id}], next_cursor}`; no `params`, `ordinal`, `required`, edges or names. It serves both `draft` and `published` revisions: a revision starts `draft` and becomes `published` only when a run references it (`plans/features/03-catalog-authoring/03.2.1-versioned-suites.md:117`), so a published-only read would be unusable for manifest generation. This is a proposal, not a property of the existing read (`contracts/openapi.yaml:5655-5683`).
- **Pagination proposal — DRAFT.** Use an opaque, server-authenticated cursor (HMAC or equivalent) bound to `(suite revision id, token project)` and keyset-ordered on `(ordinal, id)`; `next_cursor: null` terminates the walk. Pages are a snapshot for mapping only: the server's verification at `manifests upload` stays the authority on what a manifest may reference. A route-specific `limit` defaults to 200 and is at most 500, not the shared `Limit` (maximum 200, `contracts/openapi.yaml:9002-9010`). A cursor this endpoint did not issue, including one from another revision or project, is 422 `request_invalid`; an out-of-range `limit` is 422 and a non-canonical limit or undecodable query is 400, following the existing cursor convention (`contracts/openapi.yaml:1584-1591`). The CLI requests `limit=500` and caps the walk at 20 pages / 10000 members, the write-side per-revision member cap (`contracts/openapi.yaml:12078-12081`); refuse an incomplete walk, repeated cursor, oversized page or exceeded cap with `manifest_plan_limit_exceeded`; do not map a partial plan.
- **Authorization/error proposal — DRAFT.** Introduce narrow permission `suite:plan_read`; add it to `ci_producer` ONLY, in addition to its existing four permissions, never grant that role `suite:read` (`contracts/permissions.json:169-174`). The permission check is token-only and runs before lookup, so 403 depends only on the token, never the revision id. The project gate is part of the revision lookup: a revision whose project differs from the token's is 404 `not_found` with the same body as an unknown id; there is no per-member filtering. Propose 401, 403, 404 (unknown or out-of-project revision; never a 403 existence leak), 422 (foreign cursor or out-of-range limit), 429 and 503, following the existing read's status vocabulary (`contracts/openapi.yaml:5674-5683`). The order is fixed: 401, then token/permission 403, then limit and query validation, then the revision+project gate (indistinguishable 404 for an unknown and a foreign-project revision), then cursor binding (422); the lookup runs under the token's tenant scope — transaction-scoped `set_config('evidgate.org_id', …, true)` with RLS (`src/BuildingBlocks/Persistence/Tenancy/TenantScope.cs:108-112`) — and the token's project, never a project from the request. T3.1b updates the `ci_producer` description (`contracts/permissions.json:172-173`) and records that no admin or human role receives `suite:plan_read` in this proposal.
- **Accepted risk — DRAFT.** The route exposes `draft` revisions to `ci_producer`, because a manifest is built before the first run that would publish the revision. The exposure is the `case_id`/`variant_hash`/`case_revision_id` structure of one project's suite, not evidence or decisions; an owner may restrict draft reads later without changing the member shape.
- **00 §15 change-log row text — DRAFT inside this plan only:** `2026-11-20 | Proposed execution-plan read for manifest generation: GET /v1/suite-revisions/{r}/execution-plan (getSuiteRevisionExecutionPlan), project-scoped case_id/variant_hash/case_revision_id members, cursor pages <=500; new suite:plan_read for ci_producer only, no suite:read grant; CLI cap 20 pages / 10000 members and named refusal | Pending contract/server lane after S461; not adopted in 00 or OpenAPI`. Rationale: the permission and DTO gaps above (`contracts/permissions.json:169-174`; `contracts/openapi.yaml:12129-12138`). Do not edit 00 in this lane.
- **Identity decision.** Read `evidgate.id` annotations exactly as the adapter: accept canonical case-id descriptions, lowercase them, ignore invalid descriptions, count distinct valid ids; zero means unmapped, more than one means ambiguous (`packages/adapter-playwright/src/identity.ts:313-340`). Obtain the `sha256:<hex>` variant hash from project `metadata.evidgate.params` (default `{}`) through an injected hasher port whose normalization/hash semantics match `normalizeVariant` (`packages/adapter-playwright/src/variant.ts:277-297,310-317`); do not import the adapter. Match `(case_id, variant_hash)` to `case_revision_id`; two members with the same key are ambiguous, even if their revision ids agree.
