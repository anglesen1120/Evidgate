## 1. Goal and non-goals

**Goal.** `evidgate` gains the two commands that open a run: `evidgate manifests upload` (upload + verify a manifest, print `manifest_hash`) and `evidgate runs create` (create a run with a client-supplied `Idempotency-Key`, `--json` output, policy/suite/env/release flags). Both are thin, deterministic clients over the generated SDK.

**Non-goals.** Manifest verification and `execution_key` derivation (server, 05.1.1-T4), run-create orchestration and slot registration (05.2.1-T1), event sending (04.2.3), artifact upload (04.2.4), `evidgate gate` (07.6.1).

## 2. User stories and acceptance criteria

- As a CI pipeline, I upload the manifest once and create the run idempotently, so re-running the workflow step after a network blip returns the same run instead of a duplicate.
- As a developer, `--json` gives me `run_id` and `manifest_hash` I can feed into later steps.

| # | Acceptance criterion (testable) |
|---|---|
| AC1 | `evidgate manifests upload --file m.json` POSTs to `/v1/projects/{p}/manifests` and prints `manifest_id` and `manifest_hash`; a manifest that fails server verification exits 3 with `error.code` |
| AC2 | `evidgate runs create --manifest-hash h --idempotency-key k` POSTs `/v1/projects/{p}/runs` with the `Idempotency-Key` header and prints `run_id` |
| AC3 | Repeating `runs create` with the same key and same payload returns the same `run_id` (server replay); the same key with a different payload exits 3 on 409 `idempotency_conflict` (T11) |
| AC4 | When `--idempotency-key` is omitted, the CLI derives a stable key `sha256(manifest_hash + policy + suite + env + ci_ref)` ≤ 128 chars, so an accidental step-retry stays idempotent |
| AC5 | `--policy`, `--suite`, `--env`, `--release` (release binding at create, T15) and `--ci-ref` flags map to the documented request fields; `--json` prints `{run_id, manifest_hash, state}` and nothing else on stdout |

## 3. Contracts touched

- 00 §9.3 `POST /v1/projects/{p}/manifests` and `POST /v1/projects/{p}/runs` — consumed as specified; no shape change.
- `contracts/cli.md` — adds the two commands, their flags, the derived-key rule (AC4) and `--json` output shape.
- Idempotency (T11): the CLI supplies the key; `idempotency_record` arbitration stays server-side. No permanent unique on business tables is implied by the client.

## 4. Data model and migrations

None (no database objects — customer-side CLI). Manifest files are read-only inputs; no local persistence beyond the 04.2.1 token cache.

## 5. API shapes (commands, queries, endpoints)

| Command | Endpoint | Behaviour |
|---|---|---|
| `evidgate manifests upload --file <path> [--json]` | `POST /v1/projects/{p}/manifests` (`run:create`) | streams the file, prints `manifest_id`, `manifest_hash`; 422 `manifest_invalid` → exit 3 with `error.details` verbatim |
| `evidgate runs create --manifest-hash <h> [--policy p] [--suite s] [--env e] [--release r] [--ci-ref ref] [--idempotency-key k] [--json]` | `POST /v1/projects/{p}/runs` (`run:create`) | sends `Idempotency-Key` (derived per AC4 when omitted); prints `run_id`; 409 → exit 3 echoing `error.code`; 202-style async fields absent — run create is synchronous per 00 §9.3 |

Both commands reuse 04.2.1's `resolveConfig()`, token provider and exit codes; HTTP goes through `packages/sdk` (no hand-written DTOs, W5 analogue for the CLI).

## 6. States and transitions

None locally — the CLI is stateless between invocations. Server-side it triggers: manifest `verified` (05.1.1), run `created` (and `created → queued` when 05 commits the producer slots, T13). The CLI observes only the returned `state`.

## 7. Jobs and integrations

- Consumes `POST /v1/projects/{p}/manifests` (05.1.1-T4's verification result is what prints `manifest_hash`) and `POST /v1/projects/{p}/runs` (05.2.1-T1 — whose committed `producer_slot` rows are later bound by 04.1.2-T5 when events arrive).
- `--release` feeds the run↔release binding at create (T15); a missing/ambiguous release name surfaces the server's 422.
- No background jobs; `runs create` is safe to retry only with the same `Idempotency-Key` — AC4 makes that automatic.

## 8. Security, privacy and performance

| Rule | How this story meets it | Proven by |
|---|---|---|
| 00 §9.1 idempotency | header sent on every create; derived key is deterministic per identical intent | AC3, AC4 tests |
| Token scope | `ci_producer` project scope matches `--project`/`EVIDGATE_PROJECT`; mismatch → server 403 → exit 3 | integration test |
| S3 analogue | manifest content is user data — echoed only under `--verbose` to stdout files the user owns; secrets in manifests are rejected server-side (05) and never logged by the CLI | stderr redaction test |
| Input limits | manifest file size capped at the server's documented limit (1 MiB); larger file exits 3 locally before upload | boundary test |
| NFR-04-2 | Node 22+ cross-platform paths only | Vitest path tests |
| Retention/PDPL | CLI stores nothing; manifest may name suites/envs but carries no credentials | stated |
